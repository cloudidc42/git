## Step 181: ทำไม README สำคัญ — มันคือ "หน้าตา" แรกของโปรเจกต์

เมื่อมีคนเปิด repository ของคุณบน GitHub เป็นครั้งแรก ไม่ว่าจะเป็นเพื่อนร่วมทีม ผู้ว่าจ้างที่กำลังพิจารณา portfolio ของคุณ หรือคนแปลกหน้าที่เจอโปรเจกต์คุณผ่านการค้นหา **สิ่งแรกที่เขาเห็นคือไฟล์ `README.md`** ที่ GitHub render เป็น HTML สวยงามและแสดงไว้ใต้รายการไฟล์ทันที โดยที่เขาไม่ต้องคลิกอะไรเพิ่มเลย

### README คือ "ประตูบ้าน" ไม่ใช่ "ห้องเก็บของ"

ลองนึกภาพว่า repository ของคุณคือบ้านหลังหนึ่ง ไฟล์ซอร์สโค้ดทั้งหมดคือเฟอร์นิเจอร์และข้าวของภายในบ้าน ส่วน README.md ก็คือ **ประตูหน้าบ้านพร้อมป้ายทางเข้า** — ถ้าประตูดูรกและไม่มีป้ายบอกทางเลยว่าห้องน้ำอยู่ไหน ห้องนอนอยู่ไหน แขกที่มาเยี่ยมก็จะงงและอาจจะเดินออกไปเลยโดยไม่เข้าไปสำรวจข้างในต่อ

### สถิติและพฤติกรรมจริงที่ควรรู้

ในโลกของ Open Source และการสมัครงานสาย Developer มีข้อเท็จจริงที่สำคัญมาก:

1. **ผู้ประเมิน (recruiter/hiring manager) ส่วนใหญ่ใช้เวลาดู repository หนึ่งอันเพียง 10–30 วินาที** ก่อนตัดสินใจว่าจะดูต่อหรือไม่ — README ที่ดีคือสิ่งเดียวที่จะทำให้เขา "อยู่ต่อ"
2. **นักพัฒนาที่เจอโปรเจกต์ Open Source ใหม่ ๆ จะตัดสินใจว่าจะใช้ library นั้นหรือไม่จาก README เป็นหลัก** ไม่ใช่จากการไปไล่อ่านซอร์สโค้ดทีละไฟล์
3. **README ที่ไม่มีเลย หรือมีแค่บรรทัดเดียวว่า `# my-project`** คือสัญญาณเชิงลบที่บอกว่าโปรเจกต์นี้อาจถูกทิ้งร้าง ไม่ได้รับการดูแล หรือผู้เขียนไม่ใส่ใจรายละเอียด

### README ที่ดีทำหน้าที่อะไรบ้าง

README.md ที่เขียนดีต้องตอบคำถามพื้นฐานเหล่านี้ได้ภายในไม่กี่วินาทีแรกที่คนเปิดมาอ่าน:

| คำถามในใจผู้อ่าน | สิ่งที่ README ต้องตอบ |
|---|---|
| นี่คือโปรเจกต์อะไร | ชื่อ + คำอธิบายสั้น ๆ (1–2 ประโยค) |
| มันแก้ปัญหาอะไร / ใช้ทำอะไร | ส่วน Description ที่อธิบายจุดประสงค์ |
| ฉันจะติดตั้งมันอย่างไร | ส่วน Installation พร้อมคำสั่งที่ copy-paste ได้ทันที |
| ฉันจะใช้งานมันอย่างไร | ส่วน Usage พร้อมตัวอย่างโค้ดจริง |
| โปรเจกต์นี้ยังมีคนดูแลอยู่ไหม | Badge สถานะ build, เวอร์ชันล่าสุด, วันที่ commit ล่าสุด |
| ฉันมีส่วนร่วม (contribute) ได้อย่างไร | ส่วน Contributing พร้อมลิงก์ไปยังแนวทาง |
| ใช้ภายใต้เงื่อนไขอะไร | ส่วน License |
| ติดต่อผู้เขียนได้อย่างไร | ส่วน Contact / Author |

### ตัวอย่างเปรียบเทียบ: README แย่ vs README ดี

**README แย่ (สิ่งที่ไม่ควรทำ):**

```markdown
# project

my project
```

README แบบนี้ไม่บอกอะไรเลยนอกจากชื่อโปรเจกต์ ผู้อ่านจะต้องเปิดไล่อ่านโค้ดทุกไฟล์เองเพื่อเข้าใจว่ามันคืออะไร ซึ่งแทบไม่มีใครทำจริง ๆ

**README ที่ดีขึ้นมาก (แม้จะยังสั้น):**

```markdown
# Todo CLI

โปรแกรมจัดการ Todo List แบบ Command Line เขียนด้วย Node.js
เก็บข้อมูลลงไฟล์ JSON ในเครื่อง ไม่ต้องพึ่งฐานข้อมูลภายนอก

## ติดตั้ง

npm install -g todo-cli

## ใช้งาน

todo add "ซื้อของเข้าบ้าน"
todo list
todo done 1
```

แค่เพิ่มคำอธิบายสั้น ๆ กับตัวอย่างคำสั่งที่ใช้งานได้จริง ก็ทำให้ผู้อ่านเข้าใจภายใน 10 วินาทีว่าโปรเจกต์นี้คืออะไรและจะเริ่มใช้อย่างไร

### README ไม่ใช่แค่ "เอกสารประกอบ" แต่คือ "การตลาดของโปรเจกต์"

หลายคนมองว่า README เป็นแค่ "งานเอกสาร" ที่ทำทีหลังสุดหรือข้ามไปเลย แต่ในความเป็นจริง README คือเครื่องมือการตลาดที่สำคัญที่สุดของโปรเจกต์ Open Source เพราะมันคือสิ่งที่ตัดสินว่า:

- โปรเจกต์จะได้ **star** จากคนอื่นหรือไม่
- โปรเจกต์จะมีคน **contribute** เข้ามาช่วยหรือไม่
- โปรเจกต์จะถูกเลือกใช้เป็น dependency ใน production หรือไม่
- คุณในฐานะผู้สมัครงานจะถูกมองว่าเป็นคนที่ **สื่อสารเก่งและใส่ใจรายละเอียด** หรือไม่

ตลอด Part นี้เราจะเรียนรู้ Markdown ตั้งแต่พื้นฐานจนถึงเทคนิคขั้นสูงเฉพาะของ GitHub และปิดท้ายด้วยการลงมือเขียน README.md ฉบับมืออาชีพจริง ๆ ให้กับโปรเจกต์ portfolio ที่เราสร้างไว้ใน Part 15

## Step 182: Markdown syntax พื้นฐานที่ต้องรู้

**Markdown** คือภาษามาร์กอัปน้ำหนักเบา (lightweight markup language) ที่ออกแบบมาให้ **อ่านง่ายแม้จะยังไม่ถูก render** และแปลงเป็น HTML ได้ง่าย ถูกคิดค้นโดย John Gruber ในปี 2004 และปัจจุบันกลายเป็นมาตรฐานที่แทบทุกแพลตฟอร์มด้านซอฟต์แวร์ใช้ ไม่ว่าจะเป็น GitHub, GitLab, Slack, Discord, หรือแม้แต่ Notion

ไฟล์ Markdown จะใช้นามสกุล `.md` หรือ `.markdown` และเมื่อ GitHub เจอไฟล์ชื่อ `README.md` ในโฟลเดอร์ใด มันจะ **render เป็น HTML อัตโนมัติ** และแสดงไว้ใต้รายชื่อไฟล์ในหน้า repository ทันที

### 182.1 Heading (หัวข้อ)

ใช้เครื่องหมาย `#` นำหน้า จำนวน `#` บอกระดับของหัวข้อ (1–6 ระดับ):

**Source:**

```markdown
# หัวข้อระดับ 1 (H1)
## หัวข้อระดับ 2 (H2)
### หัวข้อระดับ 3 (H3)
#### หัวข้อระดับ 4 (H4)
##### หัวข้อระดับ 5 (H5)
###### หัวข้อระดับ 6 (H6)
```

**ผลลัพธ์ที่ render ออกมา:** จะได้ตัวอักษรขนาดใหญ่ลดหลั่นกันลงมาตามระดับ โดย H1 ใหญ่ที่สุดและหนาที่สุด ไปจนถึง H6 ที่เล็กที่สุด — เหมือนโครงสร้างหัวข้อในเอกสาร Word

> **ข้อควรจำ:** ต้องเว้นวรรค 1 ครั้งระหว่าง `#` กับข้อความเสมอ (`# หัวข้อ` ถูกต้อง, `#หัวข้อ` ไม่ถือเป็น heading) และในหนึ่งไฟล์ควรมี H1 (`#`) เพียงอันเดียวเท่านั้น เพราะมันคือชื่อเรื่องหลักของเอกสาร

### 182.2 การเน้นข้อความ (Emphasis): Bold และ Italic

**Source:**

```markdown
ข้อความปกติ
**ข้อความตัวหนา (bold)**
*ข้อความตัวเอียง (italic)*
***ข้อความตัวหนาและเอียงพร้อมกัน***
~~ข้อความขีดฆ่า (strikethrough)~~
```

**ผลลัพธ์:** ข้อความปกติ, **ข้อความตัวหนา (bold)**, ข้อความตัวเอียงจะแสดงเป็นตัวเอน, ข้อความหนา+เอียงจะรวมทั้งสองแบบ และข้อความขีดฆ่าจะมีเส้นพาดกลาง

สามารถใช้ `_ขีดล่าง_` แทน `*ดอกจัน*` ได้เช่นกันสำหรับ italic และ `__ขีดล่างคู่__` แทน `**ดอกจันคู่**` สำหรับ bold — ทั้งสองแบบให้ผลลัพธ์เหมือนกันทุกประการ แต่ควรเลือกใช้แบบใดแบบหนึ่งให้สม่ำเสมอตลอดทั้งเอกสารเพื่อความเป็นระเบียบ

### 182.3 List (รายการ)

**Unordered list (รายการไม่มีลำดับ)** ใช้ `-`, `*`, หรือ `+` นำหน้า (เลือกใช้แบบใดแบบหนึ่งให้สม่ำเสมอ):

**Source:**

```markdown
- กาแฟ
- ชา
- น้ำเปล่า
  - น้ำเปล่าธรรมดา
  - น้ำแร่
```

**ผลลัพธ์:** จะได้ bullet point (●) เรียงกัน โดยรายการที่ย่อหน้าเข้าไป (indent ด้วย 2 หรือ 4 spaces) จะกลายเป็น **รายการซ้อน (nested list)** แสดงด้วยสัญลักษณ์ที่ต่างระดับกัน

**Ordered list (รายการมีลำดับ)** ใช้ตัวเลขตามด้วยจุด:

**Source:**

```markdown
1. เปิดเครื่องคอมพิวเตอร์
2. เปิด Terminal
3. พิมพ์คำสั่ง `git status`
4. อ่านผลลัพธ์
```

**ผลลัพธ์:** จะได้รายการเรียงลำดับ 1. 2. 3. 4. โดยอัตโนมัติ (ข้อดีคือแม้คุณจะพิมพ์เลข `1.` ซ้ำทุกบรรทัด Markdown ก็จะเรียงเลขให้ถูกต้องเองเมื่อ render — มีประโยชน์มากตอนแทรกรายการใหม่กลางลิสต์โดยไม่ต้องแก้เลขทุกบรรทัด)

### 182.4 Link (ลิงก์)

**Source:**

```markdown
[ข้อความที่แสดง](https://www.example.com)
[ไปที่ GitHub ของฉัน](https://github.com/somchai-jaidee)
[ลิงก์พร้อม title ที่ขึ้นเมื่อ hover](https://www.example.com "นี่คือ tooltip")
```

**ผลลัพธ์:** จะได้ข้อความที่มีสีน้ำเงินและขีดเส้นใต้ (ตามธีมของ GitHub) คลิกแล้วเปิดไปยัง URL ที่กำหนด

**Link แบบอ้างอิง (reference-style link)** มีประโยชน์เมื่อใช้ลิงก์เดียวกันซ้ำหลายที่ในเอกสารยาว ๆ:

```markdown
อ่านเอกสารเพิ่มเติมได้ที่ [เว็บไซต์ทางการ][official-site]

[official-site]: https://www.example.com
```

รูปแบบนี้ทำให้ URL จริงถูกเก็บไว้ท้ายเอกสารหรือท้ายย่อหน้า ตัวเนื้อหาจึงอ่านง่ายขึ้นเพราะไม่มี URL ยาว ๆ แทรกกลางประโยค

### 182.5 Image (รูปภาพ)

Syntax เหมือน Link เป๊ะ แต่เพิ่มเครื่องหมาย `!` นำหน้า:

**Source:**

```markdown
![คำอธิบายรูปภาพ (alt text)](https://example.com/logo.png)
![โลโก้โปรเจกต์](./assets/logo.png "โลโก้ Portfolio ของสมชาย")
```

**ผลลัพธ์:** รูปภาพจะถูกแสดงตรงตำแหน่งนั้นเลย ไม่ใช่แค่ลิงก์ให้คลิก — ส่วน `คำอธิบายรูปภาพ (alt text)` จะถูกใช้เป็นข้อความสำรองในกรณีที่รูปโหลดไม่ขึ้น และยังสำคัญมากสำหรับ **accessibility** (โปรแกรมอ่านหน้าจอสำหรับผู้พิการทางสายตาจะอ่านข้อความนี้ให้ฟัง)

### 182.6 Blockquote (ข้อความอ้างอิง)

**Source:**

```markdown
> นี่คือข้อความอ้างอิง (quote) ที่มักใช้เน้นคำพูดสำคัญ
> หรือคำเตือนที่อยากให้ผู้อ่านสังเกตเป็นพิเศษ
>
> สามารถขึ้นย่อหน้าใหม่ภายใน blockquote ได้เช่นกัน
```

**ผลลัพธ์:** จะได้กล่องข้อความที่มีเส้นแนวตั้งสีเทาอยู่ทางซ้ายมือ และมักจะมีสีข้อความอ่อนกว่าปกติเล็กน้อย — GitHub นิยมใช้รูปแบบนี้สำหรับคำเตือนหรือหมายเหตุสำคัญ

### 182.7 เส้นคั่น (Horizontal Rule)

**Source:**

```markdown
เนื้อหาส่วนที่ 1

---

เนื้อหาส่วนที่ 2
```

**ผลลัพธ์:** จะได้เส้นคั่นแนวนอนพาดเต็มความกว้าง ใช้แบ่งเนื้อหาเป็นส่วน ๆ ให้อ่านง่ายขึ้น (สามารถใช้ `***` หรือ `___` แทน `---` ได้ผลลัพธ์เหมือนกัน)

### 182.8 Inline code (โค้ดสั้น ๆ ในบรรทัด)

ใช้ backtick เดี่ยว (`` ` ``) ครอบข้อความ:

**Source:**

```markdown
ใช้คำสั่ง `git status` เพื่อตรวจสอบสถานะของ repository
ตัวแปร `count` เริ่มต้นที่ `0`
```

**ผลลัพธ์:** ข้อความระหว่าง backtick จะแสดงด้วยฟอนต์ monospace (เหมือนฟอนต์ในโปรแกรมเขียนโค้ด) พร้อมพื้นหลังสีเทาอ่อน ทำให้แยกออกจากข้อความปกติได้ชัดเจนทันที เหมาะมากสำหรับการอ้างอิงชื่อไฟล์ ชื่อตัวแปร หรือคำสั่งสั้น ๆ

### สรุปตารางเปรียบเทียบ Syntax พื้นฐาน

| ต้องการ | Syntax | ตัวอย่าง |
|---|---|---|
| Heading | `#` ถึง `######` | `## หัวข้อ` |
| Bold | `**text**` | `**สำคัญ**` |
| Italic | `*text*` | `*เน้น*` |
| Strikethrough | `~~text~~` | `~~ผิด~~` |
| Unordered list | `- item` | `- ข้อ 1` |
| Ordered list | `1. item` | `1. ข้อ 1` |
| Link | `[text](url)` | `[Git](https://git-scm.com)` |
| Image | `![alt](url)` | `![โลโก้](logo.png)` |
| Blockquote | `> text` | `> คำเตือน` |
| Inline code | `` `code` `` | `` `npm install` `` |
| Horizontal rule | `---` | `---` |

Syntax เหล่านี้คือพื้นฐานที่ใช้ได้ทุกที่ที่รองรับ Markdown ไม่ว่าจะเป็น README, เอกสาร, หรือแม้แต่ comment ใน issue — ใน Step ถัดไปเราจะไปดู syntax ขั้นสูงที่ GitHub เพิ่มเข้ามาเป็นพิเศษ

## Step 183: Markdown ขั้นสูงสำหรับ GitHub (ตาราง, task list, code block พร้อม syntax highlighting)

Markdown มาตรฐานดั้งเดิมไม่มีฟีเจอร์บางอย่างที่จำเป็นมากสำหรับงานพัฒนาซอฟต์แวร์ **GitHub Flavored Markdown (GFM)** จึงเพิ่มส่วนขยายเหล่านี้เข้ามา ซึ่งทำงานได้เฉพาะบนแพลตฟอร์มที่รองรับ GFM เท่านั้น (GitHub, GitLab ก็รองรับส่วนใหญ่ของ GFM เช่นกัน)

### 183.1 ตาราง (Tables)

**Source:**

```markdown
| คำสั่ง | ความหมาย |
|---|---|
| `git init` | เริ่มต้น repository ใหม่ |
| `git add` | เพิ่มไฟล์เข้า staging area |
| `git commit` | บันทึก snapshot |
```

**ผลลัพธ์:** จะได้ตารางที่มีเส้นขอบชัดเจน หัวตาราง (`คำสั่ง`, `ความหมาย`) จะถูกทำเป็นตัวหนาโดยอัตโนมัติ

**การจัดตำแหน่งข้อความในตาราง (Alignment):** ใช้เครื่องหมาย `:` ในแถวเส้นคั่น

**Source:**

```markdown
| ซ้าย (default) | กึ่งกลาง | ขวา |
|:---|:---:|---:|
| ข้อมูล A | ข้อมูล B | ข้อมูล C |
| 100 | 200 | 300 |
```

- `:---` = ชิดซ้าย (ค่าเริ่มต้นถ้าไม่ใส่ `:` เลย)
- `:---:` = กึ่งกลาง
- `---:` = ชิดขวา

> **เทคนิคที่มือใหม่มักไม่รู้:** ไม่จำเป็นต้องจัดให้เส้นแบ่งแนวตั้ง (`|`) ตรงกันเป๊ะในไฟล์ source เลย เพราะ Markdown renderer จะจัดรูปแบบให้เองตอน render ดังนั้นเขียนแบบนี้ก็ได้ผลลัพธ์เหมือนกันทุกประการ:
> ```markdown
> | A | B |
> |-|-|
> | 1 | 2 |
> ```

### 183.2 Task List (Checkbox แบบโต้ตอบได้)

นี่คือฟีเจอร์ที่มีประโยชน์มากที่สุดอย่างหนึ่งของ GFM โดยเฉพาะใน Issue และ PR:

**Source:**

```markdown
## แผนงาน Sprint นี้

- [x] ออกแบบหน้า Login
- [x] เขียน API สำหรับ Authentication
- [ ] เขียน Unit Test ให้ครบ
- [ ] Deploy ขึ้น Staging
```

**ผลลัพธ์:** จะได้ checkbox จริง ๆ ที่แสดงเป็นสี่เหลี่ยม `☑` (ติ๊กแล้ว สำหรับ `[x]`) และ `☐` (ยังไม่ติ๊ก สำหรับ `[ ]`) และที่พิเศษกว่านั้นคือ **ถ้าใช้ใน Issue หรือ Pull Request จริง ผู้ใช้สามารถคลิกติ๊ก checkbox บนหน้าเว็บได้เลยโดยไม่ต้องแก้ไข Markdown source เอง** — GitHub จะแก้ไข commit/comment นั้นให้อัตโนมัติ และยังนำจำนวน checkbox ที่ติ๊กแล้วไปแสดงเป็น progress bar (เช่น "2 of 4 tasks") ในหน้ารายการ Issue ด้วย

ข้อควรระวัง: ต้องมีเว้นวรรคระหว่าง `[x]` หรือ `[ ]` กับข้อความเสมอ และต้องมีเว้นวรรคภายในวงเล็บสำหรับ checkbox ที่ยังไม่ติ๊ก (`[ ]` ไม่ใช่ `[]`)

### 183.3 Code Block พร้อม Syntax Highlighting

การใช้ backtick 3 ตัว (` ``` `) ครอบทั้งบล็อกจะสร้าง code block แบบหลายบรรทัด และถ้าใส่ชื่อภาษาโปรแกรมต่อท้าย backtick แรก จะได้ **syntax highlighting** (สีของ keyword, string, comment ต่างกันตามหลักไวยากรณ์ของภาษานั้น) โดยอัตโนมัติ

**Source (ตัวอย่างสำหรับ JavaScript):**

````markdown
```javascript
function greet(name) {
  console.log(`สวัสดี ${name}`);
}

greet("สมชาย");
```
````

**Source (ตัวอย่างสำหรับ Python):**

````markdown
```python
def greet(name):
    print(f"สวัสดี {name}")

greet("สมชาย")
```
````

**Source (ตัวอย่างสำหรับ Bash/Shell):**

````markdown
```bash
git clone https://github.com/somchai-jaidee/portfolio-project.git
cd portfolio-project
npm install
```
````

**Source (ตัวอย่างสำหรับ JSON):**

````markdown
```json
{
  "name": "portfolio-project",
  "version": "1.0.0",
  "license": "MIT"
}
```
````

ภาษาที่นิยมใช้กำกับ ได้แก่ `javascript`, `typescript`, `python`, `bash`/`sh`, `json`, `html`, `css`, `sql`, `yaml`, `go`, `java`, `c`, `cpp`, `diff` — GitHub ใช้ไลบรารีชื่อ Linguist ในการตรวจจับและลงสีตามภาษาที่ระบุ ถ้าไม่ใส่ชื่อภาษาเลย (แค่ ` ``` ` เปล่า ๆ) ก็ยังได้ code block ที่มีพื้นหลังสีเทาและฟอนต์ monospace แต่จะไม่มีสีสันของ syntax

> **หมายเหตุเรื่องการเขียนโค้ดที่มี backtick ซ้อนกัน:** ถ้าคุณต้องการแสดงตัวอย่าง Markdown source ที่มี code block ซ้อนอยู่ข้างในอีกที (เหมือนที่ทำใน Part นี้) ให้ใช้ backtick 4 ตัว (` ```` `) เป็นเส้นขอบชั้นนอก เพื่อไม่ให้ Markdown renderer สับสนว่า backtick 3 ตัวด้านในคือจุดปิดบล็อก

### 183.4 Diff Block (แสดงส่วนที่เพิ่ม/ลบ)

ภาษาพิเศษ `diff` ใช้แสดงการเปรียบเทียบโค้ดก่อน-หลังได้สวยงามมาก มักใช้อธิบายการเปลี่ยนแปลงใน README หรือ CHANGELOG:

**Source:**

````markdown
```diff
- const PORT = 3000;
+ const PORT = process.env.PORT || 3000;
```
````

**ผลลัพธ์:** บรรทัดที่ขึ้นต้นด้วย `-` จะมีพื้นหลังสีแดงอ่อน (แสดงว่าถูกลบ) และบรรทัดที่ขึ้นต้นด้วย `+` จะมีพื้นหลังสีเขียวอ่อน (แสดงว่าถูกเพิ่ม) — เหมือนกับที่เห็นใน `git diff` หรือหน้า "Files changed" ของ Pull Request เป๊ะ

### 183.5 รวมทุกอย่างในตัวอย่างเดียว

**Source:**

````markdown
## Roadmap

| เวอร์ชัน | สถานะ | ฟีเจอร์ |
|---|:---:|---|
| v1.0 | ✅ เสร็จแล้ว | หน้า Home, About, Projects |
| v2.0 | 🚧 กำลังทำ | ระบบ Contact Form |

### สิ่งที่ต้องทำก่อน Release v2.0

- [x] ออกแบบ UI ฟอร์มติดต่อ
- [ ] เขียน Backend รับข้อมูลฟอร์ม
- [ ] ทดสอบการส่งอีเมลจริง

### ตัวอย่างการใช้งาน API

```javascript
fetch("/api/contact", {
  method: "POST",
  body: JSON.stringify({ message: "สวัสดีครับ" })
});
```
````

ตัวอย่างนี้แสดงให้เห็นว่า README ระดับมืออาชีพมักผสมทั้งตาราง, task list, และ code block เข้าด้วยกันในหน้าเดียว เพื่อสื่อสารข้อมูลหลายมิติพร้อมกันได้อย่างมีประสิทธิภาพ

## Step 184: GitHub Flavored Markdown (GFM) พิเศษที่ไม่มีใน Markdown มาตรฐาน

นอกจากตาราง, task list และ code block แล้ว GitHub ยังมีฟีเจอร์ Markdown พิเศษอีกหลายตัวที่ **ทำงานได้เฉพาะบน GitHub เท่านั้น** (ไม่ใช่ Markdown มาตรฐานที่ใช้ได้ทุกที่) ฟีเจอร์เหล่านี้ผูกกับระบบผู้ใช้และฐานข้อมูลของ GitHub โดยตรง

### 184.1 @mentions (การกล่าวถึงผู้ใช้)

**Source:**

```markdown
ขอบคุณ @somchai-jaidee ที่ช่วยรีวิวโค้ดให้ครับ
```

**ผลลัพธ์:** ข้อความ `@somchai-jaidee` จะกลายเป็นลิงก์ไปยังโปรไฟล์ผู้ใช้คนนั้นบน GitHub ทันที และ **ผู้ใช้ที่ถูก mention จะได้รับการแจ้งเตือน (notification)** ว่ามีคนพูดถึงเขา — ฟีเจอร์นี้ทำงานได้เต็มรูปแบบเฉพาะใน Issue, Pull Request, และ Comment เท่านั้น (ถ้าใส่ไว้ใน README.md ธรรมดา มันจะกลายเป็นลิงก์ก็จริง แต่จะไม่ส่ง notification เพราะไม่ใช่ "การกระทำ" ที่เกิดขึ้น ณ ขณะนั้น)

สามารถ mention ทีมทั้งทีมได้เช่นกันถ้าอยู่ในองค์กร (Organization):

```markdown
@my-org/frontend-team ช่วยรีวิว PR นี้หน่อยครับ
```

### 184.2 Issue/PR References (#เลขที่)

**Source:**

```markdown
บั๊กนี้เกี่ยวข้องกับ #42 และถูกแก้ไปแล้วบางส่วนใน #58
Fixes #101
```

**ผลลัพธ์:** `#42`, `#58`, `#101` จะกลายเป็นลิงก์ที่คลิกแล้วเด้งไปยัง Issue หรือ Pull Request หมายเลขนั้นทันที พร้อมแสดง tooltip ตัวอย่างหัวข้อและสถานะ (เปิดอยู่/ปิดแล้ว) เมื่อเอาเมาส์ไปวางไว้

**คำสั่งพิเศษที่ทรงพลังที่สุด:** ถ้าใช้คำว่า `Fixes`, `Closes`, `Resolves` นำหน้าเลข issue **ใน commit message หรือใน description ของ Pull Request** GitHub จะ **ปิด Issue นั้นให้อัตโนมัติทันทีที่ PR ถูก merge**:

```markdown
Fixes #101
Closes #102, #103
Resolves #104
```

นี่คือฟีเจอร์ที่ทีมพัฒนามืออาชีพใช้กันแทบทุกวัน เพราะไม่ต้องมานั่งปิด issue มือทีละอันหลัง merge — เราจะเจาะลึกเรื่องนี้อีกครั้งใน Part ที่สอนเรื่อง Issue โดยเฉพาะ

การอ้างอิงข้ามระหว่าง repository ก็ทำได้เช่นกัน:

```markdown
เกี่ยวข้องกับ owner/other-repo#15
```

### 184.3 Emoji (`:emoji_name:`)

**Source:**

```markdown
เย้! ทดสอบผ่านหมดแล้ว :tada:
โปรเจกต์นี้ยังอยู่ระหว่างพัฒนา :construction:
พบบั๊กด่วนมาก :fire: :warning:
รักการเขียนโค้ด :heart: :computer:
```

**ผลลัพธ์:** ข้อความในรูปแบบ `:ชื่อ:` จะถูกแปลงเป็นอิโมจิจริงทันที เช่น 🎉, 🚧, 🔥, ⚠️, ❤️, 💻ตามลำดับ

GitHub มี emoji ให้เลือกใช้หลายพันตัว รายชื่อทั้งหมดดูได้จาก emoji cheat sheet (พิมพ์ `:` ในกล่องพิมพ์ comment ของ GitHub จะมี autocomplete แสดงรายการให้เลือกทันที) นอกจากนี้ยังสามารถ**วางอิโมจิ Unicode ตรง ๆ** ได้เลยโดยไม่ต้องใช้ syntax `:name:` เช่น พิมพ์ 🚀 ตรง ๆ ก็แสดงผลได้ปกติเช่นกัน

อิโมจิที่ใช้บ่อยในวงการพัฒนาซอฟต์แวร์:

| Syntax | อิโมจิ | ความหมายที่นิยมใช้ |
|---|---|---|
| `:rocket:` | 🚀 | Deploy สำเร็จ / เปิดตัวฟีเจอร์ใหม่ |
| `:bug:` | 🐛 | แจ้งหรือแก้บั๊ก |
| `:sparkles:` | ✨ | เพิ่มฟีเจอร์ใหม่ |
| `:construction:` | 🚧 | กำลังพัฒนา ยังไม่เสร็จ |
| `:white_check_mark:` | ✅ | เสร็จสมบูรณ์แล้ว |
| `:warning:` | ⚠️ | คำเตือนสำคัญ |
| `:memo:` | 📝 | อัปเดตเอกสาร |

### 184.4 Strikethrough (ขีดฆ่า) — ทวนซ้ำในบริบท GFM

แม้จะกล่าวถึงไปแล้วใน Step 182 แต่ต้องเน้นย้ำว่า `~~ข้อความ~~` เป็นส่วนขยายของ GFM ไม่ใช่ Markdown มาตรฐานดั้งเดิม (Markdown ต้นฉบับของ John Gruber ไม่มี syntax นี้) มักใช้ในบริบทของการทำ checklist หรือ changelog เพื่อบอกว่าอะไร "ถูกยกเลิกไปแล้ว" หรือ "ไม่รองรับอีกต่อไป":

```markdown
- ~~รองรับ Node.js 12~~ (หยุดสนับสนุนแล้วตั้งแต่ v3.0)
- รองรับ Node.js 18 ขึ้นไป
```

### 184.5 Auto-linking URL

ถ้าวาง URL เต็มรูปแบบตรง ๆ โดยไม่ใส่ syntax link ใด ๆ เลย GFM จะแปลงเป็นลิงก์ที่คลิกได้ให้อัตโนมัติ:

```markdown
เข้าไปดูเอกสารเพิ่มเติมได้ที่ https://docs.github.com
```

`https://docs.github.com` จะกลายเป็นลิงก์ทันทีโดยไม่ต้องเขียน `[text](url)` เลย — สะดวกมากเวลาแปะลิงก์เร็ว ๆ ในคอมเมนต์

### 184.6 SHA Commit Auto-linking

ถ้าวาง SHA hash ของ commit (อย่างน้อย 7 ตัวอักษร) ลงในข้อความ GitHub จะแปลงให้เป็นลิงก์ไปยัง commit นั้นโดยอัตโนมัติเช่นกัน:

```markdown
บั๊กนี้เริ่มเกิดตั้งแต่ commit a1b2c3d
```

## Step 185: Badges / Shields.io — ป้ายแสดงสถานะโปรเจกต์

**Badge** (หรือ **Shield**) คือรูปภาพเล็ก ๆ รูปทรงแคปซูลที่แสดงข้อมูลสถานะของโปรเจกต์แบบรวดเร็ว เช่น สถานะ build ผ่านหรือไม่, เวอร์ชันล่าสุด, license, จำนวน download — เกือบทุกโปรเจกต์ Open Source ระดับมืออาชีพจะมี badge เรียงกันอยู่ด้านบนสุดของ README ทันทีใต้ชื่อโปรเจกต์

### 185.1 ทำไม Badge ถึงสำคัญ

Badge ทำหน้าที่เป็น **"สรุปภาพรวม" ที่อ่านได้ในเสี้ยววินาที** โดยไม่ต้องอ่านข้อความยาว ๆ เลย ผู้ใช้เห็น badge สีเขียวเขียนว่า "passing" ก็รู้ทันทีว่า build ล่าสุดผ่านการทดสอบ เห็น badge "license: MIT" ก็รู้ทันทีว่านำไปใช้ในเชิงพาณิชย์ได้โดยไม่มีปัญหาทางกฎหมาย

### 185.2 Shields.io — บริการสร้าง Badge ที่นิยมที่สุด

เว็บไซต์ **https://shields.io** เป็นบริการฟรีที่สร้างรูปภาพ badge แบบไดนามิกให้ตาม URL ที่กำหนด รูปแบบ URL พื้นฐานคือ:

```
https://img.shields.io/badge/<label>-<message>-<color>
```

**ตัวอย่างพื้นฐาน:**

```markdown
![version](https://img.shields.io/badge/version-1.0.0-blue)
![license](https://img.shields.io/badge/license-MIT-green)
![status](https://img.shields.io/badge/status-active-brightgreen)
```

**ผลลัพธ์:** จะได้ badge สามอันเรียงกัน แต่ละอันมีสีพื้นหลังตามที่กำหนด (`blue`, `green`, `brightgreen`) พร้อมข้อความสองส่วนคั่นด้วยเส้นแบ่งกลาง (ฝั่งซ้ายคือ label สีเทา ฝั่งขวาคือ message สีตามที่ระบุ)

Shields.io ยังรองรับการดึงข้อมูล **สด ๆ** จาก GitHub API โดยตรง ไม่ต้องอัปเดตเลขเองด้วยมือ:

badge เหล่านี้จะแสดงจำนวน star, fork, issue ที่เปิดอยู่, วันที่ commit ล่าสุด และ license — โดยตัวเลขจะ**อัปเดตอัตโนมัติทุกครั้งที่มีคนเปิดดูหน้า README** เพราะเป็นการเรียก API สดทุกครั้ง ไม่ใช่รูปภาพ static

## Step 186: การใส่ภาพ, GIF, วิดีโอใน README และเทคนิค drag-and-drop upload

รูปภาพและ GIF ที่แสดงตัวอย่างการทำงานจริงของโปรแกรม (screenshot, demo GIF) เป็นสิ่งที่เพิ่มความน่าเชื่อถือให้ README ได้มากที่สุดอย่างหนึ่ง เพราะ **"เห็นภาพจริงย่อมน่าเชื่อกว่าคำบรรยาย 100 บรรทัด"**

### 186.1 การแทรกรูปภาพพื้นฐาน (ทวนจาก Step 182)

```markdown
![หน้าจอหลักของแอป](./screenshots/homepage.png)
```

ควรใช้ **path สัมพัทธ์ (relative path)** แบบนี้เมื่อรูปภาพถูกเก็บไว้ในโฟลเดอร์ของ repository เอง (เช่นโฟลเดอร์ `screenshots/` หรือ `assets/`) เพราะจะทำงานได้ถูกต้องไม่ว่า repository จะถูก clone ไปที่ไหน หรือถูก fork ไปเป็นชื่ออื่น

### 186.2 เทคนิค Drag-and-Drop Upload ไปยัง GitHub CDN

GitHub มีวิธีแทรกรูปภาพที่สะดวกมากโดยไม่ต้องสร้างโฟลเดอร์ `assets/` ในโปรเจกต์เลย นั่นคือการ **ลากไฟล์ (drag-and-drop) วางลงในกล่องข้อความ** ตอนแก้ไข Issue, Pull Request, Comment หรือแม้แต่ตอนแก้ไขไฟล์ `.md` ผ่านหน้าเว็บ GitHub โดยตรง

**ขั้นตอน:**

1. เปิดกล่องแก้ไข (เช่นกล่องเขียน Issue ใหม่ หรือหน้าแก้ไข README.md บนเว็บ GitHub)
2. **ลากไฟล์รูปภาพหรือ GIF จากเครื่องคอมพิวเตอร์วางลงในกล่องข้อความ** (หรือใช้ paste จาก clipboard ก็ได้)
3. GitHub จะอัปโหลดไฟล์นั้นขึ้นไปเก็บไว้บน **GitHub's user-content CDN** (โดเมนที่ขึ้นต้นด้วย `user-images.githubusercontent.com` หรือ `github.com/user-attachments/`) โดยอัตโนมัติ
4. GitHub จะแทรก Markdown syntax ให้เองทันทีในรูปแบบ:

```markdown
![image](https://github.com/user-attachments/assets/xxxxxxxx-xxxx-xxxx-xxxx-xxxxxxxxxxxx)
```

**ข้อดีของวิธีนี้:**

- **ไม่ต้อง commit ไฟล์รูปภาพลงใน repository เลย** ทำให้ repository มีขนาดเล็ก ไม่หนักด้วยไฟล์ binary จำนวนมาก
- ไฟล์ถูกเก็บไว้บน CDN ของ GitHub เอง โหลดเร็วและเสถียร
- ใช้ได้กับทั้งรูปภาพ (PNG, JPG, GIF) และวิดีโอ (MP4, MOV) รวมถึงไฟล์เอกสารบางประเภท

**ข้อควรระวัง:** ไฟล์ที่อัปโหลดด้วยวิธีนี้จะ**ไม่ได้อยู่ภายใต้การควบคุมเวอร์ชันของ Git** เหมือนไฟล์ในโปรเจกต์ ถ้าลบ Issue/PR/Comment ที่ใช้แนบไฟล์นั้น (ในบางกรณี) ลิงก์อาจใช้งานไม่ได้อีกต่อไป จึงเหมาะกับรูปภาพประกอบการอธิบายในบทสนทนามากกว่ารูปภาพหลักที่ต้องคงอยู่ถาวรใน README

### 186.3 การใส่ GIF สาธิตการทำงาน (Demo GIF)

GIF ที่แสดงการใช้งานจริงแบบเคลื่อนไหว (เช่น สาธิตการพิมพ์คำสั่งใน terminal แล้วเห็นผลลัพธ์) เป็นสิ่งที่ทำให้ README ของ CLI tool หรือแอปพลิเคชันดูมืออาชีพขึ้นมาก เครื่องมือยอดนิยมที่ใช้อัดหน้าจอเป็น GIF ได้แก่ **terminalizer**, **asciinema** (สำหรับ terminal), และ **LICEcap**, **Kap**, **ScreenToGif** (สำหรับหน้าจอทั่วไป)

**Source (ใส่ GIF เหมือนใส่รูปภาพทั่วไป):**

```markdown
## Demo

![สาธิตการใช้งาน Todo CLI](./assets/demo.gif)
```

GIF จะเล่นวนซ้ำอัตโนมัติทันทีที่หน้าเว็บโหลดเสร็จ โดยไม่ต้องกดเล่นเอง

### 186.4 การใส่วิดีโอ (Video)

Markdown มาตรฐานไม่มี syntax สำหรับฝังวิดีโอโดยตรง (ต่างจากรูปภาพที่มี `![]()`) แต่ GitHub มีวิธีจัดการเรื่องนี้อยู่ 2 แบบหลัก ๆ:

**แบบที่ 1: อัปโหลดไฟล์วิดีโอผ่าน Drag-and-Drop (แนะนำที่สุด)**

เมื่อลากไฟล์ `.mp4` หรือ `.mov` วางในกล่องแก้ไขของ GitHub (เหมือนวิธีในหัวข้อ 186.2) GitHub จะสร้าง syntax พิเศษให้เองในรูปแบบแท็ก video:

```markdown
https://github.com/user-attachments/assets/xxxxxxxx-video-id-xxxxxxxx
```

เมื่อ render บนหน้าเว็บ GitHub จะกลายเป็น **video player ในตัวที่กดเล่นได้ทันที** พร้อมปุ่มควบคุมเสียงและ progress bar

**แบบที่ 2: ลิงก์ไปยัง YouTube พร้อม thumbnail คลิกได้**

เนื่องจาก Markdown ของ GitHub ไม่รองรับการฝัง iframe ของ YouTube โดยตรง (ด้วยเหตุผลด้านความปลอดภัย) เทคนิคที่นิยมใช้กันคือการทำรูป thumbnail ของวิดีโอให้เป็นลิงก์คลิกได้ ด้วย syntax เดียวกับ badge ที่คลิกได้ในหัวข้อ 185.6:

```markdown
[![ดูวิดีโอสาธิตบน YouTube](https://img.youtube.com/vi/VIDEO_ID/0.jpg)](https://www.youtube.com/watch?v=VIDEO_ID)
```

โดย `https://img.youtube.com/vi/VIDEO_ID/0.jpg` คือ URL มาตรฐานของ YouTube ที่ให้ thumbnail ของวิดีโอทุกคลิปโดยอัตโนมัติ (แค่เปลี่ยน `VIDEO_ID` ให้ตรงกับวิดีโอจริง) เมื่อคลิกที่รูป thumbnail จะพาผู้ใช้ไปเปิดวิดีโอเต็มรูปแบบบน YouTube

### 186.5 คำแนะนำเรื่องขนาดไฟล์และการจัดระเบียบ

- ควรบีบอัดรูปภาพและ GIF ให้มีขนาดไฟล์เล็กที่สุดเท่าที่ยังดูดีอยู่ ก่อน commit เข้า repository (GIF ที่ไม่บีบอัดอาจมีขนาดหลายสิบ MB และทำให้ repository โตเกินจำเป็น)
- ถ้าเลือกเก็บรูปภาพไว้ในโปรเจกต์เอง ควรสร้างโฟลเดอร์เฉพาะ เช่น `assets/`, `screenshots/`, หรือ `docs/images/` เพื่อไม่ให้ปะปนกับซอร์สโค้ด
- สำหรับ GIF ที่ไฟล์ใหญ่มาก อาจพิจารณาใช้ drag-and-drop upload (186.2) แทนการ commit เข้าโปรเจกต์โดยตรง เพื่อไม่ให้ประวัติ Git หนักเกินไป

## Step 187: โครงสร้าง README มาตรฐานที่มืออาชีพใช้

หลังจากรู้ syntax ครบหมดแล้ว คำถามต่อไปคือ **"แล้วควรจัดเรียงเนื้อหาเหล่านี้อย่างไรให้เป็นระบบ"** โครงการ Open Source ระดับโลกส่วนใหญ่ใช้โครงสร้างที่คล้ายกันมาก เพราะมันตอบโจทย์ผู้อ่านได้อย่างมีลำดับขั้นตอนที่เป็นธรรมชาติ

### 187.1 โครงสร้างมาตรฐาน 9 ส่วน

```
1. Title (ชื่อโปรเจกต์)
2. Badges (แถวป้ายสถานะ)
3. Description (คำอธิบายสั้น ๆ)
4. Table of Contents (สารบัญ — สำหรับ README ยาว)
5. Installation (วิธีติดตั้ง)
6. Usage (วิธีใช้งาน)
7. Contributing (วิธีมีส่วนร่วม)
8. License (สัญญาอนุญาต)
9. Contact (ช่องทางติดต่อ)
```

### 187.2 อธิบายทีละส่วนพร้อมตัวอย่าง

**1) Title — ใช้ H1 เดียวเท่านั้น**

```markdown
# Portfolio Project
```

ชื่อควรกระชับ ตรงประเด็น และเป็น H1 ตัวเดียวในทั้งไฟล์เท่านั้น (ตามกฎที่กล่าวไว้ใน Step 182)

**2) Badges — วางไว้ทันทีใต้ Title**

```markdown
![CI](https://github.com/somchai-jaidee/portfolio-project/actions/workflows/ci.yml/badge.svg)
![license](https://img.shields.io/github/license/somchai-jaidee/portfolio-project)
![last commit](https://img.shields.io/github/last-commit/somchai-jaidee/portfolio-project)
```

**3) Description — คำอธิบาย 1–3 ประโยค**

```markdown
เว็บไซต์ portfolio ส่วนตัว สร้างด้วย HTML, CSS และ JavaScript ล้วน
ไม่พึ่งพา framework หรือ build tool ใด ๆ เพื่อให้เปิดดูได้ทันทีในทุกเบราว์เซอร์
```

ควรตอบให้ได้ภายในไม่กี่บรรทัดว่า "โปรเจกต์นี้คืออะไร" และ "ทำไมถึงมีอยู่" (motivation)

**4) Table of Contents — จำเป็นเมื่อ README ยาวเกิน 1 หน้าจอ**

```markdown
## สารบัญ

- [การติดตั้ง](#การติดตั้ง)
- [วิธีใช้งาน](#วิธีใช้งาน)
- [โครงสร้างโปรเจกต์](#โครงสร้างโปรเจกต์)
- [การมีส่วนร่วม](#การมีส่วนร่วม)
- [License](#license)
```

**สิ่งสำคัญที่ต้องเข้าใจ:** GitHub จะสร้าง **anchor link (ลิงก์ภายในหน้าเดียวกัน)** ให้กับทุก heading โดยอัตโนมัติ โดยแปลงข้อความ heading เป็นตัวพิมพ์เล็กทั้งหมด แทนที่ช่องว่างด้วยเครื่องหมายขีดกลาง (`-`) และตัดอักขระพิเศษที่ไม่ใช่ตัวอักษร/ตัวเลขออก เช่น หัวข้อ `## การติดตั้ง` จะมี anchor เป็น `#การติดตั้ง` โดยอัตโนมัติ ทำให้คลิกจากสารบัญแล้วเลื่อนไปยังหัวข้อนั้นได้ทันทีโดยไม่ต้องตั้งค่าอะไรเพิ่ม

**5) Installation — คำสั่งที่ copy-paste แล้วรันได้ทันที**

````markdown
## การติดตั้ง

```bash
git clone https://github.com/somchai-jaidee/portfolio-project.git
cd portfolio-project
```

เปิดไฟล์ `index.html` ด้วยเบราว์เซอร์ได้ทันที ไม่ต้องติดตั้ง dependency ใด ๆ เพิ่มเติม
````

**6) Usage — ตัวอย่างการใช้งานจริงพร้อมภาพประกอบ**

```markdown
## วิธีใช้งาน

เปิดเว็บไซต์แล้วเลือกเมนูด้านบนเพื่อไปยังหน้าต่าง ๆ:

- **Home** — แนะนำตัวและทักษะโดยสรุป
- **About** — ประวัติและทักษะแบบละเอียด
- **Projects** — ผลงานที่เคยทำมาทั้งหมด
```

**7) Contributing — บอกวิธีให้คนอื่นมาช่วยพัฒนาต่อ**

```markdown
## การมีส่วนร่วม

ยินดีรับ Pull Request ทุกรูปแบบ! ขั้นตอนคร่าว ๆ:

1. Fork repository นี้
2. สร้าง branch ใหม่ (`git switch -c feature/ชื่อฟีเจอร์`)
```

## Step 188: README Templates และแนวคิด Awesome README

เมื่อเข้าใจโครงสร้างมาตรฐานแล้ว ขั้นต่อไปคือการเรียนรู้จากตัวอย่างจริงที่ชุมชน Open Source ยกย่องว่าเป็น README ชั้นเลิศ

### 188.1 แนวคิด "Awesome README"

ในวงการ Open Source มีคำว่า **"Awesome List"** ซึ่งหมายถึงรายการที่ชุมชนช่วยกันรวบรวมสิ่งที่ดีที่สุดในหมวดหมู่ต่าง ๆ (เช่น awesome-python, awesome-react) และหนึ่งในรายการยอดนิยมที่สุดคือ **awesome-readme** ซึ่งรวบรวมตัวอย่าง README ที่ถูกยกย่องว่าเขียนได้ดีเยี่ยมจากโปรเจกต์จริงทั่วโลก

**ลักษณะร่วมของ README ที่อยู่ใน Awesome README มักมีดังนี้:**

1. **มี Logo หรือภาพหน้าปกที่สวยงามอยู่บนสุด** จัดกึ่งกลางหน้า (ใช้ HTML `<p align="center">` แทรกใน Markdown ได้ เพราะ GFM รองรับ inline HTML บางส่วน)
2. **แถว Badge ที่จัดวางอย่างเป็นระเบียบ** ไม่มากเกินไปจนรก แต่ครอบคลุมข้อมูลสำคัญ
3. **มี GIF สาธิตการทำงานจริง** แทนคำอธิบายยาว ๆ
4. **มีสารบัญที่คลิกได้** สำหรับ README ที่ยาว
5. **แบ่งหัวข้อด้วย emoji อย่างสม่ำเสมอ** เช่น `## 🚀 การติดตั้ง`, `## 📖 วิธีใช้งาน`, `## 🤝 การมีส่วนร่วม` เพื่อให้สแกนสายตาหาหัวข้อได้เร็ว
6. **มีตัวอย่างโค้ดที่ copy-paste แล้วรันได้ทันที** ไม่ใช่แค่คำอธิบายลอย ๆ

### 188.2 ตัวอย่างโครงสร้างแบบ "ใช้ Logo กึ่งกลางและ Badge แถวเดียว"

```markdown
<p align="center">

</p>

<h1 align="center">Portfolio Project</h1>

<p align="center">
  เว็บไซต์ portfolio ส่วนตัว สร้างด้วย HTML, CSS และ JavaScript ล้วน

<p align="center">

  <img src="https://img.shields.io/github/last-commit/somchai-jaidee/portfolio-project" alt="last commit" />

```

สังเกตว่าตัวอย่างนี้ผสม **HTML แท็ก** (`<p align="center">`, `<img>`, `<h1 align="center">`) เข้ากับ Markdown ปกติ — นี่คือความสามารถพิเศษของ GFM ที่ **อนุญาตให้แทรก inline HTML** ลงในไฟล์ `.md` ได้โดยตรง ซึ่งมีประโยชน์มากในกรณีที่ Markdown บริสุทธิ์ทำไม่ได้ เช่นการจัดกึ่งกลาง (Markdown มาตรฐานไม่มี syntax สำหรับ text-align) หรือการกำหนดความกว้างของรูปภาพ (`width="120"`)

### 188.4 แหล่งอ้างอิงเพื่อศึกษาเพิ่มเติม

โปรเจกต์ Open Source ที่ควรลองเปิดดู README จริงเพื่อศึกษาสไตล์การเขียนที่ดี (สามารถค้นหาบน GitHub ได้โดยตรง):

- โปรเจกต์ที่มีผู้ติดตาม (star) จำนวนมากในภาษาที่คุณสนใจ มักผ่านการขัดเกลา README มาอย่างดีเพราะมีคนอ่านจำนวนมาก
- โปรเจกต์ประเภท CLI tool มักมี GIF สาธิตการใช้งานที่ดีเยี่ยม เพราะเป็นวิธีเดียวที่จะ "แสดง" ว่าเครื่องมือทำงานอย่างไรโดยไม่ต้องติดตั้งเอง
- โปรเจกต์ที่มี badge จำนวนมากมักเป็นโปรเจกต์ที่มีระบบ CI/CD, code coverage และ community guideline ครบถ้วน เหมาะเป็นตัวอย่างของโปรเจกต์ที่ "ดูแลอย่างจริงจัง"

หลักการสำคัญที่สุดคือ **ไม่ต้องลอกทุกอย่างมาทั้งหมด** — ให้เลือกเฉพาะส่วนที่เหมาะกับขนาดและลักษณะของโปรเจกต์ตัวเอง โปรเจกต์เล็ก ๆ ที่มี badge เยอะเกินความจำเป็นอาจดูเยอะเกินจริงและไม่น่าเชื่อถือ

## Step 189: Markdown ใน Issue/PR/Comment ต่างจากใน README อย่างไร

แม้ Markdown ที่ใช้ใน README.md, Issue, Pull Request และ Comment จะเป็น GitHub Flavored Markdown เหมือนกันทั้งหมด แต่มี**พฤติกรรมและฟีเจอร์พิเศษบางอย่างที่ทำงานได้เฉพาะในบริบทของการสนทนา (Issue/PR/Comment) เท่านั้น** ไม่ทำงานใน README

### 189.1 @mentions ส่ง Notification จริงเฉพาะในบทสนทนา

ตามที่กล่าวไปใน Step 184 — `@username` ใน README.md จะกลายเป็นลิงก์แต่**ไม่ส่งการแจ้งเตือน** เพราะไม่มี "เหตุการณ์" ที่ทำให้ระบบแจ้งเตือนทำงาน ในขณะที่การพิมพ์ `@username` ใน Issue, PR หรือ Comment **จะส่ง notification ไปหาผู้ใช้คนนั้นทันทีที่กด submit** เพราะถือเป็นการกระทำ ณ ขณะนั้นจริง ๆ

### 189.2 Task List แบบคลิกติ๊กได้ ทำงานเต็มรูปแบบเฉพาะใน Issue/PR

Task list (`- [ ]`) ใน README.md จะแสดงเป็น checkbox ที่มองเห็นได้ แต่ **คลิกไม่ได้** (เพราะ README เป็นไฟล์ static ในโค้ด ไม่มีสถานะที่บันทึกการคลิกได้) ในขณะที่ task list ใน **body ของ Issue หรือ Pull Request** ผู้ใช้ที่มีสิทธิ์เข้าถึงสามารถ **คลิกติ๊กได้จริงบนหน้าเว็บ** และ GitHub จะบันทึกการเปลี่ยนแปลงนั้นเป็นการแก้ไข (edit) ของ Issue/PR โดยอัตโนมัติ พร้อมนำไปคำนวณเป็น progress bar แสดงในหน้ารายการ Issue ด้วย (เช่น "3 of 5 tasks complete")

### 189.3 Quote Reply — ฟีเจอร์เฉพาะของ Comment

เมื่ออ่าน comment ของคนอื่นใน Issue หรือ PR แล้วต้องการตอบกลับเฉพาะเจาะจงบางประโยค สามารถ**ไฮไลต์ข้อความที่ต้องการ** แล้วจะมีปุ่ม "Quote reply" ปรากฏขึ้นมาให้กดอัตโนมัติ ซึ่งจะแทรก syntax blockquote ให้ในกล่องคอมเมนต์ใหม่ทันที:

```markdown
> ควรจะใช้ async/await แทน callback ไหมครับ

เห็นด้วยครับ ผมแก้ไขให้แล้วใน commit ล่าสุด
```

วิธีนี้ทำให้บทสนทนาที่มีหลายประเด็นพร้อมกันยังคงอ่านเข้าใจง่าย เพราะเห็นชัดว่ากำลังตอบกลับข้อความไหน — ต่างจาก README ที่ไม่มีบริบทของ "การตอบกลับ" เพราะเป็นเอกสารทางเดียว ไม่ใช่บทสนทนา

### 189.4 Suggestion Block — ข้อเสนอแก้ไขโค้ดที่ apply ได้ทันที

นี่คือฟีเจอร์ที่ทรงพลังที่สุดอย่างหนึ่งของ GitHub ซึ่ง**ทำงานได้เฉพาะใน Code Review ของ Pull Request เท่านั้น** ใช้ syntax พิเศษ ` ```suggestion `:

````markdown
```suggestion
const PORT = process.env.PORT || 3000;
```
````

เมื่อผู้รีวิวเขียน suggestion block แบบนี้ในคอมเมนต์รีวิวโค้ดบรรทัดใดบรรทัดหนึ่ง GitHub จะแสดงเป็นกล่องพิเศษพร้อมปุ่ม **"Commit suggestion"** ให้เจ้าของ Pull Request กดยอมรับได้ทันที โดยที่ **ระบบจะสร้าง commit ใหม่ที่แก้โค้ดตรงตาม suggestion นั้นให้อัตโนมัติ** โดยไม่ต้องให้เจ้าของ PR มานั่งพิมพ์แก้เองเลยด้วยซ้ำ

ความแตกต่างสำคัญ: ใน README.md ถ้าอยากแสดงโค้ดก็ใช้ backtick 3 ตัวธรรมดา (` ``` `) แต่ในบริบทของการรีวิว PR การใช้คำว่า `suggestion` แทนชื่อภาษาโปรแกรม จะเปลี่ยนความหมายจาก "แสดงตัวอย่างโค้ดเฉย ๆ" เป็น "ข้อเสนอแก้ไขที่ apply ได้จริง" ทันที — เราจะฝึกใช้ฟีเจอร์นี้อย่างละเอียดใน Part ที่สอนเรื่อง Code Review

### 189.5 สรุปตารางเปรียบเทียบ

| ฟีเจอร์ | ใน README.md | ใน Issue/PR/Comment |
|---|---|---|
| `@mentions` | เป็นลิงก์ แต่ไม่ส่ง notification | เป็นลิงก์ **และส่ง notification จริง** |
| `#123` (issue reference) | เป็นลิงก์ | เป็นลิงก์ + อาจปิด issue อัตโนมัติถ้าใช้กับคำว่า Fixes/Closes ใน PR |
| Task list `- [ ]` | แสดงผลอย่างเดียว คลิกไม่ได้ | **คลิกติ๊กได้จริง** พร้อม progress bar |
| Quote reply | ไม่มีแนวคิดนี้ (ไม่ใช่บทสนทนา) | มีปุ่ม Quote reply ให้ใช้งาน |
| ` ```suggestion ` block | ไม่มีความหมายพิเศษ (แสดงเป็นโค้ดเฉย ๆ) | เป็นข้อเสนอแก้โค้ดที่ apply เป็น commit ได้ |
| Emoji reaction (👍 👎 🎉) | ไม่มี (README ไม่ใช่โพสต์ที่กด react ได้) | กด react ได้ที่มุมขวาบนของแต่ละ comment |

หลักการสำคัญที่ควรจำคือ **README.md คือเอกสารทางเดียว (one-way document)** ที่มีไว้ให้อ่าน ในขณะที่ Issue/PR/Comment คือ **พื้นที่สนทนาสองทาง (interactive conversation)** ที่ผูกกับระบบผู้ใช้ การแจ้งเตือน และ workflow ของ Git โดยตรง — เข้าใจความแตกต่างนี้จะช่วยให้เลือกใช้ฟีเจอร์ Markdown ได้ถูกที่ถูกเวลาเมื่อทำงานร่วมกับทีมจริงในเฟสถัด ๆ ไปของหลักสูตรนี้

### 190.4 บันทึกไฟล์และตรวจสอบผลลัพธ์

หลังจากเขียนทับไฟล์ `README.md` ตามเนื้อหาด้านบนแล้ว ตรวจสอบว่า Git เห็นการเปลี่ยนแปลง:

```bash
git status
```

```
On branch main
Changes not staged for commit:
  (use "git add <file>..." to update what will be committed)
  (use "git restore <file>..." to discard changes in working directory)
	modified:   README.md
```

ดู diff เพื่อรีวิวก่อน commit ตามนิสัยที่ดีที่เรียนมาตั้งแต่ Part 05:

```bash
git diff README.md
```

ตรวจสอบว่าเนื้อหาที่แสดงตรงกับที่ตั้งใจแก้ทั้งหมด ไม่มีอักขระแปลกปลอมหรือ marker ตกค้าง

### 190.5 Commit การเปลี่ยนแปลง

```bash
git add README.md
git commit -m "docs: ปรับปรุง README.md ให้เป็นมืออาชีพเต็มรูปแบบ พร้อม badge, สารบัญ และ roadmap"
```

```
[main 9f0a1b2] docs: ปรับปรุง README.md ให้เป็นมืออาชีพเต็มรูปแบบ พร้อม badge, สารบัญ และ roadmap
 1 file changed, 68 insertions(+), 7 deletions(-)
```

สังเกตว่าเราใช้ prefix `docs:` นำหน้าข้อความ commit — นี่คือรูปแบบที่เรียกว่า **Conventional Commits** ซึ่งเป็นแนวปฏิบัติที่ทีมมืออาชีพนิยมใช้เพื่อบอกประเภทของการเปลี่ยนแปลงตั้งแต่มองแค่ commit message (เช่น `docs:` สำหรับเอกสาร, `feat:` สำหรับฟีเจอร์ใหม่, `fix:` สำหรับแก้บั๊ก) — เราจะเจาะลึกแนวปฏิบัตินี้อย่างละเอียดใน Part ถัดไปของเฟสนี้

### 190.6 ตรวจสอบผลลัพธ์บน GitHub (เมื่อ push ขึ้นจริง)

เมื่อ push README.md เวอร์ชันใหม่ขึ้น GitHub จริง (เนื้อหาการ push จะเรียนละเอียดใน Part 16–17) หน้า repository จะแสดงผลลัพธ์ที่ผ่านการ render แล้วทันที:

- Badge ทั้งสามอันจะแสดงเป็นรูปภาพแคปซูลสีต่าง ๆ เรียงกันใต้ชื่อโปรเจกต์
- สารบัญจะกลายเป็นลิงก์ที่คลิกแล้วเลื่อนไปยังหัวข้อนั้นทันที
- Task list ในหัวข้อ "วิธีใช้งาน" จะแสดงเป็น checkbox (ติ๊กแล้ว 3 อัน ยังไม่ติ๊ก 1 อัน)
- ตาราง "แผนพัฒนาต่อ" จะแสดงเป็นตารางจัดกึ่งกลางในคอลัมน์สถานะ พร้อม emoji ✅ 🚧 📝
- โครงสร้างโปรเจกต์ในหัวข้อ "โครงสร้างโปรเจกต์" จะแสดงเป็น code block ฟอนต์ monospace อ่านง่าย

### 190.7 แบบฝึกหัดเพิ่มเติม (ทำต่อด้วยตัวเอง)

## สรุป Part 19

ใน Part นี้เราได้เรียนรู้ว่า:

1. **README.md คือ "หน้าตา" แรกของโปรเจกต์บน GitHub** ที่ตัดสินภายในไม่กี่วินาทีว่าคนจะสนใจโปรเจกต์ต่อหรือไม่
2. **Markdown syntax พื้นฐาน** ได้แก่ heading, bold/italic, list, link, image, blockquote และ inline code เป็นรากฐานที่ใช้ได้ทุกที่
3. **GitHub Flavored Markdown (GFM)** เพิ่มความสามารถพิเศษเข้ามา ได้แก่ ตาราง, task list ที่คลิกติ๊กได้จริง และ code block พร้อม syntax highlighting
4. ฟีเจอร์เฉพาะของ GFM อย่าง **@mentions, #issue references, emoji, strikethrough** ทำให้การสื่อสารบน GitHub มีประสิทธิภาพกว่ามาก
5. **Badge จาก shields.io** ช่วยสรุปสถานะโปรเจกต์ (build, license, version) ให้อ่านได้ในเสี้ยววินาที
6. การแทรก **รูปภาพ, GIF, วิดีโอ** และเทคนิค **drag-and-drop upload** ไปยัง GitHub CDN ช่วยให้ README มีชีวิตชีวาโดยไม่ต้องหนัก repository
7. **โครงสร้าง README มาตรฐาน 9 ส่วน** (Title, Badges, Description, TOC, Installation, Usage, Contributing, License, Contact) คือกรอบที่ใช้ได้กับแทบทุกโปรเจกต์
8. แนวคิด **Awesome README** สอนให้เรียนรู้จากตัวอย่างจริงของโปรเจกต์ Open Source ชั้นนำ
9. **Markdown ใน Issue/PR/Comment มีพฤติกรรมพิเศษ** ที่ README ไม่มี เช่น notification จาก @mention, task list ที่คลิกได้จริง, quote reply, และ suggestion block
10. ลงมือเขียน **README.md ฉบับมืออาชีพเต็มรูปแบบ** ให้กับโปรเจกต์ portfolio-project จาก Part 15 สำเร็จแล้ว
