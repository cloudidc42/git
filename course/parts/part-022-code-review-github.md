## Step 211: ทำไม Code Review ถึงสำคัญมากในการทำงานจริง

ถ้าคุณเคยทำงานคนเดียวมาตลอด คุณอาจสงสัยว่า "ทำไมต้องเสียเวลาให้คนอื่นมาอ่านโค้ดของฉันก่อน merge ด้วย" คำตอบคือ **Code Review คือหนึ่งในกลไกที่ทรงพลังที่สุดที่ทำให้ทีมซอฟต์แวร์ผลิตงานได้มีคุณภาพสูงอย่างยั่งยืน** และแทบทุกบริษัทซอฟต์แวร์ระดับโลก ตั้งแต่สตาร์ทอัพเล็ก ๆ ไปจนถึง Google, Microsoft, Meta ต่างก็บังคับให้ทุก Pull Request ต้องผ่านการรีวิวก่อน merge เข้า branch หลักเสมอ

### 211.1 เหตุผลหลักที่ Code Review สำคัญ

**1. คุณภาพโค้ด (Code Quality)**

คนเขียนโค้ดมักจะ "มองข้าม" จุดผิดพลาดของตัวเอง เพราะสมองคุ้นชินกับตรรกะที่ตัวเองเขียนไปแล้ว การมีคนที่สองมาอ่านโค้ดด้วยสายตาที่ไม่มีอคติ (fresh eyes) จะช่วยจับสิ่งเหล่านี้ได้:

- Logic ที่ผิดพลาดหรือ edge case ที่ลืมจัดการ
- โค้ดที่ซับซ้อนเกินความจำเป็น (over-engineering)
- การตั้งชื่อตัวแปร/ฟังก์ชันที่สื่อความหมายไม่ชัดเจน
- Pattern ที่ไม่ตรงกับมาตรฐานของทีม (coding convention)
- ช่องโหว่ด้านความปลอดภัยเบื้องต้น เช่น SQL Injection, hardcoded secret, การ validate input ที่หละหลวม
- Performance issue ที่มองแวบแรกอาจไม่เห็น เช่น query ในลูป (N+1 query)

**2. แชร์ความรู้ในทีม (Knowledge Sharing)**

Code Review ไม่ใช่แค่การ "ตรวจงาน" แต่เป็นกลไกกระจายความรู้ที่มีประสิทธิภาพสูงมาก:

- คนที่ไม่เคยแตะโค้ดส่วนนั้นมาก่อนจะได้เห็นว่าระบบส่วนนี้ทำงานอย่างไร
- ลดปัญหา **"Bus Factor"** — คือความเสี่ยงที่ถ้ามีคนคนเดียวในทีมที่เข้าใจโค้ดส่วนสำคัญ แล้ววันหนึ่งเขาลาออกหรือลาป่วยยาว ทีมจะทำงานต่อไม่ได้ การรีวิวช่วยให้อย่างน้อยมีคนที่สองที่เข้าใจโค้ดนั้นเสมอ
- รุ่นพี่ในทีม (senior) ถ่ายทอดแนวคิด best practice ให้รุ่นน้อง (junior) ผ่านคอมเมนต์ในโค้ดจริง ซึ่งจดจำได้ดีกว่าการอ่านเอกสารเฉย ๆ
- รุ่นน้องเองก็สามารถตั้งคำถามที่ทำให้รุ่นพี่ทบทวนการตัดสินใจของตัวเองได้เช่นกัน — เป็นความรู้ที่ไหลสองทาง ไม่ใช่ทางเดียว

**3. จับบั๊กก่อนถึง Production**

ยิ่งบั๊กถูกพบเร็วเท่าไหร่ ต้นทุนในการแก้ยิ่งถูกลงเท่านั้น เรียงลำดับต้นทุนของการแก้บั๊กตามจุดที่พบ (จากถูกที่สุดไปแพงที่สุด) โดยทั่วไปจะเป็นแบบนี้:

```
พบตอนเขียนโค้ด (แก้เอง) 
    < พบตอน Code Review 
        < พบตอน Testing/QA 
            < พบหลัง Deploy ไป Production แล้ว
                < ลูกค้าเจอเองแล้วมาแจ้ง
```

Code Review อยู่ในจุดที่ **ถูกที่สุดจุดหนึ่งที่จะจับบั๊กได้ก่อนที่มันจะกระทบผู้ใช้จริง** เพราะยังไม่ได้ merge เข้า branch หลัก แก้ตอนนี้ไม่กระทบใครเลย

**4. ความรับผิดชอบร่วมกัน (Collective Ownership)**

เมื่อมีคนอื่นรีวิวโค้ดของคุณ และคุณก็รีวิวโค้ดของคนอื่น ทุกคนในทีมจะค่อย ๆ รู้สึกว่าโค้ดทั้งหมดเป็น "ของทีม" ไม่ใช่ "ของฉันคนเดียว" — ซึ่งลดปัญหาการหวงโค้ด (territorial coding) และทำให้การ maintain ระยะยาวง่ายขึ้นมาก

**5. รักษามาตรฐานและความสม่ำเสมอของโค้ด**

ทีมที่มีคนเขียนโค้ดหลายคน ถ้าไม่มีการรีวิว แต่ละคนมักจะเขียนสไตล์ต่างกันไปเรื่อย ๆ จนโค้ดเบสกลายเป็น "ปะติดปะต่อ" ไม่มีความสม่ำเสมอ Code Review ช่วยบังคับใช้มาตรฐานร่วมกันของทีมอย่างต่อเนื่อง

### 211.2 สิ่งที่ Code Review ไม่ใช่

เพื่อความเข้าใจที่ถูกต้อง ต้องแยกให้ชัดว่า Code Review **ไม่ใช่**:

- ไม่ใช่การจับผิดเพื่อลดคุณค่าของคนเขียน
- ไม่ใช่ตัวแทนของการทดสอบอัตโนมัติ (automated testing) — ทั้งสองอย่างต้องทำคู่กัน ไม่ใช่แทนกัน
- ไม่ใช่ที่ที่จะถกเถียงเรื่องรสนิยมส่วนตัวที่ไม่มีผลต่อการทำงานของโค้ด (เช่น เว้นวรรค 2 กับ 4 ช่อง ควรตกลงกันไว้ล่วงหน้าด้วย linter/formatter แทนที่จะเถียงกันในทุก PR)

### 211.3 ตำแหน่งของ Code Review ใน Pull Request Workflow

จาก Part ก่อนหน้าที่คุณได้เรียนเรื่องการสร้าง Pull Request ไปแล้ว ตำแหน่งของ Code Review อยู่ตรงกลางของ workflow แบบนี้:

```
สร้าง branch ใหม่
    → เขียนโค้ด + commit
        → push ขึ้น GitHub
            → เปิด Pull Request
                → [Code Review] ← เราอยู่ตรงนี้ใน Part นี้
                    → แก้ไขตาม feedback (ถ้ามี)
                        → Approve
                            → Merge เข้า branch หลัก
```

Part นี้จะพาคุณลงลึกในขั้นตอน "Code Review" ทั้งหมด ตั้งแต่มุมมองของคนขอให้รีวิว (author) และคนที่รีวิว (reviewer)

## Step 212: การ Request Review จากเพื่อนร่วมทีม (Reviewers Panel)

เมื่อคุณเปิด Pull Request บน GitHub แล้ว ขั้นตอนถัดไปคือการบอกให้ระบบรู้ว่า **ใครควรจะเป็นคนมารีวิวโค้ดนี้**

### 212.1 ตำแหน่งของ Reviewers Panel

เปิดหน้า Pull Request ของคุณบน GitHub แล้วมองไปทาง **แถบด้านขวา (sidebar)** จะเห็นหัวข้อหลายอย่างเรียงกัน:

```
┌─────────────────────────┐
│ Reviewers            ⚙️  │
│   (No reviews)          │
├─────────────────────────┤
│ Assignees            ⚙️  │
│   (No one assigned)     │
├─────────────────────────┤
│ Labels               ⚙️  │
│   (None yet)             │
├─────────────────────────┤
│ Projects             ⚙️  │
├─────────────────────────┤
│ Milestone             ⚙️  │
└─────────────────────────┘
```

หัวข้อบนสุดคือ **Reviewers** — นี่คือจุดที่คุณจะขอให้คนอื่นมารีวิว PR ของคุณ

### 212.2 วิธี Request Review

1. คลิกที่ไอคอนรูปเฟือง (⚙️) ข้าง ๆ คำว่า **Reviewers**
2. จะมี dropdown แสดงรายชื่อคนที่สามารถ request ได้ ซึ่งมักจะเป็น:
   - Collaborators ของ repository (คนที่มีสิทธิ์เข้าถึง repo นี้)
   - สมาชิกในองค์กร (organization) ถ้า repo นั้นอยู่ใน organization
   - Team ที่ตั้งไว้ (เช่น `@my-org/backend-team`) — ถ้า request ทั้ง team ทุกคนใน team จะเห็นการแจ้งเตือน แต่บาง organization ตั้งค่าให้สุ่มเลือกเฉพาะบางคนจาก team มารีวิวเพื่อกระจายงาน (round-robin review assignment)
3. พิมพ์ชื่อผู้ใช้หรือชื่อ team ที่ต้องการ แล้วคลิกเลือก
4. สามารถเลือกได้มากกว่า 1 คนพร้อมกัน
5. ปิด dropdown — ระบบจะส่งการแจ้งเตือน (notification + email) ไปยังคนที่ถูกเลือกทันที

### 212.3 CODEOWNERS — การแนะนำ Reviewer อัตโนมัติ

ถ้า repository มีไฟล์ `.github/CODEOWNERS` (หรือ `CODEOWNERS` ที่ root หรือใน `docs/`) กำหนดไว้ เช่น:

```
# .github/CODEOWNERS
*.js            @frontend-team
/backend/       @backend-team
/docs/          @tech-writer-1
```

เมื่อคุณเปิด PR ที่แก้ไขไฟล์ในเส้นทางเหล่านี้ GitHub จะ **แนะนำ (suggest) reviewer ที่เกี่ยวข้องให้อัตโนมัติ** ในบาง repository ที่ตั้งค่า branch protection แบบ "Require review from Code Owners" ไว้ ระบบจะบังคับด้วยว่า PR นั้นต้องได้รับ approve จาก code owner ของไฟล์ที่ถูกแก้ไขก่อนถึงจะ merge ได้

### 212.4 ความแตกต่างระหว่าง Reviewer กับ Assignee

มือใหม่มักสับสนสองสิ่งนี้:

| | Reviewer | Assignee |
|---|---|---|
| ความหมาย | คนที่ถูกขอให้ตรวจสอบและให้ความเห็นต่อโค้ด | คนที่รับผิดชอบดูแล/ผลักดัน PR นี้ให้จบ |
| ใครมักจะเป็น | เพื่อนร่วมทีม, tech lead, code owner | ตัว author เอง หรือคนที่ต้องติดตามความคืบหน้า |
| ผลต่อการ merge | อาจถูกบังคับผ่าน branch protection ("ต้อง approve ก่อน merge") | ไม่มีผลต่อ branch protection โดยตรง |

โดยทั่วไปคนเปิด PR มักจะ assign ตัวเองเป็น assignee (แสดงว่าเป็นเจ้าของงานนี้) และ request คนอื่นเป็น reviewer

### 212.5 Draft Pull Request กับการ Request Review

ถ้า PR ยังอยู่ในสถานะ **Draft** (ที่เรียนไปแล้วใน Part ก่อนหน้า) ปุ่มด้านล่างจะแสดงว่า "This pull request is still a work in progress" และ GitHub จะไม่ค่อยแนะนำให้ขอรีวิวจนกว่าคุณจะกด **"Ready for review"** เปลี่ยนสถานะให้เป็น Open ปกติก่อน — ถึงแม้ในทางเทคนิคคุณจะยังสามารถ request reviewer บน draft PR ได้เพื่อขอความเห็นแบบไม่เป็นทางการ (early feedback) ก็ตาม

### 212.6 จำนวน Reviewer ที่เหมาะสม

ไม่มีกฎตายตัว แต่แนวทางที่ทีมส่วนใหญ่ใช้:

- PR เล็ก ๆ ทั่วไป: 1 reviewer ก็เพียงพอ
- PR ที่กระทบส่วนสำคัญของระบบ หรือเปลี่ยนแปลง architecture: 2 reviewer ขึ้นไป
- PR ที่แตะโค้ดของหลาย domain (เช่น ทั้ง frontend และ backend): ขอ reviewer จากแต่ละฝั่ง

การขอ reviewer มากเกินไปโดยไม่จำเป็นอาจทำให้ PR ค้างนาน เพราะทุกคนคิดว่า "อีกคนคงรีวิวแล้ว" (เรียกปรากฏการณ์นี้ว่า **diffusion of responsibility**)

## Step 213: การ Comment แบบ Inline บนโค้ดเฉพาะบรรทัด

หัวใจของการรีวิวโค้ดบน GitHub คือความสามารถในการ comment ผูกกับ **บรรทัดโค้ดที่เจาะจง** ไม่ใช่แค่คอมเมนต์ลอย ๆ ในกล่องสนทนาด้านล่างเหมือน Issue ทั่วไป

### 213.1 ไปที่แท็บ Files Changed

เปิด Pull Request แล้วคลิกแท็บ **"Files changed"** (อยู่ข้าง ๆ แท็บ Conversation, Commits, Checks) หน้านี้จะแสดง **diff** ของทุกไฟล์ที่ถูกแก้ไขใน PR นั้น โดยแสดงเป็น:

- บรรทัดสีเขียว (มี `+` นำหน้า) = โค้ดที่ถูกเพิ่มเข้ามาใหม่
- บรรทัดสีแดง (มี `-` นำหน้า) = โค้ดที่ถูกลบออก
- บรรทัดสีขาว/เทา = โค้ดเดิมที่ไม่ถูกแก้ไข (แสดงไว้เป็น context)

### 213.2 การเปิดกล่อง Comment บนบรรทัดที่ต้องการ

**ขั้นตอน:**

1. เอาเมาส์ไปวางบน**เลขบรรทัด (line number)** ทางซ้ายของบรรทัดที่ต้องการคอมเมนต์ ในฝั่ง diff
2. จะมี**เครื่องหมาย + สีน้ำเงิน** ปรากฏขึ้นทับเลขบรรทัดนั้น
3. คลิกที่เครื่องหมาย + จะมีกล่องข้อความ (comment box) เปิดขึ้นมาใต้บรรทัดนั้นทันที
4. พิมพ์ความเห็นของคุณ รองรับ **Markdown** เต็มรูปแบบ เช่น
   - ตัวหนา ตัวเอียง
   - ลิงก์
   - โค้ดบล็อกด้วย backtick สามตัว
   - รายการ (bullet list)
   - การ mention คนอื่นด้วย `@username`
   - Emoji `:emoji_name:`
5. ด้านล่างกล่องข้อความจะมีปุ่มให้เลือก 2 แบบ:
   - **"Add single comment"** — โพสต์คอมเมนต์นี้ทันที เดี่ยว ๆ (ไม่ผูกกับ review formal)
   - **"Start a review"** — เก็บคอมเมนต์นี้ไว้เป็น "pending" ก่อน แล้วค่อยรวมกับคอมเมนต์อื่น ๆ ส่งพร้อมกันทีเดียวตอน submit review (แนะนำให้ใช้แบบนี้เสมอเมื่อรีวิวจริงจัง เพราะจะไม่ spam การแจ้งเตือนทีละคอมเมนต์ และทำให้ author ได้เห็น feedback ทั้งหมดพร้อมกัน)

### 213.3 การคอมเมนต์หลายบรรทัดพร้อมกัน (Multi-line comment)

ถ้าต้องการคอมเมนต์ครอบคลุมหลายบรรทัดต่อเนื่องกัน:

1. คลิกที่เครื่องหมาย + บนบรรทัดแรกที่ต้องการ **ค้างไว้แล้วลากเมาส์** ลงไปยังบรรทัดสุดท้ายที่ต้องการ (หรือคลิกบรรทัดแรก แล้ว shift+คลิกบรรทัดสุดท้าย)
2. ช่วงบรรทัดที่เลือกจะถูกไฮไลต์เป็นแถบสีฟ้าอ่อน
3. กล่องคอมเมนต์จะแสดงหัวว่า "Commenting on lines X to Y"

การคอมเมนต์แบบหลายบรรทัดมีประโยชน์มากเมื่อ feedback ของคุณเกี่ยวข้องกับ logic ที่กระจายอยู่หลายบรรทัดต่อกัน เช่น ทั้งฟังก์ชัน

### 213.4 Unified View กับ Split View

มุมขวาบนของแท็บ Files changed มีปุ่มสลับมุมมอง diff:

- **Unified** (ค่าเริ่มต้น) — แสดงบรรทัดเก่ากับใหม่เรียงต่อกันในคอลัมน์เดียว
- **Split** — แสดงเป็น 2 คอลัมน์ซ้าย-ขวา (เก่า | ใหม่) เทียบกัน เหมาะกับการดูความเปลี่ยนแปลงที่ซับซ้อนในบรรทัดเดียวกัน

ทั้งสองมุมมองสามารถคลิก + เพื่อคอมเมนต์ได้เหมือนกัน

### 213.5 การดูโค้ดนอกเหนือจาก Diff (Expand context)

บางครั้ง diff แสดงแค่ไม่กี่บรรทัดรอบ ๆ ที่แก้ไข (เช่นแสดงแค่ 3 บรรทัดบนล่าง) แต่คุณอยากเห็นบริบทของทั้งฟังก์ชัน ให้คลิกที่ไอคอนลูกศรขึ้น/ลง หรือคำว่า `Expand up` / `Expand down` ที่อยู่ระหว่างช่วง diff เพื่อดึงโค้ดบริบทเพิ่มเติมมาแสดง — **คุณสามารถคอมเมนต์บนบรรทัดที่ขยายออกมานี้ได้เช่นกัน** แม้ว่าบรรทัดนั้นจะไม่ได้ถูกแก้ไขใน PR นี้เลยก็ตาม

### 213.6 ตัวอย่าง Inline Comment ที่ดี

```
บรรทัดที่คอมเมนต์:
  if (user.age > 18) {
    allowAccess();
  }

คอมเมนต์:
  ถ้า `age` เป็น `null` หรือ `undefined` เงื่อนไขนี้จะ throw error
  ก่อนถึงจุดนี้ครับ ลองเพิ่มการเช็ค `user.age != null` ก่อนหน้านี้ดีไหมครับ
```

## Step 214: Review States 3 แบบ — Approve, Request Changes, Comment

หลังจากใส่คอมเมนต์ (หรือไม่ใส่เลยก็ได้) เมื่อ reviewer พร้อมจะสรุปความเห็นของตัวเองต่อทั้ง PR จะต้องกดปุ่ม **"Review changes"** (อยู่มุมขวาบนของแท็บ Files changed) เพื่อเลือก **สถานะการรีวิว (review state)** ก่อน submit

หน้าต่างที่เปิดขึ้นมาจะมีช่องให้ใส่ความเห็นสรุปโดยรวม (overall summary) และตัวเลือก 3 แบบ (radio button):

### 214.1 Comment

> "Submit general feedback without explicit approval."

- ใช้เมื่อคุณมีความเห็นหรือคำถาม แต่**ไม่ต้องการบล็อกหรืออนุมัติ**การ merge
- เหมาะกับกรณีที่คุณไม่ใช่ reviewer หลักของ PR นี้ แต่อยากช่วยดูให้ หรือแค่มีคำถามทั่วไป
- **ไม่มีผลต่อสถานะ merge ใด ๆ** ต่อให้ repository ตั้งค่า branch protection ให้ต้องมี approval ก็ตาม การ comment ไม่ถูกนับเป็น approval

### 214.2 Approve

> "Submit feedback and approve merging these changes."

- ใช้เมื่อคุณตรวจสอบแล้วว่าโค้ดนี้**พร้อม merge** ไม่มีปัญหาสำคัญ (อาจมี comment เล็กน้อยประกอบได้ เช่น nitpick ที่ไม่บล็อก)
- ถ้า repository ตั้งค่า branch protection แบบ **"Require approvals"** (เช่น ต้องมีอย่างน้อย 1 หรือ 2 approval) การกด Approve จะนับเป็นหนึ่งใน requirement นั้น
- หน้า PR จะแสดงเครื่องหมายถูกสีเขียว ✅ พร้อมชื่อ reviewer ที่ approve

### 214.3 Request Changes

> "Submit feedback that must be addressed before merging."

- ใช้เมื่อคุณพบปัญหาที่**ต้องแก้ไขก่อน** ถึงจะยอมให้ merge ได้ เช่น บั๊กร้ายแรง, ปัญหาความปลอดภัย, การออกแบบที่ผิดหลักการสำคัญของทีม
- ถ้า repository ตั้งค่า branch protection ที่เหมาะสม การกด Request Changes จะ **บล็อกปุ่ม Merge ไว้ทันที** — ปุ่ม merge จะแสดงข้อความสีแดง "Changes requested" และไม่สามารถกดได้จนกว่าจะปลด block

**วิธีปลด block จาก Request Changes มี 2 ทาง:**

1. **Author แก้ไขตามที่ขอแล้ว push commit ใหม่** — บาง repository ตั้งค่าให้ request changes ถูกยกเลิกอัตโนมัติเมื่อมี commit ใหม่เข้ามา (ขึ้นกับการตั้งค่า "Dismiss stale reviews") แต่โดยทั่วไป reviewer คนเดิมยังต้องกลับมาดูใหม่แล้วเปลี่ยนสถานะเป็น Approve เอง
2. **Reviewer เข้ามาเปลี่ยนใจเอง** — โดยการ submit review รอบใหม่เป็น Approve หรือใช้เมนู **"Dismiss review"** (ตัวเลือกจุดสามจุด `...` ข้าง review นั้น) เพื่อยกเลิก request changes เดิมทิ้งไปโดยไม่ต้อง approve ก็ได้ (ต้องใส่เหตุผลประกอบ)

### 214.4 ตารางสรุปผลกระทบของแต่ละ State

| State | ความหมาย | บล็อกการ Merge ไหม | นับเป็น Approval ไหม |
|---|---|---|---|
| **Comment** | แสดงความเห็น/คำถามทั่วไป | ไม่ | ไม่ |
| **Approve** | รับรองว่าโค้ดพร้อม merge | ไม่ (ไม่บล็อก แถมช่วยปลด requirement) | นับ |
| **Request changes** | ต้องแก้ก่อนถึงจะ merge ได้ | **บล็อก** (ถ้าตั้งค่า branch protection ไว้) | ไม่นับ (และหักล้าง approval requirement) |

### 214.5 ข้อจำกัดสำคัญ: Reviewer ต้องไม่ใช่ Author เอง

GitHub **ไม่อนุญาตให้เจ้าของ PR approve PR ของตัวเอง** เสมอ (ในกรณี repository ปกติที่มีเจ้าของ/collaborator มากกว่า 1 คน) ปุ่ม "Review changes" จะไม่ปรากฏให้เจ้าของ PR เห็นเลยเมื่อดู PR ของตัวเอง คุณต้องรอให้อีกคนหนึ่งมารีวิวให้เสมอ

### 214.6 Submit Review เมื่อไหร่

หลังจากใส่คอมเมนต์แบบ pending (จากการกด "Start a review" ในแต่ละจุด) ไว้หลายจุดแล้ว ปุ่มจะเปลี่ยนเป็น **"Finish your review"** หรือ **"Review changes"** ที่มุมขวาบน — คลิกเพื่อเปิดกล่องสรุป ใส่ overall comment (ถ้ามี) เลือก state ที่ต้องการ แล้วกด **"Submit review"** เมื่อกดแล้ว คอมเมนต์ pending ทั้งหมดจะถูกโพสต์พร้อมกันในครั้งเดียว และ author จะได้รับการแจ้งเตือนเพียงครั้งเดียวแทนที่จะโดนสแปมทีละคอมเมนต์

## Step 215: Suggested Changes — เสนอแก้โค้ดตรง ๆ ที่กด Apply ได้เลย

หนึ่งในฟีเจอร์ที่มีประโยชน์มากที่สุดของ GitHub Code Review คือ **Suggested Changes** — แทนที่จะบอก author เป็นคำพูดว่า "ควรแก้เป็นแบบนี้นะ" reviewer สามารถ **เขียนโค้ดที่แก้แล้วลงไปตรง ๆ ในคอมเมนต์** และให้ author กดปุ่มเดียวเพื่อ apply การแก้ไขนั้นเข้าไปใน branch ได้ทันที โดยไม่ต้องพิมพ์โค้ดเองใหม่เลย

### 215.1 วิธีสร้าง Suggested Change

1. เปิดกล่องคอมเมนต์ inline บนบรรทัดที่ต้องการเสนอแก้ (ตามวิธีใน Step 213)
2. ในแถบเครื่องมือ (toolbar) เหนือกล่องข้อความ จะมีไอคอนรูป `+/-` อยู่ในกรอบสี่เหลี่ยม ชื่อว่า **"Insert a suggestion"** — คลิกไอคอนนี้
3. GitHub จะแทรกโค้ดบล็อกพิเศษให้อัตโนมัติ โดยดึงโค้ดต้นฉบับของบรรทัดนั้นมาใส่ไว้ในบล็อกภาษา `suggestion`:

   ````
   ```suggestion
   โค้ดเดิมของบรรทัดนี้
   ```
   ````

4. แก้ไขเนื้อหาภายในบล็อกนั้นให้เป็นโค้ดที่คุณต้องการเสนอ เช่น:

   ````
   ```suggestion
   if (user?.age != null && user.age > 18) {
   ```
   ````

5. สามารถพิมพ์คำอธิบายเพิ่มเติมเหนือหรือใต้บล็อก suggestion ได้ตามปกติ เช่น "ใช้ optional chaining เพื่อป้องกัน error ตรงนี้ครับ"
6. กด "Add single comment" หรือ "Start a review" ตามปกติ

### 215.2 มุมมองของ Author เมื่อได้รับ Suggestion

เมื่อ author เข้ามาดูคอมเมนต์นี้ จะเห็น diff ย่อยแสดงให้ชัดเจนว่าโค้ดเดิมกับโค้ดที่เสนอต่างกันตรงไหน (เหมือน diff เล็ก ๆ ซ้อนอยู่ในคอมเมนต์) พร้อมปุ่ม 2 ปุ่มใต้บล็อกนั้น:

- **"Commit suggestion"** — สร้าง commit ใหม่ทันทีบน branch ของ PR นั้น โดยนำโค้ดที่ suggest มาแทนที่บรรทัดเดิม (สามารถแก้ commit message ก่อน commit จริงได้ผ่านปุ่มลูกศรข้าง ๆ)
- **"Add suggestion to batch"** — ถ้ามี suggestion หลายจุดในหลายคอมเมนต์ที่ต้องการ apply พร้อมกันเป็น **commit เดียว** แทนที่จะสร้างหลาย commit ย่อย ให้กดปุ่มนี้ที่แต่ละ suggestion ที่ต้องการรวม แล้วไปกด **"Commit suggestions"** ที่กล่องสรุป batch ซึ่งจะปรากฏลอยอยู่ด้านล่างของหน้าจอเมื่อมี suggestion ถูกเพิ่มเข้า batch แล้วอย่างน้อย 1 จุด

### 215.3 ข้อดีของ Suggested Changes

- **ประหยัดเวลา** — author ไม่ต้องพิมพ์โค้ดใหม่เอง ไม่ต้อง pull ลงมาแก้ในเครื่องแล้ว push กลับ
- **ลดความเข้าใจผิด** — เห็นโค้ดจริงตรง ๆ ชัดเจนกว่าคำอธิบายเป็นข้อความล้วน
- **Commit สะอาด** — การใช้ batch suggestion รวมหลายจุดเป็น commit เดียว ทำให้ประวัติ commit ไม่รกด้วย commit เล็ก ๆ จำนวนมาก
- ผู้ที่กด apply ได้ไม่จำเป็นต้องเป็น author เท่านั้น — collaborator คนอื่นที่มีสิทธิ์ write เข้า branch นั้นก็กดได้เช่นกัน

### 215.4 ข้อควรระวัง

- Suggested change เหมาะกับการแก้ไขเล็ก ๆ ระดับบรรทัดหรือไม่กี่บรรทัด (typo, การตั้งชื่อ, logic สั้น ๆ) — ถ้าเป็นการเปลี่ยนแปลง architecture ใหญ่ ควรอธิบายด้วยคำพูดและปล่อยให้ author ไปออกแบบเอง ไม่ควรยัด suggestion ก้อนใหญ่ที่ทับความคิดของ author ทั้งหมด
- การ commit suggestion จะสร้าง commit ใหม่บน branch นั้นจริง ๆ (มักจะมีข้อความ commit ว่า `Apply suggestions from code review` หรือ `Update <filename>`) ซึ่งจะไปกระทบกับ local branch ของ author ถ้าเขากำลังทำงานอยู่ในเครื่องพร้อมกัน — author ต้อง `git pull` ดึง commit เหล่านี้ลงมาก่อนจะ push ต่อ ไม่งั้นจะเจอปัญหา diverge

## Step 216: การตอบกลับ Comment และ Resolve Conversation

Code Review ที่ดีมักไม่ใช่การคอมเมนต์ครั้งเดียวจบ แต่เป็น**บทสนทนา (conversation)** ไปมาระหว่าง reviewer กับ author จนกว่าทั้งสองฝ่ายจะเห็นตรงกัน

### 216.1 การตอบกลับคอมเมนต์ (Reply)

ทุกคอมเมนต์ inline จะมีกล่องข้อความเล็ก ๆ ต่อท้ายเสมอ เขียนว่า **"Reply..."** — ใครก็ตามที่เข้าถึง PR นี้ได้ (ทั้ง author, reviewer, หรือคนอื่นในทีมที่เข้ามาดู) สามารถพิมพ์คำตอบต่อท้าย thread นั้นได้ ทำให้เกิดเป็น **thread การสนทนา** อยู่ใต้บรรทัดโค้ดนั้นโดยเฉพาะ ไม่ปนกับคอมเมนต์อื่น

ตัวอย่างการสนทนาทั่วไป:

```
[Reviewer] ตรงนี้ถ้า array ว่างจะ throw error ไหมครับ

  [Author] อ๋อ จริงด้วย ผมลืมเช็ค ขอบคุณครับ เดี๋ยวแก้ให้

  [Author] แก้แล้วครับ เพิ่ม early return ถ้า array ว่าง ลองดูใน commit ล่าสุดครับ

  [Reviewer] โอเคครับ ใช้ได้แล้ว 👍
```

### 216.2 Resolve Conversation

เมื่อบทสนทนาในจุดใดจุดหนึ่งจบลงแล้ว (ปัญหาถูกแก้ไข หรือเข้าใจตรงกันแล้ว) จะมีปุ่ม **"Resolve conversation"** ปรากฏอยู่ที่มุมขวาบนของ thread นั้น

**ใครกดปุ่มนี้ได้บ้าง:**

- เจ้าของ Pull Request (author)
- ผู้ที่เขียนคอมเมนต์ต้นเรื่องนั้น (reviewer ที่เริ่ม thread)
- ใครก็ตามที่มีสิทธิ์ **write access** ต่อ repository นั้น (เช่น maintainer, collaborator)

คนที่ดู PR แบบมีสิทธิ์แค่ read เฉย ๆ (เช่นคนนอกทีมที่เข้ามาดู PR แบบ public) จะไม่เห็นปุ่มนี้

**ผลของการกด Resolve:**

- Thread นั้นจะถูก**ยุบ (collapse)** ลง แสดงเป็นแถบสีเทาสั้น ๆ เขียนว่า "X people had a conversation about this — Resolved" พร้อมเครื่องหมายถูก ✅
- ยังสามารถคลิกเพื่อขยายกลับมาดูเนื้อหาเดิมได้เสมอ ไม่ได้ถูกลบทิ้ง
- ถ้าจำเป็นสามารถกด **"Unresolve conversation"** เพื่อเปิด thread กลับมาคุยต่อได้เช่นกัน

### 216.3 การนับ Conversation ที่ยังไม่ Resolve

ที่ด้านบนของแท็บ "Files changed" (และในบางที่ของแท็บ Conversation) GitHub จะแสดงตัวนับ เช่น **"3 unresolved conversations"** พร้อมปุ่มให้กระโดดไปดู thread ที่ยังไม่ resolve ทีละอันได้เร็ว ๆ

### 216.4 Require Conversation Resolution (Branch Protection)

Repository สามารถตั้งค่า branch protection ให้เปิดออปชัน **"Require conversation resolution before merging"** ได้ — เมื่อเปิดใช้งาน ปุ่ม Merge จะถูก**บล็อกไว้จนกว่าทุก conversation ในหน้า Files changed จะถูก resolve ให้หมดก่อน** ไม่ว่าจะมาจาก reviewer ที่ approve แล้วหรือไม่ก็ตาม ทำให้มั่นใจได้ว่าไม่มีคำถามหรือประเด็นค้างคาก่อน merge

### 216.5 มารยาทของการ Resolve

โดยธรรมเนียมปฏิบัติที่นิยมในหลายทีม (ไม่ใช่กฎบังคับของ GitHub):

- **Author เป็นคนกด resolve เอง** หลังจากแก้ไขตามที่ถูกขอแล้ว ไม่ใช่ reviewer เป็นคนกด — เพราะ reviewer ควรเป็นคนตรวจสอบ**ก่อน**ว่าการแก้ไขนั้นถูกต้องแล้วจริง ๆ ก่อนจะปิด thread (ในทางปฏิบัติ ทีมจำนวนมากให้ reviewer เป็นคนกด resolve หลังตรวจดูโค้ดที่แก้แล้วว่าโอเค เพื่อยืนยันด้วยตัวเอง)
- ไม่ควร resolve thread ของตัวเองโดยไม่ตอบอะไรเลย เพราะ reviewer จะไม่รู้ว่าประเด็นนั้นถูกแก้ไขแล้วหรือถูกละเลยไปเฉย ๆ

## Step 217: Re-request Review หลังแก้ไขตามคำแนะนำแล้ว

หลังจาก author แก้ไขโค้ดตาม feedback และ push commit ใหม่ขึ้นไปที่ branch ของ PR แล้ว ขั้นตอนถัดไปที่มือใหม่มักลืมทำคือ **การแจ้งให้ reviewer กลับมาดูใหม่อย่างเป็นทางการ**

### 217.1 ทำไมต้อง Re-request

แค่ push commit ใหม่ขึ้นไป **ไม่ได้ทำให้ reviewer ได้รับการแจ้งเตือนอัตโนมัติเสมอไป** (ขึ้นกับการตั้งค่าการแจ้งเตือนส่วนตัวของแต่ละคน) และในหน้า PR เอง สถานะการรีวิวเดิมของ reviewer (เช่น "Request changes") จะยังค้างอยู่แบบเดิมจนกว่าจะมีการอัปเดตอย่างชัดเจน การกด re-request จะ:

- ส่ง notification ใหม่ไปยัง reviewer คนนั้นโดยตรง บอกว่า "มีคนขอให้คุณรีวิวอีกครั้ง"
- แสดงสถานะในหน้า PR ว่ากำลังรอการรีวิวรอบใหม่

### 217.2 วิธี Re-request Review

1. ไปที่แถบ **Reviewers** ด้านขวาของหน้า PR (จุดเดียวกับตอน request ครั้งแรกใน Step 212)
2. ถ้า reviewer คนนั้นได้ submit review ไปแล้ว (ไม่ว่าจะเป็น Approve, Request changes หรือ Comment) จะมี**ไอคอนลูกศรวนกลม (circular arrow / "re-request review")** ปรากฏขึ้นข้าง ๆ ชื่อของเขา
3. คลิกที่ไอคอนนั้น — ระบบจะส่งการแจ้งเตือนไปหา reviewer คนนั้นอีกครั้งว่ามีการเปลี่ยนแปลงใหม่ที่รอให้ตรวจสอบ
4. สถานะ badge ข้างชื่อ reviewer จะเปลี่ยนจาก ✅/❌ กลับเป็นสถานะ "รอ" (pending) อีกครั้ง

### 217.3 Dismiss Stale Pull Request Approvals

Repository สามารถตั้งค่า branch protection แบบ **"Dismiss stale pull request approvals when new commits are pushed"** ได้ — ถ้าเปิดใช้งานนี้ ทุกครั้งที่มี commit ใหม่ถูก push เข้า PR ที่เคยถูก approve ไปแล้ว **การ approve เดิมจะถูกยกเลิกอัตโนมัติทันที** เพื่อบังคับให้ reviewer ต้องกลับมาดูโค้ดเวอร์ชันล่าสุดใหม่อีกครั้งก่อนที่จะ merge ได้จริง ป้องกันปัญหาที่ author แอบเพิ่มโค้ดอื่นเข้ามาหลังจากได้รับการ approve ไปแล้ว

การตั้งค่านี้ทำให้การกด re-request review ยิ่งสำคัญมาก เพราะถ้าไม่กด reviewer อาจไม่รู้เลยว่ามีอะไรเปลี่ยนไปที่ต้องดูใหม่

### 217.4 ทางเลือกอื่นนอกจากปุ่ม Re-request

นอกจากไอคอน re-request ที่เป็นวิธีทางการ คุณยังสามารถ:

- คอมเมนต์ใน PR โดย mention ชื่อ reviewer ตรง ๆ เช่น `@somsri แก้ตามที่แนะนำแล้วครับ รบกวนดูอีกรอบ` — เป็นวิธีที่เป็นกันเองกว่าและให้บริบทเพิ่มเติมได้ (บอกว่าแก้อะไรไปบ้าง)
- ในทีมที่ใช้ Slack หรือเครื่องมือแชทอื่นเชื่อมกับ GitHub อาจมีการแจ้งเตือนอัตโนมัติเมื่อ PR ถูกอัปเดต

แนวทางที่ดีที่สุดคือ**ใช้ทั้งสองอย่างร่วมกัน**: กดปุ่ม re-request อย่างเป็นทางการ พร้อมคอมเมนต์สรุปสั้น ๆ ว่าคุณแก้อะไรไปบ้างตามที่ถูกขอ เพื่อให้ reviewer ไม่ต้องไล่ดู diff ทั้งหมดใหม่ตั้งแต่ต้น

## Step 218: มารยาทและเทคนิคการให้ Feedback ที่สร้างสรรค์

ทักษะทางเทคนิคของ GitHub (การ comment, approve, suggest) เรียนรู้ได้ไม่ยาก แต่ **ทักษะการสื่อสารระหว่างการรีวิว** ต่างหากที่แยกทีมที่ทำงานร่วมกันได้ดีออกจากทีมที่มีความขัดแย้งภายใน Step นี้จะพูดถึงมารยาทสำหรับทั้งสองฝั่ง

### 218.1 สำหรับฝั่ง Reviewer

**หลักการที่ 1: วิจารณ์โค้ด ไม่ใช่วิจารณ์คน**

ให้ความเห็นโดยพูดถึง "โค้ดนี้" หรือ "PR นี้" ไม่ใช่พูดถึง "คุณ" ในเชิงตัดสิน

| ไม่ควรพูด (โฟกัสที่คน) | ควรพูด (โฟกัสที่โค้ด) |
|---|---|
| "คุณเขียนโค้ดผิดตรงนี้" | "ตรงนี้โค้ดอาจมีปัญหาถ้า input เป็นค่าว่าง" |
| "ทำไมถึงเขียนแบบนี้" | "อยากทราบเหตุผลของแนวทางนี้ครับ มีข้อดีที่ผมอาจมองข้ามไปไหม" |
| "โค้ดนี้ห่วยมาก" | "ส่วนนี้ซับซ้อนไปหน่อย ลองแยกเป็นฟังก์ชันย่อยดูไหมครับ จะได้อ่านง่ายขึ้น" |

**หลักการที่ 2: อธิบาย "ทำไม" ไม่ใช่แค่ "ทำอะไร"**

คำสั่งเปล่า ๆ ไม่ช่วยให้ author เรียนรู้อะไร แต่การอธิบายเหตุผลจะช่วยให้เขาไม่ทำผิดซ้ำในอนาคต

| Feedback ที่ขาดเหตุผล | Feedback ที่มีเหตุผลประกอบ |
|---|---|
| "เปลี่ยนเป็น const" | "แนะนำใช้ `const` แทน `let` เพราะตัวแปรนี้ไม่ถูก reassign เลยหลังประกาศ ช่วยให้อ่านโค้ดแล้วมั่นใจได้ทันทีว่าค่ามันไม่เปลี่ยน" |
| "ใช้ early return" | "ถ้าใช้ early return ตรงนี้ จะลด nested if ลงได้ 2 ชั้น อ่านง่ายขึ้นเยอะครับ" |

**หลักการที่ 3: ตั้งคำถามแทนการออกคำสั่ง เมื่อยังไม่แน่ใจ**

ถ้าคุณไม่ได้มั่นใจ 100% ว่าวิธีของคุณดีกว่า ให้ตั้งคำถามเปิดแทนการยัดเยียดความเห็น:

- แทนที่จะพูดว่า "ต้องทำแบบนี้" ให้พูดว่า "ลองพิจารณาแบบนี้ดูไหมครับ" หรือ "มีเหตุผลอะไรไหมที่เลือกวิธีนี้แทน X"

**หลักการที่ 4: แยกระดับความสำคัญของ Comment ให้ชัดเจน**

หลายทีมมีธรรมเนียมใส่ prefix บอกระดับความสำคัญของแต่ละคอมเมนต์ เพื่อไม่ให้ author สับสนว่าอะไรต้องแก้จริง ๆ อะไรแค่ความเห็นเฉย ๆ เช่น:

| Prefix | ความหมาย |
|---|---|
| `nit:` (nitpick) | เรื่องเล็กน้อยมาก ไม่บล็อกการ merge จะแก้หรือไม่แก้ก็ได้ |
| `question:` | แค่สงสัย อยากรู้เหตุผล ไม่ได้บอกว่าต้องแก้ |
| `blocking:` หรือ `must:` | ต้องแก้ก่อน merge จริง ๆ |
| `suggestion:` | ข้อเสนอแนะ ลองพิจารณาดู แต่ไม่บังคับ |
| `praise:` | ชมส่วนที่ทำได้ดี |

ตัวอย่าง: `nit: ตัวแปรนี้ตั้งชื่อว่า data ทั่วไปไป ลองใช้ userList ไหมครับ จะสื่อความหมายชัดกว่า`

**หลักการที่ 5: ชมในสิ่งที่ทำได้ดีด้วย ไม่ใช่มีแต่จุดที่ต้องแก้**

การรีวิวที่มีแต่คำวิจารณ์ทำให้ author รู้สึกท้อ ลองแทรกคำชมเมื่อเจอโค้ดที่ออกแบบดี เช่น "วิธีจัดการ error ตรงนี้ฉลาดดีครับ อ่านง่ายกว่าที่ผมคิดไว้เยอะ" — สิ่งนี้ช่วยสร้างบรรยากาศเชิงบวกและทำให้ author เปิดใจรับ feedback จุดอื่นได้ง่ายขึ้น

**หลักการที่ 6: รีวิวให้ทันเวลา**

PR ที่ค้างรอรีวิวนานทำให้ author เสียจังหวะการทำงาน (ต้อง context-switch ไปทำงานอื่นระหว่างรอ) พยายามรีวิว PR ที่ถูกขอมาภายใน 1 วันทำการ ถ้าคาดว่าจะรีวิวช้ากว่านั้นควรแจ้ง author ล่วงหน้า

### 218.2 สำหรับฝั่ง Author (คนที่ถูกรีวิว)

**หลักการที่ 1: อย่าถือเป็นเรื่องส่วนตัว**

Feedback บนโค้ดไม่ใช่การตัดสินความสามารถของคุณในฐานะคน มันคือกระบวนการปกติที่ทุกคนต้องผ่าน แม้แต่ senior engineer ที่เก่งที่สุดก็ยังได้รับ feedback จากคนอื่นเสมอ

**หลักการที่ 2: ตอบทุกคอมเมนต์ อย่าเงียบ**

แม้แต่คอมเมนต์ที่คุณเห็นด้วยทันที ก็ควรตอบสั้น ๆ เช่น "แก้แล้วครับ" หรือ 👍 เพื่อให้ reviewer รู้ว่าคุณอ่านและรับทราบแล้ว การเงียบไปเฉย ๆ ทำให้ reviewer ไม่แน่ใจว่าประเด็นนั้นถูกจัดการหรือถูกมองข้าม

**หลักการที่ 3: ถ้าไม่เห็นด้วย ให้อธิบายเหตุผล ไม่ใช่ปฏิเสธเฉย ๆ**

| ไม่ควรพูด | ควรพูด |
|---|---|
| "ไม่จำเป็นครับ" | "ผมเลือกวิธีนี้เพราะ X ครับ แต่ถ้าคุณมองว่า Y สำคัญกว่า ผมยินดีปรับตามครับ" |
| "โค้ดเดิมก็โอเคอยู่แล้ว" | "อันนี้ตั้งใจทำแบบนี้เพราะต้องรองรับ edge case Z ด้วย ลองดู test case ด้านล่างประกอบครับ" |

**หลักการที่ 4: ขอบคุณ Reviewer**

การรีวิวใช้เวลาและความตั้งใจ การขอบคุณสั้น ๆ ท้าย PR หรือใน conversation ช่วยสร้างวัฒนธรรมการรีวิวที่ดีในทีมระยะยาว

**หลักการที่ 5: ทำให้ PR เล็กและรีวิวง่าย**

Author มีส่วนช่วยให้กระบวนการรีวิวราบรื่นได้เช่นกัน โดยการแบ่งงานเป็น PR ขนาดเล็ก ๆ ที่โฟกัสเรื่องเดียว (แทนที่จะยัดการเปลี่ยนแปลงหลายอย่างไว้ใน PR เดียวขนาดใหญ่) PR ที่เล็กจะได้รับการรีวิวที่ละเอียดและรวดเร็วกว่า PR ขนาดใหญ่ที่ reviewer มักจะเหนื่อยจนดูข้าม ๆ

### 218.3 ตารางเปรียบเทียบประโยคดี/ไม่ดี (สรุปรวม)

| สถานการณ์ | ประโยคที่ไม่ควรใช้ | ประโยคที่ควรใช้แทน |
|---|---|---|
| เจอ logic ผิด | "อันนี้ผิดชัดเจน" | "ผมทดสอบดูแล้ว ถ้า input เป็น 0 ฟังก์ชันนี้จะ return ค่าผิด ลองเช็คดูอีกทีไหมครับ" |
| เจอโค้ดซับซ้อน | "งงมาก อ่านไม่รู้เรื่อง" | "ส่วนนี้ผมตามไม่ค่อยทันครับ ช่วยอธิบายหรือแตกเป็นฟังก์ชันย่อยได้ไหม" |
| ไม่ชอบแนวทางการออกแบบ | "ทำแบบนี้ไม่ได้" | "แนวทางนี้อาจมีปัญหาเรื่อง scalability ในระยะยาว ลองดูแนวทาง X เป็นทางเลือกไหมครับ" |
| Author ตอบโต้เชิงลบ | "ก็บอกแล้วว่าไม่ต้องแก้" | "เข้าใจมุมมองของคุณครับ แต่ผมกังวลเรื่อง Y ลองคุยกันเพิ่มเติมได้ไหม" |
| รีวิวเสร็จ ไม่มีปัญหา | (เงียบ ไม่ comment อะไรเลย) | "โค้ดดูดีครับ ชอบวิธีจัดการ error ตรงนี้มาก Approve ครับ 👍" |

## Step 219: รู้จัก GitHub Copilot / AI Code Review เบื้องต้น

นอกจากการรีวิวโดยเพื่อนมนุษย์ในทีมแล้ว ปัจจุบัน GitHub ยังมีความสามารถให้ **AI เข้ามาช่วยรีวิวโค้ดเบื้องต้น** ก่อนที่จะส่งต่อให้เพื่อนร่วมทีมดูอีกที Step นี้จะแนะนำให้รู้จักแบบผิวเผิน เพื่อให้คุณรู้ว่ามันมีอยู่และทำงานคร่าว ๆ อย่างไร

### 219.1 การขอ Copilot Code Review

ในองค์กรที่มีสิทธิ์ใช้งาน GitHub Copilot (ต้องมี license ที่รองรับฟีเจอร์นี้) จะสามารถเพิ่ม **"Copilot"** เข้ามาเป็นหนึ่งใน reviewer ได้จากแถบ **Reviewers** เดียวกับที่ใช้ขอรีวิวจากคนจริงใน Step 212 — เพียงพิมพ์ค้นหาแล้วเลือก Copilot จากรายชื่อ

เมื่อถูก request แล้ว Copilot จะทำการวิเคราะห์ diff ของ PR นั้นโดยอัตโนมัติ แล้วทิ้งคอมเมนต์ inline ไว้ในตำแหน่งที่มันตรวจพบสิ่งที่น่าสนใจ เช่น:

- จุดที่อาจมีบั๊กหรือ edge case ที่ไม่ได้จัดการ
- โค้ดที่ไม่สอดคล้องกับรูปแบบส่วนที่เหลือของโปรเจกต์
- จุดที่อาจมีปัญหาด้านความปลอดภัยเบื้องต้น
- ข้อเสนอแนะเชิงสไตล์การเขียนโค้ด

### 219.2 ข้อจำกัดที่ควรรู้

- **Copilot ไม่ใช่ตัวแทนของการรีวิวโดยมนุษย์** — มันเป็นเครื่องมือช่วยกรองปัญหาเบื้องต้นก่อน เพื่อให้ reviewer ที่เป็นคนจริงไม่ต้องเสียเวลากับจุดเล็ก ๆ น้อย ๆ ที่ตรวจจับได้ง่าย และไปโฟกัสกับเรื่องที่ต้องใช้ดุลพินิจ เช่น การออกแบบสถาปัตยกรรม หรือความเหมาะสมเชิงธุรกิจ
- คอมเมนต์จาก Copilot อาจไม่ถูกต้องเสมอไป (false positive) — ทีมยังคงต้องใช้วิจารณญาณตัดสินใจเองว่าจะแก้ตามหรือไม่
- Copilot ไม่สามารถกด "Approve" ในความหมายที่ผูกกับ branch protection requirement แบบเดียวกับ human reviewer เสมอไปในทุกองค์กร — ควรตรวจสอบการตั้งค่าของ repository ตัวเองว่ารองรับอย่างไร
- ฟีเจอร์และรายละเอียดของ AI code review บน GitHub มีการพัฒนาเปลี่ยนแปลงอยู่ตลอดเวลา สิ่งสำคัญที่สุดคือเข้าใจ **แนวคิด** ว่ามันเป็นชั้นกรองเสริมก่อนถึงมือมนุษย์ ไม่ใช่ตัวแทนกระบวนการทั้งหมด

### 219.3 แนวทางการใช้งานที่เหมาะสม

แนวทางที่หลายทีมนิยมใช้ในทางปฏิบัติ:

1. Author เปิด PR แล้วปล่อยให้ Copilot รีวิวก่อนเป็นด่านแรก (บาง repository ตั้งค่าให้ทำงานอัตโนมัติทุก PR)
2. Author แก้ไขจุดที่ Copilot ชี้ให้เห็นชัดเจนว่าเป็นปัญหาจริง
3. หลังจากนั้นจึง request review จากเพื่อนร่วมทีมตามปกติ (Step 212) เพื่อรีวิวในมุมที่ต้องใช้บริบททางธุรกิจและประสบการณ์ ซึ่ง AI ยังทำได้ไม่ดีเท่ามนุษย์

ให้มองว่านี่คือเครื่องมือเสริมประสิทธิภาพ ไม่ใช่สิ่งทดแทนวัฒนธรรมการรีวิวที่ดีของทีมที่คุณเพิ่งเรียนไปใน Step 211-218

## Step 220: แบบฝึกหัด — สลับบทบาท Reviewer/Author รีวิว PR จริงอย่างน้อย 2 รอบ

ถึงเวลาลงมือปฏิบัติจริง แบบฝึกหัดนี้ออกแบบมาให้คุณได้สัมผัสทั้งสองฝั่งของ Code Review ด้วยตัวเอง

### 220.1 การเตรียมตัว

แบบฝึกหัดนี้ทำได้ดีที่สุดเมื่อทำงานคู่กับเพื่อนอีกคนหนึ่ง (pair) โดยทั้งสองคนมีสิทธิ์ collaborator ในrepository เดียวกัน (หรือทำงานผ่านการเปิด Pull Request ข้าม fork ก็ได้ตามที่เรียนมาใน Part ก่อนหน้า) ถ้าไม่มีเพื่อนร่วมฝึกในตอนนี้ ให้ใช้บัญชี GitHub สำรอง (second account) เพื่อจำลองบทบาท reviewer แยกจาก author เพราะ GitHub จะไม่อนุญาตให้ approve PR ของตัวเองด้วยบัญชีเดียวกัน

### 220.2 ขั้นตอนรอบที่ 1: คุณเป็น Author, เพื่อนเป็น Reviewer

1. สร้าง branch ใหม่ เช่น `feature/practice-review-1` จากโปรเจกต์ฝึกฝนที่คุณมีอยู่ (ใช้โฟลเดอร์ `git-course` ที่เตรียมไว้ตั้งแต่ Part 01)
2. เขียนโค้ดเล็ก ๆ ที่ตั้งใจ**ใส่จุดบกพร่องเล็กน้อยเข้าไปโดยตั้งใจ** เพื่อให้มีอะไรให้ reviewer จับได้จริง เช่น:
   - ฟังก์ชันที่ไม่ได้เช็ค null/undefined
   - ตัวแปรที่ตั้งชื่อไม่สื่อความหมาย (เช่น `x`, `data1`, `temp`)
   - โค้ดที่ทำซ้ำ (duplicate logic) ที่ควรแยกเป็นฟังก์ชัน
3. Commit และ push ขึ้น GitHub แล้วเปิด Pull Request ตามที่เรียนใน Part ก่อนหน้า
4. Request review จากเพื่อน (Step 212)
5. รอให้เพื่อนเข้ามา comment แบบ inline (Step 213) อย่างน้อย 2-3 จุด รวมถึงลองให้เขาใช้ **Suggested changes** อย่างน้อย 1 จุด (Step 215)
6. เพื่อนสรุป submit review เป็น **Request changes** (Step 214) เพราะมีจุดที่ต้องแก้จริง
7. คุณ (author) เข้ามาอ่านคอมเมนต์ทั้งหมด **ตอบกลับทุกคอมเมนต์** (Step 216) และลอง apply suggested change ที่ได้รับอย่างน้อย 1 จุด
8. แก้ไขส่วนที่เหลือด้วยตัวเอง commit และ push เพิ่ม
9. Resolve conversation ในจุดที่แก้ไขเสร็จแล้ว (Step 216)
10. กด **re-request review** ให้เพื่อน (Step 217) พร้อมคอมเมนต์สรุปว่าแก้อะไรไปบ้าง
11. เพื่อนกลับมาตรวจสอบอีกรอบ เห็นว่าแก้ครบแล้ว จึง submit review เป็น **Approve** (Step 214)
12. Merge Pull Request

### 220.3 ขั้นตอนรอบที่ 2: สลับบทบาท — เพื่อนเป็น Author, คุณเป็น Reviewer

ทำซ้ำกระบวนการเดียวกันทั้งหมดใน 220.2 แต่**สลับบทบาทกัน** โดยรอบนี้เพื่อนของคุณเป็นคนเปิด PR และคุณเป็นคนรีวิว ให้คุณฝึกใช้มารยาทการให้ feedback ที่สร้างสรรค์ตามที่เรียนใน Step 218 อย่างจริงจัง:

- ลองใช้ prefix `nit:`, `question:`, `blocking:` แยกระดับความสำคัญของคอมเมนต์แต่ละจุด
- ใส่คำชมอย่างน้อย 1 จุดในโค้ดที่เพื่อนทำได้ดี
- ลองใช้ suggested changes เสนอวิธีแก้ที่ชัดเจนอย่างน้อย 1 จุด แทนที่จะอธิบายเป็นคำพูดล้วน ๆ

### 220.4 เกณฑ์ตรวจสอบว่าคุณทำแบบฝึกหัดครบถ้วน

แบบฝึกหัดนี้ถือว่าสมบูรณ์เมื่อคุณ (ในบทบาทใดบทบาทหนึ่งอย่างน้อย) ได้ลงมือทำสิ่งต่อไปนี้ครบทุกข้อจากประสบการณ์จริง ไม่ใช่แค่อ่านผ่าน:

- [ ] Request review จากคนอื่นสำเร็จอย่างน้อย 2 ครั้ง
- [ ] คอมเมนต์แบบ inline บนบรรทัดโค้ดเฉพาะเจาะจง (ทั้งแบบบรรทัดเดียวและหลายบรรทัด) อย่างน้อย 1 ครั้ง
- [ ] ใช้ Suggested Changes และเห็นอีกฝั่งกด apply/commit suggestion จริง อย่างน้อย 1 ครั้ง
- [ ] ได้รับหรือให้ review state ครบทั้ง 3 แบบ (Comment, Approve, Request changes) อย่างน้อยแบบละ 1 ครั้งตลอดสองรอบ
- [ ] ตอบกลับ (reply) คอมเมนต์อย่างน้อย 3 ครั้ง
- [ ] Resolve conversation ด้วยตัวเองอย่างน้อย 2 ครั้ง
- [ ] กด re-request review อย่างน้อย 1 ครั้งหลังแก้ไขโค้ดตามคำแนะนำ
- [ ] Merge PR สำเร็จทั้งสองรอบ หลังผ่านกระบวนการรีวิวครบวงจร

### 220.5 คำถามทบทวนหลังทำแบบฝึกหัด

ลองตอบคำถามเหล่านี้เพื่อสะท้อนประสบการณ์ของตัวเอง:

1. ตอนเป็น reviewer คุณรู้สึกอย่างไรเมื่อต้องเขียนคอมเมนต์ที่ชี้ปัญหาในโค้ดของคนอื่น การใช้เทคนิคจาก Step 218 ช่วยให้เขียนได้ง่ายขึ้นไหม
2. ตอนเป็น author คุณรู้สึกอย่างไรเมื่อได้รับ Request changes การตอบกลับด้วยเหตุผลแทนการปฏิเสธเฉย ๆ ช่วยให้บทสนทนาไปในทิศทางที่ดีขึ้นไหม
3. Suggested Changes ช่วยประหยัดเวลาเมื่อเทียบกับการอธิบายด้วยคำพูดล้วน ๆ มากน้อยแค่ไหน
4. ถ้าทำงานในทีมจริงที่มีคนมากกว่า 2 คน คุณคิดว่าการตั้งค่า CODEOWNERS และ branch protection (Require approvals, Dismiss stale approvals, Require conversation resolution) จากที่เรียนไปจะช่วยทีมของคุณอย่างไรบ้าง

## สรุป Part 22

ใน Part นี้เราได้เรียนรู้ว่า:

1. Code Review สำคัญเพราะช่วยยกระดับคุณภาพโค้ด แชร์ความรู้ในทีม จับบั๊กก่อนถึง production และสร้างความรับผิดชอบร่วมกันของทีม
2. การ Request Review ทำผ่านแถบ Reviewers ด้านขวาของหน้า Pull Request และสามารถอาศัย CODEOWNERS ให้ระบบแนะนำ reviewer ที่เหมาะสมอัตโนมัติได้
3. การคอมเมนต์แบบ Inline ทำได้โดยคลิกเครื่องหมาย + ที่ปรากฏข้างเลขบรรทัดในแท็บ Files changed รองรับทั้งบรรทัดเดียวและหลายบรรทัดต่อเนื่อง
4. Review State มี 3 แบบคือ **Comment** (ความเห็นทั่วไป ไม่บล็อก), **Approve** (รับรองว่าพร้อม merge), และ **Request changes** (บล็อกการ merge จนกว่าจะแก้ไข)
5. **Suggested Changes** ให้ reviewer เสนอโค้ดที่แก้แล้วตรง ๆ ในคอมเมนต์ ให้ author หรือ collaborator กด apply/commit ได้ทันทีโดยไม่ต้องพิมพ์ใหม่ และรวมหลายจุดเป็น commit เดียวได้ด้วยฟีเจอร์ batch
6. การตอบกลับคอมเมนต์และ Resolve Conversation ช่วยติดตามว่าประเด็นไหนถูกจัดการแล้วบ้าง และสามารถบังคับผ่าน branch protection ด้วยออปชัน "Require conversation resolution before merging"
7. การ Re-request Review (ผ่านไอคอนลูกศรวนกลม) เป็นขั้นตอนสำคัญหลังแก้ไขโค้ดตาม feedback แล้ว โดยเฉพาะเมื่อ repository เปิดใช้ "Dismiss stale pull request approvals"
8. มารยาทการให้และรับ feedback ที่ดี คือการวิจารณ์โค้ดไม่ใช่วิจารณ์คน อธิบายเหตุผลเสมอ แยกระดับความสำคัญของคอมเมนต์ให้ชัดเจน และไม่ถือ feedback เป็นเรื่องส่วนตัว
9. GitHub Copilot สามารถถูกเพิ่มเป็น reviewer เพื่อช่วยตรวจจับปัญหาเบื้องต้นก่อน แต่ไม่ได้ทดแทนการรีวิวโดยมนุษย์ในทีม
10. แบบฝึกหัดสลับบทบาท reviewer/author ช่วยให้คุณเข้าใจกระบวนการ Code Review ทั้งวงจรจากทั้งสองมุมมอง ซึ่งเป็นทักษะที่ต้องฝึกฝนซ้ำ ๆ ในการทำงานจริงต่อไป
