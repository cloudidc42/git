## Step 271: GitHub Discussions คืออะไร ต่างจาก Issues อย่างไร

### 271.1 ที่มาของ Discussions

**GitHub Discussions** เปิดตัวอย่างเป็นทางการในปี 2020 (หลังจากทดสอบแบบ beta กับหลายโปรเจกต์ดัง เช่น React, Babel, Yarn) โดยมีเป้าหมายชัดเจนตั้งแต่ต้น:

> **สร้างพื้นที่สำหรับ "การสนทนาแบบเปิด" (open-ended conversation) ที่ไม่ผูกติดกับงานหรือบั๊กใด ๆ โดยเฉพาะ**

ก่อนที่จะมี Discussions ทีมโอเพนซอร์สจำนวนมากเจอปัญหาคล้ายกันมาก นั่นคือ **Issues ถูกใช้ผิดวัตถุประสงค์** คนจะเปิด Issue เพื่อ:

- ถามคำถามทั่วไปว่า "ใช้ยังไง"
- ขอบคุณ maintainer หรือชื่นชมโปรเจกต์
- เสนอไอเดียลอย ๆ ที่ยังไม่ชัดเจนว่าจะทำหรือไม่
- ถกเถียงเรื่องทิศทางของโปรเจกต์ในระยะยาว
- ประกาศข่าวสารให้ผู้ใช้ทราบ

สิ่งเหล่านี้ **ไม่ใช่งาน (task) ที่ต้องมีคนมา "ปิด" เมื่อเสร็จ** แต่ Issue tracker ถูกออกแบบมาให้ทุกอย่างจบด้วยสถานะ Open/Closed ทำให้เกิดความสับสนและ Issue tracker ของโปรเจกต์ดัง ๆ เต็มไปด้วยหัวข้อที่ไม่ใช่บั๊กจริง จนหา Issue ที่เป็นบั๊กจริง ๆ ยาก

### 271.2 หลักการแบ่งงานระหว่าง Issues กับ Discussions

| แง่มุม | Issues | Discussions |
|---|---|---|
| จุดประสงค์หลัก | ติดตามงาน บั๊ก และ feature request ที่ชัดเจนว่าต้องแก้/ทำ | พื้นที่พูดคุย ถามตอบ แลกเปลี่ยนความเห็น |
| มีสถานะ Open/Closed ไหม | มี (ต้องปิดเมื่อเสร็จงาน) | ไม่มีสถานะแบบเดียวกัน (ปิดได้แต่ความหมายต่างกัน คือ "ปิดการสนทนา" ไม่ใช่ "งานเสร็จ") |
| ต้องมีผลลัพธ์เป็นการเปลี่ยนแปลงโค้ดไหม | ส่วนใหญ่ใช่ (นำไปสู่ PR) | ไม่จำเป็น อาจจบแค่ได้ข้อสรุปหรือคำตอบ |
| รูปแบบการตอบ | Comment เรียงตามลำดับเวลา (linear thread) | รองรับทั้ง linear และ **threaded replies** (ตอบกลับเป็นกิ่งย่อยได้) |
| มี "คำตอบที่ถูกต้อง" ไหม | ไม่มีแนวคิดนี้ | มีใน category Q&A — mark comment เป็น "Answer" ได้ |
| เชื่อมกับ Project board / Milestone | เชื่อมได้โดยตรง | ไม่เชื่อมกับ Project board แบบ Issue (แต่ลิงก์อ้างอิงถึงกันได้) |
| เหมาะกับ | บั๊กที่ทำซ้ำได้, feature ที่นิยามชัดเจน, งานที่ต้อง assign ให้คนทำ | คำถามการใช้งาน, ไอเดียกว้าง ๆ, ประกาศ, พูดคุยทั่วไป, โพลสำรวจความเห็น |

### 271.3 ตัวอย่างการแยกแยะในสถานการณ์จริง

ลองดูตัวอย่างหัวข้อที่คนอาจโพสต์ในโปรเจกต์ open source แล้วลองแยกว่าควรไปที่ไหน:

| หัวข้อ | ควรอยู่ที่ | เหตุผล |
|---|---|---|
| "แอปพลิเคชันแครชเมื่อกดปุ่ม Save บน iOS 17" | Issue | มีขั้นตอนทำซ้ำได้ชัดเจน เป็นบั๊กที่ต้องแก้ |
| "จะเซ็ต environment variable ยังไงให้ตรงกับ production" | Discussion (Q&A) | เป็นคำถามการใช้งาน ไม่ใช่บั๊ก |
| "อยากให้เพิ่ม Dark Mode" | คลุมเครือ — เริ่มที่ Discussion (Ideas) ก่อน ถ้าทีมตกลงจะทำค่อยแปลงเป็น Issue | ไอเดียยังไม่ชัดว่าจะทำจริงหรือไม่ ควรถกกันก่อน |
| "ขอบคุณทีมงานที่ทำ library นี้ ใช้งานดีมาก" | Discussion (General) | ไม่ใช่งานที่ต้องทำอะไรต่อ |
| "ประกาศ release v2.0.0 พร้อม breaking changes" | Discussion (Announcements) | เป็นการสื่อสารทางเดียวถึงผู้ใช้ ไม่ใช่ task |
| "แชร์โปรเจกต์ที่สร้างโดยใช้ library นี้" | Discussion (Show and tell) | เป็นการอวดผลงาน ไม่ใช่บั๊กหรืองาน |
| "ทีมควรใช้ TypeScript เต็มรูปแบบไหมในเวอร์ชันหน้า" | Discussion (General หรือ Ideas) | เป็นการถกเถียงทิศทางระยะยาว ยังไม่ใช่ task ที่ทำได้ทันที |

### 271.4 ทำไม Discussions ถึงสำคัญต่อ Community

โปรเจกต์ open source ที่ประสบความสำเร็จระยะยาวมักไม่ได้อยู่ได้ด้วยโค้ดที่ดีอย่างเดียว แต่อยู่ได้ด้วย **ชุมชนที่แข็งแรง** Discussions ช่วยสร้างชุมชนได้เพราะ:

1. **ลดภาระ Issue tracker** — Maintainer แยกงานจริงออกจากการพูดคุยได้ชัดเจน ทำให้ Issue tracker สะอาดและโฟกัสกับงานจริง
2. **สร้างพื้นที่ปลอดภัยสำหรับมือใหม่ในการถาม** — คนที่ไม่แน่ใจว่าเรื่องที่จะถามเป็นบั๊กหรือไม่ สามารถถามใน Discussion ได้โดยไม่รู้สึกผิดที่ "เปิด Issue ผิดที่"
3. **เก็บความรู้แบบ searchable knowledge base** — คำถามใน Q&A ที่ถูก mark ว่าเป็น Answer แล้ว จะกลายเป็นฐานความรู้ที่คนอื่นค้นเจอผ่าน Google ได้ในอนาคต
4. **เปิดโอกาสให้ผู้ใช้ช่วยตอบกันเอง** — ไม่ต้องพึ่ง maintainer ตอบทุกคำถาม ชุมชนช่วยกันตอบได้ ลดภาระทีมหลัก
5. **ใช้สื่อสารทิศทางโปรเจกต์แบบโปร่งใส** — ประกาศ roadmap, breaking change, RFC (Request for Comments) ในที่เดียวที่ทุกคนติดตามได้

### 271.5 Discussions ใช้ได้กับ repo แบบไหนบ้าง

Discussions เปิดใช้งานได้ทั้งใน **public repository** และ **private repository** (สำหรับ private repo คนที่เห็น Discussions ได้ต้องมีสิทธิ์เข้าถึง repo นั้นอยู่แล้ว) ใช้ได้ทั้งบัญชี GitHub Free, Pro, Team และ Enterprise โดยไม่มีค่าใช้จ่ายเพิ่มเติม เพราะเป็นฟีเจอร์ที่รวมอยู่ในทุกแผนอยู่แล้ว

## Step 272: เปิดใช้งาน Discussions ใน repo settings

### 272.1 Discussions ไม่ได้เปิดเป็นค่าเริ่มต้น

ต่างจาก Issues ที่เปิดใช้งานอัตโนมัติเมื่อสร้าง repository ใหม่ **Discussions ต้องถูกเปิดใช้งานด้วยตัวเองทุกครั้ง** สำหรับแต่ละ repository เพราะ GitHub มองว่าไม่ใช่ทุกโปรเจกต์ที่ต้องการพื้นที่พูดคุยแบบนี้ (เช่น repo เล็ก ๆ ที่เป็นโปรเจกต์ทดลองส่วนตัว อาจไม่จำเป็นต้องมี)

### 272.2 ขั้นตอนการเปิดใช้งานทีละขั้น

1. ไปที่หน้า repository บน GitHub
2. คลิกแท็บ **Settings** (ต้องมีสิทธิ์ระดับ **Admin** ของ repository นั้น — ผู้ร่วมงานทั่วไปเปิดไม่ได้)
3. เลื่อนลงมาที่ส่วน **Features** ในหน้า General settings
4. หาช่องทำเครื่องหมาย **Discussions** แล้วคลิกติ๊กถูกเปิดใช้งาน

```
Settings → General → Features
┌────────────────────────────────────┐
│ ☑ Wikis                             │
│ ☑ Issues                            │
│ ☐ Discussions   ← ติ๊กตรงนี้เพื่อเปิดใช้งาน │
│ ☑ Projects                          │
│ ☑ Sponsorships                      │
└────────────────────────────────────┘
```

5. เมื่อติ๊กแล้ว ระบบจะขึ้นข้อความให้เลือก **"Set up discussions"** ทันที
6. กดปุ่ม **Set up discussions** GitHub จะพาไปที่หน้าตั้งค่าเริ่มต้น พร้อมสร้าง **welcome discussion** ให้อัตโนมัติ (เป็นโพสต์แนะนำสั้น ๆ ว่า Discussions คืออะไร)
7. เมื่อเสร็จแล้ว แท็บ **Discussions** จะปรากฏขึ้นบนแถบเมนูหลักของ repository ทันที เคียงข้างกับ Code, Issues, Pull requests, Actions, Projects, Wiki

### 272.3 สิ่งที่เกิดขึ้นทันทีหลังเปิดใช้งาน

เมื่อเปิดใช้งานครั้งแรก GitHub จะสร้าง Category เริ่มต้นให้อัตโนมัติ 5 หมวด (จะอธิบายละเอียดใน Step 273) และสร้างโพสต์ตัวอย่างในหมวด **Announcements** ชื่อประมาณ "Welcome to Discussions!" ซึ่ง maintainer สามารถแก้ไขหรือลบทิ้งได้ตามต้องการ

### 272.4 การปิดใช้งาน Discussions

หากต้องการปิดใช้งานภายหลัง (เช่น ย้ายไปใช้ช่องทางอื่น) ทำได้ที่หน้าเดียวกัน โดยไปที่ Settings → General → Features แล้วเอาเครื่องหมายถูกออกจาก Discussions

**ข้อควรระวังสำคัญ:** เมื่อปิดใช้งาน Discussions เนื้อหาทั้งหมดจะ **ไม่ถูกลบทันที** แต่จะถูกซ่อนไว้ ถ้าเปิดใช้งานใหม่อีกครั้งข้อมูลเก่าจะกลับมาแสดงตามเดิม อย่างไรก็ตาม หากปล่อยทิ้งไว้นานเกินไปโดยไม่มีการใช้งาน GitHub อาจมีนโยบายลบข้อมูลถาวรในบาง edge case จึงควร **backup หรือ export เนื้อหาสำคัญ** ก่อนปิดใช้งานถ้าเป็นไปได้ (เช่น ใช้ GitHub API หรือ GraphQL API ดึงข้อมูล Discussions ออกมาเก็บไว้)

### 272.5 สิทธิ์ที่เกี่ยวข้องกับ Discussions

| บทบาท | สร้างกระทู้ใหม่ | ตอบกระทู้ | Mark เป็น Answer | Pin/Lock/Delete/Transfer กระทู้ | เปิด/ปิดใช้งาน Discussions ทั้งระบบ |
|---|---|---|---|---|---|
| Read (ผู้อ่านทั่วไปที่มีสิทธิ์เข้า repo) | ได้ | ได้ | เฉพาะเจ้าของกระทู้หรือคนมีสิทธิ์เขียนขึ้นไป | ไม่ได้ | ไม่ได้ |
| Triage | ได้ | ได้ | ได้ | บางส่วน (ขึ้นกับสิทธิ์ที่ตั้งค่าไว้) | ไม่ได้ |
| Write | ได้ | ได้ | ได้ | ได้ (pin, lock) | ไม่ได้ |
| Maintain | ได้ | ได้ | ได้ | ได้ทั้งหมด | ไม่ได้ |
| Admin | ได้ | ได้ | ได้ | ได้ทั้งหมด | ได้ |

สำหรับ public repository คนทั่วไปที่ไม่ได้เป็นสมาชิกของ repo (ไม่มีสิทธิ์ระดับใดเลย) ก็สามารถ **สร้างกระทู้และตอบกระทู้ได้** ตราบใดที่มี GitHub account เพราะ Discussions ถูกออกแบบมาให้เป็นพื้นที่เปิดสำหรับ community ภายนอกโดยเฉพาะ ต่างจาก Issue ที่บาง repo อาจจำกัดสิทธิ์การเปิด Issue ไว้เฉพาะสมาชิก

## Step 273: Categories ของ Discussion และการสร้าง category เอง

### 273.1 Category คืออะไร

**Category** คือการจัดกลุ่มกระทู้ Discussion ตามลักษณะเนื้อหา คล้ายกับ **Label** ใน Issues แต่ต่างกันตรงที่:

- ทุกกระทู้ **ต้องมี** category เดียวเสมอ (ไม่เหมือน Label ที่ใส่ได้หลายอันหรือไม่ใส่เลยก็ได้)
- Category กำหนด **รูปแบบ (format)** ของกระทู้ในหมวดนั้นด้วย เช่น หมวด Q&A จะมีปุ่ม mark answer ให้อัตโนมัติ ส่วนหมวดอื่นจะไม่มี

### 273.2 Category เริ่มต้น 5 หมวดที่ GitHub สร้างให้อัตโนมัติ

เมื่อเปิดใช้งาน Discussions ครั้งแรก ระบบจะสร้าง category เริ่มต้นดังนี้:

| Category | ไอคอนเริ่มต้น | รูปแบบการสนทนา (Format) | ใช้ทำอะไร |
|---|---|---|---|
| **📣 Announcements** | Megaphone | Announcement (เฉพาะ maintainer ตอบ/สร้างกระทู้ได้ ผู้อื่นตอบกลับ comment ได้อย่างเดียว) | ประกาศข่าวสาร release, roadmap, การเปลี่ยนแปลงสำคัญ |
| **💡 Ideas** | Light bulb | Open-ended discussion | เสนอไอเดีย ฟีเจอร์ใหม่ที่ยังไม่ชัดเจนว่าจะทำ |
| **🙏 Q&A** | Praying hands | Question / Answer (มีปุ่ม mark เป็น answer) | ถามตอบปัญหาการใช้งาน |
| **🙌 Show and tell** | Raised hands | Open-ended discussion | อวดผลงานที่สร้างโดยใช้โปรเจกต์นี้ |
| **💬 General** | Speech bubble | Open-ended discussion | พูดคุยทั่วไปที่ไม่เข้าหมวดไหนเลย |

### 273.3 รูปแบบการสนทนา (Discussion Format) มี 3 แบบ

เวลาสร้างหรือแก้ไข category คุณต้องเลือก format หนึ่งในสามแบบนี้เสมอ:

1. **Open-ended discussion** — รูปแบบสนทนาทั่วไป ไม่มีแนวคิดเรื่อง "คำตอบที่ถูกต้อง" เหมาะกับ Ideas, General, Show and tell
2. **Question / Answer** — มีปุ่มให้เจ้าของกระทู้ (หรือ maintainer) กด **"Mark as answer"** บน comment ที่ตอบโจทย์ได้ถูกต้อง คำตอบที่ถูก mark จะถูกยกไปแสดงไว้ด้านบนสุดของกระทู้พร้อมสัญลักษณ์ติ๊กถูกสีเขียว เหมาะกับ Q&A
3. **Announcement** — จำกัดสิทธิ์การสร้างกระทู้ใหม่ไว้เฉพาะคนที่มีสิทธิ์ **Write ขึ้นไป** ส่วนคนทั่วไปตอบ (comment) ได้อย่างเดียวแต่สร้างกระทู้ใหม่ในหมวดนี้ไม่ได้ เหมาะกับ Announcements

### 273.4 การสร้าง Category ใหม่ด้วยตัวเอง

Maintainer ที่มีสิทธิ์ Write ขึ้นไปสามารถสร้าง category เพิ่มเติมได้ตามต้องการ ขั้นตอน:

1. ไปที่แท็บ **Discussions**
2. ที่แถบด้านซ้าย มองหาส่วน **Categories** แล้วคลิกไอคอนรูปฟันเฟือง (⚙️) หรือคำว่า **"Edit categories"**
3. คลิกปุ่ม **New category**
4. กรอกข้อมูล:
   - **Emoji** — เลือกไอคอนที่สื่อความหมาย
   - **Title** — ชื่อ category เช่น "Roadmap", "Help wanted", "Feedback"
   - **Description** — คำอธิบายสั้น ๆ ว่า category นี้ใช้ทำอะไร (จะแสดงให้ผู้ใช้เห็นตอนเลือก category ก่อนโพสต์)
   - **Format** — เลือกหนึ่งใน 3 แบบข้างต้น
5. กดปุ่ม **Save category**

ตัวอย่าง category ที่โปรเจกต์ขนาดใหญ่มักสร้างเพิ่มเติม:

| Category ที่สร้างเพิ่ม | Format ที่ใช้ | เหตุผล |
|---|---|---|
| **Roadmap / RFC** | Open-ended discussion | ใช้ถกทิศทางระยะยาวและ Request for Comments แยกจาก Ideas ทั่วไป |
| **Help / Support** | Question / Answer | แยกจาก Q&A ทั่วไปเมื่อโปรเจกต์มีคำถามด้าน support จำนวนมาก |
| **Show your setup** | Open-ended discussion | เฉพาะโปรเจกต์ที่เกี่ยวกับ dotfiles, config, theme ให้คนโชว์การตั้งค่า |
| **Polls** | Open-ended discussion | ใช้รวมกระทู้ที่เป็นโพลสำรวจความเห็นไว้ที่เดียว |

### 273.5 การแก้ไขและลบ Category

- **แก้ไข** — คลิกไอคอนดินสอข้าง category นั้นในหน้า Edit categories เปลี่ยน emoji, ชื่อ, คำอธิบาย หรือ format ได้ตลอดเวลา
- **ลบ** — คลิกไอคอนถังขยะ แต่ **ลบได้เฉพาะเมื่อไม่มีกระทู้เหลืออยู่ในหมวดนั้น หรือระบบจะถามให้ย้ายกระทู้ทั้งหมดไปหมวดอื่นก่อน** จึงจะลบ category เดิมได้จริง
- Category เริ่มต้นบางหมวด (เช่น General) **ลบไม่ได้ถ้าเป็น category สุดท้ายที่เหลืออยู่** เพราะระบบต้องมีอย่างน้อย 1 category เสมอ

### 273.6 การจัดลำดับ Category

สามารถลากเพื่อจัดลำดับการแสดงผลของ category ในหน้า Edit categories ได้ ลำดับนี้จะมีผลต่อการแสดงผลใน dropdown ตอนเลือก category และในแถบด้านซ้ายของหน้า Discussions หลัก แนะนำให้จัดลำดับตามความสำคัญ เช่น ให้ Announcements และ Q&A อยู่บนสุดเพราะเป็นหมวดที่คนเข้าบ่อยที่สุด

## Step 274: การตั้งคำถามใน Q&A category และการ mark comment เป็น "Answer"

### 274.1 การสร้างกระทู้ใหม่ในหมวด Q&A

ขั้นตอนตั้งคำถามใหม่:

1. ไปที่แท็บ **Discussions** ของ repository
2. คลิกปุ่ม **New discussion** มุมขวาบน
3. เลือก category **Q&A** จากรายการ category ที่แสดงเป็นการ์ดให้เลือก
4. กรอก **Title** — ควรตั้งชื่อให้กระชับและสื่อถึงปัญหาชัดเจน เช่น "วิธี config custom domain กับ GitHub Pages ทำยังไง" (หลีกเลี่ยงชื่อกำกวมเช่น "ช่วยด้วย" หรือ "มีปัญหา")
5. กรอกเนื้อหาในกล่องข้อความ รองรับ **Markdown เต็มรูปแบบ** เหมือน Issue comment — ใส่ code block, รูปภาพ, ลิงก์, checklist ได้ทั้งหมด
6. กดปุ่ม **Start discussion**

### 274.2 โครงสร้างที่ดีของคำถามใน Q&A

คำถามที่ดีควรมีองค์ประกอบครบถ้วนเพื่อให้คนอื่นตอบได้ง่ายและตรงจุด:

```markdown
## สิ่งที่พยายามทำ
กำลังพยายาม deploy โปรเจกต์ Next.js ไปที่ GitHub Pages

## สิ่งที่ลองแล้ว
```bash
npm run build
npm run export
```

## Error ที่เจอ
```
Error: Cannot find module 'next/dist/...'
```

## Environment
- Node.js: v20.10.0
- Next.js: 14.0.4
- OS: macOS 14
```

รูปแบบนี้คล้ายกับการเขียน Bug report ที่ดี (ซึ่งเราเคยพูดถึงหลักการ minimal reproducible example มาก่อนแล้วในหลักสูตรตอน Issue) เพราะ Q&A ที่ดีก็ต้องการข้อมูลบริบทครบถ้วนเช่นกัน

### 274.3 การตอบและการ "Mark as answer"

เมื่อมีคนมาตอบคำถามในกระทู้ (เขียน reply ที่ช่องด้านล่าง) จะปรากฏปุ่มเล็ก ๆ ข้าง comment นั้นชื่อ **"Mark as answer"**

**ใครกดปุ่มนี้ได้บ้าง:**

- **เจ้าของกระทู้ (ผู้ถามเอง)** กดได้เสมอ
- **Maintainer ที่มีสิทธิ์ Write ขึ้นไปของ repo** กดได้เช่นกัน แม้จะไม่ใช่คนตั้งคำถาม (เผื่อกรณีเจ้าของกระทู้หายไปไม่กลับมา mark เอง)

**ผลลัพธ์เมื่อ mark แล้ว:**

1. Comment ที่ถูก mark จะถูก **คัดลอกขึ้นไปแสดงที่ด้านบนสุดของกระทู้** พร้อมป้าย **"Answer"** สีเขียวและเครื่องหมายติ๊กถูก ทำให้คนที่เข้ามาอ่านทีหลังเห็นคำตอบได้ทันทีโดยไม่ต้องไล่อ่านทั้งกระทู้
2. กระทู้จะได้ไอคอนรูปติ๊กถูกสีเขียวแสดงในรายการ Discussions หน้าหลัก บ่งบอกว่ากระทู้นี้ "มีคำตอบแล้ว" ช่วยให้คนอื่นกรองดูได้ง่ายว่ากระทู้ไหนยังไม่มีคำตอบ ควรเข้ามาช่วยตอบ
3. **ยกเลิกการ mark ได้ตลอดเวลา** โดยกดปุ่ม "Unmark as answer" ที่ comment นั้น ถ้าพบว่าคำตอบไม่ถูกต้องหรือมีคำตอบที่ดีกว่า

### 274.4 การกรองกระทู้ Q&A ตามสถานะคำตอบ

ที่แถบด้านซ้ายของหน้า Discussions มีตัวกรอง (filter) ให้เลือกดูเฉพาะ:

- **Unanswered** — กระทู้ Q&A ที่ยังไม่มีใคร mark คำตอบ (มีประโยชน์มากสำหรับ maintainer ที่ต้องการไล่ดูว่ามีคำถามค้างอยู่กี่กระทู้ที่ต้องช่วยตอบ)
- **Answered** — กระทู้ที่ mark คำตอบแล้ว

คำสั่งค้นหาแบบพิมพ์เองก็ทำได้เช่นกัน เช่น:

```
is:open is:unanswered category:"Q&A"
```

จะกรองเฉพาะกระทู้ Q&A ที่ยังไม่มีคำตอบและยังเปิดอยู่

### 274.5 Q&A กับการสร้าง Knowledge Base

จุดแข็งที่สุดของ Q&A คือมันกลายเป็น **ฐานความรู้ที่ค้นหาได้ (searchable knowledge base)** ในระยะยาว เพราะ:

- Google และ search engine อื่น ๆ จะ index หน้า Discussions ที่เป็น public ทำให้คนค้นหาปัญหาผ่าน Google เจอคำตอบได้โดยตรง โดยไม่ต้องเข้ามาถามซ้ำ
- Maintainer สามารถ **pin กระทู้ Q&A ที่ถูกถามบ่อยที่สุด** ไว้ด้านบนสุด (คล้ายกับการทำ FAQ)
- เมื่อเจอคำถามซ้ำ maintainer สามารถตอบโดยแปะลิงก์ไปยังกระทู้เก่าที่ mark answer ไว้แล้ว แทนที่จะพิมพ์คำตอบใหม่ทุกครั้ง ประหยัดเวลาได้มาก

## Step 275: Polls ใน Discussions — สร้างโพลสำรวจความเห็น

### 275.1 Poll คืออะไร

**Poll** เป็นฟีเจอร์ที่ให้เจ้าของกระทู้ Discussion แนบ **แบบสำรวจความเห็นแบบเลือกตอบ (multiple-choice)** เข้าไปในกระทู้ได้โดยตรง โดยไม่ต้องพึ่งเครื่องมือภายนอกอย่าง Google Forms หรือให้คนตอบด้วยการ react อีโมจิแบบเดา ๆ กันเอง

Poll ใช้ได้กับกระทู้ Discussion ใน **category ที่เป็น format แบบ Open-ended discussion** เท่านั้น (ใช้กับ Q&A หรือ Announcement format ไม่ได้)

### 275.2 วิธีสร้าง Poll

1. ไปที่หน้า **New discussion** ตามปกติ
2. เลือก category ที่เป็น Open-ended discussion (เช่น General, Ideas)
3. มองหาแท็บเล็ก ๆ ด้านบนกล่องเขียนเนื้อหา จะเห็นสองแท็บคือ **"Write"** และ **"Poll"**
4. คลิกแท็บ **Poll**
5. กรอกข้อมูล:
   - **Question** — คำถามหลักของโพล เช่น "อยากให้ทีมโฟกัสฟีเจอร์ไหนก่อนใน Q3?"
   - **Options** — ตัวเลือกคำตอบ (ใส่ได้ตั้งแต่ 2 ถึง 8 ตัวเลือก) เช่น "Dark Mode", "Offline Support", "Plugin System", "Performance Improvement"
6. กดปุ่ม **Start discussion** เพื่อโพสต์กระทู้พร้อมโพล

### 275.3 การโหวตและดูผล

- ผู้ใช้แต่ละคนโหวตได้ **1 เสียงต่อโพล** (เลือกได้แค่ 1 ตัวเลือกเท่านั้น ไม่รองรับ multiple selection)
- เมื่อโหวตแล้ว ระบบจะแสดง **แถบเปอร์เซ็นต์ (progress bar)** ของแต่ละตัวเลือกให้เห็นทันที พร้อมจำนวนโหวตรวม
- **เปลี่ยนใจโหวตใหม่ได้** ตราบใดที่โพลยังไม่ปิด — กดเลือกตัวเลือกอื่นแทนที่ได้ตลอดเวลา
- โพลของ GitHub **ไม่มีวันหมดอายุอัตโนมัติ** — โพลจะเปิดรับโหวตต่อไปเรื่อย ๆ จนกว่า maintainer จะ **Lock conversation** (ดู Step 278.2) เพื่อหยุดรับโหวต ถ้าต้องการให้โพลมีกำหนดเวลาปิดชัดเจน ต้องระบุไว้ในเนื้อหากระทู้เอง แล้วมา lock ด้วยมือเมื่อถึงกำหนด

### 275.4 การใช้งาน Poll อย่างมีประสิทธิภาพในทีม

ตัวอย่างสถานการณ์ที่ Poll ถูกใช้บ่อยในโปรเจกต์จริง:

1. **สำรวจ priority ของ roadmap** — ถามชุมชนว่าอยากให้ทำฟีเจอร์ไหนก่อน แล้วใช้ผลโหวตประกอบการตัดสินใจวางแผน
2. **สำรวจ breaking change** — ก่อนจะปล่อยเวอร์ชันที่มี breaking change ถามว่าผู้ใช้ส่วนใหญ่พร้อมย้ายเมื่อไหร่ (เช่น "ควร drop support Node.js 16 เมื่อไหร่")
3. **สำรวจรูปแบบ documentation** — ถามว่าอยากได้เอกสารแบบวิดีโอหรือแบบข้อความมากกว่า
4. **สำรวจความพึงพอใจ** — ถามความรู้สึกโดยรวมต่อ release ล่าสุด

### 275.5 ข้อจำกัดที่ต้องรู้

- Poll **ไม่สามารถเพิ่มเข้าไปในกระทู้ที่สร้างไปแล้ว** — ต้องเลือกใส่ Poll ตั้งแต่ตอนสร้างกระทู้ครั้งแรกเท่านั้น (แก้ไข option ของโพลภายหลังทำได้บ้างแต่จำกัด)
- ผลโหวตเป็นแบบ **เปิดเผยต่อสาธารณะ** ใครก็ตามที่เข้าถึงกระทู้ได้ก็เห็นผลโหวตได้ (ไม่มีโหมด anonymous poll)
- Poll ไม่สามารถใช้แทนการตัดสินใจอย่างเป็นทางการของทีม (governance vote) ได้ — มันเป็นเพียงเครื่องมือสำรวจความเห็นเพื่อประกอบการตัดสินใจ ไม่ใช่ระบบโหวตที่มีผลผูกมัดทางกฎหมายหรือกฎบัตรของโปรเจกต์

## Step 276: การย้าย Issue เป็น Discussion และแปลงกลับ

### 276.1 ทำไมต้องมีการแปลงไปมา

เพราะในทางปฏิบัติ คนเปิด Issue กับ Discussion ผิดที่กันอยู่เสมอ (แม้จะมีคำอธิบายชัดเจนใน Step 271 ก็ตาม) GitHub จึงออกแบบให้ maintainer **แปลงข้ามได้ในภายหลัง** โดยไม่ต้องให้ผู้ใช้ไปโพสต์ใหม่เอง

### 276.2 การแปลง Issue เป็น Discussion

ขั้นตอน:

1. เปิด Issue ที่ต้องการแปลง
2. ที่แถบด้านขวาของหน้า Issue เลื่อนหาส่วน **"Convert to discussion"** (อยู่ใกล้กับปุ่ม Close issue หรือใน dropdown เมนู ⋯ ที่มุมบนขวา)
3. คลิก **Convert to discussion**
4. เลือก **Category** ที่ต้องการให้ Discussion ใหม่ไปอยู่ (เช่น Q&A, Ideas)
5. ยืนยันการแปลง

**สิ่งที่เกิดขึ้นหลังแปลง:**

- Issue เดิม **จะถูกปิด (closed) โดยอัตโนมัติ** และไม่สามารถเปิดกลับมาเป็น Issue เดิมได้อีก
- เนื้อหา title, body, และ **comment ทั้งหมด** จะถูกย้ายไปเป็น Discussion ใหม่ครบถ้วน (comment จะกลายเป็น reply ใน Discussion)
- ที่ตำแหน่งเดิมของ Issue จะขึ้นข้อความอ้างอิงว่า "This issue was converted to a discussion" พร้อมลิงก์ไปยัง Discussion ใหม่ ทำให้คนที่เข้ามาดู Issue เก่าจากลิงก์ค้างไม่หลงทาง
- **Label, Assignee, Milestone, Project board ที่เคยผูกกับ Issue จะหายไป** เพราะ Discussion ไม่มีแนวคิดเหล่านี้ — ควรบันทึกข้อมูลสำคัญเหล่านี้ไว้ก่อนแปลงถ้าจำเป็นต้องใช้อ้างอิงภายหลัง
- **หมายเลข Issue เดิมจะไม่ถูกนำมาใช้ซ้ำ** และ Discussion ใหม่จะได้เลขที่ของตัวเองในชุดหมายเลขของ Discussions (Issues และ Discussions ใช้ชุดหมายเลขคนละชุดกัน)

### 276.3 ใครแปลง Issue เป็น Discussion ได้บ้าง

ต้องมีสิทธิ์ระดับ **Write** ขึ้นไปของ repository เท่านั้น ผู้เปิด Issue เองที่ไม่มีสิทธิ์เขียน (เช่น ผู้ใช้ภายนอกทั่วไป) **แปลงเองไม่ได้** ต้องรอให้ maintainer แปลงให้

นอกจากแปลงทีละอันแล้ว ยังสามารถ **แปลงหลาย Issue พร้อมกัน (bulk convert)** ได้จากหน้ารายการ Issues โดยติ๊กเลือก Issue หลายอัน แล้วใช้เมนู bulk action เลือก "Convert to discussion"

### 276.4 การแปลงกลับจาก Discussion เป็น Issue

ในทิศทางกลับกัน หากพบว่ากระทู้ Discussion จริง ๆ แล้วเป็นบั๊กที่ต้องแก้ไข ก็สามารถแปลงกลับเป็น Issue ได้เช่นกัน:

1. เปิด Discussion ที่ต้องการแปลง
2. ที่เมนู ⋯ มุมบนขวาของกระทู้ เลือก **"Convert to issue"**

   (ในบางเวอร์ชันของ UI อาจปรากฏเป็นตัวเลือก **"Create issue from discussion"** หรือปุ่มลักษณะคล้ายกันในแถบด้านข้าง)
3. เลือก repository ปลายทาง (สามารถแปลงข้ามไปสร้างเป็น Issue ใน repository อื่นได้ด้วย ไม่จำเป็นต้องเป็น repo เดียวกัน — มีประโยชน์เมื่อมี monorepo แยกเป็นหลาย repo ย่อย)
4. ยืนยันการสร้าง

**ข้อแตกต่างสำคัญ:** การแปลง Discussion → Issue นี้ **ไม่ได้ลบหรือปิด Discussion เดิม** — Discussion เดิมจะยังคงอยู่ตามปกติ เพียงแค่มี Issue ใหม่ถูกสร้างขึ้นแยกต่างหาก **พร้อมลิงก์อ้างอิงกลับไปกลับมาระหว่างกัน** ต่างจากทิศทาง Issue → Discussion ที่ Issue เดิมจะถูกปิดถาวร

### 276.5 ตารางสรุปทิศทางการแปลง

| ทิศทาง | Issue เดิม/Discussion เดิมเป็นอย่างไรหลังแปลง | ข้อมูลที่ย้ายไปด้วย | ข้อมูลที่หายไป |
|---|---|---|---|
| Issue → Discussion | Issue ถูกปิดถาวร มีลิงก์ไปยัง Discussion ใหม่ | title, body, comments ทั้งหมด | label, assignee, milestone, project board |
| Discussion → Issue | Discussion ยังอยู่ตามปกติ ไม่ถูกปิด | title, body (comment ไม่ได้ย้ายอัตโนมัติทั้งหมดเหมือนทิศทางแรก) | — (ไม่มีข้อมูลอะไรหายเพราะต้นทางยังอยู่) |

### 276.6 แนวทางปฏิบัติที่แนะนำ

- **ตั้งกฎในโปรเจกต์ให้ชัดเจน** เช่น เขียนไว้ใน `CONTRIBUTING.md` หรือ Issue template ว่า "ถ้าไม่แน่ใจว่าเป็นบั๊กหรือคำถาม ให้เริ่มที่ Discussions ก่อน"
- **แปลงทันทีเมื่อเห็นว่าผิดที่** อย่าปล่อยให้ Issue tracker เต็มไปด้วยคำถามทั่วไป เพราะจะทำให้ maintainer คนอื่นหรือ contributor ใหม่สับสนว่าอะไรคืองานจริงที่ต้องทำ
- **ใช้ Issue template + Discussion link ประกอบกัน** — ตั้งค่า Issue template ให้มีลิงก์ไปยัง Discussions Q&A เป็นตัวเลือกแรกก่อนเปิด Issue ใหม่เสมอ (จะพูดถึงรายละเอียด Issue template config ใน Part ที่ว่าด้วย Issue Templates)

## Step 277: การใช้ Discussions สร้าง community สำหรับโปรเจกต์ Open Source

### 277.1 Discussions ไม่ใช่แค่ฟีเจอร์ แต่เป็นกลยุทธ์สร้างชุมชน

โปรเจกต์ open source ที่มีชุมชนแข็งแรง เช่น React, Vite, Tailwind CSS ใช้ Discussions เป็นศูนย์กลางของการมีปฏิสัมพันธ์กับผู้ใช้ ไม่ใช่แค่ที่ทิ้งขยะของคำถามที่ไม่เข้า Issue การจะทำให้ Discussions มีชีวิตชีวาต้องอาศัยการวางระบบตั้งแต่ต้น

### 277.2 การสร้าง Pinned Welcome Post

**Pinned Welcome Post** คือกระทู้แรกที่ maintainer ควรสร้างทันทีหลังเปิดใช้งาน Discussions เพื่อทักทายและวางกฎเกณฑ์ ควรมีเนื้อหาประมาณนี้:

```markdown
# ยินดีต้อนรับสู่ Discussions ของ [ชื่อโปรเจกต์]!

พื้นที่นี้สร้างขึ้นสำหรับการพูดคุย ถามตอบ และแลกเปลี่ยนความคิดเห็น
เกี่ยวกับ [ชื่อโปรเจกต์] โดยเฉพาะ — แยกต่างหากจาก Issue tracker
ที่ใช้ติดตามบั๊กและงานพัฒนาเท่านั้น

## หมวดหมู่ที่มีให้ใช้งาน

- 🙏 **Q&A** — ถามคำถามเกี่ยวกับการใช้งาน การติดตั้ง หรือปัญหาที่เจอ
- 💡 **Ideas** — เสนอไอเดียฟีเจอร์ใหม่ที่อยากให้มี
- 📣 **Announcements** — ติดตามข่าวสาร release และการเปลี่ยนแปลงสำคัญ
- 🙌 **Show and tell** — โชว์ผลงานที่คุณสร้างโดยใช้โปรเจกต์นี้
- 💬 **General** — พูดคุยเรื่องทั่วไปที่ไม่เข้าหมวดไหน

## กติกาการพูดคุย

1. ให้เกียรติซึ่งกันและกัน อ่าน [Code of Conduct](./CODE_OF_CONDUCT.md) ก่อนโพสต์
2. ค้นหาก่อนโพสต์ว่ามีคำถามคล้ายกันถูกถามไปแล้วหรือยัง
3. ตั้งชื่อกระทู้ให้ชัดเจนและอธิบายบริบทให้ครบถ้วน
4. หากเจอบั๊กที่ทำซ้ำได้ ให้เปิดเป็น Issue แทน ไม่ใช่ Discussion

ขอบคุณที่เป็นส่วนหนึ่งของชุมชนนี้!
```

หลังสร้างกระทู้นี้แล้ว ให้ **Pin** ไว้ที่หมวด Announcements ทันที (วิธี pin จะอธิบายใน Step 278) เพื่อให้เป็นกระทู้แรกที่คนใหม่เห็นเสมอ

### 277.3 การวาง Guidelines ให้ชัดเจน

นอกจาก welcome post แล้ว ควรมีการอ้างอิงกฎการพูดคุยไว้ในหลายจุดเพื่อให้คนเห็นง่าย:

- แปะลิงก์ guideline ไว้ใน **README.md** ของ repo ในส่วน "Community" หรือ "Getting Help"
- ใช้ **Discussion category description** อธิบายกฎเฉพาะของแต่ละหมวด เช่น ในคำอธิบาย category "Show and tell" เขียนว่า "โปรดใส่ screenshot หรือ demo link ประกอบทุกครั้ง"
- อ้างอิงถึง `CODE_OF_CONDUCT.md` ให้ชัดเจนว่ากฎเดียวกับที่ใช้กับ Issue/PR ก็ใช้กับ Discussions ด้วย

### 277.4 บทบาทของ Maintainer ในการดูแล Community

Maintainer ที่ดูแล Discussions อย่างมีประสิทธิภาพมักทำสิ่งเหล่านี้เป็นประจำ:

1. **ตอบกระทู้ Unanswered ใน Q&A ให้เร็วที่สุดเท่าที่ทำได้** อย่างน้อยควรมีการตอบรับเบื้องต้น (acknowledge) แม้จะยังไม่มีคำตอบสมบูรณ์ เช่น "ขอบคุณที่ถาม เดี๋ยวจะไปตรวจสอบให้"
2. **Mark คำตอบที่ถูกต้องอย่างสม่ำเสมอ** เพื่อให้ knowledge base สมบูรณ์ ไม่ปล่อยกระทู้ที่มีคำตอบดีอยู่แล้วแต่ไม่ได้ mark ทิ้งไว้
3. **ดึงกระทู้ Ideas ที่ได้รับการสนับสนุนมาก (upvote สูง) ไปพิจารณาทำจริง** และรายงานความคืบหน้ากลับไปในกระทู้เดิม เพื่อให้ชุมชนเห็นว่าเสียงของพวกเขามีความหมาย
4. **สร้างกระทู้ Announcement ทุกครั้งที่มี release ใหม่** พร้อมสรุป highlight และ breaking changes
5. **ต้อนรับ contributor หน้าใหม่** ในกระทู้ Show and tell เช่น กดหัวใจ ทิ้งคอมเมนต์ชื่นชม สร้างบรรยากาศเป็นมิตร

### 277.5 การใช้ Reactions เพื่อวัด Priority

ทุกกระทู้และทุก comment ใน Discussions รองรับ **emoji reactions** เหมือนใน Issue/PR (👍 👎 😄 🎉 😕 ❤️ 🚀 👀) Maintainer สามารถใช้จำนวน 👍 ในกระทู้ Ideas เป็นตัวชี้วัดคร่าว ๆ ว่าฟีเจอร์ไหนที่ชุมชนต้องการมากที่สุด แล้วนำไปประกอบการวางแผน roadmap ร่วมกับผลจาก Poll (Step 275)

### 277.6 ตัวอย่างโปรเจกต์จริงที่ใช้ Discussions อย่างได้ผล

- **Next.js** — ใช้ Discussions เป็นหลักสำหรับ Q&A การใช้งานทั้งหมด แทบไม่มีคำถามการใช้งานหลุดเข้าไปปนใน Issue tracker เลย
- **Vite** — มีหมวด Discussion แยกสำหรับ RFC (Request for Comments) ที่ใช้ถกทิศทางสถาปัตยกรรมสำคัญก่อนตัดสินใจ
- **GitHub เอง (community/community repo)** — ใช้ Discussions เป็นพื้นที่ให้ผู้ใช้ GitHub เสนอ feedback เกี่ยวกับผลิตภัณฑ์ GitHub เอง

การศึกษาว่าโปรเจกต์เหล่านี้จัด category และตั้งกฎอย่างไรเป็นตัวอย่างที่ดีในการวางระบบ Discussions ของโปรเจกต์ตัวเอง

## Step 278: Moderation tools (pin, lock, delete, transfer, hide comment)

Discussions มีเครื่องมือ moderation ครบชุดสำหรับ maintainer ในการดูแลคุณภาพของการสนทนา มาดูทีละเครื่องมือ

### 278.1 Pin discussion

**Pin** คือการปักหมุดกระทู้ให้แสดงอยู่บนสุดของหมวด category นั้นเสมอ ไม่ว่าจะมีกระทู้ใหม่เข้ามากี่กระทู้ก็ตาม

**วิธีทำ:** เปิดกระทู้ที่ต้องการ → คลิกเมนู ⋯ มุมบนขวา → เลือก **"Pin discussion"**

**ข้อจำกัด:** pin ได้สูงสุด **3 กระทู้ต่อ category** เท่านั้น หากต้องการ pin กระทู้ใหม่เพิ่มเมื่อครบ 3 แล้ว ต้อง unpin กระทู้เก่าออกก่อน

**ใช้เมื่อไหร่:** Welcome post, FAQ ที่ถูกถามบ่อยที่สุด, ประกาศสำคัญที่ต้องการให้ทุกคนเห็นตลอดเวลา

### 278.2 Lock conversation

**Lock** คือการปิดไม่ให้มีการตอบกลับเพิ่มเติมในกระทู้นั้นอีก (แต่เนื้อหาเดิมยังอ่านได้ตามปกติ)

**วิธีทำ:** เมนู ⋯ ของกระทู้ → **"Lock conversation"** → เลือกเหตุผลการ lock (Too heated, Resolved, Spam, Off-topic) ซึ่งจะแสดงเป็นข้อความอัตโนมัติในกระทู้ให้ทุกคนเห็นเหตุผล

**ใช้เมื่อไหร่:**
- กระทู้เริ่มมีการโต้เถียงที่ไม่สร้างสรรค์ (heated argument)
- กระทู้เก่าที่ได้ข้อสรุปแล้วแต่ยังมีคนมาตอบ comment ซ้ำ ๆ ทำให้กระทู้ไม่จบ
- ป้องกัน spam comment ในกระทู้เก่าที่ถูกบอทมาโพสต์ลิงก์โฆษณา

**การ unlock:** ทำได้ตลอดเวลาโดยกดเมนู ⋯ แล้วเลือก **"Unlock conversation"** อีกครั้ง

### 278.3 Delete discussion

**Delete** คือการลบกระทู้ทิ้งอย่างถาวร

**วิธีทำ:** เมนู ⋯ ของกระทู้ → **"Delete discussion"** → ระบบจะถามยืนยันอีกครั้งเพราะเป็นการกระทำที่ย้อนกลับไม่ได้

**ข้อควรระวังอย่างยิ่ง:** การลบ Discussion **ไม่สามารถกู้คืนได้เลย** ต่างจาก Issue ที่บาง action สามารถ reopen ได้ เมื่อลบแล้ว **เนื้อหาทั้งหมดรวมถึง comment ทุกอันในกระทู้นั้นหายไปถาวร** จึงควรใช้ด้วยความระมัดระวังสูงสุด และควรสงวนไว้สำหรับกรณีที่จำเป็นจริง ๆ เท่านั้น เช่น:

- เนื้อหาเป็น spam หรือโฆษณาชัดเจน
- เนื้อหาละเมิด Code of Conduct อย่างร้ายแรง
- ข้อมูลอ่อนไหว (เช่น เผลอโพสต์ API key หรือข้อมูลส่วนตัว) ที่ต้องลบทิ้งทันที

**ทางเลือกก่อนตัดสินใจลบ:** หากกระทู้แค่ "ไม่เหมาะสมกับหมวดหมู่" หรือ "ซ้ำกับกระทู้อื่น" ให้พิจารณาใช้ **Lock** หรือย้าย category แทนการลบ เพื่อรักษาประวัติไว้

### 278.4 Transfer discussion

**Transfer** คือการย้ายกระทู้ Discussion ไปยัง repository อื่นทั้งกระทู้ (ต้องเป็น repo ที่เปิดใช้งาน Discussions ไว้แล้วเช่นกัน)

**วิธีทำ:** เมนู ⋯ ของกระทู้ → **"Transfer discussion"** → เลือก repository ปลายทาง → เลือก category ในปลายทางที่จะให้กระทู้ไปอยู่ → ยืนยัน

**ใช้เมื่อไหร่:**
- กระทู้ถูกโพสต์ผิด repository ในกรณี organization ที่มีหลาย repo ย่อย (เช่น monorepo แยกเป็นหลาย repo, หรือมี repo หลักกับ repo ปลั๊กอิน)
- ต้องการรวมศูนย์การพูดคุยไว้ที่ repo หลักของ organization

**สิ่งที่เกิดขึ้นหลัง transfer:** กระทู้จะได้ URL ใหม่ในปลายทาง และที่ repo ต้นทางจะไม่เห็นกระทู้นั้นอีกต่อไป (ต่างจาก convert to issue ที่ยังเหลือ link อ้างอิงไว้)

### 278.5 Hide comment

**Hide comment** คือการซ่อน comment เดี่ยว ๆ ภายในกระทู้ (ไม่ใช่การซ่อนทั้งกระทู้) โดยไม่ลบถาวร

**วิธีทำ:** คลิกเมนู ⋯ ข้าง comment ที่ต้องการซ่อน → **"Hide comment"** → เลือกเหตุผล (Off-topic, Spam, Abuse, Resolved, Too heated, Outdated, Duplicate)

**ผลลัพธ์:** comment จะถูกยุบเก็บเป็นแถบเล็ก ๆ พร้อมข้อความ "This comment was hidden because [เหตุผล]" ผู้อ่านสามารถคลิกเพื่อขยายดูเนื้อหาเดิมได้ถ้าต้องการ (ต่างจาก delete ที่หายไปเลย)

**ข้อดีเทียบกับ delete comment:** hide เก็บหลักฐานไว้เผื่อจำเป็นต้องตรวจสอบย้อนหลัง (เช่น กรณีมีข้อพิพาทเรื่องการ moderate) ในขณะที่ delete comment คือการลบทิ้งถาวรแบบเดียวกับ delete discussion

### 278.6 สรุปเปรียบเทียบเครื่องมือ Moderation ทั้งหมด

| เครื่องมือ | ผลกระทบ | ย้อนกลับได้ไหม | ระดับสิทธิ์ที่ต้องมี |
|---|---|---|---|
| Pin | เด่นขึ้นในหน้ารายการ | ได้ (unpin) | Write ขึ้นไป |
| Lock | ห้ามตอบเพิ่ม เนื้อหาเดิมยังอยู่ | ได้ (unlock) | Write ขึ้นไป |
| Hide comment | ซ่อน comment เดียว ยังกู้คืนดูได้ | ได้ (unhide) | Write ขึ้นไป |
| Transfer | ย้ายไป repo อื่น | ย้ายกลับได้ (เป็นการ transfer อีกครั้ง) | Write ขึ้นไปทั้งสอง repo |
| Delete comment | ลบ comment เดียวถาวร | **ไม่ได้** | Write ขึ้นไป (หรือเจ้าของ comment เอง) |
| Delete discussion | ลบทั้งกระทู้ถาวร | **ไม่ได้** | Write ขึ้นไป (หรือเจ้าของกระทู้เอง) |

### 278.7 การรายงาน (Report) โดยผู้ใช้ทั่วไป

ผู้ใช้ทั่วไปที่ไม่มีสิทธิ์ moderate เอง (เช่น คนนอกทีม) ยังสามารถกดปุ่ม **"Report content"** ที่เมนู ⋯ ของกระทู้หรือ comment เพื่อแจ้งให้ GitHub ตรวจสอบเนื้อหาที่ละเมิดนโยบายการใช้งาน (Terms of Service) ได้โดยตรง แยกจากการ moderate ภายใน repo เอง — ใช้สำหรับกรณีร้ายแรง เช่น เนื้อหาผิดกฎหมายหรือคุกคามบุคคล

## Step 279: Discussions ระดับ Organization (org-wide discussions)

### 279.1 ความแตกต่างระหว่าง Repository Discussions กับ Organization Discussions

ที่ผ่านมาทั้งหมดในหลักสูตรนี้พูดถึง Discussions ที่ผูกกับ **repository เดียว** แต่ GitHub ยังมีอีกระดับหนึ่งคือ **Organization Discussions** ซึ่งเป็นพื้นที่พูดคุยที่ไม่ได้ผูกกับ repo ใด repo หนึ่งโดยเฉพาะ แต่เป็นของทั้ง **organization**

จุดสำคัญคือ Organization Discussions ต้อง **เลือก repository หนึ่งใน organization ให้เป็น "source repository"** ที่ใช้เก็บข้อมูลของ Discussions ระดับองค์กร กล่าวคือ:

> Owner ของ organization เปิดใช้งาน Organization Discussions ผ่านหน้า Settings ของ organization เอง แล้วเลือก repository ใดก็ได้ในองค์กร (จะสร้างใหม่หรือใช้ repo ที่มีอยู่แล้วก็ได้) ให้เป็น source repository — Discussions ที่อยู่ใน repo นั้นจะถูกยกระดับให้แสดงผลเป็น **"Discussions ของทั้ง Organization"** ที่เข้าถึงได้จากหน้าโปรไฟล์ organization โดยตรง หลายองค์กรนิยมเลือก repo ชื่อ `.github` เป็น source repository เพราะเป็น repo พิเศษที่ใช้เก็บ default community health files อยู่แล้ว แต่ **ไม่ได้บังคับว่าต้องชื่อ `.github` เท่านั้น** — repo อื่นก็ใช้เป็น source ได้เช่นกัน

### 279.2 วิธีเปิดใช้งาน Organization Discussions

1. ไปที่หน้า organization บน GitHub แล้วคลิก **Settings**
2. ในเมนูด้านซ้ายหมวด **"Code, planning, and automation"** คลิก **Discussions**
3. คลิก **Enable discussions for this organization**
4. เลือก repository ที่จะใช้เป็น **source repository** จาก dropdown (สร้าง repo ใหม่ก่อนก็ได้ถ้ายังไม่มี repo ที่เหมาะสม — หลายองค์กรเลือกใช้ repo ชื่อ `.github`)
5. เมื่อเปิดแล้ว หน้าโปรไฟล์ organization (`github.com/ชื่อorg`) จะมีแท็บ **Discussions** ปรากฏขึ้นในระดับ organization โดยอัตโนมัติ และ Discussions จะแสดงทั้งในหน้า organization และในหน้า Discussions ของ source repository เอง

### 279.3 ประโยชน์ของ Organization Discussions

| กรณีใช้งาน | ประโยชน์ |
|---|---|
| Organization ที่มีหลาย repository ย่อย | รวมศูนย์การพูดคุยเรื่องภาพรวมองค์กรไว้ที่เดียว แทนที่จะกระจายไปตอบคำถามซ้ำ ๆ ในแต่ละ repo |
| ประกาศข่าวสารระดับองค์กร | เช่น "Roadmap ปี 2027 ของทั้งบริษัท" ที่ไม่เกี่ยวกับ repo เดียว |
| ถามคำถามข้าม repo | เมื่อผู้ใช้ไม่แน่ใจว่าปัญหาที่เจอเกี่ยวกับ repo ไหนใน ecosystem ขององค์กร |
| การรวม community ของ organization ขนาดใหญ่ | เช่น องค์กรที่มี monorepo แยกเป็นหลาย package แต่ต้องการ community เดียว |

### 279.4 ข้อควรพิจารณาเมื่อใช้ทั้งสองระดับพร้อมกัน

หากทั้ง organization และ repository ย่อยแต่ละอันต่างก็เปิด Discussions ของตัวเองไว้ด้วย ควรวางกฎให้ชัดเจนว่าอะไรควรอยู่ระดับไหน เพื่อไม่ให้ชุมชนสับสนว่าจะไปโพสต์ที่ไหน:

- **ระดับ Organization (source repository):** เรื่องภาพรวม, roadmap รวม, ประกาศข้ามทีม, คำถามที่ไม่รู้ว่าเกี่ยวกับ repo ไหน
- **ระดับ Repository:** คำถามเจาะจงเกี่ยวกับการใช้งาน library/tool นั้น ๆ โดยตรง, บั๊กเฉพาะ repo, ไอเดียเฉพาะฟีเจอร์ของ repo นั้น

ควรเขียนคำอธิบายนี้ไว้ใน pinned welcome post ทั้งสองระดับ เพื่อชี้ทางให้ผู้ใช้ไปโพสต์ถูกที่ตั้งแต่แรก

### 279.5 ข้อจำกัดของ Organization Discussions

- ต้องมีสิทธิ์ระดับ **Owner ของ organization** จึงจะเปิด/ปิดใช้งาน Organization Discussions และเปลี่ยน source repository ได้ ส่วนสิทธิ์ในการสร้าง/ตอบ/ดูแลกระทู้จะอิงตามสิทธิ์ที่มีใน source repository นั้น (เหมือน Discussions ของ repository ทั่วไป)
- Organization Discussions ใช้ category และการตั้งค่าของตัว source repository เอง — ไม่ได้ผสานรวม category จาก repo อื่น ๆ ในองค์กรเข้าด้วยกันอัตโนมัติ
- ฟีเจอร์นี้ต้องการให้ organization เปิดให้ repo เป็น public หรือมีแผนที่รองรับ (บาง feature ของ community health file ระดับ org ขึ้นกับแผนบัญชีขององค์กรด้วย)

## Step 280: แบบฝึกหัด — เปิด Discussions และสร้างกระทู้ตัวอย่างให้โปรเจกต์จำลอง

ถึงเวลาลงมือปฏิบัติจริงเพื่อให้ทุกแนวคิดใน Part นี้กลายเป็นทักษะที่จับต้องได้

### 280.1 เตรียมโปรเจกต์จำลอง

ใช้ repository ฝึกฝนที่คุณสร้างไว้ตั้งแต่ Part ก่อน ๆ ของหลักสูตร (หรือสร้างใหม่ชื่อ เช่น `discussions-practice`) แล้วทำตามขั้นตอน:

```bash
# ถ้ายังไม่มี repo ฝึกฝน ให้สร้างใหม่บน GitHub ก่อน แล้ว clone ลงมา
git clone https://github.com/<username>/discussions-practice.git
cd discussions-practice
```

ควรเป็น repo แบบ **public** เพื่อจำลองสถานการณ์โปรเจกต์ Open Source ให้สมจริงที่สุด

### 280.2 ภารกิจที่ 1 — เปิดใช้งาน Discussions

1. ไปที่ **Settings → General → Features**
2. ติ๊กเปิดใช้งาน **Discussions**
3. กด **Set up discussions** และปล่อยให้ระบบสร้าง category เริ่มต้น 5 หมวดให้อัตโนมัติ

**ตรวจสอบผล:** ต้องเห็นแท็บ **Discussions** ปรากฏบนแถบเมนูของ repo แล้ว

### 280.3 ภารกิจที่ 2 — สร้าง Category เพิ่มเติมเอง

สร้าง category ใหม่อย่างน้อย 1 หมวดที่ไม่ได้อยู่ใน 5 หมวดเริ่มต้น เช่น:

- ชื่อ: **Roadmap**
- Emoji: 🗺️
- คำอธิบาย: "พื้นที่ถกทิศทางระยะยาวและแผนพัฒนาของโปรเจกต์"
- Format: **Open-ended discussion**

**ตรวจสอบผล:** category ใหม่ต้องปรากฏในแถบด้านซ้ายของหน้า Discussions พร้อม emoji ที่ตั้งไว้

### 280.4 ภารกิจที่ 3 — สร้างกระทู้ตัวอย่างอย่างน้อย 4 กระทู้

สร้างกระทู้ตัวอย่างครอบคลุมรูปแบบที่หลากหลาย ดังนี้ (ใช้เนื้อหาสมมติของโปรเจกต์จำลองของคุณเองได้ตามสบาย):

**กระทู้ที่ 1 — Announcement**
- Category: Announcements
- Title: "ประกาศเปิดตัว v0.1.0 ของโปรเจกต์"
- เนื้อหา: สรุปฟีเจอร์หลักที่มีใน release แรก พร้อมลิงก์ไปยังหน้า Releases ของ repo

**กระทู้ที่ 2 — Q&A**
- Category: Q&A
- Title: "วิธีติดตั้งโปรเจกต์นี้บน Windows ต้องทำยังไง"
- เนื้อหา: อธิบายปัญหาที่เจอ พร้อม environment (OS, เวอร์ชัน) ตามรูปแบบใน Step 274.2
- จากนั้นให้ **ตอบคำถามนี้ด้วยตัวเอง** (สมมติเป็นอีก user หรือใช้บัญชีเดียวกันตอบก็ได้ในโหมดฝึกฝน) แล้ว **Mark as answer** เพื่อฝึกกระบวนการเต็มรูปแบบ

**กระทู้ที่ 3 — Ideas พร้อม Poll**
- Category: Ideas
- Title: "อยากให้เพิ่มฟีเจอร์ไหนก่อนดี"
- ใช้แท็บ **Poll** ใส่คำถาม "ควรทำฟีเจอร์ไหนก่อนใน Q1 หน้า" พร้อม 3-4 ตัวเลือก เช่น "Dark Mode", "Export PDF", "Multi-language Support"

**กระทู้ที่ 4 — Show and tell**
- Category: Show and tell
- Title: "แชร์การนำโปรเจกต์นี้ไปประยุกต์ใช้"
- เนื้อหา: อธิบายสมมติว่านำโปรเจกต์ไปใช้ทำอะไร พร้อม screenshot หรือคำอธิบายประกอบ (ใส่ markdown image syntax ก็ได้แม้จะเป็นภาพสมมติ)

### 280.5 ภารกิจที่ 4 — ฝึก Moderation Tools

จากกระทู้ทั้ง 4 ที่สร้างไว้ ให้ฝึกใช้เครื่องมือ moderation ต่อไปนี้อย่างน้อยคนละ 1 ครั้ง:

- [ ] **Pin** กระทู้ Announcement ไว้บนสุด
- [ ] **Lock** กระทู้ใดกระทู้หนึ่งพร้อมเลือกเหตุผล "Resolved"
- [ ] ลองสร้าง comment ทดสอบใน 1 กระทู้ แล้วฝึก **Hide comment** พร้อมเลือกเหตุผล "Off-topic" แล้วลอง unhide กลับ

### 280.6 ภารกิจที่ 5 — ฝึกแปลง Issue ↔ Discussion

1. เปิด Issue ใหม่ในโปรเจกต์เดียวกัน ตั้งชื่อว่า "ถามวิธีตั้งค่า config file" (จงใจตั้งเป็นคำถามที่ไม่ใช่บั๊ก)
2. ฝึก **Convert to discussion** โดยเลือก category Q&A
3. ตรวจสอบว่า Issue เดิมถูกปิดและมีลิงก์อ้างอิงไปยัง Discussion ใหม่จริง
4. เลือก Discussion หนึ่งกระทู้ (เช่นกระทู้ Q&A ที่สร้างไว้ในภารกิจที่ 3) แล้วฝึก **Convert to issue** เพื่อดูผลลัพธ์ในทิศทางกลับ

### 280.7 เกณฑ์ตรวจสอบว่าทำครบถ้วน

ก่อนไปยัง Part ถัดไป ตรวจสอบให้แน่ใจว่า repo ฝึกฝนของคุณมี:

- [ ] Discussions เปิดใช้งานแล้ว
- [ ] มี category เพิ่มเติมอย่างน้อย 1 หมวดที่สร้างเอง (นอกเหนือจาก 5 หมวดเริ่มต้น)
- [ ] มีกระทู้อย่างน้อย 4 กระทู้ครอบคลุม category ต่างกัน (Announcement, Q&A, Ideas+Poll, Show and tell)
- [ ] กระทู้ Q&A อย่างน้อย 1 กระทู้ถูก mark answer แล้ว
- [ ] มีกระทู้ที่ผ่านการ pin อย่างน้อย 1 กระทู้
- [ ] มีกระทู้ที่ผ่านการ lock อย่างน้อย 1 กระทู้
- [ ] เคยฝึก Convert to discussion และ Convert to issue ทั้งสองทิศทางแล้ว

## สรุป Part 28

ใน Part นี้เราได้เรียนรู้ว่า:

1. **GitHub Discussions** คือพื้นที่สำหรับการสนทนาแบบเปิด แยกจาก **Issues** ซึ่งใช้ติดตามงานและบั๊กที่ชัดเจน — การแยกสองอย่างนี้ทำให้ Issue tracker สะอาดและ community มีพื้นที่พูดคุยที่เหมาะสม
2. Discussions ต้อง **เปิดใช้งานเองใน repo settings** เพราะไม่ได้เปิดเป็นค่าเริ่มต้นเหมือน Issues
3. **Categories** กำหนดทั้งการจัดกลุ่มและ **รูปแบบการสนทนา** (Open-ended, Question/Answer, Announcement) โดยมี 5 หมวดเริ่มต้นและสร้างเพิ่มเองได้
4. หมวด **Q&A** มีกลไก **Mark as answer** ที่ช่วยสร้างฐานความรู้ (knowledge base) ที่ค้นหาได้ในระยะยาว
5. **Polls** ช่วยสำรวจความเห็นแบบเลือกตอบได้โดยตรงในกระทู้ โดยจำกัด 1 โหวตต่อคน และไม่มีวันหมดอายุอัตโนมัติ — ต้อง Lock conversation เองเมื่อต้องการหยุดรับโหวต
6. **Issue และ Discussion แปลงข้ามกันได้** แต่มีทิศทางที่ไม่สมมาตรกัน — Issue → Discussion จะปิด Issue เดิมถาวร ส่วน Discussion → Issue จะไม่ลบ Discussion เดิม
7. การสร้าง **community** ที่ดีต้องมี pinned welcome post, guidelines ที่ชัดเจน และ maintainer ที่ดูแลตอบกระทู้อย่างสม่ำเสมอ
8. เครื่องมือ **Moderation** ได้แก่ Pin, Lock, Delete, Transfer, และ Hide comment แต่ละอันมีระดับความย้อนกลับได้ต่างกัน โดยเฉพาะ Delete ที่ย้อนกลับไม่ได้เลย
9. **Organization Discussions** เปิดใช้งานผ่าน Settings ของ organization โดยเลือก repository หนึ่งในองค์กรเป็น source repository (นิยมใช้ `.github` แต่ไม่บังคับ) เพื่อรวมศูนย์การพูดคุยระดับองค์กรทั้งหมด
