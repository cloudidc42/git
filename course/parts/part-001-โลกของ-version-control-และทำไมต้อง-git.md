## Step 1: ชีวิตก่อนมี Version Control เป็นอย่างไร

ก่อนที่จะเข้าใจว่าทำไม Git ถึงสำคัญ เราต้องเข้าใจก่อนว่า **โลกที่ไม่มี Version Control** มันแย่ขนาดไหน

ลองนึกภาพว่าคุณกำลังเขียนโปรแกรมคนเดียว แล้วคุณจัดการไฟล์แบบนี้:

```
project/
├── index.html
├── index_backup.html
├── index_backup2.html
├── index_final.html
├── index_final_v2.html
├── index_final_FINAL.html
├── index_final_FINAL_ใช้อันนี้จริงๆ.html
└── index_เก่าอย่าลบ.html
```

นี่คือสิ่งที่เกิดขึ้นจริงกับโปรแกรมเมอร์แทบทุกคนก่อนจะรู้จัก Version Control ปัญหาที่ตามมามีมากมาย:

1. **ไม่รู้ว่าไฟล์ไหนคือเวอร์ชันล่าสุดจริง ๆ** — ชื่อไฟล์บอกไม่ได้ว่าอันไหนถูกแก้ไขล่าสุด หรืออันไหนใช้งานได้จริง
2. **ไม่มีประวัติการเปลี่ยนแปลง** — ถ้าอยากรู้ว่า "เมื่อวานโค้ดบรรทัดนี้เขียนว่าอะไร" คุณตอบไม่ได้เลย นอกจากจะจำได้เอง
3. **ทำงานร่วมกับคนอื่นแทบเป็นไปไม่ได้** — ถ้ามีคน 2 คนแก้ไฟล์เดียวกันพร้อมกัน แล้วส่งไฟล์กลับมาให้คุณทาง email คุณต้องนั่งเทียบทีละบรรทัดด้วยตาเปล่าว่าใครแก้ตรงไหนบ้าง แล้วรวมเข้าด้วยกันเอง
4. **กู้คืนของเก่าไม่ได้อย่างมั่นใจ** — ถ้าคุณลบโค้ดบางส่วนไปแล้วพบว่ามันจำเป็นต้องใช้ในอีก 2 สัปดาห์ต่อมา คุณจะกู้คืนได้อย่างไรถ้าไม่มีการสำรองไว้
5. **ไม่มี "จุดคืนกลับ" (rollback point) ที่ปลอดภัย** — ถ้าคุณแก้โค้ดแล้วพัง คุณไม่มีทางย้อนกลับไปยังจุดที่ทุกอย่างยังทำงานได้ปกติได้อย่างแม่นยำ

ทีมพัฒนาซอฟต์แวร์ในยุคก่อนมี VCS ที่ดีจะใช้วิธีการที่เจ็บปวดมาก เช่น:

- ส่งไฟล์ทั้งโปรเจกต์ผ่านอีเมลหรือ USB drive ให้เพื่อนร่วมทีม
- ใช้โฟลเดอร์ที่แชร์กันบนเครือข่าย แล้ว "ล็อกไฟล์" ไว้ก่อนแก้ไข เพื่อไม่ให้คนอื่นแก้ไขพร้อมกัน (Pessimistic locking)
- Copy โฟลเดอร์ทั้งหมดเป็น `project_2024_01_15`, `project_2024_01_16` ทุกวันเพื่อเก็บ backup

วิธีเหล่านี้ **ใช้งานได้ในระดับหนึ่ง** แต่ขยายไม่ได้เมื่อทีมโตขึ้น และมีความเสี่ยงสูงมากที่งานจะหาย หรือมีคนเขียนทับงานของคนอื่นโดยไม่ได้ตั้งใจ

### แบบฝึกหัดทางความคิด (ไม่ต้องลงมือทำ แค่คิดตาม)

ลองตอบคำถามเหล่านี้ในใจ:

- ถ้าคุณทำงานร่วมกับเพื่อนอีก 3 คนในไฟล์เดียวกัน โดยไม่มีเครื่องมือช่วยเลย คุณจะจัดการอย่างไร
- ถ้าคุณแก้บั๊กไปแล้วพบว่าทำให้เกิดบั๊กใหม่ที่ร้ายแรงกว่าเดิม คุณจะย้อนกลับไปจุดก่อนหน้าได้อย่างไรถ้าไม่มี VCS

คำตอบของคำถามทั้งสองข้อนี้คือเหตุผลที่ Version Control System ถือกำเนิดขึ้นมา

## Step 2: Version Control System (VCS) คืออะไร

**Version Control System (VCS)** หรือ **ระบบควบคุมเวอร์ชัน** คือระบบที่ทำหน้าที่:

> **บันทึกการเปลี่ยนแปลงของไฟล์ (โดยเฉพาะซอร์สโค้ด) ตลอดช่วงเวลา เพื่อให้สามารถย้อนกลับไปดูหรือกู้คืนเวอร์ชันใดก็ได้ในอดีต**

พูดง่าย ๆ VCS คือ **"เครื่องย้อนเวลา" สำหรับโค้ดของคุณ**

VCS ที่ดีจะช่วยแก้ปัญหาทั้งหมดที่กล่าวถึงใน Step 1:

| ปัญหาที่ไม่มี VCS | สิ่งที่ VCS แก้ให้ |
|---|---|
| ไม่รู้ว่าเวอร์ชันไหนล่าสุด/ถูกต้อง | มี "จุดอ้างอิง" ที่ชัดเจนเสมอ (branch, commit) |
| ไม่มีประวัติการเปลี่ยนแปลง | บันทึกทุกการเปลี่ยนแปลงพร้อมเวลา ผู้เขียน และเหตุผล |
| ทำงานร่วมกันยาก | มีกลไก merge/conflict resolution ให้ทำงานพร้อมกันได้ |
| กู้คืนโค้ดเก่าไม่ได้ | ย้อนกลับไปยังจุดใดก็ได้ในประวัติ (checkout, revert) |
| ไม่มีจุด rollback ที่ปลอดภัย | สร้าง branch ทดลองได้โดยไม่กระทบโค้ดหลัก |

### ประโยชน์หลักของ VCS (สรุปเป็นข้อ ๆ)

1. **History (ประวัติ)** — รู้ว่าใครแก้อะไร เมื่อไหร่ ทำไม
2. **Collaboration (การทำงานร่วมกัน)** — หลายคนแก้โค้ดพร้อมกันได้อย่างปลอดภัย
3. **Backup (การสำรองข้อมูล)** — โค้ดทุกเวอร์ชันถูกเก็บไว้ ไม่มีวันหาย (ถ้า push ขึ้น remote)
4. **Branching (การแตกสาขา)** — ทดลองฟีเจอร์ใหม่โดยไม่กระทบโค้ดที่ใช้งานจริง
5. **Accountability (ความรับผิดชอบ)** — ทุก commit มีชื่อผู้เขียนกำกับ ตรวจสอบย้อนหลังได้เสมอ
6. **Automation (การทำงานอัตโนมัติ)** — ใช้เป็นจุดเริ่มต้นของ CI/CD (ซึ่งเราจะเรียนใน Part หลัง ๆ)

VCS ไม่ได้มีแค่ Git ตัวเดียว มันมีหลายตัวที่เคยได้รับความนิยม เราจะไล่ดูวิวัฒนาการของมันใน Step ถัดไป เพื่อให้เข้าใจว่าทำไม Git ถึงเป็นผู้ชนะในที่สุด

## Step 3: วิวัฒนาการของ VCS — จาก Local ไปสู่ Centralized ไปสู่ Distributed

VCS มีวิวัฒนาการผ่าน 3 ยุคหลัก ๆ:

### ยุคที่ 1: Local Version Control Systems (ระบบเก็บบนเครื่องเดียว)

ระบบยุคแรกสุด เช่น **RCS (Revision Control System)** ทำงานโดยเก็บ "ชุดของการเปลี่ยนแปลง (patch/diff)" ระหว่างไฟล์แต่ละเวอร์ชันไว้ในเครื่องเดียวกัน

```
เวอร์ชัน 1 → diff → เวอร์ชัน 2 → diff → เวอร์ชัน 3 → ...
```

**ข้อจำกัด:** ใช้ได้แค่คนเดียวบนเครื่องเดียว ทำงานเป็นทีมไม่ได้เลย

### ยุคที่ 2: Centralized Version Control Systems (CVCS)

ตัวอย่าง: **CVS (Concurrent Versions System)**, **Subversion (SVN)**, **Perforce**

แนวคิดคือมี **Server กลางเพียงเครื่องเดียว** ที่เก็บประวัติทั้งหมดของโปรเจกต์ และทุกคนในทีมต้องเชื่อมต่อกับ server นี้เพื่อ:

- **Checkout** — ดึงไฟล์ล่าสุดมาทำงาน
- **Commit** — ส่งการเปลี่ยนแปลงกลับไปที่ server

```
        ┌──────────────┐
        │   Server     │
        │  (Central    │
        │  Repository) │
        └──────┬───────┘
     ┌──────────┼──────────┐
     │          │          │
  Developer  Developer  Developer
     A          B          C
```

**ข้อดี:** ทุกคนเห็นภาพเดียวกัน จัดการ permission ได้ง่ายจากจุดเดียว

**ข้อเสียร้ายแรง:**
- ถ้า server ล่ม **ทุกคนทำงานต่อไม่ได้เลย** เพราะไม่มีที่เก็บประวัติ
- การ commit ต้องเชื่อมต่ออินเทอร์เน็ต/เครือข่ายกับ server ตลอดเวลา
- การสร้าง branch หรือทดลองอะไรใหม่ ๆ ทำได้ยากและช้า เพราะทุกการกระทำต้องคุยกับ server กลาง
- ถ้า server เสียหายและไม่มี backup ที่ดี **ประวัติทั้งหมดของโปรเจกต์อาจหายไปตลอดกาล**

### ยุคที่ 3: Distributed Version Control Systems (DVCS)

ตัวอย่าง: **Git**, **Mercurial (Hg)**, **Bazaar**

นี่คือจุดเปลี่ยนสำคัญที่สุดในประวัติศาสตร์ VCS แนวคิดคือ:

> **ทุกคนที่ clone repository จะได้ "สำเนาเต็ม" ของประวัติทั้งหมดไว้ในเครื่องตัวเอง ไม่ใช่แค่ไฟล์ล่าสุด**

```
        ┌──────────────┐
        │   Server     │
        │ (Remote Repo)│  ← มีไว้เพื่อ "ประสานงาน" ไม่ใช่จุดเดียวที่มีประวัติ
        └──────┬───────┘
     ┌──────────┼──────────┐
     │          │          │
┌────▼────┐┌────▼────┐┌────▼────┐
│  Dev A  ││  Dev B  ││  Dev C  │
│ (Full   ││ (Full   ││ (Full   │
│ History)││ History)││ History)│
└─────────┘└─────────┘└─────────┘
```

**ผลลัพธ์ที่เปลี่ยนเกมทั้งวงการ:**

1. **ทำงาน offline ได้เกือบทุกอย่าง** — commit, ดู log, สร้าง branch, ย้อนดูประวัติ ทำได้หมดโดยไม่ต้องต่อเน็ต (ต้องต่อเน็ตแค่ตอน push/pull เพื่อแลกเปลี่ยนข้อมูลกับคนอื่น)
2. **ไม่มี Single Point of Failure** — ถ้า server กลางล่ม ทุกคนยังมีสำเนาประวัติแบบเต็มอยู่ในเครื่องตัวเอง กู้คืน server ได้จากเครื่องใครก็ได้
3. **สร้าง branch ได้เร็วมากและแทบไม่มีต้นทุน** — เพราะทุกอย่างทำงานในเครื่อง local
4. **รองรับ Workflow หลากหลาย** — ทีมสามารถเลือกได้ว่าจะใช้ server กลาง 1 ที่ (เหมือน GitHub) หรือจะกระจายงานแบบ peer-to-peer ก็ได้ (แบบที่ Linux Kernel ใช้)

Git คือผู้ชนะที่ชัดเจนที่สุดของยุค DVCS และแทบจะเป็นมาตรฐานเดียวที่อุตสาหกรรมใช้ในปัจจุบัน

## Step 4: Git คืออะไร กำเนิดมาจากไหน

**Git** ถูกสร้างขึ้นในปี **2005** โดย **Linus Torvalds** ผู้สร้าง **Linux Kernel**

### เรื่องราวเบื้องหลัง (ทำไม Linus ถึงสร้าง Git)

ก่อนปี 2005 ทีมพัฒนา Linux Kernel ใช้ระบบ VCS เชิงพาณิชย์ชื่อ **BitKeeper** ในการจัดการซอร์สโค้ด แต่ในปี 2005 เกิดปัญหาด้านลิขสิทธิ์ระหว่างชุมชน Open Source กับบริษัทเจ้าของ BitKeeper จนทำให้สิทธิ์การใช้งานฟรีถูกยกเลิก

Linus Torvalds จึงตัดสินใจ **สร้าง VCS ตัวใหม่ขึ้นมาเองภายในเวลาเพียงไม่กี่สัปดาห์** โดยตั้งเป้าหมายไว้ชัดเจนมาก:

1. **เร็วมาก** (Speed) — เพราะ Linux Kernel มีขนาดใหญ่และมีนักพัฒนาหลายพันคนทั่วโลก
2. **ออกแบบมาเพื่อระบบกระจายศูนย์ (Distributed)** — ไม่ต้องพึ่งพา server กลาง
3. **รองรับ Non-linear development** — คือรองรับการแตก branch จำนวนมากและการรวม (merge) กลับมาอย่างมีประสิทธิภาพ
4. **มีความสมบูรณ์ของข้อมูลสูง (Data Integrity)** — ตรวจสอบได้ว่าข้อมูลไม่ถูกแก้ไขหรือเสียหายระหว่างทาง (ใช้ SHA-1/SHA-256 hash)
5. **ฟรีและเป็น Open Source** อย่างสมบูรณ์

ชื่อ "Git" นั้น Linus Torvalds เคยพูดติดตลกว่ามันเป็นคำสแลงในภาษาอังกฤษแบบอังกฤษที่แปลว่า "คนที่น่ารำคาญ" และเขาก็ตั้งชื่อโปรเจกต์ตามธรรมเนียมที่เขาชอบตั้งชื่อโปรเจกต์ตามตัวเอง (แบบติดตลก)

### Timeline สำคัญ

| ปี | เหตุการณ์ |
|---|---|
| 2005 | Linus Torvalds สร้าง Git ขึ้นมาใช้กับ Linux Kernel |
| 2005 | Junio Hamano เข้ามารับหน้าที่ maintainer หลักของ Git ต่อจาก Linus (และยังคงดูแลอยู่จนถึงปัจจุบัน) |
| 2008 | GitHub เปิดตัว — ทำให้ Git เข้าถึงคนทั่วไปได้ง่ายขึ้นมหาศาลผ่าน UI บนเว็บ |
| 2011 | GitLab เปิดตัว — ทางเลือกที่เน้น self-hosted และ DevOps ครบวงจร |
| 2018 | Microsoft ซื้อ GitHub |
| ปัจจุบัน | Git เป็น VCS มาตรฐานอุตสาหกรรมที่แทบทุกบริษัทซอฟต์แวร์ทั่วโลกใช้งาน |

## Step 5: ทำไม Git ถึงชนะ VCS ตัวอื่นเกือบทั้งหมด

แม้จะมี DVCS ตัวอื่นเช่น Mercurial หรือ Bazaar ที่ออกมาในช่วงเวลาใกล้เคียงกัน แต่ Git กลับเป็นผู้ชนะที่ชัดเจนที่สุด เหตุผลหลัก ๆ มีดังนี้:

### 1. ความเร็ว (Performance)

Git ถูกออกแบบมาให้เร็วมากตั้งแต่วันแรก เพราะ Linux Kernel มีไฟล์และประวัติจำนวนมหาศาล การ commit, branch, merge ใน Git ใช้เวลาระดับ milliseconds เพราะทุกอย่างทำงานในเครื่อง local

### 2. Branching ที่ "ถูกแทบไม่มีต้นทุน" (Cheap Branching)

ใน SVN การสร้าง branch คือการ copy โฟลเดอร์ทั้งหมด ซึ่งใช้เวลาและพื้นที่มาก แต่ใน Git การสร้าง branch คือการสร้าง**pointer**เล็ก ๆ ตัวหนึ่งชี้ไปยัง commit ที่มีอยู่แล้ว ทำให้สร้างได้เร็วในระดับ instant และแทบไม่กินพื้นที่เพิ่มเลย

### 3. ระบบนิเวศ (Ecosystem) ที่แข็งแกร่งที่สุด

การมาถึงของ **GitHub (2008)** และ **GitLab (2011)** ทำให้ Git มีเครื่องมือรอบข้างที่ครบครันที่สุด:

- UI สำหรับ Code Review (Pull Request / Merge Request)
- ระบบ Issue Tracking ในตัว
- CI/CD Pipeline ในตัว
- ชุมชน Open Source ขนาดใหญ่ที่สุดในโลกใช้งาน

### 4. Data Integrity (ความสมบูรณ์ของข้อมูล)

Git ใช้ hash (SHA-1 และในเวอร์ชันใหม่รองรับ SHA-256) ในการอ้างอิงทุก object ในระบบ ทำให้ **แทบเป็นไปไม่ได้ที่จะแก้ไขประวัติโดยไม่ถูกตรวจจับ** — นี่คือคุณสมบัติที่สำคัญมากสำหรับความปลอดภัยของซอร์สโค้ด

### 5. รองรับทั้ง Centralized และ Fully Distributed Workflow

ทีมเล็ก ๆ สามารถใช้ Git แบบมี server กลางเดียว (เหมือนที่ GitHub ทำ) ในขณะที่โปรเจกต์ขนาดใหญ่แบบ Linux Kernel ก็สามารถใช้ Git แบบกระจายศูนย์เต็มรูปแบบได้เช่นกัน — Git ยืดหยุ่นพอที่จะรองรับทั้งสองแบบโดยไม่ต้องเปลี่ยนเครื่องมือ

### ตารางเปรียบเทียบโดยสรุป

| คุณสมบัติ | SVN (Centralized) | Git (Distributed) |
|---|---|---|
| ต้องต่อเน็ตเพื่อ commit | ต้อง | ไม่ต้อง |
| ความเร็วในการสร้าง branch | ช้า (copy ทั้งโฟลเดอร์) | เร็วมาก (แค่สร้าง pointer) |
| Single Point of Failure | มี (server ล่ม = จบ) | ไม่มี (ทุกเครื่องมีสำเนาเต็ม) |
| การรวม branch (merge) | ยากและเสี่ยง conflict สูง | มีเครื่องมือ merge ที่ฉลาดกว่า |
| ระบบนิเวศ | จำกัด | กว้างขวางที่สุด (GitHub, GitLab, Bitbucket) |

## Step 6: Git ทำงานอย่างไรในระดับแนวคิด (Snapshot ไม่ใช่ Diff)

นี่คือแนวคิดที่สำคัญที่สุดข้อหนึ่งที่ทำให้คนเข้าใจ Git ผิดบ่อยที่สุด

### ความเข้าใจผิดที่พบบ่อย

หลายคนคิดว่า Git เก็บข้อมูลแบบ "ผลต่าง" (diff/delta) ระหว่างแต่ละเวอร์ชัน เหมือนกับ VCS รุ่นเก่า เช่น:

```
เวอร์ชัน 1: ไฟล์ A ทั้งหมด
เวอร์ชัน 2: (บันทึกแค่ส่วนที่เปลี่ยนจากเวอร์ชัน 1)
เวอร์ชัน 3: (บันทึกแค่ส่วนที่เปลี่ยนจากเวอร์ชัน 2)
```

**นี่ไม่ใช่วิธีที่ Git ทำงาน**

### วิธีที่ Git ทำงานจริง: Snapshot-based

ทุกครั้งที่คุณ **commit** ใน Git มันจะเก็บ **"ภาพถ่าย (snapshot)" ของไฟล์ทั้งหมดในโปรเจกต์ ณ ขณะนั้น** ไม่ใช่แค่ส่วนต่าง

```
Commit 1: [Snapshot ของไฟล์ทั้งหมด ณ เวลานั้น]
Commit 2: [Snapshot ของไฟล์ทั้งหมด ณ เวลานั้น]
Commit 3: [Snapshot ของไฟล์ทั้งหมด ณ เวลานั้น]
```

แต่ Git ฉลาดพอที่จะ**ไม่คัดลอกไฟล์ที่ไม่ได้เปลี่ยนแปลงซ้ำ** — ถ้าไฟล์ไหนไม่ถูกแก้ไขใน commit นั้น Git จะแค่ทำ **link (pointer)** ไปยังไฟล์เดิมที่เก็บไว้แล้วจาก commit ก่อนหน้า ไม่ได้เก็บซ้ำใหม่ทั้งหมด

```
         Commit 1        Commit 2        Commit 3
         ┌──────┐        ┌──────┐        ┌──────┐
         │ A.txt│───────▶│ A.txt│ (ไม่เปลี่ยน) │ A.txt│ (ไม่เปลี่ยน)
         │ B.txt│        │ B.txt│───────▶│      │
         │ C.txt│        │      │───────▶│ C.txt│
         └──────┘        │ B2.txt (ใหม่)│  │ D.txt (ใหม่)│
                         └──────┘        └──────┘
```

การออกแบบแบบนี้ทำให้:

1. **การดูว่าโปรเจกต์หน้าตาเป็นอย่างไร ณ commit ใด ๆ ทำได้เร็วมาก** เพราะแค่ไปดู snapshot นั้นตรง ๆ ไม่ต้องไล่ apply diff ทีละอันจากจุดเริ่มต้น
2. **การสลับ branch (checkout/switch) ทำได้เร็ว** เพราะแค่เปลี่ยนไปดูอีก snapshot หนึ่ง
3. Git เก็บข้อมูลอย่างมีประสิทธิภาพโดยที่ผู้ใช้ไม่ต้องกังวลเรื่องนี้เลย

เราจะเจาะลึกเรื่อง Object Model ของ Git (blob, tree, commit) แบบละเอียดจริง ๆ ใน **Part 56: Git Internals** แต่ ณ ตอนนี้ขอให้จำหลักการสำคัญไว้แค่ประโยคเดียว:

> **Git คิดถึงข้อมูลของมันในรูปแบบ Snapshot ของทั้งโปรเจกต์ ไม่ใช่ diff ของไฟล์ทีละไฟล์**

## Step 7: Git, GitHub, GitLab ต่างกันอย่างไร (คำถามที่มือใหม่สับสนที่สุด)

นี่คือคำถามที่ผู้เรียนใหม่เกือบทุกคนสับสน มาทำความเข้าใจให้ชัดเจนตั้งแต่ต้น

### Git = เครื่องมือ (Tool)

**Git** คือ **โปรแกรม (software)** ที่ติดตั้งลงในเครื่องคอมพิวเตอร์ของคุณ ใช้สำหรับจัดการ version control **Git ทำงานได้โดยไม่ต้องมีอินเทอร์เน็ตเลย** และไม่ได้ผูกติดกับบริษัทไหน — มันเป็น Open Source ฟรี 100%

คุณสามารถใช้ Git คนเดียวบนเครื่อง โดยไม่ต้องมีบัญชี GitHub หรือ GitLab เลยก็ได้

### GitHub = บริการออนไลน์ (บริษัท Microsoft เป็นเจ้าของ)

**GitHub** คือ **เว็บไซต์/บริการ (platform)** ที่ให้คุณ **host (ฝาก) Git repository ของคุณไว้บน Cloud** พร้อมเพิ่มฟีเจอร์ที่ Git เพียว ๆ ไม่มี เช่น:

- หน้าเว็บสำหรับดูโค้ดสวยงาม
- ระบบ Issue Tracking
- Pull Request สำหรับ Code Review
- GitHub Actions สำหรับทำ CI/CD
- GitHub Pages สำหรับ host เว็บไซต์ฟรี
- Social features: follow, star, fork โปรเจกต์คนอื่น

### GitLab = บริการออนไลน์คู่แข่งของ GitHub (เน้น DevOps ครบวงจร)

**GitLab** ทำหน้าที่คล้าย GitHub มาก แต่มีจุดเด่นต่างกันคือ:

- เน้นเป็น **"DevOps Platform" ครบวงจร** ตั้งแต่ planning, code, build, test, deploy, monitor ในที่เดียว
- รองรับการทำ **Self-hosted** (ติดตั้งบน server ของบริษัทเองได้ฟรี) ได้ง่ายกว่า GitHub มาก
- CI/CD ของ GitLab (`.gitlab-ci.yml`) ถูกมองว่าทรงพลังและใช้งานง่ายกว่าในหลายกรณี
- นิยมมากในองค์กรที่ต้องการควบคุมข้อมูลของตัวเอง (data sovereignty) เช่น หน่วยงานรัฐ ธนาคาร บริษัทขนาดใหญ่

### เปรียบเทียบแบบเข้าใจง่ายด้วยการเปรียบเปรย

ลองเปรียบเทียบกับโลกของเอกสาร:

| แนวคิด | เปรียบเสมือน |
|---|---|
| **Git** | โปรแกรม Microsoft Word ที่ติดตั้งในเครื่องคุณ (เขียนเอกสารได้แม้ไม่มีเน็ต) |
| **GitHub** | Google Drive / OneDrive ที่ให้คุณอัปโหลดเอกสารไปเก็บไว้ออนไลน์ พร้อมแชร์ให้คนอื่นดู/แก้ไขร่วมกันได้ |
| **GitLab** | คู่แข่งของ Google Drive อีกเจ้าหนึ่ง ที่มีฟีเจอร์คล้ายกันแต่เน้นจุดขายต่างกัน (เช่น ติดตั้งบน server บริษัทเองได้) |

### สรุปด้วยตาราง

| | Git | GitHub | GitLab |
|---|---|---|---|
| ประเภท | Software/Tool | Cloud Service/Platform | Cloud Service/Platform |
| เจ้าของ | Open Source (ไม่มีบริษัทเป็นเจ้าของ) | Microsoft | GitLab Inc. |
| ต้องมีเน็ตไหม | ไม่ต้อง (ทำงาน local ได้) | ต้อง (เพื่อ push/pull/ใช้ฟีเจอร์เว็บ) | ต้อง (หรือ self-host เอง) |
| ใช้ฟรีไหม | ฟรี 100% เสมอ | ฟรีสำหรับ public/private repo พื้นฐาน | ฟรีสำหรับใช้งานพื้นฐาน + self-hosted ฟรี |
| จุดเด่น | เป็นรากฐานของทุกอย่าง | ระบบนิเวศ Open Source ใหญ่ที่สุด | DevOps ครบวงจร + self-hosted ง่าย |

หลักสูตรนี้จะสอนทั้ง 3 อย่าง: **Git** (แกนกลาง), **GitHub** (แพลตฟอร์มยอดนิยมที่สุด), และ **GitLab** (ทางเลือกระดับองค์กร) — คุณจะได้เห็นภาพครบทุกมุมเพื่อเลือกใช้ได้อย่างเหมาะสมในทุกสถานการณ์การทำงานจริง

## Step 8: ศัพท์พื้นฐานที่ต้องรู้ก่อนเริ่ม (Glossary)

ก่อนไปต่อ มาทำความรู้จักคำศัพท์พื้นฐานที่จะเจอบ่อยมากตลอดหลักสูตรนี้ ยังไม่ต้องเข้าใจลึกในตอนนี้ แค่ให้คุ้นหูไว้ก่อน เดี๋ยวเราจะอธิบายแต่ละคำอย่างละเอียดใน Part ถัดไป

| คำศัพท์ | ความหมายโดยย่อ |
|---|---|
| **Repository (Repo)** | "คลัง" ที่เก็บโปรเจกต์และประวัติทั้งหมดของมัน |
| **Commit** | การบันทึก snapshot ของการเปลี่ยนแปลงพร้อมข้อความอธิบาย |
| **Branch** | เส้นทางการพัฒนาที่แยกออกจากกัน ทำงานคู่ขนานกันได้ |
| **Merge** | การรวม branch สองเส้นเข้าด้วยกัน |
| **Clone** | การคัดลอก repository ทั้งหมด (พร้อมประวัติ) มาไว้ที่เครื่อง |
| **Remote** | ที่อยู่ของ repository ที่อยู่บนเซิร์ฟเวอร์ (เช่น GitHub) |
| **Push** | การส่งการเปลี่ยนแปลงจากเครื่อง local ขึ้นไปยัง remote |
| **Pull** | การดึงการเปลี่ยนแปลงจาก remote ลงมาที่เครื่อง local |
| **Working Directory** | โฟลเดอร์จริงบนเครื่องที่คุณกำลังแก้ไขไฟล์ |
| **Staging Area (Index)** | พื้นที่พักไฟล์ที่เตรียมจะ commit |
| **Conflict** | สถานการณ์ที่ Git ไม่สามารถรวมการเปลี่ยนแปลงได้อัตโนมัติ ต้องให้คนตัดสินใจ |
| **Pull Request (PR)** / **Merge Request (MR)** | คำขอให้นำโค้ดจาก branch หนึ่งไปรวมกับอีก branch พร้อมให้ทีมรีวิวก่อน |
| **HEAD** | ตัวชี้ (pointer) ไปยังตำแหน่งปัจจุบันที่คุณกำลังทำงานอยู่ |

ไม่ต้องกังวลถ้ายังงง ๆ — เราจะอธิบายทุกคำเหล่านี้แบบละเอียดพร้อมตัวอย่างจริงใน Part 03 และ Part 04

## Step 10: ลงมือจริง — ตรวจสอบว่าคอมพิวเตอร์ของคุณพร้อมหรือยัง

ก่อนไป Part 02 (การติดตั้ง Git แบบละเอียด) เรามาเช็คสถานะเครื่องของคุณกันก่อนแบบเบื้องต้น

### 10.1 ตรวจสอบว่ามี Git ติดตั้งอยู่แล้วหรือยัง

เปิด **Terminal** (macOS/Linux) หรือ **Command Prompt / PowerShell / Git Bash** (Windows) แล้วพิมพ์คำสั่ง:

```bash
git --version
```

**ผลลัพธ์ที่เป็นไปได้:**

- ถ้าเครื่องมี Git อยู่แล้ว จะเห็นข้อความประมาณนี้:
  ```
  git version 2.43.0
  ```
  แปลว่าคุณมี Git พร้อมใช้งานแล้ว (แนะนำให้ใช้เวอร์ชัน 2.30 ขึ้นไป)

- ถ้าเครื่องยังไม่มี Git จะเห็นข้อความ error ประมาณ:
  ```
  bash: git: command not found
  ```
  หรือใน Windows ระบบอาจเปิดหน้าต่างให้ดาวน์โหลด Git ให้อัตโนมัติ

**ไม่ต้องกังวลถ้ายังไม่มี Git** — เราจะสอนวิธีติดตั้งแบบละเอียดทีละขั้นตอนสำหรับทั้ง Windows, macOS และ Linux ใน **Part 02** ครับ

### 10.2 ตรวจสอบเครื่องมือพื้นฐานอื่น ๆ ที่ควรมี

| เครื่องมือ | คำสั่งตรวจสอบ | ใช้ทำอะไร |
|---|---|---|
| Terminal / Command Line | (เปิดโปรแกรมได้เลย) | รันคำสั่ง Git ทั้งหมดในหลักสูตรนี้ |
| Text Editor / IDE | เช่น VS Code, Sublime Text | แก้ไขไฟล์โค้ดระหว่างฝึก |
| เว็บเบราว์เซอร์ | Chrome, Firefox, Edge | ใช้สมัครและใช้งาน GitHub/GitLab ใน Part หลัง ๆ |

แนะนำให้ติดตั้ง **Visual Studio Code (VS Code)** ไว้ล่วงหน้า เพราะมันมี Git integration ในตัวที่ดีมาก และเราจะใช้มันเป็นตัวอย่างประกอบตลอดหลักสูตร (ดาวน์โหลดได้ฟรีที่ https://code.visualstudio.com)

### 10.3 เตรียมโฟลเดอร์สำหรับฝึกฝน

สร้างโฟลเดอร์เปล่าไว้สำหรับฝึกทำแบบฝึกหัดตลอดหลักสูตรนี้ เช่น:

```bash
mkdir ~/git-course
cd ~/git-course
```

โฟลเดอร์นี้จะเป็น "ห้องทดลอง" ของคุณตลอดหลักสูตร — ทุก Part ที่มีแบบฝึกหัดให้ลงมือทำ จะแนะนำให้สร้างโฟลเดอร์ย่อยใหม่ภายในนี้ เพื่อไม่ให้ปนกัน เช่น:

```bash
mkdir ~/git-course/part-04-practice
mkdir ~/git-course/part-07-branching
```

## สรุป Part 01

ใน Part นี้เราได้เรียนรู้ว่า:

1. โลกก่อนมี Version Control เต็มไปด้วยความยุ่งเหยิง ไม่มีประวัติ ทำงานร่วมกันยาก
2. VCS วิวัฒนาการผ่าน 3 ยุค: Local → Centralized → Distributed
3. Git ถือกำเนิดในปี 2005 โดย Linus Torvalds เพื่อแก้ปัญหาการพัฒนา Linux Kernel
4. Git ชนะ VCS อื่นเพราะความเร็ว, branching ที่ถูก, ระบบนิเวศที่แข็งแกร่ง และความปลอดภัยของข้อมูล
5. Git ทำงานแบบ Snapshot ของทั้งโปรเจกต์ ไม่ใช่ diff ทีละไฟล์
6. **Git คือเครื่องมือ, GitHub และ GitLab คือบริการออนไลน์ที่ host Git repository** — เป็นคนละสิ่งกันแต่ทำงานร่วมกัน
7. เราเตรียมเครื่องมือพื้นฐานพร้อมสำหรับเริ่มลงมือปฏิบัติจริงใน Part ถัดไปแล้ว
