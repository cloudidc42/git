## Step 961: Google's Monorepo (Piper) — ขนาดและสถิติที่น่าทึ่ง

ใน **Part 82 Step 811** เราได้เกริ่นไว้แล้วว่า Google เก็บโค้ดเกือบทั้งหมดของบริษัทไว้ใน monorepo ที่ชื่อ **Piper** ใน Part นี้เราจะเจาะลึกว่า Piper คืออะไรจริง ๆ และมันมีขนาดใหญ่ขนาดไหน

### Piper ไม่ใช่ Git

ข้อเท็จจริงที่สำคัญที่สุดที่ต้องเข้าใจก่อนคือ **Piper ไม่ได้สร้างอยู่บน Git เลย** Piper เป็นระบบ version control ที่ Google พัฒนาขึ้นเองทั้งหมดภายในบริษัท (proprietary, internal-only) โดยมีสถาปัตยกรรมแบบ **centralized** ไม่ใช่ distributed แบบ Git

- Piper เก็บข้อมูลอยู่บน infrastructure ของ Google เอง โดยใช้ระบบเก็บข้อมูลแบบกระจาย (distributed storage) ที่สร้างขึ้นบนเทคโนโลยีฐานข้อมูลภายในของ Google เอง (แนวคิดคล้าย Bigtable) กระจายอยู่หลาย data center ทั่วโลก เพื่อให้วิศวกรในทุกภูมิภาคเข้าถึงได้เร็ว
- นักพัฒนาที่ Google **ไม่ได้ clone repository ทั้งหมดมาไว้ในเครื่องตัวเอง** เหมือนที่เราทำกับ `git clone` เพราะขนาดของมันใหญ่เกินกว่าจะทำแบบนั้นได้จริง แทนที่จะ clone Google ใช้ระบบที่ชื่อ **CitC (Client in the Cloud)** ซึ่งให้วิศวกรแต่ละคนมี "workspace เสมือน" ที่แสดงผลไฟล์ทั้งหมดของ repository ราวกับอยู่บนเครื่องจริง แต่เนื้อหาไฟล์จริง ๆ ถูกดึงมาแบบ on-demand จาก server ส่วนกลางเมื่อถูกเปิดใช้งาน (แนวคิดนี้คล้ายกับ virtual filesystem ที่เราจะเห็นอีกครั้งใน Step 966 และ 967 ในบริบทของ Microsoft และ Meta)
- การแก้ไขไฟล์ในเชิงแนวคิดคล้ายกับ Perforce (centralized VCS ที่เราเรียนถึงข้อดีข้อเสียไปแล้วใน Part 01) มากกว่า Git — คือมี server กลางเพียงชุดเดียว (แม้จะกระจายทาง infrastructure) ที่เป็นแหล่งความจริงเดียว (single source of truth) ของทั้งบริษัท

### สถิติที่น่าทึ่งของ Piper

ข้อมูลที่นักวิจัยของ Google เผยแพร่สู่สาธารณะอย่างเป็นทางการมากที่สุดมาจากบทความวิชาการชื่อ **"Why Google Stores Billions of Lines of Code in a Single Repository"** โดย Rachel Potvin และ Josh Levenberg ตีพิมพ์ใน *Communications of the ACM* ปี 2016 (อ้างอิงข้อมูลของปี 2015) ซึ่งเป็นแหล่งข้อมูลที่ถูกอ้างอิงมากที่สุดเมื่อพูดถึงเรื่องนี้ ตัวเลขสำคัญ ณ ตอนนั้นมีดังนี้:

| สถิติ | ตัวเลข (ข้อมูลปี 2015 ที่เผยแพร่สู่สาธารณะ) |
|---|---|
| ขนาดข้อมูลทั้งหมด | ประมาณ 86 เทราไบต์ (รวมประวัติทั้งหมด) |
| จำนวนไฟล์ | ประมาณ 1 พันล้านไฟล์ (รวมไฟล์ที่ไม่ใช่โค้ด เช่น ข้อมูล, config, เอกสาร) |
| จำนวนบรรทัดโค้ด | ประมาณ 2 พันล้านบรรทัด |
| จำนวนวิศวกรที่ใช้งานอยู่ | ประมาณ 25,000 คนทั่วโลก |
| จำนวนการเปลี่ยนแปลง (commit/changelist) ต่อวันทำงานปกติ | ประมาณ 16 ล้านบรรทัดที่ถูกแก้ไขในราว 24,000 ไฟล์ โดยวิศวกรราว 5,500 คน |
| จำนวน query (คำขออ่านข้อมูล) ต่อวินาที | ประมาณ 800,000 queries/วินาที จากเครื่องกว่า 8,000 เครื่อง (ทั้งจากวิศวกรและระบบอัตโนมัติ) |
| สัดส่วนของ commit ที่มาจากระบบอัตโนมัติ | มากกว่าครึ่งหนึ่งของ commit ทั้งหมดมาจากเครื่องมืออัตโนมัติ ไม่ใช่มนุษย์กดส่งเอง (เช่น การอัปเดต dependency อัตโนมัติ, การรัน large-scale change) |

ตัวเลขเหล่านี้เป็นข้อมูลที่เผยแพร่ต่อสาธารณะครั้งล่าสุดอย่างเป็นทางการในปี 2015-2016 ซึ่งเป็นเวลากว่าสิบปีมาแล้ว ในทางปฏิบัติแทบไม่มีข้อสงสัยเลยว่าตัวเลขจริงในปัจจุบันจะสูงกว่านี้อย่างมาก เพราะทั้งจำนวนวิศวกรและปริมาณโค้ดของ Google เติบโตขึ้นต่อเนื่องมาตลอด แต่ Google ไม่ได้เปิดเผยตัวเลขล่าสุดแบบละเอียดต่อสาธารณะอีกเลยนับจากนั้น สิ่งที่ควรจำจากตัวเลขนี้ไม่ใช่ค่าตัวเลขที่แน่นอน แต่คือ **ระดับขนาด (order of magnitude)** — เรากำลังพูดถึง repository เดียวที่มีขนาดใหญ่กว่า repository ทั่วไปที่เราเคยเจอเป็นพัน ๆ เท่า และมีวิศวกรจำนวนมหาศาลเข้าถึงพร้อมกันตลอดเวลาโดยไม่มีการหยุดพัก (เพราะ Google มีวิศวกรทำงานกระจายอยู่ทุก timezone ทั่วโลก)

### CitC และแนวคิด "ไม่มีใคร Clone ทั้ง Repository"

รายละเอียดที่ทำให้ Piper ต่างจาก Git โดยสิ้นเชิงคือวิธีที่วิศวกรเข้าถึงโค้ด ลองเปรียบเทียบให้เห็นภาพชัดเจน:

```
แนวทางแบบ Git (Distributed):
Developer เครื่อง A  ──clone──▶  สำเนาประวัติทั้งหมดในเครื่อง A
Developer เครื่อง B  ──clone──▶  สำเนาประวัติทั้งหมดในเครื่อง B
Developer เครื่อง C  ──clone──▶  สำเนาประวัติทั้งหมดในเครื่อง C
(แต่ละเครื่องมีสำเนาเต็ม ทำงาน offline ได้)

แนวทางแบบ Piper + CitC (Centralized + Virtual Workspace):
Developer เครื่อง A  ──มองผ่าน CitC──▶  Piper (server กลาง, เก็บทุกอย่างจริง)
Developer เครื่อง B  ──มองผ่าน CitC──▶  Piper (server กลาง, เก็บทุกอย่างจริง)
Developer เครื่อง C  ──มองผ่าน CitC──▶  Piper (server กลาง, เก็บทุกอย่างจริง)
(ไม่มีเครื่องไหนมีสำเนาเต็ม ต้องเชื่อมต่อกับ Piper ตลอดเวลาการทำงาน)
```

เมื่อวิศวกรของ Google เปิด workspace ใหม่ผ่าน CitC ระบบจะไม่ได้ดาวน์โหลดไฟล์ทั้งหมดของ repository ลงเครื่องจริง แต่จะสร้าง**มุมมองเสมือน (virtual view)** ที่แสดงไฟล์ทุกไฟล์เหมือนมีอยู่จริง ส่วนเนื้อหาไฟล์จะถูกดึงมาจาก Piper แบบ on-demand เมื่อถูกเปิดใช้งานจริงเท่านั้น — นี่คือแนวคิดเดียวกับที่เราจะเห็นอีกครั้งในรูปแบบที่ต่างออกไปเมื่อพูดถึง VFS for Git ของ Microsoft (Step 966) และ EdenFS ของ Meta (Step 967) ซึ่งเป็นข้อพิสูจน์ว่า **แนวคิด "virtualize การเข้าถึงไฟล์แทนการ clone ทุกอย่างลงเครื่องจริง" คือคำตอบร่วมที่ทุกบริษัทระดับนี้ค้นพบด้วยตัวเอง** แม้จะเริ่มต้นจากแนวคิดพื้นฐานคนละแบบ (Piper เป็น centralized ตั้งแต่ต้น ในขณะที่ Git และ Mercurial เป็น distributed)

ข้อดีของแนวทางนี้คือวิศวกรไม่จำเป็นต้องมีดิสก์ขนาดใหญ่พอจะเก็บ 86 เทราไบต์ (ซึ่งเป็นไปไม่ได้อยู่แล้วในทางปฏิบัติ) แต่ข้อแลกเปลี่ยนคือ **ไม่สามารถทำงานแบบ offline ได้เต็มรูปแบบเหมือน Git** เพราะทุกการกระทำต้องพึ่งพาการเชื่อมต่อกับ Piper อยู่เสมอ ซึ่งเป็นการแลกเปลี่ยนที่ Google ยอมรับได้ เพราะ infrastructure เครือข่ายภายในของ Google มีความเสถียรและรวดเร็วสูงมากอยู่แล้ว

### ทำไมตัวเลขเหล่านี้ถึงสำคัญต่อการเข้าใจ Part นี้

การเข้าใจสถิติเหล่านี้สำคัญมากก่อนจะไปดูเครื่องมือที่ Google สร้างขึ้นมารองรับมันใน Step 963 เพราะมันอธิบายได้ว่า **ทำไมเครื่องมือมาตรฐานอย่าง Git ธรรมดาถึงใช้ไม่ได้เลยที่ scale ระดับนี้** ย้อนกลับไปดูปัญหาที่เราเรียนใน **Part 63 Step 621** เรื่อง repository ขนาดใหญ่ — ปัญหาเรื่อง `git status` ช้า, `git clone` กินเวลานาน ที่เราเจอกับ repository ขนาดหลักร้อยกิกะไบต์ จะกลายเป็นปัญหาที่ **เป็นไปไม่ได้เลยในทางปฏิบัติ** ถ้าลองเอา Git มาตรฐานไปใช้กับ repository ขนาด 86 เทราไบต์ที่มีคนนับหมื่นเข้าถึงพร้อมกันตลอดเวลา นี่คือเหตุผลที่ Google เลือกสร้างระบบของตัวเองขึ้นมาทั้งหมดตั้งแต่ต้น แทนที่จะพยายามดัดแปลง Git ให้รองรับ scale ขนาดนี้

## Step 962: ทำไม Google เลือก Monorepo ทั้งบริษัท (ผูกกับ Trunk-Based Development)

การที่ Google เลือกเก็บโค้ดเกือบทั้งหมดของบริษัทไว้ใน repository เดียวไม่ใช่เรื่องบังเอิญ หรือเป็นเพียงมรดกทางประวัติศาสตร์ที่แก้ไม่ได้ — มันเป็น**การตัดสินใจเชิงกลยุทธ์ที่เกี่ยวพันแน่นแฟ้นกับปรัชญาการพัฒนาซอฟต์แวร์แบบ Trunk-Based Development** ที่เราเรียนไปแล้วอย่างละเอียดใน **Part 34**

### หลักการที่ผูกกันแน่นแฟ้น

Google บังคับใช้ 2 หลักการนี้ควบคู่กันเสมอ ไม่สามารถแยกจากกันได้ในทางปฏิบัติ:

1. **Monorepo** — โค้ดทั้งหมดอยู่ที่เดียว มองเห็นกันหมด
2. **Trunk-Based Development แบบเข้มงวดที่สุด** — วิศวกรแทบทุกคน commit เข้า **trunk เดียว** (Google เรียกว่า "head" หรือ "mainline") โดยตรง ไม่มี long-lived feature branch แบบที่หลายองค์กรคุ้นเคย การพัฒนาฟีเจอร์ใหม่ที่ยังไม่เสร็จจะถูกซ่อนไว้ด้วย **feature flag** แทนที่จะแยก branch (แนวคิดนี้เราเรียนไปแล้วใน Part 34 Step 336-337 เรื่อง Feature Flags/Toggles)

### ทำไมสองสิ่งนี้ต้องมาคู่กันเสมอ

**เหตุผลที่ 1: Trunk-Based Development ต้องการให้ทุกคน "เห็น" การเปลี่ยนแปลงล่าสุดตลอดเวลา**

หัวใจของ Trunk-Based Development คือการทำให้ trunk เป็น**ความจริงเพียงหนึ่งเดียว** ที่ทุกคนอ้างอิงตลอดเวลา ถ้าโค้ดกระจายอยู่คนละ repository (Polyrepo) การจะรู้ว่า "การเปลี่ยนแปลงล่าสุดในทุกส่วนของระบบ ณ ขณะนี้สอดคล้องกันหรือไม่" ทำได้ยากกว่ามาก เพราะแต่ละ repo มี trunk ของตัวเอง การจะเดินเช็คว่า trunk ของ repo A ที่เวลานี้ทำงานร่วมกับ trunk ของ repo B ได้จริงหรือไม่ ต้องอาศัยการประสานงานข้าม repo เพิ่มเติม แต่ใน Monorepo การ commit เข้า trunk เดียวหมายความว่า **ทุก commit คือสถานะของทั้งบริษัท ณ เวลานั้นจริง ๆ** ตรวจสอบความสอดคล้องได้ในจุดเดียว

**เหตุผลที่ 2: Atomic Cross-Project Commit คือสิ่งที่ทำให้ Trunk-Based Development ที่ scale ระดับนี้เป็นไปได้**

ดังที่เราเรียนไปแล้วใน **Part 82 Step 813** เรื่อง atomic commit ข้ามหลายโปรเจกต์ — Google ใช้ประโยชน์จากสิ่งนี้ในระดับที่ทั้งบริษัททำ ถ้าไลบรารีกลางตัวหนึ่งต้องเปลี่ยน API วิศวกรที่ Google สามารถเปิดการเปลี่ยนแปลงเดียว (Piper เรียกว่า **changelist หรือ CL**) ที่ครอบคลุมทั้งไลบรารีกลางและทุกจุดที่เรียกใช้มันทั่วทั้งบริษัทพร้อมกัน — สิ่งนี้เป็นไปไม่ได้เลยถ้าโค้ดกระจายอยู่คนละ repository เพราะจะต้องรอให้แต่ละทีมอัปเกรด dependency version ของตัวเองตามจังหวะที่ต่างกัน ซึ่งขัดกับหลักการของ Trunk-Based Development ที่ต้องการให้ trunk ทำงานได้สมบูรณ์ตลอดเวลา (always releasable)

**เหตุผลที่ 3: การกระจาย branch จำนวนมากขัดกับปรัชญา "There Should Be One Way To Do It" ของ Google**

Google เชื่อในหลักการที่ว่า **ควรมีวิธีทำสิ่งหนึ่งสิ่งเดียวที่ถูกต้องเพียงวิธีเดียว** ไม่ใช่ให้แต่ละทีมเลือก branching strategy ของตัวเองอย่างอิสระ (ต่างจากองค์กรทั่วไปที่บางทีมอาจใช้ Git Flow บางทีมใช้ GitHub Flow) การมี Monorepo + Trunk-Based Development แบบเดียวทั้งบริษัททำให้ทุกวิศวกรไม่ว่าจะย้ายไปทำงานทีมไหนก็ใช้ workflow เดียวกัน ลดต้นทุนการเรียนรู้ (cognitive overhead) เมื่อวิศวกรเปลี่ยนทีมบ่อย ซึ่งเกิดขึ้นบ่อยมากในองค์กรขนาดใหญ่แบบ Google

### Large-Scale Change (LSC) — ผลผลิตโดยตรงของแนวคิดนี้

เราได้เกริ่นถึงแนวคิดนี้ไปแล้วเล็กน้อยใน **Part 82 Step 813** แต่ควรย้ำอีกครั้งในบริบทนี้: Google มีกระบวนการที่เรียกว่า **Large-Scale Change (LSC)** ซึ่งหมายถึงการเปลี่ยนแปลงที่กระทบไฟล์จำนวนมากทั่วทั้ง Monorepo ในคราวเดียว (บางครั้งกระทบไฟล์หลายหมื่นถึงหลายแสนไฟล์) กระบวนการนี้เกิดขึ้นเป็นประจำ**หลายพันครั้งต่อปี** ในระดับทั้งบริษัท เช่น:

- อัปเกรด compiler หรือ runtime version ทั่วทั้งบริษัท
- แก้ security vulnerability ที่กระทบ library กลางตัวหนึ่งซึ่งถูกใช้อยู่นับพันจุด
- เปลี่ยนมาตรฐานการเขียนโค้ด (coding convention) ทั่วทั้งองค์กรด้วย automated codemod

สิ่งนี้ทำได้เพราะ Piper เป็น Monorepo เดียว และ trunk-based development ทำให้ทุกจุดที่ต้องแก้ไขอยู่ใน branch เดียวกันเสมอ (ไม่ต้องไล่ merge เข้า feature branch ที่ค้างอยู่นับร้อยอันเหมือนที่จะเกิดขึ้นถ้าใช้ long-lived branching)

> **ข้อคิดสำคัญ:** Monorepo ของ Google ไม่ใช่แค่ "ที่เก็บโค้ดขนาดใหญ่" — มันคือส่วนหนึ่งของระบบความคิดทั้งหมดที่ผูกกับ Trunk-Based Development, Feature Flags, และวัฒนธรรมวิศวกรรมที่เข้มงวดเรื่องการทดสอบอัตโนมัติ ถ้าดึงเอา Monorepo ออกมาใช้เดี่ยว ๆ โดยไม่มีองค์ประกอบอื่นเหล่านี้ประกอบ จะไม่ได้ประโยชน์แบบเดียวกับที่ Google ได้เลย

## Step 963: เครื่องมือที่ Google สร้างมารองรับ scale ขนาดนี้ (Bazel)

ใน **Part 82 Step 817** เราได้แนะนำ Bazel ในฐานะหนึ่งในเครื่องมือ build system ที่รองรับ Monorepo ไปแล้วในภาพรวม ใน Step นี้เราจะเจาะลึกว่าทำไม **Git ธรรมดาถึงใช้ไม่ได้เลย** ที่ scale ของ Google และ Bazel เข้ามาแก้ปัญหาอะไรบ้างอย่างเป็นระบบ

### ทำไม Git ธรรมดาใช้ไม่ไหวที่ scale ของ Google

ลองจินตนาการว่าถ้า Google พยายามใช้ Git แบบมาตรฐาน (แม้จะใช้เทคนิคขั้นสูงทุกอย่างที่เราเรียนใน Part 63 ครบถ้วน — shallow clone, partial clone, sparse checkout, git maintenance) ปัญหาที่จะเกิดขึ้นมีดังนี้:

1. **ไม่มี client เครื่องไหนสามารถเก็บสำเนา 86 เทราไบต์ได้จริง** — นี่คือข้อจำกัดทางกายภาพล้วน ๆ ไม่ใช่แค่เรื่องความเร็ว ดิสก์ของเครื่อง laptop ทั่วไปไม่มีทางเก็บข้อมูลระดับนี้ได้แม้จะใช้ partial clone ที่ดีที่สุดก็ตาม เพราะแม้แต่ metadata ของ tree/commit object เพียงอย่างเดียว (ไม่รวม blob) ของ repository ขนาดนี้ก็ยังใหญ่เกินกว่าจะจัดการแบบ local ได้สะดวก
2. **Git ถูกออกแบบมาให้เป็น Distributed VCS ที่ทุกเครื่องมีสำเนาประวัติแบบเต็ม** — ปรัชญานี้ (ที่เราชื่นชมไปแล้วใน Part 01 Step 5 ว่าเป็นจุดแข็งของ Git) กลับกลายเป็นข้อจำกัดที่ scale ระดับ Google เพราะ Google ต้องการรูปแบบที่ตรงข้ามเลย คือ **centralized ที่มี server กลางเดียวเป็นความจริงหนึ่งเดียว** และ client เห็นแค่ส่วนที่ต้องใช้งานจริงผ่าน virtual workspace (CitC) ไม่ใช่ทุกคนมีสำเนาเต็ม
3. **การ build/test ทุกอย่างในทุกครั้งเป็นไปไม่ได้เลย** — ถ้ามีวิศวกร 25,000 คน commit วันละหลายหมื่นครั้ง การจะ build/test ทุกส่วนของ repository ทุกครั้งที่มีการเปลี่ยนแปลง (เหมือนที่ CI ทั่วไปทำ) จะใช้ทรัพยากรมหาศาลเกินกว่าจะเป็นไปได้จริง แม้จะมี datacenter ขนาดใหญ่แค่ไหนก็ตาม

จุดที่ 3 นี้คือปัญหาที่ตรงกับสิ่งที่เราเรียนไปแล้วใน **Part 82 Step 814** เรื่อง "CI ช้าถ้าไม่จัดการ Selective Build ให้ดี" เพียงแต่ที่ scale ของ Google ปัญหานี้ไม่ใช่แค่ "ช้า" แต่คือ **เป็นไปไม่ได้ในทางปฏิบัติเลยถ้าไม่มีเครื่องมือที่ฉลาดพอ**

### Bazel คืออะไรกันแน่ และมาจากไหน

**Bazel** คือ build system แบบโอเพนซอร์สที่ Google เปิดเผยต่อสาธารณะในปี 2015 โดยมันคือเวอร์ชันที่ปรับปรุงจากระบบภายในชื่อ **Blaze** ที่ทีมวิศวกรรมของ Google พัฒนาและใช้งานภายในมานานนับสิบปีก่อนหน้านั้น (ชื่อ "Bazel" มาจากการสลับตัวอักษรของคำว่า "Blaze" นั่นเอง) Blaze/Bazel ถูกออกแบบมาตั้งแต่ต้นเพื่อแก้ปัญหาการ build โค้ดในสภาพแวดล้อม Monorepo ขนาดมหึมาของ Google โดยเฉพาะ

### หลักการทำงานที่แก้ปัญหา scale ได้จริง

**1. Explicit Dependency Graph (การประกาศ dependency ทุกจุดอย่างชัดเจน)**

ทุก target ใน Bazel (ไม่ว่าจะเป็น library, binary, test) ต้องประกาศ dependency ของตัวเองอย่างชัดเจนในไฟล์ `BUILD` โดยไม่มีการ "เดา" หรือ scan โค้ดหาความสัมพันธ์เองแบบเครื่องมืออื่น ๆ:

```python
# BUILD file ตัวอย่างในสไตล์ที่ Google ใช้จริง
cc_library(
    name = "search_ranking",
    srcs = ["ranking.cc"],
    hdrs = ["ranking.h"],
    deps = [
        "//base:logging",
        "//storage:index_reader",
    ],
)
```

การบังคับให้ประกาศทุกอย่างชัดเจนแบบนี้ทำให้ Bazel **รู้กราฟความสัมพันธ์ทั้งหมดของ repository ล่วงหน้าแบบแม่นยำ 100%** ไม่ต้องเดา ซึ่งเป็นรากฐานสำคัญที่ทำให้ความสามารถถัดไปเป็นไปได้

**2. Selective Build/Test แบบแม่นยำระดับ target**

เมื่อรู้กราฟทั้งหมดแบบแม่นยำแล้ว Bazel สามารถคำนวณได้ว่า **การเปลี่ยนแปลงไฟล์หนึ่งไฟล์ กระทบ target ใดบ้างในทั้ง Monorepo อย่างแม่นยำ** ไม่ต้อง build/test ทุกอย่างเหมือนที่กล่าวถึงในปัญหาข้อ 3 ข้างต้น คำสั่งอย่าง `bazel test //...` ที่รันเฉพาะ target ที่ได้รับผลกระทบจริง (affected targets) ทำให้ scale การ build/test ได้ตามสัดส่วนของการเปลี่ยนแปลงจริง ไม่ใช่ตามขนาดทั้งหมดของ repository

**3. Remote Caching และ Remote Execution ระดับบริษัท**

หัวใจสำคัญที่สุดที่ทำให้ Bazel ใช้งานได้จริงที่ scale ของ Google คือระบบ cache แบบกระจายทั้งบริษัท:

- ทุกครั้งที่มีการ build target ใด ๆ ผลลัพธ์จะถูก cache ไว้โดยผูกกับ hash ของ input ทั้งหมด (source code, compiler flags, dependency versions)
- ถ้าวิศวกรคนอื่นที่ไหนก็ตามในบริษัทเคย build target เดียวกันด้วย input ชุดเดียวกันมาก่อน (ซึ่งเกิดขึ้นบ่อยมากเพราะโค้ดส่วนใหญ่ไม่ได้เปลี่ยนทุกวัน) ระบบจะดึงผลลัพธ์จาก cache ทันทีแทนที่จะ build ใหม่จริง ๆ
- **Remote Execution** ไปไกลกว่านั้นอีกขั้น คือแทนที่จะ build บนเครื่องของวิศวกรเอง งาน build จะถูกกระจายไปรันบน compute cluster ขนาดใหญ่ของ Google แบบขนานกันหลายพันงานพร้อมกัน ทำให้แม้แต่การ build โปรเจกต์ขนาดใหญ่มากก็เสร็จในเวลาไม่กี่นาที

**4. Hermetic Build (Build ที่ทำซ้ำได้เป๊ะทุกครั้ง)**

Bazel ควบคุม toolchain และ dependency ทั้งหมดอย่างเข้มงวดจนสามารถรับประกันได้ว่า **build ผลลัพธ์เดียวกันทุกครั้งไม่ว่าจะรันที่เครื่องไหนหรือเวลาไหน** คุณสมบัตินี้สำคัญมากเพราะเป็นเงื่อนไขที่ทำให้ remote caching ข้างต้นเชื่อถือได้ — ถ้า build ไม่ hermetic (เช่น ผลลัพธ์ขึ้นกับ version ของ library ที่ติดตั้งบนเครื่องแต่ละคนต่างกัน) การ cache ข้ามเครื่องจะให้ผลลัพธ์ที่ผิดพลาดได้

### ตัวอย่างที่เป็นรูปธรรม: ผลต่างของ CI ก่อนและหลังมี Selective Build

เพื่อให้เห็นภาพชัดขึ้นว่าทำไม selective build ถึงจำเป็นที่ scale ของ Google ลองเปรียบเทียบสถานการณ์สมมติต่อไปนี้ ซึ่งใช้หลักการเดียวกับที่เราเรียนไปแล้วใน **Part 82 Step 814**:

```
สถานการณ์: มีวิศวกร 25,000 คน commit รวมกันหลายหมื่นครั้งต่อวัน
Repository มี target (โมดูล/ไลบรารี/binary) รวมกันหลายล้าน target

ถ้าไม่มี Selective Build (build ทุกอย่างทุกครั้งที่มีการเปลี่ยนแปลง):
  → ทุก commit ต้อง build/test เป้าหมายหลายล้าน target
  → คูณด้วยหลายหมื่น commit ต่อวัน
  → ปริมาณงาน build/test ต่อวันจะสูงเกินกว่า compute cluster ใด ๆ จะรองรับไหว

ถ้ามี Selective Build ผ่าน Bazel (build เฉพาะ target ที่ได้รับผลกระทบจริง):
  → แต่ละ commit กระทบ target จริงเพียงหลักสิบถึงหลักร้อย target โดยเฉลี่ย
  → ปริมาณงานลดลงจากระดับ "ล้าน" เหลือระดับ "ร้อย" ต่อการเปลี่ยนแปลงหนึ่งครั้ง
  → ประกอบกับ Remote Caching ที่ทำให้ target ที่เคย build ด้วย input เดิมไม่ต้อง build ซ้ำ
  → ทำให้ scale การ build/test ได้จริงในทางปฏิบัติ
```

ตัวเลขในตัวอย่างนี้เป็นการอธิบายเชิงหลักการเพื่อให้เห็นสัดส่วนของปัญหา ไม่ใช่ตัวเลขที่ Google เปิดเผยอย่างเป็นทางการ แต่หลักการ **"ลดขอบเขตงานจากทั้ง repository เหลือแค่ส่วนที่ได้รับผลกระทบจริง บวกกับการ cache ผลลัพธ์ที่เคยคำนวณแล้ว"** คือแก่นของคำตอบที่ทำให้ Monorepo ขนาดนี้ยังคง build/test ได้ทันเวลาจริงในทุกวัน

### Starlark — ภาษาที่ใช้เขียนไฟล์ BUILD

ไฟล์ `BUILD` ที่เราเห็นตัวอย่างไปแล้วนั้น แท้จริงเขียนด้วยภาษาที่ชื่อ **Starlark** (เดิมเรียกว่า Skylark) ซึ่งเป็นภาษาสไตล์คล้าย Python แต่ถูกออกแบบให้เป็น **deterministic** (ไม่มี side effect ที่คาดเดาไม่ได้) และรันได้เร็วมาก เพื่อให้ Bazel สามารถวิเคราะห์ dependency graph ของ target หลายล้านตัวได้อย่างรวดเร็วและแม่นยำ ปัจจุบัน Starlark ถูกใช้ไม่ใช่แค่ใน Bazel เท่านั้น แต่ยังถูกนำไปใช้เป็นภาษา configuration ในเครื่องมืออื่น ๆ อีกหลายตัวในวงการ build system

### ต้นทุนของ Bazel ที่ต้องรู้

ดังที่กล่าวไปแล้วใน Part 82 Step 817 **Learning curve ของ Bazel สูงมาก** และการเขียนไฟล์ `BUILD` กำกับทุกโมดูลอย่างละเอียดคือภาระที่แท้จริง ทีมที่ Google เองก็มีวิศวกรเฉพาะทางจำนวนมาก (Developer Infrastructure / "devinfra" team) ที่ทำหน้าที่ดูแลและพัฒนา build system นี้อย่างต่อเนื่องเป็นงานเต็มเวลา — นี่ไม่ใช่เครื่องมือที่ "ติดตั้งแล้วจบ" แต่เป็นระบบที่ต้องการการลงทุนบำรุงรักษาต่อเนื่องตลอดไป ซึ่งเป็นประเด็นที่เราจะกลับมาย้ำอีกครั้งใน Step 968 และ 969

Meta (Facebook เดิม) เป็นกรณีศึกษาที่น่าสนใจต่างจาก Google เพราะ Meta **เลือกใช้ Git ในตอนแรก แล้วเปลี่ยนไปใช้ Mercurial ในภายหลัง** ซึ่งเป็นทิศทางที่ตรงข้ามกับสิ่งที่คนส่วนใหญ่คาดคิด (เพราะทุกวันนี้ Git เป็นมาตรฐานที่ครองตลาดอย่างท่วมท้นตามที่เราเรียนไปแล้วใน Part 01 Step 5)

### จุดเริ่มต้น: ทำไม Facebook ถึงเลิกใช้ Git

ในช่วงต้นทศวรรษ 2010 Facebook มี Monorepo หลักสำหรับโค้ด backend (โดยเฉพาะโค้ดของเว็บไซต์ Facebook.com ที่เขียนด้วย PHP/Hack เป็นหลัก เรียกภายในว่า `www` repository) ที่กำลังเติบโตอย่างรวดเร็ว ทีมวิศวกรของ Facebook ได้ทดลองใช้ Git กับ repository นี้ แต่พบปัญหาการ scale ที่รุนแรงมาก ปัญหาหลัก ๆ ที่ Facebook เผชิญมีลักษณะเดียวกับปัญหาที่เราเรียนไปแล้วใน **Part 63 Step 621**:

- โครงสร้างข้อมูลภายในของ Git ในยุคนั้น (โดยเฉพาะการจัดการ index file และการเดินกราฟ commit) ไม่ได้ถูกออกแบบมาให้รองรับ repository ที่มีทั้งไฟล์จำนวนมหาศาลและประวัติ commit ที่เพิ่มขึ้นเร็วมากพร้อมกัน
- คำสั่งพื้นฐานอย่าง `git status`, `git log` เริ่มช้าลงอย่างเห็นได้ชัดเมื่อ repository โตขึ้นเรื่อย ๆ จนกระทบประสบการณ์การทำงานประจำวันของวิศวกรหลายพันคน

ทีมวิศวกรของ Facebook ตัดสินใจว่า **Mercurial (Hg)** ซึ่งเป็น Distributed VCS อีกตัวหนึ่งที่เกิดขึ้นในปีเดียวกับ Git (2005) มีสถาปัตยกรรมภายในที่ **ยืดหยุ่นกว่าและปรับแต่งเพื่อรองรับ scale ได้ง่ายกว่า** โดยเฉพาะโครงสร้างข้อมูลที่ Mercurial ใช้ (revlog) เปิดช่องให้ปรับแต่งเรื่องการ index และการค้นหาได้สะดวกกว่า Facebook จึงตัดสินใจย้าย `www` repository จาก Git ไปเป็น Mercurial ในช่วงราวปี 2013-2014 ซึ่งเป็นการย้ายข้อมูลระดับองค์กรที่มีความซับซ้อนสูงมาก (ทำนองเดียวกับที่เราเรียนเรื่อง Migration ไปแล้วใน **Part 93**) และได้เผยแพร่รายละเอียดทางเทคนิคเรื่องนี้ต่อสาธารณะผ่านบทความทางวิศวกรรมชื่อ **"Scaling Mercurial at Facebook"** ในปี 2014

### Mercurial เวอร์ชันที่ Facebook ปรับแต่งเอง

สิ่งสำคัญที่ต้องเข้าใจคือ Facebook **ไม่ได้ใช้ Mercurial แบบ off-the-shelf ตรง ๆ** แต่ลงทุนพัฒนา extension และปรับปรุงประสิทธิภาพของ Mercurial อย่างต่อเนื่องเพื่อให้รองรับ scale ของตัวเองได้จริง ตัวอย่างการปรับปรุงที่สำคัญได้แก่:

- **remotefilelog extension** — แนวคิดคล้ายกับ Partial Clone ของ Git ที่เราเรียนใน Part 63 Step 623 (แต่ Facebook พัฒนาแนวคิดนี้ขึ้นสำหรับ Mercurial ก่อนที่ Git จะมี partial clone อย่างเป็นทางการเสียอีก) คือแทนที่จะดาวน์โหลดเนื้อหาไฟล์ (file content) ทั้งหมดมาไว้ในเครื่อง จะดึงมาแบบ lazy เมื่อจำเป็นต้องใช้จริงเท่านั้น
- การปรับปรุงโครงสร้างข้อมูลภายในและ indexing ให้รองรับจำนวนไฟล์และจำนวน commit ที่เพิ่มขึ้นอย่างรวดเร็วโดยไม่เสื่อมประสิทธิภาพ
- Facebook ได้ส่ง patch และการปรับปรุงจำนวนมากกลับเข้าไปใน Mercurial upstream ซึ่งทำให้ชุมชน Mercurial โดยรวมได้ประโยชน์ไปด้วย ไม่ใช่แค่ Facebook ฝ่ายเดียว

### ทำไม Mercurial ไม่ใช่ Git — เหตุผลเชิงสถาปัตยกรรมภายใน

คำถามที่หลายคนสงสัยคือทำไม Facebook ไม่เลือกปรับแต่ง Git เองแบบที่ Microsoft ทำกับ Windows repo (Step 966) เหตุผลหลักที่ทีมวิศวกรของ Facebook เคยอธิบายไว้ในบทความทางวิศวกรรมช่วงปี 2013-2014 เกี่ยวข้องกับ**ความแตกต่างของโครงสร้างข้อมูลภายใน**:

- Mercurial เก็บประวัติของแต่ละไฟล์ในโครงสร้างที่เรียกว่า **revlog** ซึ่งมีลักษณะเป็น append-only log ต่อไฟล์ ทำให้การเพิ่มความสามารถเรื่อง lazy-loading เนื้อหาไฟล์ (สิ่งที่ remotefilelog extension ทำ) ทำได้โดยไม่ต้องแตะโครงสร้างข้อมูลหลักของระบบมากนัก
- Git ในยุคนั้น (ราวปี 2013) ยังไม่มีกลไกที่ยืดหยุ่นพอสำหรับการทำ partial/lazy fetch แบบเป็นทางการ (partial clone ของ Git อย่างเป็นทางการเพิ่งมาถึงใน Git 2.19 ปี 2018 ซึ่งช้ากว่าที่ Facebook ต้องการแก้ปัญหานี้หลายปี) การจะดัดแปลง Git ให้ทำสิ่งเดียวกันในตอนนั้นจึงต้องเปลี่ยนแปลงส่วนแกนกลางของ Git มากกว่า
- Mercurial ยังมีสถาปัตยกรรมแบบ extension ที่เปิดช่องให้เสริมความสามารถใหม่ ๆ ได้ค่อนข้างอิสระ (เขียนด้วย Python เป็นหลักในตอนนั้น) ซึ่งเหมาะกับแนวทางที่ Facebook ต้องการทดลองและปรับปรุงอย่างรวดเร็วต่อเนื่อง

ข้อสังเกตที่น่าสนใจคือ **ปัญหาเดียวกันที่ Facebook เจอในปี 2013 ภายหลัง Git ก็แก้ได้ด้วยตัวเองในปี 2018 ผ่าน partial clone** ซึ่งเป็นเครื่องยืนยันว่าปัญหานี้เป็นปัญหาจริงของทุก VCS ไม่ใช่ข้อจำกัดเฉพาะของ Git เพียงอย่างเดียว เพียงแต่จังหวะเวลาที่แต่ละบริษัทต้องการคำตอบไม่ตรงกับจังหวะที่แต่ละเครื่องมือพร้อมให้คำตอบนั้น

### Buck — Build System ของ Meta ที่ขนานไปกับ Bazel ของ Google

เช่นเดียวกับที่ Google มี Bazel/Blaze สำหรับแก้ปัญหา build ใน Monorepo ขนาดใหญ่ Meta (ในตอนนั้นยังชื่อ Facebook) ก็พัฒนาเครื่องมือของตัวเองขึ้นมาคู่ขนานกันชื่อ **Buck** ซึ่งเปิดเผยเป็นโอเพนซอร์สในปี 2013 หลักการพื้นฐานของ Buck คล้ายกับ Bazel มาก (explicit dependency declaration, selective build, caching) เพราะทั้งสองบริษัทเผชิญปัญหาเดียวกันในช่วงเวลาใกล้เคียงกัน ต่อมา Meta ได้พัฒนา **Buck2** ซึ่งเป็นการเขียนใหม่ทั้งหมดด้วยภาษา Rust เพื่อให้ทำงานได้เร็วและรองรับ scale ได้ดีขึ้นไปอีก และเปิดเผยเป็นโอเพนซอร์สในปี 2023 ปัจจุบัน Buck2 ทำงานร่วมกับ EdenFS และ Sapling เป็นชุดเครื่องมือ (toolchain) เดียวกันที่ Meta ใช้ดูแล Monorepo ของตัวเอง

### จุดเปลี่ยนต่อมา: Sapling

เมื่อเวลาผ่านไป แม้ Mercurial ที่ปรับแต่งแล้วจะรองรับ scale ได้ดีขึ้นมาก แต่ Meta ยังคงเจอข้อจำกัดบางอย่าง (เช่น เรื่องประสบการณ์การใช้งาน command-line ที่ผู้ใช้จำนวนมากคุ้นเคยกับ Git มากกว่า และข้อจำกัดทางสถาปัตยกรรมบางจุดของ Mercurial เองที่แก้ไขต่อได้ยากในระยะยาว) ทีม Source Control ของ Meta จึงพัฒนาระบบรุ่นถัดไปขึ้นมาชื่อ **Sapling**

Sapling ถูก **เปิดเผยเป็นโอเพนซอร์สอย่างเป็นทางการในปี 2022** จุดเด่นสำคัญของ Sapling มีดังนี้:

- **Sapling client** เป็นโปรแกรม command-line ที่เขียนขึ้นใหม่ (ด้วยภาษา Rust เป็นหลัก) โดยออกแบบ UX/UI ของคำสั่งให้เรียบง่ายและทันสมัยกว่าทั้ง Git และ Mercurial ดั้งเดิม แต่ยังคงแนวคิดพื้นฐานที่ใกล้เคียงกับ Mercurial อยู่มาก
- Sapling รองรับการทำงานร่วมกับทั้ง backend ของ Meta เอง และยังสามารถใช้เป็น client สำหรับ **Git repository ทั่วไป** ได้ด้วย (กล่าวคือสามารถใช้ Sapling เป็นหน้าตาคำสั่งที่ดีกว่าในการทำงานกับ repository บน GitHub ได้ โดยไม่จำเป็นต้องเกี่ยวข้องกับ Meta เลย)
- Sapling มาพร้อมกับระบบเสริมสำคัญ 2 ตัวที่เปิดเผยเป็นโอเพนซอร์สคู่กัน คือ **Mononoke** (source control server ฝั่ง backend ที่เขียนด้วย Rust ออกแบบมาให้รองรับ scale ระดับ Meta โดยเฉพาะ) และ **EdenFS** (virtual filesystem ที่เราจะเจาะลึกใน Step 967)

### เปรียบเทียบเส้นทางของ Meta กับ Google

| ประเด็น | Google | Meta |
|---|---|---|
| ระบบที่ใช้ | Piper (สร้างขึ้นเองทั้งหมด ไม่อิง Git/Mercurial) | เริ่มจาก Git → ย้ายไป Mercurial (ปรับแต่งเอง) → พัฒนาต่อเป็น Sapling |
| สถาปัตยกรรม | Centralized โดยสมบูรณ์ตั้งแต่ต้น | Distributed (มรดกจาก Mercurial) แต่ปรับให้ทำงานคล้าย centralized มากขึ้นผ่าน lazy fetching |
| แนวทางแก้ scale | สร้างระบบใหม่ทั้งหมด (Piper + Bazel) | ปรับปรุงระบบที่มีอยู่แล้วต่อเนื่อง (Mercurial → Sapling) |
| เปิดเผยสู่สาธารณะ | Bazel เป็นโอเพนซอร์ส, Piper ไม่เปิดเผย | Sapling, Mononoke, EdenFS เปิดเผยเป็นโอเพนซอร์สทั้งหมด |

ข้อสังเกตสำคัญ: ทั้งสองบริษัทเดินทางคนละเส้นทาง แต่ **ปลายทางที่ต้องเจอเหมือนกันคือ Git แบบมาตรฐานไม่พอสำหรับ scale ระดับนี้** และทั้งคู่ต้องลงทุนพัฒนาเครื่องมือของตัวเองอย่างจริงจังต่อเนื่องหลายปีจึงจะไปถึงจุดที่ใช้งานได้จริง

## Step 965: Microsoft Windows repo — หนึ่งใน Git repository ที่ใหญ่ที่สุดที่เคยใช้งานจริง

ต่างจาก Google และ Meta ที่เปลี่ยนไปใช้ระบบของตัวเองหรือ Mercurial กรณีของ Microsoft น่าสนใจเป็นพิเศษเพราะ **Microsoft เลือกที่จะทำให้ Git เองรองรับ scale ระดับนี้ให้ได้** แทนที่จะทิ้ง Git ไปใช้ระบบอื่น ซึ่งเป็นแนวทางที่ต่างไปจากทั้ง Google และ Meta อย่างชัดเจน

### จุดเริ่มต้น: การรวม Source Depot หลายร้อยชุดเข้าเป็น Git repository เดียว

ก่อนหน้าที่จะย้ายมาใช้ Git โค้ดของ Windows ถูกเก็บกระจายอยู่ใน **Source Depot** (ระบบ version control ภายในของ Microsoft เอง ที่มีสถาปัตยกรรมคล้าย Perforce) หลายร้อยชุดแยกกัน ทีมวิศวกรรมของ Microsoft ตัดสินใจว่าต้องการรวมโค้ดทั้งหมดของ Windows ให้กลายเป็น **Git repository เดียว** เพื่อให้ได้ประโยชน์แบบเดียวกับที่เราเรียนไปแล้วใน Part 82 เรื่อง Monorepo (atomic commit ข้ามส่วนประกอบต่าง ๆ ของ Windows, การแชร์โค้ดที่ง่ายขึ้น) โดยยังคงต้องการใช้ **Git** เพราะ Git เป็นเครื่องมือมาตรฐานที่วิศวกรทั่วโลกคุ้นเคยอยู่แล้ว ไม่ต้องการให้วิศวกรของ Microsoft ต้องเรียนรู้เครื่องมือใหม่ทั้งหมด

### ขนาดของ Windows repository

ดังที่เราได้เกริ่นไว้บ้างแล้วใน **Part 63 Step 621** และ **Part 82 Step 811** ตัวเลขที่ Microsoft เปิดเผยต่อสาธารณะผ่านบทความทางวิศวกรรม (โดยเฉพาะบล็อกโพสต์ประกาศเปิดตัว GVFS ในปี 2017) มีดังนี้:

| สถิติ | ตัวเลข |
|---|---|
| ขนาดของ working directory เมื่อ checkout เต็ม | มากกว่า 300 GB |
| จำนวนไฟล์ | ประมาณ 3.5 ล้านไฟล์ |
| จำนวนวิศวกรที่ทำงานบน repository นี้ | หลายพันคน (Microsoft เคยระบุตัวเลขระดับหลายพันคนที่ทำงานบน Windows codebase) |
| เวลาที่ใช้ในการ `git clone` แบบเต็ม (ก่อนมีเครื่องมือช่วย) | นานถึงระดับหลายชั่วโมง (มีรายงานว่ายาวนานถึงราว 12 ชั่วโมงในบางกรณี) |
| เวลาที่ใช้ในการ `git checkout` เปลี่ยน branch | นานหลายชั่วโมงเช่นกัน เพราะต้องเขียนไฟล์นับล้านไฟล์ลงดิสก์ |

ตัวเลขเหล่านี้ทำให้ Windows repository ถูกยกให้เป็นหนึ่งใน **Git repository ที่ใหญ่ที่สุดเท่าที่เคยมีการใช้งานจริงในเชิงพาณิชย์** และเป็นกรณีทดสอบที่โหดที่สุดกรณีหนึ่งสำหรับ Git core เอง

### ปัญหาที่ Git มาตรฐานเจอกับ Windows repo

เมื่อทีมวิศวกรรมของ Microsoft ลองใช้ Git มาตรฐาน (แม้จะเป็น Git เวอร์ชันที่ดีที่สุดในขณะนั้น) กับ Windows repository เต็มรูปแบบ ปัญหาที่เจอตรงกับสิ่งที่เราเรียนไปแล้วใน **Part 63 Step 621** อย่างชัดเจนแต่รุนแรงกว่ามาก:

1. `git clone` แบบเต็มใช้เวลานานเกินกว่าจะยอมรับได้ในการทำงานประจำวัน
2. `git checkout` และ `git status` ที่ต้องสแกน/เขียนไฟล์ 3.5 ล้านไฟล์ลงดิสก์และเทียบสถานะ ทำให้เครื่องของวิศวกรทำงานหนักเกินไปจนแทบใช้งานไม่ได้จริง แม้จะเป็นเครื่องระดับ workstation ที่ทรงพลังก็ตาม
3. Object database ที่บวมขึ้นอย่างรวดเร็วจากการที่วิศวกรหลายพันคน commit เข้ามาต่อเนื่องทำให้การ garbage collect และ repack กลายเป็นภาระหนักที่ต้องจัดการเป็นพิเศษ

จุดนี้เองที่นำไปสู่การพัฒนาเครื่องมือเสริมที่เราจะเจาะลึกใน Step 966 — Microsoft เลือกแนวทางที่ต่างจาก Google (สร้างระบบใหม่ทั้งหมด) และต่างจาก Meta บางส่วน (เปลี่ยนไปใช้ VCS อื่น) คือ **พยายามทำให้ Git เองรองรับ scale นี้ได้ โดยสร้างชั้นเสริมพิเศษครอบ Git ไว้** ซึ่งท้ายที่สุดแล้วส่วนหนึ่งของงานนี้ยังถูกส่งกลับ (upstream) เข้าไปเป็นฟีเจอร์มาตรฐานของ Git core ด้วย เป็นประโยชน์ต่อผู้ใช้ Git ทั่วโลกไม่ใช่แค่ Microsoft เอง

## Step 966: VFS for Git / Scalar ที่ Microsoft สร้างมาแก้ปัญหา scale ของ Windows repo

เราได้เรียนเรื่อง VFS for Git และ Scalar ไปแล้วในเชิงเทคนิคอย่างละเอียดที่ **Part 63 Step 629** — ใน Step นี้เราจะไม่พูดซ้ำรายละเอียดการใช้งาน แต่จะเติมเต็ม**บริบทของกรณีศึกษา** ว่าเครื่องมือเหล่านี้เกิดขึ้นมาได้อย่างไรและส่งผลกระทบต่อวงการ Git โดยรวมอย่างไร

### ไทม์ไลน์การพัฒนา

| ปี | เหตุการณ์ |
|---|---|
| ราว 2015-2016 | ทีมวิศวกรรมของ Microsoft เริ่มโครงการย้าย Windows codebase จาก Source Depot มาเป็น Git repository เดียว และพบว่า Git มาตรฐานรองรับ scale นี้ไม่ไหว |
| 2017 | Microsoft ประกาศเปิดตัว **GVFS (Git Virtual File System)** ต่อสาธารณะ พร้อมเผยแพร่ตัวเลขสถิติของ Windows repository ที่กล่าวถึงใน Step 965 |
| 2017-2019 | GVFS ถูกใช้งานจริงกับทีมวิศวกร Windows หลายพันคน และช่วยลดเวลา clone ที่เคยยาวนานหลายชั่วโมงให้เหลือเพียงไม่กี่นาที (มีรายงานว่าลดจากราว 12 ชั่วโมงเหลือราว 15 นาที) |
| 2019-2020 | Microsoft พัฒนา **Scalar** ขึ้นเป็นรุ่นถัดไป โดยเปลี่ยนแนวทางจากการ virtualize filesystem แบบเต็มรูปแบบ มาเป็นการรวมฟีเจอร์มาตรฐานของ Git (partial clone, sparse checkout, maintenance) ให้ทำงานร่วมกันอย่างมีประสิทธิภาพที่สุดแทน |
| 2022 (Git 2.38) | **Scalar ถูกรวมเข้าเป็นส่วนหนึ่งของ Git core อย่างเป็นทางการ** ทำให้ผู้ใช้ Git ทั่วโลกทุกคนได้ประโยชน์จากงานวิจัยและพัฒนานี้โดยไม่ต้องติดตั้งอะไรเพิ่มเติมเลย |

### ทำไมต้อง GVFS ก่อน ทั้งที่ Partial Clone ดูเหมือนจะแก้ปัญหาได้เหมือนกัน

ประเด็นที่น่าสนใจและมักถูกมองข้ามคือ**ลำดับเวลา** — ถ้าดูจากตารางไทม์ไลน์ข้างต้น จะเห็นว่า Microsoft เริ่มพัฒนา GVFS ตั้งแต่ราวปี 2015-2017 ในขณะที่ **Partial Clone อย่างเป็นทางการของ Git core เพิ่งมาถึงใน Git 2.19 ปี 2018** พูดอีกแบบคือ **ตอนที่ Microsoft ต้องการคำตอบ Git core ยังไม่มีเครื่องมือมาตรฐานที่แก้ปัญหานี้ได้เลย** ทีมวิศวกรของ Microsoft จึงจำเป็นต้องสร้าง GVFS ขึ้นมาด้วยแนวทางที่แตกต่างออกไปโดยสิ้นเชิง (virtualize ทั้ง filesystem ผ่าน ProjFS) แทนที่จะรอให้ Git core พัฒนาฟีเจอร์ที่ต้องการ

เมื่อเวลาผ่านไปและ Git core มีทั้ง partial clone, sparse checkout แบบ cone mode, และ commit-graph ครบถ้วนแล้ว (ซึ่งส่วนหนึ่งเป็นผลจากการที่วิศวกรของ Microsoft เองเข้าไปช่วยพัฒนา Git core โดยตรงหลังจากผ่านประสบการณ์ทำ GVFS มาแล้ว) Microsoft จึงพบว่า**ฟีเจอร์มาตรฐานเหล่านี้เพียงพอแล้วสำหรับ Windows repo โดยไม่ต้องพึ่งพา virtual filesystem ที่ซับซ้อนอย่าง GVFS อีกต่อไป** นี่คือที่มาของการพัฒนา Scalar ขึ้นมาแทนที่ และเป็นตัวอย่างที่ดีของวัฏจักร "แก้ปัญหาด้วยวิธีที่ซับซ้อนที่สุดเท่าที่มีในตอนนั้น แล้วค่อยย้ายไปใช้วิธีที่เรียบง่ายกว่าเมื่อเครื่องมือมาตรฐานพัฒนาทันความต้องการ"

### ผลกระทบที่มีต่อ Git core โดยรวม

นี่คือประเด็นที่สำคัญที่สุดของกรณีศึกษา Microsoft ที่ควรเน้นย้ำ: **งานที่ Microsoft ทำเพื่อแก้ปัญหาของตัวเอง ท้ายที่สุดกลับกลายเป็นประโยชน์ต่อผู้ใช้ Git ทั่วโลก** ฟีเจอร์หลายตัวที่เราเรียนไปแล้วตลอด Part 63 ไม่ได้เกิดขึ้นลอย ๆ แต่มีความเชื่อมโยงโดยตรงหรือโดยอ้อมกับความพยายามแก้ปัญหา Windows repository:

- **Partial Clone** (`--filter=blob:none` ที่เรียนใน Part 63 Step 623) ถูกพัฒนาและผลักดันโดยได้แรงบันดาลใจส่วนหนึ่งจากปัญหา scale แบบเดียวกับที่ Windows repo เจอ
- **Commit-graph** และ **Multi-pack-index** (ฟีเจอร์เร่งความเร็วการเดินกราฟ commit ที่ `git maintenance` ใช้งาน ตามที่เรียนใน Part 63 Step 625) ได้รับการพัฒนาโดยมีส่วนสนับสนุนอย่างมากจากวิศวกรของ Microsoft ที่ทำงานด้าน Git core โดยตรง
- **Sparse checkout แบบ cone mode** (Part 63 Step 624) ที่เร็วกว่า pattern แบบเดิมมาก ก็เป็นผลจากความต้องการรองรับ repository ขนาดล้านไฟล์แบบ Windows

พูดอีกแบบหนึ่งคือ **Microsoft ไม่ได้แค่สร้างเครื่องมือปิด (proprietary) ไว้ใช้เองแบบ Google ทำกับ Piper** แต่เลือกเส้นทางที่ผลักดันให้ Git เองแข็งแกร่งขึ้นในภาพรวม ซึ่งเป็นรูปแบบการลงทุนที่ต่างออกไปอย่างมีนัยสำคัญเมื่อเทียบกับสองบริษัทที่เหลือ

### เหตุผลเชิงกลยุทธ์ที่ Microsoft เลือกเส้นทางนี้

มีเหตุผลทางธุรกิจที่สมเหตุสมผลอยู่เบื้องหลังการเลือกเส้นทางนี้ของ Microsoft:

1. **Microsoft เป็นเจ้าของ GitHub** (ตามที่เราเรียนไปแล้วใน Part 01 Step 4 ว่า Microsoft ซื้อ GitHub ในปี 2018) การทำให้ Git core แข็งแกร่งขึ้นส่งผลดีโดยตรงต่อธุรกิจ GitHub ด้วย เพราะลูกค้าองค์กรขนาดใหญ่ของ GitHub จำนวนมากก็เผชิญปัญหา scale แบบเดียวกัน
2. การพึ่งพา Git มาตรฐานแทนที่จะสร้างระบบปิดของตัวเอง (แบบ Piper) ทำให้ **วิศวกรใหม่ที่เข้าร่วมทีม Windows ไม่ต้องเรียนรู้เครื่องมือใหม่ทั้งหมด** — ยังคงใช้คำสั่ง Git มาตรฐานที่คุ้นเคยได้ เพียงแต่มี Scalar/GVFS ทำงานอยู่เบื้องหลังอย่างโปร่งใส
3. การเปิดเผยงานวิจัยและโค้ดเป็นโอเพนซอร์ส (ทั้ง GVFS และ Scalar เป็นโอเพนซอร์สตั้งแต่แรก) สอดคล้องกับทิศทางเชิงกลยุทธ์ของ Microsoft ในยุคหลังปี 2014 ที่หันมาสนับสนุน Open Source อย่างจริงจังมากขึ้นเรื่อย ๆ

## Step 967: EdenFS ของ Meta — Virtual Filesystem สำหรับ Monorepo

ต่อจาก Step 964 ที่เราพูดถึง Sapling ในภาพรวม ใน Step นี้เราจะเจาะลึกเฉพาะส่วนที่เป็น **EdenFS** ซึ่งเป็นองค์ประกอบสำคัญที่ทำให้ Sapling ใช้งานได้จริงกับ Monorepo ขนาดมหึมาของ Meta และมีแนวคิดที่น่าเปรียบเทียบโดยตรงกับ VFS for Git ของ Microsoft ที่เพิ่งเรียนไปใน Step ก่อนหน้า

### ปัญหาที่ EdenFS แก้: การ Checkout ที่ช้าเกินไป

แม้ Mercurial ที่ Meta ปรับแต่งแล้ว (พร้อม remotefilelog extension ตามที่เรียนใน Step 964) จะแก้ปัญหาเรื่องการดาวน์โหลดเนื้อหาไฟล์แบบ lazy ได้ดีระดับหนึ่งแล้ว แต่ยังเหลือปัญหาสำคัญอีกจุดหนึ่ง คือ **การ checkout หรือสลับไปมาระหว่าง commit/branch ยังคงช้า** เพราะทุกครั้งที่สลับ commit ระบบไฟล์ปกติ (เช่น ext4 บน Linux หรือ APFS บน macOS) ยังคงต้องเขียนไฟล์ที่เปลี่ยนแปลงทั้งหมดลงดิสก์จริง ถ้า Monorepo มีไฟล์นับล้านไฟล์ แม้จะเปลี่ยนแค่ไม่กี่ร้อยไฟล์จริง ๆ ระบบก็ยังต้องเดินตรวจสอบไฟล์ทั้งหมดเพื่อรู้ว่าอะไรเปลี่ยนไปบ้าง (ปัญหาเดียวกับที่เราเรียนเรื่อง `git status` ช้าใน Part 63 Step 621)

### แนวคิดหลักของ EdenFS

**EdenFS** คือ virtual filesystem ที่ Meta พัฒนาขึ้นโดยมีแนวคิดหลักที่**คล้ายกันมาก**กับ VFS for Git ของ Microsoft ที่เรียนไปใน Step 966 (Step 629 ของ Part 63) แต่พัฒนาขึ้นแยกจากกันโดยอิสระ:

- EdenFS ทำหน้าที่เป็น **ตัวกลางระหว่างระบบปฏิบัติการกับข้อมูลจริงของ repository** โดยใช้เทคโนโลยี **FUSE (Filesystem in Userspace)** บน Linux และ macOS (และมีการรองรับผ่าน ProjFS บน Windows ในลักษณะที่คล้ายกับที่ VFS for Git ใช้)
- เมื่อโปรแกรมใด ๆ (editor, compiler, shell) พยายามอ่านรายชื่อไฟล์ในโฟลเดอร์ EdenFS จะตอบกลับไปว่ามีไฟล์อะไรอยู่บ้างแบบครบถ้วนราวกับไฟล์อยู่บนดิสก์จริงทั้งหมด แต่ **เนื้อหาไฟล์จริง ๆ จะถูกดึงมาจาก server ก็ต่อเมื่อมีการเปิดอ่านไฟล์นั้นจริง ๆ เท่านั้น** (lazy materialization)
- เมื่อสลับ commit หรือ branch EdenFS **ไม่ต้องเขียนไฟล์ทุกไฟล์ที่เปลี่ยนแปลงลงดิสก์จริงทันที** เพียงแค่ปรับปรุงข้อมูล metadata ภายในของตัวเองว่า "ตอนนี้ควรมองเห็นไฟล์ชุดไหน" แล้วค่อยดึงเนื้อหาจริงมาต่อเมื่อถูกเปิดใช้งาน ทำให้การสลับ commit ที่ปกติต้องใช้เวลานานหลายนาทีหรือหลายชั่วโมงในการ checkout เต็มรูปแบบ กลายเป็นการดำเนินการที่**เกือบจะทันที (near-instant)**

### เปรียบเทียบ EdenFS กับ VFS for Git

| ประเด็น | VFS for Git (Microsoft) | EdenFS (Meta) |
|---|---|---|
| ใช้กับ VCS ตัวไหน | Git | Mercurial เดิม ปัจจุบันทำงานร่วมกับ Sapling |
| เทคโนโลยี virtualize หลัก | ProjFS (Windows Projected File System) | FUSE บน Linux/macOS, ProjFS บน Windows |
| จุดเริ่มต้นของโครงการ | ราวปี 2017 (สำหรับ Windows repo) | พัฒนาขึ้นในช่วงเวลาใกล้เคียงกัน (Meta เริ่มพัฒนา Eden ตั้งแต่ราวปี 2016-2018) เพื่อ Monorepo ของ Meta เอง |
| สถานะปัจจุบัน | แนวทางที่ถูกแทนที่ด้วย Scalar เป็นหลักแล้ว | ยังคงเป็นองค์ประกอบหลักที่ Meta ใช้งานจริงควบคู่กับ Sapling/Mononoke |
| เปิดเผยเป็นโอเพนซอร์ส | ใช่ | ใช่ (เป็นส่วนหนึ่งของโครงการ Sapling ที่เปิดเผยปี 2022) |

ข้อสังเกตที่น่าสนใจคือ **ทั้งสองบริษัทเจอปัญหาแบบเดียวกันและแก้ด้วยแนวคิดพื้นฐานที่คล้ายกันมาก (virtualize filesystem เพื่อทำ lazy materialization) โดยพัฒนาขึ้นแยกจากกันโดยอิสระในช่วงเวลาใกล้เคียงกัน** นี่คือสัญญาณที่ชัดเจนว่าปัญหานี้เป็นปัญหาเชิงโครงสร้างที่แท้จริงของการทำ Monorepo ขนาดมหึมา ไม่ใช่เรื่องบังเอิญที่เกิดกับบริษัทใดบริษัทหนึ่งเพียงลำพัง — เมื่อ scale ถึงระดับหนึ่ง แนวทางแก้ปัญหาที่สมเหตุสมผลที่สุดจะมาบรรจบกันแม้จะเริ่มต้นจากคนละจุด

### ทำไม EdenFS ถึงไม่ได้ถูกแทนที่แบบเดียวกับที่ VFS for Git ถูกแทนที่ด้วย Scalar

เป็นคำถามที่น่าคิดว่าทำไม Microsoft เปลี่ยนแนวทางจาก VFS for Git (virtualize เต็มรูปแบบ) มาเป็น Scalar (รวมฟีเจอร์ partial clone + sparse checkout) แต่ Meta ยังคงใช้ EdenFS (virtualize เต็มรูปแบบ) ต่อไป คำตอบเกี่ยวข้องกับความแตกต่างของบริบทการใช้งาน:

- Windows repository แม้จะใหญ่มาก แต่วิศวกรส่วนใหญ่ทำงานอยู่ในบางส่วนของโค้ด (เช่น ทีม kernel ทำงานเฉพาะส่วน kernel) ทำให้ sparse checkout แบบเลือกโฟลเดอร์ล่วงหน้าตอบโจทย์ได้ดีพอ
- Monorepo ของ Meta (โดยเฉพาะ `www`) มีลักษณะการใช้งานที่วิศวกรมักต้องข้ามไปมาระหว่างหลายส่วนของโค้ดบ่อยกว่า และการที่ต้องเลือก path ล่วงหน้าแบบ sparse checkout จะสร้างความไม่สะดวกมากกว่า การ virtualize แบบเต็มรูปแบบที่ไม่ต้องเลือกล่วงหน้าเลยจึงยังคงเหมาะสมกับรูปแบบการทำงานของ Meta มากกว่า

นี่คือบทเรียนสำคัญที่ควรจำ: **ไม่มีคำตอบเดียวที่ถูกที่สุดสำหรับทุกองค์กร แม้แต่ในกลุ่มบริษัทที่เจอปัญหา scale ระดับเดียวกัน** การเลือกเครื่องมือยังต้องพิจารณาบริบทและรูปแบบการทำงานจริงของแต่ละองค์กรประกอบด้วยเสมอ

## Step 968: บทเรียนร่วมกันจากทั้ง 3 บริษัท — Tooling Investment คือกุญแจสำคัญ

เมื่อมองภาพรวมของทั้ง 3 กรณีศึกษา (Google/Piper/Bazel, Meta/Mercurial-Sapling/EdenFS, Microsoft/Git/VFS-Scalar) แม้แต่ละบริษัทจะเลือกเทคโนโลยีที่ต่างกันโดยสิ้นเชิง แต่มี**บทเรียนร่วมกัน**ที่ปรากฏชัดเจนในทุกกรณี

### บทเรียนที่ 1: ไม่มีบริษัทไหนใช้เครื่องมือ "แบบมาตรฐาน" ตรง ๆ โดยไม่ปรับแต่ง

ทั้งสามบริษัทพิสูจน์ให้เห็นตรงกันว่า **ที่ scale ระดับหมื่นถึงแสนวิศวกรกับข้อมูลระดับสิบ-ร้อยเทราไบต์ เครื่องมือ VCS แบบมาตรฐานไม่ว่าจะเป็น Git หรือ Mercurial ล้วนต้องการการปรับแต่งหรือเสริมเครื่องมือพิเศษเพิ่มเติมเสมอ** ไม่มีบริษัทไหนเลยที่ใช้ Git หรือ Mercurial แบบ out-of-the-box ตรง ๆ ได้ที่ scale นี้:

- Google เลือกไม่ใช้ Git/Mercurial เลย สร้าง Piper ขึ้นมาใหม่ทั้งหมด
- Meta ปรับแต่ง Mercurial อย่างหนักด้วย extension ของตัวเอง แล้วท้ายที่สุดพัฒนาระบบใหม่ (Sapling/Mononoke/EdenFS) ขึ้นมาแทนที่
- Microsoft ยังคงใช้ Git แต่ต้องสร้างชั้นเสริมพิเศษ (VFS for Git, Scalar) ครอบไว้จึงจะใช้งานได้จริง

### บทเรียนที่ 2: การลงทุนด้าน Tooling เป็นการลงทุนระยะยาวและต่อเนื่อง ไม่ใช่โครงการที่ทำครั้งเดียวจบ

ทั้ง Bazel/Blaze, Mercurial ที่ปรับแต่งแล้ว/Sapling, และ VFS for Git/Scalar ล้วนเป็นผลผลิตจาก**ทีมวิศวกรเฉพาะทางที่ทำงานเต็มเวลาต่อเนื่องเป็นเวลาหลายปี** ไม่ใช่โปรเจกต์ที่ตั้งค่าครั้งเดียวแล้วจบ:

- Google มีองค์กรภายในขนาดใหญ่ (Developer Infrastructure) ที่ดูแล Piper และ Bazel อย่างต่อเนื่องมาหลายสิบปี
- Meta มีทีม Source Control โดยเฉพาะที่พัฒนา Mercurial extensions ต่อเนื่องมาตั้งแต่ปี 2013 จนถึงการพัฒนา Sapling ในปี 2022 — รวมเวลาเกือบสิบปี
- Microsoft มีทีมวิศวกรที่ทำงานร่วมกับทีม Git core อย่างต่อเนื่องตั้งแต่ 2017 จนถึงปัจจุบัน เพื่อพัฒนาและบำรุงรักษาฟีเจอร์เหล่านี้

### บทเรียนที่ 3: Version Control ไม่ใช่แค่เครื่องมือ แต่เป็นส่วนหนึ่งของสถาปัตยกรรมระบบวิศวกรรมทั้งหมด

ทั้งสามกรณีศึกษาแสดงให้เห็นชัดเจนว่า **การเลือกเครื่องมือ VCS ที่ scale ระดับนี้ผูกติดแน่นแฟ้นกับการตัดสินใจเชิงสถาปัตยกรรมอื่น ๆ ขององค์กรทั้งหมด** ไม่ใช่การตัดสินใจแบบแยกส่วนที่เลือกได้อิสระ:

- Google ผูก Piper เข้ากับ Trunk-Based Development และวัฒนธรรมการทดสอบอัตโนมัติที่เข้มงวดที่สุด (ตามที่เรียนใน Step 962)
- Meta ผูก Mercurial/Sapling เข้ากับรูปแบบการ deploy แบบต่อเนื่อง (continuous deployment) ที่ต้องการให้วิศวกรทุกคนทำงานบน trunk ที่ทันสมัยที่สุดตลอดเวลาเช่นกัน
- Microsoft ผูก VFS for Git/Scalar เข้ากับความต้องการรักษาความคุ้นเคยของวิศวกรกับ Git มาตรฐาน เพื่อไม่ให้กระทบ workflow และวัฒนธรรมวิศวกรรมที่มีอยู่เดิม

### บทเรียนที่ 4: การแก้ปัญหาที่ scale สูงมักได้ผลพลอยได้ที่เป็นประโยชน์ต่อทั้งวงการ

อย่างที่เห็นชัดเจนที่สุดในกรณีของ Microsoft (Step 966) แต่ก็จริงบางส่วนกับ Google (Bazel เป็นโอเพนซอร์ส) และ Meta (Sapling/Mononoke/EdenFS เป็นโอเพนซอร์ส) — **การแก้ปัญหา scale ที่ยากที่สุดในโลก มักผลิตผลงานที่มีคุณค่าย้อนกลับไปสู่ชุมชนวิศวกรรมซอฟต์แวร์ทั้งหมด** ไม่ใช่แค่ประโยชน์ภายในองค์กรเดียว

### ตารางสรุปการเปรียบเทียบทั้ง 3 กรณีศึกษา

| ประเด็น | Google | Meta | Microsoft |
|---|---|---|---|
| VCS หลักที่ใช้ | Piper (สร้างเอง, centralized) | Sapling (พัฒนาจาก Mercurial, distributed) | Git (มาตรฐาน + เครื่องมือเสริม) |
| Build system เฉพาะทาง | Bazel/Blaze | Buck (เครื่องมือ build อีกตัวที่ Meta พัฒนาเอง คล้ายแนวคิด Bazel) | MSBuild + เครื่องมือภายในอื่น ๆ |
| แนวทางแก้ปัญหา checkout/working directory | CitC (virtual workspace) | EdenFS (virtual filesystem ผ่าน FUSE) | VFS for Git (ProjFS) → Scalar (มาตรฐาน Git ผสมกัน) |
| เปิดเผยต่อสาธารณะ | บางส่วน (Bazel เป็นโอเพนซอร์ส, Piper ไม่เปิดเผย) | ส่วนใหญ่เปิดเผย (Sapling, Mononoke, EdenFS ทั้งหมดเป็นโอเพนซอร์สตั้งแต่ 2022) | เปิดเผยทั้งหมด (VFS for Git, Scalar เป็นโอเพนซอร์สและ Scalar ถูกรวมเข้า Git core) |
| ผลกระทบต่อ Git core โดยตรง | น้อยมาก (ไม่ได้ใช้ Git) | ปานกลาง (Sapling ทำงานร่วมกับ Git ได้ แต่ไม่ใช่การพัฒนา Git core โดยตรง) | สูงมาก (Partial clone, commit-graph, sparse checkout cone mode ล้วนได้อิทธิพลจากงานนี้) |

> **สรุปบทเรียนที่สำคัญที่สุดของ Step นี้:** เครื่องมือชั้นยอดที่ทั้งสามบริษัทนี้มีไม่ได้เกิดจากการเลือก "เครื่องมือที่ดีที่สุด" จากตลาด แต่เกิดจาก**การลงทุนสร้างและดูแลเครื่องมือเฉพาะทางของตัวเองอย่างต่อเนื่องนานหลายปี โดยทีมวิศวกรจำนวนมากที่ทำงานเรื่องนี้เป็นอาชีพหลัก** นี่คือข้อเท็จจริงที่สำคัญที่สุดที่ต้องนำไปคิดต่อใน Step 969

## Step 969: เมื่อไหร่ที่บริษัทขนาดเล็ก-กลางไม่ควรพยายามเลียนแบบ Google/Meta/Microsoft

นี่คือ Step ที่สำคัญที่สุดของ Part นี้ในเชิงปฏิบัติ เพราะเป็นเรื่องปกติมากที่วิศวกรหรือผู้บริหารฝ่ายเทคโนโลยีในบริษัทขนาดเล็ก-กลางจะได้ยินเรื่องราวของ Google/Meta/Microsoft แล้วเกิดความคิดว่า "เราก็ควรทำแบบนั้นบ้าง" — ความคิดแบบนี้มักนำไปสู่การตัดสินใจที่ผิดพลาดร้ายแรง เรียกปรากฏการณ์นี้อย่างไม่เป็นทางการว่า **"You Are Not Google"** ซึ่งเป็นวลีที่ถูกใช้กันอย่างแพร่หลายในวงการวิศวกรรมซอฟต์แวร์เพื่อเตือนสติเรื่องการ over-engineering

### สัญญาณเตือนว่ากำลัง Over-Engineer

หากทีมของคุณกำลังพิจารณาสิ่งเหล่านี้ ให้ตั้งคำถามกับตัวเองอย่างจริงจังก่อน:

**1. กำลังจะสร้าง Build System แบบ Bazel เอง ทั้งที่มีวิศวกรไม่ถึง 200 คน**

Bazel ที่ Google ใช้เป็นผลจากทีมวิศวกร Developer Infrastructure ขนาดใหญ่ที่ทำงานเรื่องนี้เต็มเวลาต่อเนื่องหลายสิบปี ถ้าองค์กรของคุณมีวิศวกรทั้งหมดไม่ถึง 200 คน การพยายามตั้งค่า Bazel เต็มรูปแบบ (เขียนไฟล์ `BUILD` กำกับทุกโมดูล, ตั้งค่า remote caching/execution ของตัวเอง) มักจะ**ใช้เวลาและทรัพยากรมากกว่าประโยชน์ที่ได้กลับมาอย่างมาก** ดังที่เรียนไปแล้วใน Part 82 Step 817 ทางเลือกที่เหมาะสมกว่าคือเครื่องมือที่ตั้งค่าง่ายกว่ามาก เช่น **Nx** หรือ **Turborepo** ซึ่งให้ประโยชน์ 80-90% ของสิ่งที่ Bazel ให้ได้ ด้วยความซับซ้อนในการตั้งค่าเพียงเสี้ยวเดียว

**2. กำลังจะสร้าง Virtual Filesystem แบบ EdenFS/VFS for Git เอง**

ถ้า repository ของทีมคุณมีขนาดไม่ถึงระดับสิบกิกะไบต์ หรือมีไฟล์ไม่ถึงหลักแสนไฟล์ ปัญหาที่ VFS for Git และ EdenFS แก้นั้น**อาจไม่เคยเกิดขึ้นกับทีมคุณเลย** การพยายามตั้งค่าเครื่องมือระดับนี้ (ที่ต้องพึ่งพา FUSE หรือ ProjFS ซึ่งมีความซับซ้อนในการติดตั้งและดูแลสูงมาก) จะสร้างภาระด้าน infrastructure และ maintenance ที่ไม่คุ้มค่าเลย เทคนิคที่เรียนใน Part 63 (shallow clone, partial clone, sparse checkout, git maintenance) ซึ่งเป็นฟีเจอร์มาตรฐานของ Git core อยู่แล้ว **เพียงพอเกินพอ**สำหรับ repository ขนาดไม่กี่สิบกิกะไบต์

**3. กำลังจะย้ายทุกอย่างเข้า Monorepo เดียวทั้งบริษัท โดยไม่มีแผนเรื่อง Tooling**

ตามที่เรียนไปแล้วใน Part 82 Step 814 และ Step 819 **Monorepo ที่ไม่มีเครื่องมือ selective build/test รองรับ จะพัง CI ให้ช้าลงอย่างรวดเร็ว** เมื่อจำนวนโปรเจกต์ในนั้นเพิ่มขึ้น การย้ายเข้า Monorepo เดียวทั้งบริษัทโดยหวังว่าจะ "ค่อยไปหาเครื่องมือทีหลัง" เป็นการเรียงลำดับความสำคัญที่ผิดพลาด ควรมีแผนเรื่อง tooling ให้ชัดเจนก่อนตัดสินใจย้าย ไม่ใช่หลังจากย้ายไปแล้ว

**4. กำลังจะสร้างระบบ Version Control ของตัวเองแบบ Piper**

นี่คือระดับที่รุนแรงที่สุดและควรเป็นสิ่งที่บริษัทขนาดเล็ก-กลางแทบไม่ควรพิจารณาเลยแม้แต่น้อย การสร้างระบบ VCS ของตัวเองทั้งหมดตั้งแต่ต้นเหมือน Piper ต้องการทีมวิศวกรระดับผู้เชี่ยวชาญด้าน distributed systems จำนวนมาก ทำงานต่อเนื่องหลายปี พร้อม infrastructure ระดับ data center ทั่วโลก — ต้นทุนนี้สูงเกินกว่าที่บริษัทขนาดเล็ก-กลางจะแบกรับได้อย่างสิ้นเชิง และไม่มีเหตุผลทางธุรกิจใดที่จะสมเหตุสมผลพอให้ทำเช่นนั้น เมื่อ Git มาตรฐานที่มีอยู่แล้วรองรับความต้องการเกือบทั้งหมดของบริษัทขนาดนี้ได้สบาย ๆ

### กรอบคิดง่าย ๆ สำหรับประเมินว่าองค์กรของคุณ "ถึงจุดที่ต้องคิดหนัก" หรือยัง

เพื่อให้การประเมินเป็นรูปธรรมมากขึ้น ลองใช้กรอบคำถามต่อไปนี้แทนการเปรียบเทียบกับ Google/Meta/Microsoft โดยตรง:

| สัญญาณที่วัดได้จริง | ยังไม่ต้องกังวล | เริ่มต้องพิจารณาเครื่องมือเสริม |
|---|---|---|
| ขนาด repository ที่ใหญ่ที่สุด | ต่ำกว่า 5-10 GB | มากกว่า 50-100 GB ขึ้นไป |
| จำนวนไฟล์ใน working directory | ต่ำกว่าหลักหมื่นไฟล์ | มากกว่า 500,000 ไฟล์ขึ้นไป |
| เวลาเฉลี่ยที่ CI ใช้ต่อ PR | ต่ำกว่า 10 นาที | มากกว่า 30-45 นาทีอย่างต่อเนื่อง แม้ใช้ affected build แล้ว |
| จำนวนวิศวกรที่ commit เข้า repository เดียวกันต่อวัน | ต่ำกว่าหลักสิบคน | มากกว่าหลักร้อยถึงหลักพันคน |
| มีทีม platform/infra เฉพาะทางพร้อมดูแลเครื่องมือต่อเนื่องหรือไม่ | ไม่มี หรือมีแค่ 1-2 คนที่ทำเป็นงานเสริม | มีทีมเฉพาะทางอย่างน้อย 3-5 คนขึ้นไปที่ทำเรื่องนี้เป็นงานหลัก |

ถ้าองค์กรของคุณอยู่ในคอลัมน์ "ยังไม่ต้องกังวล" เกือบทั้งหมด **ฟีเจอร์มาตรฐานของ Git ที่เรียนใน Part 63 ก็เพียงพอเกินพอแล้ว** และการนำเทคนิคระดับ Google/Meta/Microsoft มาใช้จะเป็นการลงทุนที่ไม่คุ้มค่าอย่างชัดเจน

### หลักคิดที่ควรใช้แทน

แทนที่จะถามว่า **"Google/Meta/Microsoft ทำอะไร"** คำถามที่ถูกต้องกว่าคือ:

1. **"ปัญหาที่แท้จริงของทีมเราคืออะไร"** — วัดผลจริงด้วยเครื่องมืออย่าง `GIT_TRACE_PERFORMANCE` และ `git count-objects -v` ที่เรียนใน Part 63 Step 626 ก่อนเสมอ อย่าเชื่อว่ามีปัญหาเพราะบริษัทใหญ่เจอปัญหานั้น
2. **"ที่ scale ปัจจุบันของเรา เครื่องมือมาตรฐานเพียงพอหรือยัง"** — ให้ลองใช้ฟีเจอร์มาตรฐานของ Git ให้เต็มที่ก่อนเสมอ (Part 63 ทั้ง Part) ก่อนจะพิจารณาเครื่องมือเฉพาะทางที่ซับซ้อนกว่า
3. **"เรามีทรัพยากรพอจะดูแลเครื่องมือนี้ต่อเนื่องระยะยาวหรือไม่"** — ดังที่เรียนใน Step 968 ว่าเครื่องมือระดับนี้ต้องการทีมดูแลต่อเนื่อง ไม่ใช่ตั้งค่าครั้งเดียวจบ ถ้าไม่มีทีมที่จะดูแลต่อเนื่อง อย่าเริ่มต้น

> **หลักการสำคัญที่สุดของ Step นี้:** กรณีศึกษาของ Google, Meta, Microsoft มีคุณค่าในฐานะ**บทเรียนเรื่องแนวคิดและหลักการ** (เช่น ความสำคัญของ atomic commit, การวัดผลก่อนปรับแต่ง, ความเชื่อมโยงระหว่าง VCS กับสถาปัตยกรรมองค์กร) มากกว่าจะเป็น**สูตรสำเร็จที่ต้องเลียนแบบตรง ๆ** การนำเทคนิคเฉพาะทางที่ออกแบบมาสำหรับ scale ระดับหมื่นวิศวกรมาใช้กับทีม 50-100 คน มักสร้างความซับซ้อนที่ไม่จำเป็นมากกว่าจะแก้ปัญหาจริง

## Step 970: แบบฝึกหัด — วิเคราะห์ว่าเทคนิคไหนจากกรณีศึกษาเหล่านี้นำมาปรับใช้กับทีมขนาดกลาง (50-200 คน) ได้จริงอย่างสมเหตุสมผล

ถึงเวลาลงมือวิเคราะห์ด้วยตัวเอง แบบฝึกหัดนี้ไม่มีการเขียนโค้ด แต่เป็นแบบฝึกหัดเชิงการตัดสินใจเชิงสถาปัตยกรรม (architectural decision-making) ที่สำคัญมากสำหรับการเป็น Tech Lead ในอนาคต (ซึ่งเราจะเรียนเจาะลึกบทบาทนี้ใน **Part 99**)

### สถานการณ์สมมติ

สมมติว่าคุณเป็น Tech Lead ของบริษัทซอฟต์แวร์แห่งหนึ่งที่มีลักษณะดังนี้:

- มีวิศวกรทั้งหมด 120 คน แบ่งเป็น 15 ทีมย่อย
- มี repository กระจายอยู่ประมาณ 40 repository (ผสมทั้ง Polyrepo และ Monorepo เล็ก ๆ ของบางทีม)
- Repository ที่ใหญ่ที่สุดมีขนาดราว 8 GB มีไฟล์ประมาณ 60,000 ไฟล์
- CI/CD ปัจจุบันเริ่มช้าลง เฉลี่ยรอ 15-20 นาทีต่อ PR
- ทีมผู้บริหารเพิ่งอ่านบทความเกี่ยวกับ Google Monorepo แล้วถามว่า "ทำไมเราไม่ทำแบบ Google บ้าง"

### งานที่ต้องทำ

ให้คุณเขียนวิเคราะห์ (เขียนใส่ไฟล์ text หรือกระดาษก็ได้ ไม่ต้องส่งใคร) ตอบคำถามต่อไปนี้ทีละข้อ โดยอ้างอิงเนื้อหาที่เรียนมาตลอด Part นี้และ Part ที่เกี่ยวข้องประกอบการให้เหตุผล:

**คำถามที่ 1: เทคนิคใดจากกรณีศึกษาที่นำมาใช้ได้จริงและควรใช้ทันที**

ให้พิจารณาเทคนิคต่อไปนี้ และตัดสินใจว่าแต่ละอย่างเหมาะกับสถานการณ์บริษัทสมมตินี้หรือไม่ พร้อมให้เหตุผล:

| เทคนิค | เหมาะกับทีม 120 คนนี้หรือไม่ | เหตุผล |
|---|---|---|
| Trunk-Based Development (จาก Part 34, ใช้โดย Google และ Meta) | ? | ? |
| Feature Flags แทน long-lived branch | ? | ? |
| Monorepo ต่อทีม (Hybrid Approach จาก Part 82 Step 818) | ? | ? |
| Partial Clone + Sparse Checkout (จาก Part 63) | ? | ? |
| `git maintenance` อัตโนมัติ (จาก Part 63 Step 625) | ? | ? |

| สร้างระบบ VCS ของตัวเองแบบ Piper | ? | ? |

**คำถามที่ 2: จะตอบผู้บริหารที่ถามว่า "ทำไมเราไม่ทำแบบ Google บ้าง" อย่างไร**

เขียนคำตอบสั้น ๆ (3-5 ประโยค) ที่อธิบายให้ผู้บริหารที่ไม่มีพื้นฐานเทคนิคเข้าใจได้ว่าทำไมการเลียนแบบ Google ตรง ๆ ไม่ใช่ทางเลือกที่เหมาะสม โดยไม่ใช้ศัพท์เทคนิคที่เข้าใจยากเกินไป (ลองนึกถึงการเปรียบเทียบแบบที่เราเคยเห็นใน Part 01 Step 7 ที่เปรียบเทียบ Git/GitHub/GitLab กับ Google Drive)

**คำถามที่ 3: ออกแบบ Roadmap การปรับปรุงสำหรับ 6 เดือนข้างหน้า**

จากปัญหา CI ช้า 15-20 นาทีต่อ PR ที่เกิดจาก repository ขนาด 8 GB ให้ออกแบบแผนการปรับปรุงเป็นขั้นตอน 3 เฟส (เฟสละ 2 เดือน) โดยใช้เทคนิคที่ **เหมาะสมกับ scale ของบริษัทนี้จริง ๆ** ไม่ใช่เทคนิคระดับ Google/Meta/Microsoft ตัวอย่างโครงร่างที่ควรพิจารณา:

```
เฟส 1 (เดือน 1-2): วัดผลและ Quick Win
- ใช้ GIT_TRACE_PERFORMANCE วัดว่าปัญหาช้าจริง ๆ อยู่ตรงไหน (clone? build? test?)
- เปิด git maintenance ให้ทุก repository
- ตรวจสอบว่า CI ใช้ shallow clone (--depth 1) อยู่แล้วหรือยัง

เฟส 2 (เดือน 3-4): ...
เฟส 3 (เดือน 5-6): ...
```

ให้คุณเติมเฟส 2 และเฟส 3 ให้ครบด้วยตัวเอง โดยพิจารณาว่าเทคนิคใดจากตารางในคำถามที่ 1 ควรถูกนำมาใช้ในช่วงไหน

**คำถามที่ 4: เส้นแบ่งอยู่ตรงไหน**

ลองตอบคำถามเชิงหลักการ: ถ้าบริษัทสมมตินี้เติบโตขึ้นเรื่อย ๆ จนมีวิศวกร 2,000 คน และ Monorepo หลักโตขึ้นเป็น 150 GB คุณคิดว่า ณ จุดไหน (หรือสัญญาณอะไร) ที่ทีมควรเริ่มพิจารณาเครื่องมือระดับ VFS for Git/Scalar หรือ EdenFS อย่างจริงจัง แทนที่จะใช้แค่ partial clone + sparse checkout ธรรมดา

### แนวทางคร่าว ๆ สำหรับตรวจงานตัวเอง (ไม่ใช่เฉลยตายตัว)

เพื่อไม่ให้แบบฝึกหัดนี้เป็นเพียงคำถามปลายเปิดที่ไม่มีจุดอ้างอิงเลย ต่อไปนี้คือแนวทางคร่าว ๆ ที่สมเหตุสมผลสำหรับสถานการณ์บริษัทสมมตินี้ (120 คน, repo ใหญ่สุด 8 GB) ลองเทียบกับคำตอบของคุณเองว่าใกล้เคียงกันหรือไม่ และถ้าต่างกัน ลองพิจารณาว่าเหตุผลของฝ่ายไหนสมเหตุสมผลกว่า:

- **Trunk-Based Development และ Feature Flags** — โดยทั่วไปเหมาะสมและควรพิจารณาใช้ แม้ในทีมขนาด 120 คน เพราะแนวคิดนี้ไม่ได้ผูกกับขนาดของ repository แต่ผูกกับวินัยการพัฒนาและวัฒนธรรมการทดสอบอัตโนมัติ ซึ่งให้ประโยชน์ตั้งแต่ทีมขนาดเล็กไปจนถึงขนาดใหญ่มาก
- **Monorepo ต่อทีม (Hybrid)** — สมเหตุสมผลมาก โดยเฉพาะถ้า 15 ทีมย่อยมีลักษณะงานที่ค่อนข้างอิสระจากกัน การรวม repo ภายในแต่ละทีมที่ทำงานใกล้ชิดกันช่วยลด dependency hell ตามที่เรียนใน Part 82 Step 816 โดยไม่ต้องแบกรับต้นทุนของ Monorepo ทั้งบริษัทเต็มรูปแบบ
- **Partial Clone, Sparse Checkout, `git maintenance`** — ควรใช้ทันทีโดยแทบไม่มีข้อเสีย เพราะเป็นฟีเจอร์มาตรฐานของ Git core ที่ไม่ต้องเรียนรู้อะไรซับซ้อนมาก และ repo ขนาด 8 GB ก็อยู่ในระดับที่ได้ประโยชน์จากเทคนิคเหล่านี้จริง
- **Nx หรือ Turborepo** — เหมาะสมมากถ้าปัญหา CI ช้าส่วนหนึ่งมาจากการ build/test ทุกอย่างโดยไม่แยกแยะว่าอะไรเปลี่ยนจริง เครื่องมือเหล่านี้ให้ผลตอบแทนสูงเทียบกับความซับซ้อนในการตั้งค่าที่ต่ำกว่า Bazel มาก
- **Bazel เต็มรูปแบบ** — ไม่คุ้มค่าในสถานการณ์นี้ ด้วยทีมวิศวกร 120 คนและ repo ขนาด 8 GB ต้นทุนการเรียนรู้และการเขียนไฟล์ `BUILD` กำกับทุกโมดูลสูงเกินกว่าประโยชน์ที่จะได้กลับมาเมื่อเทียบกับ Nx/Turborepo
- **Virtual Filesystem แบบ EdenFS/VFS for Git** — ไม่จำเป็นเลยที่ scale นี้ ปัญหาที่เครื่องมือเหล่านี้แก้ (checkout ช้าเพราะไฟล์เป็นล้านไฟล์) ยังไม่เกิดขึ้นจริงกับ repo ขนาด 8 GB
- **สร้างระบบ VCS ของตัวเองแบบ Piper** — ไม่สมเหตุสมผลอย่างยิ่ง เป็นตัวอย่างชัดเจนของ over-engineering ที่ Step 969 เตือนไว้

สำหรับคำถามที่ 4 เรื่องเส้นแบ่ง แนวทางที่สมเหตุสมผลคือการใช้ตารางสัญญาณเตือนใน Step 969 เป็นเกณฑ์ — เมื่อ repository หลักโตถึงระดับ 50-100 GB ขึ้นไป **และ** มีทีม platform/infra ที่พร้อมดูแลเครื่องมือระดับนี้ต่อเนื่อง จึงค่อยเริ่มพิจารณาอย่างจริงจัง ไม่ใช่แค่เพราะจำนวนวิศวกรเพิ่มขึ้นเพียงอย่างเดียว

### แนวทางการประเมินคำตอบของตัวเอง (Self-Check)

หลังจากตอบครบทุกข้อแล้ว ให้ตรวจสอบว่าคำตอบของคุณมีลักษณะดังนี้หรือไม่:

- [ ] คุณเลือกใช้เทคนิคที่ **ตรงกับ scale ปัจจุบันจริง ๆ** ไม่ใช่เทคนิคที่ "ดูเท่" หรือ "บริษัทใหญ่ใช้"
- [ ] คุณให้เหตุผลโดยอ้างอิงจากปัญหาที่ระบุไว้ในโจทย์ (CI ช้า, repo ขนาด 8 GB) ไม่ใช่ปัญหาที่ยังไม่เกิดขึ้นจริง
- [ ] Roadmap ของคุณเริ่มจากสิ่งที่ทำได้ง่ายและได้ผลเร็วก่อน (quick wins) แล้วค่อยขยับไปสิ่งที่ซับซ้อนกว่า
- [ ] คุณปฏิเสธข้อเสนอที่ over-engineer (เช่น Bazel เต็มรูปแบบ, สร้าง VCS เอง) พร้อมอธิบายเหตุผลที่ชัดเจนได้
- [ ] คำตอบของคุณสำหรับผู้บริหารสื่อสารได้ชัดเจนโดยไม่ต้องใช้ศัพท์เทคนิคหนัก ๆ

## สรุป Part 97

ใน Part นี้เราได้เรียนรู้ว่า:

1. **Google** เก็บโค้ดเกือบทั้งหมดของบริษัทไว้ใน **Piper** ซึ่งเป็นระบบ centralized version control ที่สร้างขึ้นเองทั้งหมด ไม่ใช่ Git มีขนาดหลายสิบเทราไบต์ พันล้านไฟล์ และวิศวกรนับหมื่นคน เข้าถึงผ่าน virtual workspace ที่ชื่อ CitC
2. Google เลือก Monorepo เพราะผูกแน่นแฟ้นกับปรัชญา **Trunk-Based Development** (Part 34) ที่ต้องการให้ trunk เดียวเป็นความจริงหนึ่งเดียวของทั้งบริษัท และเปิดทางให้ทำ **Large-Scale Change (LSC)** ข้ามทั้งบริษัทได้ในการเปลี่ยนแปลงเดียว
3. **Bazel** (พัฒนาจาก Blaze ภายใน) คือ build system ที่ Google สร้างมาแก้ปัญหาที่ Git ธรรมดาแก้ไม่ได้ ด้วย explicit dependency graph, selective build/test, remote caching/execution, และ hermetic build
4. **Meta** เริ่มต้นด้วย Git แต่ย้ายไปใช้ **Mercurial** ที่ปรับแต่งเองในปี 2013-2014 (พร้อม remotefilelog extension) แล้วพัฒนาต่อเป็น **Sapling** ที่เปิดเผยเป็นโอเพนซอร์สในปี 2022 พร้อมกับ Mononoke (server) และ EdenFS (virtual filesystem)
5. **Windows repository** ของ Microsoft เป็นหนึ่งใน Git repository ที่ใหญ่ที่สุดที่เคยใช้งานจริง (300GB+, ไฟล์ 3.5 ล้านไฟล์) ซึ่งผลักดันให้ Microsoft ต้องพัฒนาเครื่องมือเสริมพิเศษ แทนที่จะเปลี่ยนไปใช้ VCS อื่นแบบ Meta
6. **VFS for Git** (2017) และ **Scalar** (2019-2020, รวมเข้า Git core ตั้งแต่ 2.38) คือเครื่องมือที่ Microsoft สร้างขึ้นมาแก้ปัญหา scale ของ Windows repo และท้ายที่สุดฟีเจอร์หลายอย่าง (partial clone, commit-graph, sparse checkout cone mode) ได้กลายเป็นประโยชน์ต่อผู้ใช้ Git ทั่วโลก
7. **EdenFS** ของ Meta ใช้แนวคิดคล้าย VFS for Git คือ virtualize filesystem ผ่าน FUSE เพื่อทำ checkout แบบ near-instant แม้จะพัฒนาแยกจากกันโดยอิสระ สะท้อนว่าปัญหานี้เป็นปัญหาเชิงโครงสร้างจริงของ Monorepo ขนาดมหึมา
8. บทเรียนร่วมของทั้ง 3 บริษัทคือ **ไม่มีใครใช้เครื่องมือมาตรฐานตรง ๆ ได้ที่ scale นี้** และ **การลงทุนด้าน tooling ต้องเป็นการลงทุนระยะยาวต่อเนื่องโดยทีมเฉพาะทาง** ไม่ใช่โครงการที่ตั้งค่าครั้งเดียวจบ
9. บริษัทขนาดเล็ก-กลาง **ไม่ควรพยายามเลียนแบบ** Bazel เต็มรูปแบบ, Virtual Filesystem แบบ EdenFS/VFS for Git, หรือสร้าง VCS ของตัวเองแบบ Piper เพราะต้นทุนสูงเกินความจำเป็นเทียบกับ scale จริงของตัวเอง ควรใช้ทางเลือกที่เบากว่า เช่น Nx/Turborepo และฟีเจอร์มาตรฐานของ Git core
10. เราได้ฝึกวิเคราะห์สถานการณ์สมมติของทีมขนาด 120 คน เพื่อแยกแยะว่าเทคนิคใดจากกรณีศึกษาระดับโลกเหล่านี้นำมาปรับใช้ได้จริงอย่างสมเหตุสมผล และเทคนิคใดเป็นการ over-engineering ที่ควรหลีกเลี่ยง
