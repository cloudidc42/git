## Step 201: Pull Request (PR) คืออะไร แนวคิดเบื้องหลัง

### นิยามสั้น ๆ ที่ต้องจำให้ขึ้นใจ

> **Pull Request (PR) คือ "คำขอ" ที่คุณส่งให้เจ้าของโปรเจกต์ (หรือทีม) พิจารณานำโค้ดจาก branch หนึ่งของคุณ ไปรวม (merge) เข้ากับ branch หลัก (เช่น `main`) พร้อมเปิดโอกาสให้ทุกคนตรวจสอบ อภิปราย และแก้ไขโค้ดนั้นก่อนที่จะ merge จริง**

สังเกตคำว่า "Pull" ในชื่อ — ชื่อนี้มาจากมุมมองของ **เจ้าของ repository** ไม่ใช่มุมมองของคุณที่เป็นคนส่งโค้ด กล่าวคือคุณกำลังบอกเจ้าของ repo ว่า:

> "ผม/ดิฉันมีโค้ดอยู่ใน branch นี้แล้ว ช่วย **pull** (ดึง) มันเข้าไปรวมกับ branch หลักของคุณหน่อยได้ไหม"

นี่คือที่มาของชื่อ Pull Request บน GitHub และ Bitbucket ส่วนบน GitLab เรียกกลไกเดียวกันนี้ว่า **Merge Request (MR)** ซึ่งเป็นชื่อที่ตรงไปตรงมากว่า (เพราะมันคือคำขอให้ merge นั่นเอง) — ทั้งสองชื่อหมายถึงสิ่งเดียวกันทุกประการ เราจะเจาะลึก GitLab และ MR แบบละเอียดในเฟส 5 ของหลักสูตรนี้

### ทำไมต้องมี Pull Request ทั้งที่ Git เพียว ๆ ก็ merge ได้อยู่แล้ว

นี่คือคำถามที่มือใหม่มักสงสัย เพราะใน Part 8 เราเคยเรียนไปแล้วว่า `git merge` สามารถรวม branch ได้โดยตรงจาก command line โดยไม่ต้องพึ่งเว็บไซต์ใด ๆ เลย

คำตอบคือ: **Pull Request ไม่ใช่ฟีเจอร์ของ Git แต่เป็นฟีเจอร์ของแพลตฟอร์ม (GitHub/GitLab/Bitbucket) ที่สร้างขึ้นมาครอบกลไก merge ของ Git อีกที** เพื่อเพิ่ม **กระบวนการ (process)** และ **การมองเห็นร่วมกัน (visibility)** ที่ Git เพียว ๆ ไม่มีให้ ได้แก่:

1. **พื้นที่สำหรับ Code Review** — ให้เพื่อนร่วมทีมอ่านโค้ดของคุณ คอมเมนต์ทีละบรรทัด เสนอแนะการแก้ไข ก่อนที่โค้ดจะเข้า branch หลัก
2. **ประตูคุณภาพ (Quality Gate)** — สามารถตั้งค่าให้ PR ต้อง "ผ่าน" เงื่อนไขบางอย่างก่อน merge ได้ เช่น ต้องมีคน approve อย่างน้อย 1 คน หรือต้องรัน automated test (CI) ผ่านก่อน (เราจะเรียนเรื่องนี้ละเอียดใน Part ที่ว่าด้วย Branch Protection Rules)
3. **ประวัติการอภิปราย (Discussion history)** ที่ผูกกับโค้ดชุดนั้นโดยตรง ไม่ใช่แค่ commit message สั้น ๆ
4. **จุดเชื่อมกับ Issue Tracking** — เชื่อมโยงว่า PR นี้แก้ปัญหาจาก Issue ไหน (จะเรียนใน Step 209)
5. **จุดเดียวสำหรับดูภาพรวมการเปลี่ยนแปลง** — เห็นทุกไฟล์ที่เปลี่ยน ทุก commit ในชุดนั้น ทุกความเห็นของทีม รวมอยู่ในหน้าเดียว
6. **เป็นจุดที่ CI/CD เข้ามาทำงานอัตโนมัติ** — รัน test, linter, build ก่อนที่จะยอมให้ merge เข้าไป

พูดง่าย ๆ คือ **`git merge` คือกลไกทางเทคนิคที่ทำการรวมโค้ดจริง ๆ** ในขณะที่ **Pull Request คือ "กระบวนการทางสังคมและคุณภาพ" ที่ห่อหุ้มอยู่รอบ ๆ การ merge นั้น** เพื่อให้แน่ใจว่าก่อนโค้ดจะเข้า branch หลัก มันผ่านสายตาคนอื่นมาก่อนแล้ว

### แนวคิดเบื้องหลัง Pull Request ในเชิง Workflow

Pull Request ทำให้เกิด pattern การทำงานที่เป็นมาตรฐานในอุตสาหกรรมปัจจุบันที่เรียกว่า **Feature Branch Workflow** ซึ่งมีขั้นตอนคร่าว ๆ ดังนี้:

```
1. สร้าง branch ใหม่แยกจาก main         (git checkout -b feature/xyz)
2. เขียนโค้ด commit ลง branch นั้น        (git commit)
3. push branch ขึ้น GitHub               (git push)
4. เปิด Pull Request                     (บนเว็บ GitHub)
5. ทีมรีวิว คอมเมนต์ ขอแก้ไข             (Code Review)
6. แก้ไขตามคอมเมนต์ push เพิ่ม            (git push อีกครั้ง อัปเดต PR เดิม)
7. ทีม approve PR                        (Approve)
8. Merge PR เข้า main                    (กดปุ่ม Merge บนเว็บ)
9. ลบ branch feature/xyz ทิ้ง             (ไม่ต้องใช้แล้ว)
```

สังเกตว่า **ไม่มีใครแตะ branch `main` โดยตรงเลย** — ทุกการเปลี่ยนแปลงต้องผ่านกระบวนการ Pull Request เสมอ นี่คือหัวใจสำคัญที่ทำให้โปรเจกต์ขนาดใหญ่ที่มีคนร่วมพัฒนาเป็นร้อยเป็นพันคน (เช่น React, VS Code, Linux Kernel ที่ใช้กลไกคล้ายกัน) ยังคงมีคุณภาพโค้ดที่ควบคุมได้ แม้จะมีคนจากทั่วโลกส่งโค้ดเข้ามาพร้อมกัน

### ใครใช้ Pull Request บ้าง

Pull Request ใช้ได้ทั้งใน 2 บริบทหลัก:

1. **ภายในทีม/บริษัทเดียวกัน (Internal collaboration)** — ทุกคนมีสิทธิ์ push branch เข้า repo เดียวกันได้โดยตรง (ตาม permission ที่ตั้งไว้) แล้วเปิด PR จาก branch ของตัวเองไปยัง `main`
2. **Open Source / คนนอกทีม (Fork-based collaboration)** — คนที่ไม่มีสิทธิ์ push เข้า repo ต้นทางโดยตรง จะต้อง **Fork** repo นั้นมาเป็นของตัวเองก่อน (เราเรียนเรื่อง Fork ไปแล้วใน Part ก่อนหน้า) แก้ไขใน fork ของตัวเอง แล้วเปิด PR ข้ามจาก fork กลับไปยัง repo ต้นทาง

ใน Part นี้เราจะเน้นกรณีที่ 1 ก่อน (ทำงานในทีมที่มีสิทธิ์ push branch ได้เอง) เพราะเป็นกรณีพื้นฐานที่สุดและครอบคลุมการทำงานส่วนใหญ่ ส่วนกรณี Fork-based เราจะเจาะลึกอีกครั้งใน Part ที่ว่าด้วย Open Source Contribution โดยเฉพาะ

### ภาพรวมหน้าตาของ Pull Request บน GitHub

หน้า Pull Request บน GitHub ประกอบด้วยแท็บหลัก ๆ ดังนี้:

| แท็บ | ใช้ทำอะไร |
|---|---|
| **Conversation** | หน้าหลัก แสดง description, คอมเมนต์ทั้งหมด, สถานะการ review, ปุ่ม Merge |
| **Commits** | รายการ commit ทั้งหมดที่อยู่ใน PR นี้ |
| **Checks** | ผลการรัน CI/CD (automated test, build) ถ้ามีการตั้งค่าไว้ |
| **Files changed** | Diff view ของทุกไฟล์ที่เปลี่ยนแปลง (จะเจาะลึกใน Step 204) |

ตอนนี้เราเข้าใจแนวคิดพื้นฐานแล้ว มาลงมือสร้าง Pull Request จริงเป็นครั้งแรกกันใน Step ถัดไป

## Step 202: สร้าง PR แรก — ขั้นตอนเต็มตั้งแต่สร้าง branch จนถึงกด Compare & pull request

Step นี้คือหัวใจของ Part นี้ทั้งหมด เราจะเดินผ่านทุกขั้นตอนอย่างละเอียด ตั้งแต่ศูนย์จนได้ Pull Request แรกของคุณบน GitHub

### สถานการณ์สมมติ

สมมติว่าคุณมี repository ชื่อ `my-website` ที่ push ขึ้น GitHub แล้ว (ถ้ายังไม่มี ให้ย้อนกลับไปทบทวน Part 9–10 เรื่อง Remote Repository และ Push/Pull ก่อน) และคุณต้องการเพิ่มไฟล์ `about.html` เข้าไปในโปรเจกต์

### ขั้นตอนที่ 1: ตรวจสอบว่าอยู่บน branch `main` และเป็นเวอร์ชันล่าสุด

```bash
cd my-website
git checkout main
git pull origin main
```

การ `pull` ก่อนเสมอเป็นนิสัยที่ดีมาก เพื่อให้แน่ใจว่า branch ใหม่ที่คุณกำลังจะสร้างนั้นแตกออกมาจากจุดล่าสุดของ `main` จริง ๆ ไม่ใช่จุดเก่าที่คุณอาจพลาดตกหล่นการเปลี่ยนแปลงจากเพื่อนร่วมทีม

### ขั้นตอนที่ 2: สร้าง Feature Branch ใหม่

```bash
git checkout -b feature/add-about-page
```

คำสั่งนี้ทำ 2 อย่างพร้อมกัน (ตามที่เราเคยเรียนใน Part 7): สร้าง branch ชื่อ `feature/add-about-page` และสลับ (checkout) เข้าไปอยู่บน branch นั้นทันที

> **หมายเหตุเรื่องการตั้งชื่อ branch:** การตั้งชื่อแบบ `feature/...`, `fix/...`, `docs/...` เป็น convention ที่นิยมมากในทีมมืออาชีพ ช่วยให้เห็นภาพรวมได้ทันทีว่า branch นี้ทำอะไร เราจะพูดถึง naming convention แบบละเอียดในเฟส 4 (Git Workflow มาตรฐาน)

### ขั้นตอนที่ 3: แก้ไข/สร้างไฟล์ตามที่ต้องการ

สร้างไฟล์ `about.html` ด้วย editor ที่คุณถนัด (เช่น VS Code) ใส่เนื้อหาง่าย ๆ เช่น:

```html
<!DOCTYPE html>
<html lang="th">
<head>
  <meta charset="UTF-8">
  <title>เกี่ยวกับเรา</title>
</head>
<body>
  <h1>เกี่ยวกับเรา</h1>
  <p>นี่คือหน้าเว็บที่เพิ่มเข้ามาผ่าน Pull Request แรกของฉัน</p>
</body>
</html>
```

### ขั้นตอนที่ 4: Add และ Commit การเปลี่ยนแปลง

```bash
git add about.html
git commit -m "Add about page"
```

คุณสามารถแบ่งเป็นหลาย commit ได้ถ้างานมีหลายส่วน — Pull Request ไม่ได้จำกัดว่าต้องมีแค่ 1 commit เท่านั้น สามารถมีกี่ commit ก็ได้ตราบใดที่มันยังอยู่ใน branch เดียวกัน

### ขั้นตอนที่ 5: Push Branch ขึ้น GitHub

```bash
git push -u origin feature/add-about-page
```

การใส่ `-u` (หรือ `--set-upstream`) ในการ push ครั้งแรกของ branch ใหม่ เป็นสิ่งสำคัญมาก เพราะมันจะตั้งค่าให้ branch local ของคุณ **ติดตาม (track)** branch บน remote โดยอัตโนมัติ ทำให้ครั้งต่อไปคุณพิมพ์แค่ `git push` เฉย ๆ ได้เลยโดยไม่ต้องระบุชื่อ remote/branch ซ้ำอีก

หลัง push สำเร็จ คุณจะเห็นข้อความประมาณนี้ใน terminal:

```
remote: Create a pull request for 'feature/add-about-page' on GitHub by visiting:
remote:      https://github.com/your-username/my-website/pull/new/feature/add-about-page
```

**GitHub ฉลาดพอที่จะสังเกตเห็นว่ามี branch ใหม่ถูก push เข้ามา และเสนอลิงก์ให้คุณเปิด Pull Request ได้ทันทีจาก terminal เลย** — นี่คือทางลัดที่สะดวกมาก แต่เราจะเดินผ่านขั้นตอนบนหน้าเว็บแบบเต็มรูปแบบเพื่อให้เข้าใจ UI ทั้งหมด

### ขั้นตอนที่ 6: เปิดหน้า Repository บน GitHub

เข้าไปที่ `https://github.com/your-username/my-website` คุณจะเห็นแถบสีเหลืองแจ้งเตือนขึ้นมาที่ด้านบนของหน้า ประมาณว่า:

```
feature/add-about-page had recent pushes 1 minute ago
                                          [Compare & pull request]
```

แถบนี้จะปรากฏขึ้นเองโดยอัตโนมัติทุกครั้งที่มี branch ใหม่ถูก push เข้ามาภายในไม่กี่นาทีที่ผ่านมา เป็น UX ที่ GitHub ออกแบบมาให้ผู้ใช้ไม่พลาดโอกาสเปิด PR

### ขั้นตอนที่ 7: กดปุ่ม "Compare & pull request"

เมื่อกดปุ่มนี้ ระบบจะพาคุณไปยังหน้าสร้าง Pull Request ซึ่งประกอบด้วยส่วนสำคัญดังนี้:

1. **ช่อง base และ compare (ด้านบนสุด)**
   ```
   base: main  ←  compare: feature/add-about-page
   ```
   - **base** คือ branch ปลายทางที่คุณต้องการรวมโค้ดเข้าไป (โดยปกติคือ `main`)
   - **compare** คือ branch ต้นทางที่มีโค้ดใหม่ของคุณ

   จุดนี้สำคัญมาก — **ต้องตรวจสอบทุกครั้งว่า base ถูกต้อง** เพราะถ้าเลือกผิด (เช่น ไปเลือก base เป็น branch อื่นที่ไม่ใช่ที่ตั้งใจ) โค้ดของคุณอาจถูก merge เข้าผิดที่ผิดทาง

2. **ช่องหัวข้อ (Title)** — GitHub จะดึง commit message ล่าสุดมาใส่ให้อัตโนมัติ (ในตัวอย่างนี้คือ "Add about page") คุณสามารถแก้ไขให้กระชับและสื่อความหมายมากขึ้นได้

3. **ช่อง Description** — พื้นที่ข้อความยาวสำหรับอธิบายรายละเอียดของ PR (จะเจาะลึกวิธีเขียนที่ดีใน Step 203)

4. **ฝั่งขวามือ (Sidebar)** มีตัวเลือกเพิ่มเติม เช่น:
   - **Reviewers** — เลือกคนที่ต้องการให้มารีวิว PR นี้
   - **Assignees** — กำหนดคนรับผิดชอบ PR นี้
   - **Labels** — ติด label เช่น `bug`, `enhancement`, `documentation`
   - **Projects** — เชื่อมโยงกับ GitHub Project board
   - **Milestone** — กำหนดว่า PR นี้อยู่ใน milestone ไหน

5. **ด้านล่างสุด** จะแสดง diff ของไฟล์ที่เปลี่ยนแปลงทั้งหมดแบบย่อ ๆ ให้ดูก่อนกดสร้างจริง

### ขั้นตอนที่ 8: กดปุ่ม "Create pull request"

เมื่อกรอกข้อมูลครบและพอใจแล้ว กดปุ่มสีเขียว **"Create pull request"** ระบบจะสร้าง PR ให้ทันที พร้อมเลขที่ PR (เช่น `#1`, `#42`) ที่จะติดตัว PR นี้ไปตลอด ไม่มีวันซ้ำกับ PR อื่นใน repo เดียวกัน

**ยินดีด้วย — คุณสร้าง Pull Request แรกสำเร็จแล้ว!**

## Step 203: การเขียน PR description ที่ดี พร้อมตัวอย่าง PR template

### ทำไม PR description ถึงสำคัญมาก

PR description คือ **จดหมายอธิบายงาน** ที่คุณส่งให้ผู้รีวิวอ่านก่อนที่จะไปดูโค้ดจริง มันมีผลอย่างมากต่อ:

1. **ความเร็วในการรีวิว** — ผู้รีวิวที่เข้าใจบริบทก่อน จะรีวิวได้เร็วและแม่นยำกว่ามาก
2. **คุณภาพของ feedback ที่ได้** — ถ้าอธิบายไม่ชัด ผู้รีวิวอาจถามคำถามพื้นฐานวนไปวนมา แทนที่จะโฟกัสที่ประเด็นเชิงลึก
3. **ประวัติของโปรเจกต์ในระยะยาว** — เมื่อเวลาผ่านไป 6 เดือน ถ้ามีใครย้อนกลับมาดู PR นี้ description ที่ดีจะช่วยให้เข้าใจว่า "ทำไม" ถึงเขียนโค้ดแบบนี้ ไม่ใช่แค่ "อะไร" ที่เปลี่ยนไป

> หลักการสำคัญ: **commit message บอกว่า "เปลี่ยนอะไร" ส่วน PR description ควรบอกว่า "ทำไมถึงเปลี่ยน" และ "เปลี่ยนแล้วมีผลอย่างไร"**

### โครงสร้าง PR description ที่ดี (แบบทั่วไป)

PR description ที่ดีมักประกอบด้วยส่วนต่อไปนี้:

1. **สรุปสั้น ๆ (Summary)** — 1-2 ประโยคว่า PR นี้ทำอะไร
2. **เหตุผล/บริบท (Why)** — ทำไมถึงต้องทำการเปลี่ยนแปลงนี้ แก้ปัญหาอะไร
3. **รายละเอียดการเปลี่ยนแปลง (What changed)** — รายการสิ่งที่เปลี่ยนแปลง อาจเป็น bullet list
4. **วิธีทดสอบ (How to test)** — บอกผู้รีวิวว่าจะทดสอบการเปลี่ยนแปลงนี้อย่างไร
5. **ภาพหน้าจอ (Screenshots)** — ถ้าเป็นการเปลี่ยนแปลง UI ควรแนบภาพก่อน/หลังเสมอ
6. **Issue ที่เกี่ยวข้อง (Related issues)** — เชื่อมโยงกับ Issue ด้วย closing keywords (จะเรียนใน Step 209)
7. **สิ่งที่ยังไม่ได้ทำ/ข้อควรระวัง (Notes / Known limitations)** — ถ้ามี

### ตัวอย่าง PR description ที่เขียนไม่ดี (ควรหลีกเลี่ยง)

```
แก้บั๊กแล้ว
```

คำอธิบายแบบนี้ **แทบไม่มีประโยชน์เลย** — ผู้รีวิวไม่รู้เลยว่าบั๊กคืออะไร แก้อย่างไร ทดสอบอย่างไร ทำให้ต้องเสียเวลาไปไล่อ่านโค้ดทั้งหมดเพื่อทำความเข้าใจเอง

### ตัวอย่าง PR description ที่เขียนดี

```markdown

ลดคำถามซ้ำ ๆ ที่ทีม support ต้องตอบ

- เพิ่มไฟล์ `about.html` พร้อมเนื้อหาพื้นฐานของบริษัท

- เพิ่ม style สำหรับหน้านี้ใน `styles.css`

## วิธีทดสอบ

2. เปิด `index.html` ในเบราว์เซอร์
3. คลิกลิงก์ "เกี่ยวกับเรา" ที่ navigation bar
4. ตรวจสอบว่าหน้า about แสดงผลถูกต้องบนทั้งจอ desktop และ mobile

## ภาพหน้าจอ

|---|---|

## หมายเหตุ

ยังไม่ได้ทำ SEO meta tags สำหรับหน้านี้ จะทำในอีก PR แยกต่างหาก
```

จะเห็นว่า description แบบนี้ให้ข้อมูลครบถ้วนมาก ผู้รีวิวสามารถเข้าใจภาพรวมได้ภายใน 30 วินาที ก่อนที่จะไปดูโค้ดจริงในแท็บ Files changed

### PR Template — มาตรฐานที่ทีมมืออาชีพนิยมตั้งไว้ล่วงหน้า

หลายทีมไม่อยากให้สมาชิกแต่ละคนเขียน description แบบอิสระตามใจ เพราะจะทำให้ขาดความสม่ำเสมอ จึงใช้ฟีเจอร์ **Pull Request Template** ของ GitHub ซึ่งทำงานคล้ายกับ Issue Template ที่เราเคยเรียนไปก่อนหน้านี้

วิธีสร้าง PR Template คือสร้างไฟล์ชื่อ `pull_request_template.md` ไว้ในตำแหน่งใดตำแหน่งหนึ่งต่อไปนี้ของ repository (GitHub จะมองหาโดยอัตโนมัติ):

```
.github/pull_request_template.md
docs/pull_request_template.md
pull_request_template.md          (อยู่ที่ root ของ repo)
```

ตัวอย่างเนื้อหาไฟล์ `pull_request_template.md`:

```markdown
## สรุปการเปลี่ยนแปลง

<!-- อธิบายสั้น ๆ ว่า PR นี้ทำอะไร -->

## ประเภทของการเปลี่ยนแปลง

- [ ] Bug fix
- [ ] ฟีเจอร์ใหม่
- [ ] Breaking change
- [ ] อัปเดตเอกสาร

- [ ] โค้ดผ่านการทดสอบในเครื่องของฉันแล้ว
- [ ] เพิ่ม/แก้ไข test ที่เกี่ยวข้องแล้ว (ถ้าจำเป็น)
- [ ] อัปเดตเอกสารที่เกี่ยวข้องแล้ว (ถ้าจำเป็น)

```

เมื่อมีไฟล์นี้อยู่ใน repo แล้ว **ทุกครั้งที่มีคนกดสร้าง Pull Request ใหม่ เนื้อหานี้จะถูกใส่ลงในช่อง Description ให้อัตโนมัติทันที** ทำให้ทุก PR ในโปรเจกต์มีโครงสร้างเดียวกัน ลดการลืมข้อมูลสำคัญ และทำให้ผู้รีวิวคุ้นเคยกับรูปแบบเดิมทุกครั้ง

GitHub ยังรองรับการมี **หลาย template ให้เลือก** ผ่านโฟลเดอร์ `.github/PULL_REQUEST_TEMPLATE/` (ตัวพิมพ์ใหญ่ทั้งหมด) โดยใส่ไฟล์ `.md` หลายไฟล์ไว้ข้างใน เช่น `feature.md`, `bugfix.md` แล้วผู้สร้าง PR จะเลือก template ที่ต้องการผ่าน query parameter ใน URL เช่น:

```
https://github.com/owner/repo/compare/main...feature/xyz?template=feature.md
```

1. เขียนให้คนที่ **ไม่รู้บริบทอะไรเลย** อ่านแล้วเข้าใจได้
2. บอก **"ทำไม"** ไม่ใช่แค่ "อะไร" (โค้ดบอก "อะไร" อยู่แล้วในตัวมันเอง)
3. แนบวิธีทดสอบเสมอ ถ้าเป็นไปได้
4. แนบภาพหน้าจอถ้าเป็นการเปลี่ยนแปลงด้าน UI — เป็นมารยาทที่ดีต่อผู้รีวิวมาก
5. เชื่อมโยง Issue ที่เกี่ยวข้องเสมอถ้ามี

## Step 204: การอ่าน Diff view ใน PR (Files changed tab, +/- lines, Split vs Unified view)

### แท็บ "Files changed" คืออะไร

หลังสร้าง PR แล้ว หนึ่งในแท็บที่สำคัญที่สุดคือ **Files changed** ซึ่งจะแสดง **diff** ของทุกไฟล์ที่มีการเปลี่ยนแปลงในช่วงระหว่าง branch base กับ branch compare อย่างละเอียด นี่คือที่ที่ผู้รีวิวจะใช้เวลาส่วนใหญ่ในการทำงาน

### การอ่านสัญลักษณ์ +/- ในแต่ละบรรทัด

Diff view ของ GitHub ใช้สีและสัญลักษณ์เพื่อบอกสถานะของแต่ละบรรทัด:

| สัญลักษณ์ | สี | ความหมาย |
|---|---|---|
| `+` (นำหน้าบรรทัด) | พื้นหลังสีเขียว | บรรทัดนี้ถูก **เพิ่มเข้ามาใหม่** |
| `-` (นำหน้าบรรทัด) | พื้นหลังสีแดง | บรรทัดนี้ถูก **ลบออก** |
| ไม่มีสัญลักษณ์ | พื้นหลังปกติ (สีขาว/เทา) | บรรทัดนี้ **ไม่เปลี่ยนแปลง** แสดงไว้เพื่อเป็นบริบท (context) |

ตัวอย่าง diff จริง:

```diff
 function greet(name) {
-  console.log("Hello " + name);
+  console.log(`Hello ${name}!`);
 }
```

จาก diff นี้อ่านได้ว่า: บรรทัด `console.log("Hello " + name);` (สีแดง) ถูกลบออกไป และถูกแทนที่ด้วยบรรทัด `` console.log(`Hello ${name}!`); `` (สีเขียว) — ส่วนบรรทัด `function greet(name) {` และ `}` ไม่มีการเปลี่ยนแปลงเลย แสดงไว้เป็นบริบทให้เข้าใจตำแหน่งเท่านั้น

> **จุดที่ควรระวัง:** เมื่อคุณเห็นบรรทัดสีแดงตามด้วยบรรทัดสีเขียวที่เนื้อหาคล้ายกัน นั่นหมายถึง Git มองว่าเป็นการ "แก้ไข" บรรทัดนั้น (ลบของเก่าทิ้ง แล้วเพิ่มของใหม่เข้าไปแทน) — Git **ไม่มีแนวคิดเรื่อง "แก้ไขบรรทัด" โดยตรง** มันมองทุกอย่างเป็นแค่ "ลบ" กับ "เพิ่ม" เท่านั้น ซึ่งเป็นแนวคิดเดียวกับที่เราเคยเรียนใน Part 5 เรื่อง `git diff`

### สรุปสถิติการเปลี่ยนแปลงที่หัวไฟล์

เหนือ diff ของแต่ละไฟล์ GitHub จะแสดงแถบสรุปแบบนี้:

```
about.html    +25 -0
```

หมายความว่าไฟล์ `about.html` มีการเพิ่มเข้าไป 25 บรรทัด และไม่มีการลบเลย (ไฟล์ใหม่ทั้งหมด) หรือถ้าเป็นไฟล์ที่แก้ไข อาจเห็นแบบ:

```
styles.css    +12 -3
```

หมายถึงเพิ่ม 12 บรรทัด ลบ 3 บรรทัด ในไฟล์นั้น และที่ด้านบนสุดของแท็บ Files changed ทั้งหน้า จะมีสรุปรวมของทั้ง PR เช่น:

```
3 files changed    +45 -8
```

ตัวเลขเหล่านี้ช่วยให้ผู้รีวิวประเมินขนาดของ PR ได้อย่างรวดเร็วก่อนเริ่มอ่านรายละเอียด — โดยทั่วไป **PR ที่มีขนาดเล็ก (ไม่กี่สิบถึงไม่กี่ร้อยบรรทัด) จะรีวิวง่ายและเร็วกว่า PR ขนาดใหญ่มาก** นี่คือเหตุผลที่ทีมมืออาชีพมักแนะนำให้แบ่งงานเป็น PR เล็ก ๆ หลายอันแทนที่จะทำ PR ยักษ์ใหญ่ทีเดียว

### Split view vs Unified view

GitHub มีปุ่มเล็ก ๆ มุมขวาบนของแท็บ Files changed ให้เลือกสลับรูปแบบการแสดง diff ได้ 2 แบบ:

#### 1. Unified view (ค่าเริ่มต้น)

แสดงบรรทัดเก่าและใหม่ **เรียงต่อกันในคอลัมน์เดียว** โดยใช้สีแดง/เขียวแยกความแตกต่าง (ตัวอย่างที่แสดงไปด้านบนคือรูปแบบ Unified)

**ข้อดี:** กระชับ ใช้พื้นที่แนวนอนน้อย เหมาะกับหน้าจอเล็กหรือการเปลี่ยนแปลงที่ไม่ซับซ้อนมาก

#### 2. Split view

แสดงเป็น **2 คอลัมน์คู่ขนานกัน** — คอลัมน์ซ้ายคือเนื้อหา "ก่อนแก้ไข" คอลัมน์ขวาคือ "หลังแก้ไข" เทียบกันแบบเห็นภาพชัดเจน คล้ายโปรแกรมเปรียบเทียบไฟล์ (diff tool) ทั่วไป

```
ก่อนแก้ไข (ซ้าย)                    │  หลังแก้ไข (ขวา)
─────────────────────────────────  │  ─────────────────────────────────
function greet(name) {              │  function greet(name) {
  console.log("Hello " + name);     │    console.log(`Hello ${name}!`);
}                                    │  }
```

**ข้อดี:** เห็นการเปลี่ยนแปลงแบบเทียบเคียงชัดเจนมาก โดยเฉพาะเมื่อบรรทัดมีการแก้ไขเนื้อหาเยอะ ทำให้แยกแยะง่ายว่าอันไหนคือของเก่า อันไหนคือของใหม่

**ข้อเสีย:** ใช้พื้นที่แนวนอนมากกว่า อาจต้อง scroll ซ้าย-ขวาบนหน้าจอเล็ก

> ผู้รีวิวมักเลือกใช้ตามความถนัดส่วนตัว — ไม่มีแบบไหนถูกหรือผิด ลองใช้ทั้งสองแบบแล้วเลือกแบบที่คุณอ่านสบายที่สุด การตั้งค่านี้ GitHub จะจดจำไว้ให้ในบัญชีของคุณ

### การคอมเมนต์บนบรรทัดโค้ดโดยตรง

จุดเด่นสำคัญของแท็บ Files changed คือเมื่อคุณเอาเมาส์ไปวางเหนือเลขบรรทัดใด ๆ จะมีเครื่องหมาย **`+`** สีน้ำเงินปรากฏขึ้น กดแล้วจะเปิดกล่องข้อความให้คอมเมนต์ **ผูกติดกับบรรทัดนั้นโดยเฉพาะ** ทำให้การสนทนาเกี่ยวกับโค้ดมีบริบทชัดเจนมาก แทนที่จะต้องคอมเมนต์แบบกว้าง ๆ ใน Conversation tab แล้วอธิบายว่า "บรรทัดที่เท่าไหร่ในไฟล์ไหน" — เราจะเจาะลึกกระบวนการ Code Review แบบเต็มรูปแบบ รวมถึงการคอมเมนต์แบบนี้ ใน **Part 22: Code Review บน GitHub**

### ไฟล์ที่ถูกทำเครื่องหมายพิเศษ

ในแท็บ Files changed คุณอาจเห็นป้ายกำกับพิเศษบนบางไฟล์:

| ป้ายกำกับ | ความหมาย |
|---|---|
| **Viewed** (checkbox) | คุณกดติ๊กว่าดูไฟล์นี้แล้ว ช่วยติดตามความคืบหน้าเวลารีวิว PR ที่มีหลายไฟล์ |
| **Large diffs are not rendered by default** | ไฟล์มีการเปลี่ยนแปลงจำนวนมากเกินไป (หรือเป็นไฟล์ binary) GitHub จะซ่อน diff ไว้ก่อน ต้องกด "Load diff" เพื่อดู |
| **This file was deleted** | ไฟล์นี้ถูกลบทิ้งไปใน PR นี้ |

การติ๊ก "Viewed" มีประโยชน์มากเวลารีวิว PR ขนาดใหญ่ที่มีหลายสิบไฟล์ เพราะช่วยให้คุณจำได้ว่าไฟล์ไหนดูแล้วบ้าง ไม่ต้องไล่ดูซ้ำเวลากลับมารีวิวต่อ

## Step 205: Draft Pull Request คืออะไร ใช้ตอนไหน

### ปัญหาที่ Draft PR ถูกสร้างมาแก้

ลองนึกภาพสถานการณ์นี้: คุณกำลังทำฟีเจอร์ใหญ่ที่ใช้เวลาหลายวัน แต่คุณอยากให้ทีม **เห็นความคืบหน้า** เป็นระยะ อยากให้ CI รันทดสอบให้ทุกครั้งที่ push อยากให้เพื่อนร่วมทีมเข้ามาดูโค้ดคร่าว ๆ ได้ แต่ **ยังไม่พร้อมให้ merge** และไม่อยากให้ใครกด Approve หรือ Merge โดยเข้าใจผิดว่างานเสร็จแล้ว

นี่คือปัญหาที่ **Draft Pull Request** ถูกออกแบบมาแก้โดยเฉพาะ

### นิยามของ Draft PR

> **Draft Pull Request คือ Pull Request ปกติทุกอย่าง แต่ถูกทำเครื่องหมายว่า "ยังไม่พร้อมสำหรับการรีวิวขั้นสุดท้ายหรือการ merge"**

Draft PR มีความสามารถเหมือน PR ปกติทุกอย่าง:

- push commit เพิ่มได้ตามปกติ
- CI/CD รันทดสอบให้เหมือนเดิมทุกครั้งที่ push
- เพื่อนร่วมทีมคอมเมนต์ได้ตามปกติ
- ดู diff ในแท็บ Files changed ได้ตามปกติ

**สิ่งเดียวที่ต่างคือ:** ปุ่ม **Merge** จะถูก **disable (กดไม่ได้)** จนกว่าคุณจะเปลี่ยนสถานะจาก Draft เป็น "Ready for review" และในหน้ารายการ Pull Request ของ repo, Draft PR จะแสดงไอคอนสีเทาที่ต่างจาก PR ปกติ (ที่เป็นสีเขียว) ทำให้ทุกคนมองปราดเดียวก็รู้ว่า **PR นี้ยังไม่พร้อมให้พิจารณา merge**

### วิธีสร้าง Draft Pull Request

มี 2 วิธีหลัก:

**วิธีที่ 1: สร้างเป็น Draft ตั้งแต่แรก**

ในหน้าสร้าง Pull Request (หน้าเดียวกับที่เราเจอใน Step 202) แทนที่จะกดปุ่ม **"Create pull request"** ให้กดที่ **ลูกศรเล็ก ๆ ข้างปุ่ม (dropdown arrow)** แล้วเลือก **"Create draft pull request"** แทน

```
[Create pull request ▼]
    ├─ Create pull request
    └─ Create draft pull request   ← เลือกอันนี้
```

**วิธีที่ 2: เปลี่ยน PR ปกติที่สร้างไปแล้วให้เป็น Draft**

ถ้าคุณสร้าง PR ปกติไปแล้วแต่อยากเปลี่ยนกลับเป็น Draft (เช่น พบว่ามีปัญหาเพิ่มเติมต้องแก้ก่อน) เข้าไปที่แท็บ Conversation แล้วมองหาลิงก์ **"Convert to draft"** ที่อยู่ทางฝั่งขวาของหน้าใกล้ ๆ ปุ่ม Merge

### วิธีเปลี่ยนจาก Draft เป็น Ready for review

เมื่องานเสร็จสมบูรณ์พร้อมให้รีวิวจริง กดปุ่ม **"Ready for review"** ที่อยู่ในหน้า PR (แทนที่ปุ่ม Merge ที่ถูก disable ไว้) ระบบจะเปลี่ยนสถานะทันที เปิดให้ปุ่ม Merge ใช้งานได้ และมักจะส่ง notification แจ้งผู้ที่ถูกเพิ่มเป็น reviewer ว่า PR นี้พร้อมให้พิจารณาแล้ว

### เมื่อไหร่ควรใช้ Draft PR

| สถานการณ์ | ควรใช้ Draft PR หรือไม่ |
|---|---|
| งานยังทำไม่เสร็จ แต่อยากให้ CI รันทดสอบให้ทุกครั้งที่ push | ควรใช้ |
| อยากขอความเห็นเบื้องต้นจากทีมก่อนทำงานต่อ ("ทิศทางแบบนี้โอเคไหม") | ควรใช้ |
| ทำงานคนเดียวแบบส่วนตัว ยังไม่อยากให้ใครเห็นเลย | ไม่ต้องสร้าง PR เลยจนกว่าจะพร้อม (หรือ push branch ไว้เฉย ๆ โดยยังไม่เปิด PR) |
| งานเสร็จสมบูรณ์ พร้อมให้รีวิวจริงจังแล้ว | ใช้ PR ปกติ (ไม่ใช่ Draft) |
| อยากกัน branch ไว้ก่อนไม่ให้คนอื่นมาแตะพื้นที่เดียวกัน พร้อมให้เห็นความคืบหน้า | ควรใช้ |

### ข้อดีของการใช้ Draft PR อย่างสม่ำเสมอ

1. **โปร่งใส (Transparency)** — ทีมเห็นว่าใครกำลังทำอะไรอยู่แบบ real-time ไม่ต้องรอจนงานเสร็จถึงจะรู้
2. **ได้ feedback เร็วขึ้น** — ถ้าทิศทางที่ทำผิดตั้งแต่ต้น จะรู้เร็วกว่าไปเสร็จหมดแล้วค่อยรู้ทีหลัง (ประหยัดเวลามาก)
3. **CI ทำงานให้เนียน ๆ ตลอดทาง** — ถ้ามี test พังตั้งแต่ระหว่างทาง คุณจะรู้ทันทีไม่ต้องรอจนจบงาน
4. **ป้องกันการ merge พลาด** — ปุ่ม Merge ที่ disable ไว้เป็นเกราะป้องกันความผิดพลาดที่ดีมาก โดยเฉพาะในทีมใหญ่ที่มีคนคอย merge PR หลายอันพร้อมกัน

หลายทีมมืออาชีพถือเป็นวัฒนธรรมเลยว่า **"เปิด Draft PR ตั้งแต่วันแรกที่เริ่มงาน"** แทนที่จะรอจนงานเสร็จค่อยเปิด PR — เป็นแนวปฏิบัติที่แนะนำอย่างยิ่งเมื่อคุณเริ่มทำงานเป็นทีมจริงจัง

## Step 206: การอัปเดต PR หลังสร้างแล้ว (push commit เพิ่มเข้า branch เดิม จะอัปเดต PR อัตโนมัติ)

### หลักการสำคัญที่ต้องเข้าใจให้แม่น

> **Pull Request ไม่ใช่ "สำเนา" ของโค้ด แต่เป็นแค่ "หน้าต่าง" ที่มองไปยัง branch ต้นทางของมันแบบ real-time**

พูดอีกแบบคือ PR **ไม่ได้ผูกติดกับ commit ชุดใดชุดหนึ่งตายตัว** แต่มันติดตาม branch นั้นตลอดเวลา ตราบใดที่ branch ยังไม่ถูกลบและ PR ยังไม่ถูก merge หรือปิด — **ทุกครั้งที่คุณ push commit ใหม่เข้า branch เดิมที่ผูกกับ PR นั้น หน้า PR จะอัปเดตเนื้อหาให้เองโดยอัตโนมัติทันที** ไม่ต้องไปกดปุ่มอะไรเพิ่มเติมทั้งสิ้น

### ตัวอย่างสถานการณ์การอัปเดต PR

สมมติว่า PR #1 ของคุณ (จาก branch `feature/add-about-page`) มีคนมาคอมเมนต์ขอให้แก้ไข เช่น:

> "ช่วยเพิ่ม `<meta name="description">` ในหน้า about ด้วยครับ เพื่อ SEO"

คุณกลับไปที่เครื่อง แก้ไขตามที่ขอ:

```bash
# ตรวจสอบว่าอยู่บน branch ที่ถูกต้อง
git branch
# * feature/add-about-page

# แก้ไขไฟล์ about.html ตามคอมเมนต์

git add about.html
git commit -m "Add meta description for SEO as requested in review"
git push
```

สังเกตว่าคำสั่งสุดท้ายคือ `git push` เฉย ๆ ไม่ต้องระบุ `origin feature/add-about-page` อีก เพราะเราตั้งค่า upstream ไว้แล้วตั้งแต่ Step 202 (ด้วยแฟล็ก `-u`)

เมื่อ push สำเร็จ **กลับไปดูที่หน้า PR บนเว็บ GitHub — คุณจะเห็นว่า:**

1. แท็บ **Commits** มี commit ใหม่ปรากฏเพิ่มเข้ามาโดยอัตโนมัติ
2. แท็บ **Files changed** อัปเดต diff ให้รวมการเปลี่ยนแปลงล่าสุดด้วย
3. ถ้ามี CI ตั้งไว้ จะมีการรัน CI รอบใหม่โดยอัตโนมัติกับ commit ล่าสุด
4. ผู้ที่ถูกขอให้ approve ก่อนหน้านี้ (ถ้ามี) อาจเห็นข้อความ "This branch has new changes since your last review" เตือนให้เข้ามารีวิวซ้ำ

### ข้อควรระวังเรื่อง Approval หลังมีการอัปเดต

ในบาง repository ที่ตั้งค่า Branch Protection Rule แบบเข้มงวด (จะเรียนละเอียดในเฟส 4) อาจมีการตั้งค่าให้ **"Dismiss stale pull request approvals when new commits are pushed"** ซึ่งหมายความว่า **ถ้ามีคน approve PR ไปแล้ว แต่คุณ push commit ใหม่เข้ามาอีก การ approve เดิมนั้นจะถูกยกเลิกโดยอัตโนมัติ** และต้องให้คนนั้นมา approve ใหม่อีกครั้ง — นี่เป็นกลไกป้องกันไม่ให้มีใคร "แอบ" push โค้ดเพิ่มหลังจากได้รับ approve ไปแล้วโดยไม่มีใครตรวจสอบซ้ำ

### สิ่งที่เกิดขึ้นถ้า push จาก branch อื่นโดยไม่ได้ตั้งใจ

ข้อผิดพลาดที่มือใหม่มักทำคือลืมเช็คว่าตัวเองอยู่บน branch ไหนก่อน push ทำให้ commit ไปตกอยู่ผิด branch หรือผิด PR — วิธีป้องกันคือให้เช็ค `git branch` หรือดูชื่อ branch ที่มุมล่างซ้ายของ VS Code (ถ้าใช้) ก่อน push ทุกครั้งจนเป็นนิสัย

### การ Force Push เข้า PR (ควรระวังเป็นพิเศษ)

ถ้าคุณต้องแก้ไขประวัติ commit ของ branch (เช่นใช้ `git rebase` หรือ `git commit --amend` ตามที่จะเรียนในเฟสถัดไป) แล้วต้อง `git push --force` เข้า branch ที่ผูกกับ PR อยู่ — สิ่งนี้ **ทำได้** และ PR จะยังคงอัปเดตแสดง diff ล่าสุดให้เหมือนเดิม แต่ต้อง **ระมัดระวังอย่างมาก** เพราะ:

1. commit เดิมที่ผู้รีวิวเคยคอมเมนต์ไว้อาจหายไปจากประวัติ ทำให้บริบทของคอมเมนต์เก่าดูสับสน
2. ถ้ามีคนอื่นดึง branch นี้ไปทำงานต่อพร้อมกัน การ force push อาจทำให้เกิดปัญหาประวัติขัดแย้งกัน

เราจะเจาะลึกเรื่อง force push และ rebase แบบละเอียด พร้อมกฎเกณฑ์ว่าเมื่อไหร่ควร/ไม่ควรใช้ ในเฟส 4 ของหลักสูตรนี้ (Git Workflow ขั้นสูง) — ตอนนี้ขอให้จำไว้แค่ว่า **การ push ปกติ (ไม่ force) เข้า branch เดิม คือวิธีมาตรฐานและปลอดภัยที่สุดในการอัปเดต PR**

### สรุป Step นี้เป็นประโยคเดียว

> **หนึ่ง Pull Request ผูกกับหนึ่ง branch เสมอ — ตราบใดที่คุณยัง push commit ใหม่เข้า branch นั้นต่อไป PR จะติดตามและอัปเดตตัวเองให้เห็นการเปลี่ยนแปลงล่าสุดเสมอโดยอัตโนมัติ ไม่ต้องสร้าง PR ใหม่ทุกครั้งที่มีการแก้ไข**

## Step 207: การ Merge PR — 3 วิธี (Merge commit, Squash and merge, Rebase and merge)

เมื่อ Pull Request ผ่านการรีวิวและพร้อมนำเข้า branch หลักแล้ว ถึงเวลากด merge — แต่ GitHub ไม่ได้มีวิธี merge แบบเดียว มันมีให้เลือกถึง **3 วิธี** ที่ให้ผลลัพธ์ต่อประวัติ (history) ของ repository แตกต่างกันอย่างมีนัยสำคัญ

### ภาพรวมปุ่ม Merge บน GitHub

เมื่อ PR พร้อม merge (ไม่มี conflict, ผ่านเงื่อนไขที่ตั้งไว้) คุณจะเห็นปุ่มสีม่วง/เขียวขนาดใหญ่เขียนว่า **"Merge pull request"** พร้อมลูกศร dropdown ข้าง ๆ ให้เลือกวิธี merge ทั้ง 3 แบบ:

```
[Merge pull request ▼]
    ├─ Create a merge commit
    ├─ Squash and merge
    └─ Rebase and merge
```

> **หมายเหตุ:** repository บางที่อาจถูกตั้งค่าให้เห็นแค่บางตัวเลือกเท่านั้น (เจ้าของ repo สามารถปิดตัวเลือกบางแบบได้ใน Settings → General → Pull Requests) เราจะเจาะลึกเรื่องนี้อีกครั้งใน **Part 37** ซึ่งจะอธิบายผลกระทบเชิงลึกของแต่ละวิธีต่อ Git history, การใช้ `git bisect`, และการเลือกกลยุทธ์ที่เหมาะกับทีมของคุณ ในที่นี้เราจะเข้าใจแค่ระดับแนวคิดพื้นฐานพอให้ใช้งานได้ถูกต้อง

### วิธีที่ 1: Create a merge commit (ค่าเริ่มต้นของ GitHub)

วิธีนี้คือการทำงานเหมือนคำสั่ง `git merge` แบบปกติที่เราเคยเรียนใน Part 8 — ระบบจะสร้าง **commit ใหม่ 1 อัน** ที่เรียกว่า **merge commit** ซึ่งมี "พ่อแม่" (parent) 2 commit คือปลายทางของ `main` และปลายทางของ branch feature พร้อมกัน

```
main:      A ─── B ─────────── M   (M = merge commit)
                     \         /
feature:              C ─── D
```

**ลักษณะเด่น:** ประวัติทั้งหมดของ commit ใน feature branch (C, D) ยังคงอยู่ใน `main` แบบครบถ้วนทุก commit ไม่มีการเปลี่ยนแปลงใด ๆ กับ commit เดิม แค่เพิ่ม commit ใหม่ (M) เข้ามาเพื่อรวม 2 เส้นทางเข้าด้วยกัน

**เหมาะกับ:** ทีมที่ต้องการเก็บประวัติแบบละเอียดที่สุด อยากเห็นว่า feature นี้พัฒนามาเป็นขั้นตอนอย่างไรบ้างจริง ๆ

### วิธีที่ 2: Squash and merge

วิธีนี้จะ **รวมทุก commit ใน feature branch ให้กลายเป็น commit เดียว** ก่อนนำไปต่อท้าย `main`

```
main (ก่อน):      A ─── B
feature:                 \─ C ─── D ─── E

main (หลัง squash):  A ─── B ─── S   (S = commit เดียวที่รวม C+D+E เข้าด้วยกัน)
```

เมื่อกด "Squash and merge" GitHub จะเปิดกล่องให้แก้ไข commit message ของ commit ใหม่ (S) นี้ได้ โดยปกติจะดึงหัวข้อ PR มาใส่ให้เป็นค่าเริ่มต้น และรวบรวมข้อความจากทุก commit ย่อยไว้ในส่วน description ให้อัตโนมัติ

**ลักษณะเด่น:** ประวัติของ `main` จะดูสะอาดมาก — 1 Pull Request = 1 commit เท่านั้น ไม่ว่าคุณจะ commit ย่อยไปกี่ครั้งระหว่างทำงานก็ตาม (เช่น "wip", "fix typo", "try again" ที่มักเกิดขึ้นระหว่างพัฒนาจริง) จะถูกรวบให้หายไปในประวัติของ `main`

**เหมาะกับ:** ทีมที่ต้องการ history ของ `main` ที่สะอาด อ่านง่าย 1 บรรทัดต่อ 1 ฟีเจอร์/1 บั๊กฟิกซ์ ไม่สนใจรายละเอียดปลีกย่อยระหว่างการพัฒนา — เป็นวิธีที่ **นิยมมากที่สุดในทีมสมัยใหม่จำนวนมาก** เพราะช่วยให้ `git log` ของ `main` อ่านเข้าใจง่ายมาก

### วิธีที่ 3: Rebase and merge

วิธีนี้จะนำทุก commit จาก feature branch (C, D, E) ไป **"เล่นซ้ำ" (replay)** ต่อท้ายปลายของ `main` ทีละ commit โดย **ไม่สร้าง merge commit ใด ๆ เลย**

```
main (ก่อน):      A ─── B
feature:                 \─ C ─── D ─── E

main (หลัง rebase):  A ─── B ─── C' ─── D' ─── E'
```

(สังเกตว่า C', D', E' มี `'` กำกับ เพราะแม้เนื้อหาจะเหมือนเดิม แต่ hash ของ commit จะเปลี่ยนไป เนื่องจาก parent ของมันเปลี่ยน)

**ลักษณะเด่น:** ประวัติของ `main` จะเป็นเส้นตรงสนิท (linear history) ไม่มีจุดแตกแขนงเลย และยังคงเห็น commit ย่อยทุกอันจากการพัฒนา เหมือนกับว่าคุณ commit ทุกอย่างนั้นต่อจาก `main` มาตั้งแต่แรก

**เหมาะกับ:** ทีมที่หลงใหลในประวัติที่เป็นเส้นตรงสมบูรณ์แบบ ไม่ต้องการเห็น merge commit เกะกะเลยแม้แต่อันเดียว

### ตารางเปรียบเทียบสรุป

| วิธี | จำนวน commit ที่เพิ่มใน main | มี merge commit ไหม | ประวัติ commit ย่อยยังอยู่ไหม |
|---|---|---|---|
| **Create a merge commit** | ทุก commit เดิม + 1 merge commit | มี | อยู่ครบ |
| **Squash and merge** | 1 commit เดียว | ไม่มี | ถูกรวมเป็นก้อนเดียว ไม่แยกแล้ว |
| **Rebase and merge** | ทุก commit เดิม (เขียนใหม่) | ไม่มี | อยู่ครบ (แต่ hash เปลี่ยน) |

### จะเลือกวิธีไหนดี (ระดับเบื้องต้น)

- ถ้าไม่แน่ใจ และทีมยังไม่มีข้อตกลงร่วมกัน — **Squash and merge** เป็นตัวเลือกที่ปลอดภัยและเข้าใจง่ายที่สุดสำหรับมือใหม่ เพราะทำให้ history ของ `main` อ่านง่าย ไม่ต้องกังวลเรื่อง commit ย่อยที่ไม่สวยงามระหว่างพัฒนา
- ถ้าต้องการเก็บบริบทการพัฒนาแบบละเอียดทุกขั้นตอนไว้ในประวัติ — ใช้ **Create a merge commit**
- ถ้าต้องการ history เส้นตรงสมบูรณ์แบบและทีมคุ้นเคยกับ rebase ดีแล้ว — ใช้ **Rebase and merge**

เราจะกลับมาเจาะลึกเรื่องนี้อย่างละเอียดมาก ๆ อีกครั้งใน **Part 37** ซึ่งจะพูดถึงผลกระทบต่อ `git log`, `git blame`, `git bisect` และวิธีที่ทีมระดับโลก (เช่น ทีมที่ดูแล React หรือ Kubernetes) เลือกใช้กลยุทธ์การ merge อย่างไรและทำไม

### หลังกด Merge แล้วเกิดอะไรขึ้น

ไม่ว่าจะเลือกวิธีไหน หลังกดยืนยัน merge สำเร็จ:

1. หัวข้อ PR จะเปลี่ยนสีจากม่วง (open) เป็น **สีม่วงเข้มพร้อมข้อความ "Merged"**
2. GitHub จะแสดงปุ่ม **"Delete branch"** ให้กดลบ feature branch บน remote ได้ทันที (จะพูดถึงรายละเอียดใน Step 210)
3. ถ้า PR นี้เชื่อมโยงกับ Issue ด้วย closing keyword (Step 209) Issue นั้นจะถูกปิดโดยอัตโนมัติทันที

## Step 208: การปิด PR โดยไม่ merge (Close pull request) ใช้ตอนไหน

### ไม่ใช่ทุก PR ที่จะจบด้วยการ Merge

Pull Request ไม่จำเป็นต้องจบลงด้วยการ merge เสมอไป บางครั้งการตัดสินใจที่ถูกต้องที่สุดคือ **การปิดมันทิ้งโดยไม่นำโค้ดเข้า branch หลัก** ซึ่ง GitHub รองรับผ่านปุ่ม **"Close pull request"** ที่อยู่ด้านล่างสุดของแท็บ Conversation (ปุ่มสีเทา อยู่ข้าง ๆ กล่องคอมเมนต์)

### สถานการณ์ที่ควร Close PR โดยไม่ Merge

1. **แนวทางที่เสนอไม่ถูกต้อง/ไม่เหมาะสม** — หลังรีวิวแล้วทีมเห็นว่าวิธีแก้ปัญหาที่เสนอมาไม่ใช่แนวทางที่ดีที่สุด ควรทำใหม่ด้วยวิธีอื่นทั้งหมด
2. **ฟีเจอร์นั้นไม่จำเป็นอีกต่อไป** — ระหว่างที่ทำ PR อยู่ ทีมตัดสินใจเปลี่ยนแผนธุรกิจ ทำให้ฟีเจอร์นี้ไม่จำเป็นแล้ว
3. **มี PR อื่นที่ทำสิ่งเดียวกันแล้วถูก merge ไปก่อน** — เกิดการทำงานซ้ำซ้อนกันโดยไม่ได้ตั้งใจ (พบได้บ่อยในทีมใหญ่หรือโปรเจกต์ Open Source ที่มีคนช่วยกันเยอะ)
4. **PR ทดลอง/สำรวจแนวทาง (Exploratory/Spike)** — เปิด PR เพื่อทดลองแนวคิดและขอความเห็นจากทีมเท่านั้น ไม่ได้ตั้งใจจะ merge เข้าจริงตั้งแต่แรก
5. **Contributor หายไปกลางทาง (Stale PR)** — ในโปรเจกต์ Open Source บางครั้งคนที่เปิด PR เงียบหายไป ไม่ตอบกลับการรีวิวเป็นเวลานาน maintainer อาจตัดสินใจปิด PR นั้นเพื่อความเรียบร้อยของ repository

### วิธี Close PR

ทำได้ง่ายมาก เพียงเข้าไปที่แท็บ Conversation ของ PR แล้วเลื่อนลงไปด้านล่างสุด กดปุ่ม **"Close pull request"** ระบบจะเปลี่ยนสถานะ PR จาก **Open (สีเขียว)** เป็น **Closed (สีแดง)** ทันที

> เป็นมารยาทที่ดีมากที่จะ **เขียนคอมเมนต์อธิบายเหตุผลที่ปิด PR** ก่อนกดปิดเสมอ เช่น "ขอบคุณสำหรับการเสนอโค้ดนี้ครับ แต่ทีมตัดสินใจเปลี่ยนแนวทางไปใช้วิธี X แทน จึงขอปิด PR นี้ก่อนนะครับ" — โดยเฉพาะในบริบท Open Source การปิด PR โดยไม่อธิบายอะไรเลยอาจทำให้ contributor รู้สึกไม่ดีและไม่กลับมาช่วยเหลือโปรเจกต์อีก

### ความแตกต่างระหว่าง Close กับ Merge ในแง่ผลลัพธ์ทางเทคนิค

| | Close pull request | Merge pull request |
|---|---|---|
| โค้ดจาก feature branch เข้า `main` หรือไม่ | ไม่เข้า | เข้า |
| เก็บประวัติการสนทนา/รีวิวไว้หรือไม่ | เก็บไว้ (อ่านย้อนหลังได้เสมอ) | เก็บไว้เช่นกัน |
| สถานะที่แสดง | Closed (สีแดง) | Merged (สีม่วง) |
| Branch ต้นทางถูกลบอัตโนมัติหรือไม่ | ไม่ถูกลบอัตโนมัติ (ต้องลบเอง) | มีปุ่มให้กดลบทันที |
| เปิดใหม่ได้ไหม | ได้ (กด "Reopen pull request") | ทำไม่ได้ (merge แล้วถอนกลับไม่ได้ในลักษณะเดียวกัน) |

### การเปิด PR ที่ปิดไปแล้วกลับมาใหม่

ถ้า PR ที่ถูกปิดไปแล้ว (ยังไม่ merge) กลายเป็นว่าจริง ๆ แล้วยังต้องการใช้อยู่ (เช่น เปลี่ยนใจ หรือ branch ต้นทางยังไม่ถูกลบ) สามารถกด **"Reopen pull request"** ได้ทันที ระบบจะนำ PR กลับมาที่สถานะ Open พร้อมประวัติการสนทนาเดิมทั้งหมดครบถ้วน — เงื่อนไขเดียวคือ **branch ต้นทางต้องยังไม่ถูกลบ** ถ้า branch ถูกลบไปแล้ว การ reopen จะทำให้ PR แสดงสถานะพิเศษว่า "This branch has been deleted" ซึ่งจะ reopen แล้วยังไม่มีโค้ดให้ merge จริง ต้องสร้าง branch ใหม่และ push โค้ดกลับเข้าไปที่ branch เดิมชื่อเดียวกันก่อนถึงจะใช้งานได้ตามปกติ

### สรุป Step นี้

Close pull request ไม่ใช่ "ความล้มเหลว" ของ PR แต่เป็น **เครื่องมือจัดการที่มีประโยชน์** สำหรับรักษาความเป็นระเบียบของ repository เมื่องานที่เสนอมาไม่เหมาะสมที่จะนำเข้า branch หลักอีกต่อไป

## Step 209: การเชื่อมโยง PR กับ Issue อัตโนมัติด้วย Closing Keywords ในคำอธิบาย PR

### ทำไมต้องเชื่อมโยง PR กับ Issue

ในการทำงานจริง แทบทุกฟีเจอร์หรือบั๊กฟิกซ์เริ่มต้นจากการมี **Issue** (ที่เราเคยเรียนไปแล้วใน Part ก่อนหน้าเรื่อง Issue Tracking) บันทึกไว้ก่อนว่ามีปัญหาอะไร หรือต้องทำอะไร แล้วเมื่อมีคนลงมือแก้ไขจริงผ่าน Pull Request ก็ควรจะ **เชื่อมโยง PR นั้นกับ Issue ต้นทาง** เพื่อ:

1. ให้ทุกคนเห็นว่า Issue นี้กำลังถูกแก้ไขอยู่ (ไม่ต้องมาถามซ้ำว่า "มีใครทำเรื่องนี้อยู่หรือยัง")
2. **ปิด Issue โดยอัตโนมัติทันทีที่ PR ถูก merge** โดยไม่ต้องมานั่งปิดเองด้วยมือ
3. สร้างความสามารถในการสืบย้อน (traceability) — ในอนาคตถ้าอยากรู้ว่า "บั๊กนี้ถูกแก้ด้วยโค้ดไหน" สามารถกดจาก Issue ไปดู PR ที่แก้ไขได้ทันที และในทางกลับกันก็เช่นกัน

### Closing Keywords คืออะไร

GitHub รองรับชุดคำสั่งพิเศษที่เรียกว่า **Closing Keywords** ซึ่งถ้าใส่ไว้ใน **description ของ Pull Request** (หรือแม้แต่ในข้อความ commit) ตามด้วยหมายเลข Issue จะทำให้เกิดการเชื่อมโยงและปิด Issue อัตโนมัติทันทีที่ PR ถูก merge เข้า **default branch** ของ repository (ปกติคือ `main`)

รายการ closing keyword ที่ GitHub รองรับทั้งหมด (ใช้คำไหนก็ได้ ผลลัพธ์เหมือนกัน):

```
close
closes
closed
fix
fixes
fixed
resolve
resolves
resolved
```

### รูปแบบการเขียนที่ถูกต้อง

```
<keyword> #<หมายเลข issue>
```

ตัวอย่างที่ใช้ได้จริง:

```markdown
Closes #12
Fixes #45
Resolves #7
```

หรือถ้ามีหลาย Issue ที่ PR นี้แก้พร้อมกัน สามารถเขียนแยกบรรทัดได้:

```markdown
Fixes #12
Fixes #13
Closes #20
```

### ตัวอย่างการใช้งานจริงใน PR description

```markdown
## สรุป

เพิ่มการตรวจสอบความถูกต้องของอีเมลก่อนบันทึกฟอร์มสมัครสมาชิก

## รายละเอียด

- เพิ่ม regex validation สำหรับ field email
- แสดงข้อความ error ที่ชัดเจนขึ้นเมื่อกรอกอีเมลผิดรูปแบบ

Fixes #58
```

เมื่อ PR นี้ถูก merge เข้า `main` สำเร็จ **Issue #58 จะถูกปิดโดยอัตโนมัติทันที** โดยไม่ต้องมีใครไปกดปิดเองด้วยมือเลย และในหน้า Issue #58 นั้น จะปรากฏข้อความอัตโนมัติในไทม์ไลน์ว่า:

```
[ชื่อผู้ merge] closed this in #<เลข PR>
```

พร้อมลิงก์เชื่อมกลับไปยัง PR ที่แก้ไขให้ทันที

### ข้อควรระวังสำคัญเกี่ยวกับ Closing Keywords

1. **ต้อง merge เข้า default branch เท่านั้นถึงจะปิด Issue อัตโนมัติ** — ถ้า base ของ PR เป็น branch อื่นที่ไม่ใช่ default branch (เช่น merge เข้า branch พัฒนาชั่วคราว) Issue จะ **ไม่ถูกปิดอัตโนมัติ** แม้จะใส่ closing keyword ไว้ก็ตาม
2. **การ Close PR โดยไม่ merge จะไม่ปิด Issue** — closing keyword จะทำงานก็ต่อเมื่อ PR ถูก **merge สำเร็จ** เท่านั้น ถ้าคุณ Close PR ทิ้งแบบใน Step 208 Issue ที่อ้างถึงจะยังคงเปิดอยู่ตามเดิม
3. **ต้องใช้เครื่องหมาย `#` นำหน้าหมายเลข** เสมอ ถ้าพิมพ์แค่ตัวเลขเปล่า ๆ โดยไม่มี `#` ระบบจะไม่รู้จักว่าเป็นการอ้างอิง Issue
4. **ระวังการอ้างอิง Issue ข้าม repository** — ถ้าต้องการอ้างอิง Issue ที่อยู่คนละ repo ต้องเขียนแบบเต็ม เช่น `Fixes owner/other-repo#12` แทนที่จะเขียนแค่ `#12` เฉย ๆ (ซึ่งจะหมายถึง Issue ใน repo เดียวกันกับ PR โดยอัตโนมัติ)
5. **การอ้างอิงแบบไม่มี closing keyword** — ถ้าคุณแค่พิมพ์ `#12` เฉย ๆ โดยไม่มีคำว่า Fixes/Closes นำหน้า มันจะแค่ **สร้างลิงก์เชื่อมโยง (mention)** ให้เห็นความสัมพันธ์กัน แต่จะ **ไม่ปิด Issue อัตโนมัติ** เมื่อ merge — เหมาะกับกรณีที่ PR นี้ "เกี่ยวข้อง" กับ Issue นั้นแต่ยังไม่ได้แก้ปัญหาให้ครบสมบูรณ์

### จุดที่ GitHub แสดงความเชื่อมโยงให้เห็นแบบเรียลไทม์

แม้ก่อนที่ PR จะถูก merge เสียด้วยซ้ำ ทันทีที่คุณพิมพ์ closing keyword ถูกต้องในกล่อง description แล้วกด Create/Update PR ที่ฝั่งขวามือของหน้า PR (sidebar) จะปรากฏส่วนที่เขียนว่า:

```
Development
   Successfully merging this pull request may close issue #58.
```

พร้อมลิงก์ไปยัง Issue นั้นให้กดดูได้ทันที เป็นการยืนยันล่วงหน้าว่าระบบรับรู้การเชื่อมโยงนี้ถูกต้องแล้วก่อนที่จะกด merge จริง

### สรุป Step นี้

Closing keywords คือฟีเจอร์เล็ก ๆ ที่ทรงพลังมาก ช่วยลดงานแอดมินที่น่าเบื่อ (การไปปิด Issue เองด้วยมือ) และสร้างความสามารถในการสืบย้อนที่มีค่ามหาศาลในระยะยาวของโปรเจกต์ — **ทีมมืออาชีพเกือบทุกทีมยึดถือเป็นวินัยว่า PR ทุกอันที่แก้ปัญหาจาก Issue ต้องใส่ closing keyword ไว้เสมอ**

## Step 210: แบบฝึกหัด — สร้างและ Merge PR แรกของตัวเองให้สำเร็จครบวงจร

ถึงเวลาลงมือปฏิบัติจริงแบบครบวงจร ตั้งแต่สร้าง branch จนถึง merge และลบ branch ทิ้ง แบบฝึกหัดนี้ควรใช้เวลาประมาณ 20-30 นาที ทำตามทีละขั้นตอนอย่างละเอียด

### เตรียมความพร้อมก่อนเริ่ม

ใช้ repository ที่คุณสร้างและ push ขึ้น GitHub ไว้แล้วในแบบฝึกหัดของ Part ก่อนหน้า (หรือสร้าง repo ทดสอบใหม่ชื่อ `pr-practice` ก็ได้) ให้แน่ใจว่า:

- มี repository บน GitHub ที่คุณเป็นเจ้าของหรือมีสิทธิ์ push
- Clone ไว้ในเครื่องเรียบร้อยแล้ว และตั้งค่า `git config user.name` / `user.email` ไว้ถูกต้อง (ตามที่เรียนใน Part 2)

### ขั้นตอนที่ 1: เปิด Issue ก่อน (เพื่อฝึกเชื่อมโยงกับ PR)

ก่อนเริ่มเขียนโค้ด ให้เปิด Issue ใหม่บน GitHub ก่อน เพื่อเป็นตัวอย่างสำหรับการเชื่อมโยงในภายหลัง:

1. เข้าไปที่แท็บ **Issues** ของ repo
2. กด **New issue**
3. Title: `เพิ่มไฟล์ CONTRIBUTING.md ให้โปรเจกต์`
4. Description: `โปรเจกต์นี้ยังไม่มีไฟล์อธิบายวิธีการมีส่วนร่วม ควรเพิ่มไฟล์ CONTRIBUTING.md`
5. กด **Submit new issue** — จดหมายเลข Issue ไว้ (สมมติว่าได้ `#1`)

### ขั้นตอนที่ 2: สร้าง Branch ใหม่

```bash
git checkout main
git pull origin main
git checkout -b docs/add-contributing-guide
```

### ขั้นตอนที่ 3: สร้างไฟล์และ Commit

สร้างไฟล์ `CONTRIBUTING.md` ที่ root ของโปรเจกต์:

```markdown
# วิธีมีส่วนร่วมกับโปรเจกต์นี้

ขอบคุณที่สนใจร่วมพัฒนาโปรเจกต์นี้! กรุณาทำตามขั้นตอนต่อไปนี้:

1. Fork repository นี้
2. สร้าง branch ใหม่สำหรับงานของคุณ
3. เปิด Pull Request พร้อมอธิบายการเปลี่ยนแปลงให้ชัดเจน
4. รอทีมรีวิวและให้ feedback
```

Commit การเปลี่ยนแปลง:

```bash
git add CONTRIBUTING.md
git commit -m "Add CONTRIBUTING.md guide"
```

### ขั้นตอนที่ 4: Push Branch ขึ้น GitHub

```bash
git push -u origin docs/add-contributing-guide
```

### ขั้นตอนที่ 5: สร้าง Pull Request

1. เข้าเว็บ GitHub กดปุ่ม **"Compare & pull request"** ที่ปรากฏขึ้นมา
2. ตรวจสอบว่า base เป็น `main` และ compare เป็น `docs/add-contributing-guide`
3. Title: `Add CONTRIBUTING.md guide`
4. Description ใส่ตามตัวอย่างนี้:

```markdown
## สรุป

เพิ่มไฟล์ CONTRIBUTING.md เพื่ออธิบายวิธีการมีส่วนร่วมกับโปรเจกต์ให้ผู้สนใจใหม่เข้าใจได้ง่ายขึ้น

## สิ่งที่เปลี่ยนแปลง

- เพิ่มไฟล์ `CONTRIBUTING.md` ที่ root ของโปรเจกต์

## วิธีทดสอบ

เปิดไฟล์ `CONTRIBUTING.md` แล้วอ่านตรวจสอบเนื้อหาว่าถูกต้องและเข้าใจง่าย

Closes #1
```

5. กด **Create pull request**

### ขั้นตอนที่ 6: ตรวจสอบการเชื่อมโยงกับ Issue

ดูที่ sidebar ฝั่งขวาของหน้า PR ควรเห็นข้อความ:

```
Development
   Successfully merging this pull request may close issue #1.
```

ถ้าเห็นข้อความนี้ แปลว่าการเชื่อมโยงด้วย closing keyword ทำงานถูกต้องแล้ว

### ขั้นตอนที่ 7: ตรวจสอบ Diff ในแท็บ Files changed

คลิกแท็บ **Files changed** ตรวจสอบว่าเห็นไฟล์ `CONTRIBUTING.md` ใหม่ พร้อมสัญลักษณ์ `+` สีเขียวทุกบรรทัด (เพราะเป็นไฟล์ใหม่ทั้งหมด) ลองสลับดูทั้งแบบ **Unified** และ **Split** view เพื่อความคุ้นเคย

### ขั้นตอนที่ 8: ฝึกอัปเดต PR (จำลองสถานการณ์ขอแก้ไข)

สมมติว่าคุณ (หรือเพื่อนร่วมทีม) ตรวจดูแล้วอยากเพิ่มหัวข้อ Code of Conduct เข้าไปด้วย กลับไปที่เครื่อง:

```bash
git checkout docs/add-contributing-guide
```

เพิ่มเนื้อหาต่อท้ายไฟล์ `CONTRIBUTING.md`:

```markdown

## จรรยาบรรณ

กรุณาปฏิบัติต่อผู้ร่วมพัฒนาคนอื่นด้วยความสุภาพและให้เกียรติซึ่งกันและกัน
```

```bash
git add CONTRIBUTING.md
git commit -m "Add code of conduct section"
git push
```

กลับไปดูหน้า PR บนเว็บอีกครั้ง — ตรวจสอบว่า:

- แท็บ **Commits** มี 2 commit แล้ว
- แท็บ **Files changed** อัปเดตแสดง diff ล่าสุดที่รวมส่วนที่เพิ่มใหม่ด้วย

### ขั้นตอนที่ 9: Merge Pull Request

1. เลื่อนลงมาด้านล่างของแท็บ Conversation
2. กดลูกศร dropdown ข้างปุ่ม Merge เลือก **"Squash and merge"** (แนะนำสำหรับมือใหม่ตามที่อธิบายใน Step 207)
3. ตรวจสอบ/แก้ไข commit message ที่ระบบเตรียมให้ (ปกติจะรวมหัวข้อ PR)
4. กด **"Confirm squash and merge"**

รอสักครู่ สถานะ PR จะเปลี่ยนเป็น **"Merged"** พร้อมป้ายสีม่วง

### ขั้นตอนที่ 10: ลบ Branch และตรวจสอบว่า Issue ถูกปิดอัตโนมัติ

หลัง merge สำเร็จ GitHub จะแสดงปุ่ม **"Delete branch"** ให้ทันทีในหน้าเดียวกัน — กดปุ่มนี้เพื่อลบ `docs/add-contributing-guide` ออกจาก remote (ไม่จำเป็นต้องเก็บ branch ไว้อีกแล้วเพราะงานเสร็จสมบูรณ์และถูก merge เข้า `main` แล้ว)

จากนั้นเข้าไปที่แท็บ **Issues** ของ repo ตรวจสอบว่า **Issue #1 ถูกปิดโดยอัตโนมัติแล้ว** (แสดงเป็นสีม่วงพร้อมคำว่า "Closed") — นี่คือผลของ closing keyword `Closes #1` ที่เราใส่ไว้ตอนเปิด PR

### ขั้นตอนสุดท้าย: ทำความสะอาดฝั่ง Local

Branch บน remote ถูกลบไปแล้ว แต่ branch บนเครื่อง local ของคุณยังคงอยู่ ให้ลบทิ้งและอัปเดต `main` ให้ตรงกับ remote:

```bash
git checkout main
git pull origin main
git branch -d docs/add-contributing-guide
```

คำสั่ง `git branch -d` (ตัวพิมพ์เล็ก) จะลบ branch ได้ก็ต่อเมื่อมันถูก merge เข้า `main` เรียบร้อยแล้วเท่านั้น (เป็นกลไกป้องกันการลบ branch ที่ยังมีงานค้างอยู่โดยไม่ได้ตั้งใจ ตามที่เคยเรียนไปแล้วใน Part 7) ตรวจสอบด้วย:

```bash
git log --oneline -3
git branch -a
```

ควรเห็นว่า `main` มี commit ใหม่จากการ squash merge อยู่ด้านบนสุด และ `docs/add-contributing-guide` ไม่ปรากฏอยู่ในรายการ branch อีกต่อไปทั้งฝั่ง local และ remote

### เกณฑ์ตรวจสอบว่าทำแบบฝึกหัดสำเร็จ

- [ ] สร้าง Issue ได้สำเร็จ และจดหมายเลขไว้ถูกต้อง
- [ ] สร้าง branch ใหม่แยกจาก `main` ได้สำเร็จ
- [ ] Commit และ push branch ขึ้น GitHub ได้สำเร็จ
- [ ] สร้าง Pull Request พร้อม description ที่มี closing keyword ถูกต้อง
- [ ] เห็นข้อความ "Successfully merging this pull request may close issue #..." ใน sidebar
- [ ] อ่าน diff ในแท็บ Files changed ได้ทั้งแบบ Unified และ Split view
- [ ] Push commit เพิ่มเข้า branch เดิม แล้วเห็น PR อัปเดตอัตโนมัติ
- [ ] Merge PR สำเร็จด้วยวิธี Squash and merge
- [ ] ลบ branch บน remote ผ่านปุ่มบนเว็บสำเร็จ
- [ ] ตรวจสอบพบว่า Issue ถูกปิดอัตโนมัติหลัง merge
- [ ] ลบ branch บน local ด้วย `git branch -d` สำเร็จ และ `main` อัปเดตล่าสุดแล้ว

ถ้าคุณทำครบทุกข้อในเกณฑ์นี้ได้ แปลว่าคุณเข้าใจวงจรชีวิตแบบเต็มรูปแบบของ Pull Request แล้วอย่างแท้จริง — นี่คือทักษะที่คุณจะใช้ **แทบทุกวัน** ตลอดการทำงานสายพัฒนาซอฟต์แวร์

## สรุป Part 21

ใน Part นี้เราได้เรียนรู้ว่า:

1. **Pull Request คือ "คำขอ" ให้เจ้าของ repository พิจารณานำโค้ดจาก branch หนึ่งไปรวมเข้ากับ branch หลัก** พร้อมเปิดโอกาสให้ทีมรีวิวและอภิปรายก่อน merge จริง — เป็นกระบวนการที่ห่อหุ้ม `git merge` ไว้อีกชั้นเพื่อเพิ่มคุณภาพและความโปร่งใส
2. การสร้าง PR แรกมีขั้นตอนชัดเจน: สร้าง branch → commit → push → กด "Compare & pull request" → กรอก title/description → Create pull request
3. **PR description ที่ดี** ควรบอก "ทำไม" ไม่ใช่แค่ "อะไร" พร้อมวิธีทดสอบและภาพหน้าจอ และควรใช้ **PR Template** เพื่อสร้างมาตรฐานให้ทั้งทีม
4. แท็บ **Files changed** แสดง diff ด้วยสัญลักษณ์ `+`/`-` และสามารถสลับดูแบบ **Unified** หรือ **Split view** ได้ตามความถนัด
5. **Draft Pull Request** ใช้เมื่องานยังไม่เสร็จแต่อยากให้ทีมเห็นความคืบหน้าและให้ CI รันทดสอบไปเรื่อย ๆ โดยที่ปุ่ม Merge จะถูก disable ไว้จนกว่าจะกด "Ready for review"
6. **PR ผูกติดกับ branch ไม่ใช่ commit** — push commit ใหม่เข้า branch เดิมจะอัปเดต PR ให้อัตโนมัติเสมอ โดยไม่ต้องสร้าง PR ใหม่
7. GitHub มี 3 วิธี merge: **Merge commit** (เก็บประวัติครบ), **Squash and merge** (รวมเป็น 1 commit สะอาดที่สุด), **Rebase and merge** (ประวัติเป็นเส้นตรง) — จะเจาะลึกเต็มรูปแบบใน Part 37
8. **Close pull request** ใช้เมื่อไม่ต้องการนำโค้ดเข้า branch หลักอีกต่อไป โดยไม่ลบประวัติการสนทนาทิ้ง และสามารถ Reopen กลับมาได้ภายหลัง
9. **Closing keywords** (เช่น `Fixes #12`, `Closes #45`) ในคำอธิบาย PR จะเชื่อมโยงและ **ปิด Issue โดยอัตโนมัติทันทีที่ PR ถูก merge เข้า default branch**
10. แบบฝึกหัดสุดท้ายพาคุณเดินผ่านวงจรชีวิตแบบเต็มรูปแบบของ Pull Request หนึ่งครั้งครบทุกขั้นตอน ตั้งแต่ branch จนถึง merge และลบ branch — ทักษะที่คุณจะใช้เป็นประจำทุกวันในการทำงานจริง

Pull Request คือกลไกที่ทำให้การทำงานร่วมกันบน GitHub เป็นไปได้อย่างมีคุณภาพและปลอดภัย ยิ่งคุณฝึกฝนสร้างและจัดการ PR บ่อยเท่าไหร่ ทักษะนี้จะกลายเป็นความเคยชินที่ทำได้โดยไม่ต้องคิดมากในที่สุด
