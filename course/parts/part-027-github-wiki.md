## Step 261: GitHub Wiki คืออะไร ต่างจาก README/docs โฟลเดอร์อย่างไร

ทุก repository บน GitHub สามารถมี "Wiki" ของตัวเองได้ ซึ่งเป็นพื้นที่เก็บเอกสารที่**แยกต่างหากจากซอร์สโค้ดหลัก** แต่ยังผูกติดอยู่กับ repository นั้น

### 261.1 GitHub Wiki คืออะไรกันแน่

พูดให้ชัดที่สุด:

> **GitHub Wiki คือ git repository อีกตัวหนึ่งที่ผูกกับ repository หลักของคุณโดยอัตโนมัติ ใช้เก็บหน้าเอกสารที่เขียนด้วย Markdown (หรือรูปแบบอื่นที่ GitHub รองรับ) และแสดงผลผ่าน UI แบบ wiki ที่มี sidebar, การค้นหา และประวัติการแก้ไขในตัว**

ทุก repository ที่เปิดใช้ Wiki จะมี URL รูปแบบนี้เสมอ:

```
https://github.com/<owner>/<repo>/wiki
```

และเบื้องหลังมันคือ git repository อีกตัวที่อยู่ที่:

```
https://github.com/<owner>/<repo>.wiki.git
```

นั่นหมายความว่า Wiki **ไม่ได้เป็นแค่หน้าเว็บธรรมดา** แต่เป็น git repo เต็มรูปแบบ มีการ commit, มีประวัติ, มีการ diff ระหว่างเวอร์ชันได้เหมือน repo ปกติทุกประการ (เราจะพูดถึงเรื่องนี้ละเอียดใน Step 264)

### 261.2 ทำไมต้องมี Wiki ทั้งที่มี README อยู่แล้ว

ผู้เรียนใหม่มักสงสัยว่า "ในเมื่อมี README.md อยู่แล้ว ทำไมต้องมี Wiki อีก" คำตอบคือ **README กับ Wiki ถูกออกแบบมาเพื่อวัตถุประสงค์ที่ต่างกันโดยสิ้นเชิง**

| คุณสมบัติ | README.md | GitHub Wiki |
|---|---|---|
| ตำแหน่งไฟล์ | อยู่ใน repo หลัก root ของโปรเจกต์ | อยู่ใน repo แยก (`.wiki.git`) |
| จุดประสงค์ | หน้าแรกที่คนเห็นทันทีเมื่อเข้า repo — สรุปสั้น ๆ ว่าโปรเจกต์คืออะไร | เอกสารเชิงลึก แยกเป็นหลายหัวข้อ หลายหน้า |
| จำนวนหน้า | ปกติมีไฟล์เดียว (บางทีมีหลายไฟล์ในโฟลเดอร์ `docs/`) | ออกแบบมาให้มีได้หลายสิบ-หลายร้อยหน้า พร้อม sidebar นำทาง |
| การรวมกับ Pull Request | เปลี่ยนแปลงต้องผ่าน PR เหมือนโค้ด (ถ้าทีมบังคับ) | แก้ไขได้ทันทีผ่านเว็บ ไม่ต้องผ่าน PR (ค่า default) |
| ความเหมาะสม | ข้อมูลที่ต้อง "โชว์หน้าแรก" เช่น badge, วิธีติดตั้งสั้น ๆ, license | คู่มือผู้ใช้แบบละเอียด, สถาปัตยกรรมระบบ, FAQ, runbook |
| การค้นหา | ค้นหาผ่าน GitHub code search ทั่วไป | มีระบบค้นหาภายใน Wiki โดยเฉพาะ |

### 261.3 ต่างจากโฟลเดอร์ `docs/` อย่างไร

หลายโปรเจกต์เลือกเก็บเอกสารไว้ในโฟลเดอร์ `docs/` ภายใน repo หลักแทนที่จะใช้ Wiki ความต่างหลักคือ:

1. **Version control ร่วมกับโค้ดหรือไม่** — `docs/` อยู่ใน repo เดียวกับโค้ด ดังนั้นเอกสารกับโค้ดจะถูก commit ไปด้วยกันเสมอ (ตรงกันเป๊ะทุก branch/tag) ในขณะที่ Wiki เป็น repo แยก จึงไม่ได้ผูกกับ branch หรือ release ใด ๆ ของโค้ดโดยอัตโนมัติ
2. **การรีวิว** — การแก้ไขใน `docs/` สามารถบังคับให้ผ่าน Pull Request และ Code Review ได้เหมือนโค้ดทั่วไป แต่ Wiki โดย default แก้ไขได้ทันทีโดยไม่ต้องรีวิว (แม้จะปรับสิทธิ์ได้ตาม Step 267)
3. **การ deploy เป็นเว็บไซต์** — `docs/` มักถูกนำไปสร้างเป็นเว็บไซต์เอกสารสวยงามผ่าน GitHub Pages หรือเครื่องมืออย่าง MkDocs/Docusaurus ในขณะที่ Wiki มี UI ของตัวเองอยู่แล้วบน GitHub โดยไม่ต้อง build อะไรเพิ่ม

เราจะเปรียบเทียบทั้งสามตัวเลือกอย่างละเอียดพร้อมตารางตัดสินใจใน **Step 266**

### 261.4 ข้อจำกัดสำคัญของ Wiki ที่ต้องรู้ไว้ก่อน

- Wiki เปิดใช้งานได้เฉพาะกับ repository ที่ตั้งค่าอนุญาตไว้ (เจ้าของ/ผู้ดูแลเปิดสวิตช์ Feature)
- Wiki ของ **private repository** จะมองเห็นได้เฉพาะคนที่มีสิทธิ์เข้าถึง repo นั้นเท่านั้น
- Wiki **ไม่รองรับ GitHub Actions, Issues, หรือ Pull Request ในตัวมันเอง** — มันเป็นแค่พื้นที่เก็บเอกสาร ไม่ใช่ระบบ CI/CD
- Wiki ของ repository ที่เป็น **fork** จะไม่ถูก fork ตามไปด้วย ต้องสร้าง Wiki ใหม่เองใน fork นั้น

เข้าใจภาพรวมแล้ว มาลงมือเปิดใช้งานจริงกันใน Step ถัดไป

## Step 262: เปิดใช้งานและสร้างหน้า Wiki แรก (Home page)

### 262.1 ตรวจสอบว่า Wiki ถูกเปิดใช้งานหรือยัง

ไปที่หน้า repository ของคุณบน GitHub แล้วมองหาแท็บ **Wiki** บนแถบเมนูด้านบน (อยู่แถวเดียวกับ Code, Issues, Pull requests, Actions)

ถ้าไม่เห็นแท็บ Wiki แสดงว่า feature นี้ถูกปิดอยู่ ให้ทำตามนี้ (ต้องมีสิทธิ์ระดับ **Admin** ของ repo):

1. ไปที่ **Settings** ของ repository
2. เลื่อนลงมาที่หัวข้อ **Features**
3. ติ๊กเลือกช่อง **Wikis** ให้เป็นสถานะเปิดใช้งาน

หลังจากเปิดแล้ว แท็บ Wiki จะปรากฏขึ้นทันที

### 262.2 สร้างหน้า Home page แรก

เมื่อเข้าไปที่แท็บ Wiki ครั้งแรกของ repository ที่ยังไม่มีหน้าใด ๆ เลย GitHub จะแสดงปุ่มให้กด **"Create the first page"**

ขั้นตอนการสร้างมีดังนี้:

1. คลิก **Create the first page**
2. ในช่อง **Title** ให้ใส่ชื่อ `Home` — นี่เป็นชื่อพิเศษที่ GitHub ใช้เป็น**หน้าแรก**ของ Wiki เสมอ (เทียบเท่ากับ `index.html` ของเว็บไซต์ทั่วไป)
3. ในช่อง **Edit** พิมพ์เนื้อหาด้วยภาษา Markdown เช่น:

```markdown
# ยินดีต้อนรับสู่ Wiki ของโปรเจกต์ MyAwesomeApp

MyAwesomeApp คือเครื่องมือสำหรับ... (คำอธิบายสั้น ๆ ว่าโปรเจกต์นี้คืออะไร)

## เริ่มต้นใช้งาน

- [ติดตั้งโปรแกรม](./Installation)
- [วิธีใช้งานเบื้องต้น](./Usage)
- [คำถามที่พบบ่อย](./FAQ)

## สำหรับนักพัฒนา

- [สถาปัตยกรรมระบบ](./Architecture)
- [API Reference](./API-Reference)
- [แนวทางการ Contribute](./Contributing)
```

4. เลื่อนลงมาด้านล่างและใส่ **Commit message** อธิบายว่าคุณสร้าง/แก้ไขอะไร เช่น `เพิ่มหน้า Home เริ่มต้นของ Wiki`
5. กดปุ่ม **Save Page**

เพียงเท่านี้หน้า Home page แรกของ Wiki ก็ถูกสร้างขึ้นแล้ว และจะกลายเป็นหน้าที่ผู้ใช้เห็นทันทีเมื่อเข้ามาที่ `https://github.com/<owner>/<repo>/wiki`

### 262.3 สร้างหน้าถัดไป

การสร้างหน้าใหม่ทำได้สองวิธี:

**วิธีที่ 1 — ใช้ลิงก์ที่ยังไม่มีอยู่จริง**

ถ้าในเนื้อหา Markdown ของหน้าใดหน้าหนึ่งมีลิงก์ไปยังหน้าที่ยังไม่ถูกสร้าง เช่น `[ติดตั้งโปรแกรม](./Installation)` เมื่อมีคนคลิกลิงก์นั้น GitHub จะพาไปที่หน้าสร้างหน้าใหม่ชื่อ `Installation` ให้ทันที

**วิธีที่ 2 — กดปุ่ม "New Page" โดยตรง**

ที่หน้า Wiki หลัก จะมีปุ่ม **New Page** อยู่มุมขวาบนเสมอ กดปุ่มนี้แล้วตั้งชื่อหน้าใหม่ พิมพ์เนื้อหา แล้ว Save ได้ทันที

### 262.4 กฎการตั้งชื่อหน้า

เมื่อคุณตั้งชื่อหน้าว่า `Getting Started` GitHub จะแปลงชื่อนี้เป็น URL โดยอัตโนมัติดังนี้:

```
Title: Getting Started
URL:   https://github.com/<owner>/<repo>/wiki/Getting-Started
```

สังเกตว่า **ช่องว่างจะถูกแทนที่ด้วยเครื่องหมายขีดกลาง (-)** โดยอัตโนมัติ ดังนั้นถ้าคุณจะอ้างอิงหน้าจากหน้าอื่นด้วยลิงก์ Markdown ควรใช้ชื่อไฟล์ที่มีขีดกลางแทนช่องว่างเพื่อความชัดเจน เช่น `[API Reference](./API-Reference)`

## Step 263: Wiki ใช้ Markdown ได้เต็มรูปแบบ และมี sidebar/footer กำหนดเองได้

### 263.1 Markdown เต็มรูปแบบเหมือนที่อื่นบน GitHub

Wiki รองรับ **GitHub Flavored Markdown (GFM)** เต็มรูปแบบเหมือนกับที่ใช้เขียน README, Issue หรือ Pull Request comment ทุกประการ นั่นหมายความว่าคุณสามารถใช้ได้ทั้งหมดนี้ในหน้า Wiki:

- หัวข้อ (`#`, `##`, `###`)
- รายการ (bullet list, numbered list, task list `- [ ]`)
- ตาราง (`| col1 | col2 |`)
- Code block พร้อม syntax highlighting (` ```python `, ` ```bash ` เป็นต้น)
- รูปภาพ (`![alt](url)`) — สามารถลากไฟล์รูปวางลงในกล่องแก้ไขได้โดยตรง (แนบไฟล์อัตโนมัติ)
- Blockquote (`>`)
- ลิงก์ทั้งภายในและภายนอก
- Emoji shortcode (`:tada:`, `:warning:`)
- Mermaid diagram (ในบาง context ของ GitHub รองรับการ render แผนภาพจาก syntax ของ Mermaid ภายใน code block ` ```mermaid `)

ตัวอย่างการเขียนตารางเปรียบเทียบใน Wiki:

```markdown
| เวอร์ชัน | รองรับถึงเมื่อไหร่ | หมายเหตุ |
|---|---|---|
| v1.x | สิ้นสุดการซัพพอร์ตแล้ว | อัปเกรดเป็น v2 ทันที |
| v2.x | ปัจจุบัน (LTS) | แนะนำสำหรับ production |
| v3.x | Beta | ใช้ทดสอบเท่านั้น |
```

### 263.2 Sidebar แบบกำหนดเอง

โดย default แล้ว GitHub Wiki จะสร้าง sidebar อัตโนมัติให้ โดยแสดงรายชื่อหน้าทั้งหมดเรียงตามลำดับที่สร้าง แต่คุณสามารถ**ควบคุม sidebar เองได้อย่างสมบูรณ์** โดยการสร้างหน้าพิเศษที่ชื่อ:

```
_Sidebar
```

(สังเกตว่ามีขีดล่าง `_` นำหน้า)

เมื่อสร้างหน้าชื่อ `_Sidebar` แล้วใส่เนื้อหา Markdown แบบ list ธรรมดา เช่น:

```markdown
### เมนูหลัก

- [หน้าแรก](./Home)
- [ติดตั้ง](./Installation)
- [วิธีใช้งาน](./Usage)

### สำหรับนักพัฒนา

- [สถาปัตยกรรม](./Architecture)
- [API Reference](./API-Reference)
- [Contributing Guide](./Contributing)

### อื่น ๆ

- [FAQ](./FAQ)
- [Troubleshooting](./Troubleshooting)
- [Changelog](./Changelog)
```

sidebar ที่กำหนดเองนี้จะปรากฏแทนที่ sidebar อัตโนมัติทันที และจะแสดงผลเหมือนกันทุกหน้าของ Wiki — ทำให้ผู้อ่านนำทางไปยังหมวดหมู่ต่าง ๆ ได้ง่ายขึ้นมาก โดยเฉพาะเมื่อ Wiki มีหน้าจำนวนมาก

### 263.3 Footer แบบกำหนดเอง

ในทำนองเดียวกัน คุณสามารถสร้างหน้าพิเศษชื่อ:

```
_Footer
```

เนื้อหาของหน้านี้จะถูกแสดงที่**ท้ายของทุกหน้า Wiki** เหมาะสำหรับใส่ข้อมูลที่อยากให้ปรากฏซ้ำทุกหน้า เช่น:

```markdown
---
📖 เอกสารนี้ดูแลโดยทีม Core Maintainers | พบปัญหาแจ้งได้ที่ [Issues](https://github.com/<owner>/<repo>/issues) | อัปเดตล่าสุด: ดูที่ประวัติของแต่ละหน้า
```

### 263.4 หน้าพิเศษอื่น ๆ ที่ควรรู้

| ชื่อหน้าพิเศษ | หน้าที่ |
|---|---|
| `Home` | หน้าแรกที่แสดงเมื่อเข้า Wiki |
| `_Sidebar` | กำหนด sidebar เองแทนที่ระบบอัตโนมัติ |
| `_Footer` | ข้อความที่แสดงท้ายทุกหน้า |

หน้าที่ขึ้นต้นด้วยขีดล่าง (`_`) จะไม่ถูกนับเป็น "หน้าเนื้อหา" ทั่วไป และจะไม่ปรากฏในรายการหน้าปกติ แต่จะทำหน้าที่พิเศษตามชื่อของมันเสมอ

## Step 264: การ clone wiki เป็น git repo แยกต่างหาก (`repo.wiki.git`) แก้ไขแบบ local ได้

### 264.1 Wiki คือ git repository จริง ๆ

อย่างที่กล่าวไว้ใน Step 261 GitHub Wiki แต่ละอันที่ถูกสร้างขึ้น (คือมีอย่างน้อย 1 หน้าแล้ว) จะมี git repository ของตัวเองซ่อนอยู่เบื้องหลัง สามารถ clone มาแก้ไขในเครื่องได้เหมือน repo ทั่วไปทุกประการ

URL สำหรับ clone มีรูปแบบดังนี้:

```bash
# แบบ HTTPS
git clone https://github.com/<owner>/<repo>.wiki.git

# แบบ SSH
git clone git@github.com:<owner>/<repo>.wiki.git
```

ตัวอย่างเช่น ถ้า repository หลักของคุณคือ `https://github.com/somchai/myawesomeapp` คำสั่ง clone Wiki จะเป็น:

```bash
git clone git@github.com:somchai/myawesomeapp.wiki.git
```

หลัง clone เสร็จ คุณจะเห็นไฟล์ `.md` แต่ละไฟล์แทนแต่ละหน้าของ Wiki เช่น:

```
myawesomeapp.wiki/
├── Home.md
├── Installation.md
├── Usage.md
├── FAQ.md
├── _Sidebar.md
└── _Footer.md
```

สังเกตว่าชื่อไฟล์ตรงกับชื่อหน้าเป๊ะ ๆ (แทนที่ช่องว่างด้วยขีดกลางเหมือนที่อธิบายใน Step 262.4) และมีนามสกุล `.md` ต่อท้ายเสมอ

### 264.2 แก้ไข Wiki แบบ local แล้ว push กลับ

เมื่อ clone มาแล้ว การแก้ไขก็ทำเหมือน git workflow ปกติทุกอย่าง:

```bash
cd myawesomeapp.wiki

# แก้ไขไฟล์ด้วย editor ที่ถนัด
code Installation.md

# ตรวจสอบสถานะ
git status

# stage และ commit
git add Installation.md
git commit -m "เพิ่มขั้นตอนติดตั้งบน Windows ที่ขาดหายไป"

# push กลับขึ้น GitHub
git push origin master
```

> **หมายเหตุสำคัญ:** default branch ของ Wiki repository ส่วนใหญ่คือ `master` (ไม่ใช่ `main`) แม้ว่า repository หลักของโปรเจกต์คุณจะใช้ `main` เป็น default branch ก็ตาม เพราะ Wiki repo ถูกสร้างแยกต่างหากตามค่ามาตรฐานเดิมของ Git

เมื่อ push สำเร็จ การเปลี่ยนแปลงจะไปปรากฏบนหน้าเว็บ Wiki ทันที เหมือนกับตอนที่มีคนแก้ผ่านหน้าเว็บโดยตรง

### 264.3 สร้างหน้าใหม่ผ่าน local

การสร้างหน้าใหม่ผ่านทาง local ก็ทำได้ง่าย ๆ เพียงสร้างไฟล์ `.md` ใหม่ที่มีชื่อตรงกับชื่อหน้าที่ต้องการ (แทนที่ช่องว่างด้วยขีดกลาง) แล้ว commit + push:

```bash
touch Troubleshooting.md
echo "# แก้ปัญหาที่พบบ่อย" > Troubleshooting.md
git add Troubleshooting.md
git commit -m "เพิ่มหน้า Troubleshooting"
git push origin master
```

### 264.4 ทำไมการแก้ไขแบบ local ถึงมีประโยชน์

1. **แก้ไขหลายไฟล์พร้อมกันได้สะดวก** — ใช้ editor ที่ถนัด เช่น VS Code ที่มี find & replace ข้ามหลายไฟล์
2. **เขียน script อัตโนมัติจัดการเอกสารได้** — เช่น script generate หน้า API Reference จาก docstring ในโค้ดอัตโนมัติ แล้ว push เข้า Wiki
3. **backup ประวัติ Wiki ไว้ในเครื่องได้** — เผื่อกรณีต้องการเก็บสำเนาแยกจาก GitHub
4. **ทำงานแบบ offline ได้** — เขียนเอกสารตอนไม่มีเน็ต แล้วค่อย push ทีเดียวตอนมีเน็ต
5. **ใช้ git diff / git log ตรวจสอบประวัติการแก้ไขได้ละเอียดกว่า UI บนเว็บ**

### 264.5 ข้อควรระวัง

- Wiki repo **ไม่รองรับ Pull Request** ในตัวมันเอง (ไม่มีแท็บ PR สำหรับ `.wiki.git`) ดังนั้นแม้จะ push ตรงไปที่ `master` ได้เลย แต่ก็หมายความว่า**ไม่มีการรีวิวก่อน merge โดยธรรมชาติ** หากต้องการรีวิวก่อนแก้ไขจริง ควรตกลงกันในทีมว่าจะสร้าง branch อื่นไว้ตรวจสอบก่อนแล้วค่อย merge เข้า `master` เอง หรือใช้ mechanism ภายนอกช่วย
- ถ้า Wiki ยังไม่เคยถูกสร้างหน้าใด ๆ เลย (ยังไม่มี commit แรก) คำสั่ง `git clone` จะ error ว่าไม่พบ repository — ต้องสร้างหน้าแรกผ่านหน้าเว็บก่อนอย่างน้อย 1 หน้า (ตาม Step 262) จึงจะ clone ได้

## Step 265: โครงสร้างเอกสารที่ดีสำหรับโปรเจกต์ขนาดกลาง-ใหญ่ (Getting Started, API Reference, FAQ, Troubleshooting)

เมื่อโปรเจกต์เริ่มโตขึ้น การมีแค่หน้า Home เพียงหน้าเดียวไม่เพียงพอ ต้องออกแบบโครงสร้างเอกสารที่ชัดเจน เพื่อให้ทั้งผู้ใช้งานทั่วไปและนักพัฒนาหาข้อมูลที่ต้องการได้เร็วที่สุด

### 265.1 หมวดหมู่หลักที่ควรมี

โครงสร้าง Wiki ที่ดีสำหรับโปรเจกต์ขนาดกลาง-ใหญ่ มักแบ่งเป็น 4 กลุ่มใหญ่ ดังนี้

**กลุ่มที่ 1: สำหรับผู้ใช้ใหม่ (Getting Started)**

- `Home` — ภาพรวมโปรเจกต์ พร้อมลิงก์ไปยังหมวดสำคัญ
- `Installation` — วิธีติดตั้งแยกตามระบบปฏิบัติการ/สภาพแวดล้อม
- `Quick-Start` — ตัวอย่างการใช้งานที่เร็วที่สุด ทำตามได้ใน 5 นาที
- `Configuration` — การตั้งค่าต่าง ๆ ที่ปรับแต่งได้

**กลุ่มที่ 2: คู่มือการใช้งาน (Usage Guides)**

- `Usage` — วิธีใช้งานฟีเจอร์หลักแบบละเอียด
- `Examples` — ตัวอย่างการใช้งานจริงในสถานการณ์ต่าง ๆ
- `Best-Practices` — แนวทางปฏิบัติที่แนะนำ

**กลุ่มที่ 3: สำหรับนักพัฒนา (Developer Docs)**

- `Architecture` — โครงสร้างระบบในภาพรวม อธิบายว่าส่วนต่าง ๆ ทำงานร่วมกันอย่างไร
- `API-Reference` — รายละเอียด API แต่ละ endpoint/ฟังก์ชัน พารามิเตอร์ ค่าที่คืนกลับ
- `Contributing` — วิธี contribute โค้ดเข้าโปรเจกต์ (มักลิงก์ไปยังไฟล์ `CONTRIBUTING.md` ใน repo หลักด้วย)
- `Development-Setup` — วิธีตั้งค่าสภาพแวดล้อมสำหรับพัฒนา (dev environment)

**กลุ่มที่ 4: การช่วยเหลือและอ้างอิง (Support & Reference)**

- `FAQ` — คำถามที่พบบ่อยพร้อมคำตอบ
- `Troubleshooting` — ปัญหาที่พบบ่อยและวิธีแก้
- `Changelog` — ประวัติการเปลี่ยนแปลงของแต่ละเวอร์ชัน
- `Glossary` — อธิบายศัพท์เฉพาะที่ใช้ในโปรเจกต์

### 265.2 ตัวอย่างหน้า API Reference ที่ดี

หน้า API Reference ควรมีโครงสร้างที่สม่ำเสมอทุก endpoint/ฟังก์ชัน เพื่อให้อ่านง่ายและคาดเดารูปแบบได้ ตัวอย่าง:

```markdown
# API Reference

## `POST /api/users`

สร้างผู้ใช้ใหม่ในระบบ

### Request Body

| ฟิลด์ | ชนิดข้อมูล | จำเป็นไหม | คำอธิบาย |
|---|---|---|---|
| `username` | string | ใช่ | ชื่อผู้ใช้ ไม่ซ้ำกัน |
| `email` | string | ใช่ | อีเมลที่ใช้ยืนยันตัวตน |
| `age` | number | ไม่ | อายุผู้ใช้ (ถ้าไม่ระบุจะเป็น null) |

### ตัวอย่าง Request

\`\`\`bash
curl -X POST https://api.example.com/api/users \
  -H "Content-Type: application/json" \
  -d '{"username": "somchai", "email": "somchai@example.com"}'
\`\`\`

### ตัวอย่าง Response (201 Created)

\`\`\`json
{
  "id": 42,
  "username": "somchai",
  "email": "somchai@example.com",
  "createdAt": "2026-09-26T10:00:00Z"
}
\`\`\`

### Error Codes

| Status | ความหมาย |
|---|---|
| `400` | ข้อมูลใน request body ไม่ถูกต้อง |
| `409` | username ซ้ำกับที่มีอยู่แล้ว |

---
```

รูปแบบซ้ำ ๆ แบบนี้ (คำอธิบาย → parameter table → ตัวอย่าง request → ตัวอย่าง response → error codes) ทำให้ผู้อ่านคุ้นเคยและหาข้อมูลได้เร็วขึ้นมากเมื่อมี endpoint จำนวนมาก

### 265.3 ตัวอย่างหน้า FAQ ที่ดี

หน้า FAQ ควรจัดกลุ่มคำถามตามหมวดหมู่ ไม่ใช่เรียงมั่ว ๆ:

```markdown
# คำถามที่พบบ่อย (FAQ)

## เกี่ยวกับการติดตั้ง

**Q: รองรับ Node.js เวอร์ชันไหนบ้าง?**
A: รองรับ Node.js 18 ขึ้นไป แนะนำให้ใช้ LTS เวอร์ชันล่าสุด

**Q: ติดตั้งบน Windows แล้วเจอ error `EACCES` ต้องทำอย่างไร?**
A: ดูวิธีแก้แบบละเอียดที่หน้า [Troubleshooting](./Troubleshooting#eacces-error)

## เกี่ยวกับการใช้งาน

**Q: สามารถใช้กับฐานข้อมูล PostgreSQL ได้ไหม?**
A: ได้ ตั้งแต่เวอร์ชัน 2.0 เป็นต้นไป ดูวิธีตั้งค่าที่หน้า [Configuration](./Configuration#postgresql)

## เกี่ยวกับ License และการนำไปใช้เชิงพาณิชย์

**Q: ใช้ในโปรเจกต์เชิงพาณิชย์ได้ไหม?**
A: ได้ โปรเจกต์นี้ใช้สัญญาอนุญาต MIT License
```

### 265.4 ตัวอย่างหน้า Troubleshooting ที่ดี

หน้า Troubleshooting ที่มีประโยชน์จริงควรมีโครงสร้าง: **อาการ → สาเหตุ → วิธีแก้** เสมอ

```markdown
# Troubleshooting

## ปัญหา: แอปพลิเคชันไม่สามารถเชื่อมต่อฐานข้อมูลได้

**อาการ:** เห็น error `Connection refused` เมื่อรันคำสั่ง `npm start`

**สาเหตุที่เป็นไปได้:**
1. ฐานข้อมูลยังไม่ได้เปิดใช้งาน
2. ตั้งค่า `DATABASE_URL` ผิดในไฟล์ `.env`
3. Firewall บล็อก port ที่ใช้เชื่อมต่อ

**วิธีแก้:**
1. ตรวจสอบว่าฐานข้อมูลทำงานอยู่ด้วยคำสั่ง `docker ps`
2. เปิดไฟล์ `.env` ตรวจสอบค่า `DATABASE_URL` ให้ตรงกับที่ตั้งค่าไว้จริง
3. ทดสอบเชื่อมต่อด้วยคำสั่ง `psql $DATABASE_URL`
```

การจัดโครงสร้างแบบนี้ช่วยให้ผู้ใช้ scan หาหัวข้อที่ตรงกับปัญหาตัวเองได้เร็ว แทนที่จะต้องอ่านทั้งย่อหน้า

## Step 266: เปรียบเทียบ Wiki vs docs/ โฟลเดอร์ vs GitHub Pages เมื่อไหร่ควรใช้อะไร

โปรเจกต์หนึ่ง ๆ อาจเลือกใช้เอกสารได้ 3 รูปแบบหลัก คือ **GitHub Wiki**, **โฟลเดอร์ `docs/` ใน repo หลัก**, หรือ **GitHub Pages** (เว็บไซต์ static ที่ deploy จาก repo) แต่ละแบบเหมาะกับสถานการณ์ต่างกัน

### 266.1 ตารางเปรียบเทียบโดยละเอียด

| คุณสมบัติ | GitHub Wiki | โฟลเดอร์ `docs/` | GitHub Pages |
|---|---|---|---|
| อยู่ใน repo เดียวกับโค้ดไหม | ไม่ (repo แยก `.wiki.git`) | ใช่ | ใช่ (build มาจาก repo) หรือ repo แยกก็ได้ |
| ต้องผ่าน Pull Request เพื่อแก้ไขไหม | ไม่จำเป็น (default) | บังคับได้ผ่าน branch protection | บังคับได้ผ่าน branch protection |
| แก้ไขผ่านเว็บได้ทันทีไหม | ได้ (มี editor ในตัว) | ได้ (GitHub UI แก้ไฟล์ตรง ๆ ได้) แต่ไม่มี live preview เท่า Wiki | ไม่ได้โดยตรง ต้อง build ใหม่ |
| รูปแบบหน้าตา | Template สำเร็จรูปของ GitHub | ขึ้นกับว่า render ยังไง (ปกติดูเป็น markdown ธรรมดา) | ปรับแต่งได้อิสระเต็มที่ (custom theme/CSS) |
| ต้องมีการ Build/Deploy ไหม | ไม่ต้อง | ไม่ต้อง (ถ้าแค่ดูใน GitHub) | ต้อง (ผ่าน GitHub Actions หรือ Pages build) |
| เหมาะกับเอกสารประเภทไหน | คู่มือทั่วไป, FAQ, บันทึกการประชุม, เอกสารที่แก้บ่อยแบบไม่เป็นทางการ | เอกสารที่ต้อง sync กับโค้ดเป๊ะ ๆ ทุก branch/tag | เอกสารที่ต้องการรูปลักษณ์สวยงามระดับมืออาชีพ เช่น landing page, documentation site เต็มรูปแบบ |
| การค้นหา | มี built-in search ของ Wiki | ใช้ GitHub code search | ขึ้นกับเครื่องมือที่ใช้ build (เช่น Algolia search ใน Docusaurus) |
| Custom domain | ไม่รองรับ | ไม่เกี่ยวข้อง | รองรับ (ตั้งค่า custom domain ได้) |
| History/versioning ตรงกับ release ไหม | ไม่ตรง (Wiki เป็น timeline ของตัวเอง) | ตรงเป๊ะ (อยู่ commit เดียวกับโค้ด) | ขึ้นกับ workflow การ deploy ที่ตั้งไว้ |

### 266.2 แนวทางการตัดสินใจ (Decision Guide)

**ใช้ GitHub Wiki เมื่อ:**
- ต้องการพื้นที่เขียนเอกสารที่แก้ไขง่าย รวดเร็ว ไม่ต้องผ่านกระบวนการ PR ทุกครั้ง
- เอกสารเปลี่ยนแปลงบ่อยและไม่จำเป็นต้อง sync กับ version ของโค้ดแบบเป๊ะ ๆ
- ต้องการให้ non-technical team member (เช่น PM, QA) เข้ามาแก้ไขเอกสารได้ง่ายโดยไม่ต้องรู้จัก git workflow ผ่าน PR
- โปรเจกต์เป็น internal tool หรือทีมขนาดเล็ก-กลางที่ไม่ต้องการความสวยงามระดับ marketing site

**ใช้โฟลเดอร์ `docs/` เมื่อ:**
- ต้องการให้เอกสาร**ตรงกับเวอร์ชันโค้ดเป๊ะ ๆ** เช่น เอกสาร API ต้อง match กับ branch/tag นั้น ๆ เสมอ
- ต้องการบังคับให้การแก้ไขเอกสารผ่าน Code Review เหมือนโค้ด (ผ่าน Pull Request)
- ต้องการนำเอกสารไป build เป็นเว็บไซต์ต่อด้วยเครื่องมืออย่าง MkDocs, Docusaurus, Sphinx
- ต้องการให้เอกสารถูก track อยู่ใน git log เดียวกับ commit ของโค้ดฟีเจอร์นั้น ๆ

**ใช้ GitHub Pages เมื่อ:**
- ต้องการเว็บไซต์เอกสารที่มีหน้าตาสวยงาม เป็นมืออาชีพ มี branding ของตัวเอง
- ต้องการ custom domain (เช่น `docs.myproject.com`)
- โปรเจกต์เป็น Open Source ขนาดใหญ่ที่มีผู้ใช้จำนวนมาก ต้องการ documentation site แบบมี navigation, search ที่ทรงพลัง (เช่น Algolia DocSearch)
- ต้องการทำ landing page หรือ marketing site ควบคู่กับเอกสาร

### 266.3 ใช้ร่วมกันได้ ไม่จำเป็นต้องเลือกอย่างใดอย่างหนึ่ง

ในทางปฏิบัติ หลายโปรเจกต์ขนาดใหญ่**ใช้ทั้งสามอย่างพร้อมกัน** โดยแบ่งบทบาทชัดเจน เช่น:

- **README.md** — ภาพรวมสั้น ๆ พร้อม badge และลิงก์ไปยังเอกสารเต็ม
- **`docs/` + GitHub Pages** — documentation site หลักที่เป็นทางการ sync กับทุก release
- **GitHub Wiki** — พื้นที่สำหรับบันทึกที่ไม่เป็นทางการ เช่น meeting notes, RFC draft, internal runbook สำหรับทีม, คำถามจากผู้ใช้ที่ maintainer ตอบไว้แล้วเก็บเป็นความรู้

ไม่มีคำตอบที่ถูกต้องเพียงหนึ่งเดียว — เลือกตามความเหมาะสมของทีมและลักษณะเนื้อหา

## Step 267: การจำกัดสิทธิ์แก้ไข Wiki (เฉพาะ collaborator หรือเปิดให้ทุกคนแก้ได้)

### 267.1 ค่าเริ่มต้นของสิทธิ์แก้ไข Wiki

พฤติกรรม default ของ GitHub Wiki แตกต่างกันตามประเภทของ repository:

- **Public repository:** โดย default แล้ว **ใครก็ได้ที่มีบัญชี GitHub สามารถแก้ไข Wiki ได้ทันที** โดยไม่ต้องเป็น collaborator ของ repo นั้นเลย (คล้ายกับ Wikipedia ที่ใครก็แก้ได้)
- **Private repository:** เฉพาะผู้ที่มีสิทธิ์เข้าถึง repository (collaborator หรือสมาชิกในองค์กรที่มีสิทธิ์) เท่านั้นที่แก้ไขได้

### 267.2 การเปลี่ยนสิทธิ์ให้เฉพาะ Collaborator เท่านั้นที่แก้ได้

สำหรับ public repository หากไม่ต้องการให้บุคคลภายนอกแก้ไข Wiki ได้อย่างอิสระ (ป้องกัน spam หรือการแก้ไขที่ไม่เหมาะสม) สามารถจำกัดสิทธิ์ได้ดังนี้:

1. ไปที่ **Settings** ของ repository
2. เลื่อนไปที่ส่วน **Features**
3. มองหาช่องกาเครื่องหมายที่ระบุประมาณว่า **"Restrict editing to collaborators only"** (ข้อความอาจต่างกันเล็กน้อยตามเวอร์ชัน UI ของ GitHub)
4. ติ๊กเลือกเพื่อจำกัดให้เฉพาะผู้ที่มีสิทธิ์ **Write** ขึ้นไปในโปรเจกต์เท่านั้นที่แก้ไข Wiki ได้

เมื่อเปิดใช้งานตัวเลือกนี้แล้ว บุคคลทั่วไปยังคง**อ่าน**เนื้อหา Wiki ได้ตามปกติ (ถ้า repo เป็น public) แต่จะไม่มีสิทธิ์กดปุ่ม Edit หรือ New Page อีกต่อไป

### 267.3 ระดับสิทธิ์ (Permission Levels) ที่เกี่ยวข้องกับ Wiki

สิทธิ์ในการแก้ไข Wiki ผูกกับระดับสิทธิ์ของผู้ใช้ใน repository โดยตรง ดังนี้:

| ระดับสิทธิ์ใน Repository | แก้ไข Wiki ได้ไหม (เมื่อจำกัดเฉพาะ collaborator) |
|---|---|
| **Read** | อ่านได้อย่างเดียว แก้ไขไม่ได้ |
| **Triage** | อ่านได้อย่างเดียว แก้ไขไม่ได้ |
| **Write** | แก้ไขได้เต็มที่ |
| **Maintain** | แก้ไขได้เต็มที่ |
| **Admin** | แก้ไขได้เต็มที่ และปรับ Settings ของ Wiki ได้ |

### 267.4 เหตุผลที่ควรพิจารณาก่อนตัดสินใจเปิด/ปิด

**ข้อดีของการเปิดให้ทุกคนแก้ไขได้ (public editing):**
- ชุมชนช่วยกันปรับปรุงเอกสารได้เร็ว โดยเฉพาะการแก้ typo หรือเพิ่มตัวอย่างที่เป็นประโยชน์
- ลดภาระของ maintainer ในการดูแลเอกสารคนเดียว
- เหมาะกับโปรเจกต์ Open Source ขนาดใหญ่ที่มีชุมชนเข้มแข็งและช่วยกันดูแล (self-moderating)

**ข้อเสียที่ต้องระวัง:**
- อาจถูก spam หรือแก้ไขเนื้อหาที่ไม่เหมาะสม/ผิดพลาดโดยเจตนา (vandalism)
- ไม่มีกระบวนการรีวิวก่อน publish เหมือน Pull Request ทำให้ข้อมูลผิดอาจปรากฏบนหน้าเว็บทันทีโดยไม่มีใครตรวจสอบก่อน

**คำแนะนำในทางปฏิบัติ:** สำหรับโปรเจกต์ Open Source ที่มีชุมชนขนาดใหญ่และมี maintainer คอยติดตามอยู่เสมอ การเปิดให้ทุกคนแก้ไขได้อาจเป็นประโยชน์ แต่สำหรับโปรเจกต์ภายในองค์กรหรือโปรเจกต์ที่เอกสารมีความสำคัญสูง (เช่น คู่มือความปลอดภัย, runbook สำหรับ production) ควรจำกัดให้เฉพาะ collaborator แก้ไขได้เท่านั้น

### 267.5 การติดตามการเปลี่ยนแปลง (Monitoring)

ไม่ว่าจะเปิดหรือปิดสิทธิ์แบบไหน ทุกหน้าของ Wiki มีปุ่ม **"View history"** ที่แสดงประวัติการแก้ไขทั้งหมด พร้อมชื่อผู้แก้ไขและ diff ของแต่ละครั้ง หากพบการแก้ไขที่ไม่เหมาะสม ผู้ที่มีสิทธิ์ Write ขึ้นไปสามารถกด **"Revert"** เพื่อย้อนกลับไปยังเวอร์ชันก่อนหน้าได้ทันที เหมือนกับการ revert commit ใน git ปกติ

## Step 268: เชื่อมโยง Wiki กับ Issue/PR (ลิงก์ข้ามไปมา)

การเชื่อมโยงระหว่าง Wiki กับ Issue หรือ Pull Request ช่วยให้ข้อมูลไม่กระจัดกระจาย และทำให้ผู้อ่านเห็นบริบทที่ครบถ้วนมากขึ้น

### 268.1 ลิงก์จาก Issue/PR ไปยัง Wiki

ในการเขียน comment บน Issue หรือ Pull Request คุณสามารถใส่ลิงก์ไปยังหน้า Wiki ได้โดยตรงด้วย Markdown ปกติ:

```markdown
ปัญหานี้เคยมีอธิบายไว้แล้วที่หน้า [Troubleshooting](https://github.com/somchai/myawesomeapp/wiki/Troubleshooting#database-connection) ลองทำตามขั้นตอนในหัวข้อ "แอปพลิเคชันไม่สามารถเชื่อมต่อฐานข้อมูลได้" ดูก่อนนะครับ
```

สังเกตว่าสามารถใส่ **anchor link** (`#database-connection`) เพื่อพาไปยังหัวข้อย่อยที่ตรงจุดในหน้า Wiki นั้นได้เลย โดย GitHub จะสร้าง anchor ให้อัตโนมัติจากหัวข้อ (heading) ทุกอันในหน้า Wiki เหมือนกับที่มันทำใน README

### 268.2 ลิงก์จาก Wiki ไปยัง Issue/PR

ในทางกลับกัน ภายในหน้า Wiki เอง คุณก็สามารถอ้างอิงถึง Issue หรือ Pull Request ได้ด้วยการใส่ URL แบบเต็ม:

```markdown
## ปัญหาที่ทราบแล้ว (Known Issues)

- Memory leak เมื่อใช้กับ Node.js 18 — ติดตามความคืบหน้าได้ที่ [Issue #245](https://github.com/somchai/myawesomeapp/issues/245)
- ฟีเจอร์ dark mode อยู่ระหว่างพัฒนา — ดู [PR #310](https://github.com/somchai/myawesomeapp/pull/310)
```

> **ข้อควรทราบ:** ต่างจากการเขียนใน Issue/PR/README ของ repo หลัก ที่การพิมพ์แค่ `#245` จะถูกแปลงเป็นลิงก์อัตโนมัติ (auto-linking) — **ฟีเจอร์นี้ใช้ไม่ได้ใน Wiki** เพราะ Wiki เป็น repository คนละตัวกับ repo หลัก ระบบจึงไม่รู้ว่า `#245` หมายถึง issue ของ repo ไหน ดังนั้นในหน้า Wiki **ต้องใส่ URL แบบเต็มเสมอ** เพื่อให้ลิงก์ทำงานถูกต้อง

### 268.3 รูปแบบการใช้งานที่แนะนำในทีม

แนวทางที่หลายทีมนิยมใช้คือ:

1. เมื่อมีการพูดคุยยาว ๆ ใน Issue หรือ PR ที่นำไปสู่การตัดสินใจสำคัญ (เช่น การออกแบบ API หรือแนวทางแก้ปัญหา) ให้**สรุปผลลัพธ์สุดท้ายไว้ในหน้า Wiki** เช่น หน้า `Architecture` หรือ `Design-Decisions` แล้วใส่ลิงก์ย้อนกลับไปยัง Issue/PR ต้นทางเพื่อให้ผู้ที่อยากอ่านรายละเอียดเชิงลึกตามไปดูได้
2. เมื่อมีคำถามซ้ำ ๆ เกิดขึ้นบ่อยใน Issue ให้เพิ่มคำถามนั้นเข้าไปในหน้า `FAQ` ของ Wiki แล้วเวลามีคนถามซ้ำอีก maintainer สามารถตอบสั้น ๆ พร้อมแปะลิงก์ไปยัง FAQ แทนการอธิบายซ้ำทุกครั้ง
3. ใช้ label พิเศษ เช่น `needs-docs` บน Issue เพื่อ track ว่ามีเรื่องอะไรบ้างที่ควรถูกนำไปเขียนเพิ่มใน Wiki

ตัวอย่างการตอบ Issue ที่มีคำถามซ้ำ:

```markdown
สวัสดีครับ คำถามนี้มีคนถามบ่อยมาก ผมได้รวบรวมคำตอบไว้ในหน้า FAQ แล้วที่
https://github.com/somchai/myawesomeapp/wiki/FAQ#การตั้งค่าฐานข้อมูล

ถ้าทำตามแล้วยังติดปัญหาอยู่ รบกวนแจ้งกลับมาที่ Issue นี้ได้เลยครับ
```

### 268.4 ข้อจำกัดที่ต้องระวัง

- Wiki ไม่มีระบบ mention (`@username`) ที่ส่ง notification เหมือน Issue/PR — การพิมพ์ `@somchai` ใน Wiki จะไม่แจ้งเตือนใครเลย
- Wiki ไม่รองรับการปิด/เปิดสถานะแบบ Issue (ไม่มี "closed"/"open") มันเป็นแค่หน้าเอกสารที่แก้ไขได้ตลอดเวลา
- การค้นหาข้าม Wiki กับ Issue/PR ไม่ได้รวมกันในช่องค้นหาเดียว ต้องใช้ระบบค้นหาแยกกัน (ดู Step 269)

## Step 269: Search ภายใน Wiki

### 269.1 ช่องค้นหาใน Wiki

เมื่อเข้าไปที่แท็บ Wiki ของ repository ที่มีหลายหน้า จะเห็น**ช่องค้นหา (search box)** อยู่ที่แถบด้านซ้าย เหนือรายการหน้าทั้งหมด การค้นหานี้เป็นระบบค้นหาที่ **ทำงานเฉพาะภายใน Wiki ของ repository นั้น ๆ เท่านั้น** ไม่ได้ค้นหาข้ามไปยังโค้ด, Issue หรือ PR

### 269.2 วิธีค้นหาให้ได้ผลลัพธ์ที่ตรงประเด็น

- การค้นหาจะจับคู่กับ**เนื้อหาข้อความในหน้า Wiki** รวมถึงชื่อหัวข้อ (title) ของแต่ละหน้าด้วย
- พิมพ์คำสำคัญที่คิดว่าน่าจะปรากฏในหน้าที่ต้องการ เช่น พิมพ์ `database` เพื่อหาเนื้อหาที่เกี่ยวกับฐานข้อมูลทุกหน้า
- ผลลัพธ์การค้นหาจะแสดงชื่อหน้าที่พบคำที่ตรงกัน พร้อมตัวอย่างข้อความบางส่วนที่ตรงกับคำค้น (excerpt)

### 269.3 การค้นหาแบบกว้างขึ้นด้วย GitHub Search (ทางเลือกเสริม)

หากต้องการค้นหาที่ครอบคลุมมากกว่าช่องค้นหาใน Wiki เอง สามารถใช้ **GitHub code search แบบขั้นสูง** ผ่านการระบุ qualifier บางตัวได้ (แม้ Wiki repo จะไม่ปรากฏในผลการค้นหาโค้ดทั่วไปของ repo หลักโดยตรง แต่หากทราบ URL ของ `.wiki.git` และมันถูก index ไว้ ก็อาจค้นเจอผ่านการค้นหาแบบทั่วไปของ GitHub ได้ในบางกรณี) อย่างไรก็ตาม วิธีที่แนะนำและเชื่อถือได้มากที่สุดยังคงเป็นการใช้ **ช่องค้นหาในตัว Wiki เอง** ที่อธิบายไปใน 269.1

### 269.4 เคล็ดลับการจัดโครงสร้างเนื้อหาให้ค้นหาเจอง่าย

เพื่อให้ระบบค้นหาของ Wiki ทำงานได้อย่างมีประสิทธิภาพที่สุด ควรออกแบบเนื้อหาตามหลักการเหล่านี้:

1. **ตั้งชื่อหัวข้อ (heading) ให้ชัดเจนและมีคำสำคัญ** — เช่น ใช้ `## การตั้งค่าเชื่อมต่อ PostgreSQL` แทนที่จะเขียนแค่ `## การตั้งค่า` เฉย ๆ
2. **หลีกเลี่ยงการยัดทุกอย่างไว้ในหน้าเดียว** — แยกเนื้อหาเป็นหน้าย่อยตามหัวข้อที่ชัดเจน จะทำให้ผลการค้นหาชี้ตรงไปยังหน้าที่เกี่ยวข้องที่สุด แทนที่จะได้หน้ายาวเดียวที่มีทุกอย่างปนกัน
3. **ใช้คำศัพท์ที่ผู้ใช้น่าจะพิมพ์ค้นหาจริง ๆ** — เช่น ถ้าผู้ใช้มักพิมพ์ว่า "error" ให้แน่ใจว่าในหน้า Troubleshooting มีคำว่า "error" ปรากฏอยู่จริง ไม่ใช่ใช้คำพ้องความหมายอื่นที่คนไม่คุ้นเคย
4. **เพิ่ม synonym หรือคำที่ผู้ใช้อาจพิมพ์ผิด/พิมพ์ต่างกัน** ไว้ในเนื้อหาด้วย เช่น ถ้าฟีเจอร์ชื่อทางการคือ "Authentication" ให้มีคำว่า "login" หรือ "auth" ปรากฏในเนื้อหาด้วย เพื่อให้ผู้ใช้ที่ค้นด้วยคำเหล่านั้นเจอหน้าที่ถูกต้อง

### 270.3 เกณฑ์ตรวจสอบความสำเร็จ

แบบฝึกหัดนี้ถือว่าสำเร็จเมื่อคุณทำครบทุกข้อต่อไปนี้:

- [ ] ทดสอบ Search ภายใน Wiki และได้ผลลัพธ์ที่ถูกต้อง
- [ ] เข้าใจวิธีจำกัดสิทธิ์การแก้ไข Wiki ให้เฉพาะ collaborator

## สรุป Part 27

ใน Part นี้เราได้เรียนรู้ว่า:

1. **GitHub Wiki คือ git repository แยกต่างหาก** (`<repo>.wiki.git`) ที่ผูกกับ repository หลัก ใช้เก็บเอกสารที่เขียนด้วย Markdown และมี UI สำหรับอ่าน/แก้ไข/ค้นหาในตัว แตกต่างจาก README ที่เป็นหน้าสรุปสั้น ๆ อยู่ใน repo หลัก
2. การเปิดใช้งาน Wiki ทำผ่าน Settings → Features และหน้าแรกที่ต้องสร้างเสมอคือหน้าชื่อ `Home`
3. Wiki รองรับ **GitHub Flavored Markdown เต็มรูปแบบ** และมีหน้าพิเศษสองหน้าคือ `_Sidebar` (กำหนด navigation เอง) กับ `_Footer` (ข้อความท้ายทุกหน้า)
4. Wiki สามารถ **clone มาแก้ไขแบบ local ได้เหมือน git repo ทั่วไป** ผ่าน URL `<repo>.wiki.git` และ push กลับ (default branch มักเป็น `master`)
5. โครงสร้างเอกสารที่ดีสำหรับโปรเจกต์ขนาดกลาง-ใหญ่ควรแบ่งเป็นกลุ่ม Getting Started, Usage Guides, Developer Docs และ Support & Reference (FAQ, Troubleshooting, Changelog)
6. เมื่อเทียบกับทางเลือกอื่น **Wiki เหมาะกับเอกสารที่แก้ไขบ่อยและไม่เป็นทางการ**, **`docs/` เหมาะกับเอกสารที่ต้อง sync กับโค้ดผ่าน PR**, และ **GitHub Pages เหมาะกับ documentation site ที่ต้องการความสวยงามระดับมืออาชีพ**
7. สามารถ**จำกัดสิทธิ์การแก้ไข Wiki ให้เฉพาะ collaborator** ได้ผ่าน Settings เพื่อป้องกันการแก้ไขที่ไม่เหมาะสมในโปรเจกต์ public
8. Wiki เชื่อมโยงกับ Issue/PR ได้ผ่านการใส่ **URL แบบเต็ม** (auto-linking ของ `#number` ใช้ไม่ได้ข้าม repository)
9. Wiki มี **ระบบค้นหาในตัว** ที่ทำงานเฉพาะภายใน Wiki นั้น ๆ และการออกแบบหัวข้อให้ชัดเจนจะช่วยให้ค้นหาเจอง่ายขึ้นมาก
10. เราได้ลงมือสร้างเอกสารประกอบโปรเจกต์ผ่าน Wiki จริงอย่างน้อย 5 หน้า พร้อมทดสอบการแก้ไขแบบ local และการจำกัดสิทธิ์
