## Step 141: ภาพรวมโปรเจกต์ฝึกหัด — วางแผนโครงสร้างไฟล์และแผนการ commit

ถึงจุดนี้คุณได้เรียนรู้คำสั่ง Git แยกเป็นชิ้น ๆ มาแล้วทั้งหมด 14 Part: `init`, `add`, `commit`, `log`, `diff`, `.gitignore`, `branch`, `switch`, `merge`, `conflict`, `remote`, `clone`, `push`, `pull`, `tag`, `stash`, `alias`, `checkout`/`restore`/`reset` ในโหมด soft/mixed/hard

Part นี้จะไม่สอนคำสั่งใหม่เลยแม้แต่คำสั่งเดียว — แต่จะ **เอาทุกอย่างที่เรียนมาทั้งหมดมาร้อยเรียงเข้าด้วยกันในโปรเจกต์จริงหนึ่งโปรเจกต์** ตั้งแต่การสร้างโฟลเดอร์เปล่า ๆ ไปจนถึงการ push ขึ้น remote พร้อม tag แบบมืออาชีพ

### โปรเจกต์ที่เราจะสร้าง: เว็บไซต์ Portfolio ส่วนตัว

เราจะสร้างเว็บไซต์ portfolio เล็ก ๆ ด้วย HTML/CSS/JavaScript ล้วน (ไม่ต้องพึ่ง framework หรือ build tool ใด ๆ เพื่อโฟกัสที่ Git 100%) ประกอบด้วย 3 หน้า:

1. **Home** (`index.html`) — หน้าแรก มี navigation, hero section แนะนำตัว, footer
2. **About** (`about.html`) — หน้าประวัติและทักษะ
3. **Projects** (`projects.html`) — หน้าแสดงผลงาน

### วางแผนโครงสร้างไฟล์ล่วงหน้า

```
portfolio-project/
├── .gitignore
├── README.md
├── index.html
├── about.html
├── projects.html
├── css/
│   └── style.css
└── js/
    └── main.js
```

การวางแผนโครงสร้างไฟล์ **ก่อน** ลงมือ เป็นนิสัยที่ดีมาก เพราะช่วยให้เราคาดเดาได้ว่าไฟล์ไหนจะถูกแก้โดยฟีเจอร์ไหนบ้าง — ซึ่งเป็นกุญแจสำคัญที่ทำให้เรา **คาดการณ์ conflict ได้ล่วงหน้า** (และใน Part นี้เราจะตั้งใจปล่อยให้ conflict เกิดขึ้นจริงเพื่อฝึกแก้มันอย่างมั่นใจ)

### วางแผนลำดับการ commit และ branch ทั้งหมดของ Part นี้

ก่อนลงมือ มาดูภาพรวมทั้งหมดว่า Part นี้จะพาคุณผ่านสถานการณ์อะไรบ้าง เพื่อให้เห็นภาพรวมทั้งเรื่องก่อนเริ่ม:

| Step | สิ่งที่จะเกิดขึ้น | สถานการณ์ที่จำลอง |
|---|---|---|
| 142 | `git init` + commit แรก | เริ่มโปรเจกต์ใหม่ตั้งแต่ศูนย์ |
| 143 | สร้าง `feature/home-page`, commit 3 ครั้ง | พัฒนาฟีเจอร์เดี่ยวบน branch แยก |
| 144 | สร้าง `feature/about-page` จาก `main` (ก่อน home-page merge) | ทำงาน 2 ฟีเจอร์คู่ขนานเหมือนทีมจริง |
| 145 | Merge `home-page` (fast-forward) แล้ว merge `about-page` (conflict) | Merge ปกติ vs. Merge ที่ conflict จริง |
| 146 | เริ่ม `feature/projects-page` แล้วโดนบั๊กด่วนแทรก | `git stash` ช่วยสลับงานแบบไม่เสียงาน |
| 147 | Merge `projects-page` แล้วติด tag `v1.0.0` | ปิด milestone แรกอย่างเป็นทางการ |
| 148 | Commit โค้ดพังใส่ `main` โดยไม่ตั้งใจ | `git revert` และ `git reset --soft` กู้สถานการณ์ |
| 149 | สร้าง bare repo, push ทุกอย่างรวม tag | จำลองการมี remote ก่อนเข้า GitHub จริงใน Part 16 |
| 150 | สรุปคำสั่งทั้งหมดของเฟส 2 | เตรียมพร้อมเข้าสู่เฟส 3 (GitHub) |

> **หมายเหตุสำคัญ:** Part นี้จงใจ **ไม่ใช้ GitHub จริง** เพราะ GitHub ยังไม่ได้สอนอย่างเป็นทางการจนกว่าจะถึง Part 16 เราจะสร้าง "remote" จำลองขึ้นมาเองด้วย bare repository บนเครื่องของคุณเอง (Step 149) ซึ่งใช้กลไกเดียวกันกับ GitHub ทุกประการ — ต่างกันแค่ที่อยู่ของ remote เท่านั้น

## Step 142: เริ่มต้นโปรเจกต์ (git init, .gitignore, ไฟล์เริ่มต้น, commit แรก)

### 142.1 สร้าง repository

```bash
git init
```

```
Initialized empty Git repository in /home/user/git-course/portfolio-project/.git/
```

ตรวจสอบว่า branch เริ่มต้นชื่อ `main` (ถ้าเครื่องคุณตั้งค่า `init.defaultBranch` ไว้แล้วตาม Part 02):

```bash
git branch
git status
```

```
On branch main

No commits yet

nothing to commit (create/copy files and use "git add" to track)
```

ถ้า `git branch` ไม่แสดงอะไรเลย (เพราะยังไม่มี commit ตัวไหนให้ branch ชี้ไปหา) ให้ใช้ `git symbolic-ref --short HEAD` ตรวจสอบชื่อ branch ปัจจุบันแทน

### 142.2 สร้าง .gitignore ก่อนสร้างไฟล์อื่น

การสร้าง `.gitignore` ตั้งแต่ commit แรกเป็นแนวทางปฏิบัติที่ดีที่สุด (best practice) เพราะป้องกันไม่ให้ไฟล์ขยะหลุดเข้าไปใน commit ตั้งแต่ต้น

```bash
cat > .gitignore << 'EOF'
# ไฟล์ระบบปฏิบัติการ
.DS_Store
Thumbs.db

# ไฟล์ log
*.log

# โฟลเดอร์ dependency (เผื่ออนาคตเพิ่ม build tool เช่น npm)
node_modules/

# ไฟล์ตั้งค่าส่วนตัวของ Editor
.vscode/
.idea/

# ไฟล์ที่มีข้อมูลลับ ห้าม commit เด็ดขาด
.env
EOF
```

### 142.3 สร้างไฟล์เริ่มต้นของโปรเจกต์


## Step 143: พัฒนาฟีเจอร์แรกบน branch แยก (feature/home-page)

ตามหลักการที่เรียนใน Part 07 และ Part 08 — **ไม่ควรพัฒนาฟีเจอร์ใหม่บน `main` โดยตรง** ให้สร้าง branch แยกเสมอ

### 143.1 สร้างและสลับไปยัง branch ใหม่

```bash
git switch -c feature/home-page
```

```
Switched to a new branch 'feature/home-page'
```

`git switch -c` เทียบเท่ากับ `git checkout -b` ที่เราเรียนมาก่อนหน้านี้ — ทั้งสร้าง branch ใหม่และสลับไปพร้อมกันในคำสั่งเดียว

ตรวจสอบ:

```bash
git branch
```

```
* feature/home-page
  main
```

เครื่องหมาย `*` บอกว่าเราอยู่บน `feature/home-page` แล้ว

### 143.2 Commit ที่ 1: เพิ่ม Navigation และ Hero section

```bash
  <header class="site-header">
    <nav>
      <ul>
```

### 143.5 ตรวจสอบภาพรวมของ branch นี้

```bash
git log --oneline main..feature/home-page
```

```
2f3a4b5 (HEAD -> feature/home-page) เพิ่ม Footer ท้ายหน้า Home
7a8b9c0 จัดสไตล์ Navigation และ Hero section ด้วย CSS
4d5e6f7 เพิ่ม Navigation bar และ Hero section ในหน้า Home
```

`main..feature/home-page` คือ syntax ที่บอกว่า "แสดง commit ทั้งหมดที่อยู่ใน `feature/home-page` แต่ไม่อยู่ใน `main`" — เป็นวิธีที่ดีมากในการรีวิวว่า branch ของเราทำอะไรไปบ้างก่อนจะ merge

ตอนนี้ `feature/home-page` มี 3 commit ใหม่ที่ `main` ยังไม่มี **แต่เรายังไม่ merge ทันที** — เราจะไปเปิดฟีเจอร์ที่สองก่อน เพื่อจำลองสถานการณ์การทำงานคู่ขนานที่เกิดขึ้นจริงในทีม

## Step 144: จำลองการทำงานหลายฟีเจอร์พร้อมกัน (feature/about-page จาก main)

ในทีมจริง คนสองคนมักจะเริ่มงานคนละฟีเจอร์ **พร้อมกัน** โดยแต่ละคนแตก branch จาก `main` ณ เวลาที่ตัวเองอยู่ — ไม่ใช่รอให้อีกคนทำเสร็จก่อน นี่คือสิ่งที่เราจะจำลองในขั้นตอนนี้

### 144.1 กลับไปที่ main แล้วแตก branch ใหม่จากจุดเดิม

## Step 145: Merge ฟีเจอร์แรกแบบ fast-forward และแก้ conflict จริงตอน merge ฟีเจอร์ที่สอง

### 145.1 กลับไปที่ main

### 145.2 Merge feature/home-page (คาดหวังว่าจะเป็น Fast-forward)

เนื่องจาก `main` ไม่มี commit ใหม่เพิ่มเข้ามาเลยนับตั้งแต่ `feature/home-page` แตกออกไป Git จึงสามารถ **เลื่อน pointer ของ `main` ไปชี้ที่ปลายของ `feature/home-page` ได้ตรง ๆ** โดยไม่ต้องสร้าง merge commit ใหม่เลย — นี่คือ **Fast-forward merge**

```bash
git merge feature/home-page
```

```

Fast-forward
```

ทันใดนั้น มีรายงานว่าเว็บไซต์เวอร์ชันที่ deploy จาก `main` แสดงผลไม่มีสไตล์เลย (CSS ไม่ทำงาน) ต้องรีบไปแก้ **ทันที** บน `main` แต่ตอนนี้เรามีงานค้างอยู่ที่ยังไม่พร้อม commit เลย


```

	index.html
Please commit your changes or stash them before you switch branches.
Aborting
```

Git ปฏิเสธเพราะ `index.html` มีการแก้ไขที่ยังไม่ commit ซึ่งจะถูกทับหากสลับ branch ตรง ๆ (ไฟล์ `index.html` บน `main` เป็นคนละเวอร์ชันกับที่เรากำลังแก้อยู่)

### 146.3 ใช้ git stash เก็บงานที่ทำค้างไว้ชั่วคราว

นี่คือสถานการณ์ที่ `git stash` ถูกสร้างมาเพื่อแก้โดยเฉพาะ (ตามที่เรียนละเอียดใน Part 12) เนื่องจากมีทั้งไฟล์ที่ถูก track (`index.html`) และไฟล์ใหม่ที่ยังไม่ถูก track (`projects.html`) เราต้องใช้ flag `-u` เพื่อรวมไฟล์ untracked เข้าไปด้วย มิเช่นนั้น `projects.html` จะถูกทิ้งไว้ข้างนอกและอาจสร้างความสับสน:

```bash

```


```bash

```

```
On branch feature/projects-page
nothing to commit, working tree clean
```

working directory สะอาดหมดจดแล้ว ปลอดภัยที่จะสลับ branch

## Step 147: ติด annotated tag เวอร์ชัน v1.0.0 พร้อมเขียน release message

### 147.1 Merge feature/projects-page เข้า main

```bash
git switch main
git merge --no-ff feature/projects-page -m "Merge feature/projects-page: เพิ่มหน้าผลงานครบสามหน้าตามแผน"

```

```
 css/style.css |  12 ++++++++++++
 index.html    |   6 +++++-
 projects.html |  22 ++++++++++++++++++++++
 3 files changed, 39 insertions(+), 1 deletion(-)
```

### 147.3 สร้าง Annotated Tag

## Step 148: จำลองความผิดพลาด แล้วกู้คืนด้วย git revert และ git reset --soft

หลังจากปล่อย v1.0.0 ไปแล้ว งานพัฒนายังคงดำเนินต่อไป — และในโลกจริง ความผิดพลาดเป็นเรื่องที่เกิดขึ้นได้เสมอ Step นี้จะจำลอง 2 สถานการณ์ที่พบบ่อยที่สุด และวิธีแก้ไขที่ถูกต้องของแต่ละสถานการณ์

### สถานการณ์ที่ 1: Commit โค้ดพังตรงเข้า main โดยตรง (ต้องใช้ revert)

#### 148.1 ทำผิดพลาด — commit โค้ดที่มีบั๊กตรงเข้า main

```bash
cat >> js/main.js << 'EOF'

// เพิ่ม Google Analytics tracking (เขียนรีบ ไม่ได้ทดสอบ)
function trackPageView({
  console.log("page view tracked");
}
EOF

git add js/main.js
git commit -m "เพิ่ม Google Analytics tracking code"
```

```
[main 2a3b4c5] เพิ่ม Google Analytics tracking code
 1 file changed, 5 insertions(+)
```

สังเกตว่าโค้ดที่เพิ่มเข้าไปมี **syntax error ชัดเจน** (`function trackPageView({` วงเล็บผิด) ซึ่งจะทำให้ `js/main.js` ทั้งไฟล์หยุดทำงานทันทีที่โหลดในเบราว์เซอร์ — เมนูและฟีเจอร์ JavaScript ทั้งหมดของเว็บไซต์จะพังหมด

#### 148.2 ตรวจพบปัญหา

สมมติว่าทีม QA แจ้งว่าเว็บไซต์ใช้งานไม่ได้ทันทีหลัง deploy คุณตรวจสอบและพบว่า commit ล่าสุดคือต้นเหตุ:

```bash
git log --oneline -3
```

```
2a3b4c5 (HEAD -> main) เพิ่ม Google Analytics tracking code
9e0f1a2 (tag: v1.0.0) Merge feature/projects-page: เพิ่มหน้าผลงานครบสามหน้าตามแผน
6f7a8b9 Hotfix: แก้ไข syntax error ใน css/style.css ที่ทำให้ CSS ไม่ทำงาน
```

#### 148.3 ทำไมต้องใช้ revert แทน reset ในสถานการณ์นี้

ทบทวนกฎทองจาก Part 14: **ถ้า commit นั้นมีความเป็นไปได้ว่าถูกแชร์ให้คนอื่นแล้ว (push ขึ้น remote แล้ว หรือมีคนอื่นดึงไปใช้แล้ว) ห้ามใช้ `reset` เด็ดขาด ให้ใช้ `revert` เท่านั้น** เพราะ `reset` จะลบ commit ออกจากประวัติของเราไปเลย ทำให้ประวัติของเรากับของคนอื่นไม่ตรงกัน (diverge) ส่วน `revert` จะสร้าง commit ใหม่ที่ "หักล้าง" การเปลี่ยนแปลงเดิม โดยไม่ลบอะไรออกจากประวัติเลย ปลอดภัยเสมอไม่ว่าใครจะดึงไปแล้วหรือไม่

ในโปรเจกต์นี้แม้เราจะยังไม่ได้ push จริง (จะ push ใน Step 149) แต่เราจะฝึกด้วยแนวคิดว่า **commit บน main ควรถูกปฏิบัติราวกับว่า push ไปแล้วเสมอ** เพราะ `main` คือ branch ที่ทุกคนอ้างอิง

#### 148.4 ใช้ git revert

```bash
git revert 2a3b4c5
```

Git จะเปิด editor ให้แก้ commit message ของการ revert (มี default message เตรียมไว้ให้แล้ว):

```
Revert "เพิ่ม Google Analytics tracking code"

This reverts commit 2a3b4c52c3d4e5f6a7b8c9d0e1f2a3b4c5d6e7f8.
```

บันทึกและปิด:

```
[main 7f8a9b0] Revert "เพิ่ม Google Analytics tracking code"
 1 file changed, 5 deletions(-)
```

ตรวจสอบว่าโค้ดที่มีบั๊กหายไปแล้วจริง:

```bash
cat js/main.js
```

```javascript
// main.js: จุดเริ่มต้นของ JavaScript ทั้งหมดในเว็บไซต์
console.log("Portfolio loaded");
```

โค้ดกลับมาเป็นเวอร์ชันที่ใช้งานได้ปกติแล้ว และดูประวัติ:

```bash
git log --oneline -4
```

```
7f8a9b0 (HEAD -> main) Revert "เพิ่ม Google Analytics tracking code"
2a3b4c5 เพิ่ม Google Analytics tracking code
9e0f1a2 (tag: v1.0.0) Merge feature/projects-page: เพิ่มหน้าผลงานครบสามหน้าตามแผน
6f7a8b9 Hotfix: แก้ไข syntax error ใน css/style.css ที่ทำให้ CSS ไม่ทำงาน
```

จุดสำคัญที่ต้องสังเกต: **commit ที่ทำผิด (`2a3b4c5`) ยังอยู่ในประวัติ ไม่ถูกลบ** — มีแค่ commit ใหม่ (`7f8a9b0`) ที่หักล้างผลของมัน นี่คือความแตกต่างสำคัญจาก `reset` และเป็นเหตุผลที่ `revert` ปลอดภัยกับประวัติที่แชร์ไปแล้ว เพราะไม่มีใครต้อง "เขียนประวัติทับ" เลย

### สถานการณ์ที่ 2: Commit ที่ยังไม่ได้ push อยากรวมและแก้ก่อน (ใช้ reset --soft ได้)

#### 148.5 สถานการณ์: ทำ commit ซุ่มซ่ามหลายอันติดกันโดยยังไม่ได้ push

ระหว่างอัปเดตข้อมูลติดต่อใน README คุณรีบ commit สองครั้งติดกันด้วยข้อความที่ไม่มีความหมาย (เหตุการณ์นี้เกิดขึ้นบ่อยมากตอนรีบทดสอบอะไรบางอย่าง):

```bash
cat >> README.md << 'EOF'

## ติดต่อ
EOF
git add README.md
git commit -m "fix"
```

```
[main a1b2c3e] fix
 1 file changed, 2 insertions(+)
```

```bash
cat >> README.md << 'EOF'
Email: somchai@example.com
EOF
git add README.md
git commit -m "fix again"
```

```
[main b2c3d4f] fix again
 1 file changed, 1 insertion(+)
```

ตรวจสอบ:

```bash
git log --oneline -3
```

```
b2c3d4f (HEAD -> main) fix again
a1b2c3e fix
7f8a9b0 Revert "เพิ่ม Google Analytics tracking code"
```

ข้อความ `fix` และ `fix again` ไม่สื่อความหมายอะไรเลย — ถ้าใครมาดู `git log` ในอนาคตจะไม่มีทางรู้ว่าทำอะไรไปบ้าง และเนื่องจากทั้งสอง commit นี้ **ยังไม่ได้ push ไปที่ remote เลย** (Step 149 ยังไม่เกิดขึ้น) การใช้ `git reset --soft` เพื่อ "รวบ" สอง commit นี้เป็นอันเดียวที่มีข้อความดี ๆ จึงปลอดภัย 100%

#### 148.6 ใช้ git reset --soft รวบ 2 commit เป็น 1

```bash
git reset --soft HEAD~2
```

คำสั่งนี้ทำสิ่งเดียว: **เลื่อน HEAD และ branch pointer ถอยหลังไป 2 commit** แต่ **ไม่แตะ staging area และ working directory เลย** ทบทวนตารางเปรียบเทียบจาก Part 14:

| โหมด | HEAD/branch | Staging Area | Working Directory |
|---|---|---|---|
| `--soft` | เปลี่ยน | **ไม่เปลี่ยน** (ของเก่ายังอยู่ครบ staged) | ไม่เปลี่ยน |
| `--mixed` (default) | เปลี่ยน | เปลี่ยน (unstage ทั้งหมด) | ไม่เปลี่ยน |
| `--hard` | เปลี่ยน | เปลี่ยน | เปลี่ยน (ไฟล์หายจริง) |

ตรวจสอบสถานะ:

```bash
git status
```

```
On branch main
Changes to be committed:
  (use "git restore --staged <file>..." to unstage)
	modified:   README.md
```

```bash
git log --oneline -2
```

```
7f8a9b0 (HEAD -> main) Revert "เพิ่ม Google Analytics tracking code"
6f7a8b9 Hotfix: แก้ไข syntax error ใน css/style.css ที่ทำให้ CSS ไม่ทำงาน
```

สอง commit ที่มีข้อความแย่ ๆ หายไปจากประวัติแล้ว แต่การเปลี่ยนแปลงเนื้อหาไฟล์ (`README.md`) ยังอยู่ครบและอยู่ใน staging area พร้อม commit ใหม่ทันที

#### 148.7 Commit ใหม่ด้วยข้อความที่สื่อความหมาย

```bash
git commit -m "อัปเดตข้อมูลติดต่อใน README"
```

```
[main c3d4e5f] อัปเดตข้อมูลติดต่อใน README
 1 file changed, 3 insertions(+)
```

```bash
git log --oneline -3
```

```
c3d4e5f (HEAD -> main) อัปเดตข้อมูลติดต่อใน README
7f8a9b0 Revert "เพิ่ม Google Analytics tracking code"
6f7a8b9 Hotfix: แก้ไข syntax error ใน css/style.css ที่ทำให้ CSS ไม่ทำงาน
```

ประวัติสะอาดขึ้นมาก มีแค่ 1 commit ที่สื่อความหมายชัดเจนแทนที่จะเป็น 2 commit ที่ไม่มีใครเข้าใจ

> **สรุปกฎการเลือกใช้ที่ต้องจำขึ้นใจ:**
> - **push ไปแล้ว หรือไม่แน่ใจว่ามีใครดึงไปหรือยัง** → ใช้ `git revert` เสมอ (ปลอดภัยกับทุกคน)
> - **ยังไม่ push แน่นอน และเป็น commit ของคุณคนเดียว** → ใช้ `git reset` ได้ (soft/mixed/hard ตามความจำเป็น) เพื่อจัดประวัติให้สะอาดก่อนแชร์ให้คนอื่น

## Step 149: สร้าง bare repo จำลองเป็น remote แล้ว push ทุกอย่างขึ้นไปพร้อม tag

ถึงตอนนี้เรายังไม่ได้สอน GitHub อย่างเป็นทางการ (จะเริ่มใน Part 16) แต่แนวคิดเรื่อง remote repository ไม่ได้ผูกติดกับ GitHub เลย — Git รองรับการมี remote ที่เป็นแค่โฟลเดอร์บนเครื่อง (หรือเครื่องอื่นในเครือข่าย) ก็ได้ ตราบใดที่มันเป็น **bare repository**

### 149.1 Bare Repository คืออะไร (ทบทวนสั้น ๆ จาก Part 09)

**Bare repository** คือ repository ที่ **ไม่มี working directory** — มีแต่ข้อมูลภายในของ Git (โฟลเดอร์ `.git` เพียว ๆ) ใช้สำหรับเป็น "ศูนย์กลาง" ให้หลายคน push/pull เข้ามา ไม่ได้มีไว้แก้ไขไฟล์โดยตรง ซึ่งเป็นหลักการเดียวกับที่ GitHub ใช้เก็บ repository ของทุกคนบนเซิร์ฟเวอร์ของเขา

### 149.2 สร้าง bare repository จำลอง

```bash
mkdir -p ~/git-course/remote-repos
cd ~/git-course/remote-repos
git init --bare portfolio-project.git
```

```
Initialized empty Git repository in /home/user/git-course/remote-repos/portfolio-project.git/
```

สังเกตว่าไม่มีข้อความ "empty **working** directory" เหมือน `git init` ปกติ — เพราะ bare repo ไม่มี working directory ให้พูดถึง

กลับไปที่โปรเจกต์หลัก:

```bash
cd ~/git-course/portfolio-project
```

### 149.3 เชื่อม remote

```bash
git remote add origin ~/git-course/remote-repos/portfolio-project.git
```

ตรวจสอบ:

```bash
git remote -v
```

```
origin	/home/user/git-course/remote-repos/portfolio-project.git (fetch)
origin	/home/user/git-course/remote-repos/portfolio-project.git (push)
```

> **หมายเหตุ:** โครงสร้างคำสั่งนี้เหมือนกันทุกประการกับตอนเชื่อม remote ไป GitHub ใน Part 16 — ต่างกันแค่ URL เท่านั้น ตอนใช้ GitHub จริง URL จะเป็นรูปแบบ `https://github.com/username/repo.git` หรือ `git@github.com:username/repo.git` แทน path บนเครื่อง

### 149.4 Push branch main ขึ้น remote ครั้งแรก

```bash
git push -u origin main
```

```
Enumerating objects: 45, done.
Counting objects: 100% (45/45), done.
Delta compression using up to 8 threads
Compressing objects: 100% (32/32), done.
Writing objects: 100% (45/45), 8.21 KiB | 8.21 MiB/s, done.
Total 45 (delta 12), reused 0 (delta 0), pack-reused 0
To /home/user/git-course/remote-repos/portfolio-project.git
 * [new branch]      main -> main
branch 'main' set up to track 'origin/main'.
```

`-u` (ย่อจาก `--set-upstream`) ตั้งค่าให้ `main` local ผูกกับ `origin/main` โดยอัตโนมัติ ทำให้ครั้งต่อ ๆ ไปพิมพ์แค่ `git push` หรือ `git pull` เฉย ๆ ได้เลยโดยไม่ต้องระบุ `origin main` ซ้ำ

### 149.5 Push tag ขึ้น remote ด้วย

สังเกตว่า `git push` ปกติ **จะไม่ส่ง tag ขึ้นไปด้วยโดยอัตโนมัติ** ต้องสั่งแยกต่างหาก มีสองวิธีหลัก:

**วิธีที่ 1: `git push --tags`** — ส่ง tag **ทุกอัน** ที่มีในเครื่องขึ้นไป โดยไม่สนใจว่า tag นั้นเกี่ยวข้องกับ commit ที่เพิ่ง push หรือไม่

**วิธีที่ 2: `git push --follow-tags`** — ส่งเฉพาะ **annotated tag ที่ชี้ไปยัง commit ที่กำลังจะถูก push ในครั้งนี้เท่านั้น** ปลอดภัยกว่าเพราะจะไม่พลาดส่ง tag ทดลองหรือ tag ที่ยังไม่พร้อมเผยแพร่ขึ้นไปโดยไม่ตั้งใจ

เนื่องจากเรามีแค่ tag เดียว (`v1.0.0`) และมันตั้งใจให้เผยแพร่แน่นอน ทั้งสองวิธีให้ผลเหมือนกันในกรณีนี้ แต่เพื่อฝึกนิสัยที่ปลอดภัยกว่า เราจะใช้ `--follow-tags`:

```bash
git push origin main --follow-tags
```

```
Total 0 (delta 0), reused 0 (delta 0), pack-reused 0
To /home/user/git-course/remote-repos/portfolio-project.git
 * [new tag]         v1.0.0 -> v1.0.0
```

> **ทางเลือกที่ดีกว่า:** ตั้งค่า `git config --global push.followTags true` ครั้งเดียว (แนะนำใน Part 13) เพื่อให้ `git push` ธรรมดาส่ง annotated tag ที่เกี่ยวข้องไปด้วยเสมอโดยไม่ต้องพิมพ์ `--follow-tags` ทุกครั้ง

### 149.6 ตรวจสอบผลลัพธ์ฝั่ง remote

Bare repo ไม่มี working directory ให้เปิดไฟล์ดูตรง ๆ แต่เราตรวจสอบเนื้อหาที่อยู่ข้างในได้ด้วย `git ls-remote`:

```bash
git ls-remote origin
```

```
c3d4e5f...   HEAD
c3d4e5f...   refs/heads/main
f9e8d7c6b5a4...   refs/tags/v1.0.0
9e0f1a2b3c4d...   refs/tags/v1.0.0^{}
```

สังเกตว่า `refs/tags/v1.0.0` กับ `refs/tags/v1.0.0^{}` มี hash **ไม่เหมือนกัน** — บรรทัดแรกคือ hash ของ tag object เอง (เพราะเป็น annotated tag) ส่วนบรรทัดที่มี `^{}` ต่อท้ายคือ hash ของ commit ที่ tag นั้นชี้ไปจริง ๆ (ในที่นี้คือ commit merge `9e0f1a2`) ตรงตามหลักการที่เรียนไปใน Part 11

หรือวิธีที่มั่นใจที่สุดคือ **clone จาก remote ไปยังโฟลเดอร์ใหม่** เพื่อพิสูจน์ว่าคนอื่น (หรือเครื่องอื่น) จะได้รับข้อมูลครบถ้วนจริงเมื่อ clone จากจุดนี้:

```bash
cd ~/git-course
git clone remote-repos/portfolio-project.git portfolio-verify
```

```
Cloning into 'portfolio-verify'...
done.
```

```bash
cd portfolio-verify
git log --oneline
git tag
ls
```

```
c3d4e5f (HEAD -> main, origin/main, origin/HEAD, tag: v1.0.0... ) อัปเดตข้อมูลติดต่อใน README
7f8a9b0 Revert "เพิ่ม Google Analytics tracking code"
6f7a8b9 Hotfix: แก้ไข syntax error ใน css/style.css ที่ทำให้ CSS ไม่ทำงาน
9e0f1a2 Merge feature/projects-page: เพิ่มหน้าผลงานครบสามหน้าตามแผน
5e6f7a8 Merge branch 'feature/about-page'
...

v1.0.0

README.md  about.html  css  index.html  js  projects.html
```

ทุกอย่างครบถ้วน — ประวัติทั้งหมด, tag, ไฟล์ทั้งหมด เหมือนกับที่อยู่ในเครื่อง `portfolio-project` เดิมทุกประการ นี่คือการพิสูจน์ว่า remote ของเราทำงานถูกต้อง 100% และพร้อมสำหรับการย้ายไปใช้ GitHub จริงใน Part 16 โดยใช้หลักการเดียวกันทุกประการ

กลับไปทำงานที่โปรเจกต์หลักต่อ:

```bash
cd ~/git-course/portfolio-project
```

|---|---|
| `git config --global alias.<short> "<full command>"` | สร้างคำสั่งย่อของตัวเอง |
| `git co`, `git br`, `git ci`, `git st` (ตัวอย่าง alias ยอดนิยม) | ทางลัดของ checkout, branch, commit, status |

#### จาก Part 14: Undo (checkout/restore/reset)

| คำสั่ง | หน้าที่ |
|---|---|
| `git restore <file>` | ยกเลิกการแก้ไขใน working directory กลับไปเป็นเวอร์ชันล่าสุดใน staging |
| `git restore --staged <file>` | นำไฟล์ออกจาก staging area (unstage) โดยไม่แตะ working directory |
| `git reset --soft <commit>` | ย้าย HEAD กลับไป แต่คงทุกอย่างไว้ใน staging area |
| `git reset --mixed <commit>` (default) | ย้าย HEAD กลับไป และ unstage ทุกอย่าง แต่ไฟล์ในดิสก์ไม่เปลี่ยน |
| `git reset --hard <commit>` | ย้าย HEAD กลับไป และล้างทั้ง staging area และ working directory (**อันตราย ข้อมูลหายจริง**) |
| `git revert <commit>` | สร้าง commit ใหม่ที่หักล้างผลของ commit เดิม โดยไม่ลบประวัติ (ปลอดภัยกับ branch ที่แชร์แล้ว) |

### 150.2 ตารางสรุป "เมื่อไหร่ควรใช้อะไร" (Decision Table)

| สถานการณ์ | คำสั่งที่ควรใช้ |
|---|---|
| อยากลองแนวคิดใหม่โดยไม่กระทบโค้ดหลัก | `git switch -c feature/xxx` |
| ทำงานค้างอยู่ แต่ต้องสลับไปทำอย่างอื่นด่วน | `git stash push -u -m "..."` |
| Merge แล้วเจอ conflict | แก้ marker ในไฟล์ → `git add` → `git commit` |
| ต้องการปิด milestone/เวอร์ชัน | `git tag -a vX.Y.Z -m "..."` |
| Commit ผิดที่ **push ไปแล้ว** | `git revert <commit>` |
| Commit ผิดที่ **ยังไม่ push** อยากแก้ข้อความ/รวม commit | `git reset --soft` แล้ว commit ใหม่ |
| อยากยกเลิกการแก้ไขที่ยังไม่ add | `git restore <file>` |
| Add ไฟล์ผิดพลาด อยาก unstage | `git restore --staged <file>` |
| ต้องการล้างทุกอย่างกลับไปจุดใดจุดหนึ่งแบบถอนรากถอนโคน | `git reset --hard <commit>` (ระวังให้มาก) |
| อยากส่งงานขึ้น remote ครั้งแรก | `git push -u origin <branch>` |
| อยากส่ง tag ที่สร้างไว้ขึ้น remote ด้วย | `git push --follow-tags` |

### 150.5 Checklist ทบทวนภาพรวมเฟส 2 ทั้งหมด (Part 06–15) ก่อนเข้าสู่เฟส 3

ก่อนไปต่อ Part 16 (เริ่มต้นเฟส 3: GitHub) ให้ตรวจสอบตัวเองอย่างละเอียดตามรายการนี้ ถ้าข้อไหนยังไม่มั่นใจ แนะนำให้ย้อนกลับไปอ่าน Part ที่เกี่ยวข้องอีกครั้งก่อน:

**การจัดการไฟล์**
- [ ] เขียน `.gitignore` ได้เอง และเข้าใจว่า pattern แบบไหนแปลว่าอะไร
- [ ] รู้วิธีเลิก track ไฟล์ที่ถูก track ไปแล้วโดยไม่ตั้งใจด้วย `git rm --cached`

**Branch**
- [ ] สร้าง, สลับ, ลบ, เปลี่ยนชื่อ branch ได้คล่องโดยไม่ต้องเปิดเอกสาร
- [ ] เข้าใจความแตกต่างระหว่าง `git branch -d` กับ `git branch -D`
- [ ] อธิบายได้ว่าทำไมการแตก branch ใน Git ถึง "ถูก" แทบไม่มีต้นทุน

**Merge และ Conflict**
- [ ] แยกแยะได้ว่า merge แบบไหนเป็น Fast-forward และแบบไหนสร้าง merge commit
- [ ] อ่าน conflict marker (`<<<<<<<`, `=======`, `>>>>>>>`) ได้อย่างไม่ตื่นตระหนก
- [ ] แก้ conflict จริงได้ด้วยตัวเองโดยไม่ต้องพึ่งเครื่องมือ GUI
- [ ] รู้จัก `git merge --abort` ไว้ใช้เมื่อจำเป็น

**Remote และ Push/Pull**
- [ ] เข้าใจว่า bare repository คืออะไรและทำไม remote ถึงต้องเป็น bare
- [ ] เชื่อมต่อ remote, push, pull, fetch ได้คล่อง
- [ ] เข้าใจความแตกต่างระหว่าง `fetch` กับ `pull`

**Tag**
- [ ] แยกแยะได้ระหว่าง lightweight tag กับ annotated tag และรู้ว่าเมื่อไหร่ควรใช้แบบไหน
- [ ] ติด tag พร้อมเขียน release message ที่มีประโยชน์ได้

**Stash**
- [ ] ใช้ `git stash` สลับบริบทงานได้อย่างมั่นใจโดยไม่กลัวงานหาย
- [ ] รู้ว่าเมื่อไหร่ต้องใช้ `-u` เพื่อรวมไฟล์ untracked เข้า stash ด้วย

**Alias**
- [ ] ตั้งค่า alias ส่วนตัวอย่างน้อย 3–5 ตัวที่ใช้บ่อยในชีวิตประจำวัน

**Undo**
- [ ] อธิบายความแตกต่างของ `reset --soft`, `--mixed`, `--hard` ได้อย่างชัดเจนโดยไม่สับสน
- [ ] ท่องกฎทองได้ขึ้นใจ: **push ไปแล้วใช้ revert, ยังไม่ push ใช้ reset ได้**
- [ ] ไม่เคยใช้ `reset --hard` โดยไม่เช็ค `git status` ก่อนสักครั้ง

**ภาพรวมโปรเจกต์**
- [ ] ทำโปรเจกต์ตั้งแต่ `git init` จนถึง push remote พร้อม tag ได้ครบทุกขั้นตอนด้วยตัวเองจริง โดยไม่ต้องเปิดเอกสารนี้ดูซ้ำ
- [ ] อ่านกราฟ `git log --oneline --graph --all` ของโปรเจกต์ตัวเองได้เข้าใจทุกจุด

ถ้าคุณติ๊กครบทุกข้อ (หรือเกือบครบ) แปลว่าคุณพร้อมสำหรับเฟส 3 อย่างแท้จริงแล้ว — เฟส 2 คือรากฐานที่สำคัญที่สุดของหลักสูตรทั้งหมด เพราะทุกอย่างที่จะเรียนต่อจากนี้ (GitHub, การทำงานเป็นทีม, CI/CD, Git ขั้นสูง) ล้วนสร้างอยู่บนพื้นฐานคำสั่งที่คุณเพิ่งฝึกใช้จนคล่องใน Part นี้ทั้งสิ้น

## สรุป Part 15

ใน Part นี้เราได้ลงมือสร้างโปรเจกต์เว็บไซต์ portfolio จริงตั้งแต่ต้นจนจบ โดยนำทุกคำสั่งที่เรียนมาตลอดเฟส 2 มาใช้งานร่วมกันในสถานการณ์ที่จำลองมาจากการทำงานจริง:

1. วางแผนโครงสร้างไฟล์และแผนการ commit ก่อนลงมือ (Step 141)
2. เริ่มโปรเจกต์ด้วย `git init`, `.gitignore` และ commit แรก (Step 142)
3. พัฒนาฟีเจอร์บน branch แยกอย่างมีวินัย ไม่แตะ `main` โดยตรง (Step 143)
4. จำลองการทำงานคู่ขนานของสองฟีเจอร์จากจุดเริ่มต้นเดียวกัน (Step 144)
5. Merge แบบ Fast-forward และแก้ Conflict จริงด้วยมือของตัวเอง (Step 145)
6. ใช้ `git stash` สลับไปแก้บั๊กด่วนโดยไม่ทำงานที่ค้างอยู่หาย (Step 146)
7. ติด annotated tag `v1.0.0` เพื่อปิด milestone อย่างเป็นทางการ (Step 147)
8. แก้ไขความผิดพลาดสองรูปแบบด้วย `git revert` และ `git reset --soft` อย่างถูกวิธี (Step 148)
9. สร้าง bare repository จำลอง remote และ push ทุกอย่างขึ้นไปพร้อม tag (Step 149)
10. ทบทวนภาพรวมคำสั่งทั้งหมดของเฟส 2 ผ่าน Cheat Sheet และ Checklist ครบทุกด้าน (Step 150)

Part นี้คือจุดปิดฉากของ **เฟส 2: การทำงานกับไฟล์และ Branch เบื้องต้น (Part 06–15, Step 51–150)** อย่างสมบูรณ์ คุณได้ผ่านการฝึกฝนคำสั่ง Git พื้นฐานและระดับกลางเกือบทั้งหมดที่ใช้ในชีวิตการทำงานจริงแล้ว ตั้งแต่การจัดการไฟล์ การแตกและรวม branch การจัดการ conflict การเชื่อมต่อ remote การติดเวอร์ชัน การพักงานชั่วคราว และการแก้ไขความผิดพลาดอย่างปลอดภัย
