## เข้าสู่เฟส 4: จากทักษะส่วนตัว สู่การทำงานเป็นทีม

ตลอด 3 เฟสที่ผ่านมา (Step 1–300) คุณได้ปูพื้นฐาน Git ตั้งแต่ศูนย์ จนสามารถใช้คำสั่งพื้นฐานได้คล่อง และต่อยอดไปสู่การใช้ GitHub อย่างมืออาชีพ — สร้าง repository, เปิด Pull Request, ทำ Code Review, มีส่วนร่วมกับโปรเจกต์ Open Source ได้ด้วยตัวเอง

สิ่งที่คุณทำมาทั้งหมดนั้น **ส่วนใหญ่ยังเป็นมุมมองของ "คนคนเดียว"** ที่ใช้ Git เพื่อจัดการโค้ดของตัวเอง หรือเพื่อส่ง contribution เข้าไปยังโปรเจกต์คนอื่นแบบเป็นครั้ง ๆ

แต่ในโลกการทำงานจริง แทบไม่มีใครเขียนซอฟต์แวร์คนเดียวตลอดไป ไม่ช้าก็เร็วคุณจะต้องทำงานร่วมกับเพื่อนร่วมทีม 3 คน 5 คน หรือ 50 คน ในโปรเจกต์เดียวกัน แก้ไฟล์เดียวกัน และต้องส่งโค้ดขึ้น production พร้อม ๆ กันอย่างปลอดภัย

นี่คือจุดเริ่มต้นของ **เฟส 4: การทำงานเป็นทีมด้วย Git/GitHub** (Step 301–450) ซึ่งจะพาคุณ:

1. เข้าใจ **Workflow Models** มาตรฐานที่ทีมต่าง ๆ ทั่วโลกใช้ (Centralized, Feature Branch, Git Flow, GitHub Flow, GitLab Flow, Trunk-Based Development)
2. เจาะลึกเทคนิคที่จำเป็นสำหรับการทำงานเป็นทีม เช่น Rebase, Cherry-pick, การจัดการ Conflict ระดับทีม
3. เรียนรู้มารยาทและแนวปฏิบัติที่ดี (Best Practices) ในการ commit, การเขียน PR description, การรีวิวโค้ดของเพื่อนร่วมทีม
4. ฝึกจำลองสถานการณ์ทีมจริงซ้ำแล้วซ้ำเล่า เพื่อให้คุณเจอปัญหาการทำงานร่วมกันในสภาพแวดล้อมที่ปลอดภัยก่อนไปเจอของจริงในที่ทำงาน

**Part 31 นี้คือประตูบานแรกของเฟส 4** เราจะเริ่มจากคำถามพื้นฐานที่สุด: ทำไมทีมถึงต้องมี "workflow" ด้วย ทำไมจะปล่อยให้ทุกคน commit อะไรก็ได้ไม่ได้เหรอ แล้วมาดู 2 โมเดลแรกที่เป็นรากฐานของทุก Workflow ที่ซับซ้อนกว่านั้น: **Centralized Workflow** และ **Feature Branch Workflow**

## Step 301: ทำไมทีมพัฒนาซอฟต์แวร์ต้องมี "Workflow" มาตรฐาน

### Workflow คืออะไรกันแน่

ในบริบทของ Git, **Workflow** (บางครั้งเรียก **Branching Strategy** หรือ **Branching Model**) หมายถึง:

> **ชุดกฎเกณฑ์และขั้นตอนที่ตกลงร่วมกันในทีม ว่าจะสร้าง branch เมื่อไหร่ จะ commit อย่างไร จะรวมโค้ด (merge) กันแบบไหน และใครมีสิทธิ์ทำอะไรกับ branch ไหนบ้าง**

พูดง่าย ๆ Workflow คือ **"กติกาการจราจร"** สำหรับโค้ดของทีม เหมือนกับที่ถนนต้องมีกฎจราจร (ขับชิดซ้าย, หยุดตรงไฟแดง, ให้สัญญาณก่อนเลี้ยว) เพื่อให้รถหลายคันวิ่งบนถนนเดียวกันได้โดยไม่ชนกัน ทีมพัฒนาซอฟต์แวร์ก็ต้องมีกติกาที่ชัดเจนว่า Git repository ของทีมจะถูกใช้งานอย่างไร

### ทำไมจะปล่อยให้ทุกคน commit อะไรก็ได้ตามใจไม่ได้

ลองจินตนาการทีมพัฒนา 8 คนที่ **ไม่มี workflow ใด ๆ เลย** — ทุกคนแค่ `git clone`, แก้โค้ด, แล้ว `git push` ขึ้น branch `main` ตรง ๆ เมื่อไหร่ก็ได้ที่อยากทำ สิ่งที่มักเกิดขึ้นตามมาคือ:

#### 1. ความสับสนว่าใครกำลังทำอะไรอยู่

ไม่มีใครรู้ว่าเพื่อนร่วมทีมกำลังแก้ไฟล์ไหนอยู่ ไม่มีจุดกลางที่บอกว่า "ฟีเจอร์นี้กำลังพัฒนาโดยใคร คืบหน้าถึงไหนแล้ว" ทุกคนต้องถามกันเองใน chat ตลอดเวลาว่า "ตอนนี้ใครแตะไฟล์ `payment.js` อยู่บ้าง"

#### 2. Merge Conflict เกิดขึ้นบ่อยและรุนแรง

เมื่อหลายคน commit ตรงไปที่ branch เดียวกันโดยไม่มีการประสานงาน โอกาสที่ 2 คนจะแก้ไฟล์เดียวกันในบรรทัดใกล้เคียงกันมีสูงมาก และเมื่อไม่มีกระบวนการ pull/rebase ที่เป็นระบบ conflict ที่เกิดขึ้นมักจะซับซ้อนและแก้ยาก เพราะไม่มีใครรู้ว่า "เวอร์ชันไหนถูกต้องจริง ๆ"

#### 3. คุณภาพโค้ดไม่สม่ำเสมอ

ถ้าไม่มีขั้นตอนบังคับให้ต้องมีคนอื่นตรวจสอบโค้ดก่อน merge (Code Review) โค้ดที่มีบั๊ก โค้ดที่เขียนไม่ตรงตาม convention ของทีม หรือแม้แต่โค้ดที่ commit ผิดพลาดโดยไม่ได้ตั้งใจ (เช่น หลุด API key เข้าไปในโค้ด) ก็จะเข้าไปอยู่ใน `main` ได้ทันทีโดยไม่มีใครทัดทาน

#### 4. Branch `main` ไม่เสถียร (ไม่ deployable เสมอ)

หลักการสำคัญของทีมที่เป็นมืออาชีพคือ **`main` ต้อง deploy ได้ตลอดเวลา** แต่ถ้าทุกคน push โค้ดที่ยังทำไม่เสร็จ หรือโค้ดที่ยังไม่ผ่านการทดสอบเข้า `main` โดยตรง ก็จะเกิดสถานการณ์ที่ `main` "พัง" อยู่บ่อยครั้ง ทำให้คนอื่นที่ pull โค้ดไปทำงานต่อได้รับผลกระทบไปด้วย

#### 5. ไม่มีร่องรอยการตัดสินใจ (Traceability)

เมื่อมีปัญหาเกิดขึ้นใน production ทีมจะต้องการรู้ว่า "โค้ดส่วนนี้ถูกเพิ่มเข้ามาเมื่อไหร่ ใครเป็นคนเขียน มีใครรีวิวหรือเปล่า ทำไมถึงถูก merge เข้ามา" ถ้าไม่มี workflow ที่มีขั้นตอน Pull Request/Code Review บันทึกไว้ คำถามเหล่านี้จะไม่มีคำตอบเลย

### ตัวอย่างสถานการณ์จริงที่มักเกิดขึ้น

```
09:14 - Alice push โค้ดฟีเจอร์ login เข้า main โดยตรง (ยังทดสอบไม่ครบ)
09:20 - Bob pull main มาพัฒนาต่อ แต่โค้ดของ Alice ทำให้ระบบ build ไม่ผ่าน
09:25 - Bob เสียเวลา 30 นาทีในการ debug ว่าทำไม build พัง
         (ทั้งที่ตัวเองไม่ได้แก้อะไรเลย)
09:55 - Carol push โค้ดอีกชิ้นทับการแก้ไขของ Bob บางส่วนโดยไม่รู้ตัว
         เพราะไม่ได้ pull ล่าสุดก่อน push
10:10 - เกิด merge conflict ขนาดใหญ่ที่ไม่มีใครอยากแตะ
10:30 - ทีม Standup เช้าเริ่มต้นด้วยการถกเถียงว่า "ใครทำ main พัง"
         แทนที่จะคุยเรื่องความคืบหน้าของงาน
```

สถานการณ์แบบนี้ **ไม่ใช่เรื่องสมมติ** แต่เป็นสิ่งที่เกิดขึ้นจริงกับทีมนับไม่ถ้วนที่ไม่มี workflow ที่ชัดเจน และยิ่งทีมมีขนาดใหญ่ขึ้น ความเสียหายก็ยิ่งทวีคูณ

### สิ่งที่ Workflow มาตรฐานช่วยแก้

| ปัญหาที่เกิดโดยไม่มี Workflow | สิ่งที่ Workflow มาตรฐานแก้ให้ |
|---|---|
| สับสนว่าใครทำอะไรอยู่ | แต่ละงานมี branch/PR ของตัวเองที่ติดตามได้ |
| Conflict เกิดบ่อยและซับซ้อน | แยกงานออกจากกันชัดเจน ลด overlap ของการแก้ไฟล์พร้อมกัน |
| คุณภาพโค้ดไม่สม่ำเสมอ | บังคับ Code Review ก่อน merge ทุกครั้ง |
| `main` ไม่เสถียร | โค้ดที่ยังไม่พร้อมจะไม่ถูก merge เข้า `main` |
| ไม่มี traceability | ทุกการเปลี่ยนแปลงมี PR, ผู้รีวิว, และเหตุผลบันทึกไว้ถาวร |

ตลอดเฟส 4 นี้ เราจะสำรวจ Workflow หลายแบบตั้งแต่แบบพื้นฐานที่สุดไปจนถึงแบบที่ซับซ้อนและใช้กันในองค์กรระดับโลก แต่ก่อนจะไปถึงจุดนั้น เราต้องเข้าใจโมเดลที่ "ง่ายที่สุด" ก่อน นั่นคือ **Centralized Workflow** ซึ่งเป็นจุดเริ่มต้นของทุกทีมที่เพิ่งเริ่มทำงานร่วมกัน

## Step 302: Centralized Workflow คืออะไร

### นิยาม

**Centralized Workflow** คือรูปแบบการทำงานร่วมกันแบบที่ **เรียบง่ายที่สุด** โดยมีหลักการสำคัญคือ:

> **สมาชิกทุกคนในทีม commit และ push การเปลี่ยนแปลงของตัวเอง ตรงไปยัง branch เดียว (โดยทั่วไปคือ `main` หรือ `master`) โดยไม่มีการสร้าง feature branch แยกต่างหาก**

ชื่อ "Centralized" มาจากแนวคิดที่คล้ายกับ Centralized VCS (เช่น SVN) ที่เราเคยเรียนใน Part 01 — คือมี **จุดศูนย์กลางเดียว (`main` branch)** ที่ทุกคนทำงานเข้า-ออกตลอดเวลา แม้ Git จะเป็น Distributed VCS โดยธรรมชาติ แต่ทีมสามารถ "เลือก" ใช้งานมันในสไตล์ centralized ก็ได้ ถ้าไม่สร้าง branch เพิ่ม

### ภาพรวมการทำงาน

```
                    ┌─────────────────────┐
                    │   origin (Remote)   │
                    │       main          │
                    └──────────┬──────────┘
              push/pull        │      push/pull
        ┌───────────────────────┼───────────────────────┐
        │                       │                        │
  ┌─────▼─────┐          ┌──────▼──────┐          ┌──────▼──────┐
  │  Alice     │          │    Bob      │          │   Carol     │
  │  (local    │          │  (local     │          │  (local     │
  │   main)    │          │   main)     │          │   main)     │
  └────────────┘          └─────────────┘          └─────────────┘
```

ทุกคนมี local `main` ของตัวเอง ทำงาน แก้ไฟล์ แล้ว push ตรงเข้า `origin/main` — ไม่มี branch อื่นเข้ามาเกี่ยวข้องเลย

### ขั้นตอนการทำงานทั่วไปใน Centralized Workflow

```bash
# 1. ดึงโค้ดล่าสุดจาก remote มาก่อนเริ่มงานเสมอ
git pull origin main

# 2. แก้ไขไฟล์ตามงานที่ได้รับมอบหมาย
#    (แก้ไฟล์ในโปรแกรมแก้ไขข้อความตามปกติ)

# 3. ตรวจสอบสถานะและเพิ่มไฟล์เข้า staging area
git status
git add .

# 4. Commit การเปลี่ยนแปลง
git commit -m "แก้ไขฟอร์ม login ให้ validate email"

# 5. ดึงโค้ดล่าสุดอีกครั้งก่อน push (เผื่อมีคนอื่น push ไปก่อน)
git pull origin main

# 6. ถ้ามี conflict ต้องแก้ไขให้เรียบร้อยตรงนี้ก่อน

# 7. Push ขึ้น remote
git push origin main
```

สังเกตว่า **ไม่มีขั้นตอนสร้าง branch ใหม่เลย** ทุกคนทำงานบน `main` โดยตรงตลอดเวลา

### เหมาะกับทีมขนาดไหน

Centralized Workflow เหมาะสมที่สุดกับสถานการณ์ต่อไปนี้:

1. **ทีมขนาดเล็กมาก (1–3 คน)** ที่รู้จักกันดี สื่อสารกันตลอดเวลา (เช่น นั่งห้องเดียวกัน หรือคุยกันใน chat แบบ real-time)
2. **โปรเจกต์ส่วนตัวหรือโปรเจกต์ทดลอง (side project, prototype, proof of concept)** ที่ไม่ต้องการความเป็นทางการมาก
3. **โปรเจกต์ที่มีการเปลี่ยนแปลงน้อยและไม่บ่อย** เช่น สคริปต์อัตโนมัติเล็ก ๆ ที่แก้ไขนาน ๆ ครั้ง
4. **ช่วงเริ่มต้นของโปรเจกต์ (early prototyping stage)** ที่โครงสร้างโค้ดยังไม่นิ่ง การสร้าง branch แยกอาจทำให้ overhead มากเกินความจำเป็น
5. **ทีมที่เพิ่งเริ่มเรียนรู้ Git** และยังไม่พร้อมรับความซับซ้อนของการจัดการหลาย branch พร้อมกัน

### ข้อดีของ Centralized Workflow

- **เรียบง่ายที่สุดในบรรดา Workflow ทั้งหมด** — เรียนรู้ได้เร็ว ไม่ต้องจำคำสั่งเยอะ
- **ไม่มี overhead ของการสร้าง/จัดการ branch** — ไม่ต้องเปิด Pull Request ทุกครั้งที่แก้โค้ดเล็ก ๆ น้อย ๆ
- **เห็นความเปลี่ยนแปลงของทุกคนได้ทันที** เพราะทุกคนทำงานบน branch เดียวกัน
- **เหมาะกับการทำงานที่ต้องการความเร็วสูงในทีมเล็กที่ไว้ใจกันมาก** เช่น hackathon หรือทีมพัฒนาฟีเจอร์ทดลองระยะสั้น

Centralized Workflow จึงไม่ใช่ "วิธีที่ผิด" หรือ "วิธีของมือใหม่" เสมอไป — มันเป็นเครื่องมือที่เหมาะสมกับบริบทหนึ่ง แต่ปัญหาจะเริ่มปรากฏชัดเมื่อทีมเติบโตขึ้น ซึ่งเราจะไปดูรายละเอียดกันใน Step ถัดไป

## Step 303: ข้อจำกัดของ Centralized Workflow เมื่อทีมโตขึ้น

Centralized Workflow ทำงานได้ดีมากตอนทีมมีขนาดเล็ก แต่เมื่อทีมเริ่มขยายตัว — จาก 3 คนเป็น 8 คน จาก 8 คนเป็น 20 คน — ข้อจำกัดที่ซ่อนอยู่จะเริ่มปรากฏชัดขึ้นเรื่อย ๆ

### 1. Conflict เกิดถี่ขึ้นแบบทวีคูณ ไม่ใช่แบบเชิงเส้น

ลองคิดในเชิงคณิตศาสตร์ง่าย ๆ: ถ้ามีนักพัฒนา `n` คนที่ทำงานพร้อมกันบน branch เดียว จำนวนคู่ของคนที่ **อาจจะแก้ไฟล์ทับกัน** ในช่วงเวลาเดียวกันคือ

```
จำนวนคู่ที่อาจชนกัน = n × (n - 1) / 2
```

| จำนวนคน (n) | จำนวนคู่ที่อาจชนกัน |
|---|---|
| 3 | 3 |
| 5 | 10 |
| 8 | 28 |
| 15 | 105 |
| 30 | 435 |

จะเห็นว่ายิ่งทีมโต จำนวน "จุดที่อาจเกิดการชนกัน" ไม่ได้โตแบบเป็นสัดส่วนตรง ๆ กับจำนวนคน แต่โตแบบยกกำลังสองโดยประมาณ เมื่อทุกคน push เข้า branch เดียวกันตลอดเวลา โอกาสที่ 2 คนจะแก้ไฟล์เดียวกัน หรือแก้ไฟล์คนละไฟล์แต่กระทบกันในเชิงตรรกะ (เช่น เปลี่ยน signature ของฟังก์ชันที่อีกคนกำลังเรียกใช้) จะสูงขึ้นมากอย่างเห็นได้ชัด

### 2. ไม่มีขั้นตอน Code Review ก่อน Merge

นี่คือข้อจำกัดที่ร้ายแรงที่สุดของ Centralized Workflow ในบริบททีมใหญ่ เมื่อไม่มี Pull Request หรือขั้นตอนตรวจสอบใด ๆ ก่อนที่โค้ดจะเข้า `main`:

- **บั๊กที่ควรถูกจับได้ตั้งแต่ต้น** กลับหลุดเข้า production เพราะไม่มีสายตาที่สองมาตรวจสอบ
- **ไม่มีการแชร์ความรู้ (knowledge sharing)** ระหว่างสมาชิกทีม เพราะไม่มีใครได้เห็นโค้ดของคนอื่นก่อน merge
- **มาตรฐานโค้ด (coding standard) ไม่สม่ำเสมอ** เพราะไม่มีจุดตรวจสอบที่บังคับให้ทุกคนเขียนโค้ดในรูปแบบเดียวกัน
- **ความปลอดภัย (security)** มีความเสี่ยงสูงขึ้น เพราะไม่มีใครตรวจสอบว่ามีการ commit ความลับ (secrets, API keys) เข้าไปในโค้ดโดยไม่ตั้งใจหรือไม่

### 3. `main` ไม่เสถียรบ่อยขึ้น

เมื่อคนจำนวนมาก push โค้ดที่ยังไม่สมบูรณ์เข้า `main` พร้อม ๆ กัน โอกาสที่ `main` จะอยู่ในสถานะ "ใช้งานไม่ได้ชั่วคราว" (build พัง, test ไม่ผ่าน) จะสูงขึ้นตามจำนวนคนที่ push ทำให้คนอื่นที่ pull โค้ดไปพัฒนาต่อ ได้รับผลกระทบตามไปด้วยอย่างต่อเนื่อง

### 4. งานคู่ขนานที่ไม่เกี่ยวข้องกันทำได้ยาก

สมมติทีมกำลังพัฒนา 2 ฟีเจอร์ใหญ่พร้อมกัน — ฟีเจอร์ A ยังไม่เสร็จสมบูรณ์และไม่พร้อม deploy แต่ฟีเจอร์ B เสร็จแล้วและพร้อม deploy วันนี้ ถ้าทั้งสองฟีเจอร์ถูก commit ปนกันอยู่ใน `main` เดียวกัน จะเป็นไปไม่ได้เลยที่จะ deploy เฉพาะฟีเจอร์ B โดยไม่รวมฟีเจอร์ A ที่ยังไม่เสร็จไปด้วย

### 5. ยากต่อการ Rollback แบบเจาะจง

ถ้าเกิดปัญหาขึ้นหลัง deploy และต้องการย้อนกลับเฉพาะการเปลี่ยนแปลงของฟีเจอร์ใดฟีเจอร์หนึ่ง การที่ commit ของหลายฟีเจอร์ปะปนกันอยู่ใน history เดียวกันแบบไม่มีโครงสร้าง ทำให้การหา commit ที่ต้องการ revert ทำได้ยากและเสี่ยงต่อการ revert ผิดจุด

### 6. ไม่มี "ประตูตรวจสอบคุณภาพ" อัตโนมัติ

ทีมที่โตขึ้นมักต้องการรัน automated test, linter, หรือ CI pipeline ก่อนที่โค้ดจะถูกรวมเข้า `main` แต่ Centralized Workflow ไม่มี "จุดหยุด" ตามธรรมชาติให้ pipeline เหล่านี้ทำงานก่อน merge เพราะโค้ดถูก push เข้า `main` โดยตรงทันที

### สรุปข้อจำกัด

| ข้อจำกัด | ผลกระทบที่ตามมา |
|---|---|
| Conflict เพิ่มขึ้นแบบทวีคูณ | เสียเวลาแก้ conflict บ่อยขึ้นเรื่อย ๆ |
| ไม่มี Code Review | คุณภาพโค้ดตกต่ำ บั๊กหลุด production |
| `main` ไม่เสถียร | ทีมทั้งหมดได้รับผลกระทบเมื่อมีคน push โค้ดพัง |
| งานคู่ขนานแยกกันไม่ได้ | Deploy บางส่วนโดยไม่รวมงานที่ยังไม่เสร็จทำไม่ได้ |
| Rollback เจาะจงยาก | เสี่ยง revert ผิดจุดหรือ revert มากเกินจำเป็น |
| ไม่มีจุดหยุดสำหรับ CI/CD | Quality gate อัตโนมัติทำงานไม่ได้ก่อน merge |

นี่คือเหตุผลว่าทำไมแทบทุกทีมที่มีขนาดเกิน 3–5 คน หรือทำงานกับโปรเจกต์ที่ต้อง deploy สู่ผู้ใช้จริง จึงเลือกย้ายจาก Centralized Workflow ไปสู่ **Feature Branch Workflow** ซึ่งเป็นก้าวถัดไปตามธรรมชาติ

## Step 304: Feature Branch Workflow คืออะไร

### แนวคิดหลัก

**Feature Branch Workflow** ตั้งอยู่บนหลักการที่เรียบง่ายแต่ทรงพลังมากข้อเดียว:

> **ห้าม commit หรือ push ตรงเข้า `main` โดยเด็ดขาด ทุกงาน ไม่ว่าจะเป็นฟีเจอร์ใหม่ การแก้บั๊ก หรือการปรับปรุงเล็กน้อย ต้องถูกพัฒนาบน branch แยกต่างหาก (feature branch) ก่อนเสมอ แล้วจึงขอรวมกลับเข้า `main` ผ่านกระบวนการตรวจสอบ**

นี่คือการเปลี่ยนกระบวนทัศน์ที่สำคัญที่สุดของการทำงานเป็นทีมด้วย Git — จาก "ทุกคนทำงานบนถนนเส้นเดียวกัน" ไปสู่ "แต่ละคนมีเลนของตัวเอง แล้วค่อยกลับเข้าสู่ถนนหลักเมื่อพร้อม"

### ภาพรวมการทำงาน

```
main:        A───B───────────────E───────────────H
                  \                   /
feature/login      C───D─────────────
                                          \
feature/checkout                          F───G
                                                \
                                                 (ยังไม่ merge)
```

จากภาพ:

- `main` เดินหน้าไปเรื่อย ๆ อย่างมั่นคง (commit A, B)
- เมื่อ Alice จะทำฟีเจอร์ login เธอแยก branch `feature/login` ออกจาก `main` ที่จุด B
- เธอ commit C, D บน branch ของเธอเอง โดยไม่กระทบ `main` เลย
- เมื่อฟีเจอร์เสร็จและผ่านการรีวิว จึง merge กลับเข้า `main` (จุด E)
- ในเวลาเดียวกัน Bob ก็สามารถทำงานบน `feature/checkout` คู่ขนานไปได้โดยไม่ชนกับงานของ Alice เลย

### ทำไมต้องแยก Branch — เปรียบเทียบกับโลกจริง

ลองเปรียบเทียบกับการเขียนหนังสือร่วมกันหลายคน:

- **แบบ Centralized:** ทุกคนแก้ไขเอกสารต้นฉบับไฟล์เดียวกันพร้อมกันตลอดเวลา ใครพิมพ์ก่อนพิมพ์ทับ ยากที่จะรู้ว่าใครแก้อะไรตรงไหน
- **แบบ Feature Branch:** แต่ละคนคัดลอกบทที่ตัวเองรับผิดชอบไปแก้ต่างหาก เขียนเสร็จแล้วส่งให้บรรณาธิการ (reviewer) ตรวจก่อน แล้วจึงนำกลับไปรวมเข้าต้นฉบับหลักอย่างเป็นระบบ

### หลักการสำคัญ 3 ข้อของ Feature Branch Workflow

#### 1. `main` เป็น "ของศักดิ์สิทธิ์" — ต้อง deployable เสมอ

ไม่ว่าจะเปิดดู `main` เวลาไหนก็ตาม โค้ดใน `main` ควรอยู่ในสถานะที่ build ผ่าน ทดสอบผ่าน และพร้อม deploy ได้ทันทีเสมอ

#### 2. หนึ่ง Branch ต่อหนึ่งงานที่ชัดเจน

แต่ละ feature branch ควรมีขอบเขตงานที่ชัดเจนและจำกัด (ไม่ใช่ branch เดียวทำหลายฟีเจอร์ปนกัน) เพื่อให้ง่ายต่อการรีวิวและ merge

#### 3. ทุก Branch ต้องผ่านกระบวนการตรวจสอบก่อนกลับเข้า `main`

โดยทั่วไปคือผ่าน **Pull Request (PR)** ที่มีคนอื่นในทีมรีวิวโค้ด และ/หรือผ่าน automated test ก่อนที่จะได้รับอนุญาตให้ merge

### รูปแบบการตั้งชื่อ Branch ที่นิยมใช้

ทีมส่วนใหญ่จะตั้งชื่อ branch ตามรูปแบบ `<ประเภทงาน>/<คำอธิบายสั้น ๆ>` เพื่อให้เข้าใจตรงกันทันทีว่า branch นี้ทำอะไร:

| ประเภท Prefix | ใช้เมื่อ | ตัวอย่าง |
|---|---|---|
| `feature/` | พัฒนาฟีเจอร์ใหม่ | `feature/user-login` |
| `bugfix/` หรือ `fix/` | แก้บั๊กที่ไม่เร่งด่วนมาก | `bugfix/fix-null-pointer-checkout` |
| `hotfix/` | แก้บั๊กเร่งด่วนที่ต้อง deploy ทันที | `hotfix/payment-gateway-crash` |
| `chore/` | งานบำรุงรักษา ไม่กระทบฟีเจอร์ (อัปเดต dependency, ปรับ config) | `chore/upgrade-node-version` |
| `refactor/` | ปรับโครงสร้างโค้ดโดยไม่เปลี่ยนพฤติกรรม | `refactor/extract-payment-service` |
| `docs/` | แก้ไขเอกสาร | `docs/update-readme-setup-guide` |

การตั้งชื่อที่เป็นระบบแบบนี้ทำให้ทุกคนในทีม เพียงแค่มองรายชื่อ branch ก็รู้ทันทีว่ามีงานอะไรกำลังดำเนินอยู่บ้าง โดยไม่ต้องถามใคร

### คำสั่งพื้นฐานในการสร้าง Feature Branch

```bash
# ตรวจสอบว่าอยู่ที่ main และเป็นเวอร์ชันล่าสุด
git checkout main
git pull origin main

# สร้าง branch ใหม่สำหรับฟีเจอร์ และสลับเข้าไปทำงานทันที
git checkout -b feature/user-login

# หรือใช้คำสั่งรุ่นใหม่กว่า
git switch -c feature/user-login
```

Feature Branch Workflow จึงไม่ใช่แค่ "เทคนิคการใช้คำสั่ง Git" แต่เป็น **วินัยการทำงานของทั้งทีม** ที่ต้องตกลงร่วมกันและปฏิบัติตามอย่างสม่ำเสมอ ใน Step ถัดไปเราจะไล่ดูขั้นตอนเต็มรูปแบบตั้งแต่ต้นจนจบว่า Feature Branch Workflow ทำงานอย่างไรในทางปฏิบัติจริง

## Step 305: ขั้นตอนเต็มของ Feature Branch Workflow

มาดูขั้นตอนแบบละเอียดทีละขั้น ตั้งแต่เริ่มงานจนถึงโค้ดถูก merge เข้า `main` เรียบร้อย โดยใช้ตัวอย่างสมมติว่า Alice ได้รับมอบหมายให้พัฒนาฟีเจอร์ "เพิ่มปุ่ม Reset Password"

### ขั้นตอนที่ 1: อัปเดต Local Main ให้เป็นเวอร์ชันล่าสุด

```bash
git checkout main
git pull origin main
```

**เหตุผลสำคัญ:** ต้องแยก branch ใหม่จากจุดล่าสุดของ `main` เสมอ ไม่ใช่จากเวอร์ชันเก่าที่ค้างอยู่ในเครื่อง ไม่เช่นนั้นจะพลาดการเปลี่ยนแปลงล่าสุดที่เพื่อนร่วมทีมคนอื่น merge เข้าไปแล้ว

### ขั้นตอนที่ 2: สร้าง Feature Branch ใหม่

```bash
git checkout -b feature/reset-password
```

ตอนนี้ Alice อยู่บน branch ใหม่ที่แยกออกมาจาก `main` แล้ว การเปลี่ยนแปลงใด ๆ ที่เธอทำต่อจากนี้จะไม่กระทบ `main` เลย

### ขั้นตอนที่ 3: พัฒนาโค้ดและ Commit เป็นระยะ

```bash
# แก้ไฟล์ที่เกี่ยวข้อง เช่น สร้างฟอร์ม, เขียน API endpoint

git add src/components/ResetPasswordForm.jsx
git commit -m "เพิ่มฟอร์ม UI สำหรับ reset password"

# ทำงานต่อ แล้ว commit เป็นชิ้นเล็ก ๆ ที่มีความหมายในตัวเอง
git add src/api/authApi.js
git commit -m "เพิ่ม API endpoint สำหรับส่งอีเมล reset password"

git add src/tests/resetPassword.test.js
git commit -m "เพิ่ม unit test ครอบคลุม flow reset password"
```

**หลักปฏิบัติที่ดี:** ควร commit บ่อย ๆ เป็นชิ้นเล็ก ๆ ที่มีความหมายชัดเจนในตัวเอง (atomic commit) แทนที่จะรวบทุกอย่างเป็น commit เดียวตอนจบงาน เพราะช่วยให้ประวัติอ่านง่าย และย้อนกลับเฉพาะจุดได้ถ้าจำเป็น

### ขั้นตอนที่ 4: Push Branch ขึ้น Remote

```bash
git push -u origin feature/reset-password
```

แฟลก `-u` (ย่อจาก `--set-upstream`) ทำให้ครั้งต่อไปสามารถพิมพ์แค่ `git push` เฉย ๆ ได้โดยไม่ต้องระบุชื่อ remote/branch ซ้ำอีก

### ขั้นตอนที่ 5: อัปเดต Branch ให้ทันกับ Main ระหว่างทำงาน (ถ้าใช้เวลานาน)

หากงานนี้ใช้เวลาหลายวัน และระหว่างนั้นมีคนอื่น merge งานเข้า `main` เพิ่ม ควรดึงการเปลี่ยนแปลงเหล่านั้นเข้ามาสม่ำเสมอ เพื่อลดความเสี่ยงที่ conflict จะสะสมจนแก้ยากตอนท้าย (รายละเอียดเรื่องนี้จะพูดถึงเจาะลึกใน Step 307):

```bash
git checkout main
git pull origin main
git checkout feature/reset-password
git merge main
# หรือใช้ git rebase main (จะเรียนละเอียดใน Part ถัดไปเรื่อง Rebase)
```

### ขั้นตอนที่ 6: เปิด Pull Request (PR)

เมื่องานเสร็จสมบูรณ์และ push ขึ้น remote แล้ว Alice เข้าไปที่ GitHub แล้วเปิด Pull Request จาก `feature/reset-password` เข้าสู่ `main` โดยระบุ:

- **หัวข้อ (Title)** ที่สื่อความหมายชัดเจน เช่น "เพิ่มฟีเจอร์ Reset Password ผ่านอีเมล"
- **คำอธิบาย (Description)** ว่าทำอะไร ทำไมต้องทำ ทดสอบอย่างไรบ้าง
- **เชื่อมโยงกับ Issue หรือ Ticket** ที่เกี่ยวข้อง (ถ้ามี)

### ขั้นตอนที่ 7: กระบวนการ Code Review

```
Alice เปิด PR  ──▶  ทีมได้รับแจ้งเตือน  ──▶  Bob และ Carol เข้ามารีวิว
                                                      │
                          ┌───────────────────────────┴──────────────────────┐
                          │                                                  │
                    พบปัญหา/ขอแก้ไข                                    ผ่านการรีวิว
                          │                                                  │
              Alice แก้โค้ดเพิ่ม + commit ใหม่ + push                approve PR
                          │                                                  │
                          └───────────────▶  วนกลับไปให้รีวิวอีกครั้ง          ▼
                                                                        พร้อม merge
```

ในระหว่างการรีวิว ผู้รีวิวอาจ comment ขอให้แก้ไขจุดต่าง ๆ เช่น "ควรเพิ่ม validation ตรงนี้" หรือ "ตัวแปรนี้ตั้งชื่อไม่สื่อความหมาย" — Alice แก้ไขแล้ว commit และ push เพิ่มเข้า branch เดิม ซึ่งจะไปปรากฏใน PR เดิมโดยอัตโนมัติ ไม่ต้องเปิด PR ใหม่

### ขั้นตอนที่ 8: Merge เข้า Main

เมื่อ PR ได้รับการ approve และ (ถ้ามีการตั้งค่าไว้) ผ่าน automated CI checks ทั้งหมดแล้ว จะสามารถกด Merge ผ่านหน้าเว็บ GitHub ได้ ซึ่งมักมีตัวเลือกหลายแบบ:

- **Merge commit** — รวม branch เข้ามาพร้อมสร้าง commit ใหม่ที่บันทึกว่าเป็นการ merge (เก็บประวัติ branch ไว้ครบ)
- **Squash and merge** — รวมทุก commit ใน branch เป็น commit เดียวก่อน merge เข้า `main` (ทำให้ history ของ `main` สะอาด อ่านง่าย)
- **Rebase and merge** — นำ commit ทั้งหมดจาก branch ไปเรียงต่อท้าย `main` โดยไม่มี merge commit เลย

(รายละเอียดเชิงลึกของแต่ละแบบจะอธิบายอย่างละเอียดใน Part ที่ว่าด้วย Merge Strategies โดยเฉพาะ)

### ขั้นตอนที่ 9: ลบ Feature Branch ที่ merge เสร็จแล้ว

```bash
# ลบ branch บน remote (มักมีปุ่มให้กดบน GitHub หลัง merge ได้เลย)
git push origin --delete feature/reset-password

# ลบ branch บนเครื่อง local ของตัวเอง
git branch -d feature/reset-password
```

การลบ branch ที่ merge เสร็จแล้วช่วยให้รายชื่อ branch ในโปรเจกต์ไม่รกและสับสน

### ขั้นตอนที่ 10: อัปเดต Local Main ให้ตรงกับ Remote

```bash
git checkout main
git pull origin main
```

ตอนนี้ Alice พร้อมเริ่มงานชิ้นถัดไปแล้ว โดยเริ่มจาก `main` เวอร์ชันล่าสุดที่มีฟีเจอร์ของเธอรวมอยู่ด้วย

### สรุปขั้นตอนทั้งหมดในภาพเดียว

```
pull main → สร้าง branch → commit หลายครั้ง → push branch
   → เปิด PR → code review (วนซ้ำถ้าต้องแก้ไข) → merge เข้า main
      → ลบ branch → pull main ใหม่ → เริ่มงานถัดไป
```

นี่คือวงจรการทำงานมาตรฐานที่ทีมนับล้านทีมทั่วโลกใช้ทุกวัน และเป็นพื้นฐานสำคัญที่คุณจะต้องคุ้นเคยให้ได้อย่างเป็นธรรมชาติก่อนไปเรียน Workflow ที่ซับซ้อนกว่านี้ในเฟส 4

## Step 306: ข้อดีของ Feature Branch Workflow

หลังจากเห็นขั้นตอนเต็มรูปแบบแล้ว มาสรุปกันว่าทำไม Feature Branch Workflow ถึงเป็นที่นิยมและได้รับการยอมรับอย่างกว้างขวางในอุตสาหกรรม

### 1. Isolation — แยกงานออกจากกันอย่างสมบูรณ์

แต่ละฟีเจอร์พัฒนาอยู่ใน "พื้นที่ของตัวเอง" โดยไม่กระทบงานของคนอื่น นักพัฒนาแต่ละคนสามารถทดลอง แก้ไข หรือแม้แต่ทำโค้ดพังชั่วคราวบน branch ของตัวเองได้อย่างอิสระ โดยไม่ส่งผลกระทบต่อใครเลย จนกว่าจะพร้อม merge

### 2. บังคับให้มี Code Review ก่อน Merge เสมอ

นี่คือประโยชน์ที่สำคัญที่สุด — การที่ทุกงานต้องผ่าน Pull Request หมายความว่า **จะมีสายตาอย่างน้อยหนึ่งคู่มาตรวจสอบโค้ดก่อนที่มันจะเข้าสู่ `main`** ซึ่งช่วยได้หลายด้าน:

- จับบั๊กได้ตั้งแต่ก่อนเข้า production
- แชร์ความรู้ระหว่างสมาชิกทีม (ทุกคนได้เห็นโค้ดของทุกคน)
- รักษามาตรฐานโค้ดให้สม่ำเสมอทั้งโปรเจกต์
- เป็นโอกาสสอนงานให้นักพัฒนาที่มีประสบการณ์น้อยกว่า

### 3. `main` สะอาดและ Deployable เสมอ

เพราะไม่มีใคร push ตรงเข้า `main` โค้ดใน `main` จึงมักผ่านการตรวจสอบและทดสอบมาแล้วเสมอ ทำให้ทีมสามารถ deploy จาก `main` ได้ทุกเมื่อโดยไม่ต้องกังวลว่าจะมีโค้ดที่ยังทำไม่เสร็จปะปนอยู่

### 4. รองรับงานคู่ขนานได้อย่างแท้จริง

ทีมสามารถพัฒนาหลายฟีเจอร์พร้อมกันได้โดยไม่ชนกัน แต่ละฟีเจอร์อยู่ใน branch ของตัวเอง พร้อม merge เมื่อไหร่ก็ได้ตามความพร้อม ไม่ต้องรอให้ฟีเจอร์อื่นเสร็จก่อน

### 5. CI/CD Pipeline ทำงานได้อย่างมีประสิทธิภาพ

ระบบ Continuous Integration สามารถรันชุดทดสอบอัตโนมัติ (automated test), linter, และ security scan บน **แต่ละ Pull Request** ก่อนอนุญาตให้ merge ได้ ทำให้เกิด "ประตูคุณภาพ" (quality gate) ที่แข็งแรงกว่ามาก เมื่อเทียบกับการตรวจสอบหลังจากโค้ดเข้า `main` ไปแล้ว

### 6. Rollback ทำได้แม่นยำและปลอดภัยกว่า

เมื่อแต่ละฟีเจอร์ถูก merge เป็นก้อนที่ชัดเจน (โดยเฉพาะถ้าใช้ squash merge) การ revert เฉพาะฟีเจอร์ที่มีปัญหาสามารถทำได้ง่ายด้วยคำสั่งเดียว โดยไม่กระทบฟีเจอร์อื่นที่ merge เข้ามาในเวลาใกล้เคียงกัน

### 7. ประวัติของโปรเจกต์อ่านง่ายและมีความหมาย

Pull Request แต่ละอันกลายเป็นบันทึกถาวรของ "เหตุผลที่การเปลี่ยนแปลงนี้เกิดขึ้น" — มีการพูดคุย มีข้อโต้แย้ง มีเหตุผลประกอบการตัดสินใจ ซึ่งมีคุณค่ามหาศาลเมื่อต้องย้อนกลับมาดูในอีกหลายเดือนหรือหลายปีให้หลัง

### 8. ลดความเสี่ยงเมื่อทำงานกับ Production จริง

เพราะ `main` มักถูกใช้เป็นจุดอ้างอิงสำหรับ deploy ไปยัง production การรักษาให้ `main` สะอาดและผ่านการตรวจสอบเสมอ จึงเท่ากับลดความเสี่ยงของการนำโค้ดที่มีปัญหาไปสู่ผู้ใช้จริงโดยตรง

### ตารางสรุปข้อดี

| ด้าน | ประโยชน์ที่ได้ |
|---|---|
| การทำงาน | แยกงานเป็นอิสระ ทำคู่ขนานได้จริง |
| คุณภาพโค้ด | มี Code Review บังคับ จับบั๊กได้ก่อนเข้า production |
| เสถียรภาพ | `main` deployable เสมอ |
| อัตโนมัติ | CI/CD รันตรวจสอบได้ต่อ PR |
| ความปลอดภัย | ลดความเสี่ยงจากโค้ดที่ยังไม่พร้อม |
| การย้อนกลับ | Rollback เฉพาะจุดได้แม่นยำ |
| การเรียนรู้ | สมาชิกทีมแชร์ความรู้ผ่านการรีวิว |
| ประวัติโปรเจกต์ | มีบริบทและเหตุผลของทุกการเปลี่ยนแปลง |

แม้ Feature Branch Workflow จะมีข้อดีมากมาย แต่มันก็ไม่ได้สมบูรณ์แบบ 100% — มีปัญหาสำคัญอย่างหนึ่งที่ทีมจำนวนมากเจอเมื่อใช้ Workflow นี้ นั่นคือปัญหาจาก **Long-lived Branch** ซึ่งเราจะไปดูกันใน Step ถัดไป

## Step 307: ปัญหาที่อาจเกิดขึ้นจาก Long-lived Branch

### ปัญหาคืออะไร

**Long-lived branch** คือ feature branch ที่ถูกสร้างขึ้นมาแล้ว "อยู่นาน" โดยไม่ถูก merge กลับเข้า `main` สักที — อาจเป็นเพราะฟีเจอร์มีความซับซ้อนสูง ใช้เวลาพัฒนาหลายสัปดาห์หรือหลายเดือน หรือเพราะทีมยุ่งจนไม่มีเวลารีวิว PR

### ทำไม Long-lived Branch ถึงเป็นปัญหา

ในขณะที่ feature branch หนึ่งค้างอยู่นาน ๆ โดยไม่ merge, `main` ก็ยังคงเดินหน้าต่อไปเรื่อย ๆ จากการที่เพื่อนร่วมทีมคนอื่น merge งานของพวกเขาเข้ามาเรื่อย ๆ

```
main:                A───B───C───D───E───F───G───H  (main เดินหน้าเรื่อย ๆ)
                          \
feature/big-redesign      X───Y───Z──────────────── (แยกออกมานานแล้วไม่เคย sync)
                          (สร้างจาก B)
```

จากภาพ `feature/big-redesign` ถูกแยกออกมาจาก `main` ที่จุด B แต่ตอนนี้ `main` เดินหน้าไปถึง H แล้ว ในขณะที่ branch นี้ยังคง "ค้าง" อยู่ที่จุด B และมี commit ของตัวเองเพิ่มมา (X, Y, Z)

### ผลกระทบที่ตามมา

#### 1. ความแตกต่างระหว่าง Branch สะสมมากขึ้นเรื่อย ๆ

ยิ่งเวลาผ่านไปนาน จำนวนการเปลี่ยนแปลงที่ต่างกันระหว่าง `feature/big-redesign` กับ `main` ก็ยิ่งมากขึ้น ทำให้ตอนที่ในที่สุดต้อง merge กัน จะเจอ **merge conflict จำนวนมหาศาล** ที่แก้ยากกว่าปกติหลายเท่า เพราะต้องพิจารณาความเปลี่ยนแปลงสะสมจากหลายสิบ commit พร้อมกัน

#### 2. Conflict ซับซ้อนขึ้นแบบไม่เป็นเชิงเส้น

การแก้ conflict ของการเปลี่ยนแปลง 5 commit กับการเปลี่ยนแปลง 50 commit ไม่ได้ใช้ความพยายามต่างกันแค่ 10 เท่า แต่มักจะซับซ้อนกว่ามากเพราะการเปลี่ยนแปลงหลาย ๆ จุดมักเกี่ยวโยงกันในเชิงตรรกะ (โครงสร้างไฟล์เปลี่ยน ฟังก์ชันถูก rename เปลี่ยน API) ทำให้การแก้ conflict แต่ละจุดต้องเข้าใจบริบทที่กว้างขึ้นมาก

#### 3. เสี่ยงต่อการทำงานซ้ำซ้อนกับเพื่อนร่วมทีม

ในขณะที่ branch ยาวนี้กำลังพัฒนาอยู่ อาจมีเพื่อนร่วมทีมคนอื่นแก้ไขโค้ดในส่วนเดียวกันไปแล้วใน `main` โดยที่เจ้าของ branch ไม่รู้ตัว ทำให้เมื่อถึงเวลา merge อาจพบว่างานบางส่วนที่ทำไปแล้วซ้ำซ้อนหรือขัดแย้งกับสิ่งที่มีอยู่แล้วใน `main`

#### 4. Feedback จาก Code Review มาช้าเกินไป

ถ้า branch ถูกซ่อนไว้นานโดยไม่เปิด PR ให้คนอื่นเห็นความคืบหน้า ปัญหาเชิงสถาปัตยกรรมหรือแนวทางที่ผิดพลาดอาจไม่ถูกจับได้จนกว่าจะสายเกินไป — ถ้ารีวิวเจอปัญหาใหญ่ตอนที่งานเสร็จไปแล้ว 90% การแก้ไขจะเสียเวลาและต้นทุนสูงกว่ารีวิวตั้งแต่ 10% มาก

#### 5. Merge วันสุดท้ายกลายเป็น "วันแห่งความเจ็บปวด"

ทีมจำนวนมากเจอสถานการณ์ที่เรียกกันติดตลกว่า **"Merge Hell"** — วันที่ทุกคนต้องมานั่งแก้ conflict ร่วมกันหลายชั่วโมงหรือข้ามวัน เพราะปล่อยให้หลาย branch แยกออกจาก `main` ไปไกลเกินไปพร้อมกัน

### วิธีป้องกันและบรรเทาปัญหา

#### 1. ทำ Branch ให้มีอายุสั้นที่สุดเท่าที่จะทำได้

หลักการทองคำของ Feature Branch ที่ดีคือ: **branch ควรมีอายุเป็นชั่วโมงหรือเป็นวัน ไม่ใช่เป็นสัปดาห์หรือเป็นเดือน** ถ้าฟีเจอร์ใหญ่เกินกว่าจะทำเสร็จในไม่กี่วัน ควรพิจารณาแตกงานออกเป็นชิ้นย่อยที่ merge เข้า `main` ได้เร็วขึ้น

#### 2. Sync กับ `main` บ่อย ๆ ระหว่างทำงาน

อย่ารอจนงานเสร็จทั้งหมดแล้วค่อย sync กับ `main` ครั้งเดียว ควรดึงการเปลี่ยนแปลงล่าสุดจาก `main` เข้ามาสม่ำเสมอ (เช่น ทุกวัน หรืออย่างน้อยสัปดาห์ละหลายครั้ง) เพื่อแก้ conflict ทีละน้อยตลอดทาง แทนที่จะเจอ conflict ก้อนใหญ่ตอนจบ

```bash
# วิธีที่ 1: merge main เข้า feature branch เป็นระยะ
git checkout feature/big-redesign
git merge main

# วิธีที่ 2: rebase feature branch ทับ main ล่าสุด
# (จะอธิบายรายละเอียดเชิงลึกใน Part ที่ว่าด้วย Rebase โดยเฉพาะ)
git checkout feature/big-redesign
git rebase main
```

#### 3. ใช้ Feature Flag แทนการแยก Branch ยาว

สำหรับฟีเจอร์ใหญ่ที่ยังไม่พร้อมเปิดใช้งานจริง แต่โค้ดพร้อม merge เข้า `main` แล้ว หลายทีมเลือกใช้เทคนิค **Feature Flag** (หรือ Feature Toggle) — merge โค้ดเข้า `main` ตั้งแต่เนิ่น ๆ แต่ควบคุมด้วยเงื่อนไข (flag) ว่าจะเปิดใช้งานฟีเจอร์นั้นให้ผู้ใช้เห็นหรือไม่ วิธีนี้ทำให้ `main` ไม่ต้องรอฟีเจอร์เสร็จ 100% ก่อน merge

#### 4. แตกงานใหญ่เป็น Pull Request ย่อยหลายอัน

แทนที่จะทำฟีเจอร์ทั้งหมดใน branch เดียวก้อนใหญ่ ให้แบ่งงานออกเป็นขั้นตอนย่อยที่แต่ละขั้นตอน merge เข้า `main` ได้อย่างปลอดภัยด้วยตัวเอง (เช่น แยก PR สำหรับ "สร้างโครงสร้างข้อมูล" ออกจาก PR ของ "สร้าง UI" ออกจาก PR ของ "เชื่อมต่อ API")

#### 5. ตั้งเป้าหมายเชิงวัฒนธรรมทีม: "Merge บ่อย Merge เล็ก"

หลักการนี้เป็นรากฐานสำคัญของแนวคิดที่เรียกว่า **Trunk-Based Development** ซึ่งเป็น Workflow ขั้นสูงกว่าที่เราจะเรียนอย่างละเอียดในภายหลังของเฟส 4 — แต่หลักการเบื้องต้นสามารถนำมาใช้ได้ตั้งแต่ตอนนี้แล้ว

### สรุปสัญญาณเตือนว่า Branch กำลังมีปัญหา

| สัญญาณเตือน | ควรทำอย่างไร |
|---|---|
| Branch อายุเกิน 1 สัปดาห์ยังไม่ merge | พิจารณาแบ่งงานเป็นชิ้นเล็กลง |
| `git diff main...feature-branch` แสดงไฟล์เปลี่ยนแปลงมากกว่า 20-30 ไฟล์ | อาจกำลังทำหลายเรื่องปนกันใน branch เดียว |
| ไม่เคย sync กับ `main` เลยตั้งแต่สร้าง branch | รีบ merge/rebase main เข้ามาทันที |
| PR เปิดค้างไว้เกิน 3-5 วันไม่มีคนรีวิว | ทวงถามหรือ escalate ให้ทีมช่วยรีวิว |

## Step 308: การเลือก Workflow ให้เหมาะกับทีม

ไม่มี Workflow ใด "ดีที่สุด" ในทุกสถานการณ์ — การเลือกใช้ Workflow ที่เหมาะสมต้องพิจารณาจากบริบทของทีมและโปรเจกต์อย่างรอบด้าน มาดูปัจจัยสำคัญที่ควรนำมาพิจารณา

### ปัจจัยที่ 1: ขนาดของทีม

| ขนาดทีม | Workflow ที่แนะนำ | เหตุผล |
|---|---|---|
| 1 คน | Centralized (หรือแม้แต่ไม่ต้องมี workflow เป็นทางการ) | ไม่มีใครมาชนกันอยู่แล้ว |
| 2–4 คน | Centralized (ถ้าสื่อสารกันดี) หรือ Feature Branch แบบเบา ๆ | ยังจัดการ conflict ด้วยการคุยกันตรง ๆ ได้ |
| 5–15 คน | Feature Branch Workflow | เริ่มจำเป็นต้องมี Code Review และแยกงานชัดเจน |
| 15+ คน | Feature Branch Workflow + Git Flow/GitHub Flow ที่เป็นทางการมากขึ้น | ต้องการโครงสร้างที่ชัดเจนกว่าเพื่อจัดการความซับซ้อน |

### ปัจจัยที่ 2: ความถี่ในการ Release

- **Release บ่อยมาก (Continuous Deployment หลายครั้งต่อวัน):** ต้องการ Workflow ที่ branch มีอายุสั้นมาก เช่น **Trunk-Based Development** หรือ **GitHub Flow** ที่เน้น merge เข้า `main` บ่อย ๆ และ deploy ทันทีหลัง merge
- **Release เป็นรอบ (เช่น ทุก 2 สัปดาห์ หรือทุกเดือน):** **Git Flow** ที่มี branch แยกสำหรับเตรียม release (`release/`) เหมาะสมกว่า เพราะมีเวลาให้ทดสอบก่อนปล่อยจริง
- **Release ไม่บ่อย (เช่น ซอฟต์แวร์ enterprise ที่ปล่อยปีละไม่กี่ครั้ง):** อาจต้องการ branch ระยะยาวสำหรับแต่ละเวอร์ชัน (เช่น `release/v2.0`, `release/v3.0`) ควบคู่กับ Feature Branch Workflow

### ปัจจัยที่ 3: ระดับประสบการณ์ของทีม

- ทีมที่ **เพิ่งเริ่มใช้ Git** ควรเริ่มจาก Workflow ที่เรียบง่ายก่อน (Centralized หรือ Feature Branch แบบพื้นฐาน) แล้วค่อยขยับไปใช้ Workflow ที่ซับซ้อนขึ้นเมื่อทีมคุ้นเคยมากขึ้น
- ทีมที่ **มีประสบการณ์สูง** สามารถรับมือกับ Workflow ที่ซับซ้อนกว่า เช่น Git Flow ที่มีหลายประเภท branch พร้อมกัน (feature, release, hotfix, develop) ได้โดยไม่สับสน
- การนำ Workflow ที่ซับซ้อนเกินไปมาใช้กับทีมที่ยังไม่พร้อม มักสร้างความสับสนมากกว่าประโยชน์ที่ได้

### ปัจจัยที่ 4: ระดับความเสี่ยงและความสำคัญของโปรเจกต์

- โปรเจกต์ที่กระทบผู้ใช้จำนวนมาก หรือเกี่ยวข้องกับเงิน/ข้อมูลสำคัญ (เช่น ระบบธนาคาร ระบบสุขภาพ) ควรมีขั้นตอนตรวจสอบที่เข้มงวดกว่า เช่น บังคับ Code Review อย่างน้อย 2 คน, บังคับผ่าน automated test ครบ 100% ก่อน merge
- โปรเจกต์ทดลองหรือ internal tool ความเสี่ยงต่ำ สามารถใช้ Workflow ที่เบากว่าได้โดยไม่มีปัญหา

### ปัจจัยที่ 5: ลักษณะของทีมที่กระจายตัวทางภูมิศาสตร์/เวลา

ทีมที่ทำงานคนละ time zone (เช่น ทีมกระจายในหลายประเทศ) มักได้ประโยชน์มากจาก Feature Branch Workflow เพราะแต่ละคนทำงานเป็นอิสระตาม time zone ของตัวเองได้ แล้วค่อยมารีวิวและ merge กันแบบ asynchronous (ไม่ต้องออนไลน์พร้อมกัน)

### แนวทางตัดสินใจแบบง่าย (Decision Guide)

ลองถามตัวเองตามลำดับคำถามนี้:

1. **ทีมมีมากกว่า 3 คนไหม?**
   - ไม่ → พิจารณา Centralized Workflow ได้ (ถ้าสื่อสารกันดี)
   - ใช่ → ไปข้อถัดไป

2. **โปรเจกต์นี้จะมีคนอื่นมาช่วยดูแลต่อในอนาคต หรือต้องรักษาคุณภาพโค้ดระยะยาวไหม?**
   - ไม่สำคัญมาก → Centralized ยังพอไหว
   - สำคัญ → ต้องใช้ Feature Branch Workflow เป็นอย่างน้อย

3. **ทีมต้องการ Release บ่อยแค่ไหน?**
   - บ่อยมาก (รายวัน/หลายครั้งต่อวัน) → พิจารณา GitHub Flow / Trunk-Based Development
   - เป็นรอบ (รายสัปดาห์/รายเดือน) → พิจารณา Git Flow
   - ไม่บ่อย → Feature Branch Workflow พื้นฐานก็เพียงพอ

4. **ทีมมีประสบการณ์กับ Git มากน้อยแค่ไหน?**
   - น้อย → เริ่มจาก Feature Branch Workflow แบบพื้นฐานก่อน
   - มาก → พร้อมรับ Workflow ที่ซับซ้อนกว่าได้

### ข้อคิดสำคัญ: Workflow ปรับเปลี่ยนได้ตามเวลา

ไม่มีทีมไหนต้องยึดติดกับ Workflow เดียวตลอดไป เมื่อทีมเติบโตขึ้น จำนวน release เปลี่ยนไป หรือลักษณะโปรเจกต์เปลี่ยนไป ทีมสามารถ **ปรับ Workflow ให้เข้ากับสถานการณ์ใหม่ได้เสมอ** สิ่งสำคัญคือทุกคนในทีมต้องเข้าใจตรงกันว่า ณ ตอนนี้ทีมใช้ Workflow แบบไหน และปฏิบัติตามกติกาเดียวกันอย่างสม่ำเสมอ

## Step 309: ตารางเปรียบเทียบ Centralized vs Feature Branch Workflow แบบละเอียด

มาสรุปทุกแง่มุมของทั้งสอง Workflow ในตารางเปรียบเทียบแบบครบถ้วน เพื่อให้เห็นภาพชัดเจนในการอ้างอิงกลับมาดูภายหลัง

### ตารางเปรียบเทียบหลัก

| มิติการเปรียบเทียบ | Centralized Workflow | Feature Branch Workflow |
|---|---|---|
| **แนวคิดหลัก** | ทุกคน commit ตรงเข้า `main` | แต่ละงานแยก branch ของตัวเอง |
| **ความซับซ้อนในการเรียนรู้** | ต่ำมาก — ใช้แค่ `pull`, `commit`, `push` | ปานกลาง — ต้องเข้าใจ branch, merge, PR |
| **ขนาดทีมที่เหมาะสม** | 1–4 คน | 5 คนขึ้นไป (แต่ใช้กับทีมเล็กก็ได้) |
| **Code Review ก่อน Merge** | ไม่มีโดยธรรมชาติ | มีผ่านกระบวนการ Pull Request |
| **ความเสถียรของ `main`** | ผันผวน อาจพังได้บ่อย | มั่นคง เพราะผ่านการตรวจสอบก่อนเข้า |
| **ความถี่ของ Merge Conflict** | สูง (ทุกคนชนกันที่จุดเดียว) | ต่ำกว่า (แยกกันทำงานคนละ branch) | 
| **ความรุนแรงของ Conflict เมื่อเกิดขึ้น** | มักเล็กเพราะเจอบ่อยและแก้ทันที | อาจใหญ่ถ้าปล่อย branch ไว้นาน (long-lived) |
| **รองรับงานคู่ขนานหลายฟีเจอร์** | ทำได้ยาก งานปนกันหมด | ทำได้ดี แต่ละฟีเจอร์แยกอิสระ |
| **การ Rollback เฉพาะจุด** | ยาก เพราะ commit ปนกัน | ง่ายกว่า โดยเฉพาะถ้าใช้ squash merge |
| **รองรับ CI/CD Quality Gate** | จำกัด (ตรวจได้แค่หลัง push แล้ว) | ดี (ตรวจได้ก่อน merge ทุก PR) |
| **Traceability / ประวัติที่มีบริบท** | ต่ำ — commit message คือข้อมูลเดียวที่มี | สูง — PR มีการพูดคุย เหตุผล และผู้อนุมัติบันทึกไว้ |
| **ความเร็วสำหรับงานเล็ก ๆ** | เร็วมาก ไม่มี overhead | ช้ากว่าเล็กน้อยเพราะต้องเปิด branch/PR |
| **ความเหมาะสมกับทีมกระจาย Time Zone** | ไม่เหมาะ ต้องประสานงานตรง ๆ ตลอด | เหมาะมาก ทำงาน async ได้ |
| **ความเสี่ยงต่อ Production** | สูงกว่า เพราะไม่มีด่านตรวจสอบ | ต่ำกว่า เพราะมีด่านตรวจสอบก่อนเสมอ |
| **การแชร์ความรู้ในทีม** | น้อย ไม่มีจุดบังคับให้เห็นโค้ดกัน | มาก ผ่านการรีวิว PR |
| **Overhead ในการบริหารจัดการ** | แทบไม่มี | ต้องดูแลจัดการ branch, PR ให้เป็นระเบียบ |
| **เหมาะกับ Open Source ที่มีคนนอกช่วย contribute** | ไม่เหมาะเลย | เหมาะมาก (ใช้ Fork + PR ได้ต่อยอด) |

### ตารางเปรียบเทียบเชิงสถานการณ์การใช้งานจริง

| สถานการณ์ | Workflow ที่เหมาะสมกว่า | เหตุผลสั้น ๆ |
|---|---|---|
| Hackathon 24 ชั่วโมง ทีม 2 คน | Centralized | ต้องการความเร็วสูงสุด ไม่มีเวลาทำ PR |
| Side project ส่วนตัวคนเดียว | Centralized | ไม่มีใครมารีวิวอยู่แล้ว |
| Startup ทีมพัฒนา 6 คน สร้างผลิตภัณฑ์จริง | Feature Branch | ต้องการคุณภาพโค้ดและการันตี `main` เสถียร |
| โปรเจกต์ Open Source ที่รับ contributor ภายนอก | Feature Branch (ผ่าน Fork) | ต้องตรวจสอบโค้ดจากคนแปลกหน้าก่อนรวมเข้าเสมอ |
| ระบบธนาคาร/การเงินที่ต้องผ่านมาตรฐานสูง | Feature Branch + การรีวิวหลายชั้น | ความเสี่ยงสูง ต้องมีด่านตรวจสอบเข้มงวด |
| ทีมสอนนักเรียนใหม่หัดใช้ Git ครั้งแรก | Centralized ก่อน แล้วค่อยขยับไป Feature Branch | ลดความซับซ้อนตอนเริ่มต้นเรียนรู้ |

### สิ่งที่ทั้งสอง Workflow มีเหมือนกัน

แม้จะต่างกันมาก แต่ทั้งสอง Workflow ก็มีจุดร่วมที่สำคัญ:

- ทั้งคู่ใช้ Git เป็นเครื่องมือพื้นฐานเดียวกัน คำสั่งหลัก (`commit`, `push`, `pull`) เหมือนกันทุกประการ
- ทั้งคู่สามารถทำงานร่วมกับ GitHub/GitLab ได้เหมือนกัน
- ทั้งคู่ต้องการวินัยของทีมในการปฏิบัติตามกติกาอย่างสม่ำเสมอ ไม่ว่ากติกาจะซับซ้อนแค่ไหนก็ตาม
- ทั้งคู่สามารถ "อัปเกรด" ไปสู่ Workflow ที่ซับซ้อนกว่าได้เมื่อจำเป็น (Centralized → Feature Branch → Git Flow/GitHub Flow/Trunk-Based)

การเข้าใจตารางเปรียบเทียบนี้อย่างละเอียดจะเป็นรากฐานสำคัญเมื่อเราไปเรียน Workflow ที่ซับซ้อนกว่านี้ใน Part ถัดไป ๆ เพราะ Git Flow, GitHub Flow และ Trunk-Based Development ล้วนแต่เป็นการ "ต่อยอด" มาจากหลักการพื้นฐานของ Feature Branch Workflow ที่เราเพิ่งเรียนไปทั้งสิ้น

## Step 310: แบบฝึกหัด — จำลองทีม 3 คนทำงานผ่าน Bare Repository

ถึงเวลาลงมือปฏิบัติจริง เราจะจำลองสถานการณ์ทีม 3 คน (Alice, Bob, Carol) ทำงานร่วมกันแบบ Feature Branch Workflow โดยใช้ **bare repository** เป็น "remote กลาง" แทน GitHub (เพื่อฝึกความเข้าใจกลไกเบื้องหลังโดยไม่ต้องพึ่งอินเทอร์เน็ต) และใช้ **3 โฟลเดอร์แยกกัน** แทนเครื่องคอมพิวเตอร์ของสมาชิกแต่ละคน

### ภาพรวมของแบบฝึกหัด

```
                    ┌───────────────────────────┐
                    │   team-project.git         │
                    │   (Bare Repository = จำลอง │
                    │    GitHub/GitLab กลาง)      │
                    └───────────┬─────────────────┘
              clone             │             clone
        ┌─────────────────────┬─┴───────────────────────┐
        │                     │                          │
  ┌─────▼──────┐       ┌──────▼──────┐           ┌──────▼──────┐
  │ alice-local │       │  bob-local  │           │ carol-local │
  └─────────────┘       └─────────────┘           └─────────────┘
```

### ขั้นตอนที่ 1: เตรียมพื้นที่ทำงานและสร้าง Bare Repository

```bash
mkdir -p ~/git-course/part-31-team-simulation
cd ~/git-course/part-31-team-simulation

# สร้าง bare repository เพื่อจำลอง remote กลาง (เหมือน GitHub)
git init --bare team-project.git
```

**หมายเหตุ:** `bare repository` คือ repository ที่ไม่มี working directory ไม่มีไฟล์ให้แก้ไขโดยตรง มีหน้าที่แค่เป็น "ที่เก็บกลาง" สำหรับรับ push และให้ pull เท่านั้น — นี่คือหลักการเดียวกับที่ server ของ GitHub ใช้เก็บ repository ของเรา

### ขั้นตอนที่ 2: จำลองการ Clone ของสมาชิกแต่ละคน

```bash
cd ~/git-course/part-31-team-simulation

git clone team-project.git alice-local
git clone team-project.git bob-local
git clone team-project.git carol-local
```

ตอนนี้เรามี 3 โฟลเดอร์ที่แต่ละโฟลเดอร์คือ "เครื่องคอมพิวเตอร์" ของสมาชิกแต่ละคน ทั้งหมดเชื่อมต่อกับ `team-project.git` เป็น remote `origin` เดียวกัน

### ขั้นตอนที่ 3: Alice สร้างไฟล์เริ่มต้นของโปรเจกต์และ Push ขึ้น Main

```bash
cd ~/git-course/part-31-team-simulation/alice-local

# ตั้งค่าชื่อผู้ใช้เฉพาะ repo นี้ (จำลองว่าเป็นเครื่องของ Alice)
git config user.name "Alice"
git config user.email "alice@example.com"

echo "# Team Project" > README.md
echo "ระบบจัดการสินค้าคงคลังของทีม" >> README.md

git add README.md
git commit -m "เริ่มต้นโปรเจกต์ด้วย README"

# Push ครั้งแรกเข้า main (เหตุการณ์นี้เกิดครั้งเดียวตอนตั้งโปรเจกต์)
git branch -M main
git push -u origin main
```

### ขั้นตอนที่ 4: Bob และ Carol ดึงโค้ดล่าสุดมาที่เครื่องของตัวเอง

```bash
cd ~/git-course/part-31-team-simulation/bob-local
git config user.name "Bob"
git config user.email "bob@example.com"
git pull origin main

cd ~/git-course/part-31-team-simulation/carol-local
git config user.name "Carol"
git config user.email "carol@example.com"
git pull origin main
```

ทั้งสามคนตอนนี้มี `README.md` เหมือนกันแล้ว

### ขั้นตอนที่ 5: Bob เริ่มทำ Feature Branch ของตัวเอง

```bash
cd ~/git-course/part-31-team-simulation/bob-local

git checkout -b feature/add-product-list

mkdir -p src
cat > src/product.js << 'EOF'
function listProducts(products) {
  return products.map(p => p.name).join(", ");
}

module.exports = { listProducts };
EOF

git add src/product.js
git commit -m "เพิ่มฟังก์ชัน listProducts สำหรับแสดงรายการสินค้า"

git push -u origin feature/add-product-list
```

### ขั้นตอนที่ 6: ในเวลาเดียวกัน Carol ก็เริ่มทำ Feature Branch ของตัวเอง (คู่ขนาน)

```bash
cd ~/git-course/part-31-team-simulation/carol-local

git checkout -b feature/add-inventory-count

mkdir -p src
cat > src/inventory.js << 'EOF'
function countInventory(products) {
  return products.reduce((sum, p) => sum + p.quantity, 0);
}

module.exports = { countInventory };
EOF

git add src/inventory.js
git commit -m "เพิ่มฟังก์ชัน countInventory สำหรับนับจำนวนสินค้าคงคลัง"

git push -u origin feature/add-inventory-count
```

สังเกตว่า Bob และ Carol ทำงานคนละไฟล์ (`product.js` กับ `inventory.js`) บนคนละ branch พร้อมกันโดยไม่ชนกันเลย — นี่คือประโยชน์ของ Feature Branch Workflow ที่เราพูดถึงใน Step 306

### ขั้นตอนที่ 7: จำลองกระบวนการ Pull Request และ Merge (โดย Alice ทำหน้าที่ผู้ดูแลหลัก)

เนื่องจากเราไม่มี GitHub ในแบบฝึกหัดนี้ เราจะจำลองขั้นตอน "รีวิวแล้ว merge" ด้วยคำสั่ง Git ตรง ๆ โดยใช้ `--no-ff` (no fast-forward) เพื่อให้เกิด merge commit ที่มองเห็นได้ชัดเจนในประวัติ เหมือนกับที่ GitHub ทำเวลากด "Merge pull request"

```bash
cd ~/git-course/part-31-team-simulation/alice-local

# ดึง branch ของ Bob และ Carol เข้ามาดูก่อน (จำลองการรีวิวโค้ด)
git fetch origin

git checkout main
git pull origin main

# สมมติว่า Alice รีวิวโค้ดของ Bob แล้วอนุมัติ จึง merge
git merge --no-ff origin/feature/add-product-list -m "Merge PR: เพิ่มฟังก์ชัน listProducts (รีวิวโดย Alice)"

git push origin main
```

### ขั้นตอนที่ 8: Merge งานของ Carol เข้าไปด้วย

```bash
# ยังอยู่ใน alice-local, ยังอยู่บน main
git merge --no-ff origin/feature/add-inventory-count -m "Merge PR: เพิ่มฟังก์ชัน countInventory (รีวิวโดย Alice)"

git push origin main
```

ตรวจสอบประวัติที่ได้:

```bash
git log --oneline --graph --all
```

ผลลัพธ์ที่ควรเห็นประมาณนี้ (SHA จะต่างกันไปในเครื่องของแต่ละคน):

```
*   a1b2c3d Merge PR: เพิ่มฟังก์ชัน countInventory (รีวิวโดย Alice)
|\
| * e4f5g6h เพิ่มฟังก์ชัน countInventory สำหรับนับจำนวนสินค้าคงคลัง
* |   i7j8k9l Merge PR: เพิ่มฟังก์ชัน listProducts (รีวิวโดย Alice)
|\ \
| |/
| * m1n2o3p เพิ่มฟังก์ชัน listProducts สำหรับแสดงรายการสินค้า
|/
* q4r5s6t เริ่มต้นโปรเจกต์ด้วย README
```

จะเห็นว่าทั้งสองฟีเจอร์ถูก merge เข้า `main` เป็น 2 จุดแยกกันอย่างชัดเจน พร้อมข้อความอธิบายว่าใครรีวิว — นี่คือคุณค่าของ traceability ที่เราพูดถึงใน Step 306

### ขั้นตอนที่ 9: จำลองสถานการณ์ Conflict — Bob และ Carol แก้ไฟล์เดียวกัน

มาสร้างสถานการณ์ conflict ขึ้นมาโดยตั้งใจ เพื่อฝึกการแก้ปัญหา:

```bash
# Bob สร้าง branch ใหม่และแก้ไฟล์ README
cd ~/git-course/part-31-team-simulation/bob-local
git checkout main
git pull origin main
git checkout -b feature/update-readme-bob

echo "## ทีมพัฒนา" >> README.md
echo "- Bob (Backend)" >> README.md

git add README.md
git commit -m "เพิ่มรายชื่อทีมพัฒนาส่วนของ Bob"
git push -u origin feature/update-readme-bob
```

```bash
# Carol ก็แก้ README บรรทัดใกล้เคียงกันบน branch ของตัวเอง โดยไม่รู้ว่า Bob แก้ไปแล้ว
cd ~/git-course/part-31-team-simulation/carol-local
git checkout main
git pull origin main
git checkout -b feature/update-readme-carol

echo "## ทีมพัฒนา" >> README.md
echo "- Carol (Data & Inventory)" >> README.md

git add README.md
git commit -m "เพิ่มรายชื่อทีมพัฒนาส่วนของ Carol"
git push -u origin feature/update-readme-carol
```

ตอนนี้ merge อันแรก (ของ Bob) จะผ่านฉลุยเพราะ `main` ยังไม่มีใครแก้ไฟล์นี้ก่อน:

```bash
cd ~/git-course/part-31-team-simulation/alice-local
git checkout main
git pull origin main
git merge --no-ff origin/feature/update-readme-bob -m "Merge PR: เพิ่มรายชื่อทีม (Bob)"
git push origin main
```

แต่พอถึงตาของ Carol การ merge จะเกิด **conflict** เพราะ `main` เปลี่ยนไปแล้วจากการ merge ของ Bob:

```bash
git merge --no-ff origin/feature/update-readme-carol -m "Merge PR: เพิ่มรายชื่อทีม (Carol)"
```

Git จะแจ้งเตือนประมาณนี้:

```
Auto-merging README.md
CONFLICT (content): Merge conflict in README.md
Automatic merge failed; fix conflicts and then commit the result.
```

เปิดไฟล์ `README.md` จะเห็นเครื่องหมาย conflict marker:

```
## ทีมพัฒนา
<<<<<<< HEAD
- Bob (Backend)
=======
- Carol (Data & Inventory)
>>>>>>> origin/feature/update-readme-carol
```

### ขั้นตอนที่ 10: แก้ไข Conflict และสรุปแบบฝึกหัด

แก้ไฟล์ให้รวมทั้งสองรายชื่อเข้าด้วยกัน:

```
## ทีมพัฒนา
- Bob (Backend)
- Carol (Data & Inventory)
```

จากนั้น commit ผลลัพธ์การ merge:

```bash
git add README.md
git commit -m "Merge PR: เพิ่มรายชื่อทีม (Carol) — แก้ conflict รวมรายชื่อ Bob และ Carol"
git push origin main
```

ตรวจสอบผลลัพธ์สุดท้าย:

```bash
cat README.md
git log --oneline --graph --all
```

Bob และ Carol สามารถ pull `main` ล่าสุดกลับไปที่เครื่องตัวเองเพื่อดูผลลัพธ์ และลบ feature branch ที่ใช้เสร็จแล้ว:

```bash
cd ~/git-course/part-31-team-simulation/bob-local
git checkout main
git pull origin main
git branch -d feature/add-product-list feature/update-readme-bob
git push origin --delete feature/add-product-list feature/update-readme-bob

cd ~/git-course/part-31-team-simulation/carol-local
git checkout main
git pull origin main
git branch -d feature/add-inventory-count feature/update-readme-carol
git push origin --delete feature/add-inventory-count feature/update-readme-carol
```

### สิ่งที่ควรได้เรียนรู้จากแบบฝึกหัดนี้

1. คุณได้เห็นด้วยตาตัวเองว่า bare repository ทำหน้าที่เป็น "จุดกลาง" ได้เหมือน GitHub จริง ๆ (แม้จะไม่มี UI สวยงาม)
2. คุณได้ฝึกสร้าง feature branch, commit, push, และจำลองขั้นตอนการ merge แบบมี `--no-ff` เพื่อรักษาร่องรอยของแต่ละฟีเจอร์
3. คุณได้เห็นว่างานคู่ขนาน (Bob กับ Carol ทำคนละไฟล์คนละ branch) ไม่ชนกันเลย ตรงตามหลักการ isolation ของ Feature Branch Workflow
4. คุณได้เจอและแก้ **merge conflict จริง** ที่เกิดจากสองคนแก้ไฟล์เดียวกัน และเข้าใจว่าทำไมการ sync กับ `main` บ่อย ๆ (อย่างที่พูดถึงใน Step 307) จะช่วยลดโอกาสเจอสถานการณ์แบบนี้ได้

### Checklist แบบฝึกหัด Step 310

- [ ] สร้าง bare repository สำเร็จและ clone ออกมาได้ 3 ชุด
- [ ] Alice push commit เริ่มต้นเข้า `main` ได้สำเร็จ
- [ ] Bob และ Carol สร้าง feature branch คนละอันและ push ขึ้น remote ได้
- [ ] จำลองการ merge ทั้งสอง feature branch เข้า `main` ด้วย `--no-ff` สำเร็จ
- [ ] จงใจสร้างสถานการณ์ conflict และแก้ไขได้สำเร็จ พร้อมเข้าใจเครื่องหมาย conflict marker
- [ ] ลบ feature branch ที่ merge เสร็จแล้วทั้งบน local และ remote เรียบร้อย

## สรุป Part 31

ใน Part นี้เราได้เรียนรู้ว่า:

1. **Workflow มาตรฐาน** คือกติกาที่ทีมตกลงร่วมกันในการใช้ Git ซึ่งจำเป็นมากเมื่อทีมเริ่มมีขนาดใหญ่ขึ้น เพราะช่วยลดความสับสน ลด conflict และรักษาคุณภาพโค้ดให้สม่ำเสมอ
2. **Centralized Workflow** คือรูปแบบที่ทุกคน commit ตรงเข้า `main` เหมาะกับทีมขนาดเล็กมาก (1–4 คน) ที่สื่อสารกันได้ดี แต่เริ่มมีปัญหาชัดเจนเมื่อทีมโตขึ้น เพราะ conflict เพิ่มแบบทวีคูณ ไม่มี Code Review และ `main` ไม่เสถียร
3. **Feature Branch Workflow** แก้ปัญหาเหล่านั้นด้วยหลักการ "ห้าม commit ตรงเข้า main" — แยกทุกงานเป็น branch ของตัวเอง แล้วรวมกลับผ่านกระบวนการ Pull Request และ Code Review
4. ขั้นตอนเต็มของ Feature Branch Workflow คือ: pull main → สร้าง branch → commit → push → เปิด PR → review → merge → ลบ branch → pull main ใหม่
5. ข้อดีสำคัญของ Feature Branch Workflow ได้แก่ การแยกงานเป็นอิสระ บังคับ Code Review, `main` สะอาดและ deployable เสมอ, รองรับงานคู่ขนาน, และรองรับ CI/CD ได้ดี
6. ปัญหาสำคัญที่ต้องระวังคือ **Long-lived Branch** ที่ทำให้ conflict สะสมมากเกินไป วิธีป้องกันคือทำให้ branch มีอายุสั้น sync กับ `main` บ่อย ๆ และแบ่งงานใหญ่เป็นชิ้นเล็ก
7. การเลือก Workflow ที่เหมาะสมต้องพิจารณาขนาดทีม ความถี่ release ระดับประสบการณ์ และระดับความเสี่ยงของโปรเจกต์ — ไม่มี Workflow ใดที่ดีที่สุดในทุกสถานการณ์
8. เราได้ลงมือจำลองทีม 3 คนทำงานจริงผ่าน bare repository ตั้งแต่การ clone, สร้าง feature branch, ทำงานคู่ขนาน, จำลองการ merge PR ไปจนถึงการเจอและแก้ merge conflict จริงด้วยมือตัวเอง

Centralized Workflow และ Feature Branch Workflow ที่เราเรียนใน Part นี้ คือ **รากฐานสำคัญที่สุด** ของ Workflow ทั้งหมดที่จะตามมาในเฟส 4 ทุก Workflow ที่ซับซ้อนกว่านี้ ไม่ว่าจะเป็น Git Flow, GitHub Flow, GitLab Flow หรือ Trunk-Based Development ล้วนแต่สร้างต่อยอดขึ้นจากหลักการพื้นฐานของ Feature Branch ที่คุณเพิ่งฝึกฝนมาทั้งสิ้น
