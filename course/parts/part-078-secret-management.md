## Step 771: ปัญหา secret หลุดเข้า Git repository เกิดขึ้นบ่อยแค่ไหน ผลกระทบร้ายแรงแค่ไหน

### secret คืออะไรกันแน่

ก่อนอื่นต้องนิยามคำว่า **secret** ให้ชัดเจน เพราะตลอด Part นี้เราจะใช้คำนี้ตลอด

> **Secret** คือข้อมูลใด ๆ ที่ถ้าหลุดไปอยู่ในมือคนที่ไม่ควรมี จะทำให้ระบบ บัญชี หรือข้อมูลของคุณถูกเข้าถึงโดยไม่ได้รับอนุญาต

ตัวอย่างของสิ่งที่นับเป็น secret มีมากกว่าที่มือใหม่ส่วนใหญ่คิด:

| ประเภท | ตัวอย่าง |
|---|---|
| API Key / Access Token | คีย์เชื่อมต่อบริการ cloud, payment gateway, third-party API |
| Database Credentials | username/password ของฐานข้อมูล production |
| Private Key | SSH private key, TLS/SSL private key, GPG private key |
| Cloud Provider Credentials | Access Key ID + Secret Access Key ของบัญชี cloud |
| OAuth Client Secret | ค่าลับที่ใช้คู่กับ Client ID ในระบบ login แบบ OAuth |
| Webhook Signing Secret | ค่าที่ใช้ยืนยันว่า webhook มาจากแหล่งที่ถูกต้องจริง |
| Encryption Key | คีย์ที่ใช้เข้ารหัส/ถอดรหัสข้อมูลสำคัญ |
| Internal Session/Cookie Secret | ค่าลับที่ framework ใช้เซ็นและตรวจสอบ session |

จุดร่วมของทุกข้อคือ: **ถ้าคนนอกได้ค่านี้ไป เขาสามารถ "แสร้งเป็นคุณ" หรือ "เข้าถึงสิ่งที่คุณเข้าถึงได้" ทันที โดยไม่ต้องเจาะระบบเลยแม้แต่น้อย**

### ทำไม Git ถึงเป็นแหล่งรั่วไหลอันดับต้น ๆ

ย้อนกลับไปที่สิ่งที่เราเรียนใน **Part 01 และ Part 56 (Git Internals)**: Git ถูกออกแบบมาให้ **"ไม่ลืมอะไรเลย"** ทุก commit ที่เคยเกิดขึ้นจะถูกเก็บเป็น object ถาวรอยู่ใน `.git/objects` ตราบใดที่ยังไม่ถูก garbage collect และไม่มีใครอ้างอิงถึงมันอีก

คุณสมบัตินี้คือจุดแข็งของ Git ในแง่ประวัติศาสตร์โค้ด แต่กลับกลายเป็น **จุดอ่อนร้ายแรง** เมื่อมีคน commit secret ลงไปโดยไม่ตั้งใจ เพราะ:

1. **การลบไฟล์ในภายหลังไม่ได้ลบมันออกจากประวัติ** — ถึงคุณจะลบไฟล์ `.env` ออกและ commit ใหม่ ค่าดั้งเดิมยังอยู่ใน commit เก่าที่ใครก็ตามที่ `git clone` หรือ `git log -p` ก็เห็นได้
2. **โปรเจกต์ Open Source ถูก clone/fork ได้ทันทีที่ push** — ถ้า repo เป็น public แม้จะลบ secret ออกใน 1 นาทีถัดมา ก็อาจมีคน (หรือบอทสแกนอัตโนมัติ) clone ประวัติทั้งหมดไปเก็บไว้แล้ว
3. **มีบอทสแกนหา secret บน GitHub/GitLab สาธารณะทำงานตลอด 24 ชั่วโมง** — งานวิจัยและรายงานด้านความปลอดภัยหลายฉบับยืนยันตรงกันว่า secret ที่หลุดขึ้น public repository มักถูกบอทเก็บไปใช้งาน **ภายในไม่กี่นาทีถึงไม่กี่ชั่วโมง** ไม่ใช่หลักวัน
4. **แม้แต่ private repository ก็ไม่ปลอดภัย 100%** — เพราะ collaborator ทุกคนที่มีสิทธิ์เข้าถึงจะเห็นประวัติทั้งหมด และถ้า repo ถูกเปลี่ยนเป็น public โดยไม่ตั้งใจ (หรือ token ของบัญชีถูกขโมย) ประวัติทั้งหมดก็หลุดไปด้วย

### ความรุนแรงของผลกระทบในโลกจริง

secret ที่หลุดเข้า Git ไม่ใช่แค่ "เรื่องน่าอาย" แต่เป็นเหตุการณ์ที่สร้างความเสียหายทางการเงินและทางธุรกิจได้จริง รูปแบบความเสียหายที่พบบ่อยที่สุดมีดังนี้:

**1. บัญชี Cloud ถูกขโมยไปใช้ขุด Cryptocurrency (Cryptojacking)**

รูปแบบที่พบบ่อยที่สุดในอุตสาหกรรมคือ: มีคน commit ไฟล์ credentials ของบัญชี cloud (เช่นไฟล์ config ที่เก็บ Access Key ID และ Secret Access Key ของบัญชี cloud) ขึ้น public repository โดยไม่ได้ตั้งใจ ภายในเวลาไม่กี่นาทีถึงไม่กี่ชั่วโมง บอทอัตโนมัติที่สแกน public repository ตลอดเวลาจะดึงคีย์นั้นไปใช้สร้าง instance ประสิทธิภาพสูงจำนวนมากเพื่อขุด cryptocurrency ทำให้เกิดค่าใช้จ่ายมหาศาลในเวลาอันสั้น มีกรณีที่เป็นข่าวจริงหลายครั้งที่นักพัฒนาต้องเจอบิลค่าใช้บริการ cloud สูงถึงหลักหมื่นถึงหลักแสนดอลลาร์สหรัฐภายในเวลาไม่ถึง 24 ชั่วโมง เพียงเพราะ credential หลุดไปในโค้ดที่ push ขึ้น public repository เพียงครั้งเดียว

**2. ข้อมูลลูกค้ารั่วไหลผ่าน Database Credentials**

ถ้า connection string ของฐานข้อมูล production (ที่มี username/password อยู่ในตัว) หลุดเข้า Git และมีคนนำไปใช้เชื่อมต่อ อาจนำไปสู่การขโมยข้อมูลลูกค้าทั้งฐาน ซึ่งนอกจากความเสียหายทางธุรกิจแล้ว ในหลายประเทศยังมีกฎหมายคุ้มครองข้อมูลส่วนบุคคล (เช่น GDPR ในยุโรป หรือ PDPA ในประเทศไทย) ที่กำหนดบทลงโทษทางการเงินร้ายแรงต่อองค์กรที่ปล่อยให้ข้อมูลรั่วไหลจากความประมาทเช่นนี้

**3. การเข้าควบคุมระบบทั้งหมดผ่าน API Key ที่มีสิทธิ์สูง**

หาก API Key ที่หลุดออกไปมีสิทธิ์ระดับ admin หรือสามารถสร้าง/ลบ/แก้ไขทรัพยากรได้แบบไม่จำกัด ผู้ไม่หวังดีสามารถเข้าควบคุมโครงสร้างพื้นฐานทั้งหมดขององค์กรได้ ตั้งแต่การลบข้อมูลทั้งหมดเพื่อเรียกค่าไถ่ ไปจนถึงการใช้ระบบขององค์กรเป็นฐานในการโจมตีเป้าหมายอื่นต่อ

**4. ความเสียหายต่อชื่อเสียงและความเชื่อมั่น**

แม้ในกรณีที่ความเสียหายทางการเงินไม่มาก แต่ข่าวเรื่อง "โปรเจกต์นี้ทำ secret หลุด" ก็สร้างความเสียหายต่อความน่าเชื่อถือขององค์กรหรือบุคคลได้อย่างมาก โดยเฉพาะในวงการ Open Source ที่ชื่อเสียงและความไว้วางใจของ maintainer เป็นสิ่งสำคัญที่สุด

### สถิติและแนวโน้มที่ควรตระหนัก

หน่วยงานด้านความปลอดภัยและบริษัทที่ให้บริการสแกน secret หลายแห่งเผยแพร่รายงานประจำปีที่ชี้ตรงกันในทิศทางเดียวกันมาต่อเนื่องหลายปี:

- จำนวน secret ที่ถูกตรวจพบหลุดเข้า public repository **เพิ่มขึ้นทุกปี** แปรผันตรงกับจำนวนนักพัฒนาที่ใช้ Git และแพลตฟอร์มโฮสต์โค้ดที่เพิ่มขึ้น
- สาเหตุอันดับต้น ๆ ไม่ใช่การถูกแฮ็ก แต่คือ **ความประมาทของนักพัฒนาเอง** เช่น commit ไฟล์ `.env` ไปโดยไม่ทันสังเกต, hardcode credential ไว้ในโค้ดชั่วคราวระหว่างทดสอบแล้วลืมเอาออกก่อน commit, หรือ commit ไฟล์ config ที่มี credential ติดไปโดยไม่รู้ตัว
- เวลาเฉลี่ยที่ secret จะถูกนำไปใช้งานหลังหลุดเข้า public repository นั้น **สั้นกว่าที่คนทั่วไปคาดคิดมาก** — นี่คือเหตุผลที่แพลตฟอร์มอย่าง GitHub และ GitLab ต้องลงทุนสร้างระบบสแกนและบล็อกอัตโนมัติ (ซึ่งเราได้เรียนไปแล้วในเรื่อง Secret Detection ของ GitLab ใน Part 54 และจะเชื่อมโยงกันอีกครั้งใน Step 775)

### สรุปแนวคิดสำคัญของ Step นี้

> **Secret ที่หลุดเข้า Git ไม่ใช่ "ความผิดพลาดเล็กน้อยที่แก้ทีหลังได้" แต่เป็นเหตุการณ์ที่ต้องถือว่า secret นั้น "ถูกเปิดเผยแล้วอย่างถาวร" ทันทีที่ push ออกไป ไม่ว่าจะลบออกเร็วแค่ไหนก็ตาม**

หลักคิดนี้จะเป็นแกนกลางของทุก Step ที่เหลือใน Part นี้ โดยเฉพาะ Step 773 ที่จะอธิบายว่าทำไม "revoke" ถึงสำคัญกว่า "ลบ" เสมอ

## Step 772: กฎทอง — ห้าม commit secret ลง Git เด็ดขาด และ `.gitignore` ต้องมี `.env` ตั้งแต่วันแรก

### กฎทองข้อเดียวที่สำคัญที่สุดใน Part นี้

> **ห้าม commit secret ลง Git repository เด็ดขาด ไม่ว่าจะเป็น repository แบบ public หรือ private ก็ตาม**

นี่ไม่ใช่ "แนวทางที่ควรทำ" แต่เป็น **กฎที่ต้องยึดถือแบบไม่มีข้อยกเว้น** เหตุผลที่ต้องเข้มงวดถึงขนาดนี้เพราะ:

1. Private repository วันนี้ อาจถูกเปลี่ยนเป็น public พรุ่งนี้โดยความผิดพลาดของใครสักคน
2. บัญชีของ collaborator ทุกคนที่เข้าถึง private repository ได้ อาจถูกขโมยบัญชีในภายหลัง
3. ตัว repository เองอาจถูก fork ไปที่อื่นโดยไม่มีใครสังเกตเห็น
4. เมื่อทีมโตขึ้น จำนวนคนที่เข้าถึงประวัติทั้งหมดของ repository จะเพิ่มขึ้นเรื่อย ๆ โดยที่คุณควบคุมไม่ได้ทั้งหมด

### `.env` ต้องอยู่ใน `.gitignore` ตั้งแต่วินาทีแรกที่สร้าง repo

ไฟล์ `.env` คือไฟล์มาตรฐานที่ใช้เก็บตัวแปรสภาพแวดล้อม (environment variables) รวมถึง secret ต่าง ๆ ของโปรเจกต์ในเครื่อง local ปัญหาที่พบบ่อยที่สุดในโลกจริงคือ นักพัฒนาสร้างไฟล์ `.env` ขึ้นมาก่อน แล้วค่อยนึกได้ทีหลังว่าต้องเพิ่มมันเข้า `.gitignore` — ซึ่งบ่อยครั้ง "ทีหลัง" มันสายไปแล้ว เพราะไฟล์นั้นถูก `git add .` และ commit ไปเรียบร้อยตั้งแต่รอบแรก

ลำดับที่ถูกต้องคือ:

```bash
# ขั้นตอนที่ถูกต้อง: สร้าง .gitignore และใส่ .env ไว้ก่อน สร้างไฟล์ .env จริง
mkdir my-project
cd my-project
git init

# 1) สร้าง .gitignore และใส่กฎป้องกัน .env ก่อนเป็นอันดับแรก
cat > .gitignore << 'EOF'
# Environment variables และ secrets — ห้าม commit เด็ดขาด
.env
.env.*
!.env.example
*.pem
*.key
*.p12
*credentials*.json
EOF

git add .gitignore
git commit -m "chore: เพิ่ม .gitignore ป้องกัน secret ตั้งแต่ต้น"

# 2) หลังจากนี้ค่อยสร้างไฟล์ .env จริง (จะไม่ถูก track โดย Git แล้ว)
touch .env
```

สังเกตรายละเอียดสำคัญในไฟล์ `.gitignore` ด้านบน:

| บรรทัด | ความหมาย |
|---|---|
| `.env` | บล็อกไฟล์ `.env` โดยตรงไม่ให้ถูก track |
| `.env.*` | บล็อกไฟล์ variant ทั้งหมด เช่น `.env.local`, `.env.production`, `.env.development` |
| `!.env.example` | **ยกเว้น** ไฟล์ `.env.example` ให้ยังคง track ได้ตามปกติ (ใช้เป็นแม่แบบบอกโครงสร้างตัวแปรที่ต้องมี โดยไม่มีค่าจริง) |
| `*.pem`, `*.key`, `*.p12` | บล็อกไฟล์ certificate/private key ทุกรูปแบบที่พบบ่อย |
| `*credentials*.json` | บล็อกไฟล์ credential ของบริการ cloud ที่มักถูก export มาเป็น JSON |

### ใช้ `.env.example` เป็นแม่แบบแทน `.env` จริง

รูปแบบมาตรฐานที่ทีมมืออาชีพใช้กันคือ commit ไฟล์ `.env.example` ที่มีแค่ **โครงสร้างของตัวแปร** โดยไม่มีค่าจริงเลย เช่น:

```bash
# .env.example (ไฟล์นี้ commit ได้ปกติ ไม่มีความลับอยู่ในนี้)
DATABASE_URL=
DATABASE_USER=
DATABASE_PASSWORD=
PAYMENT_GATEWAY_API_KEY=
CLOUD_PROVIDER_ACCESS_KEY_ID=
CLOUD_PROVIDER_SECRET_ACCESS_KEY=
JWT_SIGNING_SECRET=
```

สมาชิกใหม่ในทีมแค่ `cp .env.example .env` แล้วกรอกค่าจริงของตัวเองลงไป (ค่าที่ได้รับผ่านช่องทางปลอดภัย เช่น secret manager ที่จะกล่าวถึงใน Step 776 หรือส่งผ่านช่องทางที่ปลอดภัยจากทีม) โดยที่ไฟล์ `.env` จริงจะไม่มีวันถูก commit เพราะถูกกันไว้ใน `.gitignore` แล้ว

### เช็คก่อน commit ทุกครั้งด้วย `git status` และ `git diff --staged`

แม้จะมี `.gitignore` แล้ว ก็ยังควรฝึกนิสัยตรวจสอบก่อน commit ทุกครั้ง เพราะ `.gitignore` ป้องกันได้เฉพาะไฟล์ที่ตรง pattern เท่านั้น ถ้ามีคน hardcode secret ไว้ใน source code โดยตรง (เช่น เขียนค่า API key ไว้ในไฟล์ `.py` หรือ `.js` ตรง ๆ เพื่อทดสอบแล้วลืมลบออก) `.gitignore` จะช่วยอะไรไม่ได้เลย

```bash
# ก่อน commit ทุกครั้ง ควรตรวจสอบว่าไฟล์ที่จะเข้าไปมีอะไรบ้าง
git status
git diff --staged

# อ่านผลลัพธ์อย่างละเอียดว่ามีบรรทัดไหนดูเหมือนค่า credential หลุดเข้ามาหรือไม่
```

นิสัยนี้ดูเหมือนเรื่องเล็กน้อย แต่เป็นด่านสุดท้ายที่มนุษย์ยังตรวจสอบได้ด้วยตาก่อนที่ secret จะหลุดออกไปจริง ก่อนที่เราจะไปถึงเครื่องมืออัตโนมัติใน Step 775 และ 779

### ตารางสรุปกฎทองของ Step นี้

| หลักการ | รายละเอียด |
|---|---|
| ห้าม commit secret เด็ดขาด | ไม่มีข้อยกเว้น ไม่ว่า repo จะ public หรือ private |
| `.gitignore` ต้องมี `.env` ตั้งแต่วันแรก | สร้างก่อนสร้างไฟล์ `.env` จริงเสมอ |
| ใช้ `.env.example` แทน | commit แค่โครงสร้างตัวแปร ไม่มีค่าจริง |
| ตรวจสอบก่อน commit ทุกครั้ง | `git status` + `git diff --staged` เป็นด่านสุดท้ายของมนุษย์ |
| ไม่ไว้ใจแค่ `.gitignore` อย่างเดียว | ต้องมีเครื่องมือสแกนอัตโนมัติเสริมด้วย (Step 775, 779) |

## Step 773: พลาด commit secret ไปแล้วต้องทำอะไรก่อน — Revoke ก่อนเสมอ ไม่ใช่แค่ลบ

### ความเข้าใจผิดที่อันตรายที่สุดในเรื่องนี้

มือใหม่จำนวนมากเมื่อพบว่าตัวเอง commit secret ไปโดยไม่ตั้งใจ จะรีบทำสิ่งนี้ทันที:

```bash
# ❌ วิธีที่ผิด และอันตรายที่สุด — คิดว่าลบไฟล์แล้วจบ
git rm .env
git commit -m "remove .env"
git push
```

นี่คือ **ความเข้าใจผิดที่อันตรายที่สุด** ในเรื่อง secret management เพราะ commit ที่ลบไฟล์ออกไปนั้น **ไม่ได้ลบ secret ออกจากประวัติ Git เลยแม้แต่น้อย** ค่า secret ตัวเดิมยังคงอยู่ใน commit object เก่าที่ยัง reachable จาก history ทุกคนที่มี:

- สำเนา clone ของ repository ก่อนหน้านี้
- Fork ของ repository
- CI/CD build cache ที่เคย checkout commit เก่า
- แค่สิทธิ์เข้าถึง repository และรัน `git log -p -- .env` หรือ `git show <commit-เก่า>:.env`

ก็ยังสามารถเห็นค่า secret ตัวเดิมได้ทั้งหมด **ไม่ว่าจะลบไฟล์ไปกี่ commit ต่อจากนั้นก็ตาม**

### ลำดับขั้นตอนที่ถูกต้องเมื่อพบว่า secret หลุด

เมื่อพบว่า secret หลุดเข้า Git ไปแล้ว (ไม่ว่าจะรู้ตัวเองหรือมีคนแจ้ง หรือระบบสแกนอัตโนมัติแจ้งเตือน) ให้ทำตามลำดับนี้ **เรียงตามความสำคัญ**:

```
ลำดับที่ 1: REVOKE / ROTATE secret นั้นทันที (สำคัญที่สุด ทำก่อนอย่างอื่นทั้งหมด)
       │
       ▼
ลำดับที่ 2: ประเมินความเสียหาย (ตรวจ log การใช้งานว่ามีการใช้ที่ผิดปกติหรือยัง)
       │
       ▼
ลำดับที่ 3: ลบ secret ออกจากประวัติ Git ทั้งหมด (git filter-repo — Step 774)
       │
       ▼
ลำดับที่ 4: แจ้งทีม/ผู้เกี่ยวข้อง และบันทึกเป็นบทเรียน (post-mortem)
       │
       ▼
ลำดับที่ 5: ตั้งค่าป้องกันไม่ให้เกิดซ้ำ (pre-commit hook, secret scanning — Step 775, 779)
```

### ทำไม "Revoke ก่อนเสมอ" ถึงเป็นกฎเหล็ก

> **หลักการสำคัญที่สุด: ทันทีที่รู้ว่า secret หลุด ให้ถือว่ามันถูกคนอื่นเห็นไปแล้วเสมอ ไม่ว่าคุณจะมั่นใจแค่ไหนว่า "คงยังไม่มีใครเห็นหรอก"**

เหตุผลเชิงเทคนิคและเชิงความปลอดภัยมีดังนี้:

1. **การลบออกจากประวัติ (Step 774) ใช้เวลาและมีความเสี่ยง** — การรัน `git filter-repo` ต้องทำอย่างระมัดระวัง ต้องประสานงานกับทุกคนในทีมให้ clone ใหม่ ใช้เวลาเป็นนาทีถึงชั่วโมง ในขณะที่ secret ตัวเดิมยัง valid อยู่ตลอดเวลานั้น
2. **ต่อให้ลบออกจากประวัติสำเร็จ 100% ก็ไม่สามารถรับประกันได้ว่าไม่มีใคร clone ไปแล้วก่อนหน้านั้น** — โดยเฉพาะถ้าเป็น public repository หรือมีบอทสแกนทำงานอยู่ (ตามที่กล่าวใน Step 771 ว่าบอทอาจดึงไปใช้ภายในไม่กี่นาที)
3. **การ revoke/rotate ทำได้เร็วกว่ามาก** — ส่วนใหญ่ใช้เวลาแค่ไม่กี่วินาทีถึงไม่กี่นาทีผ่านหน้า dashboard ของผู้ให้บริการ และทำให้ secret ตัวเก่า **ใช้งานไม่ได้ทันที** ไม่ว่าใครจะมีสำเนาของมันอยู่ที่ไหนก็ตาม

พูดให้ชัดที่สุด: **การลบออกจากประวัติ Git คือการทำความสะอาดในระยะยาว แต่การ revoke คือการหยุดเลือดในระยะสั้นที่ต้องทำก่อนเสมอ** ถ้าทำสลับลำดับกัน ต่อให้ประวัติ Git สะอาดแล้ว แต่ secret ตัวเดิมยัง valid อยู่ และอาจมีคนเก็บสำเนาไว้ใช้งานได้เรื่อย ๆ

### วิธี revoke/rotate ตามประเภทของ secret

| ประเภท secret | วิธี revoke/rotate |
|---|---|
| API Key ของบริการ third-party | เข้า dashboard ของผู้ให้บริการ → ลบ/deactivate key เดิม → สร้าง key ใหม่ |
| Database password | เปลี่ยนรหัสผ่านฐานข้อมูลทันที และปรับ connection string ในทุกที่ที่ใช้งานจริง |
| Cloud provider access key | เข้า IAM console ของผู้ให้บริการ cloud → deactivate/delete access key เดิม → สร้างชุดใหม่ → ตรวจสอบ CloudTrail/Activity Log ว่ามีการใช้งานผิดปกติหรือไม่ |
| SSH private key | ลบ public key ที่คู่กันออกจากทุก server/service ที่เคย authorize ไว้ → สร้างคู่ key ใหม่ |
| SSL/TLS private key | เพิกถอน (revoke) certificate เดิมผ่าน Certificate Authority → ออก certificate ใหม่ |
| OAuth client secret | เข้า console ของผู้ให้บริการ OAuth → regenerate client secret |
| Webhook signing secret | สร้าง secret ใหม่ในระบบที่ส่ง webhook และปรับปรุงในฝั่งที่รับด้วย |

### ประเมินความเสียหายก่อนเดินหน้าต่อ

หลัง revoke แล้ว ควรตรวจสอบ log การใช้งาน (audit log / activity log ของบริการนั้น ๆ) ในช่วงเวลาตั้งแต่ secret หลุดจนถึงตอนที่ revoke เพื่อดูว่า:

- มีการเรียกใช้งานที่ไม่คุ้นเคย (IP แปลกหน้า, เวลาที่ผิดปกติ, ปริมาณ request สูงผิดปกติ) หรือไม่
- มีทรัพยากรใหม่ถูกสร้างขึ้นโดยไม่ได้ตั้งใจหรือไม่ (เช่น instance ใหม่ที่ไม่มีใครสร้าง)
- มีข้อมูลถูกดาวน์โหลดหรือแก้ไขผิดปกติหรือไม่

ขั้นตอนนี้สำคัญเพราะการ revoke เพียงอย่างเดียวหยุดความเสียหายในอนาคต แต่ไม่ได้บอกว่า **มีความเสียหายเกิดขึ้นไปแล้วหรือยังในช่วงเวลาที่ผ่านมา**

### สรุปหลักคิดของ Step นี้

> **ลำดับที่ถูกต้องคือ Revoke → ประเมินความเสียหาย → ลบประวัติ → แจ้งทีม → ป้องกันอนาคต ไม่ใช่ "ลบไฟล์แล้วจบ"**

ใน Step ถัดไปเราจะเรียนรู้วิธีลบ secret ออกจากประวัติ Git ทั้งหมดอย่างถูกต้องด้วย `git filter-repo` ซึ่งเป็นขั้นตอนที่ 3 ในลำดับข้างต้น — ทำ**หลัง**จาก revoke เสร็จแล้วเท่านั้น

## Step 774: ลบ secret ออกจากประวัติ Git ทั้งหมดด้วย `git filter-repo`

### ทำไมต้อง `git filter-repo` ไม่ใช่ `git filter-branch` หรือ BFG

เมื่อพูดถึงการ "แก้ไขประวัติ Git ทั้งหมด" เพื่อลบไฟล์หรือข้อมูลบางอย่างออก มีเครื่องมือหลายตัวที่เคยถูกแนะนำมาในอดีต:

| เครื่องมือ | สถานะปัจจุบัน |
|---|---|
| `git filter-branch` | เครื่องมือดั้งเดิมที่มากับ Git แต่ **เอกสารทางการของ Git เองแนะนำไม่ให้ใช้แล้ว** เพราะช้ามาก (ทำงานแบบ tree เดียวทีละ commit) มีข้อผิดพลาดง่าย และมีปัญหาเรื่อง edge case จำนวนมาก |
| BFG Repo-Cleaner | เครื่องมือของบุคคลที่สามที่เร็วกว่า `filter-branch` มาก และใช้งานง่าย เคยเป็นตัวเลือกยอดนิยม แต่ปัจจุบันการพัฒนาไม่ active เท่า `git filter-repo` และมีความสามารถจำกัดกว่า |
| **`git filter-repo`** | **เครื่องมือที่ Git โปรเจกต์หลักแนะนำอย่างเป็นทางการในปัจจุบัน** ให้ใช้แทนทั้ง `filter-branch` และ BFG เร็วกว่า ปลอดภัยกว่า ยืดหยุ่นกว่า และดูแลรักษาอย่างต่อเนื่อง |

ด้วยเหตุนี้ Part นี้จะสอน `git filter-repo` เป็นหลัก เพราะเป็นเครื่องมือที่ถูกต้องและเหมาะสมที่สุดสำหรับงานนี้ในปัจจุบัน

### การติดตั้ง `git filter-repo`

`git filter-repo` ไม่ได้มากับ Git โดยตรง (ไม่เหมือน `filter-branch`) ต้องติดตั้งแยกต่างหาก:

```bash
# macOS (ผ่าน Homebrew)
brew install git-filter-repo

# Linux (ผ่าน pip เนื่องจากตัวเครื่องมือเขียนด้วย Python)
pip install git-filter-repo

# ตรวจสอบว่าติดตั้งสำเร็จ
git filter-repo --version
```

### ข้อควรระวังที่สำคัญที่สุดก่อนเริ่มใช้งาน

`git filter-repo` เป็นเครื่องมือที่ **เขียนประวัติ Git ใหม่ทั้งหมด (rewrite history)** ซึ่งหมายความว่า:

1. **SHA-1 hash ของทุก commit ที่ถูกแก้ไขจะเปลี่ยนไปทั้งหมด** — เพราะเนื้อหาเปลี่ยน hash จึงเปลี่ยนตามหลักการที่เราเรียนใน Part 56 (Git Internals)
2. **ทุกคนในทีมต้อง clone repository ใหม่ทั้งหมด** — จะ `git pull` ตามปกติไม่ได้ เพราะประวัติเก่ากับใหม่ diverge กันโดยสิ้นเชิง
3. **Pull Request / Merge Request ที่เปิดค้างอยู่อาจได้รับผลกระทบ** — ควรปิดหรือ merge ให้เสร็จก่อนทำ หรือเตรียมเปิดใหม่หลังจากนั้น
4. **ควรทำ backup repository ทั้งหมดไว้ก่อนเสมอ** ก่อนเริ่มกระบวนการนี้

```bash
# สำรอง repository ทั้งหมดไว้ก่อนเสมอ ก่อนแก้ไขประวัติ
cp -r my-project my-project-backup-before-filter-repo
```

### ขั้นตอนการใช้ `git filter-repo` ลบไฟล์ที่มี secret ออกจากประวัติทั้งหมด

สมมติว่าไฟล์ `config/database.yml` เคยถูก commit ไปพร้อมกับ credential ของฐานข้อมูลในอดีต (สมมติเหตุการณ์เพื่อการสอน ไม่ใช่ค่าจริง) ขั้นตอนที่ถูกต้องมีดังนี้:

```bash
# ขั้นตอนที่ 1: clone repository แบบ "fresh mirror clone" ใหม่ล้วน ๆ
# (ไม่ใช้ working copy เดิมที่มีอยู่แล้ว เพื่อความปลอดภัย)
git clone --mirror https://example-git-host.internal/team/my-project.git
cd my-project.git

# ขั้นตอนที่ 2: รัน filter-repo เพื่อลบไฟล์ออกจากทุก commit ในประวัติ
git filter-repo --path config/database.yml --invert-paths

# --path config/database.yml  = ระบุไฟล์เป้าหมาย
# --invert-paths              = หมายถึง "ลบไฟล์นี้ออก" (ตรงข้ามกับการเก็บเฉพาะไฟล์นี้ไว้)
```

หากต้องการลบหลายไฟล์พร้อมกัน หรือลบทั้งโฟลเดอร์:

```bash
git filter-repo \
  --path config/database.yml \
  --path .env \
  --path secrets/ \
  --invert-paths
```

### กรณีที่ secret ไม่ได้อยู่ในไฟล์แยก แต่ฝังอยู่ในโค้ดโดยตรง

บางครั้ง secret ไม่ได้อยู่ในไฟล์ config แยก แต่ถูก hardcode ไว้กลางไฟล์โค้ด เช่นเขียนไว้เป็นค่าคงที่กลางไฟล์ `.py` หรือ `.js` ในกรณีนี้การลบทั้งไฟล์ออกอาจไม่เหมาะสมเพราะไฟล์นั้นยังมีโค้ดส่วนอื่นที่จำเป็นต้องเก็บไว้ `git filter-repo` รองรับการแทนที่ **ข้อความ (text replacement)** แทนการลบทั้งไฟล์ได้ ผ่านไฟล์ replacement:

```bash
# สร้างไฟล์ replacements.txt ระบุข้อความที่ต้องการแทนที่ในทุก commit
cat > replacements.txt << 'EOF'
<ค่าคีย์เดิมที่หลุดไป-ระบุแบบเฉพาะเจาะจง>==><FAKE_API_KEY_FOR_DEMO>
EOF

git filter-repo --replace-text replacements.txt
```

คำสั่งนี้จะไล่แทนที่ข้อความที่ระบุด้วยค่าใหม่ (เช่นข้อความบอกว่า "ถูกลบแล้ว") **ในทุก commit ที่เคยมีข้อความนั้นปรากฏอยู่** โดยไม่ต้องลบไฟล์ทั้งไฟล์ทิ้ง

### ขั้นตอนหลังจากลบประวัติสำเร็จ

```bash
# ขั้นตอนที่ 3: force push ประวัติใหม่กลับไปยัง remote
# (จำเป็นต้อง force เพราะประวัติถูกเขียนใหม่ทั้งหมด)
git push origin --force --all
git push origin --force --tags

# ขั้นตอนที่ 4: แจ้งทุกคนในทีมให้ clone ใหม่ทั้งหมด (ห้าม pull ทับของเดิม)
```

ทีมทุกคนต้อง:

```bash
# ❌ ห้ามทำแบบนี้ — จะทำให้เกิด conflict มหาศาลเพราะประวัติ diverge กันหมด
git pull

# ✅ ต้องทำแบบนี้แทน — ลบสำเนาเดิมแล้ว clone ใหม่ทั้งหมด

git clone https://example-git-host.internal/team/my-project.git
```

### สิ่งที่ `git filter-repo` ทำ**ไม่ได้**

ต้องเข้าใจให้ชัดเจนว่า `git filter-repo` **ไม่ใช่ยาวิเศษ**:

1. **ไม่สามารถลบสำเนาที่มีคน clone ไปแล้วก่อนหน้านี้ได้** — นี่คือเหตุผลที่ Step 773 ย้ำว่าต้อง revoke ก่อนเสมอ
2. **ไม่สามารถลบ cache ที่แพลตฟอร์มโฮสต์เก็บไว้ได้ทันที** — บาง repository ที่มี fork หรือ pull request ที่อ้างอิง commit เก่าอยู่ อาจยังมี object เก่าหลงเหลืออยู่ในระบบของแพลตฟอร์มโฮสต์ ในหลายกรณีต้องติดต่อฝ่าย support ของแพลตฟอร์มโดยตรงเพื่อขอให้ล้าง cache/garbage-collect เก่าทิ้งจริง ๆ
3. **ไม่ทดแทนการ revoke** — ทำหน้าที่แค่ "ทำความสะอาดประวัติในระยะยาว" เท่านั้น

### สรุปหลักคิดของ Step นี้

> **`git filter-repo` คือเครื่องมือมาตรฐานปัจจุบันสำหรับลบข้อมูลออกจากประวัติ Git ทั้งหมด แต่ต้องใช้หลัง revoke เสมอ ต้อง backup ก่อนใช้เสมอ และต้องประสานงานให้ทั้งทีม clone ใหม่หลังใช้เสร็จเสมอ**

## Step 775: เครื่องมือสแกนหา secret อัตโนมัติ — git-secrets, trufflehog, gitleaks

### ทำไมต้องมีเครื่องมือสแกนอัตโนมัติ

จาก Step 772 เราเรียนไปแล้วว่า `.gitignore` และการตรวจสอบด้วยตาเป็นด่านป้องกันขั้นต้น แต่มนุษย์ผิดพลาดได้เสมอ โดยเฉพาะเมื่อทีมโตขึ้น มีคน commit จำนวนมากต่อวัน การพึ่งพาความระมัดระวังของมนุษย์อย่างเดียวไม่เพียงพอ จึงต้องมี **เครื่องมือสแกนอัตโนมัติ** ที่ทำงานตามรูปแบบ (pattern) ของ secret ที่รู้จัก เพื่อจับก่อนที่มันจะหลุดออกไป

เครื่องมือกลุ่มนี้ทำงานโดยหลักการเดียวกันคือ: **ไล่สแกนเนื้อหาของไฟล์ (หรือประวัติ commit) เทียบกับชุดกฎ/pattern ที่รู้จักว่าหน้าตาแบบไหนคือ secret ที่น่าสงสัย** เช่น รูปแบบเฉพาะของผู้ให้บริการแต่ละราย ความยาวและความสุ่ม (entropy) ของ string หรือชื่อตัวแปรที่มักบ่งบอกว่าเป็นค่าลับ (เช่นตัวแปรที่ชื่อมีคำว่า "key", "secret", "token", "password" ประกอบกับค่าที่มีความสุ่มสูง)

### git-secrets

**git-secrets** เป็นเครื่องมือที่พัฒนาโดยทีม AWS Labs ทำงานในรูปแบบ **Git hook** (เชื่อมโยงกับ Git Hooks ที่เราเรียนไปแล้วใน Part 59) โดยจะสแกนก่อนที่การ commit จะสำเร็จ

```bash
# ติดตั้ง git-secrets (ตัวอย่างบน macOS ผ่าน Homebrew)
brew install git-secrets

# ติดตั้ง hook เข้ากับ repository ปัจจุบัน
cd my-project
git secrets --install

# เพิ่มชุด pattern มาตรฐานสำหรับตรวจจับรูปแบบ credential ของผู้ให้บริการ cloud ที่พบบ่อย
git secrets --register-aws

# ทดสอบสแกนทั้ง repository ย้อนหลัง
git secrets --scan-history
```

จุดเด่นของ `git-secrets` คือทำงานเป็น `pre-commit` hook โดยตรง หมายความว่ามันจะ **บล็อกการ commit ทันทีตั้งแต่ต้นทาง** ก่อนที่ secret จะเข้าไปอยู่ใน local repository ด้วยซ้ำ ไม่ต้องรอไปถึงขั้นตอน push

### trufflehog

**trufflehog** มีจุดเด่นตรงที่สแกน**ประวัติทั้งหมดของ repository ย้อนหลัง** ไม่ใช่แค่ commit ปัจจุบัน โดยใช้ทั้งการจับ pattern เฉพาะของผู้ให้บริการแต่ละราย และการวิเคราะห์ค่า entropy (ความสุ่ม) ของ string เพื่อตรวจจับ secret ที่อาจไม่ตรง pattern ที่รู้จักตรง ๆ

```bash
# สแกนทั้งประวัติของ repository ที่อยู่ใน local
trufflehog git file://./my-project

# สแกน repository จาก URL โดยตรงโดยไม่ต้อง clone มาก่อน
trufflehog git https://example-git-host.internal/team/my-project.git

# กรองผลลัพธ์เฉพาะกรณีที่ยืนยันได้ว่า secret นั้นยัง "ใช้งานได้จริง" (verified)
trufflehog git file://./my-project --only-verified
```

คุณสมบัติ `--only-verified` มีประโยชน์มากในทีมขนาดใหญ่ เพราะ trufflehog สามารถลองตรวจสอบกับ API ปลายทางจริง (ในกรณีที่ปลอดภัยที่จะทำ) ว่า secret ที่พบยัง active อยู่หรือไม่ ช่วยลด false positive และช่วยจัดลำดับความสำคัญว่าอันไหนต้อง revoke ด่วนที่สุด

### gitleaks

**gitleaks** เป็นเครื่องมือที่ได้รับความนิยมสูงมากในปัจจุบัน เพราะเร็ว ปรับแต่งกฎเองได้ง่ายผ่านไฟล์ config รูปแบบ TOML และรองรับการรันได้ทั้งแบบสแกนครั้งเดียว แบบ pre-commit hook และแบบ CI/CD pipeline

```bash
# สแกน repository ปัจจุบันทั้งประวัติ
gitleaks detect --source . --verbose

# สแกนเฉพาะสิ่งที่ staged ไว้ก่อน commit (ใช้คู่กับ pre-commit hook ได้พอดี)
gitleaks protect --staged --verbose
```

ตัวอย่างการปรับแต่งกฎเพิ่มเติมด้วยไฟล์ `.gitleaks.toml`:

```toml
title = "gitleaks config สำหรับโปรเจกต์นี้"

[[rules]]
id = "internal-service-token"
description = "ตรวจจับรูปแบบ token เฉพาะของระบบภายในองค์กร"
regex = '''internal_token_[A-Za-z0-9]{32,}'''
tags = ["token", "internal"]

[allowlist]
description = "ยกเว้นไฟล์ตัวอย่างที่ตั้งใจใส่ค่าจำลองไว้"
paths = [
  '''\.env\.example$''',
  '''docs/.*\.md$'''
]
```

### ตารางเปรียบเทียบเครื่องมือทั้งสาม

| เครื่องมือ | จุดเด่น | เหมาะกับ |
|---|---|---|
| **git-secrets** | ทำงานเป็น pre-commit hook ตรงไปตรงมา บล็อกตั้งแต่ต้นทาง | ทีมที่ต้องการป้องกันตั้งแต่ก่อน commit เข้า local history |
| **trufflehog** | สแกนประวัติย้อนหลังลึก + ตรวจสอบว่า secret ยัง active จริงหรือไม่ (verified) | ตรวจสอบ repository เก่าที่สงสัยว่าอาจมี secret หลงเหลืออยู่ |
| **gitleaks** | เร็ว ปรับแต่ง rule เองได้ง่าย ใช้ได้ทั้ง local hook และ CI/CD | ทีมที่ต้องการความยืดหยุ่นสูงและรวมเข้ากับ pipeline |

### เชื่อมโยงกับ Secret Detection ของ GitLab (Part 54)

ใน **Part 54: GitLab Security Features** เราได้เรียนไปแล้วว่า GitLab มีฟีเจอร์ **Secret Detection** ในตัวที่ทำงานเป็นส่วนหนึ่งของ `.gitlab-ci.yml` pipeline โดยอัตโนมัติ ซึ่งเบื้องหลังการทำงานของฟีเจอร์นี้ใช้หลักการเดียวกันทุกประการกับเครื่องมือที่กล่าวถึงในนี้ (การจับ pattern เฉพาะของผู้ให้บริการแต่ละราย + วิเคราะห์ entropy) เพียงแต่ GitLab ทำให้มันทำงานอัตโนมัติในทุก merge request โดยไม่ต้องติดตั้งเครื่องมือแยกเอง

ในทางปฏิบัติ ทีมที่ใช้ GitLab มักจะได้ประโยชน์จาก Secret Detection ในตัวอยู่แล้วเป็นด่านที่สอง (รองจาก pre-commit hook ในเครื่องนักพัฒนาเองที่เป็นด่านแรก) ส่วนทีมที่ใช้ GitHub มักต้องพึ่งพา GitHub push protection (ฟีเจอร์ที่บล็อกการ push ถ้าตรวจพบรูปแบบ secret ที่รู้จัก) ร่วมกับเครื่องมืออย่าง gitleaks หรือ trufflehog ที่รันเสริมใน CI/CD ของตัวเอง

### หลักการ "Defense in Depth" กับการสแกน secret

จุดสำคัญที่สุดของ Step นี้คือ **ไม่ควรพึ่งพาเครื่องมือใดเครื่องมือเดียว** ทีมมืออาชีพมักวางด่านป้องกันหลายชั้นพร้อมกัน:

```
ด่านที่ 1: Pre-commit hook ในเครื่องนักพัฒนา (git-secrets / gitleaks protect)
       │
       ▼
ด่านที่ 2: Push protection ของแพลตฟอร์มโฮสต์ (GitHub push protection / GitLab Secret Detection)
       │
       ▼
ด่านที่ 3: สแกนเต็มรูปแบบใน CI/CD pipeline (gitleaks detect / trufflehog ทุกครั้งที่มี merge)
       │
       ▼
ด่านที่ 4: สแกนย้อนหลังทั้ง repository เป็นระยะ (audit ประจำไตรมาส/ประจำปี)
```

แต่ละด่านจับ secret ในจังหวะที่ต่างกัน ทำให้ต่อให้ด่านหนึ่งพลาดไป ยังมีด่านถัดไปคอยจับซ้ำอยู่เสมอ

## Step 776: Secret Management ระดับองค์กร — HashiCorp Vault, AWS Secrets Manager, CI/CD Variables

### ปัญหาของการเก็บ secret แบบกระจัดกระจาย

เมื่อทีมและระบบโตขึ้น การเก็บ secret ไว้ในไฟล์ `.env` บนเครื่องนักพัฒนาแต่ละคน หรือส่งต่อกันผ่านแชทภายในทีม จะเริ่มมีปัญหาหลายด้าน:

1. **ไม่มีจุดศูนย์กลางในการจัดการ** — ไม่รู้ว่า secret ตัวไหนถูกใช้ที่ไหนบ้าง เมื่อต้อง rotate จะไม่รู้ว่าต้องไปแก้ที่กี่จุด
2. **ไม่มี audit trail** — ไม่รู้ว่าใครเข้าถึง secret ตัวไหนเมื่อไหร่
3. **การ revoke/rotate ทำได้ยากและช้า** — ต้องไล่แก้ไขในหลายที่พร้อมกัน เสี่ยงตกหล่น
4. **สิทธิ์การเข้าถึงหยาบเกินไป** — คนที่เข้าถึง secret หนึ่งตัวมักเข้าถึงได้ทั้งหมด ไม่สามารถจำกัดสิทธิ์แบบละเอียดได้

องค์กรระดับที่มีความสมบูรณ์แบบด้าน security สูงจึงหันมาใช้ **ระบบ Secret Management โดยเฉพาะ** แทนการกระจาย secret ไว้ในไฟล์ทั่วไป

### HashiCorp Vault

**HashiCorp Vault** คือระบบจัดการ secret แบบรวมศูนย์ที่ได้รับความนิยมสูงมากในระดับ enterprise แนวคิดหลักของ Vault คือ:

> **Secret ไม่ได้ถูกเก็บแบบ static ไว้ตลอดไป แต่สามารถถูกสร้างแบบ dynamic ชั่วคราว (short-lived) และหมดอายุอัตโนมัติได้**

คุณสมบัติเด่นของ Vault:

- **Dynamic Secrets** — สามารถสร้าง credential ของฐานข้อมูลหรือบริการ cloud แบบชั่วคราว มีอายุการใช้งานจำกัด (เช่น 1 ชั่วโมง) แล้วหมดอายุอัตโนมัติโดยไม่ต้องมีใครมา revoke เอง
- **Encryption as a Service** — ให้บริการเข้ารหัส/ถอดรหัสข้อมูลโดยที่แอปพลิเคชันไม่ต้องเก็บ encryption key ไว้เองเลย
- **Access Control ละเอียด** — กำหนดได้ว่าใคร/ระบบไหน เข้าถึง secret ตัวไหนได้ ในเงื่อนไขอะไรบ้าง
- **Audit Logging ครบถ้วน** — บันทึกทุกการเข้าถึง secret ไว้ตรวจสอบย้อนหลังได้เสมอ
- **Secret Versioning** — เก็บประวัติเวอร์ชันของ secret ไว้ ย้อนกลับได้หากจำเป็น

ตัวอย่างแนวคิดการทำงาน (แบบย่อ ไม่ใช่ค่าจริง):

```
แอปพลิเคชันต้องการเชื่อมต่อฐานข้อมูล
       │
       ▼
แอปขอ credential จาก Vault (ผ่านการยืนยันตัวตนของแอปเอง เช่น ผ่าน token ของระบบ)
       │
       ▼
Vault สร้าง username/password ชั่วคราวใหม่ ให้สิทธิ์ตามที่กำหนดไว้ล่วงหน้า
       │
       ▼
แอปใช้ credential นั้นเชื่อมต่อฐานข้อมูล
       │
       ▼
เมื่อครบเวลาที่กำหนด (เช่น 1 ชั่วโมง) Vault จะยกเลิก credential ตัวนั้นโดยอัตโนมัติ
```

ข้อดีมหาศาลของแนวทางนี้คือ **แม้ credential จะหลุดออกไปโดยไม่ตั้งใจ (เช่นติดไปใน log) มันก็จะหมดอายุใช้งานไม่ได้เองภายในเวลาสั้น ๆ อยู่ดี** ลดความเสียหายได้มากเมื่อเทียบกับ static credential ที่ใช้ได้ตลอดไปจนกว่าจะมีคนมา revoke เอง

### AWS Secrets Manager

**AWS Secrets Manager** คือบริการจัดการ secret ของผู้ให้บริการ cloud รายใหญ่ ทำหน้าที่คล้าย Vault แต่ผูกอยู่กับระบบนิเวศของผู้ให้บริการนั้นโดยเฉพาะ คุณสมบัติหลัก:

- **Automatic Rotation** — ตั้งค่าให้ระบบหมุนเวียน (rotate) credential ของฐานข้อมูลหรือบริการอื่นให้อัตโนมัติตามรอบเวลาที่กำหนด โดยไม่ต้องมีใครมาแก้ไขค่าด้วยมือ
- **Fine-grained Access Control** — ผูกกับระบบสิทธิ์ของผู้ให้บริการ cloud โดยตรง กำหนดได้ละเอียดว่า service/role ไหนเข้าถึง secret ตัวไหนได้
- **Integration กับบริการอื่นในระบบนิเวศเดียวกัน** — เชื่อมต่อกับบริการคำนวณ ฐานข้อมูล และบริการ container ในเครือเดียวกันได้อย่างสะดวก
- **Encryption at Rest** — เข้ารหัส secret ที่เก็บไว้ด้วยระบบจัดการคีย์ของผู้ให้บริการเองเสมอ

หลักการสำคัญที่เหมือนกับ Vault คือ: **แอปพลิเคชันไม่ควรรู้ค่า secret แบบ hardcode ไว้เลย แต่ต้อง "ขอ" มาจากระบบกลางในเวลาที่ต้องใช้งานจริงเท่านั้น**

### CI/CD Secret Variables — เครื่องมือที่เรียนไปแล้ว

ในเฟส 7 ของหลักสูตรนี้ เราได้เรียนรู้เรื่อง CI/CD Pipeline ทั้งของ GitHub Actions และ GitLab CI/CD ไปแล้ว ซึ่งทั้งสองแพลตฟอร์มมีระบบเก็บ **secret variables** ในตัว (เช่น GitHub Actions Secrets และ GitLab CI/CD Variables ที่ตั้งค่าแบบ "Protected" และ "Masked" ได้) ระบบเหล่านี้คือรูปแบบหนึ่งของ secret management เช่นกัน เพียงแต่ขอบเขตจำกัดอยู่แค่ในบริบทของ pipeline เท่านั้น

หลักการที่ควรจำจาก Step นี้คือ:

> **secret ของ CI/CD pipeline (เช่นตัวแปรลับที่ตั้งค่าไว้ในหน้าตั้งค่า repository) ไม่ควรถูกเขียนอยู่ในไฟล์ pipeline โดยตรง (เช่น `.gitlab-ci.yml` หรือ workflow YAML ของ GitHub Actions) แต่ต้องถูกอ้างอิงผ่านตัวแปรที่ระบบเก็บแยกไว้ต่างหากเสมอ**

ยกตัวอย่างแนวคิดการอ้างอิงในไฟล์ pipeline (ไม่ใช่ค่าจริง เป็นเพียงชื่อ placeholder):

```yaml
# ตัวอย่างแนวคิดใน pipeline — อ้างอิงชื่อตัวแปร ไม่ใช่ค่าจริง
deploy:
  script:
    - deploy-tool --api-key "$DEPLOY_API_KEY"
  # DEPLOY_API_KEY ถูกตั้งค่าไว้ในหน้า Settings ของ repository/project เท่านั้น
  # ไม่มีค่าจริงปรากฏอยู่ในไฟล์นี้เลย
```

### ตารางเปรียบเทียบตัวเลือก Secret Management

| ตัวเลือก | เหมาะกับ | ข้อจำกัด |
|---|---|---|
| HashiCorp Vault | องค์กรที่ต้องการควบคุมเต็มรูปแบบ ใช้ได้ข้ามผู้ให้บริการ cloud หลายเจ้า | ต้องดูแลระบบเองถ้า self-host มีความซับซ้อนในการตั้งค่าเริ่มต้น |
| AWS Secrets Manager | ทีมที่ใช้ระบบนิเวศของผู้ให้บริการ cloud รายเดียวเป็นหลัก | ผูกกับผู้ให้บริการรายนั้น ย้ายไปเจ้าอื่นทำได้ยากกว่า |
| CI/CD Secret Variables | secret ที่ใช้เฉพาะในขั้นตอน build/deploy ของ pipeline | ขอบเขตจำกัดแค่ใน pipeline ไม่เหมาะเป็นระบบกลางขององค์กร |

### สรุปหลักคิดของ Step นี้

> **ยิ่งองค์กรโตขึ้น secret ยิ่งต้องถูกจัดการแบบรวมศูนย์ มีการหมุนเวียนอัตโนมัติ และมี audit trail ที่ตรวจสอบได้ แทนที่จะกระจัดกระจายอยู่ในไฟล์ `.env` บนเครื่องของแต่ละคน**

## Step 777: ใช้ Environment Variables แทนการ hardcode secret ในโค้ด

### ปัญหาของการ hardcode secret ในโค้ด

การเขียนค่า secret ไว้ตรง ๆ ในซอร์สโค้ด (hardcoding) คือต้นตอของปัญหาเกือบทั้งหมดที่กล่าวถึงมาตลอด Part นี้ ตัวอย่างรูปแบบที่ผิดพลาด (แสดงเป็นแนวคิด ไม่ใช้ค่าจริง):

```python
# ❌ ผิดอย่างร้ายแรง — hardcode ค่า secret ไว้ตรงในโค้ด
import requests

def call_payment_api():
    api_key = "<ค่าคีย์จริงถูกเขียนไว้ตรงนี้>"  # อันตรายมาก
    response = requests.get(
        "https://payment-provider.example.com/v1/charge",
        headers={"Authorization": f"Bearer {api_key}"}
    )
    return response.json()
```

ปัญหาของโค้ดแบบนี้:

1. ทุกคนที่เห็นโค้ด (ทั้งในทีมและใครก็ตามที่เข้าถึง repository ได้) เห็นค่า secret ทันที
2. ค่าเดียวกันถูกใช้ทั้งใน environment สำหรับพัฒนา ทดสอบ และ production เพราะมันถูกเขียนตายตัวไว้ในโค้ด ไม่สามารถสลับค่าตาม environment ได้เลยโดยไม่แก้โค้ด
3. เมื่อต้อง rotate secret ต้องแก้โค้ด commit ใหม่ deploy ใหม่ทุกครั้ง แทนที่จะแค่เปลี่ยนค่าตัวแปรที่จุดเดียว
4. secret จะติดอยู่ในประวัติ Git ตลอดไปตามที่อธิบายใน Step 771–774

### วิธีที่ถูกต้อง: อ่านค่าจาก Environment Variables

```python
# ✅ ถูกต้อง — อ่านค่าจาก environment variable แทนการ hardcode
import os
import requests

def call_payment_api():
    api_key = os.environ.get("PAYMENT_API_KEY")
    if not api_key:
        raise RuntimeError("ไม่พบตัวแปร PAYMENT_API_KEY กรุณาตั้งค่าก่อนรันโปรแกรม")

    response = requests.get(
        "https://payment-provider.example.com/v1/charge",
        headers={"Authorization": f"Bearer {api_key}"}
    )
    return response.json()
```

ตัวอย่างในภาษา JavaScript / Node.js:

```javascript
// ✅ ถูกต้อง — อ่านค่าจาก process.env แทนการ hardcode
const apiKey = process.env.PAYMENT_API_KEY;

if (!apiKey) {
  throw new Error("ไม่พบตัวแปร PAYMENT_API_KEY กรุณาตั้งค่าก่อนรันโปรแกรม");
}

async function callPaymentApi() {
  const response = await fetch("https://payment-provider.example.com/v1/charge", {
    headers: { Authorization: `Bearer ${apiKey}` },
  });
  return response.json();
}
```

### การโหลดค่าจากไฟล์ `.env` เข้าสู่ environment variable

ในเครื่อง local เพื่อความสะดวกระหว่างพัฒนา นิยมใช้ library ที่ช่วยโหลดค่าจากไฟล์ `.env` (ไฟล์ที่ถูกป้องกันด้วย `.gitignore` ตามที่เรียนใน Step 772) เข้าสู่ environment variable ของกระบวนการโดยอัตโนมัติ:

```python
# Python: ใช้ library python-dotenv
from dotenv import load_dotenv
import os

load_dotenv()  # โหลดค่าจากไฟล์ .env เข้าสู่ os.environ โดยอัตโนมัติ

api_key = os.environ.get("PAYMENT_API_KEY")
```

```javascript
// Node.js: ใช้ library dotenv
require("dotenv").config();  // โหลดค่าจากไฟล์ .env เข้าสู่ process.env โดยอัตโนมัติ

const apiKey = process.env.PAYMENT_API_KEY;
```

ข้อสำคัญ: **ไฟล์ `.env` ใช้เพื่อความสะดวกในเครื่อง local เท่านั้น** ในสภาพแวดล้อม production จริง ค่าตัวแปรมักถูกตั้งผ่านระบบของแพลตฟอร์มที่ใช้ deploy โดยตรง (เช่นตั้งค่าผ่านหน้า configuration ของบริการ hosting หรือดึงมาจากระบบ secret management อย่าง Vault/Secrets Manager ตามที่กล่าวใน Step 776) ไม่ได้อ่านจากไฟล์ `.env` บน server production โดยตรงเสมอไป

### ข้อควรระวังเพิ่มเติมแม้จะใช้ Environment Variables แล้ว

การย้ายมาใช้ environment variables ช่วยแก้ปัญหาหลักได้ แต่ยังมีจุดที่ต้องระวังเพิ่มเติม:

1. **ระวัง secret หลุดผ่าน log** — ถ้าโปรแกรม log ค่าตัวแปรทั้งหมดออกมาตอน debug (เช่น log `process.env` ทั้งก้อน) secret ก็จะไปปรากฏอยู่ใน log file แทน ซึ่งอาจถูกเก็บไว้อย่างไม่ปลอดภัยพอ ๆ กับการหลุดเข้า Git
2. **ระวัง secret หลุดผ่าน error message** — ข้อความ error ที่แสดง stack trace หรือค่าตัวแปรตอน exception บางครั้งอาจเผลอแสดงค่า secret ออกมาด้วย
3. **ระวังการ commit ไฟล์ dump ของ environment** — เช่นไฟล์ core dump หรือไฟล์ export ตัวแปรสภาพแวดล้อมทั้งหมดที่นักพัฒนาสร้างขึ้นเพื่อ debug แล้วลืมลบ
4. **แยก environment variable ตามสภาพแวดล้อมเสมอ** — ค่าที่ใช้ใน development, staging, production ควรเป็นคนละชุดกันเสมอ ไม่ควรใช้ credential ชุดเดียวกันข้าม environment

### สรุปหลักคิดของ Step นี้

> **Environment Variables คือกลไกพื้นฐานที่สุดในการแยก secret ออกจากโค้ด — โค้ดรู้แค่ "ชื่อตัวแปร" ส่วน "ค่าจริง" ถูกกำหนดแยกต่างหากในแต่ละสภาพแวดล้อมที่รันจริง**

หลักการนี้จะนำไปสู่แนวคิดที่กว้างกว่าใน Step ถัดไป นั่นคือหลักการ 12-Factor App

## Step 778: หลักการ 12-Factor App ข้อที่ 3 (Config) — แยก config ออกจากโค้ดเสมอ

### 12-Factor App คืออะไร

**12-Factor App** คือชุดหลักการออกแบบซอฟต์แวร์ 12 ข้อที่รวบรวมแนวปฏิบัติที่ดีสำหรับการสร้างแอปพลิเคชันสมัยใหม่ที่ทำงานได้ดีบน cloud มีความสามารถขยายตัวได้ง่าย (scalable) และดูแลรักษาง่าย หลักการนี้ถูกเผยแพร่และได้รับการยอมรับอย่างกว้างขวางในวงการพัฒนาซอฟต์แวร์สมัยใหม่ โดยเฉพาะในบริบทของ DevOps และ Cloud-Native Application

แม้ Part นี้จะไม่ได้เจาะลึกครบทั้ง 12 ข้อ (เพราะเป้าหมายหลักคือเรื่อง Secret Management) แต่ข้อที่เกี่ยวข้องโดยตรงกับหัวข้อของเราคือ **ข้อที่ 3: Config**

### หลักการของข้อที่ 3: Config

> **"Store config in the environment" — เก็บค่า config ไว้ใน environment ไม่ใช่ในโค้ด**

หลักการนี้นิยาม **config** ไว้อย่างชัดเจนว่าคือ **ทุกสิ่งที่มีค่าแตกต่างกันไปตามแต่ละสภาพแวดล้อมที่ deploy** (development, staging, production) ซึ่งรวมถึง:

- Credential ของฐานข้อมูลและบริการภายนอก (นี่คือ secret ที่เราพูดถึงตลอด Part นี้)
- ที่อยู่ (hostname) ของบริการที่เชื่อมต่อ
- ค่าคงที่เฉพาะของแต่ละ deploy เช่น domain name

หลักการสำคัญที่สุดคือการแบ่งแยกให้ชัดเจนระหว่าง **โค้ด** กับ **config**:

```
โค้ด (Code)                          Config
├── ตรรกะทางธุรกิจ                    ├── Database credential
├── โครงสร้างของแอปพลิเคชัน            ├── API key ของบริการภายนอก
├── การไหลของข้อมูล                   ├── URL ของบริการที่เชื่อมต่อ
└── ควรเหมือนกันทุก environment       └── ต่างกันไปในแต่ละ environment
```

### ทำไมข้อนี้ถึงเชื่อมโยงกับ Secret Management โดยตรง

หลักการ 12-Factor App ให้เกณฑ์ตัดสินใจที่ชัดเจนมากว่า **อะไรควรอยู่ในโค้ด อะไรไม่ควร**:

> **ถ้าค่าไหนต้องเปลี่ยนไปตาม environment ที่ deploy (dev/staging/production) หรือถ้าค่าไหนคือความลับที่ต้องปกปิด ค่านั้นไม่ควรอยู่ในโค้ด (และไม่ควรอยู่ในไฟล์ที่ถูก commit เข้า Git) เด็ดขาด**

เกณฑ์นี้ตอบโจทย์ตรงกับปัญหา secret หลุดเข้า Git ที่เราพูดถึงมาตลอด Part นี้พอดี เพราะ:

- Secret แทบทุกประเภทที่กล่าวถึงใน Step 771 (database credential, API key, access key) **ล้วนเป็น config ตามนิยามนี้ทั้งสิ้น** เพราะมันต่างกันไปตาม environment (credential ของ development แตกต่างจาก production เสมอ) และเป็นความลับที่ต้องปกปิด
- เมื่อยึดหลัก "config อยู่ใน environment" อย่างเคร่งครัด จะไม่มีทางที่ secret จะไปอยู่ในไฟล์ source code ที่ commit เข้า Git ได้เลยตั้งแต่แรก เพราะมันไม่ควรอยู่ในโค้ดตั้งแต่ต้น

### กฎย่อยที่สำคัญ: Config ไม่ควรถูกจัดกลุ่มเป็น "environment" (dev/staging/prod) แบบตายตัวในโค้ดด้วยเช่นกัน

12-Factor App ยังเตือนอีกจุดที่มือใหม่มักเข้าใจผิด นั่นคือการเขียนโค้ดแบบนี้ (ซึ่งดูเหมือนถูกแล้วแต่จริง ๆ ยังไม่ถูกทั้งหมด):

```python
# ⚠️ ยังไม่ใช่แนวทางที่ดีที่สุดตามหลัก 12-Factor
import os

env = os.environ.get("APP_ENV", "development")

if env == "production":
    api_key = "<ค่าคีย์ production ถูกเขียนไว้ในโค้ด>"
elif env == "staging":
    api_key = "<ค่าคีย์ staging ถูกเขียนไว้ในโค้ด>"
else:
    api_key = "<ค่าคีย์ development ถูกเขียนไว้ในโค้ด>"
```

ปัญหาของรูปแบบนี้คือยังคง hardcode ค่าทุก environment ไว้ในโค้ดอยู่ดี เพียงแค่มีเงื่อนไขแยกตาม environment เท่านั้น ซึ่งขัดกับหลักการโดยตรง วิธีที่ถูกต้องตามหลัก 12-Factor คือ:

```python
# ✅ ถูกต้องตามหลัก 12-Factor App — ไม่มีค่าใด ๆ อยู่ในโค้ดเลย
import os

api_key = os.environ.get("PAYMENT_API_KEY")
# ค่าจริงถูกกำหนดแยกไว้นอกโค้ดโดยสิ้นเชิง
# environment ไหนก็อ่านตัวแปรชื่อเดียวกันนี้ แค่ค่าที่ตั้งไว้ต่างกันไปในแต่ละที่
```

จำนวน environment ในระบบสามารถเพิ่มได้ตามต้องการ (development, staging, QA, production, disaster-recovery ฯลฯ) **โดยไม่ต้องแก้โค้ดแม้แต่บรรทัดเดียว** เพราะโค้ดไม่รู้จักและไม่สนใจว่ามันกำลังรันอยู่บน environment ไหน มันรู้แค่ชื่อตัวแปรที่ต้องอ่านเท่านั้น

### เชื่อมโยงกลับไปที่ CI/CD และ Secret Manager

หลักการนี้อธิบายได้ว่าทำไมเครื่องมือที่เรียนไปแล้วใน Step 776 (CI/CD secret variables, Vault, AWS Secrets Manager) ถึงถูกออกแบบมาในรูปแบบที่เป็นอยู่: **ทุกระบบเหล่านี้คือกลไกที่ทำให้ config/secret "อยู่นอกโค้ด" ได้จริงในทางปฏิบัติ** ไม่ว่าจะเป็นการฉีดค่าตัวแปรเข้าไปตอน pipeline รัน หรือการให้แอปพลิเคชัน "ขอ" ค่ามาตอน runtime จากระบบกลาง

### สรุปหลักคิดของ Step นี้

> **หลักการ Config ของ 12-Factor App สรุปสั้น ๆ ได้ว่า "โค้ดควรเหมือนกันทุกที่ที่มันรัน สิ่งที่ต่างกันไปในแต่ละที่ (รวมถึงทุก secret) ต้องอยู่นอกโค้ดเสมอ" — นี่คือรากฐานทางทฤษฎีที่อธิบายว่าทำไมกฎทองใน Step 772 ถึงสำคัญ**

## Step 779: Pre-commit Hook ป้องกัน secret หลุดตั้งแต่ต้นทาง

### ทบทวน Git Hooks จาก Part 59

ใน **Part 59: Git Hooks: Client-side Hooks** เราเรียนไปแล้วว่า **`pre-commit` hook** คือสคริปต์ที่ Git รันโดยอัตโนมัติ **ก่อน** ที่การ commit จะสำเร็จ ถ้าสคริปต์นั้น exit ด้วยค่าที่ไม่ใช่ 0 (คือมีข้อผิดพลาด) Git จะ **ยกเลิกการ commit นั้นทันที** ผู้ใช้ต้องแก้ไขปัญหาก่อนจึงจะ commit ผ่านได้

คุณสมบัตินี้เหมาะสมอย่างยิ่งกับการป้องกัน secret หลุด เพราะมันคือ **ด่านสุดท้ายที่ทำงานอัตโนมัติก่อนที่ secret จะเข้าไปอยู่ใน local Git history ด้วยซ้ำ** เร็วกว่าการรอไปเจอตอน push หรือตอน CI/CD ทำงาน

### เขียน pre-commit hook แบบพื้นฐานด้วย bash เอง

ทบทวนจาก Part 59 hook ถูกเก็บไว้ที่ `.git/hooks/pre-commit` และต้องมีสิทธิ์ execute:

```bash
#!/usr/bin/env bash
# .git/hooks/pre-commit
# สคริปต์ตรวจสอบเบื้องต้นก่อน commit เพื่อจับสัญญาณของ secret ที่อาจหลุดเข้าไป

# ดึงรายชื่อไฟล์ที่ staged ไว้ (เฉพาะไฟล์ที่จะถูก commit จริง ๆ)
staged_files=$(git diff --cached --name-only --diff-filter=ACM)

found_issue=0

for file in $staged_files; do
    # ข้ามไฟล์ที่ถูกลบไปแล้ว
    [ -f "$file" ] || continue

    # ตรวจสอบชื่อไฟล์ที่ไม่ควรถูก commit เด็ดขาด
    case "$file" in
        .env|.env.*|*credentials*.json|*.pem|*.key)
            if [ "$file" != ".env.example" ]; then
                echo "ปฏิเสธการ commit: พบไฟล์ที่น่าจะเป็นไฟล์ลับ -> $file"
                found_issue=1
            fi
            ;;
    esac

    # ตรวจสอบเนื้อหาไฟล์ว่ามีคำที่บ่งชี้ว่าอาจเป็น secret ที่ hardcode ไว้หรือไม่
    if grep -Iq -E "(password|secret|api_key|access_key|private_key)\s*=\s*['\"][A-Za-z0-9/+=_-]{12,}['\"]" "$file" 2>/dev/null; then
        echo "คำเตือน: พบรูปแบบที่คล้าย credential ถูก hardcode ไว้ในไฟล์ -> $file"
        found_issue=1
    fi
done

if [ "$found_issue" -eq 1 ]; then
    echo ""
    echo "การ commit ถูกยกเลิก กรุณาตรวจสอบไฟล์ข้างต้นก่อน"
    echo "หากมั่นใจว่าไม่ใช่ secret จริง ใช้ 'git commit --no-verify' เพื่อข้าม (ใช้อย่างระมัดระวังเท่านั้น)"
    exit 1
fi

exit 0
```

```bash
# อย่าลืมให้สิทธิ์ execute กับ hook (ทบทวนจาก Part 59)
chmod +x .git/hooks/pre-commit
```

### ปัญหาของการเขียน hook เองแบบข้างต้น และเหตุผลที่ควรใช้เครื่องมือสำเร็จรูป

hook ตัวอย่างข้างต้นใช้สอนแนวคิดได้ดี แต่ในโลกจริงมีข้อจำกัดสำคัญที่ Part 59 เคยกล่าวถึงไว้แล้ว:

1. **hook ที่เก็บไว้ใน `.git/hooks/` ไม่ถูก track โดย Git** — ไม่ถูก commit ไปพร้อมโปรเจกต์ สมาชิกใหม่ในทีมจะไม่มี hook นี้โดยอัตโนมัติ
2. **regex ที่เขียนเองมักไม่ครอบคลุมรูปแบบ secret ของผู้ให้บริการทุกเจ้า** และต้องคอยอัปเดตเองตลอดเวลา

ทางแก้ตามที่ Part 59 แนะนำไว้คือใช้ **`core.hooksPath`** เพื่อกำหนดโฟลเดอร์ hook ที่ commit เข้า repository ได้ (ไม่ใช่ `.git/hooks/` ที่ไม่ถูก track) หรือใช้ framework อย่าง **husky** (สำหรับโปรเจกต์ Node.js) หรือ **pre-commit framework** (เครื่องมือ Python ที่ใช้ได้ข้ามภาษา)

### ใช้ gitleaks ร่วมกับ pre-commit framework

แนวทางที่แนะนำที่สุดในทางปฏิบัติคือ ผสาน gitleaks (จาก Step 775) เข้ากับ **pre-commit framework** ผ่านไฟล์ config ที่ถูก commit เข้า repository เพื่อให้ทุกคนในทีมได้ hook เดียวกันโดยอัตโนมัติเมื่อตั้งค่าครั้งแรก:

```yaml
# .pre-commit-config.yaml (ไฟล์นี้ commit เข้า repository ได้ตามปกติ)
repos:
  - repo: https://github.com/gitleaks/gitleaks
    rev: v8.18.0
    hooks:
      - id: gitleaks
```

```bash
# ติดตั้ง pre-commit framework (ครั้งเดียวต่อเครื่อง)
pip install pre-commit

# ติดตั้ง hook เข้ากับ repository ปัจจุบัน (สมาชิกทีมทุกคนต้องรันคำสั่งนี้ครั้งแรกหลัง clone)
pre-commit install

# ทดสอบรัน hook กับไฟล์ทั้งหมดในโปรเจกต์
pre-commit run --all-files
```

จากนี้ไปทุกครั้งที่มีการ `git commit` gitleaks จะสแกนไฟล์ที่ staged ไว้โดยอัตโนมัติก่อนอนุญาตให้ commit ผ่าน

### ใช้ `core.hooksPath` กับ git-secrets โดยไม่ต้องพึ่ง framework ภายนอก

อีกทางเลือกหนึ่งตามที่ Part 59 เคยแนะนำไว้ คือสร้างโฟลเดอร์ hook ของตัวเองในโปรเจกต์ (เช่น `.githooks/`) แล้วตั้งค่าให้ Git ใช้โฟลเดอร์นี้แทน:

```bash
# สร้างโฟลเดอร์ hook ที่ commit เข้า repository ได้จริง
mkdir -p .githooks

# ย้ายสคริปต์ pre-commit (เช่นตัวอย่างที่เขียนเองด้านบน หรือเรียก git-secrets) มาไว้ที่นี่
mv .git/hooks/pre-commit .githooks/pre-commit
chmod +x .githooks/pre-commit

# ตั้งค่าให้ Git ใช้โฟลเดอร์นี้เป็นแหล่ง hook
git config core.hooksPath .githooks

# commit โฟลเดอร์นี้เข้า repository เพื่อแชร์ให้ทุกคนในทีม
git add .githooks
git commit -m "chore: เพิ่ม pre-commit hook ป้องกัน secret หลุด"
```

หลังจากนี้สมาชิกทีมที่ clone repository ใหม่เพียงแค่รัน `git config core.hooksPath .githooks` ครั้งเดียว ก็จะได้ hook ป้องกัน secret ตัวเดียวกันทันที

### ข้อจำกัดที่ต้องรู้: Pre-commit Hook ป้องกันได้แค่ในเครื่อง ไม่ใช่ทุกที่

ต้องย้ำเตือนเสมอว่า pre-commit hook เป็นเพียง **ด่านแรก** เท่านั้น (ตามผังใน Step 775) เพราะ:

- hook รันอยู่ในเครื่อง local ของนักพัฒนาแต่ละคน หากใครใช้ `git commit --no-verify` เพื่อข้าม hook ไปตรง ๆ (ตามที่ Part 59 เคยสอนไว้ว่าเป็นการข้าม hook ชั่วคราว) การป้องกันนี้ก็ถูกข้ามไปทันที
- สมาชิกใหม่ที่ยังไม่ได้ตั้งค่า `core.hooksPath` หรือยังไม่ได้รัน `pre-commit install` จะไม่มี hook นี้ทำงานเลย

ด้วยเหตุนี้จึงต้องมีด่านที่สองและสามเสมอ (push protection ของแพลตฟอร์ม และการสแกนใน CI/CD) เป็นตาข่ายรองรับกรณีที่ด่านแรกถูกข้ามไปไม่ว่าจะตั้งใจหรือไม่ตั้งใจก็ตาม

### สรุปหลักคิดของ Step นี้

> **Pre-commit hook คือด่านป้องกันที่เร็วและถูกที่สุด เพราะจับ secret ได้ตั้งแต่ก่อนที่มันจะเข้าไปอยู่ใน Git history ด้วยซ้ำ แต่ต้องแชร์ hook นี้ให้ทุกคนในทีมได้จริงผ่าน `core.hooksPath` หรือ pre-commit framework ไม่ใช่แค่ตั้งไว้ในเครื่องตัวเองคนเดียว**

## Step 780: แบบฝึกหัด — จำลองสถานการณ์ secret หลุด แล้วฝึกกู้สถานการณ์ครบขั้นตอน

### วัตถุประสงค์ของแบบฝึกหัด

แบบฝึกหัดนี้จะให้คุณจำลองสถานการณ์ secret หลุดเข้า Git repository ด้วยตัวเอง (ใช้ค่าปลอมที่ไม่มีความหมายจริงเท่านั้น) แล้วฝึกทำตามลำดับขั้นตอนกู้สถานการณ์ที่ถูกต้องครบทุกขั้นตอนที่เรียนมาตลอด Part นี้:

```
1) Revoke (จำลอง) → 2) ประเมินความเสียหาย (จำลอง) → 3) ลบประวัติด้วย filter-repo → 4) ตั้งค่าป้องกันอนาคตด้วย pre-commit hook
```

**คำเตือนสำคัญ:** ตลอดแบบฝึกหัดนี้ ให้ใช้ค่าปลอมที่ชัดเจนว่าไม่ใช่ของจริงเท่านั้น เช่น `<FAKE_API_KEY_FOR_DEMO>` ห้ามใช้ค่าที่มีรูปแบบตรงกับ credential จริงของผู้ให้บริการรายใดเด็ดขาด แม้จะเป็นการฝึกก็ตาม เพราะระบบสแกนอัตโนมัติของแพลตฟอร์มโฮสต์จริงจะตรวจจับและบล็อกได้แม้ในบริบทการฝึก

### ขั้นตอนที่ 1: จำลองสถานการณ์ secret หลุด

```bash
# สร้างโฟลเดอร์ config และไฟล์ที่มีค่าปลอมชัดเจน (ไม่ใช่รูปแบบจริงของผู้ให้บริการใด ๆ)
mkdir -p config
cat > config/app-config.txt << 'EOF'
service_name=demo-payment-service
api_key=<FAKE_API_KEY_FOR_DEMO_00000000>
database_password=<FAKE_DB_PASSWORD_FOR_DEMO>
EOF

git add config/app-config.txt
git commit -m "feat: เพิ่มไฟล์ตั้งค่า (จำลองสถานการณ์พลาด commit secret)"
```

*(สังเกตว่านี่คือการจำลองความผิดพลาดโดยตั้งใจเพื่อการฝึกเท่านั้น ในสถานการณ์จริงห้ามทำแบบนี้ตามกฎทองใน Step 772)*

ทำ commit ต่อไปอีกสัก 1–2 ครั้งเพื่อให้สถานการณ์เหมือนของจริงมากขึ้น (ที่ secret ฝังอยู่ลึกในประวัติ ไม่ใช่แค่ commit ล่าสุด):

```bash
echo "readme demo" > README.md
git add README.md
git commit -m "docs: เพิ่ม README"
```

### ขั้นตอนที่ 2: จำลองการ Revoke ทันทีที่รู้ตัว (Step 773)

ในสถานการณ์จริง ขั้นตอนนี้คือการเข้า dashboard ของผู้ให้บริการจริงเพื่อ deactivate key ทันที สำหรับแบบฝึกหัดนี้ ให้เขียนบันทึกจำลองขั้นตอนนี้ไว้เพื่อฝึกความเข้าใจลำดับความสำคัญ:

```bash
cat > incident-log.md << 'EOF'
# บันทึกเหตุการณ์ (จำลอง)

- เวลาที่พบ: (ระบุเวลาจำลอง)
- Secret ที่หลุด: api_key ในไฟล์ config/app-config.txt
- การกระทำลำดับที่ 1: REVOKE ค่า <FAKE_API_KEY_FOR_DEMO_00000000> ทันที (จำลองว่าดำเนินการแล้ว)
- การกระทำลำดับที่ 2: ตรวจสอบ log การใช้งานย้อนหลัง (จำลองว่าไม่พบการใช้งานผิดปกติ)
EOF

git add incident-log.md
git commit -m "docs: บันทึกเหตุการณ์ secret หลุด (จำลอง)"
```

**ข้อคิดสำคัญของขั้นตอนนี้:** ให้สังเกตว่าเราทำขั้นตอน "revoke" (แม้จะเป็นแค่บันทึกจำลอง) **ก่อน** ที่จะไปยุ่งกับการแก้ประวัติ Git เสมอ นี่คือลำดับที่ถูกต้องตามหลักการใน Step 773

### ขั้นตอนที่ 3: ลบ secret ออกจากประวัติทั้งหมดด้วย `git filter-repo` (Step 774)

ก่อนอื่นตรวจสอบว่า secret ยังอยู่ในประวัติจริงหรือไม่:

```bash
git log --all -p -- config/app-config.txt
# ควรเห็นว่าค่า <FAKE_API_KEY_FOR_DEMO_00000000> ยังปรากฏอยู่ใน commit เก่า
```

ทำการ backup ก่อนแก้ไขประวัติ (ตามหลักการที่เรียนไปแล้ว):

```bash
cd ..
cp -r part-78-secret-practice part-78-secret-practice-backup
cd part-78-secret-practice
```

ลบไฟล์ที่มี secret ออกจากประวัติทั้งหมดด้วย `git filter-repo`:

```bash
git filter-repo --path config/app-config.txt --invert-paths --force
```

*(หมายเหตุ: แฟล็ก `--force` ในที่นี้จำเป็นเพราะ `git filter-repo` จะปฏิเสธการทำงานกับ repository ที่ไม่ใช่ fresh clone โดยปริยาย เพื่อความปลอดภัย ในสถานการณ์การฝึกหัดกับ repository ทดลองของตัวเองถือว่ายอมรับได้ แต่ในสถานการณ์จริงกับ repository ของทีม ควรทำตามขั้นตอนแบบ mirror clone ตามที่อธิบายไว้ใน Step 774)*

ตรวจสอบผลลัพธ์:

```bash
git log --all -p -- config/app-config.txt
# ตอนนี้ควรไม่พบไฟล์นี้ในประวัติอีกต่อไปเลย

git log --oneline --all
# สังเกตว่า hash ของทุก commit เปลี่ยนไปทั้งหมด เพราะประวัติถูกเขียนใหม่
```

### ขั้นตอนที่ 4: ตั้งค่าป้องกันอนาคตด้วย Pre-commit Hook (Step 779)

ติดตั้ง hook ป้องกันไม่ให้เกิดเหตุการณ์ซ้ำอีกในอนาคต โดยใช้แนวทาง `core.hooksPath` ที่แชร์ให้ทั้งทีมได้จริง:

```bash
mkdir -p .githooks

cat > .githooks/pre-commit << 'EOF'
#!/usr/bin/env bash
staged_files=$(git diff --cached --name-only --diff-filter=ACM)
found_issue=0

for file in $staged_files; do
    [ -f "$file" ] || continue
    case "$file" in
        .env|.env.*|*credentials*.json|*.pem|*.key)
            if [ "$file" != ".env.example" ]; then
                echo "ปฏิเสธการ commit: พบไฟล์ที่น่าจะเป็นไฟล์ลับ -> $file"
                found_issue=1
            fi
            ;;
    esac
    if grep -Iq -E "(password|secret|api_key|access_key|private_key)\s*=\s*['\"][A-Za-z0-9/+=_-]{12,}['\"]" "$file" 2>/dev/null; then
        echo "คำเตือน: พบรูปแบบที่คล้าย credential ถูก hardcode ไว้ในไฟล์ -> $file"
        found_issue=1
    fi
done

if [ "$found_issue" -eq 1 ]; then
    echo "การ commit ถูกยกเลิก กรุณาตรวจสอบไฟล์ข้างต้นก่อน"
    exit 1
fi
exit 0
EOF

chmod +x .githooks/pre-commit
git config core.hooksPath .githooks

git add .githooks
git commit -m "chore: เพิ่ม pre-commit hook ป้องกัน secret หลุดในอนาคต"
```

### ขั้นตอนที่ 5: ทดสอบว่า hook ทำงานจริง

ลองจำลองความพยายาม commit secret อีกครั้งเพื่อยืนยันว่า hook ทำงาน:

```bash
mkdir -p config2
echo 'api_key="<FAKE_API_KEY_FOR_DEMO_11111111>"' > config2/settings.txt
git add config2/settings.txt
git commit -m "ทดสอบว่า hook บล็อกได้จริงหรือไม่"

# ผลลัพธ์ที่ควรเห็น: การ commit ถูกปฏิเสธ พร้อมข้อความคำเตือนจาก hook
```

ถ้า hook ทำงานถูกต้อง คุณจะเห็นข้อความ "การ commit ถูกยกเลิก" และไฟล์นั้นจะไม่ถูก commit เข้าไป — ลบไฟล์ทดสอบทิ้งเพื่อความสะอาด:

```bash
git reset
rm -rf config2
```

- [ ] ตรวจสอบด้วย `git log --all -p` ยืนยันว่าไม่พบ secret ในประวัติอีกแล้ว
- [ ] ตั้งค่า pre-commit hook ผ่าน `core.hooksPath` และยืนยันว่ามันบล็อกการ commit secret ใหม่ได้จริง
- [ ] เข้าใจว่าเหตุใดลำดับ Revoke → ประเมินความเสียหาย → ลบประวัติ → ป้องกันอนาคต ถึงสำคัญกว่าการลบไฟล์เพียงอย่างเดียว

## สรุป Part 78

ใน Part นี้เราได้เรียนรู้เรื่อง Secret Management และการป้องกันข้อมูลรั่วไหลใน Git อย่างครบวงจร:

1. Secret ที่หลุดเข้า Git เป็นปัญหาที่เกิดขึ้นบ่อยในโลกจริงและสร้างความเสียหายทางการเงินได้รุนแรงมาก โดยเฉพาะเมื่อบัญชี cloud ถูกขโมยไปใช้งานโดยไม่ได้รับอนุญาต
2. กฎทองที่ต้องยึดถือเสมอคือห้าม commit secret ลง Git เด็ดขาด และ `.gitignore` ต้องมี `.env` ตั้งแต่วินาทีแรกที่สร้าง repository
3. เมื่อพลาด commit secret ไปแล้ว ลำดับที่ถูกต้องคือ **Revoke ก่อนเสมอ** ตามด้วยการประเมินความเสียหาย ไม่ใช่แค่ลบไฟล์ออกจาก commit ล่าสุดซึ่งไม่ได้ลบอะไรออกจากประวัติเลย
4. `git filter-repo` คือเครื่องมือมาตรฐานปัจจุบันสำหรับลบข้อมูลออกจากประวัติ Git ทั้งหมด แทนที่ `git filter-branch` และ BFG Repo-Cleaner แบบเก่า
5. เครื่องมือสแกน secret อัตโนมัติอย่าง git-secrets, trufflehog และ gitleaks ทำงานร่วมกับ Secret Detection ของ GitLab ที่เรียนไปแล้วใน Part 54 เป็นแนวป้องกันหลายชั้น (defense in depth)
6. ระบบ secret management ระดับองค์กรอย่าง HashiCorp Vault และ AWS Secrets Manager ช่วยให้จัดการ secret แบบรวมศูนย์ หมุนเวียนอัตโนมัติ และมี audit trail ที่ตรวจสอบได้
7. Environment Variables คือกลไกพื้นฐานที่สุดในการแยก secret ออกจากโค้ด สอดคล้องกับหลักการ 12-Factor App ข้อที่ 3 (Config) ที่ว่า config ต้องแยกออกจากโค้ดเสมอ
8. Pre-commit hook (เชื่อมโยงกับ Git Hooks ที่เรียนใน Part 59) คือด่านป้องกันแรกสุดและเร็วที่สุด แต่ต้องแชร์ให้ทั้งทีมผ่าน `core.hooksPath` หรือ pre-commit framework จึงจะได้ผลจริง
9. เราได้ฝึกจำลองสถานการณ์ secret หลุดครบทุกขั้นตอน ตั้งแต่ revoke ไปจนถึงการลบประวัติและตั้งค่าป้องกันอนาคต โดยใช้ค่าปลอมที่ปลอดภัยตลอดการฝึก
