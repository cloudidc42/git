## Step 851: Maintainer คืออะไร บทบาทและความรับผิดชอบหลัก

### ความเข้าใจผิดที่พบบ่อยที่สุด

คนส่วนใหญ่ที่ยังไม่เคยเป็น Maintainer คิดว่างานของ Maintainer คือ:

> "คนที่เขียนโค้ดเก่งที่สุดในโปรเจกต์ คอย merge PR ที่คนอื่นส่งมา"

นี่คือความเข้าใจผิดที่อันตรายมาก เพราะในความเป็นจริง **การเขียนโค้ดอาจเป็นสัดส่วนที่น้อยที่สุด** ในงานประจำวันของ Maintainer โปรเจกต์ Open Source ที่ประสบความสำเร็จและมีขนาดใหญ่พอสมควร

จากการสำรวจ maintainer ของโปรเจกต์ดัง ๆ หลายโปรเจกต์ (เช่นงานวิจัยของ Tidelift, GitHub Open Source Survey) พบว่าเวลาของ maintainer ถูกใช้ไปกับ:

| กิจกรรม | สัดส่วนเวลาโดยประมาณ |
|---|---|
| ตอบและ triage issue | 25–35% |
| Review Pull Request | 20–30% |
| เขียน/อัปเดตเอกสาร | 10–15% |
| ตอบคำถามในช่องทางชุมชน (Discord, Slack, Discussions) | 10–20% |
| วางแผน roadmap และตัดสินใจเชิงทิศทาง | 5–10% |
| เขียนโค้ดเอง (feature/bugfix) | 10–20% |
| งานด้านความปลอดภัย (security advisory, patch) | ไม่แน่นอน แต่สำคัญมากเมื่อเกิดขึ้น |
| ดูแลเรื่อง release, CI, infrastructure | 5–15% |

จะเห็นว่า **การเขียนโค้ดจริง ๆ อาจใช้เวลาน้อยกว่าครึ่งหนึ่งของเวลาทั้งหมด** ด้วยซ้ำ

### นิยามที่ถูกต้องของ Maintainer

> **Maintainer คือผู้ที่รับผิดชอบต่อ "สุขภาพโดยรวม" ของโปรเจกต์ ทั้งในมิติทางเทคนิค (คุณภาพโค้ด สถาปัตยกรรม ความปลอดภัย) และมิติทางสังคม (ชุมชนผู้ใช้และผู้ร่วมพัฒนา ความยั่งยืนในระยะยาว)**

พูดให้ชัดขึ้นคือ Maintainer มีหน้าที่หลัก 6 ด้าน:

#### 1. Technical Stewardship (ดูแลทิศทางทางเทคนิค)

- ตัดสินใจว่าโปรเจกต์จะไปทางไหน (roadmap, architecture decisions)
- รักษาคุณภาพโค้ดให้สม่ำเสมอ แม้จะมีคนหลายร้อยคนมาส่ง PR
- ตัดสินใจเรื่อง breaking change, deprecation policy, versioning
- ดูแล technical debt ไม่ให้สะสมจนโปรเจกต์พังในระยะยาว

#### 2. Gatekeeping ที่มีคุณภาพ (Quality Gate)

- Review และตัดสินใจว่า PR ไหนควร merge ไม่ควร merge
- รักษามาตรฐานของ test coverage, documentation, backward compatibility
- ป้องกันไม่ให้โค้ดที่มีช่องโหว่ด้านความปลอดภัยหลุดเข้าไปใน codebase

#### 3. Community Management (บริหารชุมชน)

- ตอบคำถามผู้ใช้งาน ต้อนรับ contributor ใหม่
- ไกล่เกลี่ยความขัดแย้งระหว่างสมาชิกในชุมชน
- บังคับใช้ Code of Conduct อย่างเป็นธรรม
- สร้างบรรยากาศที่ทำให้คนอยากกลับมาช่วยพัฒนาต่อ

#### 4. Project Governance (การปกครองโปรเจกต์)

- ตัดสินใจว่าใครจะได้สิทธิ์ commit/merge เพิ่ม
- กำหนดกระบวนการตัดสินใจเมื่อมีความเห็นขัดแย้งกัน
- วางแผนสืบทอดตำแหน่ง (succession) เผื่อวันหนึ่งตัวเองต้องออกจากโปรเจกต์

#### 5. Release Management (จัดการการปล่อยเวอร์ชัน)

- ตัดสินใจว่าเมื่อไหร่ควร release เวอร์ชันใหม่
- เขียน changelog, release notes
- ดูแลเรื่อง semantic versioning ให้ผู้ใช้ upgrade ได้อย่างมั่นใจ

#### 6. Security & Trust (ความปลอดภัยและความน่าเชื่อถือ)

- รับผิดชอบต่อรายงานช่องโหว่ (vulnerability report) อย่างมืออาชีพ
- ออก security advisory และ patch อย่างทันท่วงที
- เป็นผู้ค้ำประกันว่าโค้ดที่คนนับล้าน `npm install` หรือ `pip install` ไปใช้นั้นปลอดภัย

### ทำไมบทบาทนี้ถึงสำคัญมากในโลกปัจจุบัน

Open Source ไม่ใช่แค่ "งานอดิเรกของแฮกเกอร์" อีกต่อไป จากรายงาน Linux Foundation และ Synopsys พบว่า **โค้ดในซอฟต์แวร์เชิงพาณิชย์กว่า 70–90% เป็น Open Source dependency** ทั้งทางตรงและทางอ้อม นั่นแปลว่า Maintainer ของ library เล็ก ๆ ตัวหนึ่งอาจเป็นคนที่ระบบสำคัญของธนาคาร โรงพยาบาล หรือโครงสร้างพื้นฐานของประเทศพึ่งพาอยู่โดยที่พวกเขาอาจไม่รู้ตัวด้วยซ้ำ

เหตุการณ์ **XZ Utils backdoor (2024)** เป็นตัวอย่างที่ชัดเจนที่สุดว่าทำไมบทบาท Maintainer ถึงสำคัญ — โปรเจกต์ `xz-utils` ซึ่งเป็น library บีบอัดข้อมูลที่ถูกใช้แทบทุกที่ใน Linux distribution ถูกแทรกซึมโดยผู้ไม่หวังดีที่ค่อย ๆ สร้างความไว้ใจกับ maintainer เดิมที่กำลังเหนื่อยล้าจนกระทั่งได้รับสิทธิ์ maintainer ร่วม แล้วแอบฝัง backdoor เข้าไปในโค้ด เหตุการณ์นี้เกือบกลายเป็นภัยพิบัติด้านความปลอดภัยระดับโลก และถูกค้นพบโดยบังเอิญก่อนที่จะแพร่กระจายไปในระบบ production จำนวนมาก

เหตุการณ์นี้สอนบทเรียนสำคัญหลายข้อที่เราจะพูดถึงตลอด Part นี้: ความเสี่ยงจากการมี maintainer เดี่ยว (bus factor = 1), ปัญหา burnout ที่ทำให้คนยอมมอบสิทธิ์ให้คนแปลกหน้าเร็วเกินไป และความสำคัญของกระบวนการตรวจสอบที่รัดกุม

## Step 852: ความแตกต่างระหว่าง Contributor, Maintainer, Core Team

โปรเจกต์ Open Source ที่จัดการดีจะมีโครงสร้างบทบาทที่ชัดเจน ไม่ใช่ "ใครก็ได้ที่ push โค้ดได้" แบบสุ่มสี่สุ่มห้า โครงสร้างทั่วไปมีลักษณะเป็นพีระมิด:

```
                    ┌─────────────────┐
                    │   Core Team /   │   ← จำนวนน้อยที่สุด
                    │   Steering      │      อำนาจตัดสินใจสูงสุด
                    │   Committee     │
                    └────────┬────────┘
                    ┌────────┴────────┐
                    │   Maintainers   │   ← มีสิทธิ์ merge/release
                    │  (per-module)   │      ดูแลส่วนใดส่วนหนึ่ง
                    └────────┬────────┘
              ┌──────────────┴──────────────┐
              │      Regular Contributors    │  ← ส่ง PR เป็นประจำ
              │   (Trusted, มี track record) │     ได้รับความไว้ใจ
              └──────────────┬──────────────┘
      ┌───────────────────────┴───────────────────────┐
      │            One-time / Casual Contributors       │  ← จำนวนมากที่สุด
      │     (แก้ typo, รายงานบั๊ก, ส่ง PR ครั้งเดียว)      │
      └─────────────────────────────────────────────────┘
```

### Contributor คือใคร

**Contributor** คือใครก็ได้ที่มีส่วนช่วยโปรเจกต์ ไม่ว่าจะเล็กหรือใหญ่แค่ไหน การมีส่วนร่วม (contribution) ไม่ได้จำกัดแค่การเขียนโค้ด แต่รวมถึง:

- รายงานบั๊ก (bug report) ที่มีคุณภาพ
- แก้ typo ในเอกสาร
- ตอบคำถามคนอื่นใน issue/discussion
- แปลเอกสารเป็นภาษาอื่น
- เขียนบทความ/สอนคนอื่นใช้โปรเจกต์
- ส่ง Pull Request แก้บั๊กหรือเพิ่มฟีเจอร์
- ทดสอบ release candidate และรายงานปัญหา

Contributor **ไม่มีสิทธิ์เขียน (write access)** ในตัว repository โดยตรง — ทุกอย่างที่พวกเขาทำต้องผ่านการอนุมัติจาก Maintainer เสมอ (ผ่าน Pull Request, Issue)

### Maintainer คือใคร

**Maintainer** คือ Contributor ที่ได้รับความไว้ใจให้มี **write access** เข้า repository ซึ่งหมายความว่าสามารถ:

- Merge Pull Request ได้โดยตรง
- Push โค้ดเข้า branch หลักได้ (แม้ปกติจะยังผ่าน PR review อยู่ดีตามธรรมเนียมที่ดี)
- จัดการ label, milestone, project board
- ปิด/เปิด issue ได้
- บางครั้งมีสิทธิ์ trigger release หรือ publish package

ในโปรเจกต์ขนาดใหญ่ Maintainer มักจะถูกแบ่งเป็น **Maintainer เฉพาะโมดูล (module owner)** เช่นใน Kubernetes ที่แต่ละ SIG (Special Interest Group) จะมี maintainer ของตัวเองที่ดูแลเฉพาะส่วนที่ตัวเองรับผิดชอบ ไม่ใช่ maintainer คนเดียวดูแลทั้งหมด

### Core Team / Steering Committee คือใคร

**Core Team** (บางโปรเจกต์เรียก Steering Committee, Technical Committee, หรือ TSC — Technical Steering Committee) คือกลุ่มคนเล็ก ๆ ที่มีอำนาจตัดสินใจสูงสุดในเรื่องที่กระทบทั้งโปรเจกต์ เช่น:

- ทิศทางเชิงกลยุทธ์ของโปรเจกต์ในระยะยาว
- การตัดสิน breaking change ระดับใหญ่
- การรับ/ถอดถอน maintainer คนใหม่หรือคนเดิม
- การจัดการเรื่องการเงิน สปอนเซอร์ ทรัพย์สินทางปัญญา
- การไกล่เกลี่ยข้อขัดแย้งที่ maintainer ระดับโมดูลตกลงกันไม่ได้
- ความสัมพันธ์กับมูลนิธิ (foundation) ถ้าโปรเจกต์อยู่ภายใต้องค์กรใดองค์กรหนึ่ง

### ตารางเปรียบเทียบสรุป

| มิติ | Contributor | Maintainer | Core Team |
|---|---|---|---|
| Write access ใน repo | ไม่มี | มี | มี (มักมีสิทธิ์ admin) |
| ตัดสินใจ merge PR | ไม่ได้ (แค่เสนอ) | ได้ในส่วนที่ตนดูแล | ได้ทุกส่วน |
| กำหนดทิศทางโปรเจกต์ | ไม่ได้โดยตรง | มีอิทธิพลบางส่วน | มีอำนาจตัดสินใจสุดท้าย |
| รับผิดชอบด้าน security | ไม่ต้อง | ต้องรับผิดชอบเมื่อพบใน scope ตน | ต้องรับผิดชอบภาพรวมทั้งหมด |
| จำนวนคนโดยทั่วไป | มากที่สุด (หลักร้อย–พัน) | ปานกลาง (หลักสิบ) | น้อยที่สุด (มักไม่เกิน 5–15 คน) |
| วิธีได้ตำแหน่ง | ส่ง PR/report แรก | ได้รับการโหวต/เสนอชื่อจาก maintainer เดิม | ได้รับเลือกจากชุมชนหรือ maintainer ด้วยกันเอง |

### เส้นทางการเลื่อนขั้น (Contributor Ladder)

โปรเจกต์ที่จัดการดีมักมีเอกสารที่เรียกว่า **Contributor Ladder** หรือ **Governance.md** ที่อธิบายเส้นทางชัดเจนว่าจะขยับจากขั้นหนึ่งไปอีกขั้นได้อย่างไร ตัวอย่างเกณฑ์ทั่วไป (อ้างอิงแนวทางจากโปรเจกต์อย่าง Kubernetes, Node.js):

1. **First-time Contributor** — ส่ง PR แรก มักได้รับ label `first-timers-only` ช่วยแนะนำ
2. **Regular Contributor** — ส่ง PR สม่ำเสมอ (เช่น มากกว่า 5 PR ที่ merge แล้วใน 3–6 เดือน) มีคุณภาพโค้ดสม่ำเสมอ
3. **Reviewer** — ได้รับความไว้ใจให้ช่วย review PR ของคนอื่น (แต่ยัง merge เองไม่ได้ในบางโปรเจกต์ จะเรียกสิทธิ์นี้ว่า `/lgtm` แยกจาก `/approve`)
4. **Maintainer / Approver** — ได้รับ write access เต็มรูปแบบในโมดูลที่ตนเชี่ยวชาญ
5. **Core Team Member** — ได้รับเลือกจากกลุ่ม maintainer ด้วยกันเองเมื่อมีประสบการณ์และความไว้ใจสูงสุด

การมีเส้นทางที่ชัดเจนแบบนี้ช่วยสองอย่าง: (1) สร้างแรงจูงใจให้ contributor อยากมีส่วนร่วมต่อเนื่อง และ (2) ทำให้กระบวนการมอบอำนาจโปร่งใส ตรวจสอบได้ ไม่ใช่การให้สิทธิ์แบบสุ่มหรือให้เพราะสนิทกันเฉย ๆ ซึ่งเป็นปัจจัยเสี่ยงด้านความปลอดภัยแบบที่เกิดในกรณี XZ Utils

## Step 853: การ Triage Issue — จัดลำดับความสำคัญและปิด Issue ที่ไม่เกี่ยวข้อง

### ทำไม Triage ถึงเป็นทักษะที่สำคัญที่สุดอย่างหนึ่ง

โปรเจกต์ที่ได้รับความนิยมจะมี issue ไหลเข้ามาต่อเนื่องทุกวัน ถ้าไม่มีกระบวนการ triage ที่ดี จะเกิดปัญหาคลาสสิกที่เรียกว่า **Issue Bankruptcy** — จำนวน issue ค้างอยู่มากจนไม่มีใครอยากเปิดดูอีกต่อไป ผู้ใช้ใหม่ที่มาเจอ issue เก่า 3,000 อันที่ไม่มีคนตอบจะรู้สึกว่าโปรเจกต์นี้ "ตายแล้ว" แม้ในความจริงจะยังมีคนดูแลอยู่ก็ตาม

**Triage** คือกระบวนการตรวจสอบ issue ที่เข้ามาใหม่ แล้วจัดหมวดหมู่ ให้ priority และตัดสินใจว่าจะดำเนินการอย่างไรต่อ **โดยไม่จำเป็นต้องแก้ปัญหานั้นทันที**

### กระบวนการ Triage ที่แนะนำ (5 ขั้นตอน)

#### ขั้นที่ 1: ยืนยันว่า Issue สมบูรณ์พอจะดำเนินการต่อได้

ก่อนทำอะไรอื่น ตรวจสอบว่า issue มีข้อมูลครบตาม template หรือไม่:

- มีขั้นตอนการ reproduce ปัญหาชัดเจนไหม (Steps to Reproduce)
- มีเวอร์ชันของซอฟต์แวร์/environment ระบุไว้ไหม
- มี error message หรือ log แนบมาไหม

ถ้าข้อมูลไม่ครบ ให้ติด label `needs-more-info` และตั้งคำถามกลับอย่างสุภาพ พร้อมกำหนด (ผ่าน bot อัตโนมัติหรือ policy) ว่าถ้าไม่มีการตอบกลับภายใน 14–30 วัน จะปิด issue โดยอัตโนมัติ

#### ขั้นที่ 2: ตรวจสอบว่าซ้ำกับ Issue เดิมหรือไม่ (Deduplication)

ก่อนที่จะดำเนินการต่อ ต้องค้นหาก่อนว่าเคยมีคนรายงานปัญหาเดียวกันมาแล้วหรือยัง วิธีปฏิบัติที่ดี:

- ใช้ search ด้วย keyword สำคัญจาก error message
- ถ้าพบว่าซ้ำ ให้ปิด issue ใหม่พร้อม comment อธิบายว่าซ้ำกับ issue ไหน แล้วติด label `duplicate`
- ลิงก์กลับไปยัง issue ต้นฉบับเพื่อให้ผู้รายงานไปติดตามที่นั่นแทน ไม่ทำให้การสนทนากระจัดกระจาย

```
สวัสดีครับ ขอบคุณที่รายงานปัญหานี้เข้ามา 🙏
ปัญหานี้ตรงกับที่มีคนรายงานไว้แล้วใน #1234 ผมขอปิด issue นี้และ
รวม discussion ไว้ที่เดียวกันนะครับ ถ้ามีข้อมูลเพิ่มเติมที่ต่างจาก
issue เดิม รบกวน comment ไว้ที่ #1234 ได้เลยครับ
```

#### ขั้นที่ 3: จัดหมวดหมู่ด้วย Label

ระบบ label ที่ดีควรครอบคลุมอย่างน้อย 3 มิติ:

| ประเภท Label | ตัวอย่าง |
|---|---|
| **ประเภทของปัญหา** | `bug`, `feature-request`, `question`, `documentation`, `performance` |
| **ระดับความสำคัญ** | `priority: critical`, `priority: high`, `priority: low` |
| **สถานะกระบวนการ** | `needs-triage`, `needs-more-info`, `confirmed`, `help-wanted`, `good-first-issue` |
| **ขอบเขต/โมดูล** | `area: cli`, `area: api`, `area: docs` |

Label อย่าง `good-first-issue` และ `help-wanted` มีความสำคัญมากเชิงกลยุทธ์ เพราะเป็นสะพานเชื่อมให้ contributor หน้าใหม่เข้ามาช่วยงาน — Maintainer ที่ดีควรอุทิศเวลาส่วนหนึ่งเป็นประจำเพื่อหา issue ที่เหมาะกับมือใหม่แล้วติด label เหล่านี้ไว้ล่วงหน้า

#### ขั้นที่ 4: กำหนดลำดับความสำคัญ (Prioritization)

กรอบที่ใช้ได้จริงและนิยมมากคือดัดแปลงจาก **Severity × Frequency Matrix**:

| | ผู้ใช้จำนวนน้อยได้รับผลกระทบ | ผู้ใช้จำนวนมากได้รับผลกระทบ |
|---|---|---|
| **ผลกระทบร้ายแรง** (data loss, security, crash) | Priority: High | Priority: Critical — แก้ทันที |
| **ผลกระทบเล็กน้อย** (UI แปลก ๆ, edge case) | Priority: Low / Backlog | Priority: Medium |

ปัจจัยอื่นที่ควรพิจารณาร่วมด้วย:

- **ตรงกับ roadmap ของโปรเจกต์หรือไม่** — feature request ที่ไม่ตรงทิศทางโปรเจกต์ ควรปิดอย่างสุภาพแม้จะเป็นไอเดียที่ดีก็ตาม
- **มีคน "+1" หรือ react จำนวนมากไหม** — สะท้อนความต้องการจริงของชุมชน (แต่ไม่ควรเป็นปัจจัยเดียวในการตัดสินใจ)
- **มีคนอาสาทำ PR ให้ไหม** — issue ที่มีคนพร้อมช่วยแก้ควรได้รับความสำคัญเชิง engagement แม้ severity จะไม่สูงมาก

#### ขั้นที่ 5: ปิด Issue ที่ไม่เกี่ยวข้องอย่างสุภาพแต่เด็ดขาด

การปิด issue คือทักษะที่ Maintainer มือใหม่มักกลัวที่สุด เพราะกลัวทำให้ผู้ใช้ไม่พอใจ แต่การปล่อยให้ issue ที่ไม่มีทางไปต่อค้างอยู่เป็นการทำร้ายโปรเจกต์ในระยะยาวมากกว่า เหตุผลที่ควรปิด issue ได้แก่:

- **Out of scope** — ไม่ตรงกับเป้าหมายของโปรเจกต์
- **Won't fix** — รับทราบปัญหาแต่ตัดสินใจไม่แก้ (เช่น กระทบ backward compatibility มากเกินไป)
- **Cannot reproduce** — พยายาม reproduce แล้วไม่พบปัญหา และผู้รายงานไม่ตอบกลับข้อมูลเพิ่มเติม
- **Stale** — ไม่มีความเคลื่อนไหวเป็นเวลานาน (มักใช้ bot อัตโนมัติ เช่น `stale` bot ของ GitHub Actions)

ตัวอย่างข้อความปิด issue ที่ดี (สุภาพ ให้เหตุผล เปิดทางให้อภิปรายต่อได้):

```
ขอบคุณสำหรับข้อเสนอนี้ครับ หลังจากพิจารณาแล้ว ทีมเห็นว่าฟีเจอร์นี้
อยู่นอกขอบเขตที่โปรเจกต์นี้ต้องการรองรับ (ดูเหตุผลใน ROADMAP.md
หัวข้อ "Non-goals") เราขอปิด issue นี้ไว้ก่อนนะครับ แต่ยินดีเปิด
ใหม่ถ้ามีบริบทหรือกรณีการใช้งานเพิ่มเติมที่เปลี่ยนสถานการณ์ครับ
```

### การใช้ระบบอัตโนมัติช่วย Triage

เมื่อโปรเจกต์โตขึ้น การ triage ด้วยมือล้วน ๆ จะทำไม่ทัน เครื่องมือที่นิยมใช้ร่วม ได้แก่:

- **GitHub Issue Templates / Forms** — บังคับให้ผู้รายงานกรอกข้อมูลที่จำเป็นตั้งแต่ต้น ลดภาระ triage
- **Stale bot / Actions workflow** — ปิด issue ที่ไม่มีความเคลื่อนไหวอัตโนมัติหลังแจ้งเตือนล่วงหน้า
- **Triage rotation** — กำหนดให้ maintainer แต่ละคนผลัดกันรับผิดชอบ triage สัปดาห์ละคน (ใช้ในโปรเจกต์ขนาดใหญ่อย่าง Rust, Kubernetes)
- **Triage meeting ประจำสัปดาห์** — ประชุมสั้น ๆ (30 นาที) ทบทวน issue ใหม่ที่ยังไม่ได้ label ร่วมกัน

## Step 854: การ Review PR จากคนภายนอกอย่างมีประสิทธิภาพ

### ความแตกต่างสำคัญจากการ Review ในทีมของตัวเอง

การ review PR ในทีมบริษัทที่คุณคุ้นเคยกับเพื่อนร่วมทีมมานาน แตกต่างจากการ review PR ของคนแปลกหน้าใน Open Source อย่างมีนัยสำคัญ:

| มิติ | Review ในทีมบริษัท | Review PR จากคนภายนอกใน Open Source |
|---|---|---|
| ความคุ้นเคยกับผู้เขียน | รู้จักกันดี เข้าใจ context งาน | อาจไม่เคยเจอกันมาก่อนเลย |
| Context ที่ผู้เขียนมี | เข้าใจ business logic, สถาปัตยกรรมภายในอยู่แล้ว | อาจไม่รู้ประวัติ การตัดสินใจเก่า ๆ ของโปรเจกต์ |
| แรงจูงใจของผู้ส่ง PR | ได้รับมอบหมายงาน มีเงินเดือนรองรับ | ทำด้วยความสมัครใจ ไม่มีค่าตอบแทน |
| ผลกระทบจาก feedback ที่รุนแรง | กระทบขวัญกำลังใจ แต่ยังมาทำงานต่อ | อาจทำให้คนคนนั้นเลิกช่วยโปรเจกต์ไปตลอดกาล |
| จำนวนคนดู | จำกัดเฉพาะทีม | สาธารณะ คนทั่วโลกเห็น รวมถึง contributor คนอื่นในอนาคต |

จุดสุดท้ายในตารางสำคัญมาก: **ทุก comment review ที่คุณเขียนในที่สาธารณะ ไม่ได้ส่งผลแค่กับคนที่ถูก review เท่านั้น** แต่ยังเป็นการสื่อสารกับ contributor คนอื่น ๆ ที่กำลังอ่านอยู่ (หรือจะมาอ่านในอนาคต) ว่าโปรเจกต์นี้ "เป็นมิตร" กับคนนอกแค่ไหน

### หลักการ Review PR จากคนภายนอกที่ควรยึดถือ

#### 1. สันนิษฐานเจตนาดีเสมอ (Assume Good Intent)

คนที่ส่ง PR มาให้คุณ **สละเวลาส่วนตัวโดยไม่มีค่าตอบแทน** เพื่อช่วยโปรเจกต์ของคุณ แม้โค้ดของเขาจะมีปัญหามากแค่ไหน จุดเริ่มต้นควรเป็นความขอบคุณเสมอ ไม่ใช่การตั้งคำถามเชิงตำหนิ

**ตัวอย่างที่ไม่ดี:**
> "ทำไมถึงเขียนแบบนี้ นี่มันผิด pattern ที่โปรเจกต์ใช้ชัด ๆ"

**ตัวอย่างที่ดีกว่า:**
> "ขอบคุณสำหรับ PR นี้ครับ! มีจุดหนึ่งที่อยากปรับ — ปกติในโปรเจกต์นี้เราใช้ pattern X แทน Y เพราะเหตุผล Z (ดูตัวอย่างใน `src/utils/foo.ts`) ลองปรับตามนี้ดูไหมครับ?"

#### 2. อธิบาย "ทำไม" ไม่ใช่แค่ "อะไร"

Contributor ภายนอกไม่มี context ภายในหัวเหมือนทีมคุณ การบอกแค่ "เปลี่ยนตรงนี้" โดยไม่อธิบายเหตุผลจะทำให้เขาไม่เข้าใจและอาจรู้สึกว่าถูกสั่งอย่างไม่มีเหตุผล ควรอธิบายเสมอว่าทำไมถึงต้องการให้แก้แบบนั้น เช่น ผลกระทบด้าน performance, ความสอดคล้องกับ API design, หรือ backward compatibility

#### 3. แยกแยะระหว่าง "ต้องแก้" กับ "ความเห็นส่วนตัว"

ใช้ระบบ prefix แบบที่ชุมชนวิศวกรรมนิยมใช้ (แนวทาง Conventional Comments) เพื่อให้ผู้เขียน PR รู้ทันทีว่า comment ไหนคือ blocker และไหนคือแค่ข้อเสนอแนะ:

```
blocking: ฟังก์ชันนี้ไม่ได้ handle กรณี input เป็น null
          ทำให้ crash ได้ ต้องแก้ก่อน merge

nitpick: ส่วนตัวผมจะตั้งชื่อตัวแปรนี้ว่า `userCount` แทน
         `cnt` แต่ไม่ blocking นะครับ แล้วแต่สะดวก

question: อยากทราบว่าทำไมเลือกใช้ recursive function
          ตรงนี้แทน loop ครับ มีเหตุผลด้าน performance ไหม
```

การแยกแบบนี้ช่วยลดความรู้สึก "โดนบั่นทอน" ของผู้ส่ง PR อย่างมาก เพราะเขารู้ชัดว่าอะไรคือสิ่งที่ต้องทำจริง ๆ ก่อน merge ได้

#### 4. ให้ Feedback ที่รวดเร็ว แม้จะยังไม่ใช่ Feedback สุดท้าย

Contributor ภายนอกไม่ได้รอเงินเดือนคุณ พวกเขามีชีวิตอื่นและอาจหมดความสนใจถ้ารอนานเกินไป การตอบกลับแม้เพียงสั้น ๆ ว่า "เห็นแล้วครับ กำลังทดสอบอยู่ จะรีวิวให้ภายในสัปดาห์นี้" ดีกว่าการเงียบหายไปเป็นเดือน ๆ มาก งานวิจัยเรื่อง contributor retention พบว่า **เวลาตอบกลับ PR ครั้งแรก (first response time)** เป็นปัจจัยที่กระทบต่อการที่ contributor จะกลับมาช่วยครั้งที่สองมากที่สุดปัจจัยหนึ่ง

#### 5. ใช้ฟีเจอร์ "Suggested Changes" แทนการอธิบายยาว ๆ

แพลตฟอร์มอย่าง GitHub มีฟีเจอร์ suggestion ที่ให้คุณเสนอโค้ดที่แก้แล้วโดยตรง และผู้เขียน PR กด commit ได้ในคลิกเดียว วิธีนี้ลด friction ได้มากกว่าการอธิบายเป็นข้อความว่า "ควรเปลี่ยนบรรทัดนี้เป็นแบบนั้นแบบนี้"

#### 6. ระวังเรื่อง Bikeshedding

**Bikeshedding** (มาจากกฎ Parkinson's Law of Triviality) คือปรากฏการณ์ที่คนถกเถียงเรื่องเล็กน้อยที่เข้าใจง่าย (เช่น การตั้งชื่อตัวแปร, การจัดรูปแบบโค้ด) นานกว่าประเด็นสำคัญจริง ๆ (เช่น สถาปัตยกรรมของฟีเจอร์) มาก เพราะทุกคนรู้สึกว่าตัวเองมีความเห็นเรื่องนี้ได้ Maintainer ที่ดีต้องรู้จักตัดจบการถกเถียงเรื่องรูปแบบด้วยเครื่องมืออัตโนมัติ (linter, formatter เช่น Prettier, Black) แทนการถกเถียงด้วยคน และโฟกัส human review ไปที่ตรรกะและสถาปัตยกรรมที่สำคัญกว่า

#### 7. จัดการเรื่อง CLA / DCO อย่างชัดเจนตั้งแต่ต้น

หลายโปรเจกต์ (โดยเฉพาะที่อยู่ภายใต้บริษัทหรือมูลนิธิ) กำหนดให้ contributor ต้องเซ็น **CLA (Contributor License Agreement)** หรือใช้ **DCO (Developer Certificate of Origin)** ก่อนที่ PR จะถูก merge ได้ เพื่อยืนยันสิทธิ์ทางกฎหมายของโค้ดที่ส่งมา สิ่งนี้ควรถูกทำเป็นระบบอัตโนมัติ (bot ตรวจสอบอัตโนมัติใน CI) ไม่ใช่ให้ maintainer คอยเช็คเอง และควรอธิบายไว้ใน CONTRIBUTING.md อย่างชัดเจนตั้งแต่ต้น เพื่อไม่ให้ contributor เสียเวลาเขียนโค้ดไปแล้วมาเจอปัญหานี้ทีหลัง

#### 8. รับมือกับ "Drive-by PR" อย่างมีวุฒิภาวะ

Drive-by PR คือ PR ที่ส่งมาครั้งเดียวแล้วผู้เขียนหายไป ไม่ตอบ comment review อีกเลย สถานการณ์นี้เกิดขึ้นบ่อยมาก แนวทางที่แนะนำ:

- ให้เวลาตอบกลับที่สมเหตุสมผล (เช่น 2–4 สัปดาห์) พร้อมแจ้งเตือนก่อนปิด
- ถ้า PR มีประโยชน์จริงแต่ผู้เขียนหายไป Maintainer สามารถ **fork branch นั้นมาทำต่อเองได้** (โดยให้เครดิตผู้เขียนเดิมไว้ใน commit/changelog) แทนที่จะทิ้งงานที่ดีไป
- ปิด PR ที่ไม่มีความเคลื่อนไหวอย่างสุภาพ พร้อมขอบคุณสำหรับความพยายาม และเปิดโอกาสให้กลับมาทำต่อได้เสมอ

## Step 855: การจัดการ Contributor ที่หลากหลาย

โปรเจกต์ Open Source ที่ได้รับความนิยมจะดึงดูดคนที่มีพื้นเพ ประสบการณ์ และบุคลิกที่แตกต่างกันสุดขั้ว ตั้งแต่นักเรียนที่เพิ่งเขียนโค้ดเป็นครั้งแรก ไปจนถึงวิศวกรอาวุโสที่มีประสบการณ์ 20 ปีและมีความเห็นที่หนักแน่นมาก การบริหารความหลากหลายนี้คือทักษะที่แยก Maintainer มือใหม่ออกจาก Maintainer ที่มีประสบการณ์อย่างชัดเจน

### กลุ่มที่ 1: มือใหม่สุด (First-time Contributor)

**ลักษณะ:** กังวลมาก กลัวทำผิด อาจไม่กล้าถามคำถามที่ดูเหมือน "โง่" ต้องการความมั่นใจและกำลังใจ

**แนวทางที่ควรทำ:**

- ใช้ label `good-first-issue` และเขียนคำอธิบายที่ละเอียดกว่าปกติในตัว issue นั้น (บอกไฟล์ที่ต้องแก้ ฟังก์ชันที่เกี่ยวข้อง)
- ตอบกลับด้วยความอดทนแม้คำถามจะดูพื้นฐาน
- ชมเชยในสิ่งที่ทำถูกต้องก่อนชี้จุดที่ต้องปรับปรุง (sandwich feedback)
- ชี้ไปยัง CONTRIBUTING.md และ Code of Conduct อย่างเป็นมิตร ไม่ใช่เชิงตำหนิ
- พิจารณาใช้ mentorship program เช่น การจับคู่ mentor–mentee แบบที่โปรเจกต์อย่าง Rust หรือ Outreachy ทำ

### กลุ่มที่ 2: Contributor ประจำที่กำลังเติบโต (Regular Contributor)

**ลักษณะ:** เข้าใจโค้ดพอสมควรแล้ว อยากมีบทบาทมากขึ้น อาจรู้สึกท้อถ้าไม่เห็นเส้นทางความก้าวหน้า

**แนวทางที่ควรทำ:**

- มอบหมายความรับผิดชอบที่ใหญ่ขึ้นทีละนิด (triage issue, review PR ของคนอื่น)
- พูดคุยตรง ๆ เกี่ยวกับเส้นทางสู่การเป็น maintainer ถ้าเห็นศักยภาพ
- ให้เครดิตอย่างชัดเจนใน release notes, contributor list

### กลุ่มที่ 3: มือเก๋าที่มีความเห็นแรง (Experienced, Opinionated Contributor)

นี่คือกลุ่มที่ท้าทายที่สุดสำหรับ Maintainer หลายคน วิศวกรอาวุโสมักมาพร้อมประสบการณ์และความเชื่อมั่นสูง บางครั้งอาจแสดงออกในลักษณะที่ดูก้าวร้าวหรือดูถูกแนวทางที่โปรเจกต์เลือกใช้อยู่แล้ว

**สถานการณ์ทั่วไปที่พบ:**

- ยืนกรานว่าวิธีของตัวเอง "ถูกต้องกว่า" โดยไม่ยอมรับบริบทของโปรเจกต์
- Comment ในเชิงตำหนิสถาปัตยกรรมเดิมของโปรเจกต์อย่างรุนแรง
- ผลักดัน PR ขนาดใหญ่ที่เปลี่ยนแปลงเชิงโครงสร้างโดยไม่ปรึกษาก่อน
- ตอบโต้ feedback ของ maintainer ในเชิงป้องกันตัวหรือแข่งขัน

**แนวทางที่แนะนำ:**

1. **แยกแยะระหว่าง "ความเห็นที่ตรงและมีประโยชน์" กับ "พฤติกรรมที่เป็นพิษ (toxic)"** — ความเห็นที่ตรงไปตรงมาแต่มีเหตุผลทางเทคนิครองรับ ควรได้รับการรับฟังอย่างจริงจัง แม้น้ำเสียงจะไม่นุ่มนวลก็ตาม แต่พฤติกรรมที่ข้ามเส้นไปสู่การดูถูก โจมตีตัวบุคคล หรือทำให้คนอื่นในชุมชนรู้สึกไม่ปลอดภัย ต้องถูกจัดการทันทีตาม Code of Conduct
2. **ตั้งกฎก่อนเริ่มงานใหญ่เสมอ** — สำหรับ PR ที่เปลี่ยนแปลงเชิงโครงสร้าง ควรกำหนดให้ต้องเปิด issue หรือ RFC (Request for Comments) เพื่อพูดคุยแนวทางก่อนเริ่มเขียนโค้ดจริง ป้องกันการเสียเวลาทำงานใหญ่แล้วมาขัดแย้งทีหลัง
3. **ใช้อำนาจตัดสินใจสุดท้ายอย่างมั่นใจแต่สุภาพ** — Maintainer มีสิทธิ์ปฏิเสธ PR แม้จะเขียนดีทางเทคนิค ถ้าไม่ตรงกับทิศทางของโปรเจกต์ การอธิบายเหตุผลอย่างชัดเจนและยึดหลักการ (ไม่ใช่อารมณ์) จะช่วยลดความขัดแย้งได้มาก
4. **อย่ากลัวที่จะพูดว่า "ไม่"** — Maintainer มือใหม่จำนวนมากยอมรับ PR ที่ไม่เห็นด้วยเพียงเพราะกลัวความขัดแย้งกับคนที่มีเสียงดังหรือมีชื่อเสียงในวงการ นี่เป็นกับดักที่อันตราย เพราะจะทำให้ทิศทางโปรเจกต์เพี้ยนไปเรื่อย ๆ ตามคนที่ดังที่สุด ไม่ใช่ตามวิสัยทัศน์ที่แท้จริงของโปรเจกต์

### การบังคับใช้ Code of Conduct

ทุกโปรเจกต์ที่จริงจังควรมี **Code of Conduct (CoC)** ที่ชัดเจน (เราจะเจาะลึกการเขียน CoC ใน Part 87) และที่สำคัญกว่าการมีเอกสารคือ **การบังคับใช้อย่างสม่ำเสมอ ไม่เลือกปฏิบัติ** ไม่ว่าผู้กระทำผิดจะเป็นมือใหม่หรือเป็นผู้เชี่ยวชาญที่มีชื่อเสียงในวงการก็ตาม โปรเจกต์จำนวนมากเสียชื่อเสียงเพราะปล่อยให้ contributor ที่มีความสามารถสูงแต่มีพฤติกรรมไม่เหมาะสม ลอยนวลเพราะ "เขาเก่งเกินกว่าจะเสีย" — ผลลัพธ์ระยะยาวคือคนดี ๆ จำนวนมากค่อย ๆ ถอนตัวออกจากชุมชนอย่างเงียบ ๆ

### เทคนิคการสื่อสารข้ามวัฒนธรรม

Open Source เป็นเวทีระดับโลก contributor ของคุณอาจมาจากประเทศที่มีบรรทัดฐานการสื่อสารต่างจากคุณมาก สิ่งที่ควรระวัง:

- ภาษาอังกฤษของ contributor อาจไม่ใช่ภาษาแม่ — น้ำเสียงที่ดูห้วนอาจเป็นเพราะข้อจำกัดทางภาษา ไม่ใช่ความไม่สุภาพ
- ความแตกต่างของ time zone ทำให้การตอบสนองล่าช้าเป็นเรื่องปกติ ไม่ควรตีความว่าเป็นการเพิกเฉย
- หลีกเลี่ยงสำนวน สแลง หรือมุกตลกที่อาจเข้าใจยากข้ามวัฒนธรรม ใช้ภาษาที่ตรงไปตรงมาและชัดเจน

## Step 856: Maintainer Burnout — ปัญหาจริงและวิธีป้องกัน

### Burnout คืออะไร และทำไมถึงเกิดขึ้นบ่อยมากใน Open Source

**Maintainer Burnout** คือภาวะเหนื่อยล้าทางร่างกาย จิตใจ และอารมณ์ ที่เกิดจากการดูแลโปรเจกต์ Open Source เป็นเวลานานโดยไม่ได้พัก มักมาพร้อมความรู้สึกสิ้นหวัง หมดไฟ และในหลายกรณีคือความรู้สึกโกรธหรือขมขื่นต่อชุมชนที่ตัวเองเคยรัก

นี่ไม่ใช่ปัญหาเล็ก ๆ — มันเป็นปัญหาระดับโครงสร้างของวงการ Open Source ทั้งหมด บทความและงานวิจัยจากองค์กรอย่าง Tidelift, GitHub, และ Nadia Eghbal (ผู้เขียนหนังสือ *Working in Public*) ชี้ให้เห็นตรงกันว่า maintainer จำนวนมากดูแลโปรเจกต์ที่มีผู้ใช้นับล้านโดยไม่ได้รับค่าตอบแทนใด ๆ เลย

### สาเหตุหลักของ Burnout

#### 1. ภาระงานที่ไม่สมดุลกับค่าตอบแทน (Unpaid Labor at Scale)

Maintainer จำนวนมากทำงานนี้ในเวลาว่างหลังเลิกงานประจำ หรือในวันหยุด แต่ความคาดหวังจากผู้ใช้กลับสูงเทียบเท่ากับซอฟต์แวร์เชิงพาณิชย์ที่มีทีมงานเต็มเวลาดูแล

#### 2. ความรู้สึก "เป็นหนี้บุญคุณ" ที่ไม่มีวันหมด (Sense of Obligation)

เมื่อโปรเจกต์มีคนใช้เยอะขึ้น maintainer มักรู้สึกผูกพันทางศีลธรรมว่าต้อง "รับผิดชอบ" ต่อผู้ใช้ทุกคน แม้จะไม่มีสัญญาหรือข้อผูกมัดใด ๆ ตามกฎหมายก็ตาม ความรู้สึกนี้ทำให้หลายคนไม่กล้าหยุดพัก แม้จะเหนื่อยมากแล้ว

#### 3. Entitlement จากผู้ใช้ (User Entitlement)

นี่คือปัจจัยที่ maintainer จำนวนมากระบุว่าเจ็บปวดที่สุด — ผู้ใช้บางคนที่ **ไม่เคยจ่ายเงินสักบาทหรือมีส่วนร่วมใด ๆ เลย** กลับแสดงความไม่พอใจหรือเรียกร้องอย่างรุนแรงเมื่อ maintainer แก้บั๊กช้า หรือปฏิเสธ feature request ตัวอย่างข้อความที่ maintainer หลายคนเจอบ่อยคือ:

> "ทำไมยังไม่ fix bug นี้เลย ผ่านมา 3 วันแล้ว! โปรเจกต์นี้ maintain แย่มาก"

โดยลืมไปว่า maintainer คนนั้นทำงานนี้ฟรีในเวลาว่าง กรณีที่โด่งดังในวงการคือเหตุการณ์ **left-pad (2016)** ที่แม้จะเป็นเรื่องข้อพิพาททางกฎหมาย/ชื่อ package มากกว่า burnout โดยตรง แต่ก็สะท้อนว่าระบบนิเวศ Open Source ทั้งหมดพึ่งพา maintainer จำนวนน้อยมากที่ไม่ได้รับการสนับสนุนเพียงพอ

#### 4. ความโดดเดี่ยว (Isolation)

Maintainer โดยเฉพาะของโปรเจกต์ที่มีคนดูแลคนเดียวหรือสองคน มักทำงานคนเดียวโดยไม่มีใครแบ่งเบาภาระ ทุกการตัดสินใจ ทุกข้อร้องเรียน ตกอยู่ที่คนคนเดียว

#### 5. ความกดดันด้านความปลอดภัย (Security Pressure)

เมื่อพบช่องโหว่ความปลอดภัยร้ายแรง maintainer ต้องรับมือกับความกดดันมหาศาลในเวลาอันสั้น ทั้งจากนักวิจัยด้านความปลอดภัย สื่อ และผู้ใช้งานจำนวนมากที่ต้องการ patch ทันที

### สัญญาณเตือนของ Burnout

- รู้สึกหวาดกลัวหรือเบื่อหน่ายทุกครั้งที่เห็น notification จาก GitHub
- เริ่มตอบ issue/PR ด้วยน้ำเสียงหงุดหงิดหรือประชดประชันมากขึ้นเรื่อย ๆ
- เลื่อนงาน maintainer ออกไปเรื่อย ๆ จนรู้สึกผิด แต่ก็ยังทำไม่ได้อยู่ดี
- รู้สึกว่าตัวเองเป็น "ตัวประกัน" ของโปรเจกต์ตัวเอง ไม่กล้าหยุดเพราะกลัวคนอื่นเดือดร้อน
- คิดเรื่องโปรเจกต์ตลอดเวลาแม้ในวันหยุดหรือเวลาพักผ่อน

### วิธีป้องกันและรับมือกับ Burnout

#### 1. ตั้งขอบเขตเวลาที่ชัดเจน (Set Boundaries)

กำหนดเวลาที่แน่นอนสำหรับงาน maintainer เช่น "ตอบ issue เฉพาะวันเสาร์" และสื่อสารสิ่งนี้ให้ชุมชนรับรู้อย่างเปิดเผยในเอกสาร เช่น README หรือ CONTRIBUTING.md — การตั้งความคาดหวังที่ชัดเจนล่วงหน้าช่วยลดแรงกดดันจากความรู้สึกผิดได้มาก

#### 2. เรียนรู้ที่จะพูดว่า "ไม่" หรือ "ยังไม่ใช่ตอนนี้"

ไม่จำเป็นต้องรับทุก feature request หรือแก้ทุกบั๊กทันที Maintainer มีสิทธิ์เต็มที่ในการปฏิเสธหรือเลื่อนงานตามสิ่งที่ตัวเองมีกำลังจะทำได้

#### 3. ใช้ระบบอัตโนมัติลดภาระงานซ้ำ ๆ

Automated bot สำหรับ triage, stale issue closing, CLA checking, CI ที่รันเทสต์อัตโนมัติ — ทั้งหมดนี้ช่วยลดงานที่ทำซ้ำ ๆ ทุกวันได้อย่างมาก ปลดปล่อยเวลาให้ maintainer โฟกัสกับงานที่ต้องใช้วิจารณญาณของมนุษย์จริง ๆ

#### 4. กระจายอำนาจ อย่าผูกขาดทุกอย่างไว้คนเดียว

นี่คือเหตุผลที่ Step 857 (การหา co-maintainer) สำคัญมาก การมี **bus factor** สูง (จำนวนคนที่ต้อง "หายไป" ก่อนโปรเจกต์จะพัง) ไม่เพียงลดความเสี่ยงด้านความปลอดภัยแบบ XZ Utils แต่ยังช่วยลดภาระงานที่ตกอยู่กับคนคนเดียวโดยตรง

#### 5. หาการสนับสนุนทางการเงินหรือทรัพยากร

การได้รับค่าตอบแทนแม้เพียงบางส่วน (ผ่าน GitHub Sponsors, Open Collective ที่จะพูดถึงใน Step 859) ช่วยเปลี่ยนความรู้สึกจาก "งานอดิเรกที่ไม่มีที่สิ้นสุด" เป็น "งานที่มีคุณค่าและได้รับการยอมรับ" ได้มาก

#### 6. หยุดพักอย่างเป็นทางการเมื่อจำเป็น (Maintainer Sabbatical)

โปรเจกต์ใหญ่หลายโปรเจกต์เริ่มมีธรรมเนียมที่ maintainer ประกาศพักงานชั่วคราวอย่างเป็นทางการ (เช่น ประกาศใน README หรือ pinned issue ว่า "กำลังพักจากการดูแลโปรเจกต์ 1 เดือน") แทนที่จะหายไปเงียบ ๆ โดยไม่บอกใคร ซึ่งจะทำให้ชุมชนสับสนและวิตกกังวลมากกว่า

#### 7. หาคนคุยหรือกลุ่มสนับสนุนของ maintainer ด้วยกัน

องค์กรอย่าง Tidelift, Open Source Collective, และชุมชน maintainer หลายแห่งมีพื้นที่ให้ maintainer มาพูดคุยแบ่งปันปัญหาที่เจอร่วมกัน การรู้ว่า "เราไม่ได้เจอปัญหานี้คนเดียว" ช่วยลดความรู้สึกโดดเดี่ยวได้มาก

### บทเรียนจากกรณี XZ Utils เชื่อมโยงกับ Burnout

กรณี XZ Utils backdoor ที่กล่าวถึงใน Step 851 มีรากเหง้ามาจาก burnout โดยตรง — maintainer เดิมของโปรเจกต์ (Lasse Collin) ดูแลโปรเจกต์นี้มาเป็นเวลานานเกือบคนเดียว และเคยแสดงความเหนื่อยล้าต่อสาธารณะในอีเมลลิสต์มาก่อนหน้านั้น เมื่อมีคนแปลกหน้า (บัญชีที่ใช้ชื่อ "Jia Tan") เข้ามาช่วยงานอย่างสม่ำเสมอและดูมีความสามารถ maintainer เดิมจึงค่อย ๆ มอบสิทธิ์ maintainer ร่วมให้ ซึ่งภายหลังพบว่าเป็นการวางแผนแทรกซึม backdoor เข้าไปในโค้ดอย่างแนบเนียนเป็นเวลานาน

บทเรียนนี้ตอกย้ำว่า **burnout ไม่ใช่แค่ปัญหาสุขภาพจิตส่วนบุคคล แต่เป็นความเสี่ยงด้านความปลอดภัยของทั้งระบบนิเวศซอฟต์แวร์โลก** — เมื่อ maintainer เหนื่อยล้าจนต้องการความช่วยเหลือเร่งด่วน กระบวนการตรวจสอบที่ควรรัดกุมอาจถูกลดทอนลงโดยไม่รู้ตัว

## Step 857: การหา Co-maintainer และ Project Succession Planning

### ทำไมต้องวางแผนล่วงหน้า ไม่ใช่รอให้เกิดวิกฤตก่อน

โปรเจกต์ Open Source จำนวนมากล่มสลายหรือถูกทิ้งร้าง (abandoned) ไม่ใช่เพราะโค้ดไม่ดี แต่เพราะ **maintainer เพียงคนเดียวหายไปโดยไม่มีแผนสำรอง** ไม่ว่าจะเพราะเปลี่ยนงาน มีลูก ป่วย หมดไฟ หรือแม้แต่เสียชีวิต — สถานการณ์แบบนี้เรียกว่ามี **bus factor = 1** (แปลตรงตัวว่า "ถ้ามีคนคนนี้โดนรถบัสชน โปรเจกต์จะจบทันที")

Succession Planning ไม่ใช่เรื่องน่ากลัวหรือเป็นลางร้าย แต่เป็นสัญญาณของความเป็นมืออาชีพ — เหมือนบริษัทที่ดีต้องมีแผนสืบทอดตำแหน่ง CEO แม้ CEO คนปัจจุบันจะยังแข็งแรงดีอยู่ก็ตาม

### วิธีการหา Co-maintainer

#### 1. สังเกตพฤติกรรมของ Contributor ที่โดดเด่น

สัญญาณที่บ่งบอกว่า contributor คนหนึ่งมีศักยภาพเป็น co-maintainer:

- ส่ง PR คุณภาพสูงอย่างสม่ำเสมอเป็นเวลานาน (ไม่ใช่แค่ 1–2 ครั้ง)
- ช่วยตอบคำถามคนอื่นใน issue/discussion โดยไม่มีใครขอ
- แสดงความเข้าใจในวิสัยทัศน์และทิศทางของโปรเจกต์ ไม่ใช่แค่เขียนโค้ดเก่ง
- สื่อสารอย่างสุภาพและสร้างสรรค์แม้ในสถานการณ์ที่ตึงเครียด
- แสดงความสนใจอย่างชัดเจนที่จะมีส่วนร่วมมากขึ้น

#### 2. มอบสิทธิ์อย่างค่อยเป็นค่อยไป (Gradual Trust)

**ห้ามมอบสิทธิ์ maintainer เต็มรูปแบบในทันที** แม้ contributor คนนั้นจะดูน่าเชื่อถือแค่ไหนก็ตาม — นี่คือบทเรียนตรงจากกรณี XZ Utils ควรทำแบบขั้นบันได:

1. ให้สิทธิ์ **triage** ก่อน (จัดการ label, ปิด/เปิด issue) ซึ่งไม่กระทบโค้ดโดยตรง
2. ให้สิทธิ์ **review/approve** PR (แต่ยัง merge เองไม่ได้ ต้องให้อีกคน merge)
3. ให้สิทธิ์ **merge** ในโมดูลที่จำกัดขอบเขตก่อน
4. ให้สิทธิ์ **write access เต็มรูปแบบ** เมื่อมีประวัติความไว้ใจสะสมมานานพอ (มักอย่างน้อย 6 เดือน–1 ปี)
5. ให้สิทธิ์ **publish/release** และ **admin** เป็นขั้นสุดท้าย

ควรมีกระบวนการที่โปร่งใสและบันทึกไว้เป็นลายลักษณ์อักษร ไม่ใช่การตัดสินใจเงียบ ๆ คนเดียว — โปรเจกต์ขนาดใหญ่มักให้ maintainer ปัจจุบันทุกคนโหวตก่อนรับ maintainer ใหม่

#### 3. ทำ Public Announcement

เมื่อมอบสิทธิ์ maintainer ใหม่ ควรประกาศต่อสาธารณะ (ใน release notes, README, หรือ blog post) เพื่อความโปร่งใส ให้ชุมชนรับทราบและช่วยกันตรวจสอบ ไม่ใช่การเปลี่ยนแปลงที่เกิดขึ้นแบบเงียบ ๆ

### Project Succession Planning — วางแผนล่วงหน้า

#### เขียนเอกสาร SUCCESSION.md หรือระบุใน GOVERNANCE.md

เอกสารนี้ควรตอบคำถามสำคัญไว้ล่วงหน้า:

- ถ้า maintainer หลักหายไปโดยไม่แจ้งล่วงหน้าเป็นเวลานาน (เช่น ไม่มีการตอบสนองใด ๆ ภายใน 3–6 เดือน) ใครมีสิทธิ์เข้ามาดูแลต่อ
- ใครถือกุญแจสำคัญ (npm publish token, domain name, social media account, package registry ownership) และมีแผนสำรองอย่างไรถ้าคนนั้นติดต่อไม่ได้
- กระบวนการโหวตหรือแต่งตั้ง maintainer ใหม่เป็นอย่างไร

#### ใช้บริการช่วยระบุ Maintainer ที่ไม่ใช้งานแล้ว

แพลตฟอร์มอย่าง npm มีนโยบายที่อนุญาตให้ผู้ดูแล registry เข้ามาช่วยโอนสิทธิ์ package ที่ maintainer หายไปนานเกินไปให้กับ contributor ที่น่าเชื่อถือ ภายใต้เงื่อนไขที่รัดกุม (ต้องพยายามติดต่อ maintainer เดิมก่อนอย่างสมเหตุสมผล)

#### กรณีศึกษาการส่งต่อโปรเจกต์ที่ทำได้ดี

- **Python**: Guido van Rossum ผู้สร้างภาษา Python และเคยดำรงตำแหน่ง BDFL (Benevolent Dictator For Life) มาอย่างยาวนาน ประกาศลาออกจากตำแหน่งนี้อย่างเป็นทางการในปี 2018 พร้อมเปิดพื้นที่ให้ชุมชนถกเถียงและออกแบบ governance model ใหม่ ซึ่งท้ายที่สุดได้พัฒนาเป็นระบบ **Python Steering Council** ที่มาจากการเลือกตั้งประจำปีแทนการมี BDFL คนเดียว — เป็นตัวอย่างที่ดีของการเปลี่ยนผ่านอำนาจอย่างมีแผนและโปร่งใส แม้จะไม่มีเหตุฉุกเฉินบังคับก็ตาม
- **Node.js**: มีโครงสร้าง Technical Steering Committee (TSC) ที่ประกอบด้วยหลายคน ไม่พึ่งพา maintainer เดี่ยว ทำให้เมื่อสมาชิกคนใดคนหนึ่งลดบทบาทลง โปรเจกต์ยังเดินหน้าต่อได้อย่างราบรื่น

### สิ่งที่ต้องทำเมื่อคุณเองต้องการถอนตัวจากการเป็น Maintainer

ถ้าวันหนึ่งคุณต้องการหยุดดูแลโปรเจกต์ของตัวเอง แนวทางที่รับผิดชอบต่อชุมชนที่สุดคือ:

1. **ประกาศล่วงหน้าให้นานที่สุดเท่าที่ทำได้** (อย่างน้อย 1–3 เดือน ไม่ใช่หายไปทันที)
2. **เปิดหาผู้สืบทอดอย่างเปิดเผย** ผ่าน issue หรือ discussion ที่ปักหมุดไว้
3. **ถ่ายทอดความรู้ที่จำเป็น** (เอกสาร architecture ที่ไม่ได้เขียนไว้ กุญแจ/access ต่าง ๆ)
4. **อย่าลบหรือ archive repository ทิ้งไปเฉย ๆ** โดยไม่ให้โอกาสชุมชน fork ไปดูแลต่อ

## Step 858: Governance Model ต่าง ๆ ของโปรเจกต์ Open Source

**Governance Model** คือกรอบที่กำหนดว่า "ใครมีอำนาจตัดสินใจอะไร และตัดสินใจอย่างไร" ในโปรเจกต์ การเลือก governance model ที่เหมาะสมส่งผลต่อความยั่งยืน ความเร็วในการตัดสินใจ และความสามารถในการดึงดูด contributor ในระยะยาวอย่างมาก

### โมเดลที่ 1: BDFL (Benevolent Dictator For Life)

**แนวคิด:** มีบุคคลเดียว (มักเป็นผู้ก่อตั้งโปรเจกต์) ที่มีอำนาจตัดสินใจสุดท้ายในทุกเรื่อง แม้จะรับฟังความเห็นจากชุมชนก็ตาม

**ตัวอย่าง:**
- **Linux Kernel** — Linus Torvalds ยังคงเป็นผู้มีอำนาจตัดสินใจสูงสุดในเรื่องสถาปัตยกรรมหลัก แม้จะมี maintainer ของแต่ละ subsystem จำนวนมาก
- **Python** — Guido van Rossum เคยดำรงตำแหน่งนี้จนถึงปี 2018 (ก่อนเปลี่ยนไปใช้ Steering Council)

**ข้อดี:**
- ตัดสินใจได้เร็ว ไม่ต้องผ่านกระบวนการโหวตที่ซับซ้อน
- วิสัยทัศน์ของโปรเจกต์มีความสอดคล้องกันสูง เพราะมาจากคนคนเดียว
- ลดการถกเถียงที่ไม่มีที่สิ้นสุด (bikeshedding ระดับใหญ่)

**ข้อเสีย:**
- Bus factor = 1 ความเสี่ยงสูงมากถ้า BDFL หายไปโดยไม่มีแผนสำรอง
- อาจกลายเป็นคอขวด (bottleneck) เมื่อโปรเจกต์โตขึ้นมาก
- ถ้า BDFL ตัดสินใจผิดพลาด ไม่มีกลไกถ่วงดุลที่ชัดเจน

### โมเดลที่ 2: Meritocracy (ระบบคุณธรรม/ผลงาน)

**แนวคิด:** อำนาจในการตัดสินใจขึ้นอยู่กับ "ผลงานและความไว้ใจที่สั่งสม" ไม่ใช่ตำแหน่งที่ตายตัว คนที่ contribute มากและมีคุณภาพสูงจะค่อย ๆ ได้รับอำนาจมากขึ้นตามธรรมชาติ

**ตัวอย่าง:**
- **Apache Software Foundation** ใช้หลักการที่เรียกว่า **"The Apache Way"** ซึ่งเป็นระบบ meritocracy อย่างเป็นทางการ — ใครก็ตามที่ contribute มากพอและได้รับการโหวตจาก PMC (Project Management Committee) ที่มีอยู่ จะได้เป็น **Committer** และต่อมาอาจได้เป็น **PMC Member**

**ข้อดี:**
- ยุติธรรมในเชิงหลักการ — ใครก็ได้ที่ทำงานหนักและมีคุณภาพสามารถไต่เต้าขึ้นไปได้
- กระจายอำนาจมากกว่า BDFL ลด bus factor
- สร้างแรงจูงใจให้คนอยาก contribute ต่อเนื่อง

**ข้อเสีย:**
- คำว่า "merit" วัดได้ยากและอาจถูกตีความไม่เป็นธรรม (bias โดยไม่รู้ตัวต่อคนที่มีเวลาว่างมากกว่า เช่น คนที่ไม่มีภาระครอบครัว)
- กระบวนการตัดสินใจอาจช้าลงเพราะต้องผ่านการโหวตหรือ consensus
- อาจเกิดกลุ่มก้อนอำนาจ (in-group) ที่ทำให้คนนอกเข้าถึงยากในทางปฏิบัติ แม้หลักการจะเปิดกว้างก็ตาม

### โมเดลที่ 3: Foundation-based Governance

**แนวคิด:** โปรเจกต์ถูกโอนเข้าไปอยู่ภายใต้มูลนิธิ (non-profit foundation) ที่เป็นกลาง ไม่ผูกกับบริษัทใดบริษัทหนึ่ง มูลนิธิทำหน้าที่จัดการเรื่องกฎหมาย ทรัพย์สินทางปัญญา การเงิน และ governance structure อย่างเป็นทางการ

**ตัวอย่างที่สำคัญ:**

| มูลนิธิ | ตัวอย่างโปรเจกต์ในสังกัด |
|---|---|
| **Apache Software Foundation (ASF)** | Apache Kafka, Apache Spark, Apache HTTP Server |
| **Linux Foundation** | Linux Kernel, Kubernetes (ผ่าน CNCF), Node.js (ผ่าน OpenJS Foundation) |
| **Cloud Native Computing Foundation (CNCF)** — อยู่ภายใต้ Linux Foundation | Kubernetes, Prometheus, Envoy, containerd |
| **OpenJS Foundation** | Node.js, jQuery, Electron |
| **Python Software Foundation (PSF)** | CPython (ภาษา Python เอง) |

**โครงสร้างการตัดสินใจของโปรเจกต์ภายใต้ CNCF โดยทั่วไป:**

```
        ┌───────────────────────────┐
        │   CNCF Governing Board    │  ← กำหนดนโยบายระดับมูลนิธิ
        │  (ตัวแทนบริษัทสมาชิก)      │
        └─────────────┬─────────────┘
        ┌─────────────┴─────────────┐
        │  Technical Oversight       │  ← ดูแลมาตรฐานทางเทคนิค
        │  Committee (TOC)           │     ของทุกโปรเจกต์ใน CNCF
        └─────────────┬─────────────┘
   ┌──────────────────┼──────────────────┐
   │                  │                  │
┌──▼──────┐    ┌──────▼─────┐    ┌───────▼────┐
│Kubernetes│    │ Prometheus │    │   Envoy    │  ← แต่ละโปรเจกต์มี
│Steering  │    │ Governance │    │ Maintainers│     governance ของตัวเอง
│Committee │    │            │    │            │     (Kubernetes ใช้ SIG)
└──────────┘    └────────────┘    └────────────┘
```

**ข้อดี:**
- มีความเป็นกลางทางองค์กร ลดความกังวลว่าบริษัทใดบริษัทหนึ่งจะควบคุมโปรเจกต์เพื่อผลประโยชน์ตัวเอง
- มีทรัพยากรสนับสนุนด้านกฎหมาย, การเงิน, event, marketing ที่โปรเจกต์เดี่ยวไม่มีปัญญาทำเอง
- สร้างความน่าเชื่อถือให้องค์กรใหญ่กล้านำไปใช้งาน (enterprise adoption) เพราะรู้ว่ามีโครงสร้างธรรมาภิบาลที่ตรวจสอบได้

**ข้อเสีย:**
- กระบวนการเป็นทางการมากขึ้น อาจช้ากว่าโปรเจกต์อิสระเล็ก ๆ
- อิทธิพลของบริษัทใหญ่ที่เป็นสมาชิกมูลนิธิ (ผ่านเงินสนับสนุน) อาจยังคงส่งผลทางอ้อมต่อทิศทางโปรเจกต์ได้ แม้จะมีกลไกป้องกันแล้วก็ตาม
- การเข้าร่วมมูลนิธิมีข้อกำหนด กระบวนการ และค่าใช้จ่ายบางอย่างที่โปรเจกต์เล็กอาจไม่พร้อม

### โมเดลที่ 4: Corporate-backed Single-vendor Open Source

**แนวคิด:** โปรเจกต์ถูกพัฒนาและดูแลโดยบริษัทเดียวเป็นหลัก แม้จะเปิดให้ contributor ภายนอกส่ง PR ได้ แต่การตัดสินใจสุดท้ายอยู่ที่พนักงานของบริษัทนั้น

**ตัวอย่าง:** React (Meta), TypeScript (Microsoft), Vue.js (นำโดย Evan You ผ่านบริษัทของตัวเอง), Redis (Redis Ltd. ก่อนเปลี่ยนไลเซนส์)

**ข้อดี:**
- มีทรัพยากรเต็มเวลาดูแล ความเร็วในการพัฒนาสูง
- ทิศทางชัดเจน ไม่ต้องผ่านกระบวนการ consensus ที่ซับซ้อน

**ข้อเสีย:**
- ความเสี่ยงที่บริษัทจะเปลี่ยนทิศทางหรือเปลี่ยนไลเซนส์เพื่อผลประโยชน์ทางธุรกิจ (ดู Step 859 เรื่อง license เปลี่ยนแปลงของ Redis, MongoDB, Elasticsearch)
- Contributor ภายนอกอาจรู้สึกว่าเสียงตัวเองมีน้ำหนักน้อยกว่าพนักงานบริษัท

### จะเลือก Governance Model ไหนดี

ไม่มีโมเดลที่ "ดีที่สุด" ตายตัว การเลือกขึ้นอยู่กับบริบท:

| สถานการณ์ | โมเดลที่มักเหมาะสม |
|---|---|
| โปรเจกต์เล็ก เพิ่งเริ่ม มีคนดูแล 1–2 คน | BDFL แบบไม่เป็นทางการ (ยังไม่ต้องมีโครงสร้างซับซ้อน) |
| โปรเจกต์เติบโต มี contributor หลากหลายจากหลายองค์กร | Meritocracy พร้อมเอกสาร governance ชัดเจน |
| โปรเจกต์กลายเป็นโครงสร้างพื้นฐานสำคัญของอุตสาหกรรม | Foundation-based เพื่อความเป็นกลางและความน่าเชื่อถือระยะยาว |
| โปรเจกต์เป็นกลยุทธ์ทางธุรกิจหลักของบริษัท | Corporate-backed พร้อมเปิดรับ contribution ภายนอกอย่างมีขอบเขตชัดเจน |

## Step 859: การสร้างรายได้จาก Open Source อย่างยั่งยืน

### ทำไมเรื่องเงินถึงเป็นเรื่องที่หลีกเลี่ยงไม่ได้

หลายคนเข้าสู่วงการ Open Source ด้วยอุดมการณ์เรื่องการแบ่งปันความรู้และไม่คิดเรื่องเงินตั้งแต่ต้น แต่อย่างที่เห็นใน Step 856 ปัญหา burnout ส่วนใหญ่มีรากมาจากการที่งานหนักมากแต่ไม่มีรายได้รองรับ การหาทางสร้างรายได้ที่ยั่งยืนจึงไม่ใช่เรื่องขัดกับอุดมการณ์ Open Source แต่เป็นเงื่อนไขจำเป็นสำหรับความอยู่รอดของโปรเจกต์ในระยะยาว

### โมเดลที่ 1: Individual Sponsorship (การบริจาคส่วนบุคคล)

#### GitHub Sponsors

แพลตฟอร์มที่ผนวกเข้ากับ GitHub โดยตรง ให้ผู้ใช้สามารถบริจาคเงินรายเดือนหรือครั้งเดียวให้ maintainer โดยตรง ข้อดีคือความสะดวก (ผู้บริจาคใช้บัญชี GitHub ที่มีอยู่แล้ว) และในบางกรณี GitHub เคยมีโปรแกรม matching fund ที่สมทบเงินให้ maintainer บางกลุ่มเพิ่มเติม

#### Open Collective

แพลตฟอร์มที่เน้นความโปร่งใสสูงมาก — ทุกรายรับรายจ่ายของโปรเจกต์แสดงต่อสาธารณะ ให้ทั้งบุคคลและองค์กรบริจาคได้ และรองรับการเป็น **fiscal host** ให้โปรเจกต์ที่ยังไม่มีสถานะนิติบุคคลของตัวเอง (เช่น Webpack, Babel ใช้ Open Collective ในการจัดการเงินทุนอย่างโปร่งใส)

#### Patreon / Ko-fi / Buy Me a Coffee

แพลตฟอร์มทั่วไปที่ไม่ได้เฉพาะเจาะจงกับซอฟต์แวร์ แต่บาง maintainer เลือกใช้เพราะความคุ้นเคยของผู้บริจาค

### โมเดลที่ 2: Tidelift และแพลตฟอร์มลักษณะ "Subscription for Maintenance"

**Tidelift** เป็นตัวอย่างที่น่าสนใจของโมเดลที่จับคู่ maintainer กับองค์กรที่ต้องการความมั่นใจด้าน security/maintenance ของ dependency ที่ใช้อยู่ องค์กรจ่ายค่าสมัครสมาชิกให้ Tidelift ซึ่งจะกระจายส่วนหนึ่งเป็นรายได้ให้ maintainer ที่เข้าร่วมโปรแกรม แลกกับการที่ maintainer ต้องรับผิดชอบดูแลด้าน security patch, license compliance ตามมาตรฐานที่ตกลงกัน

### โมเดลที่ 3: Corporate Sponsorship (การสนับสนุนจากองค์กร)

บริษัทที่ใช้โปรเจกต์ Open Source เป็นส่วนสำคัญของ business (เช่นใช้เป็น dependency หลักในผลิตภัณฑ์) มักยินดีสนับสนุนเงินให้โปรเจกต์นั้นโดยตรง หรือจ้าง maintainer เข้าเป็นพนักงานเพื่อทำงานดูแลโปรเจกต์แบบเต็มเวลา (เช่น บริษัทเทคโนโลยีใหญ่จำนวนมากจ้างวิศวกรที่เป็น core maintainer ของ Kubernetes, React, Rust ให้ทำงานนี้เป็นงานประจำ)

### โมเดลที่ 4: Dual Licensing

**แนวคิด:** โปรเจกต์เปิด source code ภายใต้ license แบบ copyleft ที่เข้มงวด (เช่น AGPL) สำหรับผู้ใช้ทั่วไปที่ยินดีเปิด source code ของตัวเองด้วย ในขณะที่เสนอ **license เชิงพาณิชย์แยกต่างหาก** ให้บริษัทที่ต้องการใช้โค้ดในผลิตภัณฑ์ปิด (closed-source) โดยไม่ต้องเปิดเผยโค้ดของตัวเอง

**ตัวอย่าง:** MongoDB (ก่อนเปลี่ยนเป็น SSPL), MySQL (Oracle ใช้ dual license ระหว่าง GPL และ commercial license มายาวนาน), Qt Framework

**ข้อควรระวัง:** dual licensing ต้องการให้เจ้าของ codebase มีสิทธิ์ทางกฎหมายเต็มรูปแบบเหนือโค้ดทั้งหมด (ต้องมี Contributor License Agreement ที่รัดกุมจาก contributor ทุกคน) ซึ่งเป็นเงื่อนไขที่ทำให้บาง license แบบนี้ถูกวิจารณ์ว่าไม่ใช่ Open Source อย่างแท้จริงในเชิงจิตวิญญาณ

### กรณีศึกษาการเปลี่ยน License เพื่อความอยู่รอดทางธุรกิจ (และข้อถกเถียงที่ตามมา)

หลายบริษัทที่สร้างโปรเจกต์ Open Source ยอดนิยมเผชิญปัญหาที่ **ผู้ให้บริการ Cloud รายใหญ่นำโค้ด Open Source ของตนไปให้บริการเชิงพาณิชย์โดยไม่ได้สนับสนุนกลับคืนสู่โปรเจกต์ต้นทาง** ทำให้บริษัทเจ้าของโปรเจกต์เดิมสูญเสียรายได้ กรณีที่เป็นที่ถกเถียงมาก ได้แก่:

- **MongoDB** เปลี่ยนจาก AGPL ไปเป็น **SSPL (Server Side Public License)** ในปี 2018 ซึ่งกำหนดว่าถ้าใครนำ MongoDB ไปให้บริการเป็น "Service" เชิงพาณิชย์ ต้องเปิดเผย source code ของระบบทั้งหมดที่ใช้ให้บริการนั้นด้วย — SSPL ไม่ได้รับการรับรองจาก Open Source Initiative (OSI) ว่าเป็น Open Source license ที่แท้จริง
- **Elasticsearch** เปลี่ยนจาก Apache 2.0 ไปเป็น license แบบ dual (SSPL/Elastic License) ในปี 2021 หลังมีข้อพิพาทกับ AWS ที่ให้บริการ Elasticsearch แบบ managed service
- **Redis** เปลี่ยนจาก BSD ไปเป็น dual (RSALv2/SSPLv1) ในปี 2024 ด้วยเหตุผลคล้ายกัน ก่อนที่ชุมชนบางส่วนจะแยกไป fork เป็นโปรเจกต์ **Valkey** ภายใต้การดูแลของ Linux Foundation เพื่อรักษาความเป็น Open Source แบบดั้งเดิมไว้

เหตุการณ์เหล่านี้สอนบทเรียนสำคัญ: **การเปลี่ยน license เพื่อความอยู่รอดทางธุรกิจเป็นทางเลือกที่ถูกกฎหมายเสมอ (ถ้าเจ้าของสิทธิ์ทำได้จริงตามกฎหมาย)** แต่ก็มาพร้อมความเสี่ยงที่ชุมชนจะไม่พอใจและแยกไป fork โปรเจกต์อื่นแทน Maintainer และองค์กรที่คิดจะเปลี่ยน license ต้องชั่งน้ำหนักระหว่างความอยู่รอดทางธุรกิจกับความไว้วางใจของชุมชนอย่างรอบคอบ

### ข้อพิจารณาด้านจริยธรรมของการหาเงินจาก Open Source

- **ความโปร่งใส** — ถ้าโปรเจกต์รับเงินสนับสนุนจากบริษัทใดบริษัทหนึ่ง ควรเปิดเผยต่อสาธารณะเสมอ เพื่อป้องกันข้อครหาเรื่องผลประโยชน์ทับซ้อน
- **อย่าให้เงินซื้ออิทธิพลต่อทิศทางเทคนิค** — สปอนเซอร์ไม่ควรมีสิทธิ์สั่งการทิศทางโปรเจกต์โดยตรง มิเช่นนั้นจะสูญเสียความเป็นกลางที่ทำให้ชุมชนไว้ใจ
- **การกระจายรายได้อย่างเป็นธรรม** — ถ้ามี maintainer หลายคน ควรมีกลไกแบ่งรายได้ที่ชัดเจนและเป็นธรรม ไม่ใช่ให้คนเดียวเก็บทั้งหมดขณะที่คนอื่นทำงานเท่ากัน

## Step 860: แบบฝึกหัด — เขียนแผนการเป็น Maintainer ให้โปรเจกต์ของตัวเอง

ถึงเวลานำสิ่งที่เรียนมาทั้งหมดใน Step 851–859 มาประยุกต์ใช้จริง แบบฝึกหัดนี้ให้คุณเขียน **Maintainer Plan** สำหรับโปรเจกต์ Open Source ของตัวเอง (ถ้ามีอยู่แล้ว) หรือโปรเจกต์สมมติที่คุณอยากสร้างในอนาคต

### ขั้นตอนที่ 1: เลือกโปรเจกต์

เลือกอย่างใดอย่างหนึ่ง:

- โปรเจกต์ Open Source ที่คุณมีอยู่แล้วบน GitHub/GitLab (แม้จะยังเล็กมาก)
- โปรเจกต์สมมติที่คุณตั้งใจจะสร้างในอนาคต (เช่น "CLI tool สำหรับจัดการ dotfiles" หรือ "library แปลงไฟล์ Markdown เป็น PDF")

### ขั้นตอนที่ 2: เขียนเอกสาร MAINTAINER_PLAN.md ตามหัวข้อต่อไปนี้

สร้างไฟล์ `MAINTAINER_PLAN.md` ในโปรเจกต์ของคุณ (หรือในโฟลเดอร์ฝึกฝนที่เตรียมไว้ตั้งแต่ Part 01) แล้วตอบคำถามต่อไปนี้ให้ครบทุกหัวข้อ:

```markdown
# Maintainer Plan: [ชื่อโปรเจกต์]

## 1. วิสัยทัศน์และขอบเขต (Vision & Scope)
- โปรเจกต์นี้มีเป้าหมายอะไร
- อะไรคือสิ่งที่โปรเจกต์นี้ "จะไม่ทำ" (Non-goals) — ระบุให้ชัดเพื่อใช้ปฏิเสธ
  feature request ที่ไม่ตรงทิศทางในอนาคต

## 2. Governance Model ที่เลือกใช้
- เลือกโมเดลไหนในช่วงเริ่มต้น (BDFL แบบไม่เป็นทางการ / Meritocracy)
- เกณฑ์อะไรที่จะทำให้เปลี่ยนโมเดลเมื่อโปรเจกต์โตขึ้น

## 3. Contributor Ladder
- นิยามขั้นบันไดการเลื่อนขั้นของ contributor ในโปรเจกต์นี้
  (เช่น First-time → Regular → Reviewer → Maintainer)
- เกณฑ์เชิงปริมาณ/คุณภาพของแต่ละขั้น

## 4. Triage Workflow
- จะใช้ label ชุดไหน (ระบุอย่างน้อย 8-10 label พร้อมความหมาย)
- ความถี่ในการ triage issue ใหม่ (เช่น สัปดาห์ละครั้ง)
- นโยบายปิด stale issue (กี่วันไม่มีการตอบกลับจะปิด)

## 5. PR Review Policy
- จำนวน approval ขั้นต่ำก่อน merge ได้
- นโยบายเรื่อง CLA/DCO
- เวลาตอบกลับ PR ที่ตั้งเป้าไว้ (SLA ภายใน)

## 6. Burnout Prevention Plan
- ขอบเขตเวลาที่จะทุ่มเทให้โปรเจกต์นี้ต่อสัปดาห์
- แผนสำรองถ้ารู้สึกเหนื่อยล้า (จะประกาศพักอย่างไร)
- ระบบอัตโนมัติที่จะใช้ลดภาระงานซ้ำ ๆ

## 7. Succession Plan
- ถ้าคุณหายไปโดยไม่แจ้งล่วงหน้าเกิน 3 เดือน ใครควรเข้ามาดูแลต่อ
- ใครถือกุญแจสำคัญอะไรบ้าง (publish token, domain, ฯลฯ) และมีแผนสำรองไหม

## 8. Funding Plan
- จะเปิดรับ sponsorship ผ่านช่องทางไหน (ถ้ายังไม่พร้อม ให้ระบุเงื่อนไข
  ที่จะทำให้เริ่มเปิดรับในอนาคต)
- นโยบายความโปร่งใสเรื่องเงินที่ได้รับ

## 9. Code of Conduct และการบังคับใช้
- จะใช้ CoC ฉบับไหนเป็นต้นแบบ (จะเจาะลึกใน Part 87)
- ใครมีหน้าที่รับผิดชอบบังคับใช้เมื่อมีการรายงานปัญหา
```

### ขั้นตอนที่ 3: ทดสอบแผนของคุณด้วยสถานการณ์จำลอง

ลองตอบคำถามเหล่านี้โดยอ้างอิงจากแผนที่เขียนไว้ในขั้นตอนที่ 2 เพื่อทดสอบว่าแผนใช้งานได้จริงหรือไม่:

1. มีคนแปลกหน้าเปิด PR ขนาดใหญ่ที่ปรับสถาปัตยกรรมทั้งหมดโดยไม่ได้ปรึกษาก่อน คุณจะตอบอย่างไรตามนโยบายที่เขียนไว้
2. มี issue เดียวกันถูกรายงานซ้ำเป็นครั้งที่ 5 คุณจะจัดการอย่างไรตาม triage workflow ที่วางไว้
3. คุณรู้สึกเหนื่อยล้ามากจนไม่อยากเปิด GitHub อีกเลยเป็นเวลา 2 สัปดาห์ที่ผ่านมา แผน burnout prevention ของคุณบอกให้ทำอะไร
4. มีนักพัฒนาอาวุโสคนหนึ่งวิจารณ์การตัดสินใจของคุณอย่างรุนแรงในที่สาธารณะ คุณจะตอบสนองอย่างไรโดยยึดหลักจาก Step 855

### ขั้นตอนที่ 4 (ถ้ามีโปรเจกต์จริง): เผยแพร่แผนบางส่วนสู่สาธารณะ

ถ้าคุณมีโปรเจกต์ Open Source จริงอยู่แล้ว ให้นำเนื้อหาบางส่วนจากแผนนี้ (โดยเฉพาะหัวข้อ Governance, Contributor Ladder, Triage Workflow) ไปเขียนเป็นไฟล์ `GOVERNANCE.md` ในโปรเจกต์จริงของคุณ เพื่อสร้างความโปร่งใสให้กับชุมชนตั้งแต่วันนี้ ไม่ต้องรอให้โปรเจกต์ใหญ่ก่อนแล้วค่อยทำ — ยิ่งวางรากฐานเร็วเท่าไหร่ ยิ่งป้องกันปัญหาที่จะเกิดขึ้นตอนโปรเจกต์โตได้มากเท่านั้น

## สรุป Part 86

ใน Part นี้เราได้เรียนรู้ว่า:

1. **Maintainer ไม่ใช่แค่คนเขียนโค้ดเก่ง** แต่ต้องรับผิดชอบ 6 ด้านหลัก: technical stewardship, quality gatekeeping, community management, governance, release management และ security
2. โครงสร้างบทบาทในโปรเจกต์ Open Source แบ่งเป็นพีระมิด: **Contributor → Regular Contributor → Maintainer → Core Team** โดยแต่ละขั้นมีระดับสิทธิ์และความรับผิดชอบต่างกัน
3. **การ Triage issue** ที่ดีต้องมี 5 ขั้นตอน: ตรวจสอบความสมบูรณ์ → เช็คความซ้ำซ้อน → จัดหมวดหมู่ด้วย label → กำหนด priority → ปิด issue ที่ไม่เกี่ยวข้องอย่างสุภาพแต่เด็ดขาด
4. **การ Review PR จากคนภายนอก** ต่างจากการ review ในทีมตัวเองมาก ต้องสันนิษฐานเจตนาดี อธิบายเหตุผล แยก feedback ที่ต้องแก้กับความเห็นส่วนตัว และตอบกลับให้รวดเร็ว
5. การจัดการ **contributor ที่หลากหลาย** ตั้งแต่มือใหม่ถึงมือเก๋าที่มีความเห็นแรง ต้องใช้วิธีที่ต่างกัน และต้องกล้าปฏิเสธเมื่อจำเป็น พร้อมบังคับใช้ Code of Conduct อย่างเสมอภาค
6. **Maintainer Burnout** เป็นปัญหาเชิงโครงสร้างที่ร้ายแรงของวงการ Open Source ถึงขั้นเชื่อมโยงกับความเสี่ยงด้านความปลอดภัยระดับโลกอย่างกรณี **XZ Utils backdoor**
7. การหา **co-maintainer** ควรทำแบบค่อยเป็นค่อยไป มอบสิทธิ์เป็นขั้นบันได และควรมี **Succession Plan** เขียนไว้ล่วงหน้าเสมอ ไม่ใช่รอวิกฤต
8. **Governance Model** มีหลายแบบ — BDFL, Meritocracy, Foundation-based (Apache, CNCF, Linux Foundation), Corporate-backed — แต่ละแบบมีข้อดีข้อเสียต่างกัน ต้องเลือกให้เหมาะกับขนาดและบริบทของโปรเจกต์
9. การสร้างรายได้จาก Open Source อย่างยั่งยืนทำได้หลายทาง ทั้ง GitHub Sponsors, Open Collective, Tidelift, Corporate Sponsorship และ Dual Licensing แต่ทุกทางเลือกมีข้อพิจารณาด้านความไว้ใจของชุมชนที่ต้องชั่งน้ำหนักเสมอ
