## Step 861: ทำไมต้องมี CONTRIBUTING.md — ผลกระทบต่อความเร็วในการ onboard contributor ใหม่

### ย้อนความจาก Part 24 Step 236

ใน **Part 24 Step 236** เราเรียนไปแล้วว่าในฐานะ **contributor** ที่จะไปช่วยโปรเจกต์คนอื่น สิ่งแรกที่ต้องทำคือ **อ่าน CONTRIBUTING.md ก่อนลงมือ** เพราะแต่ละโปรเจกต์มีกฎที่ต่างกัน ตอนนั้นเราสัญญาไว้ว่าจะกลับมาเจาะลึกเรื่องนี้ใน Part 87 — และนี่คือ Part นั้น

แต่คราวนี้เราจะสลับมุมมอง จากคนที่ **"อ่าน"** ไฟล์นี้ มาเป็นคนที่ **"เขียน"** ไฟล์นี้ในฐานะเจ้าของโปรเจกต์หรือ maintainer เพราะไม่ว่าคุณจะเปิดโปรเจกต์ Open Source เล็ก ๆ ของตัวเอง หรือดูแลโปรเจกต์ภายในบริษัทที่มีทีมเปลี่ยนคนบ่อย ทักษะการเขียนเอกสารกำกับการ contribute ที่ดีคือทักษะที่จำเป็นมาก

### ปัญหาของโปรเจกต์ที่ไม่มี CONTRIBUTING.md

ลองจินตนาการว่าคุณเป็นนักพัฒนาที่อยากช่วยแก้บั๊กเล็ก ๆ ในโปรเจกต์หนึ่งที่ไม่มี CONTRIBUTING.md เลย คุณจะต้องเดาเอาเองทุกเรื่อง:

- ต้องรันคำสั่งอะไรก่อนถึงจะได้โปรเจกต์ขึ้นมาทำงานบนเครื่อง
- ต้องใช้ Node.js เวอร์ชันไหน Python เวอร์ชันไหน
- มี test suite ไหม รันด้วยคำสั่งอะไร
- commit message ต้องเขียนแบบไหน มีกฎไหม
- ต้องเปิด issue ก่อนไหม หรือส่ง PR ได้เลย
- PR จะไปที่ branch ไหน `main` หรือ `develop`
- ใครจะเป็นคน review ใช้เวลานานแค่ไหน

เมื่อไม่มีคำตอบ contributor ส่วนใหญ่จะเลือกทำทางใดทางหนึ่งจากสองทาง: **(1) เดาเอาเองแล้วเสี่ยงทำผิดจนถูก reject** หรือ **(2) เลิกล้มความตั้งใจไปเลยเพราะรู้สึกว่ามันยุ่งยากเกินไป** ทั้งสองทางล้วนเป็นการเสียโอกาสของโปรเจกต์ทั้งสิ้น เพราะ contributor ที่ตั้งใจจะช่วยเหลือ กลับต้องเดินจากไปเพียงเพราะไม่มีเอกสารบอกทาง

### CONTRIBUTING.md แก้ปัญหาอะไรบ้าง

| ปัญหาที่ไม่มี CONTRIBUTING.md | สิ่งที่ CONTRIBUTING.md แก้ให้ |
|---|---|
| Setup environment ใช้เวลาหลายชั่วโมงเพราะต้องเดา | มีคำสั่ง setup ที่ copy-paste แล้วรันได้ทันที |
| Maintainer ต้องตอบคำถามเดิม ๆ ซ้ำ ๆ ในทุก PR | คำตอบถูกเขียนไว้ล่วงหน้าครั้งเดียว ใช้ได้ตลอด |
| PR ถูก reject เพราะรูปแบบไม่ตรงที่ทีมต้องการ | Contributor รู้กฎล่วงหน้า ทำถูกตั้งแต่รอบแรก |
| Contributor ใหม่ไม่รู้ว่าจะเริ่มจากตรงไหน | มีลิงก์ไปยัง good first issue และช่องทางถามคำถาม |
| Code review ใช้เวลานานเพราะต้องแก้ style ซ้ำหลายรอบ | Linter/formatter ถูกกำหนดไว้ชัดเจน รันอัตโนมัติได้ |

### ผลกระทบเชิงปฏิบัติที่สังเกตได้จริง

โปรเจกต์ Open Source ขนาดใหญ่แทบทุกโปรเจกต์ที่ประสบความสำเร็จในการดึงดูด contributor ภายนอกจำนวนมาก — ไม่ว่าจะเป็น Kubernetes, Rust, VS Code, React — ล้วนมี CONTRIBUTING.md ที่เขียนไว้อย่างละเอียดและปรับปรุงอยู่เสมอ นี่ไม่ใช่เรื่องบังเอิญ เพราะ:

1. **ลดต้นทุนการสื่อสารซ้ำ (Reduce repeated communication cost)** — คำถามที่ maintainer ต้องตอบซ้ำ ๆ ทุกวันถูกย้ายไปอยู่ในเอกสารที่อ่านได้เอง ทำให้ maintainer มีเวลาไปโฟกัสกับการ review โค้ดจริง ๆ มากขึ้น
2. **ลด friction ตั้งแต่วินาทีแรก** — ยิ่ง contributor ใหม่เจอ friction (อุปสรรคเล็ก ๆ น้อย ๆ) มากเท่าไหร่ในช่วง 10 นาทีแรกที่เข้ามา โอกาสที่เขาจะเลิกล้มกลางทางก็ยิ่งสูงขึ้นเท่านั้น เอกสารที่ดีคือการลด friction นี้ให้เหลือน้อยที่สุด
3. **สร้างความยุติธรรมและความสม่ำเสมอ** — เมื่อกฎถูกเขียนไว้ชัดเจนเป็นลายลักษณ์อักษร ทุกคนถูกตัดสินด้วยมาตรฐานเดียวกัน ลดข้อครหาว่า maintainer เลือกปฏิบัติ
4. **เป็นเอกสารอ้างอิงเมื่อเกิดข้อโต้แย้ง** — เวลามีคน contribute ผิดกฎ maintainer สามารถชี้ไปที่ CONTRIBUTING.md ได้ทันทีโดยไม่ต้องอธิบายด้วยน้ำเสียงส่วนตัว ซึ่งช่วยลดความขัดแย้งเชิงอารมณ์ได้มาก

### CONTRIBUTING.md ไม่ใช่แค่ "มารยาท" แต่คือ "โครงสร้างพื้นฐาน"

หลายคนเข้าใจผิดว่า CONTRIBUTING.md เป็นแค่เอกสารมารยาทดี ๆ ที่มีก็ได้ไม่มีก็ได้ แต่ในความเป็นจริง มันคือ **โครงสร้างพื้นฐาน (infrastructure)** ของโปรเจกต์ไม่ต่างจาก CI/CD pipeline หรือ test suite เพราะมันทำหน้าที่ **automate การสื่อสาร** ระหว่าง maintainer กับ contributor ในอนาคตที่ยังไม่เคยรู้จักกันมาก่อน

GitHub เองก็ให้ความสำคัญกับเรื่องนี้ถึงขนาดสร้างฟีเจอร์ **"Community Standards"** (เข้าถึงได้ที่ tab Insights → Community ของ repo) ที่จะเช็คว่า repository ของคุณมีไฟล์เหล่านี้ครบหรือไม่: README, CONTRIBUTING, LICENSE, CODE_OF_CONDUCT, ISSUE_TEMPLATE, PULL_REQUEST_TEMPLATE, SECURITY.md — และแสดงเป็น checklist เปอร์เซ็นต์ความสมบูรณ์ของ repo ให้เห็นชัดเจน

ใน Step ถัดไป เราจะมาดูกันว่า CONTRIBUTING.md ที่ "ดี" ต้องมีโครงสร้างอย่างไรบ้าง

## Step 862: โครงสร้างของ CONTRIBUTING.md ที่ดี

CONTRIBUTING.md ที่ดีไม่ได้แปลว่ายาวที่สุด แต่แปลว่า **ตอบคำถามที่ contributor ต้องการรู้ได้ครบถ้วนตามลำดับที่เขาจะเจอปัญหาจริง** ต่อไปนี้คือโครงสร้างมาตรฐานที่โปรเจกต์ระดับมืออาชีพส่วนใหญ่ใช้

### โครงสร้างหลัก 8 ส่วน

| # | ส่วน | ตอบคำถามอะไร |
|---|---|---|
| 1 | Welcome / Introduction | โปรเจกต์นี้คืออะไร ยินดีต้อนรับแบบไหน |
| 2 | Code of Conduct | ต้องประพฤติตัวอย่างไร (ลิงก์ไป CODE_OF_CONDUCT.md) |
| 3 | Ways to Contribute | contribute ได้กี่แบบ ไม่ใช่แค่เขียนโค้ด |
| 4 | Development Setup | ต้อง clone/install/run อย่างไรให้ทำงานได้บนเครื่อง |
| 5 | Coding Style & Linting | เขียนโค้ดสไตล์ไหน มีเครื่องมือตรวจอะไรบ้าง |
| 6 | Running Tests | รัน test อย่างไร ต้องเขียน test เพิ่มไหม |
| 7 | Commit Message Convention | commit message ต้องเขียนแบบไหน |
| 8 | Pull Request Process | ขั้นตอนตั้งแต่เปิด PR จนถึง merge เป็นอย่างไร |

มาดูรายละเอียดของแต่ละส่วนกัน

### 1. Welcome / Introduction

ควรสั้น กระชับ บอกว่าโปรเจกต์นี้ยินดีต้อนรับ contributor แบบไหน (ต้องการ bug report, feature, docs, translation หรือทั้งหมด) และควรมีลิงก์ไปยัง README สำหรับคนที่ยังไม่รู้จักโปรเจกต์เลย

```markdown
# Contributing to TaskFlow

ขอบคุณที่สนใจช่วยพัฒนา TaskFlow! เอกสารนี้จะแนะนำทุกอย่างที่คุณต้องรู้
ก่อนเริ่ม contribute ไม่ว่าจะเป็นการรายงานบั๊ก เสนอฟีเจอร์ใหม่ แก้ไขเอกสาร
หรือส่งโค้ดเข้ามาโดยตรง
```

### 2. Code of Conduct

ทุก CONTRIBUTING.md ควรมีลิงก์ชัดเจนไปยัง `CODE_OF_CONDUCT.md` ตั้งแต่ต้นเอกสาร เพื่อยืนยันว่าโปรเจกต์นี้เป็นพื้นที่ปลอดภัย เราจะเจาะลึกเรื่อง Code of Conduct ใน Step 863-865

### 3. Ways to Contribute

จุดที่โปรเจกต์มือใหม่มักพลาดคือคิดว่า "contribute = เขียนโค้ดเท่านั้น" แต่โปรเจกต์ที่แข็งแรงจะเปิดกว้างให้ contribute ได้หลายรูปแบบ:

- **Bug reports** — รายงานปัญหาที่เจอ พร้อมขั้นตอนการทำซ้ำ (reproduction steps)
- **Feature requests** — เสนอไอเดียฟีเจอร์ใหม่
- **Code contributions** — แก้บั๊กหรือเพิ่มฟีเจอร์จริง
- **Documentation** — แก้ไข/เพิ่มเติมเอกสาร README, Wiki, คู่มือ API
- **Translation** — แปลเอกสารหรือ UI เป็นภาษาอื่น
- **Design** — ออกแบบ UI/UX, icon, logo
- **Triage** — ช่วยตอบ/จัดหมวดหมู่ issue ที่เข้ามาใหม่ (ไม่ต้องเขียนโค้ดเลย)
- **Community support** — ตอบคำถามใน Discussion/Discord ให้ผู้ใช้คนอื่น

การระบุช่องทาง contribute ที่หลากหลายแบบนี้สำคัญมาก เพราะไม่ใช่ทุกคนที่อยากช่วยจะเขียนโค้ดเก่ง แต่ทุกคนสามารถช่วยได้ในทางใดทางหนึ่งเสมอ

### 4. Development Setup

ส่วนนี้ต้อง **ทดสอบจริงว่ารันได้** ก่อนเผยแพร่ ไม่ใช่แค่เขียนจากความจำ เพราะเป็นส่วนที่ contributor ใหม่จะเจอเป็นด่านแรก ถ้าด่านนี้ไม่ผ่าน (เช่น คำสั่งพิมพ์ผิด, ลืมบอก dependency บางตัว) contributor จะเลิกตั้งแต่ต้น

```bash
# 1. Fork และ clone repository
git clone https://github.com/YOUR_USERNAME/taskflow.git
cd taskflow

# 2. ติดตั้ง dependencies
npm install

# 3. ตั้งค่า environment variables
cp .env.example .env

# 4. รันฐานข้อมูลสำหรับพัฒนา (ใช้ Docker)
docker compose up -d db

# 5. รัน migration
npm run db:migrate

# 6. เริ่ม development server
npm run dev
```

ควรระบุ **เวอร์ชันขั้นต่ำ** ของเครื่องมือที่ต้องใช้เสมอ (เช่น Node.js >= 20, Python >= 3.11) เพราะ error ที่เกิดจากเวอร์ชันไม่ตรงกันเป็นสาเหตุอันดับต้น ๆ ที่ contributor ใหม่ติดขัด

### 5. Coding Style & Linting

ระบุเครื่องมือที่ใช้ตรวจสอบ style ให้ชัดเจน พร้อมคำสั่งรัน และบอกว่าเครื่องมือเหล่านี้รันอัตโนมัติใน CI หรือไม่

```markdown
## Coding Style

โปรเจกต์นี้ใช้ ESLint + Prettier ในการควบคุมสไตล์โค้ด กรุณารันคำสั่งนี้
ก่อน commit ทุกครั้ง:

    npm run lint       # ตรวจสอบปัญหา style
    npm run lint:fix    # แก้ไขปัญหาที่แก้อัตโนมัติได้

แนะนำให้ติดตั้ง ESLint extension ใน editor ของคุณ เพื่อเห็น error แบบ
real-time ขณะเขียนโค้ด เราไม่รับ PR ที่ CI lint ไม่ผ่าน
```

### 6. Running Tests

บอกวิธีรัน test ทั้งหมด รวมถึงกฎว่าฟีเจอร์ใหม่ต้องมี test ประกอบด้วยหรือไม่

```markdown
## Testing

รัน test suite ทั้งหมดด้วยคำสั่ง:

    npm test

รัน test เฉพาะไฟล์:

    npm test -- src/utils/date.test.ts

**กฎสำคัญ:** ทุก PR ที่เพิ่มฟีเจอร์ใหม่หรือแก้บั๊ก ต้องมี test ประกอบมาด้วยเสมอ
PR ที่ทำให้ code coverage ลดลงจะไม่ถูก merge จนกว่าจะเพิ่ม test ให้ครบ
```

### 7. Commit Message Convention

หลายโปรเจกต์ใช้มาตรฐาน **Conventional Commits** ซึ่งเราเรียนหลักการเบื้องต้นไปแล้วในหลาย Part ก่อนหน้า — ในบริบทของ CONTRIBUTING.md ควรเขียนกฎนี้ให้ชัดเจนพร้อมตัวอย่าง:

```markdown
## Commit Messages

เราใช้รูปแบบ Conventional Commits:

    <type>(<scope>): <description>

ประเภท (type) ที่ใช้ได้:
- feat:     เพิ่มฟีเจอร์ใหม่
- fix:      แก้บั๊ก
- docs:     แก้ไขเอกสารเท่านั้น
- style:    แก้ formatting ไม่กระทบ logic
- refactor: ปรับโครงสร้างโค้ดโดยไม่เปลี่ยนพฤติกรรม
- test:     เพิ่มหรือแก้ไข test
- chore:    งานบำรุงรักษาอื่น ๆ เช่นอัปเดต dependency

ตัวอย่าง:
    feat(auth): add support for OAuth login
    fix(api): correct pagination offset calculation
```

### 8. Pull Request Process

ส่วนนี้สำคัญที่สุดเพราะเป็นด่านสุดท้ายก่อนโค้ดถูก merge ควรระบุ:

- Branch ต้นทางที่ต้อง base (เช่น `main` หรือ `develop`)
- ต้องเปิด issue ก่อนไหมสำหรับงานขนาดใหญ่
- ขนาด PR ที่รับ (เน้น PR เล็ก ทำเรื่องเดียว)
- ต้องผ่าน CI checks อะไรบ้างก่อน merge ได้
- ต้องมี reviewer approve กี่คน
- นโยบาย merge (squash, rebase, merge commit)
- Developer Certificate of Origin (DCO) หรือ CLA ถ้ามี

```markdown
## Pull Request Process

1. สำหรับการเปลี่ยนแปลงขนาดใหญ่ กรุณาเปิด issue เพื่อพูดคุยก่อนเริ่มเขียนโค้ด
2. Fork repository และสร้าง branch ใหม่จาก `main` โดยตั้งชื่อในรูปแบบ
   `feat/short-description` หรือ `fix/short-description`
3. ตรวจสอบว่า `npm run lint` และ `npm test` ผ่านทั้งหมดก่อน push
4. เขียน PR description อธิบาย "ทำไม" ไม่ใช่แค่ "ทำอะไร" และอ้างอิง
   issue ที่เกี่ยวข้องด้วย `Closes #123`
5. ต้องผ่าน CI ทั้งหมด และได้รับ approve จาก maintainer อย่างน้อย 1 คน
   ก่อนจึงจะ merge ได้
6. เราใช้ Squash and Merge เป็นค่าเริ่มต้น ดังนั้นไม่ต้องกังวลเรื่องจำนวน
   commit ระหว่างพัฒนา
```

## Step 863: Code of Conduct คืออะไร ทำไมสำคัญกับ Community

### Code of Conduct คืออะไร

**Code of Conduct (จรรยาบรรณชุมชน)** คือเอกสารที่กำหนด **มาตรฐานพฤติกรรมที่ยอมรับได้และยอมรับไม่ได้** สำหรับทุกคนที่เข้ามามีปฏิสัมพันธ์ในพื้นที่ของโปรเจกต์ ไม่ว่าจะเป็นใน issue, pull request, discussion, chat channel, งาน conference ที่เกี่ยวข้องกับโปรเจกต์ หรือแม้แต่ social media ที่พูดถึงโปรเจกต์ในนามตัวแทน

Code of Conduct **ไม่ใช่** กฎเกี่ยวกับเทคนิคการเขียนโค้ด (นั่นคือหน้าที่ของ CONTRIBUTING.md) แต่เป็นกฎเกี่ยวกับ **การปฏิบัติต่อกันในฐานะมนุษย์** — เช่น ห้ามคุกคาม (harassment) ห้ามเหยียดหยาม (discrimination) ห้ามใช้ถ้อยคำหยาบคายโจมตีบุคคล และกำหนดว่าเมื่อมีการละเมิดเกิดขึ้น จะมีกระบวนการจัดการอย่างไร

### ทำไม Community ถึงต้องมี Code of Conduct

#### 1. สร้างพื้นที่ปลอดภัยสำหรับทุกคน

Open Source เปิดให้ใครก็ได้จากทั่วโลกเข้ามามีส่วนร่วม นั่นหมายความว่าจะมีคนหลากหลายพื้นเพ วัฒนธรรม เพศ อายุ ระดับประสบการณ์ เข้ามาปฏิสัมพันธ์กัน หากไม่มีกรอบพฤติกรรมที่ชัดเจน พื้นที่นี้อาจกลายเป็นที่ที่คนบางกลุ่มถูกกลั่นแกล้งหรือคุกคามได้ง่าย โดยเฉพาะกลุ่มที่เปราะบางกว่า (เช่น ผู้หญิงในวงการเทคโนโลยี, มือใหม่, คนที่ภาษาอังกฤษไม่ใช่ภาษาแม่)

#### 2. ให้ maintainer มีเครื่องมือในการจัดการปัญหา

เมื่อเกิดพฤติกรรมไม่เหมาะสม maintainer ที่ไม่มี Code of Conduct จะต้องตัดสินใจโดยใช้ "ดุลยพินิจส่วนตัว" ซึ่งมักถูกโต้แย้งได้ง่ายว่าลำเอียง แต่หากมี Code of Conduct ที่เขียนไว้ล่วงหน้าและทุกคนยอมรับร่วมกันตั้งแต่เข้าร่วมโปรเจกต์ maintainer สามารถอ้างอิงกฎที่ชัดเจนในการตัดสินใจได้ ลดความขัดแย้งเชิงอารมณ์ และเพิ่มความชอบธรรมในการดำเนินการ

#### 3. ส่งสัญญาณต่อสาธารณะว่าโปรเจกต์นี้ให้ความสำคัญกับความหลากหลายและการเปิดกว้าง

การมี Code of Conduct ที่มองเห็นได้ชัดเจน (ไม่ใช่แค่มีแต่ไม่มีใครรู้) เป็นการส่งสัญญาณเชิงบวกต่อ contributor ที่กำลังพิจารณาว่าจะเข้าร่วมโปรเจกต์นี้หรือไม่ โดยเฉพาะคนกลุ่มที่เคยมีประสบการณ์แย่ ๆ ในชุมชนอื่นมาก่อน

#### 4. เป็นข้อกำหนดของหลายแพลตฟอร์มและองค์กร

GitHub แนะนำอย่างเป็นทางการให้ทุก repository มี Code of Conduct ผ่านฟีเจอร์ Community Standards มูลนิธิ Open Source ขนาดใหญ่หลายแห่ง เช่น **Cloud Native Computing Foundation (CNCF)**, **Apache Software Foundation (ASF)** และ **Linux Foundation** ล้วนกำหนดให้โปรเจกต์ภายใต้ร่มของตนต้องมี Code of Conduct เป็นเงื่อนไขพื้นฐาน

### ความเข้าใจผิดที่พบบ่อยเกี่ยวกับ Code of Conduct

| ความเข้าใจผิด | ความจริง |
|---|---|
| "Code of Conduct เป็นแค่พิธีการ ไม่มีใครอ่านจริง" | เมื่อเกิดปัญหาจริง มันคือเอกสารแรกที่ทุกฝ่ายจะหยิบมาอ้างอิง |
| "มีไว้เพื่อจำกัดเสรีภาพในการพูด" | มีไว้เพื่อป้องกันการคุกคามเป็นการส่วนตัว ไม่ใช่ห้ามวิจารณ์โค้ดหรือไอเดีย |
| "โปรเจกต์เล็ก ๆ ไม่จำเป็นต้องมี" | ยิ่งโปรเจกต์เล็กและ maintainer มีน้อย ยิ่งต้องมีกฎชัดเจนไว้ล่วงหน้า เพราะไม่มีทีมกลางคอยไกล่เกลี่ย |
| "เขียนเองแบบไหนก็ได้ ไม่ต้องอ้างอิงมาตรฐาน" | การใช้ template มาตรฐานที่เป็นที่ยอมรับ (เช่น Contributor Covenant) ทำให้ contributor รู้จักรูปแบบทันทีโดยไม่ต้องอ่านใหม่ทุกครั้ง |

ใน Step ถัดไป เราจะมาดู template มาตรฐานที่โปรเจกต์ Open Source นับแสนโปรเจกต์ทั่วโลกใช้ นั่นคือ **Contributor Covenant**

## Step 864: Contributor Covenant — Template มาตรฐานที่นิยมใช้มากที่สุด

### ประวัติโดยย่อ

**Contributor Covenant** ถูกสร้างขึ้นโดย **Coraline Ada Ehmke** วิศวกรซอฟต์แวร์และนักเคลื่อนไหวด้านความหลากหลายในวงการเทคโนโลยี เผยแพร่ครั้งแรกในปี 2014 ปัจจุบันเป็น Code of Conduct ที่ถูกใช้งานมากที่สุดในโลก Open Source โดยถูกนำไปใช้ในโปรเจกต์ขนาดใหญ่จำนวนมาก เช่น Kubernetes, Rails, Linux Kernel (ในรูปแบบที่ปรับแก้), Swift, Angular, Vue.js และอีกนับแสนโปรเจกต์

เอกสารนี้เผยแพร่ภายใต้สัญญาอนุญาต **Creative Commons Attribution 4.0 International (CC BY 4.0)** ซึ่งหมายความว่าใคร ๆ ก็สามารถนำไปใช้ ปรับแก้ และเผยแพร่ต่อได้ฟรี ขอเพียงให้เครดิตแหล่งที่มา เวอร์ชันล่าสุดคือ **2.1** สามารถดาวน์โหลดต้นฉบับภาษาอังกฤษได้ที่ contributor-covenant.org

### โครงสร้างหลักของ Contributor Covenant

Contributor Covenant มีโครงสร้าง 6 ส่วนหลัก ดังนี้:

#### 1. Our Pledge (คำมั่นสัญญาของเรา)

ส่วนเปิดที่ประกาศเจตนารมณ์ว่าชุมชนนี้มุ่งมั่นที่จะทำให้การมีส่วนร่วมเป็นประสบการณ์ที่ปราศจากการคุกคามสำหรับทุกคน โดยไม่คำนึงถึงอายุ ขนาดร่างกาย ความพิการที่มองเห็นหรือไม่เห็น ชาติพันธุ์ ลักษณะทางเพศ อัตลักษณ์ทางเพศ ระดับประสบการณ์ การศึกษา สถานะทางเศรษฐกิจสังคม สัญชาติ รูปลักษณ์ภายนอก เชื้อชาติ ศาสนา หรือรสนิยมทางเพศ

#### 2. Our Standards (มาตรฐานของเรา)

แบ่งเป็นสองฝั่งชัดเจน:

**ตัวอย่างพฤติกรรมที่ส่งเสริมสภาพแวดล้อมเชิงบวก:**
- แสดงความเห็นอกเห็นใจและความมีน้ำใจต่อผู้อื่น
- เคารพความคิดเห็น มุมมอง และประสบการณ์ที่แตกต่าง
- ให้และรับ feedback เชิงสร้างสรรค์อย่างสุภาพ
- ยอมรับผิดและขอโทษเมื่อทำผิดพลาด พร้อมเรียนรู้จากประสบการณ์นั้น
- มุ่งเน้นสิ่งที่ดีที่สุดสำหรับชุมชนโดยรวม ไม่ใช่แค่ตัวเอง

**ตัวอย่างพฤติกรรมที่ยอมรับไม่ได้:**
- การใช้ภาษาหรือภาพที่มีนัยทางเพศ และการเข้าหาหรือให้ความสนใจทางเพศที่ไม่พึงประสงค์
- การล้อเลียน ดูหมิ่น และความคิดเห็นที่โจมตีบุคคล (trolling, insulting comments)
- การคุกคามในที่สาธารณะหรือส่วนตัว (public or private harassment)
- การเผยแพร่ข้อมูลส่วนตัวของผู้อื่นโดยไม่ได้รับอนุญาต (doxxing)
- พฤติกรรมอื่นใดที่ไม่เหมาะสมกับสภาพแวดล้อมทางวิชาชีพ

#### 3. Enforcement Responsibilities (ความรับผิดชอบในการบังคับใช้)

ระบุว่าผู้นำชุมชน (community leaders) มีหน้าที่ชี้แจงและบังคับใช้มาตรฐานพฤติกรรมที่ยอมรับได้ และจะดำเนินการแก้ไขที่เหมาะสมและยุติธรรมเมื่อพบพฤติกรรมที่ไม่เหมาะสม รวมถึงมีสิทธิ์ลบ แก้ไข หรือปฏิเสธ comment, commit, code, wiki edit, issue และการมีส่วนร่วมอื่น ๆ ที่ไม่สอดคล้องกับ Code of Conduct

#### 4. Scope (ขอบเขตการบังคับใช้)

ระบุว่า Code of Conduct นี้ใช้บังคับในพื้นที่ใดบ้าง โดยทั่วไปครอบคลุม:
- พื้นที่ของโปรเจกต์ทั้งหมด (issue, PR, discussion, wiki)
- พื้นที่สาธารณะเมื่อบุคคลนั้นเป็นตัวแทนของชุมชนอย่างเป็นทางการ เช่น การใช้อีเมลทางการของโปรเจกต์ การโพสต์ผ่านบัญชี social media ทางการ หรือการเป็นตัวแทนที่ได้รับการแต่งตั้งในงาน conference

#### 5. Enforcement (การบังคับใช้)

ระบุ **ช่องทางการรายงาน** ที่ชัดเจน โดยทั่วไปคืออีเมลเฉพาะที่ maintainer ดูแล (เช่น `conduct@taskflow-project.org`) และย้ำว่าทุกข้อร้องเรียนจะถูกตรวจสอบและสอบสวนอย่างรวดเร็วและเป็นธรรม พร้อมรักษาความลับของผู้รายงาน (reporter)

#### 6. Enforcement Guidelines (แนวทางการบังคับใช้)

ส่วนที่มีรายละเอียดมากที่สุด กำหนดระดับความรุนแรงของการละเมิดและบทลงโทษที่สอดคล้องกันเป็น 4 ระดับ:

| ระดับ | ชื่อ | ลักษณะการละเมิด | ผลที่ตามมา |
|---|---|---|---|
| 1 | **Correction** | การใช้ภาษาไม่เหมาะสมเล็กน้อย หรือพฤติกรรมที่ถือว่าไม่เป็นมืออาชีพ | คำเตือนส่วนตัวเป็นลายลักษณ์อักษรจากผู้นำชุมชน อธิบายว่าทำไมพฤติกรรมนั้นไม่เหมาะสม อาจขอให้ขอโทษต่อสาธารณะ |
| 2 | **Warning** | การละเมิดจากเหตุการณ์เดียวหรือชุดของการกระทำ | คำเตือนอย่างเป็นทางการพร้อมผลที่ตามมาหากมีพฤติกรรมต่อเนื่อง ห้ามติดต่อกับผู้ที่เกี่ยวข้องในช่วงเวลาที่กำหนด รวมถึงการมีปฏิสัมพันธ์ในพื้นที่ของชุมชนและช่องทางภายนอก |
| 3 | **Temporary Ban** | การละเมิดมาตรฐานชุมชนอย่างร้ายแรง รวมถึงพฤติกรรมไม่เหมาะสมต่อเนื่อง | ระงับสิทธิ์การมีปฏิสัมพันธ์หรือสื่อสารกับชุมชนเป็นการชั่วคราวตามระยะเวลาที่กำหนด |
| 4 | **Permanent Ban** | แสดงรูปแบบของการละเมิดมาตรฐานชุมชนอย่างต่อเนื่อง รวมถึงการคุกคามบุคคลใดบุคคลหนึ่ง หรือแสดงความก้าวร้าว/ดูหมิ่นต่อกลุ่มบุคคล | ระงับสิทธิ์การมีปฏิสัมพันธ์ใด ๆ กับชุมชนอย่างถาวร |

### ตัวอย่างการปรับใช้ Contributor Covenant ในภาษาไทย

```markdown

ในฐานะสมาชิก ผู้สนับสนุน และผู้นำของชุมชนนี้ เราให้คำมั่นว่าจะทำให้การมี
ส่วนร่วมในชุมชนของเราเป็นประสบการณ์ที่ปราศจากการคุกคามสำหรับทุกคน
ไม่ว่าจะมีอายุ ขนาดร่างกาย ความพิการที่มองเห็นหรือไม่เห็น ชาติพันธุ์
ลักษณะทางเพศ อัตลักษณ์และการแสดงออกทางเพศ ระดับประสบการณ์
การศึกษา สถานะทางเศรษฐกิจสังคม สัญชาติ รูปลักษณ์ภายนอก เชื้อชาติ
วรรณะ สีผิว ศาสนา หรือรสนิยมทางเพศแบบใดก็ตาม

## มาตรฐานของเรา

การเคารพความคิดเห็นที่แตกต่าง การให้ feedback เชิงสร้างสรรค์อย่างสุภาพ

ทุกข้อร้องเรียนจะถูกตรวจสอบและสอบสวนอย่างรวดเร็ว เป็นธรรม และรักษา

```

การใช้ template ที่เป็นมาตรฐานสากลแบบนี้มีข้อดีสำคัญคือ contributor ที่เคย contribute โปรเจกต์อื่นมาก่อนจะคุ้นเคยกับโครงสร้างทันที ไม่ต้องอ่านใหม่ทั้งหมดตั้งแต่ศูนย์ทุกครั้งที่เข้าโปรเจกต์ใหม่ — เปรียบเสมือนการที่ทุกเว็บไซต์ใช้ไอคอนตะกร้าสินค้าคล้ายกัน ผู้ใช้ก็เข้าใจได้ทันทีโดยไม่ต้องเรียนรู้ใหม่

## Step 865: การบังคับใช้ Code of Conduct จริง (Enforcement)

การมี Code of Conduct ที่เขียนสวยงามไม่มีประโยชน์เลยถ้าไม่มีกระบวนการบังคับใช้ที่ชัดเจนและน่าเชื่อถือ Step นี้จะพาไปดูรายละเอียดของ **enforcement** ในทางปฏิบัติจริง

### ใครเป็นคนตัดสิน

โปรเจกต์ขนาดต่าง ๆ มีวิธีจัดการเรื่องนี้แตกต่างกัน:

| ขนาดโปรเจกต์ | ผู้รับผิดชอบการบังคับใช้ |
|---|---|
| โปรเจกต์เล็ก / บุคคลเดียวดูแล | เจ้าของโปรเจกต์ (maintainer) เป็นผู้ตัดสินใจเอง |
| โปรเจกต์ขนาดกลาง | **Core team** หรือกลุ่ม maintainer หลักร่วมกันตัดสินใจ |
| โปรเจกต์ขนาดใหญ่ / มูลนิธิ | **Code of Conduct Committee (CoC Committee)** ที่แยกออกมาต่างหาก ประกอบด้วยสมาชิกหลายคนเพื่อลด conflict of interest |

โปรเจกต์ขนาดใหญ่ภายใต้มูลนิธิ เช่น CNCF มักมีคณะกรรมการเฉพาะที่เรียกว่า **Code of Conduct Committee** ที่ไม่ได้เป็นชุดเดียวกับทีมพัฒนาทางเทคนิค เพื่อให้การตัดสินใจเป็นกลางและไม่ถูกอิทธิพลจากความสัมพันธ์ในการทำงานร่วมกัน

### ขั้นตอนมาตรฐานของกระบวนการ Enforcement

#### ขั้นที่ 1: การรับรายงาน (Receiving Reports)

ต้องมีช่องทางรายงานที่ **เป็นความลับ (private)** เสมอ — ห้ามให้รายงานผ่าน public issue เด็ดขาด เพราะจะทำให้ผู้ถูกกล่าวหาและผู้รายงานต้องเผชิญหน้ากันต่อหน้าสาธารณะก่อนมีการสอบสวน ช่องทางที่นิยมใช้:

- อีเมลเฉพาะ เช่น `conduct@project.org`
- ฟอร์มออนไลน์แบบไม่เปิดเผยตัวตน (anonymous form)
- ข้อความส่วนตัวถึงสมาชิก CoC Committee โดยตรง

#### ขั้นที่ 2: การรับทราบ (Acknowledgment)

ทีมที่รับผิดชอบควรตอบกลับผู้รายงานภายในระยะเวลาที่กำหนดไว้ล่วงหน้า (เช่น ภายใน 48 ชั่วโมง) เพื่อยืนยันว่าได้รับรายงานแล้ว แม้จะยังไม่มีข้อสรุป การนิ่งเงียบเป็นสิ่งที่บั่นทอนความเชื่อมั่นในระบบมากที่สุด

#### ขั้นที่ 3: การสอบสวน (Investigation)

ทีมจะรวบรวมข้อมูลจากทุกฝ่ายที่เกี่ยวข้องอย่างเป็นความลับ อาจรวมถึงการขอ screenshot, log การสนทนา, หรือคำให้การจากพยาน สิ่งสำคัญคือต้อง **รักษาความเป็นกลาง** — หากสมาชิกในทีม enforcement มีความสัมพันธ์ใกล้ชิดกับฝ่ายใดฝ่ายหนึ่ง (เช่น เป็นเพื่อนสนิท หรือเป็นคู่กรณีเอง) จะต้อง **recuse ตัวเอง (ถอนตัวออกจากการตัดสินใจกรณีนั้น)**

#### ขั้นที่ 4: การตัดสินใจ (Decision)

ใช้ **Enforcement Guidelines** ที่กำหนดไว้ล่วงหน้า (ตามที่อธิบายใน Step 864 — 4 ระดับ: Correction, Warning, Temporary Ban, Permanent Ban) เป็นกรอบในการตัดสินความรุนแรงและบทลงโทษที่เหมาะสม ไม่ตัดสินตามอารมณ์หรือความคิดเห็นส่วนตัว

#### ขั้นที่ 5: การแจ้งผล (Communication of Outcome)

แจ้งผลการตัดสินใจให้ทั้งผู้รายงานและผู้ถูกร้องเรียนทราบ โดยรักษาระดับความเป็นส่วนตัวที่เหมาะสม — ผู้รายงานควรได้รับทราบว่ามีการดำเนินการแล้ว แต่ไม่จำเป็นต้องเห็นรายละเอียดการลงโทษทั้งหมดหากไม่เกี่ยวข้องโดยตรง

#### ขั้นที่ 6: การอุทธรณ์ (Appeal)

ควรมีช่องทางให้ผู้ถูกลงโทษสามารถอุทธรณ์คำตัดสินได้ผ่านกระบวนการที่แยกออกจากผู้ตัดสินใจเดิม เพื่อป้องกันความผิดพลาดหรือความไม่เป็นธรรม

#### ขั้นที่ 7: การบันทึกและรักษาความลับ (Documentation & Confidentiality)

ทีม enforcement ควรบันทึกกรณีที่เกิดขึ้นไว้เป็นความลับ (ไม่เปิดเผยต่อสาธารณะ) เพื่อใช้อ้างอิงในอนาคตหากมีพฤติกรรมซ้ำจากบุคคลเดียวกัน แต่ **ไม่ควร** เปิดเผยรายละเอียดกรณีต่อสาธารณะโดยไม่จำเป็น เพื่อปกป้องความเป็นส่วนตัวของทุกฝ่าย

### สิ่งที่ทำให้ระบบ Enforcement ล้มเหลว

| ปัญหา | ผลที่ตามมา |
|---|---|
| ไม่มีช่องทางรายงานที่เป็นความลับ | ผู้เสียหายไม่กล้ารายงาน เพราะกลัวถูกแก้แค้นในที่สาธารณะ |
| Maintainer ตัดสินโดยไม่มีกรอบชัดเจน | ถูกครหาว่าลำเอียง โดยเฉพาะถ้าคู่กรณีเป็นคนที่มีชื่อเสียงในชุมชน |
| ไม่มีการติดตามผล | ผู้ถูกลงโทษกลับมาทำผิดซ้ำโดยไม่มีใครสังเกต |
| เปิดเผยรายละเอียดต่อสาธารณะทันที | สร้างความขัดแย้งในชุมชนเป็นวงกว้าง กลายเป็นดราม่าแทนที่จะแก้ปัญหา |
| Maintainer ที่เป็นคู่กรณีตัดสินใจเอง | Conflict of interest ทำให้ผลการตัดสินไม่น่าเชื่อถือ |

### ตัวอย่างข้อความในเอกสารที่อธิบายกระบวนการ Enforcement

```markdown
## กระบวนการบังคับใช้ Code of Conduct

1. รายงานพฤติกรรมที่ไม่เหมาะสมได้ที่ conduct@taskflow-project.org
2. ทีม Code of Conduct จะตอบรับภายใน 48 ชั่วโมง
3. การสอบสวนจะดำเนินการอย่างเป็นความลับ โดยสมาชิกที่มีส่วนได้ส่วนเสีย
   กับกรณีนั้นจะถอนตัวออกจากการพิจารณา
4. ผลการตัดสินใจจะอ้างอิงตาม Enforcement Guidelines ที่ระบุไว้ใน
   CODE_OF_CONDUCT.md
5. ผู้ถูกร้องเรียนมีสิทธิ์อุทธรณ์คำตัดสินภายใน 14 วัน โดยส่งคำร้องไปยัง
   คณะกรรมการชุดอื่นที่ไม่ได้ร่วมตัดสินใจในรอบแรก
```

## Step 866: Issue/PR Template สำหรับ Open Source Contributor ภายนอก

ใน **Part 26** เราเรียนเรื่อง Issue templates (ทั้งแบบ Markdown และแบบ YAML Issue Forms) และ Pull Request template ไปแล้วอย่างละเอียดในบริบททั่วไป ใน Step นี้เราจะมาต่อยอดโดยเจาะจงไปที่ **บริบทของ Open Source ที่มี contributor ภายนอกจำนวนมาก** ซึ่งมีความต้องการต่างจากทีมภายในองค์กรที่รู้จักกันอยู่แล้ว

### ความแตกต่างระหว่าง Internal Team กับ External Contributor

| ด้าน | ทีมภายในองค์กร | Contributor ภายนอก |
|---|---|---|
| ความคุ้นเคยกับ codebase | สูง รู้ context อยู่แล้ว | ต่ำ อาจเห็นโค้ดครั้งแรก |
| ความคุ้นเคยกับ workflow ของทีม | สูง ผ่านการ onboard แล้ว | ต่ำ ต้องอ่านทุกอย่างจาก template |
| ช่องทางสื่อสารนอกรอบ | มี (Slack, ประชุม, นั่งข้างกัน) | มักไม่มี ต้องพึ่ง comment ใน issue/PR เท่านั้น |
| แรงจูงใจในการอยู่ต่อ | ได้เงินเดือน ต้องทำต่อ | สมัครใจล้วน ๆ เลิกได้ทุกเมื่อถ้ารู้สึกไม่ดี |

จากตารางนี้จะเห็นว่า template สำหรับ external contributor ต้อง **อธิบายมากกว่า สุภาพกว่า และให้กำลังใจมากกว่า** template ที่ใช้ภายในทีมองค์กร

### ปรับ Issue Template ให้เหมาะกับ External Contributor

```yaml
# .github/ISSUE_TEMPLATE/bug_report.yml
name: 🐛 Bug Report
description: รายงานปัญหาที่พบใน TaskFlow
labels: ["bug", "needs-triage"]
body:
  - type: markdown
    attributes:
      value: |
        ขอบคุณที่สละเวลารายงานปัญหา! กรุณาตรวจสอบก่อนว่ามีคนรายงาน
        ปัญหาเดียวกันไปแล้วหรือยังใน [Issues ที่เปิดอยู่](../issues)
        และอ่าน [CONTRIBUTING.md](../CONTRIBUTING.md) เพื่อความเข้าใจ
        ตรงกันเรื่องขั้นตอนต่อไป
  - type: textarea
    id: description
    attributes:
      label: อธิบายปัญหา
      description: เกิดอะไรขึ้น คาดหวังให้เกิดอะไรแทน
    validations:
      required: true
  - type: textarea
    id: steps
    attributes:
      label: ขั้นตอนการทำซ้ำ (Reproduction Steps)
      placeholder: |
        1. ไปที่หน้า...
        2. คลิกที่...
        3. เห็น error...
    validations:
      required: true
  - type: input
    id: version
    attributes:
      label: เวอร์ชันของ TaskFlow ที่ใช้
    validations:
      required: true
  - type: checkboxes
    id: terms
    attributes:
      label: Checklist ก่อนส่ง
      options:
        - label: ฉันได้ค้นหา issue ที่มีอยู่แล้วและไม่พบปัญหาซ้ำ
          required: true
        - label: ฉันได้อ่าน CODE_OF_CONDUCT.md แล้ว
          required: true
```

จุดที่เพิ่มเข้ามาสำหรับบริบท external contributor คือ:

1. **ข้อความต้อนรับ (welcoming message)** ที่ไม่มีในโปรเจกต์ภายในองค์กร เพราะทีมภายในไม่จำเป็นต้องถูก "ต้อนรับ" ทุกครั้งที่เปิด issue
2. **ลิงก์ไป CONTRIBUTING.md และ CODE_OF_CONDUCT.md** อย่างชัดเจนในทุก template
3. **Checkbox ยืนยันว่าได้อ่านเอกสารสำคัญแล้ว** ก่อนส่ง

### ปรับ PR Template ให้เหมาะกับ External Contributor

```markdown
<!-- .github/PULL_REQUEST_TEMPLATE.md -->
## คำอธิบาย

<!-- อธิบายว่า PR นี้ทำอะไร และทำไมถึงจำเป็น -->

## Issue ที่เกี่ยวข้อง

Closes #

## ประเภทของการเปลี่ยนแปลง

- [ ] Bug fix
- [ ] ฟีเจอร์ใหม่
- [ ] Breaking change
- [ ] อัปเดตเอกสาร

## Checklist ก่อนขอ Review

- [ ] ฉันได้อ่าน [CONTRIBUTING.md](../CONTRIBUTING.md) แล้ว
- [ ] โค้ดของฉันผ่าน `npm run lint` แล้ว
- [ ] ฉันได้เพิ่ม test ที่ครอบคลุมการเปลี่ยนแปลงนี้แล้ว
- [ ] Test ทั้งหมดผ่าน (`npm test`)
- [ ] ฉันได้ sign-off commit ด้วย `git commit -s` แล้ว (Developer
      Certificate of Origin)

## นี่คือ Pull Request แรกของคุณในโปรเจกต์นี้หรือไม่?

- [ ] ใช่ นี่คือครั้งแรก 🎉 (ยินดีต้อนรับ! หากมีคำถามระหว่างรอ review
      สามารถ comment ถามได้ในนี้เลย ทีมงานยินดีช่วยเหลือ)
```

การเพิ่มช่องเช็ก **"นี่คือ Pull Request แรกของคุณหรือไม่"** เป็นเทคนิคที่โปรเจกต์ Open Source ใหญ่หลายแห่งใช้ เพื่อให้ maintainer หรือ bot ทราบทันทีว่าควรให้ feedback อย่างละเอียดและให้กำลังใจเป็นพิเศษกับ PR นี้ ต่างจาก PR จาก contributor ที่ทำมาหลายรอบแล้วซึ่งอาจ review แบบตรงประเด็นได้เลย

### การเชื่อม DCO/CLA เข้ากับ PR Template

หากโปรเจกต์ต้องการ **Developer Certificate of Origin (DCO)** หรือ **Contributor License Agreement (CLA)** ตามที่กล่าวถึงใน Part 24 ควรมี bot อัตโนมัติ (เช่น `dco-check` GitHub Action หรือ CLA Assistant) ที่ตรวจสอบและ comment แจ้งเตือนอัตโนมัติใน PR ทันทีที่เปิด แทนที่จะให้ maintainer ต้องมานั่งเช็คเองทุกครั้ง — นี่คือการนำ automation เข้ามาช่วยลดภาระงานซ้ำซากที่เราพูดถึงใน Step 861

## Step 867: Good First Issue Curation — คัดเลือกและติด Label งานที่เหมาะกับมือใหม่

### ทำไมต้องคัดสรร ไม่ใช่แค่ติด label มั่ว ๆ

Label `good first issue` เป็นหนึ่งใน label มาตรฐานที่ GitHub รู้จัก (แสดงผลพิเศษในหน้า Explore ของ GitHub) แต่ปัญหาที่พบบ่อยมากคือ maintainer ติด label นี้ให้กับ issue ที่จริง ๆ แล้ว **ไม่เหมาะกับมือใหม่เลย** เช่น issue ที่ต้องเข้าใจ architecture ทั้งระบบ หรือ issue ที่ requirement ยังไม่ชัดเจน ผลคือมือใหม่เข้ามาลองแล้วเจอทางตัน สูญเสียความมั่นใจ และอาจเลิกไปเลย

### คุณสมบัติของ Issue ที่เหมาะจะติด "good first issue" จริง ๆ

1. **ขอบเขตชัดเจนและเล็ก (Well-scoped)** — แก้ไขได้ในไม่กี่ไฟล์ ไม่ต้องแตะหลายระบบพร้อมกัน
2. **ไม่ต้องมีความรู้เชิงลึกเกี่ยวกับ architecture** — ไม่จำเป็นต้องเข้าใจการออกแบบระบบทั้งหมดถึงจะแก้ได้
3. **มี acceptance criteria ชัดเจน** — รู้ว่า "เสร็จแล้ว" หมายถึงอะไร ไม่ใช่ปัญหาที่ยังไม่มีคำตอบเป็นที่ยุติ
4. **มีตัวอย่างหรือแนวทางเริ่มต้นแนบมาด้วย** — maintainer ควร comment แนะนำไฟล์ที่ต้องแก้ หรือ pattern ที่ควรทำตาม
5. **มีคนพร้อมตอบคำถามระหว่างทำ** — ไม่ใช่ปล่อยให้มือใหม่งมเองคนเดียวโดยไม่มีใครติดตาม

### ตัวอย่างการเขียน Issue ที่ curate มาอย่างดีสำหรับมือใหม่

```markdown
**Title:** เพิ่ม dark mode toggle ใน Settings page

**Labels:** good first issue, help wanted, ui

**คำอธิบาย:**
ตอนนี้แอปมีแค่ light mode เราต้องการเพิ่มปุ่ม toggle ใน Settings page
เพื่อสลับเป็น dark mode

**ไฟล์ที่เกี่ยวข้อง:**
- `src/pages/Settings.tsx` — เพิ่ม toggle component ที่นี่
- `src/hooks/useTheme.ts` — hook ที่มีอยู่แล้วสำหรับจัดการ theme state
- `src/styles/theme.css` — มี CSS variable สำหรับ dark mode เตรียมไว้แล้ว

**Acceptance Criteria:**
- [ ] มีปุ่ม toggle ใน Settings page
- [ ] คลิกแล้วเปลี่ยน theme ทันทีโดยไม่ต้อง reload หน้า
- [ ] ค่าที่เลือกถูกจำไว้ใน localStorage

**ระดับความยาก:** เหมาะกับมือใหม่ — ไม่ต้องแก้ business logic ใด ๆ
**คนดูแล issue นี้:** @maintainer-name (คอมเมนต์ถามได้ตลอด)
```

### เครื่องมือและแพลตฟอร์มช่วยรวบรวม Good First Issue

นอกจาก label บน GitHub เอง ยังมีแพลตฟอร์มภายนอกที่รวบรวม good first issue จากหลายโปรเจกต์มาไว้ที่เดียว เพื่อช่วยให้มือใหม่หาโปรเจกต์ที่เหมาะกับตัวเองได้ง่ายขึ้น เช่น **goodfirstissue.dev**, **up-for-grabs.net**, และบอทอย่าง **CodeTriage** ที่ส่งอีเมลแนะนำ issue ให้ผู้ใช้ที่สมัครติดตามโปรเจกต์นั้น ๆ เป็นระยะ

### ปัญหา "Issue Sniping" และวิธีจัดการ

เมื่อ issue ที่ดีถูก curate ไว้อย่างดี มักเกิดปัญหาที่เรียกว่า **issue sniping** — มีคนหลายคนอยากทำ issue เดียวกันพร้อมกัน ทำให้เกิดความสับสนว่าใครกำลังทำอยู่ วิธีจัดการที่นิยมใช้:

1. **ให้ comment "ขอทำ" ก่อนเริ่ม** และให้ maintainer หรือ bot assign ให้อย่างเป็นทางการ
2. **จำกัดเวลาการ claim** — เช่น ถ้า assign ไปแล้ว 14 วันไม่มีความคืบหน้า (ไม่มี PR หรือ commit ใหม่) ให้ถอด assignment ออกอัตโนมัติด้วย stale bot เพื่อเปิดโอกาสให้คนอื่น
3. **ใช้ label `claimed` แยกจาก `good first issue`** เพื่อให้เห็นภาพรวมชัดเจนว่า issue ไหนว่าง ไหนมีคนทำแล้ว

```yaml
# ตัวอย่างส่วนหนึ่งของ stale bot config สำหรับ unassign issue ที่ไม่มีความคืบหน้า
daysUntilStale: 14
staleLabel: inactive-assignee
markComment: >
  Issue นี้ถูก assign มา 14 วันแล้วแต่ยังไม่มีความคืบหน้า เราจะถอด
  assignment ออกเพื่อเปิดโอกาสให้คนอื่นได้ลองทำ หากยังสนใจอยู่
  comment แจ้งได้เลยครับ
```

## Step 868: Mentorship Program สำหรับ Contributor ใหม่

### ทำไมแค่มี Good First Issue ยังไม่พอ

การติด label good first issue ที่ดีเป็นจุดเริ่มต้นที่ดี แต่หลายครั้งมือใหม่ยังคง **ไม่กล้าเริ่ม** เพราะรู้สึกว่า "ถ้าติดปัญหาระหว่างทางจะถามใคร" การมี **Mentorship Program** ที่เป็นระบบช่วยลดความกังวลนี้ลงได้มาก และเป็นปัจจัยสำคัญที่ทำให้ contributor ครั้งแรกกลายเป็น contributor ประจำ (retention)

### รูปแบบของ Mentorship Program ที่นิยมใช้

#### 1. Buddy System / 1:1 Pairing

จับคู่ contributor ใหม่กับ mentor ที่มีประสบการณ์ในโปรเจกต์ 1 ต่อ 1 โดย mentor ทำหน้าที่:
- ตอบคำถามด้าน technical และช่วยชี้ทางเมื่อติดขัด
- Review PR แรก ๆ อย่างละเอียดพร้อมอธิบายเหตุผล ไม่ใช่แค่บอกว่าผิดตรงไหน
- ติดตามความคืบหน้าเป็นระยะโดยไม่กดดันจนเกินไป

#### 2. Office Hours

จัดเวลานัดหมายประจำ (เช่น ทุกวันพุธ 20:00 น. เวลาไทย) ผ่าน video call หรือ voice channel ใน Discord/Slack ให้ contributor คนไหนก็ได้เข้ามาถามคำถามสด ๆ ได้โดยไม่ต้องนัดล่วงหน้าเป็นรายบุคคล วิธีนี้ scale ได้ดีกว่า 1:1 pairing สำหรับโปรเจกต์ที่มี contributor จำนวนมาก

#### 3. Structured Mentorship Program ระดับองค์กร

โปรเจกต์ Open Source ขนาดใหญ่บางแห่งจัดโปรแกรม mentorship อย่างเป็นทางการที่มีระยะเวลาชัดเจน (เช่น 3 เดือน) พร้อมเป้าหมายที่ตกลงกันล่วงหน้า ตัวอย่างโปรแกรมระดับอุตสาหกรรมที่รู้จักกันดี ได้แก่:

- **Google Summer of Code (GSoC)** — โปรแกรมที่ Google สนับสนุนให้นักศึกษาทำงานร่วมกับโปรเจกต์ Open Source ภายใต้การดูแลของ mentor เป็นเวลาหลายเดือนในช่วงฤดูร้อน
- **Outreachy** — โปรแกรม internship ระยะไกลที่เน้นเปิดโอกาสให้กลุ่มที่มีตัวแทนน้อยในวงการเทคโนโลยี (underrepresented groups) ได้เข้ามา contribute โปรเจกต์ Open Source พร้อม mentor ดูแลตลอดโปรแกรม

โปรเจกต์ที่ไม่ได้มีขนาดใหญ่ระดับเข้าร่วมโปรแกรมเหล่านี้ได้ ก็สามารถประยุกต์แนวคิดเดียวกันมาใช้ในสเกลเล็กลงได้ เช่น การจัด "First-Timers-Only" event ที่เปิด issue เฉพาะสำหรับคนที่ไม่เคย contribute Open Source มาก่อนเลย พร้อม mentor ประกบใกล้ชิดเป็นพิเศษ

### การระบุ Mentorship Program ใน CONTRIBUTING.md

```markdown
## Mentorship

หากคุณเป็นมือใหม่และไม่แน่ใจว่าจะเริ่มต้นอย่างไร เรามีโปรแกรม mentorship
ที่ช่วยได้:

- **Office Hours**: ทุกวันพุธ 20:00 น. (เวลาไทย) ใน Discord channel
  #office-hours สามารถเข้ามาถามคำถามอะไรก็ได้แบบสด ๆ
- **Buddy System**: comment ใน issue ที่ติด label `good first issue`
  ว่าอยากลองทำ ทีมงานจะจับคู่ mentor ให้ภายใน 24 ชั่วโมง
- **First-Timers-Only issues**: ดู issue ที่ติด label
  `first-timers-only` สำหรับงานที่ออกแบบมาเฉพาะคนที่ไม่เคย
  contribute Open Source มาก่อนเลย
```

### บทบาทของ Mentor เทียบกับ Reviewer

สิ่งสำคัญที่ต้องแยกให้ชัดคือ **mentor ไม่ใช่คนเดียวกับ reviewer เสมอไป** แม้บางกรณีจะเป็นคนเดียวกันได้ แต่บทบาทต่างกัน:

| บทบาท | Mentor | Reviewer |
|---|---|---|
| เป้าหมายหลัก | ช่วยให้ contributor เรียนรู้และสำเร็จงาน | ตรวจสอบคุณภาพโค้ดก่อน merge |
| ช่วงเวลาที่เข้ามาเกี่ยวข้อง | ตั้งแต่ก่อนเริ่มเขียนโค้ด | หลังจากเปิด PR แล้ว |
| น้ำเสียงที่ใช้ | ให้กำลังใจ อธิบายละเอียด สอน | ตรงประเด็น มุ่งคุณภาพโค้ด |
| ความรับผิดชอบต่อผลลัพธ์ | ความสำเร็จของ "คน" | คุณภาพของ "โค้ด" |

การแยกบทบาทนี้ให้ชัดเจนช่วยลดความกดดันของทั้งสองฝ่าย — mentor ไม่ต้องกังวลว่าต้อง approve PR ทุกอันที่ตัวเองสอน และ contributor ก็เข้าใจว่า feedback ที่ได้รับตอน review ไม่ใช่การตัดสินความสามารถโดยรวมของตัวเอง

## Step 869: Recognition — การให้เครดิต Contributor อย่างเหมาะสม

### ทำไม Recognition ถึงสำคัญพอ ๆ กับ Onboarding

หลายโปรเจกต์ทุ่มเทมากกับการทำให้คนเข้ามา contribute ง่าย (Step 861-868) แต่กลับละเลยขั้นตอนสุดท้ายที่สำคัญไม่แพ้กัน นั่นคือ **การให้เครดิตหลังจาก contribute สำเร็จแล้ว** Contributor ที่ทำงานให้ฟรีโดยไม่ได้รับค่าตอบแทน สิ่งที่พวกเขาต้องการกลับมาไม่ใช่เงิน แต่คือ **การยอมรับ (recognition)** ว่าตัวเองมีส่วนสร้างสิ่งที่มีคุณค่า การไม่ให้เครดิตอย่างเหมาะสมเป็นสาเหตุอันดับต้น ๆ ที่ทำให้ contributor ทำครั้งเดียวแล้วไม่กลับมาอีก (one-time contributor)

### All Contributors Bot / Specification

**All Contributors** เป็นทั้งข้อกำหนด (specification) และเครื่องมือ (bot) ที่ได้รับความนิยมมากในการรับรองว่าทุกรูปแบบของการ contribute จะได้รับเครดิต ไม่ใช่แค่คนที่เขียนโค้ด จุดเด่นสำคัญคือแนวคิด **"contributions are more than code"** — แบ่งประเภทของ contribution ออกเป็นหมวดหมู่ที่แสดงด้วย emoji เช่น:

| Emoji | ประเภท contribution |
|---|---|
| 💻 | Code |
| 📖 | Documentation |
| 🎨 | Design |
| 🐛 | Bug reports |
| 💡 | Ideas & Planning |
| 🌍 | Translation |
| ⚠️ | Tests |
| 👀 | Reviewed Pull Requests |
| 💬 | Answering Questions |

การใช้งานทำได้โดยติดตั้ง bot แล้วใช้คำสั่ง comment ใน issue/PR เพื่อเพิ่มชื่อ contributor เข้าไปในตาราง README อัตโนมัติ:

```
@all-contributors please add @jane-doe for code, doc
```

Bot จะสร้าง PR อัตโนมัติเพื่ออัปเดตตาราง contributor ใน README ให้ ซึ่งหน้าตาจะออกมาประมาณนี้:

```markdown
## Contributors ✨

<table>
  <tr>
    <td align="center">
      <a href="https://github.com/jane-doe">
        <img src="https://avatars.githubusercontent.com/jane-doe" width="80px;"/>
        <br /><sub><b>Jane Doe</b></sub>
      </a>
      <br />💻 📖
    </td>
  </tr>
</table>
```

### การให้เครดิตใน Release Notes

อีกช่องทางสำคัญคือการใส่ชื่อ contributor ไว้ใน **release notes** ทุกครั้งที่ออกเวอร์ชันใหม่ วิธีที่นิยมทำ:

1. **GitHub's "Generate release notes" feature** — GitHub สามารถสร้าง release notes อัตโนมัติที่รวมรายชื่อทุก PR ที่ merge เข้ามาในเวอร์ชันนั้น พร้อมชื่อผู้เขียน และจะขึ้นข้อความพิเศษว่า **"New Contributors"** สำหรับคนที่ contribute เป็นครั้งแรกในโปรเจกต์นั้นด้วย ซึ่งเป็นจุดที่สร้างความรู้สึกดีมากให้กับมือใหม่
2. **release-drafter** — เครื่องมือ third-party ที่ช่วยร่าง release notes อัตโนมัติจาก label ของ PR แต่ละอัน แยกหมวดหมู่ Features / Bug Fixes / Documentation พร้อมเครดิตผู้เขียนในแต่ละหัวข้อ

ตัวอย่าง release notes ที่ให้เครดิตอย่างเหมาะสม:

```markdown
## v2.4.0

### 🚀 Features
- เพิ่ม dark mode toggle (@jane-doe in #142)

### 🐛 Bug Fixes
- แก้ปัญหา pagination offset ผิดพลาด (@john-smith in #145)

### 📖 Documentation
- ปรับปรุงคำอธิบาย API authentication (@translator-th in #148)

## New Contributors
- @jane-doe ทำ contribution แรกใน #142 🎉
- @translator-th ทำ contribution แรกใน #148 🎉

**Full Changelog**: https://github.com/org/taskflow/compare/v2.3.0...v2.4.0
```

### หลักการสำคัญของ Recognition ที่ดี

1. **ให้เครดิตทุกรูปแบบของการช่วยเหลือ ไม่ใช่แค่โค้ด** — คนที่ตอบคำถามใน Discussion, คนที่แปลเอกสาร, คนที่ report บั๊กอย่างละเอียด ล้วนควรได้รับการยอมรับเช่นเดียวกับคนเขียนโค้ด
2. **ทำให้เป็นอัตโนมัติมากที่สุดเท่าที่ทำได้** — ถ้าต้องพึ่งความจำของ maintainer ในการให้เครดิต จะมีคนตกหล่นแน่นอนเมื่อโปรเจกต์โตขึ้น ควรใช้เครื่องมืออัตโนมัติอย่าง All Contributors bot หรือ GitHub release notes generator
3. **เน้นย้ำ "first-time contributor" เป็นพิเศษ** — ช่วงเวลาที่สำคัญที่สุดในการสร้างความประทับใจคือ contribution แรก ให้ความสำคัญกับช่วงเวลานี้มากเป็นพิเศษ
4. **สม่ำเสมอในทุก release ไม่ใช่แค่บางครั้ง** — ถ้าให้เครดิตเป็นบางครั้งจะดูเหมือนลำเอียง ควรทำเป็นส่วนหนึ่งของ release process ทุกครั้ง

## Step 870: แบบฝึกหัด — เขียน CONTRIBUTING.md และ CODE_OF_CONDUCT.md ฉบับเต็ม

ถึงเวลาลงมือทำจริง ในแบบฝึกหัดนี้ เราจะเขียนเอกสารทั้งสองไฟล์แบบเต็มให้กับโปรเจกต์จำลองชื่อ **TaskFlow** (แอปจัดการงานแบบ Open Source ที่เราใช้เป็นตัวอย่างตลอด Part นี้) โดยรวมทุกหลักการจาก Step 861-869 เข้าด้วยกัน

### โจทย์

1. สร้างโฟลเดอร์ฝึกฝนใหม่ในห้องทดลองของคุณ
   ```bash
   mkdir ~/git-course/part-87-contributing-coc
   cd ~/git-course/part-87-contributing-coc
   ```
2. สร้างไฟล์ `CONTRIBUTING.md` แบบเต็มตามโครงสร้าง 8 ส่วนจาก Step 862 พร้อมเพิ่มส่วน Mentorship (Step 868) และ Recognition (Step 869)
3. สร้างไฟล์ `CODE_OF_CONDUCT.md` ที่ดัดแปลงจาก Contributor Covenant พร้อมกระบวนการ Enforcement แบบเต็มจาก Step 865
4. สร้างไฟล์ template เพิ่มเติม: `.github/ISSUE_TEMPLATE/bug_report.yml` และ `.github/PULL_REQUEST_TEMPLATE.md`

กรุณาอ่าน [Code of Conduct](./CODE_OF_CONDUCT.md) ก่อนเริ่มมีส่วนร่วม

## ช่องทางการ Contribute

คุณสามารถช่วยเหลือ TaskFlow ได้หลายรูปแบบ ไม่จำเป็นต้องเขียนโค้ดเท่านั้น:

- 🐛 รายงานบั๊กที่พบ
- 💡 เสนอฟีเจอร์ใหม่
- 💻 เขียนโค้ดแก้บั๊กหรือเพิ่มฟีเจอร์
- 📖 ปรับปรุงเอกสาร README, Wiki
- 🌍 แปลเอกสารหรือ UI เป็นภาษาอื่น
- 🎨 ออกแบบ UI/UX ใหม่
- 👀 ช่วย triage issue ที่เข้ามาใหม่
- 💬 ตอบคำถามผู้ใช้ใน GitHub Discussions

## การตั้งค่า Development Environment

**ข้อกำหนดขั้นต่ำ:** Node.js >= 20, npm >= 10, Docker (สำหรับฐานข้อมูล)

    # 1. Fork repository นี้ แล้ว clone จาก fork ของคุณ
    git clone https://github.com/YOUR_USERNAME/taskflow.git
    cd taskflow

    # 2. ติดตั้ง dependencies
    npm install

    # 3. คัดลอกไฟล์ตั้งค่า
    cp .env.example .env

    # 4. รันฐานข้อมูลด้วย Docker
    docker compose up -d db

    # 5. รัน migration
    npm run db:migrate

    # 6. เริ่ม development server
    npm run dev

เปิดเบราว์เซอร์ไปที่ http://localhost:3000 หากทุกอย่างสำเร็จ คุณจะเห็น
หน้าแรกของ TaskFlow

หากติดขัดขั้นตอนใด สามารถถามได้ใน GitHub Discussions หมวด "Setup Help"
หรือเข้าร่วม Office Hours (ดูหัวข้อ Mentorship ด้านล่าง)

## Coding Style

เราใช้ ESLint และ Prettier ควบคุมสไตล์โค้ดโดยอัตโนมัติ

    npm run lint        # ตรวจสอบปัญหา
    npm run lint:fix     # แก้ไขปัญหาที่แก้อัตโนมัติได้

กรุณารันคำสั่งนี้ก่อน commit ทุกครั้ง PR ที่ CI lint ไม่ผ่านจะไม่ถูก
พิจารณา review จนกว่าจะแก้ไข

## การรัน Test

    npm test                          # รันทั้งหมด
    npm test -- src/utils/date.test.ts # รันเฉพาะไฟล์

**กฎสำคัญ:** PR ที่เพิ่มฟีเจอร์ใหม่หรือแก้บั๊กต้องมี test ประกอบเสมอ
เราไม่รับ PR ที่ทำให้ code coverage โดยรวมลดลง

## Commit Message Convention

เราใช้ [Conventional Commits](https://www.conventionalcommits.org):

    <type>(<scope>): <description>

ประเภทที่ใช้ได้: feat, fix, docs, style, refactor, test, chore

ตัวอย่าง:

    feat(auth): add OAuth login support
    fix(api): correct pagination offset calculation
    docs(readme): clarify installation steps

## Pull Request Process

1. สำหรับการเปลี่ยนแปลงขนาดใหญ่ กรุณาเปิด issue พูดคุยก่อนเริ่มเขียนโค้ด
2. สร้าง branch จาก `main` ตั้งชื่อรูปแบบ `feat/xxx` หรือ `fix/xxx`
3. ตรวจสอบว่า `npm run lint` และ `npm test` ผ่านทั้งหมดก่อน push
4. เปิด PR โดยใช้ template ที่กำหนดให้ และอ้างอิง issue ด้วย `Closes #123`
5. Sign-off commit ของคุณด้วย `git commit -s` (Developer Certificate
   of Origin — ยืนยันว่าคุณมีสิทธิ์ในโค้ดที่ส่งมา)
6. ต้องผ่าน CI ทั้งหมดและได้รับ approve จาก maintainer อย่างน้อย 1 คน
7. เราใช้ Squash and Merge เป็นค่าเริ่มต้น

## Mentorship

หากคุณเป็นมือใหม่และไม่แน่ใจว่าจะเริ่มต้นอย่างไร:

- **Good First Issues**: ดู issue ที่ติด label `good first issue`
  ทุกอันมีคำอธิบายไฟล์ที่เกี่ยวข้องและ acceptance criteria ชัดเจน
- **Office Hours**: ทุกวันพุธ 20:00 น. (เวลาไทย) ใน Discord
  channel #office-hours
- **Buddy System**: comment ใน issue ว่าอยากลองทำ ทีมงานจะจับคู่
  mentor ให้ภายใน 24 ชั่วโมง

## Recognition

ทุก contribution จะได้รับการบันทึกไว้ในตาราง Contributors ของ README
ผ่าน All Contributors bot และชื่อของคุณจะปรากฏใน Release Notes ของ
เวอร์ชันที่ PR ของคุณถูก merge เข้าไป ไม่ว่า contribution นั้นจะเป็น
โค้ด เอกสาร การแปล หรือการรายงานบั๊ก

## คำมั่นสัญญาของเรา

ในฐานะสมาชิก ผู้สนับสนุน และผู้นำของชุมชน TaskFlow เราให้คำมั่นว่าจะ

### ตัวอย่างพฤติกรรมที่ส่งเสริมสภาพแวดล้อมเชิงบวก

- แสดงความเห็นอกเห็นใจและความมีน้ำใจต่อผู้อื่น
- เคารพความคิดเห็น มุมมอง และประสบการณ์ที่แตกต่าง
- ให้และรับ feedback เชิงสร้างสรรค์อย่างสุภาพ
- ยอมรับผิดและขอโทษเมื่อทำผิดพลาด พร้อมเรียนรู้จากประสบการณ์นั้น
- มุ่งเน้นสิ่งที่ดีที่สุดสำหรับชุมชนโดยรวม ไม่ใช่แค่ตัวเอง

### ตัวอย่างพฤติกรรมที่ยอมรับไม่ได้

- การใช้ภาษาหรือภาพที่มีนัยทางเพศ และการเข้าหาทางเพศที่ไม่พึงประสงค์
- การล้อเลียน ดูหมิ่น และความคิดเห็นที่โจมตีบุคคลหรือกลุ่มบุคคล

## แนวทางการบังคับใช้

ผู้นำชุมชนจะใช้แนวทางต่อไปนี้ในการพิจารณาผลที่ตามมาสำหรับการกระทำ
ที่ละเมิด Code of Conduct นี้:

### 1. การแก้ไข (Correction)

**ลักษณะ:** การใช้ภาษาไม่เหมาะสม หรือพฤติกรรมที่ถือว่าไม่เป็นมืออาชีพ
**ผลที่ตามมา:** คำเตือนส่วนตัวเป็นลายลักษณ์อักษร พร้อมคำอธิบายว่า
ทำไมพฤติกรรมนั้นไม่เหมาะสม อาจมีการขอให้ขอโทษต่อสาธารณะ

### 2. คำเตือน (Warning)

**ลักษณะ:** การละเมิดจากเหตุการณ์เดียวหรือชุดของการกระทำ
**ผลที่ตามมา:** คำเตือนอย่างเป็นทางการพร้อมผลที่ตามมาหากมีพฤติกรรม
ต่อเนื่อง รวมถึงข้อจำกัดในการมีปฏิสัมพันธ์กับผู้ที่เกี่ยวข้องตาม
ระยะเวลาที่กำหนด

### 3. การระงับชั่วคราว (Temporary Ban)

**ลักษณะ:** การละเมิดมาตรฐานชุมชนอย่างร้ายแรง หรือพฤติกรรมไม่เหมาะสม
ต่อเนื่อง
**ผลที่ตามมา:** ระงับสิทธิ์การมีปฏิสัมพันธ์หรือสื่อสารกับชุมชนเป็น
การชั่วคราวตามระยะเวลาที่กำหนด

### 4. การระงับถาวร (Permanent Ban)

**ลักษณะ:** แสดงรูปแบบของการละเมิดมาตรฐานชุมชนอย่างต่อเนื่อง รวมถึง
การคุกคามบุคคลใดบุคคลหนึ่ง หรือแสดงความก้าวร้าวต่อกลุ่มบุคคล
**ผลที่ตามมา:** ระงับสิทธิ์การมีปฏิสัมพันธ์ใด ๆ กับชุมชนอย่างถาวร

7. **Good First Issue** ที่มีคุณภาพต้องผ่านการ curate อย่างตั้งใจ ไม่ใช่แค่ติด label ตามใจ และต้องมีระบบจัดการ issue sniping
8. **Mentorship program** ในรูปแบบ buddy system, office hours หรือโปรแกรมแบบเป็นทางการ (GSoC, Outreachy) ช่วยเปลี่ยน contributor ครั้งแรกให้กลายเป็น contributor ประจำ
9. **Recognition** ผ่านเครื่องมืออย่าง All Contributors bot และ release notes ที่ให้เครดิตอัตโนมัติ เป็นปัจจัยสำคัญที่ทำให้ contributor รู้สึกว่าการช่วยเหลือของตัวเองมีความหมาย
10. เราได้ลงมือเขียน CONTRIBUTING.md และ CODE_OF_CONDUCT.md ฉบับเต็มให้กับโปรเจกต์จำลอง TaskFlow ครบทุกองค์ประกอบที่เรียนมาใน Part นี้
