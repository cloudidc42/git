## Step 551: ทบทวน Git Object จาก Part 03/27 แล้วเจาะลึกแบบลงมือจริง

### ทบทวนสั้น ๆ ว่าเคยรู้อะไรมาบ้าง

จาก Part 03 Step 27 คุณได้เรียนมาแล้วว่า Git มี object หลัก 3 ประเภทที่เกี่ยวข้องกับการ commit ปกติ (และมีประเภทที่ 4 คือ tag object สำหรับ annotated tag):

| Object | หน้าที่โดยย่อ (ทบทวนจาก Part 03) |
|---|---|
| **Blob** | เก็บเนื้อหาไฟล์ดิบ ๆ |
| **Tree** | เก็บโครงสร้างโฟลเดอร์หนึ่งระดับ ชี้ไปยัง blob/tree อื่น |
| **Commit** | ชี้ไปยัง tree หนึ่งอัน พร้อม metadata (parent, author, committer, message) |
| **Tag (annotated)** | ชี้ไปยัง commit หนึ่งอัน พร้อมข้อมูลผู้สร้าง tag และข้อความประกอบ (จะเรียนละเอียดตอนพูดถึง annotated tag) |

และจาก Part 01 Step 6 คุณรู้ว่า Git มองข้อมูลเป็น **snapshot ของทั้งโปรเจกต์ในแต่ละ commit** ไม่ใช่ diff สะสมทีละไฟล์แบบ VCS รุ่นเก่า

สิ่งเหล่านี้ถูกต้อง 100% แต่ยังเป็นความเข้าใจใน "ระดับแนวคิด" เท่านั้น — คุณยังไม่เคยเปิดไฟล์จริงดู ไม่เคยรู้ว่า object แต่ละตัวมีหน้าตาเป็น byte อย่างไรบนดิสก์ และยังไม่เคยคำนวณ hash ด้วยมือ

### สิ่งที่ Part นี้จะเพิ่มเข้าไป: มุมมองแบบ "content-addressable storage"

หัวใจของ Git Internals ทั้งหมดสรุปเป็นประโยคเดียวได้ว่า:

> **Git คือฐานข้อมูลแบบ key-value ที่เรียบง่ายมาก ซึ่ง key คือ hash ที่คำนวณจากเนื้อหาของ value เอง (content-addressable storage)**

พูดให้เป็นรูปธรรม: ถ้าคุณเอาข้อมูลก้อนหนึ่ง (ไม่ว่าจะเป็นเนื้อหาไฟล์, รายการไฟล์ในโฟลเดอร์, หรือข้อมูล commit) ไปคำนวณ hash แล้วเก็บมันไว้โดยใช้ hash นั้นเป็น "ชื่อไฟล์" — นั่นคือทั้งหมดที่ Git object database ทำ ไม่มีอะไรซับซ้อนไปกว่านี้

คุณสมบัติที่ตามมาจากการออกแบบแบบนี้ (ซึ่งเป็นเหตุผลที่ Git ทำงานได้เร็วและปลอดภัย):

1. **Object เดียวกันทุกประการ (เนื้อหาเหมือนกันเป๊ะ) จะมี hash เดียวกันเสมอ** ไม่ว่าจะอยู่ใน repo ไหน คอมพิวเตอร์เครื่องไหน — นี่คือเหตุผลที่บล็อบของไฟล์ว่างเปล่ามี hash เดียวกันทุก repository ในโลก (จะพิสูจน์ให้ดูใน Step 553)
2. **Object ไม่มีวันถูกแก้ไข (immutable)** — ถ้าเปลี่ยนเนื้อหาแม้แต่ 1 byte จะได้ hash ใหม่ กลายเป็น object คนละตัวทันที object เก่ายังอยู่เหมือนเดิมไม่ถูกแตะต้อง
3. **การอ้างอิงกันระหว่าง object ทั้งหมด ใช้ hash ล้วน ๆ** — commit ไม่ได้ "เก็บ" tree ไว้ข้างใน แต่เก็บแค่ "เลขที่อยู่" (hash) ของ tree นั้น เหมือนตัวชี้ (pointer) ในภาษาโปรแกรม
4. **ตรวจจับความเสียหายหรือการปลอมแปลงได้ทันที** — ถ้าไฟล์ใน `.git/objects/` เสียหายแม้แต่นิดเดียว การคำนวณ hash ของเนื้อหาที่อ่านได้จะไม่ตรงกับชื่อไฟล์ Git จะรู้ทันที (ทวนความเข้าใจจาก Part 03 Step 28)

### แนวทางการเรียนใน Part นี้

เราจะไม่หยุดแค่ทฤษฎี ทุก Step ตั้งแต่นี้ไปจะมีคำสั่งจริงให้คุณลองรันตามในเครื่องของคุณเอง (แนะนำให้เปิด terminal ไว้ข้าง ๆ และมี repository ทดสอบพร้อมสัก 1 อัน — จะใช้ `~/git-course` ที่เตรียมไว้ตั้งแต่ Part 01 หรือสร้างโฟลเดอร์ใหม่ก็ได้) เพื่อให้คุณเห็นด้วยตาตัวเองว่า:

- object แต่ละตัวเก็บอยู่ที่ไหนบนดิสก์จริง ๆ
- ข้างในไฟล์นั้นมีอะไร (หลังถอดการบีบอัดออก)
- คำสั่งระดับสูงที่คุณคุ้นเคย เช่น `git commit`, `git log`, `git show` แท้จริงแล้วกำลังอ่าน/เขียน object เหล่านี้อยู่เบื้องหลังตลอดเวลา

> **หมายเหตุ:** Part นี้จะยังไม่ลงลึกคำสั่ง plumbing ทุกตัวแบบละเอียด (เช่นตัวเลือกทั้งหมดของ `git cat-file`, การเขียน tree ด้วย `git mktree`, การจัดการ ref ด้วย `git update-ref`) — ส่วนนั้นคือเนื้อหาเต็มของ **Part 57: Git Plumbing Commands** ที่ต่อจาก Part นี้โดยตรง ใน Part 56 นี้เราจะโฟกัสที่ "โมเดลข้อมูล" ให้แน่นก่อน แล้วค่อยไปเรียนเครื่องมือสำหรับจัดการมันแบบเต็มรูปแบบใน Part ถัดไป

## Step 552: โครงสร้างโฟลเดอร์ `.git/objects/` เก็บอะไรบ้าง

### เปิดดูโฟลเดอร์จริง

ลองสร้าง repository ทดสอบใหม่ แล้วสร้าง commit แรกดู:

```bash
mkdir -p ~/git-course/part-56-internals
cd ~/git-course/part-56-internals
git init
echo "Hello Git Internals" > hello.txt
git add hello.txt
git commit -m "commit แรกสำหรับสำรวจ object"
```

จากนั้นดูข้างใน `.git/objects/`:

```bash
find .git/objects -type f
```

ผลลัพธ์โดยประมาณ (hash จริงในเครื่องคุณจะไม่เหมือนตัวอย่างนี้ เพราะ hash ขึ้นกับเวลา ผู้เขียน และเนื้อหาที่ต่างกัน):

```
.git/objects/1f/7a94f2c1e6a9b8d3f0a2c4e5b6d7f8a9c0b1d2
.git/objects/6b/584e8ece562ebffc15d38808cd6b98fc3d97ea
.git/objects/9d/8f2a1c3e5b7d9f1a3c5e7b9d1f3a5c7e9b1d3f
```

### กฎการตั้งชื่อ: 2 ตัวอักษรแรก = ชื่อโฟลเดอร์ย่อย

สังเกตว่าแต่ละ object ไม่ได้เก็บเป็นไฟล์เดี่ยว ๆ อยู่ใน `objects/` ตรง ๆ แต่ถูกแบ่งเป็น 2 ชั้น:

```
.git/objects/
├── 1f/
│   └── 7a94f2c1e6a9b8d3f0a2c4e5b6d7f8a9c0b1d2
├── 6b/
│   └── 584e8ece562ebffc15d38808cd6b98fc3d97ea
└── 9d/
    └── 8f2a1c3e5b7d9f1a3c5e7b9d1f3a5c7e9b1d3f
```

กฎคือ:

> **hash เต็ม 40 ตัวอักษร (สำหรับ SHA-1) ถูกแบ่งเป็น 2 ส่วน: 2 ตัวอักษรแรกกลายเป็นชื่อ "โฟลเดอร์ย่อย" และ 38 ตัวอักษรที่เหลือกลายเป็น "ชื่อไฟล์" ภายในโฟลเดอร์นั้น**

ตัวอย่าง: ถ้า commit มี hash เต็มคือ `9d8f2a1c3e5b7d9f1a3c5e7b9d1f3a5c7e9b1d3f` มันจะถูกเก็บไว้ที่:

```
.git/objects/9d/8f2a1c3e5b7d9f1a3c5e7b9d1f3a5c7e9b1d3f
              └┬┘ └──────────────────┬───────────────────┘
        โฟลเดอร์ย่อย (2 ตัวแรก)      ชื่อไฟล์ (38 ตัวที่เหลือ)
```

(ถ้า repository ใช้โหมด SHA-256 hash จะยาว 64 ตัวอักษร กฎเดียวกัน: 2 ตัวแรกเป็นชื่อโฟลเดอร์ อีก 62 ตัวเป็นชื่อไฟล์)

### ทำไมต้องแบ่งเป็นโฟลเดอร์ย่อยแบบนี้ — เหตุผลด้าน Performance ของระบบไฟล์

เหตุผลไม่ได้เกี่ยวกับความปลอดภัยหรือการจัดหมวดหมู่แต่อย่างใด แต่เป็นเรื่อง **ประสิทธิภาพของระบบไฟล์ (filesystem performance)** ล้วน ๆ:

- ระบบไฟล์จำนวนมาก (โดยเฉพาะระบบเก่า เช่น ext2, FAT) จะทำงาน**ช้าลงอย่างมาก**เมื่อมีไฟล์จำนวนมหาศาลอยู่ในโฟลเดอร์เดียวกัน (การค้นหาไฟล์หนึ่งไฟล์อาจต้องไล่ดูรายการทั้งหมด)
- โปรเจกต์ขนาดใหญ่ที่มีประวัติหลายแสน commit จะมี object รวมกันเป็นแสนถึงล้านตัว ถ้าใส่ทุกตัวไว้ในโฟลเดอร์เดียว ระบบไฟล์จะแย่มาก
- การแบ่งด้วย 2 ตัวอักษรแรกของ hash (ซึ่งเป็นเลขฐาน 16 คือ 0-9 และ a-f) ทำให้ได้โฟลเดอร์ย่อยสูงสุด **256 โฟลเดอร์** (16 × 16) และเพราะ hash มีคุณสมบัติกระจายตัวสม่ำเสมอ (uniform distribution) object นับล้านตัวจะถูกกระจายไปตามโฟลเดอร์ทั้ง 256 นี้อย่างเท่า ๆ กันโดยอัตโนมัติ ทำให้แต่ละโฟลเดอร์มีไฟล์ไม่มากเกินไป

### ไฟล์/โฟลเดอร์อื่นที่อยู่ใน `.git/objects/`

นอกจากโฟลเดอร์ 2 ตัวอักษรที่เก็บ "loose object" (object เดี่ยว ๆ ที่ยังไม่ถูกอัดรวม) แล้ว ยังมีอีก 2 โฟลเดอร์ที่อาจเจอ:

| โฟลเดอร์/ไฟล์ | เก็บอะไร |
|---|---|
| `.git/objects/<xx>/<...>` | **Loose object** — object เดี่ยว ๆ แต่ละตัว บีบอัดด้วย zlib แยกไฟล์ (สิ่งที่เราสำรวจอยู่ตอนนี้) |
| `.git/objects/pack/` | **Packfiles** — object จำนวนมากถูกอัดรวมเป็นไฟล์เดียว ใช้ delta compression ประหยัดพื้นที่กว่ามาก (เจาะลึกเต็มใน **Part 58**) |
| `.git/objects/info/` | ไฟล์ metadata เสริมเกี่ยวกับ packfiles เช่น `commit-graph` (ใช้เร่งความเร็วคำสั่งบางตัว) |

> **ข้อควรรู้ล่วงหน้า (จะอธิบายเต็มใน Part 58):** object ที่คุณเพิ่งสร้างด้วย `git commit` จะเป็น **loose object** เสมอในตอนแรก แต่เมื่อเวลาผ่านไป (หรือรัน `git gc`) Git จะเก็บกวาด loose object จำนวนมากมาอัดรวมเป็น packfile เพื่อประหยัดพื้นที่และเพิ่มความเร็ว ดังนั้นใน repository ที่ clone มาจาก remote object เก่า ๆ ส่วนใหญ่มักจะอยู่ใน packfile ไม่ใช่ loose object แล้ว — ประเด็นนี้สำคัญมากสำหรับแบบฝึกหัดใน Step 560

### ทำไมเปิดไฟล์ object ด้วย `cat` ตรง ๆ แล้วอ่านไม่ออก

ลองรันดู:

```bash
cat .git/objects/9d/8f2a1c3e5b7d9f1a3c5e7b9d1f3a5c7e9b1d3f
```

จะได้ตัวอักษรมั่ว ๆ อ่านไม่ออกเลย เพราะ **object ทุกตัวถูกบีบอัดด้วยอัลกอริทึม zlib (DEFLATE) ก่อนเขียนลงดิสก์** ต้องใช้เครื่องมือที่รู้จักถอดรหัส zlib เท่านั้นถึงจะอ่านได้ ซึ่งก็คือ `git cat-file` ที่จะเรียนใน Step 558 (หรือใช้ `python3 -c "import zlib,sys; print(zlib.decompress(open(sys.argv[1],'rb').read()))"` ก็ถอดได้เช่นกัน เพราะ zlib เป็นมาตรฐานเปิด ไม่ใช่ format เฉพาะของ Git)

## Step 553: Blob Object คืออะไร เก็บเนื้อหาไฟล์อย่างไร

### นิยาม

**Blob** (ย่อมาจาก **B**inary **L**arge **OB**ject) คือ object ที่เก็บ **เนื้อหาไฟล์ดิบ ๆ (raw byte content) เพียงอย่างเดียว** — นี่คือประเภท object ที่ "ต่ำที่สุด" ในลำดับชั้นของ Git object

### สิ่งที่ Blob ไม่เก็บ (สำคัญมาก)

ย้ำสิ่งที่ Part 03 เคยบอกไว้ให้ชัดเจนขึ้นอีกระดับ **Blob ไม่เก็บสิ่งเหล่านี้เลยแม้แต่นิดเดียว:**

- ❌ ชื่อไฟล์ (filename)
- ❌ ตำแหน่งที่อยู่ในโฟลเดอร์ (path)
- ❌ สิทธิ์การเข้าถึง/permission (เช่น executable หรือไม่)
- ❌ เวลาที่สร้าง/แก้ไข (timestamp)
- ❌ ประวัติว่ามันเคยถูกแก้ไขมาจากอะไร

ข้อมูลทั้งหมดข้างต้นนี้ **tree object เป็นคนเก็บแทน** (จะเรียนใน Step 554) — Blob สนใจแค่ "ไบต์ข้างในไฟล์" เท่านั้น

### รูปแบบที่แท้จริงก่อนคำนวณ hash

นี่คือรายละเอียดที่ Part 03 ยังไม่เคยพูดถึง: ก่อนที่ Git จะคำนวณ hash ของเนื้อหาไฟล์ มันจะ**เติม header สั้น ๆ นำหน้าเนื้อหาก่อนเสมอ** ตามรูปแบบนี้:

```
blob <ขนาดเนื้อหาเป็นไบต์ในเลขฐาน 10>\0<เนื้อหาไฟล์จริง>
```

โดย `\0` คือ null byte (ไบต์ค่า 0) ใช้เป็นตัวคั่นระหว่าง header กับเนื้อหา

ตัวอย่างถ้าไฟล์ `hello.txt` มีเนื้อหา `Hello Git Internals\n` (21 ไบต์รวม newline):

```
สิ่งที่ถูกนำไปคำนวณ hash จริง ๆ คือสตริง:
"blob 21\0Hello Git Internals\n"
```

จากนั้น Git จะ:
1. คำนวณ **SHA-1** (หรือ SHA-256 ถ้าตั้งค่าไว้) ของสตริงทั้งก้อนนี้ (header + null byte + เนื้อหา) → ได้ hash 40 ตัวอักษรซึ่งคือชื่อของ object นี้
2. บีบอัดสตริงทั้งก้อนเดียวกันนี้ด้วย zlib
3. เขียนผลลัพธ์ที่บีบอัดแล้วลงไฟล์ที่ `.git/objects/<2 ตัวแรกของ hash>/<38 ตัวที่เหลือ>`

### พิสูจน์ด้วยมือ: hash ที่คำนวณเองต้องตรงกับที่ Git คำนวณ

```bash
echo -n "Hello Git Internals" > hello.txt
git hash-object hello.txt
```

คำสั่งนี้จะพิมพ์ hash ออกมาโดยที่ **ยังไม่ได้เขียนอะไรลงดิสก์เลย** (แค่คำนวณให้ดูเฉย ๆ) และ hash ที่ได้จะตรงกับ hash ของ blob ที่ `git add` จะสร้างขึ้นเป๊ะ ๆ ทุกครั้ง เพราะสูตรการคำนวณคือสูตรเดียวกัน

### ข้อเท็จจริงที่พิสูจน์ Content-Addressable ได้ชัดที่สุด: Hash ของไฟล์ว่างเปล่า

นี่คือตัวอย่างที่ทรงพลังมากในการทำความเข้าใจแนวคิด content-addressable: **ไฟล์ว่างเปล่า (0 ไบต์) ทุกไฟล์ ในทุก repository ทั่วโลก จะได้ blob hash เดียวกันเป๊ะเสมอ**

ลองพิสูจน์เอง:

```bash
touch empty.txt
git hash-object empty.txt
```

ผลลัพธ์ที่ได้จะเป็น:

```
e69de29bb2d1d6434b8b29ae775ad8c2e48c5391
```

**ไม่ว่าคุณจะรันคำสั่งนี้ที่เครื่องไหน ปีไหน ก็จะได้ค่านี้เหมือนกันเป๊ะเสมอ** เพราะ header ที่ใช้คำนวณคือ `"blob 0\0"` (ขนาดเนื้อหาเป็น 0 ไบต์ ตามด้วย null byte แล้วไม่มีเนื้อหาต่อท้ายอีกเลย) ซึ่งเป็นสตริงคงที่ ไม่ขึ้นกับเวลา ผู้เขียน หรือเครื่องที่รัน — ต่างจาก commit hash ที่จะไม่มีวันซ้ำกันเพราะมี timestamp กับชื่อผู้เขียนปนอยู่ในข้อมูลที่ใช้คำนวณ

### Blob ซ้ำกัน = เก็บครั้งเดียว (Deduplication)

ทวนความเข้าใจจาก Part 03 ให้แม่นขึ้นด้วยตัวอย่างจริง: ลองสร้างไฟล์ 2 ไฟล์ที่มีเนื้อหาเหมือนกันเป๊ะ คนละตำแหน่ง คนละชื่อ:

```bash
mkdir -p src config
echo "VERSION=1.0.0" > src/version.txt
echo "VERSION=1.0.0" > config/version.txt
git add src/version.txt config/version.txt
git commit -m "เพิ่มไฟล์ version สองที่"
git cat-file -p HEAD^{tree}
```

ถ้าไปดูใน tree ของ `src/` และ `config/` จะพบว่า **hash ของ blob ที่ทั้งสองไฟล์ชี้ไปคือ hash เดียวกันเป๊ะ** — Git ไม่ได้เก็บเนื้อหา `VERSION=1.0.0` ซ้ำสองรอบในดิสก์ แต่เก็บ blob เพียงชุดเดียว แล้วให้ tree entry สองอัน (คนละชื่อ คนละที่อยู่) ชี้มายัง blob ตัวเดียวกันนี้ นี่คือกลไกที่ทำให้ Git ประหยัดพื้นที่ได้มากในโปรเจกต์จริงที่มักมีไฟล์ config หรือไฟล์ template คล้าย ๆ กันกระจายอยู่หลายที่

### สรุปคุณสมบัติของ Blob

| คุณสมบัติ | รายละเอียด |
|---|---|
| เก็บอะไร | เนื้อหาไฟล์ดิบ ๆ เท่านั้น (raw bytes) |
| ไม่เก็บอะไร | ชื่อไฟล์, path, permission, timestamp |
| Hash คำนวณจาก | `"blob " + ขนาดไบต์ + "\0" + เนื้อหา` |
| ระบุตัวตนด้วย | เนื้อหา ไม่ใช่ชื่อไฟล์ |
| ไฟล์เนื้อหาเหมือนกัน | ได้ blob hash เดียวกันเสมอ ไม่ว่าอยู่ที่ไหน |
| แก้ไขได้ไหม | ไม่ได้ (immutable) — แก้เนื้อหา = ได้ blob ใหม่ hash ใหม่ |

## Step 554: Tree Object คืออะไร เทียบเท่าโฟลเดอร์ในโลกจริง

### นิยาม

**Tree** คือ object ที่แทน **สถานะของโฟลเดอร์หนึ่งระดับ ณ ขณะหนึ่ง** — ถ้า blob คือ "เนื้อหาไฟล์" tree ก็คือ "รายการไฟล์/โฟลเดอร์พร้อมชื่อของมัน" นั่นเอง เป็นตัวเชื่อมช่องว่างระหว่างข้อมูลดิบกับโครงสร้างไฟล์จริงที่มนุษย์เข้าใจได้

### แต่ละแถวใน Tree เก็บอะไรบ้าง

Tree object หนึ่งอันประกอบด้วยหลาย ๆ "entry" เรียงต่อกัน แต่ละ entry เก็บ 3 อย่าง:

1. **Mode** — เลขบอกประเภทและสิทธิ์ของ entry นั้น
2. **ชื่อไฟล์หรือโฟลเดอร์ย่อย** (แค่ชื่อ ไม่ใช่ path เต็ม เพราะ tree เก็บแค่ระดับเดียว)
3. **Hash ที่ชี้ไปยัง object อื่น** — ถ้า entry เป็นไฟล์ hash จะชี้ไปยัง **blob** ถ้า entry เป็นโฟลเดอร์ย่อย hash จะชี้ไปยัง **tree** อีกอันหนึ่ง (ซ้อนกันไปเรื่อย ๆ)

### ค่า Mode ที่เป็นไปได้

| Mode | ความหมาย |
|---|---|
| `100644` | ไฟล์ปกติ อ่าน/เขียนได้ ไม่ใช่ executable (พบบ่อยที่สุด) |
| `100755` | ไฟล์ที่เป็น executable (มีสิทธิ์ `+x`) เช่น script |
| `120000` | Symbolic link (ไฟล์ที่ blob เก็บ "path ปลายทาง" แทนเนื้อหาไฟล์จริง) |
| `040000` | โฟลเดอร์ย่อย (ชี้ไปยัง tree object อื่น ไม่ใช่ blob) |
| `160000` | Gitlink — ตัวชี้ไปยัง commit ของ Git repository อื่นที่ฝังอยู่ข้างใน (ใช้ในกลไก **submodule**) |

### ดูเนื้อหา Tree จริงด้วย `git cat-file -p`

ต่อจาก repository ที่สร้างไว้ใน Step 552 ลองดู tree ของ commit ล่าสุด:

```bash
git cat-file -p HEAD^{tree}
```

ผลลัพธ์ตัวอย่าง (สมมติมีไฟล์ `hello.txt` และโฟลเดอร์ `src/`):

```
100644 blob 6b584e8ece562ebffc15d38808cd6b98fc3d97e	hello.txt
040000 tree 3f5b9d2a7c1e4f6a8b0d2c4e6a8b0d2c4e6a8b0d	src
```

อ่านออกเสียงเป็นภาษาคนได้ว่า: "ในโฟลเดอร์ root ของ commit นี้ มีไฟล์ปกติชื่อ `hello.txt` ที่เนื้อหาอยู่ใน blob hash `6b58...` และมีโฟลเดอร์ย่อยชื่อ `src` ซึ่งโครงสร้างข้างในถูกเก็บไว้ใน tree อีกอันหนึ่ง hash `3f5b...`"

ถ้าอยากดูข้างใน `src/` ต่อ ก็แค่เอา hash ของ tree นั้นไป cat-file ต่อ:

```bash
git cat-file -p 3f5b9d2a7c1e4f6a8b0d2c4e6a8b0d2c4e6a8b0d
```

### Tree ซ้อนกันเป็นชั้น ๆ (Nested Tree)

โครงสร้างโปรเจกต์จริงที่มีหลายระดับโฟลเดอร์ จะถูกแทนด้วย tree ที่ซ้อนกันหลายชั้น ตัวอย่างโครงสร้างไฟล์:

```
my-project/
├── README.md
└── src/
    ├── app.js
    └── utils/
        └── helper.js
```

จะถูกแปลงเป็นโครงสร้าง tree แบบนี้:

```
Tree (root)
├── "README.md" ──▶ Blob
└── "src"        ──▶ Tree (src/)
                      ├── "app.js" ──▶ Blob
                      └── "utils"  ──▶ Tree (src/utils/)
                                        └── "helper.js" ──▶ Blob
```

ยิ่งโฟลเดอร์ลึกเท่าไหร่ ก็ยิ่งมี tree object ซ้อนกันมากขึ้นเท่านั้น — โครงสร้างนี้เองที่ Part 03 Step 27 เรียกว่า "tree structure" และเป็นเหตุผลที่คำว่า "tree" ถูกใช้เรียก object ประเภทนี้

### Tree ก็เป็น Content-Addressable เหมือนกัน

จุดที่หลายคนมองข้าม: **tree object ก็มี hash ที่คำนวณจากเนื้อหาของมันเองเช่นกัน** (รายการ entries ทั้งหมด รวม mode, ชื่อ, และ hash ของลูกทุกตัว) ผลที่ตามมาคือ:

> **ถ้าโฟลเดอร์หนึ่ง ๆ ไม่มีการเปลี่ยนแปลงอะไรเลยระหว่าง 2 commit (ทั้งชื่อไฟล์ เนื้อหา และโครงสร้างย่อยข้างใน) tree object ของโฟลเดอร์นั้นจะมี hash เดิมทุกประการ และ Git จะใช้ tree ตัวเดิมซ้ำ ไม่สร้างใหม่**

นี่คือกลไกจริงที่อยู่เบื้องหลังคำกล่าวใน **Part 01 Step 6** ที่ว่า "ไฟล์ที่ไม่เปลี่ยนจะแค่ทำ pointer ไปยังของเดิม" — ในระดับ object จริง ๆ แล้วสิ่งที่เกิดขึ้นคือ **tree object ทั้งอันถูกใช้ซ้ำ** (ไม่ใช่แค่ blob) เพราะถ้าไม่มีไฟล์ใดในโฟลเดอร์นั้นเปลี่ยนเลย ข้อมูลที่ใช้คำนวณ hash ของ tree ก็เหมือนเดิมทุกประการ hash จึงเหมือนเดิม

ผลลัพธ์ในทางปฏิบัติ: การ commit หนึ่งครั้งที่แก้ไฟล์เพียงไฟล์เดียวลึกลงไปในโฟลเดอร์ที่ซ้อนกันหลายชั้น จะสร้าง object ใหม่แค่ **blob ของไฟล์นั้น + tree ทุกชั้นที่อยู่บน "เส้นทาง" ไปถึงไฟล์นั้น (จนถึง root) + commit ใหม่หนึ่งอัน** — ส่วนโฟลเดอร์พี่น้องอื่น ๆ ที่ไม่เกี่ยวข้องจะใช้ tree hash เดิมทั้งหมด

### สรุปคุณสมบัติของ Tree

| คุณสมบัติ | รายละเอียด |
|---|---|
| เก็บอะไร | รายการ (mode, ชื่อ, hash ลูก) ของโฟลเดอร์หนึ่งระดับ |
| ชี้ไปยัง | Blob (ถ้าเป็นไฟล์) หรือ Tree อื่น (ถ้าเป็นโฟลเดอร์ย่อย) |
| เทียบเท่ากับ | โฟลเดอร์หนึ่งโฟลเดอร์ในระบบไฟล์จริง |
| ซ้อนกันได้ | ได้ ตามจำนวนระดับของโฟลเดอร์จริง |
| Reuse ได้ไหม | ได้ ถ้าเนื้อหา+โครงสร้างข้างในเหมือนเดิมทุกประการ hash จะเหมือนเดิม ใช้ object ซ้ำ |

## Step 555: Commit Object คืออะไร โครงสร้างเนื้อหาจริงเป็นอย่างไร

### ดูเนื้อหา Commit จริงแบบดิบ ๆ

Part 03 Step 25 เคยอธิบายด้วยไดอะแกรมว่า commit เก็บอะไรบ้าง คราวนี้มาดูของจริงกัน:

```bash
git cat-file -p HEAD
```

ผลลัพธ์จริง (ไม่ใช่ไดอะแกรมสมมติ) จะหน้าตาประมาณนี้:

```
tree 9d8f2a1c3e5b7d9f1a3c5e7b9d1f3a5c7e9b1d3f
author Somchai <somchai@example.com> 1735182000 +0700
committer Somchai <somchai@example.com> 1735182000 +0700

commit แรกสำหรับสำรวจ object
```

(commit แรกสุดของ repo จะไม่มีบรรทัด `parent` เพราะไม่มี commit ก่อนหน้า — จะอธิบายเพิ่มด้านล่าง)

### ผ่าโครงสร้างทีละบรรทัด

| ส่วน | ความหมาย |
|---|---|
| `tree <hash>` | ชี้ไปยัง tree object ที่แทนสถานะไฟล์ทั้งหมด ณ commit นี้ (ต้องมีเสมอ 1 บรรทัด) |
| `parent <hash>` | ชี้ไปยัง commit ก่อนหน้า — **0 บรรทัด** สำหรับ commit แรกสุด (root commit), **1 บรรทัด** สำหรับ commit ปกติ, **2 บรรทัดขึ้นไป** สำหรับ merge commit (แต่ละ parent คือ branch ที่ถูกรวมเข้ามา) |
| `author <ชื่อ> <email> <unix timestamp> <timezone offset>` | ผู้ที่**เขียนโค้ด**นี้จริง ๆ พร้อมเวลาที่เขียน |
| `committer <ชื่อ> <email> <unix timestamp> <timezone offset>` | ผู้ที่**สั่งบันทึก**commit นี้เข้า repository พร้อมเวลาที่สั่ง commit |
| (บรรทัดว่าง) | ตัวคั่นระหว่าง metadata กับข้อความ commit เสมอ |
| ข้อความ commit | ส่วนที่เหลือทั้งหมดหลังบรรทัดว่างคือ commit message (จะยาวกี่บรรทัดก็ได้) |

### รูปแบบของ Timestamp

สังเกตรูปแบบ `1735182000 +0700` — นี่คือ:

- `1735182000` คือ **Unix timestamp** (จำนวนวินาทีนับจากเที่ยงคืนวันที่ 1 มกราคม 1970 UTC)
- `+0700` คือ **timezone offset** ของเครื่องผู้เขียน/ผู้ commit ในขณะนั้น (ในที่นี้คือ UTC+7 ซึ่งคือเขตเวลาไทย)

การเก็บทั้งสองค่าคู่กันแบบนี้ทำให้ Git แสดงเวลาของ commit ได้ตามเขตเวลาต้นทางเสมอ ไม่ว่าคนที่มาดูภายหลังจะอยู่เขตเวลาไหนก็ตาม (ลองสังเกตว่า `git log` ปกติจะแสดงเวลาพร้อม offset ต่อท้ายเสมอ)

### Merge Commit มี Parent หลายอัน

ลองสร้าง merge commit จริงเพื่อดูผลต่าง:

```bash
git checkout -b feature
echo "feature code" > feature.txt
git add feature.txt
git commit -m "เพิ่ม feature"
git checkout main
git merge feature --no-ff -m "รวม feature เข้า main"
git cat-file -p HEAD
```

จะเห็นว่า commit ที่เพิ่งสร้างมี**สองบรรทัด parent**:

```
tree a1b2c3d4e5f6...
parent 6b584e8ece562ebffc15d38808cd6b98fc3d97e
parent 7c695f9fdf673acb98fc3d97ea6b584e8ece562e
committer Somchai <somchai@example.com> 1735182500 +0700

รวม feature เข้า main
```

parent อันแรกคือปลาย branch ที่คุณยืนอยู่ตอน merge (`main`) parent อันที่สองคือปลาย branch ที่ถูกดึงเข้ามา (`feature`) ลำดับนี้มีความหมาย — Git ใช้มันตัดสินว่า "สายหลัก (first parent)" ของประวัติคือเส้นไหน ซึ่งจะสำคัญมากตอนเรียนคำสั่งอย่าง `git log --first-parent` ในเฟสถัดไป

### Commit ที่เซ็นด้วย GPG (แค่ให้รู้จักไว้)

ถ้า commit ถูกเซ็นด้วย GPG (เรื่องนี้จะเรียนละเอียดในเฟส 8 เรื่อง Security) เนื้อหา commit object จะมี header เพิ่มชื่อ `gpgsig` แทรกอยู่ก่อนบรรทัดว่างและข้อความ commit โดยเก็บลายเซ็นดิจิทัลแบบหลายบรรทัดไว้ในนั้น — สิ่งนี้ยืนยันอีกครั้งว่า commit object ไม่ใช่รูปแบบตายตัวที่มีแค่ 4-5 บรรทัดเสมอไป แต่เป็น "ชุด header ตามด้วยข้อความ" ที่ยืดหยุ่นพอจะใส่ข้อมูลเสริมได้

### Hash ของ Commit คำนวณจากอะไร

เหมือนกับ blob และ tree ทุกประการ — เนื้อหาทั้งหมดที่คุณเห็นจาก `git cat-file -p` (tree, parent, author, committer, message) ถูกนำหน้าด้วย header `commit <ขนาดไบต์>\0` แล้วนำทั้งก้อนไปคำนวณ SHA-1 เพื่อได้ hash ของ commit นั้น เช่นเดียวกับ blob/tree — **ถ้าแก้ข้อความ commit แม้แต่ตัวอักษรเดียว, เปลี่ยนเวลา, หรือ tree ที่ชี้ไปเปลี่ยน hash ของ commit จะเปลี่ยนทันที** (นี่คือกลไกจริงเบื้องหลังสิ่งที่ Part 03 Step 28 เคยอธิบายไว้เป็นไดอะแกรมความคิด)

### สรุปคุณสมบัติของ Commit

| คุณสมบัติ | รายละเอียด |
|---|---|
| เก็บอะไร | tree hash, parent hash (0/1/2+ อัน), author, committer, message |
| ชี้ไปยัง | Tree object เดียว (โครงสร้างทั้งโปรเจกต์ ณ ขณะนั้น) + Commit อื่น (parent) |
| Root commit | ไม่มีบรรทัด parent เลย |
| Commit ปกติ | มี parent 1 อัน |
| Merge commit | มี parent ตั้งแต่ 2 อันขึ้นไป |
| Immutable ไหม | ใช่ — "แก้ commit" ที่แท้จริงคือการสร้าง commit ใหม่แทนที่เสมอ |

## Step 556: Ref คืออะไร — ไฟล์ Text ธรรมดาที่เก็บ Hash

### ปัญหาที่ Ref มาแก้

Object ทุกตัวที่เรียนมา (blob, tree, commit) ถูกอ้างอิงด้วย **hash 40 ตัวอักษรที่จำไม่ได้เลยในชีวิตจริง** ลองนึกภาพว่าทุกครั้งที่จะสลับไปทำงานที่ branch `main` คุณต้องพิมพ์ `git checkout 9d8f2a1c3e5b7d9f1a3c5e7b9d1f3a5c7e9b1d3f` — นี่คือปัญหาที่ **Ref (Reference)** เข้ามาแก้

> **Ref คือ "ชื่อที่จำง่าย" ที่ทำหน้าที่ชี้ไปยัง commit hash หนึ่งอัน**

พูดให้ตรงที่สุด: **branch และ tag ที่คุณใช้งานมาตลอดหลักสูตรนี้ ไม่ใช่ object ชนิดพิเศษอะไรเลย มันเป็นแค่ไฟล์ text ธรรมดาไฟล์หนึ่งที่ข้างในมี hash เขียนอยู่บรรทัดเดียว**

### ดูของจริง: Branch คือไฟล์ธรรมดาแค่นั้นเอง

```bash
cat .git/refs/heads/main
```

ผลลัพธ์:

```
9d8f2a1c3e5b7d9f1a3c5e7b9d1f3a5c7e9b1d3f
```

**แค่นั้นจริง ๆ** — ไม่มีอะไรมากไปกว่า hash หนึ่งบรรทัดบวก newline ท้ายบรรทัด คุณสามารถเปิดด้วย text editor ธรรมดา ๆ ดูได้เลย (แม้ปกติไม่ควรแก้มันด้วยมือ ควรใช้คำสั่ง Git เสมอ เพื่อป้องกันการพิมพ์ hash ผิดจนได้ branch ที่ชี้ไป commit ที่ไม่มีอยู่จริง)

### โครงสร้างโฟลเดอร์ `refs/`

```
.git/refs/
├── heads/              # ref ของ branch ทุกตัวในเครื่อง (local branches)
│   ├── main
│   └── feature
├── tags/                # ref ของ tag ทุกตัว
│   └── v1.0.0
└── remotes/             # ref ที่ "จำ" สถานะล่าสุดของ branch บน remote (remote-tracking branches)
    └── origin/
        └── main
```

| โฟลเดอร์ | เก็บ ref ของอะไร |
|---|---|
| `refs/heads/<ชื่อ>` | Branch ในเครื่อง (local branch) — ไฟล์ชื่อ branch เก็บ hash ของ commit ล่าสุดใน branch นั้น |
| `refs/tags/<ชื่อ>` | Tag — สำหรับ **lightweight tag** ไฟล์จะเก็บ hash ของ commit ตรง ๆ เหมือน branch สำหรับ **annotated tag** ไฟล์จะเก็บ hash ของ **tag object** (ซึ่งค่อยชี้ไปยัง commit อีกที) |
| `refs/remotes/<remote>/<branch>` | Remote-tracking branch — "ความจำ" ว่าครั้งล่าสุดที่ sync กับ remote นั้น branch อยู่ที่ commit ไหน จะอัปเดตก็ต่อเมื่อสั่ง `git fetch`/`git pull` เท่านั้น |

### Branch = Ref ที่ "เขยื้อน" ตัวเองอัตโนมัติ

จุดที่ทำให้ branch มีประโยชน์คือพฤติกรรมนี้: **ทุกครั้งที่คุณ commit ขณะอยู่บน branch หนึ่ง ไฟล์ ref ของ branch นั้นจะถูกอัปเดตให้ชี้ไปยัง commit ใหม่ล่าสุดโดยอัตโนมัติ**

ลองพิสูจน์:

```bash
cat .git/refs/heads/main
echo "more content" >> hello.txt
git add hello.txt
git commit -m "แก้ไขเพิ่มเติม"
cat .git/refs/heads/main
```

จะเห็นว่า hash ในไฟล์ `refs/heads/main` เปลี่ยนไปเป็น hash ของ commit ล่าสุด — นี่คือกลไกที่แท้จริงเบื้องหลังคำว่า "branch เดินหน้าไปเรื่อย ๆ ตามที่คุณ commit"

ต่างจาก **tag** ซึ่งปกติจะถูกสร้างเพื่อ "ปักหมุด" ไว้ที่ commit ใดหนึ่งตายตัว — เมื่อคุณ commit ต่อไปอีก ref ของ tag จะไม่ขยับตามเลย (เว้นแต่คุณย้าย tag ด้วยมือ)

### `packed-refs` — เมื่อ Ref จำนวนมากถูกอัดรวม

ในหลาย ๆ repository (โดยเฉพาะที่ได้จากการ `git clone`) คุณอาจไม่เจอไฟล์ใน `refs/heads/` หรือ `refs/tags/` ตรง ๆ สำหรับ ref บางตัว เพราะมันถูกอัดรวมไว้ในไฟล์เดียวคือ `.git/packed-refs`:

```bash
cat .git/packed-refs
```

```
# pack-refs with: peeled fully-peeled sorted
9d8f2a1c3e5b7d9f1a3c5e7b9d1f3a5c7e9b1d3f refs/heads/main
7c695f9fdf673acb98fc3d97ea6b584e8ece562e refs/tags/v1.0.0
```

กฎการค้นหาของ Git คือ: **เช็คว่ามี loose ref (ไฟล์แยกใน `refs/heads/`, `refs/tags/`) อยู่ก่อนไหม ถ้ามีให้ใช้อันนั้นเป็นหลัก ถ้าไม่มีค่อยไปหาใน `packed-refs`** — เหตุผลที่ต้องมีกลไกนี้ก็เหมือนกับ packfile คือประหยัดพื้นที่และเวลาเปิดไฟล์ ในโปรเจกต์ที่มี tag เป็นพันตัว การเปิดไฟล์เป็นพัน ๆ ไฟล์แยกกันจะช้ากว่าการอ่านไฟล์เดียวมาก

### สรุปคุณสมบัติของ Ref

| คุณสมบัติ | รายละเอียด |
|---|---|
| คืออะไร | ไฟล์ text ธรรมดา เก็บ hash ของ commit (หรือ tag object) 1 บรรทัด |
| อยู่ที่ไหน | `.git/refs/heads/`, `.git/refs/tags/`, `.git/refs/remotes/` หรืออัดรวมใน `.git/packed-refs` |
| Branch | ref ที่เขยื้อนตัวเองอัตโนมัติทุกครั้งที่ commit บน branch นั้น |
| Tag (lightweight) | ref ที่ชี้ commit ตรง ๆ ไม่ขยับเอง |
| Tag (annotated) | ref ที่ชี้ไปยัง tag object (ซึ่งชี้ต่อไปยัง commit อีกที) |
| แก้ไขได้ไหม | ได้ — ต่างจาก object ตรงที่ ref เป็น "ตัวชี้ที่เปลี่ยนได้" (mutable pointer) ไม่ใช่ content-addressable |

## Step 557: HEAD คืออะไรจริง ๆ (Symbolic Ref ไม่ใช่ Hash โดยตรง)

### ทวนความเข้าใจเดิมจาก Part 03

Part 03 Step 26 เคยอธิบาย HEAD ในเชิงแนวคิดว่าเป็น "Snapshot ของ commit ล่าสุดที่ถูก commit ไปแล้ว" คราวนี้มาดูรูปแบบไฟล์จริงกัน

### เปิดดูไฟล์ `.git/HEAD` ตรง ๆ

```bash
cat .git/HEAD
```

ผลลัพธ์ปกติ (เมื่อคุณอยู่บน branch ใด ๆ):

```
ref: refs/heads/main
```

**นี่คือจุดสำคัญที่สุดของ Step นี้:** สังเกตว่าเนื้อหาไม่ใช่ hash โดยตรง แต่เป็นข้อความ `ref: refs/heads/main` — HEAD **ไม่ได้ชี้ไปยัง commit ตรง ๆ** แต่ชี้ไปยัง **ref อีกตัวหนึ่ง** (ในที่นี้คือ `refs/heads/main`) ซึ่ง ref ตัวนั้นถึงจะชี้ไปยัง commit hash อีกที

รูปแบบพิเศษแบบนี้เรียกว่า **Symbolic Ref (symref)** — คือ "ตัวชี้ที่ชี้ไปยังตัวชี้อื่นอีกที" ไม่ใช่ตัวชี้ไปยัง object โดยตรง

### ทำไมต้องออกแบบให้ HEAD เป็น Symbolic Ref

ถ้า HEAD เก็บ hash ของ commit ตรง ๆ แล้วคุณ commit ใหม่ 1 ครั้ง ระบบจะต้องอัปเดตทั้ง HEAD และ ref ของ branch พร้อมกันสองที่ ซึ่งไม่จำเป็นและเสี่ยงต่อความไม่สอดคล้องกัน การให้ HEAD ชี้ไปยัง**ชื่อ branch**แทนที่จะชี้ไปยัง hash ตรง ๆ ทำให้:

1. Git แค่อัปเดต `refs/heads/main` ที่เดียวตอน commit — HEAD ไม่ต้องแตะเลยเพราะมันแค่ "ชี้บอกว่ากำลังดู branch ไหนอยู่" เท่านั้น
2. การอ่านค่า "commit ปัจจุบัน" ทำได้โดย Git ไล่ตาม HEAD → อ่านว่าชี้ไปยัง ref ไหน → ไปอ่าน ref นั้น → ได้ hash ของ commit ปัจจุบัน (สองขั้นตอน แต่เร็วมากเพราะเป็นการอ่านไฟล์ text เล็ก ๆ)
3. คำสั่ง `git branch` ถึงรู้ได้ว่า branch ไหนคือ "branch ปัจจุบัน" (ใส่เครื่องหมาย `*` นำหน้า) เพราะแค่เทียบว่า HEAD ชี้ไปยัง ref ของ branch ไหนอยู่

### Detached HEAD: เมื่อ HEAD ชี้ไปยัง Hash ตรง ๆ

มีสถานการณ์หนึ่งที่ HEAD **ไม่ได้เป็น symbolic ref** อีกต่อไป นั่นคือสถานะที่เรียกว่า **Detached HEAD**

ลองสร้างสถานการณ์นี้ดู:

```bash
git log --oneline
# สมมติมี commit เก่าชื่อ hash 6b584e8...
git checkout 6b584e8
cat .git/HEAD
```

ผลลัพธ์ของ `cat .git/HEAD` คราวนี้จะเป็น:

```
6b584e8ece562ebffc15d38808cd6b98fc3d97e
```

**เห็นความต่างชัดเจน:** แทนที่จะเป็น `ref: refs/heads/xxx` ไฟล์ HEAD กลับมี **hash ของ commit ตรง ๆ เต็ม 40 ตัว** อยู่ในนั้นเลย นี่คือความหมายที่แท้จริงของคำว่า "detached" (หลุดออกจากกัน) — HEAD หลุดออกจากการชี้ผ่าน branch ใด ๆ แล้วไปชี้ตรงยัง commit เลย

### ทำไม Detached HEAD ถึงอันตราย

เพราะ commit ใหม่ ๆ ที่คุณสร้างขณะอยู่ใน detached HEAD **จะไม่มี branch (ref) ไหนชี้มาหามันเลย** — มันจะลอยอยู่เดี่ยว ๆ ถ้าคุณสลับไป branch อื่นโดยไม่สร้าง branch ใหม่มาเก็บไว้ก่อน commit เหล่านั้นจะกลายเป็น "commit ที่ไม่มีใครอ้างอิงถึง" (unreachable) และจะถูกเก็บกวาดทิ้งในที่สุดโดยกลไก garbage collection (`git gc`) ซึ่งจะเรียนรายละเอียดเต็มในเฟส 6 ตอนหลัง

Git เองก็รู้ว่านี่เป็นสถานะที่เสี่ยง จึงมักเตือนข้อความประมาณนี้ทุกครั้งที่เข้าสู่ detached HEAD:

```
You are in 'detached HEAD' state...
If you want to create a new branch to retain commits you create, you may
do so (now or later) by using -c with the switch command...
```

### สรุปคุณสมบัติของ HEAD

| สถานะ | เนื้อหาไฟล์ `.git/HEAD` | ความหมาย |
|---|---|---|
| ทำงานอยู่บน branch ปกติ | `ref: refs/heads/<ชื่อ branch>` | Symbolic ref — ชี้ไปยัง ref ของ branch อีกที |
| Detached HEAD | `<commit hash เต็ม 40 ตัว>` | ชี้ตรงไปยัง commit โดยไม่ผ่าน branch ใด ๆ |

## Step 558: สำรวจ Object ด้วยตัวเองด้วย `git cat-file` และ `git hash-object`

Step นี้เป็นการแนะนำเครื่องมือ plumbing สองตัวที่ใช้ตลอดมาแบบไม่เป็นทางการ ให้เห็นภาพรวมของตัวเลือกหลัก ๆ ก่อน — **การเจาะลึกทุกฟีเจอร์ ทุก flag แบบเต็มรูปแบบ (รวมถึงคำสั่ง plumbing ตัวอื่น ๆ เช่น `git ls-tree`, `git update-ref`, `git mktree`, `git write-tree`) จะเป็นเนื้อหาทั้งหมดของ Part 57**

### `git cat-file` — เครื่องมือ "ถอดรหัส" Object

`cat-file` คือคำสั่งที่ทำหน้าที่อ่าน object จาก `.git/objects/`, ถอดการบีบอัด zlib ออก แล้วแสดงผลลัพธ์ในรูปแบบที่มนุษย์เลือกได้ ผ่าน flag หลัก 3 ตัว:

| Flag | ทำอะไร | ตัวอย่าง |
|---|---|---|
| `-t` | บอก**ประเภท** (type) ของ object | `git cat-file -t 6b584e8` → `blob` |
| `-s` | บอก**ขนาด** (size) ของเนื้อหา object เป็นไบต์ (ไม่รวม header) | `git cat-file -s 6b584e8` → `21` |
| `-p` | **Pretty-print** — แสดงเนื้อหาแบบอ่านง่ายตามประเภทของ object นั้น | `git cat-file -p 6b584e8` → เนื้อหาไฟล์จริง |

ลองไล่ทั้งสามคำสั่งกับ hash เดียวกัน:

```bash
git cat-file -t 6b584e8ece562ebffc15d38808cd6b98fc3d97e
# blob

git cat-file -s 6b584e8ece562ebffc15d38808cd6b98fc3d97e
# 21

git cat-file -p 6b584e8ece562ebffc15d38808cd6b98fc3d97e
# Hello Git Internals
```

**เทคนิคที่มีประโยชน์มาก:** ไม่จำเป็นต้องพิมพ์ hash เต็ม 40 ตัวอักษรเสมอไป — ถ้า hash เริ่มต้นไม่กี่ตัวแรก (โดยทั่วไป 7 ตัวก็เพียงพอในโปรเจกต์ขนาดปกติ) ไม่ซ้ำกับ object อื่นเลย Git จะรู้ได้เองว่าคุณหมายถึง object ไหน (นี่คือเหตุผลที่ `git log --oneline` แสดง hash แค่ 7 ตัวเสมอ)

### `git hash-object` — คำนวณ Hash (และเขียน Blob ได้)

`hash-object` ทำหน้าที่ตรงข้ามในบางแง่ — รับไฟล์เข้าไป แล้วคำนวณว่า **ถ้า Git จะเก็บไฟล์นี้เป็น blob มันจะได้ hash อะไร** โดยที่ **ค่าเริ่มต้นจะไม่เขียนอะไรลงดิสก์เลย** (แค่คำนวณโชว์)

| คำสั่ง | ทำอะไร |
|---|---|
| `git hash-object <ไฟล์>` | คำนวณ hash ของไฟล์ พิมพ์ออกมา แต่ไม่เขียนลง object database |
| `git hash-object -w <ไฟล์>` | คำนวณ hash **และเขียน** blob object นั้นลง `.git/objects/` จริง ๆ (`-w` ย่อมาจาก write) |
| `git hash-object --stdin` | อ่านเนื้อหาจาก standard input แทนที่จะอ่านจากไฟล์ ใช้คู่กับ pipe เช่น `echo "test" \| git hash-object --stdin` |

ตัวอย่างที่แสดงให้เห็นว่า `git add` ภายในไปเรียกกลไกเดียวกันนี้เอง:

```bash
echo "ทดลอง hash-object" > test.txt
git hash-object test.txt
# ได้ hash เช่น a3f5c8e...

git hash-object -w test.txt
# เขียน blob object นี้ลง .git/objects/ จริง ๆ ทันที (แม้ยังไม่ได้ git add เลยด้วยซ้ำ!)

find .git/objects -type f | grep a3f5c8
# เจอไฟล์ object ที่เพิ่งสร้าง
```

ข้อสังเกตสำคัญ: **`git hash-object -w` สร้าง blob object ได้โดยไม่ต้องผ่าน staging area หรือ commit เลย** — นี่พิสูจน์ชัดเจนว่า object database ของ Git (`.git/objects/`) เป็นระบบที่ **แยกอิสระจาก concept ของ commit/branch โดยสิ้นเชิง** มันเป็นแค่ที่เก็บข้อมูลแบบ content-addressable เฉย ๆ ส่วนกลไกอย่าง staging area, branch, HEAD คือ "ชั้นที่สร้างขึ้นมาครอบ" object database นี้อีกที เพื่อให้มนุษย์ใช้งานได้สะดวกขึ้น

### ตัวอย่างเชื่อมโยง: ยืนยันว่า `git show` กับ `git cat-file -p` ให้ข้อมูลตรงกัน

```bash
git show --no-patch --format="tree:%T%nparent:%P%nauthor:%an <%ae>%nmessage:%s" HEAD
git cat-file -p HEAD
```

ทั้งสองคำสั่งควรให้ข้อมูล tree hash, parent hash, ผู้เขียน และข้อความ commit ที่**ตรงกันเป๊ะ** เพียงแค่แสดงผลคนละรูปแบบ — `git show` คือ porcelain command ที่จัดรูปแบบให้อ่านง่าย ส่วน `git cat-file -p` คือการมองเห็น "ข้อมูลดิบจริง" ที่อยู่เบื้องหลัง

> **ต่อยอดใน Part 57:** เราจะกลับมาเจาะลึกคำสั่งกลุ่มนี้อีกครั้งพร้อมคำสั่งเพิ่มเติมอย่าง `git ls-tree` (แสดง tree แบบมีตัวเลือกจัดรูปแบบ), `git rev-parse` (แปลง reference ทุกชนิดเป็น hash), `git update-ref` (แก้ ref ด้วยมืออย่างปลอดภัยแทนการแก้ไฟล์ตรง ๆ), และ `git write-tree`/`git commit-tree` (สร้าง object เองตั้งแต่ต้นโดยไม่ผ่าน `git commit` เลย)

## Step 559: ไดอะแกรมความสัมพันธ์ทั้งหมด — Ref → Commit → Tree → Blob

ตอนนี้คุณรู้จักทุกชิ้นส่วนแยกกันแล้ว มาประกอบมันเข้าด้วยกันเป็นภาพเดียวที่ครบวงจร

### ภาพรวมเต็มระบบ

```
                         .git/HEAD
                    "ref: refs/heads/main"
                              │
                              │ (symbolic ref ชี้ไปยัง ref อีกที)
                              ▼
                  .git/refs/heads/main
              "9d8f2a1c3e5b7d9f1a3c5e7b9d1f3a5c7e9b1d3f"
                              │
                              │ (ref ชี้ไปยัง commit hash)
                              ▼
        ┌─────────────────────────────────────────────┐
        │  Commit  9d8f2a1c...                         │
        │  tree:      3f5b9d2a... ───────────────┐     │
        │  parent:    6b584e8e... ──────┐        │     │
        │  author:    Somchai ...       │        │     │
        │  committer: Somchai ...       │        │     │
        │  message:   "แก้ไขเพิ่มเติม"     │        │     │
        └────────────────────────────────┼────────┼─────┘
                                          │        │
                          ย้อนกลับไปหา     │        │ ชี้ไปยัง
                          commit ก่อนหน้า │        │ tree ของ commit นี้
                                          ▼        ▼
        ┌───────────────────────────┐   ┌─────────────────────────────┐
        │ Commit  6b584e8e... (parent)│   │  Tree  3f5b9d2a...            │
        │ tree:   ...                 │   │  100644 blob 6b58... hello.txt│
        │ parent: (ไม่มี — root commit) │   │  040000 tree 8a2f... src       │
        │ message: "commit แรก..."     │   └──────────┬──────────────────┘
        └───────────────────────────┘              │
                                                     │ โฟลเดอร์ src/
                                                     ▼
                                    ┌─────────────────────────────────┐
                                    │  Tree  8a2f...  (src/)             │
                                    │  100644 blob c4d1... app.js         │
                                    └──────────┬──────────────────────┘
                                               │
                                               ▼
                                 ┌───────────────────────────┐
                                 │  Blob  c4d1...              │
                                 │  "console.log('hi')"        │
                                 └───────────────────────────┘
```

### อ่านไดอะแกรมนี้เป็นเรื่องราว

ไล่จากบนลงล่าง นี่คือสิ่งที่เกิดขึ้นทุกครั้งที่มีคนรัน `git checkout main` แล้วเปิดไฟล์ `src/app.js` ขึ้นมาดู (แม้จะไม่รู้ตัวก็ตาม):

1. Git เปิด `.git/HEAD` → เจอว่าเป็น symbolic ref ชี้ไปยัง `refs/heads/main`
2. Git เปิด `.git/refs/heads/main` → เจอ commit hash `9d8f2a1c...`
3. Git อ่าน commit object นั้น → เจอว่า tree ของมันคือ `3f5b9d2a...`
4. Git อ่าน tree `3f5b9d2a...` (root) → เจอ entry ชื่อ `src` ชี้ไปยัง tree `8a2f...`
5. Git อ่าน tree `8a2f...` (โฟลเดอร์ `src/`) → เจอ entry ชื่อ `app.js` ชี้ไปยัง blob `c4d1...`
6. Git อ่าน blob `c4d1...` → ได้เนื้อหาไฟล์จริง เอาไปวางลง Working Directory ให้คุณเห็น

และเมื่อไล่จากซ้ายไปขวาในแนวนอน (เส้น `parent`): commit ทุกอันชี้ย้อนกลับไปหา commit ก่อนหน้าเสมอ ต่อกันเป็นสายโซ่ยาวไปจนถึง **root commit** ที่ไม่มี parent — นี่คือสิ่งที่ `git log` เดินไล่ตามเพื่อแสดงประวัติทั้งหมดของโปรเจกต์

### สองทิศทางของกราฟที่ต้องแยกให้ออก

จุดที่ช่วยให้เข้าใจ Git แบบไม่งงอีกต่อไปคือการสังเกตว่าลูกศรในระบบนี้ชี้ **2 ทิศทางที่ไม่เหมือนกันเลย**:

| ความสัมพันธ์ | ทิศทางลูกศร | ตัวอย่าง |
|---|---|---|
| **Ref → Commit** | ชี้ไปยัง commit "ล่าสุด" ของสาย | branch, tag, HEAD |
| **Commit → Commit (parent)** | ชี้ **ย้อนอดีต** เสมอ | commit ใหม่รู้จัก parent แต่ parent ไม่รู้จัก "ลูก" ของตัวเอง |
| **Commit → Tree** | ชี้ไปยัง snapshot ของโปรเจกต์ ณ ขณะนั้น | ทุก commit มี tree เดียว |
| **Tree → Tree/Blob** | ชี้ลงไปสู่รายละเอียดที่ลึกขึ้น | ลอกโครงสร้างโฟลเดอร์จริงลงมา |

ไม่มี object ใดในระบบนี้ "รู้จักผู้ที่ชี้มาหาตัวเอง" เลย — blob ไม่รู้ว่า tree ไหนชี้มาหามัน, commit ไม่รู้ว่ามี "ลูก" commit ไหนบ้าง, tree ไม่รู้ว่า commit ไหนใช้มันเป็น root — ทุกความสัมพันธ์เป็นแบบ "ทางเดียว" (one-directional) ทั้งหมด การจะไล่หา "ใครชี้มาหาฉัน" ต้องสแกนหาจาก object อื่นทั้งหมดเสมอ (ซึ่งคือสิ่งที่คำสั่งอย่าง `git log --all --source` หรือ `git branch --contains` ทำอยู่เบื้องหลัง)

## Step 560: แบบฝึกหัด — ขุด `.git` ของ Repo จริงด้วยมือ เทียบกับ `git log`/`git show`

ถึงเวลาพิสูจน์ทุกอย่างที่เรียนมาด้วยมือของคุณเองแบบครบวงจร แบบฝึกหัดนี้จะให้คุณสร้าง commit ใหม่ในโปรเจกต์ทดสอบ แล้วไล่ตามโครงสร้าง object ทั้งหมดด้วยคำสั่งดิบ ๆ จนกลับมาเจอผลลัพธ์เดียวกับที่ `git log`/`git show` แสดงให้ดู

> **ทำไมต้องสร้าง commit ใหม่ก่อน:** ตามที่บอกไว้ใน Step 552 — object เก่า ๆ ในโปรเจกต์ที่เคยถูก clone หรือรัน `git gc` มาก่อน อาจถูกอัดรวมอยู่ใน packfile แล้ว ทำให้หาไฟล์ loose object แบบ `.git/objects/xx/yyyy` ไม่เจอโดยตรง (เรื่อง packfile จะเรียนเต็มใน Part 58) การสร้าง commit ใหม่ตอนนี้จะรับประกันว่า object ที่เราจะตามหาต้องเป็น loose object แน่นอน มองเห็นเป็นไฟล์เดี่ยว ๆ ได้ทันที

cd ~/git-course/part-56-internals   # ใช้ repo ที่สร้างไว้ตั้งแต่ Step 552

### ขั้นตอนที่ 2: หา Commit Hash ล่าสุดจากทุกมุมที่เป็นไปได้

ลองหา hash เดียวกันด้วย 3 วิธีที่ต่างกัน แล้วเทียบว่าตรงกันไหม:

```bash
# วิธีที่ 1: คำสั่งระดับสูงที่คุ้นเคย
git log -1 --format="%H"

# วิธีที่ 2: คำสั่งที่แปลง reference ใด ๆ เป็น hash เต็ม
git rev-parse HEAD

# วิธีที่ 3: อ่านไฟล์ ref ตรง ๆ ด้วยมือ (ไล่ตาม HEAD เอง)
cat .git/HEAD
# จะได้ "ref: refs/heads/main" — เอาชื่อ branch จากตรงนี้ไปเปิดต่อ
cat .git/refs/heads/main
```

ทั้ง 3 วิธีต้องให้ hash เดียวกันเป๊ะ — ถ้าไม่ตรงกัน แปลว่าคุณอาจสับสน branch หรือยังไม่ได้ commit จริง ให้ตรวจสอบใหม่ก่อนไปขั้นตอนถัดไป

จดค่า hash นี้ไว้ (สมมติในตัวอย่างนี้คือ `f4a72b1c9e3d5f7a9b1c3e5f7a9b1c3e5f7a9b1c`)

### ขั้นตอนที่ 3: หา Loose Object File บนดิสก์ด้วยมือ

```bash
HASH=f4a72b1c9e3d5f7a9b1c3e5f7a9b1c3e5f7a9b1c   # แทนด้วย hash จริงของคุณ
FOLDER=${HASH:0:2}
FILENAME=${HASH:2}
ls -la .git/objects/$FOLDER/$FILENAME
```

ถ้าเจอไฟล์ แปลว่าคุณเพิ่งยืนยันด้วยมือว่ากฎ "2 ตัวแรกเป็นชื่อโฟลเดอร์ 38 ตัวที่เหลือเป็นชื่อไฟล์" จาก Step 552 เป็นจริงในทางปฏิบัติ ไม่ใช่แค่ทฤษฎี

### ขั้นตอนที่ 4: ถอดรหัส Commit Object แล้วเทียบกับ `git show`

```bash
git cat-file -p $HASH
```

เทียบกับ:

```bash
git show --no-patch --format="tree:      %T%nparent:    %P%nauthor:    %an <%ae> %at %ai%ncommitter: %cn <%ce> %ct %ci%nmessage:   %s" $HASH
```

ตรวจสอบว่า:
- tree hash ที่ `cat-file -p` แสดง **ตรงกัน** กับ `%T` จาก `git show`
- parent hash **ตรงกัน** กับ `%P`
- ชื่อ/อีเมล author และ committer **ตรงกัน**
- ข้อความ commit **ตรงกัน**

### ขั้นตอนที่ 5: ไล่ตาม Tree ไปจนถึง Blob ของไฟล์ที่เพิ่งสร้าง

```bash
# เอา tree hash จากผลลัพธ์ขั้นตอนที่ 4 มาดู root tree
git cat-file -p $HASH^{tree}
```

ควรเห็น entry ชื่อ `app.js` และ `docs` (ที่ mode `040000` เพราะเป็นโฟลเดอร์) ให้เอา hash ของ `docs` ไปดูต่อ:

```bash
git cat-file -p <hash-ของ-docs-tree>
```

ควรเห็น entry ชื่อ `notes.md` ชี้ไปยัง blob หนึ่งอัน ให้เอา hash นั้นมาดูเนื้อหา:

```bash
git cat-file -p <hash-ของ-blob-notes.md>
```

ผลลัพธ์ต้องตรงกับเนื้อหาไฟล์ `docs/notes.md` ที่คุณสร้างไว้จริง ๆ ทุกตัวอักษร ("# บันทึกการสำรวจ Git Internals")

### ขั้นตอนที่ 6: เทียบผลรวมกับ `git show <hash> --stat` และ `git ls-tree`

```bash
git show $HASH --stat
git ls-tree -r $HASH
```

`git ls-tree -r` (แสดงแบบ recursive ไล่ทุกระดับในคำสั่งเดียว) ควรแสดงรายการไฟล์ทั้งหมดพร้อม mode และ blob hash ที่**ตรงกันทุกตัว**กับสิ่งที่คุณไล่หาด้วยมือทีละขั้นในขั้นตอนที่ 5 — ถ้าตรงกันหมด แปลว่าคุณเพิ่งพิสูจน์ให้ตัวเองเห็นแล้วว่า `git ls-tree` (และคำสั่งระดับสูงทุกตัว) ไม่มีอะไรลี้ลับเลย มันแค่ทำสิ่งเดียวกับที่คุณเพิ่งทำด้วยมือ เพียงแต่ทำให้อัตโนมัติและเร็วกว่ามาก

### ขั้นตอนที่ 7 (ท้าทายเพิ่ม): ตรวจสอบ Deduplication ด้วยมือ

ลองสร้างไฟล์ใหม่ที่มีเนื้อหาซ้ำกับ `app.js` เป๊ะ ๆ ในตำแหน่งอื่น แล้วเช็คว่าได้ blob hash เดียวกันไหม:

```bash
cp app.js docs/app-copy.js
git add docs/app-copy.js
git commit -m "Step 560: ทดสอบ deduplication"
git ls-tree -r HEAD | grep app
```

ผลลัพธ์ทั้งสองบรรทัด (`app.js` และ `docs/app-copy.js`) ต้องมี **blob hash คอลัมน์เดียวกันเป๊ะ** — นี่คือการพิสูจน์ Step 553 ด้วยข้อมูลจากมือคุณเองในตอนนี้ ไม่ใช่แค่ตัวอย่างสมมติในเอกสารอีกต่อไป

### เช็คลิสต์ผลลัพธ์ที่ควรได้

- [ ] hash จาก `git log`, `git rev-parse HEAD`, และการอ่าน `.git/refs/heads/main` ตรงกันทั้ง 3 วิธี
- [ ] หาไฟล์ loose object เจอจริงที่ `.git/objects/<2 ตัวแรก>/<38 ตัวที่เหลือ>`
- [ ] เนื้อหาจาก `git cat-file -p` ของ commit ตรงกับที่ `git show` แสดง
- [ ] ไล่จาก commit → tree (root) → tree (docs/) → blob (notes.md) จนได้เนื้อหาไฟล์จริงครบทุกขั้น
- [ ] `git ls-tree -r` แสดงผลตรงกับสิ่งที่ไล่หาด้วยมือ
- [ ] พิสูจน์ deduplication ได้ว่าไฟล์เนื้อหาเหมือนกันได้ blob hash เดียวกัน

## สรุป Part 56

ใน Part นี้เราได้เจาะลึก Git Object Model จนถึงระดับไฟล์จริงบนดิสก์แล้ว สรุปสิ่งที่ได้เรียนรู้:

1. **Git คือฐานข้อมูลแบบ content-addressable** — ทุก object ถูกระบุตัวตนด้วย hash ที่คำนวณจากเนื้อหาของมันเอง ไม่ใช่จากชื่อไฟล์หรือตำแหน่งใด ๆ
2. **`.git/objects/`** เก็บ object ทุกตัวเป็น "loose object" โดยใช้ 2 ตัวอักษรแรกของ hash เป็นชื่อโฟลเดอร์ย่อย (เพื่อประสิทธิภาพของระบบไฟล์) และบีบอัดด้วย zlib ก่อนเขียนลงดิสก์เสมอ
3. **Blob** เก็บเนื้อหาไฟล์ดิบล้วน ๆ ไม่เก็บชื่อไฟล์หรือ permission — ไฟล์เนื้อหาเหมือนกันได้ blob hash เดียวกันเสมอ (พิสูจน์ได้ด้วย hash ของไฟล์ว่างที่เหมือนกันทุก repo ในโลก)
4. **Tree** แทนโฟลเดอร์หนึ่งระดับ เก็บ mode + ชื่อ + hash ของ blob/tree ลูก ซ้อนกันได้หลายชั้นตามโครงสร้างโฟลเดอร์จริง และสามารถ reuse ซ้ำได้เมื่อเนื้อหาไม่เปลี่ยน
5. **Commit** ชี้ไปยัง tree หนึ่งอันพร้อม parent (0/1/2+ อัน), author, committer และข้อความ commit — เป็นตัวเชื่อมสายโซ่ประวัติทั้งหมดของโปรเจกต์
6. **Ref** เป็นเพียงไฟล์ text ธรรมดาที่เก็บ hash หนึ่งบรรทัด — branch คือ ref ที่เขยื้อนตัวเองอัตโนมัติทุกครั้งที่ commit ส่วน tag มักตายตัว
7. **HEAD** ปกติเป็น **symbolic ref** ที่ชี้ไปยัง ref ของ branch ปัจจุบัน (`ref: refs/heads/<branch>`) ไม่ใช่ชี้ไปยัง commit hash โดยตรง ยกเว้นตอนอยู่ใน **detached HEAD** ที่จะเก็บ commit hash ตรง ๆ แทน
8. **`git cat-file`** และ **`git hash-object`** คือเครื่องมือพื้นฐานที่ใช้ถอดรหัสและสร้าง object ได้โดยตรง โดยไม่ต้องผ่าน staging area หรือ commit เลย
9. ความสัมพันธ์ทั้งระบบ (ref → commit → tree → blob) เป็นกราฟที่ลูกศรชี้ทางเดียวเสมอ ไม่มี object ใดรู้จัก "ผู้ที่ชี้มาหาตัวเอง"
10. แบบฝึกหัดในการขุด `.git` ด้วยมือพิสูจน์ให้เห็นว่าคำสั่งระดับสูงทุกตัวที่เคยใช้มาตลอดหลักสูตร ล้วนแต่เป็นการอ่าน/เขียน object พื้นฐานเหล่านี้เบื้องหลังทั้งสิ้น ไม่มีเวทมนตร์ซ่อนอยู่เลย
