## Step 651: Continuous Integration (CI) คืออะไร แก้ปัญหาอะไร

### นิยามของ Continuous Integration

**Continuous Integration (CI)** หรือ **การรวมโค้ดอย่างต่อเนื่อง** คือแนวปฏิบัติทางวิศวกรรมซอฟต์แวร์ที่นักพัฒนาในทีม **นำโค้ดของตัวเองไปรวม (integrate) เข้ากับโค้ดหลักของทีมบ่อย ๆ** (อย่างน้อยวันละครั้ง หรือบ่อยกว่านั้น) โดยทุกครั้งที่มีการรวมโค้ด ระบบจะ **build และรัน automated test ทันทีโดยอัตโนมัติ** เพื่อตรวจจับปัญหาให้เร็วที่สุดเท่าที่จะทำได้

แนวคิดนี้ถูกเสนอครั้งแรกโดย **Grady Booch** ในช่วงปลายทศวรรษ 1980 และถูกทำให้เป็นที่รู้จักอย่างกว้างขวางในวงการ Extreme Programming (XP) โดย **Kent Beck** และ **Martin Fowler** ในช่วงปลายทศวรรษ 1990 ถึงต้นทศวรรษ 2000

หัวใจของ CI ไม่ได้อยู่ที่ "มีเครื่องมือรัน test อัตโนมัติ" เพียงอย่างเดียว แต่อยู่ที่ **วินัยของทีม** ที่ต้อง:

1. Commit และ push โค้ดเข้าสู่ branch หลัก (หรือ integration branch) **บ่อย ๆ**
2. มีชุด automated test ที่ครอบคลุมพอสมควร
3. เมื่อ build หรือ test ล้มเหลว **ต้องแก้ไขทันทีเป็นลำดับความสำคัญสูงสุด** ไม่ปล่อยให้ branch หลักอยู่ในสถานะพังต่อเนื่อง

### ปัญหาที่ CI แก้: "Integration Hell"

ก่อนที่แนวคิด CI จะแพร่หลาย ทีมพัฒนาซอฟต์แวร์จำนวนมากทำงานในรูปแบบที่เรียกว่า **"Big Bang Integration"** — คือแต่ละคน หรือแต่ละทีมย่อย จะแยกกันพัฒนาฟีเจอร์ของตัวเองใน branch หรือแม้แต่ใน copy ของโค้ดแยกกันเป็นเวลานาน (หลายสัปดาห์ หรือหลายเดือน) แล้วค่อยเอาโค้ดทั้งหมดมา **"รวมกันทีเดียว"** ตอนใกล้ถึงกำหนดส่งงาน

สถานการณ์นี้นำไปสู่สิ่งที่วงการเรียกกันติดปากว่า **"Integration Hell"** (นรกแห่งการรวมโค้ด) ซึ่งมีลักษณะดังนี้:

```
สัปดาห์ที่ 1-8: ทีม A, B, C, D ต่างคนต่างพัฒนาแยกกัน
                (ไม่มีใครรู้ว่าโค้ดของคนอื่นเปลี่ยนไปแค่ไหน)

สัปดาห์ที่ 9: "วันรวมโค้ด" มาถึง...

  ทีม A: merge เข้า main → conflict 47 จุด
  ทีม B: merge เข้า main → build พังเพราะ A เปลี่ยน API
  ทีม C: merge เข้า main → test ของ D พังเพราะ C เปลี่ยน database schema
  ทีม D: merge เข้า main → ทุกอย่างพังหมด ไม่รู้จะแก้จากตรงไหนก่อน

ผลลัพธ์: ใช้เวลาอีก 2-3 สัปดาห์ถัดมาแก้ปัญหาการรวมโค้ดอย่างเดียว
         ก่อนจะได้ระบบที่ build ผ่านและใช้งานได้จริง
```

ปัญหาของ Integration Hell มีสาเหตุหลักมาจาก:

1. **Merge conflict สะสม** — ยิ่งแยกกันทำงานนาน โค้ดยิ่งเบี่ยงเบนออกจากกันมาก การ merge ยิ่งซับซ้อนและเสี่ยงผิดพลาดสูงขึ้นแบบทวีคูณ ไม่ใช่แบบเชิงเส้น
2. **หาต้นตอของปัญหายาก** — เมื่อโค้ดจากหลายคนถูกรวมเข้าด้วยกันทีเดียวเป็นก้อนใหญ่ หากมีอะไรพัง แทบเป็นไปไม่ได้ที่จะรู้ทันทีว่า "การเปลี่ยนแปลงของใคร" เป็นสาเหตุ เพราะมีการเปลี่ยนแปลงหลายร้อยจุดเกิดขึ้นพร้อมกัน
3. **Feedback ช้ามาก** — นักพัฒนาที่เขียนโค้ดผิดพลาดตั้งแต่สัปดาห์ที่ 2 อาจไม่รู้ตัวจนถึงสัปดาห์ที่ 9 ซึ่งตอนนั้นเขาอาจจำรายละเอียดของโค้ดตัวเองไม่ได้แล้ว หรือแย่กว่านั้นคือลืมไปแล้วว่าทำไมถึงเขียนแบบนั้น
4. **ขวัญกำลังใจตกต่ำ** — ทีมต้องเข้า "โหมดดับไฟ" (firefighting mode) ต่อเนื่องหลายสัปดาห์ ซึ่งบั่นทอนทั้งกำลังใจและคุณภาพของ fix ที่ทำแบบเร่งรีบ
5. **Deploy ไม่ได้ตามกำหนด** — เมื่อ integration ใช้เวลานานเกินคาด กำหนดการ release ทั้งหมดก็เลื่อนออกไปเป็นลูกโซ่

### หลักการแก้ปัญหาของ CI

CI แก้ปัญหานี้ด้วยหลักการที่ตรงข้ามกันโดยสิ้นเชิง:

> **แทนที่จะรวมโค้ดก้อนใหญ่ทีเดียวตอนท้าย ให้รวมโค้ดก้อนเล็ก ๆ บ่อย ๆ ตลอดเวลา แล้วตรวจสอบทันทีทุกครั้งที่รวม**

```
วันที่ 1: Dev A commit เล็ก ๆ → CI build+test อัตโนมัติ → ผ่าน ✓
วันที่ 1: Dev B commit เล็ก ๆ → CI build+test อัตโนมัติ → ผ่าน ✓
วันที่ 2: Dev C commit เล็ก ๆ → CI build+test อัตโนมัติ → ล้มเหลว ✗
          → Dev C รู้ทันทีภายในไม่กี่นาที ว่า commit ของตัวเองมีปัญหา
          → แก้ไขทันทีขณะที่บริบทยังสดใหม่ในหัว
วันที่ 2: Dev D commit เล็ก ๆ → CI build+test อัตโนมัติ → ผ่าน ✓
...
```

ด้วยวิธีนี้ ปัญหาการรวมโค้ดจะถูกตรวจจับ **ทีละก้อนเล็ก ๆ** แทนที่จะสะสมเป็นก้อนใหญ่มหาศาล ทำให้:

- แต่ละปัญหาที่เกิดขึ้นมีขนาดเล็กและแก้ง่าย
- รู้ทันทีว่าใครเป็นคนทำให้พัง (เพราะมีแค่ commit เดียวที่เพิ่งเข้ามา)
- แก้ไขได้เร็วเพราะบริบทยังสดใหม่ในความจำของผู้เขียนโค้ด
- ไม่มี "วันรวมโค้ด" ที่น่ากลัวอีกต่อไป เพราะการรวมโค้ดเกิดขึ้นตลอดเวลาอยู่แล้ว

### ระดับของ "การตรวจสอบอัตโนมัติ" ใน CI

เมื่อพูดถึง CI ระบบอัตโนมัติที่ทำงานทุกครั้งที่มีการ push โค้ด โดยทั่วไปจะครอบคลุมอย่างน้อย:

| สิ่งที่ตรวจสอบ | ตัวอย่าง |
|---|---|
| **Build สำเร็จหรือไม่** | โค้ด compile ผ่านไหม, dependency ติดตั้งได้ครบไหม |
| **Unit Test ผ่านหรือไม่** | ทดสอบฟังก์ชัน/โมดูลย่อยแต่ละส่วนแยกกัน |
| **Integration Test ผ่านหรือไม่** | ทดสอบว่าหลายส่วนทำงานร่วมกันได้ถูกต้อง |
| **Code Style/Lint ผ่านหรือไม่** | โค้ดเป็นไปตามมาตรฐานที่ทีมกำหนดไหม |
| **Static Analysis/Security Scan** | มีช่องโหว่ความปลอดภัยที่ตรวจจับได้อัตโนมัติไหม |

CI ที่ดีต้องมี **สัญญาณที่ชัดเจนและรวดเร็ว** ว่า build นั้น "เขียว" (ผ่านทุกอย่าง) หรือ "แดง" (มีอะไรพัง) — และเมื่อ build เป็นสีแดง ทีมต้องมีวัฒนธรรมที่ให้ความสำคัญกับการแก้ไขทันที ไม่ปล่อยให้ branch หลักอยู่ในสถานะพังข้ามคืน เพราะยิ่งปล่อยไว้นาน คนอื่นที่ pull โค้ดไปทำงานต่อก็จะได้โค้ดที่พังไปด้วย ทำให้ปัญหาลุกลามเป็นวงกว้าง

## Step 652: Continuous Delivery vs Continuous Deployment ต่างกันอย่างไร

นี่คือคำถามที่แม้แต่คนที่ทำงานสาย DevOps มาสักพักก็ยังสับสนบ่อยครั้ง เพราะทั้งสองคำใช้ตัวย่อเดียวกันคือ **"CD"** แต่มีความหมายต่างกันชัดเจน

### จุดร่วมของทั้งคู่: ต่อยอดจาก CI

ทั้ง Continuous Delivery และ Continuous Deployment ต่างก็ **สร้างอยู่บนรากฐานของ CI** กล่าวคือ ทั้งคู่สมมติว่ามี CI ที่ทำงานได้ดีอยู่แล้ว (build อัตโนมัติ, test อัตโนมัติ, ได้ผลลัพธ์เร็ว) แล้วจึงขยายขอบเขตต่อไปอีกขั้นหนึ่ง คือ **ทำให้ซอฟต์แวร์พร้อม หรือถูก deploy ออกไปสู่ผู้ใช้จริงโดยอัตโนมัติเช่นกัน**

```
Continuous Integration (CI)
        │
        ▼
   [Build + Test อัตโนมัติทุกครั้งที่มีการ push]
        │
        ├──────────────────────┬──────────────────────┐
        ▼                      ▼                       
Continuous Delivery      Continuous Deployment         
(พร้อม deploy            (deploy อัตโนมัติ              
 แต่ต้องกดปุ่มเอง)         เต็มรูปแบบ ไม่ต้องกดอะไรเลย)   
```

### Continuous Delivery: พร้อมส่ง แต่ยังต้อง "กดปุ่ม" เอง

**Continuous Delivery** คือแนวปฏิบัติที่ทำให้ **ทุก commit ที่ผ่าน CI สำเร็จ อยู่ในสถานะ "พร้อม deploy สู่ production ได้ตลอดเวลา"** แต่การ deploy จริงยังคง **ต้องมีมนุษย์เป็นผู้ตัดสินใจกดปุ่ม** ว่าจะ deploy เมื่อไหร่

ลักษณะสำคัญ:

- ทุก build ที่ผ่าน pipeline จะถูก package ให้พร้อมใช้งานจริง (เช่น สร้าง artifact, Docker image ที่ผ่านการทดสอบเรียบร้อยแล้ว)
- มีขั้นตอนสุดท้ายเป็น **manual approval/manual trigger** ก่อนจะ deploy ขึ้น production จริง
- เหตุผลที่ยังต้องมีคนกดปุ่มอาจเป็นเรื่องธุรกิจ (เช่น อยากเลือกเวลา deploy ให้ตรงกับช่วงที่ผู้ใช้น้อย) เรื่อง compliance (ต้องมีการอนุมัติจากทีม QA หรือทีมความปลอดภัยก่อน) หรือความระมัดระวังขององค์กร

```yaml
# ตัวอย่างแนวคิด (pseudo-code) ของ Continuous Delivery
stages:
  - build
  - test
  - package        # ได้ artifact ที่พร้อม deploy
  - deploy_staging  # deploy อัตโนมัติขึ้น staging เพื่อทดสอบ
  - deploy_production:
      when: manual  # ★ ต้องมีคนกดปุ่มยืนยันก่อน ★
```

### Continuous Deployment: deploy อัตโนมัติเต็มรูปแบบ ไม่ต้องมีคนกด

**Continuous Deployment** เป็นขั้นที่ก้าวไปไกลกว่า Continuous Delivery อีกขั้นหนึ่ง โดย **ทุก commit ที่ผ่าน automated test ทั้งหมดสำเร็จ จะถูก deploy ขึ้น production โดยอัตโนมัติทันที โดยไม่ต้องมีใครกดปุ่มยืนยันเลย**

```yaml
# ตัวอย่างแนวคิด (pseudo-code) ของ Continuous Deployment
stages:
  - build
  - test
  - package
  - deploy_staging
  - deploy_production:
      when: automatic  # ★ deploy ทันทีถ้า test ผ่านทั้งหมด ไม่มีคนกด ★
```

นี่หมายความว่า **ทุก commit ที่ merge เข้า main อาจกลายเป็นสิ่งที่ผู้ใช้จริงเห็นภายในไม่กี่นาที** โดยไม่มีใครต้องตัดสินใจอีกครั้งหนึ่ง องค์กรที่ขึ้นชื่อว่าใช้แนวทางนี้อย่างจริงจัง เช่น Amazon, Netflix, Etsy — ซึ่งเคยมีการรายงานว่า Amazon deploy โค้ดขึ้น production เฉลี่ยทุก ๆ ไม่กี่วินาทีทั่วทั้งองค์กร

### ตารางเปรียบเทียบให้เห็นภาพชัด

| ประเด็น | Continuous Delivery | Continuous Deployment |
|---|---|---|
| ต้อง build/test อัตโนมัติผ่านก่อนไหม | ต้อง | ต้อง |
| Package/สร้าง artifact อัตโนมัติไหม | ใช่ | ใช่ |
| Deploy ขึ้น production อัตโนมัติไหม | **ไม่** — ต้องมีคนกดปุ่ม | **ใช่** — อัตโนมัติเต็มรูปแบบ |
| ต้องการความมั่นใจในชุด test มากแค่ไหน | สูง | สูงมาก (ไม่มีด่านมนุษย์คอยเช็คซ้ำ) |
| เหมาะกับองค์กรแบบไหน | ส่วนใหญ่ที่ยังต้องการจุดอนุมัติทางธุรกิจ/compliance | ทีมที่มีวัฒนธรรม test เข้มแข็งมาก และมั่นใจใน pipeline สูง |
| ความเสี่ยงถ้า test มีช่องโหว่ | จำกัดความเสียหาย เพราะมีคนตรวจก่อน deploy | ความเสียหายอาจถึงผู้ใช้จริงเร็วกว่า |

### สิ่งที่ต้องระวัง: "CD" เป็นคำที่กำกวมในบทสนทนาจริง

ในการทำงานจริง เวลาคนพูดว่า "เรามี CI/CD" หรือ "pipeline ของเรารองรับ CD" **บ่อยครั้งไม่ได้ชัดเจนว่าหมายถึง Delivery หรือ Deployment** ดังนั้นเมื่อคุยกับทีมหรือเขียนเอกสาร ควรระบุให้ชัดเจนเสมอว่ากำลังพูดถึงแบบไหน เพื่อป้องกันความเข้าใจผิดที่อาจนำไปสู่การ deploy โดยไม่ตั้งใจ หรือความคาดหวังที่ไม่ตรงกันระหว่างทีม

หลักการจำง่าย ๆ:

> **Delivery = พร้อมส่งของถึงหน้าประตูแล้ว แต่รอให้เจ้าของบ้าน (มนุษย์) เปิดประตูรับเอง**
> **Deployment = ของถูกส่งเข้าไปวางในบ้านให้เลย ไม่ต้องมีใครมาเปิดประตู**

## Step 653: CI/CD Pipeline คืออะไร มีขั้นตอนทั่วไปอะไรบ้าง

### นิยามของ Pipeline

**CI/CD Pipeline** คือ **ลำดับขั้นตอนอัตโนมัติที่ถูกกำหนดไว้ล่วงหน้า ซึ่งโค้ดต้องผ่านไปตามลำดับ ตั้งแต่ถูก commit เข้าสู่ระบบ จนกระทั่งพร้อมใช้งาน (หรือถูกใช้งานจริง) โดยผู้ใช้ปลายทาง**

คำว่า "Pipeline" (ท่อส่ง) ถูกเลือกใช้เพราะเปรียบเสมือนท่อที่โค้ดไหลผ่านไปทีละขั้น เหมือนสายการผลิตในโรงงาน — วัตถุดิบ (source code) เข้าที่ปลายด้านหนึ่ง แล้วผ่านกระบวนการหลายขั้นตอน จนออกมาเป็นสินค้าสำเร็จรูป (running application) ที่ปลายอีกด้านหนึ่ง

ในทางเทคนิค Pipeline หนึ่งชุดมักประกอบด้วย **Stages (ขั้นตอนหลัก)** และในแต่ละ Stage มี **Jobs (งานย่อย)** ที่อาจรันแบบ sequential (เรียงลำดับ) หรือ parallel (รันพร้อมกัน) ก็ได้

### ขั้นตอนทั่วไปของ Pipeline มาตรฐาน

แม้แต่ละองค์กรจะออกแบบ pipeline ของตัวเองแตกต่างกันไปตามความต้องการเฉพาะ แต่ pipeline ส่วนใหญ่ในอุตสาหกรรมมักมีโครงสร้างพื้นฐานคล้ายกัน ดังนี้:

```
┌─────────┐   ┌────────┐   ┌─────────┐   ┌────────┐   ┌────────┐
│  Build  │──▶│  Test  │──▶│ Package │──▶│ Deploy │──▶│ Monitor│
└─────────┘   └────────┘   └─────────┘   └────────┘   └────────┘
```

#### 1. Build (การสร้าง/คอมไพล์)

ขั้นตอนแรกคือการนำ source code มาแปลงให้อยู่ในรูปแบบที่รันได้จริง ตัวอย่างเช่น:

- ภาษาที่ต้อง compile (Java, C++, Go, Rust) → คอมไพล์ source code เป็น binary หรือ bytecode
- ภาษาที่ไม่ต้อง compile (Python, JavaScript, Ruby) → ขั้นตอนนี้อาจเป็นการติดตั้ง dependency (`npm install`, `pip install`), การ bundle โค้ด (webpack, esbuild) หรือ transpile (Babel, TypeScript compiler)
- หากขั้นตอนนี้ล้มเหลว (เช่น syntax error, dependency หาไม่เจอ) pipeline จะหยุดทันทีและแจ้งเตือนทีม เพราะไม่มีประโยชน์ที่จะเดินหน้าไป test โค้ดที่ยัง build ไม่ผ่าน

#### 2. Test (การทดสอบ)

เมื่อ build ผ่านแล้ว ขั้นตอนถัดไปคือรัน automated test ชุดต่าง ๆ ซึ่งมักแบ่งเป็นหลายระดับ:

- **Unit Test** — ทดสอบฟังก์ชัน/class/module เดี่ยว ๆ แยกจากส่วนอื่น รันเร็วที่สุด ควรมีจำนวนมากที่สุด
- **Integration Test** — ทดสอบว่าหลายโมดูลทำงานร่วมกันถูกต้อง เช่น เชื่อมต่อกับฐานข้อมูลจริงได้ไหม
- **End-to-End (E2E) Test** — จำลองการใช้งานจริงของผู้ใช้ตั้งแต่ต้นจนจบ เช่นทดสอบผ่านเบราว์เซอร์อัตโนมัติ รันช้าที่สุดและมักมีจำนวนน้อยที่สุดในชุด test
- อาจรวมถึง Linting (ตรวจสอบรูปแบบโค้ด) และ Security Scanning (ตรวจหาช่องโหว่หรือ dependency ที่มีความเสี่ยง) ในขั้นตอนนี้ด้วย

#### 3. Package (การบรรจุภัณฑ์)

เมื่อโค้ดผ่านการทดสอบแล้ว ขั้นตอนนี้คือการ "บรรจุ" ซอฟต์แวร์ให้อยู่ในรูปแบบที่พร้อมนำไป deploy ตัวอย่างเช่น:

- สร้าง **Docker image** แล้ว push ขึ้น container registry
- สร้างไฟล์ **binary/executable** สำหรับแต่ละแพลตฟอร์ม
- สร้าง **package** สำหรับภาษาต่าง ๆ (เช่น `.jar` สำหรับ Java, wheel สำหรับ Python)
- สิ่งที่ได้จากขั้นตอนนี้มักถูกเรียกว่า **"Artifact"** — ผลผลิตที่จับต้องได้และพร้อมนำไปใช้ในขั้นถัดไป โดยไม่ต้อง build ซ้ำอีก

#### 4. Deploy (การนำไปใช้งานจริง)

ขั้นตอนนี้คือการนำ artifact ที่ได้ไปติดตั้งหรือรันในสภาพแวดล้อมเป้าหมาย ซึ่งมักมีหลายระดับสภาพแวดล้อม (environment) เรียงลำดับความใกล้เคียงกับ production:

```
Development → Staging (หรือ QA/Pre-production) → Production
```

- **Development** — สภาพแวดล้อมสำหรับพัฒนา ทดสอบเบื้องต้น
- **Staging** — สภาพแวดล้อมที่จำลองใกล้เคียง production มากที่สุด ใช้ทดสอบขั้นสุดท้ายก่อนปล่อยจริง
- **Production** — สภาพแวดล้อมจริงที่ผู้ใช้ปลายทางเข้าถึง

#### 5. Monitor (การเฝ้าติดตาม)

หลังจาก deploy ไปแล้ว ขั้นตอนที่มักถูกมองข้ามแต่สำคัญไม่แพ้กันคือการเฝ้าติดตามว่าระบบทำงานปกติหรือไม่ ผ่านเครื่องมือ monitoring, logging และ alerting เพื่อให้ทีมรู้ตัวทันทีหากมีปัญหาเกิดขึ้นหลัง deploy แทนที่จะรอให้ผู้ใช้มาแจ้งเอง

### Pipeline ไม่จำเป็นต้องเป็นเส้นตรงเสมอไป

ในทางปฏิบัติจริง Pipeline มักมีความซับซ้อนกว่าเส้นตรงธรรมดา เช่น:

- มีหลาย job รันแบบขนาน (parallel) ในขั้นตอนเดียวกัน เพื่อความเร็ว เช่น รัน unit test ของหลาย module พร้อมกัน
- มีเงื่อนไข (conditional) ว่า job บางตัวรันเฉพาะบาง branch เท่านั้น เช่น deploy production รันเฉพาะเมื่อ push เข้า `main`
- มี manual gate (จุดที่ต้องรอคนอนุมัติ) คั่นระหว่าง stage เช่นก่อนจะ deploy ขึ้น production (ตามที่กล่าวถึงในเรื่อง Continuous Delivery)
- มี "fan-out/fan-in" คือ job หนึ่งแตกออกเป็นหลาย job ย่อยแล้วมารวมผลกันอีกที

```
                ┌─▶ Unit Test (Module A) ─┐
Build ─────────▶├─▶ Unit Test (Module B) ─┼──▶ Package ──▶ Deploy Staging ──▶ [รออนุมัติ] ──▶ Deploy Production
                └─▶ Unit Test (Module C) ─┘
```

เราจะได้ลงมือสร้าง pipeline ที่มีโครงสร้างซับซ้อนแบบนี้จริง ๆ ทั้งใน GitHub Actions และ GitLab CI/CD ในหลาย Part ถัดจากนี้

## Step 654: ประโยชน์ของ CI/CD

หลังจากเข้าใจว่า CI/CD คืออะไรแล้ว มาดูกันว่าทำไมองค์กรซอฟต์แวร์แทบทุกแห่งในปัจจุบันถึงลงทุนกับมันอย่างจริงจัง

### 1. Feedback เร็วขึ้นอย่างมหาศาล

นี่คือประโยชน์ที่สำคัญที่สุดของ CI/CD หากไม่มีระบบอัตโนมัติ นักพัฒนาต้อง build และ test โค้ดด้วยตัวเองบนเครื่อง หรือแย่กว่านั้นคือรอให้คนอื่นมาทดสอบให้ ซึ่งอาจใช้เวลาเป็นวันหรือเป็นสัปดาห์กว่าจะรู้ว่าโค้ดที่เขียนมีปัญหา

ด้วย CI/CD นักพัฒนาจะรู้ผลลัพธ์ **ภายในไม่กี่นาทีหลังจาก push โค้ด** ยิ่งรู้เร็วเท่าไหร่ ยิ่งแก้ไขได้ง่ายเท่านั้น เพราะบริบทของโค้ดยังสดใหม่อยู่ในหัว หลักการนี้สอดคล้องกับแนวคิดที่เรียกว่า **"Shift Left"** ในวงการ DevOps — คือการเลื่อนการตรวจจับปัญหาให้เกิดขึ้นเร็วที่สุดเท่าที่จะเป็นไปได้ในวงจรการพัฒนา แทนที่จะปล่อยให้ปัญหาไปโผล่ตอนท้ายสุด

### 2. ลดความเสี่ยงจาก Human Error

การ build, test และ deploy ด้วยมือ (manual) มีจุดที่มนุษย์ผิดพลาดได้ง่ายมาก เช่น:

- ลืม run test บางชุดก่อน deploy
- Deploy ผิด environment (deploy staging build ขึ้น production โดยไม่ตั้งใจ)
- ลืมขั้นตอนสำคัญบางอย่าง เช่น migrate database ก่อน deploy โค้ดใหม่
- Config ของแต่ละ environment ไม่ตรงกัน เพราะตั้งค่าด้วยมือแยกกันคนละครั้ง

CI/CD ทำให้ทุกขั้นตอนเหล่านี้ **ถูกกำหนดไว้เป็นสคริปต์ที่แน่นอนตายตัว (deterministic)** และรันเหมือนเดิมทุกครั้ง ไม่ขึ้นกับว่าใครเป็นคนกดปุ่ม หรือกดในวันไหนเวลาไหน ลดโอกาสความผิดพลาดจากความเหนื่อยล้า ความเร่งรีบ หรือการลืมขั้นตอนของมนุษย์ไปได้มาก

### 3. Deploy ได้บ่อยขึ้นอย่างมั่นใจ

เมื่อกระบวนการ deploy ถูกทำให้เป็นอัตโนมัติและน่าเชื่อถือ ทีมจะกล้า deploy บ่อยขึ้น เพราะแต่ละครั้งที่ deploy มีความเสี่ยงต่ำลง (การเปลี่ยนแปลงแต่ละครั้งมีขนาดเล็กลง และผ่านการทดสอบอัตโนมัติมาแล้ว) สิ่งนี้นำไปสู่วงจรที่ดี:

```
Deploy บ่อยขึ้น → การเปลี่ยนแปลงแต่ละครั้งมีขนาดเล็กลง
       → หา root cause ของปัญหาได้ง่ายขึ้น (เพราะมีการเปลี่ยนแปลงน้อยจุด)
       → แก้ไขได้เร็วขึ้น → มั่นใจมากขึ้น → กล้า deploy บ่อยขึ้นไปอีก
```

งานวิจัยที่มีชื่อเสียงในวงการ DevOps อย่างรายงาน **State of DevOps Report** (จัดทำโดยทีม DORA — DevOps Research and Assessment) พบซ้ำแล้วซ้ำเล่าตลอดหลายปีว่า **ทีมที่ deploy บ่อย (high performers) มักมีอัตราความล้มเหลวหลัง deploy ต่ำกว่า และกู้คืนจากปัญหาได้เร็วกว่าทีมที่ deploy ไม่บ่อย** ซึ่งขัดกับสัญชาตญาณของหลายคนที่คิดว่า "deploy บ่อยน่าจะเสี่ยงกว่า" — ความจริงคือตรงกันข้าม

### 4. คุณภาพซอฟต์แวร์โดยรวมดีขึ้น

เมื่อทีมรู้ว่าทุก commit จะถูกทดสอบอัตโนมัติทันที มันสร้างแรงจูงใจทางอ้อมให้นักพัฒนา:

- เขียน automated test คู่กับฟีเจอร์ตั้งแต่แรก (แทนที่จะข้ามไปเพราะขี้เกียจทดสอบด้วยมือ)
- แบ่งงานเป็นก้อนเล็ก ๆ commit บ่อย ๆ (เพราะรู้ว่าจะได้ feedback เร็ว)
- กล้า refactor โค้ดมากขึ้น เพราะมี safety net จาก automated test คอยจับความผิดพลาด

### 5. ลดภาระงานที่น่าเบื่อและซ้ำซาก ของทีม

การ build, test, deploy ด้วยมือเป็นงานที่น่าเบื่อ ซ้ำซาก และมักถูกมองข้ามความสำคัญ (จนกว่าจะมีอะไรผิดพลาด) CI/CD ปลดปล่อยเวลาของนักพัฒนาให้ไปโฟกัสกับงานที่สร้างมูลค่าจริง เช่น การออกแบบระบบ การแก้ปัญหาเชิงตรรกะ แทนที่จะเสียเวลาไปกับขั้นตอนซ้ำ ๆ ที่เครื่องจักรทำได้ดีกว่ามนุษย์

### 6. เอกสารประกอบระบบที่มีชีวิต (Living Documentation)

ไฟล์ config ของ pipeline (เช่น `.gitlab-ci.yml` หรือไฟล์ workflow ของ GitHub Actions) ทำหน้าที่เป็นเอกสารบอกขั้นตอนการ build/test/deploy ของโปรเจกต์อย่างชัดเจนและเป็นปัจจุบันเสมอ (เพราะถ้าไม่ตรงกับความจริง pipeline จะรันไม่ผ่าน) ต่างจากเอกสารที่เขียนแยกไว้ต่างหากซึ่งมักล้าสมัยไม่ตรงกับของจริง

## Step 655: CI/CD กับ Workflow model ที่เรียนมาก่อนหน้า

ใน **เฟส 4 (Part 31–40)** เราได้เรียนรู้ Workflow model หลายแบบสำหรับการทำงานเป็นทีมด้วย Git ซึ่งสอง Workflow ที่สำคัญที่สุดคือ **GitHub Flow (Part 33)** และ **Trunk-Based Development (Part 34)** ทั้งสองแบบนี้มีจุดร่วมที่สำคัญมากคือ **ต่างพึ่งพา CI ที่แข็งแรงเป็นเงื่อนไขจำเป็น** ไม่ใช่แค่ "มีก็ดี" แต่เป็น "ถ้าไม่มี ก็ใช้ workflow นี้ไม่ได้จริง"

### ทบทวน GitHub Flow (Part 33)

**GitHub Flow** คือ Workflow ที่เรียบง่าย มี branch หลักเพียงเส้นเดียวคือ `main` ซึ่งต้องอยู่ในสถานะ **deployable ได้ตลอดเวลา** ทุกฟีเจอร์ใหม่ถูกพัฒนาใน feature branch อายุสั้น แล้ว merge กลับเข้า `main` ผ่าน Pull Request

จุดที่ GitHub Flow **ต้องพึ่งพา CI อย่างขาดไม่ได้** คือ:

1. ก่อน merge PR เข้า `main` ทุกครั้ง ต้องมี CI รัน automated test บน branch นั้นก่อนเสมอ เพื่อยืนยันว่าโค้ดใหม่จะไม่ทำให้ `main` พัง
2. เพราะ `main` ต้อง deployable ได้ตลอดเวลา หมายความว่า **ทุก commit ที่เข้า main ต้องผ่าน CI สำเร็จแล้วเท่านั้น** — ถ้าไม่มี CI คอยตรวจสอบอัตโนมัติ การรับประกัน "deployable เสมอ" นี้เป็นไปไม่ได้เลยในทางปฏิบัติ เพราะต้องพึ่งการตรวจสอบด้วยมือซึ่งช้าและไม่น่าเชื่อถือ
3. หลังจาก merge เข้า `main` แล้ว มักมีการ deploy อัตโนมัติทันที (Continuous Delivery/Deployment) ซึ่งเป็นส่วนขยายของ CI/CD โดยตรง

พูดง่าย ๆ คือ GitHub Flow คือ workflow ระดับ Git ในขณะที่ CI/CD คือ "เครื่องยนต์" ที่ทำให้คำสัญญาของ GitHub Flow (main พร้อม deploy เสมอ) เป็นจริงได้

### ทบทวน Trunk-Based Development (Part 34)

**Trunk-Based Development (TBD)** ยิ่งพึ่งพา CI มากกว่า GitHub Flow เสียอีก เพราะ TBD เน้นให้นักพัฒนา commit เข้า trunk (main) **บ่อยมาก** (อย่างน้อยวันละครั้ง บางทีมอาจหลายครั้งต่อวัน) และ branch มีอายุสั้นมาก (ไม่กี่ชั่วโมงถึงไม่กี่วัน)

เงื่อนไขที่ทำให้ TBD ทำงานได้จริงตามที่กล่าวถึงใน Part 34 มีอยู่ 2 ข้อหลัก คือ **CI ที่แข็งแรง** และ **Feature Flags** โดยในส่วนของ CI นั้น:

- เพราะมีคน commit เข้า trunk บ่อยมาก ถ้าไม่มี CI คอยตรวจจับปัญหาทันที trunk จะพังบ่อยมากจนทำงานต่อไม่ได้
- CI ต้อง **รันเร็ว** (fast feedback loop) เพราะถ้า CI ใช้เวลานานเกินไป (เช่น 1-2 ชั่วโมง) นักพัฒนาจะ commit เข้า trunk บ่อยไม่ได้จริงตามที่ TBD ต้องการ
- ทีมที่ใช้ TBD ระดับองค์กรใหญ่อย่าง Google หรือ Meta ที่กล่าวถึงใน Part 34 มักลงทุนมหาศาลกับโครงสร้างพื้นฐาน CI ของตัวเอง เพื่อให้ build/test ขนาดใหญ่ทำงานเสร็จได้ในเวลาไม่กี่นาที แม้จะมี codebase ขนาดมหึมา

### สรุปความเชื่อมโยง

> **Workflow model (GitHub Flow, Trunk-Based Development, Git Flow ฯลฯ) กำหนด "กติกาการจัดการ branch และการรวมโค้ด" ส่วน CI/CD คือ "เครื่องมือทางเทคนิคที่ทำให้กติกาเหล่านั้นเป็นไปได้จริงอย่างปลอดภัยและน่าเชื่อถือ"**

ถ้าไม่มี CI/CD ที่ดี Workflow แบบ GitHub Flow หรือ Trunk-Based Development จะเป็นเพียงแนวคิดในกระดาษที่ทำตามไม่ได้จริงในทางปฏิบัติ เพราะการรับประกันว่า "main พร้อม deploy เสมอ" หรือ "trunk ไม่พังแม้จะมีคน commit บ่อยมาก" ต้องอาศัยการตรวจสอบอัตโนมัติที่รวดเร็วและน่าเชื่อถือ ซึ่งคือหน้าที่โดยตรงของ CI/CD

ในทางกลับกัน หากทีมมี Workflow ที่สับสน branch มีอายุยาวนาน merge ไม่บ่อย การมี CI/CD ที่ดีเพียงอย่างเดียวก็ช่วยได้จำกัด เพราะปัญหา Integration Hell ยังคงเกิดขึ้นได้จากการที่โค้ดถูกแยกกันพัฒนานานเกินไป — CI/CD กับ Workflow model ที่ดีจึงต้องไปด้วยกันเสมอ ไม่ใช่เลือกอย่างใดอย่างหนึ่ง

## Step 656: เครื่องมือ CI/CD ยอดนิยมในตลาดปัจจุบัน

ก่อนจะเจาะลึก GitHub Actions และ GitLab CI/CD แบบเต็มรูปแบบในหลาย Part ถัดจากนี้ มาดูภาพรวมของเครื่องมือ CI/CD หลัก ๆ ที่ครองตลาดในปัจจุบันกันก่อน เพื่อให้เห็นบริบทว่าทำไมหลักสูตรนี้เลือกโฟกัสที่สองตัวนี้เป็นหลัก

### GitHub Actions

- เปิดตัวโดย GitHub ในปี 2019 (เข้าสู่สถานะพร้อมใช้งานเต็มรูปแบบ)
- ผูกแนบแน่นกับ GitHub repository — trigger จาก event บน GitHub ได้โดยตรง เช่น push, pull request, issue comment, release
- ใช้ syntax แบบ YAML เก็บไฟล์ workflow ไว้ในโฟลเดอร์ `.github/workflows/`
- มี **Marketplace** ขนาดใหญ่ที่รวม "Actions" สำเร็จรูปนับหมื่นตัวให้นำมาประกอบใน workflow ได้ทันที (เช่น action สำหรับ deploy ขึ้น AWS, ส่งข้อความ Slack)
- รันบน **GitHub-hosted runner** (เครื่องที่ GitHub เตรียมไว้ให้ฟรีในโควตาที่กำหนด) หรือ **self-hosted runner** (เครื่องของเราเอง) ก็ได้
- เหมาะมากสำหรับโปรเจกต์ที่ host อยู่บน GitHub อยู่แล้ว เพราะไม่ต้องเชื่อมต่อระบบภายนอกใด ๆ เพิ่ม

### GitLab CI/CD

- เป็นส่วนหนึ่งของ GitLab มาตั้งแต่ยุคแรก ๆ และถูกพัฒนาให้แข็งแกร่งขึ้นเรื่อย ๆ จนกลายเป็นจุดขายหลักของ GitLab ในฐานะ "DevOps Platform ครบวงจร" ตามที่กล่าวถึงใน Part 01
- ใช้ syntax แบบ YAML เช่นกัน เก็บไว้ในไฟล์ `.gitlab-ci.yml` ที่ root ของ repository (ตามที่เรียนไปแล้วใน Part 50)
- แนวคิดเรื่อง Stages/Jobs ชัดเจนและตรงไปตรงมา
- รันงานผ่าน **GitLab Runner** (ตามที่เรียนไปแล้วใน Part 51) ซึ่งอาจเป็น Shared Runner ที่ GitLab เตรียมให้ หรือ Self-hosted Runner ของทีมเองก็ได้
- มีจุดเด่นเรื่อง **Auto DevOps**, **Environments**, และการจัดการ deployment ที่ครบวงจรในตัว GitLab เอง ไม่ต้องพึ่งบริการภายนอกมาก
- เหมาะมากสำหรับองค์กรที่ใช้ GitLab เป็นหลัก โดยเฉพาะที่ต้องการ self-host ระบบทั้งหมด

### Jenkins

- เป็นหนึ่งในเครื่องมือ CI/CD ที่เก่าแก่ที่สุดในตลาด (เริ่มต้นในชื่อ Hudson ปี 2004 ก่อนเปลี่ยนชื่อเป็น Jenkins ในปี 2011) และยังคงถูกใช้งานอย่างแพร่หลายในองค์กรจำนวนมาก โดยเฉพาะองค์กรขนาดใหญ่ที่มีระบบ legacy
- เป็น **Open Source** และติดตั้ง self-hosted เองทั้งหมด (ไม่ใช่ SaaS)
- ใช้ **Groovy-based DSL** เขียน pipeline ผ่านไฟล์ `Jenkinsfile` (มีทั้งแบบ Declarative และ Scripted syntax)
- จุดเด่นคือ **Plugin ecosystem ที่ใหญ่มาก** สะสมมานานหลายสิบปี รองรับการเชื่อมต่อกับระบบแทบทุกชนิดที่มีในโลก
- ข้อเสียคือ ต้องดูแลระบบ (server, plugin, security patch) เองทั้งหมด ซึ่งใช้แรงงานดูแลรักษามากกว่าเครื่องมือแบบ SaaS อย่าง GitHub Actions/GitLab CI/CD

### CircleCI

- เป็นบริการ CI/CD แบบ SaaS ที่เน้นความเร็วและ Developer Experience ที่ดี
- ใช้ syntax แบบ YAML เก็บไว้ในไฟล์ `.circleci/config.yml`
- มีแนวคิดเรื่อง **Orbs** (ชุดคำสั่งสำเร็จรูปที่แชร์กันได้ คล้าย ๆ กับ Actions ของ GitHub) และ caching ที่ทำได้ดีมาก ช่วยให้ pipeline รันเร็ว
- รองรับการเชื่อมต่อกับหลาย VCS ไม่ได้ผูกกับเจ้าใดเจ้าหนึ่งโดยเฉพาะ (เชื่อมกับ GitHub, GitLab, Bitbucket ได้)
- นิยมในบริษัท startup และบริษัทเทคโนโลยีขนาดกลางถึงใหญ่จำนวนมาก

### เครื่องมืออื่น ๆ ที่ควรรู้จักชื่อไว้

| เครื่องมือ | จุดเด่นโดยสังเขป |
|---|---|
| **Travis CI** | หนึ่งในเครื่องมือ CI/CD SaaS รุ่นบุกเบิกที่ได้รับความนิยมมากในยุค 2013-2018 โดยเฉพาะในวงการ Open Source แต่ปัจจุบันความนิยมลดลงมาก |
| **Azure DevOps (Azure Pipelines)** | ของ Microsoft เหมาะกับองค์กรที่ใช้ระบบนิเวศ Azure/Microsoft เป็นหลัก |
| **AWS CodePipeline** | ของ Amazon Web Services เหมาะกับองค์กรที่ใช้ AWS เป็น cloud หลักอยู่แล้ว |
| **TeamCity** | ของ JetBrains เน้นตลาดองค์กร (enterprise) |
| **Argo CD** | เครื่องมือเฉพาะทางด้าน Continuous Deployment สำหรับ Kubernetes โดยเฉพาะ ใช้แนวคิด GitOps |

### ทำไมหลักสูตรนี้เลือกโฟกัส GitHub Actions และ GitLab CI/CD

หลักสูตรนี้เลือกเจาะลึกสองตัวนี้เป็นหลักด้วยเหตุผล:

1. **ครอบคลุมส่วนแบ่งตลาดมากที่สุด** — GitHub และ GitLab คือสองแพลตฟอร์มที่หลักสูตรนี้สอนมาตั้งแต่ต้น (Part 01) การมี CI/CD ในตัวแพลตฟอร์มเดียวกันทำให้เรียนรู้ได้ต่อเนื่องไม่ต้องเปิดบัญชีบริการที่สาม
2. **ไม่ต้องพึ่งพา infrastructure ภายนอกเพิ่มเติม** — ทั้งสองตัวใช้งานได้ทันทีจาก repository ที่มีอยู่แล้ว โดยไม่ต้องสมัครบริการเพิ่มหรือติดตั้ง server เอง (ต่างจาก Jenkins ที่ต้อง self-host)
3. **แนวคิดพื้นฐานถ่ายทอดข้ามเครื่องมือได้** — เมื่อเข้าใจ Pipeline as Code, Stages/Jobs, Runner/Agent อย่างลึกซึ้งแล้ว การไปเรียนรู้ Jenkins, CircleCI หรือเครื่องมือใดเพิ่มเติมในอนาคตจะทำได้เร็วมาก เพราะโครงสร้างแนวคิดคล้ายกันเกือบทั้งหมด

## Step 657: แนวคิด "Pipeline as Code"

### นิยาม

**Pipeline as Code** คือแนวคิดที่ว่า **การกำหนดค่าของ CI/CD Pipeline (ว่าจะ build อย่างไร, test อย่างไร, deploy อย่างไร) ถูกเขียนเป็นไฟล์ configuration ที่เก็บไว้ในตัว repository เดียวกันกับซอร์สโค้ด และผ่านการควบคุมด้วย Version Control เหมือนกับไฟล์โค้ดทั่วไป**

ตัวอย่างที่เป็นรูปธรรม:

- GitLab CI/CD → ไฟล์ `.gitlab-ci.yml`
- GitHub Actions → ไฟล์ YAML ในโฟลเดอร์ `.github/workflows/`
- Jenkins (แบบสมัยใหม่) → ไฟล์ `Jenkinsfile`
- CircleCI → ไฟล์ `.circleci/config.yml`

### เปรียบเทียบกับยุคก่อน Pipeline as Code

ก่อนแนวคิดนี้จะแพร่หลาย การตั้งค่า CI/CD มักทำผ่าน **หน้าเว็บ UI ของ CI server โดยตรง** (คลิกตั้งค่าผ่านหน้าจอ) เช่น Jenkins ยุคแรกที่ผู้ดูแลระบบต้องเข้าไปตั้งค่า job ผ่านหน้าเว็บทีละขั้นตอน

```
วิธีเก่า (Configuration ผ่าน UI):
┌─────────────────────────────────────┐
│ 1. เข้าเว็บ Jenkins                    │
│ 2. คลิก "New Job"                      │
│ 3. กรอกฟอร์มตั้งค่าทีละช่อง               │
│ 4. บันทึกไว้ในฐานข้อมูลของ Jenkins       │
│    (ไม่ได้อยู่ใน repository ของโปรเจกต์)  │
└─────────────────────────────────────┘

ปัญหา: ไม่มีประวัติการเปลี่ยนแปลง config, ย้อนกลับไม่ได้,
       ต้องตั้งค่าใหม่ทุกครั้งถ้าย้าย server, ไม่มีใครรู้ว่าใครเปลี่ยนอะไรเมื่อไหร่
```

```
วิธีใหม่ (Pipeline as Code):
project/
├── src/
├── tests/
└── .gitlab-ci.yml    ← config ของ pipeline อยู่ใน repo เดียวกับโค้ด

ข้อดี: เห็นประวัติการเปลี่ยนแปลงผ่าน git log, review ผ่าน Pull/Merge Request ได้,
       ย้อนกลับ (revert) ได้ทันทีถ้า pipeline ใหม่มีปัญหา,
       copy ไปใช้กับโปรเจกต์อื่นได้ง่าย
```

### ประโยชน์ของ Pipeline as Code

1. **Version Control เต็มรูปแบบ** — ทุกการเปลี่ยนแปลงของ pipeline ถูกบันทึกใน git history เหมือนโค้ดทั่วไป รู้ว่าใครแก้อะไร เมื่อไหร่ ทำไม (เชื่อมโยงกับ Step 8 ของ Part 01 เรื่องประโยชน์ของ VCS โดยตรง)
2. **Code Review ได้** — การเปลี่ยนแปลง pipeline สามารถถูกเสนอผ่าน Pull Request/Merge Request และให้ทีมรีวิวก่อน merge เหมือนโค้ดฟีเจอร์ทั่วไป ลดโอกาสที่ config ผิดพลาดจะหลุดเข้าไปโดยไม่มีใครตรวจสอบ
3. **Reproducible (ทำซ้ำได้แม่นยำ)** — เมื่อ checkout โค้ดที่ commit ใดก็ตาม จะได้ pipeline config ที่ตรงกับช่วงเวลานั้นเป๊ะ ๆ ไปด้วย ไม่มีความคลาดเคลื่อนระหว่าง "โค้ดที่มี" กับ "pipeline ที่ใช้ทดสอบโค้ดนั้น"
4. **Portable (ย้ายที่ได้ง่าย)** — เพราะทุกอย่างเป็นไฟล์ text ธรรมดา การย้าย pipeline ไปรันบน infrastructure อื่น หรือแชร์ pattern เดียวกันข้ามหลายโปรเจกต์ทำได้สะดวกกว่าการตั้งค่าผ่าน UI มาก
5. **สอดคล้องกับหลักการ "Everything as Code"** — แนวคิดนี้ไม่ได้จำกัดแค่ pipeline แต่ขยายไปถึง Infrastructure as Code (เช่น Terraform), Configuration as Code ฯลฯ ซึ่งเป็นแนวโน้มหลักของวงการ DevOps ยุคปัจจุบันทั้งหมด

### ตัวอย่างโครงสร้างไฟล์ Pipeline as Code (แนวคิดทั่วไป ไม่ผูกเครื่องมือใดเฉพาะ)

```yaml
# ตัวอย่างเชิงแนวคิด — ไม่ใช่ syntax ของเครื่องมือใดเครื่องมือหนึ่งโดยเฉพาะ
stages:
  - build
  - test
  - deploy

build_job:
  stage: build
  script:
    - echo "กำลัง build โปรเจกต์..."
    - <YOUR_BUILD_COMMAND>

test_job:
  stage: test
  script:
    - echo "กำลังรัน automated test..."
    - <YOUR_TEST_COMMAND>

deploy_job:
  stage: deploy
  script:
    - echo "กำลัง deploy..."
    - <YOUR_DEPLOY_COMMAND>
  only:
    - main
```

ไฟล์แบบนี้ถูกเก็บไว้ใน repository ตั้งแต่ commit แรกที่สร้างมันขึ้นมา และวิวัฒนาการไปพร้อมกับโปรเจกต์ตลอดอายุการใช้งาน — นี่คือหัวใจของ Pipeline as Code

## Step 658: Build server/Runner/Agent คืออะไร

### ปัญหาที่ต้องมีสิ่งเหล่านี้

ไฟล์ config อย่าง `.gitlab-ci.yml` หรือ GitHub Actions workflow เป็นเพียง **"คำสั่ง"** ว่าต้องทำอะไรบ้าง แต่คำสั่งเหล่านั้น **ต้องมีเครื่องจริง ๆ ที่รันมันจริง ๆ** — ไม่มีเครื่อง ก็ไม่มีอะไรเกิดขึ้น เปรียบเหมือนสูตรอาหารที่เขียนไว้ดีแค่ไหน ก็ต้องมีคนหรือเครื่องครัวจริง ๆ มาทำตามสูตรนั้น อาหารถึงจะเกิดขึ้นมาได้

**Build server**, **Runner**, และ **Agent** คือคำที่ใช้เรียกสิ่งเดียวกันในแก่นแท้ (อาจมีรายละเอียดปลีกย่อยต่างกันไปตามเครื่องมือ) นั่นคือ:

> **เครื่องคอมพิวเตอร์ (จริงหรือเสมือน) ที่ทำหน้าที่รับคำสั่งจาก pipeline config แล้วรันคำสั่งเหล่านั้นจริง ๆ เช่น compile โค้ด, รัน test, สร้าง Docker image, หรือ deploy ขึ้น server ปลายทาง**

### ชื่อเรียกที่ต่างกันไปตามเครื่องมือ

| เครื่องมือ | ชื่อเรียก |
|---|---|
| GitLab CI/CD | **Runner** (ตามที่เรียนไปแล้วใน Part 51) |
| GitHub Actions | **Runner** เช่นกัน (GitHub-hosted runner / self-hosted runner) |
| Jenkins | **Agent** (เดิมเรียกว่า Slave ในเวอร์ชันเก่า ก่อนเปลี่ยนคำในภายหลัง) |
| CircleCI | **Executor** |

แม้ชื่อเรียกต่างกัน แต่หน้าที่หลักเหมือนกันทั้งหมด

### ทบทวนแนวคิด GitLab Runner จาก Part 51

ใน Part 51 เราได้เรียนไปแล้วว่า GitLab Runner แบ่งเป็น 2 ประเภทหลัก:

1. **Shared Runner** — Runner ที่ GitLab.com เตรียมไว้ให้ใช้งานร่วมกันในระดับแพลตฟอร์ม (สำหรับ SaaS) ไม่ต้องติดตั้งอะไรเอง แต่มีข้อจำกัดเรื่องโควตาเวลาใช้งานฟรี
2. **Self-hosted Runner** — Runner ที่ทีมติดตั้งและดูแลเอง ให้ควบคุมสภาพแวดล้อมได้เต็มที่ เหมาะกับงานที่ต้องการ hardware เฉพาะทาง (เช่น GPU) หรือต้องเข้าถึงระบบภายในองค์กรที่ไม่เปิดสู่อินเทอร์เน็ตภายนอก

แนวคิดนี้ **ใช้ได้เหมือนกันทุกประการกับ GitHub Actions Runner** ซึ่งก็แบ่งเป็น GitHub-hosted runner (เครื่องที่ GitHub เตรียมให้) และ Self-hosted runner (เครื่องของทีมเอง) เราจะเจาะลึกความแตกต่างและวิธีตั้งค่านี้อย่างละเอียดใน Part ที่ว่าด้วย GitHub Actions โดยเฉพาะ

### หลักการทำงานทั่วไปของ Runner/Agent

```
1. Runner/Agent เชื่อมต่อ (register/poll) เข้ากับ CI/CD server (GitHub/GitLab)
   เพื่อรอรับงาน

2. เมื่อมี event เกิดขึ้น (เช่น push โค้ดเข้า branch)
   CI/CD server จะสร้าง "job" ตาม pipeline config

3. Job ถูกส่งไปให้ Runner/Agent ที่ว่างอยู่ (หรือตรงกับเงื่อนไข เช่น tag ที่กำหนด)

4. Runner/Agent รันคำสั่งตามที่ config บอกไว้ (build, test, deploy)
   ในสภาพแวดล้อมที่แยกจากกัน (มักเป็น container หรือ virtual machine ใหม่ทุกครั้ง)

5. Runner/Agent ส่งผลลัพธ์ (สำเร็จ/ล้มเหลว) พร้อม log กลับไปแสดงบน UI
```

### ทำไมเรื่องนี้สำคัญ

การเข้าใจว่า pipeline ต้องมี Runner/Agent มารันจริง ๆ ช่วยให้เข้าใจปัญหาที่พบบ่อยในการทำงานจริง เช่น:

- **"Pipeline ค้าง ไม่ยอมรัน"** — สาเหตุที่พบบ่อยที่สุดคือไม่มี Runner ที่ว่างพอจะรับงาน หรือ Runner ที่มีไม่ตรงกับ `tags` ที่ job ต้องการ (ตามที่กล่าวถึงใน Part 51)
- **"งาน build ช้ามาก"** — อาจเป็นเพราะ Runner มีสเปกไม่พอ หรือมี job จำนวนมากรอคิวอยู่ที่ Runner จำนวนจำกัด
- **"ทำไม deploy ขึ้น internal server ของบริษัทไม่ได้"** — เพราะ Shared Runner ของ GitHub/GitLab อยู่นอกเครือข่ายบริษัท เข้าไม่ถึง internal network จึงต้องใช้ Self-hosted Runner ที่อยู่ในเครือข่ายเดียวกัน

## Step 659: ต้นทุนของการไม่มี CI/CD เทียบกับการลงทุนตั้งระบบ CI/CD

### ต้นทุนที่มองไม่เห็นของการไม่มี CI/CD

หลายทีมที่ยังไม่มี CI/CD มักคิดว่า "เราไม่มีเวลาไปตั้งระบบ CI/CD หรอก งานเยอะจะแย่อยู่แล้ว" แต่ในความเป็นจริง **การไม่มี CI/CD มีต้นทุนแฝงที่สูงกว่ามาก เพียงแต่มันกระจายตัวออกไปจนมองไม่เห็นเป็นก้อนเดียวชัด ๆ**

ลองพิจารณาต้นทุนที่เกิดขึ้นจริงในทีมที่ไม่มี CI/CD:

#### 1. เวลาที่เสียไปกับการ integrate ด้วยมือ

- นักพัฒนาต้อง pull โค้ดล่าสุด, build เอง, รัน test เอง (ถ้ามี) ทุกครั้งก่อนจะมั่นใจว่าโค้ดของตัวเองใช้ได้ ซึ่งกินเวลาที่ควรใช้ไปกับการเขียนโค้ดจริง
- เมื่อถึงเวลา merge โค้ดจากหลายคน มักเกิด conflict ที่ต้องแก้ด้วยมือ และไม่มีใครแน่ใจว่าหลัง merge แล้วทุกอย่างยังทำงานถูกต้องหรือไม่ จนกว่าจะมีคนมาทดสอบด้วยมืออีกรอบ
- สมมติทีมมีนักพัฒนา 5 คน แต่ละคนเสียเวลาเฉลี่ยวันละ 30 นาทีไปกับการ build/test ด้วยมือซ้ำ ๆ นั่นคือ 2.5 ชั่วโมงต่อวันของทีมทั้งหมด หรือประมาณ 50 ชั่วโมงต่อเดือน ที่หายไปกับงานที่เครื่องจักรทำได้ดีกว่าและเร็วกว่ามนุษย์มาก

#### 2. บั๊กที่หลุดไป production

- หากไม่มี automated test ที่รันอัตโนมัติทุกครั้ง การตรวจจับบั๊กจะขึ้นอยู่กับความขยันและความละเอียดของแต่ละคน ซึ่งไม่แน่นอน
- บั๊กที่หลุดไปถึง production มีต้นทุนแก้ไขสูงกว่าบั๊กที่ถูกจับได้ตั้งแต่ตอนพัฒนาอย่างมาก งานวิจัยหลายชิ้นในวงการวิศวกรรมซอฟต์แวร์ (เช่นงานของ IBM System Sciences Institute ที่มีการอ้างอิงกันอย่างแพร่หลาย) ชี้ให้เห็นแนวโน้มว่ายิ่งพบบั๊กช้าเท่าไหร่ในวงจรพัฒนา ต้นทุนการแก้ไขยิ่งสูงขึ้นแบบทวีคูณ ไม่ใช่เชิงเส้น — บั๊กที่พบตอนพัฒนาอาจแก้ได้ในไม่กี่นาที แต่บั๊กเดียวกันที่หลุดไปถึงผู้ใช้จริง อาจต้องใช้เวลาสืบสวน แก้ไข ทดสอบ และ deploy ฉุกเฉิน กินเวลาเป็นชั่วโมงหรือเป็นวัน
- นอกจากต้นทุนด้านเวลาแล้ว บั๊กที่หลุดไป production ยังมีต้นทุนด้านความเชื่อมั่นของผู้ใช้ ชื่อเสียงขององค์กร และในบางกรณี (เช่นระบบการเงิน หรือระบบสุขภาพ) อาจมีความเสียหายทางกฎหมายหรือทางการเงินโดยตรง

#### 3. ความเครียดและ Burnout ของทีม

- ทีมที่ต้อง deploy ด้วยมือบ่อย ๆ มักเกิดความเครียดสูงในวัน deploy เพราะกลัวว่าจะพลาดขั้นตอนใดขั้นตอนหนึ่ง
- เมื่อเกิดปัญหาหลัง deploy การหาสาเหตุยากกว่ามากถ้าไม่มีระบบ log/monitoring ที่เป็นระบบ ทำให้ทีมต้องทำงานดึกดื่นเพื่อไล่หาปัญหา ซึ่งสะสมนำไปสู่ภาวะหมดไฟ (burnout) ในระยะยาว

### ต้นทุนของการลงทุนตั้งระบบ CI/CD

ในทางกลับกัน การตั้งระบบ CI/CD ก็มีต้นทุนของมันเช่นกัน ซึ่งควรพิจารณาอย่างตรงไปตรงมา ไม่ใช่มองว่า CI/CD ไม่มีต้นทุนเลย:

1. **เวลาตั้งค่าเริ่มต้น** — ต้องเขียน pipeline config, ตั้งค่า Runner/Agent, เชื่อมต่อกับระบบ deploy ปลายทาง ซึ่งอาจใช้เวลาตั้งแต่ไม่กี่ชั่วโมง (โปรเจกต์เล็ก) ไปจนถึงหลายสัปดาห์ (ระบบองค์กรขนาดใหญ่ที่ซับซ้อน)
2. **ต้นทุนการดูแลรักษาต่อเนื่อง** — pipeline ต้องถูกปรับปรุงตามการเปลี่ยนแปลงของโปรเจกต์ เช่น เพิ่ม dependency ใหม่ เปลี่ยนโครงสร้างโปรเจกต์ ก็ต้องแก้ config ตาม
3. **ต้นทุนการเขียน automated test** — CI จะมีประโยชน์จริงก็ต่อเมื่อมีชุด test ที่ครอบคลุมเพียงพอ การเขียนและดูแล test suite เป็นงานที่ต้องลงทุนอย่างต่อเนื่อง ไม่ใช่ทำครั้งเดียวจบ
4. **ต้นทุนโครงสร้างพื้นฐาน** — หากใช้ Self-hosted Runner จะมีต้นทุนค่าเครื่อง ค่าไฟ ค่าดูแลระบบเพิ่มเติม แม้จะใช้ Shared Runner ของ GitHub/GitLab ก็อาจมีค่าใช้จ่ายเมื่อใช้เกินโควตาฟรี

### การชั่งน้ำหนักที่สมเหตุสมผล

ในทางปฏิบัติ ต้นทุนการตั้งระบบ CI/CD เป็น **"ต้นทุนคงที่ (fixed cost) ที่จ่ายครั้งเดียวแล้วได้ผลตอบแทนต่อเนื่องไปตลอด"** ในขณะที่ต้นทุนของการไม่มี CI/CD เป็น **"ต้นทุนผันแปร (variable cost) ที่เพิ่มขึ้นเรื่อย ๆ ตามขนาดทีมและอายุของโปรเจกต์"**

```
ต้นทุน
  │                                    ╱ ไม่มี CI/CD (เพิ่มขึ้นเรื่อย ๆ)
  │                                  ╱
  │                                ╱
  │                              ╱
  │            ┌────────────────╱────── มี CI/CD (คงที่หลังตั้งค่าเสร็จ)
  │            │              ╱
  │  (ต้นทุน   │            ╱
  │   ตั้งค่า) │          ╱
  │            │        ╱  จุดตัด: หลังจากจุดนี้ การไม่มี CI/CD
  │            └──────╱     แพงกว่าการมี CI/CD อย่างชัดเจน
  └──────────────────────────────────────────────▶ เวลา/ขนาดทีม
```

ยิ่งทีมมีขนาดใหญ่ขึ้น โปรเจกต์มีอายุยาวนานขึ้น และมีการ deploy บ่อยขึ้นเท่าไหร่ จุดคุ้มทุนของการมี CI/CD ยิ่งมาถึงเร็วขึ้นเท่านั้น ในทางปฏิบัติ แม้แต่โปรเจกต์ส่วนตัวขนาดเล็กหรือโปรเจกต์เรียนรู้ ก็ยังได้ประโยชน์จากการมี CI/CD ตั้งแต่ต้น เพราะเครื่องมืออย่าง GitHub Actions และ GitLab CI/CD ในปัจจุบันตั้งค่าได้ง่ายมากและมีโควตาฟรีให้ใช้งานเพียงพอสำหรับการเรียนรู้และโปรเจกต์ขนาดเล็ก ทำให้ต้นทุนเริ่มต้นแทบไม่มีนัยสำคัญเมื่อเทียบกับประโยชน์ที่ได้

## Step 660: แบบฝึกหัด — วางแผน CI/CD pipeline สำหรับโปรเจกต์จำลองบนกระดาษ

Step นี้เป็นแบบฝึกหัดเชิงความคิด (ไม่ต้องเปิดคอมพิวเตอร์เขียนโค้ดจริง) เพื่อฝึกให้คุณคิดเป็นระบบก่อนจะไปลงมือเขียน pipeline จริงใน Part ถัดไป

### โจทย์สมมติ

สมมติว่าคุณกำลังพัฒนาโปรเจกต์เว็บแอปพลิเคชันชื่อ **"TaskManager"** ซึ่งมีองค์ประกอบดังนี้:

- **Backend**: เขียนด้วยภาษาโปรแกรมที่คุณถนัด ให้บริการ REST API เชื่อมต่อกับฐานข้อมูล
- **Frontend**: เว็บแอปที่เรียกใช้ API ของ Backend
- ทีมมีนักพัฒนา 4 คน ทำงานพร้อมกันในหลาย feature branch
- ทีมใช้ **GitHub Flow** เป็น Workflow model (ตามที่เรียนใน Part 33)
- โปรเจกต์มี environment แยกเป็น **staging** และ **production**
- ทีมต้องการ **Continuous Delivery** (ไม่ใช่ Continuous Deployment เต็มรูปแบบ) — คือพร้อม deploy ได้ตลอดเวลา แต่ deploy ขึ้น production ต้องมีคนกดปุ่มอนุมัติก่อนเสมอ

### สิ่งที่ต้องวางแผนบนกระดาษ (หรือไฟล์ text ธรรมดา)

ให้ลองตอบคำถามต่อไปนี้ด้วยตัวเองก่อน แล้วจึงดูแนวทางเฉลยที่ให้ไว้ด้านล่าง:

1. Pipeline นี้ควรมี **stage** อะไรบ้าง เรียงลำดับอย่างไร
2. ในแต่ละ stage ควรมี **job** อะไรบ้าง job ไหนควรรันแบบขนาน (parallel) ได้บ้าง
3. ควรมี **เงื่อนไข (condition)** อะไรบ้างที่กำหนดว่า job ไหนรันเมื่อไหร่ (เช่น รันเฉพาะ branch ไหน)
4. จุดไหนควรเป็น **manual approval** ตามที่ทีมต้องการ Continuous Delivery
5. ควรเก็บ **artifact** อะไรบ้างระหว่างทาง เพื่อไม่ต้อง build ซ้ำ

### แนวทางเฉลย (ตัวอย่างหนึ่งในหลายความเป็นไปได้ที่สมเหตุสมผล)

```
Stage 1: Lint
  ├─ job: lint_backend        (ตรวจสอบ code style ของ backend)
  └─ job: lint_frontend       (ตรวจสอบ code style ของ frontend)
  → ทั้งสอง job รันขนานกันได้ เพราะไม่ขึ้นต่อกัน

Stage 2: Build
  ├─ job: build_backend       (compile/ติดตั้ง dependency backend)
  └─ job: build_frontend      (bundle โค้ด frontend)
  → รันขนานกันได้เช่นกัน แต่ต้องรอ Stage 1 ผ่านก่อน

Stage 3: Test
  ├─ job: unit_test_backend
  ├─ job: unit_test_frontend
  └─ job: integration_test    (ทดสอบว่า backend+frontend ทำงานร่วมกันถูกต้อง
                                ต้องรอทั้ง build_backend และ build_frontend เสร็จก่อน)
  → unit test สองตัวแรกรันขนานกันได้ แต่ integration test ต้องรอทั้งคู่เสร็จก่อน

Stage 4: Package
  └─ job: package_artifact    (สร้าง Docker image ทั้ง backend และ frontend
                                เก็บเป็น artifact พร้อมนำไป deploy)
  → รันเฉพาะเมื่อ push เข้า main เท่านั้น (ไม่ต้องรันทุก feature branch)

Stage 5: Deploy Staging
  └─ job: deploy_staging      (deploy อัตโนมัติขึ้น staging ทันทีที่ package เสร็จ
                                ใช้ artifact จาก Stage 4 โดยไม่ build ซ้ำ)
  → รันอัตโนมัติ เฉพาะ branch main

Stage 6: Deploy Production
  └─ job: deploy_production   (deploy ขึ้น production)
  → ★ ตั้งเป็น manual trigger ★ ต้องมีคนกดยืนยันก่อนเสมอ
     (นี่คือจุดที่ทำให้ pipeline นี้เป็น Continuous Delivery ไม่ใช่ Continuous Deployment)
```

### เหตุผลเบื้องหลังการออกแบบนี้

- **Lint มาก่อน Build เสมอ** — เพราะการตรวจสอบ code style ทำได้เร็วมากและไม่ต้องพึ่งพา dependency ใด ๆ ถ้าโค้ดมีปัญหาเรื่อง style ควรรู้เร็วที่สุดโดยไม่ต้องเสียเวลารอ build ก่อน (หลักการ "fail fast")
- **แยก job ของ backend/frontend ให้รันขนานกัน** — เพราะทั้งสองส่วนไม่ได้ขึ้นต่อกันโดยตรงในขั้นตอน build/lint/unit test ทำให้ pipeline โดยรวมเสร็จเร็วขึ้นมาก แทนที่จะรันเรียงกันทีละอย่าง
- **Integration test ต้องรอทั้งสองส่วนเสร็จก่อน** — เพราะการทดสอบว่า backend กับ frontend ทำงานร่วมกันได้ ต้องมีทั้งสองส่วนพร้อมใช้งานก่อน
- **Package/Deploy รันเฉพาะ branch main** — สอดคล้องกับ GitHub Flow ที่ feature branch ไม่จำเป็นต้อง deploy จริง แค่ต้องผ่าน lint/build/test ก่อน merge ก็เพียงพอ
- **แยก Deploy Staging (อัตโนมัติ) กับ Deploy Production (manual)** — สะท้อนความต้องการ Continuous Delivery ของทีมตามโจทย์อย่างตรงไปตรงมา คือพร้อม deploy เสมอ แต่ให้มนุษย์เป็นคนตัดสินใจขั้นสุดท้ายก่อนถึงผู้ใช้จริง
- **สร้าง artifact ครั้งเดียวใน Stage 4 แล้วนำไปใช้ซ้ำใน Stage 5-6** — หลีกเลี่ยงการ build ซ้ำโดยไม่จำเป็น ซึ่งช่วยประหยัดเวลาและรับประกันว่าสิ่งที่ทดสอบใน staging คือสิ่งเดียวกันเป๊ะ ๆ กับที่จะ deploy ขึ้น production (ไม่มีความเสี่ยงว่า build คนละครั้งจะได้ผลลัพธ์ต่างกัน)

### ลองฝึกเพิ่มด้วยตัวเอง

หากมีเวลา ลองปรับโจทย์เพิ่มเติมเพื่อฝึกคิดต่อ:

- ถ้าทีมต้องการเปลี่ยนจาก Continuous Delivery เป็น **Continuous Deployment เต็มรูปแบบ** ต้องปรับ pipeline ตรงไหนบ้าง (คำตอบ: เอา `when: manual` ใน Stage 6 ออก ให้รันอัตโนมัติทันทีที่ Stage 5 ผ่าน — แต่ต้องมั่นใจว่าชุด test ใน Stage 3 ครอบคลุมเพียงพอจริง ๆ ก่อนตัดขั้นตอนอนุมัติของมนุษย์ออก)
- ถ้าทีมใช้ **Trunk-Based Development** แทน GitHub Flow จะต้องปรับเงื่อนไขการรันแต่ละ stage อย่างไรบ้าง (คำตอบ: CI ทั้งหมดต้องรันเร็วกว่าเดิมมาก เพราะมีคน commit เข้า trunk บ่อยกว่าเดิมมาก และอาจต้องพึ่ง Feature Flags แทนการแยก branch เพื่อซ่อนฟีเจอร์ที่ยังไม่เสร็จ)
- ถ้ามี test บางชุดที่รันช้ามาก (เช่น E2E test ใช้เวลา 20 นาที) ควรจัดวางไว้ตรงไหนของ pipeline เพื่อไม่ให้ feedback loop ของนักพัฒนาช้าเกินไป (คำตอบ: อาจแยก E2E test ออกมาเป็น stage/job ต่างหากที่รันเฉพาะตอน merge เข้า main เท่านั้น ไม่รันทุกครั้งที่ push เข้า feature branch เพื่อให้ feedback ของงานประจำวันยังคงเร็วอยู่)

การฝึกคิดแบบนี้บนกระดาษก่อนลงมือเขียนโค้ดจริง จะช่วยให้เมื่อถึงเวลาต้องเขียน `.github/workflows/*.yml` หรือ `.gitlab-ci.yml` จริง ๆ ใน Part ถัดไป คุณจะรู้อยู่แล้วว่าต้องออกแบบโครงสร้างอย่างไร เหลือแค่การแปลความคิดนี้ให้เป็น syntax ที่ถูกต้องของแต่ละเครื่องมือเท่านั้น

- [ ] ลองวางแผน pipeline สำหรับโปรเจกต์จำลองด้วยตัวเองแล้ว (แบ่ง stage, job, เงื่อนไข, จุด manual approval)

## สรุป Part 66

ใน Part นี้เราได้วางรากฐานความคิดที่สำคัญที่สุดของเฟส 7 ทั้งเฟส:

1. **Continuous Integration (CI)** คือการรวมโค้ดบ่อย ๆ พร้อม build/test อัตโนมัติทันที เพื่อแก้ปัญหา "Integration Hell" ที่เกิดจากการรวมโค้ดก้อนใหญ่ทีเดียวตอนท้าย
2. **Continuous Delivery** คือการทำให้โค้ดพร้อม deploy ได้ตลอดเวลา แต่ยังต้องมีคนกดปุ่มยืนยันก่อน deploy จริง ส่วน **Continuous Deployment** คือ deploy อัตโนมัติเต็มรูปแบบโดยไม่ต้องมีใครกดปุ่มเลย
3. **CI/CD Pipeline** มีโครงสร้างทั่วไปคือ Build → Test → Package → Deploy → Monitor ซึ่งอาจซับซ้อนกว่าเส้นตรงธรรมดาด้วยการรันขนาน เงื่อนไข และจุดอนุมัติของมนุษย์
4. ประโยชน์หลักของ CI/CD คือ feedback ที่เร็วขึ้น ลดความเสี่ยงจาก human error และทำให้ทีมกล้า deploy บ่อยขึ้นอย่างมั่นใจ ซึ่งสวนทางกับความเข้าใจผิดที่ว่า deploy บ่อยจะเสี่ยงกว่า
5. Workflow model อย่าง **GitHub Flow** (Part 33) และ **Trunk-Based Development** (Part 34) ต่างพึ่งพา CI ที่แข็งแรงเป็นเงื่อนไขจำเป็น ไม่ใช่ตัวเลือกเสริม
6. เครื่องมือ CI/CD หลักในตลาดปัจจุบันได้แก่ GitHub Actions, GitLab CI/CD, Jenkins และ CircleCI โดยหลักสูตรนี้จะเจาะลึกสองตัวแรกเป็นหลัก
7. **Pipeline as Code** คือการเก็บ config ของ pipeline ไว้ใน repository เดียวกับโค้ด ทำให้ได้ประโยชน์จาก Version Control เต็มรูปแบบ เช่นเดียวกับที่โค้ดปกติได้รับ
8. **Runner/Agent/Build server** คือเครื่องจริงที่รันคำสั่งตาม pipeline config ซึ่งเชื่อมโยงโดยตรงกับ GitLab Runner ที่เรียนไปแล้วใน Part 51
9. การไม่มี CI/CD มีต้นทุนแฝงที่สูงและเพิ่มขึ้นเรื่อย ๆ ตามขนาดทีมและอายุโปรเจกต์ ในขณะที่การลงทุนตั้งระบบ CI/CD เป็นต้นทุนคงที่ที่ให้ผลตอบแทนต่อเนื่อง

จากนี้ไปในเฟส 7 เราจะเริ่มลงมือปฏิบัติจริงกับเครื่องมือ CI/CD ทั้งสองตัว โดยเริ่มจาก GitHub Actions ก่อนใน Part ถัดไป
