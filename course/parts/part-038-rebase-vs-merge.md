## Step 371: `git rebase` คืออะไร แนวคิดพื้นฐาน

ใน Part 08 เราเรียนรู้ `git merge` ไปแล้วว่ามันคือการ "รวม" ประวัติของสอง branch เข้าด้วยกัน ใน Part นี้เราจะเรียนรู้เครื่องมืออีกตัวหนึ่งที่ทำหน้าที่คล้ายกันแต่ **มีปรัชญาแตกต่างกันโดยสิ้นเชิง** — นั่นคือ `git rebase`

### นิยามที่ต้องจำให้แม่น

> **Rebase คือการ "ย้ายจุดเริ่มต้น (base)" ของ branch หนึ่ง ไปตั้งต้นใหม่บน commit ล่าสุดของอีก branch หนึ่ง โดยการเล่นซ้ำ (replay) commit ทีละตัวขึ้นไปบนฐานใหม่นั้น**

คำว่า "base" ในที่นี้หมายถึง **จุดที่ branch ของคุณแยกออกมาจาก branch อื่น** (จุดที่ Git เรียกว่า **merge base** หรือ common ancestor) ทุก branch มีจุดแยกแบบนี้เสมอ

ลองดูตัวอย่าง: สมมติคุณมี branch `main` และสร้าง branch `feature` แยกออกมาจาก commit `C2`

```
      C1 - C2 - C3 - C4        (main)
            \
             C5 - C6           (feature)
```

- จุดที่ `feature` แยกออกมาคือ `C2` — นี่คือ **base เดิม** ของ `feature`
- ระหว่างที่คุณทำงานบน `feature` (สร้าง `C5`, `C6`) ทีมของคุณก็เดินหน้า `main` ต่อไปจนถึง `C4`

ถ้าคุณสั่ง:

```bash
git switch feature
git rebase main
```

Git จะทำสิ่งนี้:

1. หา **commit ร่วมล่าสุด (merge base)** ระหว่าง `feature` กับ `main` → คือ `C2`
2. รวบรวม commit ทั้งหมดที่อยู่บน `feature` แต่ไม่อยู่บน `main` → คือ `C5`, `C6`
3. "ย้าย" จุดเริ่มต้นของ `feature` จาก `C2` ไปเป็น `C4` (ปลายสุดของ `main` ในตอนนี้)
4. เล่นซ้ำ (replay) `C5` แล้วตามด้วย `C6` ทีละตัว บนฐานใหม่คือ `C4`

ผลลัพธ์คือ:

```
      C1 - C2 - C3 - C4                 (main)
                        \
                         C5' - C6'      (feature, หลัง rebase)
```

### จุดที่สำคัญที่สุดที่ต้องเข้าใจ: commit ใหม่ไม่ใช่ commit เดิม

สังเกตว่า `C5` กลายเป็น `C5'` และ `C6` กลายเป็น `C6'` — **นี่ไม่ใช่ commit ตัวเดิมที่ถูกย้ายที่** แต่เป็น **commit ใหม่ทั้งหมด** ที่ถูกสร้างขึ้นมาใหม่

เหตุผลเชิงเทคนิค: ใน Git object model (ซึ่งเราจะเจาะลึกใน Part 56) commit object แต่ละตัวจะเก็บ **hash ของ parent commit** ไว้เป็นส่วนหนึ่งของเนื้อหา เมื่อ Git นำ diff ของ `C5` (ที่เดิมมี parent เป็น `C2`) มา apply ซ้ำบนฐานใหม่ (`C4`) มันต้องสร้าง commit object ใหม่ที่มี parent เป็น `C4` แทน — และเพราะเนื้อหาของ commit object เปลี่ยนไป (parent hash เปลี่ยน) ค่า **SHA-1/SHA-256 hash ของ commit ก็เปลี่ยนตามไปด้วยเสมอ**

> **จำไว้ให้ขึ้นใจ: `git rebase` ไม่ได้ "ย้าย" commit เดิม แต่ "สร้าง commit ใหม่" ที่มีเนื้อหา diff เหมือนเดิม แต่มี hash ใหม่ทั้งหมด** — commit เดิม (`C5`, `C6`) ยังคงอยู่ใน object database ของ Git จนกว่าจะถูกเก็บกวาดโดย garbage collection แต่ branch `feature` จะไม่ชี้ไปหามันอีกต่อไป

นี่คือความจริงที่จะอธิบายทุกอย่างที่เหลือใน Part นี้ ทั้งเรื่องกฎทอง เรื่อง conflict และเรื่องความปลอดภัย

### ทำไมถึงเรียกว่า "Rebase"

ชื่อ "Rebase" มาจากคำว่า **Re-base** = ตั้ง**ฐาน**ใหม่ ตรงตัวเลย — คุณกำลังเปลี่ยนว่า branch ของคุณ "แตกออกมาจากจุดไหน" ในประวัติ จากเดิมที่แตกจาก `C2` ตอนนี้ถูกเขียนประวัติใหม่ให้เหมือนกับว่าคุณแตก branch ออกมาจาก `C4` ตั้งแต่แรก

## Step 372: Merge vs Rebase — ประวัติแบบ Non-linear กับ Linear History

นี่คือหัวใจของ Part นี้ ต้องเข้าใจให้แม่นก่อนไปต่อ

### `git merge` สร้างประวัติแบบ Non-linear (มีกิ่งก้าน)

จากสถานการณ์ตั้งต้นเดิม:

```
      C1 - C2 - C3 - C4        (main)
            \
             C5 - C6           (feature)
```

ถ้าคุณ `git switch main` แล้ว `git merge feature` (สมมติว่า merge แบบสร้าง merge commit ปกติ ไม่ fast-forward) จะได้ผลลัพธ์:

```
      C1 - C2 - C3 - C4 --------- M     (main)
            \                    /
             C5 ------------- C6
```

`M` คือ **merge commit** — commit พิเศษที่มี **parent สองตัว** พร้อมกัน (`C4` และ `C6`) ประวัติที่ได้จะมีลักษณะเป็น "เพชร" (diamond shape) เห็นได้ชัดว่าเคยมีการแตกและรวม branch เกิดขึ้น — เราเรียกลักษณะนี้ว่า **Non-linear history**

**คุณสมบัติสำคัญของ merge:**
- commit เดิมทั้งหมด (`C5`, `C6`) **ไม่ถูกแก้ไขหรือสร้างใหม่เลย** hash ของมันเหมือนเดิมทุกประการ
- มี merge commit (`M`) เป็นหลักฐานบันทึกไว้ชัดเจนว่า "การรวมงานเกิดขึ้นตอนไหน" และรวมอะไรกับอะไร
- ประวัติสะท้อน "ความเป็นจริง" ของสิ่งที่เกิดขึ้น คือมีการทำงานคู่ขนานกันจริง ๆ

### `git rebase` สร้างประวัติแบบ Linear (เส้นตรง)

ถ้าแทนที่จะ merge คุณไป rebase `feature` เข้ากับ `main` ก่อน (`git switch feature && git rebase main`) แล้วค่อย fast-forward `main` เข้าไปหา `feature`:

```
ขั้นที่ 1 - หลัง rebase feature:

      C1 - C2 - C3 - C4                 (main)
                        \
                         C5' - C6'      (feature)

ขั้นที่ 2 - git switch main && git merge feature (แบบ fast-forward):

      C1 - C2 - C3 - C4 - C5' - C6'    (main, feature ก็ชี้จุดเดียวกัน)
```

เพราะตอนนี้ `feature` มี `main` (`C4`) เป็น ancestor โดยตรงอยู่แล้ว การ merge ครั้งสุดท้ายจึงเป็นแค่ **fast-forward** (เลื่อน pointer ของ `main` ไปข้างหน้าเฉย ๆ ไม่ต้องสร้าง merge commit เลย) ผลลัพธ์สุดท้ายคือประวัติที่ **เรียงเป็นเส้นตรงเส้นเดียว** ราวกับว่าไม่เคยมีการแตก branch เกิดขึ้นมาก่อนเลย

**คุณสมบัติสำคัญของ rebase:**
- ประวัติดูสะอาด อ่านง่าย ไล่ทีละ commit จากบนลงล่างได้โดยไม่ต้องนึกภาพกิ่งก้าน
- **ไม่มีร่องรอย** ว่าเคยมีการแตก branch คู่ขนานกันมาก่อน — ประวัติถูก "เขียนใหม่" ให้ดูเหมือนพัฒนาทีละ commit บนเส้นเดียว
- commit ดั้งเดิม (`C5`, `C6`) หายไปจาก branch (แม้จะยังอยู่ใน object database ชั่วคราว) ถูกแทนที่ด้วย `C5'`, `C6'` ที่มี hash ใหม่

### ไดอะแกรมเปรียบเทียบแบบเห็นภาพชัด

```
ก่อนทำอะไรเลย:

main:     A---B---C---D
                   \
feature:            E---F


หลัง git merge feature (บน main):

main:     A---B---C---D-------M
                   \          /
feature:            E--------F


หลัง git rebase main (บน feature) แล้ว fast-forward main:

main:     A---B---C---D---E'---F'
```

### สรุปความแตกต่างในหนึ่งประโยค

> **Merge เพิ่มเข้าไปในประวัติ (additive) — ไม่แก้ไขอะไรที่มีอยู่แล้ว แต่เพิ่ม commit ใหม่เพื่อเชื่อมสองประวัติเข้าด้วยกัน ในขณะที่ Rebase เขียนประวัติใหม่ (rewrite) — สร้าง commit ทดแทนของเดิมทั้งหมดเพื่อให้ดูเหมือนพัฒนาเรียงเส้นตรงมาตลอด**

นี่คือความแตกต่างเชิงปรัชญาที่จะนำไปสู่ "กฎทอง" ใน Step 375

## Step 373: ขั้นตอน Rebase จริงทีละคำสั่ง

มาลงมือทำจริงเพื่อให้เห็นภาพ สมมติสถานการณ์: คุณกำลังพัฒนา feature branch ชื่อ `feature/login` และระหว่างนั้นเพื่อนร่วมทีมได้ push commit ใหม่เข้า `main` ไปหลายตัวแล้ว

### ขั้นตอนที่ 1: ดูสถานะปัจจุบันก่อน

```bash
git switch feature/login
git log --oneline --graph --all
```

ผลลัพธ์ตัวอย่าง:

```
* c3d4e5f (HEAD -> feature/login) เพิ่มหน้า login form
* b2c3d4e เพิ่ม validation อีเมล
| * f6e5d4c (origin/main, main) แก้บั๊ก payment
| * a1b2c3d เพิ่มฟีเจอร์ export CSV
|/
* 9f8e7d6 initial commit
```

จะเห็นว่า `feature/login` กับ `main` แยกออกจากกันที่ `9f8e7d6` และทั้งสองฝั่งเดินหน้าไปคนละทาง

### ขั้นตอนที่ 2: อัปเดตข้อมูล remote ให้ล่าสุดก่อนเสมอ

```bash
git fetch origin
```

คำสั่งนี้ดึงข้อมูลล่าสุดจาก remote มาไว้ใน `origin/main` โดย **ไม่แตะ working directory หรือ branch ปัจจุบันเลย** (ต่างจาก `git pull` ที่จะ merge/rebase ให้ทันที) เป็นนิสัยที่ดีที่ควรทำก่อน rebase เสมอ เพื่อให้แน่ใจว่าคุณกำลัง rebase กับข้อมูลล่าสุดจริง ๆ

### ขั้นตอนที่ 3: ตรวจสอบให้แน่ใจว่าอยู่บน branch ที่ถูกต้อง

```bash
git switch feature/login
```

**ข้อควรระวังสำคัญมาก:** ต้องอยู่บน branch ที่คุณต้องการ "ย้ายฐาน" (คือ `feature/login`) เสมอ ไม่ใช่อยู่บน `main` แล้วสั่ง rebase กลับ — ถ้าสลับผิด คุณจะไป rewrite ประวัติของ `main` แทน ซึ่งอันตรายมาก (ดู Step 375)

### ขั้นตอนที่ 4: สั่ง rebase

```bash
git rebase main
```

หรือถ้าต้องการ rebase กับ remote-tracking branch ล่าสุดโดยตรงหลัง fetch (ปลอดภัยกว่าเพราะไม่ต้องพึ่งว่า local `main` อัปเดตหรือยัง):

```bash
git rebase origin/main
```

Git จะแสดงผลประมาณนี้ถ้าไม่มี conflict:

```
Successfully rebased and updated refs/heads/feature/login.
```

### ขั้นตอนที่ 5: ตรวจสอบผลลัพธ์

```bash
git log --oneline --graph --all
```

```
* 7h8i9j0 (HEAD -> feature/login) เพิ่มหน้า login form
* 6g7h8i9 เพิ่ม validation อีเมล
* f6e5d4c (origin/main, main) แก้บั๊ก payment
* a1b2c3d เพิ่มฟีเจอร์ export CSV
* 9f8e7d6 initial commit
```

สังเกตว่า:
1. hash ของ commit ทั้งสองตัวเปลี่ยนไปแล้ว (`c3d4e5f` → `7h8i9j0`, `b2c3d4e` → `6g7h8i9`)
2. ประวัติเรียงเป็นเส้นตรง ไม่มีกิ่งก้านแยกอีกต่อไป
3. `feature/login` ตอนนี้ "แตกออกมาจาก" `f6e5d4c` (ปลายสุดของ main ล่าสุด) แทนที่จะเป็น `9f8e7d6` เหมือนเดิม

### ขั้นตอนที่ 6: ถ้าเคย push branch นี้ไปแล้ว ต้อง force push

เพราะ hash เปลี่ยนไปหมดแล้ว การ push แบบปกติจะถูกปฏิเสธ (non-fast-forward) คุณต้องใช้:

```bash
git push --force-with-lease origin feature/login
```

**สำคัญ:** ใช้ `--force-with-lease` แทน `--force` เสมอ เพราะ `--force-with-lease` จะตรวจสอบก่อนว่า remote branch ไม่ได้ถูกใครอัปเดตไปหลังจากที่คุณ fetch ล่าสุด ถ้ามีคนอื่น push ทับไปแล้ว มันจะปฏิเสธและเตือนคุณ แทนที่จะเขียนทับงานของคนอื่นไปแบบเงียบ ๆ เหมือน `--force` ธรรมดา

> ข้อควรจำ: การ `--force-with-lease` แบบนี้ **ทำได้เฉพาะกับ branch ส่วนตัวที่ไม่มีใครอื่นดึงไปใช้ต่อ** เช่น feature branch ของคุณคนเดียวที่กำลังพัฒนาอยู่ ไม่ใช่ `main` หรือ branch ที่ทีมใช้ร่วมกัน — เนื้อหานี้จะอธิบายลึกใน Step 375

## Step 374: การแก้ Conflict ระหว่าง Rebase ต่างจาก Merge Conflict อย่างไร

นี่คือจุดที่มือใหม่มักงงที่สุด เพราะพฤติกรรมของ conflict ระหว่าง merge กับ rebase **แตกต่างกันโดยพื้นฐาน**

### Merge Conflict: แก้ครั้งเดียวจบ

เมื่อคุณ `git merge feature` แล้วเกิด conflict Git จะรวม diff ของทุก commit ฝั่ง `feature` เข้ามาเทียบกับ `main` **ในคราวเดียว** แล้วแสดง conflict marker ในไฟล์ที่ชนกัน คุณแก้ conflict, `git add` ไฟล์ที่แก้แล้ว แล้วจบด้วย `git commit` เพียง**ครั้งเดียว** เพื่อสร้าง merge commit

```bash
git merge feature
# CONFLICT (content): Merge conflict in login.js
# แก้ conflict ในไฟล์ login.js
git add login.js
git commit          # จบใน commit เดียว
```

### Rebase Conflict: แก้ทีละ commit ตามลำดับ

เมื่อ rebase Git จะ **เล่นซ้ำ (replay) commit ทีละตัวตามลำดับเวลาเดิม** ถ้า commit ตัวที่ 1 ชนกับฐานใหม่ Git จะหยุดตรงนั้นทันทีเพื่อให้คุณแก้ **เฉพาะ conflict ของ commit ตัวนั้น** พอแก้เสร็จและสั่ง `--continue` มันจะเล่นซ้ำ commit ตัวถัดไป ซึ่ง**อาจชนอีกรอบแยกกันอย่างอิสระ** แม้จะเป็นบรรทัดใกล้เคียงกันก็ตาม

```bash
git rebase main
# CONFLICT (content): Merge conflict in login.js
# Auto-merging login.js
# error: could not apply b2c3d4e... เพิ่ม validation อีเมล

# แก้ conflict ในไฟล์ login.js (สำหรับ commit นี้เท่านั้น)
git add login.js
git rebase --continue

# ถ้า commit ถัดไปชนอีก Git จะหยุดอีกครั้ง
# CONFLICT (content): Merge conflict in login.js
# error: could not apply c3d4e5f... เพิ่มหน้า login form

# แก้ conflict รอบที่สอง (คนละรอบกับรอบแรก แม้ไฟล์เดียวกัน)
git add login.js
git rebase --continue

# ทำซ้ำแบบนี้จนกว่า commit ทั้งหมดจะถูก replay ครบ
```

### ทำไมต้องแก้หลายรอบ

เพราะ rebase คือการ **cherry-pick** commit ทีละตัวไปวางบนฐานใหม่ — แต่ละ commit มี diff ของตัวเองที่ต้อง apply แยกกัน ถ้า commit สองตัวติดกันแก้ไขบรรทัดใกล้เคียงกันในไฟล์เดียวกัน มีโอกาสสูงที่ **ทั้งสอง commit จะ conflict แยกกันคนละรอบ** แม้จะดูเหมือนเป็นปัญหาเดียวกันในสายตาคุณก็ตาม

### ตารางเปรียบเทียบพฤติกรรม Conflict

| ด้าน | Merge Conflict | Rebase Conflict |
|---|---|---|
| จำนวนรอบที่ต้องแก้ | ครั้งเดียว (รวมทุก commit) | อาจหลายรอบ (ทีละ commit ที่ชน) |
| คำสั่งจบหลังแก้ | `git commit` | `git rebase --continue` |
| ยกเลิกได้อย่างไร | `git merge --abort` | `git rebase --abort` |
| commit ที่ได้ | 1 merge commit ใหม่ | commit เดิมแต่ละตัวถูกสร้างใหม่ (hash เปลี่ยน) |
| ความซับซ้อนโดยรวม | ต่ำกว่า (จบเร็ว) | สูงกว่า (อาจต้องใช้เวลานานถ้ามีหลาย commit ชนกัน) |

### เช็คสถานะระหว่าง rebase ค้าง

ถ้าคุณลืมว่ากำลังทำอะไรอยู่ระหว่าง rebase ใช้ `git status` ได้เสมอ Git จะบอกชัดเจนว่า:

```
interactive rebase in progress; onto f6e5d4c
Last command done (1 command done):
   pick b2c3d4e เพิ่ม validation อีเมล
Next command to do (1 remaining command):
   pick c3d4e5f เพิ่มหน้า login form
You are currently rebasing branch 'feature/login' on 'f6e5d4c'.
  (fix conflicts and run "git rebase --continue")
  (use "git rebase --skip" to skip this patch)
  (use "git rebase --abort" to check out the original branch)

Unmerged paths:
  (use "git restore --staged <file>..." to unstage)
  (use "git add <file>..." to mark resolution)
	both modified:   login.js
```

Git บอกทุกอย่างให้ครบ ทั้งว่าอยู่ระหว่างขั้นตอนไหน เหลืออะไรอีก และคำสั่งที่ใช้ได้ในสถานการณ์นี้

## Step 375: กฎทองของ Rebase — ห้าม Rebase Branch ที่แชร์ให้คนอื่นแล้ว

นี่คือกฎที่สำคัญที่สุดของทั้ง Part นี้ ถ้าจำได้แค่เรื่องเดียวจาก Part 38 ต้องเป็นเรื่องนี้

### กฎทอง (The Golden Rule of Rebasing)

> **ห้าม rebase commit ที่ถูก push ออกไปยัง remote ที่คนอื่นได้ fetch/pull ไปใช้งานต่อแล้วเด็ดขาด**

พูดง่าย ๆ คือ: **rebase ได้เฉพาะประวัติที่ยังเป็น "ของส่วนตัว" คุณคนเดียวเท่านั้น** ทันทีที่ commit ถูกแชร์ออกไปให้คนอื่นเห็นและอาจเอาไปต่อยอดแล้ว ห้าม rebase มันอีก

### เหตุผลเชิงลึกว่าทำไมถึงอันตราย

ย้อนกลับไปที่ Step 371: rebase **ไม่ได้ย้าย commit เดิม แต่สร้าง commit ใหม่ที่มี hash ต่างไปโดยสิ้นเชิง** ลองดูสถานการณ์นี้:

**สถานการณ์:** คุณ push `feature/login` (มี `C5`, `C6`) ขึ้น remote แล้วเพื่อนร่วมทีมชื่อ Bob `git pull` ไปแล้ว และ Bob เริ่มสร้าง commit ของตัวเองต่อจากมัน (`C7`)

```
บนเครื่องของ Bob:

main:     A---B
                \
feature:         C5---C6---C7(Bob)
```

จากนั้นคุณ (โดยไม่รู้ว่า Bob ดึงไปแล้ว) ตัดสินใจ rebase `feature/login` ทับกับ `main` ที่อัปเดตแล้วบนเครื่องของคุณ แล้ว force push ทับ remote:

```
บนเครื่องของคุณหลัง rebase + force push:

main:     A---B---D---E
                        \
feature:                 C5'---C6'
```

ตอนนี้ remote มี `C5'`, `C6'` (คนละตัวกับ `C5`, `C6` แม้เนื้อหา diff จะเหมือนกัน) เมื่อ Bob สั่ง `git pull` อีกครั้ง Git จะเจอว่า **local `feature/login` ของ Bob กับ remote แยกออกจากกันไม่รู้เรื่อง** (diverged) เพราะ Bob มี `C5`, `C6`, `C7` แต่ remote มี `C5'`, `C6'` ที่ Git มองว่าเป็น **commit คนละตัวกันโดยสิ้นเชิง** (แม้เนื้อหาจะเหมือนเดิมทุกประการ เพราะ hash ต่างกัน)

ผลที่ตามมามีได้หลายแบบ ทุกแบบแย่ทั้งนั้น:

1. **Git ปฏิเสธการ push ของ Bob** (non-fast-forward) — Bob งงว่าทำไม push ไม่ได้ทั้งที่ตัวเองไม่ได้ทำอะไรผิด
2. **ถ้า Bob merge เพื่อแก้ปัญหา** จะได้ merge commit ที่รวมทั้ง `C5`/`C6` (ของเก่า) และ `C5'`/`C6'` (ของใหม่) เข้าด้วยกัน ทำให้ **commit ที่มีเนื้อหาเดียวกันปรากฏซ้ำสองครั้งในประวัติ** สร้างความสับสนมหาศาลเวลาดู `git log`
3. **ถ้า Bob ใช้ `pull --rebase` เพื่อแก้ปัญหา** Git อาจพยายาม replay `C7` ของ Bob ทับบนฐานใหม่ แต่บางครั้งจะพยายาม replay `C5`, `C6` เดิมของ Bob ทับไปด้วย (เพราะ Git ไม่รู้ว่ามันคือ commit เดียวกับ `C5'`, `C6'` แค่คนละ hash) เกิด conflict ที่ไม่ควรจะมีอยู่แต่แรก
4. **กรณีเลวร้ายที่สุด:** ถ้ามีคนไม่ระวังแล้ว push `C5`, `C6` (ของเก่าที่ถูก rebase ทิ้งไปแล้ว) กลับขึ้น remote ได้สำเร็จ จะเท่ากับ **ล้าง (undo) การ rebase ของคุณไปเลยโดยไม่มีใครตั้งใจ** ทำให้เกิดทั้ง `C5`/`C6` เดิม และ `C5'`/`C6'` ใหม่ปะปนกันอยู่ในประวัติถาวร

### สรุปเหตุผลเชิงแนวคิด

Rebase คือการ **"โกหกประวัติ"** ในเชิงเทคนิค (บอกว่า commit นี้แตกจากจุดนี้ ทั้งที่จริงมันแตกจากจุดอื่น) การโกหกแบบนี้ไม่มีปัญหาถ้ามีแค่คุณคนเดียวที่รู้เรื่อง เพราะคุณคือคนเดียวที่ถืออ้างอิงถึง commit เวอร์ชันเก่า แต่ **ทันทีที่มีคนอื่นเห็นและอ้างอิงถึง commit เวอร์ชันเก่าไปแล้ว การเปลี่ยนแปลงของคุณจะขัดแย้งกับความจริงที่พวกเขารับรู้ไปแล้ว** — นี่คือธรรมชาติของระบบกระจายศูนย์ (Distributed) ที่ทุกคนมีสำเนาประวัติเต็มของตัวเอง (ตามที่เรียนใน Part 01)

### วิธีจำกฎทองแบบง่าย ๆ

> **"ถ้ามีใครอื่นนอกจากคุณ pull commit นั้นไปแล้ว ห้าม rebase มันอีก"**

หรือพูดอีกแบบ:

- **Branch ส่วนตัวที่ยังไม่ push หรือ push ไปแต่ยังไม่มีใครดึงไปใช้ต่อ** → rebase ได้อย่างอิสระ
- **Branch สาธารณะที่ทีมใช้ร่วมกัน เช่น `main`, `develop`, `release/*`** → **ห้าม rebase เด็ดขาด**
- **Branch feature ของคุณที่เพื่อนร่วม pair-program ด้วยกันแล้ว pull ไปแก้ต่อ** → ต้องคุยกันในทีมก่อนเสมอ ถ้าจะ rebase ต้องแจ้งทุกคนให้รู้และทำตามขั้นตอนกู้คืนร่วมกัน

## Step 376: `git pull --rebase` เจาะลึก

ใน Part 10 เราแนะนำ `git push`/`git pull` แบบพื้นฐานไปแล้ว มาต่อยอดให้ลึกขึ้นในหัวข้อนี้

### `git pull` ปกติทำอะไรกันแน่

`git pull` คือคำสั่งลัดที่รวมสองขั้นตอนเข้าด้วยกัน:

```bash
git pull = git fetch + git merge
```

ถ้า local branch ของคุณมี commit ที่ remote ไม่มี (คุณ commit ไว้แล้วแต่ยังไม่ push) และ remote ก็มี commit ใหม่ที่คุณไม่มี (คนอื่น push มา) `git pull` แบบปกติจะสั่ง `git merge` ให้อัตโนมัติ ซึ่งจะสร้าง **merge commit** ขึ้นมาโดยไม่ถามคุณก่อน

```
local:    A---B---C(คุณ)
                \
remote:          D(เพื่อน push มา)

หลัง git pull ธรรมดา:

local:    A---B---C-------M
                \         /
remote:          D-------
```

ถ้าคุณ pull บ่อย ๆ ในสถานการณ์แบบนี้ทุกวัน ประวัติของ branch จะเต็มไปด้วย merge commit เล็ก ๆ น้อย ๆ ที่ไม่มีความหมายอะไรมากไปกว่า "sync กับ remote" — เรียกกันเล่น ๆ ว่า **"merge commit noise"**

### `git pull --rebase` ทำอะไรต่างออกไป

```bash
git pull --rebase = git fetch + git rebase
```

แทนที่จะ merge มันจะ **เอา commit ของคุณ (`C`) ไป rebase ทับบนฐานใหม่ที่ fetch มา (`D`)**

```
local:    A---B---C(คุณ)
                \
remote:          D(เพื่อน push มา)

หลัง git pull --rebase:

local:    A---B---D---C'
```

ผลลัพธ์คือประวัติเรียงเส้นตรง ไม่มี merge commit ที่ไม่จำเป็นเลย

### ทำไม `pull --rebase` ถึงไม่ขัดกับกฎทองใน Step 375

คำถามที่มักเกิดขึ้น: "นี่ก็เป็น rebase เหมือนกัน แล้วทำไมถึงปลอดภัย?"

คำตอบ: เพราะ commit ที่ถูก rebase ในกรณีนี้ (`C`) คือ **commit ที่ยังไม่เคยถูก push ไปที่ไหนเลย** มันมีอยู่แค่ในเครื่อง local ของคุณเท่านั้น ยังไม่มีใครอื่นได้เห็นหรือดึงมันไปต่อยอด ดังนั้นการเปลี่ยน hash ของมันจึง **ไม่กระทบใครเลยนอกจากตัวคุณเอง** — สอดคล้องกับกฎทองเป๊ะ ๆ

> **ข้อควรระวัง:** ถ้าคุณเคย push `C` ไปที่ remote อื่น (เช่น fork ของตัวเอง หรือ branch สำรอง) หรือแชร์ให้เพื่อนดึงไปแล้ว การ `pull --rebase` ก็จะละเมิดกฎทองเช่นเดียวกับ rebase ปกติทุกประการ กฎทองไม่ได้ยกเว้นให้กับคำสั่งนี้ มันขึ้นอยู่กับว่า **commit นั้นถูกแชร์ไปแล้วหรือยัง** ไม่ใช่ขึ้นอยู่กับว่าใช้คำสั่งไหน

### ตั้งค่าให้ `git pull` ใช้ rebase เป็นค่าเริ่มต้น

ถ้าคุณต้องการให้ `git pull` เปล่า ๆ (ไม่ต้องพิมพ์ `--rebase` ทุกครั้ง) ทำงานแบบ rebase เสมอ ตั้งค่าได้ดังนี้:

```bash
# ตั้งเฉพาะ repository ปัจจุบัน
git config pull.rebase true

# ตั้งเป็นค่า default สำหรับทุก repository ในเครื่อง
git config --global pull.rebase true
```

หลังตั้งค่านี้แล้ว `git pull` จะเทียบเท่ากับ `git pull --rebase` โดยอัตโนมัติทุกครั้ง

### ค่าที่ตั้งให้ `pull.rebase` ได้ทั้งหมด

| ค่า | พฤติกรรม |
|---|---|
| `false` (ค่า default ของ Git) | `git pull` = fetch + merge (สร้าง merge commit ถ้าจำเป็น) |
| `true` | `git pull` = fetch + rebase (ประวัติเรียงเส้นตรง) |
| `merges` | `git pull` = fetch + rebase แบบคงรูป merge commit เดิมไว้ (เทียบเท่า `--rebase=merges`) ใช้เมื่อประวัติ local มี merge commit ที่ต้องการรักษาโครงสร้างไว้ |
| `interactive` | `git pull` = fetch + interactive rebase (เปิดหน้าจอแก้ไข todo list ให้ทุกครั้ง) |

### คำแนะนำเชิงปฏิบัติ

หลายทีมตั้งค่า `pull.rebase = true` เป็นมาตรฐานของทั้งทีม เพราะช่วยลด "merge commit noise" บน feature branch ส่วนตัวได้มาก แต่ **ยังต้องระวังกฎทองเสมอ** — ถ้า branch นั้นมีคนอื่นทำงานร่วมด้วยจริง ๆ (ไม่ใช่ branch ส่วนตัวคนเดียว) การ pull --rebase อาจ rewrite commit ของคนอื่นที่ push ร่วมกันมาแล้วโดยไม่ตั้งใจ ต้องตกลงกับทีมให้ชัดเจนก่อนตั้งค่านี้เป็น global default

## Step 377: ตารางเปรียบเทียบ Merge vs Rebase แบบละเอียด

รวบยอดทุกแง่มุมที่เรียนมาให้อยู่ในตารางเดียว เพื่อใช้เป็นตารางอ้างอิงเวลาตัดสินใจหน้างานจริง

| แง่มุม | `git merge` | `git rebase` |
|---|---|---|
| **ผลต่อรูปร่างประวัติ** | Non-linear — มีกิ่งก้านและ merge commit | Linear — เรียงเป็นเส้นตรงเส้นเดียว |
| **สร้าง commit ใหม่ไหม** | สร้างเพิ่ม 1 merge commit (ถ้าไม่ fast-forward) | สร้างใหม่ทดแทน commit เดิมทุกตัวที่ถูก replay |
| **Hash ของ commit เดิม** | ไม่เปลี่ยนแปลงเลย | เปลี่ยนทั้งหมด (commit ใหม่ทุกตัว) |
| **ความปลอดภัยกับ branch สาธารณะ** | ปลอดภัยเสมอ ใช้ได้กับทุก branch รวมถึง `main` | อันตราย ถ้าใช้กับ branch ที่แชร์ไปแล้ว (ผิดกฎทอง) |
| **ร่องรอยว่าทำงานคู่ขนานกัน** | มี merge commit บันทึกไว้ชัดเจนว่ารวมกันตอนไหน | ไม่มีร่องรอยเลย ดูเหมือนพัฒนาต่อเนื่องเส้นเดียว |
| **การแก้ conflict** | แก้ครั้งเดียวจบ (รวมทุก commit เข้าด้วยกัน) | อาจต้องแก้หลายรอบ (ทีละ commit ที่ replay ชน) |
| **คำสั่งยกเลิกระหว่างแก้ conflict** | `git merge --abort` | `git rebase --abort` |
| **ความซับซ้อนของคำสั่ง** | เข้าใจง่ายกว่า เหมาะกับมือใหม่ | ต้องเข้าใจกลไกภายในลึกกว่าถึงจะใช้ปลอดภัย |
| **ผลต่อการ push ครั้งถัดไป** | push แบบปกติได้เสมอ (fast-forward หรือสร้าง merge ธรรมดา) | ถ้า branch เคย push ไปแล้ว ต้อง force push (`--force-with-lease`) |
| **เหมาะกับสถานการณ์** | รวมงานที่ "เสร็จแล้ว" เข้า branch หลัก, ทำงานกับ branch สาธารณะ | ทำความสะอาด branch ส่วนตัวก่อนแชร์, sync กับ main ระหว่างพัฒนา |
| **การอ่าน `git log` ย้อนหลัง** | เห็นบริบทว่า feature นี้พัฒนาคู่ขนานกับอะไรตอนไหน | อ่านง่าย เรียงลำดับเดียว แต่ไม่เห็นบริบทการทำงานคู่ขนาน |
| **ความเสี่ยงต่อทีม** | ต่ำมาก แทบไม่มีทางทำลายงานคนอื่น | สูง ถ้าใช้ผิดที่ผิดเวลา อาจทำให้ประวัติของทีมสับสนถาวร |

## Step 378: เมื่อไหร่ควรใช้ Merge เมื่อไหร่ควรใช้ Rebase (Decision Guide)

หลังเข้าใจความแตกต่างแล้ว มาสรุปเป็นแนวทางตัดสินใจที่ใช้ได้จริงในงานประจำวัน

### ใช้ **Merge** เมื่อ...

1. **รวม feature branch ที่พัฒนาเสร็จแล้วเข้า `main` หรือ `develop`** — โดยเฉพาะผ่าน Pull Request บน GitHub/GitLab การ merge (หรือ squash-merge) คือมาตรฐานที่ปลอดภัยที่สุดสำหรับจุดนี้
2. **Branch ที่กำลังทำงานด้วยเป็น branch สาธารณะที่ทีมใช้ร่วมกัน** เช่น `main`, `develop`, `release/1.2` — ห้าม rebase branch เหล่านี้เด็ดขาดตามกฎทอง
3. **ต้องการเก็บบริบทว่าเกิดการรวมงานคู่ขนานกันตอนไหน** เช่น ทีม QA อยากรู้ว่า feature ไหนถูกรวมเข้า main ในรอบ sprint ไหน merge commit ช่วยตอบคำถามนี้ได้ดี
4. **ทำงานร่วมกับคนอื่นบน branch เดียวกันแบบ real-time** (pair programming, mob programming) ที่มีการ push/pull สลับกันตลอดเวลา

### ใช้ **Rebase** เมื่อ...

1. **ทำความสะอาด branch ส่วนตัวก่อนเปิด Pull Request** — จัดเรียง/รวม commit ให้อ่านง่าย (เตรียมความรู้พื้นฐานไว้ก่อนเรียน interactive rebase ใน Part 39)
2. **sync feature branch ส่วนตัวของคุณให้ทันกับ `main`** ระหว่างที่ยังพัฒนาอยู่และยังไม่ได้แชร์ให้ใครดึงไปต่อ (`git rebase main` บ่อย ๆ ระหว่างทำงาน ดีกว่าปล่อยให้ diverge ไปไกลแล้วค่อย merge ทีเดียวตอนจบซึ่งจะมี conflict มหาศาล)
3. **`git pull --rebase`** สำหรับ commit ส่วนตัวที่ยังไม่ push เพื่อหลีกเลี่ยง merge commit ที่ไม่จำเป็น
4. **ต้องการประวัติเรียงเส้นตรงสวยงามสำหรับ branch ที่จะเป็นต้นแบบอ้างอิง** เช่นเตรียม branch ไปทำ bisect หาบั๊ก (`git bisect` ทำงานได้ดีกว่ามากบนประวัติเส้นตรง)

### กฎการตัดสินใจแบบเร็ว (Quick Decision Rule)

```
ถาม 1: Branch นี้ถูก push ให้คนอื่นดึงไปใช้ต่อแล้วหรือยัง?
        ├── ใช่ → ห้าม rebase เด็ดขาด ใช้ merge เท่านั้น
        └── ไม่ → ไปถามข้อ 2

ถาม 2: ต้องการเก็บร่องรอยว่าทำงานคู่ขนานกันไว้ไหม?
        ├── ต้องการ → ใช้ merge
        └── ไม่ต้องการ (อยากได้ประวัติสะอาด) → ใช้ rebase ได้อย่างปลอดภัย
```

### รูปแบบที่หลายทีมมืออาชีพใช้จริง (Common Team Convention)

รูปแบบที่พบบ่อยที่สุดในทีมที่ใช้ GitHub/GitLab:

1. นักพัฒนาสร้าง feature branch ของตัวเอง ทำงานและ `git rebase main` เป็นระยะเพื่อไม่ให้ diverge ไกลเกินไป (branch นี้ยังเป็นของส่วนตัว จึง rebase ได้อย่างปลอดภัย)
2. ก่อนเปิด Pull Request อาจทำ interactive rebase เพื่อจัดระเบียบ commit ให้อ่านง่าย (Part 39)
3. เมื่อ Pull Request ผ่านการรีวิวแล้ว ใช้ **Merge** หรือ **Squash and Merge** ผ่านปุ่มบน GitHub เพื่อรวมเข้า `main` — จุดนี้ **ไม่ rebase `main`** เด็ดขาด

รูปแบบนี้ได้ประโยชน์ทั้งสองฝั่ง: ประวัติของ feature branch สะอาดระหว่างพัฒนา และ `main` ยังคงปลอดภัยตามกฎทองเสมอ

## Step 379: การควบคุม Rebase — `--abort`, `--continue`, `--skip`

ระหว่างทำ rebase โดยเฉพาะเมื่อเจอ conflict คุณมีคำสั่งควบคุมสถานะอยู่ 3 ตัวหลักที่ต้องรู้จักให้แม่น

### `git rebase --continue`

ใช้เมื่อคุณ**แก้ conflict ของ commit ปัจจุบันเสร็จแล้ว** และต้องการให้ Git เล่นซ้ำ commit ตัวถัดไปต่อ

```bash
# แก้ conflict ในไฟล์เสร็จแล้ว
git add <ไฟล์ที่แก้แล้ว>
git rebase --continue
```

**ข้อควรระวัง:** ต้อง `git add` ไฟล์ที่แก้ conflict ก่อนเสมอ ไม่เช่นนั้น Git จะแจ้งว่ายังมีไฟล์ที่ยัง unmerged อยู่และไม่ยอมให้ continue

หากไม่มีการเปลี่ยนแปลงเนื้อหาเลย (เช่น commit ที่ถูก replay ไม่มีอะไรต้องแก้ต่อจริง ๆ) บางครั้ง Git จะเปิด editor ให้แก้ commit message ของ commit ที่กำลัง replay — พิมพ์ข้อความแล้วบันทึกปิดได้ตามปกติ

### `git rebase --skip`

ใช้เมื่อคุณต้องการ **ข้าม commit ปัจจุบันไปเลย ไม่นำมันไปรวมกับผลลัพธ์สุดท้าย**

```bash
git rebase --skip
```

สถานการณ์ที่ใช้บ่อย: commit นั้นมีการเปลี่ยนแปลงที่ **ถูกรวมเข้าไปในฐานใหม่อยู่แล้ว** (เช่นมีคน cherry-pick การแก้ไขเดียวกันไปไว้ใน `main` ก่อนหน้านี้) ทำให้ diff ของ commit นี้ไม่เหลืออะไรให้ apply หรือขัดแย้งจนไม่มีความหมายอีกต่อไป

**ข้อควรระวังสำคัญ:** `--skip` จะ **ทิ้งการเปลี่ยนแปลงของ commit นั้นไปเลยอย่างถาวร** จากผลลัพธ์สุดท้ายของ branch ต้องมั่นใจจริง ๆ ว่าเนื้อหาของมันไม่จำเป็นแล้ว ไม่เช่นนั้นคุณจะเสียงานที่ทำไว้ไปโดยไม่ตั้งใจ

### `git rebase --abort`

ใช้เมื่อ **ต้องการยกเลิกการ rebase ทั้งหมด** และกลับไปอยู่ในสถานะเดิมทุกประการ ราวกับไม่เคยสั่ง rebase มาก่อนเลย

```bash
git rebase --abort
```

นี่คือ **ทางออกที่ปลอดภัยที่สุด** เมื่อคุณรู้สึกว่า conflict ซับซ้อนเกินไป สับสนกับสถานะปัจจุบัน หรือแก้ไปแล้วผิดพลาดจนไม่แน่ใจว่าผลลัพธ์จะถูกต้องหรือไม่ `--abort` จะคืน branch กลับไปยัง commit ตัวสุดท้ายก่อนเริ่ม rebase ทันที (เหมือนไม่มีอะไรเกิดขึ้น) ให้คุณเริ่มใหม่ได้อย่างสบายใจ

### เปรียบเทียบทั้งสามคำสั่งในตารางเดียว

| คำสั่ง | ใช้เมื่อ | ผลลัพธ์ |
|---|---|---|
| `--continue` | แก้ conflict ของ commit ปัจจุบันเสร็จแล้ว | เล่นซ้ำ commit ตัวถัดไปต่อ |
| `--skip` | ต้องการทิ้ง commit ปัจจุบันไปเลย | commit นั้นหายไปจากผลลัพธ์ ไปทำตัวถัดไปต่อ |
| `--abort` | ต้องการยกเลิกทั้งหมด กลับไปจุดเริ่มต้น | branch กลับสู่สถานะก่อน rebase ทุกประการ |

### คำสั่งเสริมที่ควรรู้จักไว้: `git rebase --quit`

มีอีกคำสั่งหนึ่งที่คล้ายกันแต่**อันตรายกว่า**คือ `git rebase --quit` ซึ่งจะ**หยุดกระบวนการ rebase ทันทีโดยไม่คืนสถานะกลับไปจุดเดิม** — HEAD จะค้างอยู่ ณ ตำแหน่งที่ rebase ทำไปถึงตอนนั้น (อาจอยู่กลางทาง ครึ่ง ๆ กลาง ๆ) ต่างจาก `--abort` ที่คืนกลับให้เสมอ คำสั่งนี้ใช้เฉพาะกรณีพิเศษจริง ๆ เท่านั้น (เช่นต้องการแก้ปัญหาด้วยมือต่อเอง) สำหรับมือใหม่ **แนะนำให้ใช้ `--abort` เสมอเมื่อไม่แน่ใจ** อย่าใช้ `--quit` โดยไม่เข้าใจผลที่ตามมา

## Step 380: แบบฝึกหัด — Rebase Branch ที่มี Conflict จริงจนสำเร็จ

ถึงเวลาลงมือทำจริงด้วยตัวเอง เปิด terminal แล้วทำตามทีละขั้นตอนในโฟลเดอร์ฝึกฝนของคุณ (`~/git-course/part-38-rebase`)

### ขั้นตอนที่ 1: เตรียม repository ฝึกฝน

```bash
mkdir ~/git-course/part-38-rebase
cd ~/git-course/part-38-rebase
git init
git config user.name "ผู้ฝึกหัด Git"
git config user.email "practice@example.com"
```

### ขั้นตอนที่ 2: สร้าง commit เริ่มต้นบน `main`

```bash
echo "หน้าแรกของเว็บไซต์" > home.txt
git add home.txt
git commit -m "initial commit: สร้างหน้า home"
```

### ขั้นตอนที่ 3: สร้าง feature branch แล้วแก้ไฟล์เดียวกัน

```bash
git switch -c feature/greeting
echo "ยินดีต้อนรับสู่เว็บไซต์ของเรา" >> home.txt
git add home.txt
git commit -m "เพิ่มข้อความต้อนรับ"

echo "ติดต่อเราได้ที่ contact@example.com" >> home.txt
git add home.txt
git commit -m "เพิ่มข้อมูลติดต่อ"
```

### ขั้นตอนที่ 4: กลับไปที่ `main` แล้วแก้ไฟล์เดียวกันในบรรทัดใกล้เคียงกันเพื่อสร้าง conflict โดยตั้งใจ

```bash
git switch main
echo "หน้าแรกของเว็บไซต์ (อัปเดตล่าสุด)" > home.txt
git add home.txt
git commit -m "แก้ไขข้อความหน้าแรกจากทีมกลาง"
```

ตอนนี้ประวัติของคุณหน้าตาแบบนี้:

```bash
git log --oneline --graph --all
```

```
* 3f4a5b6 (feature/greeting) เพิ่มข้อมูลติดต่อ
* 2e3f4a5 เพิ่มข้อความต้อนรับ
| * 9c8d7e6 (HEAD -> main) แก้ไขข้อความหน้าแรกจากทีมกลาง
|/
* 1a2b3c4 initial commit: สร้างหน้า home
```

### ขั้นตอนที่ 5: ลงมือ rebase feature branch เข้ากับ main

```bash
git switch feature/greeting
git rebase main
```

Git จะแจ้ง conflict ทันทีที่ commit แรก (`เพิ่มข้อความต้อนรับ`):

```
Auto-merging home.txt
CONFLICT (content): Merge conflict in home.txt
error: could not apply 2e3f4a5... เพิ่มข้อความต้อนรับ
```

### ขั้นตอนที่ 6: ตรวจสอบสถานะและเปิดไฟล์ที่ conflict

```bash
git status
```

เปิดไฟล์ `home.txt` จะเห็น conflict marker แบบนี้:

```
<<<<<<< HEAD
หน้าแรกของเว็บไซต์ (อัปเดตล่าสุด)
=======
หน้าแรกของเว็บไซต์
ยินดีต้อนรับสู่เว็บไซต์ของเรา
>>>>>>> 2e3f4a5 (เพิ่มข้อความต้อนรับ)
```

### ขั้นตอนที่ 7: แก้ conflict ด้วยมือ

แก้ไฟล์ให้เหลือเนื้อหาที่ถูกต้องตามที่ต้องการจริง เช่น:

```
หน้าแรกของเว็บไซต์ (อัปเดตล่าสุด)
ยินดีต้อนรับสู่เว็บไซต์ของเรา
```

ลบ conflict marker (`<<<<<<<`, `=======`, `>>>>>>>`) ออกให้หมด แล้ว:

```bash
git add home.txt
git rebase --continue
```

### ขั้นตอนที่ 8: แก้ conflict รอบที่สอง (commit ถัดไปก็ชนอีก)

เพราะ commit ที่สอง (`เพิ่มข้อมูลติดต่อ`) ก็แก้ไฟล์เดียวกัน มีโอกาสสูงที่จะชนอีกครั้ง:

```
CONFLICT (content): Merge conflict in home.txt
error: could not apply 3f4a5b6... เพิ่มข้อมูลติดต่อ
```

ทำซ้ำขั้นตอนเดิม: เปิดไฟล์ แก้ conflict ให้ถูกต้อง แล้ว:

```bash
git add home.txt
git rebase --continue
```

ถ้าไม่เหลือ commit ให้ replay อีกแล้ว Git จะแจ้ง:

```
Successfully rebased and updated refs/heads/feature/greeting.
```

### ขั้นตอนที่ 9: ตรวจสอบผลลัพธ์สุดท้าย

```bash
git log --oneline --graph --all
cat home.txt
```

ควรเห็นประวัติเรียงเส้นตรงแล้ว:

```
* b7c8d9e (HEAD -> feature/greeting) เพิ่มข้อมูลติดต่อ
* a6b7c8d เพิ่มข้อความต้อนรับ
* 9c8d7e6 (main) แก้ไขข้อความหน้าแรกจากทีมกลาง
* 1a2b3c4 initial commit: สร้างหน้า home
```

สังเกตว่า hash ของ commit ทั้งสองตัวบน `feature/greeting` เปลี่ยนไปจากเดิมแล้ว (`2e3f4a5` → `a6b7c8d`, `3f4a5b6` → `b7c8d9e`) ตรงตามที่อธิบายไว้ใน Step 371

### ขั้นตอนที่ 10 (แบบฝึกหัดเสริม): ลองยกเลิกกลางทางด้วย `--abort`

ทำซ้ำตั้งแต่ขั้นตอนที่ 5 อีกครั้ง (ลบ branch เก่าแล้วสร้างสถานการณ์เดิมใหม่ หรือใช้ `git reflog` ย้อนกลับ) แต่รอบนี้เมื่อเจอ conflict รอบแรก ให้ลองสั่ง:

```bash
git rebase --abort
git log --oneline --graph --all
```

ตรวจสอบว่า `feature/greeting` กลับไปมี `2e3f4a5` และ `3f4a5b6` เหมือนก่อนเริ่ม rebase ทุกประการ — นี่คือการยืนยันว่า `--abort` ปลอดภัยและคืนสถานะได้จริง ทำให้คุณกล้าทดลอง rebase มากขึ้นโดยรู้ว่ามีทางถอยเสมอ

### เกณฑ์ตรวจว่าทำสำเร็จ

- [ ] สร้าง conflict ได้จริงระหว่าง rebase (ไม่ใช่ merge)
- [ ] แก้ conflict ได้ครบทุกรอบด้วยตัวเอง โดยไม่ลอกคำตอบ
- [ ] ใช้ `git rebase --continue` ได้ถูกจังหวะ
- [ ] เห็นด้วยตาตัวเองว่า hash ของ commit เปลี่ยนไปหลัง rebase
- [ ] ทดลอง `git rebase --abort` แล้วยืนยันว่าคืนสถานะเดิมได้จริง
- [ ] อธิบายได้ด้วยคำพูดตัวเองว่าทำไมข้อ 4 ถึงเกิดขึ้น (คำใบ้: ดู Step 371)

ใน Part นี้เราได้เรียนรู้:

1. `git rebase` คือการย้าย "ฐาน" ของ branch ไปตั้งต้นใหม่บน commit ล่าสุดของอีก branch โดยเล่นซ้ำ (replay) commit ทีละตัว ซึ่ง**สร้าง commit ใหม่ที่มี hash ต่างจากเดิมทั้งหมด**
2. `git merge` สร้างประวัติแบบ **non-linear** (มีกิ่งก้านและ merge commit เป็นหลักฐาน) ในขณะที่ `git rebase` สร้างประวัติแบบ **linear** (เรียงเส้นตรง ไม่มีร่องรอยการแตก branch)
3. ขั้นตอน rebase จริงคือ `git switch <feature-branch>` แล้ว `git rebase <base-branch>` และถ้าเคย push ไปแล้วต้อง `git push --force-with-lease` ตามหลัง
4. Conflict ระหว่าง rebase ต่างจาก merge ตรงที่ต้อง**แก้ทีละ commit** ที่ถูก replay ไม่ใช่แก้รวมกันครั้งเดียวเหมือน merge
5. **กฎทองของ rebase: ห้าม rebase commit ที่ถูกแชร์ให้คนอื่น pull ไปใช้งานต่อแล้วเด็ดขาด** เพราะจะทำให้เกิด commit ซ้ำซ้อนและประวัติแตกแยกกันระหว่างเครื่องของแต่ละคนอย่างแก้ไขยาก
6. `git pull --rebase` ปลอดภัยเพราะ rebase เฉพาะ commit ที่ยังไม่เคยถูก push ไปให้ใครเห็น ตั้งค่าเป็นค่า default ได้ด้วย `pull.rebase = true`
7. ตารางเปรียบเทียบและ decision guide ช่วยให้ตัดสินใจได้ทันทีหน้างานจริงว่าเมื่อไหร่ควร merge เมื่อไหร่ควร rebase
8. `--continue`, `--skip`, `--abort` คือเครื่องมือควบคุม rebase ระหว่างทาง โดย `--abort` คือทางออกที่ปลอดภัยที่สุดเมื่อไม่แน่ใจ
9. ฝึกลงมือ rebase branch ที่มี conflict จริงจนสำเร็จครบทุกขั้นตอน พร้อมยืนยันด้วยตาตัวเองว่า hash เปลี่ยนไปและ `--abort` คืนสถานะได้จริง
