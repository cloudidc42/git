## Step 901: Agile/Scrum เบื้องต้น (Sprint, Backlog, User Story) และความสัมพันธ์กับ Git workflow

ก่อนจะพูดถึงว่า Git กับ Scrum เชื่อมกันอย่างไร เราต้องเข้าใจ Scrum ในระดับที่ถูกต้องเสียก่อน เพราะในความเป็นจริง ทีมจำนวนมากเรียกตัวเองว่า "ทำ Scrum" ทั้งที่จริง ๆ แล้วทำแค่บางส่วนของมัน (เช่น มีแค่ Daily Standup แต่ไม่มี Sprint Goal ที่ชัดเจน) ซึ่งทำให้การเชื่อมกับ Git workflow ผิดเพี้ยนไปด้วย

### Scrum คืออะไรกันแน่

**Scrum** คือ **กรอบการทำงาน (framework)** ไม่ใช่ระเบียบวิธี (methodology) แบบละเอียดยิบ Scrum ถูกกำหนดไว้อย่างเป็นทางการใน **Scrum Guide** (เขียนโดย Ken Schwaber และ Jeff Sutherland ผู้ร่วมสร้าง Scrum) ซึ่งระบุกฎขั้นต่ำที่จำเป็นเพื่อให้ทีมสามารถส่งมอบงานที่มีคุณค่าซ้ำ ๆ ได้อย่างสม่ำเสมอในรอบเวลาสั้น ๆ ที่คาดเดาได้

Scrum เป็นหนึ่งในกรอบการทำงานภายใต้ปรัชญาที่ใหญ่กว่าเรียกว่า **Agile** ซึ่งมีรากฐานมาจาก **Agile Manifesto (2001)** ที่เน้นคุณค่า 4 ข้อ:

1. **Individuals and interactions** มากกว่า processes and tools
2. **Working software** มากกว่า comprehensive documentation
3. **Customer collaboration** มากกว่า contract negotiation
4. **Responding to change** มากกว่า following a plan

Agile ไม่ใช่ชื่อของกรอบการทำงานใดกรอบหนึ่ง แต่เป็น "แนวคิด" ที่ Scrum, Kanban, XP (Extreme Programming), Lean และอื่น ๆ ต่างก็เป็นการนำแนวคิดนี้ไปปฏิบัติในรูปแบบที่ต่างกัน ในหลักสูตรนี้เราจะเน้น Scrum เป็นหลักเพราะเป็นกรอบที่ทีมพัฒนาซอฟต์แวร์ทั่วโลกใช้มากที่สุด และจะเทียบกับ Kanban ใน Step 909

### องค์ประกอบหลักของ Scrum ที่ต้องรู้จักก่อน

#### 1. Product Backlog (แบ็กล็อกของผลิตภัณฑ์)

รายการงานทั้งหมดที่ **อาจ** ต้องทำเพื่อพัฒนาผลิตภัณฑ์ เรียงลำดับความสำคัญโดย **Product Owner (PO)** Product Backlog ไม่มีวันสมบูรณ์ 100% เพราะมันถูกปรับปรุงตลอดเวลาตามความเข้าใจตลาด ฟีดแบ็กจากลูกค้า และลำดับความสำคัญทางธุรกิจที่เปลี่ยนไป

#### 2. Sprint (รอบการทำงาน)

**Sprint** คือกรอบเวลาคงที่ (time-box) ที่ทีมใช้ในการผลิตงานที่ "เสร็จสมบูรณ์" ชิ้นหนึ่งออกมา โดยทั่วไปมีความยาว **1–4 สัปดาห์** (ที่นิยมที่สุดคือ 2 สัปดาห์) Sprint จะไม่ถูกยืดหรือย่นระหว่างทาง และเมื่อ Sprint เริ่มแล้ว ขอบเขตงานจะถูก "ล็อก" ไว้ในระดับหนึ่ง (ยกเว้นในกรณีพิเศษที่ Product Owner ต้อง cancel Sprint)

#### 3. Sprint Backlog (แบ็กล็อกของ Sprint)

ชุดของ Product Backlog Item ที่ทีมเลือกมาทำใน Sprint นั้น ๆ พร้อมแผนว่าจะส่งมอบอย่างไร Sprint Backlog เป็นของทีม Dev เอง ไม่ใช่ของ PO

#### 4. User Story (เรื่องราวของผู้ใช้งาน)

หน่วยงานที่เล็กที่สุดใน Backlog ที่อธิบายความต้องการจากมุมมองผู้ใช้ มักเขียนในรูปแบบ:

```
ในฐานะ <บทบาทของผู้ใช้>
ฉันต้องการ <สิ่งที่ต้องการทำ>
เพื่อที่ <เหตุผล/คุณค่าที่ได้รับ>
```

ตัวอย่างจริง:

```
ในฐานะผู้ใช้ที่ยังไม่ได้ล็อกอิน
ฉันต้องการรีเซ็ตรหัสผ่านผ่านอีเมล
เพื่อที่ฉันจะกลับเข้าใช้งานบัญชีของตัวเองได้เมื่อลืมรหัสผ่าน
```

User Story แต่ละใบมักมี **Acceptance Criteria (เกณฑ์การยอมรับ)** กำกับไว้ด้วย เพื่อบอกว่าเงื่อนไขอะไรบ้างที่ต้องเป็นจริงถึงจะถือว่า Story นี้ทำเสร็จ

#### 5. บทบาทหลักใน Scrum (Scrum Team)

| บทบาท | หน้าที่หลัก |
|---|---|
| **Product Owner (PO)** | รับผิดชอบคุณค่าของผลิตภัณฑ์ จัดลำดับความสำคัญของ Product Backlog |
| **Scrum Master (SM)** | ดูแลให้ทีมปฏิบัติตามกรอบ Scrum อย่างถูกต้อง กำจัดอุปสรรค (impediment) ที่ทีมเจอ |
| **Developers** | ทีมที่ลงมือสร้างงานจริง (รวมถึง dev, QA, designer ที่อยู่ในทีมข้ามสายงาน) |

#### 6. เหตุการณ์หลักใน Scrum (Scrum Events)

| เหตุการณ์ | เกิดขึ้นเมื่อไร | เป้าหมาย |
|---|---|---|
| **Sprint Planning** | ต้น Sprint | เลือกงานจาก Backlog มาใส่ Sprint Backlog พร้อมตั้ง Sprint Goal |
| **Daily Scrum** | ทุกวัน (สั้น ๆ ~15 นาที) | ซิงก์ทีมว่าใครทำอะไร ติดอะไรอยู่ |
| **Sprint Review** | ปลาย Sprint | สาธิตงานที่ทำเสร็จให้ stakeholder ดู รับฟีดแบ็ก |
| **Sprint Retrospective** | หลัง Review ก่อนเริ่ม Sprint ถัดไป | ทีมทบทวนกระบวนการทำงานของตัวเอง หาทางปรับปรุง |

### ทำไมต้องรู้เรื่องนี้ก่อนพูดถึง Git

ประเด็นสำคัญที่สุดของ Part นี้คือ: **Scrum Guide ฉบับทางการไม่ได้พูดถึง Git, branch, หรือ pull request แม้แต่คำเดียว** เพราะ Scrum เป็นกรอบการบริหารจัดการงาน (process framework) ที่เป็นกลางทางเทคนิค ใช้ได้กับงานก่อสร้าง งานการตลาด หรืองานพัฒนาซอฟต์แวร์ก็ได้

สิ่งที่เราจะทำใน Part นี้คือการ **เอากรอบ Scrum มาจับคู่กับเครื่องมือ Git/GitHub/GitLab ที่เป็นรูปธรรม** เพื่อให้ทีมพัฒนาซอฟต์แวร์นำ Scrum ไปปฏิบัติได้จริงโดยไม่ต้องเดาเอาเองว่า "แล้ว Sprint กับ branch ควรจะเกี่ยวกันยังไง"

### ตารางเทียบแนวคิด Scrum กับ Git workflow (ภาพรวมก่อนลงรายละเอียด)

| แนวคิดใน Scrum | สิ่งที่จับคู่กันในโลก Git |
|---|---|
| Product Backlog Item / User Story | GitHub Issue หรือ GitLab Issue หนึ่งใบ |
| Sprint | ช่วงเวลาที่ branch หลายเส้นถูกสร้าง พัฒนา และ merge เข้า main/develop |
| Sprint Backlog | รายการ Issue ที่ถูก assign เข้า Milestone/Iteration ของ Sprint นั้น |
| Sprint Goal | คำอธิบายใน Milestone description หรือ Sprint board |
| Definition of Done | Checklist ใน PR template + branch protection rules + CI status |
| Sprint Review | Demo จาก branch ที่ merge เข้า staging/main แล้ว |
| Sprint Retrospective | วิเคราะห์ประวัติ commit/PR ของ Sprint ที่ผ่านมา |
| Daily Scrum | สถานะ PR/commit ที่เกิดขึ้นเมื่อวาน (เสริม ไม่ใช่แทนที่การพูดคุย) |

จาก Step 902 เป็นต้นไป เราจะลงรายละเอียดของแต่ละคู่นี้ทีละคู่

## Step 902: การตั้งชื่อ branch ผูกกับ Sprint/Story ID

ใน **Part 35** เราได้เรียนรู้ branch naming convention มาตรฐานไปแล้ว (`feature/`, `bugfix/`, `hotfix/`, `release/`, `chore/`, `docs/`) และหลักการใส่หมายเลข ticket/issue เข้าไปในชื่อ branch ใน Step นี้เราจะขยายแนวคิดนั้นให้เจาะจงกับบริบทของ Scrum โดยตรง

### ทำไมต้องผูกชื่อ branch กับ Story ID

เมื่อทีมทำงานแบบ Scrum ทุก branch ที่ถูกสร้างขึ้นควรมี **ที่มาที่ไป** เสมอ นั่นคือควรตอบได้ทันทีว่า branch นี้ทำเพื่อ Story ใบไหน อยู่ใน Sprint ไหน หากไม่มีการผูกกัน ปัญหาที่ตามมาจะเหมือนที่ Part 35 อธิบายไว้ แต่รุนแรงกว่าเดิม เพราะทีม Scrum ต้องรายงานความคืบหน้าเป็น Sprint ๆ — ถ้าตามไม่ได้ว่า branch ไหนคือ branch ของ Story ไหน การติดตาม Sprint Burndown หรือ Sprint Review จะทำได้ยากมาก

### รูปแบบมาตรฐานที่แนะนำ

```
<type>/<story-id>-<short-description>
```

โดย `<story-id>` คือหมายเลขอ้างอิงจาก issue tracker ที่ทีมใช้ ซึ่งอาจเป็น:

- หมายเลข GitHub Issue: `#142` → ใช้ในชื่อ branch เป็น `142`
- หมายเลข GitLab Issue: `#87` → ใช้เป็น `87`
- Ticket key จากเครื่องมือภายนอก เช่น Jira: `PROJ-231`, Linear: `ENG-45`

**ตัวอย่างจริง:**

```bash
git checkout -b feature/142-password-reset-via-email
git checkout -b bugfix/87-cart-total-rounding-error
git checkout -b feature/PROJ-231-dark-mode-toggle
```

### ทำไมต้องใส่คำอธิบายสั้น ๆ ต่อท้ายเลข ticket ด้วย ไม่ใช่ใส่แค่เลขอย่างเดียว

หลายทีมทำผิดพลาดโดยตั้งชื่อ branch แค่ `feature/142` เฉย ๆ ปัญหาคือเมื่อดู `git branch` หรือ `git log --graph` แบบเร็ว ๆ จะไม่มีทางรู้เลยว่า `142` คือเรื่องอะไรโดยไม่ต้องเปิด issue tracker ไปดู การใส่คำอธิบายสั้น ๆ ต่อท้ายทำให้อ่านออกได้ทันทีจากหน้าจอ terminal โดยไม่ต้องสลับหน้าต่างไปเช็ค

### ควรผูก Sprint number เข้าไปในชื่อ branch ด้วยหรือไม่

คำถามที่พบบ่อยคือ ควรตั้งชื่อแบบ `sprint23/feature/142-password-reset` เพื่อบอกว่างานนี้อยู่ใน Sprint 23 หรือไม่

**คำตอบคือ โดยทั่วไป "ไม่แนะนำ"** ด้วยเหตุผลสำคัญดังนี้:

1. **Branch ควรมีอายุสั้นและอ้างอิงกับ "งาน" ไม่ใช่ "เวลา"** — Story หนึ่งใบอาจเริ่มทำใน Sprint 23 แต่ยังทำไม่เสร็จ ต้องยกยอดไป Sprint 24 (เรียกว่า **spillover**) ถ้าชื่อ branch มีเลข Sprint ฝังอยู่ พอ Story ข้าม Sprint จะทำให้ชื่อ branch ผิดความจริงทันที ต้อง rename branch ไปเรื่อย ๆ ซึ่งไม่มีประโยชน์
2. **Sprint คือหน่วยของการวางแผนและรายงาน ไม่ใช่หน่วยของโค้ด** — ข้อมูลว่า Story นี้อยู่ Sprint ไหนควรถูกเก็บไว้ที่ **issue tracker** (ผ่าน Milestone/Iteration ตามที่จะเรียนใน Step 903) ไม่ใช่ที่ชื่อ branch
3. **แนวทางที่ถูกต้องคือให้ branch อ้างอิง Story ID เพียงอย่างเดียว** แล้วปล่อยให้ issue tracker เป็นผู้บอกว่า Story นั้นอยู่ Sprint ไหน — เมื่อต้องการรู้ว่า Sprint 23 มี branch ไหนบ้าง ให้ query จาก issue tracker (ดูว่า issue ไหนอยู่ Milestone "Sprint 23") แล้วดูว่า issue เหล่านั้นถูกอ้างอิงใน PR ไหนบ้าง ไม่ใช่ไล่ grep ชื่อ branch

### กรณีที่ "ควร" ผูก Sprint เข้ากับ branch โดยตรง: Release Branch เท่านั้น

ข้อยกเว้นเดียวที่การอ้างอิงช่วงเวลาลงในชื่อ branch สมเหตุสมผลคือ **release branch** ที่สร้างขึ้นเพื่อตัดเวอร์ชันปล่อยจริงเมื่อจบ Sprint (ถ้าทีมใช้ release cadence แบบผูกกับ Sprint) เช่น:

```bash
git checkout -b release/2026-sprint-23
```

กรณีนี้ไม่ใช่ branch ของ Story แต่เป็น branch ของ "การปล่อยเวอร์ชัน" ซึ่งผูกกับเวลาโดยธรรมชาติอยู่แล้ว จึงไม่ขัดกับหลักการข้อ 1–3 ข้างต้น

### การเชื่อม branch เข้ากับ issue โดยอัตโนมัติ

ทั้ง GitHub และ GitLab มีกลไกช่วยเชื่อม branch กับ issue แบบกึ่งอัตโนมัติ:

**บน GitHub:** ถ้าเปิดหน้า Issue แล้วกดปุ่ม **Create a branch** ในส่วน Development ระบบจะสร้างชื่อ branch ให้อัตโนมัติในรูปแบบ `<number>-<title-slug>` เช่น issue "Password reset via email" หมายเลข `#142` จะได้ชื่อ branch แนะนำเป็น `142-password-reset-via-email` และ GitHub จะ **ผูก branch นี้กับ issue โดยอัตโนมัติ** ทำให้เห็น branch/PR ที่เกี่ยวข้องแสดงอยู่ในหน้า issue ทันที

**บน GitLab:** กดปุ่ม **Create merge request** จากหน้า Issue โดยตรง ระบบจะสร้าง branch ในรูปแบบ `<number>-<title-slug>` ให้เช่นกัน และสร้าง Draft Merge Request ที่เชื่อมกับ issue นั้นให้อัตโนมัติ

| สถานการณ์ | รูปแบบชื่อ branch | ตัวอย่าง |
|---|---|---|
| Feature ใหม่จาก User Story | `feature/<id>-<desc>` | `feature/142-password-reset` |
| แก้บั๊กที่พบระหว่าง Sprint | `bugfix/<id>-<desc>` | `bugfix/87-cart-rounding` |
| แก้บั๊กด่วนบน production | `hotfix/<id>-<desc>` | `hotfix/201-payment-down` |
| งาน Technical Debt ที่มี issue ของตัวเอง | `chore/<id>-<desc>` | `chore/305-upgrade-node18` |
| ตัดเวอร์ชันปล่อยท้าย Sprint | `release/<sprint-หรือ-version>` | `release/2026-sprint-23` |

หลักการที่ต้องจำให้ขึ้นใจ: **branch ผูกกับ "งาน" (Story/Issue), ส่วน Sprint ผูกกับ "เวลา" ผ่าน Milestone/Iteration ใน issue tracker** — อย่าผสมสองแนวคิดนี้เข้าด้วยกันในชื่อ branch

## Step 903: เชื่อม GitHub/GitLab Issues กับ Sprint board (GitHub Projects, GitLab Milestone)

Step นี้จะตอบคำถามที่ทีม Scrum ทุกทีมต้องเจอ: **"Sprint" ในความหมายของเครื่องมือจริง ๆ คืออะไร และตั้งค่ายังไงให้ Sprint board ใช้งานได้จริง**

### บน GitHub: ใช้ GitHub Projects (v2) กับ Field แบบ Iteration

จาก **Part 23** เราได้เรียนรู้ GitHub Projects (v2) ไปแล้วว่ามันคือเลเยอร์บริหารจัดการที่วางอยู่เหนือ Issue/PR โดย Projects v2 มี **Custom Field ประเภท Iteration** ที่ถูกออกแบบมาโดยเฉพาะสำหรับงานแบบ Sprint

**วิธีตั้งค่า Sprint บน GitHub Projects:**

1. เปิด Project แล้วไปที่ **Settings** ของ field
2. เพิ่ม field ใหม่ ประเภท **Iteration**
3. ตั้งค่าความยาวรอบ (duration) เช่น **2 weeks** ให้ตรงกับความยาว Sprint ของทีม
4. GitHub จะสร้างรายการ Iteration ให้อัตโนมัติต่อเนื่องกันไปตามความยาวที่ตั้ง (เช่น "Iteration 1: 6–19 ม.ค.", "Iteration 2: 20 ม.ค.–2 ก.พ." ...) ซึ่งแต่ละ Iteration ก็คือแต่ละ Sprint ของทีมนั่นเอง
5. เมื่อทำ **Sprint Planning** ให้เปิด Table view หรือ Board view แล้วกำหนดค่า field Iteration ให้กับ Issue ที่เลือกเข้ามาใน Sprint นั้น

หลังตั้งค่าแล้ว ทีมสามารถสลับมุมมองได้ทันที:

- **Board view จัดกลุ่มตาม Status** (To do / In progress / Done) — ใช้เป็น Sprint board ประจำวัน
- **Table view จัดกลุ่มตาม Iteration** — ใช้ดูภาพรวมว่า Sprint ไหนมีงานอะไรบ้าง เปรียบเทียบข้าม Sprint ได้
- Insight/Chart ใน Projects สามารถสร้างกราฟแบบ burndown-like ได้จากข้อมูล field เดียวกันนี้

### บน GitLab: ใช้ Milestone (และ Iteration ถ้ามี tier ที่รองรับ)

จาก **Part 49** เราได้เรียนรู้ GitLab Issues และ Milestone ไปแล้ว GitLab มีแนวคิดเรื่องช่วงเวลาอยู่ 2 แบบที่มักสับสนกัน:

| แนวคิด | ความหมาย | เหมาะกับ |
|---|---|---|
| **Milestone** | ช่วงเวลาที่ยืดหยุ่น มีวันเริ่ม–จบตามที่กำหนดเอง ไม่บังคับต้องต่อเนื่องกัน | เหมาะกับ "Release" หรือเป้าหมายระยะยาวที่ไม่จำเป็นต้องตรงกับ Sprint พอดี |
| **Iteration** (ต้องมี GitLab Premium ขึ้นไป) | ช่วงเวลาแบบ time-box ต่อเนื่องกันเป็นรอบ ๆ ไม่ทับซ้อนกัน | ออกแบบมาสำหรับ Sprint โดยเฉพาะ — ตรงกับแนวคิด Scrum ที่สุด |

**สำหรับทีมที่ใช้ GitLab Free:** เนื่องจาก Iteration เป็นฟีเจอร์ระดับ Premium ทีมส่วนใหญ่ที่ใช้ tier ฟรีจะจำลอง Sprint ด้วย **Milestone** แทน โดยตั้งชื่อ Milestone ให้ตรงกับรอบ Sprint เช่น `Sprint 23 (6–19 ม.ค. 2026)` แล้วกำหนดวัน Start date/Due date ให้ตรงกับวันเริ่ม-จบของ Sprint จริง จากนั้นดึง issue ที่วางแผนไว้เข้ามาผูกกับ Milestone นี้

**สำหรับทีมที่มี GitLab Premium ขึ้นไป:** แนะนำให้ใช้ **Iteration** โดยตรง เพราะระบบจะช่วยสร้าง **Iteration Cadence** (รอบต่อเนื่องอัตโนมัติ) ให้ ไม่ต้องสร้าง Milestone ใหม่มือทุกรอบ และ GitLab จะสร้าง **Burndown chart / Burnup chart** ให้อัตโนมัติจาก Iteration นี้โดยตรง ซึ่งแม่นยำกว่าการเอา Milestone มาจำลอง Sprint

**การดู Sprint board บน GitLab:**

ไปที่เมนู **Plan > Issue boards** แล้วสร้าง board list โดย group ตาม label หรือกรอง issue ด้วย Milestone/Iteration ที่ต้องการ เพื่อให้เห็นเฉพาะงานของ Sprint ปัจจุบัน

### ตารางเปรียบเทียบสรุป: GitHub Projects vs GitLab สำหรับงาน Sprint

| ความสามารถ | GitHub Projects (v2) | GitLab Milestone | GitLab Iteration (Premium+) |
|---|---|---|---|
| รอบเวลาต่อเนื่องอัตโนมัติ | มี (Iteration field) | ไม่มี (ต้องสร้างเองทุกรอบ) | มี (Iteration Cadence) |
| Burndown chart ในตัว | ไม่มีในตัวโดยตรง (ต้องต่อ 3rd-party/Insights เสริม) | ไม่มี | มี |
| ใช้ได้กับ Free tier | ใช่ | ใช่ | ไม่ (ต้อง Premium ขึ้นไป) |
| ผูกกับหลาย repo พร้อมกัน | ใช่ (Org-level project) | ใช่ (Group-level milestone/iteration) | ใช่ (Group-level) |

### หลักปฏิบัติที่แนะนำไม่ว่าจะใช้แพลตฟอร์มไหน

1. **Sprint = หนึ่ง Milestone/Iteration เสมอ** อย่าใช้ label แทน Milestone เพราะ label ไม่มีแนวคิดวันเริ่ม-จบในตัว
2. **ตั้งชื่อ Sprint ให้เป็นมาตรฐานเดียวกันทุกครั้ง** เช่น `Sprint 23`, `Sprint 24` เรียงเลขต่อเนื่อง หรือใส่ช่วงวันที่กำกับไว้ในคำอธิบายเสมอ เพื่อให้ค้นย้อนหลังง่าย
3. **ทุก Issue ที่ถูกเลือกเข้า Sprint ต้องถูก assign เข้า Milestone/Iteration ก่อนเริ่ม Sprint Planning เสร็จสิ้น** — ถ้า Sprint เริ่มไปแล้วแต่ยังมี issue ที่ไม่ได้ผูก Milestone แปลว่า Sprint Backlog ยังไม่สมบูรณ์
4. **Sprint Goal ควรเขียนไว้ในคำอธิบายของ Milestone/Iteration** ไม่ใช่แค่พูดปากเปล่าในที่ประชุม Planning เพื่อให้ทุกคนย้อนกลับมาอ่านได้ตลอด Sprint

## Step 904: Definition of Done ที่รวมเกณฑ์ด้าน Git (PR merged, CI ผ่าน, code review อนุมัติแล้ว)

### Definition of Done คืออะไร

**Definition of Done (DoD)** คือ **ข้อตกลงร่วมกันของทีมทั้งทีม** ว่างานชิ้นหนึ่ง (User Story, task, PR) จะถือว่า "เสร็จจริง" ก็ต่อเมื่อผ่านเงื่อนไขอะไรบ้าง Scrum Guide ระบุว่า DoD เป็นสิ่งที่ **ทีม Scrum ทั้งทีมต้องสร้างขึ้นร่วมกันเอง** ไม่ใช่สิ่งที่ Scrum Master หรือ PO กำหนดฝ่ายเดียว และ DoD จะถูกใช้เป็นเกณฑ์ตัดสินว่า Item ใดควรถูกนับรวมใน **Sprint Review** ว่าทำสำเร็จหรือไม่

จุดสำคัญที่ต้องเข้าใจให้ถูกคือ DoD **ต่างจาก Acceptance Criteria**:

| | Acceptance Criteria | Definition of Done |
|---|---|---|
| ขอบเขต | เฉพาะ Story ใบนั้น ๆ | ใช้กับ **ทุก** Story/Task ในทีม |
| ใครเป็นผู้กำหนด | Product Owner (บางครั้งร่วมกับทีม) | ทีมทั้งทีม (Dev + PO + SM) |
| เนื้อหา | เงื่อนไขเชิงฟังก์ชันเฉพาะของ Story นั้น | มาตรฐานคุณภาพทั่วไปที่ใช้ซ้ำได้ทุกงาน |
| ตัวอย่าง | "ต้องส่งอีเมลยืนยันภายใน 5 วินาที" | "ต้องมี unit test ครอบคลุมและ code review ผ่านแล้ว" |

### ทำไม DoD ยุคใหม่ต้องรวมเกณฑ์ที่มาจาก Git/CI

ในยุคก่อนที่ CI/CD และ Pull Request จะเป็นมาตรฐาน DoD มักเขียนกว้าง ๆ เช่น "โค้ดต้องถูกทดสอบแล้ว" หรือ "ต้องผ่านการรีวิวแล้ว" ซึ่งเป็นข้อความที่ **ตรวจสอบได้ยากและตีความต่างกันได้** แต่เมื่อทีมมี Git workflow ที่มี PR/MR และ CI pipeline เป็นมาตรฐานอยู่แล้ว เราสามารถเปลี่ยน DoD ให้เป็น **เกณฑ์ที่ตรวจสอบได้อัตโนมัติและเป็นภววิสัย (objective)** แทนการอาศัยดุลยพินิจคน

### ตัวอย่าง Definition of Done ที่รวมเกณฑ์ Git (ระดับ Story)

```markdown
## Definition of Done

งานหนึ่งชิ้นจะถือว่า "Done" ก็ต่อเมื่อครบทุกข้อต่อไปนี้:

### ด้านโค้ดและ Git
- [ ] โค้ดถูก push ขึ้น branch ที่ตั้งชื่อตามมาตรฐานทีม (ผูกกับ Issue ID)
- [ ] เปิด Pull Request / Merge Request แล้ว โดยอธิบาย "อะไร" และ "ทำไม" ชัดเจน
- [ ] PR เชื่อมโยงกับ Issue ที่เกี่ยวข้องด้วย closing keyword (เช่น `Closes #142`)
- [ ] Pull Request ผ่านการ Review และได้รับ Approve จากผู้รีวิวอย่างน้อย 1 คน (โค้ดที่กระทบส่วน critical ต้อง 2 คน)
- [ ] ไม่มี unresolved conversation เหลืออยู่ใน PR
- [ ] CI Pipeline ผ่านทุกขั้นตอน (lint, unit test, integration test, build) เป็นสีเขียวทั้งหมด
- [ ] Code coverage ของโค้ดที่เปลี่ยนแปลงไม่ต่ำกว่าเกณฑ์ที่ทีมกำหนด (เช่น 80%)
- [ ] PR ถูก merge เข้า branch หลัก (main/develop) เรียบร้อยแล้ว ไม่ใช่แค่ approve ทิ้งไว้
- [ ] Branch ที่ใช้งานเสร็จแล้วถูกลบทิ้ง (ไม่ปล่อยให้ branch ค้างใน repo)

### ด้านคุณภาพ
- [ ] มี Automated test ครอบคลุม logic หลักของ feature/แก้บั๊กนั้น
- [ ] ไม่มี regression กับฟีเจอร์เดิม (ตรวจจากผลของ CI test suite เต็มรูปแบบ)
- [ ] Documentation ที่เกี่ยวข้อง (README, API doc, changelog) ถูกอัปเดตแล้วถ้าจำเป็น

### ด้านการส่งมอบ
- [ ] Feature ถูก deploy ไปยัง environment ที่ตกลงกันไว้ (staging อย่างน้อย)
- [ ] Product Owner ได้เห็นผลลัพธ์และยืนยันว่าตรงกับ Acceptance Criteria ของ Story
```

### ทำไม "PR merged" ต้องเป็นเกณฑ์ ไม่ใช่แค่ "PR approved"

ทีมจำนวนไม่น้อยเข้าใจผิดว่างานเสร็จเมื่อ reviewer กด Approve แล้ว แต่ในทางปฏิบัติ **PR ที่ approve แล้วแต่ยังไม่ merge ยังไม่สร้างคุณค่าอะไรเลย** เพราะโค้ดยังไม่ได้อยู่ใน branch หลักที่จะถูกนำไป build/deploy จริง การนับ "merged" เป็นเกณฑ์บังคับช่วยป้องกันปัญหาคลาสสิกที่เรียกว่า **"approved แต่ merge ค้าง"** ซึ่งทำให้ Sprint Review เอางานไปโชว์ไม่ได้ทั้งที่ทีมคิดว่า "เสร็จแล้ว"

### การบังคับใช้ DoD ด้วยเครื่องมือ ไม่ใช่แค่ด้วยความจำ

DoD ที่ดีที่สุดคือ DoD ที่ **เครื่องมือบังคับให้ทำตามโดยอัตโนมัติ** แทนที่จะหวังพึ่งวินัยของคนอย่างเดียว ทีมควรตั้งค่าต่อไปนี้ให้ตรงกับ DoD ที่ตกลงกันไว้:

| ข้อใน DoD | เครื่องมือที่บังคับใช้ได้ |
|---|---|
| ต้อง approve อย่างน้อย 1–2 คน | Branch protection rule: **Require approvals** |
| ไม่มี unresolved conversation | Branch protection: **Require conversation resolution before merging** |
| CI ต้องผ่าน | Branch protection: **Require status checks to pass before merging** |
| Coverage ต้องไม่ต่ำกว่าเกณฑ์ | CI step เช่น `codecov`/`nyc check-coverage` ที่ fail pipeline ถ้าต่ำกว่าเกณฑ์ |
| ต้องเชื่อมกับ Issue | Bot/Action ตรวจสอบว่า PR description มี closing keyword หรือ template บังคับกรอกช่อง "Related issue" |
| Branch ต้องถูกลบหลัง merge | ตั้งค่า repo: **Automatically delete head branches** |

เมื่อ DoD ถูกฝังเข้าไปในการตั้งค่า repository แล้ว การตรวจสอบว่า "งานนี้เสร็จจริงหรือยัง" จะไม่ต้องอาศัยการถามปากเปล่าหรือเชื่อคำพูดใครอีกต่อไป — GitHub/GitLab จะไม่ยอมให้กด merge ได้เลยถ้ายังไม่ผ่านเงื่อนไข

## Step 905: Sprint Retrospective โดยใช้ข้อมูลจาก Git ประกอบ (cycle time, PR size เฉลี่ย)

### ปัญหาของ Retrospective ที่พึ่งความรู้สึกล้วน ๆ

**Sprint Retrospective** คือเหตุการณ์ที่ทีมมานั่งทบทวนว่า Sprint ที่ผ่านมา "ทำงานเป็นทีมได้ดีแค่ไหน" ไม่ใช่แค่ "ผลิตภัณฑ์ดีแค่ไหน" (นั่นคือหน้าที่ของ Sprint Review) รูปแบบคลาสสิกที่ทีมส่วนใหญ่ใช้คือถามคำถาม 3 ข้อ: **What went well? What didn't go well? What will we improve?**

ปัญหาคือถ้า Retro พึ่งพาความทรงจำและความรู้สึกของสมาชิกล้วน ๆ มันมักจะ:

- เอนเอียงไปทางเหตุการณ์ที่ "เพิ่งเกิดขึ้นใกล้ ๆ วัน Retro" (recency bias) มากกว่าที่เกิดขึ้นจริงตลอด Sprint
- ถูกครอบงำโดยเสียงของคนที่พูดเก่งหรือมีตำแหน่งสูงในทีม
- ไม่มีหลักฐานยืนยันว่า "รู้สึกว่าช้าลง" นั้นเป็นจริงตามข้อมูลหรือไม่

การนำ **ข้อมูลจริงจาก Git history** มาประกอบการพูดคุยใน Retro ช่วยให้บทสนทนาเปลี่ยนจาก "ความรู้สึก" มาเป็น "ข้อเท็จจริงที่ทุกคนเห็นตรงกัน" แล้วค่อยคุยกันว่าทำไมตัวเลขถึงเป็นแบบนั้น ซึ่งเป็นจุดเริ่มต้นของบทสนทนาที่มีคุณภาพกว่ามาก

### ตัวชี้วัดหลักที่ควรดึงมาใช้ใน Retro

#### 1. Cycle Time (เวลาตั้งแต่เริ่มลงมือทำจนถึง merge)

**Cycle Time** ในบริบทนี้หมายถึงระยะเวลาตั้งแต่ **commit แรกของ branch นั้นถูกสร้าง** จนถึง **PR ถูก merge เข้า branch หลัก** สูตรคำนวณอย่างง่าย:

```
Cycle Time = เวลาที่ PR ถูก merge − เวลาของ commit แรกใน branch
```

วิธีดึงข้อมูลนี้ด้วย Git ล้วน ๆ (ไม่ต้องพึ่ง GUI):

```bash
# ดูเวลาของ commit แรกใน branch เทียบกับ main
git log main..feature/142-password-reset --reverse --format="%ai" | head -1

# เทียบกับเวลาที่ merge commit ถูกสร้างบน main
git log main --merges --grep="142" --format="%ai" | head -1
```

ในทางปฏิบัติ ทีมส่วนใหญ่จะดึงตัวเลขนี้ผ่าน **GitHub GraphQL API** หรือ **GitLab API** แทนการไล่คำสั่ง git เอง เพราะสามารถดึง `createdAt` ของ PR และ `mergedAt` มาคำนวณส่วนต่างได้ตรง ๆ และทำเป็น dashboard อัตโนมัติได้

Cycle Time ที่ยาวผิดปกติมักบ่งชี้ปัญหาอย่างใดอย่างหนึ่ง:

- PR มีขนาดใหญ่เกินไป (ดูข้อ 2 ประกอบ)
- คิวการรีวิวยาว (reviewer ไม่มีเวลาว่างพอ)
- Story มีความไม่ชัดเจน ทำให้ dev ต้องหยุดถามระหว่างทางบ่อย
- มี dependency ระหว่างทีม/ระบบที่ทำให้ต้องรอ

#### 2. PR Size เฉลี่ย (ขนาดของแต่ละ Pull Request)

วัดจากจำนวนบรรทัดที่เปลี่ยนแปลง (`+` เพิ่ม, `-` ลบ) และจำนวนไฟล์ที่แตะต้อง:

```bash
# ดูขนาดของการเปลี่ยนแปลงเทียบกับ main ก่อน merge
git diff main...feature/142-password-reset --stat
```

ตัวอย่างผลลัพธ์:

```
 src/auth/reset-password.ts   | 120 +++++++++++++++++++++++
 src/auth/reset-password.test.ts |  85 ++++++++++++++++++++
 src/mailer/templates/reset.html |  40 +++++++++
 3 files changed, 245 insertions(+)
```

งานวิจัยด้าน Software Engineering หลายชิ้น (รวมถึงข้อสังเกตจากทีมวิศวกรรมของ Google และ Microsoft) พบข้อเท็จจริงที่สอดคล้องกันว่า **PR ที่มีขนาดเล็กจะถูกรีวิวได้เร็วกว่า แม่นยำกว่า และมี defect หลุดรอดน้อยกว่า PR ขนาดใหญ่อย่างมีนัยสำคัญ** เหตุผลเชิงความรู้ความเข้าใจ (cognitive) คือสมองมนุษย์มีขีดจำกัดในการถือรายละเอียดจำนวนมากไว้ในความจำระยะสั้นพร้อมกัน เมื่อ PR ใหญ่เกินไป reviewer มักจะ "กวาดตาผ่าน ๆ" แทนที่จะอ่านลึกจริง

แนวทางที่ทีม Scrum ที่ดีมักตั้งเป็นแนวปฏิบัติ (ไม่ใช่กฎตายตัว): พยายามให้ PR หนึ่งใบเปลี่ยนแปลงไม่เกินประมาณ **400 บรรทัด** (ไม่รวมไฟล์ที่ auto-generate หรือไฟล์ lock) ถ้า Story หนึ่งใบทำให้เกิดการเปลี่ยนแปลงมากกว่านั้น ควรพิจารณาแตกเป็นหลาย PR ย่อยที่ merge ทีละส่วนได้ (incremental delivery)

#### 3. จำนวน Round-trip ของการรีวิว (Review iterations)

นับจำนวนรอบที่ PR ถูกส่งกลับไปแก้ก่อนจะได้รับ approve — ถ้าค่าเฉลี่ยสูงผิดปกติในบาง Sprint อาจสะท้อนว่า Definition of Done หรือมาตรฐานโค้ดยังสื่อสารกันไม่ชัดตั้งแต่ต้น

#### 4. อัตราการ Spillover (งานที่ทำไม่เสร็จใน Sprint แล้วต้องยกไป Sprint ถัดไป)

ดึงจาก Milestone/Iteration ของ issue tracker: นับจำนวน issue ที่ยังเปิดอยู่เมื่อ Sprint ปิด เทียบกับจำนวนทั้งหมดที่วางแผนไว้ตอนเริ่ม Sprint

### ตัวอย่างการนำข้อมูลไปใช้ใน Retro จริง

```
Sprint 23 — สรุปข้อมูลจาก Git ก่อนเข้า Retro

- จำนวน PR ที่ merge สำเร็จ: 14 PR
- Cycle Time เฉลี่ย: 3.2 วัน (Sprint ก่อนหน้า: 1.8 วัน) ← เพิ่มขึ้นมาก
- PR Size เฉลี่ย: 310 บรรทัด (Sprint ก่อนหน้า: 180 บรรทัด) ← ใหญ่ขึ้นมาก
- Story ที่ Spillover ไป Sprint 24: 2 จาก 8 Story ที่วางแผนไว้
```

จากตัวเลขนี้ ทีมสามารถตั้งคำถามที่ตรงจุดใน Retro ได้ทันที เช่น "ทำไม PR ใน Sprint นี้ถึงใหญ่ขึ้นเกือบเท่าตัว มีอะไรทำให้เราไม่ได้แตก PR ย่อยเหมือนที่เคยทำ" แทนที่จะคุยกันแบบเลื่อนลอยว่า "รู้สึกว่า Sprint นี้ทำงานช้ากว่าปกติ"

### ข้อควรระวัง: อย่าใช้ตัวเลขเหล่านี้ตัดสินผลงานรายบุคคล

ข้อมูลจาก Git ใน Retro มีไว้เพื่อ **ปรับปรุงกระบวนการทำงานของทีม** ไม่ใช่เพื่อจัดอันดับหรือตัดสินผลงานรายบุคคล (เช่น "ใครเขียน commit น้อยที่สุด") การนำ metric ไปใช้ประเมินผลงานรายบุคคลโดยตรงเป็นความเข้าใจผิดที่อันตรายมาก เพราะจะทำให้คนเริ่ม "เล่นกับตัวเลข" (เช่น แตก commit ให้เยอะ ๆ โดยไม่จำเป็น) แทนที่จะโฟกัสที่คุณค่าจริงของงาน เราจะพูดถึงเรื่องนี้ลึกขึ้นในเรื่อง Metrics/DORA ใน Part ถัดไป

## Step 906: การจัดการ Technical Debt ผ่าน issue tracker ให้ไม่ถูกลืม

### Technical Debt คืออะไร

**Technical Debt (หนี้ทางเทคนิค)** คือแนวคิดที่เปรียบเทียบการตัดสินใจเขียนโค้ดแบบลัด/ง่าย/เร็วในระยะสั้น กับการกู้หนี้ทางการเงิน — คุณได้ความเร็วในวันนี้ แลกกับ "ดอกเบี้ย" ที่ต้องจ่ายในอนาคตในรูปของโค้ดที่ดูแลยากขึ้น บั๊กที่เกิดถี่ขึ้น หรือความเร็วในการพัฒนาที่ลดลงเรื่อย ๆ คำนี้ถูกบัญญัติขึ้นโดย **Ward Cunningham** หนึ่งในผู้ร่วมเขียน Agile Manifesto

Technical Debt ไม่ใช่สิ่งเลวร้ายเสมอไป บางครั้งการกู้หนี้ทางเทคนิคอย่างมีสติ (เช่น เขียนแบบง่ายก่อนเพื่อทดสอบตลาดให้ทันเวลา) เป็นการตัดสินใจทางธุรกิจที่สมเหตุสมผล **ปัญหาที่แท้จริงไม่ใช่การมีหนี้ แต่คือการมีหนี้ที่ไม่มีใครรู้ว่ามีอยู่ หรือรู้แต่ไม่เคยถูกจัดลำดับความสำคัญให้ชำระคืน**

### ทำไม Technical Debt มักถูกลืมในทีม Scrum

Scrum เน้นการส่งมอบคุณค่าให้ผู้ใช้ปลายทางเป็นหลัก (Increment ที่ใช้งานได้จริง) ซึ่งทำให้ Product Owner ที่ต้องจัดลำดับความสำคัญของ Backlog มักให้น้ำหนักกับ feature ที่ผู้ใช้มองเห็นได้ก่อนเสมอ ปัญหาคือ Technical Debt แบบ "เห็นได้แค่ในโค้ด" (เช่น โค้ดซ้ำซ้อน, dependency เก่ามาก, ไม่มี test coverage) มักถูกดันไปอยู่ท้าย Backlog ตลอดกาล เพราะไม่มีใครมองเห็นผลกระทบต่อธุรกิจโดยตรง จนกระทั่งมันสร้างปัญหาใหญ่ (เช่น security vulnerability หรือระบบล่มบ่อยขึ้น) ถึงจะถูกหยิบมาแก้แบบฉุกเฉิน

### หลักการสำคัญ: Technical Debt ต้องมี "ตัวตน" ใน Issue Tracker เสมอ

กฎข้อแรกและสำคัญที่สุดคือ **ห้ามให้ Technical Debt อยู่แค่ใน "หัวของนักพัฒนา" หรือใน TODO comment ที่ไม่มีใครติดตาม** ทุกครั้งที่นักพัฒนาสังเกตเห็นหนี้ทางเทคนิค ต้องเปลี่ยนมันให้เป็น issue ที่จับต้องได้ในระบบ ไม่ว่าจะเป็น GitHub Issues หรือ GitLab Issues

### วิธีปฏิบัติที่แนะนำ

#### 1. สร้าง Label เฉพาะสำหรับ Technical Debt

```
tech-debt         → หนี้ทางเทคนิคทั่วไป
tech-debt:security → หนี้ที่มีความเสี่ยงด้านความปลอดภัย
tech-debt:perf     → หนี้ที่กระทบ performance
tech-debt:test     → ขาด test coverage
```

การแยก label ย่อยช่วยให้จัดลำดับความสำคัญได้ละเอียดขึ้น เพราะ debt ด้าน security ควรถูกให้ความสำคัญสูงกว่า debt ด้านความสวยงามของโค้ดทั่วไป

#### 2. เชื่อม TODO comment ในโค้ดเข้ากับหมายเลข Issue เสมอ

แทนที่จะเขียน:

```javascript
// TODO: ควร refactor ตรงนี้ทีหลัง
```

ให้เขียนโดยอ้างอิง issue ที่สร้างไว้แล้วเสมอ:

```javascript
// TODO(#318): refactor ฟังก์ชันนี้ให้แยก validation logic ออกจาก business logic
// ดูรายละเอียดเพิ่มเติมที่ https://github.com/org/repo/issues/318
```

วิธีนี้ทำให้สามารถค้นหา TODO ทั้งหมดที่ **ยังไม่ได้ผูกกับ issue** ได้ด้วยคำสั่งง่าย ๆ เพื่อบังคับให้ทีมสร้าง issue ตามทันที:

```bash
git grep -n "TODO" -- '*.js' '*.ts' | grep -v "TODO(#"
```

บางทีมถึงขั้นเขียน CI step ที่ **fail build** ถ้าเจอ `TODO` ที่ไม่มีเลข issue กำกับ เพื่อบังคับให้วินัยนี้เกิดขึ้นจริงแทนที่จะพึ่งความจำ

#### 3. ตั้ง Backlog Refinement ให้ทบทวน Technical Debt เป็นประจำ

**Backlog Refinement (หรือ Backlog Grooming)** คือกิจกรรมที่ทีมนัดคุยกันเป็นระยะ (ไม่ใช่ Scrum Event อย่างเป็นทางการ แต่เป็นแนวปฏิบัติที่แนะนำอย่างยิ่งใน Scrum Guide) เพื่อทำความสะอาดและจัดลำดับ Product Backlog ทีมควรกำหนดวาระตายตัวไว้เสมอว่า **ทุกครั้งที่ Refinement ต้องหยิบ Technical Debt issue ขึ้นมาพิจารณาด้วย** ไม่ใช่พิจารณาแค่ feature ใหม่อย่างเดียว

#### 4. จัดสรรสัดส่วน Capacity ของ Sprint ให้ Technical Debt อย่างชัดเจน

แนวปฏิบัติที่พบได้บ่อยในทีมมืออาชีพคือการตกลงล่วงหน้ากับ Product Owner ว่าจะจัดสรร **10–20% ของ capacity ในแต่ละ Sprint** ให้กับงาน Technical Debt/Maintenance โดยอัตโนมัติ (บางทีมเรียกวิธีนี้ว่า "20% time" หรือ "maintenance budget") แทนที่จะรอให้ debt สะสมจนต้องมี "Tech Debt Sprint" แยกต่างหากเป็นครั้งคราว ซึ่งมักถูกเลื่อนออกไปเรื่อย ๆ เพราะ feature ใหม่ดูสำคัญกว่าเสมอในสายตาธุรกิจ

#### 5. ทำ Debt ให้ "มองเห็นผลกระทบทางธุรกิจ" ได้

Technical Debt issue ที่ดีไม่ควรเขียนแค่ "โค้ดตรงนี้ไม่สวย" แต่ควรอธิบายผลกระทบเชิงธุรกิจให้ Product Owner ตัดสินใจจัดลำดับความสำคัญได้ เช่น:

```markdown
## [Tech Debt] Dependency `express@3.x` หมดอายุการซัพพอร์ตแล้ว

**ผลกระทบถ้าไม่แก้:**
- ไม่มี security patch ใหม่จากทีม Express อีกต่อไป
- Library อื่นที่ทีมต้องการอัปเดตในอนาคต (เช่น body-parser เวอร์ชันใหม่) ไม่รองรับ Express 3.x แล้ว
- ความเสี่ยง: สูง (มี CVE ที่ยังไม่ patch จำนวน 2 รายการ)

**Effort โดยประมาณ:** 3 story points

**คำแนะนำ:** ควรจัดเข้า Sprint ภายใน 1 เดือนข้างหน้า ก่อนที่จะมีการเพิ่ม dependency ใหม่ที่ผูกกับเวอร์ชันนี้มากขึ้นไปอีก
```

การเขียนแบบนี้ช่วยให้ Technical Debt แข่งขันอย่างเป็นธรรมกับ feature อื่น ๆ ใน Backlog แทนที่จะถูกมองข้ามเพราะ "ดูเป็นเรื่องทางเทคนิคที่ไม่มีใครสนใจ"

## Step 907: Story Point Estimation กับความซับซ้อนของ PR ที่แท้จริง (ทำไม estimate มักผิดพลาด)

### Story Point คืออะไร

**Story Point** คือหน่วยวัด **ความซับซ้อนสัมพัทธ์ (relative complexity)** ของงานชิ้นหนึ่ง เทียบกับงานชิ้นอื่นในทีมเดียวกัน ไม่ใช่หน่วยวัดเวลาโดยตรง (เช่น ไม่ใช่ "1 point = 1 ชั่วโมง") ทีมมักใช้ตัวเลขในชุด **Fibonacci ที่ปรับแล้ว** (1, 2, 3, 5, 8, 13, 21, ...) เพราะยิ่งงานใหญ่ขึ้น ความไม่แน่นอนก็ยิ่งสูงขึ้นแบบไม่เป็นเส้นตรง การเว้นช่วงตัวเลขให้ห่างขึ้นเรื่อย ๆ จึงสะท้อนความเป็นจริงมากกว่าสเกลเชิงเส้น (1, 2, 3, 4, 5...)

กระบวนการที่นิยมใช้ประเมิน Story Point คือ **Planning Poker** — สมาชิกทีมแต่ละคนเลือกตัวเลขพร้อมกัน (มักใช้การ์ดคว่ำหรือแอปดิจิทัล) แล้วเปิดพร้อมกัน ถ้าตัวเลขต่างกันมาก ให้อภิปรายเหตุผลแล้วโหวตใหม่ กระบวนการนี้ช่วยลดอคติจากการที่คนพูดคนแรกชี้นำความเห็นของคนอื่น (anchoring bias)

### ทำไม Story Point จึงมักประเมินผิดพลาดเมื่อเทียบกับความซับซ้อนจริงของ PR

นี่คือประเด็นที่ทีมพัฒนาซอฟต์แวร์เกือบทุกทีมเจอ ไม่ว่าจะมีประสบการณ์มากแค่ไหน สาเหตุหลักมีดังนี้:

#### 1. Estimate มักประเมินแค่ "การเขียนโค้ด" แต่ไม่รวม "ต้นทุนแฝงของ Git workflow"

เวลาที่ทีมประเมิน Story Point มักคิดถึงแค่ "เขียน logic นี้ยากแค่ไหน" แต่ในความเป็นจริง ระยะเวลาที่ใช้จริงตั้งแต่เริ่ม branch จนถึง merge สำเร็จ (Cycle Time ที่เรียนใน Step 905) มีต้นทุนแฝงจำนวนมากที่ไม่ถูกนับตอน estimate:

- เวลารอคิว code review จาก reviewer ที่ไม่ว่าง
- รอบการแก้ไขตามคอมเมนต์ของ reviewer (round-trip)
- เวลารอ CI pipeline รัน (ยิ่ง test suite ใหญ่ ยิ่งรอนาน)
- Merge conflict ที่เกิดจาก branch อื่นที่ merge ก่อนหน้า ต้อง rebase/resolve ใหม่
- Context switching เมื่อถูกดึงไปช่วยงานด่วนระหว่างทำ Story นี้

#### 2. "Unknown Unknowns" — สิ่งที่ไม่รู้ว่าไม่รู้

เมื่อประเมิน Story ก่อนเริ่มลงมือทำจริง ทีมมักมองเห็นแค่ความซับซ้อนที่ **คาดการณ์ได้ล่วงหน้า** (known unknowns) เช่น "ต้องเขียน API ใหม่ 2 endpoint" แต่พอลงมือทำจริงถึงจะเจอปัญหาที่ **ไม่มีใครคาดคิดมาก่อน** (unknown unknowns) เช่น library ที่ใช้อยู่มี bug แปลก ๆ กับ edge case นี้โดยเฉพาะ หรือ schema ของฐานข้อมูลเดิมออกแบบมาไม่รองรับ requirement ใหม่เลย

#### 3. ขนาด PR ที่แท้จริงมักใหญ่กว่าที่คาดไว้ตอน Planning

ตอน Sprint Planning ทีมมักจินตนาการว่า Story หนึ่งใบจะสร้างการเปลี่ยนแปลงในโค้ด "เท่านี้" แต่พอเริ่มเขียนจริงมักพบว่าต้องแตะไฟล์ที่ไม่คาดคิดไว้ก่อน เช่น ต้องแก้ type definition ที่ใช้ร่วมกันทั้งระบบ ทำให้ PR ขยายขนาดเกินคาด ซึ่งย้อนกลับไปกระทบ Cycle Time ตามที่อธิบายในข้อ 1

#### 4. Definition of Done ที่เข้มงวดขึ้นทำให้ effort เพิ่มขึ้นโดยไม่ถูกนับใน estimate เดิม

ถ้าทีมเพิ่งเพิ่มเกณฑ์ใหม่เข้าไปใน Definition of Done (เช่น เพิ่มเกณฑ์ coverage ขั้นต่ำ หรือบังคับให้เขียน integration test เพิ่ม) แต่ทีมยัง estimate ด้วยความเคยชินแบบเดิม (ที่ไม่รวมงานเพิ่มนี้) ตัวเลข Story Point เดิมจะประเมินต่ำกว่าความเป็นจริงเสมอจนกว่าทีมจะปรับฐานความเข้าใจใหม่ (recalibrate)

#### 5. ความแตกต่างระหว่างสมาชิกในทีม (Estimation ไม่ใช่ค่าคงที่สากล)

Story Point เป็นหน่วยวัดที่ **สัมพัทธ์กับทีมหนึ่ง ๆ เท่านั้น** Story ที่คนหนึ่งประเมินไว้ 3 point อาจใช้เวลาต่างกันมากถ้าทำโดยคนละคน เพราะความคุ้นเคยกับส่วนของโค้ดที่ต้องแก้ไม่เท่ากัน นี่คือเหตุผลที่ **ห้ามเปรียบเทียบ Story Point ข้ามทีม** และห้ามใช้ Story Point เป็นตัวชี้วัดผลงานรายบุคคลโดยเด็ดขาด

### วิธีใช้ข้อมูลจริงจาก Git ช่วยปรับปรุงความแม่นยำของการ estimate

แนวทางที่ทีมมืออาชีพใช้เพื่อลดช่องว่างระหว่าง Estimate กับความจริง คือการนำข้อมูลจาก Git มาเทียบย้อนหลังกับ Story Point ที่เคย estimate ไว้:

```
ตัวอย่างตารางเปรียบเทียบท้าย Sprint

| Story         | Story Point | PR Size (บรรทัด) | Cycle Time จริง |
|---------------|-------------|-------------------|------------------|
| #142 (reset)  | 3           | 245               | 2.1 วัน          |
| #150 (search) | 5           | 610               | 5.4 วัน          |
| #151 (export) | 3           | 90                | 0.8 วัน          |
| #155 (import) | 5           | 580               | 4.9 วัน          |
```

จากตารางนี้ ทีมจะเริ่มเห็นแนวโน้มว่า Story ที่ประเมิน 3 point บางใบ (#151) ใช้เวลาน้อยกว่าที่คาดมาก ในขณะที่บางใบ (#142) มี PR ขนาดใหญ่กว่าที่ควรจะเป็นสำหรับ 3 point เมื่อสะสมข้อมูลแบบนี้ไปหลาย Sprint ทีมจะค่อย ๆ **ปรับเทียบสัญชาตญาณของตัวเอง (calibrate)** ให้ประเมินได้แม่นยำขึ้นเรื่อย ๆ โดยไม่ต้องพึ่งสูตรคำนวณตายตัว เพราะ Story Point โดยธรรมชาติแล้วเป็นการประมาณด้วยสัญชาตญาณของทีมที่ฝึกฝนผ่านประสบการณ์ ไม่ใช่วิทยาศาสตร์ที่แม่นยำ 100%

### ข้อควรระวังสำคัญ: อย่าไล่ตาม "ความแม่นยำสมบูรณ์แบบ"

เป้าหมายของการ estimate ไม่ใช่การทำนายอนาคตให้แม่นยำ 100% (ซึ่งเป็นไปไม่ได้ในงานที่มีความไม่แน่นอนสูงอย่างซอฟต์แวร์) แต่คือการทำให้ทีมสามารถ **วางแผน Sprint ได้อย่างสมเหตุสมผลพอที่จะไม่รับงานเกิน capacity ตัวเองซ้ำ ๆ** Retrospective ที่ดีจะโฟกัสที่คำถาม "ทำไมตัวเลขถึงต่างจากที่คาด และเราเรียนรู้อะไรจากมันได้บ้าง" มากกว่าการพยายามหาสูตรวิเศษที่ทำให้ estimate แม่นยำเป๊ะทุกครั้ง

## Step 908: Daily Standup และการรายงานความคืบหน้าผ่าน commit/PR status แทนการรายงานปากเปล่าล้วน

### Daily Scrum คืออะไรกันแน่ (และมันไม่ใช่ "การรายงานสถานะให้ Scrum Master ฟัง")

**Daily Scrum** (มักเรียกกันติดปากว่า Daily Standup) คือประชุมสั้น ๆ ไม่เกิน 15 นาที ที่ทีม Developer จัดขึ้นทุกวันในเวลาและสถานที่เดียวกัน จุดประสงค์ตาม Scrum Guide คือให้ **ทีมตรวจสอบความคืบหน้าของตัวเองต่อ Sprint Goal และปรับแผนการทำงานของวันนั้น** ประเด็นสำคัญที่มักเข้าใจผิดคือ:

- Daily Scrum **เป็นของทีม Dev เอง ไม่ใช่การรายงานให้ Scrum Master หรือ PO ฟัง** (แม้ทั้งสองบทบาทจะเข้าร่วมสังเกตการณ์ได้)
- รูปแบบ 3 คำถามคลาสสิก ("เมื่อวานทำอะไร, วันนี้จะทำอะไร, มีอะไรติดขัด") เป็นแค่ **ตัวอย่างหนึ่ง** ที่ Scrum Guide เคยแนะนำ ไม่ใช่กฎตายตัวที่ทุกทีมต้องทำตามเป๊ะ ๆ

### ปัญหาคลาสสิกของ Daily Standup ที่กลายเป็น "พิธีกรรมรายงานสถานะ"

ในทีมจำนวนมาก Daily Standup เสื่อมสภาพกลายเป็น **"status theater"** — แต่ละคนพูดวนซ้ำทุกวันว่า "เมื่อวานทำ feature X ต่อ วันนี้ทำ feature X ต่อ ไม่มีอะไรติดขัด" โดยไม่มีใครฟังจริง ๆ เพราะมันไม่ใช่ข้อมูลที่มีคุณค่าต่อการตัดสินใจ ทีมประชุมแค่ "ให้ครบพิธี" แต่ไม่ได้เปิดเผยอุปสรรคจริงที่กระทบ Sprint Goal

### แนวทางแก้ไข: ให้สถานะ Git/PR เป็น "ข้อมูลพื้นฐาน" ที่ทุกคนเห็นล่วงหน้า แล้วใช้เวลาคุยเรื่องที่สำคัญจริง ๆ

หลักการสำคัญคือ **ข้อมูลที่ระบบสามารถแสดงให้เห็นเองได้อยู่แล้ว ไม่ควรถูกพูดซ้ำด้วยปากเปล่าใน Standup** — สิ่งที่ commit history, PR status และ Sprint board แสดงให้เห็นอยู่แล้วแบบ real-time คือ **"ข้อเท็จจริงของสิ่งที่เกิดขึ้น"** ในขณะที่สิ่งที่มนุษย์ต้องพูดคุยกันคือ **"อุปสรรคและการตัดสินใจ"** ซึ่งเป็นสิ่งที่ระบบบอกไม่ได้

**ข้อมูลที่ควรดูจาก Git/board ก่อนเข้า Standup (ไม่ต้องพูดในที่ประชุม):**

- Sprint board (GitHub Projects Board view / GitLab Issue Board) ว่า card ไหนอยู่คอลัมน์ไหน
- PR ที่เปิดค้างอยู่ พร้อมสถานะ CI (เขียว/แดง/กำลังรัน) และจำนวนวันที่ค้าง
- Commit ที่เกิดขึ้นเมื่อวานในแต่ละ branch (ดูได้จาก activity feed ของ repo)
- PR ที่รออยู่ในคิวรีวิวของตัวเอง (assigned as reviewer แต่ยังไม่ได้ดู)

**สิ่งที่ควรเอาเวลามาพูดคุยกันจริง ๆ ใน Standup:**

- "PR #150 ค้างรีวิวมา 2 วันแล้วเพราะไม่มีใครว่าง ใครช่วยรีวิวได้บ้างวันนี้"
- "ผมติดปัญหา merge conflict กับงานของคุณ B ต้องคุยกันก่อนว่าจะแก้ schema ยังไง"
- "CI ของ branch ผมแดงมา 2 รอบแล้วจากปัญหา flaky test ต้องขอเวลาทีม infra ช่วยดู"
- "Story #155 ผมเจอ requirement ที่ไม่ชัดเจน ต้องคุยกับ PO ก่อนถึงจะทำต่อได้"

### การตั้งค่าให้ Sprint board/PR status "รายงานตัวเองอัตโนมัติ" ก่อนเข้า Standup

หลายทีมตั้งค่าบอทหรือ integration ให้สรุปสถานะ Git ส่งเข้า channel การสื่อสารของทีม (เช่น Slack/Teams) โดยอัตโนมัติทุกเช้าก่อนเวลา Standup เช่น:

```
[Daily Git Summary — 26 ม.ค. 2026]

PR ที่ merge เมื่อวาน (3):
✅ #148 feature/142-password-reset (โดย Alice)
✅ #149 bugfix/87-cart-rounding (โดย Bob)
✅ #151 docs/update-api-reference (โดย Carol)

PR ที่ยังเปิดค้างอยู่ (2):
🟡 #150 feature/150-search-autocomplete (CI: กำลังรัน, ค้างมา 1 วัน, รอ review จาก Dave)
🔴 #152 feature/155-bulk-import (CI: ล้มเหลว — unit test 3 รายการ, ค้างมา 2 วัน)

Issue ที่ยังไม่เริ่ม branch ใด ๆ ใน Sprint 23 (1):
⬜ #156 chore/upgrade-eslint-config
```

เมื่อทุกคนเห็นภาพนี้ **ก่อน** เข้าห้อง Standup การประชุมจะไม่เสียเวลาไล่รายงานทีละคนว่า "เมื่อวานทำอะไร" (เพราะเห็นแล้วจากสรุปนี้) แต่จะเข้าประเด็นตรง ๆ ได้ทันทีว่า "PR #152 CI แดงมา 2 วันแล้ว มีใครช่วยดูได้ไหม" ซึ่งเป็นการใช้เวลา 15 นาทีของทั้งทีมอย่างมีคุณค่าที่สุด

### ข้อควรระวัง: สถานะ Git ไม่สามารถแทนที่การพูดคุยได้ทั้งหมด

สิ่งสำคัญที่ต้องย้ำคือ ข้อมูลจาก Git/PR **เป็นส่วนเสริม ไม่ใช่ตัวแทนทั้งหมดของ Daily Scrum** เพราะข้อมูลเหล่านี้บอกได้แค่ "อะไรเกิดขึ้นในโค้ด" แต่บอกไม่ได้ว่า:

- คนในทีมกำลังเผชิญความเครียดหรือภาระงานที่หนักเกินไปหรือไม่
- มีความเข้าใจไม่ตรงกันระหว่างทีมเกี่ยวกับ Sprint Goal หรือไม่
- มีปัจจัยภายนอกทีม (เช่น รอทีมอื่น รอ vendor) ที่กำลังบล็อกงานอยู่โดยที่ไม่ปรากฏใน Git เลย

ดังนั้นเป้าหมายที่ถูกต้องคือ **ใช้ Git/PR status ตัดขั้นตอน "รายงานข้อเท็จจริงที่เห็นได้อยู่แล้ว" ออกไป เพื่อเอาเวลาที่เหลือทั้งหมดไปทุ่มกับการพูดคุยเรื่องอุปสรรคและการตัดสินใจที่มีแต่มนุษย์เท่านั้นที่ให้คำตอบได้**

## Step 909: Kanban vs Scrum กับ workflow ของ Git (WIP limit เชื่อมโยงกับ GitHub Projects Board จาก Part 23)

### Kanban คืออะไร

**Kanban** เป็นอีกหนึ่งกรอบการทำงานภายใต้ปรัชญา Agile เช่นเดียวกับ Scrum แต่มีที่มาแตกต่างกันโดยสิ้นเชิง — Kanban มีรากฐานมาจากระบบการผลิตของ **Toyota Production System** ในอุตสาหกรรมยานยนต์ ถูกนำมาปรับใช้กับงานความรู้ (knowledge work) รวมถึงงานพัฒนาซอฟต์แวร์โดย **David J. Anderson**

หลักการสำคัญของ Kanban มี 4 ข้อหลัก:

1. **มองเห็นงานทั้งหมด (Visualize the workflow)** — ใช้บอร์ดแสดงสถานะงานทุกชิ้นเป็นคอลัมน์
2. **จำกัดปริมาณงานที่ทำพร้อมกัน (Limit Work In Progress — WIP limit)** — กำหนดเพดานจำนวนงานสูงสุดที่แต่ละคอลัมน์รับได้พร้อมกัน
3. **จัดการการไหลของงาน (Manage flow)** — เน้นให้งานไหลผ่านระบบอย่างสม่ำเสมอ ไม่ติดขัด
4. **ปรับปรุงอย่างต่อเนื่อง (Continuous improvement / Kaizen)** — ปรับกระบวนการทีละเล็กละน้อยตลอดเวลา ไม่ใช่แค่ตอน Retro

### ความแตกต่างพื้นฐานระหว่าง Kanban กับ Scrum

| มิติ | Scrum | Kanban |
|---|---|---|
| หน่วยของเวลา | Sprint (time-box คงที่ เช่น 2 สัปดาห์) | ไม่มี time-box บังคับ ทำงานแบบไหลต่อเนื่อง (continuous flow) |
| การวางแผน | วางแผนล่วงหน้าเป็นชุดตอน Sprint Planning | ดึงงานเข้ามาทีละชิ้นเมื่อมีที่ว่าง (pull-based) ไม่ต้องวางแผนเป็นชุดล่วงหน้า |
| บทบาทบังคับ | PO, Scrum Master, Developers (ระบุชัดเจนใน Scrum Guide) | ไม่มีบทบาทบังคับตายตัว |
| การวัดผล | Velocity (Story Point ที่ทำเสร็จต่อ Sprint) | Lead Time / Cycle Time ต่อชิ้นงาน |
| กลไกควบคุมปริมาณงาน | Sprint Backlog ที่ล็อกขอบเขตไว้ตอนต้น Sprint | WIP Limit ต่อคอลัมน์ ควบคุมตลอดเวลาแบบต่อเนื่อง |
| เหมาะกับงานประเภทไหน | งานที่วางแผนเป็นชุดได้ มี Sprint Goal ชัดเจน | งานที่มีลักษณะ "รับคำขอเข้ามาเรื่อย ๆ" เช่น Support, Maintenance, Bug triage |

### WIP Limit คืออะไร และทำไมมันสำคัญมาก

**WIP Limit (Work In Progress Limit)** คือการกำหนด **จำนวนสูงสุด** ของงานที่อนุญาตให้อยู่ในสถานะใดสถานะหนึ่งพร้อมกันได้ เช่น กำหนดว่าคอลัมน์ "In Progress" รับได้สูงสุดแค่ **3 งานต่อครั้ง** ถ้าคอลัมน์เต็มแล้ว ทีมจะ **ห้ามดึงงานใหม่เข้ามาเพิ่มเด็ดขาด** จนกว่าจะมีงานไหลออกจากคอลัมน์นั้นก่อน (ทำเสร็จหรือย้ายไปคอลัมน์ถัดไป)

หลักการเบื้องหลัง WIP Limit มาจากกฎที่เรียกว่า **Little's Law** ในทฤษฎีแถวคอย (queueing theory):

```
Lead Time = Work In Progress ÷ Throughput
```

ถ้าปริมาณงานที่ทำพร้อมกัน (WIP) สูงเกินไปเทียบกับความสามารถของทีมในการทำงานให้เสร็จ (Throughput) เวลาที่งานแต่ละชิ้นต้องรอคิว (Lead Time) จะยืดยาวขึ้นเรื่อย ๆ แบบไม่เป็นสัดส่วนเชิงเส้น — นี่คือเหตุผลเชิงคณิตศาสตร์ว่าทำไม "การทำหลายอย่างพร้อมกัน" มักทำให้งานทุกอย่างช้าลงพร้อมกันหมด ทั้งที่ความรู้สึกโดยสัญชาตญาณของคนมักบอกว่ายิ่งเริ่มงานเยอะ ยิ่งได้งานเยอะ ซึ่งเป็นความเข้าใจผิดที่พบบ่อยมาก

### การนำ WIP Limit มาใช้กับ GitHub Projects Board (เชื่อมโยงกับ Part 23)

ใน **Part 23** เราได้เรียนรู้ Board View ของ GitHub Projects (v2) ที่แสดงผลเป็นคอลัมน์ Kanban ตาม field Status แม้ GitHub Projects จะ **ไม่มีกลไกบังคับ WIP Limit แบบ hard-block ในตัว** (ไม่เหมือนเครื่องมือ Kanban เฉพาะทางบางตัวที่จะเปลี่ยนสีคอลัมน์เป็นแดงหรือห้ามลากการ์ดเข้าไปเพิ่มเมื่อเกินโควตา) แต่ทีมสามารถ **สร้างวินัยของทีมเอง** โดยใช้ Board ของ GitHub Projects ร่วมกับกฎที่ตกลงกันไว้:

1. ตั้งชื่อคอลัมน์ให้ระบุ WIP Limit ไว้ตรง ๆ เช่น `In Progress (Max 3)`, `In Review (Max 4)`
2. ใช้ automation ของ Projects (ตามที่เรียนใน Part 23) ตั้ง Insight/Chart นับจำนวนการ์ดในแต่ละ Status แบบ real-time เพื่อให้ทีมเห็นตัวเลขชัดเจนตลอดเวลา
3. ผูกกฎเข้ากับ Definition of Working Agreement ของทีม: "ถ้าคอลัมน์ In Progress มีครบ 3 การ์ดแล้ว ห้ามใครเริ่ม branch ใหม่เพิ่มจนกว่าจะมีงานถูกย้ายออก"
4. เชื่อมกับพฤติกรรมจริงในการเปิด branch: ก่อนจะ `git checkout -b` สร้าง branch ใหม่ ให้เช็คก่อนว่าคอลัมน์ In Progress เต็มโควตาหรือยัง — ถ้าเต็ม ให้ไปช่วย review PR ที่ค้างอยู่แทนการเริ่มงานใหม่

### ทีมจำนวนมากใช้ทั้งสองแบบผสมกัน (Scrumban)

ในทางปฏิบัติจริง ทีมพัฒนาซอฟต์แวร์จำนวนมากไม่ได้เลือกใช้ Scrum หรือ Kanban แบบสุดโต่งด้านใดด้านหนึ่ง แต่ผสมผสานทั้งสองแนวคิดเข้าด้วยกัน เรียกว่า **Scrumban** — ใช้โครงสร้าง Sprint แบบ Scrum (มี Sprint Planning, Review, Retro เป็นจังหวะ) ควบคู่กับการใช้ **WIP Limit แบบ Kanban** ควบคุมปริมาณงานระหว่าง Sprint เพื่อป้องกันไม่ให้สมาชิกทีมเริ่มงานหลายอย่างพร้อมกันจนไม่มีอะไรเสร็จสักอย่างในช่วงกลาง Sprint

ในบริบท Git workflow วิธี Scrumban มักแปลงเป็นกฎง่าย ๆ ว่า **"หนึ่งคนควรมี branch/PR ที่ active อยู่ไม่เกิน 1–2 อันในเวลาเดียวกัน"** เพื่อลดปัญหา context switching ที่ทำให้ทั้ง Cycle Time และคุณภาพของโค้ดแย่ลงตามที่อธิบายไปแล้วใน Step 905 และ 907

### ตารางสรุปว่าควรเลือกแบบไหน

| ลักษณะทีม/งาน | แนวทางที่เหมาะสม |
|---|---|
| ทีมพัฒนา Product ที่มี Roadmap ชัดเจน วางแผนล่วงหน้าได้ | Scrum |
| ทีม Support/Maintenance ที่รับ ticket เข้ามาไม่แน่นอน | Kanban |
| ทีมที่อยากมีจังหวะ Retro/Review สม่ำเสมอ แต่งานมีลักษณะไหลเข้ามาไม่สม่ำเสมอ | Scrumban |
| ทีมเล็กมาก (1–3 คน) ที่ overhead ของพิธีกรรม Scrum เต็มรูปแบบสูงเกินไป | Kanban แบบง่าย + WIP Limit |

## Step 910: แบบฝึกหัด — จำลอง 1 Sprint เต็มรูปแบบ (2 สัปดาห์) ที่เชื่อม Git workflow เข้ากับ Scrum board

ถึงเวลาเอาทุกอย่างที่เรียนมาใน Part นี้มาประกอบร่างเป็นภาพเดียว แบบฝึกหัดนี้จะให้คุณจำลอง **Sprint หนึ่งเต็มรูปแบบ** ตั้งแต่วันแรกจนถึงวันสุดท้าย โดยไม่จำเป็นต้องมีทีมจริง — คุณสามารถทำคนเดียวโดยสวมบทบาทหลายตำแหน่งสลับกันไปเพื่อฝึกความเข้าใจกระบวนการทั้งหมด

### เตรียมความพร้อมก่อนเริ่ม

สร้าง repository ทดลองใหม่บน GitHub (หรือใช้ repo ฝึกฝนที่มีอยู่แล้วจาก Part ก่อนหน้า):

```bash
mkdir sprint-simulation && cd sprint-simulation
git init
git branch -M main
echo "# Sprint Simulation Project" > README.md
git add README.md
git commit -m "chore: initial commit"
```

Push ขึ้น GitHub แล้วเปิดใช้งาน **GitHub Projects** สำหรับ repo นี้ตามที่เรียนใน Part 23

### วันที่ 0 — Sprint Planning (จำลอง)

**ภารกิจ:**

1. เปิด Product Backlog สมมติที่มี User Story อย่างน้อย 8 ใบ เขียนในรูปแบบ:
   ```
   ในฐานะ...
   ฉันต้องการ...
   เพื่อที่...
   ```
2. สร้างแต่ละ Story เป็น GitHub Issue จริง ใส่ Acceptance Criteria เป็น checklist ในตัว issue
3. เปิด GitHub Projects เพิ่ม field ประเภท **Iteration** ตั้งความยาว 2 สัปดาห์ (ตาม Step 903)
4. เลือก Story 5 ใบเข้า Sprint นี้ (เหลืออีก 3 ใบไว้ใน Backlog สำหรับ Sprint ถัดไป) — กำหนดค่า Iteration ของทั้ง 5 issue ให้เป็น "Sprint 1"
5. ประเมิน Story Point ให้แต่ละใบ (ใช้สเกล 1, 2, 3, 5, 8) บันทึกไว้เป็น custom field ใน Projects
6. เขียน **Sprint Goal** หนึ่งประโยคไว้ในคำอธิบายของ Iteration เช่น "ผู้ใช้สามารถสมัครสมาชิกและรีเซ็ตรหัสผ่านได้ครบวงจร"
7. เขียน **Definition of Done** ของทีม (อ้างอิงจาก Step 904) ไว้เป็นไฟล์ `DEFINITION_OF_DONE.md` ใน repo แล้ว commit

```bash
git add DEFINITION_OF_DONE.md
git commit -m "docs: add team definition of done"
git push
```

8. ตั้งค่า Branch Protection Rule บน `main`: บังคับ require approval อย่างน้อย 1 คน, require status check ผ่าน, require conversation resolution

### วันที่ 1–8 — จำลองการทำงานระหว่าง Sprint

สำหรับแต่ละ Story ที่เลือกเข้า Sprint ให้ทำตามลำดับนี้ (ทำซ้ำ 5 รอบ หรือมากกว่านั้นถ้าต้องการฝึกกรณี spillover):

1. **เริ่มงาน:** สร้าง branch จาก issue โดยตรงผ่านปุ่ม "Create a branch" (ตาม Step 902) เพื่อให้ผูกกับ issue อัตโนมัติ
   ```bash
   git fetch origin
   git checkout -b feature/1-user-signup origin/main
   ```
2. **ลงมือทำ:** เขียนโค้ดจำลอง (ไฟล์อะไรก็ได้ ไม่จำเป็นต้องเป็นแอปจริง) แบ่งเป็นหลาย commit เล็ก ๆ ที่มีความหมายชัดเจนตามหลัก Conventional Commits ที่เรียนใน Part 35
   ```bash
   git add .
   git commit -m "feat(auth): add signup form validation"
   git add .
   git commit -m "test(auth): add unit test for signup validation"
   ```
3. **เปิด PR:** เปิด Pull Request กลับเข้า `main` ใส่คำอธิบาย พร้อม closing keyword เช่น `Closes #1`
4. **ย้ายการ์ดใน Sprint board:** ย้าย Status ของ issue นี้จาก "Todo" ไปเป็น "In Progress" แล้วไปเป็น "In Review" เมื่อ PR เปิดแล้ว (จำลองการทำตาม WIP Limit สูงสุด 2 งานพร้อมกัน ตาม Step 909)
5. **จำลอง Code Review:** ถ้าทำคนเดียว ให้เปิดจากอีก account หนึ่ง หรือขอเพื่อนช่วยกด Approve/Request changes อย่างน้อยหนึ่งรอบ เพื่อฝึกกระบวนการจริง
6. **Merge:** เมื่อ CI ผ่าน (ตั้ง GitHub Actions ง่าย ๆ ที่รัน lint/test) และได้รับ approve แล้ว ให้กด Merge แล้วลบ branch ทิ้ง — ย้ายการ์ดไปคอลัมน์ "Done"
7. **บันทึกข้อมูลไว้สำหรับ Retro:** จดเวลาที่ branch เริ่มสร้าง กับเวลาที่ PR merge สำเร็จของแต่ละ Story ไว้ในตารางแยก (จะใช้ตอน Retro)

ทำซ้ำขั้นตอนนี้จน Story ทั้ง 5 ใบเสร็จ หรือถ้าต้องการฝึกสถานการณ์จริงมากขึ้น ให้จงใจปล่อยให้ 1 Story ทำไม่เสร็จภายในกำหนด (จำลอง spillover) เพื่อฝึกวันที่ 9 ต่อไป

### วันที่ 9 — Sprint Review (จำลอง)

1. เปิดดู PR ที่ merge เข้า `main` สำเร็จทั้งหมดใน Sprint นี้
2. เขียนสรุปสั้น ๆ ในรูปแบบ Release Note ว่า Sprint นี้ส่งมอบอะไรบ้าง (จำลองการ demo ให้ stakeholder ดู)
3. ตรวจสอบ Story ที่ไม่เสร็จ (ถ้ามี) — ย้าย issue นั้นกลับเข้า Product Backlog หรือย้ายเข้า Iteration ถัดไป (Sprint 2) แทนที่จะปล่อยค้างไว้เฉย ๆ

### วันที่ 10 — Sprint Retrospective (จำลอง) พร้อมข้อมูลจริงจาก Git

1. ดึงข้อมูล Cycle Time ของแต่ละ PR ที่บันทึกไว้ระหว่างทาง คำนวณค่าเฉลี่ย
2. รันคำสั่งดูขนาดของแต่ละ PR ที่ merge ไปแล้ว:
   ```bash
   git log main --merges --format="%H %s" | head -5
   ```
   จากนั้นสำหรับแต่ละ merge commit ให้ดูขนาดการเปลี่ยนแปลงย้อนหลังด้วย:
   ```bash
   git show --stat <merge-commit-hash>
   ```
3. สร้างตารางสรุปแบบเดียวกับตัวอย่างใน Step 905 (Story / Story Point / PR Size / Cycle Time)
4. เขียนสรุป Retro 3 หัวข้อ: **What went well? What didn't go well? What will we improve next Sprint?** โดยอ้างอิงตัวเลขจากตารางในข้อ 3 ประกอบทุกข้อ ไม่ใช่แค่ความรู้สึก
5. ถ้ามี Story ที่ estimate ผิดพลาดมาก (เช่น ประเมิน 2 point แต่ PR ใหญ่และ Cycle Time นานผิดปกติ) ให้เขียนวิเคราะห์สาเหตุตามแนวทาง Step 907 ว่าเป็น unknown unknown, ต้นทุนแฝงจาก Git workflow หรือ DoD ที่เข้มขึ้น
6. ถ้าระหว่าง Sprint คุณเจอสิ่งที่ควรเป็น Technical Debt (เช่น โค้ดที่เขียนลวก ๆ เพื่อให้ทันตามกำหนด) ให้สร้าง Issue ติด label `tech-debt` ไว้ทันที (ตาม Step 906) ก่อนที่จะลืมมันไป

### เกณฑ์ตรวจสอบว่าทำแบบฝึกหัดนี้ครบถ้วน

- [ ] มี Product Backlog อย่างน้อย 8 Story เป็น GitHub Issue จริง
- [ ] มี Sprint (Iteration) ที่ตั้งค่าไว้ใน GitHub Projects พร้อม Sprint Goal
- [ ] ทุก branch ที่สร้างตั้งชื่อตามรูปแบบ `<type>/<issue-id>-<desc>` และผูกกับ issue จริง
- [ ] มี Definition of Done เป็นลายลักษณ์อักษรใน repo และถูกบังคับใช้จริงผ่าน branch protection
- [ ] มี PR อย่างน้อย 4–5 ใบที่ผ่านกระบวนการ review และ merge จริง
- [ ] มีการจำลอง spillover อย่างน้อย 1 Story และจัดการอย่างถูกต้องใน Sprint Review
- [ ] มีตารางเปรียบเทียบ Story Point กับ PR Size/Cycle Time จริงที่ใช้ประกอบ Retro
- [ ] มี Retro summary ที่อ้างอิงข้อมูลจาก Git จริง ไม่ใช่แค่ความรู้สึกล้วน ๆ
- [ ] มี Issue อย่างน้อย 1 รายการที่ติด label `tech-debt` ถูกสร้างขึ้นระหว่างจำลอง Sprint

## สรุป Part 91

ใน Part นี้เราได้เรียนรู้ว่า:

1. **Scrum เป็นกรอบการทำงานที่เป็นกลางทางเทคนิค** — Product Backlog, Sprint, User Story, Sprint Backlog, Definition of Done ไม่ได้ผูกกับ Git โดยตรง แต่ทีมพัฒนาซอฟต์แวร์ต้อง "จับคู่" แนวคิดเหล่านี้เข้ากับเครื่องมือ Git/GitHub/GitLab ด้วยตัวเอง
2. **Branch ควรผูกกับ "งาน" (Story/Issue ID) ไม่ใช่ผูกกับ "เวลา" (Sprint number)** — ยกเว้น release branch เท่านั้นที่ผูกกับเวลาได้ตามธรรมชาติ
3. **Sprint ที่แท้จริงในเครื่องมือคือ Iteration บน GitHub Projects หรือ Milestone/Iteration บน GitLab** — ต้องตั้งค่าให้ตรงกับความยาว Sprint จริง และผูก Sprint Goal ไว้ในคำอธิบายเสมอ
4. **Definition of Done ยุคใหม่ต้องรวมเกณฑ์ที่ตรวจสอบได้อัตโนมัติผ่าน Git/CI** เช่น PR merged, CI ผ่าน, ได้รับ approve ครบตามจำนวน ไม่มี unresolved conversation — และควรบังคับใช้ผ่าน branch protection rule ไม่ใช่พึ่งความจำคน
5. **Cycle Time และ PR Size เฉลี่ยเป็นข้อมูลที่มีคุณค่ามากสำหรับ Sprint Retrospective** เพราะเปลี่ยนบทสนทนาจาก "ความรู้สึก" เป็น "ข้อเท็จจริงที่วัดผลได้" — แต่ห้ามนำไปใช้ตัดสินผลงานรายบุคคลเด็ดขาด
6. **Technical Debt ต้องมีตัวตนใน issue tracker เสมอ** ผ่าน label เฉพาะ การผูก TODO comment เข้ากับหมายเลข issue และการจัดสรร capacity ของ Sprint ให้กับมันอย่างสม่ำเสมอ ไม่ปล่อยให้สะสมจนต้องแก้แบบฉุกเฉิน
7. **Story Point มักประเมินผิดพลาดเพราะไม่ได้นับต้นทุนแฝงของ Git workflow** เช่น เวลารอ review, merge conflict, CI ที่ล้มเหลว และ unknown unknowns ที่พบระหว่างลงมือทำจริง — การเทียบ Story Point กับ PR Size/Cycle Time ย้อนหลังช่วยปรับเทียบสัญชาตญาณของทีมให้แม่นยำขึ้นเรื่อย ๆ
8. **Daily Scrum ควรใช้สถานะ Git/PR เป็นข้อมูลพื้นฐานที่ทุกคนเห็นล่วงหน้า** แล้วเอาเวลาในที่ประชุมไปโฟกัสที่อุปสรรคและการตัดสินใจที่มีแต่มนุษย์เท่านั้นที่ให้คำตอบได้ ไม่ใช่ไล่รายงานสิ่งที่ระบบแสดงให้เห็นอยู่แล้ว
9. **Kanban กับ Scrum ต่างกันที่การจัดการเวลาและปริมาณงาน** — Scrum ใช้ Sprint (time-box) ส่วน Kanban ใช้ WIP Limit ควบคุมการไหลของงานแบบต่อเนื่อง ทีมจำนวนมากผสมทั้งสองแนวคิดเข้าด้วยกันเป็น Scrumban และนำ WIP Limit มาผูกกับวินัยการเปิด branch ใหม่ในทางปฏิบัติ
10. เราได้ลงมือจำลอง **Sprint เต็มรูปแบบ 2 สัปดาห์** ตั้งแต่ Planning จนถึง Retrospective โดยเชื่อม Git workflow เข้ากับ Scrum board ในทุกขั้นตอนจริง
