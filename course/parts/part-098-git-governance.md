## Step 971: Git Governance คืออะไร ทำไมองค์กรขนาดใหญ่ต้องมีมาตรฐานกลาง

### 971.1 ทบทวนสิ่งที่เรียนมาแล้ว และสิ่งที่ Part นี้จะเพิ่มเข้ามา

ใน **Part 83** เราเจาะลึกกลไก**เชิงเทคนิค**ที่ทำให้องค์กรระดับ enterprise ควบคุมมาตรฐานได้ที่ scale ใหญ่ — Organization-level Ruleset, SSO/SAML/SCIM, Standardized CI/CD Templates, Internal Developer Platform และ DORA Metrics กลไกเหล่านั้นตอบคำถามว่า **"เราบังคับใช้กฎได้อย่างไรในทางเทคนิค"**

แต่ก่อนจะมีกฎให้บังคับใช้ ต้องมีคนตอบคำถามที่มาก่อนหน้านั้นทั้งหมด:

- กฎอะไรบ้างที่องค์กรควรมี และกฎไหนที่ไม่จำเป็น
- ใครเป็นผู้มีอำนาจตัดสินใจว่ากฎนั้นคืออะไร
- จะสื่อสารกฎเหล่านั้นให้วิศวกรหลักพันคนเข้าใจตรงกันได้อย่างไร
- จะรู้ได้อย่างไรว่ากฎถูกปฏิบัติตามจริงหรือไม่ ในเมื่อ Ruleset บังคับได้แค่บางเรื่อง (เช่น branch protection) แต่บังคับเรื่องพฤติกรรมของคน (เช่น การเขียน commit message ที่มีความหมาย) ไม่ได้โดยตรง
- จะปรับปรุงกฎอย่างไรเมื่อบริบทเปลี่ยนไป โดยไม่ทำให้ทุกคนสับสน

คำถามทั้งหมดนี้คือขอบเขตของ **Git Governance** — และนี่คือความแตกต่างสำคัญที่ต้องเข้าใจตั้งแต่ต้น Part:

> **Part 83 สอนกลไก (mechanism) ที่ใช้บังคับใช้กฎ ส่วน Part 98 สอนโปรแกรม (program) ที่ตัดสินใจว่ากฎคืออะไร ดูแลให้คนปฏิบัติตามด้วยความเข้าใจ ไม่ใช่แค่ด้วยการบังคับทางเทคนิคอย่างเดียว**

### 971.2 นิยามของ Git Governance

**Git Governance** คือ **ระบบของนโยบาย กระบวนการตัดสินใจ บทบาทความรับผิดชอบ และกลไกการสื่อสาร ที่องค์กรใช้กำหนด เผยแพร่ ดูแลรักษา และปรับปรุงมาตรฐานการใช้งาน Git และแพลตฟอร์มที่เกี่ยวข้อง (GitHub/GitLab) ให้สอดคล้องกันทั่วทั้งองค์กร**

Governance ไม่ใช่แค่ "เอกสารกฎ" อย่างเดียว แต่ประกอบด้วย 4 องค์ประกอบที่ต้องทำงานร่วมกัน:

```
┌─────────────────────────────────────────────────────────┐
│                     GIT GOVERNANCE                        │
├───────────────┬───────────────┬───────────────┬──────────┤
│   นโยบาย       │   โครงสร้าง     │   กลไก          │  วัฒนธรรม  │
│  (Policy)     │  (Structure)  │  (Mechanism)  │ (Culture)│
├───────────────┼───────────────┼───────────────┼──────────┤
│ Git Standards │ Center of     │ Ruleset,      │ Champions│
│ Document      │ Excellence,   │ SSO/SCIM,     │ Program, │
│               │ RACI, Escala- │ CI/CD Template│ Recognit-│
│               │ tion path     │ (จาก Part 83) │ ion, Buy-│
│               │               │               │ in       │
└───────────────┴───────────────┴───────────────┴──────────┘
```

ถ้าองค์กรมีแค่ "นโยบาย" (เอกสารสวย ๆ) แต่ไม่มี "กลไก" บังคับใช้ กฎก็จะถูกละเลย ถ้ามีแค่ "กลไก" (Ruleset ที่เข้มงวด) แต่ไม่มี "วัฒนธรรม" ที่ยอมรับ วิศวกรจะรู้สึกว่าถูกบังคับและหาทางเลี่ยงกฎ (workaround) เสมอ Governance ที่ดีต้องมีครบทั้ง 4 องค์ประกอบพร้อมกัน

### 971.3 ทำไมองค์กรขนาดเล็กไม่ต้องการ Governance แบบเป็นทางการ

ทีมที่มีวิศวกร 10 คน นั่งห้องเดียวกัน (หรือคุยกันใน Slack channel เดียว) แทบไม่ต้องการเอกสาร governance อย่างเป็นทางการเลย เพราะ:

- ทุกคนรู้จักกันและคุยกันได้โดยตรงเมื่อมีคำถาม
- การเปลี่ยนใจเรื่องมาตรฐาน (เช่น เปลี่ยน branching strategy) ทำได้ในที่ประชุมเดียว ไม่ต้องมีกระบวนการอนุมัติซับซ้อน
- ผลกระทบของการตัดสินใจผิดพลาดจำกัดอยู่แค่ทีมเดียว ไม่กระทบทั้งบริษัท

นี่คือเหตุผลที่ startup และทีมขนาดเล็กมักมองว่า governance เป็นภาระที่ไม่จำเป็น — และในบริบทของพวกเขา **มันถูกต้อง** การมี governance แบบเป็นทางการเกินไปในทีมเล็กคือ over-engineering ขององค์กร (organizational over-engineering) ที่สร้างความล่าช้าโดยไม่ได้ประโยชน์คุ้มค่า

### 971.4 จุดเปลี่ยนที่องค์กรต้องการ Governance อย่างเป็นทางการ

จุดเปลี่ยนไม่ได้อยู่ที่ตัวเลขคงที่ตายตัว แต่มีสัญญาณที่บ่งบอกชัดเจนหลายอย่าง:

| สัญญาณ | ทำไมถึงต้องมี Governance |
|---|---|
| วิศวกรเกิน ~150 คน (Dunbar's number) | ไม่มีใครรู้จักทุกคนในองค์กรได้อีกต่อไป การสื่อสารแบบไม่เป็นทางการล้มเหลว |
| มีมากกว่า 1 ทีมที่ทำงานอิสระจากกันจริง (autonomous team) | แต่ละทีมเริ่มตัดสินใจต่างกันโดยไม่รู้ตัว จนเกิดความไม่สม่ำเสมอ |
| ต้องปฏิบัติตาม regulation ภายนอก (SOC 2, PCI-DSS, ISO 27001, GDPR) | ผู้ตรวจสอบต้องการหลักฐานที่เป็นระบบ ไม่ใช่คำบอกเล่าปากต่อปาก |
| เกิด incident ด้านความปลอดภัยที่สืบสาวไปถึงความไม่สม่ำเสมอของมาตรฐาน | บทเรียนราคาแพงที่มักเป็นจุดเริ่มต้นของโปรแกรม governance จริงจังในหลายองค์กร |
| มีคนใหม่เข้าองค์กรมากกว่า 1 คนต่อสัปดาห์ | ไม่มีเวลาสอนแบบตัวต่อตัวได้อีกต่อไป ต้องมีมาตรฐานที่ตัวเองอธิบายตัวเองได้ |
| มี Git hosting platform มากกว่า 1 ตัวใช้งานพร้อมกันโดยไม่มีเหตุผล (tool sprawl) | สัญญาณว่าไม่มีการตัดสินใจกลางเรื่องเครื่องมือ |
| ผู้บริหารเริ่มถามคำถามที่ทีมเดียวตอบไม่ได้ (เช่น "ทั้งบริษัท deploy บ่อยแค่ไหน") | ต้องมีมาตรฐานการเก็บข้อมูลที่สอดคล้องกันก่อนถึงจะตอบได้ |

องค์กรที่รอจนกว่าจะเกิด incident ร้ายแรงก่อนถึงเริ่มสร้าง governance มักต้องจ่ายราคาแพงกว่าองค์กรที่ลงทุนล่วงหน้า — นี่คือเหตุผลที่วิศวกรระดับ Staff/Principal/Tech Lead ควรเสนอเรื่อง governance ก่อนที่ปัญหาจะบานปลาย ไม่ใช่รอให้ผู้บริหารสั่งลงมาหลัง incident

### 971.5 Governance ไม่ใช่ Bureaucracy (ระบบราชการ)

ความเข้าใจผิดที่พบบ่อยที่สุดคือการมอง "governance" เท่ากับ "กฎเกณฑ์ที่ทำให้ทำงานช้าลง" ความจริงแล้ว governance ที่ดีมีเป้าหมายตรงกันข้าม:

> **Governance ที่ดีทำให้องค์กรเคลื่อนที่เร็วขึ้นในภาพรวม แม้จะดูเหมือนช้าลงในบางจุดที่ต้องผ่านขั้นตอนเพิ่ม**

เหตุผลคือ governance ที่ดีลด **coordination overhead** (ภาระการประสานงาน) ที่มิฉะนั้นแล้วแต่ละทีมต้องคิดค้นวิธีแก้ปัญหาเดียวกันซ้ำ ๆ ด้วยตัวเอง — ทีมที่ 46 ที่ต้องตัดสินใจว่าจะตั้งชื่อ branch อย่างไร ไม่ต้องเสียเวลาถกเถียงกันเองถ้ามีมาตรฐานที่ตอบคำถามนั้นไว้แล้วอย่างชัดเจนและมีเหตุผลรองรับ

ตารางเปรียบเทียบ 3 รูปแบบที่มักถูกสับสน:

| รูปแบบ | ลักษณะ | ผลลัพธ์ |
|---|---|---|
| **Anarchy (ไม่มี Governance เลย)** | แต่ละทีมตัดสินใจเองทั้งหมด ไม่มีมาตรฐานกลาง | ความคล่องตัวสูงในระยะสั้น แต่ต้นทุนการประสานงานและความเสี่ยงพุ่งสูงเมื่อ scale ใหญ่ |
| **Bureaucracy (Governance ที่ผิดวิธี)** | กฎเยอะเกินจำเป็น กระบวนการอนุมัติซับซ้อน ไม่มีการทบทวน | ทีมหาทางเลี่ยงกฎ (shadow process) ความเชื่อมั่นในส่วนกลางลดลง ความเร็วลดลงจริง |
| **Good Governance ("Freedom within a Framework")** | กำหนดกรอบขั้นต่ำที่จำเป็นจริง ๆ ปล่อยรายละเอียดให้ทีมตัดสินใจเอง มีกระบวนการทบทวนสม่ำเสมอ | ความเร็วและความปลอดภัยไปด้วยกันได้ ทีมรู้สึกได้รับการสนับสนุน ไม่ใช่ถูกควบคุม |

หลักการ **"Freedom within a Framework"** ที่กล่าวถึงสั้น ๆ ใน Part 83 (Step 821.2) คือแก่นของ Part นี้ทั้งหมด — ตลอด 10 Step ต่อจากนี้เราจะออกแบบ "กรอบ" (framework) ที่ให้อิสระกับทีมย่อยมากที่สุดเท่าที่จำเป็น โดยยังคงความปลอดภัยและความสม่ำเสมอในระดับที่องค์กรต้องการ

### 971.6 ผู้มีส่วนได้ส่วนเสียของ Git Governance

Git Governance ไม่ใช่เรื่องของทีมวิศวกรรมเพียงฝ่ายเดียว แต่เกี่ยวข้องกับผู้มีส่วนได้ส่วนเสียหลายฝ่าย ซึ่งแต่ละฝ่ายมีมุมมองและความต้องการต่างกัน:

| ผู้มีส่วนได้ส่วนเสีย | สิ่งที่ต้องการจาก Governance |
|---|---|
| **CTO / VP Engineering** | ภาพรวมสุขภาพขององค์กรวิศวกรรม ความสามารถในการปรับขนาด (scale) โดยไม่เพิ่มความเสี่ยง |
| **Security Team** | มาตรฐานความปลอดภัยที่บังคับใช้ได้จริงทุก repository ไม่มีข้อยกเว้นที่ไม่มีเหตุผล |
| **Compliance / Legal** | หลักฐานที่ตรวจสอบได้ (auditable evidence) สำหรับ SOC 2, ISO 27001, PCI-DSS ฯลฯ |
| **Platform Engineering** | มาตรฐานที่ชัดเจนพอจะนำไปสร้างเป็นเครื่องมืออัตโนมัติได้ (Ruleset, Template ตาม Part 83) |
| **Engineering Manager แต่ละทีม** | มาตรฐานที่ไม่รบกวนความสามารถในการส่งมอบงานของทีมตัวเอง |
| **วิศวกรแต่ละคน** | ความชัดเจนว่าต้องทำอะไร ทำไมต้องทำ และเครื่องมือที่ช่วยให้ทำตามมาตรฐานได้ง่าย ไม่ใช่เป็นภาระ |
| **Finance** | ต้นทุนของเครื่องมือและ license ที่ควบคุมได้ ไม่บานปลายแบบไร้ทิศทาง (เชื่อมโยงกับ Cost Management ใน Part 83 Step 829) |

การออกแบบ governance โดยไม่ฟังเสียงของฝ่ายใดฝ่ายหนึ่งมักนำไปสู่ความล้มเหลว เช่น governance ที่ออกแบบโดย Security ฝ่ายเดียวมักเข้มงวดเกินจนทีมพัฒนาไม่พอใจและหาทางเลี่ยง ในขณะที่ governance ที่ออกแบบโดยวิศวกรฝ่ายเดียวอาจไม่ผ่านการตรวจสอบจาก compliance ได้ — Step 976 จะกลับมาเจาะลึกเรื่องการจัดสมดุลนี้อีกครั้ง

## Step 972: การสร้าง Git Standards Document ระดับองค์กร

### 972.1 ทำไมต้องมีเอกสารที่เป็นลายลักษณ์อักษร

หลายองค์กรมี "มาตรฐานที่ไม่ได้เขียนไว้" (tribal knowledge) — ทุกคนรู้ว่า "เราไม่ push ตรงเข้า main" แต่ไม่มีใครเขียนไว้เป็นเอกสารที่ค้นหาได้ ปัญหาของ tribal knowledge คือ:

1. **ไม่ scale** — คนใหม่ต้องถามคนเก่าซ้ำ ๆ คำถามเดิม ๆ
2. **ไม่สอดคล้องกัน** — แต่ละคนจำมาตรฐานได้ไม่เหมือนกัน โดยเฉพาะรายละเอียดปลีกย่อย
3. **ตรวจสอบไม่ได้ (not auditable)** — เมื่อ auditor ถามว่า "นโยบายการ commit คืออะไร" คำตอบ "ทุกคนก็รู้กันอยู่แล้ว" ไม่ผ่านการตรวจสอบ
4. **หายไปเมื่อคนลาออก** — ความรู้ที่อยู่แค่ในหัวคนจะหายไปพร้อมกับการลาออกของคนนั้น

**Git Standards Document** คือเอกสารกลางที่แปลง tribal knowledge ให้เป็นมาตรฐานที่เป็นทางการ ค้นหาได้ อ้างอิงได้ และตรวจสอบได้

### 972.2 โครงสร้างเนื้อหาที่ควรมีในเอกสาร

จากประสบการณ์จริงขององค์กรที่มีโปรแกรม governance ที่ดี เอกสาร Git Standards ควรมีหัวข้อหลักดังนี้:

```
Git Standards Document (โครงร่างมาตรฐาน)
├── 1. Purpose & Scope (จุดประสงค์และขอบเขต)
│    - เอกสารนี้ใช้กับใคร repository ประเภทไหนบ้าง
│    - ข้อยกเว้นที่ชัดเจน (เช่น sandbox repo ส่วนตัวไม่บังคับ)
│
├── 2. Repository Standards
│    - Naming convention (เช่น <domain>-<service-type>-<name>)
│    - Visibility default (internal-by-default ตามแนวคิด InnerSource จาก Part 83)
│    - Metadata ที่บังคับต้องมี (README, CODEOWNERS, LICENSE ภายใน, catalog-info.yaml)
│    - Repository lifecycle (active/deprecated/archived) และกระบวนการ archive
│
├── 3. Branching Strategy
│    - Branching model มาตรฐานขององค์กร (Trunk-based / GitHub Flow / Git Flow)
│    - กฎการตั้งชื่อ branch (เช่น feature/, fix/, hotfix/)
│    - อายุสูงสุดของ feature branch ก่อนต้อง merge หรือ rebase
│
├── 4. Commit Message Convention
│    - รูปแบบมาตรฐาน (เช่น Conventional Commits: type(scope): subject)
│    - ภาษาที่ใช้เขียน (อังกฤษ/ไทย และเหตุผล)
│    - การอ้างอิง issue/ticket number
│
├── 5. Pull Request / Merge Request Standards
│    - จำนวน approval ขั้นต่ำ (baseline vs elevated ตาม risk tier)
│    - ขนาด PR ที่แนะนำ (เช่น ไม่เกิน 400 บรรทัดที่เปลี่ยนแปลง)
│    - Template มาตรฐานของ PR description
│    - SLA การ review (เช่น ต้อง review ภายใน 1 วันทำการ)
│
├── 6. Branch Protection / Ruleset Baseline
│    - อ้างอิงกฎขั้นต่ำที่บังคับทุก repo (เชื่อมโยงตรงกับ Organization Ruleset ใน Part 83)
│    - Elevated tier สำหรับ repository ที่มีความเสี่ยงสูง
│
├── 7. Security Requirements
│    - Secret scanning, dependency scanning บังคับหรือแนะนำ
│    - นโยบาย signed commit (บังคับกับ repo ระดับไหน)
│    - การจัดการ credential/token (ไม่ commit secret ลงโค้ดเด็ดขาด)
│
├── 8. CI/CD Standards
│    - บังคับใช้ Golden Path Template หรือไม่ (อ้างอิง Part 83 Step 826)
│    - นโยบาย pipeline ขั้นต่ำที่ต้องมี (test, lint, security scan)
│
├── 9. Access Control Standards
│    - Role-based access model มาตรฐาน (อ้างอิง SSO/SCIM จาก Part 83)
│    - กระบวนการขอ/ถอน access
│
├── 10. Exception Process (กระบวนการขอยกเว้น)
│    - ใครมีสิทธิ์อนุมัติข้อยกเว้น
│    - ระยะเวลาสูงสุดของข้อยกเว้นชั่วคราว (time-boxed exception)
│    - บันทึกและติดตามข้อยกเว้นทั้งหมด
│
├── 11. Roles & Responsibilities
│    - CoE, Champions, Platform Team, Repository Owner (เชื่อมโยง Step 973, 977)
│
├── 12. Review & Change History
│    - Version ของเอกสาร, วันที่แก้ไขล่าสุด, ใครอนุมัติการเปลี่ยนแปลง
│    - Changelog แบบสั้น ๆ ของแต่ละเวอร์ชัน
```

### 972.3 หลักการเขียนเอกสารที่ดี

**1. อธิบาย "ทำไม" ไม่ใช่แค่ "อะไร"**

เอกสารที่ดีไม่ใช่แค่รายการคำสั่ง (rulebook) แต่ต้องอธิบายเหตุผลเบื้องหลังแต่ละกฎ เพราะวิศวกรที่เข้าใจเหตุผลจะปฏิบัติตามด้วยความเต็มใจมากกว่าถูกบังคับ ตัวอย่าง:

```markdown
## กฎ: ห้าม force-push เข้า branch `main`

**เหตุผล:** force-push จะเขียนทับประวัติที่ทีมอื่นอาจอ้างอิงอยู่แล้ว
(เช่น deployment pipeline ที่ trigger จาก commit SHA เฉพาะ)
ทำให้เกิดปัญหาที่ตามรอยยาก และในบาง regulatory framework
(เช่น SOX) การแก้ไขประวัติ commit ที่ผ่านการ approve แล้วถือเป็น
การละเมิดหลักฐานการตรวจสอบ (audit trail integrity)

**บังคับใช้ผ่าน:** Organization-level Ruleset (ดู Part 83)
**ข้อยกเว้น:** ไม่มี — repository ที่ต้องการ workflow พิเศษ
ให้ยื่นคำขอผ่าน Exception Process (หัวข้อ 10)
```

**2. เขียนให้เครื่องมือ enforce ได้จริง (Machine-enforceable)**

กฎที่ดีที่สุดคือกฎที่แปลงเป็นการตั้งค่าอัตโนมัติได้ (เชื่อมกับ Ruleset, CI check) ไม่ใช่กฎที่พึ่งพาการจดจำของมนุษย์เพียงอย่างเดียว หากกฎไหน "enforce อัตโนมัติไม่ได้" ต้องระบุชัดเจนว่าใครมีหน้าที่ตรวจสอบด้วยมือ (manual audit) และตรวจบ่อยแค่ไหน

**3. เอกสารต้อง Version Control ตัวเอง (Dogfooding)**

Git Standards Document ควรเก็บเป็นไฟล์ Markdown ใน repository กลาง (เช่น `org-standards/git-governance.md`) ผ่านกระบวนการ Pull Request เหมือนโค้ดทั่วไป — นี่คือการนำหลักการที่สอนไปแล้วมาใช้กับตัวเอง (dogfooding) และทำให้ทุกการเปลี่ยนแปลงมี review, ประวัติ (git log), และ audit trail อัตโนมัติโดยไม่ต้องสร้างระบบใหม่

**4. แยกระดับความบังคับให้ชัดเจน**

ใช้คำที่มีความหมายชัดเจนตามมาตรฐาน RFC 2119 ที่วงการวิศวกรรมซอฟต์แวร์คุ้นเคย:

| คำ | ความหมาย |
|---|---|
| **ต้อง (MUST)** | บังคับ ไม่มีข้อยกเว้นนอกจากผ่าน Exception Process |
| **ควร (SHOULD)** | แนะนำอย่างยิ่ง มีเหตุผลหนักแน่นถ้าจะไม่ทำตาม |
| **อาจ (MAY)** | ทางเลือก แล้วแต่บริบทของทีม |

### 972.4 ที่เก็บและวิธีเผยแพร่เอกสาร

เอกสารที่เขียนดีแต่ไม่มีคนอ่านก็ไร้ประโยชน์ องค์กรที่ทำสำเร็จมักทำสิ่งเหล่านี้ร่วมกัน:

- เก็บไว้ที่เดียวที่ทุกคนหาเจอง่าย เชื่อมโยงจาก Developer Portal (Backstage TechDocs ตาม Part 83 Step 827.2)
- ทำสรุปแบบ "quick reference" หน้าเดียวสำหรับกฎที่ใช้บ่อยที่สุด แยกจากเอกสารฉบับเต็มที่ละเอียดกว่า
- ฝังลิงก์เอกสารไว้ใน PR template และ repository scaffolding tool โดยตรง เพื่อให้เจอโดยไม่ต้องค้นหาเอง
- ประกาศทุกครั้งที่มีการอัปเดตผ่านช่องทางที่วิศวกรทุกคนติดตามอยู่แล้ว (เช่น engineering-wide Slack channel หรือ newsletter รายเดือน)

## Step 973: Center of Excellence (CoE) สำหรับ Developer Experience/Git Practices

### 973.1 CoE คืออะไร และทำไมต้องมี

**Center of Excellence (CoE)** คือทีมกลางขนาดเล็กที่ได้รับมอบหมายอย่างเป็นทางการให้เป็น **เจ้าของมาตรฐานและแนวปฏิบัติที่ดีที่สุด (best practices)** ในเรื่องใดเรื่องหนึ่งขององค์กร ในบริบทของเรา คือเรื่อง **Git Practices และ Developer Experience**

ข้อควรระวังตั้งแต่ต้น: CoE **ไม่ใช่** ทีมเดียวกับ **Platform Engineering** ที่กล่าวถึงใน Part 83 แม้จะทำงานใกล้ชิดกันมาก:

| มิติ | Center of Excellence (CoE) | Platform Engineering |
|---|---|---|
| โฟกัสหลัก | นโยบาย มาตรฐาน การเผยแพร่ความรู้ วัฒนธรรม | เครื่องมือ automation infrastructure ที่บังคับใช้นโยบาย |
| ผลผลิตหลัก | Git Standards Document, Training, Champions Program | Ruleset, CI/CD Template, Developer Portal, Scaffolder |
| วัดผลด้วย | Adoption rate, ความพึงพอใจของวิศวกร, ความสม่ำเสมอ | Uptime, ความเร็วของ pipeline, ต้นทุน infrastructure |
| ทำงานคล้าย | ที่ปรึกษา/ครู/ผู้ออกแบบนโยบาย | ทีมวิศวกรที่สร้าง product ให้วิศวกรคนอื่นใช้ |

ในองค์กรขนาดกลาง มักรวม CoE กับ Platform Engineering เป็นทีมเดียวกันโดยแบ่งบทบาทภายใน แต่ในองค์กรขนาดใหญ่มาก (หลายพันคน) มักแยกเป็นสองทีมที่ทำงานร่วมกันอย่างใกล้ชิด เพราะแต่ละงานต้องการทักษะคนละแบบ (นักออกแบบนโยบาย/นักสื่อสาร เทียบกับวิศวกรที่สร้างระบบอัตโนมัติ)

### 973.2 พันธกิจ (Mission) ของ CoE

ตัวอย่างพันธกิจที่ชัดเจนของ Git CoE:

> "ทำให้วิศวกรทุกคนในองค์กรใช้งาน Git และแพลตฟอร์มที่เกี่ยวข้องได้อย่างมีมาตรฐานเดียวกัน ปลอดภัย และมีประสิทธิภาพสูงสุด โดยไม่สร้างภาระที่ไม่จำเป็นต่อความเร็วในการส่งมอบงานของแต่ละทีม"

พันธกิจนี้มี 3 ส่วนที่ต้องสมดุลกันเสมอ (สังเกตว่าไม่มีคำว่า "บังคับ" อยู่ในพันธกิจ — CoE เน้นการทำให้ทำตามได้ง่าย มากกว่าการบังคับด้วยอำนาจ):

1. **มาตรฐานเดียวกัน (Consistency)** — จาก Step 972
2. **ปลอดภัยและมีประสิทธิภาพ (Safety & Efficiency)** — จากกลไกใน Part 83
3. **ไม่สร้างภาระที่ไม่จำเป็น (Minimal Friction)** — จะเจาะลึกใน Step 976

### 973.3 หน้าที่รับผิดชอบหลักของ CoE

| หน้าที่ | รายละเอียด |
|---|---|
| **เจ้าของ Git Standards Document** | เขียน ทบทวน อนุมัติการเปลี่ยนแปลงเอกสารมาตรฐาน (Step 972, 979) |
| **จัดอบรมและ Onboarding** | ออกแบบหลักสูตร training และกระบวนการ onboarding มาตรฐาน (Step 975) |
| **ดูแลโปรแกรม Champions** | คัดเลือก สนับสนุน และประสานงานกับ Git Champions ทุกทีม (Step 977) |
| **รวบรวมและวิเคราะห์ Feedback** | เปิดช่องทางรับฟังปัญหาจากวิศวกรทุกทีม แล้วนำมาปรับปรุงมาตรฐาน |
| **พิจารณาคำขอ Exception** | เป็นผู้อนุมัติ (หรือส่งต่อผู้มีอำนาจที่เหมาะสม) เมื่อทีมขอยกเว้นกฎ |
| **วัดผลและรายงาน Adoption** | ดูแล Dashboard การปฏิบัติตามมาตรฐาน รายงานต่อผู้บริหาร (Step 978) |
| **ติดตามแนวโน้มอุตสาหกรรม** | ศึกษาฟีเจอร์ใหม่ แนวปฏิบัติใหม่ และปรับมาตรฐานให้ทันสมัย (Step 979) |
| **ประสานงานกับ Platform Engineering** | แปลงมาตรฐานที่ตกลงกันเป็นข้อกำหนดทางเทคนิคให้ทีม Platform นำไปสร้างเครื่องมือ |

### 973.4 โครงสร้างทีม CoE ที่แนะนำ

CoE ไม่จำเป็นต้องเป็นทีมใหญ่ — ในความเป็นจริงแล้ว CoE ที่มีประสิทธิภาพมักมีขนาดเล็กโดยตั้งใจ เพื่อไม่ให้กลายเป็นอีกหนึ่งชั้นของระบบราชการ โครงสร้างที่พบบ่อย:

```
Git / DevEx Center of Excellence
├── CoE Lead (1 คน)
│    - รับผิดชอบภาพรวม เป็นตัวแทนสื่อสารกับผู้บริหารระดับสูง
│    - มักเป็น Staff/Principal Engineer หรือ Engineering Manager ที่มีประสบการณ์ cross-team สูง
│
├── Core Members (2–4 คน แบบ full-time หรือ dedicated part-time)
│    - เขียนและดูแล Git Standards Document
│    - ดูแล Champions Program
│    - วิเคราะห์ metrics และจัดทำ dashboard
│
├── Rotating Representatives (1 คนต่อ Business Unit ใหญ่ หมุนเวียนทุก 6-12 เดือน)
│    - นำเสียงและบริบทของแต่ละ Business Unit เข้ามาในการตัดสินใจ
│    - ป้องกันไม่ให้ CoE ตัดสินใจแบบตัดขาดจากความเป็นจริงของทีมหน้างาน
│
└── Executive Sponsor (ผู้บริหารระดับ VP/CTO)
     - ไม่ได้ทำงานประจำวัน แต่ให้การสนับสนุนเชิงอำนาจเมื่อจำเป็น
     - อนุมัติงบประมาณและช่วยแก้ปัญหาเมื่อทีมใดทีมหนึ่งไม่ให้ความร่วมมือ
```

**ทำไมต้องมี Rotating Representatives:** นี่คือกลไกสำคัญที่ป้องกันปัญหาคลาสสิกของ CoE ทุกประเภท — การกลายเป็น **"หอคอยงาช้าง" (ivory tower)** ที่ตัดสินใจโดยไม่เข้าใจความเป็นจริงของทีมหน้างาน การหมุนเวียนตัวแทนเข้ามาช่วยรักษาความเชื่อมโยงกับความเป็นจริงอยู่เสมอ และยังเป็นการสร้าง "ทูต" (ambassador) ที่กลับไปทีมเดิมพร้อมความเข้าใจเชิงลึกเรื่อง governance

### 973.5 RACI Matrix ระหว่าง CoE กับผู้มีส่วนเกี่ยวข้องอื่น

RACI (Responsible, Accountable, Consulted, Informed) เป็นเครื่องมือมาตรฐานสำหรับกำหนดบทบาทให้ชัดเจนเมื่อมีหลายฝ่ายเกี่ยวข้อง:

| กิจกรรม | CoE | Platform Eng | Security | Team Lead แต่ละทีม | CTO/VP Eng |
|---|---|---|---|---|---|
| เขียน Git Standards Document | R/A | C | C | C | I |
| สร้าง Ruleset/CI Template ทางเทคนิค | C | R/A | C | I | I |
| อนุมัติข้อยกเว้นความปลอดภัยระดับสูง | C | I | R/A | I | I |
| ปฏิบัติตามมาตรฐานในทีมตัวเอง | C | I | I | R/A | I |
| อนุมัติงบประมาณเครื่องมือ | C | C | I | I | R/A |
| รายงาน Adoption Metrics รายไตรมาส | R/A | C | C | I | I |

R/A = Responsible & Accountable (ผู้ลงมือทำและรับผิดชอบผลลัพธ์), C = Consulted (ต้องปรึกษา), I = Informed (แจ้งให้ทราบ)

## Step 974: การเลือกเครื่องมือมาตรฐานทั้งองค์กร (GitHub vs GitLab vs Self-hosted)

### 974.1 ทำไมการเลือกเครื่องมือคือการตัดสินใจเชิง Governance ไม่ใช่แค่เชิงเทคนิค

การเลือกว่าองค์กรจะใช้ GitHub, GitLab หรือ self-hosted solution เป็นหนึ่งในการตัดสินใจที่ **มีต้นทุนเปลี่ยนใจสูงที่สุด (high switching cost)** ในสาย engineering ทั้งหมด เพราะเมื่อเลือกแล้ว องค์กรจะผูกติดกับเครื่องมือนั้นในหลายมิติพร้อมกัน: CI/CD pipeline configuration, integration กับระบบอื่น, ความคุ้นเคยของวิศวกรหลายพันคน, และ workflow ที่สร้างขึ้นรอบเครื่องมือนั้นมาหลายปี

ด้วยเหตุนี้ การตัดสินใจเรื่องเครื่องมือมาตรฐานจึงต้องเป็นส่วนหนึ่งของ Git Governance โดยตรง ไม่ใช่ปล่อยให้แต่ละทีมเลือกเอง (ซึ่งจะนำไปสู่ **tool sprawl** — ความหลากหลายที่ไร้การควบคุมตามที่กล่าวถึงใน Part 83 Step 821.2)

### 974.2 ตัวเลือกหลักในตลาด (ภาพรวม ณ ปัจจุบัน)

| ตัวเลือก | ลักษณะ |
|---|---|
| **GitHub Enterprise Cloud** | SaaS เต็มรูปแบบ ดูแลโดย Microsoft ระบบนิเวศ Open Source ใหญ่ที่สุด GitHub Actions เป็น CI/CD ในตัว |
| **GitHub Enterprise Server** | ติดตั้งเองในโครงสร้างพื้นฐานขององค์กร (self-managed) เหมาะกับองค์กรที่ต้องการควบคุม data residency เต็มรูปแบบ |
| **GitLab SaaS (GitLab.com)** | บริการ cloud ของ GitLab เน้น DevOps platform ครบวงจรตั้งแต่ planning ถึง monitoring |
| **GitLab Self-managed** | ติดตั้งเองบน infrastructure ขององค์กร รองรับการ customize สูง เป็นตัวเลือกยอดนิยมของหน่วยงานที่ต้องการ data sovereignty |
| **Bitbucket (Atlassian)** | เหมาะกับองค์กรที่ใช้ระบบนิเวศ Atlassian อยู่แล้ว (Jira, Confluence) ผสานรวมกันได้แน่นหนา |
| **Self-hosted แบบ Fully Open Source (Gitea, Forgejo, Gitolite + Gerrit)** | ควบคุมได้เต็มรูปแบบ ต้นทุน license ต่ำที่สุด แต่ภาระ operational สูงที่สุด และระบบนิเวศเสริมจำกัดกว่า |

### 974.3 กรอบการตัดสินใจ (Decision Framework)

การเลือกเครื่องมือที่ดีไม่ควรเกิดจากความชอบส่วนตัวหรือกระแสตลาด แต่ควรใช้กรอบการให้คะแนนถ่วงน้ำหนัก (weighted scorecard) ที่โปร่งใสและอธิบายให้ผู้บริหารเข้าใจได้ ตัวอย่างเกณฑ์ที่ควรพิจารณา:

| เกณฑ์ | คำถามที่ต้องตอบ | น้ำหนักตัวอย่าง (ปรับตามบริบทองค์กร) |
|---|---|---|
| **Data Residency / Compliance** | องค์กรต้องเก็บข้อมูลในประเทศ/ภูมิภาคที่กำหนดหรือไม่ (เช่น กฎหมายธนาคาร กฎหมายข้อมูลส่วนบุคคล) | สูงมากสำหรับองค์กรกำกับดูแลเข้มงวด |
| **ต้นทุนรวม (TCO)** | ค่า license, ค่า CI/CD compute, ค่าดูแลระบบ (ถ้า self-hosted) รวมกี่บาทต่อปี | สูง |
| **ระบบนิเวศและ Integration** | เชื่อมต่อกับเครื่องมือที่องค์กรใช้อยู่แล้วได้ดีแค่ไหน (IdP, ticketing, monitoring, security scanner) | สูง |
| **ความสามารถด้าน CI/CD ในตัว** | ต้องการ CI/CD platform แยกต่างหาก (Jenkins) หรือใช้ในตัวได้เลย | กลาง-สูง |
| **ความสามารถด้าน Security & Compliance** | Advanced security scanning, audit log, SSO/SAML/SCIM ครบหรือไม่ (ดู Part 83) | สูงมากสำหรับองค์กรที่ต้อง audit |
| **ความคุ้นเคยของตลาดแรงงาน** | วิศวกรที่จ้างใหม่ส่วนใหญ่คุ้นเคยกับเครื่องมือนี้อยู่แล้วหรือไม่ ลด learning curve | กลาง |
| **ภาระ Operational (ถ้า Self-hosted)** | องค์กรมีทีมที่พร้อมดูแล infrastructure, patching, backup, disaster recovery เองหรือไม่ (เชื่อมโยง Part 84) | สูงถ้าพิจารณา self-hosted |
| **Vendor Lock-in และ Exit Strategy** | ถ้าต้องย้ายออกในอนาคต ทำได้ยากแค่ไหน มี export/migration path ที่ชัดเจนหรือไม่ | กลาง |
| **Roadmap และความมั่นคงของผู้ให้บริการ** | บริษัทเจ้าของผลิตภัณฑ์มีทิศทางการพัฒนาที่ชัดเจน และมีแนวโน้มอยู่ในตลาดระยะยาวหรือไม่ | กลาง |
| **Support & SLA** | ระดับการสนับสนุนที่ตรงกับความสำคัญของระบบต่อธุรกิจ (business-critical) | สูงสำหรับองค์กรขนาดใหญ่ |

**วิธีใช้ scorecard ในทางปฏิบัติ:**

1. รวบรวมผู้มีส่วนได้ส่วนเสียหลัก (CoE, Security, Platform Eng, ตัวแทนวิศวกร, Finance) มากำหนดน้ำหนักของแต่ละเกณฑ์ร่วมกัน **ก่อน** ให้คะแนนตัวเลือกใด ๆ (ป้องกัน bias ที่เลือกเครื่องมือไว้ล่วงหน้าแล้วค่อยหาเกณฑ์มารองรับ)
2. ให้คะแนนแต่ละตัวเลือกตามเกณฑ์ (เช่น 1–5) โดยอิงข้อมูลจริง (proof of concept, การทดลองใช้งานจริงกับทีมนำร่อง) ไม่ใช่แค่เอกสารการตลาดของผู้ให้บริการ
3. คำนวณคะแนนรวมถ่วงน้ำหนัก และนำเสนอผลพร้อมเหตุผลต่อผู้บริหารที่มีอำนาจตัดสินใจสุดท้าย
4. บันทึกการตัดสินใจเป็น **Architecture Decision Record (ADR)** ที่ระบุบริบท ทางเลือกที่พิจารณา เหตุผลที่เลือก และเงื่อนไขที่จะทบทวนการตัดสินใจนี้อีกครั้งในอนาคต

### 974.4 กรณีพิเศษ: การใช้เครื่องมือมากกว่า 1 ตัวพร้อมกัน

ในทางปฏิบัติ องค์กรขนาดใหญ่บางแห่ง (โดยเฉพาะที่เติบโตผ่านการควบรวมกิจการ/M&A) อาจมีเหตุผลที่หลีกเลี่ยงไม่ได้ในการใช้มากกว่า 1 แพลตฟอร์ม เช่น บริษัทลูกที่เพิ่งถูกซื้อกิจการมายังใช้ GitLab อยู่ ในขณะที่บริษัทแม่ใช้ GitHub

Governance ที่ดีในกรณีนี้ไม่ได้บังคับให้รวมเป็นหนึ่งเดียวทันที (ซึ่งมักมีต้นทุนสูงเกินความจำเป็นในระยะสั้น) แต่ควรมี:

- **มาตรฐานกลางที่ไม่ผูกกับเครื่องมือ (tool-agnostic)** ให้มากที่สุดเท่าที่ทำได้ (เช่น branching strategy, commit convention ใช้ได้กับทั้งสองแพลตฟอร์ม)
- **แผน consolidation ระยะยาว** ที่ชัดเจนพร้อม timeline แม้จะยังไม่ทำทันที เพื่อไม่ให้ tool sprawl กลายเป็นสถานะถาวรโดยไม่ตั้งใจ
- **เหตุผลที่บันทึกไว้ชัดเจน** ว่าทำไมถึงยอมให้มีมากกว่า 1 เครื่องมือในช่วงเปลี่ยนผ่าน เพื่อไม่ให้กลายเป็นข้ออ้างที่ทีมอื่นใช้ขอยกเว้นมาตรฐานโดยไม่มีเหตุผลที่หนักแน่นเท่ากัน

## Step 975: Onboarding Process มาตรฐานสำหรับพนักงานใหม่เรื่อง Git/Workflow ขององค์กร

### 975.1 ทำไม Onboarding คือจุดที่ Governance ประสบความสำเร็จหรือล้มเหลวตั้งแต่วันแรก

พนักงานใหม่คือกลุ่มคนที่ **ยังไม่มี tribal knowledge เก่าที่ต้องลบทิ้ง** — นี่คือโอกาสทองที่สุดที่จะปลูกฝังมาตรฐานให้ถูกต้องตั้งแต่ต้น ถ้า onboarding ทำได้ดี พนักงานใหม่จะซึมซับมาตรฐานเป็นเรื่องปกติทันทีโดยไม่รู้สึกว่าเป็นภาระเพิ่มเติม แต่ถ้า onboarding ทำได้แย่ (ปล่อยให้เรียนรู้เองแบบ trial-and-error หรือถามเพื่อนร่วมทีมที่อาจสอนผิดมาตรฐานเก่า) พนักงานใหม่จะสร้างพฤติกรรมที่ผิดจากมาตรฐานตั้งแต่วันแรก และแก้ไขทีหลังยากกว่ามาก

### 975.2 โครงสร้าง Onboarding มาตรฐาน (Day 1 – Day 30)

```
วันที่ 1: การเข้าถึงพื้นฐาน (Access & Setup)
├── บัญชี Git hosting platform ถูกสร้างอัตโนมัติผ่าน SCIM
│   (ผูกกับระบบ HR ตามที่เรียนใน Part 83 Step 823.4 — ไม่ต้องรอ admin)
├── เข้าทีม/group ที่ถูกต้องอัตโนมัติตาม role ใน HR system
├── ได้รับลิงก์ Git Standards Document และ Quick Reference Guide
└── ได้รับมอบหมาย "Onboarding Buddy" จากทีมตัวเอง

สัปดาห์ที่ 1: Git 101 ตามมาตรฐานองค์กร
├── ทำ Training Module ภาคบังคับ (อาจเป็น e-learning หรือ workshop สด)
│   เนื้อหาไม่ใช่ "Git คืออะไร" ทั่วไป แต่เป็น "องค์กรเราใช้ Git อย่างไร"
│   - Branching strategy ที่องค์กรใช้จริง
│   - วิธีเขียน commit message ตามมาตรฐาน
│   - วิธีเปิด PR ตาม template ขององค์กร
│   - ใครคือ Git Champion ของทีมตัวเอง (ดู Step 977)
├── ฝึกทำ Pull Request แรกใน "Sandbox Repository"
│   (repository ฝึกฝนที่ไม่กระทบ production เลย จำลองสถานการณ์จริง)
└── ผ่านแบบทดสอบสั้น ๆ (quiz) ยืนยันความเข้าใจมาตรฐานพื้นฐาน

สัปดาห์ที่ 2–3: การมีส่วนร่วมจริงแบบมี Guardrail
├── รับมอบหมาย "Good First Issue" ในโปรเจกต์จริงของทีม
│   (งานขนาดเล็ก ความเสี่ยงต่ำ เหมาะสำหรับฝึกกระบวนการเต็มรูปแบบ)
├── เปิด PR แรกในโปรเจกต์จริง โดยมี Buddy คอย review อย่างใกล้ชิด
└── ได้รับ feedback เชิงสร้างสรรค์เกี่ยวกับการปฏิบัติตามมาตรฐาน
    (ไม่ใช่แค่ feedback เชิงเทคนิคของโค้ด)

สัปดาห์ที่ 4: ยืนยันความพร้อม (Readiness Check)
├── Time-to-first-merged-PR ถูกบันทึกเป็น metric (ดู Step 975.4)
├── Buddy และ Manager ยืนยันว่าพนักงานใหม่เข้าใจมาตรฐานครบถ้วน
└── พนักงานใหม่ทำงานได้อย่างอิสระตามมาตรฐานองค์กรโดยไม่ต้องมี guardrail พิเศษอีกต่อไป
```

### 975.3 องค์ประกอบสำคัญที่ทำให้ Onboarding มีมาตรฐานจริง

**1. Sandbox Repository มาตรฐาน**

องค์กรควรมี repository ฝึกฝนกลางที่ทุกคนใหม่ใช้ร่วมกัน ออกแบบให้จำลองสถานการณ์จริงมากที่สุด (มี branch protection เหมือนของจริง มี CI pipeline จำลอง) เพื่อให้พนักงานใหม่เจอ workflow จริงตั้งแต่ในสภาพแวดล้อมที่ปลอดภัย ไม่ใช่แค่ทำตามตัวอย่างในเอกสารเฉย ๆ

**2. Onboarding Buddy ไม่ใช่แค่ "เพื่อนคุยเล่น"**

Buddy ควรเป็นบทบาทที่มีความรับผิดชอบชัดเจน มักเป็นบทบาทเดียวกับ (หรือทำงานร่วมกับ) **Git Champion** ของทีมนั้น (Step 977) เพื่อให้แน่ใจว่าสิ่งที่พนักงานใหม่ได้รับการสอนสอดคล้องกับมาตรฐานองค์กรจริง ไม่ใช่ "วิธีที่ฉันเคยทำมาแบบเดิม ๆ" ที่อาจไม่ตรงกับมาตรฐานปัจจุบันแล้ว

**3. เนื้อหา Onboarding ต้องอัปเดตพร้อมกับ Git Standards Document เสมอ**

จุดที่มักถูกมองข้าม: หลายองค์กรอัปเดตเอกสารมาตรฐานแต่ลืมอัปเดตเนื้อหา training module ให้ตรงกัน ทำให้พนักงานใหม่ยังคงเรียนรู้มาตรฐานเก่าที่ถูกยกเลิกไปแล้ว **CoE ควรกำหนดให้การอัปเดต Onboarding Content เป็นส่วนหนึ่งของ Definition of Done ทุกครั้งที่มีการเปลี่ยนแปลงมาตรฐานสำคัญ** (เชื่อมโยงกับกระบวนการใน Step 979)

### 975.4 การวัดผลความสำเร็จของ Onboarding

| Metric | ความหมาย | เป้าหมายตัวอย่าง |
|---|---|---|
| **Time to First Commit** | เวลาจากวันแรกที่เริ่มงานถึง commit แรกที่ push เข้า repository จริง | ภายใน 3 วันทำการ |
| **Time to First Merged PR** | เวลาจากวันแรกถึง PR แรกที่ผ่านการ review และ merge สำเร็จ | ภายใน 2 สัปดาห์ |
| **Onboarding Quiz Pass Rate** | สัดส่วนพนักงานใหม่ที่ผ่านแบบทดสอบความเข้าใจมาตรฐานในครั้งแรก | มากกว่า 90% |
| **Standards Violation ในช่วง 90 วันแรก** | จำนวนครั้งที่พนักงานใหม่ทำผิดมาตรฐานหลังจบ onboarding (เช่น commit message ผิดรูปแบบ, พยายาม force-push) | แนวโน้มลดลงเมื่อเทียบรุ่นต่อรุ่น |
| **Buddy/Manager Satisfaction Score** | ความพึงพอใจของ Buddy และ Manager ต่อความพร้อมของพนักงานใหม่หลังจบ onboarding | สำรวจทุกไตรมาส |

ตัวเลขเหล่านี้ไม่ได้มีไว้เพื่อประเมินตัวพนักงานใหม่เป็นรายบุคคล แต่ใช้เพื่อประเมิน**คุณภาพของกระบวนการ onboarding เอง** — ถ้า Time to First Merged PR นานผิดปกติทั่วทั้งองค์กร นั่นคือสัญญาณว่ากระบวนการ onboarding หรือมาตรฐานเองมีปัญหาที่ต้องแก้ ไม่ใช่ปัญหาของพนักงานใหม่แต่ละคน

## Step 976: การจัดการ Technical Governance กับ Business Governance ให้สมดุล

### 976.1 นิยามความแตกต่างระหว่างสองแนวคิด

| ประเภท | ขับเคลื่อนโดย | ตัวอย่าง |
|---|---|---|
| **Technical Governance** | ทีมวิศวกรรม, Platform Engineering, CoE | Branching strategy, commit convention, CI/CD pipeline standard |
| **Business Governance** | Legal, Compliance, Risk, Finance, ผู้บริหารระดับสูง | ข้อกำหนดจาก SOC 2/PCI-DSS/GDPR, นโยบายการจัดซื้อเครื่องมือ, ข้อกำหนดสัญญากับลูกค้า |

ทั้งสองแนวคิดไม่ได้แยกขาดจากกันอย่างสิ้นเชิง — ในทางปฏิบัติ Business Governance มักถูก**แปลง**เป็นข้อกำหนดทางเทคนิคที่ Technical Governance ต้องนำไปปฏิบัติ ตัวอย่างเช่น ข้อกำหนด PCI-DSS ที่ว่า "ต้องมีการควบคุมการเข้าถึงข้อมูลบัตรเครดิตอย่างเข้มงวด" (Business Governance) ถูกแปลงเป็น Elevated Ruleset ที่บังคับ 2 approver และ signed commit สำหรับ repository ที่แตะข้อมูลบัตรเครดิต (Technical Governance ตาม Part 83 Step 824)

### 976.2 แรงตึงที่หลีกเลี่ยงไม่ได้ (The Inherent Tension)

ปัญหาที่ทำให้ Governance ล้มเหลวบ่อยที่สุดคือการปล่อยให้ Business Governance "ชนะ" อยู่เสมอโดยไม่ผ่านการกลั่นกรองผลกระทบทางเทคนิค — ผลลัพธ์คือกฎที่ปลอดภัยในทางทฤษฎีแต่ทำงานจริงไม่ได้ หรือทำได้แต่ช้ามากจนวิศวกรหาทางเลี่ยง

ตัวอย่างสถานการณ์จริงที่พบบ่อย:

```
Legal/Compliance เสนอ: "ทุก commit ต้องผ่านการอนุมัติจากผู้จัดการระดับ Director ขึ้นไป
เพื่อความปลอดภัยสูงสุด"

ผลกระทบทางเทคนิคที่ไม่ได้ถูกพิจารณา:
- Director แต่ละคนดูแลวิศวกรหลายสิบคน ไม่มีเวลา review โค้ดทุกบรรทัด
- PR จะค้างรอ approve เป็นสัปดาห์ ความเร็วในการส่งมอบงานลดลงหลายเท่า
- วิศวกรเริ่มรวม commit หลาย ๆ อันเป็นก้อนใหญ่เพื่อลดจำนวนครั้งที่ต้องขออนุมัติ
  (ผลคือ PR ใหญ่ขึ้น ตรวจสอบยากขึ้น ความปลอดภัยกลับแย่ลงกว่าเดิม)
- ในที่สุดทีมเริ่มขอ "Director" ที่ไม่เข้าใจบริบทงานให้ approve แบบเร็ว ๆ
  โดยไม่ได้อ่านจริง (rubber-stamping) — กฎกลายเป็นพิธีกรรมที่ไม่มีความหมาย
  (เรียกว่า "Governance Theater")
```

นี่คือเหตุผลที่ CoE (Step 973) ต้องมีที่นั่งในการเจรจาทุกครั้งที่ Business Governance ต้องการแปลงเป็นกฎทางเทคนิค — เพื่อแปลความต้องการที่แท้จริง (เช่น "ต้องการความมั่นใจว่ามีการตรวจสอบก่อน deploy") ให้เป็นกลไกที่ทำงานได้จริง (เช่น "ต้องมี approval จากอย่างน้อย 1 คนที่มีความเชี่ยวชาญทางเทคนิคในโค้ดส่วนนั้น บวก required status check ด้าน security scan" แทนที่จะบังคับให้ผู้บริหารระดับสูงมา approve ทุกครั้ง)

### 976.3 หลักการออกแบบเพื่อรักษาสมดุล

**1. หลักการ Minimum Viable Governance**

ก่อนเพิ่มกฎใหม่ทุกครั้ง ให้ถามคำถามนี้เสมอ: **"นี่คือกฎขั้นต่ำที่สุดที่ยังบรรลุเป้าหมายด้าน compliance/ความปลอดภัยได้ไหม หรือเรากำลังเพิ่มความเข้มงวดเกินความจำเป็นเพราะความรู้สึกปลอดภัยเทียม (false sense of security)"**

**2. Tiered Enforcement (การบังคับใช้แบบแบ่งชั้น)**

ใช้แนวคิดเดียวกับ Ruleset แบบ Baseline/Elevated ใน Part 83 Step 824.2 — ไม่ใช่ทุก repository ต้องเข้มงวดระดับเดียวกัน จับคู่ระดับความเข้มงวดของกฎกับระดับความเสี่ยงจริงของ repository นั้น (data classification, regulatory scope) ไม่ใช่บังคับระดับสูงสุดกับทุกอย่างเพราะ "ปลอดภัยไว้ก่อน"

**3. Cost-Benefit Analysis ก่อนเพิ่มกฎใหม่ทุกครั้ง**

ทุกข้อเสนอกฎใหม่ควรผ่านการวิเคราะห์แบบมีโครงสร้าง ก่อนนำเข้าสู่ Git Standards Document:

```
Checklist ก่อนเพิ่มกฎใหม่:
[ ] กฎนี้แก้ปัญหาที่เกิดขึ้นจริง (มีหลักฐาน incident/ความเสี่ยงที่ระบุได้) หรือเป็นการป้องกันเชิงทฤษฎี?
[ ] ผลกระทบต่อความเร็วในการส่งมอบงานคืออะไร (ประมาณการเวลาที่เพิ่มขึ้นต่อ PR/repository)
[ ] มีวิธี enforce กฎนี้แบบอัตโนมัติหรือไม่ (ถ้าไม่มี ต้องพึ่งพา manual process ซึ่งมักล้มเหลวที่ scale ใหญ่)
[ ] กฎนี้ใช้กับทุก repository จริงหรือ หรือควรจำกัดแค่ repository ที่มีความเสี่ยงสูงจริง (tiered)
[ ] มี Exception Process รองรับกรณีพิเศษที่สมเหตุสมผลหรือไม่
[ ] ใครเป็นผู้รับผิดชอบทบทวนกฎนี้ในอนาคต และทบทวนเมื่อไหร่ (ไม่ใช่กฎที่ตั้งแล้วลืม)
```

**4. Participatory Rule-Making (การมีส่วนร่วมในการออกกฎ)**

กฎที่ทีมหน้างานมีส่วนร่วมในการออกแบบตั้งแต่ต้น (ผ่าน Champions Program ใน Step 977 หรือ Rotating Representatives ใน CoE) มักได้รับการยอมรับมากกว่ากฎที่ถูก "สั่งลงมา" จากส่วนกลางโดยไม่ปรึกษาใครเลย แม้เนื้อหาของกฎจะเหมือนกันทุกประการก็ตาม — นี่คือหลักการด้านจิตวิทยาองค์กรที่สำคัญมากในการทำ governance ให้สำเร็จจริง

**5. Sunset Clause (เงื่อนไขหมดอายุ)**

กฎชั่วคราวหรือกฎที่เกิดจากเหตุการณ์เฉพาะหน้า (เช่น กฎเข้มงวดพิเศษที่ออกทันทีหลัง incident) ควรมีวันหมดอายุหรือกำหนดการทบทวนที่ชัดเจนตั้งแต่ตอนออกกฎ ไม่ใช่ปล่อยให้เป็นกฎถาวรโดยไม่มีใครกลับมาพิจารณาอีกว่ายังจำเป็นอยู่หรือไม่ — กฎที่ไม่เคยถูกทบทวนคือต้นตอสำคัญของ "governance ที่บวมเกินไป" (governance bloat) ในระยะยาว

### 976.4 กรอบการตัดสินใจเมื่อ Business Governance กับ Technical Governance ขัดแย้งกัน

```
ข้อเสนอจาก Business Governance
         │
         ▼
CoE วิเคราะห์: เป้าหมายที่แท้จริงคืออะไร (ไม่ใช่แค่ข้อเสนอผิวเผิน)
         │
         ▼
CoE ออกแบบกลไกทางเทคนิคที่บรรลุเป้าหมายเดียวกัน
โดยกระทบความเร็วในการทำงานน้อยที่สุดเท่าที่เป็นไปได้
         │
         ▼
นำเสนอทางเลือกทางเทคนิคกลับไปให้ Business Governance พิจารณา
พร้อมข้อมูลผลกระทบที่ประเมินไว้ชัดเจน (เวลา, ต้นทุน, ความเสี่ยงที่เหลืออยู่)
         │
         ▼
    ตกลงกันได้ไหม?
    ├── ได้ → บันทึกเป็นกฎในเอกสารมาตรฐาน พร้อม sunset/review date
    └── ไม่ได้ → ยกระดับ (escalate) ให้ Executive Sponsor ตัดสินใจ
                 โดยมีข้อมูล trade-off ครบถ้วนทั้งสองฝ่ายประกอบการตัดสินใจ
```

## Step 977: Git Champions/Ambassadors Program

### 977.1 ปัญหาที่ Champions Program แก้

CoE (Step 973) แม้จะมีขนาดเล็กโดยตั้งใจ แต่ก็ไม่สามารถอยู่ในทุกทีม ทุกการประชุม ทุกการตัดสินใจประจำวันได้ ในองค์กรที่มี 100+ ทีม การพึ่งพา CoE เพียงอย่างเดียวในการเผยแพร่มาตรฐานและตอบคำถามจะกลายเป็นคอขวดทันที (เหมือนปัญหา bottleneck ที่กล่าวถึงใน Part 83 Step 822.3 และ Step 826.3)

**Git Champions Program** (บางองค์กรเรียก Ambassadors, Advocates หรือ Guild Member) คือการสร้างเครือข่ายกระจายศูนย์ของอาสาสมัครในแต่ละทีมที่ทำหน้าที่เป็น **"ตัวแทนของ CoE ที่อยู่ในทีมนั้นจริง ๆ"**

แนวคิดนี้คล้ายกับโมเดล **Guild** ที่ Spotify เผยแพร่ให้เป็นที่รู้จักในวงการ — กลุ่มคนที่มีความสนใจ/ความเชี่ยวชาญร่วมกันข้ามทีม มารวมตัวกันเป็นระยะเพื่อแลกเปลี่ยนความรู้ โดยไม่ต้องเปลี่ยนโครงสร้างองค์กรที่เป็นทางการ

### 977.2 บทบาทและหน้าที่ของ Git Champion

| หน้าที่ | รายละเอียด |
|---|---|
| **ด่านหน้าของการสนับสนุน (First Line of Support)** | ตอบคำถามพื้นฐานเรื่อง Git/มาตรฐานให้ทีมตัวเองก่อนที่จะต้องส่งต่อไปหา CoE |
| **เผยแพร่มาตรฐานใหม่** | เมื่อ Git Standards Document อัปเดต Champion เป็นคนแรกที่สื่อสารการเปลี่ยนแปลงให้ทีมตัวเองเข้าใจในบริบทของงานจริง |
| **ช่วย Onboard สมาชิกใหม่** | ทำงานร่วมกับ Onboarding Buddy (Step 975) เพื่อให้แน่ใจว่าคนใหม่ได้รับการสอนที่ตรงมาตรฐาน |
| **ช่องทาง Feedback สู่ CoE** | รวบรวมความคิดเห็น ปัญหา และข้อเสนอแนะจากทีมตัวเอง แล้วนำเข้าสู่การประชุม Champions Guild |
| **ตรวจจับปัญหา Compliance เบื้องต้น** | สังเกตเห็นเมื่อทีมเริ่มเบี่ยงเบนจากมาตรฐาน และช่วยแก้ไขก่อนกลายเป็นปัญหาใหญ่ |
| **ทดลองใช้มาตรฐานใหม่ก่อนใคร (Early Adopter)** | เมื่อ CoE เสนอมาตรฐานใหม่ที่ยังไม่ประกาศทั่วองค์กร มักให้ Champions ทดลองใช้ก่อนเพื่อรับ feedback รอบแรก |

### 977.3 การคัดเลือกและดูแล Champions

**เกณฑ์การคัดเลือก:**

- เป็นอาสาสมัคร ไม่ใช่การแต่งตั้งบังคับ (บังคับมักทำให้ได้คนที่ไม่มีแรงจูงใจจริง)
- มีความสนใจเรื่อง developer experience/best practices อยู่แล้วโดยธรรมชาติ
- ได้รับความเชื่อถือจากเพื่อนร่วมทีม (ไม่จำเป็นต้องเป็นวิศวกรอาวุโสที่สุดในทีมเสมอไป)
- มีเวลาเพียงพอที่จะทุ่มเทให้บทบาทนี้ได้จริง (ไม่ใช่แค่รับตำแหน่งแต่ไม่มีเวลาทำ)

**การจัดสรรเวลาอย่างเป็นทางการ:**

จุดที่องค์กรจำนวนมากทำผิดพลาดคือการคาดหวังให้ Champion ทำหน้าที่นี้ "แถม" นอกเหนือจากงานประจำโดยไม่มีการจัดสรรเวลาอย่างเป็นทางการ ซึ่งนำไปสู่ความเหนื่อยล้า (burnout) และโปรแกรมล้มเหลวในระยะยาว แนวปฏิบัติที่ดีคือ:

- จัดสรรเวลาอย่างเป็นทางการให้ Champion ใช้กับบทบาทนี้ (เช่น 10-15% ของเวลาทำงานต่อสัปดาห์) โดยได้รับความเห็นชอบจาก Engineering Manager ของ Champion คนนั้น
- นับบทบาท Champion เป็นส่วนหนึ่งของการประเมินผลงานประจำปี ไม่ใช่ "งานอาสาที่ไม่มีใครเห็นคุณค่า"

**โครงสร้างการดูแลโปรแกรม:**

```
Git Champions Program
├── Champions Guild Meeting (ทุก 2-4 สัปดาห์)
│    - CoE นำเสนอมาตรฐานใหม่/แผนงาน
│    - Champions แลกเปลี่ยนปัญหาที่พบในทีมตัวเอง
│    - โหวต/ให้ความเห็นต่อข้อเสนอกฎใหม่ (Participatory Rule-Making จาก Step 976)
│
├── Champions Onboarding (สำหรับ Champion คนใหม่)
│    - อบรมเชิงลึกกว่าวิศวกรทั่วไป เพื่อให้ตอบคำถามยาก ๆ ได้
│    - เข้าถึงช่องทางสื่อสารตรงกับ CoE (เช่น Slack channel เฉพาะ Champions)
│
├── Recognition & Incentive
│    - ประกาศยกย่อง Champion ที่มีส่วนร่วมโดดเด่นในที่ประชุมระดับองค์กร
│    - อาจมีสิทธิพิเศษ เช่น ได้เข้าร่วม conference ภายนอกที่เกี่ยวกับ DevEx
│
└── Champion Rotation
     - Champion หมุนเวียนทุก 6-12 เดือน เพื่อกระจายความรู้ในทีมให้กว้างขึ้น
       ไม่ให้ความรู้กระจุกอยู่ที่คนเดียวตลอดไป
```

### 977.4 ตัววัดความสำเร็จของโปรแกรม Champions

| Metric | ความหมาย |
|---|---|
| **Coverage Rate** | สัดส่วนทีมที่มี Champion ประจำการอยู่จริง (เป้าหมาย 100% ของทีมที่มีขนาดเกินเกณฑ์ที่กำหนด) |
| **Champion Retention** | สัดส่วน Champion ที่ยังทำหน้าที่ต่อเนื่องเกิน 1 รอบการหมุนเวียน (บ่งบอกว่าโปรแกรมมีคุณค่าจริงต่อผู้ทำหน้าที่) |
| **Time-to-Resolution ของคำถามในทีม** | คำถามพื้นฐานเรื่อง Git ที่ Champion ตอบได้เองโดยไม่ต้องส่งต่อ CoE ลดภาระของ CoE ลงเท่าไหร่ |
| **จำนวน Feedback ที่นำไปสู่การปรับปรุงมาตรฐานจริง** | บ่งบอกว่าช่องทาง feedback ทำงานได้จริง ไม่ใช่แค่พิธีการ |

## Step 978: การวัดผล Adoption ของ Git Standards ในองค์กร

### 978.1 ทำไมต้องวัดผล Adoption แยกจาก DORA Metrics

Part 83 (Step 828) แนะนำ DORA Metrics ซึ่งวัด**ประสิทธิภาพของกระบวนการส่งมอบซอฟต์แวร์โดยรวม** (deployment frequency, lead time, change failure rate, MTTR) แต่ DORA Metrics **ไม่ได้บอกโดยตรงว่าองค์กรปฏิบัติตามมาตรฐาน Git Governance ที่ตั้งไว้มากน้อยแค่ไหน**

ตัวอย่างเช่น องค์กรอาจมี Deployment Frequency สูงมาก (DORA ดูดี) แต่ในขณะเดียวกันมี repository จำนวนมากที่ไม่มี CODEOWNERS ไม่ผ่าน baseline ruleset หรือมี secret หลุดอยู่ในโค้ด — ตัวเลข DORA ที่ดีไม่ได้รับประกันว่า governance ทำงานได้ผล นี่คือเหตุผลที่ต้องมี **Compliance/Adoption Metrics** เป็นชุดตัวชี้วัดแยกต่างหากที่ CoE เป็นเจ้าของโดยตรง

### 978.2 ชุดตัวชี้วัด Adoption ที่แนะนำ

| Metric | วิธีวัด | เป้าหมายตัวอย่าง |
|---|---|---|
| **Baseline Ruleset Compliance Rate** | % ของ repository ที่ผ่านกฎขั้นต่ำครบทุกข้อ (branch protection, CODEOWNERS, ห้าม force-push) | 100% (บังคับได้จริงเพราะ Ruleset enforce อัตโนมัติ) |
| **Elevated Ruleset Compliance Rate** | % ของ repository ที่อยู่ใน scope ความเสี่ยงสูง ที่ผ่านกฎระดับสูง | 100% สำหรับ repo ที่ประกาศ compliance-scope ชัดเจน |
| **Commit Message Convention Compliance** | % ของ commit ที่ตรงตามรูปแบบมาตรฐาน (ตรวจผ่าน CI hook อัตโนมัติ) | มากกว่า 90% (ยากจะได้ 100% เพราะ commit เก่าและ merge commit บางประเภท) |
| **CODEOWNERS Coverage** | % ของ repository ที่มีไฟล์ CODEOWNERS ที่ผ่านการ validate ว่าทีมยัง active จริง | 100% ของ repository ที่ไม่ถูก archive |
| **Orphaned Repository Rate** | % ของ repository ที่ตรวจพบว่าไม่มีเจ้าของที่ active (ตาม Part 83 Step 822.3) | ต่ำกว่า 2% และมีแนวโน้มลดลง |
| **Champion Coverage** | % ของทีมที่มี Git Champion ประจำการ (จาก Step 977) | 100% ของทีมที่มีขนาดเกินเกณฑ์ |
| **Onboarding Metrics** | Time to First Merged PR, Quiz Pass Rate (จาก Step 975) | ตามเป้าหมายที่กำหนดในแต่ละ metric |
| **Exception Request Volume** | จำนวนคำขอยกเว้นกฎต่อเดือน แยกตามประเภทกฎ | แนวโน้มคงที่หรือลดลง (ถ้าเพิ่มขึ้นเรื่อย ๆ อาจบ่งบอกว่ากฎไม่เหมาะกับความเป็นจริง) |
| **Standards Document Read/Engagement Rate** | สถิติการเข้าถึงเอกสารมาตรฐานผ่าน Developer Portal | ใช้เป็นตัวชี้วัดเสริม ไม่ใช่ตัวหลัก |

### 978.3 ออกแบบ Dashboard สำหรับผู้ชมต่างกลุ่ม

Dashboard เดียวไม่สามารถตอบโจทย์ผู้ชมทุกกลุ่มได้ดีเท่ากัน ควรออกแบบแยกระดับ:

```
┌─────────────────────────────────────────────────────────┐
│  Level 1: Executive Dashboard (สำหรับ CTO/VP/Board)       │
│  - ตัวเลขสรุประดับสูงมาก: % compliance รวม, แนวโน้มรายไตรมาส│
│  - เปรียบเทียบกับเป้าหมายที่ตั้งไว้ (RAG status: แดง/เหลือง/เขียว)│
│  - เชื่อมโยงกับความเสี่ยงทางธุรกิจ ไม่ใช่รายละเอียดทางเทคนิค  │
├─────────────────────────────────────────────────────────┤
│  Level 2: CoE/Platform Dashboard (สำหรับทีม Governance)   │
│  - รายละเอียดแยกตาม Business Unit/Domain                   │
│  - รายชื่อ repository ที่ไม่ผ่านมาตรฐาน พร้อมเจ้าของ         │
│  - แนวโน้มของแต่ละ metric ย้อนหลัง เพื่อวิเคราะห์สาเหตุ       │
├─────────────────────────────────────────────────────────┤
│  Level 3: Team-level Dashboard (สำหรับแต่ละทีม/Champion)   │
│  - สถานะ compliance ของ repository ที่ทีมตัวเองดูแลเท่านั้น  │
│  - คำแนะนำเชิงปฏิบัติที่ทำได้ทันที (actionable next step)    │
└─────────────────────────────────────────────────────────┘
```

แหล่งข้อมูลของ Dashboard ควรดึงมาจากระบบที่มีอยู่แล้วให้มากที่สุด แทนที่จะสร้างระบบเก็บข้อมูลใหม่ซ้ำซ้อน เช่น ดึงจาก Software Catalog ของ Backstage (Part 83 Step 827.2), API ของ GitHub/GitLab เอง, และผลลัพธ์จาก scheduled compliance check job ที่รันอัตโนมัติ

### 978.4 ข้อควรระวัง: Goodhart's Law

> "เมื่อตัวชี้วัดกลายเป็นเป้าหมาย มันจะเลิกเป็นตัวชี้วัดที่ดี" — Goodhart's Law

อันตรายของการวัดผล Adoption คือทีมอาจเริ่ม "เล่นกับตัวเลข" (game the metric) แทนที่จะปฏิบัติตามเจตนารมณ์ที่แท้จริงของมาตรฐาน ตัวอย่างเช่น:

- ทีมสร้าง CODEOWNERS ที่มีชื่อทีมอยู่ แต่ทีมนั้นไม่เคย review จริง เพียงเพื่อให้ผ่าน metric "CODEOWNERS Coverage"
- ทีมเขียน commit message ให้ตรงรูปแบบทางไวยากรณ์ แต่เนื้อหาไม่มีความหมายจริง (เช่น `fix: fix bug`) เพียงเพื่อผ่าน automated check

วิธีลดความเสี่ยงนี้:

1. **ใช้ metric หลายตัวประกอบกัน** ไม่พึ่งพา metric เดียวเป็นตัวตัดสินความสำเร็จ
2. **ผสมผสาน Quantitative กับ Qualitative** — สำรวจความคิดเห็นวิศวกร (developer experience survey) ควบคู่กับตัวเลข ไม่ใช่ดูแค่ dashboard
3. **สื่อสารเสมอว่า metric มีไว้เพื่อ "ช่วยทีมที่ต้องการความช่วยเหลือ" ไม่ใช่ "จับผิดเพื่อลงโทษ"** — วัฒนธรรมที่ไม่กลัวถูกลงโทษจะทำให้ตัวเลขสะท้อนความเป็นจริงมากกว่าวัฒนธรรมที่กลัว
4. **ทบทวน metric เองเป็นระยะ** ว่ายังสะท้อนเจตนารมณ์ที่แท้จริงอยู่หรือไม่ เช่นเดียวกับการทบทวนกฎอื่น ๆ (เชื่อมโยงกับ Step 979)

## Step 979: การอัปเดต Standards ให้ทันสมัยอยู่เสมอ

### 979.1 ทำไม Governance ที่หยุดนิ่งคือ Governance ที่กำลังตาย

เทคโนโลยีเปลี่ยนแปลงเร็วมาก — ฟีเจอร์ใหม่ของ GitHub/GitLab ออกแทบทุกเดือน มาตรฐานความปลอดภัยใหม่เกิดขึ้นตามภัยคุกคามที่เปลี่ยนไป กฎหมาย/ข้อบังคับก็ปรับปรุงอยู่เสมอ เอกสาร Git Standards Document ที่เขียนไว้เมื่อ 3 ปีก่อนแล้วไม่เคยแตะต้องอีกเลย มีแนวโน้มสูงที่จะ:

- อ้างอิงถึงฟีเจอร์ที่ถูกยกเลิกไปแล้ว หรือไม่ได้ใช้ประโยชน์จากฟีเจอร์ใหม่ที่ดีกว่า
- ไม่ครอบคลุมความเสี่ยงใหม่ที่เพิ่งเกิดขึ้น (เช่น ความเสี่ยงจาก AI-generated code, supply chain attack รูปแบบใหม่)
- สูญเสียความน่าเชื่อถือในสายตาวิศวกร ("เอกสารนี้ล้าสมัย ไม่ต้องอ่านก็ได้") ซึ่งทำลาย governance ทั้งระบบแม้ส่วนที่ยังใช้ได้จริงก็ตาม

### 979.2 กระบวนการทบทวนแบบมีรอบเวลา (Review Cadence)

| ประเภทการทบทวน | ความถี่ | ผู้รับผิดชอบ |
|---|---|---|
| **Full Document Review** | ทุก 12 เดือน | CoE ร่วมกับ Rotating Representatives |
| **Quarterly Health Check** | ทุกไตรมาส | CoE พิจารณา adoption metrics และ exception request trend |
| **Ad-hoc Review** | เมื่อเกิด incident สำคัญ หรือมีการเปลี่ยนแปลง regulation ใหม่ | CoE + Security/Compliance |
| **Champions Feedback Loop** | ต่อเนื่องผ่าน Guild Meeting (Step 977) | CoE รับ feedback สะสมนำเข้าสู่รอบทบทวนถัดไป |

### 979.3 กระบวนการเสนอเปลี่ยนแปลงมาตรฐานแบบเป็นทางการ (RFC-style Process)

การเปลี่ยนแปลงมาตรฐานที่มีผลกระทบสูงไม่ควรทำโดย CoE ตัดสินใจฝ่ายเดียวทันที ควรมีกระบวนการที่โปร่งใสคล้ายกับ **RFC (Request for Comments)** ที่ใช้ในโครงการ Open Source ขนาดใหญ่:

```
1. Proposal (ข้อเสนอ)
   - ใครก็ได้ในองค์กรเสนอการเปลี่ยนแปลงผ่าน Pull Request
     เข้า repository ของ Git Standards Document โดยตรง
   - ต้องระบุ: ปัญหาที่ต้องการแก้, ทางเลือกที่พิจารณา, ผลกระทบที่คาดว่าจะเกิดขึ้น

2. Discussion Period (ช่วงเวลาถกเถียง)
   - เปิดให้ Champions และวิศวกรทั่วไปแสดงความเห็นในตัว PR
     เป็นเวลาอย่างน้อย 1-2 สัปดาห์ (ขึ้นกับความสำคัญของการเปลี่ยนแปลง)
   - CoE รวบรวมและตอบข้อกังวลที่สำคัญ

3. Pilot (ทดลองใช้กับกลุ่มนำร่อง)
   - สำหรับการเปลี่ยนแปลงที่มีผลกระทบสูง ให้ทดลองกับทีมอาสาสมัคร
     (มักเป็นทีมที่มี Champion เข้าร่วมด้วย) ก่อนประกาศใช้ทั่วองค์กร

4. Approval (การอนุมัติ)
   - CoE Lead อนุมัติการเปลี่ยนแปลงเล็กน้อย
   - การเปลี่ยนแปลงใหญ่ (เช่น เปลี่ยน branching strategy ทั้งองค์กร)
     ต้องผ่าน Executive Sponsor ด้วย

5. Rollout with Deprecation Window (การประกาศใช้พร้อมช่วงเปลี่ยนผ่าน)
   - ประกาศล่วงหน้าอย่างน้อย 30-90 วันก่อนกฎเก่าถูกยกเลิกจริง
     (สอดคล้องกับแนวทาง version migration ของ CI/CD Template ใน Part 83 Step 826.2)
   - จัดทำ migration guide และถ้าเป็นไปได้ automated codemod ช่วยแก้ไขให้อัตโนมัติ

6. Update Downstream Artifacts (อัปเดตสิ่งที่เกี่ยวข้องทั้งหมด)
   - อัปเดต Onboarding Training (Step 975)
   - อัปเดต Ruleset/CI Template ทางเทคนิค (ประสานกับ Platform Engineering)
   - บันทึก Changelog ในเอกสารมาตรฐาน
```

### 979.4 ติดตามแนวโน้มภายนอกอย่างเป็นระบบ

CoE ควรมีกลไกติดตามการเปลี่ยนแปลงภายนอกอย่างสม่ำเสมอ ไม่ใช่รอให้ปัญหาเกิดก่อนถึงจะรู้ตัว:

- **Release notes ของแพลตฟอร์มที่ใช้** (GitHub Changelog, GitLab Release Notes) — ตรวจสอบทุกเดือนว่ามีฟีเจอร์ governance ใหม่ที่ควรนำมาใช้หรือไม่
- **แนวโน้มด้านความปลอดภัย** — ติดตามรายงานภัยคุกคามใหม่ที่เกี่ยวกับ software supply chain (เช่น ผ่านรายงานจาก OWASP, CISA)
- **การเปลี่ยนแปลงด้านกฎหมาย/ข้อบังคับ** — ประสานงานใกล้ชิดกับ Legal/Compliance เพื่อรู้ล่วงหน้าเมื่อมีข้อบังคับใหม่ที่จะกระทบมาตรฐาน
- **ชุมชนภายนอกและองค์กรอื่น** — เข้าร่วม conference/community ด้าน Platform Engineering, DevEx (เช่น PlatformCon, InnerSource Commons) เพื่อเรียนรู้จากองค์กรอื่น

### 979.5 Versioning เอกสารมาตรฐานเอง

เอกสาร Git Standards Document ควรมีเลขเวอร์ชันของตัวเองและ Changelog ที่ชัดเจน เพื่อให้วิศวกรที่อ้างอิงเอกสารเก่าไว้ (เช่น ใน internal wiki ของทีมตัวเอง) รู้ว่าเนื้อหาที่ตัวเองอ้างอิงล้าสมัยหรือยัง:

```markdown
# Git Standards Document
**เวอร์ชันปัจจุบัน:** 4.2.0
**อัปเดตล่าสุด:** 2026-08-15
**อนุมัติโดย:** Git/DevEx Center of Excellence

## Changelog
### v4.2.0 (2026-08-15)
- เพิ่มข้อกำหนดเรื่อง AI-assisted commit review สำหรับ repository ระดับ Elevated
### v4.1.0 (2026-05-01)
- ปรับ SLA การ review PR จาก 2 วันทำการ เหลือ 1 วันทำการ ตามผลสำรวจ Champions
### v4.0.0 (2026-01-10)
- เปลี่ยน Branching Strategy มาตรฐานจาก Git Flow เป็น Trunk-based Development
  (Breaking Change — ดู Migration Guide แนบท้าย)
```

## Step 980: แบบฝึกหัด — ร่าง Git Governance Charter ฉบับเต็มให้องค์กรสมมติระดับพันคน

### 980.1 สถานการณ์สมมติ

คุณเพิ่งได้รับการแต่งตั้งเป็น **Head of Developer Experience** คนแรกของบริษัท **"NovaLogistics"** บริษัทซอฟต์แวร์ด้าน logistics/supply chain ที่เติบโตอย่างรวดเร็วผ่านทั้งการเติบโตภายในและการควบรวมกิจการ (M&A)

**ข้อมูลองค์กร:**

- พนักงานฝ่ายวิศวกรรม: **1,100 คน** กระจายใน 6 ประเทศ 4 ไทม์โซน
- เกิดจากการควบรวม 3 บริษัทในช่วง 2 ปีที่ผ่านมา — บริษัทเดิมใช้ GitHub, บริษัทที่ถูกซื้อกิจการหนึ่งใช้ GitLab Self-managed อีกหนึ่งใช้ Bitbucket
- ยังไม่มี Git Standards Document อย่างเป็นทางการ — แต่ละบริษัทเดิมมีวัฒนธรรม Git ของตัวเอง
- Employee turnover ของฝ่ายวิศวกรรมอยู่ที่ 18% ต่อปี (สูงกว่าค่าเฉลี่ยอุตสาหกรรม) ผู้บริหารสงสัยว่าส่วนหนึ่งมาจากประสบการณ์ onboarding ที่สับสนและไม่มีมาตรฐาน
- เพิ่งผ่านการตรวจสอบ SOC 2 Type II ครั้งแรกแบบหวุดหวิด (มี finding หลายข้อเกี่ยวกับความไม่สม่ำเสมอของ access control และ code review ระหว่าง 3 หน่วยธุรกิจ)
- CEO ตั้งเป้าว่าภายใน 18 เดือน ทั้ง 3 หน่วยธุรกิจต้อง "รู้สึกเหมือนเป็นบริษัทเดียวกัน" ในแง่วิธีการทำงานด้านวิศวกรรม
- งบประมาณสำหรับโปรแกรมนี้ปีแรก: จำกัด ต้องแสดงผลตอบแทนความคุ้มค่า (ROI) ให้ชัดเจนต่อ Board

### 980.2 โจทย์: จัดทำ Git Governance Charter ฉบับเต็ม

Charter ของคุณต้องครอบคลุมหัวข้อต่อไปนี้ทั้งหมด โดยอ้างอิงหลักการจากทุก Step ใน Part นี้ (และเชื่อมโยงกับกลไกเทคนิคจาก Part 83 เมื่อเกี่ยวข้อง)

**ส่วนที่ 1: Vision & Mandate**

1. เขียน Mission Statement ของโปรแกรม Git Governance ที่ NovaLogistics ในหนึ่งย่อหน้า
2. ระบุว่า Charter นี้มีอำนาจ (mandate) มาจากใคร และขอบเขตอำนาจคืออะไร (บังคับได้แค่ไหน ที่ไหนต้องขอความร่วมมือ)
3. กำหนด Success Criteria ของปีแรกอย่างเป็นรูปธรรม อย่างน้อย 3 ข้อ ที่วัดผลได้จริง

**ส่วนที่ 2: โครงสร้างองค์กรของ Governance**

1. ออกแบบโครงสร้าง Center of Excellence ที่เหมาะกับบริบทของ NovaLogistics (ขนาดทีม บทบาท Rotating Representatives จาก 3 หน่วยธุรกิจเดิม)
2. เขียน RACI Matrix สำหรับกิจกรรมหลัก 5 อย่างที่เกี่ยวข้องกับการรวม 3 บริษัทเข้าด้วยกัน
3. ออกแบบโครงสร้างโปรแกรม Git Champions ให้ครอบคลุมทั้ง 6 ประเทศ พร้อมข้อเสนอเรื่องการจัดสรรเวลาอย่างเป็นทางการ

**ส่วนที่ 3: การตัดสินใจเรื่องเครื่องมือ**

1. ใช้ Decision Framework จาก Step 974 วิเคราะห์ว่า NovaLogistics ควรรวมเป็นเครื่องมือเดียว (GitHub, GitLab หรืออื่น) หรือไม่ พร้อมเหตุผลอย่างน้อย 4 เกณฑ์ที่ให้น้ำหนักมากที่สุดในบริบทนี้
2. เสนอแผน migration ระดับสูง (high-level) พร้อม timeline คร่าว ๆ ถ้าตัดสินใจรวมเป็นเครื่องมือเดียว
3. ถ้าตัดสินใจไม่รวมทันที ให้เสนอมาตรฐานที่ tool-agnostic ที่ทำให้ทั้ง 3 หน่วยธุรกิจทำงานสอดคล้องกันได้แม้ใช้เครื่องมือต่างกันในช่วงเปลี่ยนผ่าน

**ส่วนที่ 4: เอกสารมาตรฐานและ Onboarding**

1. ร่างโครงร่าง (table of contents) ของ Git Standards Document ฉบับแรกของ NovaLogistics โดยเน้นหัวข้อที่ตอบโจทย์ finding จาก SOC 2 audit โดยตรง
2. ออกแบบ Onboarding Process มาตรฐานที่แก้ปัญหา turnover 18% โดยเชื่อมโยงกับประสบการณ์การเข้าทำงานที่สับสนในปัจจุบัน
3. เสนอ metric อย่างน้อย 3 ตัวที่จะใช้วัดว่า Onboarding ที่ปรับปรุงใหม่ได้ผลจริง

**ส่วนที่ 5: การจัดสมดุลและ Compliance**

1. ระบุว่า SOC 2 finding ที่เกิดขึ้น (ความไม่สม่ำเสมอของ access control และ code review) ควรถูกแปลงเป็นกฎ Technical Governance แบบไหน (Baseline หรือ Elevated) และทำไม
2. ยกตัวอย่างสถานการณ์ที่ Business Governance (เช่น Compliance ต้องการความเข้มงวดสูงสุดทุก repo) อาจขัดแย้งกับความคล่องตัวของทีมพัฒนา และเสนอทางออกตามหลักการ Step 976
3. ออกแบบ Exception Process ที่เหมาะกับองค์กรที่เพิ่งผ่าน M&A (ซึ่งมักมีกรณีพิเศษเยอะกว่าองค์กรทั่วไป)

**ส่วนที่ 6: การวัดผลและความยั่งยืน**

1. ออกแบบ Dashboard 3 ระดับ (Executive, CoE, Team) ที่เหมาะกับบริบทนี้ พร้อมระบุว่าแต่ละระดับควรเห็น metric อะไรบ้าง
2. กำหนดรอบเวลาการทบทวน Git Standards Document ของ NovaLogistics ปีแรก (ควรถี่กว่าปกติหรือไม่ เพราะเหตุใด)
3. เสนอวิธีนำเสนอความคืบหน้าของโปรแกรมนี้ต่อ Board ทุกไตรมาส ในรูปแบบที่แสดง ROI ได้ชัดเจน

### 980.3 แนวทางเฉลยโดยสรุป (แนวคิดหลัก ไม่ใช่คำตอบสำเร็จรูปเดียว)

**Vision & Mandate:** Mission Statement ควรเน้นคำว่า "รวมเป็นหนึ่งเดียว" (unify) และ "ลดความเสี่ยง" มากกว่าคำว่า "บังคับ" Mandate ควรมาจาก CEO/CTO โดยตรงเนื่องจากเกี่ยวข้องกับการรวม 3 หน่วยธุรกิจซึ่งเป็นการตัดสินใจระดับสูง Success Criteria ปีแรกที่สมเหตุสมผล เช่น "ผ่าน SOC 2 Type II รอบถัดไปโดยไม่มี finding ด้าน access control ซ้ำ", "Baseline Ruleset Compliance ถึง 95% ทั่วทั้ง 3 หน่วยธุรกิจ", "Time to First Merged PR ของพนักงานใหม่ลดลง 30%"

**โครงสร้าง Governance:** CoE ควรมีตัวแทนจากทั้ง 3 หน่วยธุรกิจเดิมอย่างชัดเจนตั้งแต่วันแรก เพื่อป้องกันความรู้สึกว่า "บริษัทที่ถูกซื้อกิจการถูกบังคับให้ทำตามมาตรฐานของบริษัทแม่" ซึ่งเป็นสาเหตุทั่วไปของความล้มเหลวใน M&A integration Champions Program ต้องคำนึงถึงไทม์โซนที่ต่างกัน 4 โซน — Guild Meeting ควรมีอย่างน้อย 2 รอบเวลาที่ต่างกันเพื่อให้ทุกภูมิภาคเข้าร่วมได้จริง

**เครื่องมือ:** เกณฑ์ที่ควรให้น้ำหนักสูงสุดในบริบทนี้คือ Data Residency/Compliance (เพราะเพิ่งมี SOC 2 finding) และ Integration/ระบบนิเวศ (เพราะต้องรวม 3 ระบบเดิมเข้าด้วยกัน) การรวมเป็นเครื่องมือเดียวมักคุ้มค่าในระยะยาวสำหรับสถานการณ์ M&A แต่ควรทำแบบค่อยเป็นค่อยไป (phased migration ทีละหน่วยธุรกิจ ไม่ใช่ big-bang) เพื่อลดความเสี่ยงต่อการดำเนินธุรกิจ ระหว่างช่วงเปลี่ยนผ่านควรมีมาตรฐาน tool-agnostic (เช่น branching strategy, commit convention) ที่ใช้ได้กับทุกเครื่องมือไปพลางก่อน

**เอกสารและ Onboarding:** โครงร่าง Git Standards Document ควรให้น้ำหนักกับหัวข้อ Access Control Standards และ PR/Code Review Standards เป็นพิเศษ เนื่องจากตรงกับ SOC 2 finding โดยตรง Onboarding ควรออกแบบให้เป็น "ประสบการณ์เดียวกัน" ไม่ว่าพนักงานใหม่จะเข้าทำงานที่หน่วยธุรกิจไหน เพื่อสร้างความรู้สึกเป็นบริษัทเดียวกันตามเป้าหมายของ CEO

**การจัดสมดุลและ Compliance:** SOC 2 finding เรื่อง access control/code review ควรกลายเป็น **Baseline Ruleset** (ไม่ใช่แค่ Elevated) เพราะเป็นข้อกำหนดขั้นต่ำที่ auditor ตรวจสอบทุก repository ไม่ใช่แค่ repository ที่มีความเสี่ยงสูงเป็นพิเศษ Exception Process ควรออกแบบให้รองรับกรณีเฉพาะหน้าของ M&A ได้ (เช่น ระบบ legacy ของบริษัทที่ถูกซื้อกิจการที่ยังไม่พร้อม migrate ทันที) แต่ต้องมี time-boxed migration plan แนบไปกับทุกข้อยกเว้น ไม่ใช่ปล่อยเป็นข้อยกเว้นถาวร

**การวัดผลและความยั่งยืน:** ปีแรกควรทบทวน Git Standards Document ถี่กว่าปกติ (ทุกไตรมาสแทนที่จะเป็นรายปี) เนื่องจากอยู่ในช่วงเปลี่ยนผ่านที่มีความไม่แน่นอนสูง การนำเสนอต่อ Board ควรเชื่อมโยงตัวเลข compliance เข้ากับความเสี่ยงทางธุรกิจโดยตรง (เช่น "ความเสี่ยงที่จะไม่ผ่าน SOC 2 ลดลงจาก X% เหลือ Y%") มากกว่าการนำเสนอตัวเลขทางเทคนิคที่ Board ไม่คุ้นเคย

### 980.4 การขยายผล

หลังทำแบบฝึกหัดนี้เสร็จ ให้ลองพิจารณาเพิ่มเติม:

- ถ้าหน่วยธุรกิจหนึ่งใน 3 หน่วยต่อต้านการเปลี่ยนแปลงอย่างรุนแรง (เช่น อ้างว่ามาตรฐานใหม่ไม่เข้าใจบริบทเฉพาะของธุรกิจตัวเอง) จะใช้หลักการจาก Step 976 และ Step 977 มาคลี่คลายสถานการณ์นี้อย่างไร
- ถ้างบประมาณปีแรกถูกตัดลงครึ่งหนึ่งกะทันหัน จะจัดลำดับความสำคัญของ 10 Step ในเนื้อหา Part นี้อย่างไรให้ยังคงบรรลุ Success Criteria หลักได้
- อีก 3 ปีข้างหน้า เมื่อโปรแกรม Governance เข้าสู่ภาวะที่มั่นคงแล้ว บทบาทของ Head of Developer Experience ควรเปลี่ยนไปอย่างไร (จากการ "สร้างระบบ" ไปสู่การ "ดูแลรักษาและพัฒนาต่อยอด")

การฝึกคิดในระดับนี้คือทักษะที่แยกวิศวกรที่เก่งด้านเทคนิคออกจาก **ผู้นำด้านวิศวกรรมระดับองค์กร (Engineering Leader)** ที่ต้องมองเห็นภาพรวมทั้งมิติเทคนิค มิติคน และมิติธุรกิจไปพร้อมกัน ซึ่งเป็นทักษะที่เราจะเจาะลึกต่อในบทถัดไปว่าด้วยการเป็น Tech Lead

## สรุป Part 98

ใน Part นี้เราได้เรียนรู้ว่า:

1. **Git Governance คือโปรแกรมขององค์กร ไม่ใช่แค่กฎเทคนิค** — มันคือระบบของนโยบาย โครงสร้าง กลไก และวัฒนธรรมที่ทำงานร่วมกัน โดยกลไกเชิงเทคนิคที่เรียนใน Part 83 เป็นเพียงหนึ่งในสี่องค์ประกอบเท่านั้น
2. **Git Standards Document** ที่ดีต้องอธิบาย "ทำไม" ไม่ใช่แค่ "อะไร" ต้อง machine-enforceable ให้มากที่สุด และต้อง version control ตัวเองผ่านกระบวนการเดียวกับที่สอนทีมอื่นให้ทำ (dogfooding)
3. **Center of Excellence (CoE)** เป็นเจ้าของนโยบายและการเผยแพร่ความรู้ แยกบทบาทชัดเจนจาก Platform Engineering ที่สร้างเครื่องมือบังคับใช้ และควรมี Rotating Representatives เพื่อไม่ให้กลายเป็นหอคอยงาช้าง
4. **การเลือกเครื่องมือมาตรฐานทั้งองค์กร** ต้องใช้ weighted scorecard ที่โปร่งใส พิจารณา Data Residency, TCO, ระบบนิเวศ, ความปลอดภัย และ Vendor Lock-in ร่วมกัน ไม่ใช่ตัดสินใจตามความชอบส่วนตัว
5. **Onboarding มาตรฐาน** คือจุดที่ Governance ประสบความสำเร็จหรือล้มเหลวตั้งแต่วันแรก ต้องมี Sandbox Repository, Buddy ที่เชื่อมกับ Champion, และวัดผลด้วย Time-to-First-Merged-PR
6. **การจัดสมดุล Technical กับ Business Governance** ต้องใช้หลักการ Minimum Viable Governance, Tiered Enforcement, Cost-Benefit Analysis และ Participatory Rule-Making เพื่อป้องกันไม่ให้เกิด "Governance Theater"
7. **Git Champions Program** สร้างเครือข่ายกระจายศูนย์ที่ทำหน้าที่แทน CoE ในแต่ละทีม ต้องมีการจัดสรรเวลาอย่างเป็นทางการและ recognition ที่จริงจัง ไม่ใช่ "งานอาสาที่ไม่มีใครเห็นคุณค่า"
8. **การวัดผล Adoption** ต้องแยกจาก DORA Metrics และออกแบบ Dashboard หลายระดับสำหรับผู้ชมต่างกลุ่ม พร้อมระวัง Goodhart's Law ที่ตัวเลขอาจถูก "เล่น" แทนที่จะสะท้อนความเป็นจริง
9. **การอัปเดต Standards** ต้องมีรอบเวลาทบทวนชัดเจน ใช้กระบวนการแบบ RFC ที่โปร่งใส และมี Deprecation Window ที่เพียงพอ พร้อม versioning เอกสารเองเหมือนซอฟต์แวร์
10. แบบฝึกหัดร่าง Git Governance Charter สำหรับองค์กรหลัง M&A ช่วยฝึกการมองภาพรวมทุกมิติพร้อมกัน — เทคนิค คน วัฒนธรรม และธุรกิจ — ซึ่งเป็นทักษะแกนกลางของการเป็นผู้นำด้านวิศวกรรมระดับองค์กร
