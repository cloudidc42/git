ตลอด 4 เฟสที่ผ่านมา (Part 1–45, Step 1–450) เราใช้เวลาทั้งหมดไปกับการปูพื้นฐาน Git ให้แน่น เรียนรู้การใช้งาน GitHub อย่างมืออาชีพ และฝึกทำงานเป็นทีมด้วย Workflow มาตรฐานต่าง ๆ จนถึงจุดที่คุณสามารถจำลองทีมพัฒนาซอฟต์แวร์ทั้งทีมได้ด้วยตัวเองใน Part 45 ที่ผ่านมา

แต่โลกของ Version Control ไม่ได้มีแค่ GitHub เพียงเจ้าเดียว ในความเป็นจริง มีองค์กรจำนวนมหาศาลทั่วโลก — ตั้งแต่หน่วยงานรัฐ ธนาคาร บริษัทการเงิน ไปจนถึงองค์กรอวกาศระดับ NASA — ที่เลือกใช้แพลตฟอร์มอีกตัวหนึ่งที่ชื่อว่า **GitLab** แทน หรือใช้ควบคู่กันไป

หลายคนที่เรียนรู้ Git ผ่าน GitHub มาตลอด อาจไม่เคยรู้เลยว่า GitLab มีจุดกำเนิดและปรัชญาการออกแบบที่ต่างจาก GitHub อย่างมีนัยสำคัญ ไม่ใช่แค่ "GitHub อีกยี่ห้อหนึ่ง" แต่เป็นแพลตฟอร์มที่เกิดมาจากวิสัยทัศน์คนละแบบตั้งแต่วันแรก และวิสัยทัศน์นั้นเองที่ทำให้ GitLab กลายเป็นตัวเลือกอันดับหนึ่งในหลายองค์กรขนาดใหญ่ทั่วโลก

ใน **เฟส 5 นี้ (Part 46–55, Step 451–550)** เราจะพาคุณเดินทางจากความเข้าใจพื้นฐานเรื่อง GitLab ไปจนถึงการติดตั้ง ใช้งาน และทำ CI/CD เบื้องต้นด้วย GitLab CI/CD จริง — เพื่อให้คุณเป็นวิศวกรที่ **เลือกเครื่องมือได้อย่างเหมาะสมกับสถานการณ์** ไม่ใช่แค่รู้จักเครื่องมือเดียวแล้วยึดติดกับมันโดยไม่รู้ทางเลือกอื่น

และ **Part 46 นี้คือจุดเริ่มต้นของเฟสใหม่ทั้งหมด** เราจะเริ่มจากศูนย์: GitLab คืออะไร มาจากไหน ต่างจาก GitHub ตรงไหนบ้างอย่างละเอียด และทำไมองค์กรจำนวนมากถึงเลือกมันแทนที่จะใช้ GitHub เพียงอย่างเดียว มาเริ่มกันเลยครับ

## Step 451: ประวัติ GitLab — กำเนิดจากยูเครนสู่แพลตฟอร์มระดับโลก

### จุดเริ่มต้นที่เรียบง่ายมาก

**GitLab** ถือกำเนิดขึ้นในปี **2011** โดยวิศวกรซอฟต์แวร์ชาวยูเครนสองคนคือ **Dmitriy Zaporozhets** และ **Valery Sizov**

เรื่องราวเริ่มต้นจากปัญหาที่เรียบง่ายมาก: Dmitriy Zaporozhets ทำงานเป็นวิศวกรซอฟต์แวร์และต้องการเครื่องมือจัดการโปรเจกต์ Git ที่มี Web UI ใช้งานง่าย แต่โซลูชันที่มีอยู่ในตลาดตอนนั้นไม่ตอบโจทย์เขา ไม่ว่าจะเป็นเรื่องราคา ความยืดหยุ่นในการติดตั้งเอง หรือฟีเจอร์ที่ต้องการ

เขาจึงเริ่มเขียนโปรเจกต์ส่วนตัวขึ้นมาเองในภาษา **Ruby on Rails** ชื่อว่า **"GitLab"** (มาจาก "Git" + "Lab" ที่สื่อถึงการเป็นห้องทดลอง/พื้นที่ทำงานร่วมกัน) แล้วเผยแพร่เป็น **Open Source project** บน GitHub เอง (ใช่ครับ — GitLab เวอร์ชันแรกสุดถูกโฮสต์อยู่บน GitHub นั่นเอง) เพื่อให้ชุมชนนักพัฒนาคนอื่น ๆ นำไปใช้และช่วยกันพัฒนาต่อได้ฟรี

### จาก Side Project สู่บริษัท

ในช่วงแรก GitLab เป็นเพียงโปรเจกต์ Open Source เล็ก ๆ ที่มีผู้ร่วมพัฒนาจากทั่วโลกเข้ามาช่วยกันปรับปรุง จุดเปลี่ยนสำคัญเกิดขึ้นเมื่อ **Sytse Sijbrandij** ผู้ประกอบการชาวดัตช์ เข้ามาสนใจโปรเจกต์นี้และร่วมกับ Dmitriy Zaporozhets ก่อตั้ง **GitLab Inc.** ขึ้นอย่างเป็นทางการในปี **2014** โดยเข้าร่วมโครงการบ่มเพาะสตาร์ทอัพชื่อดัง **Y Combinator**

Sytse Sijbrandij ดำรงตำแหน่ง CEO ของ GitLab Inc. มาอย่างยาวนาน และเป็นผู้ผลักดันวิสัยทัศน์ที่ทำให้ GitLab เติบโตจากโปรเจกต์ Open Source เล็ก ๆ กลายเป็นบริษัทระดับพันล้านดอลลาร์

### จุดเด่นที่ทำให้ GitLab แตกต่างตั้งแต่วันแรก

สิ่งที่ทำให้ GitLab แตกต่างจากคู่แข่งตั้งแต่ยุคแรกเริ่มคือ **ปรัชญาความโปร่งใสสุดขั้ว (extreme transparency)** บริษัท GitLab Inc. เผยแพร่แทบทุกอย่างต่อสาธารณะ ไม่ว่าจะเป็น:

- **คู่มือพนักงาน (Team Handbook)** ที่เปิดให้ทุกคนอ่านได้ฟรีบนเว็บไซต์ ครอบคลุมตั้งแต่วัฒนธรรมองค์กร กระบวนการทำงาน ไปจนถึงนโยบายเงินเดือน
- **แผนงานผลิตภัณฑ์ (Product Roadmap)** ที่เปิดเผยต่อสาธารณะ ทุกคนเห็นได้ว่า GitLab กำลังจะพัฒนาฟีเจอร์อะไรต่อไป
- **การเป็นบริษัท All-Remote** ตั้งแต่ก่อนที่การทำงานทางไกลจะเป็นกระแสหลัก พนักงานของ GitLab Inc. กระจายอยู่ทั่วโลกโดยไม่มีสำนักงานกลางแบบดั้งเดิม

### สิ่งที่ควรจำจาก Step นี้

GitLab ไม่ได้เกิดมาจากบริษัทเทคโนโลยียักษ์ใหญ่ที่มีทุนมหาศาลตั้งแต่ต้นแบบ GitHub (ที่ภายหลังถูก Microsoft ซื้อไป) แต่เกิดจาก **โปรเจกต์ Open Source ของวิศวกรสองคนที่แก้ปัญหาของตัวเอง** แล้วค่อย ๆ เติบโตจนกลายเป็นบริษัทมหาชนที่แข่งขันโดยตรงกับ GitHub ในระดับโลก — เรื่องราวนี้สะท้อนถึงจิตวิญญาณ Open Source ที่ฝังอยู่ใน DNA ของ GitLab มาตั้งแต่วันแรก และยังคงเป็น Open Source Core อยู่จนถึงปัจจุบัน (โค้ดหลักส่วน Community Edition เปิดเผยต่อสาธารณะทั้งหมด)

## Step 452: GitLab คืออะไร วิสัยทัศน์ "The DevOps Platform"

### นิยามของ GitLab

**GitLab** คือแพลตฟอร์มที่ให้บริการ **host Git repository พร้อมเครื่องมือครบวงจรสำหรับกระบวนการพัฒนาซอฟต์แวร์ทั้งหมด** ตั้งแต่การวางแผนโปรเจกต์ ไปจนถึงการ deploy และ monitor ระบบที่ทำงานอยู่จริงบน production

ถ้า GitHub เริ่มต้นจากการเป็น "ที่เก็บโค้ดพร้อม Social Coding" แล้วค่อย ๆ เพิ่มฟีเจอร์อื่นเข้ามาทีหลัง (เช่น GitHub Actions ที่มาในปี 2019) GitLab กลับมีแนวคิดตรงกันข้ามตั้งแต่ต้น นั่นคือการเป็น **"เครื่องมือเดียวที่ครอบคลุมทุกขั้นตอน"**

### วิสัยทัศน์ "The DevOps Platform"

GitLab นิยามตัวเองอย่างชัดเจนว่าเป็น **"The One DevOps Platform"** โดยมีแนวคิดหลักคือ **"One application for the entire DevOps lifecycle"** — แอปพลิเคชันเดียวที่ครอบคลุมวงจรชีวิตทั้งหมดของ DevOps

วงจร DevOps ที่ GitLab พยายามครอบคลุมมักถูกอธิบายด้วยขั้นตอนต่อไปนี้ (บางครั้งเรียกว่า DevOps Lifecycle หรือ Infinity Loop):

```
   Plan → Create → Verify → Package → Release → Configure → Monitor → Govern
     ↑                                                                    │
     └────────────────────────────────────────────────────────────────────┘
```

แต่ละขั้นตอนแปลเป็นฟีเจอร์จริงในตัวผลิตภัณฑ์ GitLab ดังนี้:

| ขั้นตอน | ความหมาย | ฟีเจอร์ใน GitLab |
|---|---|---|
| **Plan** | วางแผนงานและติดตามงาน | Issues, Epics, Boards, Milestones, Roadmaps |
| **Create** | เขียนโค้ดและจัดการซอร์สโค้ด | Repository, Merge Request, Code Review, Web IDE |
| **Verify** | ทดสอบคุณภาพโค้ด | GitLab CI/CD, Unit Test Reports, Code Quality, Test Coverage |
| **Package** | บรรจุซอฟต์แวร์ให้พร้อมใช้ | Container Registry, Package Registry |
| **Release** | ปล่อยซอฟต์แวร์ออกสู่ผู้ใช้ | Continuous Delivery, Release Management, Feature Flags |
| **Configure** | จัดการโครงสร้างพื้นฐาน | Infrastructure as Code, Kubernetes Integration |
| **Monitor** | เฝ้าดูระบบที่ทำงานจริง | Metrics, Incident Management, Error Tracking |
| **Govern** | ควบคุมความปลอดภัยและ compliance | Security Scanning (SAST/DAST), Compliance Management, Audit Events |

### ทำไมแนวคิดนี้ถึงสำคัญ

ก่อนที่ GitLab จะมี ทีมพัฒนาซอฟต์แวร์ทั่วไปมักต้องใช้เครื่องมือแยกกันหลายตัวสำหรับแต่ละขั้นตอน เช่น:

- ใช้ Jira สำหรับ Plan
- ใช้ GitHub สำหรับ Create (เก็บโค้ด + Pull Request)
- ใช้ Jenkins สำหรับ Verify/Release (CI/CD)
- ใช้ Docker Hub หรือ Artifactory สำหรับ Package
- ใช้ Datadog หรือ New Relic สำหรับ Monitor
- ใช้ Snyk หรือ Checkmarx สำหรับ Govern (security)

การมีเครื่องมือแยกกันแบบนี้สร้างปัญหาหลายอย่าง เช่น ข้อมูลกระจัดกระจายไม่เชื่อมโยงกัน ต้องบริหารจัดการหลายระบบพร้อมกัน (แต่ละระบบมีการตั้งค่าสิทธิ์ ผู้ดูแล และค่าใช้จ่ายของตัวเอง) และการเชื่อมต่อระหว่างเครื่องมือ (integration) มักจะเปราะบางและต้องบำรุงรักษาต่อเนื่อง

GitLab เสนอทางเลือกที่ต่างออกไปอย่างสิ้นเชิง คือการรวมทุกอย่างไว้ **ในแอปพลิเคชันเดียว ฐานข้อมูลเดียว ระบบสิทธิ์เดียว** ทำให้ทุกขั้นตอนของ DevOps เชื่อมโยงกันโดยธรรมชาติ เช่น การเชื่อม Issue เข้ากับ Merge Request เข้ากับ Pipeline เข้ากับ Deployment โดยไม่ต้องตั้งค่า integration ใด ๆ เพิ่มเติมเลย เพราะทุกอย่างอยู่ในระบบเดียวกันตั้งแต่ต้น

### ข้อควรระวัง: "ครบวงจร" ไม่ได้แปลว่า "ดีที่สุดในทุกด้าน"

สิ่งที่ควรเข้าใจอย่างตรงไปตรงมาคือ ปรัชญา All-in-One ของ GitLab มีทั้งข้อดีและข้อเสีย ข้อดีคือความสะดวกและการเชื่อมโยงข้อมูลที่ไร้รอยต่อ แต่ข้อเสียคือในบางฟีเจอร์เฉพาะทาง เครื่องมือเฉพาะทางที่ทำสิ่งนั้นสิ่งเดียว (best-of-breed tools) อาจมีความสามารถเหนือกว่า เช่น Jira อาจมีฟีเจอร์บริหารโปรเจกต์ที่ซับซ้อนกว่า GitLab Issues ในบางกรณี หรือ Datadog อาจมี Monitoring ที่ลึกกว่า GitLab Monitor

การเลือกใช้ GitLab จึงเป็นการ **แลกความลึกเฉพาะทางบางจุด กับความสะดวกในการเชื่อมโยงทุกอย่างเข้าด้วยกัน** ซึ่งสำหรับหลายองค์กรแล้ว การแลกเปลี่ยนนี้คุ้มค่ามาก โดยเฉพาะทีมขนาดกลางถึงใหญ่ที่ต้องการลดความซับซ้อนของ Tool Stack

## Step 453: GitLab.com, GitLab Self-Managed และ GitLab Dedicated ต่างกันอย่างไร

หนึ่งในสิ่งที่ทำให้ GitLab แตกต่างจาก GitHub อย่างชัดเจนที่สุดคือ **รูปแบบการใช้งานที่หลากหลายกว่ามาก** GitLab เสนอทางเลือก 3 รูปแบบหลักให้กับผู้ใช้

### 1. GitLab.com (SaaS — Software as a Service)

นี่คือรูปแบบที่คุ้นเคยที่สุด เทียบเท่ากับการใช้ github.com โดยตรง

**ลักษณะ:**
- สมัครใช้งานผ่านเว็บไซต์ **gitlab.com** ได้ทันที ไม่ต้องติดตั้งอะไรเอง
- GitLab Inc. เป็นผู้ดูแล infrastructure ทั้งหมด (server, database, backup, security patch)
- ใช้งานได้ทันทีหลังสมัคร คล้าย GitHub.com ทุกประการ
- มีทั้งแผนฟรีและแผนเสียเงิน (Premium, Ultimate)
- เหมาะกับทีมที่ไม่ต้องการดูแล infrastructure เอง หรือทีมขนาดเล็ก/สตาร์ทอัพที่ต้องการเริ่มงานได้เร็ว

**ข้อจำกัด:** ข้อมูลทั้งหมดอยู่บน server ของ GitLab Inc. (ซึ่งอาจไม่ตอบโจทย์องค์กรที่มีข้อกำหนดด้าน data sovereignty หรือกฎหมายควบคุมข้อมูลที่เข้มงวด)

### 2. GitLab Self-Managed (ติดตั้งเองบน Server ของบริษัท)

นี่คือจุดขายที่โดดเด่นที่สุดของ GitLab เมื่อเทียบกับ GitHub

**ลักษณะ:**
- ดาวน์โหลดซอฟต์แวร์ GitLab มาติดตั้งเองบน server ของบริษัท ไม่ว่าจะเป็น on-premise data center, private cloud, หรือแม้แต่เครื่อง cloud VM ของตัวเอง (AWS, GCP, Azure)
- บริษัทเป็นผู้ควบคุมข้อมูลทั้งหมด 100% — ไม่มีข้อมูลใดออกไปนอกเครือข่ายของบริษัทเลยถ้าไม่ต้องการ
- มีให้เลือกทั้งเวอร์ชัน **Community Edition (CE)** ที่เป็น Open Source ฟรี 100% และเวอร์ชัน **Enterprise Edition (EE)** ที่มีฟีเจอร์ระดับองค์กรเพิ่มเติม (ต้องมี license)
- เหมาะกับองค์กรที่มีข้อกำหนดด้านความปลอดภัยสูง เช่น หน่วยงานรัฐ ธนาคาร สถาบันการเงิน โรงพยาบาล หรือบริษัทที่ทำงานกับข้อมูลลับ/ความมั่นคง

**ข้อควรพิจารณา:** บริษัทต้องรับผิดชอบเรื่อง infrastructure เอง ตั้งแต่การติดตั้ง อัปเดตเวอร์ชัน สำรองข้อมูล ไปจนถึงการรักษาความปลอดภัยของ server เอง ซึ่งต้องมีทีม IT/DevOps ที่มีความรู้เพียงพอ

### 3. GitLab Dedicated

รูปแบบที่ 3 นี้เป็นทางเลือกที่อยู่ตรงกลางระหว่างสองแบบแรก เปิดตัวในภายหลังเพื่อตอบโจทย์องค์กรขนาดใหญ่โดยเฉพาะ

**ลักษณะ:**
- GitLab Inc. เป็นผู้ดูแล infrastructure ให้ทั้งหมด **เหมือน GitLab.com** แต่สิ่งที่ต่างคือ **แต่ละองค์กรจะได้ instance ของตัวเองแยกต่างหาก (single-tenant)** ไม่ใช้ทรัพยากรร่วมกับลูกค้ารายอื่นเหมือน GitLab.com ที่เป็นแบบ multi-tenant
- ลูกค้าเลือกได้ว่าต้องการให้ข้อมูลอยู่ในภูมิภาค (region) ใดของโลก เพื่อตอบโจทย์กฎหมายคุ้มครองข้อมูล เช่น GDPR ในยุโรป
- เหมาะกับองค์กรขนาดใหญ่มากที่ต้องการความยืดหยุ่นด้าน compliance และ data residency แต่ไม่ต้องการรับภาระดูแล infrastructure เองทั้งหมดแบบ Self-Managed
- เป็นส่วนหนึ่งของแผน **Ultimate** เท่านั้น และมีค่าใช้จ่ายสูงกว่ารูปแบบอื่น

### ตารางสรุปเปรียบเทียบทั้ง 3 รูปแบบ

| ประเด็น | GitLab.com | GitLab Self-Managed | GitLab Dedicated |
|---|---|---|---|
| ใครดูแล Infrastructure | GitLab Inc. | บริษัทของคุณเอง | GitLab Inc. |
| Multi-tenant หรือ Single-tenant | Multi-tenant | Single-tenant (ของตัวเอง 100%) | Single-tenant |
| ควบคุมข้อมูลได้เต็มที่แค่ไหน | ปานกลาง (อยู่บน cloud ของ GitLab) | สูงสุด (อยู่ในเครือข่ายบริษัทเอง) | สูง (แยก instance แต่ GitLab ดูแล) |
| ความรับผิดชอบด้าน Ops | ไม่ต้องดูแลเอง | ต้องดูแลเองทั้งหมด | ไม่ต้องดูแลเอง |
| ค่าใช้จ่าย | ต่ำ–ปานกลาง | ฟรี (CE) หรือมี license (EE) | สูงสุด |
| เหมาะกับ | ทีมทั่วไป/สตาร์ทอัพ | องค์กรที่ต้องการ data sovereignty | องค์กรใหญ่ที่ต้องการ compliance เฉพาะ |

### เทียบกับ GitHub

จุดที่น่าสนใจคือ GitHub ก็มี **GitHub Enterprise Server** ที่คล้ายกับ GitLab Self-Managed เช่นกัน แต่โดยทั่วไปแล้ว GitHub เน้นหนักไปทาง SaaS (github.com) เป็นหลัก ในขณะที่วัฒนธรรมและชุมชนผู้ใช้ GitLab ให้ความสำคัญกับการ self-host มากกว่าอย่างชัดเจน และที่สำคัญคือ **GitLab Community Edition เป็น Open Source ฟรี 100% ไม่มีข้อจำกัดจำนวนผู้ใช้** ในขณะที่ GitHub Enterprise Server เป็นผลิตภัณฑ์เชิงพาณิชย์ที่ต้องเสียค่า license เสมอ ไม่มีเวอร์ชันฟรีสำหรับติดตั้งเอง

## Step 454: ตารางเปรียบเทียบ GitLab vs GitHub แบบละเอียด

มาถึง Step ที่หลายคนรอคอย นั่นคือการเปรียบเทียบ GitLab กับ GitHub แบบละเอียดในทุกมิติ

### 1. โครงสร้างเจ้าของและบริษัท

| ประเด็น | GitHub | GitLab |
|---|---|---|
| เจ้าของ | Microsoft (ซื้อในปี 2018) | GitLab Inc. (บริษัทมหาชน จดทะเบียน NASDAQ: GTLB) |
| ก่อตั้งปี | 2008 | 2011 |
| ต้นกำเนิด | บริษัทสตาร์ทอัพในซิลิคอนวัลเลย์ | โปรเจกต์ Open Source จากยูเครน |
| วัฒนธรรมองค์กร | ผสานเข้ากับ Microsoft ecosystem | All-Remote และโปร่งใสสุดขั้ว (public handbook) |

### 2. โครงสร้างราคา

| แผน | GitHub | GitLab |
|---|---|---|
| ฟรี | Free — private/public repo ไม่จำกัด, collaborator ไม่จำกัดในหลายกรณี, GitHub Actions มีโควตาฟรีจำกัดต่อเดือน | Free — repo ไม่จำกัด, CI/CD minutes มีโควตาฟรีจำกัดต่อเดือน, self-host CE ฟรีไม่จำกัดผู้ใช้ |
| ระดับกลาง | Team | Premium |
| ระดับสูงสุด | Enterprise | Ultimate |
| Self-host ฟรี | ไม่มี (GitHub Enterprise Server เสียเงินเท่านั้น) | มี (Community Edition ฟรี 100% ไม่จำกัดผู้ใช้) |

**จุดสำคัญ:** ความแตกต่างที่ชัดเจนที่สุดคือ **GitLab เปิดให้ self-host แบบฟรีสมบูรณ์** ในขณะที่ GitHub ไม่มีทางเลือก self-host ที่ฟรีเลย นี่คือจุดขายที่ GitLab ใช้ดึงดูดองค์กรที่งบจำกัดแต่ต้องการควบคุม infrastructure เอง

### 3. Ecosystem และชุมชน

| ประเด็น | GitHub | GitLab |
|---|---|---|
| ขนาดชุมชน Open Source | ใหญ่ที่สุดในโลก — โปรเจกต์ Open Source ระดับโลกส่วนใหญ่อยู่ที่นี่ (Linux kernel mirror, React, Kubernetes ฯลฯ) | เล็กกว่า GitHub มาก ในแง่จำนวนโปรเจกต์สาธารณะ แต่ตัว GitLab เองก็เป็น Open Source ที่พัฒนาบน GitLab.com |
| Social Coding Features | แข็งแกร่งมาก (star, fork, follow, trending, GitHub profile) | มีแต่เน้นน้อยกว่า เพราะเน้นไปทาง Enterprise/DevOps มากกว่า social |
| Marketplace/Integrations | GitHub Marketplace ใหญ่มาก มี third-party app นับพัน | มี GitLab Integrations แต่จำนวนน้อยกว่า เพราะเน้นให้ฟีเจอร์อยู่ใน platform เดียวแทน |
| การใช้เป็น "Portfolio" ของนักพัฒนา | เป็นมาตรฐานที่บริษัทส่วนใหญ่ดูโปรไฟล์ GitHub ตอนสมัครงาน | ไม่ได้รับความนิยมในลักษณะนี้เท่า GitHub |

### สรุปภาพรวม

โดยสรุปแล้ว **GitHub แข็งแกร่งที่สุดในเรื่องระบบนิเวศ Open Source, Social Coding และนวัตกรรม AI (Copilot)** ในขณะที่ **GitLab แข็งแกร่งที่สุดในเรื่อง All-in-One DevOps Platform, Self-hosting แบบฟรี และ Compliance/Security ระดับองค์กร** — ทั้งสองไม่ได้มีฝ่ายไหน "ดีกว่า" อย่างสมบูรณ์ แต่เหมาะกับบริบทและความต้องการที่ต่างกัน ซึ่งเราจะวิเคราะห์ให้ลึกยิ่งขึ้นใน Step 458 และแบบฝึกหัดท้าย Part นี้

## Step 455: Merge Request (MR) คือ Pull Request ในร่างของ GitLab

### ความสับสนที่พบบ่อยที่สุดของคนย้ายจาก GitHub มา GitLab

ถ้าคุณคุ้นเคยกับ GitHub มาก่อน (ซึ่งเราเรียนกันมาอย่างละเอียดในเฟส 3 ของหลักสูตรนี้) สิ่งแรกที่คุณจะงงเมื่อเปิด GitLab ครั้งแรกคือ **ไม่มีปุ่ม "Pull Request" ที่ไหนเลย** แทนที่ด้วยปุ่มที่ชื่อว่า **"Merge Request"** หรือย่อว่า **MR**

ข่าวดีคือ **แนวคิดเบื้องหลังเหมือนกันทุกประการ 100%** สิ่งที่ต่างกันมีแค่ "ชื่อเรียก" เท่านั้น

### นิยามของ Merge Request

**Merge Request (MR)** คือคำขอให้นำการเปลี่ยนแปลงจาก branch หนึ่ง (มักเป็น feature branch) ไปรวม (merge) เข้ากับอีก branch หนึ่ง (มักเป็น main/master) โดยผ่านกระบวนการตรวจสอบ (review) ก่อนที่จะ merge จริง

กระบวนการทำงานเหมือนกับ Pull Request ของ GitHub ทุกขั้นตอนที่เราเคยเรียนมาในเฟส 3:

1. สร้าง feature branch จาก main
2. commit การเปลี่ยนแปลงลงใน feature branch
3. push branch ขึ้นไปที่ GitLab
4. เปิด Merge Request เพื่อขอให้นำ branch นี้ไปรวมกับ main
5. ทีมรีวิวโค้ด (Code Review) แสดงความคิดเห็น (comment) ตรงบรรทัดโค้ดที่ต้องการ
6. แก้ไขตามที่รีวิว แล้ว push เพิ่มเข้าไปใน branch เดิม (MR จะอัปเดตอัตโนมัติ)
7. เมื่อได้รับการอนุมัติ (Approve) ครบตามเงื่อนไข ก็กด Merge เพื่อรวมเข้า main

### ทำไมชื่อถึงต่างกัน

เหตุผลเชิงประวัติศาสตร์คือทั้งสองแพลตฟอร์มพัฒนาฟีเจอร์นี้ขึ้นมาอย่างเป็นอิสระจากกัน โดยตั้งชื่อตามมุมมองที่ต่างกันเล็กน้อย:

- **GitHub** เรียกว่า **"Pull Request"** เพราะมองจากมุมของผู้ดูแล repository (maintainer) — เป็นการขอให้ maintainer "pull" (ดึง) การเปลี่ยนแปลงจาก branch ของคุณเข้าไป ชื่อนี้มาจากธรรมชาติของ Git ที่คำสั่ง `git pull` มีอยู่แล้ว
- **GitLab** เรียกว่า **"Merge Request"** เพราะมองจากมุมของการกระทำที่เกิดขึ้นจริงในตอนจบ นั่นคือการ "merge" สอง branch เข้าด้วยกัน ชื่อนี้ตรงไปตรงมากับสิ่งที่กำลังจะเกิดขึ้น

### ตารางเทียบฟีเจอร์ MR vs PR แบบละเอียด

| ฟีเจอร์ | GitHub Pull Request | GitLab Merge Request |
|---|---|---|
| ชื่อย่อที่ใช้เรียก | PR | MR |
| การขอรีวิว | Request Reviewers | Assign Reviewers |
| การอนุมัติ | Approve (ในหน้า Review) | Approve (มีระบบ Approval Rules ที่ละเอียดกว่าใน Premium/Ultimate) |
| การตรวจสอบก่อน merge | Required Status Checks / Branch Protection Rules | Merge Checks / Pipeline ต้องผ่านก่อน (Merge When Pipeline Succeeds) |
| Draft/WIP | Draft Pull Request | Draft Merge Request (เดิมใช้ prefix "WIP:") |
| การ merge อัตโนมัติเมื่อเงื่อนไขผ่าน | Auto-merge | Merge Trains / Auto-merge |
| Threaded discussion บนโค้ด | มี | มี พร้อมระบบ "Resolve thread" ที่บังคับให้ปิด comment ก่อน merge ได้ |
| การเชื่อมกับ Issue | `Closes #123` ใน description | `Closes #123` เช่นกัน เชื่อมกับ Issue ได้เหมือนกัน |

### จุดเด่นเฉพาะของ GitLab Merge Request

GitLab มีฟีเจอร์บางอย่างที่ผูกกับ Merge Request ซึ่งไม่มีในระบบ Pull Request พื้นฐานของ GitHub (บางส่วนเป็นฟีเจอร์แบบเสียเงินใน Premium/Ultimate):

- **Merge Trains** — ระบบคิวการ merge ที่รับประกันว่า MR หลายตัวที่กำลังจะ merge พร้อมกันจะถูกทดสอบร่วมกันตามลำดับคิว ป้องกันปัญหาที่ MR สองตัวผ่าน pipeline แยกกันได้ แต่พอ merge รวมกันแล้วพัง
- **Approval Rules** — กำหนดกฎการอนุมัติที่ซับซ้อนได้ เช่น ต้องมีคนจากทีม Security อนุมัติเสมอถ้ามีการแก้ไขไฟล์ที่เกี่ยวกับ authentication
- **Squash and Merge ที่ตั้งค่าระดับ Project ได้ละเอียด** — กำหนดพฤติกรรมเริ่มต้นของการ squash commit ได้ตายตัวในระดับโปรเจกต์
- **Merge Request Dependencies** — กำหนดได้ว่า MR หนึ่งต้อง merge อีก MR หนึ่งให้เสร็จก่อนจึงจะ merge ตัวเองได้ (Premium ขึ้นไป)

### สรุป

จำไว้ง่าย ๆ ว่า **"Merge Request" ของ GitLab เทียบเท่ากับ "Pull Request" ของ GitHub 100% ในเชิงแนวคิด** ต่างกันแค่ชื่อและรายละเอียดฟีเจอร์เสริมบางส่วนเท่านั้น ทักษะการทำ Code Review, การเขียน commit message ที่ดี, และการจัดการ branch ที่เราเรียนมาตลอดหลักสูตรนี้สามารถนำไปใช้กับ GitLab ได้โดยตรงแทบไม่ต้องปรับตัวเลย

## Step 456: CI/CD ในตัวของ GitLab vs GitHub Actions ที่มาทีหลัง

### ความแตกต่างเชิงประวัติศาสตร์ที่สำคัญมาก

นี่คือหนึ่งในความแตกต่างเชิงปรัชญาที่สำคัญที่สุดระหว่างสองแพลตฟอร์ม และเป็นกุญแจสำคัญที่ทำให้เข้าใจว่าทำไม GitLab ถึงถูกมองว่าเป็น "DevOps Platform" ที่สมบูรณ์กว่าในมุมมองขององค์กรจำนวนมาก

### GitLab CI/CD: มีมาตั้งแต่ปี 2015

GitLab เปิดตัวระบบ CI/CD ในตัวตั้งแต่ปี **2015** ซึ่งเป็นเวลาเพียง 4 ปีหลังจากที่ GitLab ก่อตั้ง และเป็นส่วนหนึ่งของแพลตฟอร์มมาตั้งแต่ยุคแรก ๆ ของผลิตภัณฑ์

สิ่งนี้สะท้อนอยู่ในการออกแบบสถาปัตยกรรมของ GitLab อย่างลึกซึ้ง เพราะ CI/CD ถูกคิดมาเป็น **ส่วนหนึ่งของแกนกลางของผลิตภัณฑ์** ไม่ใช่ feature เสริมที่แปะเข้ามาทีหลัง ผลลัพธ์คือ:

- Pipeline ผูกกับ Merge Request, Issue, และ Repository อย่างแนบแน่นเป็นธรรมชาติ
- มี UI แสดงผล Pipeline ที่ออกแบบมาให้เป็นศูนย์กลางของหน้าโปรเจกต์ ไม่ใช่แท็บรอง
- แนวคิดอย่าง **Auto DevOps** (ตรวจจับภาษาโปรแกรมและ framework อัตโนมัติ แล้วตั้งค่า pipeline การ build, test, security scan, deploy ให้อัตโนมัติทั้งหมดโดยแทบไม่ต้องเขียน config เอง) เป็นไปได้ก็เพราะ CI/CD ถูกออกแบบเป็นแกนกลางของระบบตั้งแต่ต้น

### GitHub Actions: มาทีหลังในปี 2019

**GitHub Actions** เปิดตัวในปี **2019** ซึ่งช้ากว่า GitLab CI/CD ถึง 4 ปี ก่อนหน้านั้น GitHub ไม่มีระบบ CI/CD ของตัวเองเลย ผู้ใช้ GitHub ต้องพึ่งพาบริการภายนอกอย่าง **Travis CI**, **CircleCI**, หรือ **Jenkins** เพื่อทำ CI/CD กับโค้ดที่อยู่บน GitHub

การที่ GitHub Actions มาทีหลังไม่ได้แปลว่ามันด้อยกว่า — ในทางตรงกันข้าม GitHub ได้เรียนรู้จากจุดอ่อนของระบบ CI/CD รุ่นก่อน ๆ ในตลาด แล้วออกแบบ GitHub Actions ให้มีจุดแข็งเฉพาะตัว เช่น:

- **GitHub Marketplace สำหรับ Actions** — มี Action สำเร็จรูปนับหมื่นตัวที่ชุมชนสร้างไว้ให้ใช้งานได้ทันที (reusable actions)
- **Matrix Build ที่ยืดหยุ่นสูง** — ทดสอบข้ามหลายเวอร์ชันของภาษา/OS ได้ง่าย
- **การเชื่อมต่อกับ Event ของ GitHub ที่หลากหลายมาก** — เช่น trigger เมื่อมีคน react อีโมจิ, เมื่อมีการสร้าง release, เมื่อมี issue ถูก label ฯลฯ

### ตารางเปรียบเทียบ GitLab CI/CD vs GitHub Actions

| ประเด็น | GitLab CI/CD | GitHub Actions |
|---|---|---|
| เปิดตัวปี | 2015 | 2019 |
| ไฟล์ config หลัก | `.gitlab-ci.yml` (ไฟล์เดียวที่ root แม้จะแยกเป็นหลายไฟล์ include ได้) | ไฟล์ YAML แยกหลายไฟล์ใน `.github/workflows/` |
| หน่วยรัน | Runner (self-hosted หรือ SaaS runner ของ GitLab) | Runner (self-hosted หรือ GitHub-hosted runner) |
| Marketplace สำเร็จรูป | GitLab CI/CD Catalog (เล็กกว่า และเพิ่งพัฒนาแข็งแกร่งขึ้นในช่วงหลัง) | GitHub Marketplace (ใหญ่มาก มี community actions นับหมื่น) |
| Auto DevOps (ตั้ง pipeline อัตโนมัติ) | มี (จุดขายเฉพาะของ GitLab) | ไม่มีในลักษณะเดียวกัน ต้องเขียน workflow เอง |
| ความผูกพันกับ platform หลัก | แนบแน่นมาก (Pipeline เป็นแกนกลางของหน้า Project) | เป็น Feature แยกที่เชื่อมกับ repo |
| Built-in Container/Package Registry | มี ผูกกับ pipeline ได้แนบแน่น | มี (GitHub Container Registry, GitHub Packages) เช่นกัน แต่เพิ่มเข้ามาทีหลัง |
| Security Scanning ในตัว | มีตั้งแต่ระดับ Free/Premium (SAST พื้นฐาน) | ต้องพึ่ง Actions จากภายนอกหรือ GitHub Advanced Security (เสียเงินแยก) |

### ผลกระทบต่อการตัดสินใจเลือกแพลตฟอร์ม

ความแตกต่างเชิงประวัติศาสตร์นี้ส่งผลต่อการตัดสินใจของหลายองค์กรอย่างแท้จริง องค์กรที่มองหา **"เครื่องมือเดียวที่ครบวงจรตั้งแต่ต้นจนจบโดยไม่ต้องต่อเครื่องมือหลายตัวเข้าด้วยกัน"** มักจะโน้มเอียงไปทาง GitLab เพราะ CI/CD ถูกออกแบบให้เป็นส่วนหนึ่งของ DNA สินค้ามาตั้งแต่ต้น ในขณะที่องค์กรที่ต้องการ **"ความยืดหยุ่นสูงสุดและ ecosystem ของ community actions ที่หลากหลายที่สุด"** มักจะเลือก GitHub Actions

เราจะได้ลงมือเขียน `.gitlab-ci.yml` จริงและเปรียบเทียบกับ GitHub Actions ที่เราเคยเรียนมาในเฟส 3 อย่างละเอียดใน Part หลัง ๆ ของเฟส 5 นี้ (โดยเฉพาะช่วง Step 500 ขึ้นไป)

## Step 457: ภาพรวม GitLab Tiers — Free, Premium, Ultimate

GitLab แบ่งระดับการใช้งาน (Tiers) ออกเป็น 3 ระดับหลัก ทั้งบน GitLab.com (SaaS) และ GitLab Self-Managed โดยแต่ละ Tier จะปลดล็อกฟีเจอร์เพิ่มเติมตามลำดับ

### GitLab Free

**เป้าหมาย:** นักพัฒนาอิสระ ทีมเล็ก และโปรเจกต์ Open Source

ฟีเจอร์หลักที่ได้ในระดับ Free:

- Repository ไม่จำกัดจำนวน ทั้ง private และ public
- Merge Request พร้อม Code Review พื้นฐาน
- GitLab CI/CD พร้อมโควตา CI/CD minutes ฟรีต่อเดือน (จำนวนจำกัด)
- Issue Tracking, Issue Boards พื้นฐาน
- Container Registry และ Package Registry พื้นฐาน
- Self-host ได้ฟรีแบบไม่จำกัดผู้ใช้ผ่าน Community Edition

### GitLab Premium

**เป้าหมาย:** ทีมระดับองค์กรขนาดกลางที่ต้องการฟีเจอร์การจัดการทีมและ workflow ที่ซับซ้อนขึ้น

ฟีเจอร์เพิ่มเติมจาก Free ที่สำคัญ:

- **Merge Approval Rules ขั้นสูง** — กำหนดกฎการอนุมัติที่ซับซ้อนได้ เช่น ต้องมีผู้อนุมัติจากทีมเฉพาะ
- **Code Owners** — กำหนดเจ้าของโค้ดในแต่ละส่วนของ repository (คล้าย CODEOWNERS ของ GitHub ที่เราเรียนมาแล้วในเฟส 4)
- **Merge Trains** — จัดคิวการ merge หลาย MR พร้อมกันอย่างปลอดภัย
- **Epics** — จัดกลุ่ม Issue หลายตัวเข้าด้วยกันเป็นเป้าหมายใหญ่ระดับไตรมาส/ปี
- **Advanced CI/CD features** — เช่น Multi-project pipelines, parent-child pipelines
- **Priority Support** จากทีม GitLab
- **Group-level Analytics** ที่ละเอียดขึ้น

### GitLab Ultimate

**เป้าหมาย:** องค์กรขนาดใหญ่ที่ต้องการ Security, Compliance และ Portfolio Management ระดับสูงสุด

ฟีเจอร์เพิ่มเติมจาก Premium ที่สำคัญ:

- **Security Dashboard เต็มรูปแบบ** — SAST (Static Application Security Testing), DAST (Dynamic Application Security Testing), Dependency Scanning, Container Scanning, License Compliance ครบชุด
- **Vulnerability Management** — ติดตามและจัดการช่องโหว่ความปลอดภัยที่ตรวจพบทั้งหมดในที่เดียว
- **Compliance Management** — สร้างและบังคับใช้นโยบาย compliance ระดับองค์กร พร้อม Audit Events ละเอียด
- **Value Stream Analytics ขั้นสูง** — วิเคราะห์ประสิทธิภาพของกระบวนการ DevOps ทั้งหมดตั้งแต่ Plan ถึง Monitor
- **Portfolio Management** — จัดการ Epic หลายระดับ (Epics ซ้อน Epics) สำหรับองค์กรขนาดใหญ่ที่มีหลายทีม หลายผลิตภัณฑ์
- **GitLab Dedicated** เป็นตัวเลือกเสริมสำหรับ Ultimate เท่านั้น (ตามที่กล่าวไปใน Step 453)

### ตารางสรุปเปรียบเทียบ 3 Tiers

| ฟีเจอร์ | Free | Premium | Ultimate |
|---|---|---|---|
| Repository และ MR พื้นฐาน | ✓ | ✓ | ✓ |
| CI/CD พื้นฐาน | ✓ | ✓ | ✓ |
| Merge Approval Rules ขั้นสูง | ✗ | ✓ | ✓ |
| Code Owners | ✗ | ✓ | ✓ |
| Merge Trains | ✗ | ✓ | ✓ |
| Epics | ✗ | ✓ | ✓ (พร้อม nested epics) |
| Security Scanning เต็มรูปแบบ (SAST/DAST) | บางส่วน | บางส่วน | ครบชุด |
| Compliance Management | ✗ | ✗ | ✓ |
| Vulnerability Management | ✗ | ✗ | ✓ |
| GitLab Dedicated | ✗ | ✗ | ✓ (ตัวเลือกเสริม) |

### หมายเหตุสำคัญ

รายละเอียดฟีเจอร์ในแต่ละ Tier และราคาอาจมีการเปลี่ยนแปลงอยู่เสมอตามที่ GitLab Inc. ปรับปรุงผลิตภัณฑ์ ผู้เรียนควรตรวจสอบหน้า pricing อย่างเป็นทางการของ GitLab เพื่อดูรายละเอียดล่าสุดก่อนตัดสินใจใช้งานจริงในองค์กร สิ่งที่หลักสูตรนี้ต้องการให้จำคือ **โครงสร้างแนวคิดของการแบ่ง Tier** ที่ไล่ระดับจากการใช้งานพื้นฐาน ไปสู่การบริหารทีมขนาดกลาง และสุดท้ายคือ Security/Compliance ระดับองค์กรขนาดใหญ่ — ไม่ใช่ตัวเลขราคาที่เปลี่ยนแปลงได้ตลอดเวลา

## Step 458: ทำไมองค์กรจำนวนมากเลือก GitLab

หลังจากที่เราเข้าใจความแตกต่างเชิงเทคนิคและโครงสร้างธุรกิจของ GitLab แล้ว มาถึงคำถามสำคัญ: **ทำไมองค์กรจำนวนมากถึงเลือกใช้ GitLab แทนที่จะใช้ GitHub ซึ่งเป็นเจ้าตลาดที่มีชุมชนใหญ่กว่ามาก**

### เหตุผลที่ 1: Data Sovereignty (อธิปไตยของข้อมูล)

นี่คือเหตุผลที่สำคัญที่สุดสำหรับองค์กรจำนวนมาก โดยเฉพาะในอุตสาหกรรมที่มีการกำกับดูแลเข้มงวด (regulated industries)

หลายประเทศและหลายอุตสาหกรรมมีกฎหมายหรือข้อบังคับที่กำหนดว่าข้อมูลบางประเภท (โดยเฉพาะซอร์สโค้ดที่เกี่ยวข้องกับความมั่นคง การเงิน หรือข้อมูลส่วนบุคคลที่อ่อนไหว) **ต้องถูกจัดเก็บภายในประเทศ หรือภายในเครือข่ายที่องค์กรควบคุมได้เองเท่านั้น** ตัวอย่างเช่น:

- หน่วยงานรัฐบาลหลายประเทศที่มีกฎหมายความมั่นคงไซเบอร์เข้มงวด
- ธนาคารและสถาบันการเงินที่อยู่ภายใต้การกำกับดูแลของธนาคารกลาง
- บริษัทด้านกลาโหมและอวกาศที่ทำงานกับข้อมูลที่เป็นความลับ
- โรงพยาบาลและสถาบันสุขภาพที่ต้องปฏิบัติตามกฎหมายคุ้มครองข้อมูลสุขภาพ

องค์กรเหล่านี้ **ไม่สามารถฝากซอร์สโค้ดไว้บน cloud ของบริษัทภายนอกได้เลยไม่ว่าจะเป็น GitHub หรือ GitLab.com** ทางออกเดียวคือการ self-host และ **GitLab Self-Managed Community Edition ที่ฟรี 100% ไม่จำกัดผู้ใช้** ตอบโจทย์นี้ได้ตรงจุดที่สุด เมื่อเทียบกับ GitHub ที่ทางเลือก self-host (GitHub Enterprise Server) มีค่าใช้จ่าย license เสมอ

### เหตุผลที่ 2: All-in-One Platform ลดความซับซ้อนของ Tool Stack

ตามที่อธิบายไปใน Step 452 การรวมทุกขั้นตอนของ DevOps ไว้ในเครื่องมือเดียวช่วยลดภาระการบริหารจัดการอย่างมหาศาลสำหรับทีม IT/DevOps ขององค์กร

ลองนึกภาพองค์กรขนาดใหญ่ที่มีทีมพัฒนาซอฟต์แวร์หลายสิบทีม ถ้าแต่ละขั้นตอนของ DevOps ต้องใช้เครื่องมือแยกกัน (Jira + GitHub + Jenkins + Artifactory + Datadog + Snyk) ทีม IT ต้องดูแล:

- License และค่าใช้จ่ายของเครื่องมือ 6 ตัวแยกกัน
- ระบบ Authentication/Authorization (SSO) ที่ต้องเชื่อมกับทุกเครื่องมือ
- การอัปเดตเวอร์ชันของแต่ละเครื่องมือแยกกัน (ถ้า self-host)
- Integration ระหว่างเครื่องมือที่อาจพังเมื่อมีการอัปเดตเวอร์ชัน

การใช้ GitLab เพียงตัวเดียวช่วยลดจำนวนเครื่องมือที่ต้องบริหารจัดการลงอย่างมาก ทำให้ทีม IT/DevOps ทำงานง่ายขึ้น ค่าใช้จ่ายด้าน license รวมลดลง และลดความเสี่ยงจาก integration ที่ซับซ้อน

### เหตุผลที่ 3: ความโปร่งใสของ Roadmap และ Open Core

เนื่องจาก GitLab เป็น **Open Core** (โค้ดหลักส่วน Community Edition เปิดเผยต่อสาธารณะทั้งหมด) องค์กรที่กังวลเรื่องการถูกล็อกเข้ากับผลิตภัณฑ์เชิงพาณิชย์แบบปิด (vendor lock-in) รู้สึกมั่นใจมากกว่า เพราะสามารถตรวจสอบโค้ดได้เองว่าไม่มีอะไรแอบแฝง และในกรณีเลวร้ายที่สุดที่ต้องเลิกใช้บริการของ GitLab Inc. ก็ยังสามารถ self-host เวอร์ชัน Community Edition ต่อไปได้เองโดยไม่ต้องพึ่งพาบริษัทอีกต่อไป

### เหตุผลที่ 4: ต้นทุนรวม (Total Cost of Ownership) ที่คุ้มค่ากว่าในบางบริบท

สำหรับองค์กรที่มีทีม IT ที่มีความสามารถดูแล infrastructure เองอยู่แล้ว การ self-host GitLab Community Edition แบบฟรีไม่จำกัดผู้ใช้ อาจมีต้นทุนรวมต่ำกว่าการซื้อ license หลายตัวสำหรับเครื่องมือ DevOps แยกกันหลายตัวอย่างมีนัยสำคัญ โดยเฉพาะในองค์กรขนาดใหญ่ที่มีนักพัฒนาหลายพันคน ซึ่งค่า license แบบคิดตามหัวคน (per-seat pricing) ของเครื่องมือหลายตัวรวมกันอาจสูงกว่าการดูแล GitLab instance ของตัวเองมาก

### เหตุผลที่ 5: Auto DevOps และความง่ายสำหรับทีมที่มีทรัพยากร DevOps จำกัด

สำหรับทีมขนาดเล็กถึงกลางที่ไม่มีวิศวกร DevOps เฉพาะทางมากพอ ฟีเจอร์ **Auto DevOps** ของ GitLab ที่ตั้งค่า pipeline การ build, test, security scan และ deploy ให้อัตโนมัติโดยตรวจจับจากภาษาโปรแกรมมิ่งและ framework ที่ใช้ ช่วยลดภาระในการเขียน CI/CD pipeline เองตั้งแต่ศูนย์ได้มาก

### สรุปภาพรวม

จะเห็นได้ว่าเหตุผลหลักที่องค์กรเลือก GitLab ไม่ใช่เพราะ GitLab "ดีกว่า" GitHub ในทุกมิติ แต่เป็นเพราะ **บริบทและความต้องการเฉพาะขององค์กรนั้น ๆ ตรงกับจุดแข็งของ GitLab พอดี** โดยเฉพาะเรื่อง data sovereignty, การลดความซับซ้อนของ tool stack, และต้นทุนรวมในระยะยาว — นี่คือเหตุผลว่าทำไมวิศวกรมืออาชีพจึงจำเป็นต้องเข้าใจทั้งสองแพลตฟอร์ม ไม่ใช่ยึดติดกับแพลตฟอร์มเดียว

## Step 459: กรณีศึกษาจริง — องค์กรระดับโลกที่ใช้ GitLab

เพื่อให้เห็นภาพชัดเจนว่า GitLab ไม่ได้เป็นเพียงทางเลือกทางทฤษฎี แต่ถูกใช้งานจริงในระดับองค์กรขนาดใหญ่ทั่วโลก มาดูตัวอย่างองค์กรที่เคยถูกกล่าวถึงในสื่อและกรณีศึกษาที่เผยแพร่ต่อสาธารณะว่าใช้งาน GitLab

### NASA

**องค์การบริหารการบินและอวกาศแห่งชาติ (NASA)** ของสหรัฐอเมริกา เป็นหนึ่งในตัวอย่างที่ถูกกล่าวถึงบ่อยที่สุดในฐานะองค์กรภาครัฐขนาดใหญ่ที่นำ GitLab มาใช้ในการจัดการซอร์สโค้ดของโครงการต่าง ๆ

เหตุผลที่องค์กรลักษณะนี้มักเลือก GitLab สอดคล้องกับสิ่งที่เราอธิบายไปใน Step 458 นั่นคือความต้องการด้าน **data sovereignty และความปลอดภัยระดับสูงสุด** เนื่องจากโครงการด้านอวกาศจำนวนมากเกี่ยวข้องกับเทคโนโลยีที่มีความอ่อนไหวด้านความมั่นคงของชาติ การมีทางเลือกให้ self-host ระบบจัดการโค้ดไว้ภายในเครือข่ายที่ควบคุมได้เองอย่างสมบูรณ์จึงเป็นข้อกำหนดที่สำคัญมาก

### Goldman Sachs

**Goldman Sachs** หนึ่งในสถาบันการเงินและวาณิชธนกิจ (investment bank) ชั้นนำของโลก เป็นอีกตัวอย่างที่มักถูกยกมาพูดถึงในบริบทของการนำ GitLab มาใช้ในอุตสาหกรรมการเงิน

อุตสาหกรรมการเงินเป็นหนึ่งในอุตสาหกรรมที่มีการกำกับดูแล (regulation) เข้มงวดที่สุดในโลก ธนาคารและสถาบันการเงินขนาดใหญ่ต้องปฏิบัติตามกฎระเบียบด้านความปลอดภัยไซเบอร์และการตรวจสอบ (audit) ที่เข้มงวดมาก การมีระบบ Version Control ที่สามารถควบคุมได้เองอย่างสมบูรณ์ พร้อมความสามารถด้าน Compliance Management และ Audit Events ที่ GitLab Ultimate มีให้ จึงตอบโจทย์ความต้องการเฉพาะทางของอุตสาหกรรมนี้ได้ดี

### รูปแบบทั่วไปที่พบในองค์กรที่เลือก GitLab

จากกรณีศึกษาเหล่านี้ เราสามารถสรุปรูปแบบร่วมที่มักพบในองค์กรที่ตัดสินใจเลือก GitLab ได้ดังนี้:

1. **อยู่ในอุตสาหกรรมที่มีการกำกับดูแลเข้มงวด** เช่น การเงิน การบินอวกาศ กลาโหม สุขภาพ หรือหน่วยงานภาครัฐ
2. **มีทีม IT/Infrastructure ภายในที่แข็งแกร่งพอจะดูแล self-hosted platform เองได้** เพราะการ self-host ต้องใช้ความรู้และทรัพยากรบุคคลด้าน Ops
3. **ต้องการลดความซับซ้อนของ Tool Stack** ในองค์กรขนาดใหญ่ที่มีทีมพัฒนาจำนวนมากและหลากหลายโปรเจกต์
4. **ให้ความสำคัญกับความสามารถในการตรวจสอบและควบคุม (auditability)** ของกระบวนการพัฒนาซอฟต์แวร์ทั้งหมด ตั้งแต่ code review ไปจนถึง deployment

### ข้อควรระวังในการอ้างอิงกรณีศึกษา

สิ่งที่ควรทำความเข้าใจคือ การที่องค์กรใหญ่ระดับ NASA หรือ Goldman Sachs เคยถูกกล่าวถึงว่าใช้ GitLab ไม่ได้แปลว่าทั้งองค์กรใช้ GitLab เพียงแพลตฟอร์มเดียวสำหรับทุกโครงการ ในความเป็นจริง องค์กรขนาดใหญ่ระดับนี้มักมีทีมย่อยจำนวนมากที่ใช้เครื่องมือหลากหลายแตกต่างกันไปตามความเหมาะสมของแต่ละโครงการ บางทีมอาจใช้ GitHub บางทีมอาจใช้ GitLab และบางทีมอาจใช้ Bitbucket หรือระบบภายในที่พัฒนาขึ้นเอง — สิ่งสำคัญคือการเข้าใจ **เหตุผลเชิงหลักการ** ว่าทำไมองค์กรลักษณะนี้ถึงพิจารณา GitLab เป็นตัวเลือก มากกว่าการท่องจำชื่อบริษัทเพียงอย่างเดียว

เหตุผล: นี่คือสถานการณ์คลาสสิกที่ตรงกับจุดขายหลักของ GitLab พอดี นั่นคือการเป็น All-in-One DevOps Platform ที่รวม Plan (แทน Jira), Create (แทน GitHub), Verify/Release (แทน Jenkins), และ Monitor (แทน Datadog บางส่วน) ไว้ในที่เดียว การย้ายมาใช้ GitLab ตัวเดียวจะช่วยลดจำนวนเครื่องมือที่ต้องดูแล ลดปัญหา integration ที่พังบ่อย และอาจลดค่าใช้จ่าย license รวมในระยะยาว อย่างไรก็ตาม ควรพิจารณาต้นทุนการย้ายระบบ (migration cost) และเวลาที่ทีมต้องใช้ปรับตัวกับเครื่องมือใหม่ประกอบการตัดสินใจด้วย ไม่ควรตัดสินใจย้ายแบบทันทีทั้งองค์กรโดยไม่ทำ pilot project ก่อน

</details>

### สถานการณ์ที่ 5: ทีมพัฒนาเกมอินดี้ที่ต้องการ AI ช่วยเขียนโค้ด

ทีมพัฒนาเกมอินดี้ขนาดเล็ก 5 คน งบประมาณจำกัดมาก ต้องการเครื่องมือที่ช่วยเพิ่มความเร็วในการเขียนโค้ดให้มากที่สุดผ่าน AI code assistant เพราะทีมเล็กต้องทำงานหลายอย่างพร้อมกัน ไม่มีข้อกำหนดด้าน data sovereignty ใด ๆ และไม่จำเป็นต้อง self-host

**ลองคิดเอง:** ควรเลือกอะไร เพราะอะไร?

<details>
<summary>แนวทางการวิเคราะห์ (คลิกดูหลังจากคิดเองแล้ว)</summary>

**แนะนำ: GitHub**

เหตุผล: ทีมนี้ไม่มีข้อจำกัดด้าน data sovereignty และไม่ต้องการ self-host ดังนั้นจุดขายหลักของ GitLab (self-hosting ฟรี, data control) จึงไม่มีน้ำหนักในการตัดสินใจ ในขณะที่ความต้องการหลักของทีมคือ "AI ช่วยเขียนโค้ดให้เร็วที่สุดด้วยงบจำกัด" ซึ่ง GitHub Copilot ที่ผูกกับ GitHub โดยตรงเป็นผู้นำตลาดในด้านนี้อย่างชัดเจน และ GitHub Free ก็เพียงพอสำหรับทีมขนาด 5 คนอยู่แล้วโดยไม่ต้องเสียค่าใช้จ่ายเพิ่ม

</details>

### ข้อคิดสรุปจากแบบฝึกหัดนี้

จะเห็นได้ว่าไม่มีคำตอบตายตัวว่า "GitHub ดีกว่า" หรือ "GitLab ดีกว่า" เสมอไป การตัดสินใจที่ถูกต้องขึ้นอยู่กับปัจจัยเฉพาะของแต่ละสถานการณ์เสมอ ปัจจัยหลักที่ควรใช้ในการวิเคราะห์ทุกครั้งคือ:

1. **ข้อกำหนดด้าน Data Sovereignty/Compliance** — มีกฎหมายหรือนโยบายบังคับให้ต้อง self-host หรือไม่
2. **ขนาดและความสามารถของทีม IT/DevOps** — มีทรัพยากรพอจะดูแล self-hosted platform เองหรือไม่
3. **ความสำคัญของ Ecosystem/Community** — ต้องการเข้าถึงชุมชน Open Source ขนาดใหญ่หรือไม่
4. **ความซับซ้อนของ Tool Stack ปัจจุบัน** — ต้องการรวมเครื่องมือหลายตัวเข้าเป็นหนึ่งเดียวหรือไม่
5. **งบประมาณและต้นทุนรวม** — เปรียบเทียบ TCO ระหว่างสองแพลตฟอร์มในบริบทของตัวเองอย่างละเอียด

ทักษะการวิเคราะห์แบบนี้คือสิ่งที่แยกวิศวกรที่ "รู้จักเครื่องมือ" ออกจากวิศวกรที่ "เลือกเครื่องมือได้อย่างชาญฉลาด" ซึ่งเป็นทักษะระดับ Senior/Tech Lead ที่มีค่ามากในโลกการทำงานจริง

## สรุป Part 46

ใน Part นี้เราได้เปิดประตูสู่เฟส 5 ของหลักสูตร ด้วยการทำความรู้จัก GitLab อย่างละเอียดในทุกมิติ:

1. GitLab ก่อตั้งในปี 2011 โดย Dmitriy Zaporozhets และ Valery Sizov ที่ยูเครน เริ่มจากโปรเจกต์ Open Source ก่อนที่ Sytse Sijbrandij จะเข้ามาร่วมก่อตั้ง GitLab Inc. ในปี 2014 (Step 451)
2. GitLab มีวิสัยทัศน์เป็น "The DevOps Platform" ที่รวมทุกขั้นตอนตั้งแต่ Plan ถึง Monitor ไว้ในเครื่องมือเดียว (Step 452)
3. GitLab มี 3 รูปแบบการใช้งาน: GitLab.com (SaaS), GitLab Self-Managed (ติดตั้งเอง), และ GitLab Dedicated (single-tenant ที่ GitLab ดูแลให้) (Step 453)
4. เปรียบเทียบ GitLab กับ GitHub แบบละเอียดในทุกมิติ ทั้งราคา ecosystem ความสามารถ CI/CD และศัพท์เฉพาะที่ต่างกัน (Step 454)
5. Merge Request ของ GitLab คือแนวคิดเดียวกับ Pull Request ของ GitHub 100% ต่างกันแค่ชื่อและฟีเจอร์เสริมบางส่วน (Step 455)
6. GitLab มี CI/CD ในตัวมาตั้งแต่ปี 2015 ในขณะที่ GitHub Actions เพิ่งเปิดตัวปี 2019 ซึ่งส่งผลต่อความแนบแน่นของ CI/CD กับแกนกลางของแต่ละแพลตฟอร์ม (Step 456)
7. GitLab แบ่งเป็น 3 Tiers คือ Free, Premium, Ultimate โดยไล่ระดับฟีเจอร์จากพื้นฐานไปจนถึง Security/Compliance ระดับองค์กร (Step 457)
8. องค์กรจำนวนมากเลือก GitLab เพราะเหตุผลด้าน Data Sovereignty, All-in-One Platform, ความโปร่งใสของ Open Core, ต้นทุนรวม และ Auto DevOps (Step 458)
9. องค์กรอย่าง NASA และ Goldman Sachs เคยถูกกล่าวถึงในฐานะตัวอย่างองค์กรขนาดใหญ่ที่ใช้ GitLab สอดคล้องกับความต้องการด้าน data sovereignty และ compliance (Step 459)
10. ฝึกวิเคราะห์สถานการณ์สมมติ 5 แบบเพื่อตัดสินใจเลือกระหว่าง GitHub และ GitLab อย่างมีเหตุผล (Step 460)

Part นี้คือรากฐานสำคัญที่จะทำให้คุณเข้าใจ "ทำไม" ก่อนที่จะไปเรียนรู้ "อย่างไร" ใน Part ถัดไป เมื่อเราเข้าใจแล้วว่า GitLab คืออะไร ต่างจาก GitHub อย่างไร และทำไมองค์กรถึงเลือกใช้มัน ก็ถึงเวลาที่จะลงมือติดตั้งและตั้งค่า GitLab จริง ๆ เพื่อเริ่มใช้งานด้วยตัวเอง
