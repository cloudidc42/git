## Step 911: ทำไมต้องวัดผลทีม Dev ด้วยข้อมูล ไม่ใช่แค่ความรู้สึกหรือ "จำนวนบรรทัดโค้ด"

### 911.1 ปัญหาของการบริหารทีมวิศวกรรมด้วย "ความรู้สึก" ล้วน ๆ

ผู้จัดการวิศวกรรม (Engineering Manager) หลายคนตัดสินใจเรื่องสำคัญ เช่น "ทีมนี้ทำงานได้ดีหรือไม่" "ควรเพิ่มคนตรงไหน" "กระบวนการตรงไหนที่เป็นคอขวด" โดยอาศัยความรู้สึกล้วน ๆ — ใครดูยุ่งที่สุดในที่ประชุม ใครพูดเก่งที่สุดตอนรายงานความคืบหน้า ใครดูเหมือน "ทำงานหนัก" เพราะ online จนดึก

ปัญหาของวิธีนี้คือ **ความรู้สึกมีอคติ (bias) สูงมาก** และมักวัดผิดเป้าโดยไม่รู้ตัว เช่น:

- **Visibility bias** — คนที่พูดในที่ประชุมบ่อย หรือ commit เวลาที่ manager เห็นพอดี มักถูกมองว่า "ทำงานหนักกว่า" ทั้งที่จริงอาจไม่ใช่
- **Recency bias** — ผลงานในสัปดาห์ล่าสุดมีน้ำหนักมากกว่าผลงานตลอดทั้งไตรมาสในความทรงจำของผู้จัดการ
- **Halo effect** — ถ้าคนคนหนึ่งเก่งเรื่องหนึ่งชัดเจน (เช่น debug เก่งมาก) คนอื่นมักเหมาโยงว่าเขาต้อง "เก่งทุกด้าน" ทั้งที่ไม่จริงเสมอไป
- **ไม่มีข้อมูลย้อนหลังที่ตรวจสอบได้** — เมื่อถูกถามว่า "ทำไมถึงคิดว่าทีม A ช้ากว่าทีม B" คำตอบที่ได้มักเป็น "รู้สึกแบบนั้น" ซึ่งไม่สามารถนำไปปรับปรุงอะไรได้อย่างเป็นระบบ

การตัดสินใจเชิงกลยุทธ์ระดับองค์กร (เช่น จะลงทุนด้าน platform engineering หรือไม่ จะจ้างคนเพิ่มในทีมไหน จะรื้อกระบวนการ code review ใหม่หรือไม่) ต้องการ**ข้อมูลเชิงประจักษ์ (empirical data)** ที่ตรวจสอบซ้ำได้ ไม่ใช่ความรู้สึกของคนคนเดียว

### 911.2 ทำไม "จำนวนบรรทัดโค้ด" (Lines of Code) ถึงเป็น Metric ที่วัดผิด

ในอดีต (และแม้แต่ปัจจุบันในบางองค์กรที่ยังไม่เข้าใจเรื่องนี้ดีพอ) มีความพยายามวัดผลงานวิศวกรด้วย **จำนวนบรรทัดโค้ดที่เขียน (Lines of Code — LOC)** ต่อวัน/สัปดาห์/เดือน แนวคิดนี้มีปัญหาร้ายแรงหลายชั้น:

**1. LOC วัดปริมาณ ไม่ใช่คุณค่า**

วิศวกรที่เก่งจริงมักทำให้โค้ด**สั้นลง**ไม่ใช่ยาวขึ้น การ refactor โค้ด 500 บรรทัดให้เหลือ 50 บรรทัดที่อ่านง่ายกว่า ทำงานถูกต้องกว่า และบำรุงรักษาง่ายกว่า คือผลงานที่มีคุณค่ามหาศาล แต่ถ้าวัดด้วย LOC ผลลัพธ์จะออกมาเป็น **"−450 บรรทัด"** ซึ่งดูเหมือนเป็นผลงานติดลบ ทั้งที่ในความเป็นจริงคือผลงานที่ดีที่สุดของสัปดาห์นั้น

**2. LOC สร้างแรงจูงใจที่ผิด (Perverse Incentive)**

ถ้าวิศวกรรู้ว่าตัวเองถูกวัดด้วย LOC พฤติกรรมที่มีเหตุผล (แต่ทำลายองค์กร) คือ:
- เขียนโค้ดยาวเกินจำเป็นโดยตั้งใจ (copy-paste แทนการเรียกใช้ function ร่วม)
- แตก logic ที่ควรอยู่บรรทัดเดียวออกเป็นหลายบรรทัดโดยไม่จำเป็น
- หลีกเลี่ยงการใช้ library หรือ framework ที่ช่วยลดโค้ด เพราะจะทำให้ LOC ของตัวเองต่ำ
- หลีกเลี่ยงงาน refactor/cleanup ทั้งที่จำเป็น เพราะงานเหล่านี้มักทำให้ LOC สุทธิติดลบ

**3. LOC ไม่แยกความแตกต่างระหว่างงานยากกับงานง่าย**

การแก้บั๊กที่ซับซ้อนมากอาจใช้เวลาค้นคว้า 3 วันเต็ม แต่สุดท้ายแก้ด้วยโค้ด 2 บรรทัด ในขณะที่การเขียนฟอร์มธรรมดา ๆ ที่ generate จาก template อาจได้โค้ด 2,000 บรรทัดในครึ่งวัน ถ้าวัดด้วย LOC งานแรกจะดูเหมือน "ไม่มีผลงาน" ทั้งที่มีมูลค่าสูงกว่ามาก

**4. งานสำคัญจำนวนมากไม่มี LOC เลย**

การช่วย code review ให้เพื่อนร่วมทีม การเขียนเอกสาร (documentation) การ mentor รุ่นน้อง การออกแบบสถาปัตยกรรมในกระดาน whiteboard การไปคุยกับทีมอื่นเพื่อลด dependency ที่ซับซ้อน — งานเหล่านี้ล้วนสร้างคุณค่ามหาศาลให้องค์กร แต่ **ไม่มี LOC แม้แต่บรรทัดเดียว**

Bill Gates เคยพูดประโยคที่มักถูกอ้างถึงในวงการนี้ (แม้จะไม่มีหลักฐานยืนยันแหล่งที่มาชัดเจน 100% แต่สาระของมันถูกต้องและเป็นที่ยอมรับกันอย่างกว้างขวางในวงการวิศวกรรมซอฟต์แวร์):

> "การวัดความคืบหน้าของโปรเจกต์ซอฟต์แวร์ด้วยจำนวนบรรทัดโค้ด ก็เหมือนกับการวัดความคืบหน้าของการสร้างเครื่องบินด้วยน้ำหนักของมัน"

### 911.3 Metric อื่น ๆ ที่วัดผิดในลักษณะเดียวกัน

นอกจาก LOC ยังมี metric ยอดนิยมอีกหลายตัวที่มีปัญหาคล้ายกันถ้าใช้วัด**รายบุคคล**หรือใช้แบบตื้น ๆ โดยไม่เข้าใจบริบท:

| Metric ที่วัดผิดบ่อย | ปัญหาที่แท้จริง |
|---|---|
| จำนวน Commit ต่อวัน | นับได้ง่ายจนถูก game ได้ทันที เช่น แตก 1 commit เป็น 10 commit เล็ก ๆ |
| จำนวน Pull Request ที่ merge | ไม่บอกอะไรเรื่องคุณภาพ อาจ merge PR เล็ก ๆ ไม่มีนัยสำคัญจำนวนมากเพื่อดันตัวเลข |
| ชั่วโมงทำงาน (เวลา login/logout) | วัด "การมีตัวตนอยู่" ไม่ใช่ "ผลลัพธ์" — คนนั่งหน้าจอนานอาจ productive น้อยกว่าคนที่คิดแล้วเขียนเร็ว |
| จำนวนบั๊กที่แก้ | ถ้าใช้วัดรายบุคคลจะสร้างแรงจูงใจให้ "ไม่รายงานบั๊กของตัวเอง" หรือแก้บั๊กง่าย ๆ จำนวนมากแทนบั๊กยากที่สำคัญกว่า |

### 911.4 แล้วควรวัดอะไรแทน

คำตอบที่งานวิจัยด้าน software engineering productivity ชี้ตรงกันคือ ต้องวัดที่ **outcome ของระบบส่งมอบซอฟต์แวร์ในภาพรวม (delivery system)** ไม่ใช่ output ของบุคคล และต้องวัดทั้ง **ความเร็ว (velocity/throughput)** และ **คุณภาพ/ความเสถียร (stability)** ไปพร้อมกันเสมอ เพราะการวัดแค่ด้านใดด้านหนึ่งจะนำไปสู่การ optimize ที่บิดเบี้ยว (เร็วแต่พังบ่อย หรือช้าแต่นิ่ง)

นี่คือเหตุผลที่ทีมวิจัย **DevOps Research and Assessment (DORA)** ใช้เวลาหลายปีศึกษาองค์กรซอฟต์แวร์หลายพันแห่งทั่วโลก จนตกผลึกออกมาเป็น **4 metric หลัก** ที่พิสูจน์แล้วทางสถิติว่าสามารถแยกแยะองค์กรที่มีประสิทธิภาพสูงออกจากองค์กรที่มีประสิทธิภาพต่ำได้อย่างชัดเจน และไม่ถูก game ได้ง่ายเท่า metric แบบ LOC หรือจำนวน commit — เราจะเจาะลึกเรื่องนี้ใน Step ถัดไป

นอกจาก DORA แล้ว ยังมีกรอบคิดเสริมที่ควรรู้จักไว้ชื่อ **SPACE Framework** (เสนอโดยนักวิจัยจาก Microsoft, GitHub และ University of Victoria ในปี 2021) ซึ่งมองว่า productivity ของวิศวกรไม่ควรวัดด้วยมิติเดียว แต่ต้องมองทั้ง 5 มิติร่วมกัน: **S**atisfaction and well-being (ความพึงพอใจและสุขภาวะ), **P**erformance (ผลลัพธ์ของงาน), **A**ctivity (ปริมาณกิจกรรม), **C**ommunication and collaboration (การสื่อสารและร่วมมือ), และ **E**fficiency and flow (ความลื่นไหลในการทำงาน) — DORA Metrics ที่เราจะเรียนต่อจากนี้จัดอยู่ในมิติ Performance และ Efficiency เป็นหลัก ส่วนมิติอื่นต้องใช้เครื่องมือวัดคนละแบบ (เช่น แบบสำรวจความพึงพอใจ) ซึ่งอยู่นอกขอบเขตของ Part นี้ที่เน้นข้อมูลจาก Git โดยเฉพาะ

## Step 912: DORA Metrics 4 ตัวหลัก ที่มาจากงานวิจัยของ DevOps Research and Assessment

### 912.1 DORA คืออะไร มาจากไหน

**DORA** ย่อมาจาก **DevOps Research and Assessment** เป็นทีมวิจัยที่เริ่มต้นการศึกษาอย่างเป็นระบบผ่านโครงการ **State of DevOps Report** ซึ่งเริ่มตีพิมพ์ครั้งแรกในปี **2014** โดยความร่วมมือกับบริษัท Puppet ก่อนที่ทีมวิจัยจะแยกตัวออกมาก่อตั้งบริษัท **DevOps Research and Assessment LLC** อย่างเป็นทางการในปี **2015** นำโดยนักวิจัยหลัก 3 คน:

- **Dr. Nicole Forsgren** — นักวิจัยด้าน software engineering productivity ผู้เป็นหัวหอกหลักด้านสถิติและระเบียบวิธีวิจัย
- **Jez Humble** — ผู้เขียนหนังสือ "Continuous Delivery" ที่มีอิทธิพลอย่างสูงต่อวงการ DevOps
- **Gene Kim** — ผู้เขียนหนังสือ "The Phoenix Project" และผู้ร่วมก่อตั้งงานประชุม DevOps Enterprise Summit

ทั้งสามคนร่วมกันเขียนหนังสือ **"Accelerate: The Science of Lean Software and DevOps"** ตีพิมพ์ปี **2018** ซึ่งเป็นการรวบรวมผลการวิจัยหลายปีให้อยู่ในรูปแบบที่นำไปปฏิบัติได้จริง หนังสือเล่มนี้ถือเป็นงานอ้างอิงสำคัญที่สุดเล่มหนึ่งของวงการ Software Delivery Performance จนถึงปัจจุบัน

ในปี **2018** บริษัท **Google Cloud ได้เข้าซื้อกิจการ DORA** และทำให้ทีมวิจัยกลายเป็นส่วนหนึ่งของ Google Cloud นับแต่นั้น State of DevOps Report ก็ยังคงตีพิมพ์ต่อเนื่องทุกปีภายใต้ชื่อ Google Cloud DORA จนถึงปัจจุบัน โดยอาศัยข้อมูลจากแบบสำรวจ (survey) องค์กรซอฟต์แวร์หลายพันแห่งทั่วโลกในแต่ละปี

### 912.2 ระเบียบวิธีวิจัย — ทำไมตัวเลขนี้ถึงน่าเชื่อถือ

สิ่งที่ทำให้ DORA Metrics แตกต่างจาก metric ทั่วไปที่มีคนเสนอกันเยอะแยะในวงการคือ **มันมาจากการวิจัยเชิงสถิติจริงจัง** ไม่ใช่ความเห็นส่วนตัวของใครคนหนึ่ง ทีม DORA ใช้วิธีการทางสถิติ (เช่น cluster analysis) วิเคราะห์ข้อมูลแบบสำรวจจากองค์กรหลายพันแห่ง เพื่อหาว่า:

1. มี pattern การรวมกลุ่ม (cluster) ขององค์กรตามพฤติกรรมการส่งมอบซอฟต์แวร์หรือไม่
2. กลุ่มที่ทำผลงานได้ดี (high performer) มีลักษณะร่วมอะไรที่แตกต่างจากกลุ่มที่ทำได้ไม่ดี (low performer)
3. ลักษณะเหล่านั้นมีความสัมพันธ์เชิงสถิติ (correlation) กับผลลัพธ์ทางธุรกิจจริงหรือไม่ เช่น profitability, market share, productivity, customer satisfaction

ผลการวิจัยพบว่ามี **4 ตัวชี้วัดหลัก** ที่สามารถแยกแยะองค์กรที่มีประสิทธิภาพการส่งมอบซอฟต์แวร์สูงออกจากองค์กรที่มีประสิทธิภาพต่ำได้อย่างชัดเจนและสม่ำเสมอทุกปีที่ทำการศึกษา:

| # | Metric | มิติที่วัด | คำถามที่ตอบ |
|---|---|---|---|
| 1 | **Deployment Frequency** | ความเร็ว (Throughput) | "ทีมนี้ปล่อยโค้ดขึ้น production บ่อยแค่ไหน" |
| 2 | **Lead Time for Changes** | ความเร็ว (Throughput) | "จากตอนที่ commit โค้ดจนถึงตอนที่มันทำงานบน production ใช้เวลานานแค่ไหน" |
| 3 | **Change Failure Rate** | คุณภาพ/ความเสถียร (Stability) | "การเปลี่ยนแปลงที่ปล่อยออกไป ทำให้เกิดปัญหากับผู้ใช้บ่อยแค่ไหน" |
| 4 | **Time to Restore Service (MTTR)** | คุณภาพ/ความเสถียร (Stability) | "เมื่อระบบมีปัญหา ทีมกู้คืนกลับมาให้ใช้งานได้ปกติเร็วแค่ไหน" |

สังเกตว่า 2 ตัวแรกวัด **ความเร็ว** และ 2 ตัวหลังวัด **ความเสถียร** — นี่คือการออกแบบที่ตั้งใจ เพราะถ้าวัดแค่ความเร็วอย่างเดียว ทีมอาจ deploy บ่อยมากแต่พังตลอดเวลา และถ้าวัดแค่ความเสถียรอย่างเดียว ทีมอาจนิ่งเกินไปจนไม่ส่งมอบคุณค่าใหม่ให้ผู้ใช้เลย

### 912.3 ข้อค้นพบที่สำคัญที่สุดของงานวิจัย DORA

ข้อค้นพบที่พลิกความเข้าใจเดิมของวงการมากที่สุดคือ:

> **ความเร็วกับความเสถียรไม่ใช่ trade-off ที่ต้องเลือกอย่างใดอย่างหนึ่ง**

ก่อนงานวิจัยนี้ ความเชื่อทั่วไปในวงการคือ "ถ้าอยาก deploy เร็วขึ้น ต้องยอมรับความเสี่ยงที่จะพังบ่อยขึ้น" (speed vs. stability trade-off) แต่ข้อมูลจากองค์กรนับพันแห่งที่ DORA เก็บมาต่อเนื่องหลายปีกลับแสดงตรงกันข้าม: **องค์กรระดับ Elite Performer ทำได้ทั้งเร็วและมีคุณภาพสูงไปพร้อมกัน** ไม่ใช่แค่ทำได้อย่างใดอย่างหนึ่ง

เหตุผลเชิงกลไก (mechanism) ที่อธิบายปรากฏการณ์นี้คือ **ขนาดของการเปลี่ยนแปลง (batch size)** — องค์กรที่ deploy บ่อยมักทำเช่นนั้นได้เพราะแต่ละครั้งเปลี่ยนแปลงโค้ดในปริมาณน้อย (small batch) ซึ่งมีความเสี่ยงต่อครั้ง**ต่ำกว่า**การรวบรวมการเปลี่ยนแปลงจำนวนมากไว้ deploy ทีเดียวเป็นก้อนใหญ่ (big-bang release) นอกจากนี้ องค์กรที่ deploy บ่อยมักลงทุนกับระบบอัตโนมัติ (automated testing, automated rollback, feature flag) ที่ทำให้ทั้งความเร็วและความปลอดภัยเพิ่มขึ้นพร้อมกัน แทนที่จะขัดแย้งกัน

### 912.4 ตัวชี้วัดที่ 5 — Reliability

ในรายงาน State of DevOps ปี **2021** ทีม DORA ได้เพิ่มตัวชี้วัดที่ 5 เข้ามาเสริมชื่อ **Reliability** (ความน่าเชื่อถือของระบบที่ผู้ใช้สัมผัสจริง เช่น availability, latency, ความสามารถในการตอบสนองต่อความต้องการของผู้ใช้) เพื่อให้ครอบคลุมมุมมองของ operational performance ที่ไม่ได้จับได้จาก 4 metric เดิมทั้งหมด อย่างไรก็ตาม **4 metric ดั้งเดิม (Deployment Frequency, Lead Time, Change Failure Rate, MTTR) ยังคงเป็นแกนหลักที่ถูกอ้างอิงและนำไปใช้งานจริงมากที่สุด** และเป็นสิ่งที่ Part นี้จะเจาะลึกในรายละเอียด ส่วน Reliability มักต้องอาศัยข้อมูลจากระบบ monitoring/observability เพิ่มเติมนอกเหนือจากข้อมูล Git/CI ล้วน ๆ จึงอยู่นอกขอบเขตหลักของ Part นี้ที่เน้นข้อมูลจาก Git โดยเฉพาะ

## Step 913: Deployment Frequency — วัดอย่างไรจากข้อมูล Git/CI

### 913.1 นิยามอย่างเป็นทางการ

**Deployment Frequency** คือ **ความถี่ที่องค์กรปล่อยโค้ดขึ้นสู่ production สำเร็จ** โดย DORA ให้ความสำคัญกับคำว่า "production" อย่างเคร่งครัด — การ deploy ขึ้น staging หรือ QA environment **ไม่นับ** เพราะมันยังไม่ส่งมอบคุณค่าจริงให้ผู้ใช้ปลายทาง

ข้อควรระวังสำคัญ: Deployment Frequency **ไม่ใช่**เรื่องเดียวกับ "Release Frequency" ในความหมายดั้งเดิม องค์กรสมัยใหม่จำนวนมากแยก **การ deploy โค้ด** (การนำโค้ดไปรันบน production) ออกจาก **การ release ฟีเจอร์** (การเปิดให้ผู้ใช้เห็นฟีเจอร์นั้นจริง) โดยใช้เทคนิค **Feature Flag** — โค้ดอาจถูก deploy ขึ้น production ทุกวัน แต่ฟีเจอร์ใหม่อาจยังถูกปิดไว้ด้วย flag จนกว่าทีม product จะพร้อมเปิดให้ผู้ใช้เห็น สิ่งที่ DORA วัดคือ**การ deploy** ไม่ใช่การ release ฟีเจอร์

### 913.2 แหล่งข้อมูลสำหรับคำนวณ

ข้อมูลดิบที่ใช้คำนวณ Deployment Frequency มาจาก **CI/CD pipeline** เป็นหลัก ไม่ใช่จาก Git commit history ตรง ๆ เพราะการ commit หรือ merge เข้า `main` **ไม่ได้แปลว่า deploy ขึ้น production เสมอไป** (บางองค์กรใช้ trunk-based development ที่ merge เข้า main บ่อยมาก แต่การ deploy จริงอาจเกิดขึ้นเป็นรอบที่กำหนดไว้ต่างหาก)

แนวทางที่ถูกต้องคือ **นับจาก deploy job ที่รันสำเร็จ (successful) และมีเป้าหมายเป็น production environment เท่านั้น**

**ตัวอย่างจาก GitHub Actions:**

```yaml
# .github/workflows/deploy-production.yml
name: Deploy to Production

on:
  push:
    branches: [main]

jobs:
  deploy:
    runs-on: ubuntu-latest
    environment: production   # <-- จุดสำคัญ: ระบุ environment ชัดเจน
    steps:
      - uses: actions/checkout@v4
      - name: Deploy
        run: ./scripts/deploy.sh production
```

เมื่อ workflow ที่ระบุ `environment: production` รันสำเร็จ (conclusion เป็น `success`) นับเป็น 1 deployment event หนึ่งครั้ง สามารถดึงข้อมูลผ่าน GitHub REST API ได้จาก endpoint `GET /repos/{owner}/{repo}/deployments` ร่วมกับ `GET /repos/{owner}/{repo}/deployments/{deployment_id}/statuses` เพื่อกรองเฉพาะ status เป็น `success`

**ตัวอย่างจาก GitLab CI/CD:**

```yaml
# .gitlab-ci.yml
deploy-production:
  stage: deploy
  environment:
    name: production
    url: https://app.example.com
  script:
    - ./scripts/deploy.sh production
  rules:
    - if: '$CI_COMMIT_BRANCH == "main"'
```

GitLab เก็บข้อมูล deployment ทุกครั้งไว้ในตาราง `deployments` ภายใน และสามารถดูสรุปได้ผ่านหน้า **Operate > Environments** หรือดึงผ่าน GraphQL/REST API endpoint `/projects/:id/deployments` โดยกรอง `status=success` และ `environment=production`

### 913.3 สูตรคำนวณและตัวอย่าง

```
Deployment Frequency = จำนวน deployment ที่สำเร็จไปยัง production
                        ------------------------------------------
                                      ช่วงเวลาที่วัด
```

**ตัวอย่างการคำนวณ:**

```
สมมติทีม A มี deploy job ที่ status = success ไปยัง environment "production"
จำนวน 42 ครั้ง ในช่วง 30 วัน

Deployment Frequency = 42 / 30 วัน ≈ 1.4 ครั้งต่อวัน
→ จัดอยู่ในระดับ "หลายครั้งต่อวัน" ถ้านับเป็นค่าเฉลี่ยรายวันทำการ
```

### 913.4 ข้อควรระวังในการนับ

1. **ต้องแยก environment ให้ชัดเจน** — pipeline เดียวกันมักมี stage deploy ไป dev/staging/production หลายครั้ง ถ้านับรวมทุก environment ตัวเลขจะเฟ้อผิดความจริงมาก
2. **ต้องนับเฉพาะที่สำเร็จ (success)** — deploy ที่ fail กลางทางไม่ควรถูกนับเป็น deployment ที่สมบูรณ์ แต่ควรถูกเก็บแยกไว้ใช้คำนวณ Change Failure Rate แทน (Step 915)
3. **ระวัง deploy ซ้ำที่ไม่มีการเปลี่ยนแปลงจริง** — บาง pipeline อาจ trigger deploy ใหม่โดยไม่มีโค้ดเปลี่ยนแปลง (เช่น กด re-run ซ้ำเพราะ infrastructure ล่ม) ควรพิจารณาว่าจะนับหรือไม่นับกรณีนี้ตามบริบทขององค์กร
4. **สำหรับระบบที่มีหลาย service (microservices)** ควรตัดสินใจให้ชัดว่าจะวัดต่อ service หรือรวมทั้งระบบ — DORA แนะนำให้วัดในระดับที่ "ทีมหนึ่งรับผิดชอบ" เพื่อให้ actionable

## Step 914: Lead Time for Changes — วัดอย่างไรตั้งแต่ Commit แรกจนถึง Production

### 914.1 นิยามอย่างเป็นทางการ

**Lead Time for Changes** คือ **ระยะเวลาตั้งแต่โค้ดถูก commit จนถึงโค้ดนั้นทำงานสำเร็จบน production**

ข้อควรระวังสำคัญมาก: นี่**ไม่ใช่**เรื่องเดียวกับ "Lead Time" ในความหมายกว้างของวงการ Lean/Kanban ที่มักวัดตั้งแต่ "ตอนที่ลูกค้าขอฟีเจอร์" จนถึง "ตอนที่ได้ใช้งาน" (concept-to-cash) DORA นิยาม Lead Time for Changes ให้แคบและวัดได้จริงกว่านั้นมาก โดยเริ่มนับจาก**จุดที่มีโค้ดจริงในระบบ (code committed)** ไม่ใช่จุดที่เริ่มคิดไอเดีย

### 914.2 จุดเริ่มต้นและจุดสิ้นสุดที่ใช้วัดจริง

ในทางปฏิบัติ มี 2 แนวทางหลักที่ใช้กันในการกำหนด "จุดเริ่มต้น":

**แนวทางที่ 1: First commit ของ Pull Request/Merge Request**

```
first commit ใน branch feature/xyz    →  timestamp T1
                    │
                    ▼ (พัฒนาต่อ, เพิ่ม commit, ผ่าน code review)
                    │
merge เข้า main/trunk สำเร็จ            →  timestamp T2
                    │
                    ▼ (ผ่าน CI/CD pipeline)
                    │
deploy สำเร็จขึ้น production           →  timestamp T3

Lead Time for Changes = T3 - T1
```

**แนวทางที่ 2: เวลาที่ merge เข้า main (นิยมใช้มากกว่าในทางปฏิบัติ เพราะวัดง่ายกว่า)**

```
merge เข้า main สำเร็จ                 →  timestamp T2
                    │
                    ▼
deploy สำเร็จขึ้น production           →  timestamp T3

Lead Time for Changes (แบบง่าย) = T3 - T2
```

แนวทางที่ 2 มักถูกเรียกแยกว่า **"Lead Time for Changes (merge-based)"** ซึ่งวัดง่ายกว่าเพราะไม่ต้องตามหา first commit ของทุก branch แต่จะไม่รวมเวลาที่ใช้ในการพัฒนาและ review ก่อน merge เข้ามา ในขณะที่แนวทางที่ 1 ให้ภาพที่ครบถ้วนกว่าแต่คำนวณซับซ้อนกว่า **องค์กรควรเลือกแนวทางเดียวและใช้ให้สม่ำเสมอ** เพื่อให้เปรียบเทียบแนวโน้มข้ามช่วงเวลาได้อย่างมีความหมาย

### 914.3 วิธีดึงข้อมูลจริงด้วย Git

**หา first commit ของ Pull Request:**

```bash
# หา commit แรกใน branch feature ที่แยกออกจาก main
git log main..feature/xyz --reverse --pretty=format:"%H %ad" --date=iso | head -1
```

**หาเวลาที่ merge เข้า main:**

```bash
# ดู timestamp ของ merge commit บน main
git log main --merges --pretty=format:"%H %ad %s" --date=iso --grep="Merge pull request #1234"
```

**หาเวลาที่ deploy สำเร็จ:** ต้องดึงจาก CI/CD system (GitHub Actions run completion time, GitLab deployment `finished_at`) เพราะ Git เองไม่รู้เรื่องการ deploy — Git รู้แค่เรื่อง commit/branch/merge เท่านั้น

### 914.4 ตัวอย่างการคำนวณแบบสมบูรณ์

```
Pull Request #1234 "เพิ่มฟีเจอร์ export รายงาน PDF"

first commit ของ branch:     2026-03-10 09:15:00
merge เข้า main สำเร็จ:        2026-03-12 14:30:00
deploy สำเร็จขึ้น production:  2026-03-12 15:05:00

Lead Time (แบบเต็ม, commit แรก → deploy)
  = 2026-03-12 15:05:00 - 2026-03-10 09:15:00
  = 2 วัน 5 ชั่วโมง 50 นาที

Lead Time (merge-based, merge → deploy)
  = 2026-03-12 15:05:00 - 2026-03-12 14:30:00
  = 35 นาที
```

สังเกตว่าตัวเลขทั้งสองแบบต่างกันมาก — แบบเต็มสะท้อนเวลาทั้งหมดที่ใช้ในการพัฒนาและ review (2 วันกว่า) ในขณะที่แบบ merge-based สะท้อนแค่ความเร็วของ deployment pipeline หลัง merge เท่านั้น (35 นาที) ทั้งสองแบบมีประโยชน์คนละแบบ: แบบเต็มช่วยดูว่า**กระบวนการพัฒนาและ review**ช้าหรือเร็ว ส่วนแบบ merge-based ช่วยดูว่า**pipeline การ deploy เองนั้น**เร็วหรือช้า

### 914.5 การคำนวณในระดับองค์กร (ค่ามัธยฐาน ไม่ใช่ค่าเฉลี่ย)

ในทางปฏิบัติ ควรคำนวณ Lead Time ของ**หลาย ๆ** การเปลี่ยนแปลงในช่วงเวลาหนึ่ง แล้วใช้ **ค่ามัธยฐาน (median)** แทน **ค่าเฉลี่ย (mean)** เพราะข้อมูล lead time มักมีการกระจายแบบเบ้ขวา (right-skewed) — มี PR ส่วนน้อยที่ใช้เวลานานผิดปกติ (เช่น ค้างรอ review เป็นสัปดาห์) ซึ่งจะดึงค่าเฉลี่ยให้สูงเกินจริงและไม่สะท้อนประสบการณ์ทั่วไปของทีม ค่ามัธยฐานจึงเป็นตัวแทนที่ทนทาน (robust) ต่อ outlier มากกว่า และเป็นวิธีที่ DORA ใช้ในการรายงานผลด้วยเช่นกัน

## Step 915: Change Failure Rate และ MTTR (Mean Time To Recovery) วัดอย่างไร

### 915.1 Change Failure Rate — นิยามและวิธีวัด

**Change Failure Rate (CFR)** คือ **สัดส่วนของการ deploy ที่ทำให้เกิดความล้มเหลวใน production** ซึ่งต้องได้รับการแก้ไขเร่งด่วน เช่น hotfix, rollback, patch หรือ manual intervention

```
Change Failure Rate = จำนวน deployment ที่ทำให้เกิดความล้มเหลว
                       ------------------------------------------  × 100%
                       จำนวน deployment ทั้งหมดในช่วงเวลาเดียวกัน
```

**สิ่งที่นับว่าเป็น "ความล้มเหลว" (failure) ตามนิยามของ DORA:**

- ต้อง **rollback** deployment นั้นกลับไปเวอร์ชันก่อนหน้า
- ต้องออก **hotfix** เร่งด่วนตามมาเพื่อแก้ปัญหาที่ deployment นั้นก่อขึ้น
- เกิด **service outage หรือ service impairment** ที่ผู้ใช้สัมผัสได้ (เช่น ระบบล่ม, ฟีเจอร์สำคัญใช้งานไม่ได้, response time แย่ลงจนกระทบผู้ใช้)
- ต้องใช้ **manual remediation** อื่นใดเพื่อแก้ปัญหาที่เกิดจาก deployment นั้นโดยตรง

**สิ่งที่ไม่นับ:** บั๊กเล็กน้อยที่ไม่กระทบผู้ใช้และแก้ในรอบ deploy ปกติถัดไปโดยไม่ต้องเร่งด่วน ไม่ถือเป็น failure ตามนิยามนี้

### 915.2 วิธี track ข้อมูลจริงด้วย Git

การเชื่อมโยง deployment กับความล้มเหลวในทางปฏิบัติมักทำผ่านหนึ่งในวิธีต่อไปนี้:

**วิธีที่ 1: Revert commit**

```bash
# ค้นหา commit ที่เป็นการ revert
git log --grep="^Revert" --pretty=format:"%H %ad %s" --date=iso
```

เมื่อพบ commit ที่ขึ้นต้นด้วย `Revert "..."` (รูปแบบมาตรฐานที่ `git revert` สร้างให้อัตโนมัติ) สามารถย้อนกลับไปหาว่า commit ที่ถูก revert นั้นอยู่ใน deployment รอบไหน แล้วนับ deployment รอบนั้นเป็น 1 failure

**วิธีที่ 2: Naming convention สำหรับ hotfix**

หลายองค์กรกำหนดให้ branch หรือ tag ที่เป็น hotfix ต้องมี prefix ชัดเจน เช่น `hotfix/`, `v1.2.1-hotfix` เพื่อให้ query ได้ง่าย:

```bash
# หา tag ที่เป็น hotfix ทั้งหมด
git tag -l "*hotfix*" --sort=creatordate --format='%(creatordate:iso) %(refname:short)'
```

```
2026-03-12 15:05:00 v1.2.1
2026-03-12 19:40:00 v1.2.1-hotfix1   ← บ่งชี้ว่า v1.2.1 มีปัญหา ต้องออก hotfix ตามมา
2026-03-14 10:00:00 v1.2.2
```

**วิธีที่ 3: เชื่อมโยงกับระบบ Incident Management**

วิธีที่แม่นยำที่สุดคือเชื่อมโยงข้อมูล deployment เข้ากับระบบจัดการ incident (เช่น PagerDuty, Opsgenie, Jira Service Management) โดยกำหนดให้ทุก incident ที่เปิดขึ้นต้องระบุ **deployment ที่เป็นสาเหตุ (linked deployment)** วิธีนี้ให้ความแม่นยำสูงสุดแต่ต้องมีวินัยขององค์กรในการบันทึกข้อมูลอย่างสม่ำเสมอ

### 915.3 ตัวอย่างการคำนวณ CFR

```
เดือนมีนาคม 2026 ทีม A มี deployment ทั้งหมด 60 ครั้ง
ในจำนวนนี้มี 5 ครั้งที่ต้องตามด้วย hotfix หรือ rollback

Change Failure Rate = 5 / 60 × 100% ≈ 8.3%
```

### 915.4 MTTR (Mean Time To Recovery) — นิยามและวิธีวัด

**Time to Restore Service** หรือที่มักเรียกย่อว่า **MTTR (Mean Time To Recovery/Restore)** คือ **ระยะเวลาเฉลี่ยที่ใช้ในการกู้คืนบริการให้กลับมาทำงานปกติ นับตั้งแต่เกิดความล้มเหลวใน production**

```
MTTR = ผลรวมของ (เวลาที่กู้คืนสำเร็จ - เวลาที่ตรวจพบ/เกิด incident) ของทุก incident
       --------------------------------------------------------------------
                                จำนวน incident ทั้งหมด
```

### 915.5 วิธี track ข้อมูลจริงด้วย Git/CI

```
Incident เริ่ม (T_start):
  = เวลาที่ deployment ที่มีปัญหาถูก deploy สำเร็จ (ถ้าถือว่า incident เริ่มทันทีที่โค้ดพัง)
    หรือ
  = เวลาที่ระบบ monitoring/alert ตรวจพบความผิดปกติ (แม่นยำกว่า แต่ต้องมีระบบ monitoring แยก)

Incident จบ (T_end):
  = เวลาที่ deployment ของ hotfix/rollback สำเร็จ และระบบ monitoring ยืนยันว่ากลับมาปกติ
```

**ตัวอย่าง:**

```
15:05:00  deploy v1.2.1 สำเร็จ → เริ่มเกิดปัญหา (error rate พุ่งสูง)
15:12:00  ทีม on-call ได้รับ alert และเริ่มตรวจสอบ
15:38:00  พบสาเหตุ ตัดสินใจ rollback
15:44:00  rollback สำเร็จ (deploy v1.2.0 กลับมา) → error rate กลับสู่ปกติ

MTTR สำหรับ incident นี้ = 15:44:00 - 15:05:00 = 39 นาที
```

ถ้าใช้เวลาเริ่มนับจากตอนที่ alert แจ้ง (15:12:00) แทนตอน deploy จริง MTTR จะกลายเป็น 32 นาที — นี่คือเหตุผลที่องค์กรต้อง**กำหนดจุดเริ่มต้นที่ชัดเจนและใช้สม่ำเสมอ** เพื่อให้ตัวเลขเปรียบเทียบข้ามช่วงเวลาได้อย่างมีความหมาย โดยทั่วไป DORA แนะนำให้นับจากเวลาที่ **ตรวจพบ (detected)** มากกว่าเวลาที่เกิดขึ้นจริง เพราะสะท้อนประสบการณ์การตอบสนองของทีมได้ตรงกว่า

### 915.6 ทำไม CFR และ MTTR ต้องดูคู่กันเสมอ

CFR บอกว่า "พังบ่อยแค่ไหน" ส่วน MTTR บอกว่า "พังแล้วกลับมาเร็วแค่ไหน" ทั้งสองต้องดูคู่กันเสมอ เพราะทีมที่มี CFR ต่ำมากแต่ MTTR สูงมาก (พังไม่บ่อย แต่พังทีนานมาก) อาจมีความเสี่ยงต่อธุรกิจสูงกว่าทีมที่มี CFR สูงกว่าเล็กน้อยแต่ MTTR ต่ำมาก (พังบ่อยกว่านิดหน่อย แต่กู้คืนได้เร็วมาก) — นี่คือเหตุผลที่ DORA ออกแบบให้มี metric คุณภาพ 2 ตัวที่เสริมกัน ไม่ใช่ตัวเดียว

## Step 916: Elite/High/Medium/Low Performer Benchmark ตามงานวิจัย DORA

### 916.1 ที่มาของ Benchmark

ทีม DORA จัดกลุ่มองค์กรที่ทำการสำรวจออกเป็น 4 ระดับ (performance cluster) โดยใช้การวิเคราะห์เชิงสถิติจากข้อมูลแบบสำรวจจริง ไม่ใช่การกำหนดตัวเลขขึ้นมาลอย ๆ ตารางด้านล่างนี้คือ benchmark ที่มาจาก **State of DevOps Report ปี 2019** ซึ่งเป็นฉบับที่นิยามทั้ง 4 ระดับ (Elite, High, Medium, Low) ไว้อย่างชัดเจนเป็นครั้งแรก และเป็นตารางอ้างอิงที่ถูกนำไปใช้และอ้างอิงต่อกันมากที่สุดในวงการจนถึงปัจจุบัน (ตัวเลขในรายงานปีถัด ๆ มามีการปรับปรุงรายละเอียดบ้างเล็กน้อยตามข้อมูลที่เก็บได้ใหม่ในแต่ละปี แต่โครงสร้าง 4 ระดับและลำดับขนาดของตัวเลขยังคงสอดคล้องกัน):

| Metric | Elite | High | Medium | Low |
|---|---|---|---|---|
| **Deployment Frequency** | On-demand (deploy ได้หลายครั้งต่อวัน) | ระหว่าง 1 ครั้งต่อสัปดาห์ ถึง 1 ครั้งต่อเดือน | ระหว่าง 1 ครั้งต่อเดือน ถึง 1 ครั้งต่อ 6 เดือน | น้อยกว่า 1 ครั้งต่อ 6 เดือน |
| **Lead Time for Changes** | น้อยกว่า 1 ชั่วโมง | ระหว่าง 1 วัน ถึง 1 สัปดาห์ | ระหว่าง 1 เดือน ถึง 6 เดือน | มากกว่า 6 เดือน |
| **Change Failure Rate** | 0–15% | 0–15% | 0–15% | 46–60% |
| **Time to Restore Service** | น้อยกว่า 1 ชั่วโมง | น้อยกว่า 1 วัน | น้อยกว่า 1 วัน | มากกว่า 6 เดือน |

### 916.2 ข้อสังเกตสำคัญจากตาราง

**1. Change Failure Rate ของ Elite, High, Medium อยู่ในช่วงเดียวกัน (0–15%)**

จุดที่น่าสนใจมากคือ CFR ไม่ได้แยกความแตกต่างระหว่าง Elite, High และ Medium performer เลย — ทั้งสามกลุ่มมี CFR ใกล้เคียงกัน สิ่งที่แยกพวกเขาออกจากกันจริง ๆ คือ **ความเร็ว** (Deployment Frequency และ Lead Time) เป็นหลัก ในขณะที่กลุ่ม Low performer เท่านั้นที่มี CFR สูงกว่าอย่างมีนัยสำคัญ (46–60%) นี่ยืนยันข้อค้นพบใน Step 912 ว่าความเร็วกับคุณภาพไม่ใช่ trade-off — องค์กรสามารถเร็วขึ้นได้มากโดยไม่จำเป็นต้องแลกกับคุณภาพที่แย่ลง

**2. ช่องว่างระหว่าง Elite กับ Low ห่างกันมหาศาล**

Deployment Frequency ระหว่าง Elite (หลายครั้งต่อวัน) กับ Low (น้อยกว่า 1 ครั้งต่อ 6 เดือน) ต่างกันในระดับ**หลายร้อยถึงหลายพันเท่า** ไม่ใช่แค่ต่างกันเป็นเปอร์เซ็นต์เล็กน้อย นี่สะท้อนว่าองค์กรที่ยังใช้กระบวนการ release แบบดั้งเดิม (waterfall, big-bang release ปีละ 1–2 ครั้ง) กับองค์กรที่ทำ Continuous Delivery เต็มรูปแบบนั้นอยู่คนละโลกกันจริง ๆ ในเชิงประสิทธิภาพ

**3. Benchmark นี้ใช้เพื่อการเทียบเคียง ไม่ใช่เป้าหมายที่ต้องไล่ตามแบบสุดโต่ง**

องค์กรควรใช้ตารางนี้เพื่อ**เข้าใจตำแหน่งปัจจุบันของตัวเอง** และวางแผนปรับปรุงอย่างค่อยเป็นค่อยไป ไม่ใช่ตั้งเป้าให้ทุกทีมต้อง "เป็น Elite" ภายในไตรมาสเดียว เพราะบริบทของแต่ละองค์กร แต่ละ domain ธุรกิจ (เช่น software ทางการแพทย์ที่มี regulatory requirement เข้มงวด กับ mobile app ทั่วไป) มีข้อจำกัดที่แตกต่างกันมาก การไล่ตามตัวเลข Elite แบบไม่คำนึงถึงบริบทอาจนำไปสู่การลดคุณภาพ testing หรือข้าม compliance process ที่จำเป็นจริง ๆ

### 916.3 แนวโน้มจากรายงานปีหลัง ๆ

ในรายงาน State of DevOps ปีถัด ๆ มา (2021–2023) DORA พบว่าสัดส่วนองค์กรที่จัดอยู่ในกลุ่ม Elite performer **เพิ่มขึ้นอย่างต่อเนื่อง** เมื่อเทียบกับปีที่เริ่มทำการสำรวจ สะท้อนว่าอุตสาหกรรมโดยรวมกำลังพัฒนาขึ้นเรื่อย ๆ ในการนำแนวปฏิบัติของ Elite performer (เช่น trunk-based development, continuous integration ที่เข้มงวด, automated testing ที่ครอบคลุม, feature flag) ไปใช้อย่างแพร่หลายมากขึ้น อย่างไรก็ตาม แนวคิดหลัก 4 metric และการที่ Elite performer ทำได้ทั้งเร็วและมีคุณภาพสูงพร้อมกันยังคงเป็นข้อค้นพบหลักที่สอดคล้องกันในทุกปีที่มีการศึกษา

## Step 917: เครื่องมือวัด DORA Metrics ในทางปฏิบัติ

การคำนวณ DORA Metrics ด้วยมือแบบ Step 914–915 เหมาะสำหรับการเข้าใจหลักการ แต่ในทางปฏิบัติจริงที่มี deployment หลายสิบถึงหลายร้อยครั้งต่อวัน จำเป็นต้องใช้เครื่องมือที่ดึงข้อมูลและคำนวณให้อัตโนมัติ

### 917.1 เครื่องมือในตัว Git Hosting Platform

**GitHub Insights**

GitHub มีชุดฟีเจอร์ **Insights** ในระดับ repository (แท็บ Insights) ที่แสดงข้อมูลพื้นฐาน เช่น Pulse (สรุปกิจกรรมล่าสุด), Contributors (กราฟการ commit ของแต่ละคน), Code frequency (กราฟบรรทัดที่เพิ่ม/ลบต่อสัปดาห์), Traffic นอกจากนี้ GitHub Enterprise ยังมีฟีเจอร์ **Engineering metrics / DORA metrics dashboard** ในระดับ organization ที่ดึงข้อมูล deployment และ pull request มาคำนวณ Deployment Frequency, Lead Time for Changes, Change Failure Rate และ Time to Restore Service ให้โดยอัตโนมัติ โดยอ้างอิงจากข้อมูล deployment environment และ workflow run ที่ตั้งค่าไว้ใน GitHub Actions

**GitLab Value Stream Analytics**

GitLab มีฟีเจอร์ **Value Stream Analytics** (อยู่ในเมนู Analyze) ซึ่งในระดับ GitLab Ultimate มีหน้า **DORA metrics** โดยเฉพาะที่แสดงทั้ง 4 ตัวชี้วัดหลักเป็นกราฟแนวโน้มตามเวลา สามารถเปรียบเทียบข้าม project หรือ group ได้โดยตรงในตัวแพลตฟอร์ม โดยอาศัยข้อมูล deployment ที่บันทึกจาก GitLab CI/CD environment และข้อมูล incident ที่เชื่อมโยงกับ GitLab's Incident Management feature สำหรับคำนวณ Change Failure Rate และ MTTR

### 917.2 เครื่องมือ Third-party เฉพาะทาง

เมื่อองค์กรต้องการความสามารถขั้นสูงกว่าที่ platform หลักให้มา (เช่น รวมข้อมูลจากหลาย repository/หลาย platform เข้าด้วยกัน, แบ่งกลุ่มตามทีม, เชื่อมกับระบบ incident management ภายนอก) มักหันไปใช้เครื่องมือเฉพาะทาง:

- **LinearB** — แพลตฟอร์ม engineering analytics ที่เน้น DORA metrics และ cycle time breakdown อย่างละเอียด (แยกเวลาออกเป็น coding time, pickup time, review time, deploy time) พร้อมฟีเจอร์ automation เช่น gitStream สำหรับกำหนดกฎ workflow อัตโนมัติ
- **Sleuth** — เครื่องมือที่ออกแบบมาเพื่อ track deployment และคำนวณ DORA metrics โดยตรง เน้นการมองเห็น deployment timeline และเชื่อมโยงกับ incident ได้ง่าย
- **Faros AI** — แพลตฟอร์มที่รวบรวมข้อมูลจากหลายแหล่ง (Git, CI/CD, project management, incident management) เข้าด้วยกันเพื่อคำนวณ engineering metrics ครบวงจร รวมถึง DORA metrics
- **Jellyfish** และ **Swarmia** — เครื่องมือ engineering management platform ที่นอกจาก DORA metrics แล้วยังเชื่อมโยงกับข้อมูลการลงทุนทางวิศวกรรม (engineering investment) เพื่อช่วยผู้บริหารตัดสินใจเชิงกลยุทธ์

### 917.3 การสร้างเครื่องมือวัดเอง (Build vs. Buy)

องค์กรที่มีทรัพยากรด้าน data engineering เพียงพอ อาจเลือกสร้างระบบวัด DORA metrics เองโดยดึงข้อมูลผ่าน API ของ Git hosting platform (GitHub/GitLab REST หรือ GraphQL API) และ CI/CD system เก็บลง data warehouse แล้วสร้าง dashboard เอง (เช่นด้วย Metabase, Looker, Grafana) ข้อดีคือปรับแต่งได้ตรงกับบริบทองค์กรมากที่สุดและควบคุมข้อมูลได้เต็มที่ ข้อเสียคือต้องดูแลรักษาระบบต่อเนื่องและใช้เวลาพัฒนานานกว่าการซื้อเครื่องมือสำเร็จรูป องค์กรขนาดกลางถึงเล็กส่วนใหญ่มักคุ้มค่ากว่าถ้าเริ่มจากฟีเจอร์ในตัว platform (GitHub/GitLab) ก่อน แล้วค่อยพิจารณา third-party หรือ build เองเมื่อความต้องการซับซ้อนขึ้นจริง ๆ

## Step 918: PR Metrics เพิ่มเติมที่มีประโยชน์

นอกจาก DORA Metrics ทั้ง 4 ตัวแล้ว ยังมี metric ระดับ Pull Request ที่มีประโยชน์มากในการเข้าใจ**กระบวนการทำงานภายในของทีม**ในรายละเอียดที่ลึกกว่า DORA Metrics ให้ได้

### 918.1 Time to First Review

**นิยาม:** ระยะเวลาตั้งแต่ Pull Request ถูกเปิด (opened) จนถึงมีคน review ครั้งแรก (comment, approve หรือ request changes อย่างใดอย่างหนึ่ง)

```bash
# ตัวอย่างแนวคิดการดึงข้อมูลผ่าน GitHub API (pseudocode)
PR opened at:        2026-03-10 09:00:00
first review event:  2026-03-10 15:30:00

Time to First Review = 6 ชั่วโมง 30 นาที
```

Time to First Review ที่นานเกินไปเป็นสัญญาณเตือนสำคัญของปัญหาคอขวดในกระบวนการ review — ถ้าค่านี้สูงต่อเนื่อง มักหมายความว่าทีมมี reviewer ไม่เพียงพอ หรือ PR ถูกเปิดทิ้งไว้โดยไม่มีใครรับผิดชอบชัดเจนว่าต้อง review ใคร (ปัญหาที่ CODEOWNERS และ review rotation ช่วยแก้ได้ ตามที่กล่าวถึงใน Part 83) งานวิจัยหลายชิ้นในวงการ (รวมถึงข้อมูลจาก LinearB และ GitClear) ชี้ตรงกันว่า **Time to First Review เป็นหนึ่งในปัจจัยที่ส่งผลต่อ Lead Time for Changes มากที่สุด** เพราะ PR ส่วนใหญ่มักใช้เวลารอ review นานกว่าเวลาที่ใช้ในการเขียนโค้ดจริง

### 918.2 PR Size เฉลี่ย

**นิยาม:** จำนวนบรรทัดที่เปลี่ยนแปลง (เพิ่ม + ลบ) โดยเฉลี่ยต่อ Pull Request หนึ่งใบ

```bash
# ตัวอย่างคำสั่งดู diff size ของ PR ที่ merge แล้ว
git diff --shortstat main~1 main
# 3 files changed, 45 insertions(+), 12 deletions(-)
```

**ความสัมพันธ์ระหว่าง PR Size กับคุณภาพและความเร็ว** เป็นที่ยอมรับกันอย่างกว้างขวางในวงการ software engineering:

- **PR ขนาดเล็กได้รับการ review เร็วกว่าและละเอียดกว่า** — reviewer มีแนวโน้มอ่านโค้ด 50 บรรทัดอย่างละเอียด แต่มักอ่านโค้ด 1,000 บรรทัดแบบผ่าน ๆ เพราะภาระทางความคิด (cognitive load) สูงเกินไป
- **PR ขนาดเล็กมีโอกาสพบบั๊กจาก review มากกว่า** — การศึกษาการทำ code review ของ Cisco/SmartBear (จากหนังสือ "Best Kept Secrets of Peer Code Review") พบว่าอัตราการพบข้อบกพร่องต่อบรรทัด (defect density) ลดลงอย่างมากเมื่อขนาดของสิ่งที่ต้อง review เกินประมาณ 200–400 บรรทัดในครั้งเดียว
- **PR ขนาดเล็กมี Change Failure Rate ต่ำกว่า** เพราะความเสี่ยงต่อการเปลี่ยนแปลงหนึ่งครั้งน้อยกว่า และง่ายต่อการ rollback หรือระบุสาเหตุเมื่อเกิดปัญหา

ทีมที่ track PR Size เฉลี่ยและพยายามลดขนาดลงอย่างต่อเนื่อง (เช่น สนับสนุนให้ split งานใหญ่เป็น PR ย่อยหลายใบที่ merge ได้อิสระต่อกัน) มักเห็นทั้ง Lead Time และ Change Failure Rate ดีขึ้นพร้อมกัน

### 918.3 Merge Frequency

**นิยาม:** จำนวนครั้งที่ Pull Request ถูก merge เข้า branch หลักในช่วงเวลาหนึ่ง เป็นตัวชี้วัด throughput ระดับ PR ที่หยาบกว่า Deployment Frequency แต่วัดง่ายกว่าและเป็นสัญญาณเตือนล่วงหน้าที่ดี — ถ้า Merge Frequency ลดลงต่อเนื่องแต่จำนวนวิศวกรในทีมเท่าเดิม อาจบ่งชี้ปัญหาบางอย่าง เช่น PR ค้างนานขึ้น, งานถูกบล็อกด้วย dependency ระหว่างทีม, หรือ scope ของแต่ละ PR ใหญ่ขึ้นเรื่อย ๆ

### 918.4 Cycle Time Breakdown

แนวคิดที่มีประโยชน์มากคือการแยก **Cycle Time** ของ Pull Request ออกเป็นช่วงย่อย ๆ เพื่อระบุว่าคอขวดที่แท้จริงอยู่ตรงไหน (แนวคิดนี้เป็นที่นิยมในเครื่องมืออย่าง LinearB):

```
[Coding Time]     [Pickup Time]      [Review Time]      [Deploy Time]
first commit  →   PR opened     →   first review   →   approved      →  deployed
                                                          & merged

Coding Time  = เวลาตั้งแต่ commit แรกจนถึง PR ถูกเปิด
Pickup Time  = เวลาตั้งแต่ PR เปิดจนถึงมี reviewer เข้ามาดูครั้งแรก
Review Time  = เวลาตั้งแต่ review ครั้งแรกจนถึง approve และ merge สำเร็จ
Deploy Time  = เวลาตั้งแต่ merge จนถึง deploy ขึ้น production สำเร็จ
```

การแยกแบบนี้ช่วยให้ทีมรู้ว่าควรแก้ปัญหาตรงไหนก่อน — ถ้า Pickup Time สูงผิดปกติ ปัญหาอยู่ที่การจัดสรร reviewer ถ้า Review Time สูง ปัญหาอาจอยู่ที่ PR มีขนาดใหญ่เกินไปหรือมีการถกเถียงเรื่อง design มาก ถ้า Deploy Time สูง ปัญหาอาจอยู่ที่ CI/CD pipeline เองที่ช้าหรือไม่เสถียร — การแก้ปัญหาที่ถูกจุดย่อมมีประสิทธิภาพกว่าการพยายามแก้ "Lead Time โดยรวม" อย่างเลื่อนลอย

## Step 919: ข้อควรระวังสำคัญ — Goodhart's Law และการไม่ใช้ Metrics ตัดสินคนเป็นรายบุคคล

### 919.1 Goodhart's Law คืออะไร

**Goodhart's Law** ตั้งชื่อตาม **Charles Goodhart** นักเศรษฐศาสตร์ชาวอังกฤษ ผู้เสนอแนวคิดนี้ครั้งแรกในปี 1975 ในบริบทของนโยบายการเงิน โดยมีใจความดั้งเดิมประมาณว่า "ความสม่ำเสมอทางสถิติใด ๆ ที่สังเกตพบ มีแนวโน้มจะพังทลายลงทันทีที่มีการกดดันให้ใช้มันเพื่อการควบคุม"

ในภายหลัง นักมานุษยวิทยา **Marilyn Strathern** ได้สรุปแนวคิดนี้ให้กระชับและเป็นที่จดจำง่ายในปี 1997 จนกลายเป็นประโยคที่ถูกอ้างอิงกันทั่วไปในวงการต่าง ๆ รวมถึงวงการวิศวกรรมซอฟต์แวร์:

> **"When a measure becomes a target, it ceases to be a good measure"**
> **(เมื่อ metric กลายเป็นเป้าหมาย มันจะหยุดเป็น metric ที่ดี)**

### 919.2 กลไกของ Goodhart's Law ในบริบท Engineering Metrics

เมื่อองค์กรประกาศว่าจะใช้ metric ใด metric หนึ่งวัดผลงาน**รายบุคคล**อย่างเป็นทางการ (เช่น ผูกกับโบนัส การเลื่อนตำแหน่ง หรือการประเมินผลประจำปี) พฤติกรรมของคนจะเปลี่ยนไปเพื่อ **optimize ตัวเลขนั้นโดยตรง** แทนที่จะ optimize เป้าหมายที่แท้จริงที่ metric นั้นตั้งใจจะสะท้อน ตัวอย่างที่เกิดขึ้นจริงในวงการเมื่อนำ Engineering Metrics ไปใช้ผิดวิธี:

**ถ้าวัด Deployment Frequency รายบุคคล:**
- วิศวกรอาจแตก PR ที่ควรเป็นก้อนเดียวออกเป็นหลาย deployment เล็ก ๆ โดยไม่มีเหตุผลทางเทคนิครองรับ เพียงเพื่อดันตัวเลข
- อาจหลีกเลี่ยงงานที่จำเป็นต้องใช้เวลาสะสมนาน (เช่น migration ฐานข้อมูลขนาดใหญ่) เพราะทำให้ deployment ถี่ ๆ ทำไม่ได้ในช่วงนั้น

**ถ้าวัด Lead Time รายบุคคล:**
- วิศวกรอาจข้าม code review ที่ควรทำอย่างละเอียด หรือกดดัน reviewer ให้ approve เร็วเกินจำเป็นเพื่อลดตัวเลข lead time ของตัวเอง
- อาจเลือกทำงานเล็ก ๆ ง่าย ๆ ที่ปิดเร็วแทนงานที่ซับซ้อนแต่มีคุณค่าทางธุรกิจสูงกว่า

**ถ้าวัด Change Failure Rate รายบุคคล:**
- วิศวกรอาจ**ไม่กล้ารายงาน incident** ที่ตัวเองเป็นสาเหตุ หรือพยายามปกปิด/บิดเบือนสาเหตุที่แท้จริงเพื่อไม่ให้ถูกนับเป็น "ความล้มเหลว" ของตัวเอง ซึ่งเป็นผลลัพธ์ที่**อันตรายกว่าปัญหาเดิมมาก** เพราะองค์กรจะสูญเสียความสามารถในการเรียนรู้จากความผิดพลาด (post-incident learning)
- วิศวกรอาจหลีกเลี่ยงงานที่มีความเสี่ยงสูงแต่จำเป็น (เช่น การ migrate ระบบเก่าที่ซับซ้อน) เพราะกลัวว่าจะทำให้ CFR ส่วนตัวแย่ลง ทั้งที่งานนั้นจำเป็นต่อองค์กรในระยะยาว

### 919.3 หลักการที่ถูกต้อง: วัดระดับทีม/ระบบ ไม่ใช่ระดับบุคคล

ทีม DORA เองระบุอย่างชัดเจนในงานวิจัยและหนังสือ "Accelerate" ว่า **DORA Metrics ถูกออกแบบมาเพื่อวัดประสิทธิภาพของระบบการส่งมอบซอฟต์แวร์ในระดับทีมหรือองค์กร ไม่ใช่เพื่อจัดอันดับหรือประเมินผลงานวิศวกรเป็นรายบุคคล** การนำ metric เหล่านี้ไปใช้ผิดวัตถุประสงค์ (เช่น สร้าง leaderboard เปรียบเทียบวิศวกรแต่ละคนด้วย Deployment Frequency ส่วนตัว) ขัดกับเจตนารมณ์ดั้งเดิมของงานวิจัยโดยตรง และมีแนวโน้มสูงที่จะสร้างผลเสียมากกว่าผลดีตามกลไกของ Goodhart's Law ที่อธิบายไว้ข้างต้น

**แนวทางที่ถูกต้องในการใช้ DORA Metrics:**

1. **วัดที่ระดับทีม (team) หรือระบบ (system) เท่านั้น** — ไม่แยกเป็นรายบุคคลเด็ดขาด
2. **ใช้เพื่อเปิดบทสนทนาเรื่องการปรับปรุงกระบวนการ** ไม่ใช่เพื่อตัดสินคน — เมื่อพบว่า Lead Time สูงขึ้น คำถามที่ควรถามคือ "กระบวนการตรงไหนที่ทำให้ช้าลง" ไม่ใช่ "ใครเป็นคนทำให้ช้า"
3. **ใช้แนวโน้ม (trend) ของทีมตัวเองเทียบกับอดีตของตัวเอง** มากกว่าการเปรียบเทียบข้ามทีมแบบตรง ๆ เพราะแต่ละทีมมีบริบทต่างกัน (ทีมที่ดูแลระบบ legacy ที่มี regulatory constraint ย่อมมี metric ที่ต่างจากทีมที่สร้าง greenfield project)
4. **ไม่ผูก metric เหล่านี้กับโบนัสหรือการประเมินผลรายบุคคลโดยตรง** — ควรเป็นเครื่องมือสำหรับทีมและผู้จัดการใช้ร่วมกันเพื่อหาจุดปรับปรุง ไม่ใช่เครื่องมือลงโทษ
5. **ให้ความสำคัญกับ Westrum Organizational Culture** — งานวิจัยของ DORA เองยังพบว่าวัฒนธรรมองค์กรแบบ **Generative** (ตามกรอบคิดของ Ron Westrum ที่เน้นความไว้วางใจ การแบ่งปันข้อมูลอย่างเปิดเผย และมองความล้มเหลวเป็นโอกาสเรียนรู้ ไม่ใช่โอกาสลงโทษ) มีความสัมพันธ์เชิงบวกอย่างมีนัยสำคัญกับ Software Delivery Performance — องค์กรที่ใช้ metrics เพื่อสร้างบรรยากาศแบบกลัวถูกจับผิด (Pathological culture ตามกรอบคิดเดียวกัน) มักเห็นผลลัพธ์แย่ลงในระยะยาว แม้ตัวเลขระยะสั้นอาจดูดีขึ้นจากการ "เล่นกับตัวเลข"

### 919.4 สรุปสั้น ๆ ที่ควรจำ

> **Metric ที่ดีที่สุดในโลก จะกลายเป็น metric ที่แย่ที่สุด ทันทีที่มันถูกใช้เป็นเป้าหมายที่ผูกกับผลตอบแทนหรือการลงโทษของปัจเจกบุคคล**

จำหลักการนี้ไว้เสมอทุกครั้งที่นำ Engineering Metrics ไปใช้ในองค์กรจริง ไม่ว่าจะเป็น DORA Metrics หรือ metric อื่นใดก็ตาม

## Step 920: แบบฝึกหัด — คำนวณ DORA Metrics เบื้องต้นด้วยมือจาก `git log`

### 920.1 เป้าหมายของแบบฝึกหัด

แบบฝึกหัดนี้ให้คุณฝึกดึงข้อมูลจาก `git log` และ `git tag` ของโปรเจกต์จำลอง แล้วคำนวณ Deployment Frequency, Lead Time for Changes และ Change Failure Rate ด้วยมือ เพื่อให้เข้าใจกลไกเบื้องหลังก่อนที่จะไปพึ่งพาเครื่องมืออัตโนมัติในงานจริง

### 920.2 เตรียมโปรเจกต์จำลอง

```bash
mkdir ~/git-course/part-92-dora-practice
cd ~/git-course/part-92-dora-practice
git init
git config user.email "you@example.com"
git config user.name "Your Name"
```

สร้าง commit และ tag จำลองให้มี timestamp ตามที่กำหนด (ใช้ `GIT_AUTHOR_DATE` และ `GIT_COMMITTER_DATE` เพื่อกำหนดเวลาย้อนหลังสำหรับฝึกฝน):

```bash
echo "v1" > app.txt
GIT_AUTHOR_DATE="2026-03-01T09:00:00" GIT_COMMITTER_DATE="2026-03-01T09:00:00" \
  git commit -am "feat: เพิ่มฟีเจอร์ login"

GIT_AUTHOR_DATE="2026-03-01T18:00:00" GIT_COMMITTER_DATE="2026-03-01T18:00:00" \
  git tag -a v1.0.0 -m "release v1.0.0"

echo "v2" >> app.txt
GIT_AUTHOR_DATE="2026-03-03T10:00:00" GIT_COMMITTER_DATE="2026-03-03T10:00:00" \
  git commit -am "feat: เพิ่มฟีเจอร์ export PDF"

GIT_AUTHOR_DATE="2026-03-05T14:00:00" GIT_COMMITTER_DATE="2026-03-05T14:00:00" \
  git commit -am "fix: แก้บั๊กหน้า export PDF ก่อน merge"

GIT_AUTHOR_DATE="2026-03-05T16:30:00" GIT_COMMITTER_DATE="2026-03-05T16:30:00" \
  git tag -a v1.1.0 -m "release v1.1.0"

echo "hotfix" >> app.txt
GIT_AUTHOR_DATE="2026-03-05T20:15:00" GIT_COMMITTER_DATE="2026-03-05T20:15:00" \
  git commit -am "fix: v1.1.0 ทำให้ export PDF ล่ม ต้อง hotfix ด่วน"

GIT_AUTHOR_DATE="2026-03-05T20:45:00" GIT_COMMITTER_DATE="2026-03-05T20:45:00" \
  git tag -a v1.1.1-hotfix -m "hotfix สำหรับ v1.1.0"

echo "v3" >> app.txt
GIT_AUTHOR_DATE="2026-03-10T11:00:00" GIT_COMMITTER_DATE="2026-03-10T11:00:00" \
  git commit -am "feat: เพิ่มฟีเจอร์ dashboard สรุปยอดขาย"

GIT_AUTHOR_DATE="2026-03-14T09:20:00" GIT_COMMITTER_DATE="2026-03-14T09:20:00" \
  git tag -a v1.2.0 -m "release v1.2.0"
```

### 920.3 ขั้นที่ 1: ดึงรายการ Tag เรียงตามเวลา (สมมติว่า 1 tag = 1 deployment ขึ้น production)

```bash
git tag -l --sort=creatordate --format='%(creatordate:iso) %(refname:short) %(contents:subject)'
```

**ผลลัพธ์ที่ควรได้:**

```
2026-03-01 18:00:00 +0000  v1.0.0        release v1.0.0
2026-03-05 16:30:00 +0000  v1.1.0        release v1.1.0
2026-03-05 20:45:00 +0000  v1.1.1-hotfix hotfix สำหรับ v1.1.0
2026-03-14 09:20:00 +0000  v1.2.0        release v1.2.0
```

### 920.4 ขั้นที่ 2: คำนวณ Deployment Frequency

```
ช่วงเวลาที่วัด: 2026-03-01 ถึง 2026-03-14  =  13 วัน
จำนวน deployment (นับทุก tag รวม hotfix) = 4 ครั้ง

Deployment Frequency = 4 / 13 วัน ≈ 0.31 ครั้งต่อวัน
                      ≈ 1 ครั้งทุก ๆ 3.25 วัน
```

เทียบกับตาราง benchmark ใน Step 916 ตัวเลขนี้ (ประมาณ 1 ครั้งทุก 3 วัน) อยู่ระหว่างช่วง "High" (1 ครั้งต่อสัปดาห์ ถึง 1 ครั้งต่อเดือน) กับ "Elite" (on-demand หลายครั้งต่อวัน) — ค่อนไปทาง High performer

### 920.5 ขั้นที่ 3: คำนวณ Lead Time for Changes ของแต่ละ Release

ใช้วิธี merge-based (คำนวณจาก commit สุดท้ายที่รวมอยู่ใน release จนถึงเวลาที่ tag release ถูกสร้าง) และดูรายละเอียด commit ในแต่ละช่วงด้วย:

```bash
# ดู commit ทั้งหมดระหว่าง v1.0.0 กับ v1.1.0 พร้อมเวลา
git log v1.0.0..v1.1.0 --pretty=format:"%ad %h %s" --date=iso
```

**ผลลัพธ์:**

```
2026-03-05 14:00:00 +0000  <hash2>  fix: แก้บั๊กหน้า export PDF ก่อน merge
2026-03-03 10:00:00 +0000  <hash1>  feat: เพิ่มฟีเจอร์ export PDF
```

**คำนวณ Lead Time ของ release v1.1.0 (แบบเต็ม: first commit → tag time):**

```
first commit ของงานชุดนี้:  2026-03-03 10:00:00
tag v1.1.0 ถูกสร้าง:         2026-03-05 16:30:00

Lead Time = 2026-03-05 16:30:00 - 2026-03-03 10:00:00
          = 2 วัน 6 ชั่วโมง 30 นาที
```

**คำนวณ Lead Time ของ release v1.2.0:**

```bash
git log v1.1.1-hotfix..v1.2.0 --pretty=format:"%ad %h %s" --date=iso
```

```
2026-03-10 11:00:00 +0000  <hash4>  feat: เพิ่มฟีเจอร์ dashboard สรุปยอดขาย
```

```
first commit:        2026-03-10 11:00:00
tag v1.2.0 ถูกสร้าง:  2026-03-14 09:20:00

Lead Time = 2026-03-14 09:20:00 - 2026-03-10 11:00:00
          = 3 วัน 22 ชั่วโมง 20 นาที
```

**สรุป Lead Time ของทั้ง 2 release ที่คำนวณได้:**

```
v1.1.0: 2 วัน 6 ชั่วโมง 30 นาที  (=  ~54.5 ชั่วโมง)
v1.2.0: 3 วัน 22 ชั่วโมง 20 นาที (=  ~94.3 ชั่วโมง)

ค่ามัธยฐาน (median) ของ 2 ค่านี้ = (54.5 + 94.3) / 2 ≈ 74.4 ชั่วโมง (~3.1 วัน)
```

ตัวเลขนี้ (ประมาณ 3 วัน) อยู่ในช่วง "High performer" ตามตาราง Step 916 (ระหว่าง 1 วัน ถึง 1 สัปดาห์)

### 920.6 ขั้นที่ 4: คำนวณ Change Failure Rate

จากข้อมูลที่มี พบว่า release `v1.1.0` มีปัญหาและต้องตามด้วย `v1.1.1-hotfix` ทันที (ห่างกันแค่ 4 ชั่วโมง 15 นาที) ส่วน `v1.0.0` และ `v1.2.0` ไม่มี hotfix ตามมา จึงถือว่าไม่มีปัญหา

```
จำนวน deployment ที่ "นับเป็น release" ทั้งหมด (ไม่นับ hotfix ซ้ำเป็น deployment แยก
เพื่อไม่ให้ซ้ำซ้อนกับ deployment ที่มันแก้)  = 3 ครั้ง (v1.0.0, v1.1.0, v1.2.0)
จำนวน release ที่ทำให้เกิดปัญหาต้อง hotfix   = 1 ครั้ง (v1.1.0)

Change Failure Rate = 1 / 3 × 100% ≈ 33.3%
```

ตัวเลขนี้ (33.3%) สูงกว่าช่วง Elite/High/Medium (0–15%) มาก แม้จะยังไม่ถึงระดับ Low (46–60%) — นี่คือสัญญาณเตือนที่ชัดเจนว่าทีมสมมตินี้ควรตรวจสอบกระบวนการ testing ก่อน release ให้ละเอียดขึ้น เพราะแม้ Lead Time และ Deployment Frequency จะอยู่ในระดับ High performer แต่คุณภาพของการ release ยังมีความเสี่ยงสูงเกินกว่าที่ควรจะเป็น

### 920.7 คำถามท้ายแบบฝึกหัด (ลองตอบเองก่อนดูแนวคำตอบ)

1. ถ้าทีมนี้ลดขนาดของแต่ละ release ให้เล็กลง (deploy บ่อยขึ้นแต่ทีละน้อย) คุณคาดว่า Change Failure Rate จะเปลี่ยนแปลงอย่างไร และเพราะเหตุใด
2. ถ้าคุณเป็นหัวหน้าทีมและเห็นตัวเลขนี้ คุณจะเริ่มการสนทนากับทีมด้วยประโยคแบบไหน ระหว่าง *"ใครทำให้ v1.1.0 พัง"* กับ *"กระบวนการตรวจสอบก่อน release ของเรามีช่องโหว่ตรงไหนบ้าง"* — ทำไมประโยคหนึ่งถึงสอดคล้องกับหลักการใน Step 919 มากกว่าอีกประโยคหนึ่ง
3. ลองเขียนคำสั่ง `git log` และ `git tag` แบบข้างต้นกับ repository จริงของคุณเอง (หรือ open-source repository ใดก็ได้ที่มีการ tag release สม่ำเสมอ) แล้วลองคำนวณ Deployment Frequency ย้อนหลัง 3 เดือนด้วยมือ

ก่อนไปต่อ Part 93 ให้ตรวจสอบว่าคุณ:

- [ ] อธิบายได้ว่าทำไม LOC และจำนวน commit ถึงเป็น metric ที่วัดผิด
- [ ] บอกชื่อและนิยามของ DORA Metrics ทั้ง 4 ตัวได้โดยไม่ต้องเปิดเอกสาร
- [ ] อธิบายวิธีคำนวณ Deployment Frequency, Lead Time for Changes, Change Failure Rate และ MTTR จากข้อมูล Git/CI ได้
- [ ] จำตาราง Benchmark Elite/High/Medium/Low ได้อย่างน้อยในเชิงลำดับ (ไม่ต้องจำตัวเลขแม่นทุกตัว)
- [ ] รู้จักเครื่องมืออย่างน้อย 3 ตัวที่ใช้วัด DORA metrics ในทางปฏิบัติ
- [ ] เข้าใจ PR metrics เสริม (Time to First Review, PR Size, Merge Frequency, Cycle Time Breakdown) และประโยชน์ของแต่ละตัว
- [ ] อธิบาย Goodhart's Law ได้ และบอกได้ว่าทำไมห้ามใช้ metrics ตัดสินคนเป็นรายบุคคล
- [ ] คำนวณ DORA metrics เบื้องต้นด้วยมือจากข้อมูล `git log`/`git tag` ได้จริงตามแบบฝึกหัด

## สรุป Part 92

ใน Part นี้เราได้เรียนรู้ว่า:

1. การวัดผลทีมพัฒนาซอฟต์แวร์ด้วยความรู้สึกหรือ metric ที่วัดผิด เช่น จำนวนบรรทัดโค้ด สร้างอคติและแรงจูงใจที่ผิดเพี้ยน ต้องใช้ข้อมูลเชิงประจักษ์จากระบบส่งมอบซอฟต์แวร์แทน
2. **DORA Metrics** ทั้ง 4 ตัว — Deployment Frequency, Lead Time for Changes, Change Failure Rate, Time to Restore Service (MTTR) — มาจากงานวิจัยหลายปีของทีม DevOps Research and Assessment นำโดย Nicole Forsgren, Jez Humble และ Gene Kim ผ่านหนังสือ "Accelerate" และ State of DevOps Report
3. Deployment Frequency วัดจากจำนวน deploy job ที่สำเร็จไปยัง production environment ผ่านข้อมูล CI/CD ไม่ใช่แค่การ merge เข้า main
4. Lead Time for Changes วัดตั้งแต่ commit แรก (หรือเวลา merge) จนถึง deploy สำเร็จ ควรใช้ค่ามัธยฐานแทนค่าเฉลี่ยเพื่อลดผลกระทบจาก outlier
5. Change Failure Rate และ MTTR วัดคุณภาพและความเสถียรของการเปลี่ยนแปลง โดยเชื่อมโยงกับ revert commit, hotfix tag หรือระบบ incident management
6. งานวิจัยพบว่าองค์กรระดับ Elite performer ทำได้ทั้งเร็วและมีคุณภาพสูงพร้อมกัน ความเร็วกับความเสถียรไม่ใช่ trade-off ที่ต้องเลือกอย่างใดอย่างหนึ่งเสมอไป
7. มีทั้งเครื่องมือในตัว platform (GitHub Insights, GitLab Value Stream Analytics) และเครื่องมือ third-party (LinearB, Sleuth, Faros AI, Jellyfish, Swarmia) สำหรับวัด DORA metrics ในทางปฏิบัติ
8. PR metrics เสริม เช่น Time to First Review, PR Size, Merge Frequency และ Cycle Time Breakdown ช่วยระบุคอขวดของกระบวนการได้ละเอียดกว่า DORA metrics เพียงอย่างเดียว
9. **Goodhart's Law** เตือนว่าเมื่อ metric กลายเป็นเป้าหมายที่ผูกกับผลตอบแทนรายบุคคล มันจะหยุดเป็น metric ที่ดี — ต้องใช้ metrics ระดับทีม/ระบบเพื่อปรับปรุงกระบวนการ ไม่ใช่เพื่อตัดสินหรือลงโทษบุคคล
10. ฝึกคำนวณ DORA metrics ด้วยมือจากข้อมูล `git log`/`git tag` จริง ทำให้เข้าใจกลไกเบื้องหลังก่อนพึ่งพาเครื่องมืออัตโนมัติในงานจริง
