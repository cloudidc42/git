## Step 981: บทบาท Tech Lead ต่างจาก Senior Engineer ทั่วไปอย่างไร

ตลอด 98 Part ที่ผ่านมา หลักสูตรนี้สอนให้คุณเป็น **ผู้ใช้ Git ระดับผู้เชี่ยวชาญ** — เข้าใจ internals, แก้ปัญหาซับซ้อน, ออกแบบ workflow, วาง security policy ระดับองค์กร แต่ทักษะเหล่านี้ทั้งหมด ไม่ว่าจะเก่งแค่ไหน ก็ยังเป็นเพียง **"ทักษะเชิงเทคนิค (technical skill)"** เท่านั้น

Part นี้จะเปลี่ยนมุมมองอย่างสิ้นเชิง จากคำถามที่ว่า **"จะทำสิ่งนี้อย่างไร (How)"** ไปสู่คำถามที่ว่า **"ควรทำสิ่งนี้หรือไม่ ทำไม และใครจะได้รับผลกระทบ (Should we, Why, and Who is affected)"** — นี่คือขอบเขตความรับผิดชอบของ **Tech Lead**

### 981.1 นิยามของ Tech Lead ที่ชัดเจน

**Tech Lead** ไม่ใช่ตำแหน่งที่นิยามด้วย seniority อย่างเดียว แต่นิยามด้วย **ขอบเขตของผลกระทบจากการตัดสินใจ (scope of decision impact)** Senior Engineer ที่เก่งมากอาจไม่เคยเป็น Tech Lead เลยก็ได้ ถ้าเขาเลือกเส้นทางสายเทคนิคเชิงลึก (Individual Contributor / Staff Engineer track) แทนที่จะรับผิดชอบการตัดสินใจระดับทีม

Will Larson ผู้เขียนหนังสือ *Staff Engineer* แบ่งบทบาทระดับสูงของสายเทคนิคออกเป็นหลายรูปแบบ (archetype) เช่น Tech Lead, Architect, Solver, Right Hand — แต่ทั้งหมดมีจุดร่วมเดียวกันคือ **ผลกระทบของงานขยายออกไปไกลกว่าโค้ดที่ตัวเองเขียน**

### 981.2 ตารางเปรียบเทียบ Senior Engineer กับ Tech Lead

| มิติ | Senior Engineer | Tech Lead |
|---|---|---|
| **ขอบเขตความรับผิดชอบ** | Feature/Module ที่ตัวเองดูแล | ทั้งทีม หรือหลายทีมที่เกี่ยวข้อง |
| **หน่วยเวลาที่คิดถึง** | Sprint ปัจจุบัน (1–2 สัปดาห์) | Quarter ถึง Year (3 เดือน–1 ปี) |
| **ประเภทการตัดสินใจ** | "จะ implement อย่างไร" | "จะเลือกแนวทางไหน และทำไม" |
| **ตัวชี้วัดความสำเร็จ** | คุณภาพโค้ดของตัวเอง, ความเร็วในการส่งงาน | ความสำเร็จของทีมโดยรวม, สุขภาพของระบบในระยะยาว |
| **ทิศทางการสื่อสาร** | รับ requirement, ส่งมอบโค้ด | สื่อสารสองทาง — รับจากผู้บริหาร ส่งลงทีม และรายงานกลับ |
| **ความสัมพันธ์กับความขัดแย้ง** | มักเป็นฝ่ายเสนอความเห็นทางเทคนิค | ต้อง facilitate และตัดสินใจเมื่อความเห็นขัดแย้งกัน |
| **ผลลัพธ์เมื่อทำงานพลาด** | บั๊กในโค้ดตัวเอง | ทีมทั้งทีมทำงานผิดทิศทาง หรือกระบวนการทั้งองค์กรสะดุด |

### 981.3 ขอบเขตความรับผิดชอบที่ Tech Lead ต้องแบกรับเพิ่ม

1. **Technical Direction (ทิศทางเทคนิค)** — ตัดสินใจว่าจะใช้เครื่องมือ/สถาปัตยกรรม/workflow แบบไหน ไม่ใช่แค่ implement ตามที่มีคนสั่ง
2. **People Growth (การเติบโตของคน)** — รับผิดชอบว่าคนในทีมจะเก่งขึ้นหรือไม่ ไม่ใช่แค่ตัวเองเก่งขึ้น
3. **Cross-team Representation (ตัวแทนทีมเวลาคุยกับทีมอื่น)** — เป็นจุดติดต่อหลักเวลาต้องเจรจากับทีมอื่นเรื่อง dependency, API contract, breaking change (ต่อยอดจาก Part 90)
4. **Business Alignment (ความสอดคล้องกับธุรกิจ)** — ต้องเข้าใจว่าทำไมธุรกิจต้องการสิ่งนี้ ไม่ใช่แค่รับ requirement มาทำ
5. **Risk Ownership (การเป็นเจ้าของความเสี่ยง)** — เป็นคนที่ต้องตอบคำถามว่า "ถ้าเราเลือกทางนี้ ความเสี่ยงคืออะไร และเราจะจัดการอย่างไร"

### 981.4 กับดักที่พบบ่อยเมื่อ Senior Engineer เพิ่งขึ้นเป็น Tech Lead

- **ยังคงอยากเขียนโค้ดเองทุกบรรทัดที่สำคัญ** — แทนที่จะมอบหมายและให้คำปรึกษา ทำให้ทีมไม่เติบโตและตัวเองกลายเป็นคอขวด
- **ตัดสินใจทางเทคนิคโดยไม่อธิบายเหตุผลเชิงธุรกิจ** — ทำให้ทีมทำตามแบบไม่เข้าใจ "ทำไม" และผู้บริหารไม่สนับสนุน
- **หลีกเลี่ยงความขัดแย้งแทนที่จะจัดการมันอย่างสร้างสรรค์** — ปล่อยให้ปัญหาสะสมจนระเบิดในภายหลัง
- **มองข้ามมิติ "คน" เพราะโฟกัสที่ "เทคนิค" อย่างเดียว** — ลืมว่าการเปลี่ยนแปลงทุกอย่างต้องผ่านคนก่อนเสมอ

### 981.5 สัญญาณที่บ่งบอกว่าคุณพร้อมก้าวขึ้นเป็น Tech Lead

ก่อนไปต่อ ลองประเมินตัวเองด้วยคำถามเหล่านี้ ซึ่งสะท้อนความพร้อมด้าน "ขอบเขตความรับผิดชอบ" มากกว่าความสามารถทางเทคนิคล้วน ๆ:

- คุณเคยอธิบายเหตุผลของการตัดสินใจทางเทคนิคให้คนที่ไม่ใช่วิศวกรฟังจนเขาเห็นด้วยหรือไม่
- เมื่อทีมมีความเห็นขัดแย้งกัน คุณเคยเป็นคนที่ช่วยหาทางออกร่วมกัน แทนที่จะเป็นฝ่ายใดฝ่ายหนึ่งของความขัดแย้งหรือไม่
- คุณเคยสอนคนอื่นจนเขาเก่งขึ้นและทำงานแทนคุณได้ โดยไม่รู้สึกว่าตัวเอง "เสียคุณค่า" ไปหรือไม่
- คุณเคยยอมรับว่าไอเดียของตัวเองผิด แล้วเปลี่ยนทิศทางตามข้อมูลใหม่ โดยไม่ยึดติดกับความเห็นเดิมหรือไม่
- คุณมองปัญหาทางเทคนิคในแง่ของ "ผลกระทบต่อผู้ใช้และธุรกิจ" ควบคู่ไปกับ "ความถูกต้องทางวิศวกรรม" หรือไม่

ถ้าคุณตอบว่า "ใช่" กับคำถามส่วนใหญ่ นั่นคือสัญญาณว่าคุณกำลังคิดแบบ Tech Lead อยู่แล้ว แม้ตำแหน่งอย่างเป็นทางการอาจยังไม่เปลี่ยน — เพราะการเป็นผู้นำทางเทคนิคเริ่มต้นจาก **วิธีคิด** ก่อนตำแหน่งเสมอ

Part ที่เหลือทั้งหมดใน Part 99 นี้ จะพาคุณไล่เรียงทักษะความเป็นผู้นำทีละด้าน โดยใช้ **Version Control และ DevOps Practice** เป็นบริบทหลักในการฝึกฝน เพราะมันคือสิ่งที่คุณคุ้นเคยที่สุดหลังจากเรียนมาเกือบ 1,000 Step

## Step 982: การตัดสินใจเชิงกลยุทธ์เรื่อง Version Control — เลือก Workflow ให้เหมาะกับทีม

ใน Part 31–34 คุณได้เรียนรู้ Workflow หลัก 4 แบบอย่างละเอียด: **Centralized/Feature Branch Workflow** (Part 31), **Git Flow** (Part 32), **GitHub Flow** (Part 33) และ **Trunk-Based Development** (Part 34) แต่ละ Part สอนวิธีใช้งานอย่างลึกซึ้ง ทว่าคำถามที่ Tech Lead ต้องตอบไม่ใช่ "ใช้อย่างไร" แต่คือ **"ควรเลือกอันไหนสำหรับทีมนี้ ในบริบทนี้"**

### 982.1 ทำไม "เลือกตามกระแส" ถึงเป็นความผิดพลาดที่พบบ่อยที่สุด

Tech Lead มือใหม่จำนวนมากเลือก workflow เพราะ "บริษัทดัง ๆ ใช้แบบนี้" เช่น เห็น Google/Meta ใช้ Trunk-Based Development แล้วคิดว่าทีมตัวเองต้องใช้แบบเดียวกันถึงจะ "ทันสมัย" — นี่คือความผิดพลาดเชิงกลยุทธ์ที่ร้ายแรง เพราะ Trunk-Based Development ที่ Google ใช้ได้ผลดี **วางอยู่บนเงื่อนไขเฉพาะ** ที่ทีมเล็ก ๆ ส่วนใหญ่ไม่มี เช่น test suite ที่ครอบคลุมระดับสูงมาก, CI ที่รันเสร็จในไม่กี่นาที, ระบบ feature flag ที่แข็งแรง, และวัฒนธรรมวินัยการเขียนโค้ดที่เข้มงวด

### 982.2 กรอบการตัดสินใจ (Decision Framework) ที่ใช้ได้จริง

Tech Lead ที่ดีจะประเมิน workflow จากปัจจัยเชิงบริบท ไม่ใช่ความชอบส่วนตัว ปัจจัยหลักที่ต้องพิจารณา:

| ปัจจัย | คำถามที่ต้องตอบ |
|---|---|
| **ขนาดทีมและจำนวน contributor พร้อมกัน** | ทีม 3 คน กับทีม 300 คน ต้องการโครงสร้างต่างกันโดยสิ้นเชิง |
| **ความถี่ในการ deploy** | deploy วันละหลายครั้ง (Continuous Deployment) หรือ deploy เป็น cycle รายเดือน/ไตรมาส |
| **ความแข็งแรงของ CI/CD และ automated test** | ถ้า test coverage ต่ำ การ merge เข้า main บ่อย ๆ (TBD) จะอันตรายมาก |
| **ข้อกำหนดด้านกฎระเบียบ (regulatory requirement)** | ธุรกิจ fintech/healthcare อาจต้องการ release ที่ผ่านการอนุมัติเป็นทางการก่อนเสมอ ซึ่งสอดคล้องกับ Git Flow มากกว่า |
| **ความจำเป็นต้องซัพพอร์ตหลายเวอร์ชันพร้อมกัน** | ซอฟต์แวร์ที่ลูกค้าติดตั้งเอง (on-premise) มักต้อง maintain หลาย release พร้อมกัน ซึ่ง Git Flow รองรับได้ดีกว่า SaaS ที่มีเวอร์ชันเดียวบน production เสมอ |
| **ความสามารถและวินัยของทีม (team maturity)** | ทีมที่ยังใหม่กับ code review วินัยต่ำ อาจต้องเริ่มจาก GitHub Flow ที่เข้าใจง่ายก่อน แล้วค่อยขยับไป TBD เมื่อพร้อม |

### 982.3 ตารางสรุปคำแนะนำเชิงบริบท

| บริบทองค์กร | Workflow ที่มักเหมาะสม | เหตุผล |
|---|---|---|
| Startup ทีมเล็ก, SaaS, deploy บ่อย | GitHub Flow หรือ Trunk-Based Development | ต้องการความเร็ว ไม่มี overhead ของ release branch |
| องค์กรที่ต้อง maintain หลายเวอร์ชัน (on-premise software) | Git Flow | ต้องมี release/hotfix branch ที่แยกชัดเจน |
| องค์กร fintech/healthcare ที่มี compliance เข้มงวด | Git Flow หรือ GitHub Flow + mandatory approval gate | ต้องการจุดอนุมัติที่ตรวจสอบย้อนหลังได้ชัดเจน (เชื่อมโยง Part 81) |
| องค์กรขนาดใหญ่ที่มี test suite และ CI แข็งแรงระดับสูง | Trunk-Based Development + Feature Flag | ลด merge conflict, เพิ่มความเร็วในการ deploy จริง |
| ทีมที่เพิ่งเริ่มใช้ Git อย่างเป็นระบบ | Centralized/Feature Branch Workflow แบบง่าย | ลดความซับซ้อนของการเรียนรู้ในช่วงเริ่มต้น |

### 982.4 หลักการสำคัญที่ Tech Lead ต้องยึดไว้เสมอ

> **ไม่มี Workflow ใดที่ "ถูกต้องที่สุด" ในตัวเอง มีแต่ Workflow ที่ "เหมาะสมกับบริบทปัจจุบัน" ของทีม — และหน้าที่ของ Tech Lead คือประเมินบริบทให้แม่นยำ ไม่ใช่หาคำตอบสำเร็จรูปจากอินเทอร์เน็ต**

นอกจากนี้ Tech Lead ที่ดีต้องเข้าใจว่า **การตัดสินใจนี้ไม่ใช่ถาวร** — ทีมที่เติบโตขึ้น มี CI ที่แข็งแรงขึ้น ควรพิจารณาขยับจาก Git Flow ไปสู่ workflow ที่เบากว่าอย่าง GitHub Flow หรือ Trunk-Based Development ได้ในอนาคต การกำหนดเงื่อนไข (trigger) ล่วงหน้าว่า "เมื่อไหร่ควรทบทวน workflow ใหม่" เช่น ทุก 6 เดือน หรือเมื่อขนาดทีมเปลี่ยนแปลงเกิน 50% คือทักษะเชิงกลยุทธ์ที่แยก Tech Lead ที่ดีออกจากคนที่แค่ทำตามมาตรฐานเดิม

### 982.5 กรณีศึกษาสั้น: สองบริษัทที่เลือกต่างกันด้วยเหตุผลที่ถูกต้องทั้งคู่

**บริษัท A — ผู้ให้บริการซอฟต์แวร์ core banking แบบ on-premise:** ลูกค้าแต่ละรายติดตั้งซอฟต์แวร์เวอร์ชันของตัวเองและอัปเดตตามรอบที่ตกลงในสัญญา (ทุก 6 เดือน) ทีมยังคงเลือกใช้ **Git Flow** ต่อไป เพราะต้องรองรับการทำ hotfix ให้ลูกค้าหลายเวอร์ชันพร้อมกันจริง ๆ การมี `release` branch แยกชัดเจนตาม version คือความจำเป็น ไม่ใช่ความล้าสมัย

**บริษัท B — สตาร์ทอัพ SaaS ที่ deploy วันละหลายสิบครั้ง:** มีลูกค้าเพียงเวอร์ชันเดียวบน production เสมอ (multi-tenant SaaS) ทีมเลือกใช้ **Trunk-Based Development พร้อม Feature Flag** เพราะไม่มีความจำเป็นต้อง maintain หลายเวอร์ชันเลย และการ deploy บ่อยคือหัวใจของความได้เปรียบทางธุรกิจ

ทั้งสองบริษัทเลือก workflow "ถูกต้อง" สำหรับบริบทของตัวเอง แม้จะเป็นแนวทางที่ตรงข้ามกันโดยสิ้นเชิง — นี่คือหลักฐานที่ชัดเจนที่สุดว่าไม่มี Workflow ที่ดีที่สุดในตัวเอง มีแต่ Workflow ที่เหมาะกับบริบท

## Step 983: การประเมิน Trade-off ระหว่างความเร็วของทีมกับความปลอดภัยของกระบวนการ

ใน Part 76–85 คุณได้เรียนรู้แนวปฏิบัติด้านความปลอดภัยและ compliance ระดับองค์กรอย่างครบถ้วน ตั้งแต่ GitOps (Part 76), Infrastructure as Code (Part 77), Secret Management (Part 78), Signed Commits (Part 79), Dependency Scanning/Supply Chain Security (Part 80), Compliance/Audit Trail (Part 81), Monorepo/Polyrepo (Part 82), Repository Governance ระดับ Enterprise (Part 83), Disaster Recovery (Part 84) ไปจนถึงการรวมทุกอย่างเป็น Security Policy ฉบับเต็ม (Part 85)

คำถามที่ Tech Lead ต้องเผชิญทุกวันคือ **"เราจะบังคับใช้ทุกมาตรการเหล่านี้เข้มงวดแค่ไหน โดยไม่ทำให้ทีมทำงานช้าลงจนรับไม่ได้"**

### 983.1 ความเข้าใจผิดที่พบบ่อยที่สุด: "เร็ว" กับ "ปลอดภัย" ต้องแลกกันเสมอ

หลายคนเชื่อว่าความเร็วกับความปลอดภัยเป็นสองปลายของสเกลเดียวกัน (zero-sum) — ยิ่งเข้มงวดมากยิ่งช้าลง แต่ข้อมูลจากงานวิจัย **DORA (DevOps Research and Assessment)** ที่คุณเรียนไปแล้วใน Part 92 ชี้ตรงกันข้าม: **องค์กรระดับ Elite Performer มีทั้งความเร็วในการ deploy สูงที่สุด และมี change failure rate ต่ำที่สุดในเวลาเดียวกัน**

เหตุผลคือ ความเร็วและความปลอดภัยไม่ใช่ trade-off โดยธรรมชาติ แต่เป็น trade-off ก็ต่อเมื่อ **กระบวนการรักษาความปลอดภัยยังทำด้วยมือ (manual)** เมื่อองค์กรลงทุนทำให้กระบวนการเหล่านั้น**อัตโนมัติ** (automated security gate, automated compliance check, automated secret scanning) ทั้งสองอย่างจะไปด้วยกันได้

### 983.2 กรอบการประเมินความเสี่ยงแบบแบ่งระดับ (Risk-Tiered Approach)

Tech Lead ที่ดีจะไม่บังคับใช้มาตรการความปลอดภัยระดับเดียวกันกับทุก repository เพราะต้นทุนของกระบวนการต้องสอดคล้องกับ **ระดับความเสี่ยง (blast radius)** ของระบบนั้น

| ระดับความเสี่ยง | ตัวอย่างระบบ | มาตรการที่ควรบังคับใช้ |
|---|---|---|
| **Critical (สูงสุด)** | ระบบชำระเงิน, ระบบจัดการข้อมูลผู้ป่วย, Infrastructure as Code ของ production | Signed commits บังคับ (Part 79), 2+ approval, branch protection เข้มงวดสุด, dependency scanning บล็อก build เมื่อพบช่องโหว่ระดับสูง (Part 80), audit log ครบทุกการกระทำ (Part 81) |
| **High** | Core API, ระบบที่ลูกค้าใช้งานโดยตรง | 1–2 approval, CI ต้องผ่านก่อน merge, secret scanning บังคับ (Part 78) |
| **Medium** | Internal tooling, admin dashboard | 1 approval, CI พื้นฐาน, scanning แบบ warning ไม่บล็อก |
| **Low** | Documentation, proof-of-concept, sandbox repo | Review แบบยืดหยุ่น เน้นความเร็วมากกว่า |

การจัดระดับนี้ทำให้ทีมที่ทำงานกับระบบความเสี่ยงต่ำไม่ต้องแบกรับ overhead ที่ไม่จำเป็น ในขณะที่ระบบความเสี่ยงสูงได้รับการปกป้องอย่างเข้มงวดตามจริง

### 983.3 การประเมิน Cost-Benefit ของแต่ละมาตรการ

ก่อนเพิ่มมาตรการใหม่ทุกครั้ง Tech Lead ควรถามคำถามเหล่านี้:

1. **ต้นทุนที่แท้จริงของมาตรการนี้คืออะไร** — เพิ่ม lead time กี่นาที/ชั่วโมงต่อ pull request หนึ่งอัน
2. **มาตรการนี้ป้องกันความเสียหายแบบไหน และความเสียหายนั้นมีโอกาสเกิดสูงแค่ไหน** — ใช้หลักการเดียวกับการทำ risk register ใน Disaster Recovery Plan (Part 84)
3. **มีวิธีทำให้มาตรการนี้เร็วขึ้นโดยไม่ลดทอนความปลอดภัยหรือไม่** — เช่น เปลี่ยนจาก manual security review เป็น automated SAST scan ที่รันคู่ขนานกับ CI แทนที่จะรันแบบต่อคิว
4. **มาตรการนี้จำเป็นสำหรับทุก repository หรือเฉพาะบาง tier** — ใช้ risk-tiered approach ข้างต้น

### 983.4 ตัวอย่างสถานการณ์จริงที่ Tech Lead ต้องตัดสินใจ

**สถานการณ์:** ทีม deploy วันละ 10 ครั้ง แต่ผู้บริหารฝ่าย Compliance ขอให้เพิ่ม mandatory manual security review ก่อน merge ทุก PR หลังเกิดเหตุการณ์ secret หลุดในอีกทีมหนึ่ง

**แนวทางที่ Tech Lead ที่ดีควรทำ แทนที่จะปฏิเสธหรือยอมรับตรง ๆ ทันที:**

- เสนอ **automated secret scanning gate** (gitleaks/trufflehog ที่เรียนใน Part 78) เป็นด่านแรกที่รันอัตโนมัติทุก commit แทนการรอคนตรวจด้วยมือ
- เสนอ **manual review เฉพาะ repository ระดับ Critical/High** ตาม risk tier แทนที่จะบังคับทุก repo เท่ากันหมด
- นำเสนอข้อมูล DORA metrics ของทีมตัวเองเปรียบเทียบก่อน-หลัง เพื่อพิสูจน์ว่ามาตรการใหม่ไม่ได้ทำให้ lead time แย่ลงอย่างมีนัยสำคัญ
- เสนอ **ทดลองใช้ (pilot) 2 สัปดาห์** ก่อนบังคับใช้ถาวร เพื่อวัดผลกระทบจริงก่อนตัดสินใจถาวร

> **หลักการทองของ Step นี้:** ความเร็วกับความปลอดภัยไม่ใช่ศัตรูกัน ศัตรูตัวจริงคือ **กระบวนการที่ทำด้วยมือและกระจัดกระจาย** — หน้าที่ของ Tech Lead คือหาจุดที่ลงทุนทำ automation แล้วได้ทั้งสองอย่างพร้อมกัน ไม่ใช่เลือกอย่างใดอย่างหนึ่ง

### 983.5 การวัดผลด้วยตัวเลข ไม่ใช่ความรู้สึก

เมื่อเสนอมาตรการด้านความปลอดภัยใหม่ Tech Lead ควรเก็บข้อมูล before/after เสมอ เพื่อพิสูจน์ว่ามาตรการนั้นคุ้มค่าจริง ไม่ใช่แค่สร้าง overhead:

| ตัวชี้วัด | ก่อนเพิ่มมาตรการ | หลังเพิ่มมาตรการ (automated) |
|---|---|---|
| เวลาเฉลี่ยจาก PR เปิดถึง merge (Lead Time) | 4 ชั่วโมง | 4.5 ชั่วโมง (เพิ่มขึ้นเล็กน้อยจาก automated scan) |
| จำนวน secret ที่หลุดเข้า repository ต่อไตรมาส | 3 ครั้ง | 0 ครั้ง |
| Change Failure Rate | 12% | 7% |
| เวลาที่ auditor ใช้ตรวจสอบ compliance ต่อรอบ | 3 สัปดาห์ (ค้นเอกสารด้วยมือ) | 3 วัน (ดึงจาก audit log อัตโนมัติ) |

ตารางลักษณะนี้คือหลักฐานที่ทรงพลังที่สุดเวลาต้องโน้มน้าวทั้งทีมวิศวกรรมและผู้บริหารว่ามาตรการที่เพิ่มเข้ามาคุ้มค่ากับต้นทุนที่เสียไปจริง

## Step 984: การนำการเปลี่ยนแปลง (Change Management) เมื่อต้องเปลี่ยน Workflow ทั้งทีม/องค์กร

การรู้ว่า "ควรเปลี่ยนไปใช้ workflow ไหน" (Step 982) เป็นแค่ครึ่งแรกของงาน อีกครึ่งที่ยากกว่ามากคือ **การทำให้การเปลี่ยนแปลงนั้นเกิดขึ้นจริงในทีมที่มีมนุษย์อยู่ ซึ่งมีความเคยชิน ความกลัว และความไม่ไว้วางใจเป็นธรรมชาติ**

### 984.1 ทำไมการเปลี่ยน Workflow ถึงล้มเหลวบ่อยครั้ง แม้ไอเดียจะดีมาก

สาเหตุที่พบบ่อยที่สุดไม่ใช่ว่าไอเดียไม่ดี แต่คือ:

- **ประกาศเปลี่ยนทันทีโดยไม่อธิบายเหตุผล** — ทีมรู้สึกว่าถูกสั่งการ ไม่ใช่ถูกชวนคุย
- **ไม่มีช่วง pilot ทดลอง** — บังคับใช้กับทั้งองค์กรพร้อมกันวันเดียว ถ้าเจอปัญหาจะกระทบวงกว้างทันที
- **ไม่รับฟัง feedback ระหว่างทาง** — ทำให้ทีมรู้สึกว่าความเห็นของตัวเองไม่มีความหมาย
- **ไม่มีแผนสำหรับคนที่ยังไม่พร้อม** — บางคนอาจต้องการเวลาเรียนรู้เพิ่มเติมก่อนปรับตัว

### 984.2 กรอบการนำการเปลี่ยนแปลงที่ใช้ได้จริง

แนวคิด **Kotter's 8-Step Change Model** ของ John Kotter เป็นกรอบที่นำมาประยุกต์ใช้กับการเปลี่ยน Git workflow ได้ดีมาก:

| ขั้นตอนของ Kotter | การประยุกต์ใช้กับการเปลี่ยน Git Workflow |
|---|---|
| 1. สร้างความรู้สึกเร่งด่วน (Sense of urgency) | แสดงข้อมูลจริง เช่น merge conflict เกิดบ่อยแค่ไหน, deploy ใช้เวลานานแค่ไหนในปัจจุบัน |
| 2. สร้างทีมแนวร่วม (Guiding coalition) | ชวน senior engineer ที่มีอิทธิพลในทีมมาร่วมออกแบบตั้งแต่ต้น ไม่ใช่ประกาศคนเดียว |
| 3. สร้างวิสัยทัศน์ (Vision) | อธิบายภาพในอนาคตให้ชัดเจน เช่น "ทีมจะ deploy ได้ทุกวันโดยไม่ต้องรอ release window" |
| 4. สื่อสารวิสัยทัศน์ | จัดประชุมอธิบาย เปิดโอกาสถาม-ตอบ ไม่ใช่แค่ส่งเอกสาร |
| 5. ให้อำนาจในการลงมือทำ (Empower action) | ให้ทีมมีส่วนร่วมออกแบบรายละเอียด เช่น branch naming convention ใหม่ |
| 6. สร้างชัยชนะระยะสั้น (Short-term wins) | เริ่ม pilot กับ 1 ทีมก่อน แสดงผลลัพธ์ที่จับต้องได้ภายใน 2–4 สัปดาห์ |
| 7. ต่อยอดจากชัยชนะ (Build on the change) | ขยายจากทีม pilot ไปทีมอื่นทีละขั้น พร้อมปรับปรุงจาก feedback |
| 8. ฝังเข้าไปในวัฒนธรรม | อัปเดต onboarding document, CONTRIBUTING.md, และ CI/CD template ให้สะท้อน workflow ใหม่ถาวร |

### 984.3 แผนงานที่แนะนำสำหรับการเปลี่ยน Workflow ระดับองค์กร

1. **เดือนที่ 1 — วิเคราะห์และสร้างข้อเสนอ:** เก็บข้อมูล pain point ปัจจุบัน เขียน RFC (Part 90) เสนอแนวทางพร้อมเหตุผลและ trade-off ชัดเจน
2. **เดือนที่ 2 — Pilot กับทีมอาสาสมัคร:** เลือกทีมที่เปิดรับการเปลี่ยนแปลงและมี CI/test พร้อม ทดลองใช้ workflow ใหม่จริง เก็บ metric เปรียบเทียบก่อน-หลัง
3. **เดือนที่ 3 — ทบทวนผลและปรับปรุง:** จัด retrospective กับทีม pilot สรุปปัญหาที่เจอ ปรับ workflow ให้เข้ากับบริบทจริงมากขึ้น
4. **เดือนที่ 4–6 — ขยายผลทีละขั้น (phased rollout):** ขยายไปทีมถัดไปทีละกลุ่ม พร้อมจัด training session และเตรียม documentation/CI template ให้พร้อมใช้งานทันที
5. **หลังจากนั้น — ฝังเข้าเป็นมาตรฐานถาวร:** อัปเดต onboarding ของพนักงานใหม่ และทบทวนผลลัพธ์ระยะยาวทุกไตรมาส

### 984.4 การรับมือกับแรงต้าน (Resistance) อย่างมีชั้นเชิง

| ประเภทแรงต้าน | สาเหตุที่แท้จริง | วิธีรับมือ |
|---|---|---|
| "ของเดิมก็ใช้ได้อยู่แล้ว" | กลัวการเรียนรู้สิ่งใหม่ / ไม่เห็นปัญหาที่คนอื่นเจอ | แสดงข้อมูล pain point ที่จับต้องได้ ไม่ใช่แค่ความเห็น |
| "เคยเปลี่ยนมาแล้วล้มเหลว" | ประสบการณ์แย่จากการเปลี่ยนแปลงครั้งก่อน (change fatigue) | ยอมรับความล้มเหลวเดิมตรง ๆ อธิบายว่าครั้งนี้ต่างกันอย่างไร (เช่น มี pilot และ rollback plan) |
| "จะทำให้งานฉันช้าลง" | กังวลเรื่อง productivity ส่วนตัว | ให้ pilot เป็นผู้พิสูจน์ด้วยข้อมูลจริง ไม่ใช่คำสัญญาลอย ๆ |
| ความเงียบ (ไม่พูดอะไรเลย) | อาจไม่เชื่อว่าความเห็นตัวเองมีผล | สร้างช่องทางให้ feedback แบบไม่ต้องเปิดเผยตัวตน (anonymous survey) |

### 984.5 มี "ทางถอย" เสมอ

การเปลี่ยนแปลงทุกครั้งควรมี **rollback plan สำหรับตัวการเปลี่ยนแปลงเอง** ไม่ใช่แค่ rollback โค้ด — ถ้า pilot พิสูจน์ว่า workflow ใหม่ไม่เหมาะกับบริบทจริง ต้องกล้ายอมรับและถอยกลับโดยไม่มองว่าเป็นความล้มเหลวส่วนตัว เพราะ **การทดลองแล้วพบว่าไม่เหมาะ คือข้อมูลที่มีค่า ไม่ใช่ความผิดพลาด**

### 984.6 การวัดผลว่าการเปลี่ยนแปลงสำเร็จจริงหรือไม่

อย่าตัดสินความสำเร็จของการเปลี่ยนแปลงจากความรู้สึกหรือเสียงบ่นที่เงียบลง แต่ให้กำหนดตัวชี้วัดล่วงหน้าก่อนเริ่ม pilot เสมอ เช่น:

- **ตัวชี้วัดเชิงกระบวนการ:** จำนวน merge conflict ต่อสัปดาห์ลดลงหรือไม่, เวลาเฉลี่ยจาก commit ถึง production (Lead Time) เปลี่ยนแปลงอย่างไร
- **ตัวชี้วัดเชิงคุณภาพ:** Change Failure Rate เพิ่มขึ้นหรือลดลงหลังเปลี่ยน workflow (อ้างอิง DORA Metrics จาก Part 92)
- **ตัวชี้วัดเชิงคน:** ผลสำรวจความพึงพอใจของทีมแบบไม่เปิดเผยตัวตน ก่อนและหลังการเปลี่ยนแปลง

การมีตัวเลขชัดเจนตั้งแต่ต้น ทำให้การตัดสินใจ "ขยายผลต่อ" หรือ "ถอยกลับ" เป็นการตัดสินใจที่อิงข้อมูล ไม่ใช่อิงความรู้สึกของคนที่เสียงดังที่สุดในทีม

## Step 985: การสื่อสารการตัดสินใจทางเทคนิคให้ผู้บริหารที่ไม่ใช่สายเทคนิคเข้าใจและสนับสนุน

Tech Lead จำนวนมากมีไอเดียทางเทคนิคที่ดีเยี่ยม แต่ล้มเหลวเพราะ **สื่อสารไม่ได้ผล** เมื่อต้องคุยกับผู้บริหารที่ไม่มีพื้นฐานเทคนิค (CEO, CFO, VP Sales, board member) ทักษะนี้สำคัญไม่แพ้ทักษะทางเทคนิคเลย

### 985.1 ทำไมผู้บริหารถึงไม่สนใจ "รายละเอียดทางเทคนิค"

ผู้บริหารไม่ได้ไม่สนใจเพราะพวกเขาไม่ฉลาด แต่เพราะ **หน่วยการตัดสินใจของพวกเขาคือความเสี่ยงทางธุรกิจและต้นทุน ไม่ใช่รายละเอียดการทำงาน** เมื่อ Tech Lead พูดว่า "เราต้อง migrate จาก Git Flow ไป Trunk-Based Development เพราะ merge conflict เยอะเกินไป" ผู้บริหารจะไม่เข้าใจว่ามันสำคัญอย่างไรกับธุรกิจเลย

### 985.2 หลักการแปลภาษาเทคนิคเป็นภาษาธุรกิจ

| ภาษาเทคนิค | แปลเป็นภาษาธุรกิจ |
|---|---|
| "Merge conflict เกิดบ่อยทำให้เสียเวลา" | "ทีมพัฒนาเสียเวลาโดยเฉลี่ย X ชั่วโมงต่อสัปดาห์ไปกับปัญหานี้ คิดเป็นต้นทุนแรงงานประมาณ Y บาทต่อเดือน ที่สามารถนำไปใช้พัฒนาฟีเจอร์ใหม่แทนได้" |
| "เราต้องเพิ่ม signed commit และ branch protection" | "มาตรการนี้ลดความเสี่ยงที่โค้ดที่ไม่ผ่านการตรวจสอบจะเข้าไปอยู่ใน production ซึ่งเป็นข้อกำหนดที่ลูกค้าองค์กรระดับ enterprise มักถามในขั้นตอน security audit ก่อนเซ็นสัญญา" |
| "Deploy ช้าเพราะ workflow ซับซ้อน" | "ปัจจุบันจากไอเดียถึงมือลูกค้าใช้เวลา X วัน ถ้าปรับปรุงกระบวนการจะลดเหลือ Y ชั่วโมง ทำให้ตอบสนองต่อ feedback ลูกค้าและคู่แข่งได้เร็วขึ้น" |

### 985.3 โครงสร้างการนำเสนอที่ได้ผล: Situation – Complication – Resolution

1. **Situation (สถานการณ์ปัจจุบัน):** อธิบายสถานการณ์ปัจจุบันสั้น ๆ ด้วยข้อมูล ไม่ใช่ความรู้สึก
2. **Complication (ปัญหา/ความเสี่ยง):** อธิบายว่าอะไรจะเกิดขึ้นถ้าไม่ทำอะไรเลย (cost of inaction) — ผู้บริหารมักตัดสินใจง่ายขึ้นเมื่อเห็นความเสี่ยงของการ "ไม่ทำ"
3. **Resolution (ทางออกที่เสนอ):** เสนอทางแก้พร้อมตัวเลือก 2–3 ทาง พร้อมข้อดี-ข้อเสีย-ต้นทุนของแต่ละทาง ให้ผู้บริหารมีส่วนร่วมตัดสินใจ ไม่ใช่แค่ฟังคำสั่งเดียว

### 985.4 เทคนิคเสริมที่ใช้ได้ผลจริง

- **เริ่มด้วย Executive Summary หนึ่งย่อหน้าเสมอ** — ผู้บริหารมักอ่านแค่ย่อหน้าแรก รายละเอียดทางเทคนิคทั้งหมดใส่ไว้ใน appendix
- **ใช้ตัวเลขและ metric ที่จับต้องได้เสมอ** — อ้างอิง DORA metrics (Part 92) เช่น Lead Time for Changes, Change Failure Rate, Deployment Frequency แปลงเป็นตัวเลขที่ผู้บริหารคุ้นเคย เช่น "เร็วขึ้น 3 เท่า" หรือ "ลดความเสี่ยง downtime ลง 40%"
- **ใช้การเปรียบเทียบ (analogy) แทนศัพท์เทคนิค** — เช่น เปรียบ branch protection กับ "ระบบตรวจสอบสองชั้นก่อนอนุมัติจ่ายเงินในองค์กร" ซึ่งผู้บริหารที่ไม่ใช่สายเทคนิคเข้าใจได้ทันที
- **เตรียมคำตอบสำหรับคำถาม "ต้นทุน" และ "ความเสี่ยง" ล่วงหน้าเสมอ** — ผู้บริหารมักถามสองเรื่องนี้เป็นหลัก
- **อย่าขอ "ความไว้วางใจแบบเปล่า ๆ"** — เสนอ pilot เล็ก ๆ ที่วัดผลได้ภายในกรอบเวลาสั้น แทนการขออนุมัติเปลี่ยนแปลงทั้งหมดในครั้งเดียว

> **หลักการสำคัญ:** ผู้บริหารไม่ได้ต้องการรู้ว่า Git ทำงานอย่างไร พวกเขาต้องการรู้แค่ **"สิ่งนี้ทำให้ธุรกิจเร็วขึ้น ปลอดภัยขึ้น หรือถูกลงหรือไม่ และมีความเสี่ยงอะไรที่ต้องรับ"** — หน้าที่ของ Tech Lead คือแปลความซับซ้อนทางเทคนิคทั้งหมดให้เหลือแค่คำตอบของคำถามนี้

### 985.5 ตัวอย่างบทสนทนาเปรียบเทียบ: สื่อสารแบบที่ใช้ไม่ได้ผล กับแบบที่ใช้ได้ผล

**แบบที่ใช้ไม่ได้ผล (พูดภาษาเทคนิคล้วน):**

> "เราอยากเปลี่ยนจาก Git Flow ไป Trunk-Based Development เพราะ `develop` branch กับ `release` branch conflict กันบ่อยมาก แล้วก็อยากเพิ่ม signed commit กับ branch protection rule ด้วยครับ"

ผลลัพธ์ที่มักเกิดขึ้น: ผู้บริหารฟังไม่เข้าใจ เห็นเป็นเรื่อง "งานภายในของฝ่ายไอที" ที่ไม่เกี่ยวกับธุรกิจ แล้วปฏิเสธหรือเลื่อนการอนุมัติออกไปเรื่อย ๆ

**แบบที่ใช้ได้ผล (แปลเป็นภาษาธุรกิจ):**

> "ตอนนี้ทีมวิศวกรรมใช้เวลาเฉลี่ย 14 วันกว่าฟีเจอร์ใหม่จะถึงมือลูกค้า ในขณะที่คู่แข่งเราทำได้ภายใน 2–3 วัน ผมเสนอปรับกระบวนการพัฒนาซอฟต์แวร์ภายในทีม ซึ่งจะลดเวลานี้เหลือประมาณ 3 วัน โดยไม่กระทบต่อความปลอดภัย เพราะเราจะเพิ่มการตรวจสอบอัตโนมัติแทนการตรวจด้วยมือ ทีมขอเวลา 2 สัปดาห์ทดลองกับ 1 ทีมก่อน แล้วจะกลับมารายงานผลตัวเลขจริงให้ทราบครับ"

สังเกตว่าเวอร์ชันที่สองไม่มีศัพท์เทคนิคเลยแม้แต่คำเดียว แต่สื่อสารครบทั้งปัญหา ทางออก ต้นทุนเวลา และแผนพิสูจน์ผลลัพธ์ — นี่คือทักษะที่ทำให้ผู้บริหารสนับสนุนได้จริง

## Step 986: การสร้างวัฒนธรรมวิศวกรรมที่ดีผ่านการปฏิบัติด้าน Git ในชีวิตประจำวัน

**Engineering Culture (วัฒนธรรมวิศวกรรม)** ไม่ได้ถูกสร้างจากเอกสารนโยบายที่แขวนไว้บนผนัง แต่ถูกสร้างจาก **พฤติกรรมเล็ก ๆ ที่ทำซ้ำทุกวัน** และ Git คือเครื่องมือที่สะท้อนวัฒนธรรมวิศวกรรมของทีมได้ชัดเจนที่สุด เพราะทุก commit, ทุก pull request, ทุก code review comment คือ **ร่องรอยพฤติกรรม** ที่บันทึกไว้ถาวรและตรวจสอบย้อนหลังได้

### 986.1 Git เป็นกระจกสะท้อนวัฒนธรรมทีม

ลองสังเกตสัญญาณเหล่านี้ในประวัติ Git ของทีมใดก็ได้ — มันจะบอกวัฒนธรรมที่แท้จริงของทีมได้แม่นยำกว่าคำพูดในที่ประชุม:

| สัญญาณที่สังเกตได้ | สะท้อนวัฒนธรรมแบบไหน |
|---|---|
| Commit message เขียนสั้น ๆ ว่า "fix", "update", "wip" ตลอด | ทีมไม่ได้ให้คุณค่ากับการสื่อสารผ่าน history ที่คนอื่นจะอ่านในอนาคต |
| PR ถูก approve ภายใน 1 นาทีโดยไม่มี comment เลย | Code review เป็นพิธีกรรม (rubber-stamp) ไม่ใช่การตรวจสอบจริง |
| Comment ใน code review มีทั้งคำชมและคำติเชิงสร้างสรรค์ | วัฒนธรรมความปลอดภัยทางจิตใจ (psychological safety) ดี |
| มีแค่ 1–2 คนที่ commit เข้า core module ตลอดเวลา | Bus factor ต่ำ, knowledge silo, ทีมพึ่งพา "hero" คนเดียว |
| Branch ค้างไม่ merge เป็นเวลานานหลายเดือน | ขาดวินัยในการปิดงานให้จบ หรือ CI/review process มีคอขวด |

### 986.2 พฤติกรรมที่ Tech Lead ควรปลูกฝังผ่าน Git ในชีวิตประจำวัน

1. **เขียน Commit Message คุณภาพสูงเป็นแบบอย่าง** — Tech Lead ที่เขียน commit message ตาม Conventional Commits หรือรูปแบบที่ทีมตกลงกันอย่างสม่ำเสมอ จะทำให้คนอื่นทำตามโดยธรรมชาติ
2. **ให้ Code Review อย่างมีคุณภาพ ไม่ใช่แค่ approve** — ทิ้ง comment ที่อธิบายเหตุผล ไม่ใช่แค่บอกว่าต้องแก้อะไร และให้คำชมเมื่อเห็นโค้ดที่เขียนดี ไม่ใช่ชี้แต่ข้อผิดพลาด
3. **ทำ Blameless Postmortem อย่างจริงจัง** — เมื่อเกิด incident จาก commit ใดก็ตาม โฟกัสที่ "ระบบพลาดตรงไหน" ไม่ใช่ "ใครทำพลาด" (ต่อยอดจากแนวคิดใน Part 90 และ Part 95)
4. **แชร์ความรู้ผ่าน Pull Request Description อย่างสม่ำเสมอ** — อธิบาย "ทำไม" ไม่ใช่แค่ "ทำอะไร" ในทุก PR ที่สำคัญ
5. **ให้เครดิตอย่างเปิดเผยผ่านประวัติ Git** — Git เก็บ authorship ไว้ถาวร Tech Lead ควรใช้สิ่งนี้ในการยกย่องผลงานของทีมต่อหน้าผู้บริหาร ไม่ใช่รับเครดิตคนเดียว

### 986.3 Anti-pattern ที่ทำลายวัฒนธรรมวิศวกรรมโดยไม่รู้ตัว

- **Hero Culture** — ยกย่องเฉพาะคนที่ "ดับไฟ" ตอนวิกฤต แต่ไม่ให้คุณค่ากับคนที่ทำงานป้องกันปัญหาล่วงหน้า (เช่นเขียน test ดี, เขียน documentation ดี) ทำให้ทีมสร้างปัญหาโดยไม่ตั้งใจเพื่อให้ตัวเองได้เป็น hero
- **Gatekeeping ผ่าน Code Review** — ใช้ตำแหน่ง reviewer เป็นเครื่องมือแสดงอำนาจ แทนที่จะช่วยกันปรับปรุงคุณภาพโค้ด
- **Fear-based Review** — ทีมกลัวการถูกวิจารณ์ใน PR จนไม่กล้าเสนอไอเดียใหม่ หรือซ่อนโค้ดที่ไม่มั่นใจ
- **Silent Force Push** — การ force push ทับประวัติของคนอื่นโดยไม่แจ้งล่วงหน้า เป็นสัญญาณของการขาดความเคารพต่องานของเพื่อนร่วมทีม

> **หลักการสำคัญ:** วัฒนธรรมวิศวกรรมไม่ได้ถูกสร้างจากคำพูดในที่ประชุม All-hands แต่ถูกสร้างจาก **สิ่งที่ Tech Lead ทำจริงในทุก commit, ทุก PR, ทุกวัน** — คนในทีมจะเลียนแบบพฤติกรรมที่เห็น ไม่ใช่พฤติกรรมที่ถูกบอกให้ทำ

### 986.4 การวัดผลวัฒนธรรมวิศวกรรมด้วยข้อมูลเชิงปริมาณ

วัฒนธรรมเป็นเรื่องนามธรรม แต่ Git ทิ้งร่องรอยที่วัดผลได้จริงไว้เสมอ Tech Lead ที่ดีควรติดตามตัวชี้วัดเหล่านี้เป็นระยะ เพื่อจับสัญญาณปัญหาก่อนที่มันจะลุกลาม:

| ตัวชี้วัด | สัญญาณที่ดี | สัญญาณเตือน |
|---|---|---|
| **Bus Factor** (จำนวนคนที่เข้าใจ module สำคัญ) | มีอย่างน้อย 2–3 คนต่อ module สำคัญ | มีคนเดียวที่ commit เข้า module นั้นมาตลอด |
| **PR Review Turnaround Time** | ได้รับ comment แรกภายในไม่กี่ชั่วโมง | ค้างหลายวันโดยไม่มีใคร review |
| **จำนวน comment เฉลี่ยต่อ PR** | มีการอภิปรายเนื้อหาจริง | ใกล้ 0 (แปลว่า approve แบบไม่อ่าน) |
| **สัดส่วน PR ที่ถูก merge โดยไม่มี review** | ใกล้ 0% (ยกเว้นกรณีฉุกเฉินที่มีบันทึกเหตุผล) | สูงผิดปกติ แปลว่า process ถูกข้ามบ่อย |
| **การกระจายตัวของ contributor ในแต่ละ repository** | กระจายทั่วทีม | กระจุกอยู่ที่ 1–2 คน |

การติดตามตัวเลขเหล่านี้ทุกไตรมาสช่วยให้ Tech Lead เห็นปัญหาเชิงวัฒนธรรมได้เร็วกว่าการรอให้คนมาบ่นหรือรอให้เกิด incident ก่อน

## Step 987: การ Mentor วิศวกรรุ่นใหม่ให้เข้าใจ Git อย่างลึกซึ้ง ไม่ใช่แค่ท่องจำคำสั่ง

ย้อนกลับไปที่ **Step 6 ของ Part 01** เราได้เน้นย้ำหลักการสำคัญที่สุดข้อหนึ่งของทั้งหลักสูตรนี้ไว้ว่า **"Git คิดถึงข้อมูลของมันในรูปแบบ Snapshot ของทั้งโปรเจกต์ ไม่ใช่ diff ของไฟล์ทีละไฟล์"** — นี่ไม่ใช่แค่ข้อเท็จจริงทางเทคนิค แต่คือ **ปรัชญาการสอนที่ยึดโยงทั้งหลักสูตรนี้ไว้ด้วยกัน**: สอนแนวคิด (mental model) ก่อนสอนคำสั่ง เสมอ

Tech Lead ที่ดีต้องส่งต่อปรัชญานี้ไปยังวิศวกรรุ่นใหม่ในทีม ไม่ใช่แค่สอนให้ท่องจำคำสั่งไปใช้แก้ปัญหาเฉพาะหน้า

### 987.1 ความแตกต่างระหว่าง "จำคำสั่งได้" กับ "เข้าใจแนวคิด"

| ลักษณะ | จำคำสั่งได้ (Command Memorization) | เข้าใจแนวคิด (Mental Model) |
|---|---|---|
| เมื่อเจอปัญหาที่ไม่เคยเจอมาก่อน | ค้นหาคำสั่งสำเร็จรูปจากอินเทอร์เน็ตโดยไม่เข้าใจว่าทำไมมันทำงาน | วิเคราะห์จากหลักการพื้นฐาน (เช่น Git object model, DAG ของ commit) แล้วสรุปวิธีแก้เอง |
| เมื่อคำสั่งทำงานผิดจากที่คาด | ตกใจ ไม่รู้จะทำอย่างไรต่อ | เข้าใจว่าทำไมมันทำงานแบบนั้น เพราะรู้กลไกเบื้องหลัง |
| เมื่อต้องอธิบายให้คนอื่นฟัง | อธิบายได้แค่ "ให้พิมพ์คำสั่งนี้" | อธิบายได้ว่า "ทำไมต้องทำแบบนี้ เกิดอะไรขึ้นเบื้องหลัง" |
| ความมั่นใจในสถานการณ์กดดัน (เช่น production incident) | ตื่นตระหนก กลัวทำพัง | สงบ เพราะเข้าใจว่าระบบทำงานอย่างไรจริง ๆ |

### 987.2 เทคนิคการ Mentor ที่เน้นแนวคิด ไม่ใช่คำสั่ง

1. **ถามว่า "ทำไม" ก่อนบอกว่า "ทำอย่างไร"** — เมื่อลูกทีมมาถามว่า "ทำ merge conflict ยังไง" ให้ถามกลับก่อนว่า "คุณเข้าใจไหมว่าทำไมมันถึงเกิด conflict ตรงนี้" แล้วค่อยอธิบายกลไกก่อนสอนคำสั่ง
2. **ใช้ Sandbox Repository ให้ทดลองพัง** — สร้าง repository ทดลองที่อนุญาตให้ลูกทีม `reset --hard`, `rebase`, force push ได้อย่างอิสระโดยไม่กระทบงานจริง เพื่อให้เห็นผลลัพธ์ของคำสั่งด้วยตาตัวเอง
3. **สอนผ่าน Code Review เป็นโอกาสการเรียนรู้** — แทนที่จะแค่บอกว่า "commit นี้ควรแยกเป็น 2 commit" ให้อธิบายว่าทำไม atomic commit ถึงสำคัญต่อการ `git bisect` หรือการ revert ในอนาคต
4. **เชื่อมโยงกลับไปที่ Internals เสมอเมื่อมีโอกาส** — เมื่อลูกทีมงงเรื่อง merge conflict ให้อธิบายย้อนไปถึงแนวคิด three-way merge และ object model ที่เรียนใน Part 56 แทนที่จะบอกแค่ "กดยอมรับฝั่งไหนก็ได้"
5. **ให้พื้นที่ผิดพลาดอย่างปลอดภัย** — เมื่อลูกทีมทำพลาด เช่น push โค้ดผิด branch หรือลบไฟล์สำคัญโดยไม่ตั้งใจ ให้ใช้เป็นโอกาสสอนเรื่อง reflog และการกู้คืนข้อมูล แทนที่จะตำหนิ

### 987.3 เส้นทางการเติบโตที่ Tech Lead ควรออกแบบให้ลูกทีม

จากประสบการณ์การสอน Git ที่ดีที่สุด เส้นทางการเติบโตควรเป็นแบบ **spiral** คือกลับมาเรียนเรื่องเดิมซ้ำในระดับที่ลึกขึ้นเรื่อย ๆ ไม่ใช่เส้นตรง:

- **รอบที่ 1 (มือใหม่):** ใช้คำสั่งพื้นฐานได้ (add, commit, push, pull) โดยยังไม่ต้องเข้าใจกลไกเบื้องหลังทั้งหมด
- **รอบที่ 2 (เริ่มทำงานเป็นทีม):** เข้าใจ branching, merge conflict, และเริ่มเห็นภาพว่า Git เก็บข้อมูลแบบ snapshot/DAG
- **รอบที่ 3 (มีประสบการณ์):** เข้าใจ internals ลึกพอที่จะ debug ปัญหาซับซ้อนได้เอง เช่น bisect, reflog, filter-repo
- **รอบที่ 4 (ระดับ senior):** สามารถออกแบบ workflow และตัดสินใจเชิงกลยุทธ์ได้เอง — นี่คือจุดที่พวกเขาพร้อมเป็น Tech Lead รุ่นต่อไป

> **นี่คือปรัชญาที่ยึดโยงหลักสูตรทั้งหมดตั้งแต่ Step 1 ถึง Step 990:** การเข้าใจ "ทำไม" อย่างลึกซึ้งเสมอมีค่ามากกว่าการจำ "อย่างไร" ได้เยอะ ๆ เพราะเมื่อเจอสถานการณ์ที่ไม่เคยเจอมาก่อน — ซึ่งเกิดขึ้นเสมอในงานจริง — คนที่เข้าใจแนวคิดจะแก้ปัญหาได้ ในขณะที่คนที่จำคำสั่งได้อย่างเดียวจะติดขัด

### 987.4 วิธีรู้ว่าการ Mentor ได้ผลจริง

Tech Lead ควรสังเกตสัญญาณเหล่านี้เพื่อประเมินว่าลูกทีมเข้าใจแนวคิดจริง ไม่ใช่แค่ทำตามได้:

- ลูกทีมเริ่ม**ถามคำถามที่ลึกขึ้น** แทนที่จะถามแค่ "พิมพ์คำสั่งอะไร" เช่น เริ่มถามว่า "ทำไม rebase ถึงเปลี่ยน commit hash" แทนที่จะถามแค่ "rebase ยังไง"
- ลูกทีม**แก้ปัญหาที่ไม่เคยเจอมาก่อนได้เอง** โดยไม่ต้องมาถามทุกครั้ง เพราะสามารถประยุกต์แนวคิดพื้นฐานไปใช้ได้
- ลูกทีม**เริ่มอธิบายแนวคิดให้เพื่อนร่วมทีมคนอื่นฟังได้เอง** — นี่คือสัญญาณที่ชัดเจนที่สุดว่าความเข้าใจฝังลึกจริง เพราะการสอนคนอื่นได้ต้องเข้าใจมากกว่าการทำตามได้เพียงอย่างเดียว
- ลูกทีม**ไม่ตื่นตระหนกเมื่อเจอสถานการณ์ผิดพลาด** เช่น history เสียหาย หรือ merge ผิดพลาด เพราะเข้าใจว่ามีทางกู้คืนเสมอ (reflog, backup branch)

เมื่อเห็นสัญญาณเหล่านี้ แปลว่าคุณกำลังสร้าง Tech Lead รุ่นต่อไปให้องค์กรอยู่จริง ไม่ใช่แค่สร้างคนที่ทำงานตามคำสั่งได้เท่านั้น

## Step 988: การรับมือกับความขัดแย้งทางเทคนิค (Technical Disagreement) อย่างสร้างสรรค์

ทีมวิศวกรรมที่ดีที่สุดในโลกไม่ใช่ทีมที่ไม่มีความขัดแย้งทางเทคนิค แต่คือทีมที่ **รู้วิธีจัดการความขัดแย้งให้กลายเป็นการตัดสินใจที่ดีขึ้น** แทนที่จะกลายเป็นความบาดหมางส่วนตัว

### 988.1 ประเภทของความขัดแย้งทางเทคนิคที่พบบ่อย

| ประเภท | ตัวอย่าง |
|---|---|
| **ความเห็นต่างเรื่อง Workflow/Process** | ทีมหนึ่งอยากใช้ Trunk-Based Development อีกทีมอยากคง Git Flow ไว้ |
| **ความเห็นต่างเรื่องสถาปัตยกรรม** | ควรใช้ Monorepo หรือ Polyrepo (Part 82) |
| **ความเห็นต่างเรื่องเครื่องมือ** | ใช้ GitHub Actions หรือ GitLab CI สำหรับ pipeline ใหม่ |
| **ความเห็นต่างเรื่องมาตรฐานโค้ด** | รูปแบบ commit message, การตั้งชื่อ branch, กฎ code review |

### 988.2 กรอบการจัดการความขัดแย้งอย่างสร้างสรรค์

1. **แยก "ไอเดีย" ออกจาก "ตัวตน" ของคนเสนอ** — Tech Lead ต้องตั้งกฎในทีมว่าการวิจารณ์ไอเดียไม่ใช่การวิจารณ์ตัวบุคคล และต้องเป็นแบบอย่างเรื่องนี้ด้วยตัวเองก่อนเสมอ
2. **ใช้ข้อมูลและการทดลองแทนการเถียงด้วยความเห็น** — เมื่อสองฝ่ายเห็นต่างเรื่อง workflow ให้เสนอ pilot เล็ก ๆ เทียบกันด้วยข้อมูลจริง (เช่นเดียวกับหลักการใน Step 984) แทนที่จะเถียงกันด้วยความเชื่อส่วนตัว
3. **ใช้กระบวนการ RFC เป็นเวทีถกเถียงอย่างเป็นทางการ** — ตามที่เรียนใน Part 90 การเขียน RFC บังคับให้ทุกฝ่ายต้องเขียนเหตุผลออกมาเป็นลายลักษณ์อักษร ซึ่งช่วยลดอคติทางอารมณ์ในการถกเถียงแบบปากเปล่า
4. **กำหนดกรอบเวลาการตัดสินใจ (timebox)** — ความขัดแย้งที่ยืดเยื้อไม่มีที่สิ้นสุดสร้างความเสียหายมากกว่าการตัดสินใจที่ไม่สมบูรณ์แบบแต่ทันเวลา
5. **ใช้หลักการ "Disagree and Commit"** — หลักการที่ Amazon ใช้อย่างเป็นทางการ: เมื่อถกเถียงกันอย่างเต็มที่แล้วแต่ยังไม่ได้ข้อสรุปเป็นเอกฉันท์ ทีมต้องเลือกทางใดทางหนึ่งและ **ทุกคนต้องสนับสนุนการตัดสินใจนั้นอย่างเต็มที่** แม้จะไม่ใช่ทางเลือกที่ตัวเองชอบที่สุด

### 988.3 บทบาทของ Tech Lead เมื่อถกเถียงกันไม่จบ

เมื่อทีมถกเถียงกันอย่างมีเหตุผลเต็มที่แล้วแต่ยังไม่สามารถหาข้อสรุปร่วมกันได้ Tech Lead มีหน้าที่เป็น **ผู้ตัดสินใจสุดท้าย (tie-breaker)** ซึ่งต้องทำอย่างมีชั้นเชิง:

- **รับฟังทุกฝ่ายอย่างเท่าเทียมก่อนตัดสินใจ** — อย่าตัดสินใจก่อนฟังครบทุกมุมมอง
- **อธิบายเหตุผลของการตัดสินใจอย่างชัดเจนเสมอ** — แม้ฝ่ายที่ไม่ได้รับเลือกจะไม่เห็นด้วย แต่ต้องเข้าใจว่าทำไมถึงตัดสินใจแบบนั้น
- **บันทึกการตัดสินใจไว้เป็นลายลักษณ์อักษรผ่าน ADR** — เพื่อให้ตรวจสอบย้อนหลังได้ และเป็นหลักฐานว่ากระบวนการตัดสินใจโปร่งใส (เชื่อมโยงไปยัง Step 990)
- **ไม่ลงโทษหรือมองข้ามฝ่ายที่ไม่ได้รับเลือกในอนาคต** — เพื่อรักษาความไว้วางใจในการถกเถียงครั้งต่อไป

### 988.4 สัญญาณอันตรายที่ Tech Lead ต้องเข้าไปแทรกแซงทันที

- การถกเถียงเปลี่ยนจาก "เรื่องงาน" เป็น "เรื่องส่วนตัว" (personal attack)
- ฝ่ายใดฝ่ายหนึ่งเริ่มเงียบและถอนตัวจากการมีส่วนร่วม (silent disengagement) — อันตรายกว่าการเถียงเสียงดัง เพราะสะสมความไม่พอใจโดยไม่แสดงออก
- การถกเถียงเดิมถูกหยิบยกขึ้นมาซ้ำ ๆ ทุกครั้งที่มีโอกาส แม้จะตัดสินใจไปแล้ว (relitigating decisions)

> **หลักการสำคัญ:** ความขัดแย้งทางเทคนิคที่จัดการดีคือสัญญาณของทีมที่แข็งแรง เพราะแสดงว่าทุกคนใส่ใจกับคุณภาพงานมากพอที่จะถกเถียง — หน้าที่ของ Tech Lead ไม่ใช่กำจัดความขัดแย้ง แต่คือ **ออกแบบกระบวนการที่ทำให้ความขัดแย้งนำไปสู่การตัดสินใจที่ดีขึ้น แล้วจบลงด้วยความเคารพซึ่งกันและกัน**

### 988.5 ตัวอย่างสถานการณ์จริง: เมื่อ Senior Engineer สองคนเถียงกันไม่จบ

**สถานการณ์:** Engineer A ยืนยันว่าทีมควรใช้ **Monorepo** เพื่อให้ refactor ข้ามบริการง่ายขึ้น ส่วน Engineer B ยืนยันว่าควรใช้ **Polyrepo** เพื่อให้แต่ละทีม deploy อิสระจากกัน (อ้างอิงเนื้อหาจาก Part 82) ทั้งคู่ถกเถียงกันในที่ประชุมมาสองรอบแล้วยังไม่ได้ข้อสรุป และเริ่มมีน้ำเสียงไม่พอใจกันในแชทของทีม

**สิ่งที่ Tech Lead ควรทำ:**

1. **หยุดการถกเถียงในแชท/ที่ประชุมแบบไม่มีโครงสร้างทันที** เพราะการเถียงแบบปากเปล่าซ้ำ ๆ มักวนซ้ำประเด็นเดิมและสะสมอารมณ์
2. **ขอให้ทั้งสองฝ่ายเขียน RFC สั้น ๆ คนละฉบับ** ระบุข้อดี ข้อเสีย และเงื่อนไขที่แนวทางของตัวเองจะไม่เหมาะ (บังคับให้แต่ละฝ่ายคิดถึงจุดอ่อนของตัวเองด้วย)
3. **นัดประชุมครั้งเดียวแบบมี timebox ชัดเจน (เช่น 45 นาที)** ให้แต่ละฝ่ายนำเสนอ แล้วเปิดให้ทีมอื่นถามคำถาม
4. **ถ้ายังไม่ได้ข้อสรุปหลังจากนั้น Tech Lead ตัดสินใจเองโดยอ้างอิงบริบทจริงของทีม** เช่น ถ้าทีมมี deployment lifecycle ต่างกันชัดเจนระหว่างบริการ (ตามหลักการใน Part 82) จึงเลือก Polyrepo และอธิบายเหตุผลนี้ให้ทั้งสองฝ่ายฟังอย่างตรงไปตรงมา
5. **บันทึกผลเป็น ADR** เพื่อไม่ให้ประเด็นนี้ถูกหยิบมาเถียงซ้ำในอีก 3 เดือนข้างหน้าโดยไม่มีข้อมูลใหม่

ผลลัพธ์ที่ดีของสถานการณ์นี้ไม่ใช่ "ทุกคนเห็นด้วย 100%" แต่คือ **ทั้งสองฝ่ายรู้สึกว่าความเห็นของตัวเองถูกรับฟังอย่างจริงจัง แม้จะไม่ใช่ฝ่ายที่ถูกเลือก** และยังคงทำงานร่วมกันต่อไปได้อย่างมืออาชีพ

## Step 989: การวางแผนระยะยาว (Technical Roadmap) ที่รวม Git/DevOps Practice เข้ากับกลยุทธ์องค์กร

ทักษะสุดท้ายก่อนแบบฝึกหัดปิดท้าย คือความสามารถในการมองภาพระยะยาว — Tech Lead ที่ดีไม่ได้แก้ปัญหาแค่ sprint ต่อ sprint แต่ต้องมี **แผนที่เชื่อมโยง Git/DevOps practice เข้ากับเป้าหมายทางธุรกิจในระยะ 1–3 ปีข้างหน้า**

### 989.1 ทำไม Git/DevOps Practice ต้องอยู่ใน Technical Roadmap

หลายองค์กรมองว่าการปรับปรุง workflow, CI/CD, หรือ security practice เป็นแค่ "งานเสริม" ที่ทำเมื่อมีเวลาว่าง แต่ Tech Lead ที่มีวิสัยทัศน์ต้องเข้าใจว่า **ความสามารถด้าน Software Delivery (ตามที่วัดด้วย DORA Metrics ใน Part 92) คือความได้เปรียบทางการแข่งขันโดยตรง** องค์กรที่ deploy ได้เร็วและปลอดภัยกว่า จะตอบสนองต่อตลาดได้เร็วกว่าคู่แข่งเสมอ

### 989.2 การใช้ Maturity Model เป็นเข็มทิศ

Tech Lead ควรประเมินระดับความสมบูรณ์ (maturity) ของทีมตนเองในแต่ละมิติ แล้ววางแผนยกระดับอย่างเป็นระบบ:

| มิติ | ระดับ Ad-hoc | ระดับ Developing | ระดับ Mature | ระดับ Elite |
|---|---|---|---|---|
| **Workflow** | ไม่มีมาตรฐาน ต่างคนต่างทำ | มี workflow เอกสารแต่ไม่บังคับใช้จริง | มี workflow ที่บังคับใช้ผ่าน branch protection | Workflow เบา เร็ว พร้อม feature flag รองรับ |
| **CI/CD** | Manual deploy | CI พื้นฐาน มนุษย์ต้องกด deploy | CI/CD อัตโนมัติเต็มรูปแบบ | Continuous Deployment พร้อม automated rollback |
| **Security** | ไม่มีมาตรการชัดเจน | มี policy เอกสารแต่ยังพึ่งมนุษย์ตรวจ | มี automated scanning ในบาง pipeline | Security-as-Code ครบทุก pipeline (Part 76–85) |
| **Documentation** | ความรู้อยู่ในหัวคนเท่านั้น | มี README บางส่วน | มี RFC/ADR อย่างสม่ำเสมอ | Documentation-as-Code ครบทุก repository |

### 989.3 การเขียน Roadmap ที่เชื่อมโยงกับเป้าหมายธุรกิจ

Roadmap ที่ดีไม่ใช่แค่รายการ "สิ่งที่อยากทำทางเทคนิค" แต่ต้องตอบคำถามธุรกิจให้ได้เสมอว่า **"ทำไมสิ่งนี้ต้องอยู่ในไตรมาสนี้ และมันช่วยเป้าหมายธุรกิจอะไร"**

ตัวอย่างการเขียน OKR (Objectives and Key Results) ที่เชื่อมโยง Git/DevOps practice กับธุรกิจ:

```
Objective: ลดความเสี่ยงด้าน Security ที่อาจกระทบการขยายตลาดสู่ลูกค้าองค์กร (Enterprise)

Key Result 1: บังคับใช้ Signed Commits และ Branch Protection ครบ
              100% ของ repository ระดับ Critical ภายใน Q2

Key Result 2: ผ่านการตรวจสอบ SOC 2 Type II ด้าน Audit Trail
              ของ Source Code Management ภายใน Q3

Key Result 3: ลดเวลาตอบสนองต่อช่องโหว่ security ระดับ Critical
              จาก 14 วัน เหลือไม่เกิน 3 วัน ผ่าน automated
              dependency scanning (Part 80)
```

จะเห็นว่า Objective เชื่อมกับเป้าหมายธุรกิจ (ขยายตลาดสู่ enterprise) โดยตรง ไม่ใช่แค่ "อยากทำเรื่อง security ให้ดีขึ้น" ลอย ๆ

### 989.4 การจัดสรรเวลาระหว่างงานใหม่กับการชำระหนี้ทางเทคนิค

Tech Lead ต้องต่อรองกับผู้บริหารเรื่องสัดส่วนเวลาที่ทีมใช้ไปกับ feature ใหม่เทียบกับการปรับปรุง infrastructure/process โดยพื้นฐาน แนวทางที่หลายองค์กรใช้ได้ผลจริงคือการกำหนดสัดส่วนคงที่ล่วงหน้า เช่น จัดสรร 70–80% ของเวลาให้ feature งานตามธุรกิจ และ 20–30% ให้การลงทุนด้าน engineering practice/infrastructure อย่างต่อเนื่องทุก sprint แทนที่จะรอให้ปัญหาสะสมจนวิกฤตแล้วค่อยขอเวลาพิเศษ

### 989.5 การทบทวนและปรับ Roadmap อย่างสม่ำเสมอ

Roadmap ที่ดีไม่ใช่เอกสารที่เขียนครั้งเดียวแล้วจบ Tech Lead ควรทบทวนทุกไตรมาสโดยถามคำถามเหล่านี้:

- เป้าหมายทางธุรกิจเปลี่ยนไปหรือไม่ (เช่น บริษัทเปลี่ยนกลยุทธ์จากขยายตลาดไปเป็นลดต้นทุน)
- Maturity ของทีมในแต่ละมิติขยับไปถึงไหนแล้วเทียบกับแผนที่วางไว้
- มีเทคโนโลยีหรือแนวปฏิบัติใหม่ในอุตสาหกรรมที่ควรนำมาพิจารณาหรือไม่
- มี technical debt สะสมใหม่ที่ต้องเพิ่มเข้าไปใน roadmap หรือไม่

> **หลักการสำคัญ:** Technical Roadmap ที่ดีคือสะพานเชื่อมระหว่าง "งานประจำวันของทีมวิศวกรรม" กับ "ทิศทางเชิงกลยุทธ์ขององค์กร" — Tech Lead คือคนเดียวในองค์กรที่ยืนอยู่ตรงกลางสะพานนี้ได้ดีที่สุด เพราะเข้าใจทั้งสองฝั่งอย่างลึกซึ้ง

### 989.6 ตัวอย่าง Technical Roadmap เต็มปีที่รวม Git/DevOps Practice

| ไตรมาส | เป้าหมายหลัก | ความเชื่อมโยงกับธุรกิจ |
|---|---|---|
| **Q1** | ยกระดับ test coverage จาก 60% เป็น 75% ในบริการหลัก | ลดความเสี่ยง production incident ก่อนเข้าสู่ช่วงขยายตลาด |
| **Q2** | Pilot Trunk-Based Development กับ 2 ทีมที่พร้อมที่สุด | ลด lead time เพื่อตอบสนองต่อ feedback ลูกค้าเร็วขึ้น |
| **Q3** | บังคับใช้ Signed Commit และ Automated Dependency Scanning ทุก repository ระดับ Critical | เตรียมความพร้อมสำหรับการตรวจสอบ SOC 2 / ISO 27001 |
| **Q4** | ขยาย Trunk-Based Development สู่ทุกทีมที่ผ่านเกณฑ์ พร้อมเปิดใช้ Internal Developer Platform | รองรับการขยายทีมวิศวกรรมในปีถัดไปโดยไม่เพิ่ม operational overhead ตามสัดส่วน |

Roadmap ลักษณะนี้แสดงให้ทั้งทีมวิศวกรรมและผู้บริหารเห็นภาพเดียวกันว่า **การลงทุนด้าน Git/DevOps practice ในแต่ละไตรมาสไม่ใช่งาน "แถม" แต่คือรากฐานที่รองรับเป้าหมายทางธุรกิจของไตรมาสถัดไปเสมอ**

## Step 990: แบบฝึกหัด — เขียน Technical Decision Document (ADR) สำหรับเปลี่ยน Git Workflow ขององค์กรสมมติ

ถึงเวลาสังเคราะห์ทุกอย่างที่เรียนมาใน Part นี้ให้กลายเป็นผลงานจริงชิ้นหนึ่ง — การเขียน **ADR (Architecture Decision Record)** ที่เรียนหลักการไว้แล้วใน **Part 90 (Step 899)** สำหรับการตัดสินใจเปลี่ยน Git Workflow ระดับองค์กร

### 990.1 โจทย์สถานการณ์สมมติ

คุณเป็น Tech Lead ของบริษัท **"FinNova"** บริษัท fintech ขนาดกลางที่มีทีมวิศวกรรม 12 ทีม รวมพนักงาน 90 คน สถานการณ์ปัจจุบันมีดังนี้:

- ปัจจุบันทุกทีมใช้ **Git Flow** มาตั้งแต่ก่อตั้งบริษัท 5 ปีก่อน
- Release เข้าสู่ production ทุก 2 สัปดาห์ผ่าน release branch ที่ QA ต้องทดสอบเต็มรูปแบบก่อนเสมอ
- ทีม engineering บ่นบ่อยครั้งว่า merge conflict ระหว่าง `develop` กับ `release` branch เกิดขึ้นบ่อยมาก และ hotfix ต้องแก้ทั้งใน `main`, `develop`, และ `release` พร้อมกันทุกครั้ง ทำให้เกิดความผิดพลาดซ้ำ ๆ
- ทีม Product ต้องการให้ deploy ฟีเจอร์ใหม่ได้เร็วขึ้นเพื่อแข่งขันกับคู่แข่งที่ deploy ทุกวัน
- บริษัทอยู่ระหว่างเตรียมสอบ **SOC 2 Type II** ซึ่งต้องมี audit trail และ approval process ที่ตรวจสอบย้อนหลังได้ชัดเจน (เชื่อมโยง Part 81)
- ทีม engineering มี automated test coverage เฉลี่ยประมาณ 65% และกำลังปรับปรุงอย่างต่อเนื่อง

ทีม engineering ส่วนหนึ่งเสนอให้เปลี่ยนไปใช้ **Trunk-Based Development พร้อม Feature Flag** เต็มรูปแบบ แต่อีกส่วนกังวลว่าจะกระทบต่อ compliance และความเสี่ยงจาก test coverage ที่ยังไม่ถึง 80%

### 990.2 โจทย์ของแบบฝึกหัด

ให้คุณเขียน **ADR ฉบับเต็ม** โดยใช้ template มาตรฐานจาก Part 90 ที่ต้องมีหัวข้อครบถ้วนดังนี้: **Status, Context, Decision, Consequences (ทั้งด้านบวกและด้านลบ), Alternatives Considered, และ Stakeholders**

ตัวอย่างโครงร่างเริ่มต้นที่คุณควรใช้เป็นฐาน (ให้เติมเนื้อหาให้ครบถ้วนด้วยเหตุผลของตัวเองตามหลักการที่เรียนมาตลอด Part นี้):

```markdown
# ADR-042: ปรับ Git Workflow จาก Git Flow เต็มรูปแบบ
# สู่ Trunk-Based Development แบบมีเงื่อนไข (Phased Adoption)

## Status
Proposed (2026-XX-XX) — รอการอนุมัติจากคณะกรรมการเทคนิค

## Context
อธิบายสถานการณ์ปัจจุบันของ FinNova ตามโจทย์ด้านบน:
pain point ของ Git Flow ปัจจุบัน, ความต้องการทางธุรกิจ
ในการ deploy เร็วขึ้น, และข้อจำกัดด้าน compliance (SOC 2)
และ test coverage ที่ยังไม่ถึงเกณฑ์ที่ปลอดภัยสำหรับ TBD เต็มรูปแบบ

## Decision
ระบุการตัดสินใจที่ชัดเจน เช่น: นำ Trunk-Based Development
มาใช้แบบ phased adoption โดยเริ่ม pilot กับ 2 ทีมที่มี test
coverage สูงที่สุดก่อน ควบคู่กับการลงทุนเพิ่ม test coverage
ให้ถึง 80% ก่อนขยายผลเต็มองค์กร พร้อมคง mandatory approval
gate สำหรับ repository ที่เกี่ยวข้องกับ compliance โดยตรง

## Consequences
### ผลด้านบวกที่คาดหวัง
- ลด merge conflict และความผิดพลาดจาก hotfix ที่ต้องแก้หลาย branch
- ลด lead time จากไอเดียถึง production
- ตอบสนองต่อคู่แข่งได้เร็วขึ้น

### ผลด้านลบ/ความเสี่ยงที่ต้องยอมรับ
- ทีมต้องลงทุนเวลาเพิ่ม test coverage ก่อนขยายผลเต็มองค์กร
- ต้องมีการ training และ change management ระยะเวลา X เดือน
- ความเสี่ยงชั่วคราวระหว่างช่วง pilot ที่ 2 ทีมใช้ workflow
  ต่างกับอีก 10 ทีม

## Alternatives Considered
1. คง Git Flow ไว้เหมือนเดิม — ไม่แก้ pain point ที่มีอยู่
2. เปลี่ยนไป GitHub Flow แทน TBD — ลดความซับซ้อนกว่า Git Flow
   แต่ยังไม่ตอบโจทย์ความเร็วสูงสุดที่ Product ต้องการ
3. เปลี่ยนไป TBD เต็มรูปแบบทันทีทั้งองค์กร — เสี่ยงเกินไป
   เมื่อพิจารณา test coverage ปัจจุบันและกำหนดสอบ SOC 2

## Stakeholders
- Engineering teams (ผู้ปฏิบัติตาม workflow ใหม่)
- QA team (ต้องปรับกระบวนการทดสอบ)
- Compliance/Security team (ต้องอนุมัติเรื่อง audit trail)
- Product team (ผู้ได้รับประโยชน์จากความเร็วที่เพิ่มขึ้น)
```

### 990.3 ข้อกำหนดของแบบฝึกหัด

ให้คุณเติมเนื้อหาในทุกหัวข้อของ ADR ข้างต้นให้สมบูรณ์ด้วยตัวเอง โดยต้อง:

1. **เชื่อมโยงเหตุผลกับ Decision Framework ใน Step 982** — อธิบายว่าทำไมถึงเลือก phased adoption แทนการเปลี่ยนทันที
2. **ใช้หลักการ Risk-Tiered Approach จาก Step 983** — ระบุชัดเจนว่า repository ประเภทไหนยังต้องคง mandatory approval ไว้ และประเภทไหนใช้ TBD ได้เต็มรูปแบบ
3. **ออกแบบแผน Change Management ตาม Step 984** — ระบุ timeline การทำ pilot, การเก็บ feedback, และเงื่อนไขที่จะขยายผลหรือถอยกลับ
4. **เขียน Executive Summary แยกต่างหาก 1 ย่อหน้า ตามหลักการ Step 985** — สำหรับนำเสนอต่อ CEO/CFO ที่ไม่ใช่สายเทคนิค โดยเน้นผลกระทบทางธุรกิจ ไม่ใช่รายละเอียดทางเทคนิค
5. **ระบุว่าจะรับมือกับความเห็นต่างระหว่างทีมที่อยากเปลี่ยนกับทีมที่กังวลอย่างไร ตามหลักการ Step 988**

### 990.4 เกณฑ์การประเมินตัวเอง (Self-check)

ตรวจสอบ ADR ที่คุณเขียนด้วยคำถามเหล่านี้:

- [ ] Context อธิบายปัญหาปัจจุบันด้วยข้อมูลที่จับต้องได้ ไม่ใช่แค่ความรู้สึกทั่วไป
- [ ] Decision ระบุชัดเจนว่า "ทำอะไร" ไม่คลุมเครือ และมีเงื่อนไข/ขอบเขตที่ชัดเจน
- [ ] Consequences ระบุทั้งผลด้านบวกและด้านลบอย่างตรงไปตรงมา ไม่ปิดบังความเสี่ยง
- [ ] Alternatives Considered มีอย่างน้อย 2 ทางเลือกอื่นพร้อมเหตุผลที่ไม่เลือก
- [ ] มี Executive Summary ที่ผู้บริหารที่ไม่ใช่สายเทคนิคอ่านแล้วเข้าใจภายใน 1 นาที
- [ ] แผน rollout มีจุดตรวจสอบ (checkpoint) ที่ชัดเจนว่าจะขยายผลต่อหรือถอยกลับเมื่อไหร่
- [ ] ระบุ Stakeholders ครบทุกฝ่ายที่ได้รับผลกระทบ ไม่ตกหล่นทีมไหน
- [ ] เอกสารนี้พร้อมเก็บไว้ใน Git repository (`docs/adr/`) เพื่อตรวจสอบย้อนหลังได้ตลอดไปตามหลักการใน Part 90

### 990.5 ต่อยอดแบบฝึกหัด (สำหรับผู้ที่ต้องการฝึกฝนเพิ่มเติม)

หากต้องการฝึกฝนให้ลึกยิ่งขึ้น ลองจำลองสถานการณ์ต่อไปนี้เพิ่มเติม:

1. เขียน **สไลด์นำเสนอ 3 หน้า** สำหรับนำเสนอ ADR นี้ต่อคณะกรรมการบริหาร โดยใช้เฉพาะภาษาธุรกิจล้วน ไม่มีศัพท์เทคนิคเลยแม้แต่คำเดียว
2. จำลองบทสนทนาที่ Senior Engineer ในทีมคัดค้านการเปลี่ยนแปลงนี้อย่างรุนแรง แล้วเขียนว่าคุณจะตอบสนองอย่างไรตามหลักการใน Step 988
3. เขียน ADR ฉบับที่สอง ที่ **สมมติว่าผ่านไป 8 เดือนแล้วพบว่า TBD ไม่เหมาะกับทีม Compliance** ให้เขียน ADR ใหม่ที่ระบุว่า **"Supersedes ADR-042"** บางส่วน ตามหลักการ immutable ADR ที่เรียนใน Part 90

## สรุป Part 99

ใน Part นี้เราได้สังเคราะห์ทักษะทั้งหมดของหลักสูตร Git/GitHub/GitLab เกือบ 1,000 Step ให้กลายเป็นความสามารถระดับผู้นำทางเทคนิค:

1. **Tech Lead ต่างจาก Senior Engineer** ตรงขอบเขตของผลกระทบจากการตัดสินใจ — ไม่ใช่แค่โค้ดของตัวเอง แต่คือทิศทางของทั้งทีม การเติบโตของคน และความสอดคล้องกับธุรกิจ
2. **การเลือก Git Workflow** ต้องอิงบริบทของทีม (ขนาด, ความถี่ deploy, ความแข็งแรงของ CI, ข้อกำหนด compliance) ไม่ใช่กระแสนิยม — ไม่มี Workflow ใดถูกต้องที่สุดในตัวเอง
3. **ความเร็วกับความปลอดภัยไม่ใช่ trade-off โดยธรรมชาติ** — ศัตรูตัวจริงคือกระบวนการที่ยังทำด้วยมือ การลงทุนทำ automation และการจัดระดับความเสี่ยง (risk-tiered approach) ทำให้ได้ทั้งสองอย่างพร้อมกัน
4. **การนำการเปลี่ยนแปลงที่ดี** ต้องมี pilot, การรับฟัง feedback, และแผน rollback เสมอ — แรงต้านมักมาจากความกลัวและประสบการณ์แย่ในอดีต ไม่ใช่จากไอเดียที่ไม่ดี
5. **การสื่อสารกับผู้บริหาร** ต้องแปลภาษาเทคนิคเป็นภาษาธุรกิจเสมอ ใช้โครงสร้าง Situation-Complication-Resolution และเน้นตัวเลขที่จับต้องได้
6. **วัฒนธรรมวิศวกรรมที่ดี** ถูกสร้างจากพฤติกรรมประจำวันใน Git — commit message, code review, การให้เครดิต — ไม่ใช่จากนโยบายที่เขียนไว้เฉย ๆ
7. **การ Mentor ที่แท้จริง** คือการสอนแนวคิด (mental model) ไม่ใช่การท่องจำคำสั่ง — นี่คือปรัชญาที่ยึดโยงหลักสูตรนี้ตั้งแต่ Step 1 ถึง Step 990
8. **ความขัดแย้งทางเทคนิคที่จัดการดี** คือสัญญาณของทีมที่แข็งแรง ใช้ข้อมูล การทดลอง RFC และหลักการ "Disagree and Commit" แทนการเถียงด้วยอารมณ์
9. **Technical Roadmap ที่ดี** เชื่อมโยง Git/DevOps practice เข้ากับเป้าหมายธุรกิจโดยตรง ผ่าน Maturity Model และ OKR ที่วัดผลได้จริง
10. **ADR** คือเครื่องมือสำคัญที่สุดในการบันทึกและสื่อสารการตัดสินใจเชิงกลยุทธ์อย่างโปร่งใสและตรวจสอบย้อนหลังได้ตลอดไป
