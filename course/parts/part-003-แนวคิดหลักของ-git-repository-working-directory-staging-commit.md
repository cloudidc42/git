## Step 21: Repository คืออะไร — เจาะโครงสร้างโฟลเดอร์ `.git`

### Repository คืออะไรกันแน่

**Repository (repo)** ในความหมายของ Git คือ **โฟลเดอร์โปรเจกต์ที่ Git กำลัง "เฝ้าติดตาม" (track) การเปลี่ยนแปลงอยู่** พูดให้แม่นยำกว่านั้นคือ:

> Repository = โฟลเดอร์โปรเจกต์ปกติ **บวกกับ** โฟลเดอร์ซ่อนชื่อ `.git` ที่เก็บประวัติ, metadata และข้อมูลทั้งหมดที่ทำให้ Git รู้จักโปรเจกต์นี้

สิ่งสำคัญที่ต้องเข้าใจให้แม่นคือ **Repository ไม่ใช่ "เซิร์ฟเวอร์" หรือ "เว็บไซต์"** อย่างที่มือใหม่มักเข้าใจผิดจากการได้ยินคำว่า "GitHub repository" มาก่อน ในบริบทของ Git ล้วน ๆ (ไม่พึ่ง GitHub/GitLab) repository คือ **โฟลเดอร์บนเครื่องของคุณเอง** นี่แหละ

### ความแตกต่างระหว่าง "โปรเจกต์ธรรมดา" กับ "Git repository"

| | โปรเจกต์ธรรมดา (ไม่มี Git) | Git Repository |
|---|---|---|
| มีโฟลเดอร์ `.git` ไหม | ไม่มี | มี |
| Git รู้จักไฟล์ในนี้ไหม | ไม่รู้จักเลย | รู้จักและติดตามการเปลี่ยนแปลงได้ |
| มีประวัติการแก้ไขไหม | ไม่มี | มี (เก็บใน `.git`) |
| รันคำสั่ง `git status`, `git log` ได้ไหม | ไม่ได้ (error) | ได้ |
| ย้อนกลับเวอร์ชันเก่าได้ไหม | ไม่ได้ | ได้ |

การเปลี่ยน "โปรเจกต์ธรรมดา" ให้กลายเป็น "Git repository" ทำได้ด้วยคำสั่งเดียวคือ `git init` (จะเรียนละเอียดใน Part 04) ซึ่งจริง ๆ แล้วสิ่งที่คำสั่งนี้ทำก็แค่ **สร้างโฟลเดอร์ `.git` ขึ้นมา** เท่านั้นเอง ไม่มีอะไรมากไปกว่านั้น

```
ก่อน git init                        หลัง git init
project/                             project/
├── index.html                       ├── .git/          ← โฟลเดอร์ใหม่ที่ถูกสร้างขึ้น
├── style.css                        ├── index.html
└── app.js                           ├── style.css
                                      └── app.js

(ไม่ใช่ Git repository)              (เป็น Git repository แล้ว!)
```

ข้อสังเกตสำคัญ: **การลบโฟลเดอร์ `.git` ออกไปเท่ากับลบประวัติทั้งหมดของโปรเจกต์ทิ้ง** โดยที่ไฟล์งานจริง (working directory) จะยังอยู่ครบ แต่จะกลายเป็น "โปรเจกต์ธรรมดา" ที่ไม่มีประวัติทันที ดังนั้นห้ามลบโฟลเดอร์นี้โดยรู้เท่าไม่ถึงการณ์เด็ดขาด

### เจาะโครงสร้างภายใน `.git`

มาดูกันว่าเมื่อสร้าง repository ใหม่ ๆ ด้วย `git init` แล้ว โฟลเดอร์ `.git` มีอะไรอยู่ข้างในบ้าง:

```bash
git init my-project
cd my-project
ls -la .git
```

ผลลัพธ์โดยประมาณ:

```
.git/
├── HEAD                 # ไฟล์ข้อความสั้น ๆ ชี้ว่าตอนนี้อยู่ branch ไหน
├── config               # ค่าตั้งค่าเฉพาะของ repo นี้ (ไม่ใช่ค่า global)
├── description          # ใช้โดยโปรแกรมเก่าอย่าง gitweb เท่านั้น ไม่สำคัญกับงานทั่วไป
├── hooks/                # สคริปต์ที่รันอัตโนมัติเมื่อเกิดเหตุการณ์บางอย่าง (เช่น ก่อน commit)
├── info/                 # เก็บไฟล์ exclude เพิ่มเติม (คล้าย .gitignore แต่ไม่ commit)
├── objects/              # "คลังข้อมูลจริง" ของ Git — เก็บ blob, tree, commit ทุกตัว
└── refs/                 # เก็บตัวชี้ (pointer) ไปยัง commit เช่น branch, tag
    ├── heads/            # ตัวชี้ของ branch ต่าง ๆ
    └── tags/             # ตัวชี้ของ tag ต่าง ๆ
```

อธิบายทีละส่วนที่สำคัญที่สุด:

**`HEAD`** — เป็นไฟล์ข้อความธรรมดา (plain text) เปิดดูได้ด้วย `cat .git/HEAD` เนื้อหาปกติจะเป็นแบบนี้:

```
ref: refs/heads/main
```

แปลว่า "ตอนนี้ฉันกำลังอยู่ที่ branch ชื่อ `main`" — HEAD คือตัวชี้ว่า "คุณกำลังยืนอยู่ตรงไหนในประวัติของโปรเจกต์" เราจะพูดถึง HEAD อย่างละเอียดใน Step 26

**`config`** — เก็บการตั้งค่าที่ใช้เฉพาะกับ repository นี้เท่านั้น เช่น remote URL, branch ที่ track อยู่ ต่างจากค่า `--global` ที่ตั้งครั้งเดียวใช้ได้ทุก repo (ที่เคยตั้งไปแล้วใน Part 02 ตอนตั้งค่า `user.name` / `user.email`)

**`objects/`** — นี่คือ **หัวใจที่แท้จริงของ Git** ทุกอย่างที่คุณเคย commit — เนื้อหาไฟล์ทุกเวอร์ชัน, โครงสร้างโฟลเดอร์ทุกสถานะ, ข้อมูล commit ทุกอัน — ถูกเก็บไว้ในนี้ทั้งหมดในรูปแบบที่เรียกว่า **Git Objects** (จะอธิบายใน Step 27) แต่ละ object ถูกบีบอัด (compress) และตั้งชื่อไฟล์ด้วยค่า hash ของมันเอง

**`refs/`** — เก็บ "ตัวชี้" ไปยัง commit ต่าง ๆ ในรูปของไฟล์เล็ก ๆ ที่ข้างในมีแค่ hash หนึ่งบรรทัด เช่น `refs/heads/main` คือไฟล์ที่บอกว่า branch `main` ตอนนี้ชี้ไปที่ commit ไหน

**`hooks/`** — เมื่อสร้าง repo ใหม่ Git จะใส่ไฟล์ตัวอย่าง (`.sample`) ไว้ให้หลายไฟล์ เช่น `pre-commit.sample`, `pre-push.sample` ถ้าเราเอานามสกุล `.sample` ออกและใส่โค้ดเข้าไป มันจะกลายเป็นสคริปต์ที่รันอัตโนมัติในจังหวะนั้น ๆ (เราจะเรียนเรื่อง Git Hooks แบบละเอียดในเฟสหลัง ๆ ของหลักสูตร)

> **ข้อควรระวัง:** ห้ามเข้าไปแก้ไขไฟล์ใน `.git/objects/` ด้วยมือเด็ดขาด เพราะมันถูกออกแบบให้ Git จัดการเองเท่านั้น การแก้ไขตรง ๆ อาจทำให้ repository เสียหายจนกู้คืนไม่ได้ ไฟล์ในโฟลเดอร์นี้ที่ปลอดภัยที่จะแก้ด้วยมือ (ในกรณีพิเศษที่รู้ตัวว่ากำลังทำอะไรอยู่) มีแค่ `config`, `HEAD` และไฟล์ text ใน `hooks/`, `info/` เท่านั้น

## Step 22: The Three States ของ Git — Modified, Staged, Committed

นี่คือแนวคิดที่ถูกยกมาอธิบายในเอกสารทางการของ Git เองว่าเป็นสิ่งแรกที่ต้องเข้าใจก่อนเรียนคำสั่งใด ๆ ทั้งสิ้น เพราะคำสั่งเกือบทุกตัวใน Git คือการ "ย้ายไฟล์ไปมาระหว่าง 3 สถานะนี้"

### สามสถานะของไฟล์ในสายตา Git

ไฟล์ทุกไฟล์ที่ Git ติดตามอยู่ จะอยู่ในหนึ่งในสามสถานะนี้เสมอ:

| สถานะ | ความหมาย |
|---|---|
| **Modified (แก้ไขแล้ว)** | ไฟล์ถูกแก้ไขแล้ว แต่ยัง **ไม่ได้** บอก Git ว่าจะเอาการแก้ไขนี้ไปเก็บใน commit ถัดไป |
| **Staged (พร้อม commit)** | ไฟล์ที่แก้ไข (หรือไฟล์ใหม่) ถูก "ทำเครื่องหมาย" ไว้แล้วว่าจะเอาไปรวมใน commit ถัดไปแน่นอน |
| **Committed (บันทึกแล้ว)** | ข้อมูลถูกเก็บลง database ของ Git (`.git/objects/`) อย่างปลอดภัยเรียบร้อยแล้ว |

### ไดอะแกรมแสดงความสัมพันธ์ของ Three States กับพื้นที่ทำงาน 3 แห่ง

แต่ละสถานะจะสัมพันธ์กับ "พื้นที่" (area) หนึ่งแห่งในระบบของ Git เสมอ:

```
┌─────────────────────┐     git add      ┌─────────────────┐     git commit    ┌──────────────────┐
│  Working Directory   │ ───────────────▶ │  Staging Area    │ ────────────────▶ │  .git directory   │
│  (ไฟล์จริงบนดิสก์)    │                  │  (Index)         │                   │  (Repository)     │
│                      │                  │                  │                   │                   │
│  สถานะ: Modified     │                  │  สถานะ: Staged   │                   │  สถานะ: Committed  │
└─────────────────────┘                  └─────────────────┘                   └──────────────────┘
        ▲                                                                                │
        │                          git checkout / git restore (ดึงกลับมาดู)                │
        └────────────────────────────────────────────────────────────────────────────────┘
```

อธิบายเป็นเรื่องราว (workflow ทั่วไปที่คุณจะทำซ้ำ ๆ ตลอดหลักสูตรนี้):

1. คุณเปิดไฟล์ `app.js` แล้วแก้โค้ดบางบรรทัด → ตอนนี้ไฟล์อยู่ในสถานะ **Modified** (แก้ไขแล้วในพื้นที่ Working Directory แต่ Git ยังไม่รู้ว่าคุณจะเก็บมันไว้จริงไหม)
2. คุณรันคำสั่ง `git add app.js` → ไฟล์ถูกย้ายไปอยู่ในสถานะ **Staged** (บอก Git แล้วว่า "การแก้ไขนี้ ฉันจะเอาไปเก็บใน commit ถัดไปแน่นอน")
3. คุณรันคำสั่ง `git commit -m "แก้บั๊ก login"` → ข้อมูลที่ staged ไว้ทั้งหมดถูกห่อรวมเป็น commit หนึ่งก้อน และถูกเก็บลง `.git/objects/` อย่างถาวร → ตอนนี้ไฟล์อยู่ในสถานะ **Committed**

### ทำไมต้องรู้ Three States

เพราะคำสั่ง Git แทบทุกตัวที่คุณจะเรียนต่อจากนี้ ล้วนแต่เป็นการ "ย้ายข้อมูลระหว่างสามสถานะนี้" ทั้งสิ้น เช่น:

- `git status` — บอกว่าตอนนี้ไฟล์ไหนอยู่สถานะไหน
- `git add` — ย้ายจาก Modified → Staged
- `git commit` — ย้ายจาก Staged → Committed
- `git restore --staged` — ย้ายจาก Staged → Modified (ถอยกลับ)
- `git diff` — ดูความต่างระหว่าง Working Directory กับ Staging Area
- `git diff --staged` — ดูความต่างระหว่าง Staging Area กับ Committed ล่าสุด

ถ้าเข้าใจภาพนี้แม่น ๆ แล้ว การเรียนคำสั่งต่าง ๆ ใน Part ถัดไปจะง่ายขึ้นมาก เพราะแทนที่จะท่องจำคำสั่งเป็นตัว ๆ คุณจะเข้าใจว่า "คำสั่งนี้ย้ายข้อมูลจากพื้นที่ไหนไปพื้นที่ไหน"

## Step 23: Working Directory คืออะไร

### นิยาม

**Working Directory** (บางครั้งเรียก **Working Tree**) คือ **โฟลเดอร์จริง ๆ ที่คุณเห็นและแก้ไขไฟล์อยู่บนเครื่องคอมพิวเตอร์ของคุณ** พูดง่าย ๆ คือไฟล์ที่คุณเปิดด้วย text editor, ไฟล์ที่คุณเห็นเวลาเปิด File Explorer / Finder นั่นเอง

```
my-project/              ← นี่คือ Working Directory ทั้งหมด (ไม่รวม .git/)
├── .git/                ← ไม่นับเป็นส่วนหนึ่งของ Working Directory (เป็นพื้นที่ของ Git เอง)
├── index.html           ← ไฟล์เหล่านี้คือ Working Directory
├── style.css
├── app.js
└── README.md
```

### จุดสำคัญที่ต้องเข้าใจ

1. **Working Directory คือ Working Directory เดียวที่ "ปรากฏ ณ ขณะปัจจุบัน"** — มันแสดงเนื้อหาของ **commit ที่คุณ checkout อยู่ ณ ตอนนี้เท่านั้น** บวกกับการแก้ไขใด ๆ ที่คุณทำเพิ่มเติมแต่ยังไม่ได้ commit
2. **Git ไม่ได้เฝ้าดู Working Directory แบบ real-time ตลอดเวลา** — Git จะไป "สแกน" ดูว่าไฟล์เปลี่ยนไปหรือไม่ก็ต่อเมื่อคุณสั่งคำสั่งบางอย่าง เช่น `git status`, `git add`, `git diff` (ไม่ใช่ background process ที่ทำงานตลอดเวลาเหมือนบางโปรแกรม)
3. **ไฟล์ใน Working Directory อาจจะยังไม่ถูก Git รู้จักเลยก็ได้** — เช่น ไฟล์ใหม่ที่คุณเพิ่งสร้าง จะถูกเรียกว่า **Untracked file** (ยังไม่เคยถูก track จะอธิบายเพิ่มใน Step 29)

### เปรียบเทียบ Working Directory กับพื้นที่อื่น

| | Working Directory | Staging Area | Repository (`.git`) |
|---|---|---|---|
| อยู่ที่ไหน | ไฟล์จริงในโฟลเดอร์โปรเจกต์ | ไฟล์ `.git/index` (ไฟล์เดียว) | โฟลเดอร์ `.git/objects/` |
| แก้ไขด้วยอะไร | Text editor / IDE ตามปกติ | คำสั่ง `git add` / `git restore --staged` | คำสั่ง `git commit` (Git จัดการให้เอง) |
| มองเห็นด้วยตาเปล่าได้ไหม | ได้ (เปิดไฟล์ดูตรง ๆ) | ไม่ได้โดยตรง (ต้องใช้ `git status`/`git diff` ดู) | ไม่ได้โดยตรง (เป็น binary object) |
| เปลี่ยนแปลงบ่อยแค่ไหน | เปลี่ยนทุกครั้งที่พิมพ์/บันทึกไฟล์ | เปลี่ยนเมื่อสั่ง `git add` เท่านั้น | เปลี่ยนเมื่อสั่ง `git commit` เท่านั้น |

พูดง่าย ๆ ในเชิงเปรียบเปรย: ถ้า repository คือ "ห้องสมุด" ที่เก็บหนังสือทุกเวอร์ชันที่เคยพิมพ์ Working Directory ก็คือ **"โต๊ะทำงานของคุณ"** ที่มีสำเนาหนังสือเล่มปัจจุบันวางอยู่ให้คุณแก้ไขได้อย่างอิสระ โดยที่การแก้ไขบนโต๊ะจะยังไม่กระทบกับหนังสือต้นฉบับในห้องสมุดจนกว่าคุณจะ "ส่งคืน" (commit) กลับไป

## Step 24: Staging Area (Index) คืออะไร ทำไม Git ต้องมีขั้นตอนนี้

### นิยาม

**Staging Area** หรือที่ Git เรียกในเชิงเทคนิคว่า **Index** คือ **พื้นที่พักไฟล์ระหว่าง Working Directory กับ Repository** ทำหน้าที่เป็น "ร่างของ commit ถัดไป" — มันคือรายการไฟล์ (พร้อมเนื้อหา ณ ขณะนั้น) ที่คุณตัดสินใจแล้วว่า **"เอาไปเก็บใน commit ถัดไปแน่นอน"**

ในทางเทคนิค Staging Area ถูกเก็บเป็นไฟล์ไบนารีไฟล์เดียวชื่อ `.git/index` ซึ่งเป็นไฟล์ binary ที่มีโครงสร้างเฉพาะ ไม่ใช่ text ธรรมดา (ห้ามเปิดแก้ไขตรง ๆ)

### ทำไม Git ต้องมีขั้นตอน Staging (ข้อดีเทียบกับ VCS ที่ commit ตรง ๆ)

VCS หลายตัว (เช่น Subversion แบบดั้งเดิม) ไม่มีแนวคิด staging area — เวลาสั่ง commit จะเป็นการเก็บ **ทุกไฟล์ที่เปลี่ยนแปลงในโปรเจกต์ทั้งหมด** ไปในคราวเดียว ซึ่งมีข้อจำกัดชัดเจน

Git เลือกออกแบบให้มีขั้นตอนพักไฟล์ตรงกลางนี้ ด้วยเหตุผลหลัก ๆ ดังนี้:

**1. เลือก commit เฉพาะบางส่วนของการเปลี่ยนแปลงได้ (Partial Commit)**

สมมติคุณแก้ไข 3 ไฟล์พร้อมกัน แต่ไฟล์หนึ่งในนั้นยังแก้ไม่เสร็จ คุณสามารถ `git add` เฉพาะ 2 ไฟล์ที่เสร็จแล้ว แล้ว commit แค่ 2 ไฟล์นั้นก่อนได้ โดยไฟล์ที่ยังไม่เสร็จจะยังคงอยู่ในสถานะ Modified รอจนกว่าจะพร้อม

```bash
# แก้ไข 3 ไฟล์: login.js (เสร็จแล้ว), payment.js (เสร็จแล้ว), experiment.js (ยังทดลองอยู่)
git add login.js payment.js
git commit -m "เพิ่มระบบ login และ payment"
# experiment.js ยังคงเป็น Modified อยู่ ไม่ถูกเก็บเข้า commit นี้
```

**2. Commit แบบละเอียด แยกเป็นก้อนเล็ก ๆ ที่มีความหมาย (Atomic Commits)**

แม้จะแก้ไฟล์เดียวกัน คุณยังสามารถใช้ `git add -p` (patch mode) เพื่อเลือก **เฉพาะบางส่วนของไฟล์เดียวกัน** ไปอยู่ใน commit หนึ่ง และเก็บส่วนที่เหลือไว้ทำ commit แยกอีกอันได้ ทำให้แต่ละ commit มีจุดประสงค์ชัดเจน อ่านประวัติย้อนหลังได้ง่าย (จะเรียนคำสั่งนี้แบบละเอียดในภายหลัง)

**3. ตรวจทานก่อน commit ได้เสมอ (Review before commit)**

Staging Area ทำหน้าที่เป็น "ด่านตรวจสอบสุดท้าย" — คุณสามารถรัน `git diff --staged` เพื่อดูว่าอะไรจะถูกบันทึกจริง ๆ ก่อนกดยืนยันด้วย `git commit` ลดโอกาสที่จะ commit สิ่งที่ไม่ตั้งใจ เช่น ไฟล์ debug, console.log ที่ลืมลบ

**4. แยกขั้นตอน "ตัดสินใจว่าจะเก็บอะไร" ออกจาก "การบันทึกจริง"**

การแยกสองขั้นตอนนี้ออกจากกันทำให้แต่ละขั้นตอนมีความรับผิดชอบชัดเจน (separation of concerns) — Working Directory คือที่ทดลอง, Staging Area คือที่ตัดสินใจ, Commit คือการบันทึกถาวร

### ไดอะแกรมเปรียบเทียบ: มี Staging Area vs ไม่มี Staging Area

```
แบบไม่มี Staging Area (VCS ทั่วไปบางตัว):

  Working Directory ────────────────────────▶ Repository
   (แก้ไข 5 ไฟล์)         commit                (เก็บทั้ง 5 ไฟล์
                                                  ไม่ว่าจะพร้อมหรือไม่)


แบบมี Staging Area (Git):

  Working Directory ──add──▶ Staging Area ──commit──▶ Repository
   (แก้ไข 5 ไฟล์)         (เลือกแค่ 3 ไฟล์         (เก็บแค่ 3 ไฟล์
                            ที่พร้อมจริง)            ที่เลือกไว้)
                                                    
                        (2 ไฟล์ที่เหลือยังเป็น Modified
                         รอ commit รอบถัดไป)
```

## Step 25: Commit คืออะไร เก็บข้อมูลอะไรบ้าง

### นิยาม

**Commit** คือ **การบันทึก snapshot ของทั้งโปรเจกต์ ณ ขณะนั้นอย่างถาวรลงใน repository** พร้อมข้อมูลประกอบที่อธิบายว่า "เกิดอะไรขึ้น" เมื่อสร้างเสร็จแล้ว commit จะได้รับ **hash เฉพาะตัว** (จะอธิบายละเอียดใน Step 28) ที่ใช้อ้างอิงถึงมันได้ตลอดไป และ **commit ที่สร้างเสร็จแล้วจะไม่ถูกแก้ไขอีก** (immutable) — ถ้าอยากแก้ จริง ๆ แล้ว Git จะสร้าง commit ใหม่ขึ้นมาแทนที่เสมอ

### ข้อมูลที่ commit หนึ่งก้อนเก็บไว้

commit แต่ละอันไม่ได้เก็บแค่ "โค้ด" แต่เก็บ metadata ครบชุดดังนี้:

| ข้อมูล | ความหมาย |
|---|---|
| **Snapshot ของ Tree** | ตัวชี้ไปยัง tree object ที่แทนโครงสร้างไฟล์/โฟลเดอร์ทั้งหมด ณ ขณะ commit นั้น |
| **Parent commit hash** | ตัวชี้ไปยัง commit ก่อนหน้า (commit แรกสุดของ repo จะไม่มี parent) |
| **Author (ผู้เขียน)** | ชื่อและอีเมลของคนที่ **เขียนโค้ด** นี้ขึ้นมาจริง ๆ พร้อม timestamp ตอนที่เขียน |
| **Committer (ผู้ commit)** | ชื่อและอีเมลของคนที่ **สั่งบันทึก** commit นี้เข้า repository พร้อม timestamp ตอนที่ commit |
| **Commit message** | ข้อความอธิบายว่า commit นี้ทำอะไร/ทำไมถึงทำ |
| **Commit hash (SHA)** | ลายนิ้วมือดิจิทัลเฉพาะตัวของ commit นี้ คำนวณจากข้อมูลทั้งหมดข้างต้นรวมกัน |

> **ทำไมต้องมีทั้ง Author และ Committer แยกกัน?** ในกรณีปกติที่คุณเขียนโค้ดแล้ว commit เอง ทั้งสองค่าจะเป็นคนเดียวกัน แต่ในสถานการณ์เช่นการ `cherry-pick` commit ของคนอื่นมาใส่ใน branch ตัวเอง หรือมีคนช่วย apply patch ให้ ค่า Author จะยังคงเป็นเจ้าของโค้ดตัวจริง ในขณะที่ Committer จะเป็นคนที่กดปุ่ม commit ทำให้ระบบยังคง "ให้เครดิต" คนเขียนโค้ดจริงไว้เสมอ แม้จะไม่ได้เป็นคน commit เอง

### ไดอะแกรม: โครงสร้างของ Commit หนึ่งก้อน

```
┌───────────────────────────────────────────┐
│ Commit: a3f5c8e...                         │
├───────────────────────────────────────────┤
│ tree:      9d8f2a1... (snapshot โครงสร้างไฟล์) │
│ parent:    7b2e441... (commit ก่อนหน้า)        │
│ author:    Somchai <somchai@example.com>    │
│            วันเวลาที่เขียนโค้ด                    │
│ committer: Somchai <somchai@example.com>    │
│            วันเวลาที่สั่ง commit                  │
│ message:   "แก้บั๊กระบบ login เมื่อรหัสผ่านว่าง"     │
└───────────────────────────────────────────┘
```

### สายโซ่ของ Commit (Commit Chain)

เพราะ commit ทุกอันมี "parent" ชี้กลับไปยัง commit ก่อนหน้าเสมอ (ยกเว้น commit แรกสุด) ทำให้ commit ทั้งหมดในโปรเจกต์เชื่อมโยงกันเป็นสายโซ่ย้อนกลับไปในอดีต ซึ่งนี่คือที่มาของคำว่า **history (ประวัติ)** ใน Git

```
Commit 1 ◀── Commit 2 ◀── Commit 3 ◀── Commit 4 (HEAD ปัจจุบันชี้ที่นี่)
(ไม่มี           (parent =         (parent =         (parent =
 parent)         Commit 1)         Commit 2)         Commit 3)
```

ลูกศรในภาพนี้ชี้ "ย้อนกลับ" ไปหา parent เสมอ — Git ไม่มีแนวคิดว่า commit หนึ่งรู้จัก "ลูก" ของตัวเอง มันรู้จักแค่ "พ่อ" ของตัวเองเท่านั้น การจะหา "ลูก" ต้องไล่ดูจาก commit ทั้งหมดว่าใครชี้ parent มาที่ตัวเอง

## Step 26: The Three Trees — HEAD, Index, Working Directory

นี่คือแนวคิดที่ **สำคัญที่สุดข้อหนึ่งในหลักสูตรทั้งหมด** เพราะมันจะเป็นกุญแจสำคัญที่ทำให้คุณเข้าใจคำสั่งที่ดูซับซ้อนในอนาคต เช่น `git diff`, `git reset`, `git checkout`, `git restore` อย่างถ่องแท้ ไม่ใช่แค่ท่องจำ

### ทำไมถึงเรียกว่า "Three Trees"

Git มองข้อมูลผ่าน "ต้นไม้ของไฟล์" (tree) 3 ชุดพร้อมกันตลอดเวลา:

| Tree | คืออะไร | เก็บอยู่ที่ไหน |
|---|---|---|
| **HEAD** | Snapshot ของ commit ล่าสุดที่ถูก commit ไปแล้ว (ของ branch ปัจจุบัน) | `.git/objects/` (อ้างอิงผ่าน `.git/HEAD`) |
| **Index (Staging Area)** | Snapshot ของสิ่งที่ **จะ** เอาไปเก็บใน commit ถัดไป | `.git/index` |
| **Working Directory** | ไฟล์จริงที่คุณเห็นและแก้ไขอยู่ตอนนี้ | โฟลเดอร์โปรเจกต์จริง ๆ |

### ไดอะแกรม: Three Trees ทำงานร่วมกันอย่างไร

```
                    ┌─────────────┐
                    │    HEAD     │   Snapshot ของ commit ล่าสุด
                    │  (Repository)│   "สิ่งที่ถูกบันทึกไปแล้ว"
                    └──────┬──────┘
                           │
                    git reset (ย้อน HEAD)
                           │
                    ┌──────▼──────┐
                    │    Index    │   Snapshot ของสิ่งที่ "จะ" commit
                    │  (Staging)  │   ต่อไป
                    └──────┬──────┘
                           │
                git add / git restore --staged
                           │
                    ┌──────▼──────────┐
                    │ Working Directory│   ไฟล์จริงที่แก้ไขอยู่ตอนนี้
                    │                  │
                    └─────────────────┘
```

### เชื่อมโยงกับคำสั่งจริง (ภาพรวมคร่าว ๆ ก่อนเรียนละเอียดใน Part หลัง)

การเข้าใจ Three Trees ช่วยไขความสับสนของคำสั่งกลุ่ม checkout/reset/restore ได้ทันที เพราะแต่ละคำสั่งคือ **การ "คัดลอกข้อมูล" จาก tree หนึ่งไปทับอีก tree หนึ่ง** เท่านั้นเอง:

| คำสั่ง (ภาพรวม จะเรียนละเอียดภายหลัง) | ทำอะไรกับ Three Trees |
|---|---|
| `git add <file>` | คัดลอกจาก Working Directory → Index |
| `git commit` | คัดลอกจาก Index → HEAD (สร้าง commit ใหม่) |
| `git restore --staged <file>` | คัดลอกจาก HEAD → Index (ยกเลิกการ stage) |
| `git restore <file>` | คัดลอกจาก Index → Working Directory (ทิ้งการแก้ไขที่ยังไม่ stage) |
| `git reset --soft <commit>` | ย้าย HEAD เท่านั้น ไม่แตะ Index/Working Directory |
| `git reset --mixed <commit>` | ย้าย HEAD และคัดลอกทับ Index (ค่าเริ่มต้นของ `git reset`) |
| `git reset --hard <commit>` | ย้าย HEAD และคัดลอกทับทั้ง Index และ Working Directory |

> หมายเหตุ: ตารางนี้เป็นภาพรวมเพื่อให้เห็นว่าแนวคิด Three Trees เชื่อมกับคำสั่งจริงอย่างไร รายละเอียดการใช้งานคำสั่งเหล่านี้แบบเจาะลึก (พร้อมตัวอย่างและข้อควรระวัง) จะอยู่ใน Part ที่ว่าด้วยเรื่อง `git reset`/`git restore`/`git checkout` โดยเฉพาะในเฟสถัดไป ไม่ต้องกังวลถ้ายังไม่เข้าใจคำสั่งเหล่านี้ทั้งหมดตอนนี้ — สิ่งที่ต้องจำให้ได้ตอนนี้คือ **แนวคิดเรื่อง 3 tree** เท่านั้น

### HEAD ในรายละเอียดเพิ่มเติม

คำว่า HEAD มีสองความหมายที่ต้องแยกให้ออก:

1. **HEAD ในฐานะไฟล์** — คือไฟล์ `.git/HEAD` ที่เก็บว่าตอนนี้กำลังอยู่ branch ไหน (`ref: refs/heads/main`)
2. **HEAD ในฐานะแนวคิด** — คือ "ตัวชี้ไปยังตำแหน่งปัจจุบันที่คุณกำลังยืนอยู่" ในประวัติของโปรเจกต์ ปกติ HEAD จะชี้ไปที่ปลายสุดของ branch ที่คุณกำลังทำงานอยู่เสมอ

```
refs/heads/main  ──▶  Commit 4 (a3f5c8e)
                              ▲
                              │
                            HEAD
                    (HEAD ชี้ไปที่ branch main
                     ซึ่ง main ชี้ไปที่ commit ล่าสุด)
```

เราจะเจาะลึกเรื่อง HEAD แบบละเอียดมากขึ้นอีกครั้งเมื่อเรียนเรื่อง Branching ในเฟสถัดไป โดยเฉพาะสถานะพิเศษที่เรียกว่า **detached HEAD**

## Step 27: Git Object Types เบื้องต้น — blob, tree, commit

Git ไม่ได้เก็บข้อมูลแบบไฟล์ระบบปกติ แต่เก็บทุกอย่างเป็น **"Object"** ในฐานข้อมูลภายในของมันเอง (`.git/objects/`) โดยมี object หลัก ๆ 3 ประเภทที่เกี่ยวข้องกับสิ่งที่เราเรียนใน Part นี้ (ยังมี object ประเภทที่ 4 คือ **tag object** ซึ่งจะเรียนภายหลังตอนพูดถึง annotated tags)

> **หมายเหตุสำคัญ:** เนื้อหาใน Step นี้เป็นการแนะนำแบบ "ผิวเผินพอให้เข้าใจภาพรวม" เท่านั้น การเจาะลึกเรื่อง Git Object Model แบบละเอียดจริงจัง — รวมถึงการใช้คำสั่งระดับ plumbing อย่าง `git cat-file`, `git hash-object` เพื่อดู object ตรง ๆ — จะอยู่ใน **Part 56: Git Internals** ซึ่งเป็นส่วนหนึ่งของเฟส 6 ของหลักสูตรนี้

### 1. Blob (Binary Large Object)

**Blob** คือ object ที่เก็บ **เนื้อหาไฟล์ดิบ ๆ** (raw content) เพียงอย่างเดียว **ไม่เก็บชื่อไฟล์ ไม่เก็บ permission ไม่เก็บตำแหน่งโฟลเดอร์** — เก็บแค่ "เนื้อหาข้างในไฟล์" เท่านั้น

ข้อเท็จจริงที่น่าสนใจ: **ถ้าไฟล์สองไฟล์มีเนื้อหาเหมือนกันเป๊ะ (ถึงจะอยู่คนละโฟลเดอร์ คนละชื่อไฟล์) Git จะเก็บ blob เพียงชุดเดียว** เพราะ blob ถูกระบุตัวตนด้วย hash ของเนื้อหา ไม่ใช่ชื่อไฟล์ — นี่คือเหตุผลหนึ่งที่ทำให้ Git ประหยัดพื้นที่จัดเก็บได้มาก

### 2. Tree

**Tree** คือ object ที่แทน **โครงสร้างโฟลเดอร์หนึ่งระดับ** โดยแต่ละแถวในนั้นจะเก็บ:

- ชื่อไฟล์/โฟลเดอร์ย่อย
- Permission mode (เช่นไฟล์ปกติ หรือไฟล์ executable)
- Hash ที่ชี้ไปยัง blob (ถ้าเป็นไฟล์) หรือ tree อื่น (ถ้าเป็นโฟลเดอร์ย่อย)

พูดง่าย ๆ **tree object ทำหน้าที่เหมือนชื่อไฟล์และโครงสร้างโฟลเดอร์** ในขณะที่ **blob object ทำหน้าที่เก็บเนื้อหา** — การแยกสองอย่างนี้ออกจากกันคือกลไกที่ทำให้ Git รองรับการ "rename ไฟล์โดยไม่เปลี่ยนเนื้อหา" ได้อย่างมีประสิทธิภาพ

### 3. Commit

**Commit object** ตามที่อธิบายไปใน Step 25 คือ object ที่ **ชี้ไปยัง tree object หนึ่งอัน** (ซึ่งแทนสถานะทั้งโปรเจกต์ ณ ขณะนั้น) พร้อมข้อมูล metadata (author, committer, message, parent)

### ไดอะแกรม: ความสัมพันธ์ของ 3 Object Types

```
Commit object
├── tree ──────────▶ Tree object (แทนโฟลเดอร์ root ของโปรเจกต์)
│                     ├── "index.html"  ──▶ Blob (เนื้อหาไฟล์ index.html)
│                     ├── "style.css"   ──▶ Blob (เนื้อหาไฟล์ style.css)
│                     └── "src/"        ──▶ Tree object (โฟลเดอร์ย่อย src/)
│                                             └── "app.js" ──▶ Blob (เนื้อหาไฟล์ app.js)
├── parent ────────▶ Commit object ก่อนหน้า
├── author: ...
├── committer: ...
└── message: "..."
```

จะเห็นว่าโครงสร้างนี้เป็นแบบ **ต้นไม้ (tree structure)** ที่ซ้อนกันไปเรื่อย ๆ ตามจำนวนระดับของโฟลเดอร์จริง และนี่คือเหตุผลที่ Step 6 ใน Part 01 บอกว่า **"Git เก็บข้อมูลแบบ snapshot ของทั้งโปรเจกต์"** — เพราะทุก commit จะมี tree object ของตัวเองที่ชี้ไปยังสถานะทั้งหมดของโฟลเดอร์ root ณ เวลานั้น ไม่ใช่แค่ diff บางส่วน

## Step 28: SHA-1/SHA-256 Hash คืออะไร ทำไม Commit ถึงมี Hash ยาว ๆ

### Hash คืออะไร

**Hash function** คือฟังก์ชันทางคณิตศาสตร์ที่รับข้อมูลขนาดเท่าไหร่ก็ได้เป็น input แล้วคำนวณออกมาเป็น **ค่าความยาวคงที่** (fixed-length) ที่เรียกว่า **hash value** หรือ **digest**

คุณสมบัติสำคัญของ hash function ที่ Git ใช้ (เรียกว่า **cryptographic hash function**):

1. **Deterministic** — input เดียวกัน จะได้ hash เดิมทุกครั้งเสมอ ไม่ว่าจะรันกี่รอบ กี่เครื่อง
2. **One-way** — คำนวณจาก input ไป hash ได้ง่าย แต่ทำย้อนกลับจาก hash ไปหา input ไม่ได้ (ในทางปฏิบัติ)
3. **Avalanche effect** — ต่อให้เปลี่ยน input แค่ 1 ตัวอักษร ค่า hash ที่ได้จะเปลี่ยนไปแบบสิ้นเชิง (ดูไม่ออกเลยว่ามีความเกี่ยวข้องกับ hash เดิม)
4. **Collision resistant** — แทบเป็นไปไม่ได้ที่ input สองชุดที่ต่างกันจะให้ hash ค่าเดียวกัน

### Git ใช้ hash แบบไหน

Git แบบดั้งเดิม (และที่ใช้เป็นค่าเริ่มต้นในทุก repository ปัจจุบันส่วนใหญ่) ใช้ **SHA-1** ซึ่งให้ผลลัพธ์เป็นเลขฐาน 16 (hexadecimal) ความยาว **40 ตัวอักษร** เช่น:

```
a3f5c8e9d2b1470f8e6c3d9a1b7e5f2c8d4a6b90
```

ในเวอร์ชันใหม่ ๆ ของ Git (ตั้งแต่ประมาณ 2.29 เป็นต้นมา) เริ่มรองรับโหมดทดลองที่ใช้ **SHA-256** แทน ซึ่งให้ผลลัพธ์ความยาว **64 ตัวอักษร** เนื่องจากมีความกังวลด้านความปลอดภัยระยะยาวของ SHA-1 (เคยมีการค้นพบทฤษฎีการโจมตีแบบ collision ในปี 2017 โดยทีม Google ที่เรียกว่า "SHAttered") แต่ ณ ปัจจุบัน repository ส่วนใหญ่ในโลก **ยังคงใช้ SHA-1 เป็นค่าเริ่มต้น** เพราะการเปลี่ยนไปใช้ SHA-256 ทั้งระบบต้องอาศัยความร่วมมือจากทุกเครื่องมือในระบบนิเวศ (GitHub, GitLab ฯลฯ ยังไม่รองรับเต็มรูปแบบ)

### ทำไม hash ถึงสำคัญต่อ Data Integrity

นี่คือจุดที่ Git ฉลาดมาก: **hash ของแต่ละ object ไม่ได้ถูกสุ่มขึ้นมา แต่คำนวณมาจากเนื้อหาของ object นั้นเองทั้งหมด** พูดให้ชัดคือ:

```
Hash ของ blob        = SHA-1(เนื้อหาไฟล์)
Hash ของ tree        = SHA-1(รายการ entries ทั้งหมดในนั้น รวมถึง hash ของ blob/tree ย่อย)
Hash ของ commit      = SHA-1(tree hash + parent hash + author + committer + message)
```

ผลลัพธ์ที่ตามมาคือ:

1. **ถ้าเนื้อหาไฟล์เปลี่ยนแม้แต่ตัวอักษรเดียว hash ของ blob จะเปลี่ยนทันที** → hash ของ tree ที่ชี้มาที่ blob นั้นก็จะเปลี่ยนตาม (เพราะ tree เก็บ hash ของ blob ไว้ข้างใน) → hash ของ commit ก็จะเปลี่ยนตามไปด้วย
2. **ผลกระทบนี้ไล่ต่อไปเรื่อย ๆ ยัง commit ถัดไปทุกตัวที่มี parent ต่อจากมัน** เพราะ commit ถัดไปเก็บ hash ของ parent ไว้ในตัวมันเอง
3. นี่หมายความว่า **ถ้ามีใครพยายามแอบแก้ไขประวัติ (เช่น เปลี่ยนเนื้อหา commit เก่า ๆ) hash ของ commit นั้นและทุก commit ที่ตามมาหลังจากนั้นจะเปลี่ยนไปหมด ทำให้ตรวจจับการปลอมแปลงได้ทันที**

```
Commit A (hash: aaa111)  ◀── Commit B (hash: bbb222, parent: aaa111)  ◀── Commit C (hash: ccc333, parent: bbb222)

ถ้ามีคนแอบแก้เนื้อหาใน Commit A แม้แต่นิดเดียว:

Commit A (hash: xyz999!)  ◀── Commit B (hash: ???, parent ยังชี้ไปที่ aaa111 ที่ไม่มีอยู่แล้ว!)

→ ทันทีที่ระบบตรวจสอบ hash ของ A ใหม่ พบว่าไม่ตรงกับที่คาดไว้
→ ทุกอย่างที่ต่อจาก A ถือว่าไม่น่าเชื่อถือทันที
```

คุณสมบัตินี้ทำให้ Git เหมาะสมมากกับงานที่ต้องการความน่าเชื่อถือของประวัติสูง เช่น การพัฒนา Open Source ขนาดใหญ่แบบ Linux Kernel ที่มีคนนับพันช่วยกันแก้ไข — ทุกคนสามารถมั่นใจได้ว่าประวัติที่ตัวเองได้รับมา ไม่ได้ถูกดัดแปลงระหว่างทาง

### hash ไม่ใช่ "หมายเลขลำดับ" (ไม่ใช่ Sequential ID)

ข้อควรระวังสำหรับมือใหม่: hash ของ commit **ไม่ได้เรียงลำดับ** เหมือนหมายเลข commit ใน SVN (r1, r2, r3, ...) มันเป็นค่า hash ที่ดูสุ่ม ไม่มีความหมายเชิงลำดับใด ๆ ในตัวมันเอง การจะรู้ว่า commit ไหนเกิดก่อนเกิดหลัง ต้องดูจากความสัมพันธ์ parent-child เท่านั้น ไม่ใช่ดูจากค่า hash ว่ามากหรือน้อยกว่ากัน

ในทางปฏิบัติเวลาใช้งานจริง คุณไม่จำเป็นต้องพิมพ์ hash เต็ม 40 ตัวอักษรเสมอไป — Git ฉลาดพอที่จะรู้จัก commit จาก hash แบบย่อ (เช่น 7 ตัวอักษรแรก) ตราบใดที่ยังไม่ชนกับ commit อื่นในโปรเจกต์นั้น เราจะได้ลองใช้งานจริงเรื่องนี้เมื่อเรียน `git log` ใน Part ถัดไป ๆ

## Step 29: วงจรชีวิตของไฟล์ใน Git

ตอนนี้เรารู้จัก Three States, Three Trees, Object Types และ Hash แล้ว มาประกอบทุกอย่างเข้าด้วยกันเป็น **"วงจรชีวิตของไฟล์"** หนึ่งไฟล์ตั้งแต่เกิดจนถูก commit ซึ่งจะเป็นภาพสรุปที่คุณจะใช้อ้างอิงตลอดการเรียนหลักสูตรนี้

### สถานะทั้งหมดที่ไฟล์หนึ่งไฟล์สามารถอยู่ได้

| สถานะ | ความหมาย |
|---|---|
| **Untracked** | ไฟล์ใหม่ที่ Git ยังไม่เคยรู้จักมาก่อนเลย (ยังไม่เคยถูก `git add`) |
| **Unmodified (Tracked, ไม่มีการเปลี่ยนแปลง)** | ไฟล์ที่ Git รู้จักแล้ว (เคย commit ไปแล้ว) และเนื้อหาปัจจุบันตรงกับ commit ล่าสุดเป๊ะ ไม่มีอะไรเปลี่ยน |
| **Modified** | ไฟล์ที่ Git รู้จัก แต่เนื้อหาปัจจุบันในดิสก์ต่างจากที่เคย commit ไว้ล่าสุด |
| **Staged** | ไฟล์ที่ถูก `git add` ไปแล้ว รอ commit ครั้งถัดไป |

### ไดอะแกรมวงจรชีวิตแบบเต็ม

```
                    ┌─────────────┐
        สร้างไฟล์ใหม่  │  Untracked  │
        ───────────▶ │             │
                    └──────┬──────┘
                           │
                       git add
                           │
                           ▼
                    ┌─────────────┐
                    │   Staged    │◀───────────────────┐
                    │  (ครั้งแรก)  │                      │
                    └──────┬──────┘                      │
                           │                              │
                       git commit                     git add
                           │                              │
                           ▼                              │
                    ┌─────────────┐        แก้ไขไฟล์        │
                    │ Unmodified  │ ───────────────▶ ┌──────────┐
                    │ (Tracked)   │                   │ Modified │
                    └─────────────┘ ◀─────────────────└──────────┘
                           ▲              git commit
                           │              (หลัง add แล้ว)
                           │
                   git checkout / git restore
                    (ยกเลิกการแก้ไข กลับสู่
                     เนื้อหา commit ล่าสุด)
```

### อธิบายทีละขั้นตอนแบบละเอียด

**ขั้นที่ 1: สร้างไฟล์ใหม่ → สถานะ Untracked**

เมื่อคุณสร้างไฟล์ใหม่ในโฟลเดอร์ที่เป็น Git repository เช่น `touch newfile.txt` ไฟล์นี้จะอยู่ในสถานะ **Untracked** ทันที — หมายความว่า Git *เห็น* ไฟล์นี้อยู่ในโฟลเดอร์ (และจะเตือนเวลารัน `git status`) แต่ **ยังไม่ได้เอาไปติดตามประวัติการเปลี่ยนแปลงใด ๆ ให้เลย**

**ขั้นที่ 2: `git add` ครั้งแรก → สถานะ Staged**

เมื่อรัน `git add newfile.txt` ไฟล์จะย้ายเข้าสู่ Staging Area ทันที กลายเป็นสถานะ Staged (นี่คือ "การ track" ไฟล์ครั้งแรก)

**ขั้นที่ 3: `git commit` → สถานะ Unmodified (Tracked)**

หลังจาก commit ไฟล์จะกลายเป็น **Unmodified** — คำนี้อาจฟังดูแปลกเพราะ "Unmodified" หมายถึง "ไฟล์นี้ตรงกับสิ่งที่ commit ล่าสุดบันทึกไว้เป๊ะ ไม่มีความต่างเลย" ไม่ใช่ว่าไฟล์นี้ไม่เคยถูกแก้ไข

**ขั้นที่ 4: แก้ไขไฟล์ที่ commit ไปแล้ว → กลับไปสถานะ Modified**

ถ้าคุณเปิดไฟล์ที่เคย commit ไปแล้วขึ้นมาแก้ไขอีกครั้ง ไฟล์จะเปลี่ยนจาก Unmodified กลายเป็น **Modified** ทันที (Git ตรวจจับความต่างนี้โดยเทียบ hash ของเนื้อหาไฟล์ปัจจุบัน กับ hash ที่บันทึกไว้ใน commit ล่าสุด)

**ขั้นที่ 5: วนซ้ำ Staged → Committed → Unmodified ต่อไปเรื่อย ๆ**

จากนั้นวงจร `git add` → `git commit` จะวนซ้ำไปเรื่อย ๆ ตลอดอายุของโปรเจกต์ นี่คือ "จังหวะการทำงาน" (rhythm) พื้นฐานที่สุดของการใช้ Git ในชีวิตประจำวัน

### สรุปการเปลี่ยนสถานะแบบตาราง (State Transition Table)

| จากสถานะ | คำสั่งที่ทำให้เปลี่ยนสถานะ | ไปสถานะ |
|---|---|---|
| Untracked | `git add` | Staged |
| Staged (ไฟล์ใหม่) | `git commit` | Unmodified |
| Unmodified | แก้ไขเนื้อหาไฟล์ | Modified |
| Modified | `git add` | Staged |
| Staged (ไฟล์เดิมที่แก้ไข) | `git commit` | Unmodified |
| Modified | `git restore <file>` | Unmodified (ทิ้งการแก้ไข) |
| Staged | `git restore --staged <file>` | Modified |
| Untracked | `git rm --cached <file>` (หลัง add แล้ว) | Untracked (เอาออกจาก staging โดยไม่ลบไฟล์จริง) |

> หมายเหตุ: คำสั่ง `git restore` เป็นคำสั่งที่ค่อนข้างใหม่ (เพิ่มมาใน Git 2.23) ซึ่งถูกออกแบบมาให้แยกหน้าที่ของ `git checkout` เดิมที่เคยทำหลายอย่างปนกันจนสับสน เราจะเรียนคำสั่งทั้งหมดในตารางนี้แบบละเอียดพร้อมตัวอย่างจริงใน Part 04 และ Part ถัดไปที่ว่าด้วยการจัดการไฟล์

## Step 30: แบบฝึกหัดลงมือทำ — ทดลองดูสถานะไฟล์เปลี่ยนไปมา

ถึงแม้ Part นี้จะเน้นแนวคิดเป็นหลัก (คำสั่งแบบเจาะลึกจะอยู่ใน Part 04) แต่เราจะลองทำแบบฝึกหัดสั้น ๆ เพื่อ **เห็นภาพ Three States และวงจรชีวิตของไฟล์ด้วยตาตัวเอง** ก่อนไปเรียนคำสั่งแบบเต็มรูปแบบ

> หมายเหตุ: แบบฝึกหัดนี้ใช้คำสั่งพื้นฐานเพียงเพื่อ "สังเกตการเปลี่ยนสถานะ" เท่านั้น รายละเอียดของแต่ละคำสั่ง (options, พฤติกรรมแบบเจาะลึก) จะอธิบายอย่างครบถ้วนใน Part 04

### 30.1 เตรียม repository ทดลอง

```bash
mkdir -p ~/git-course/part-03-practice
cd ~/git-course/part-03-practice
git init
```

ผลลัพธ์ที่ควรเห็น:

```
Initialized empty Git repository in /home/user/git-course/part-03-practice/.git/
```

ลองสำรวจโครงสร้าง `.git` ที่เพิ่งสร้าง (ตามที่อธิบายใน Step 21):

```bash
ls -la .git
cat .git/HEAD
```

ควรเห็น `ref: refs/heads/main` (หรือ `refs/heads/master` ถ้ายังไม่ได้ตั้งค่า `init.defaultBranch` ตาม Part 02)

### 30.2 สังเกตสถานะ Untracked

สร้างไฟล์ใหม่ แล้วดูสถานะ:

```bash
echo "สวัสดี Git" > note.txt
git status
```

ผลลัพธ์ควรมีข้อความประมาณนี้ (สังเกตคำว่า **Untracked files**):

```
On branch main

No commits yet

Untracked files:
  (use "git add <file>..." to include in what will be committed)
        note.txt

nothing added to commit but untracked files present (use "git add" to track)
```

### 30.3 สังเกตสถานะ Staged

```bash
git add note.txt
git status
```

ผลลัพธ์จะเปลี่ยนไป (สังเกตคำว่า **Changes to be committed**):

```
On branch main

No commits yet

Changes to be committed:
  (use "git rm --cached <file>..." to unstage)
        new file:   note.txt
```

### 30.4 สังเกตสถานะ Committed (Unmodified)

```bash
git commit -m "เพิ่มไฟล์ note.txt ครั้งแรก"
git status
```

ผลลัพธ์:

```
On branch main
nothing to commit, working tree clean
```

ข้อความ `working tree clean` คือคำยืนยันว่า **ไม่มีไฟล์ไหนอยู่ในสถานะ Modified หรือ Staged เลย** — ทุกอย่างตรงกับ commit ล่าสุดเป๊ะ

ลองดูประวัติ commit ที่เพิ่งสร้าง:

```bash
git log
```

จะเห็น commit hash แบบเต็ม (40 ตัวอักษรตามที่อธิบายใน Step 28), ชื่อผู้เขียน, วันเวลา และข้อความ commit

### 30.5 สังเกตสถานะ Modified

แก้ไขไฟล์เดิมที่ commit ไปแล้ว:

```bash
echo "เพิ่มบรรทัดใหม่" >> note.txt
git status
```

ผลลัพธ์จะเปลี่ยนอีกครั้ง (สังเกตคำว่า **Changes not staged for commit**):

```
On branch main
Changes not staged for commit:
  (use "git add <file>..." to update what will be committed)
  (use "git restore <file>..." to discard changes in working directory)
        modified:   note.txt

no changes added to commit (use "git add" and/or "git commit -m ...")
```

ลองดูความต่างระหว่าง Working Directory กับ Staging Area/HEAD ด้วยคำสั่ง (ยังไม่ต้องเข้าใจ options ลึก ๆ ตอนนี้):

```bash
git diff
```

จะเห็นบรรทัดที่เพิ่มเข้ามา แสดงด้วยเครื่องหมาย `+` สีเขียว

### 30.6 วนกลับไป Staged แล้ว Commit อีกครั้ง

```bash
git add note.txt
git status    # ควรเห็นสถานะ Staged อีกครั้ง
git commit -m "เพิ่มบรรทัดที่สองใน note.txt"
git status    # ควรกลับมา clean อีกครั้ง
git log       # ควรเห็น 2 commits แล้ว พร้อม parent เชื่อมกัน
```

### 30.7 ทดลองเพิ่มไฟล์ที่สอง เพื่อดู Partial Staging (ตามที่อธิบายใน Step 24)

```bash
echo "ไฟล์ที่สอง" > second.txt
echo "แก้ไขไฟล์แรกอีกครั้ง" >> note.txt
git status
```

ตอนนี้ควรเห็นทั้ง **Untracked files** (second.txt) และ **Changes not staged** (note.txt) พร้อมกัน — สาธิตให้เห็นว่าไฟล์แต่ละไฟล์ในโปรเจกต์เดียวกันสามารถอยู่คนละสถานะพร้อมกันได้

ลอง stage เฉพาะไฟล์เดียว:

```bash
git add second.txt
git status
```

จะเห็นว่า `second.txt` ขึ้นใน "Changes to be committed" ในขณะที่ `note.txt` ยังอยู่ใน "Changes not staged for commit" — นี่คือตัวอย่างจริงของ **Partial Commit** ที่อธิบายไว้ใน Step 24

```bash
git commit -m "เพิ่ม second.txt (ยังไม่รวมการแก้ไข note.txt)"
git status
```

จะเห็นว่า `note.txt` ยังคงเป็น Modified อยู่ ไม่ได้ถูกเก็บเข้า commit นี้ไปด้วย ตรงตามที่อธิบายไว้ในทฤษฎี

## สรุป Part 03

ใน Part นี้เราได้เรียนรู้ว่า:

1. **Repository** คือโฟลเดอร์โปรเจกต์ธรรมดาบวกกับโฟลเดอร์ `.git` ซึ่งเก็บ HEAD, config, objects และ refs ไว้ข้างใน — การลบ `.git` เท่ากับลบประวัติทั้งหมดทิ้ง
2. **Three States** ของ Git คือ Modified, Staged, Committed ซึ่งเป็นแกนกลางที่คำสั่ง Git แทบทุกตัวหมุนรอบอยู่
3. **Working Directory** คือไฟล์จริงที่แก้ไขอยู่บนดิสก์ เทียบได้กับ "โต๊ะทำงาน" ที่แยกจากห้องสมุด (repository)
4. **Staging Area (Index)** คือพื้นที่พักไฟล์ก่อน commit ที่ทำให้ Git รองรับ partial commit, atomic commit และการ review ก่อนบันทึกได้
5. **Commit** คือ snapshot ของทั้งโปรเจกต์พร้อม metadata ครบชุด (tree, parent, author, committer, message) และเชื่อมโยงกันเป็นสายโซ่ประวัติผ่าน parent hash
6. **Three Trees** — HEAD, Index, Working Directory — คือกรอบความคิดที่อธิบายคำสั่งย้ายข้อมูล เช่น add, commit, restore, reset ได้อย่างเป็นระบบ
7. **Git Object Types** พื้นฐานมี 3 แบบคือ blob (เนื้อหาไฟล์), tree (โครงสร้างโฟลเดอร์), commit (snapshot + metadata) โดยจะเจาะลึกจริงจังใน Part 56
8. **Hash (SHA-1/SHA-256)** ของ Git คำนวณจากเนื้อหาของ object เอง ทำให้ตรวจจับการปลอมแปลงประวัติได้ทันที และไม่ใช่เลขลำดับแบบ sequential ID
9. **วงจรชีวิตของไฟล์** ใน Git ไล่จาก Untracked → Staged → Committed (Unmodified) → Modified → Staged → Committed วนซ้ำไปเรื่อย ๆ ตลอดอายุโปรเจกต์
10. เราได้ลงมือทดลองจริงด้วย `git status`, `git add`, `git commit`, `git diff` เพื่อเห็นการเปลี่ยนสถานะไฟล์แบบเป็นรูปธรรมแล้ว

พร้อมแนวคิดครบทุกด้านแล้ว ต่อไปเราจะเจาะลึกคำสั่งพื้นฐานชุดแรกของ Git อย่างเต็มรูปแบบ ทั้ง options ที่สำคัญ, กรณีการใช้งานจริง และข้อผิดพลาดที่มือใหม่มักเจอ
