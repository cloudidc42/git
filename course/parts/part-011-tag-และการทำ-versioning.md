## Step 101: Tag คืออะไร ต่างจาก Branch อย่างไร

ก่อนจะลงลึกเรื่องคำสั่งต่าง ๆ เราต้องเข้าใจแนวคิดพื้นฐานของ **Tag** ก่อนว่ามันคืออะไร และทำไม Git ถึงต้องมีสิ่งนี้แยกออกมาจาก Branch ทั้งที่หน้าตาการใช้งานคล้ายกันมาก

### Tag คืออะไร

**Tag** คือ **"ป้ายชื่อ" ที่ผูกติดกับ Commit ใดหนึ่งอย่างถาวร** เพื่อทำเครื่องหมายว่า commit นั้นมีความสำคัญเป็นพิเศษ เช่น เป็นจุดที่ปล่อยซอฟต์แวร์เวอร์ชันหนึ่งออกสู่สาธารณะ (release)

พูดให้ง่ายที่สุด Tag คือการบอกว่า:

> **"commit นี้แหละ คือเวอร์ชัน v1.0.0 ที่เรา release ออกไปแล้ว"**

เมื่อคุณสร้าง Tag ขึ้นมา มันจะกลายเป็น **จุดอ้างอิงถาวร** ที่คุณสามารถกลับมาดูได้เสมอว่า "ตอนที่ปล่อยเวอร์ชัน 1.0.0 นั้น โค้ดหน้าตาเป็นอย่างไร" โดยไม่ต้องจำ commit hash ที่ยาวและจำยากอย่าง `a3f9c21e8b4d...`

### ทำไมถึงต้องมี Tag ทั้งที่มี Branch อยู่แล้ว

นี่คือคำถามที่ผู้เรียนใหม่มักสงสัย เพราะทั้ง Tag และ Branch ต่างก็เป็น "ตัวชี้ (pointer)" ที่ชี้ไปยัง commit เหมือนกัน แต่ความแตกต่างที่สำคัญที่สุดคือ:

| คุณสมบัติ | Branch | Tag |
|---|---|---|
| ขยับได้ไหม | **ขยับได้ตลอดเวลา** — ทุกครั้งที่ commit ใหม่บน branch นั้น ตัวชี้จะเลื่อนไปยัง commit ล่าสุดเสมอ | **ไม่ขยับ** — ชี้ commit เดิมตลอดไป (นอกจากคุณจะลบแล้วสร้างใหม่โดยตั้งใจ) |
| จุดประสงค์ | ใช้เป็น "เส้นทางการพัฒนา" ที่กำลังดำเนินไปเรื่อย ๆ | ใช้เป็น "จุดคงที่ในประวัติศาสตร์" เพื่ออ้างอิงย้อนหลัง |
| commit ต่อได้ไหม | ได้ — commit ใหม่จะถูกเพิ่มเข้าไปในสาย branch นั้น | ไม่ได้โดยตรง — Tag ไม่ใช่จุดที่คุณ "อยู่บน" มันแล้ว commit ต่อได้เหมือน branch |
| ตัวอย่างการใช้งาน | `main`, `develop`, `feature/login` | `v1.0.0`, `v2.3.1`, `release-2024-01` |
| เปลี่ยนชื่อ/ย้ายที่ได้ง่ายไหม | ทำได้บ่อย เป็นเรื่องปกติของการทำงาน | ควรทำน้อยที่สุด เพราะ Tag คือ "สัญญา" ว่า commit นี้คือเวอร์ชันที่ปล่อยจริง |

### ภาพประกอบแนวคิด

ลองนึกภาพประวัติ commit เส้นหนึ่งบน branch `main`:

```
A ─── B ─── C ─── D ─── E ─── F   (main, ขยับไปเรื่อย ๆ ตาม commit ใหม่)
      │           │
      │           └── v1.0.0 (Tag ชี้ commit D ตลอดไป ไม่ขยับตาม)
      │
      └── v0.9.0-beta (Tag ชี้ commit B ตลอดไป ไม่ขยับตาม)
```

จากภาพจะเห็นว่า:

- `main` เดินหน้าไปเรื่อย ๆ ทุกครั้งที่มี commit ใหม่ (จาก A ไปจนถึง F)
- `v1.0.0` ยังคงชี้ commit `D` อยู่เสมอ ไม่ว่า `main` จะไปไกลแค่ไหนแล้วก็ตาม
- `v0.9.0-beta` ก็เช่นกัน ยังคงชี้ commit `B` ตลอดไป

นี่คือเหตุผลสำคัญที่สุดที่ Git แยก Tag ออกจาก Branch เพราะการ **release ซอฟต์แวร์** ต้องการ "จุดอ้างอิงที่ตายตัว" ไม่ใช่ "จุดที่เคลื่อนที่ได้" — ถ้าคุณบอกลูกค้าว่า "เวอร์ชัน 1.0.0 อยู่ที่ branch `main`" แล้วทีมยัง commit ต่อบน `main` ไปเรื่อย ๆ ความหมายของคำว่า "เวอร์ชัน 1.0.0" ก็จะพร่าเลือนทันที เพราะ `main` ไม่เท่าเดิมอีกต่อไป แต่ถ้าบอกว่า "เวอร์ชัน 1.0.0 อยู่ที่ Tag `v1.0.0`" คุณจะมั่นใจได้ 100% ว่าโค้ดที่เห็นตอนนี้กับตอนที่ release จริงจะเหมือนกันทุกตัวอักษรเสมอ

### กรณีใช้งานจริงของ Tag

Tag ถูกใช้อย่างแพร่หลายในโลกจริงสำหรับ:

1. **ทำเครื่องหมาย release ของซอฟต์แวร์** — เช่น `v1.0.0`, `v2.1.3`
2. **สร้าง GitHub Release / GitLab Release** — แพลตฟอร์มทั้งสองใช้ Tag เป็นฐานในการสร้างหน้า release พร้อมไฟล์แนบและ release notes (เราจะเรียนเรื่องนี้ละเอียดใน Part ที่เกี่ยวกับ GitHub)
3. **ทำเครื่องหมายจุดสำคัญในประวัติศาสตร์โปรเจกต์** — เช่น "commit นี้คือจุดที่ผ่านการตรวจสอบความปลอดภัยแล้ว" หรือ "commit นี้คือจุดที่ deploy ขึ้น production ครั้งล่าสุด"
4. **ใช้เป็น reference สำหรับ deployment/CI-CD pipeline** — หลายระบบ deploy จะดึงโค้ดจาก Tag แทนที่จะดึงจาก branch เพื่อความแน่นอนว่าสิ่งที่ deploy คือเวอร์ชันที่ต้องการจริง ๆ
5. **ช่วยในการ bisect หาบั๊ก** — เมื่อรู้ว่าบั๊กเกิดขึ้นระหว่างเวอร์ชัน `v1.2.0` กับ `v1.3.0` การมี Tag ทำให้ค้นหาช่วง commit ที่ต้องตรวจสอบได้แม่นยำและรวดเร็ว

จำหลักการสำคัญที่สุดของ Step นี้ไว้ให้ขึ้นใจ:

> **Branch คือเส้นทางที่กำลังเดินไปข้างหน้า ส่วน Tag คือหมุดปักหมายไว้ที่จุดใดจุดหนึ่งในอดีตอย่างถาวร**

## Step 102: Lightweight Tag vs Annotated Tag ความแตกต่างและควรใช้แบบไหนเมื่อไหร่

Git รองรับ Tag สองประเภทที่มีพฤติกรรมและการใช้งานต่างกันพอสมควร คือ **Lightweight Tag** และ **Annotated Tag** การเข้าใจความแตกต่างนี้สำคัญมาก เพราะการเลือกใช้ผิดประเภทอาจทำให้ข้อมูลสำคัญของ release หายไป

### Lightweight Tag คืออะไร

**Lightweight Tag** คือ Tag แบบง่ายที่สุด เปรียบเสมือน **"ป้ายชื่อเปล่า ๆ"** ที่แค่ชี้ไปยัง commit hash โดยตรง โดยไม่มีข้อมูลเพิ่มเติมใด ๆ แนบมาด้วยเลย

พูดในเชิงเทคนิค Lightweight Tag คือไฟล์เล็ก ๆ ในโฟลเดอร์ `.git/refs/tags/` ที่เก็บแค่ **commit hash** ตรง ๆ ไม่มีการสร้าง object ใหม่ใน Git object database เลย มันจึงคล้ายกับ branch ที่ไม่ขยับตาม commit ใหม่มากกว่า

**ข้อมูลที่ Lightweight Tag เก็บ:**
- ชื่อของ Tag
- Commit hash ที่ชี้ไป

**ข้อมูลที่ Lightweight Tag ไม่มี:**
- ไม่มีชื่อผู้สร้าง Tag
- ไม่มีวันที่สร้าง Tag
- ไม่มีข้อความอธิบาย (message)
- ไม่สามารถเซ็นลายเซ็นดิจิทัล (GPG signature) ได้

### Annotated Tag คืออะไร

**Annotated Tag** คือ Tag แบบเต็มรูปแบบที่ Git แนะนำให้ใช้เป็นค่าเริ่มต้นสำหรับการทำ release จริง เพราะมันถูกเก็บเป็น **object เต็มรูปแบบตัวหนึ่งในฐานข้อมูลของ Git (tag object)** ไม่ใช่แค่ตัวชี้เปล่า ๆ

**ข้อมูลที่ Annotated Tag เก็บไว้:**
- ชื่อผู้สร้าง Tag (tagger name และ email)
- วันที่และเวลาที่สร้าง Tag
- ข้อความอธิบาย (tag message) เช่นเดียวกับ commit message
- Commit hash ที่ชี้ไป
- รองรับการเซ็นลายเซ็นดิจิทัลด้วย GPG เพื่อยืนยันความถูกต้องของ release (เรื่องนี้จะเจาะลึกในหัวข้อความปลอดภัยของหลักสูตรช่วงหลัง)

เพราะ Annotated Tag เป็น object เต็มรูปแบบ มันจึงมี **hash ของตัวมันเอง** แยกต่างหากจาก hash ของ commit ที่มันชี้ไป ต่างจาก Lightweight Tag ที่ไม่มี hash ของตัวเองเลย (ใช้ hash ของ commit ตรง ๆ)

### ตารางเปรียบเทียบสรุป

| คุณสมบัติ | Lightweight Tag | Annotated Tag |
|---|---|---|
| เก็บเป็น Git object ไหม | ไม่ (แค่ pointer ไปยัง commit) | ใช่ (เป็น tag object เต็มรูปแบบ) |
| มีชื่อผู้สร้างและวันที่ไหม | ไม่มี | มี |
| มีข้อความอธิบาย (message) ไหม | ไม่มี | มี |
| รองรับ GPG signature ไหม | ไม่รองรับ | รองรับ |
| คำสั่งที่ใช้สร้าง | `git tag <name>` | `git tag -a <name> -m "message"` |
| Git แนะนำให้ใช้กรณีไหน | การทำเครื่องหมายชั่วคราว ใช้ส่วนตัว ไม่เป็นทางการ | การทำ release อย่างเป็นทางการ ควรใช้เป็นค่าเริ่มต้นเสมอ |

### ควรใช้แบบไหนเมื่อไหร่

หลักการที่ควรจำไว้และปฏิบัติตามในการทำงานจริงมีดังนี้:

1. **ใช้ Annotated Tag สำหรับการ release ซอฟต์แวร์เสมอ** เพราะมันมีข้อมูลครบถ้วนว่าใครเป็นคนปล่อยเวอร์ชันนี้ เมื่อไหร่ และทำไม (ผ่าน message) ซึ่งเป็นข้อมูลสำคัญมากในการตรวจสอบย้อนหลัง โดยเฉพาะในทีมงานขนาดใหญ่หรือโปรเจกต์ Open Source
2. **ใช้ Lightweight Tag เฉพาะกรณีที่เป็นการทำเครื่องหมายชั่วคราวสำหรับตัวเองเท่านั้น** เช่น การจดจุดไว้เพื่อทดสอบอะไรบางอย่างชั่วคราวแล้วจะลบทิ้งในภายหลัง
3. **เอกสารและเครื่องมือส่วนใหญ่ในโลกจริงคาดหวัง Annotated Tag** — เช่น เมื่อคุณ push Tag ขึ้น GitHub เพื่อสร้าง Release, GitHub จะดึงข้อมูล tag message มาแสดงเป็นค่าเริ่มต้นให้ ถ้าคุณใช้ Lightweight Tag ข้อมูลตรงนี้จะไม่มีให้แสดงเลย

> **กฎทองที่ควรจำ:** ถ้าไม่แน่ใจว่าจะใช้ Tag แบบไหน ให้ใช้ **Annotated Tag เสมอ** ด้วยการใส่ `-a` และ `-m` ทุกครั้ง มันแทบไม่มีข้อเสียเลยเมื่อเทียบกับ Lightweight Tag นอกจากใช้พื้นที่เก็บข้อมูลเพิ่มขึ้นเล็กน้อยมาก (ซึ่งไม่มีนัยสำคัญใด ๆ ในทางปฏิบัติ)

เราจะไปดูวิธีสร้าง Tag ทั้งสองแบบนี้อย่างละเอียดใน Step ถัดไป

## Step 103: สร้าง Tag ด้วย `git tag`

มาถึง Step ที่ลงมือปฏิบัติจริงกันแล้ว ในหัวข้อนี้เราจะเรียนรู้วิธีสร้าง Tag ทั้งสองแบบที่กล่าวถึงใน Step 102

### เตรียมความพร้อมก่อนเริ่ม

สมมติว่าคุณมี repository อยู่แล้วพร้อมประวัติ commit อยู่บ้าง ลองสร้างโฟลเดอร์ทดลองใหม่เพื่อฝึกฝนตาม Step นี้:

```bash
mkdir ~/git-course/part-11-tags
cd ~/git-course/part-11-tags
git init
```

จากนั้นสร้างไฟล์และ commit สักสองสามครั้งเพื่อให้มีประวัติให้ทดลอง:

```bash
echo "Version 1" > app.txt
git add app.txt
git commit -m "Initial commit"

echo "Version 2" >> app.txt
git add app.txt
git commit -m "Add feature X"
```

### 103.1 สร้าง Lightweight Tag

คำสั่งพื้นฐานที่สุดในการสร้าง Tag คือ:

```bash
git tag <ชื่อ-tag>
```

ตัวอย่าง:

```bash
git tag v0.1.0
```

คำสั่งนี้จะสร้าง Lightweight Tag ชื่อ `v0.1.0` ที่ชี้ไปยัง **commit ปัจจุบันที่ HEAD กำลังอยู่** ทันที ไม่มีข้อความ ไม่มีการถามอะไรเพิ่มเติม เสร็จสิ้นในบรรทัดเดียว

### 103.2 สร้าง Annotated Tag

สำหรับการทำ release จริง ให้ใช้ flag `-a` (annotate) พร้อม `-m` (message) เสมอ:

```bash
git tag -a <ชื่อ-tag> -m "<ข้อความอธิบาย>"
```

ตัวอย่าง:

```bash
git tag -a v1.0.0 -m "First stable release: core features complete"
```

เมื่อรันคำสั่งนี้ Git จะสร้าง **tag object** เต็มรูปแบบขึ้นมา พร้อมบันทึกชื่อผู้สร้าง (ดึงจาก `git config user.name` และ `user.email` ที่เราตั้งค่าไว้ตั้งแต่ Part ต้น ๆ), วันเวลาปัจจุบัน, และข้อความที่เราใส่ไว้

**เคล็ดลับ:** ถ้าคุณไม่ใส่ `-m` แล้วรันแค่ `git tag -a v1.0.0` เปล่า ๆ Git จะเปิด text editor เริ่มต้น (เช่น Vim หรือ Nano) ให้คุณพิมพ์ข้อความ เหมือนกับตอนที่ทำ `git commit` โดยไม่ใส่ `-m` ทุกประการ — เหมาะสำหรับ release ที่ต้องการเขียนรายละเอียดยาว ๆ หลายบรรทัด

### 103.3 สร้าง Annotated Tag แบบหลายบรรทัด

ถ้าต้องการใส่รายละเอียดของ release ยาว ๆ หลายบรรทัด สามารถใช้ `-m` ซ้ำหลายครั้งได้ (แต่ละครั้งจะกลายเป็นคนละย่อหน้า) หรือเปิด editor ก็ได้:

```bash
git tag -a v1.0.0 -m "Release v1.0.0" -m "- เพิ่มระบบ login" -m "- แก้บั๊กเรื่องการคำนวณราคา"
```

หรือถ้าต้องการความยืดหยุ่นเต็มที่ ให้เปิด editor:

```bash
git tag -a v1.0.0
```

แล้วพิมพ์ข้อความยาว ๆ ในหน้าต่าง editor ที่เปิดขึ้นมา บันทึกและปิดเหมือนตอนเขียน commit message

### 103.4 ตรวจสอบว่า Tag ถูกสร้างสำเร็จ

หลังจากสร้าง Tag แล้ว ให้ตรวจสอบด้วยคำสั่ง:

```bash
git tag
```

ผลลัพธ์ควรแสดงรายชื่อ Tag ทั้งหมดที่มีในเครื่องตอนนี้:

```
v0.1.0
v1.0.0
```

### 103.5 ข้อควรระวังตอนสร้าง Tag

1. **ชื่อ Tag ต้องไม่ซ้ำกัน** — ถ้าคุณพยายามสร้าง Tag ชื่อที่มีอยู่แล้ว Git จะแจ้ง error ว่า `fatal: tag 'v1.0.0' already exists` ทันที ต้องลบ Tag เดิมก่อนถ้าต้องการสร้างใหม่ทับ (จะสอนวิธีลบใน Step 107)
2. **Tag ชี้ไปที่ commit ที่ HEAD อยู่ ณ ตอนที่รันคำสั่ง** — ถ้าคุณลืม commit งานที่แก้ไว้ก่อนสร้าง Tag, Tag จะไปชี้ commit เก่าที่ยังไม่มีงานล่าสุดรวมอยู่ ดังนั้นต้อง commit ให้เรียบร้อยก่อนเสมอ
3. **ชื่อ Tag ไม่ควรมีช่องว่าง** — ใช้ขีดกลาง (`-`) หรือจุด (`.`) แทน เช่น `v1.0.0` หรือ `release-2024-01-15`
4. **แนวทางการตั้งชื่อ Tag ที่เป็นมาตรฐานอุตสาหกรรม** คือการขึ้นต้นด้วยตัว `v` ตามด้วยเลขเวอร์ชันแบบ Semantic Versioning เช่น `v1.0.0`, `v2.3.1` (เราจะเจาะลึกเรื่องนี้ใน Step 105)

## Step 104: ดูรายการ Tag และดูรายละเอียดของ Tag

เมื่อโปรเจกต์มี Tag สะสมมากขึ้นเรื่อย ๆ การรู้จักคำสั่งค้นหาและดูรายละเอียด Tag จึงสำคัญมาก

### 104.1 ดูรายการ Tag ทั้งหมด

```bash
git tag
```

หรือใช้ flag `-l` (list) ที่ให้ผลลัพธ์เหมือนกัน:

```bash
git tag -l
```

ผลลัพธ์จะเรียงตามลำดับตัวอักษร (alphabetical order) **ไม่ใช่ตามลำดับเวลาที่สร้าง**:

```
v0.1.0
v0.2.0
v1.0.0
v1.0.1
v2.0.0
```

### 104.2 ค้นหา Tag ด้วย Pattern (Wildcard)

เมื่อมี Tag จำนวนมาก คุณสามารถกรองรายการด้วย pattern ได้ โดยใช้ `-l` ร่วมกับเครื่องหมาย `*`:

```bash
git tag -l "v1.*"
```

ผลลัพธ์จะแสดงเฉพาะ Tag ที่ขึ้นต้นด้วย `v1.` เท่านั้น:

```
v1.0.0
v1.0.1
```

ตัวอย่างอื่น ๆ ที่ใช้บ่อย:

```bash
# ดู Tag ทั้งหมดที่เป็น pre-release (มีคำว่า beta หรือ rc)
git tag -l "*beta*"
git tag -l "*rc*"

# ดู Tag เฉพาะ major version 2
git tag -l "v2.*"

# ดู Tag ที่มีคำว่า release อยู่ในชื่อ
git tag -l "*release*"
```

**หมายเหตุสำคัญ:** เมื่อใช้ pattern ที่มีเครื่องหมาย `*` ต้องใส่เครื่องหมายคำพูด (quotes) ครอบไว้เสมอ ไม่เช่นนั้น shell (เช่น Bash) จะพยายามตีความ `*` เป็นการขยายชื่อไฟล์ในโฟลเดอร์ปัจจุบันแทนที่จะส่งต่อให้ Git โดยตรง ซึ่งจะทำให้ได้ผลลัพธ์ที่ผิดพลาด

### 104.3 เรียง Tag ตามลำดับเวลาหรือเวอร์ชัน

ค่าเริ่มต้นของ `git tag` จะเรียงตามตัวอักษร ซึ่งบางครั้งไม่ตรงกับลำดับเวอร์ชันจริง (เช่น `v9.0.0` จะโผล่มาก่อน `v10.0.0` เพราะเทียบตัวอักษร `9` มาก่อน `1` แบบ string ธรรมดา) หากต้องการเรียงตามเวอร์ชันอย่างถูกต้อง ให้ใช้:

```bash
git tag --sort=v:refname
```

หรือเรียงตามวันที่สร้าง (ใหม่สุดอยู่ล่างสุด):

```bash
git tag --sort=creatordate
```

หรือกลับด้าน (ใหม่สุดอยู่บนสุด) โดยใส่เครื่องหมายลบนำหน้า:

```bash
git tag --sort=-creatordate
```

### 104.4 ดูรายละเอียดของ Tag ด้วย `git show`

คำสั่ง `git show` ใช้ดูรายละเอียดของ Tag ได้ทั้งสองประเภท:

```bash
git show v1.0.0
```

**ถ้าเป็น Annotated Tag** ผลลัพธ์จะแสดงข้อมูลสองส่วนต่อกัน:

1. **ส่วนของ tag object** — แสดงชื่อผู้สร้าง Tag, วันที่, และข้อความ (message) ที่ใส่ไว้ตอนสร้าง
2. **ส่วนของ commit ที่ Tag ชี้ไป** — แสดงรายละเอียด commit ตามปกติ (ผู้เขียน, วันที่ commit, ข้อความ commit) พร้อม diff ของการเปลี่ยนแปลงใน commit นั้น

ตัวอย่างผลลัพธ์โดยประมาณ:

```
tag v1.0.0
Tagger: Somchai Devteam <somchai@example.com>
Date:   Mon Jan 15 10:30:00 2024 +0700

First stable release: core features complete

commit a3f9c21e8b4d5f6a7b8c9d0e1f2a3b4c5d6e7f8a
Author: Somchai Devteam <somchai@example.com>
Date:   Mon Jan 15 10:25:00 2024 +0700

    Add feature X

diff --git a/app.txt b/app.txt
...
```

**ถ้าเป็น Lightweight Tag** ผลลัพธ์จะแสดง **เฉพาะรายละเอียดของ commit ที่มันชี้ไปเลย** โดยไม่มีข้อมูล tag object เพิ่มเติม เพราะ Lightweight Tag ไม่มี object ของตัวเอง

นี่คือความแตกต่างที่มองเห็นได้ชัดเจนที่สุดระหว่าง Tag สองแบบเมื่อใช้งานจริง — ถ้าคุณรัน `git show` แล้วเห็นบรรทัด `tag <ชื่อ>`, `Tagger:` ขึ้นก่อน แปลว่าเป็น Annotated Tag แต่ถ้าเจอ `commit <hash>` ขึ้นทันทีเลย แปลว่าเป็น Lightweight Tag

### 104.5 ตรวจสอบว่า Tag ไหนเป็นแบบไหนอย่างรวดเร็ว

อีกวิธีหนึ่งที่ใช้แยกประเภท Tag ได้เร็ว คือคำสั่ง `git cat-file`:

```bash
git cat-file -t v1.0.0
```

- ถ้าผลลัพธ์คือ `tag` แปลว่าเป็น **Annotated Tag**
- ถ้าผลลัพธ์คือ `commit` แปลว่าเป็น **Lightweight Tag** (เพราะมันชี้ตรงไปยัง commit object เลย ไม่มี tag object คั่นกลาง)

### 104.6 ดู Tag ทั้งหมดพร้อมข้อความในบรรทัดเดียว

หากต้องการภาพรวมแบบกระชับของทุก Tag พร้อมข้อความกำกับ ใช้:

```bash
git tag -n
```

ผลลัพธ์จะแสดง Tag พร้อมบรรทัดแรกของ message (สำหรับ Annotated Tag):

```
v0.1.0          Initial beta release
v1.0.0          First stable release: core features complete
```

ถ้าต้องการดูหลายบรรทัดของ message ให้ใส่ตัวเลขต่อท้าย เช่น `git tag -n5` เพื่อดู 5 บรรทัดแรก

## Step 105: Semantic Versioning เบื้องต้น (Major.Minor.Patch)

เมื่อพูดถึงการตั้งชื่อ Tag สำหรับ release ซอฟต์แวร์ มาตรฐานที่ได้รับความนิยมสูงสุดในอุตสาหกรรมคือ **Semantic Versioning** หรือเรียกย่อ ๆ ว่า **SemVer**

### Semantic Versioning คืออะไร

**Semantic Versioning** คือระบบการตั้งเลขเวอร์ชันของซอฟต์แวร์ที่มีความหมายชัดเจน ทำให้ทุกคนที่เห็นเลขเวอร์ชันสามารถเข้าใจได้ทันทีว่า "การอัปเดตครั้งนี้มีผลกระทบมากแค่ไหน" โดยไม่ต้องอ่าน changelog ทั้งหมด

รูปแบบมาตรฐานคือ:

```
MAJOR.MINOR.PATCH
```

ตัวอย่าง: `2.4.1`

### ความหมายของแต่ละตัวเลข

| ตำแหน่ง | ชื่อ | ความหมาย | เพิ่มเลขเมื่อไหร่ |
|---|---|---|---|
| ตัวแรก | **MAJOR** | การเปลี่ยนแปลงที่ **breaking change** — ทำให้โค้ดที่ใช้เวอร์ชันเก่าอาจพังหรือใช้งานไม่ได้ทันทีถ้าอัปเกรดมา | เมื่อมีการเปลี่ยนแปลง API หรือพฤติกรรมที่ไม่ backward compatible |
| ตัวกลาง | **MINOR** | การเพิ่มฟีเจอร์ใหม่ที่ **ไม่ทำให้ของเดิมพัง** — ใช้งานร่วมกับเวอร์ชันเก่าได้ (backward compatible) | เมื่อเพิ่มความสามารถใหม่โดยไม่กระทบของเดิม |
| ตัวหลังสุด | **PATCH** | การแก้บั๊กเล็ก ๆ น้อย ๆ ที่ไม่เพิ่มฟีเจอร์ใหม่และไม่กระทบ API | เมื่อแก้ไขข้อผิดพลาดโดยไม่เปลี่ยนพฤติกรรมที่ตั้งใจไว้ |

### ตัวอย่างการไล่เลขเวอร์ชันแบบเป็นเหตุเป็นผล

```
v1.0.0  → เริ่มต้น release เวอร์ชันแรกที่เสถียร
v1.0.1  → แก้บั๊กเล็กน้อย (PATCH +1)
v1.1.0  → เพิ่มฟีเจอร์ใหม่ เช่น เพิ่มระบบแจ้งเตือน แต่ของเดิมยังใช้ได้ปกติ (MINOR +1, PATCH รีเซ็ตเป็น 0)
v1.1.1  → แก้บั๊กของฟีเจอร์แจ้งเตือนที่เพิ่งเพิ่มไป (PATCH +1)
v2.0.0  → เปลี่ยนโครงสร้าง API ทั้งหมด ทำให้โค้ดเก่าที่เรียกใช้ API แบบเดิมพังทันที (MAJOR +1, MINOR และ PATCH รีเซ็ตเป็น 0)
```

สังเกตกฎสำคัญ: **เมื่อเลขตำแหน่งซ้ายเพิ่มขึ้น เลขตำแหน่งขวาทั้งหมดจะถูกรีเซ็ตกลับเป็น 0 เสมอ**

### เวอร์ชันก่อน 1.0.0 มีความหมายพิเศษ

ตาม SemVer เวอร์ชันที่ขึ้นต้นด้วย `0.x.x` (เช่น `0.1.0`, `0.9.5`) หมายถึง **ซอฟต์แวร์ยังอยู่ในช่วงพัฒนาเริ่มต้น (initial development)** ยังไม่รับประกันความเสถียรของ API ใด ๆ ทั้งสิ้น สามารถเปลี่ยนแปลงแบบ breaking change ได้ตลอดเวลาแม้จะเป็นแค่การขยับเลข MINOR ก็ตาม

เมื่อทีมพัฒนามั่นใจว่าซอฟต์แวร์พร้อมใช้งานจริงและ API เริ่มนิ่งแล้ว จึงจะปล่อยเป็น `1.0.0` ซึ่งถือเป็นจุดเปลี่ยนสำคัญที่บอกว่า "จากนี้ไปเราจะรักษาความเข้ากันได้ (compatibility) อย่างจริงจัง"

### ส่วนขยายเพิ่มเติม: Pre-release และ Build Metadata

SemVer ยังรองรับการต่อท้ายข้อมูลเพิ่มเติมได้ เช่น:

```
v1.0.0-alpha        → เวอร์ชันทดลองระยะแรกสุด ยังไม่เสถียรเลย
v1.0.0-beta.1       → เวอร์ชันทดสอบระยะที่ใกล้เสร็จมากขึ้น (ครั้งที่ 1)
v1.0.0-rc.1         → Release Candidate ครั้งที่ 1 (ผู้สมัครที่คาดว่าจะเป็นตัวจริง ถ้าไม่มีปัญหาก็จะกลายเป็น v1.0.0 ตัวจริง)
v1.0.0+build.20240115  → build metadata ระบุข้อมูลเพิ่มเติมเกี่ยวกับ build โดยไม่มีผลต่อลำดับความสำคัญของเวอร์ชัน
```

ลำดับความ "เก่าไปใหม่" ของ pre-release โดยทั่วไปคือ:

```
alpha < beta < rc < (เวอร์ชันตัวจริงที่ไม่มีคำต่อท้าย)
```

### ทำไมนักพัฒนาซอฟต์แวร์ทุกคนควรเข้าใจ SemVer

1. **ช่วยให้ผู้ใช้ตัดสินใจอัปเดตได้อย่างมั่นใจ** — เห็นเลข MAJOR เปลี่ยนก็รู้ทันทีว่าต้องอ่าน migration guide ก่อนอัปเดต
2. **เครื่องมือจัดการ dependency ใช้ SemVer เป็นมาตรฐาน** — เช่น `npm`, `pip`, `composer` ล้วนใช้กฎ SemVer ในการกำหนดช่วงเวอร์ชันที่ยอมรับได้ (เช่น `^1.2.0` หมายถึงยอมรับ `1.x.x` ทุกตัวที่ไม่ต่ำกว่า `1.2.0` แต่ไม่ข้ามไปเวอร์ชัน `2.0.0`)
3. **สื่อสารกับทีมและผู้ใช้ได้ชัดเจนโดยไม่ต้องอธิบายยาว** — เลขเวอร์ชันเพียงสามตัวบอกเรื่องราวความเปลี่ยนแปลงได้ทันที

> **หมายเหตุ:** หัวข้อนี้เป็นเพียงการปูพื้นฐานเบื้องต้นของ Semantic Versioning เท่านั้น เราจะกลับมาเจาะลึกเรื่องนี้อย่างละเอียดอีกครั้งใน **Part 88** ซึ่งจะครอบคลุมเรื่อง versioning strategy ระดับองค์กร, การจัดการ changelog อัตโนมัติ, และการเชื่อมโยง SemVer เข้ากับ CI/CD pipeline

ตอนนี้สิ่งที่ต้องจำให้ขึ้นใจคือโครงสร้าง `MAJOR.MINOR.PATCH` และความหมายของแต่ละตัวเลข เพราะเราจะใช้หลักการนี้ในการตั้งชื่อ Tag ตลอดทั้ง Part นี้และ Part ต่อ ๆ ไป

## Step 106: Tag ย้อนหลังกับ Commit เก่า

ในโลกความเป็นจริง คุณจะไม่ได้สร้าง Tag ทันทีหลังจาก commit เสมอไป บางครั้งคุณอาจนึกขึ้นได้ทีหลังว่า "commit เมื่อ 3 วันก่อนนี่แหละคือจุดที่ควรจะเป็น v1.0.0" Git รองรับการสร้าง Tag ย้อนหลังไปยัง commit เก่าได้อย่างง่ายดาย

### วิธีการสร้าง Tag ย้อนหลัง

คำสั่งพื้นฐานคือการเพิ่ม commit hash (หรือส่วนย่อของ hash) ต่อท้ายคำสั่งสร้าง Tag ปกติ:

```bash
git tag -a <ชื่อ-tag> <commit-hash> -m "<ข้อความ>"
```

### ตัวอย่างการใช้งานจริง

ก่อนอื่น ลองดูประวัติ commit ทั้งหมดด้วย `git log` แบบย่อ:

```bash
git log --oneline
```

ผลลัพธ์ตัวอย่าง:

```
f4e2a91 Add logout feature
b8c3d12 Fix login bug
a3f9c21 Add feature X
7d1e8f0 Initial commit
```

สมมติว่าคุณต้องการติด Tag `v1.0.0` ย้อนหลังไปที่ commit `a3f9c21` (ซึ่งเป็นจุดที่ระบบเสร็จสมบูรณ์ครั้งแรก) ไม่ใช่ commit ล่าสุด:

```bash
git tag -a v1.0.0 a3f9c21 -m "First stable release"
```

คำสั่งนี้จะสร้าง Tag `v1.0.0` ที่ชี้ไปยัง commit `a3f9c21` โดยตรง **โดยไม่กระทบ HEAD หรือ branch ปัจจุบันเลยแม้แต่น้อย** — HEAD ยังคงอยู่ที่ commit ล่าสุด (`f4e2a91`) เหมือนเดิมทุกประการ

### ตรวจสอบว่า Tag ชี้ไปยัง commit ที่ถูกต้อง

ใช้คำสั่งที่เรียนไปใน Step 104 เพื่อยืนยัน:

```bash
git show v1.0.0
```

ควรเห็นว่ารายละเอียด commit ที่แสดงตรงกับ commit `a3f9c21` (ข้อความ "Add feature X") ไม่ใช่ commit ล่าสุด

หรือใช้คำสั่งนี้เพื่อดูว่า Tag แต่ละตัวชี้ไปที่ commit ไหนแบบเห็นภาพรวมทั้งหมดในหน้าจอเดียว:

```bash
git log --oneline --decorate
```

ผลลัพธ์จะแสดงชื่อ Tag ต่อท้าย commit ที่มันชี้ไปโดยตรง:

```
f4e2a91 (HEAD -> main) Add logout feature
b8c3d12 Fix login bug
a3f9c21 (tag: v1.0.0) Add feature X
7d1e8f0 Initial commit
```

### กรณีใช้งานที่พบบ่อยของการ Tag ย้อนหลัง

1. **ลืมติด Tag ตอน release จริง** — เมื่อนึกขึ้นได้ทีหลังว่าลืมทำเครื่องหมายจุด release ก็สามารถย้อนกลับไปติดได้โดยไม่ต้องแก้ไขประวัติใด ๆ
2. **จัดระเบียบประวัติของโปรเจกต์เก่าที่ไม่เคยมี Tag มาก่อน** — เมื่อนำโปรเจกต์เก่าที่ไม่เคยทำ versioning อย่างเป็นระบบมาจัดระเบียบใหม่ สามารถไล่ดู `git log` แล้วติด Tag ย้อนหลังตามจุดสำคัญในอดีตได้ทั้งหมด
3. **ทำ Tag สำหรับ hotfix ที่แตก branch ออกจาก commit เก่า** — เมื่อต้องแก้บั๊กด่วนบนเวอร์ชันเก่าที่ยังใช้งานอยู่ (ไม่ใช่เวอร์ชันล่าสุด) การติด Tag ย้อนหลังช่วยระบุจุดเริ่มต้นที่ถูกต้องให้ทีมอื่นเข้าใจตรงกัน

### ข้อควรระวัง

การระบุ commit hash สามารถใช้แค่ **ส่วนย่อ (short hash)** ได้เช่นกัน เช่น `a3f9c21` แทนที่จะพิมพ์ hash เต็ม 40 ตัวอักษร ขอเพียงให้ส่วนย่อนั้นยาวพอที่จะไม่ชนกับ commit อื่นในโปรเจกต์ (โดยทั่วไป 7-8 ตัวอักษรแรกก็เพียงพอสำหรับโปรเจกต์ขนาดทั่วไป)

นอกจากนี้ยังสามารถใช้ **relative reference** แทน hash ได้ เช่น:

```bash
git tag -a v0.9.0 HEAD~3 -m "Beta release, 3 commits before latest"
```

คำสั่งนี้จะติด Tag ที่ commit ซึ่งอยู่ก่อนหน้า HEAD ปัจจุบัน 3 commit พอดี ซึ่งสะดวกมากเมื่อคุณจำได้แค่ "ตำแหน่งสัมพัทธ์" แต่จำ hash ที่แน่นอนไม่ได้

## Step 107: ลบ Tag ทั้งแบบ Local และแบบ Remote

Tag ที่สร้างผิด สร้างซ้ำ หรือไม่ต้องการแล้ว สามารถลบออกได้ แต่ต้องเข้าใจว่า **การลบ Tag ในเครื่อง (local) กับการลบ Tag บน remote server เป็นคนละขั้นตอนกันโดยสิ้นเชิง**

### 107.1 ลบ Tag แบบ Local

คำสั่งพื้นฐาน:

```bash
git tag -d <ชื่อ-tag>
```

ตัวอย่าง:

```bash
git tag -d v0.1.0
```

ผลลัพธ์ที่ได้:

```
Deleted tag 'v0.1.0' (was a1b2c3d)
```

คำสั่งนี้จะลบ Tag ออกจาก **เครื่อง local ของคุณเท่านั้น** ถ้า Tag นี้เคยถูก push ขึ้น remote (เช่น GitHub) ไปแล้วก่อนหน้านี้ Tag บน remote **จะยังคงอยู่เหมือนเดิม** ไม่ได้ถูกลบตามไปด้วย

### 107.2 ลบ Tag บน Remote

เนื่องจาก Tag บน remote ไม่ได้หายไปพร้อมกับการลบ local คุณต้องสั่งลบบน remote แยกต่างหากอีกครั้งด้วยคำสั่ง:

```bash
git push origin --delete <ชื่อ-tag>
```

ตัวอย่าง:

```bash
git push origin --delete v0.1.0
```

ผลลัพธ์ที่ได้:

```
To github.com:username/project.git
 - [deleted]         v0.1.0
```

### วิธีเก่าที่ยังพบเห็นได้ (Syntax ทางเลือก)

ก่อนที่ Git จะมี flag `--delete` ที่อ่านง่าย ผู้ใช้จำนวนมากยังใช้ syntax แบบเก่าซึ่งยังใช้งานได้จนถึงปัจจุบัน โดยอาศัยหลักการ "push ค่าว่างไปทับ ref เดิม":

```bash
git push origin :v0.1.0
```

เครื่องหมาย `:` ด้านหน้าชื่อ Tag หมายถึง "push ค่าว่างไปแทนที่ ref นี้บน remote" ซึ่งมีผลเทียบเท่ากับการลบ Tag นั้นทิ้ง แต่ในทางปฏิบัติแนะนำให้ใช้ `git push origin --delete <tag>` เพราะอ่านเข้าใจง่ายกว่ามาก และลดโอกาสพิมพ์ผิดพลาด

### ลำดับขั้นตอนที่ถูกต้องในการลบ Tag ให้หมดจดทั้งระบบ

เมื่อต้องการลบ Tag ที่ทั้งมี local และ push ไปยัง remote แล้ว ให้ทำตามลำดับนี้:

```bash
# ขั้นที่ 1: ลบ Tag ออกจากเครื่อง local ก่อน
git tag -d v0.1.0

# ขั้นที่ 2: ลบ Tag ออกจาก remote ด้วย
git push origin --delete v0.1.0
```

**ลำดับไหนก่อนหลังไม่มีผลต่อผลลัพธ์สุดท้าย** แต่ผู้เขียนแนะนำให้ลบ local ก่อนเสมอเพื่อความเป็นระเบียบและป้องกันความสับสน

### ข้อควรระวังสำคัญเกี่ยวกับการลบ Tag ที่คนอื่นอาจดึงไปแล้ว

การลบ Tag บน remote มีความเสี่ยงคล้ายกับการ force push เพราะถ้าเพื่อนร่วมทีมคนอื่น **ได้ fetch หรือ pull Tag นั้นไปเก็บไว้ในเครื่องของเขาแล้ว** การลบของคุณบน remote จะไม่ลบ Tag ในเครื่องของเขาโดยอัตโนมัติ เขาจะยังมี Tag นั้นค้างอยู่ในเครื่องต่อไป ซึ่งอาจทำให้เกิดความสับสนภายหลังว่า "ทำไมเครื่องฉันมี Tag นี้ แต่บน GitHub ไม่มี"

ดังนั้นเมื่อจำเป็นต้องลบ Tag ที่เผยแพร่ออกไปแล้ว **ควรแจ้งทีมทุกคนให้ทราบ** และให้แต่ละคนลบ Tag ในเครื่องตัวเองด้วยคำสั่ง `git tag -d <ชื่อ-tag>` เช่นกัน

### กรณีที่ควรลบ Tag

1. **สร้าง Tag ผิดชื่อหรือผิด commit โดยไม่ตั้งใจ** และยังไม่ได้แจ้งให้ใครใช้อ้างอิง
2. **ต้องการสร้าง Tag ใหม่ทับชื่อเดิม** เพราะ Git จะไม่ยอมให้สร้าง Tag ชื่อซ้ำโดยตรง ต้องลบตัวเก่าก่อนเสมอ
3. **ทำความสะอาด Tag ทดลอง** ที่สร้างไว้ใน development environment แต่ไม่เกี่ยวข้องกับ release จริง

### กรณีที่ไม่ควรลบ Tag

- **Tag ของ release ที่เผยแพร่ให้ผู้ใช้จริงไปแล้ว** ไม่ควรลบเด็ดขาด เพราะผู้ใช้อาจอ้างอิง Tag นั้นในระบบของเขาอยู่ (เช่น ใน `package.json` หรือไฟล์ dependency อื่น ๆ) การลบจะทำให้ระบบของเขาพังทันทีเมื่อพยายามดึงเวอร์ชันนั้นมาใช้อีกครั้ง

## Step 108: Push Tag ขึ้น Remote

ประเด็นสำคัญที่ผู้เรียนใหม่มักพลาดคือ **Git ไม่ push Tag ขึ้น remote โดยอัตโนมัติ** แม้จะสั่ง `git push` ตามปกติแล้วก็ตาม เพราะ Tag ถูกออกแบบมาให้เป็นสิ่งที่คุณต้อง push อย่างจงใจแยกต่างหาก

### 108.1 ทดสอบพฤติกรรมเริ่มต้น

ลองสร้าง Tag แล้วสั่ง push ปกติ:

```bash
git tag -a v1.0.0 -m "First release"
git push origin main
```

ผลลัพธ์ที่ได้คือ **มีแค่ commit ที่ถูก push ขึ้นไป ส่วน Tag `v1.0.0` จะยังคงอยู่แค่ในเครื่อง local เท่านั้น** ถ้าคุณไปดูที่ GitHub หรือ GitLab ตอนนี้ จะไม่เห็น Tag นี้เลยแม้แต่น้อย

### 108.2 Push Tag เดี่ยว ๆ ไปยัง Remote

วิธีที่ถูกต้องในการ push Tag หนึ่งตัวคือระบุชื่อ Tag ต่อท้ายคำสั่ง push ตรง ๆ:

```bash
git push origin <ชื่อ-tag>
```

ตัวอย่าง:

```bash
git push origin v1.0.0
```

ผลลัพธ์:

```
To github.com:username/project.git
 * [new tag]         v1.0.0 -> v1.0.0
```

วิธีนี้เหมาะกับสถานการณ์ที่คุณต้องการ push แค่ Tag เดียวที่เพิ่งสร้างเสร็จ โดยไม่กระทบ Tag อื่น ๆ ที่อาจยังไม่พร้อม push

### 108.3 Push Tag ทั้งหมดพร้อมกันด้วย `--tags`

ถ้าคุณมี Tag หลายตัวในเครื่องที่ยังไม่เคย push ขึ้น remote เลย และต้องการส่งทั้งหมดในคำสั่งเดียว ให้ใช้:

```bash
git push origin --tags
```

คำสั่งนี้จะ push **Tag ทุกตัวที่มีในเครื่อง local ที่ยังไม่มีอยู่บน remote** ขึ้นไปทั้งหมดในครั้งเดียว

### ความแตกต่างระหว่าง `git push origin <tagname>` กับ `git push --tags`

นี่คือจุดที่ต้องเข้าใจให้ชัดเจน เพราะเป็นคำถามที่พบบ่อยมาก:

| คำสั่ง | ผลลัพธ์ |
|---|---|
| `git push origin <tagname>` | push **เฉพาะ Tag ที่ระบุชื่อไว้เท่านั้น** ตัวเดียว |
| `git push --tags` | push **Tag ทุกตัวในเครื่อง** ที่ยังไม่มีอยู่บน remote ขึ้นไปทั้งหมด |
| `git push origin main --tags` | push branch `main` พร้อมกับ Tag ทุกตัวที่ยังไม่มีบน remote ในคำสั่งเดียว |

**ข้อควรระวังของ `--tags`:** เพราะมันจะ push Tag **ทุกตัว** ที่มีในเครื่อง หากคุณมี Tag ทดลองหรือ Tag ส่วนตัวที่ไม่ได้ตั้งใจจะเผยแพร่ปะปนอยู่ด้วย มันจะถูก push ขึ้นไปด้วยเช่นกันโดยไม่มีการเลือกเฉพาะเจาะจง ดังนั้นในทีมงานที่ต้องการความรอบคอบ นักพัฒนาหลายคนเลือกที่จะ push Tag ทีละตัวด้วยชื่อที่ระบุชัดเจนแทนการใช้ `--tags` แบบเหวี่ยงแห

### 108.4 push Tag พร้อมกับตั้งค่าให้ push อัตโนมัติเสมอในอนาคต (แนวทางเสริม)

โดยค่าเริ่มต้น Git ตั้งใจให้ผู้ใช้ push Tag แบบระบุชัดเจนเสมอ เพื่อป้องกันการ push โดยไม่ตั้งใจ อย่างไรก็ตาม หากทีมของคุณต้องการเปลี่ยนพฤติกรรมนี้ สามารถตั้งค่าได้ด้วย:

```bash
git config --global push.followTags true
```

เมื่อตั้งค่านี้แล้ว การรัน `git push` ธรรมดา (ไม่ต้องมี `--tags`) จะ push **Annotated Tag ที่ชี้ไปยัง commit ที่กำลังถูก push ขึ้นไปด้วยโดยอัตโนมัติ** (แต่ยังไม่ push Lightweight Tag หรือ Tag ที่ชี้ไปยัง commit ที่ไม่ได้อยู่ในรอบการ push นั้น) — เป็นการตั้งค่าที่สะดวกสำหรับทีมที่ทำ release ผ่าน Tag เป็นประจำ แต่ผู้เขียนแนะนำให้ผู้เริ่มต้นยังคง push Tag แบบระบุชื่อชัดเจนด้วยตัวเองไปก่อน เพื่อให้เข้าใจกลไกอย่างถ่องแท้ก่อนเปิดใช้ automation

### 108.5 ตรวจสอบ Tag บน Remote

หลังจาก push แล้ว สามารถตรวจสอบว่า Tag ขึ้นไปอยู่บน remote จริงหรือไม่ด้วยคำสั่ง:

```bash
git ls-remote --tags origin
```

ผลลัพธ์จะแสดงรายการ Tag ทั้งหมดที่มีอยู่บน remote พร้อม hash ที่มันชี้ไป:

```
a1b2c3d4e5f6... refs/tags/v1.0.0
b2c3d4e5f6a7... refs/tags/v1.0.0^{}
```

**หมายเหตุ:** สำหรับ Annotated Tag จะเห็นสองบรรทัดต่อหนึ่ง Tag คือบรรทัดของ tag object เอง กับบรรทัดที่มี `^{}` ต่อท้ายซึ่งหมายถึง commit ที่ Tag นั้นชี้ไปจริง ๆ (dereference) ส่วน Lightweight Tag จะมีแค่บรรทัดเดียว

## Step 109: Checkout ไปที่ Tag และการสร้าง Branch จาก Tag

เมื่อคุณต้องการย้อนกลับไปดูโค้ดที่จุดใดจุดหนึ่งในอดีตที่ถูกทำเครื่องหมายด้วย Tag ไว้ Git มีวิธีให้คุณ "ไปดู" ที่จุดนั้นได้ แต่มีพฤติกรรมพิเศษที่ต้องเข้าใจให้ดีก่อน

### 109.1 Checkout ไปยัง Tag

คำสั่งพื้นฐาน:

```bash
git checkout <ชื่อ-tag>
```

ตัวอย่าง:

```bash
git checkout v1.0.0
```

เมื่อรันคำสั่งนี้ Git จะแสดงข้อความเตือนประมาณนี้:

```
Note: switching to 'v1.0.0'.

You are in 'detached HEAD' state. You can look around, make experimental
changes and commit them, and you can discard any commits you make in this
state without impacting any branches by switching back to a branch.

If you want to create a new branch to retain commits you create, you may
do so (now or later) by using -c with the switch command. Example:

  git switch -c <new-branch-name>

Or undo this operation with:

  git switch -

Turn off this advice by setting config variable advice.detachedHead to false

HEAD is now at a3f9c21 Add feature X
```

### 109.2 Detached HEAD คืออะไร และทำไมถึงเกิดขึ้น

**Detached HEAD** คือสถานะที่ **HEAD ไม่ได้ชี้ไปยัง branch ใด ๆ เลย แต่ชี้ไปยัง commit โดยตรง**

ปกติแล้ว HEAD จะชี้ไปยัง branch (เช่น `main`) และ branch นั้นจะชี้ไปยัง commit ล่าสุดอีกทอดหนึ่ง:

```
HEAD → main → commit ล่าสุด
```

แต่เมื่อ checkout ไปยัง Tag (หรือ commit hash โดยตรง) HEAD จะข้ามขั้นตอนของ branch ไปชี้ที่ commit นั้นเลยทันที:

```
HEAD → commit a3f9c21  (ไม่มี branch คั่นกลาง)
```

เหตุผลที่ Git ต้องทำแบบนี้เพราะ **Tag ไม่ใช่ branch** มันเป็นแค่จุดอ้างอิงคงที่ ไม่มีแนวคิดของ "การ commit ต่อบน Tag" อยู่ในระบบ ดังนั้นเมื่อคุณ checkout ไปยัง Tag, Git จึงต้องพาคุณไปอยู่ในสถานะที่ไม่ผูกกับ branch ใด ๆ

### 109.3 อันตรายของการ commit ขณะอยู่ใน Detached HEAD

ถ้าคุณลองแก้ไขไฟล์และ commit ขณะอยู่ใน detached HEAD:

```bash
echo "experimental change" >> app.txt
git add app.txt
git commit -m "Experimental fix"
```

commit นี้ **จะถูกสร้างขึ้นจริง** แต่มันจะ **ไม่ได้อยู่ในสาย branch ใดเลย** ถ้าคุณสลับกลับไปที่ branch อื่น (เช่น `git checkout main`) โดยไม่ได้สร้าง branch ใหม่มารองรับ commit นี้ไว้ก่อน **commit นี้จะกลายเป็น "commit ลอย" ที่ไม่มีอะไรชี้ถึงมันอีกต่อไป** และในที่สุดจะถูก Git garbage collector ลบทิ้งอย่างถาวรหลังจากผ่านไประยะเวลาหนึ่ง (โดยปกติประมาณ 30 วัน ตามค่า `gc.reflogExpire` เริ่มต้น)

นี่คือเหตุผลที่ Git แสดงคำเตือนตัวใหญ่ทุกครั้งที่เข้าสู่ detached HEAD — เพื่อป้องกันไม่ให้คุณทำงานสำคัญไปแล้วทำหายโดยไม่ตั้งใจ

### 109.4 วิธีที่ถูกต้อง: สร้าง Branch จาก Tag เพื่อแก้ไขต่อ

หากคุณต้องการแก้ไขโค้ดต่อจากจุดที่ Tag ชี้ไป (เช่น ต้องทำ **hotfix** บนเวอร์ชันเก่าที่ release ไปแล้ว) วิธีที่ถูกต้องและปลอดภัยคือ **สร้าง branch ใหม่ออกจาก Tag นั้นทันที** ก่อนจะเริ่มแก้ไขอะไร

**วิธีที่ 1: สร้าง branch จาก Tag โดยตรง โดยไม่ต้อง checkout ก่อน**

```bash
git checkout -b hotfix/v1.0.1 v1.0.0
```

คำสั่งนี้จะสร้าง branch ใหม่ชื่อ `hotfix/v1.0.1` โดยเริ่มต้นจาก commit ที่ Tag `v1.0.0` ชี้ไป และสลับ HEAD ไปยัง branch ใหม่นี้ทันที — สังเกตว่าครั้งนี้ **ไม่มี detached HEAD เกิดขึ้นเลย** เพราะ HEAD ชี้ไปยัง branch `hotfix/v1.0.1` ซึ่งเป็น branch จริง ไม่ใช่ commit ลอย ๆ

**วิธีที่ 2: ใช้คำสั่ง `git switch` แบบใหม่ (Git 2.23 ขึ้นไป)**

```bash
git switch -c hotfix/v1.0.1 v1.0.0
```

`git switch -c` ทำหน้าที่เหมือนกับ `git checkout -b` ทุกประการ แต่เป็นคำสั่งที่ Git ออกแบบมาใหม่ให้เจาะจงหน้าที่ชัดเจนกว่า (แยกหน้าที่การสลับ branch ออกจากหน้าที่การจัดการไฟล์ที่ `git checkout` เดิมทำอยู่ปนกัน)

**วิธีที่ 3: ถ้าคุณ checkout ไปยัง Tag แล้ว (อยู่ใน detached HEAD) และเพิ่งนึกขึ้นได้ว่าต้องการสร้าง branch**

ไม่ต้องกังวล ยังไม่สายเกินไป ตราบใดที่ยังไม่ได้สลับออกจาก detached HEAD:

```bash
git checkout v1.0.0
# ทำงานบางอย่าง หรือแค่ดูโค้ด...
# นึกขึ้นได้ว่าต้องการแก้ไขต่อ:
git switch -c hotfix/v1.0.1
```

คำสั่ง `git switch -c hotfix/v1.0.1` (ไม่ระบุจุดเริ่มต้น) จะสร้าง branch ใหม่จาก **ตำแหน่งปัจจุบันที่ HEAD อยู่** ซึ่งก็คือ commit ที่ Tag ชี้ไปนั่นเอง พร้อมกับ commit ใด ๆ ที่คุณอาจสร้างไว้ระหว่างอยู่ใน detached HEAD (ถ้ามี) ก็จะถูกรักษาไว้ในสาย branch ใหม่นี้ด้วย ไม่สูญหายอีกต่อไป

### 109.5 สรุปกรณีการใช้งาน Checkout Tag

| สถานการณ์ | คำแนะนำ |
|---|---|
| ต้องการแค่ **ดูโค้ด** ณ จุด release โดยไม่แก้ไขอะไรเลย | `git checkout <tag>` เข้า detached HEAD ได้ตามปกติ ดูเสร็จแล้วสั่ง `git checkout main` กลับไปที่เดิม |
| ต้องการ **แก้ไขโค้ดต่อ** จากจุดของ Tag (เช่นทำ hotfix) | สร้าง branch ใหม่ทันทีด้วย `git checkout -b <branch> <tag>` หรือ `git switch -c <branch> <tag>` |
| อยู่ใน detached HEAD แล้วและเผลอ commit ไปแล้ว แต่ยังไม่ได้สร้าง branch | รีบสร้าง branch ทันทีด้วย `git switch -c <branch-name>` ก่อนจะสลับไปที่อื่น ไม่เช่นนั้น commit จะเสี่ยงหายไปถาวร |
| กลับจาก detached HEAD ไปยัง branch เดิมโดยไม่ต้องการเก็บอะไรไว้ | `git checkout main` หรือ `git switch main` ได้เลยตามปกติ |

> **จำไว้เสมอ:** Tag ไม่ใช่สถานที่สำหรับ "ทำงานต่อ" มันเป็นแค่ "จุดอ้างอิง" การแก้ไขโค้ดใด ๆ จากจุดของ Tag ต้องผ่าน branch ใหม่เสมอ ไม่มีข้อยกเว้น

## Step 110: แบบฝึกหัด — สร้างประวัติ Commit จำลองแล้วติด Tag ตามหลัก Semver

ถึงเวลาลงมือปฏิบัติจริงเพื่อรวบรวมทุกสิ่งที่เรียนมาใน Part นี้เข้าด้วยกัน ในแบบฝึกหัดนี้ คุณจะสร้างประวัติ commit จำลองของโปรเจกต์เล็ก ๆ แล้วติด Tag ตามหลัก Semantic Versioning ให้ถูกต้อง

### เตรียมโฟลเดอร์สำหรับแบบฝึกหัด

```bash
mkdir ~/git-course/part-11-practice
cd ~/git-course/part-11-practice
git init
```

ตั้งค่าผู้ใช้ในเครื่อง (ถ้ายังไม่เคยตั้งค่า global ไว้):

```bash
git config user.name "ชื่อของคุณ"
git config user.email "email@example.com"
```

### ขั้นที่ 1: สร้าง Commit แรก — เริ่มต้นโปรเจกต์

```bash
echo "# My Todo App" > README.md
echo "console.log('Todo App v0.1');" > app.js
git add README.md app.js
git commit -m "Initial project setup"
```

ติด Tag เวอร์ชันเริ่มต้นในช่วงพัฒนา (ยังไม่เสถียร ใช้ `0.x.x`):

```bash
git tag -a v0.1.0 -m "Initial development version: basic project skeleton"
```

### ขั้นที่ 2: เพิ่มฟีเจอร์แรก — เพิ่มรายการ Todo ได้

```bash
cat >> app.js << 'EOF'

function addTodo(text) {
  console.log('Added:', text);
}
EOF
git add app.js
git commit -m "Add addTodo function"
```

ยังอยู่ในช่วง 0.x.x เพราะยังไม่พร้อมใช้งานจริง เพิ่มแค่ PATCH หรือ MINOR ตามความเหมาะสม (ในที่นี้ถือว่าเป็นฟีเจอร์ใหม่ระดับเล็ก):

```bash
git tag -a v0.2.0 -m "Add ability to add todo items"
```

### ขั้นที่ 3: เพิ่มฟีเจอร์ที่สอง — ลบรายการ Todo ได้

```bash
cat >> app.js << 'EOF'

function removeTodo(id) {
  console.log('Removed:', id);
}
EOF
git add app.js
git commit -m "Add removeTodo function"
```

```bash
git tag -a v0.3.0 -m "Add ability to remove todo items"
```

### ขั้นที่ 4: แก้บั๊กเล็กน้อยในฟีเจอร์ที่มีอยู่

```bash
cat >> app.js << 'EOF'

// Fixed: removeTodo now validates id type
EOF
git add app.js
git commit -m "Fix removeTodo id validation bug"
```

เนื่องจากนี่เป็นแค่การแก้บั๊ก ไม่ใช่ฟีเจอร์ใหม่ ให้เพิ่มแค่ตัวเลข PATCH:

```bash
git tag -a v0.3.1 -m "Fix bug in removeTodo validation"
```

### ขั้นที่ 5: ครบฟีเจอร์ที่วางแผนไว้ พร้อม Release ตัวจริงครั้งแรก

```bash
cat >> README.md << 'EOF'

## Features
- Add todo
- Remove todo
- Stable API ready for v1.0.0
EOF
git add README.md
git commit -m "Update documentation for v1.0.0 release"
```

นี่คือจุดสำคัญ — เมื่อทีมมั่นใจว่า API เสถียรพร้อมใช้งานจริงแล้ว จึงปล่อยเป็นเวอร์ชัน `1.0.0` ตามหลัก SemVer:

```bash
git tag -a v1.0.0 -m "First stable release: Todo App with add/remove functionality"
```

### ขั้นที่ 6: เพิ่มฟีเจอร์ใหม่หลังจาก 1.0.0 (Breaking Change)

สมมติว่าทีมตัดสินใจเปลี่ยนโครงสร้างฟังก์ชันทั้งหมดให้เป็น object-based API ซึ่งทำให้โค้ดเดิมที่เรียกใช้ `addTodo()`, `removeTodo()` แบบเดิมใช้งานไม่ได้อีกต่อไป (breaking change):

```bash
cat > app.js << 'EOF'
const TodoApp = {
  add(text) { console.log('Added:', text); },
  remove(id) { console.log('Removed:', id); }
};
module.exports = TodoApp;
EOF
git add app.js
git commit -m "BREAKING CHANGE: refactor to TodoApp object API"
```

เพราะเป็น breaking change ต้องเพิ่มตัวเลข MAJOR และรีเซ็ต MINOR, PATCH กลับเป็น 0:

```bash
git tag -a v2.0.0 -m "BREAKING CHANGE: migrate to TodoApp object-based API"
```

### ขั้นที่ 7: ตรวจสอบผลลัพธ์ทั้งหมด

ดูรายการ Tag ทั้งหมดที่สร้างมา เรียงตามลำดับเวอร์ชัน:

```bash
git tag --sort=v:refname
```

ผลลัพธ์ที่ควรได้:

```
v0.1.0
v0.2.0
v0.3.0
v0.3.1
v1.0.0
v2.0.0
```

ดูประวัติทั้งหมดพร้อม Tag กำกับในแต่ละ commit:

```bash
git log --oneline --decorate --graph
```

ผลลัพธ์ตัวอย่าง:

```
* 9f8e7d6 (HEAD -> main, tag: v2.0.0) BREAKING CHANGE: refactor to TodoApp object API
* 8e7d6c5 (tag: v1.0.0) Update documentation for v1.0.0 release
* 7d6c5b4 (tag: v0.3.1) Fix removeTodo id validation bug
* 6c5b4a3 (tag: v0.3.0) Add removeTodo function
* 5b4a3f2 (tag: v0.2.0) Add addTodo function
* 4a3f2e1 (tag: v0.1.0) Initial project setup
```

### ขั้นที่ 8: ทดลองสร้าง Hotfix Branch จาก Tag เก่า

สมมติว่ามีลูกค้าบางรายยังใช้เวอร์ชัน `v1.0.0` อยู่ และพบบั๊กที่ต้องแก้ด่วนโดยไม่กระทบเวอร์ชัน `v2.0.0` ที่กำลังพัฒนาต่ออยู่ ลองสร้าง hotfix branch จาก Tag `v1.0.0`:

```bash
git checkout -b hotfix/v1.0.1 v1.0.0
```

ตรวจสอบว่าอยู่ใน branch ใหม่จริง (ไม่ใช่ detached HEAD):

```bash
git status
```

ควรเห็นข้อความ `On branch hotfix/v1.0.1` แก้บั๊กแล้ว commit:

```bash
echo "// hotfix applied for v1.0.x line" >> app.js
git add app.js
git commit -m "Hotfix: critical bug in v1.0.x line"
git tag -a v1.0.1 -m "Hotfix release for v1.0.x line"
```

ตรวจสอบผลลัพธ์สุดท้ายทั้งหมดอีกครั้ง:

```bash
git tag --sort=v:refname
git log --all --oneline --decorate --graph
```

คุณจะเห็นว่าตอนนี้มีสอง "สาย" เวอร์ชันคู่ขนานกัน คือสาย `v1.0.x` (สำหรับลูกค้าเก่า) และสาย `v2.0.0` (สำหรับเวอร์ชันใหม่ที่มี breaking change) ซึ่งเป็นสถานการณ์ที่พบได้บ่อยมากในโปรเจกต์ระดับองค์กรจริง

### เฉลยแนวคิดสำคัญของแบบฝึกหัดนี้

1. **เวอร์ชันที่ขึ้นต้นด้วย `0.x.x`** ใช้สำหรับช่วงพัฒนาเริ่มต้นที่ API ยังไม่นิ่ง
2. **การเพิ่มฟีเจอร์ที่ไม่กระทบของเดิม** ให้เพิ่มเลข MINOR
3. **การแก้บั๊กเล็กน้อยที่ไม่เปลี่ยนพฤติกรรม** ให้เพิ่มเลข PATCH เท่านั้น
4. **การเปลี่ยนแปลงที่ทำให้โค้ดเดิมพัง (breaking change)** ต้องเพิ่มเลข MAJOR และรีเซ็ตตัวเลขที่เหลือ
5. **การแก้ไขเวอร์ชันเก่าที่ยัง release อยู่ (hotfix)** ต้องสร้าง branch จาก Tag ของเวอร์ชันนั้นเสมอ ไม่ใช่แก้บน branch หลักที่เดินหน้าไปไกลแล้ว
6. **ทุก Tag ที่สร้างในแบบฝึกหัดนี้ใช้ Annotated Tag ทั้งหมด** (มี `-a` และ `-m` เสมอ) ตามหลักการที่แนะนำใน Step 102

### ถ้าต้องการ Push ขึ้น GitHub จริง (ทางเลือกเสริม)

หากคุณมี repository บน GitHub ที่เชื่อมต่อไว้แล้ว สามารถลองฝึก push Tag ทั้งหมดขึ้นจริงได้ด้วย:

```bash
git remote add origin <URL ของ repository บน GitHub>
git push origin main
git push origin --tags
```

แล้วเข้าไปดูที่หน้า **Releases** หรือ **Tags** บนเว็บ GitHub เพื่อยืนยันว่า Tag ทุกตัวถูกส่งขึ้นไปเรียบร้อย พร้อมข้อความ (message) ที่ตั้งไว้ครบถ้วน (เนื้อหาการสร้าง Release อย่างเป็นทางการบน GitHub จากการใช้ Tag เหล่านี้ จะสอนอย่างละเอียดใน Part ที่เกี่ยวกับ GitHub Release ในเฟสถัดไป)

### Checklist ก่อนไป Part 12

ก่อนไปต่อ Part 12 ให้ตรวจสอบว่าคุณ:

- [ ] เข้าใจความแตกต่างระหว่าง Tag กับ Branch อย่างชัดเจน (Tag ไม่ขยับ, Branch ขยับตาม commit ใหม่)
- [ ] แยกความแตกต่างระหว่าง Lightweight Tag กับ Annotated Tag ได้ และรู้ว่าควรใช้ Annotated Tag เป็นค่าเริ่มต้นเสมอ
- [ ] สร้าง Tag ทั้งสองแบบได้ด้วย `git tag` และ `git tag -a -m`
- [ ] ใช้ `git tag -l` พร้อม pattern และ `git show <tag>` เพื่อดูรายละเอียด Tag ได้
- [ ] เข้าใจโครงสร้าง Semantic Versioning (`MAJOR.MINOR.PATCH`) และความหมายของแต่ละตัวเลข
- [ ] สร้าง Tag ย้อนหลังไปยัง commit เก่าได้ด้วย `git tag -a <name> <commit-hash>`
- [ ] ลบ Tag ได้ทั้งแบบ local (`git tag -d`) และแบบ remote (`git push origin --delete`)
- [ ] เข้าใจว่า `git push origin <tagname>` กับ `git push --tags` ต่างกันอย่างไร
- [ ] เข้าใจ Detached HEAD คืออะไร และรู้วิธีสร้าง branch จาก Tag เพื่อแก้ไขต่ออย่างปลอดภัย
- [ ] ทำแบบฝึกหัดจำลองประวัติ commit พร้อมติด Tag ตามหลัก Semver ครบทุกขั้นตอนด้วยตัวเอง

## สรุป Part 11

ใน Part นี้เราได้เรียนรู้ว่า:

1. **Tag คือป้ายชื่อที่ผูกกับ commit อย่างถาวร ไม่ขยับตามการ commit ใหม่** ต่างจาก Branch ที่เป็นเส้นทางการพัฒนาที่เคลื่อนที่ไปเรื่อย ๆ
2. **Git มี Tag สองประเภท** คือ Lightweight Tag (แค่ pointer เปล่า ๆ) และ Annotated Tag (object เต็มรูปแบบพร้อมชื่อผู้สร้าง วันที่ และข้อความ) — ควรใช้ Annotated Tag เป็นค่าเริ่มต้นเสมอสำหรับการ release จริง
3. **สร้าง Tag ได้ด้วย `git tag <name>`** สำหรับ Lightweight และ **`git tag -a <name> -m "message"`** สำหรับ Annotated
4. **ดูรายการ Tag ด้วย `git tag -l`** พร้อม pattern และดูรายละเอียดด้วย `git show <tag>`
5. **Semantic Versioning ใช้รูปแบบ `MAJOR.MINOR.PATCH`** — MAJOR สำหรับ breaking change, MINOR สำหรับฟีเจอร์ใหม่ที่ไม่กระทบของเดิม, PATCH สำหรับการแก้บั๊ก (จะเจาะลึกเพิ่มเติมใน Part 88)
6. **สามารถสร้าง Tag ย้อนหลังไปยัง commit เก่าได้** ด้วยการระบุ commit hash ต่อท้ายคำสั่งสร้าง Tag โดยไม่กระทบ HEAD ปัจจุบัน
7. **ลบ Tag ต้องทำสองขั้นตอนแยกกัน** คือ `git tag -d` สำหรับ local และ `git push origin --delete` สำหรับ remote
8. **Tag ไม่ถูก push ขึ้น remote โดยอัตโนมัติ** ต้องระบุชื่อ Tag หรือใช้ `--tags` อย่างจงใจเสมอ
9. **การ checkout ไปยัง Tag จะเข้าสู่ Detached HEAD** และหากต้องการแก้ไขโค้ดต่อจากจุดนั้น ต้องสร้าง branch ใหม่ทันทีเพื่อป้องกัน commit สูญหาย
10. **ฝึกฝนจริงด้วยการสร้างประวัติ commit จำลองและติด Tag ตามหลัก Semver** ตั้งแต่ `v0.1.0` ไปจนถึง `v2.0.0` พร้อมทดลองสร้าง hotfix branch จาก Tag เวอร์ชันเก่า
