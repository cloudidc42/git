## Step 571: ปัญหาที่ packfile แก้

ใน **Part 56** เราเรียนไปแล้วว่า Git เก็บทุกอย่างเป็น **object** สี่ชนิด (blob, tree, commit, tag) และแต่ละ object เมื่อถูกสร้างขึ้นใหม่ครั้งแรก (เช่นตอน `git add` หรือ `git commit`) จะถูกเขียนลงดิสก์ในรูปแบบที่เรียกว่า **loose object** — คือไฟล์เดี่ยว ๆ หนึ่งไฟล์ต่อหนึ่ง object เก็บอยู่ใต้ `.git/objects/`

ลองนึกภาพ repository ที่มีการทำงานมานานหลายปี มีนักพัฒนาหลายสิบคน commit กันวันละหลายสิบครั้ง เมื่อเวลาผ่านไป จำนวน object ในระบบจะเพิ่มขึ้นเรื่อย ๆ แบบไม่มีที่สิ้นสุด เพราะ Git ไม่เคย "ลบ" object เก่าออกเองโดยอัตโนมัติ (ประวัติต้องคงอยู่ตลอดไปตามธรรมชาติของ VCS) ปัญหาที่ตามมาจากการเก็บทุกอย่างเป็น loose object ล้วน ๆ มีอยู่ 3 ประการหลัก:

### 1. กินพื้นที่ดิสก์มากเกินความจำเป็น

Loose object แต่ละไฟล์ถูกบีบอัดด้วย zlib (DEFLATE) แยกกันเป็นเอกเทศ ไม่มีการอ้างอิงถึงกันระหว่าง object ที่มีเนื้อหาคล้ายกัน ยกตัวอย่างเช่น ถ้าคุณมีไฟล์ `README.md` ขนาด 50 KB แล้วแก้ไขแค่ 2 บรรทัดแล้ว commit ใหม่ Git จะสร้าง blob object ใหม่ทั้งก้อนสำหรับไฟล์เวอร์ชันใหม่นี้ (เพราะ Git เก็บแบบ snapshot ไม่ใช่ diff ตามที่เรียนใน Part 01) ถ้าเก็บแบบ loose object ล้วน ๆ ก็คือมีไฟล์ที่ถูกบีบอัดแยกกันสองไฟล์ที่เนื้อหาเหมือนกัน 99% เก็บซ้ำซ้อนอยู่บนดิสก์

เมื่อคูณด้วยจำนวน commit หลักพันหรือหมื่นครั้งตลอดอายุของ repository ขนาดของโฟลเดอร์ `.git` จะบวมขึ้นเรื่อย ๆ อย่างไม่สมเหตุสมผล ทั้งที่จริง ๆ แล้วเนื้อหาส่วนใหญ่ระหว่าง object ที่คล้ายกันนั้น "ซ้ำกัน" เกือบทั้งหมด เพียงแต่ Git ยังไม่ได้นำความคล้ายคลึงนี้มาใช้ประโยชน์ตอนที่เก็บเป็น loose object

### 2. Filesystem มีปัญหากับไฟล์เล็ก ๆ จำนวนมาก

Loose object หนึ่ง object คือหนึ่งไฟล์ในระบบไฟล์ (filesystem) เมื่อ repository มี object รวมกันหลักแสนหรือหลักล้าน (เรื่องปกติสำหรับโปรเจกต์ใหญ่อย่าง Linux Kernel หรือ Chromium) การมีไฟล์เล็ก ๆ กระจัดกระจายจำนวนมหาศาลขนาดนี้สร้างปัญหาให้กับระบบไฟล์เอง:

- แต่ละไฟล์บน filesystem ส่วนใหญ่จะกิน**อย่างน้อยหนึ่ง block** ของดิสก์เสมอ (เช่น 4 KB) แม้ตัวไฟล์จะเล็กกว่านั้นมาก ทำให้เกิด **internal fragmentation** — พื้นที่ที่ถูกจองไว้แต่ใช้งานจริงไม่เต็ม
- การเปิด/อ่านไฟล์แต่ละไฟล์มี overhead ของระบบปฏิบัติการ (system call, metadata lookup, inode lookup) เมื่อต้องไล่อ่าน object นับหมื่นนับแสนไฟล์ (เช่นตอน `git log --all`, `git gc`, หรือการ walk ทั้งประวัติ) ความเร็วโดยรวมจะช้าลงมาก เมื่อเทียบกับการอ่านไฟล์ใหญ่ไฟล์เดียวที่มีข้อมูลเรียงต่อกัน (sequential read)
- โฟลเดอร์ `.git/objects/xx/` แต่ละโฟลเดอร์ย่อย (แบ่งตาม 2 ตัวอักษรแรกของ SHA) อาจมีไฟล์สะสมอยู่เป็นพัน ๆ ไฟล์ ทำให้การ list directory หรือค้นหาไฟล์ช้าลงตามจำนวนไฟล์ในโฟลเดอร์

### 3. การถ่ายโอนผ่านเครือข่ายช้าและกินแบนด์วิดท์มาก

นี่คือปัญหาที่ร้ายแรงที่สุดในทางปฏิบัติ เวลาคุณ `git clone` repository หนึ่งครั้ง Git ต้องส่ง object **ทุกตัว**ที่จำเป็นสำหรับสร้างประวัติทั้งหมดของ repository ไปให้เครื่องปลายทาง ถ้า object เหล่านั้นถูกส่งในรูปแบบ loose object ที่ไม่มีการบีบอัดข้ามกัน (cross-object compression) เลย จะเกิดปัญหา:

- ขนาดข้อมูลที่ต้องส่งผ่านเครือข่ายจะใหญ่กว่าที่ควรจะเป็นมาก เพราะไม่ได้ใช้ประโยชน์จากความคล้ายคลึงกันระหว่าง object รุ่นต่าง ๆ ของไฟล์เดียวกัน
- การส่งไฟล์เดี่ยว ๆ จำนวนมากผ่าน protocol เครือข่าย (แม้จะรวมเป็น stream เดียวก็ตาม) มี overhead ต่อ object สูงกว่าการส่งเป็นก้อนใหญ่ก้อนเดียวที่มีโครงสร้างดัชนีในตัว
- Repository ขนาดใหญ่ที่มีประวัติหลายปีอาจมี object รวมกันหลายแสนตัว การ clone แบบ loose object ล้วน ๆ อาจใช้เวลาหลายสิบนาทีหรือเป็นชั่วโมง ซึ่งไม่สามารถยอมรับได้ในทางปฏิบัติ

### ทางออก: Packfile

Git แก้ปัญหาทั้ง 3 ข้อนี้ด้วยแนวคิดที่เรียกว่า **packfile** — การนำ object จำนวนมากมา**บีบอัดรวมกันเป็นไฟล์เดียว** โดยใช้เทคนิค **delta compression** ระหว่าง object ที่มีเนื้อหาคล้ายกัน (จะอธิบายละเอียดใน Step 575) ผลลัพธ์คือ:

| ปัญหาเดิม (loose object ล้วน) | สิ่งที่ packfile แก้ให้ |
|---|---|
| แต่ละ object บีบอัดแยกกัน ไม่ใช้ความคล้ายคลึงข้าม object | บีบอัดร่วมกันด้วย delta ทำให้ขนาดรวมเล็กลงมาก |
| ไฟล์เล็ก ๆ จำนวนมหาศาลบน filesystem | รวมเป็นไฟล์ใหญ่ 1-2 ไฟล์ (`.pack` + `.idx`) |
| Clone/fetch/push ช้า กินแบนด์วิดท์มาก | ส่งเป็น packfile ก้อนเดียวที่บีบอัดแล้ว เร็วกว่ามาก |
| การ walk ประวัติช้าเพราะต้องเปิดไฟล์ทีละไฟล์ | อ่านจากไฟล์ pack ต่อเนื่องกันได้เร็วกว่า |

Packfile จึงเป็นกลไกสำคัญที่ทำให้ Git ยังคงเร็วและประหยัดพื้นที่แม้ repository จะโตขึ้นมหาศาลตามกาลเวลา และเป็นรูปแบบเดียวที่ Git ใช้ในการถ่ายโอนข้อมูลผ่านเครือข่ายเสมอ (ไม่ว่าจะ clone, fetch หรือ push ก็ตาม — ไม่มีทางที่ Git จะส่ง loose object ทีละไฟล์ผ่านเครือข่ายในกรณีทั่วไป)

## Step 572: Loose objects vs Packed objects

ก่อนจะเจาะลึกโครงสร้างของ packfile เราต้องเข้าใจความแตกต่างระหว่าง object สองรูปแบบนี้ให้ชัดเจนก่อน เพราะ **ตลอดเวลาที่คุณทำงานกับ Git จริง ๆ object ในระบบของคุณจะอยู่ผสมกันทั้งสองแบบเสมอ**

### Loose object

Loose object คือรูปแบบที่ Git สร้างขึ้นก่อนเสมอเมื่อมีการเขียน object ใหม่ (เช่น `git add`, `git commit`, `git hash-object -w`) โครงสร้างของมันคือ:

```
.git/objects/
├── 4b/
│   └── 825dc642cb6eb9a060e54bf8d69288fbee4904   ← object เดี่ยว 1 ไฟล์
├── a8/
│   └── 7f3a8b1e5e8f9c3d2a1b0e9d8c7b6a5f4e3d2c1
└── ...
```

ชื่อไฟล์คือ SHA-1 (หรือ SHA-256 ถ้าใช้ repository format ใหม่) ของ object นั้น โดยเอา 2 ตัวอักษรแรกมาเป็นชื่อโฟลเดอร์ และ 38 ตัวที่เหลือเป็นชื่อไฟล์ เนื้อหาข้างในคือ:

```
<header>\0<content>
```

ที่ถูกบีบอัดด้วย **zlib deflate** ทั้งก้อน โดย header มีรูปแบบ `<type> <size>` เช่น `blob 1234` หรือ `commit 245`

**คุณสมบัติของ loose object:**

- สร้างง่ายและเร็ว — เขียนทันทีที่มี content ใหม่โดยไม่ต้องรอ
- บีบอัดแบบ**เอกเทศ** ไม่มีการอ้างอิงถึง object อื่นเลย แต่ละไฟล์บีบอัดตัวเองล้วน ๆ
- อ่าน/เขียนง่าย ตรงไปตรงมา ใช้ zlib inflate อย่างเดียวก็ถอดรหัสได้
- **ไม่มีดัชนี** — การหา object จาก SHA ทำได้โดยคำนวณ path ตรง ๆ จาก SHA (`objects/xx/yyyy...`) ไม่ต้องมีไฟล์ดัชนีแยก

### Packed object

Packed object คือ object ที่ถูกนำมารวมกันไว้ในไฟล์ `.pack` ซึ่งอาจเก็บในรูปแบบ**เต็ม (full/undeltified)** หรือ**เก็บเป็น delta** เทียบกับ object อื่นในแพ็คเดียวกันก็ได้ (อธิบายละเอียดใน Step 575) พร้อมกับมีไฟล์ `.idx` คู่กันเพื่อทำหน้าที่เป็นดัชนีค้นหา

```
.git/objects/pack/
├── pack-3f8a2b91c4d5e6f7a8b9c0d1e2f3a4b5c6d7e8f9.pack
├── pack-3f8a2b91c4d5e6f7a8b9c0d1e2f3a4b5c6d7e8f9.idx
├── pack-1a2b3c4d5e6f7a8b9c0d1e2f3a4b5c6d7e8f9a0b.pack
└── pack-1a2b3c4d5e6f7a8b9c0d1e2f3a4b5c6d7e8f9a0b.idx
```

**คุณสมบัติของ packed object:**

- บีบอัดร่วมกันได้ — object ที่คล้ายกันสามารถเก็บเป็น delta เทียบกับ object อื่นได้ ประหยัดพื้นที่กว่ามาก
- ต้องมี `.idx` คู่กันเสมอเพื่อค้นหา object จาก SHA ได้อย่างรวดเร็ว (ไม่งั้นต้องไล่อ่านทั้งไฟล์ pack ทีละ object)
- การอ่าน object ที่เป็น delta ต้องไล่ apply delta chain ย้อนกลับไปจนถึง base object ที่เป็น full object ก่อน จึงจะได้เนื้อหาจริง (มี cost ในการคำนวณเพิ่มขึ้นเล็กน้อยเมื่อเทียบกับ loose object แต่แลกมาด้วยพื้นที่ที่เล็กลงมาก)
- Repository หนึ่งอาจมีไฟล์ pack ได้หลายคู่พร้อมกัน (multi-pack) และ Git จะค้นหาข้าม pack ทั้งหมดโดยอัตโนมัติเมื่อหา object

### ทำไมต้องมีทั้งสองแบบอยู่ร่วมกัน

คำถามที่พบบ่อยคือ "ทำไม Git ไม่เก็บทุกอย่างเป็น pack ไปเลยตั้งแต่แรก" คำตอบคือการสร้าง packfile ที่มีประสิทธิภาพ (หา delta ที่ดีที่สุดระหว่าง object) เป็นงานที่ **หนักในเชิงการคำนวณ** (ต้องเปรียบเทียบ object จำนวนมากเพื่อหาคู่ที่คล้ายกันที่สุด) จึงไม่เหมาะที่จะทำทุกครั้งที่มี object ใหม่เข้ามาแบบ real-time

Git จึงเลือกกลยุทธ์แบบ **write-fast, compact-later**:

1. เมื่อมี object ใหม่ (เช่นตอน commit) — เขียนเป็น **loose object** ทันที เร็วและง่าย ไม่ block การทำงานของผู้ใช้
2. เมื่อถึงเวลาที่เหมาะสม (loose object สะสมมากพอ หรือถูกเรียกโดยตรง) — รัน **`git gc`** หรือ **`git repack`** เพื่อรวบรวม loose object เหล่านั้นมาอัดเป็น packfile คุณภาพสูงในคราวเดียว

การทำงานแบบนี้เหมือนกับการ "เก็บกวาดบ้านเป็นระยะ ๆ" แทนที่จะพยายามจัดบ้านให้เป๊ะทุกครั้งที่มีของใหม่เข้ามาชิ้นเดียว ซึ่งจะทำให้ทุกการกระทำช้าลงโดยไม่จำเป็น

### สรุปเปรียบเทียบ

| คุณสมบัติ | Loose Object | Packed Object |
|---|---|---|
| จำนวนไฟล์บนดิสก์ | 1 ไฟล์ต่อ 1 object | รวมหลายพัน/หมื่น object ไว้ในไฟล์เดียว |
| การบีบอัด | zlib เอกเทศต่อ object | zlib + delta compression ข้าม object |
| ความเร็วในการสร้าง | เร็ว เขียนได้ทันที | ช้ากว่า (ต้องคำนวณหา delta ที่ดีที่สุด) |
| ความเร็วในการอ่าน | เร็ว (อ่านตรง ไม่ต้อง apply delta) | อาจต้องไล่ delta chain ก่อนได้เนื้อหาจริง |
| ต้องมีดัชนีไหม | ไม่ต้อง (path มาจาก SHA ตรง ๆ) | ต้องมี `.idx` คู่กันเสมอ |
| ขนาดรวมบนดิสก์ | ใหญ่กว่ามาก | เล็กกว่ามาก (บางกรณีเล็กกว่าหลายสิบเท่า) |
| ใช้ตอนไหน | หลัง `git add`/`commit` ใหม่ ๆ | หลัง `git gc`/`repack` หรือรับมาจาก push/fetch/clone |

ในทางปฏิบัติ Git ดูแลเรื่องนี้ให้เราโดยอัตโนมัติเกือบทั้งหมด — คำสั่งระดับ porcelain อย่าง `git cat-file`, `git log`, `git show` จะทำงานถูกต้องเหมือนกันไม่ว่า object นั้นจะเป็น loose หรือ packed ก็ตาม เพราะ Git มีชั้นนามธรรม (object database abstraction) ที่ค้นหา object จาก SHA โดยไม่สนใจว่ามันถูกเก็บในรูปแบบไหนอยู่เบื้องหลัง

## Step 573: `git gc` คืออะไร ทำอะไรบ้าง

`git gc` ย่อมาจาก **garbage collection** เป็นคำสั่งที่ทำหน้าที่ "ทำความสะอาดและปรับปรุงประสิทธิภาพ" ของ repository โดยรวม ไม่ใช่แค่การอัด pack เพียงอย่างเดียว แต่เป็นชุดของงานบำรุงรักษาหลายอย่างรวมกัน

### สิ่งที่ `git gc` ทำภายใน (โดยสรุป)

เมื่อรัน `git gc` (แบบ default โดยไม่มี flag) Git จะทำงานหลายอย่างต่อเนื่องกันตามลำดับประมาณนี้:

1. **`git pack-refs --all --prune`** — รวบรวม reference ทั้งหมด (branch, tag) ที่ปกติเก็บเป็นไฟล์เดี่ยว ๆ ใน `.git/refs/` ให้มารวมอยู่ในไฟล์เดียวคือ `.git/packed-refs` เพื่อลดจำนวนไฟล์เล็ก ๆ ในระบบ (คล้ายแนวคิดเดียวกับ packfile แต่ใช้กับ ref แทน object)
2. **`git reflog expire`** — ลบรายการใน reflog ที่หมดอายุแล้ว (ตาม `gc.reflogExpire` ค่า default คือ 90 วัน สำหรับ entry ที่ยัง reachable และ `gc.reflogExpireUnreachable` ค่า default 30 วัน สำหรับ entry ที่ unreachable) reflog คือประวัติการเปลี่ยนแปลงของ HEAD/branch ที่ใช้กู้คืนงานที่ดูเหมือนหายไป
3. **`git repack -d -l`** (โดยประมาณ) — รวบรวม loose object ทั้งหมดที่มีอยู่ พร้อมกับ pack เดิมที่มีอยู่แล้ว มาอัดรวมกันใหม่เป็น packfile ชุดใหม่ที่มีประสิทธิภาพกว่า แล้วลบ pack เก่าที่ซ้ำซ้อนทิ้ง (จะอธิบายรายละเอียด flag เหล่านี้ใน Step 576)
4. **`git prune`** — ลบ **loose object ที่ unreachable** (object ที่ไม่มี branch, tag, หรือ ref ใด ๆ ชี้ถึงอีกต่อไป และไม่ถูกอ้างอิงจาก reflog ที่ยังไม่หมดอายุ) ออกจากดิสก์อย่างถาวร โดยจะลบเฉพาะ object ที่ "เก่าพอ" แล้วเท่านั้น (ตาม grace period ที่กำหนดโดย `gc.pruneExpire` ค่า default คือ 2 สัปดาห์)
5. **`git worktree prune`** — ลบข้อมูลของ worktree ที่ถูกลบไปแล้วแต่ยังมี metadata ค้างอยู่
6. **`git rerere gc`** — ลบข้อมูล conflict resolution ที่บันทึกไว้โดยฟีเจอร์ `rerere` ที่หมดอายุแล้ว

### ทำไม unreachable object ต้องมี grace period ก่อนถูกลบ

จุดที่สำคัญมากคือ Git **ไม่ลบ unreachable object ทันที** แม้จะรู้ว่ามันไม่ถูกอ้างอิงจากที่ไหนแล้วก็ตาม เหตุผลคือ:

> **มีหน้าต่างเวลาสั้น ๆ ระหว่างตอนที่ Git สร้าง object ใหม่ กับตอนที่ ref ถูกอัปเดตให้ชี้ไปยัง object นั้น** ถ้ามี process อื่น (เช่น `git gc` ที่รันพร้อมกัน) มาเก็บกวาด object ในช่วงเวลาสั้น ๆ นี้พอดี อาจเข้าใจผิดว่า object ที่เพิ่งสร้างเสร็จใหม่ ๆ (แต่ยังไม่ทันมี ref ชี้ถึง) เป็นขยะ แล้วลบทิ้งไปโดยไม่ตั้งใจ ทำให้ข้อมูลเสียหาย

Grace period (ค่า default 2 สัปดาห์สำหรับ `gc.pruneExpire`) จึงเป็นกลไกความปลอดภัยที่สำคัญ — object ที่เพิ่งกลายเป็น unreachable เร็ว ๆ นี้ (อายุน้อยกว่า 2 สัปดาห์) จะยังไม่ถูกลบ เผื่อกรณีที่คุณทำ `git reset --hard` พลาด หรือลบ branch ผิดตัว แล้วอยากกู้คืนผ่าน `git reflog` + `git checkout <sha>`

### `git gc --auto` — การรันแบบอัตโนมัติเบื้องหลัง

Git ไม่ได้บังคับให้คุณรัน `git gc` ด้วยตัวเองตลอดเวลา แต่คำสั่งหลายตัว (เช่น `git commit`, `git merge`, `git fetch`) จะเรียก **`git gc --auto`** โดยอัตโนมัติเป็นครั้งคราวเบื้องหลัง โดยจะ**ตรวจสอบก่อน**ว่าจำนวน loose object หรือจำนวน pack file เกิน threshold ที่กำหนดไว้หรือยัง ถ้ายังไม่เกินก็จะไม่ทำอะไรเลย (เพื่อไม่ให้เสียเวลาโดยไม่จำเป็น)

Threshold สำคัญที่ควบคุมพฤติกรรมนี้:

| ตัวแปร config | ค่า default | ความหมาย |
|---|---|---|
| `gc.auto` | 6700 | ถ้าจำนวน loose object เกินค่านี้ จะสั่ง repack อัตโนมัติ (ตั้งเป็น 0 เพื่อปิดการรัน auto gc ด้วย loose object) |
| `gc.autoPackLimit` | 50 | ถ้าจำนวนไฟล์ pack (ที่ไม่ใช่ผลจาก keep) เกินค่านี้ จะสั่งรวม pack เข้าด้วยกัน |
| `gc.pruneExpire` | "2.weeks.ago" | อายุขั้นต่ำก่อน unreachable object จะถูกลบจริง |
| `gc.reflogExpire` | "90.days" | อายุขั้นต่ำก่อน reflog entry ที่ reachable จะหมดอายุ |
| `gc.reflogExpireUnreachable` | "30.days" | อายุขั้นต่ำก่อน reflog entry ที่ unreachable จะหมดอายุ |

คุณสามารถดูค่าปัจจุบันของ config เหล่านี้ได้ด้วย:

```bash
git config --get gc.auto
git config --get gc.pruneExpire
```

และปรับแต่งได้ตามความเหมาะสมของแต่ละ repository เช่น repository ที่มีขนาดใหญ่มากอาจต้องการ threshold ที่สูงขึ้นเพื่อไม่ให้ `git gc --auto` ทำงานบ่อยเกินไปจนรบกวน workflow ประจำวัน

### คำสั่งย่อยที่มักใช้คู่กับ `git gc`

```bash
# รัน gc แบบธรรมดา (เร็ว เหมาะกับการรันบ่อย ๆ)
git gc

# รัน gc แบบเข้มข้นที่สุด เพื่อบีบอัดให้ได้ขนาดเล็กที่สุดเท่าที่จะทำได้
# ใช้เวลานานกว่ามาก เหมาะกับการรันนาน ๆ ครั้งกับ repository ขนาดใหญ่
git gc --aggressive

# บังคับให้รันแม้จะมี gc process อื่นทำงานค้างอยู่ (ระวังใช้)
git gc --force

# แสดงรายละเอียดขณะทำงาน
git gc --verbose
```

**ข้อควรระวังของ `--aggressive`:** flag นี้จะบังคับให้ Git คำนวณหา delta ที่ดีที่สุดใหม่ทั้งหมดสำหรับทุก object (ไม่ใช่แค่ loose object ใหม่) โดยเพิ่มค่า `--window` และ `--depth` ให้สูงขึ้นมาก (ใช้เวลาการคำนวณนานกว่าปกติหลายเท่า) เหมาะกับการรันเป็นครั้งคราวกับ repository ที่ไม่ได้ใช้งานหนักบ่อย ๆ ไม่ใช่คำสั่งที่ควรรันเป็นประจำทุกวัน

## Step 574: โครงสร้างไฟล์ packfile (`.pack` และ `.idx`)

ตอนนี้เรามาเจาะลึกดูว่าไฟล์ `.pack` และ `.idx` มีโครงสร้างภายในหน้าตาเป็นอย่างไรจริง ๆ

### โครงสร้างไฟล์ `.pack`

ไฟล์ packfile (`pack-<SHA>.pack`) มีโครงสร้างระดับ byte ประมาณนี้:

```
┌─────────────────────────────────────────┐
│ Header (12 bytes)                        │
│  - "PACK" (4 bytes, magic number)        │
│  - Version number (4 bytes, ปัจจุบันคือ 2) │
│  - จำนวน object ทั้งหมดในแพ็ค (4 bytes)     │
├─────────────────────────────────────────┤
│ Object entry #1                          │
│  - Type + Size (variable-length header)  │
│  - [Base reference ถ้าเป็น delta object]   │
│  - Compressed data (zlib deflate)        │
├─────────────────────────────────────────┤
│ Object entry #2                          │
│  ...                                     │
├─────────────────────────────────────────┤
│ Object entry #N                          │
├─────────────────────────────────────────┤
│ Trailer: SHA-1/SHA-256 checksum          │
│ (checksum ของเนื้อหาทั้งหมดก่อนหน้านี้)     │
└─────────────────────────────────────────┘
```

**รายละเอียดของแต่ละส่วน:**

- **Header**: 4 ไบต์แรกเป็นข้อความ `PACK` เพื่อระบุ magic number, ตามด้วย version (2 ในปัจจุบัน — version 3 มีการพูดถึงแต่ไม่ได้ใช้งานจริง) และจำนวน object ทั้งหมด (32-bit big-endian integer)
- **Object entry**: แต่ละ entry เริ่มด้วย header แบบความยาวผันแปร (variable-length) ที่เก็บทั้ง **object type** (1 ใน 7 ค่า: OBJ_COMMIT, OBJ_TREE, OBJ_BLOB, OBJ_TAG, OBJ_OFS_DELTA, OBJ_REF_DELTA และค่าที่สงวนไว้) และ **ขนาดของข้อมูลหลัง decompress** โดยเข้ารหัสแบบ variable-length integer (bit ที่ 8 ของแต่ละไบต์บอกว่ามีไบต์ถัดไปต่อหรือไม่)
- ถ้า type เป็น **OFS_DELTA** หรือ **REF_DELTA** จะมีข้อมูลเพิ่มเติมระบุว่า object นี้เป็น delta เทียบกับ object ฐาน (base object) ตัวไหน (อธิบายละเอียดใน Step 575)
- **Compressed data**: เนื้อหาจริงของ object (หรือ delta instruction ถ้าเป็น delta object) ถูกบีบอัดด้วย zlib deflate อีกชั้นหนึ่ง
- **Trailer**: 20 ไบต์สุดท้ายของไฟล์ (หรือ 32 ไบต์ถ้าใช้ SHA-256) คือ checksum ของเนื้อหาทั้งหมดก่อนหน้านี้ในไฟล์ ใช้ตรวจสอบว่าไฟล์ pack ไม่เสียหายหรือถูกแก้ไข

### โครงสร้างไฟล์ `.idx`

ปัญหาของไฟล์ `.pack` เดี่ยว ๆ คือมันเป็นแค่ **stream ของ object เรียงต่อกัน** ไม่มีการจัดเรียงตาม SHA และไม่มีตำแหน่ง (offset) บอกไว้ล่วงหน้า ถ้า Git ต้องการหา object ตัวหนึ่งจาก SHA ของมัน มันจะต้องไล่อ่านทั้งไฟล์ทีละ object ตั้งแต่ต้นจนกว่าจะเจอ — ซึ่งช้ามากถ้า pack มีขนาดใหญ่

ไฟล์ `.idx` (index) จึงถูกสร้างคู่กับทุก `.pack` เสมอ เพื่อทำหน้าที่เป็น **ดัชนีค้นหาแบบสุ่ม (random access index)** โครงสร้างของมัน (idx version 2 ซึ่งเป็นมาตรฐานปัจจุบัน) มีดังนี้:

```
┌─────────────────────────────────────────┐
│ Magic number + Version (8 bytes)         │
├─────────────────────────────────────────┤
│ Fanout table (256 entries × 4 bytes)     │
│  - แต่ละช่องบอกจำนวน object สะสมที่ SHA    │
│    ขึ้นต้นด้วยไบต์นั้นหรือน้อยกว่า            │
├─────────────────────────────────────────┤
│ ตาราง SHA ของ object ทั้งหมด               │
│ (เรียงจากน้อยไปมาก, 20 ไบต์ต่อ object)     │
├─────────────────────────────────────────┤
│ ตาราง CRC32 checksum ของแต่ละ object      │
│ (4 ไบต์ต่อ object)                        │
├─────────────────────────────────────────┤
│ ตาราง offset ตำแหน่งของแต่ละ object        │
│ ในไฟล์ .pack (4 ไบต์ต่อ object)            │
├─────────────────────────────────────────┤
│ ตาราง 64-bit offset (เฉพาะกรณี pack       │
│ มีขนาดใหญ่กว่า 2GB เท่านั้น)                │
├─────────────────────────────────────────┤
│ Checksum ของไฟล์ pack ที่คู่กัน (20 ไบต์)  │
├─────────────────────────────────────────┤
│ Checksum ของไฟล์ idx เอง (20 ไบต์)        │
└─────────────────────────────────────────┘
```

**Fanout table** คือกลไกที่ทำให้การค้นหาเร็วมาก — เพราะ SHA ถูกเรียงลำดับไว้แล้ว การจะหาว่า SHA ที่ขึ้นต้นด้วยไบต์ `0xa8` อยู่ที่ตำแหน่งไหนในตาราง สามารถกระโดดไปที่ช่อง `fanout[0xa8]` ได้ทันทีเพื่อรู้ช่วงตำแหน่งคร่าว ๆ แล้วค่อยทำ **binary search** ภายในช่วงแคบ ๆ นั้นต่อ ทำให้การค้นหา object หนึ่งตัวจาก SHA ใน pack ที่มี object นับแสนตัวใช้เวลาระดับ **O(log n)** เท่านั้น ไม่ใช่ O(n)

### ขั้นตอนการหา object จาก SHA ผ่าน `.idx`

1. ดูไบต์แรกของ SHA ที่ต้องการหา → เปิด fanout table เพื่อรู้ช่วงตำแหน่งใน SHA table
2. ทำ binary search ใน SHA table ภายในช่วงนั้นเพื่อหาตำแหน่ง (index) ที่ตรงกับ SHA เป๊ะ
3. ใช้ตำแหน่ง (index) เดียวกันนั้นไปเปิดดูใน offset table เพื่อรู้ว่า object นี้อยู่ที่ byte offset เท่าไหร่ในไฟล์ `.pack`
4. Seek ไปยัง offset นั้นในไฟล์ `.pack` โดยตรง แล้วอ่าน object entry ออกมา (ถ้าเป็น delta ต้อง apply chain ต่อ)

กระบวนการนี้ทั้งหมดเกิดขึ้นเร็วมาก (เป็น millisecond) แม้ pack จะมี object นับล้านตัวก็ตาม เพราะไม่ต้องอ่านไฟล์ pack ทั้งไฟล์เลย — นี่คือเหตุผลว่าทำไม `.idx` ถึงเป็นไฟล์ที่ **ขาดไม่ได้** เมื่อทำงานกับ `.pack` (ถ้าไฟล์ `.idx` หายไป Git จะสร้างมันขึ้นมาใหม่ได้ด้วยคำสั่ง `git index-pack` โดยอ่านจากเนื้อหาใน `.pack` เอง)

### Multi-Pack-Index (MIDX)

ในเวอร์ชันใหม่ ๆ ของ Git (ตั้งแต่ 2.19 เป็นต้นมา) ยังมีฟีเจอร์ **multi-pack-index** (`.git/objects/pack/multi-pack-index`) เพิ่มเข้ามา ซึ่งทำหน้าที่เป็นดัชนีรวมสำหรับ pack file **หลายไฟล์พร้อมกัน** ในกรณีที่ repository มี pack file หลายคู่ (เช่นยังไม่ได้ repack รวมเป็นไฟล์เดียว) ทำให้ไม่ต้องไล่เปิด `.idx` ของทุก pack ทีละไฟล์เพื่อค้นหา object แต่มาดูที่ MIDX ไฟล์เดียวก็รู้ทันทีว่า object นั้นอยู่ใน pack ไฟล์ไหน สร้างได้ด้วยคำสั่ง `git multi-pack-index write`

## Step 575: Delta compression คืออะไร

**Delta compression** คือหัวใจสำคัญที่สุดที่ทำให้ packfile มีขนาดเล็กกว่าการเก็บ loose object หลายสิบเท่าในหลายกรณี แนวคิดพื้นฐานคือ:

> **แทนที่จะเก็บเนื้อหาเต็มของ object ที่คล้ายกันซ้ำ ๆ กันหลายรอบ Git จะเลือก object หนึ่งตัวเป็น "base" (เก็บแบบเต็ม) แล้วเก็บ object ที่เหลือที่คล้ายกันเป็นแค่ "ชุดคำสั่งการแปลง" (delta instructions) ว่าจะต้อง copy ส่วนไหนจาก base object มา และ insert ข้อมูลใหม่ตรงไหนบ้าง เพื่อสร้างเนื้อหาของ object นั้นขึ้นมาใหม่**

### ตัวอย่างแนวคิดแบบง่าย

สมมติมี blob สองตัว:

```
Base object (v1):
"function hello() {\n  console.log('Hello, World!');\n}\n"

Object ใหม่ (v2) — แก้ข้อความใน console.log เพียงจุดเดียว:
"function hello() {\n  console.log('Hello, Git!');\n}\n"
```

แทนที่จะเก็บ v2 เป็นเนื้อหาเต็มอีกชุด Git จะเก็บ v2 เป็น delta ประมาณนี้ (แบบย่อเพื่อความเข้าใจ ไม่ใช่ syntax จริงของ binary format):

```
COPY  bytes 0-32   จาก base   ("function hello() {\n  console.log('Hello, ")
INSERT "Git"
COPY  bytes 41-56  จาก base   ("!');\n}\n")
```

จะเห็นว่า delta instruction มีขนาดเล็กกว่าการเก็บเนื้อหาเต็มของ v2 มาก เพราะข้อมูลส่วนใหญ่เหมือนกับ base object เกือบทั้งหมด มีแค่คำว่า "World" ที่ถูกแทนที่ด้วย "Git" เท่านั้น

### รูปแบบ delta จริงที่ Git ใช้

Git ใช้รูปแบบ delta ที่เรียกว่า **copy/insert delta** ซึ่งประกอบด้วยคำสั่งสองแบบเท่านั้น:

1. **Copy** — คัดลอกช่วง byte จาก base object (ระบุ offset และความยาว)
2. **Insert** — แทรกข้อมูลใหม่ที่ไม่มีอยู่ใน base object (เก็บข้อมูลจริงตรง ๆ ในตัว delta)

ชุดคำสั่งเหล่านี้เมื่อ apply กับ base object ตามลำดับ จะได้เนื้อหาของ object ปลายทางกลับมาครบถ้วนตรงตาม byte ทุกประการ (Git ตรวจสอบด้วยการเทียบ SHA หลัง apply delta เสมอ เพื่อความมั่นใจว่าข้อมูลไม่เพี้ยน)

### OFS_DELTA vs REF_DELTA

เวลา Git เก็บว่า object ตัวหนึ่งเป็น delta เทียบกับ object ฐานตัวไหน มันมี 2 วิธีอ้างอิงถึง base object:

| รูปแบบ | วิธีอ้างอิง base | ใช้ตอนไหน |
|---|---|---|
| **OFS_DELTA** (offset delta) | อ้างอิงด้วย **ระยะห่าง (offset)** ย้อนกลับไปจากตำแหน่งปัจจุบันในไฟล์ pack เดียวกัน | ใช้เมื่อ base object อยู่ใน pack เดียวกัน — ประหยัดกว่าเพราะเลขระยะห่างมักสั้นกว่า 20 ไบต์ของ SHA เต็ม |
| **REF_DELTA** (reference delta) | อ้างอิงด้วย **SHA เต็ม 20 ไบต์** ของ base object | ใช้เมื่อ base object **ไม่ได้อยู่ใน pack เดียวกัน** (เช่นตอนสร้าง "thin pack" สำหรับส่งผ่านเครือข่าย ที่ base object มีอยู่แล้วฝั่งรับ ไม่จำเป็นต้องส่งซ้ำ) |

โดยทั่วไป pack ที่เก็บอยู่บนดิสก์ถาวร (หลัง `git repack` หรือ `git index-pack` เสร็จสมบูรณ์) จะใช้ **OFS_DELTA** เป็นหลักเพราะประหยัดพื้นที่กว่า ส่วน **REF_DELTA** มักพบใน "thin pack" ที่ถูกส่งผ่านเครือข่ายชั่วคราว (จะอธิบายเพิ่มใน Step 578)

### กระบวนการหา delta ที่ดีที่สุด (Delta selection)

การหาว่า object ไหนควรเป็น base และ object ไหนควรเก็บเป็น delta เทียบกับใคร เป็นปัญหาที่คำนวณหนักมาก (การเทียบทุกคู่ที่เป็นไปได้ในทางทฤษฎีคือ O(n²) ซึ่งไม่สามารถทำได้จริงกับ object นับล้านตัว) Git จึงใช้ **heuristic** เพื่อลดขอบเขตการค้นหาให้แคบลง:

1. **จัดกลุ่ม object ตามชื่อ path และขนาด** — object ที่มีแนวโน้มจะคล้ายกัน (คือไฟล์เดียวกันแต่คนละเวอร์ชัน) มักจะมีชื่อไฟล์เดิม (แม้ Git จะไม่เก็บชื่อไฟล์ไว้ใน blob object โดยตรง แต่ Git ใช้ข้อมูลจาก tree entry ประกอบการจัดกลุ่ม) และมีขนาดใกล้เคียงกัน
2. **เรียง object ตามขนาดจากใหญ่ไปเล็ก** แล้วเปรียบเทียบเฉพาะกับ object ที่อยู่ใน **sliding window** (หน้าต่างขนาดจำกัด) รอบ ๆ ตำแหน่งนั้นเท่านั้น ไม่เทียบกับทุก object ในระบบ
3. ขนาดของ window นี้ควบคุมได้ด้วย `--window` (ค่า default คือ 10 หมายถึงเทียบกับ object ข้างเคียง 10 ตัว)
4. **ความลึกของ delta chain** (จำนวนครั้งสูงสุดที่ delta หนึ่งจะอ้างอิงไปยัง delta อื่นต่อกันเป็นทอด ๆ ก่อนจะถึง object ฐานที่เป็น full object) ควบคุมด้วย `--depth` (ค่า default คือ 50)

### Trade-off ของ delta depth

ยิ่ง delta chain ลึกเท่าไหร่ (จำนวนขั้นที่ต้อง apply ก่อนได้เนื้อหาจริง) ยิ่งประหยัดพื้นที่มากขึ้น แต่ก็ยิ่งช้าลงตอนอ่าน object นั้น (เพราะต้อง apply delta ทีละขั้นตามลำดับ) Git จึงต้องหาจุดสมดุลระหว่าง**ขนาดที่เล็กที่สุด**กับ**ความเร็วในการอ่านที่ยอมรับได้** ค่า default ของ Git ถูกปรับแต่งมาอย่างดีแล้วสำหรับกรณีทั่วไป แต่สามารถปรับได้เองผ่าน `git repack --depth=<N> --window=<N>` สำหรับกรณีพิเศษ

### ทำไม text ถึงบีบอัดด้วย delta ได้ดีกว่า binary

ประเด็นนี้สำคัญมากและจะเชื่อมโยงไปถึง Step 579 — delta compression ทำงานได้ดีเมื่อการเปลี่ยนแปลงระหว่าง object เป็น**การเปลี่ยนแปลงเฉพาะจุดในรูปแบบ byte ที่ยังคงเรียงต่อเนื่องกันในตำแหน่งเดิมเป็นส่วนใหญ่** (เช่นไฟล์ text ที่แก้แค่บางบรรทัด) แต่ถ้าการเปลี่ยนแปลงทำให้ byte ทั้งไฟล์เลื่อนตำแหน่งหรือเปลี่ยนแปลงแบบกระจัดกระจายทั่วทั้งไฟล์ (ซึ่งเป็นธรรมชาติของไฟล์ binary ที่ถูก compress หรือ encode ไว้แล้ว เช่น รูปภาพ, วิดีโอ, ไฟล์ที่ zip ไว้) delta algorithm จะหาช่วง byte ที่ตรงกันได้ยากมาก ทำให้ delta ที่ได้มีขนาดใหญ่ใกล้เคียงกับการเก็บเนื้อหาเต็มเลย ไม่ประหยัดพื้นที่เท่าที่ควร

## Step 576: `git repack` เจาะลึก

`git gc` ที่เราเรียนใน Step 573 นั้น **เรียกใช้ `git repack` เป็นแกนหลัก** ในขั้นตอนการอัดข้อมูล แต่ `git repack` เองก็เป็นคำสั่งที่สามารถเรียกใช้แยกต่างหากได้โดยตรง และมี flag ที่ควบคุมพฤติกรรมได้ละเอียดกว่า `git gc` มาก เหมาะสำหรับกรณีที่ต้องการควบคุมกระบวนการ repack อย่างจำเพาะเจาะจง

### รูปแบบการใช้งานพื้นฐาน

```bash
git repack
```

คำสั่งเปล่า ๆ จะรวบรวม loose object ทั้งหมด (ที่ยัง reachable) มาสร้างเป็น packfile ใหม่ 1 ชุด โดย**ไม่ลบ pack เก่าที่มีอยู่**และ**ไม่ลบ loose object เดิม** (เพื่อความปลอดภัย — ถ้า repack ล้มเหลวกลางทาง ข้อมูลต้นฉบับยังอยู่ครบ)

### `-a` — repack ทุก object ให้อยู่ใน pack เดียว

```bash
git repack -a
```

Flag `-a` (all) จะบังคับให้ Git นำ object **ทุกตัวที่มีอยู่ในระบบ** ไม่ว่าจะเป็น loose object หรือ object ที่อยู่ใน pack เดิมอยู่แล้วก็ตาม มารวมกันสร้างเป็น **pack ก้อนใหญ่ก้อนเดียว** ใหม่ทั้งหมด

ประโยชน์คือ: ถ้า repository มี pack เก่าหลายไฟล์สะสมอยู่ (จากการ fetch/pull หลายรอบ) การรวมทุกอย่างเป็น pack เดียวจะทำให้ Git สามารถหา delta ที่ดีกว่าเดิมได้ (เพราะตอนนี้ candidate สำหรับ delta compression ขยายวงกว้างครอบคลุมทุก object ในระบบ ไม่ใช่แค่ในแต่ละ pack แยกกัน) ผลลัพธ์มักได้ pack ที่มีขนาดเล็กลงกว่าการมี pack หลายไฟล์แยกกัน

### `-d` — ลบ pack และ loose object เก่าที่ซ้ำซ้อน

```bash
git repack -a -d
```

Flag `-d` จะสั่งให้ Git **ลบไฟล์ pack เก่าและ loose object เดิมทิ้ง**ทันทีหลังจากสร้าง pack ใหม่เสร็จสมบูรณ์และตรวจสอบแล้วว่าไม่มีปัญหา (คือ object ทุกตัวถูกย้ายเข้าไปอยู่ใน pack ใหม่ครบถ้วนแล้วจริง ๆ)

**นี่คือ combination ที่ `git gc` ใช้เป็นค่าเริ่มต้นภายใน** (`git repack -d -l` ร่วมกับการเรียก prune แยกต่างหากสำหรับ unreachable object) — `-a -d` ร่วมกันคือชุดคำสั่งที่ทำให้ได้ประโยชน์สูงสุดในแง่การประหยัดพื้นที่ดิสก์ เพราะไม่มีข้อมูลซ้ำซ้อนหลงเหลืออยู่เลยหลังจบกระบวนการ

**ข้อควรระวัง:** ถ้าไม่ใส่ `-d` ไฟล์ pack เก่าและ loose object เดิมจะยังคงอยู่บนดิสก์ต่อไป ทำให้พื้นที่ดิสก์ไม่ได้ลดลงจริง (แม้จะมี pack ใหม่ที่ดีกว่าเกิดขึ้นแล้วก็ตาม) — เป็นสาเหตุที่พบบ่อยที่คนสงสัยว่า "ทำไม repack แล้วขนาด `.git` ไม่ลดลงเลย"

### `-A` — Unpack unreachable objects กลับเป็น loose แทนที่จะลบทิ้ง

```bash
git repack -A -d
```

Flag `-A` ต่างจาก `-a` ตรงที่เมื่อทำการ repack และเจอ object ที่ **unreachable** (ไม่มี ref ใดชี้ถึง) มันจะ**แตก object เหล่านั้นกลับมาเป็น loose object เดี่ยว ๆ ธรรมดา** แทนที่จะไม่ใส่ไว้ใน pack ใหม่เลยทันที เหตุผลคือเพื่อให้ unreachable object เหล่านี้ยังคงอยู่ในระบบต่อไปอีกสักระยะ (รอ grace period ของ prune ตามที่อธิบายใน Step 573) เผื่อผู้ใช้ต้องการกู้คืนผ่าน reflog ในภายหลัง — **นี่คือ flag ที่ `git gc` เรียกใช้จริงเบื้องหลัง** (ไม่ใช่ `-a` ตรง ๆ) เพื่อความปลอดภัยของข้อมูลผู้ใช้

### `-f` — บังคับคำนวณ delta ใหม่ทั้งหมด (force)

```bash
git repack -a -d -f
```

ตามปกติเมื่อ repack ใหม่ Git อาจ**นำ delta ที่มีอยู่แล้วในของเดิมมาใช้ซ้ำ** (reuse) โดยไม่คำนวณใหม่ทั้งหมด เพื่อประหยัดเวลา (เพราะการหา delta ที่ดีที่สุดเป็นงานหนัก) แต่บางครั้งการ reuse delta เดิมอาจทำให้ผลลัพธ์ไม่ได้ optimal ที่สุดเท่าที่จะเป็นไปได้ (เช่นถ้า base object เดิมที่เคยเลือกไว้ไม่ใช่ตัวที่ดีที่สุดอีกต่อไปหลังมี object ใหม่เข้ามา)

Flag `-f` จะบังคับให้ Git **คำนวณ delta ใหม่ทั้งหมดจากศูนย์** โดยไม่ reuse ของเดิมเลย ใช้เวลานานกว่ามากแต่ได้ผลลัพธ์ที่ compact ที่สุด — นี่คือสิ่งที่ `git gc --aggressive` ใช้ภายใน

### `--window` และ `--depth` — ปรับความเข้มข้นของการหา delta

```bash
git repack -a -d --window=250 --depth=250
```

ตามที่อธิบายใน Step 575 ค่าเหล่านี้ควบคุมว่า Git จะพยายามหา delta ที่ดีที่สุดมากแค่ไหน (ยิ่งค่าสูง ยิ่งได้ผลลัพธ์ที่เล็กลงแต่ใช้เวลานานขึ้นแบบไม่เป็นเชิงเส้น) ค่าเหล่านี้เหมาะสำหรับการรันครั้งเดียวแบบเข้มข้นเมื่อต้องการบีบอัด repository ขนาดใหญ่ให้เล็กที่สุดก่อนเก็บถาวรหรือย้าย server เช่น

### สรุปตาราง flag สำคัญของ `git repack`

| Flag | ความหมาย |
|---|---|
| `-a` | รวม object ทุกตัวในระบบเข้า pack เดียว |
| `-A` | เหมือน `-a` แต่ unreachable object จะถูกแตกเป็น loose object แทนที่จะทิ้งไปเลย |
| `-d` | ลบ pack เก่าและ loose object เดิมที่ซ้ำซ้อนหลัง repack สำเร็จ |
| `-f` | บังคับคำนวณ delta ใหม่ทั้งหมด ไม่ reuse ของเดิม |
| `-l` | จำกัดเฉพาะ object ในเครื่อง local ไม่ยุ่งกับ alternate object store |
| `--window=<N>` | จำนวน object ข้างเคียงที่นำมาเทียบหา delta (default 10) |
| `--depth=<N>` | ความลึกสูงสุดของ delta chain (default 50) |
| `-q` | ทำงานแบบเงียบ ไม่แสดง progress |

## Step 577: `git verify-pack` และ `git count-objects -v`

เมื่อเข้าใจโครงสร้างและกลไกของ packfile แล้ว ขั้นตอนต่อไปคือการเรียนรู้เครื่องมือ**ตรวจสอบสถานะ**ของ object store เพื่อดูว่า repository ของเรามีสภาพเป็นอย่างไรจริง ๆ

### `git count-objects -v`

คำสั่งนี้เป็นวิธีที่เร็วที่สุดในการดูภาพรวมของ object store:

```bash
git count-objects -v
```

**ตัวอย่างผลลัพธ์:**

```
count: 42
size: 168
in-pack: 15230
packs: 2
size-pack: 4521
prune-packable: 3
garbage: 0
size-garbage: 0
```

**ความหมายของแต่ละบรรทัด:**

| ฟิลด์ | ความหมาย |
|---|---|
| `count` | จำนวน **loose object** ที่ยังไม่ถูก pack |
| `size` | ขนาดรวมของ loose object เหล่านั้น (หน่วย KiB) |
| `in-pack` | จำนวน object ทั้งหมดที่อยู่ใน packfile แล้ว |
| `packs` | จำนวนไฟล์ `.pack` ที่มีอยู่ใน repository |
| `size-pack` | ขนาดรวมของไฟล์ pack ทั้งหมด (หน่วย KiB) |
| `prune-packable` | จำนวน loose object ที่**มีอยู่ใน pack แล้วด้วย** (คือ redundant สามารถลบตัว loose ทิ้งได้โดย `git prune-packed`) |
| `garbage` | จำนวนไฟล์ขยะที่ Git เจอในโฟลเดอร์ object แต่ไม่ใช่ object ที่ถูกต้อง (เช่นไฟล์ที่เสียหาย) |
| `size-garbage` | ขนาดรวมของไฟล์ขยะเหล่านั้น |

จากตัวอย่างข้างต้น จะเห็นว่ามี loose object เหลืออยู่ 42 ตัว (168 KiB) ในขณะที่ object ส่วนใหญ่ (15,230 ตัว) ถูกอัดไว้ใน pack แล้ว 2 ไฟล์ รวมขนาด 4,521 KiB — ค่า `count` ที่สูงมากเมื่อเทียบกับ `gc.auto` (default 6700) จะเป็นสัญญาณว่าถึงเวลาที่ `git gc --auto` จะเริ่มทำงานโดยอัตโนมัติแล้ว

คำสั่งนี้เหมาะมากสำหรับใช้**เปรียบเทียบขนาดก่อน-หลัง**การรัน `git gc` (จะใช้ในแบบฝึกหัด Step 580)

### `git verify-pack`

ถ้าอยากดูรายละเอียดลึกลงไปถึงระดับ **object เดี่ยว ๆ ภายใน pack แต่ละไฟล์** ว่ามี object อะไรบ้าง แต่ละตัวมีขนาดเท่าไหร่ เป็น delta หรือเปล่า ต้อง apply delta ผ่านกี่ขั้น (depth) ใช้คำสั่ง:

```bash
git verify-pack -v .git/objects/pack/pack-<SHA>.idx
```

**ตัวอย่างผลลัพธ์:**

```
a1b2c3d4... commit 245 178 12
e5f6a7b8... tree   89  71  190
c9d0e1f2... blob   1234 421 261 1 a1b2c3d4...
b3a2c1d0... blob   1240 45  682 2 c9d0e1f2...
...
non delta: 8123 objects
chain length = 1: 5210 objects
chain length = 2: 1450 objects
chain length = 3: 447 objects
.git/objects/pack/pack-<SHA>.pack: ok
```

**การอ่านผลลัพธ์แต่ละคอลัมน์:**

```
<SHA> <type> <size> <size-in-packfile> <offset> [<depth> <base-SHA>]
```

- **SHA** — hash ของ object
- **type** — ประเภท object (commit, tree, blob, tag)
- **size** — ขนาดจริงของเนื้อหาหลัง decompress/apply delta แล้ว
- **size-in-packfile** — ขนาดที่ใช้จริงในไฟล์ pack (ถ้าเป็น delta ตัวเลขนี้จะเล็กกว่า size มาก แสดงถึงประสิทธิภาพของการบีบอัด)
- **offset** — ตำแหน่ง byte ของ object นี้ในไฟล์ pack
- **depth** (ถ้ามี) — ความลึกของ delta chain ที่ต้อง apply ก่อนได้เนื้อหาเต็ม (0 หรือไม่แสดง = full object ไม่ใช่ delta)
- **base-SHA** (ถ้ามี) — SHA ของ base object ที่ delta นี้อ้างอิงถึง

ท้ายผลลัพธ์จะสรุปจำนวน object แยกตาม chain length และแสดงว่า pack file นั้น `ok` (ผ่านการตรวจสอบ checksum) หรือมีปัญหา (`bad`) ซึ่งเป็นวิธีที่ดีในการ**ตรวจสอบความสมบูรณ์ของ packfile** ว่าไม่มีข้อมูลเสียหาย

### `git fsck` — ตรวจสอบความสมบูรณ์ของทั้ง repository

เครื่องมือที่มักใช้คู่กันคือ `git fsck` ซึ่งตรวจสอบความสมบูรณ์ของ object database ทั้งหมด (ทั้ง loose และ packed) รวมถึงหา object ที่ dangling (unreachable แต่ยังไม่ถูกลบ):

```bash
git fsck --full --unreachable --dangling
```

ใช้ร่วมกับ `git count-objects -v` และ `git verify-pack` เพื่อวินิจฉัยปัญหาของ repository ได้ครบทุกมิติ — `count-objects` ให้ภาพรวมระดับสถิติ, `verify-pack` ให้รายละเอียดระดับ object ใน pack, และ `fsck` ตรวจสอบความถูกต้องเชิงโครงสร้างของ object graph ทั้งหมด

## Step 578: การส่ง packfile ตอน push/fetch/clone

หัวข้อนี้จะอธิบายว่าเมื่อคุณ `git clone`, `git fetch`, หรือ `git push` เกิดอะไรขึ้นเบื้องหลังในระดับ protocol และทำไม packfile ถึงมีบทบาทสำคัญในทุกการถ่ายโอนข้อมูลผ่านเครือข่าย

### หลักการพื้นฐาน: ไม่มีการส่ง object ทีละไฟล์ผ่านเครือข่าย

ไม่ว่าจะเป็น protocol แบบไหน (`git://`, `ssh://`, `https://` แบบ smart HTTP) การถ่ายโอน object ระหว่างสอง repository จะถูก**บรรจุเป็น packfile เสมอ** ไม่มีกรณีที่ Git ส่ง loose object ทีละไฟล์ผ่านเครือข่ายในการทำงานปกติ เพราะจะช้าและกินทรัพยากรมากเกินไปตามที่อธิบายใน Step 571

### ขั้นตอนของ Fetch/Clone (Upload-Pack Protocol)

เมื่อคุณรัน `git fetch` หรือ `git clone` ฝั่ง client จะคุยกับฝั่ง server ผ่านโปรแกรมที่ชื่อ **`git-upload-pack`** (ฝั่ง server) โดยมีขั้นตอนคร่าว ๆ ดังนี้:

```
Client                                    Server (git-upload-pack)
  │                                              │
  │  1. เชื่อมต่อ ─────────────────────────────▶ │
  │                                              │
  │  ◀───────── 2. Server ประกาศ ref ทั้งหมด     │
  │              ที่มี (ref advertisement)        │
  │              พร้อม SHA ของแต่ละ ref           │
  │                                              │
  │  3. Client เทียบกับ ref ที่ตัวเองมีอยู่แล้ว    │
  │     (จาก .git/refs และ .git/packed-refs)     │
  │                                              │
  │  4. ส่ง "want <SHA>" ───────────────────────▶│  (บอกว่าอยากได้ object
  │     สำหรับทุก ref ที่ยังไม่มี                  │   ที่ปลายทางของ ref เหล่านี้)
  │                                              │
  │  5. ส่ง "have <SHA>" ───────────────────────▶│  (บอกว่ามี object นี้อยู่แล้ว
  │     สำหรับ commit ที่มีอยู่ใน local           │   ไม่ต้องส่งซ้ำ)
  │                                              │
  │  ◀───────── 6. Server คำนวณว่า object ชุดไหน │
  │              ที่ client ยังไม่มี (negotiation) │
  │                                              │
  │  ◀───────── 7. Server ส่ง packfile ที่มีเฉพาะ │
  │              object ที่ client ขาดไปเท่านั้น   │
  └──────────────────────────────────────────────┘
```

### Negotiation คืออะไร (ทำไมต้อง "have"/"want")

จุดที่ฉลาดที่สุดของ protocol นี้คือขั้นตอน **negotiation** — client จะบอก server ว่า "ฉันมี commit เหล่านี้อยู่แล้ว" (ผ่านคำสั่ง `have`) โดยเริ่มจาก ref ปลายทาง (branch tip) ที่ client มีอยู่ในเครื่อง แล้ว server จะคำนวณ **จุดร่วมล่าสุด (common ancestor)** ระหว่างสิ่งที่ client มีกับสิ่งที่ client ต้องการ (`want`)

ผลลัพธ์คือ server จะสร้าง packfile ที่มี**เฉพาะ object ที่ client ยังไม่มีเท่านั้น** — ถ้าคุณ `git fetch` เพื่ออัปเดตแค่ 5 commit ใหม่ที่เพื่อนร่วมทีม push ขึ้นมา server จะไม่ส่ง object ของทั้ง repository ใหม่ทั้งหมด แต่จะส่งเฉพาะ object ของ 5 commit นั้น (blob, tree, commit object ที่เกี่ยวข้อง) เท่านั้น ทำให้ `fetch` ครั้งถัดไปหลัง clone ครั้งแรกเร็วกว่ามาก

สำหรับ **`git clone`** (ที่ client ยังไม่มี object อะไรเลย) ขั้นตอน negotiation จะง่ายกว่า — client จะขอ (`want`) ทุก ref โดยไม่มี `have` เลย (หรือมีน้อยมาก) ทำให้ server ต้องส่ง object ทั้งหมดของประวัติที่ขอ (เว้นแต่จะใช้ `--depth` ทำ shallow clone)

### Thin Pack — packfile ที่อาศัย object ฝั่งรับ

ในขั้นตอนที่ 7 packfile ที่ server สร้างขึ้นเพื่อส่งให้ client มักถูกเรียกว่า **thin pack** เพราะ delta object ข้างในอาจใช้ **REF_DELTA** อ้างอิงไปยัง base object ที่**ไม่ได้รวมอยู่ในแพ็คที่กำลังส่งเลย** แต่เป็น object ที่ server รู้ว่า client มีอยู่แล้ว (จากขั้นตอน negotiation) วิธีนี้ทำให้ packfile ที่ส่งผ่านเครือข่ายมีขนาดเล็กที่สุดเท่าที่จะเป็นไปได้ เพราะไม่ต้องส่ง base object ซ้ำโดยไม่จำเป็น

เมื่อ client รับ thin pack มา จะใช้คำสั่ง `git index-pack --fix-thin` เพื่อ "เติมเต็ม" pack ให้สมบูรณ์ — โดยหา base object ที่ REF_DELTA อ้างถึงจาก object store ของตัวเอง แล้วแปลง REF_DELTA เหล่านั้นให้กลายเป็น OFS_DELTA ที่ชี้เข้าไปใน pack เดียวกัน (เพิ่ม base object นั้นเข้าไปในไฟล์ pack ที่บันทึกจริงบนดิสก์ด้วย) ทำให้ pack ที่เก็บอยู่บนเครื่อง client กลายเป็น pack ที่สมบูรณ์ในตัวเอง ไม่ต้องพึ่งพา object ภายนอกอีกต่อไป

### ขั้นตอนของ Push (Receive-Pack Protocol)

การ push ทำงานในทิศทางตรงข้าม โดยใช้โปรแกรมฝั่ง server ชื่อ **`git-receive-pack`**:

1. Client เชื่อมต่อไปยัง server, server ประกาศ ref ปัจจุบันที่มีอยู่ (ref advertisement เหมือนตอน fetch)
2. Client เปรียบเทียบกับ ref ที่ตัวเองต้องการ push แล้วคำนวณว่า object ชุดไหนที่ server ยังไม่มี (โดยอาศัยข้อมูลจาก ref advertisement เป็นตัวช่วยระบุ common ancestor คล้ายกับตอน fetch)
3. Client สร้าง packfile ที่มีเฉพาะ object ใหม่ (ที่ reachable จาก ref ที่จะ push แต่ไม่ reachable จาก ref เดิมที่ server มีอยู่) แล้วส่งไปพร้อมกับคำสั่งอัปเดต ref (`<old-SHA> <new-SHA> <ref-name>`)
4. Server รับ packfile มา ตรวจสอบความถูกต้อง (รัน pre-receive/update/post-receive hook ตามที่จะเรียนใน **Part 60**) แล้วจึงอัปเดต ref ของตัวเองให้ตรงกับที่ client ร้องขอ

### สรุปภาพรวม

| การกระทำ | ทิศทาง packfile | หลักการเลือก object ที่จะส่ง |
|---|---|---|
| `git clone` | Server → Client | ส่งทุก object ที่ reachable จาก ref ที่ขอ (หรือจำกัดด้วย `--depth`) |
| `git fetch` | Server → Client | ส่งเฉพาะ object ที่ client ยังไม่มี (คำนวณจาก have/want negotiation) |
| `git push` | Client → Server | ส่งเฉพาะ object ใหม่ที่ server ยังไม่มี (คำนวณจาก ref advertisement) |

การออกแบบ protocol ให้ negotiation กันแบบนี้คือเหตุผลสำคัญที่ทำให้ Git DVCS ใช้งานได้จริงในทางปฏิบัติแม้กับ repository ขนาดใหญ่มาก — ถ้าทุกครั้งที่ fetch ต้องส่งประวัติทั้งหมดใหม่ Git คงไม่สามารถขยายสเกลไปถึงระดับที่ใช้งานกันทั่วโลกได้อย่างทุกวันนี้

## Step 579: ข้อจำกัดของ packfile กับไฟล์ binary ขนาดใหญ่ที่เปลี่ยนบ่อย

หลังจากเข้าใจว่า packfile และ delta compression ทรงพลังแค่ไหนสำหรับไฟล์ text ตอนนี้เราต้องเข้าใจ**ข้อจำกัดที่สำคัญมาก**ของกลไกนี้ ซึ่งเป็นสาเหตุที่ทำให้เกิดเครื่องมือเสริมอย่าง **Git LFS** ขึ้นมา (จะเรียนละเอียดใน **Part 62**)

### ทำไม delta compression ทำงานได้ไม่ดีกับไฟล์ binary

ตามที่กล่าวไว้ท้าย Step 575 delta compression อาศัยหลักการหา **ช่วง byte ที่เหมือนกันและอยู่ในตำแหน่งที่ยังพอเทียบเคียงกันได้** ระหว่าง object สองตัว ปัญหาคือไฟล์ binary หลายประเภทมีธรรมชาติที่ขัดกับหลักการนี้โดยตรง:

1. **ไฟล์ที่ถูกบีบอัดอยู่แล้ว** (เช่น `.jpg`, `.png`, `.mp4`, `.zip`, `.pdf` ที่มี stream บีบอัดข้างใน) — การเปลี่ยนแปลงเนื้อหาแม้เพียงเล็กน้อย (เช่นปรับความสว่างของภาพนิดเดียว) มักทำให้ **byte stream ทั้งไฟล์เปลี่ยนแปลงไปเกือบทั้งหมด** เพราะ algorithm การบีบอัดภายในไฟล์เหล่านั้น (เช่น DEFLATE ใน PNG หรือ DCT ใน JPEG) มีลักษณะที่การเปลี่ยนแปลงเล็ก ๆ ส่งผลกระเจิงไปทั่วทั้งไฟล์ที่ถูก encode แล้ว
2. **ไฟล์ binary ที่ compiled** (เช่น `.exe`, `.dll`, `.so`) — แม้ source code จะเปลี่ยนแค่บรรทัดเดียว แต่หลังผ่าน compiler แล้ว ไฟล์ binary ที่ได้อาจมี layout, offset ของ symbol, หรือ address ที่เปลี่ยนไปทั้งไฟล์ ทำให้ byte content ต่างจากเวอร์ชันก่อนหน้าอย่างกระจัดกระจาย
3. **ไฟล์ฐานข้อมูลหรือไฟล์ binary format พิเศษ** (เช่น `.sqlite`, `.psd` จาก Photoshop) — โครงสร้างภายในอาจมีการจัดเรียงใหม่ (reorganize) ทุกครั้งที่บันทึก ทำให้แม้เนื้อหาเชิงตรรกะจะเปลี่ยนน้อย แต่ byte layout เปลี่ยนไปมาก

ผลลัพธ์คือเมื่อ Git พยายามหา delta ระหว่างไฟล์ binary สองเวอร์ชันเหล่านี้ delta ที่ได้จะ**มีขนาดใหญ่เกือบเท่ากับการเก็บเนื้อหาเต็มทั้งไฟล์** (แทบไม่มีช่วง byte ที่ copy ได้เลย ส่วนใหญ่ต้องใช้คำสั่ง insert ข้อมูลใหม่ทั้งหมด) การบีบอัดจึงแทบไม่ได้ประโยชน์อะไรเพิ่มเติมจากการเก็บแบบ full object เลย

### ผลกระทบที่เกิดขึ้นจริงกับ repository

เมื่อ repository มีไฟล์ binary ขนาดใหญ่ (เช่นไฟล์วิดีโอสอน, asset ของเกม, ไฟล์ design, ไฟล์ dataset สำหรับ machine learning) ที่ **ถูกแก้ไขบ่อยครั้ง** ปัญหาที่ตามมาคือ:

- **ขนาด repository โตขึ้นอย่างรวดเร็วและไม่มีวันเล็กลง** — เพราะทุกเวอร์ชันของไฟล์ binary นั้นถูกเก็บแบบเกือบเต็มไฟล์ (delta ไม่ช่วยอะไรมาก) และ Git ไม่เคยลบประวัติเก่าทิ้งตามธรรมชาติของมัน แม้แต่ `git gc` ก็ช่วยได้จำกัดมากในกรณีนี้ เพราะปัญหาไม่ได้อยู่ที่การจัดเก็บไม่ดี แต่อยู่ที่**ธรรมชาติของข้อมูลเองที่ไม่เหมาะกับ delta**
- **การ `clone` ช้ามากและใช้พื้นที่ดิสก์มหาศาล** — เพราะทุกคนที่ clone repository ต้องดาวน์โหลดทุกเวอร์ชันของไฟล์ binary เหล่านั้นตลอดประวัติทั้งหมด แม้จะสนใจแค่เวอร์ชันล่าสุดก็ตาม (คนละแนวคิดกับระบบจัดการไฟล์แบบ cloud storage ทั่วไปที่มักเก็บแค่เวอร์ชันปัจจุบัน)
- **การทำงานประจำวันช้าลง** — คำสั่งพื้นฐานอย่าง `git status`, `git checkout`, `git clone` ต้องจัดการกับข้อมูลจำนวนมหาศาลที่ไม่จำเป็นต้องใช้งานจริงในขณะนั้น
- **ไม่มีทาง "ลืม" ไฟล์เก่าได้ง่าย** — แม้จะลบไฟล์ binary ออกจาก commit ล่าสุดแล้ว แต่เวอร์ชันเก่าของมันยังคงฝังอยู่ในประวัติ (และในทุก clone ที่มีอยู่แล้ว) ตลอดไป จนกว่าจะทำการแก้ไขประวัติแบบพิเศษ (เช่น `git filter-repo`) ซึ่งเป็นการกระทำที่มีความเสี่ยงสูงและกระทบทุกคนที่ clone repository ไปแล้ว

### แนวทางแก้ปัญหาที่จะเรียนต่อใน Part 62: Git LFS

Git ไม่ได้ออกแบบมาให้เก็บไฟล์ binary ขนาดใหญ่ที่เปลี่ยนบ่อยได้อย่างมีประสิทธิภาพ เพราะสถาปัตยกรรมทั้งหมดของมัน (snapshot-based storage, delta compression, การที่ต้องมีสำเนาเต็มของประวัติทุกเครื่องในระบบ distributed) ถูกออกแบบมาโดยมีสมมติฐานว่าเนื้อหาส่วนใหญ่เป็น **source code แบบ text** ที่ delta compression ทำงานได้ดี

**Git LFS (Large File Storage)** คือส่วนขยายที่ถูกสร้างขึ้นมาเพื่อแก้ปัญหานี้โดยเฉพาะ แนวคิดหลักคือ:

> **แทนที่จะเก็บเนื้อหาไฟล์ binary ขนาดใหญ่ไว้ใน Git object database โดยตรง Git LFS จะเก็บแค่ "pointer file" ขนาดเล็ก ๆ (ไม่กี่ร้อยไบต์) ไว้แทน ส่วนเนื้อหาจริงของไฟล์จะถูกอัปโหลดไปเก็บไว้ยัง LFS server แยกต่างหาก และดาวน์โหลดมาเฉพาะตอนที่จำเป็นต้องใช้งานจริงเท่านั้น**

ด้วยวิธีนี้ object ที่อยู่ใน Git object database (และถูกส่งผ่าน packfile ตามที่เรียนในบทนี้) จะมีแค่ pointer file ขนาดเล็กเท่านั้น ไม่ใช่เนื้อหาไฟล์ binary เต็ม ๆ ทำให้ปัญหาเรื่อง repository บวมและ clone ช้าลดลงอย่างมาก เราจะลงรายละเอียดการติดตั้งและใช้งาน Git LFS อย่างละเอียดใน **Part 62: Git LFS: จัดการไฟล์ขนาดใหญ่**

สำหรับตอนนี้ ให้จำหลักการสำคัญไว้เป็นเกณฑ์ตัดสินใจ:

> **ถ้าไฟล์เป็น text-based (source code, config, markdown, JSON) → เก็บใน Git ตรง ๆ ได้เต็มประสิทธิภาพ เพราะ delta compression ช่วยได้มาก**
> **ถ้าไฟล์เป็น binary ขนาดใหญ่ที่เปลี่ยนบ่อย (วิดีโอ, asset, dataset, ไฟล์ compiled) → ควรพิจารณาใช้ Git LFS หรือระบบจัดเก็บภายนอกแทน**

## Step 580: แบบฝึกหัด — วัดผลของ `git gc` ด้วยตาตัวเอง

ถึงเวลาลงมือทำจริงเพื่อยืนยันทุกสิ่งที่เรียนมาในบทนี้ เราจะสร้าง repository ที่มีประวัติ commit จำนวนมาก (ทำให้เกิด loose object เยอะ ๆ) แล้ววัดขนาดก่อนและหลังรัน `git gc` เพื่อดูผลลัพธ์จริงด้วยตาตัวเอง

### ขั้นตอนที่ 1: เตรียม repository ทดสอบ

```bash
mkdir ~/git-course/part-58-packfiles
cd ~/git-course/part-58-packfiles
git init
```

### ขั้นตอนที่ 2: สร้างประวัติ commit จำนวนมากด้วย script

เราจะเขียน loop ที่แก้ไขไฟล์เล็กน้อยแล้ว commit ซ้ำ ๆ หลายร้อยครั้ง เพื่อจำลอง repository ที่ผ่านการใช้งานมานาน (แต่ละ commit จะสร้าง loose object ใหม่ทันที ยังไม่ถูก pack)

```bash
for i in $(seq 1 500); do
  echo "บรรทัดที่เพิ่มในรอบที่ $i - $(date +%s%N)" >> log.txt
  git add log.txt
  git commit -m "Update log.txt (round $i)" --quiet
done
```

คำสั่งนี้จะสร้าง commit 500 ครั้ง แต่ละครั้งจะสร้าง object ใหม่อย่างน้อย 2 ตัว (blob ใหม่ของ `log.txt` และ commit object ใหม่) — เพราะไม่มี tree อื่นเปลี่ยนแปลง จึงมี tree object ใหม่ต่อ commit ด้วย รวมแล้วประมาณ 1,500 object ใหม่

### ขั้นตอนที่ 3: วัดขนาดก่อนรัน `git gc`

```bash
git count-objects -v
```

**ผลลัพธ์ที่คาดว่าจะเห็น (ตัวเลขจริงอาจต่างกันเล็กน้อยตามระบบ):**

```
count: 1500
size: 210
in-pack: 0
packs: 0
size-pack: 0
prune-packable: 0
garbage: 0
size-garbage: 0
```

จะเห็นว่า `count` มีค่าสูงมาก (loose object ทั้งหมด 1,500 ตัว) และยังไม่มี pack เลย (`packs: 0`) ลองดูจำนวนไฟล์จริงบนดิสก์ด้วย:

```bash
find .git/objects -type f | grep -v pack | wc -l
du -sh .git
```

### ขั้นตอนที่ 4: รัน `git gc`

```bash
git gc
```

สังเกต progress ที่แสดงระหว่างการทำงาน (เช่น "Enumerating objects", "Counting objects", "Compressing objects", "Writing objects") ซึ่งสะท้อนขั้นตอนที่เราเรียนมาทั้งหมดในบทนี้ — enumerate ทุก object, หา delta ที่ดีที่สุดภายใน window, บีบอัดและเขียนเป็น packfile ใหม่

### ขั้นตอนที่ 5: วัดขนาดหลังรัน `git gc`

```bash
git count-objects -v
```

**ผลลัพธ์ที่คาดว่าจะเห็น:**

```
count: 0
size: 0
in-pack: 1503
packs: 1
size-pack: 45
prune-packable: 0
garbage: 0
size-garbage: 0
```

สังเกตความเปลี่ยนแปลง:

- `count` ลดจาก 1500 เหลือ 0 — loose object ทั้งหมดถูกย้ายเข้า pack และลบ loose ทิ้งแล้ว (เพราะ `git gc` เรียก `repack -d` ภายใน)
- `packs` เพิ่มจาก 0 เป็น 1 — ตอนนี้มีไฟล์ `.pack` (พร้อม `.idx` คู่กัน) หนึ่งชุด
- `size-pack` (45 KiB ในตัวอย่าง) มักจะ**เล็กกว่า `size` เดิมของ loose object รวมกันมาก** — เพราะเนื้อหาของ `log.txt` แต่ละเวอร์ชันคล้ายกันเกือบทั้งหมด (มีแค่บรรทัดใหม่เพิ่มเข้ามาทีละบรรทัด) ทำให้ delta compression ทำงานได้ดีมากในกรณีนี้

ตรวจสอบขนาดโฟลเดอร์ `.git` โดยรวมอีกครั้ง:

```bash
du -sh .git
```

จะเห็นว่าขนาดรวมลดลงอย่างชัดเจนเมื่อเทียบกับก่อนรัน `git gc`

### ขั้นตอนที่ 6: ตรวจสอบ pack ที่ได้ด้วย `git verify-pack`

```bash
git verify-pack -v .git/objects/pack/*.idx | tail -20
```

ลองสังเกตคอลัมน์ depth และ base-SHA ของแต่ละ object — จะเห็นว่า blob object ของ `log.txt` ในแต่ละเวอร์ชันส่วนใหญ่ถูกเก็บเป็น delta เทียบกับ blob เวอร์ชันก่อนหน้า (มี depth มากกว่า 0) ยืนยันสิ่งที่เรียนมาใน Step 575 ได้อย่างเป็นรูปธรรม

### ขั้นตอนที่ 7 (โบนัส): ทดลองเปรียบเทียบกับไฟล์ binary

เพื่อยืนยันสิ่งที่เรียนใน Step 579 ลองทำการทดลองเปรียบเทียบ โดยสร้าง repository ใหม่ที่ commit ไฟล์ binary แบบสุ่ม (จำลองพฤติกรรมของไฟล์ binary ที่บีบอัดไม่ได้ดี) แทนไฟล์ text:

```bash
cd ~/git-course
mkdir part-58-binary-test && cd part-58-binary-test
git init

for i in $(seq 1 20); do
  head -c 1000000 /dev/urandom > data.bin   # สร้างไฟล์ binary สุ่ม 1 MB
  git add data.bin
  git commit -m "Update binary file (round $i)" --quiet
done

git count-objects -v
git gc
git count-objects -v
```

**สิ่งที่ควรสังเกต:** ต่างจากตัวอย่างไฟล์ text ก่อนหน้านี้ `size-pack` หลัง `git gc` ในกรณีนี้จะ**ใกล้เคียงกับขนาดไฟล์ binary ทั้งหมดรวมกัน** (20 MB) ไม่ได้ลดลงอย่างมีนัยสำคัญเหมือนกรณีไฟล์ text เพราะข้อมูลสุ่ม (random data) ไม่มีความคล้ายคลึงกันเลยระหว่างแต่ละเวอร์ชัน delta compression จึงแทบไม่ได้ประโยชน์อะไร — นี่คือการพิสูจน์ด้วยตัวเลขจริงถึงข้อจำกัดที่อธิบายไว้ใน Step 579 และเป็นเหตุผลที่จะนำไปสู่การเรียนรู้ Git LFS ใน Part 62 ต่อไป

### เฉลยแนวคิดของแบบฝึกหัด

| คำถาม | คำตอบที่คาดหวัง |
|---|---|
| ทำไม `count` หลัง gc ถึงเป็น 0 | เพราะ `git gc` เรียก `git repack -d` ที่ลบ loose object ที่ถูกย้ายเข้า pack แล้วทิ้ง |
| ทำไม `size-pack` ของไฟล์ text เล็กกว่า `size` เดิมมาก | เพราะ delta compression หาความคล้ายคลึงระหว่าง blob แต่ละเวอร์ชันของ `log.txt` ได้ดี (มีแค่ข้อความเพิ่มทีละบรรทัด) |
| ทำไม `size-pack` ของไฟล์ binary สุ่มไม่เล็กลงมาก | เพราะข้อมูลสุ่มไม่มีรูปแบบ byte ที่ซ้ำกันให้ delta compression นำไปใช้ประโยชน์ได้เลย |
| ถ้า repository จริงมีไฟล์ binary แบบนี้และเปลี่ยนบ่อยควรทำอย่างไร | พิจารณาย้ายไปใช้ Git LFS แทนการเก็บตรงใน Git object database (Part 62) |

## สรุป Part 58

ใน Part นี้เราได้เรียนรู้ว่า:

1. **Loose object จำนวนมาก** สร้างปัญหาสามด้าน คือกินพื้นที่ดิสก์เกินจำเป็น สร้างภาระให้ filesystem จากไฟล์เล็ก ๆ จำนวนมหาศาล และทำให้การถ่ายโอนผ่านเครือข่ายช้าและกินแบนด์วิดท์มาก
2. **Loose object กับ packed object** ต่างกันทั้งในแง่โครงสร้างไฟล์ ความเร็วในการอ่าน/เขียน และประสิทธิภาพการบีบอัด — Git ใช้กลยุทธ์ write-fast-compact-later คือเขียน loose object ก่อนแล้วค่อยอัดเป็น pack ทีหลัง
3. **`git gc`** เป็นชุดงานบำรุงรักษาที่รวม pack-refs, reflog expire, repack, prune, worktree prune และ rerere gc เข้าไว้ด้วยกัน โดย unreachable object จะไม่ถูกลบทันทีแต่มี grace period (`gc.pruneExpire`) เพื่อความปลอดภัย
4. **โครงสร้าง packfile** ประกอบด้วยไฟล์ `.pack` (เก็บข้อมูล object จริง) และ `.idx` (ดัชนีค้นหาผ่าน fanout table + binary search ทำให้ค้นหา object ได้เร็วระดับ O(log n))
5. **Delta compression** คือการเก็บ object ที่คล้ายกันเป็น copy/insert instruction เทียบกับ base object แทนที่จะเก็บเนื้อหาเต็มซ้ำ ๆ โดยมีทั้งแบบ OFS_DELTA (อ้างอิงด้วย offset) และ REF_DELTA (อ้างอิงด้วย SHA เต็ม)
6. **`git repack`** มี flag สำคัญคือ `-a` (รวมทุก object เป็น pack เดียว), `-d` (ลบของเก่าที่ซ้ำซ้อน), `-A` (แตก unreachable object กลับเป็น loose แทนลบทิ้ง), `-f` (บังคับคำนวณ delta ใหม่ทั้งหมด)
7. **`git verify-pack -v`** และ **`git count-objects -v`** เป็นเครื่องมือหลักในการตรวจสอบสถานะของ object store ทั้งในระดับภาพรวมและระดับ object เดี่ยว ๆ
8. **การ push/fetch/clone** ใช้กลไก negotiation ผ่าน want/have เพื่อให้ server ส่งเฉพาะ object ที่ client ยังไม่มี บรรจุเป็น thin pack ที่อาจใช้ REF_DELTA อ้างอิงไปยัง object ที่ client มีอยู่แล้ว
9. **Delta compression ทำงานได้ไม่ดีกับไฟล์ binary** ที่บีบอัดหรือ encode ไว้แล้ว (รูปภาพ, วิดีโอ, ไฟล์ compiled) เพราะการเปลี่ยนแปลงเล็กน้อยมักทำให้ byte content เปลี่ยนไปทั้งไฟล์ นำไปสู่ปัญหา repository บวมเมื่อมีไฟล์เหล่านี้เปลี่ยนบ่อย ซึ่งจะแก้ด้วย Git LFS ใน Part 62
10. เราได้พิสูจน์ทุกแนวคิดด้วยแบบฝึกหัดจริง ผ่านการวัดขนาดก่อน-หลัง `git gc` ทั้งกรณีไฟล์ text (บีบอัดได้ดีมาก) และไฟล์ binary สุ่ม (บีบอัดได้น้อยมาก)
