## Step 191: Issue คืออะไร ใช้ทำอะไรได้บ้าง

ก่อนหน้านี้ในเฟส 1–2 เราเน้นเรียนรู้ Git ในฐานะเครื่องมือที่รันบนเครื่อง local ล้วน ๆ (init, commit, branch, merge, remote, push, pull) แต่พอเข้าสู่เฟส 3 ที่ว่าด้วย **GitHub** เราจะเริ่มเห็นฟีเจอร์ที่ Git เพียว ๆ ไม่มีให้ แต่ GitHub เพิ่มเข้ามาเพื่อช่วยให้ทีมทำงานร่วมกันได้อย่างเป็นระบบ และหนึ่งในฟีเจอร์ที่สำคัญที่สุดของ GitHub ก็คือ **Issues**

### Issue คืออะไร

**Issue** คือ **"รายการงานหรือเรื่องที่ต้องติดตาม"** ที่ผูกอยู่กับ repository หนึ่ง ๆ บน GitHub พูดง่าย ๆ Issue คือกระดานบันทึกงานในตัว repository นั่นเอง แต่ละ issue จะมี:

- หมายเลขประจำตัว (เช่น `#42`) ที่ไม่ซ้ำกันภายใน repository นั้น
- หัวข้อ (title)
- รายละเอียด (description) ที่เขียนด้วย Markdown ได้เต็มรูปแบบ
- สถานะ **Open** (ยังไม่เสร็จ/ยังไม่ปิด) หรือ **Closed** (ปิดแล้ว)
- ผู้เปิด (author), ผู้รับผิดชอบ (assignee), label, milestone, comment และอื่น ๆ อีกมาก

สิ่งสำคัญที่ต้องเข้าใจให้ชัดคือ **Issue ไม่ใช่ส่วนหนึ่งของ Git** — มันเป็น**ฟีเจอร์ของแพลตฟอร์ม GitHub** (เก็บอยู่ในฐานข้อมูลของ GitHub เอง ไม่ได้อยู่ใน `.git` ของ repository) ถ้าคุณ clone repository มาที่เครื่อง คุณจะไม่เห็น issue ติดมาด้วยเลย ต้องเข้าเว็บ GitHub หรือใช้ GitHub CLI/API เท่านั้นถึงจะเห็นได้ (GitLab ก็มีฟีเจอร์แบบเดียวกันเรียกว่า "Issues" เหมือนกัน ซึ่งเราจะเรียนในเฟส 5)

### Issue ใช้ทำอะไรได้บ้าง

Issue เป็นเครื่องมืออเนกประสงค์มาก การใช้งานหลัก ๆ มี 4 แบบ:

1. **Report Bug (รายงานบั๊ก)** — เมื่อมีคนพบว่าโปรแกรมทำงานผิดพลาด ก็เปิด issue เพื่อบันทึกอาการ ขั้นตอนการทำให้เกิดซ้ำ (steps to reproduce) และผลลัพธ์ที่คาดหวัง เพื่อให้ทีมพัฒนานำไปแก้ไข

   ตัวอย่าง: `[Bug] ปุ่ม Login ไม่ทำงานบน Safari เวอร์ชัน 17`

2. **Feature Request (ขอฟีเจอร์ใหม่)** — ผู้ใช้หรือทีมงานเสนอไอเดียฟีเจอร์ใหม่ที่อยากให้เพิ่มเข้ามาในโปรเจกต์

   ตัวอย่าง: `[Feature] เพิ่มโหมด Dark Mode ให้กับหน้า Dashboard`

3. **Task Tracking (ติดตามงาน)** — ใช้เป็น to-do list สำหรับงานที่ต้องทำ ไม่ว่าจะเป็นงาน refactor, งานเขียน document, งาน setup infrastructure ฯลฯ ที่ไม่ใช่บั๊กหรือฟีเจอร์โดยตรง

   ตัวอย่าง: `[Task] อัปเดต dependency ของโปรเจกต์ทั้งหมดให้เป็นเวอร์ชันล่าสุด`

4. **Discussion (พูดคุย/ถกเถียงประเด็นทางเทคนิค)** — ใช้เป็นพื้นที่ถกเถียงแนวทางการออกแบบ สถาปัตยกรรม หรือแม้แต่นโยบายของโปรเจกต์ ก่อนจะลงมือเขียนโค้ดจริง (แม้ GitHub จะมีฟีเจอร์ **Discussions** แยกต่างหากสำหรับการพูดคุยแบบเปิดกว้างกว่านี้ แต่หลายทีมก็ยังใช้ issue สำหรับ discussion เชิงเทคนิคที่ผูกกับงานเฉพาะเจาะจงอยู่ดี)

### ทำไม Issue ถึงสำคัญมากในการทำงานเป็นทีม

ลองจินตนาการทีมที่ไม่มี issue tracker เลย — การสื่อสารเรื่องบั๊กและงานที่ต้องทำจะกระจัดกระจายอยู่ใน Slack, อีเมล, หรือแม้แต่ปากเปล่า ซึ่งจะเกิดปัญหา:

- ไม่มีที่อ้างอิงกลับได้ว่า "งานนี้เคยพูดถึงที่ไหน"
- ไม่รู้ว่างานไหนมีคนรับผิดชอบแล้วหรือยัง
- ไม่รู้ว่างานไหนเสร็จแล้ว งานไหนยังค้างอยู่
- ไม่สามารถเชื่อมโยงกับ commit หรือ pull request ที่แก้ปัญหานั้นได้โดยตรง

Issue แก้ปัญหาทั้งหมดนี้โดยทำให้ทุกอย่างอยู่ **ในที่เดียวกับโค้ด** ซึ่งเป็นจุดแข็งสำคัญของ GitHub ที่ทำให้มันกลายเป็นศูนย์กลางของ Open Source และทีมพัฒนาซอฟต์แวร์ทั่วโลก

### ภาพรวมของหน้า Issues บน GitHub

เมื่อเข้าไปที่ repository บน GitHub แล้วคลิกแท็บ **Issues** คุณจะเห็น:

```
┌─────────────────────────────────────────────────────────┐
│  Issues                          [New issue]             │
├─────────────────────────────────────────────────────────┤
│  [Open (12)]  [Closed (48)]                              │
│  🔍 is:issue is:open                    Labels ▾ Sort ▾  │
├─────────────────────────────────────────────────────────┤
│  #42  [Bug] ปุ่ม Login ไม่ทำงานบน Safari    bug          │
│        opened 2 days ago by user123                      │
├─────────────────────────────────────────────────────────┤
│  #41  [Feature] เพิ่มโหมด Dark Mode         enhancement  │
│        opened 3 days ago by user456                      │
└─────────────────────────────────────────────────────────┘
```

จะเห็นได้ว่าหน้า Issues มีตัวกรอง (Open/Closed), ช่องค้นหา, ตัวจัดเรียง และรายการ issue แต่ละอันพร้อม label กำกับ — ทั้งหมดนี้เราจะเรียนรู้ทีละส่วนใน Step ถัดไป

## Step 192: สร้าง Issue ใหม่ (title ที่ดี, description ด้วย Markdown, template ถ้ามี)

มาลงมือสร้าง issue จริงกัน

### 192.1 ขั้นตอนพื้นฐานในการสร้าง Issue

1. เข้าไปที่ repository บน GitHub
2. คลิกแท็บ **Issues**
3. คลิกปุ่มสีเขียว **New issue**
4. กรอก **Title** และ **Description**
5. (ถ้ามี) เลือก **Labels**, **Assignees**, **Milestone** ทางด้านขวา
6. คลิก **Submit new issue**

### 192.2 การตั้ง Title ที่ดี

Title คือสิ่งแรกที่คนเห็นในรายการ issue ทั้งหมด และเป็นสิ่งที่ค้นหาเจอบ่อยที่สุด ดังนั้นการตั้ง title ที่ดีสำคัญมาก หลักการตั้ง title ที่ดี:

**ควรทำ:**
- สั้น กระชับ แต่บอกปัญหา/งานได้ชัดเจนในตัวเอง
- ใช้ prefix บอกประเภทถ้าทีมมีธรรมเนียมนี้ เช่น `[Bug]`, `[Feature]`, `[Docs]`, `[Chore]`
- เขียนในมุมมองของ "ปัญหา" หรือ "สิ่งที่ต้องการ" ไม่ใช่คำถามลอย ๆ

**ตัวอย่าง Title ที่ดี:**
```
[Bug] API /users คืนค่า 500 เมื่อส่ง email ที่มีอักขระพิเศษ
[Feature] รองรับการ login ด้วย Google OAuth
[Docs] เพิ่มตัวอย่างการใช้งาน API endpoint /orders
```

**ตัวอย่าง Title ที่ไม่ดี:**
```
มันพัง
ช่วยดูหน่อย
bug
ทำไมใช้ไม่ได้
```

Title แบบไม่ดีเหล่านี้ทำให้เวลาค้นหาหรือดูรายการ issue ทีหลัง จะไม่สามารถเข้าใจได้เลยว่าเรื่องอะไร ต้องเปิดเข้าไปอ่านทุกอันซึ่งเสียเวลามาก

### 192.3 การเขียน Description ด้วย Markdown

ช่อง description ของ issue รองรับ **Markdown** เต็มรูปแบบ (เหมือนกับ commit message บางส่วน แต่ทรงพลังกว่ามาก) ทำให้เราจัดโครงสร้างเนื้อหาให้อ่านง่ายได้ ฟีเจอร์ Markdown ที่ใช้บ่อยในการเขียน issue:

```markdown
## สรุปปัญหา
เมื่อผู้ใช้กด login ด้วยอีเมลที่มีอักขระ `+` เช่น `user+test@example.com`
ระบบจะคืนค่า HTTP 500 แทนที่จะ login สำเร็จ

## ขั้นตอนการทำให้เกิดซ้ำ (Steps to Reproduce)
1. ไปที่หน้า `/login`
2. กรอกอีเมล `user+test@example.com`
3. กรอกรหัสผ่านที่ถูกต้อง
4. กดปุ่ม "เข้าสู่ระบบ"

## ผลลัพธ์ที่คาดหวัง (Expected Behavior)
ควร login สำเร็จและ redirect ไปหน้า dashboard

## ผลลัพธ์ที่เกิดขึ้นจริง (Actual Behavior)
หน้าเว็บแสดง Error 500 พร้อมข้อความ `Internal Server Error`

## สภาพแวดล้อม (Environment)
- Browser: Chrome 128
- OS: Windows 11
- Environment: Staging

## Screenshot
![error screenshot](https://example.com/screenshot.png)

## ข้อมูลเพิ่มเติม
- [ ] ตรวจสอบ log ฝั่ง backend แล้วหรือยัง
- [ ] เขียน unit test ครอบกรณีนี้เพิ่ม
```

สังเกตองค์ประกอบที่ใช้:

- **หัวข้อ (`##`)** แบ่งเนื้อหาเป็นส่วน ๆ ให้อ่านง่าย
- **Numbered list** สำหรับขั้นตอนที่ต้องทำตามลำดับ
- **Code span** (backtick) สำหรับข้อความที่เป็นค่าจริง เช่น อีเมล, error message
- **Task list** (`- [ ]`) สำหรับ checklist งานย่อยที่ยังไม่เสร็จ — พอติ๊กถูกในหน้า GitHub มันจะกลายเป็น `- [x]` และ GitHub จะแสดงความคืบหน้าเป็น progress bar ให้อัตโนมัติที่หน้ารายการ issue ด้วย (เช่น "0/2" หรือ "1/2")
- **รูปภาพ** — สามารถลากไฟล์รูปวางลงในกล่อง description ได้โดยตรง GitHub จะอัปโหลดให้อัตโนมัติแล้วแทรก syntax `![...](...)` ให้เอง

### 192.4 Issue Template

หลาย repository (โดยเฉพาะโปรเจกต์ Open Source ที่มีคนนอกทีมมาเปิด issue บ่อย ๆ) จะตั้งค่า **Issue Template** ไว้ล่วงหน้า เพื่อบังคับให้ผู้เปิด issue กรอกข้อมูลที่จำเป็นครบถ้วน ไม่ปล่อยให้เขียนอิสระซึ่งมักขาดรายละเอียดสำคัญ

Template เหล่านี้ถูกเก็บไว้ในโฟลเดอร์ `.github/ISSUE_TEMPLATE/` ของ repository เช่น:

```
.github/
└── ISSUE_TEMPLATE/
    ├── bug_report.md
    ├── feature_request.md
    └── config.yml
```

ตัวอย่างไฟล์ `bug_report.md` แบบ Markdown เดิม (legacy format):

```markdown
---
name: Bug report
about: รายงานบั๊กที่พบในโปรเจกต์
title: '[Bug] '
labels: bug
assignees: ''
---

## สรุปปัญหา
<!-- อธิบายปัญหาสั้น ๆ -->

## ขั้นตอนการทำให้เกิดซ้ำ
1.
2.
3.

## ผลลัพธ์ที่คาดหวัง

## ผลลัพธ์ที่เกิดขึ้นจริง
```

GitHub ยังรองรับ **Issue Forms** แบบ YAML ที่ทันสมัยกว่า (ไฟล์นามสกุล `.yml`) ซึ่งจะสร้างเป็นฟอร์มที่มีช่องกรอกแยกเป็นฟิลด์ ๆ (เหมือนฟอร์มบนเว็บจริง ๆ) แทนการให้พิมพ์ Markdown ดิบ:

```yaml
name: Bug Report
description: รายงานบั๊กที่พบในระบบ
title: "[Bug]: "
labels: ["bug", "triage"]
body:
  - type: textarea
    id: description
    attributes:
      label: อธิบายปัญหา
      description: บอกว่าเกิดอะไรขึ้น
    validations:
      required: true
  - type: input
    id: version
    attributes:
      label: เวอร์ชันของแอปพลิเคชัน
      placeholder: เช่น v2.3.1
    validations:
      required: true
  - type: dropdown
    id: browser
    attributes:
      label: เบราว์เซอร์ที่ใช้
      options:
        - Chrome
        - Firefox
        - Safari
        - Edge
```

เมื่อมี template แล้ว ตอนกด **New issue** ผู้ใช้จะเห็นตัวเลือกให้เลือกก่อนว่าจะเปิด issue แบบไหน (Bug report / Feature request / ฯลฯ) แทนที่จะเจอกล่องข้อความเปล่า ๆ

> **หมายเหตุ:** เราจะเจาะลึกการสร้าง Issue Template และ Issue Forms แบบละเอียดในเฟส 4 เมื่อพูดถึงมาตรฐานของโปรเจกต์ Open Source ณ ตอนนี้ขอให้รู้จักไว้ก่อนว่ามันมีอยู่และทำหน้าที่อะไร

## Step 193: Labels — จัดหมวดหมู่ issue และวิธีสร้าง label เอง

เมื่อ repository มี issue เยอะขึ้นเรื่อย ๆ การจะไล่ดูทีละอันเพื่อรู้ว่าอันไหนเป็นบั๊ก อันไหนเป็นฟีเจอร์ใหม่ จะกลายเป็นเรื่องยากมาก **Label** คือเครื่องมือที่ช่วยแก้ปัญหานี้

### 193.1 Label คืออะไร

**Label** คือ "ป้ายกำกับสี" ที่ติดกับ issue (หรือ pull request ก็ได้เช่นกัน) เพื่อจัดหมวดหมู่ ค้นหา และกรองได้ง่ายขึ้น หนึ่ง issue สามารถมีได้หลาย label พร้อมกัน

### 193.2 Label มาตรฐานที่ GitHub สร้างให้อัตโนมัติ

ทุก repository ใหม่บน GitHub จะมี label เริ่มต้นให้ใช้งานทันที:

| Label | สี (default) | ความหมาย |
|---|---|---|
| `bug` | แดง | สิ่งที่ทำงานผิดพลาดจากที่ควรเป็น |
| `documentation` | ฟ้า | เกี่ยวข้องกับการปรับปรุงเอกสารประกอบ |
| `duplicate` | ขาว | issue นี้ซ้ำกับ issue อื่นที่มีอยู่แล้ว |
| `enhancement` | ฟ้าอมเขียว | คำขอฟีเจอร์ใหม่หรือปรับปรุงของเดิม |
| `good first issue` | ม่วง | เหมาะสำหรับผู้มีส่วนร่วมหน้าใหม่ (มือใหม่ในโปรเจกต์) |
| `help wanted` | เขียว | ต้องการความช่วยเหลือเป็นพิเศษจากภายนอกทีม |
| `invalid` | เหลือง | ไม่ใช่ปัญหาจริง หรือไม่เกี่ยวข้องกับโปรเจกต์ |
| `question` | ชมพู | เป็นคำถามมากกว่าปัญหาหรือฟีเจอร์ |
| `wontfix` | ขาว | รับทราบแล้วแต่จะไม่แก้ไข/ไม่ทำตามคำขอนี้ |

Label สองตัวที่มือใหม่ในวงการ Open Source ควรรู้จักเป็นพิเศษคือ **`good first issue`** และ **`help wanted`** เพราะ Maintainer มักจะติด label เหล่านี้ให้กับ issue ที่เหมาะกับคนนอกทีมที่อยากเริ่มมีส่วนร่วม (contribute) กับโปรเจกต์เป็นครั้งแรก — GitHub ถึงกับมีหน้ารวม https://github.com/issues?q=label:%22good+first+issue%22 ให้ค้นหา issue เหล่านี้ข้ามทุก repository ทั่วโลกด้วย

### 193.3 วิธีติด Label ให้กับ Issue

**วิธีที่ 1 — ตอนสร้าง issue ใหม่:** เลือกจากช่อง **Labels** ด้านขวามือของฟอร์มสร้าง issue

**วิธีที่ 2 — ที่ issue ที่มีอยู่แล้ว:**
1. เปิด issue นั้นขึ้นมา
2. ที่แถบด้านขวา (sidebar) หาหัวข้อ **Labels**
3. คลิกไอคอนรูปเฟือง (⚙️) ข้าง ๆ
4. ติ๊กเลือก label ที่ต้องการ (เลือกได้หลายอัน)
5. คลิกที่อื่นเพื่อปิดเมนู การเปลี่ยนแปลงจะถูกบันทึกทันที

### 193.4 การสร้าง Label เอง (Custom Label)

Label เริ่มต้นของ GitHub อาจไม่ครอบคลุมพอสำหรับทีมที่มี workflow เฉพาะตัว เราสามารถสร้าง label ใหม่ได้เอง:

1. เข้าไปที่ repository → แท็บ **Issues**
2. คลิก **Labels** (อยู่ข้าง ๆ ปุ่ม Milestones มุมขวาบนของรายการ issue)
3. คลิกปุ่ม **New label**
4. กรอก:
   - **Label name** — ชื่อ label เช่น `priority: high`, `needs-triage`, `frontend`, `backend`
   - **Description** — คำอธิบายสั้น ๆ ว่า label นี้ใช้ตอนไหน
   - **Color** — เลือกสีได้ทั้งจาก color picker หรือใส่ hex code เอง เช่น `#D93F0B`
5. คลิก **Create label**

### 193.5 แนวทางการออกแบบระบบ Label ที่ดีสำหรับทีม

ทีมมืออาชีพมักจะออกแบบ label เป็น **กลุ่ม (category)** โดยใช้ prefix เพื่อไม่ให้ปนกันมั่ว เช่น:

```
type: bug
type: feature
type: docs
type: chore

priority: critical
priority: high
priority: medium
priority: low

status: needs-triage
status: in-progress
status: blocked
status: ready-for-review

area: frontend
area: backend
area: database
area: ci-cd
```

การตั้งชื่อแบบ `หมวด: ค่า` ทำให้เวลาดูในรายการ label ทั้งหมดจะถูกจัดกลุ่มได้เป็นระเบียบ และเมื่อใช้ search filter อย่าง `label:"priority: high"` ก็จะกรองได้ตรงจุดชัดเจน (สังเกตว่าต้องใส่เครื่องหมายคำพูดครอบเมื่อชื่อ label มีช่องว่างหรือเครื่องหมาย `:` อยู่ในชื่อ)

> **ข้อควรระวัง:** อย่าสร้าง label เยอะเกินความจำเป็น ยิ่งมี label เยอะเท่าไหร่ ยิ่งต้องมีวินัยในการติดให้ถูกต้องสม่ำเสมอ ไม่อย่างนั้น label จะกลายเป็นสิ่งที่ไม่มีใครดูแลและไม่มีประโยชน์

## Step 194: Assignees — มอบหมายงานให้คนในทีม

### 194.1 Assignee คืออะไร

**Assignee** คือผู้ใช้ GitHub ที่ถูก **มอบหมาย** ให้รับผิดชอบ issue นั้น ๆ พูดง่าย ๆ คือ "ใครเป็นคนทำเรื่องนี้" การกำหนด assignee ช่วยให้:

- ทีมรู้ทันทีว่างานนี้มีเจ้าของแล้วหรือยัง ไม่เกิดเหตุการณ์ "ต่างคนต่างคิดว่าอีกคนทำ"
- กรอง issue ตามคนได้ง่าย (ดูว่าใครมีงานค้างอยู่เท่าไหร่)
- แสดงผลใน Dashboard ส่วนตัวของแต่ละคนบน GitHub (`github.com` หน้าแรกจะมีสรุป issue/PR ที่ถูก assign ให้ตัวเอง)

### 194.2 วิธี Assign คนให้กับ Issue

**ข้อจำกัดสำคัญที่ต้องรู้:** จะ assign ใครให้กับ issue ได้ คน ๆ นั้นต้องเป็น **Collaborator** ของ repository นั้นก่อน (มีสิทธิ์เข้าถึง repository อย่างน้อยระดับ read ขึ้นไป ถ้าเป็น private repo) ถ้าเป็น public repository แบบ Open Source ทั่วไป คนนอกทีมมักจะ assign ตัวเองไม่ได้ทันที ต้องขอสิทธิ์จาก maintainer ก่อน หรือ maintainer เป็นคน assign ให้เอง

ขั้นตอนการ assign:

1. เปิด issue ขึ้นมา
2. ที่แถบด้านขวา หาหัวข้อ **Assignees**
3. คลิกไอคอนรูปเฟือง
4. เลือกชื่อผู้ใช้จากรายการ (ระบบจะค้นหาให้จากรายชื่อ collaborator)
5. ปิดเมนู — บันทึกทันที

GitHub รองรับการ **assign ได้มากกว่า 1 คน** ต่อ issue เดียว เผื่อกรณีที่งานนั้นต้องทำร่วมกันหลายคน (pair programming, งานที่ต้องข้ามทีม)

### 194.3 การ Assign ตัวเอง (Self-assign)

ถ้าคุณเป็น collaborator ของ repository อยู่แล้ว วิธีที่เร็วที่สุดในการ assign ตัวเองคือ:

- คลิกที่คำว่า **"assign yourself"** ซึ่งจะปรากฏในแถบ Assignees หากคุณยังไม่ได้ถูก assign
- หรือคอมเมนต์คำว่า `/assign` ในบาง repository ที่ตั้งค่า bot ไว้รองรับคำสั่งนี้ (เป็นฟีเจอร์ของ bot เสริม เช่น Probot ไม่ใช่ฟีเจอร์ดั้งเดิมของ GitHub)

### 194.4 ความแตกต่างระหว่าง Assignee กับ Author

มือใหม่มักสับสนสองคำนี้:

| | Author (ผู้เปิด issue) | Assignee (ผู้รับผิดชอบ) |
|---|---|---|
| ความหมาย | คนที่กด "New issue" สร้างมันขึ้นมา | คนที่ถูกมอบหมายให้แก้ไข/ดำเนินการ |
| เปลี่ยนได้ไหม | เปลี่ยนไม่ได้ (fix ตายตัวตลอดไป) | เปลี่ยนได้ตลอดเวลา |
| จำนวน | มีได้แค่ 1 คนเสมอ | มีได้หลายคน |

ตัวอย่างเช่น ผู้ใช้ทั่วไป (author) รายงานบั๊กเข้ามา แต่คนที่ถูก assign ให้แก้บั๊กนั้นอาจเป็นนักพัฒนาในทีมคนละคนกับ author เลยก็ได้

## Step 195: Milestones เบื้องต้น (จัดกลุ่ม issue ตาม release)

### 195.1 Milestone คืออะไร

**Milestone** คือการจัดกลุ่ม issue (และ pull request) จำนวนหนึ่งเข้าด้วยกันภายใต้ **เป้าหมายเดียวกัน** ซึ่งมักจะผูกกับ:

- การออก release เวอร์ชันใดเวอร์ชันหนึ่ง เช่น `v1.0.0`, `v2.1.0`
- ช่วงเวลาทำงาน (sprint) เช่น `Sprint 12`
- เป้าหมายใหญ่ของโปรเจกต์ เช่น `Public Beta Launch`

แต่ละ milestone มี:
- ชื่อ (title)
- คำอธิบาย (description)
- วันครบกำหนด (due date) — ไม่บังคับ
- Progress bar ที่คำนวณอัตโนมัติจากสัดส่วน issue ที่ปิดแล้ว/ทั้งหมดใน milestone นั้น

### 195.2 วิธีสร้างและใช้งาน Milestone

1. เข้าไปที่ repository → แท็บ **Issues**
2. คลิก **Milestones**
3. คลิก **New milestone**
4. กรอกชื่อ เช่น `v1.0.0 Release`, กำหนดวันครบกำหนด (ถ้ามี), ใส่คำอธิบาย
5. คลิก **Create milestone**

เมื่อสร้างแล้ว สามารถผูก issue เข้ากับ milestone นี้ได้จากแถบด้านขวาของ issue (คล้ายกับการติด label) โดยคลิกที่หัวข้อ **Milestone** แล้วเลือกจากรายการ

```
Milestone: v1.0.0 Release
Progress: ████████░░ 8/10 issues closed (80%)
Due: 15 ธันวาคม 2026
```

### 195.3 ประโยชน์ของ Milestone

- เห็นภาพรวมว่า release ถัดไปเหลืองานอะไรอีกบ้างก่อนจะปล่อยได้จริง
- ใช้ progress bar (คำนวณอัตโนมัติ) เป็นตัวชี้วัดความคืบหน้าให้ทีมและผู้บริหารดูได้ง่าย โดยไม่ต้องนับเองด้วยมือ
- กรอง issue ตาม milestone ได้ผ่าน search syntax `milestone:"v1.0.0 Release"`
- ปิด milestone ได้เมื่องานทั้งหมดเสร็จ ซึ่งเป็นสัญญาณบอกว่า release นั้นพร้อมออกจริง

### 195.4 Milestone vs Label — ต่างกันอย่างไร

จุดที่มือใหม่มักสับสนคือ Label กับ Milestone ดูคล้ายกันตรงที่ใช้จัดหมวดหมู่ issue เหมือนกัน แต่มีความต่างสำคัญ:

| | Label | Milestone |
|---|---|---|
| จำนวนต่อ issue | ติดได้หลายอันพร้อมกัน | ผูกได้แค่ **อันเดียว** ต่อ issue |
| จุดประสงค์หลัก | บอก "ประเภท/ลักษณะ" ของ issue | บอก "issue นี้อยู่ใน release/sprint ไหน" |
| มี due date ไหม | ไม่มี | มีได้ |
| มี progress bar ไหม | ไม่มี | มี (คำนวณอัตโนมัติ) |

พูดง่าย ๆ **Label ตอบคำถามว่า "นี่คืออะไร"** ส่วน **Milestone ตอบคำถามว่า "นี่จะเสร็จเมื่อไหร่/อยู่ในรอบไหน"**

> **หมายเหตุสำคัญ:** เนื้อหาเรื่อง Milestone ในที่นี้เป็นเพียงความรู้เบื้องต้นเพื่อให้ใช้งานร่วมกับ Issue ได้อย่างครบถ้วนเท่านั้น เราจะกลับมาเจาะลึกเรื่อง **Milestone และการวางแผน Release อย่างมืออาชีพ** อีกครั้งแบบละเอียดใน **Part 26** ซึ่งจะรวมถึงการเชื่อมโยง Milestone กับ Project Board, การวางแผน Roadmap และการบริหารทีมด้วย Milestone ในสถานการณ์จริง

## Step 196: การอ้างอิงข้าม issue/PR ด้วย `#number`, closing keywords

หนึ่งในฟีเจอร์ที่ทรงพลังที่สุดของ GitHub คือความสามารถในการ **เชื่อมโยง (link)** issue, pull request และ commit เข้าหากันโดยอัตโนมัติ

### 196.1 การอ้างอิงด้วย `#number`

ทุก issue และ pull request ใน repository เดียวกันจะมีหมายเลขไม่ซ้ำกัน (นับรวมกันทั้ง issue และ PR ในลำดับเดียวกัน) เมื่อคุณพิมพ์ `#` ตามด้วยหมายเลข ที่ใดก็ตามใน:

- Description ของ issue
- Comment ของ issue หรือ PR
- Commit message
- Description ของ PR

GitHub จะแปลงข้อความนั้นให้กลายเป็น **ลิงก์คลิกได้** ไปยัง issue/PR นั้นโดยอัตโนมัติ ตัวอย่าง:

```markdown
บั๊กนี้เกี่ยวข้องกับ #38 ที่เคยรายงานไว้เมื่อเดือนก่อน
น่าจะเกิดจากการแก้ไขใน PR #45 ที่เพิ่ง merge เข้าไป
```

เมื่อโพสต์ข้อความนี้ ทั้ง `#38` และ `#45` จะกลายเป็นลิงก์ และที่สำคัญกว่านั้นคือ **GitHub จะไปสร้าง back-reference (การอ้างอิงย้อนกลับ)** ที่ issue #38 และ PR #45 โดยอัตโนมัติด้วย ทำให้เมื่อเปิด #38 ขึ้นมาดู จะเห็นข้อความ "mentioned this issue" พร้อมลิงก์กลับมายัง issue ปัจจุบัน — เกิดเป็นเครือข่ายการเชื่อมโยงที่ตามรอยได้ทั้งหมด

### 196.2 การอ้างอิงข้าม Repository

ถ้าต้องการอ้างอิง issue หรือ PR ที่อยู่ต่าง repository กัน ให้ใช้รูปแบบเต็ม:

```markdown
owner/repo#number
```

ตัวอย่าง:

```markdown
ปัญหานี้คล้ายกับที่เคยเจอใน facebook/react#12345
```

### 196.3 Closing Keywords — คำสั่งปิด Issue อัตโนมัติผ่าน PR

นี่คือฟีเจอร์ที่ทีมมืออาชีพใช้เป็นประจำ เมื่อคุณสร้าง Pull Request เพื่อแก้ไขปัญหาที่ระบุใน issue ใดไว้ คุณสามารถใช้ **closing keyword** ใน description หรือ commit message ของ PR นั้น เพื่อสั่งให้ GitHub **ปิด issue นั้นโดยอัตโนมัติทันทีที่ PR ถูก merge เข้า default branch**

**Closing keywords ที่ GitHub รองรับ (ภาษาอังกฤษเท่านั้น ไม่รองรับภาษาไทย):**

```
close, closes, closed
fix, fixes, fixed
resolve, resolves, resolved
```

**ตัวอย่างการใช้งานจริงใน PR description:**

```markdown
## รายละเอียด
แก้ไขปัญหาปุ่ม Login ที่ error 500 เมื่อกรอกอีเมลที่มีอักขระ `+`

fixes #42
```

หรือใช้อ้างอิงหลาย issue พร้อมกันในบรรทัดเดียวหรือหลายบรรทัดก็ได้:

```markdown
closes #42, closes #45
resolves #50
```

หรือใช้ในกรณีข้าม repository:

```markdown
fixes owner/repo#42
```

**เงื่อนไขสำคัญที่ต้องรู้:**

1. Keyword เหล่านี้จะทำงาน (ปิด issue อัตโนมัติ) **ก็ต่อเมื่อ PR ถูก merge เข้า default branch เท่านั้น** (โดยปกติคือ `main`) ถ้า merge เข้า branch อื่นจะไม่มีผลปิด issue อัตโนมัติ
2. ถ้าใส่ keyword ไว้แต่ PR ยังไม่ merge (แค่เปิดค้างไว้) issue จะยัง **ไม่ปิด** — จะแค่ขึ้นข้อความว่า "will close this issue" เป็นการเตือนล่วงหน้าเท่านั้น
3. ถ้า PR ถูกปิดโดยไม่ merge (close โดยไม่รวมโค้ด) issue ที่อ้างถึงจะ **ไม่ถูกปิด**
4. สามารถใส่ keyword ไว้ใน **commit message** ของ commit ใดก็ได้ใน PR นั้นแทนก็ได้ ไม่จำเป็นต้องอยู่ใน PR description เท่านั้น
5. คำที่ไม่อยู่ในลิสต์นี้ (เช่นแค่พิมพ์ `#42` เฉย ๆ โดยไม่มี keyword นำหน้า) จะแค่ **ลิงก์ไปหา** issue นั้นเฉย ๆ ไม่ได้สั่งปิดอัตโนมัติ

### 196.4 ทำไม Closing Keywords ถึงสำคัญ

ฟีเจอร์นี้ช่วยลดงานที่ต้องทำด้วยมือ (manual work) และลดโอกาสที่คนจะลืมปิด issue หลังจากแก้ปัญหาเสร็จแล้ว นอกจากนี้ยังสร้าง **audit trail** ที่ชัดเจนมาก — ใครก็ตามที่มาดู issue ในภายหลังจะเห็นทันทีว่า "ปัญหานี้ถูกแก้ด้วย PR ไหน commit ไหน" โดยไม่ต้องถามใครเลย

```
Issue #42: [Bug] ปุ่ม Login ไม่ทำงานบน Safari
Status: Closed ✅

🔗 timeline:
- user123 opened this issue 3 days ago
- dev456 self-assigned this
- dev456 mentioned this issue in PR #45 "fixes #42"
- dev456 closed this via PR #45  ← ปิดอัตโนมัติตอน merge
```

เราจะพูดถึงเรื่อง Pull Request แบบละเอียดเต็มรูปแบบใน **Part 21** ที่กำลังจะถึงต่อไป และจะได้ลองใช้ closing keyword จริงในแบบฝึกหัดของ Part นั้น

## Step 197: Issue comments และ reactions (👍👎🎉)

### 197.1 Comments — การพูดคุยภายใน Issue

ทุก issue สามารถมี **comment** ต่อท้ายได้ไม่จำกัดจำนวน ใช้สำหรับ:

- อัปเดตความคืบหน้า
- ถามคำถามเพิ่มเติม
- แจ้งว่าพบข้อมูลใหม่ที่เกี่ยวข้อง
- พูดคุยหาทางออกก่อนลงมือแก้จริง

Comment รองรับ Markdown เต็มรูปแบบเหมือน description ของ issue รวมถึงสามารถ:

- **@mention** ผู้ใช้คนอื่นได้ด้วย `@username` เพื่อแจ้งเตือน (notification) ให้เขาเข้ามาดู
- แนบไฟล์/รูปภาพได้โดยลากวาง
- ใช้ code block พร้อม syntax highlighting ได้ (` ```javascript ... ``` `)
- **Quote reply** — เลือกข้อความในคอมเมนต์ก่อนหน้าแล้วกด "Reply" หรือพิมพ์ `>` นำหน้าเพื่ออ้างอิงข้อความที่ตอบกลับ

ตัวอย่าง comment ที่ดี:

```markdown
@dev456 ผมลองทดสอบใน Firefox แล้วก็เจอปัญหาเดียวกันครับ ไม่ใช่แค่ Safari

> เมื่อผู้ใช้กด login ด้วยอีเมลที่มีอักขระ `+`

เพิ่มเติมคือแม้แต่อักขระ `.` ซ้อนกันก็ทำให้ error เหมือนกัน เช่น `a..b@example.com`

น่าจะเป็นปัญหาที่ regex validation ฝั่ง backend ครับ
```

### 197.2 การแก้ไขและลบ Comment

ผู้เขียน comment (หรือคนที่มีสิทธิ์ระดับ maintainer ขึ้นไปของ repository) สามารถ:

- **Edit** — คลิกไอคอนสามจุด (`...`) มุมขวาบนของ comment แล้วเลือก Edit — GitHub จะแสดงคำว่า "edited" กำกับไว้พร้อมประวัติการแก้ไขที่ดูย้อนหลังได้
- **Delete** — ลบ comment ทิ้งได้เช่นกัน (แต่ควรใช้อย่างระมัดระวัง เพราะอาจทำให้บทสนทนาขาดตอนไม่ต่อเนื่อง)
- **Hide** — Maintainer สามารถ "ซ่อน" comment ที่ไม่เหมาะสม เช่น spam, off-topic, abusive โดยไม่ต้องลบทิ้งถาวร (เลือกเหตุผลได้ เช่น Spam, Abusive, Off-topic, Outdated, Resolved)

### 197.3 Reactions — การตอบสนองด้วยอิโมจิ

แทนที่จะต้องคอมเมนต์ "+1" หรือ "เห็นด้วยครับ" ซึ่งจะทำให้เกิด notification สแปมโดยไม่จำเป็น GitHub มีฟีเจอร์ **Reactions** ให้กดตอบสนองด้วยอิโมจิได้โดยตรงที่ตัว issue หรือ comment แต่ละอัน

**อิโมจิที่ใช้ได้:**

| อิโมจิ | ความหมายที่มักใช้ |
|---|---|
| 👍 (thumbs up) | เห็นด้วย / สนับสนุนไอเดียนี้ |
| 👎 (thumbs down) | ไม่เห็นด้วย / คัดค้าน |
| 😄 (smile) | ตลก / เบาสมอง |
| 🎉 (hooray/tada) | ยินดี / ดีใจกับความสำเร็จ |
| 😕 (confused) | สับสน / ไม่เข้าใจ |
| ❤️ (heart) | ชื่นชอบมาก |
| 🚀 (rocket) | ตื่นเต้น / รอคอยให้เกิดขึ้นจริง |
| 👀 (eyes) | กำลังติดตามดูอยู่ / รับทราบแล้ว |

วิธีกด reaction: เลื่อนเมาส์ไปที่มุมขวาบนของ issue หรือ comment แล้วคลิกไอคอนหน้ายิ้ม (😊) ที่ปรากฏขึ้นมา จากนั้นเลือกอิโมจิที่ต้องการ

### 197.4 ทำไม Reactions ถึงมีประโยชน์มากกว่าที่คิด

Reactions ไม่ได้เป็นแค่ของเล่นสนุก ๆ แต่มีประโยชน์จริงจังมาก:

1. **วัดความนิยมของ feature request ได้เชิงปริมาณ** — Maintainer ของโปรเจกต์ Open Source ใหญ่ ๆ มักจะเรียงลำดับ feature request ตามจำนวน 👍 เพื่อดูว่าอะไรที่ชุมชนต้องการมากที่สุด สามารถ sort issue list ด้วยตัวเลือก "Sort by: Most reacted" ได้โดยตรง
2. **ลด notification spam** — ถ้าไม่มี reaction คนที่อยากบอกว่า "เห็นด้วย" จะต้องคอมเมนต์ ซึ่งจะส่ง notification ไปหาทุกคนที่ subscribe อยู่ที่ issue นั้น (อาจเป็นร้อยคนในโปรเจกต์ดัง ๆ) แค่กด reaction ไม่ทำให้เกิด notification ก่อกวนแบบนั้น
3. **บอกอารมณ์/ท่าทีของทีมได้เร็ว** โดยไม่ต้องพิมพ์อะไรเลย

## Step 198: การค้นหาและกรอง issue ด้วย search syntax

เมื่อ repository มี issue หลักร้อยหลักพันอัน การไล่ดูทีละหน้าเป็นไปไม่ได้เลย GitHub จึงมีระบบ **Search Syntax** ที่ทรงพลังมากสำหรับกรอง issue (และ PR) ตามเงื่อนไขที่ต้องการ

### 198.1 ตำแหน่งของช่องค้นหา

ที่หน้า **Issues** ของ repository จะมีช่องค้นหาด้านบน ซึ่งค่าเริ่มต้นจะใส่ `is:issue is:open` ไว้ให้อยู่แล้ว (แปลว่า "แสดงเฉพาะ issue ที่ยัง open")

### 198.2 Qualifiers พื้นฐานที่ใช้บ่อยที่สุด

| Syntax | ความหมาย |
|---|---|
| `is:issue` | เฉพาะ issue (ไม่รวม pull request) |
| `is:pr` | เฉพาะ pull request |
| `is:open` | สถานะ open เท่านั้น |
| `is:closed` | สถานะ closed เท่านั้น |
| `label:bug` | มี label ชื่อ `bug` |
| `label:"priority: high"` | มี label ที่ชื่อมีช่องว่าง/เครื่องหมาย ให้ใส่ในเครื่องหมายคำพูด |
| `assignee:username` | ถูก assign ให้ผู้ใช้ชื่อนี้ |
| `assignee:@me` | ถูก assign ให้ตัวเอง (ผู้ที่กำลัง login อยู่) |
| `author:username` | เปิดโดยผู้ใช้ชื่อนี้ |
| `mentions:username` | มีการ @mention ผู้ใช้ชื่อนี้อยู่ในเนื้อหาหรือ comment |
| `milestone:"v1.0.0 Release"` | อยู่ใน milestone นี้ |
| `no:label` | ไม่มี label ติดอยู่เลย |
| `no:assignee` | ยังไม่มีใคร assign |
| `no:milestone` | ยังไม่ถูกผูกกับ milestone ใด |
| `comments:>5` | มี comment มากกว่า 5 อัน |
| `created:>2026-01-01` | สร้างหลังวันที่ที่กำหนด |
| `updated:<2026-06-01` | อัปเดตล่าสุดก่อนวันที่ที่กำหนด |
| `sort:created-desc` | เรียงจากสร้างล่าสุดไปเก่าสุด |
| `in:title` | ค้นหาคำเฉพาะใน title เท่านั้น |
| `in:body` | ค้นหาคำเฉพาะใน description/body เท่านั้น |

### 198.3 การรวมหลาย Qualifier เข้าด้วยกัน

จุดแข็งที่สุดของ search syntax คือสามารถ **รวมหลายเงื่อนไขในคำค้นหาเดียวได้** โดยแค่เว้นวรรคระหว่างแต่ละ qualifier (เป็นการ "AND" กันโดยอัตโนมัติ):

```
is:issue is:open label:bug assignee:dev456
```

ความหมาย: หา issue (ไม่ใช่ PR) ที่ยัง open อยู่ ติด label `bug` และถูก assign ให้ `dev456`

```
is:issue is:open label:"priority: high" no:assignee
```

ความหมาย: หาบั๊กความสำคัญสูงที่ยังไม่มีใครรับผิดชอบ — คำค้นหานี้มีประโยชน์มากสำหรับการประชุม triage (คัดกรองงาน) ประจำสัปดาห์

```
is:issue is:closed label:bug milestone:"v1.0.0 Release" sort:created-asc
```

ความหมาย: หาบั๊กทั้งหมดที่ปิดแล้วภายใต้ milestone v1.0.0 เรียงจากเก่าไปใหม่ — ใช้สำหรับเขียน release notes

### 198.4 การค้นหาแบบข้อความอิสระ (Free-text search)

นอกจาก qualifier แล้ว ยังพิมพ์คำค้นหาแบบข้อความธรรมดาผสมเข้าไปได้เลย เช่น:

```
is:open label:bug login error
```

ความหมาย: หา issue ที่ยัง open ติด label bug และมีคำว่า "login" กับ "error" อยู่ใน title หรือ body

### 198.5 การบันทึกคำค้นหาที่ใช้บ่อย

ถ้าคุณใช้คำค้นหาชุดหนึ่งบ่อยมาก (เช่นคำค้นหาสำหรับ triage ประจำสัปดาห์) สามารถ bookmark URL ของหน้าค้นหานั้นไว้ได้เลย เพราะเงื่อนไขค้นหาทั้งหมดจะถูกเก็บอยู่ใน URL ในรูปแบบ query parameter `?q=...` ทำให้แชร์ลิงก์คำค้นหาให้เพื่อนร่วมทีมได้ง่ายมาก เช่น:

```
https://github.com/owner/repo/issues?q=is%3Aopen+is%3Aissue+label%3Abug+no%3Aassignee
```

## Step 199: Pin issue, lock conversation, transfer issue ข้าม repository

Step นี้จะพูดถึงฟีเจอร์การจัดการ issue ระดับที่ maintainer ใช้บ่อยเมื่อดูแลโปรเจกต์ขนาดใหญ่หรือมีคนเข้ามาเกี่ยวข้องเยอะ

### 199.1 Pin Issue — ปักหมุด Issue สำคัญไว้ด้านบน

**Pinned Issue** คือ issue ที่ถูก "ปักหมุด" ให้ปรากฏอยู่บนสุดของหน้า Issues เสมอ ไม่ว่าจะเรียงลำดับแบบไหนก็ตาม เหมาะสำหรับ issue ที่ต้องการให้ทุกคนเห็นเป็นอันดับแรก เช่น:

- ประกาศสำคัญ (roadmap ของโปรเจกต์, การเปลี่ยนแปลง breaking change)
- คำแนะนำสำหรับผู้ที่จะมาช่วย contribute
- Issue ติดตามสถานะบางอย่างระยะยาว (tracking issue)

**วิธี Pin:**
1. เปิด issue ที่ต้องการ
2. คลิกไอคอนสามจุด (`...`) มุมขวาบน
3. เลือก **Pin issue**

**ข้อจำกัด:** repository หนึ่งสามารถ pin issue ได้สูงสุด **3 อันเท่านั้น** ต่อครั้ง (แสดงเรียงกันด้านบนสุดของหน้า Issues) ถ้าต้องการ pin อันใหม่เพิ่มเมื่อครบ 3 แล้ว ต้อง unpin อันเก่าออกก่อน

### 199.2 Lock Conversation — ล็อกไม่ให้คอมเมนต์เพิ่ม

**Lock conversation** คือการปิดกั้นไม่ให้มีใคร (ยกเว้น collaborator ที่มีสิทธิ์เขียนของ repository) คอมเมนต์เพิ่มเติมใน issue นั้นได้อีก ใช้ในสถานการณ์:

- บทสนทนาเริ่มออกนอกเรื่อง (off-topic) หรือกลายเป็นการทะเลาะกัน
- Issue เก่ามากที่ถูกปิดไปนานแล้ว แต่ยังมีคนเข้ามาคอมเมนต์ต่อท้ายเรื่อย ๆ ("necroposting") ทำให้เกิด notification รบกวนคนที่เกี่ยวข้อง
- ต้องการหยุดการพูดคุยในหัวข้อที่อ่อนไหวเป็นการชั่วคราว

**วิธี Lock:**
1. เปิด issue ที่ต้องการ
2. คลิกไอคอนสามจุด มุมขวาบน
3. เลือก **Lock conversation**
4. เลือกเหตุผล (ไม่บังคับ แต่แนะนำให้เลือก): `Off-topic`, `Too heated`, `Resolved`, `Spam`
5. คลิก **Lock conversation** เพื่อยืนยัน

เมื่อ lock แล้ว issue จะแสดงไอคอนแม่กุญแจ 🔒 กำกับไว้ และคนทั่วไป (non-collaborator) จะไม่สามารถคอมเมนต์เพิ่มได้อีก แต่ยังคง **อ่านเนื้อหาเดิมได้ตามปกติ** สามารถ **Unlock** กลับมาได้ทีหลังหากสถานการณ์คลี่คลายแล้ว

> **ข้อควรรู้:** การ lock ไม่เหมือนกับการ close — issue ที่ถูก lock ยังสามารถเป็น open หรือ closed ก็ได้ ทั้งสองสถานะนี้เป็นอิสระต่อกัน (คุณสามารถ lock issue ที่ยัง open อยู่ก็ได้ ถ้าอยากหยุดการพูดคุยแต่งานยังไม่เสร็จ)

### 199.3 Transfer Issue — โอนย้าย Issue ข้าม Repository

บางครั้ง issue อาจถูกเปิดผิดที่ เช่น ผู้ใช้รายงานบั๊กที่ repository ของ frontend ทั้งที่จริง ๆ ต้นตอปัญหาอยู่ที่ repository ของ backend API แทนที่จะต้องปิด issue เดิมแล้วให้คนเปิดใหม่เอง GitHub มีฟีเจอร์ **Transfer issue** ให้ maintainer ย้าย issue ไปยัง repository อื่นได้โดยตรง โดยที่ **เนื้อหา comment ทั้งหมดยังคงอยู่ครบถ้วน**

**เงื่อนไขการ Transfer:**
- คุณต้องมีสิทธิ์ระดับ **Admin** (หรือสูงกว่า) ทั้งใน repository ต้นทางและปลายทาง
- Repository ปลายทางต้องเปิดใช้งานฟีเจอร์ Issues อยู่

**วิธี Transfer:**
1. เปิด issue ที่ต้องการโอนย้าย
2. คลิกไอคอนสามจุด มุมขวาบน
3. เลือก **Transfer issue**
4. พิมพ์ชื่อ repository ปลายทางที่ต้องการโอนไป (รูปแบบ `owner/repo`)
5. คลิก **Transfer issue** เพื่อยืนยัน

**สิ่งที่เกิดขึ้นหลัง Transfer:**
- Issue จะได้ **หมายเลขใหม่** ตามลำดับของ repository ปลายทาง (เช่นจาก `#42` ใน repo เดิม อาจกลายเป็น `#7` ใน repo ใหม่ เพราะนับแยกกันคนละ repository)
- Comment ทั้งหมด, ผู้เขียนดั้งเดิม (author) ยังคงเดิม
- Label และ Assignee ของ repository เดิม **จะไม่ถูกโอนย้ายไปด้วย** เพราะ label/collaborator ของสอง repository อาจไม่ตรงกัน ต้องไปติด label และ assign ใหม่ที่ repository ปลายทางเอง
- ที่ repository เดิม จะมีข้อความอัตโนมัติเหลือไว้บอกว่า issue นี้ถูกโอนย้ายไปที่ไหน พร้อมลิงก์ตามไปดูได้ (ลิงก์เดิมจะ redirect ไปยังตำแหน่งใหม่ให้อัตโนมัติ ไม่มีวัน 404)

## Step 200: แบบฝึกหัด — จัดการ issue tracker เต็มรูปแบบสำหรับโปรเจกต์จำลอง

ถึงเวลาลงมือปฏิบัติจริงเพื่อรวบทุกเรื่องที่เรียนมาในเฟส Issue นี้เข้าด้วยกัน

### 200.1 เป้าหมายของแบบฝึกหัด

สร้าง repository จำลองบน GitHub ชื่อ `todo-app-demo` (หรือใช้ repository เดิมที่คุณสร้างไว้ตั้งแต่ Part ก่อนหน้าก็ได้) แล้วจัดการ issue tracker ให้ครบวงจรตามที่กำหนด:

- สร้าง issue อย่างน้อย **8 อัน**
- ติด label ให้ครบทุก issue
- Assign ผู้รับผิดชอบให้อย่างน้อยครึ่งหนึ่งของ issue ทั้งหมด
- สร้าง milestone อย่างน้อย 1 อัน แล้วผูก issue เข้าไป
- ทดลองใช้ closing keyword, การอ้างอิงข้าม issue, comment, reaction, search filter, pin และ lock ให้ครบ

### 200.2 ขั้นตอนที่ 1 — เตรียม Label

สร้าง label เพิ่มเติมจากที่ GitHub มีให้ (นอกเหนือจาก `bug`, `enhancement`, `documentation` ที่มีอยู่แล้ว):

```
priority: high      (สีแดง #B60205)
priority: medium    (สีส้ม #FBCA04)
```

### 200.6 ขั้นตอนที่ 5 — ฝึก Closing Keyword ผ่าน Branch และ Commit (ไม่ต้องสร้าง PR จริงก็ได้ในขั้นนี้)

ทดลองสร้าง branch ใหม่ชื่อ `fix/login-double-click` แล้ว commit โดยใส่ข้อความอ้างอิง issue ในรูปแบบที่ถูกต้อง:

```bash
git checkout -b fix/login-double-click
# แก้ไขไฟล์ที่เกี่ยวข้อง...
git add .
git commit -m "fix: ป้องกันการกดปุ่ม login ซ้ำหลายครั้ง

fixes #1"
```

เก็บ branch นี้ไว้ก่อน เราจะนำมันมาเปิดเป็น Pull Request จริงใน **Part 21** เพื่อดูว่า `fixes #1` จะไปปิด issue #1 ให้อัตโนมัติตอน merge จริงหรือไม่

### 200.7 ขั้นตอนที่ 6 — ฝึกการค้นหา

เปิดหน้า Issues แล้วลองพิมพ์คำค้นหาต่อไปนี้ทีละอัน สังเกตผลลัพธ์ที่ได้ในแต่ละครั้ง:

```
is:open is:issue label:bug
is:open is:issue no:assignee
is:open is:issue priority:high
is:closed is:issue
is:open is:issue milestone:"v1.0.0 - Initial Release"
is:open is:issue label:"good first issue"
```

(หมายเหตุ: `priority:high` ในตัวอย่างข้างต้นควรแก้เป็น `label:"priority: high"` เพราะเป็นชื่อ label ไม่ใช่ qualifier พิเศษของ GitHub — ลองทั้งสองแบบเพื่อดูความแตกต่างของผลลัพธ์)

## สรุป Part 20

ใน Part นี้เราได้เรียนรู้ว่า:

1. **Issue** คือฟีเจอร์ของ GitHub (ไม่ใช่ของ Git) สำหรับติดตามบั๊ก ฟีเจอร์ใหม่ งานที่ต้องทำ และการพูดคุยเชิงเทคนิค
2. การสร้าง issue ที่ดีต้องมี **title ที่ชัดเจน** และ **description ที่มีโครงสร้าง** เขียนด้วย Markdown รวมถึงรู้จัก **Issue Template/Issue Forms** ที่ช่วยบังคับให้กรอกข้อมูลครบ
3. **Labels** ใช้จัดหมวดหมู่ issue ทั้งแบบ default ของ GitHub (`bug`, `enhancement` ฯลฯ) และแบบสร้างเอง ควรออกแบบเป็นระบบด้วย prefix เช่น `priority:`, `type:`, `area:`
4. **Assignees** ใช้มอบหมายผู้รับผิดชอบ ต้องเป็น collaborator ของ repository และ assign ได้มากกว่า 1 คน
5. **Milestones** ใช้จัดกลุ่ม issue ตาม release หรือ sprint พร้อม progress bar อัตโนมัติ — เราจะเจาะลึกเรื่องนี้อีกครั้งใน Part 26
6. การอ้างอิง `#number` เชื่อมโยง issue/PR เข้าหากันพร้อม back-reference อัตโนมัติ และ **closing keywords** (`fixes`, `closes`, `resolves`) ทำให้ issue ปิดอัตโนมัติเมื่อ PR ที่อ้างอิงถูก merge เข้า default branch
7. **Comments** และ **Reactions** (👍👎🎉 ฯลฯ) ช่วยให้ทีมสื่อสารกันได้อย่างเป็นระเบียบและลด notification spam
8. **Search syntax** (`is:open`, `label:bug`, `assignee:username` และอื่น ๆ) ช่วยกรอง issue จำนวนมากให้เจอสิ่งที่ต้องการได้อย่างแม่นยำ
9. **Pin** ปักหมุด issue สำคัญ (สูงสุด 3 อัน), **Lock** ปิดกั้นการคอมเมนต์เพิ่ม, และ **Transfer** โอนย้าย issue ข้าม repository พร้อมรักษาเนื้อหาเดิมไว้ครบถ้วน
10. ลงมือปฏิบัติจริงด้วยการสร้าง issue tracker เต็มรูปแบบ ครบทั้ง label, assignee, milestone และเตรียม branch สำหรับใช้ closing keyword ใน Part ถัดไป
