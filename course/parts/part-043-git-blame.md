## Step 421: `git blame` คืออะไร ใช้ทำอะไร

เวลาคุณเปิดไฟล์โค้ดขึ้นมาสักไฟล์หนึ่งที่มีอายุหลายเดือนหรือหลายปี แล้วเจอบรรทัดแปลก ๆ ที่ดูเหมือนไม่มีเหตุผล เช่น:

```python
# TODO: อย่าลบบรรทัดนี้ ไม่งั้น production จะพัง
timeout = 30 + 5  # เผื่อ latency ของ payment gateway เก่า
```

คำถามที่ผุดขึ้นมาในหัวทันทีคือ:

- ใครเป็นคนเขียนบรรทัดนี้
- เขียนเมื่อไหร่
- เขียนใน commit ไหน มี commit message ว่าอะไร
- ตอนนั้นแก้ไขปัญหาอะไรอยู่

นี่คือคำถามที่ `git blame` มีไว้ตอบโดยเฉพาะ

### นิยาม

> **`git blame` คือคำสั่งที่แสดงผลไฟล์ทีละบรรทัด พร้อมกำกับว่าแต่ละบรรทัดถูกแก้ไข "ล่าสุด" โดย commit ไหน ใครเป็นผู้เขียน (author) และแก้ไขเมื่อวันที่เท่าไหร่**

ชื่อ "blame" แปลตรงตัวว่า "การตำหนิ/โทษ" ซึ่งเป็นชื่อที่ค่อนข้างจะสร้างความเข้าใจผิดโดยไม่ตั้งใจของ Git เอง (เราจะพูดเรื่องนี้ละเอียดใน Step 429) แต่ในทางเทคนิคแล้วมันไม่ได้มีไว้ "จับผิดใคร" เลย มันเป็นเครื่องมือ **สืบหาประวัติ (history archaeology)** ของโค้ดแต่ละบรรทัดต่างหาก

Git บางเวอร์ชันและบาง GUI จึงเรียกคำสั่งเดียวกันนี้ว่า `git annotate` (มีอยู่จริงเป็น alias เก่าแก่ของ blame) ซึ่งสื่อความหมายได้ตรงกว่า คือ "การใส่คำอธิบายกำกับ (annotate) แต่ละบรรทัด"

### วิธีใช้งานพื้นฐานที่สุด

```bash
git blame ชื่อไฟล์
```

ตัวอย่าง:

```bash
git blame src/payment.py
```

Git จะพิมพ์เนื้อหาของไฟล์ `src/payment.py` ออกมาทั้งไฟล์ โดยแต่ละบรรทัดจะมีข้อมูลกำกับไว้ทางซ้ายมือ บอกว่าบรรทัดนั้นมาจาก commit อะไร ใครเขียน เขียนเมื่อไหร่

### ใช้ทำอะไรได้บ้างในชีวิตจริง

1. **สืบหาสาเหตุของบั๊ก** — เจอโค้ดแปลก ๆ ที่ทำให้เกิดบั๊ก อยากรู้ว่าใครเพิ่มมันเข้ามาและทำไม
2. **หาบริบทของ business logic ที่ดูไม่มีเหตุผล** — เช่นทำไมต้อง `+ 5` ในตัวอย่างข้างต้น การเปิดดู commit message ที่เขียนบรรทัดนั้นมักให้คำตอบ
3. **หาคนที่เหมาะจะถามเกี่ยวกับโค้ดส่วนนั้น** — ถ้าคุณต้องแก้ไขโค้ดที่ไม่คุ้นเคย การรู้ว่าใครเขียนล่าสุดช่วยให้รู้ว่าควรไปคุยกับใคร
4. **ตรวจสอบว่า refactor ครั้งไหนที่ทำให้โค้ดเปลี่ยนพฤติกรรม** — ใช้คู่กับ bisect เพื่อหาว่า regression เกิดจาก commit ไหน (จะเรียนละเอียดเรื่อง `git bisect` ใน Part อื่น)
5. **ทำความเข้าใจ code ownership แบบไม่เป็นทางการ** — ดูคร่าว ๆ ว่าใครเป็นคนดูแลไฟล์นี้เป็นหลัก

### ตัวอย่างสถานการณ์จริง

สมมติคุณเป็นนักพัฒนาที่เพิ่งเข้าทีมใหม่ ได้รับมอบหมายให้แก้บั๊กในฟังก์ชัน `calculate_discount()` ในไฟล์ `pricing.py` แต่โค้ดมีเงื่อนไขประหลาดที่ไม่มีคอมเมนต์อธิบายเลย:

```python
def calculate_discount(price, user_tier):
    if user_tier == "gold" and price > 1000:
        return price * 0.85
    elif price == 999.99:  # เงื่อนไขนี้มาจากไหน?
        return price * 0.5
    ...
```

แทนที่จะเดาสุ่มหรือไปรบกวนทั้งทีมใน chat กลาง คุณสามารถรัน:

```bash
git blame -L 4,4 pricing.py
```

เพื่อดูว่าบรรทัดที่ 4 (เงื่อนไข `price == 999.99`) มาจาก commit ไหน แล้วเปิดดู commit message และรายละเอียดของ commit นั้นต่อ ซึ่งมักจะให้คำตอบที่ชัดเจนกว่าการถามคนในทีมเสียอีก เพราะข้อมูลถูกบันทึกไว้ ณ เวลาที่เขียนจริง ไม่ผ่านความจำที่อาจคลาดเคลื่อนของใครก็ตาม

### สิ่งสำคัญที่ต้องเข้าใจก่อนไปต่อ: blame ดูที่ "การแก้ไขล่าสุด" ไม่ใช่ "ผู้เขียนดั้งเดิม"

ข้อควรระวังที่สำคัญมากคือ `git blame` แสดง **commit ล่าสุดที่แตะบรรทัดนั้น** ไม่ใช่คนที่เขียนบรรทัดนั้นเป็นคนแรกในประวัติศาสตร์ของโปรเจกต์เสมอไป

ตัวอย่างเช่น:

- Alice เขียนฟังก์ชันทั้งฟังก์ชันในปี 2022
- Bob มาแก้ไข typo ในคอมเมนต์ของบรรทัดหนึ่งในฟังก์ชันนั้นในปี 2024

ถ้าคุณ blame บรรทัดที่ Bob แก้ไข ผลลัพธ์จะโชว์ชื่อ **Bob** และวันที่ **2024** ไม่ใช่ Alice และปี 2022 — เพราะ Bob คือคนที่แก้ไข "ล่าสุด" ของบรรทัดนั้น แม้ว่า logic ส่วนใหญ่รอบ ๆ บรรทัดนั้นจะยังเป็นของ Alice ก็ตาม

นี่คือเหตุผลที่เราต้องเรียนรู้ตัวเลือกอย่าง `-w` และ `-C` ใน Step ถัดไป ๆ เพื่อ "มองทะลุ" การแก้ไขเล็ก ๆ น้อย ๆ ที่บดบัง commit ที่แท้จริงซึ่งเปลี่ยนแปลง **เนื้อหา (content)** ของบรรทัดนั้นจริง ๆ

## Step 422: อ่านผลลัพธ์ของ `git blame` ให้เป็น

การรู้จักคำสั่งอย่างเดียวไม่พอ ต้องอ่านผลลัพธ์ที่มันแสดงออกมาให้เข้าใจทุกส่วนด้วย มาดูตัวอย่างผลลัพธ์จริงกัน

### ตัวอย่างผลลัพธ์

```
$ git blame README.md

^a1b2c3d (Somchai Devcode 2023-01-10 14:22:31 +0700  1) # โปรเจกต์ตัวอย่าง
a1b2c3d4 (Somchai Devcode 2023-01-10 14:22:31 +0700  2)
f5e6d7c8 (Malee Coder     2023-03-15 09:10:05 +0700  3) โปรเจกต์นี้ใช้สำหรับสาธิตระบบชำระเงิน
9a8b7c6d (Malee Coder     2023-05-02 18:44:12 +0700  4)
b2c3d4e5 (Somchai Devcode 2024-02-20 11:05:44 +0700  5) ## การติดตั้ง
```

### แยกส่วนประกอบของแต่ละบรรทัด

ผลลัพธ์แต่ละบรรทัดของ `git blame` มีโครงสร้างดังนี้:

```
<commit-hash> (<author>  <date>  <time>  <timezone>  <line-number>) <เนื้อหาบรรทัดจริง>
```

| ส่วนประกอบ | ตัวอย่าง | ความหมาย |
|---|---|---|
| **Commit hash (ย่อ)** | `a1b2c3d4` | SHA ของ commit ที่แก้ไขบรรทัดนี้ล่าสุด (ย่อเหลือ ~8 ตัวอักษรโดย default) |
| **Author** | `Malee Coder` | ชื่อผู้เขียน (author) ของ commit นั้น (ตาม `user.name` ที่ตั้งค่าไว้ตอน commit) |
| **Date & Time** | `2023-03-15 09:10:05` | วันเวลาที่ commit ถูกสร้าง (author date ไม่ใช่ commit date — จะอธิบายความต่างด้านล่าง) |
| **Timezone** | `+0700` | โซนเวลาของผู้เขียน ณ ตอนที่ commit |
| **เลขบรรทัด** | `3)` | เลขบรรทัดในไฟล์ปัจจุบัน |
| **เนื้อหา** | `โปรเจกต์นี้ใช้...` | เนื้อหาจริงของบรรทัดนั้น |

### สัญลักษณ์ `^` หน้า commit hash คืออะไร

สังเกตบรรทัดแรกในตัวอย่างที่มี `^a1b2c3d` — เครื่องหมาย `^` นำหน้า hash หมายถึง **commit นี้คือ "boundary commit"** หรือ commit ที่เก่าที่สุดในขอบเขตที่ Git กำลังไล่ดูอยู่ (โดยทั่วไปคือ commit แรกสุดของประวัติทั้งหมด หรือ commit ที่เป็นขอบเขตของช่วงที่เรากำหนดไว้ เช่นตอนใช้ `git blame <rangeA>..<rangeB>`)

พูดง่าย ๆ คือ ถ้าเห็น `^` แปลว่า Git ไล่ตามรอยบรรทัดนี้ย้อนกลับไปได้สุดขอบเขตแล้ว ไม่สามารถหาต้นตอที่เก่ากว่านี้ได้อีก (อาจเป็นเพราะเป็น initial commit จริง ๆ หรือเพราะเรากำหนด boundary ไว้เอง)

### commit hash ซ้ำกันหลายบรรทัดหมายความว่าอย่างไร

สังเกตว่าบรรทัด 1 และ 2 ในตัวอย่างมี hash เดียวกันคือ `a1b2c3d4` (บรรทัดที่ 1 มีสัญลักษณ์ `^` เพิ่ม ซึ่งในทางปฏิบัติมักจะเป็น hash เดียวกันแค่ initial commit) — ความหมายคือ **บรรทัดเหล่านั้นถูกเพิ่มเข้ามาพร้อมกันใน commit เดียวกัน** ซึ่งเป็นเรื่องปกติมาก เพราะการ commit หนึ่งครั้งมักจะเพิ่ม/แก้หลายบรรทัดพร้อมกันเสมอ

Git ยังฉลาดพอที่จะ "ย่อ" การแสดงผลให้อ่านง่ายขึ้นด้วย — ถ้าบรรทัดติดกันมาจาก commit และ author เดียวกัน มันจะแสดงชื่อ author และวันที่ **เฉพาะบรรทัดแรกของกลุ่มเท่านั้น** บรรทัดถัดไปที่ต่อเนื่องกันจะเว้นว่างส่วนนั้นไว้ (ในการแสดงผลบาง mode) เพื่อไม่ให้ตารางรกจนเกินไป

### ตัวเลือกที่ช่วยให้อ่านง่ายขึ้น

#### `--show-email` แสดงอีเมลแทนชื่อ

```bash
git blame --show-email README.md
```

มีประโยชน์เมื่อในทีมมีคนชื่อซ้ำกัน หรือต้องการ identity ที่ชัดเจนกว่าชื่อที่อาจสะกดคล้ายกัน

#### `--date=` กำหนดรูปแบบวันที่

```bash
git blame --date=short README.md      # แสดงแค่ 2023-03-15
git blame --date=relative README.md   # แสดงแบบ "2 years ago"
git blame --date=iso README.md        # แสดงแบบ ISO 8601 เต็มรูปแบบ
```

รูปแบบ `relative` มีประโยชน์มากเวลาต้องการประเมินคร่าว ๆ ว่าโค้ดส่วนนี้ "เก่า" หรือ "ใหม่" แค่ไหนโดยไม่ต้องคำนวณวันที่เอง

#### `--abbrev=<n>` กำหนดความยาวของ hash ที่แสดง

```bash
git blame --abbrev=12 README.md
```

ค่า default ของความยาว hash ที่ย่อจะขึ้นกับขนาด repository (Git จะเลือกความยาวที่สั้นที่สุดแต่ยังไม่ชนกับ hash อื่น) แต่ถ้าต้องการบังคับความยาวที่แน่นอนเพื่อความสม่ำเสมอ ใช้ `--abbrev` ได้

#### `-e` แสดงอีเมล (ย่อของ `--show-email`)

```bash
git blame -e README.md
```

#### `-s` (`--suppress-author`) ซ่อนชื่อ author ออก แสดงแค่ hash วันที่ และเนื้อหา

```bash
git blame -s README.md
```

มีประโยชน์เวลาต้องการโฟกัสที่ commit hash และเนื้อหาเป็นหลัก ไม่สนใจว่าใครเขียน (เช่นตอนใช้ script ประมวลผลผลลัพธ์ต่อ)

### Author date กับ Commit date ต่างกันอย่างไร (ทบทวนสั้น ๆ)

Git แยกวันที่ของ commit ออกเป็น 2 แบบ:

- **Author date** — วันเวลาที่ผู้เขียนสร้างการเปลี่ยนแปลงครั้งแรก (เช่นตอน `git commit` ครั้งแรกก่อน rebase)
- **Committer date** — วันเวลาที่ commit ถูกเขียนลงในประวัติจริง (อาจเปลี่ยนได้เมื่อทำ rebase, cherry-pick)

โดย default `git blame` จะแสดง **author date** เพราะสื่อถึง "เมื่อไหร่ที่เนื้อหานี้ถูกคิดขึ้นมาจริง ๆ" ได้ดีกว่า ถ้าต้องการดู committer date แทน ใช้ตัวเลือก:

```bash
git blame --date=format-local:'%Y-%m-%d' README.md
```

หรือใช้ `git log` ควบคู่ไปเพื่อเทียบทั้งสองค่า (จะพูดถึงใน Step 426)

## Step 423: `git blame -L` จำกัดช่วงบรรทัดที่สนใจ

ไฟล์ในโปรเจกต์จริงบางไฟล์อาจมีความยาวหลายร้อยหรือหลายพันบรรทัด การรัน `git blame` เปล่า ๆ แล้วดูทั้งไฟล์เป็นเรื่องที่ไม่มีประสิทธิภาพเลย ส่วนใหญ่แล้วเราสนใจแค่ **บางบรรทัดที่เจาะจง** ที่กำลังมีปัญหาหรือกำลังสงสัยอยู่

### รูปแบบคำสั่ง

```bash
git blame -L <start>,<end> ชื่อไฟล์
```

ตัวอย่าง:

```bash
git blame -L 45,60 src/payment.py
```

คำสั่งนี้จะแสดงผล blame **เฉพาะบรรทัดที่ 45 ถึง 60** เท่านั้น ไม่แสดงทั้งไฟล์ ช่วยประหยัดเวลาในการอ่านผลลัพธ์มหาศาลเมื่อทำงานกับไฟล์ขนาดใหญ่

### รูปแบบอื่น ๆ ของ `-L` ที่มีประโยชน์

#### ระบุบรรทัดเดียว

```bash
git blame -L 45,45 src/payment.py
```

หรือเขียนแบบสั้นได้ว่า:

```bash
git blame -L 45,+1 src/payment.py
```

#### ระบุจำนวนบรรทัดต่อจากจุดเริ่มต้น (`+N`)

```bash
git blame -L 45,+10 src/payment.py
```

หมายถึง เริ่มจากบรรทัด 45 แสดงต่ออีก 10 บรรทัด (คือบรรทัด 45–55)

#### ระบุจำนวนบรรทัดก่อนจุดสิ้นสุด (`-N`)

```bash
git blame -L 60,-10 src/payment.py
```

หมายถึง สิ้นสุดที่บรรทัด 60 แสดงย้อนขึ้นไป 10 บรรทัด (คือบรรทัด 50–60)

#### ระบุด้วยชื่อฟังก์ชันหรือ regular expression

Git ยังฉลาดพอที่จะรับ **regex** แทนเลขบรรทัดได้ ซึ่งมีประโยชน์มากเวลาไม่รู้เลขบรรทัดที่แน่นอน แต่รู้ว่าฟังก์ชันชื่ออะไร:

```bash
git blame -L '/def calculate_discount/,/^def /' src/pricing.py
```

ความหมายคือ เริ่มจากบรรทัดที่ match กับ `def calculate_discount` ไปจนถึงบรรทัดที่ match กับ `^def ` ถัดไป (คือจุดเริ่มต้นของฟังก์ชันถัดไป) ซึ่งจะครอบคลุมพอดีกับเนื้อหาทั้งหมดของฟังก์ชัน `calculate_discount`

หรือใช้ regex เดียวแบบระบุแค่จุดเริ่มต้น แล้วให้ Git เดาว่าจบที่ขอบเขต (scope) เดียวกัน (ใน Git เวอร์ชันใหม่ ๆ):

```bash
git blame -L '/def calculate_discount/' src/pricing.py
```

#### ใช้ `-L` หลายครั้งในคำสั่งเดียว (ตั้งแต่ Git 2.35 ขึ้นไป)

```bash
git blame -L 10,20 -L 50,60 src/payment.py
```

จะแสดงทั้งสองช่วงพร้อมกันในผลลัพธ์เดียว

### ทำไม `-L` ถึงสำคัญมากในการทำงานจริง

1. **เร็วขึ้นในการอ่าน** — ไฟล์ขนาด 2,000 บรรทัด ไม่มีใครอยากไล่อ่านทั้งหมด
2. **โฟกัสตรงจุด** — เวลามีบั๊กเฉพาะจุด การเห็นแค่บริบทรอบ ๆ บรรทัดที่มีปัญหาช่วยให้เข้าใจง่ายกว่าเห็นทั้งไฟล์
3. **ใช้ร่วมกับ error stack trace ได้ทันที** — เวลาโปรแกรม crash แล้วบอกเลขบรรทัดที่ error เช่น `payment.py:127`, สามารถ copy เลข 127 มาใช้กับ `-L 120,135` ได้ทันทีเพื่อดูบริบทรอบ ๆ จุดที่ error

### ตัวอย่างการใช้งานจริงแบบครบวงจร

สมมติ error log บอกว่า:

```
Traceback (most recent call last):
  File "src/payment.py", line 88, in process_refund
    amount = amount * REFUND_RATE
NameError: name 'REFUND_RATE' is not defined
```

คุณสามารถสืบสวนได้ทันทีว่า:

```bash
git blame -L 80,95 src/payment.py
```

ดูบริบทรอบบรรทัด 88 ว่า `REFUND_RATE` ควรถูก define ไว้ตรงไหน หรือถูกลบออกไปเมื่อไหร่โดยใคร ซึ่งอาจนำไปสู่การใช้ `git log -p` เจาะลึกต่อใน Step 426

## Step 424: `git blame -w` ไม่ให้ whitespace บังหน้า commit จริง

นี่คือหนึ่งในตัวเลือกที่มีประโยชน์ที่สุดแต่คนใหม่ ๆ มักไม่รู้จัก

### ปัญหาที่เกิดขึ้นบ่อยมาก

ลองนึกภาพสถานการณ์นี้:

1. Alice เขียนฟังก์ชันขึ้นมาในปี 2022 ด้วย logic ที่ซับซ้อน
2. ปี 2024 มีคนรัน **code formatter** (เช่น Prettier, Black, gofmt) ทั่วทั้งโปรเจกต์ ซึ่งไปเปลี่ยน indentation จาก tab เป็น space หรือจัดเรียงวงเล็บใหม่ทั้งไฟล์
3. ตอนนี้เมื่อคุณ `git blame` ไฟล์นั้น **ทุกบรรทัดจะโชว์ชื่อคนที่รัน formatter ในปี 2024** ทั้งที่ logic จริง ๆ ยังเป็นของ Alice ในปี 2022 อยู่เหมือนเดิม

นี่คือปัญหาที่เรียกกันว่า **"blame ถูกทำลายด้วย whitespace/formatting change"** ซึ่งทำให้ blame กลายเป็นเครื่องมือที่ไม่มีประโยชน์ทันทีหลังจากมีการ reformat ครั้งใหญ่

### ทางแก้: ตัวเลือก `-w`

```bash
git blame -w src/payment.py
```

ตัวเลือก `-w` (ย่อมาจาก `--ignore-whitespace-changes`... จริง ๆ แล้วชื่อเต็มตาม Git คือ "ignore whitespace") จะบอกให้ Git **มองข้าม commit ที่เปลี่ยนแปลงแค่ whitespace เพียงอย่างเดียว** (เช่น เว้นวรรค, tab, การขึ้นบรรทัดใหม่ ที่ไม่กระทบเนื้อหาจริง) แล้วไล่หา commit ที่แก้ไข **เนื้อหาจริง** ก่อนหน้านั้นแทน

ผลลัพธ์คือ blame จะกลับไปแสดงชื่อ Alice และปี 2022 อีกครั้ง แม้ว่าจะมีการรัน formatter ทับไปแล้วก็ตาม เพราะ Git มองข้าม commit ของ formatter ไปเลย

### หลักการทำงานเบื้องหลัง

`-w` ทำงานโดยเปรียบเทียบเนื้อหาของแต่ละบรรทัดแบบ **normalize whitespace ก่อนเปรียบเทียบ** — ถ้าบรรทัดสองบรรทัดต่างกันแค่ whitespace (เช่น `  x=1` กับ `    x = 1`) Git จะถือว่ามัน "เหมือนเดิม" ในทางเนื้อหา แล้วไล่ตามรอยไปหา commit ที่เปลี่ยนเนื้อหาจริงก่อนหน้านั้นต่อไปเรื่อย ๆ

### ตัวเลือกใกล้เคียงที่ควรรู้จักไว้ด้วย

```bash
git blame --ignore-rev <commit-hash> src/payment.py
```

ตัวเลือกนี้เจาะจงกว่า `-w` มาก คือสามารถบอก Git ว่า **"ให้มองข้าม commit นี้เจาะจงเลย"** ไม่ว่าการเปลี่ยนแปลงใน commit นั้นจะเป็น whitespace หรือไม่ก็ตาม มีประโยชน์เวลารู้แน่ชัดแล้วว่า commit ไหนคือ commit ที่ "ไม่ควรถูกนับ" เช่น commit ที่รัน auto-formatter ทั้งไฟล์ หรือ commit ที่ทำ mass rename ตัวแปร

สามารถระบุได้หลาย commit พร้อมกัน:

```bash
git blame --ignore-rev commit1 --ignore-rev commit2 src/payment.py
```

หรือเก็บรายการ commit ที่ต้องการ ignore ไว้ในไฟล์แล้วอ้างอิงด้วย:

```bash
git blame --ignore-revs-file .git-blame-ignore-revs src/payment.py
```

ซึ่งเทคนิคนี้จะถูกอธิบายอย่างละเอียดใน Step 427

### ตัวอย่างเปรียบเทียบก่อน-หลังใช้ `-w`

**ก่อนใช้ `-w`:**

```
$ git blame src/utils.py

d4e5f6a7 (Bot Formatter  2024-06-01 03:00:00 +0700  10) function calculateTotal(items) {
d4e5f6a7 (Bot Formatter  2024-06-01 03:00:00 +0700  11)   return items.reduce((sum, i) => sum + i.price, 0);
d4e5f6a7 (Bot Formatter  2024-06-01 03:00:00 +0700  12) }
```

**หลังใช้ `-w`:**

```
$ git blame -w src/utils.py

a1b2c3d4 (Somchai Devcode 2022-08-14 10:15:00 +0700  10) function calculateTotal(items) {
a1b2c3d4 (Somchai Devcode 2022-08-14 10:15:00 +0700  11)   return items.reduce((sum, i) => sum + i.price, 0);
a1b2c3d4 (Somchai Devcode 2022-08-14 10:15:00 +0700  12) }
```

เห็นได้ชัดว่า `-w` ช่วยให้เราเห็น "ผู้เขียนตัวจริง" ของ logic แทนที่จะเห็นแค่ bot ที่รัน formatter

### แนวปฏิบัติที่แนะนำ

ทีมที่มีการรัน formatter เป็นประจำ (เช่นตั้ง pre-commit hook ให้รัน Prettier อัตโนมัติ) **ควรใช้ `git blame -w` เป็นค่าเริ่มต้นเสมอ** ไม่ใช่ blame เปล่า ๆ เพราะผลลัพธ์แบบไม่ใช้ `-w` แทบไม่มีประโยชน์เลยในทีมแบบนี้ บางทีมถึงขั้นตั้ง git alias ให้ `git blame` เรียก `-w` โดยอัตโนมัติ:

```bash
git config --global alias.bl "blame -w"
```

จากนั้นใช้แค่ `git bl <ไฟล์>` ก็จะได้ผลลัพธ์ที่มองข้าม whitespace โดยอัตโนมัติทุกครั้ง

## Step 425: `git blame -C` ตามรอยโค้ดที่ถูก copy/move ข้ามไฟล์

ปัญหาถัดไปที่พบบ่อยไม่แพ้กันคือ **การย้ายโค้ด (move)** หรือ **การคัดลอกโค้ด (copy)** จากไฟล์หนึ่งไปอีกไฟล์หนึ่ง หรือแม้แต่ย้ายภายในไฟล์เดียวกัน

### ปัญหา

สมมติ:

1. Alice เขียนฟังก์ชัน `validateEmail()` ไว้ในไฟล์ `utils.js` ตั้งแต่ปี 2021
2. ปี 2023 Bob refactor โปรเจกต์ใหม่ ย้ายฟังก์ชันนี้ไปอยู่ในไฟล์ `validators.js` แทน (คือ cut จากไฟล์เก่า ไป paste ในไฟล์ใหม่)

ถ้าคุณ `git blame validators.js` แบบธรรมดา ผลลัพธ์จะโชว์ว่า **Bob เป็นคนเขียนฟังก์ชันนี้ในปี 2023** ทั้งที่จริง ๆ แล้ว logic ทั้งหมดเป็นฝีมือของ Alice ตั้งแต่ปี 2021 — Bob แค่ย้ายมันไปเก็บที่ใหม่เท่านั้นเอง

### ทางแก้: ตัวเลือก `-C`

```bash
git blame -C src/validators.js
```

`-C` (`--find-copies`) จะบอกให้ Git **ค้นหาว่าบรรทัดที่กำลังดูอยู่นี้ ก่อนหน้านี้เคยมีอยู่ในไฟล์อื่นในโปรเจกต์หรือไม่** ถ้าเจอว่าเนื้อหาเหมือนกัน (หรือคล้ายกันมากพอ) Git จะไล่ตามรอยข้ามไฟล์ไปหา commit ดั้งเดิมที่เขียนเนื้อหานั้นจริง ๆ

### ระดับความเข้มข้นของ `-C`

`-C` สามารถใส่ซ้ำได้หลายครั้งเพื่อขยายขอบเขตการค้นหา:

| คำสั่ง | ความหมาย |
|---|---|
| `git blame -C` | ค้นหา copy จากไฟล์อื่นที่ถูกแก้ไขใน **commit เดียวกัน** เท่านั้น |
| `git blame -C -C` | ขยายขอบเขตค้นหาไปยังไฟล์อื่นทั้งหมดใน commit นั้น (ไม่ใช่แค่ไฟล์ที่ถูกแก้ไข) |
| `git blame -C -C -C` | ขยายขอบเขตไปค้นหาใน **commit ก่อนหน้า** ของไฟล์นั้นด้วย (กว้างที่สุด ช้าที่สุด) |

พูดง่าย ๆ คือยิ่งใส่ `-C` มากครั้ง Git ยิ่งค้นหากว้างขึ้น แต่ก็จะ**ช้าลงตามไปด้วย** เพราะต้องเปรียบเทียบเนื้อหากับไฟล์จำนวนมากขึ้นเรื่อย ๆ

### กำหนดเกณฑ์ความคล้าย (similarity threshold)

`-C` ยังรับค่าตัวเลขเปอร์เซ็นต์ต่อท้ายได้ เพื่อกำหนดว่า "คล้ายกันแค่ไหนถึงจะนับว่าเป็นการ copy":

```bash
git blame -C50% src/validators.js
```

ค่า default คือ 40% (บรรทัดต้องเหมือนกันอย่างน้อย 40% ของเนื้อหาในไฟล์ต้นทาง) การลดเปอร์เซ็นต์ลงจะทำให้ Git หาการ copy ได้ไวขึ้นแต่เสี่ยง false positive (จับคู่ผิด) มากขึ้น

### `-M` สำหรับการตรวจจับการย้ายภายในไฟล์เดียวกัน

มีอีกตัวเลือกที่คล้ายกันคือ `-M` (`--find-renames` หรือในบริบทของ blame คือ `--find-movements`... จริง ๆ แล้ว `git blame` ใช้ `-M` เพื่อตรวจจับ **การย้ายบรรทัดภายในไฟล์เดียวกัน** เช่น ย้ายฟังก์ชันขึ้นไปอยู่ตอนบนของไฟล์เดิม):

```bash
git blame -M src/validators.js
```

และสามารถใช้ร่วมกับ `-C` ได้พร้อมกันเพื่อความครอบคลุมสูงสุด:

```bash
git blame -M -C -C src/validators.js
```

### ตัวอย่างเปรียบเทียบก่อน-หลังใช้ `-C`

**ก่อนใช้ `-C`:**

```
$ git blame src/validators.js

f9e8d7c6 (Bob Refactor    2023-11-02 16:30:00 +0700  1) function validateEmail(email) {
f9e8d7c6 (Bob Refactor    2023-11-02 16:30:00 +0700  2)   return /^[^\s@]+@[^\s@]+\.[^\s@]+$/.test(email);
f9e8d7c6 (Bob Refactor    2023-11-02 16:30:00 +0700  3) }
```

**หลังใช้ `-C`:**

```
$ git blame -C src/validators.js

3c4d5e6f (Alice Coder     2021-04-18 09:00:00 +0700  1) function validateEmail(email) {
3c4d5e6f (Alice Coder     2021-04-18 09:00:00 +0700  2)   return /^[^\s@]+@[^\s@]+\.[^\s@]+$/.test(email);
3c4d5e6f (Alice Coder     2021-04-18 09:00:00 +0700  3) }
```

### ข้อควรระวังเรื่องความเร็ว

`-C` โดยเฉพาะระดับ `-C -C -C` เป็นการค้นหาที่ **หนักมาก** สำหรับ repository ขนาดใหญ่ เพราะต้องเปรียบเทียบเนื้อหากับไฟล์จำนวนมากย้อนกลับไปในประวัติศาสตร์ทั้งหมด ในทางปฏิบัติ แนะนำให้:

1. เริ่มจาก `-C` เฉย ๆ ก่อน (ระดับเบาสุด) แล้วค่อยเพิ่มความเข้มข้นถ้ายังไม่พบสิ่งที่ต้องการ
2. ใช้ `-L` ควบคู่ไปด้วยเสมอเพื่อจำกัดขอบเขตบรรทัด ลดภาระการประมวลผล
3. หลีกเลี่ยงการรันบนทั้ง repository ขนาดใหญ่แบบไม่จำกัดขอบเขต

## Step 426: ใช้ blame คู่กับ `git log -p <commit>` เพื่อดูบริบทเต็ม

`git blame` บอกเราแค่ **"บรรทัดนี้มาจาก commit ไหน"** แต่มันไม่ได้แสดงบริบทแวดล้อมทั้งหมดของการเปลี่ยนแปลงนั้น ถ้าอยากรู้ว่า **commit นั้นทำอะไรไปทั้งหมด** (ไม่ใช่แค่บรรทัดเดียวที่เรากำลังดูอยู่) ต้องใช้ `git log -p` หรือ `git show` ควบคู่ไปด้วยเสมอ

### ขั้นตอนการสืบสวนแบบครบวงจร

ขั้นตอนที่แนะนำเมื่อสืบสวนโค้ดอย่างจริงจังมีดังนี้:

**ขั้นที่ 1: หา commit hash ด้วย blame**

```bash
git blame -w -C -L 45,60 src/payment.py
```

สมมติได้ผลลัพธ์ว่าบรรทัดที่สงสัยมาจาก commit `7f3a9c2e`

**ขั้นที่ 2: ดูรายละเอียดเต็มของ commit นั้นด้วย `git show`**

```bash
git show 7f3a9c2e
```

คำสั่งนี้จะแสดง:
- Commit message เต็ม (ซึ่งมักจะอธิบายว่า **ทำไม** ถึงแก้ไขแบบนั้น)
- Diff เต็มของทุกไฟล์ที่ถูกแก้ไขใน commit นั้น ไม่ใช่แค่บรรทัดเดียวที่เราสนใจ
- ชื่อ author, committer, วันที่ครบถ้วน

**ขั้นที่ 3: ถ้าต้องการดูบริบทที่กว้างกว่าคือ "ประวัติทั้งหมดของไฟล์นั้นรอบ ๆ commit นั้น"**

```bash
git log -p --follow -- src/payment.py
```

ตัวเลือก `--follow` สำคัญมาก เพราะมันบอกให้ Git **ติดตามไฟล์แม้ว่ามันจะเคยถูก rename มาก่อน** — ถ้าไฟล์ `payment.py` เคยชื่อ `checkout.py` มาก่อนใน commit เก่า ๆ `--follow` จะยังแสดงประวัติของมันต่อเนื่องไปจนถึงตอนที่ยังใช้ชื่อเดิมอยู่ (ในขณะที่ `git blame` เองก็ตามรอย rename ได้อัตโนมัติโดย default อยู่แล้วเช่นกัน)

**ขั้นที่ 4: ถ้าอยากดูเฉพาะการเปลี่ยนแปลงของไฟล์นั้นใน commit นั้นเจาะจง (ไม่เอาไฟล์อื่นที่ commit เดียวกันแตะด้วย)**

```bash
git show 7f3a9c2e -- src/payment.py
```

### เทคนิค: ใช้ `git log -S` หรือ `git log -G` ควบคู่ไปด้วย

บางครั้งเราไม่ได้อยากรู้แค่ "ใครแก้บรรทัดนี้ล่าสุด" แต่อยากรู้ "**commit ไหนที่เพิ่มหรือลบข้อความ `REFUND_RATE` เข้า/ออกจากโปรเจกต์**" ซึ่งอาจไม่ตรงกับบรรทัดที่ blame ชี้ไปพอดี (เช่น ถ้าตัวแปรนั้นถูกลบไปแล้วในปัจจุบัน blame จะไม่มีบรรทัดให้ดูเลย)

ในกรณีนี้ใช้ **pickaxe search** ของ `git log`:

```bash
git log -S "REFUND_RATE" --oneline -- src/payment.py
```

`-S` จะค้นหา commit ที่ **จำนวนครั้งที่ข้อความ `REFUND_RATE` ปรากฏในไฟล์เปลี่ยนแปลง** (คือถูกเพิ่มเข้ามาหรือถูกลบออกไป) ซึ่งช่วยหาได้ทั้งตอนที่โค้ดถูกเพิ่มและตอนที่โค้ดถูกลบ — มีประโยชน์มากเวลาสืบหาว่า "ใครลบโค้ดที่ควรจะยังอยู่ออกไป"

ส่วน `-G` จะค้นหาแบบ regular expression ที่กว้างกว่า โดยดูว่า diff (ผลต่าง) มีข้อความที่ match กับ pattern หรือไม่ ต่างจาก `-S` ตรงที่ `-G` จะจับได้แม้จำนวนครั้งที่ปรากฏจะเท่าเดิมแต่ตำแหน่งเปลี่ยน:

```bash
git log -G "REFUND_RATE\s*=" --oneline -- src/payment.py
```

### ตัวอย่างการสืบสวนแบบเต็มรูปแบบ

```bash
# ขั้นที่ 1: หาว่าบรรทัดที่ error มาจาก commit ไหน
git blame -w -L 88,88 src/payment.py
# ผลลัพธ์: 7f3a9c2e (Somchai 2024-01-05 ...) amount = amount * REFUND_RATE

# ขั้นที่ 2: ดูรายละเอียดเต็มของ commit นั้น
git show 7f3a9c2e

# ขั้นที่ 3: ถ้า commit message ไม่ชัดเจน ลองดูว่า REFUND_RATE ถูกกำหนดไว้ที่ไหน
git log -S "REFUND_RATE" --oneline --all

# ขั้นที่ 4: ดูว่า commit ที่ประกาศตัวแปรนี้ครั้งแรกเขียนว่าอะไร
git show <commit-hash-ที่เจอ>
```

การผสมผสานคำสั่งเหล่านี้เข้าด้วยกันคือหัวใจของสิ่งที่เรียกว่า **"code archaeology"** หรือการขุดค้นประวัติศาสตร์ของโค้ด ซึ่งเป็นทักษะที่มีค่ามากสำหรับนักพัฒนาที่ทำงานกับ codebase ขนาดใหญ่และเก่าแก่

## Step 427: `.git-blame-ignore-revs` — ซ่อน commit ที่เป็นแค่ reformat

ใน Step 424 เราเรียนรู้ตัวเลือก `--ignore-rev` และ `-w` เพื่อแก้ปัญหา blame ที่ถูกบดบังด้วยการจัดฟอร์แมต แต่ปัญหาคือ **ต้องพิมพ์ flag เหล่านี้ทุกครั้ง** ซึ่งไม่สะดวกและคนอื่นในทีมอาจลืมใช้

Git จึงมีกลไกที่ดีกว่า คือไฟล์พิเศษชื่อ **`.git-blame-ignore-revs`** ที่เก็บรายการ commit ที่ **ควรถูกมองข้ามโดย blame เป็นค่าเริ่มต้นสำหรับทุกคนในทีม**

### วิธีสร้างไฟล์

สร้างไฟล์ชื่อ `.git-blame-ignore-revs` ไว้ที่ root ของ repository:

```
# .git-blame-ignore-revs
#
# Commit นี้คือการรัน Prettier ทั่วทั้งโปรเจกต์ ไม่ได้เปลี่ยน logic ใด ๆ
7c9f3e1d2a8b4c5d6e7f8091a2b3c4d5e6f7a8b9

# Commit นี้คือการแปลง indentation จาก tab เป็น space ทั้งโปรเจกต์
a1b2c3d4e5f6a7b8c9d0e1f2a3b4c5d6e7f8a9b0

# Commit นี้คือการ sort import statements อัตโนมัติด้วย isort
b2c3d4e5f6a7b8c9d0e1f2a3b4c5d6e7f8a9b0c1
```

ไฟล์นี้เป็นแค่ text file ธรรมดา:
- บรรทัดที่ขึ้นต้นด้วย `#` คือคอมเมนต์ (ใส่เหตุผลกำกับไว้ให้คนอื่นเข้าใจว่าทำไมถึง ignore commit นี้)
- บรรทัดที่เหลือคือ **full commit hash** (แนะนำให้ใช้ hash เต็ม 40 ตัวอักษร ไม่ใช่แบบย่อ เพื่อความแน่นอนไม่ให้ชนกับ hash อื่นในอนาคต)

### วิธีใช้งานไฟล์นี้แบบ manual (ต่อคำสั่ง)

```bash
git blame --ignore-revs-file .git-blame-ignore-revs src/payment.py
```

### วิธีตั้งค่าให้ Git ใช้ไฟล์นี้โดยอัตโนมัติเสมอ (แนะนำที่สุด)

ตั้งค่า config ของ repository ให้ชี้ไปที่ไฟล์นี้ครั้งเดียว:

```bash
git config blame.ignoreRevsFile .git-blame-ignore-revs
```

หลังจากตั้งค่านี้แล้ว **ทุกครั้งที่รัน `git blame` เฉย ๆ (ไม่ต้องใส่ flag เพิ่ม)** Git จะมองข้าม commit ที่อยู่ในไฟล์นี้โดยอัตโนมัติทันที

### ข้อควรรู้: config นี้เป็น local ต่อเครื่อง ไม่ได้ผูกกับ repo อัตโนมัติ

สิ่งสำคัญที่ต้องเข้าใจคือ คำสั่ง `git config blame.ignoreRevsFile ...` ที่รันไปนั้น **บันทึกลงใน `.git/config` ของเครื่องนั้น ๆ เท่านั้น** ไม่ได้ถูก commit เข้าไปใน repository เพื่อให้ทุกคนในทีมได้ค่านี้อัตโนมัติ

ดังนั้นแนวปฏิบัติที่ถูกต้องคือ:

1. **Commit ไฟล์ `.git-blame-ignore-revs` เข้า repository** (เป็นไฟล์ปกติ ให้ทุกคนเห็นและแก้ไขร่วมกันได้)
2. **แต่ละคนในทีมต้องรัน `git config blame.ignoreRevsFile .git-blame-ignore-revs` เองครั้งหนึ่งบนเครื่องของตัวเอง** (หรือใส่ไว้ใน script ตอน setup โปรเจกต์ใหม่ เช่น `setup.sh` หรือคำแนะนำใน README)
3. **GitHub เองก็รองรับไฟล์นี้โดยอัตโนมัติ** — ถ้า repository มีไฟล์ `.git-blame-ignore-revs` อยู่ที่ root, หน้า Blame บน GitHub UI จะมองข้าม commit เหล่านั้นให้อัตโนมัติโดยไม่ต้องตั้งค่าอะไรเพิ่มเลย (จะพูดถึงใน Step 428)

### เมื่อไหร่ควรเพิ่ม commit เข้าไปในไฟล์นี้

ควรเพิ่มเฉพาะ commit ที่เป็นไปตามเงื่อนไขนี้:

- **ไม่เปลี่ยนแปลง logic หรือพฤติกรรมของโปรแกรมเลย** เปลี่ยนแค่รูปแบบการเขียน (formatting)
- ตัวอย่างทั่วไป: การรัน Prettier/Black/gofmt/rustfmt ครั้งใหญ่ทั้งโปรเจกต์, การแปลง tabs เป็น spaces, การ sort imports อัตโนมัติ, การเปลี่ยน quote style (single เป็น double quote), การจัดเรียง property ใน object ใหม่ตามกฎ linter

**ไม่ควรเพิ่ม** commit ที่มีการเปลี่ยนแปลง logic ปนอยู่ด้วย แม้จะเล็กน้อยก็ตาม เพราะจะทำให้สูญเสียการติดตามการเปลี่ยนแปลงจริงนั้นไป

### เวิร์กโฟลว์ที่แนะนำเมื่อทำ mass reformat

เมื่อทีมตัดสินใจจะรัน formatter ทั่วทั้งโปรเจกต์ (สถานการณ์ที่เกิดขึ้นบ่อยเมื่อเริ่มใช้ linter ใหม่ หรือเปลี่ยน code style guide) แนะนำขั้นตอนนี้:

```bash
# 1. รัน formatter ให้ครอบคลุมทั้งโปรเจกต์ในคราวเดียว แยกจาก commit อื่นโดยเด็ดขาด
npx prettier --write .

# 2. Commit การเปลี่ยนแปลงนี้แยกเดี่ยว ๆ ด้วย message ที่ชัดเจน
git add -A
git commit -m "chore: reformat entire codebase with Prettier (no logic changes)"

# 3. คัดลอก hash ของ commit ที่เพิ่งสร้าง
git rev-parse HEAD

# 4. เพิ่ม hash นั้นเข้าไปใน .git-blame-ignore-revs
echo "$(git rev-parse HEAD)  # reformat ทั้งโปรเจกต์ด้วย Prettier" >> .git-blame-ignore-revs

# 5. Commit ไฟล์ .git-blame-ignore-revs ที่อัปเดตแล้ว
git add .git-blame-ignore-revs
git commit -m "chore: add reformat commit to blame ignore list"
```

ขั้นตอนนี้สำคัญมาก เพราะถ้าไม่แยก commit การ reformat ออกจาก logic change แล้วค่อยเพิ่มเข้าไฟล์ ignore, blame ของทั้งโปรเจกต์จะพังทันทีหลัง reformat และไม่มีทางแก้ไขย้อนหลังได้ง่ายอีกต่อไป

## Step 428: Blame ใน GitHub UI

ไม่ใช่ทุกครั้งที่เราจะเปิด terminal เพื่อรัน `git blame` โดยเฉพาะเวลากำลังอ่านโค้ดเล่น ๆ บนเว็บ GitHub หรือกำลังรีวิว Pull Request อยู่ GitHub จึงมีปุ่ม **Blame** ให้ใช้งานผ่านหน้าเว็บโดยตรง

### วิธีเข้าถึงปุ่ม Blame

1. เปิดไฟล์ใดก็ได้ใน repository บน GitHub (เช่น `https://github.com/<org>/<repo>/blob/main/src/payment.py`)
2. มองหาปุ่ม **"Blame"** อยู่บริเวณแถบเครื่องมือด้านบนของหน้าไฟล์ (อยู่ข้าง ๆ ปุ่ม "Raw", "Copy raw contents", ไอคอนดินสอสำหรับ Edit)
3. คลิกปุ่ม Blame

### สิ่งที่จะเห็นหลังคลิก Blame

หน้าจอจะเปลี่ยนเป็นมุมมองที่แต่ละบรรทัดมีข้อมูลกำกับทางซ้ายมือ คล้ายกับผลลัพธ์ของ `git blame` ใน terminal แต่จัดรูปแบบให้อ่านง่ายขึ้นมาก:

- **รูปโปรไฟล์และชื่อผู้เขียน** ของ commit ที่แก้ไขบรรทัดนั้นล่าสุด
- **ข้อความ commit** (แสดงบางส่วน คลิกดูเต็มได้)
- **วันเวลาแบบ relative** เช่น "2 years ago" (เอาเมาส์ไปชี้จะเห็นวันที่เต็ม)
- คลิกที่ commit message หรือ hash จะพาไปหน้า **commit detail** เต็มรูปแบบทันที เห็น diff ทั้งหมดของ commit นั้น

### ฟีเจอร์ "View blame prior to this change" (ตามรอยย้อนหลัง)

จุดที่มีประโยชน์มากของ Blame บน GitHub คือ เมื่อคุณเปิดดู commit ใด ๆ ในหน้า blame แล้วพบว่า commit นั้นเป็นแค่การ reformat หรือการแก้เล็กน้อยที่ไม่ได้ให้บริบทที่ต้องการ คุณสามารถกดปุ่ม **"View blame prior to this change"** (มักจะอยู่ในหน้ารายละเอียด commit หรือปุ่มลูกศรถัดจากบรรทัดในหน้า blame) เพื่อ **ย้อนกลับไปดู blame ของบรรทัดนั้น ณ ก่อนหน้า commit นี้** — เป็นการไล่ตามรอยย้อนหลังทีละชั้นแบบไม่ต้อง copy hash ไปรันคำสั่งเองใน terminal เลย

พูดง่าย ๆ คือฟีเจอร์นี้เทียบเท่ากับการรัน `git blame <commit>^ -- <file>` (บอกให้ blame มองแค่ประวัติ**ก่อนหน้า** commit ที่ระบุ) ซ้ำไปเรื่อย ๆ จนกว่าจะเจอ commit ที่ให้บริบทที่ต้องการจริง ๆ

### GitHub เคารพไฟล์ `.git-blame-ignore-revs` โดยอัตโนมัติ

อย่างที่กล่าวไว้ใน Step 427 ถ้า repository มีไฟล์ `.git-blame-ignore-revs` วางไว้ที่ root, GitHub จะ **มองข้าม commit ที่อยู่ในไฟล์นั้นโดยอัตโนมัติในหน้า Blame ของเว็บ** โดยไม่ต้องตั้งค่าอะไรเพิ่มเติมในฝั่ง GitHub เลย ทำให้ทั้งคนที่ใช้ terminal และคนที่ดูผ่านเว็บได้ประสบการณ์ blame ที่สอดคล้องกัน

### Blame บน Pull Request (มุมมองต่างจาก blame บนไฟล์ปกติ)

เวลารีวิว Pull Request บน GitHub ตัว diff viewer เองก็มีลักษณะคล้าย blame บางส่วนอยู่แล้วในตัว เพราะมันแสดงว่าบรรทัดไหนถูกเพิ่ม (สีเขียว) บรรทัดไหนถูกลบ (สีแดง) แต่ **นี่ไม่ใช่ blame แบบเต็มรูปแบบ** เพราะมันโชว์แค่การเปลี่ยนแปลงใน PR นั้นเท่านั้น ไม่ได้บอกประวัติทั้งหมดของไฟล์

ถ้าต้องการดู blame แบบเต็มของไฟล์ในสาขาที่กำลังรีวิวอยู่ ต้องออกจากหน้า diff ของ PR แล้วไปเปิดไฟล์นั้นในสาขาต้นทาง (source branch) ของ PR โดยตรง แล้วกด Blame ตามปกติ

### GitLab ก็มีฟีเจอร์เดียวกัน

แม้บทเรียนนี้เน้น GitHub เป็นหลัก แต่ควรรู้ไว้ว่า **GitLab ก็มีปุ่ม "Blame"** อยู่ในตำแหน่งใกล้เคียงกันบนหน้าไฟล์เช่นกัน (เราจะเรียนรายละเอียดของ GitLab แบบเจาะลึกใน Part ของเฟส 5) หลักการทำงานเบื้องหลังเหมือนกันทุกประการเพราะทั้งสองแพลตฟอร์มเรียกใช้ `git blame` engine ของ Git เองอยู่ดี เพียงแค่ห่อ UI ที่ต่างกัน

## Step 429: ข้อควรระวังในการใช้ blame (เครื่องมือเข้าใจบริบท ไม่ใช่เครื่องมือจับผิด)

Step นี้สำคัญไม่แพ้ Step ทางเทคนิคก่อนหน้าเลย เพราะการใช้ `git blame` ผิดวิธีในเชิง**วัฒนธรรมการทำงานเป็นทีม** สามารถสร้างความเสียหายที่ร้ายแรงต่อความสัมพันธ์ในทีมได้

### ปัญหาที่มาจากชื่อคำสั่งเอง

ชื่อ "blame" แปลว่า "ตำหนิ" หรือ "โทษ" ซึ่งเป็นชื่อที่สื่อความหมายผิดเพี้ยนไปจากเจตนารมณ์ที่แท้จริงของเครื่องมือนี้ตั้งแต่ต้น หลายคนเมื่อเห็นชื่อ blame ครั้งแรกจะคิดว่ามันมีไว้ **"หาคนผิด"** เมื่อเกิดบั๊ก แต่ในความเป็นจริงมันเป็นแค่เครื่องมือแสดง **metadata ของประวัติโค้ด** เท่านั้นเอง

ด้วยเหตุนี้เอง เครื่องมือ GUI หลายตัวจึงเลือกใช้ชื่ออื่นแทน เพื่อลดความรู้สึกด้านลบ เช่น:

- IntelliJ / VS Code บาง extension เรียกฟีเจอร์นี้ว่า **"Annotate"**
- Some git tooling เก่าใช้คำสั่ง `git annotate` ที่ทำงานคล้ายกันมาก (ต่างกันแค่รูปแบบผลลัพธ์เล็กน้อย)
- GitLens (extension ยอดนิยมบน VS Code) เรียกมันว่า **"Git Blame"** เหมือนกันแต่แสดงผลในรูปแบบ inline annotation ที่นุ่มนวลกว่า ไม่เน้นคำว่า "blame" มากนัก

### ข้อควรระวังที่ 1: อย่าใช้ blame เพื่อเปิดประเด็นตำหนิเพื่อนร่วมทีม

ตัวอย่างการใช้ blame **ในทางที่ผิด**:

> "เฮ้ blame บอกว่านายเป็นคนเขียนบั๊กนี้เมื่อ 3 เดือนก่อนนะ อธิบายหน่อยว่าทำไมถึงเขียนแบบนี้"

การพูดแบบนี้สร้างบรรยากาศการทำงานที่ไม่ดี เพราะ:

1. **โค้ดที่ผ่าน code review แล้วไม่ใช่ความรับผิดชอบของคนเขียนคนเดียวอีกต่อไป** — ถ้าโค้ดนั้นผ่านการอนุมัติจาก reviewer คนอื่นด้วย ความรับผิดชอบเป็นของทีมร่วมกัน
2. **บริบทตอนเขียนโค้ดอาจต่างจากตอนนี้มาก** — ตอนที่เขียน อาจจะยังไม่มี edge case ที่พบในภายหลัง, requirements อาจเปลี่ยนไปแล้ว, library ที่ใช้อาจมี behavior เปลี่ยนไปในเวอร์ชันใหม่
3. **การชี้นิ้วโทษกันทำลาย psychological safety ของทีม** — ทีมที่กลัวถูกตำหนิจะไม่กล้าทดลองอะไรใหม่ ๆ จะเขียนโค้ดแบบ defensive มากเกินไป หรือแย่ที่สุดคือปิดบังปัญหาแทนที่จะรายงาน

### วิธีใช้ blame ที่ถูกต้องในเชิงวัฒนธรรมทีม

**ใช้เพื่อ "เข้าใจ" ไม่ใช่เพื่อ "ตัดสิน":**

> "ผมเจอ logic แปลก ๆ ตรงนี้ ลอง blame ดูแล้วเจอ commit ของพี่สมชายเมื่อปีที่แล้ว commit message บอกว่าแก้ปัญหา timeout ของ payment gateway ตัวเก่า ผมสงสัยว่าตอนนี้ปัญหานั้นยังมีอยู่ไหม ถ้าไม่มีแล้วอาจจะลบโค้ดนี้ออกได้"

สังเกตความต่าง: การใช้แบบนี้เน้นไปที่ **"ทำความเข้าใจบริบทเพื่อตัดสินใจต่อ"** ไม่ใช่ "หาคนรับผิดชอบ"

**ใช้เพื่อหาคนที่เหมาะจะปรึกษา ไม่ใช่หาคนที่ต้องขอโทษ:**

> "ไฟล์นี้ดูซับซ้อน ลอง blame ดูเห็นว่าพี่มาลีเป็นคนเขียนหลักและแก้ไขบ่อยที่สุด ผมจะไปถามพี่มาลีเรื่อง edge case นี้ดีกว่า"

**ใช้เพื่อเรียนรู้ประวัติศาสตร์การตัดสินใจของโปรเจกต์:**

> commit message ที่ดีมักอธิบายว่า "ทำไม" ถึงตัดสินใจแบบนั้น การอ่าน commit message ผ่าน blame ช่วยให้เข้าใจ "ทำไม" ของโค้ดที่ดูแปลกได้ โดยไม่ต้องรบกวนใครเลย

### ข้อควรระวังที่ 2: blame ไม่ได้บอกว่า "ใครสมควรรับผิดชอบบั๊กจริง ๆ"

อย่างที่อธิบายไว้ใน Step 421 blame แสดงคนที่แก้ไข **บรรทัดนั้นล่าสุด** ซึ่งอาจไม่ใช่คนที่เขียน logic ผิดจริง ๆ เลยด้วยซ้ำ ตัวอย่างเช่น:

- Bob แก้ typo ในคอมเมนต์ของฟังก์ชันที่ Alice เขียน logic ผิดไว้ตั้งแต่แรก → blame จะโชว์ Bob ทั้งที่ Alice คือคนที่ควรถูกถามถึง logic
- โค้ดถูกย้ายไฟล์โดยไม่ใช้ `-C` → blame โชว์คนที่ย้าย ไม่ใช่คนที่เขียนต้นฉบับ

การไม่เข้าใจข้อจำกัดนี้แล้วรีบสรุปว่า "คนนี้ต้องรับผิดชอบ" จากผลลัพธ์ blame เพียงอย่างเดียว **เป็นความผิดพลาดทั้งทางเทคนิคและทางจริยธรรมในการทำงานร่วมกัน**

### ข้อควรระวังที่ 3: อย่าตัดสินคุณภาพนักพัฒนาจากปริมาณบรรทัดที่ blame แสดงชื่อ

บางทีมเคยเข้าใจผิดถึงขั้นเอา blame ไปนับว่าใคร "เขียนโค้ดเยอะที่สุด" แล้วเอาไปประเมินผลงาน (performance review) ซึ่งเป็นการนำเครื่องมือไปใช้ผิดวัตถุประสงค์อย่างรุนแรง เพราะ:

- คนที่ทำ refactor ใหญ่ ๆ (เช่นเปลี่ยนชื่อตัวแปรทั้งโปรเจกต์) อาจมีชื่อโผล่ในบรรทัดจำนวนมาก ทั้งที่ไม่ได้เพิ่มคุณค่าทาง logic เลย
- คนที่เขียนโค้ดสั้น กระชับ อาจดูเหมือน "ทำน้อย" แต่จริง ๆ แล้วมีคุณภาพสูงกว่าโค้ดยาวที่ซับซ้อนโดยไม่จำเป็น
- Metric แบบนี้ส่งเสริมพฤติกรรมที่ผิด เช่น จงใจเขียนโค้ดยาวเกินจำเป็นเพื่อ "โชว์ผลงาน"

### สรุปหลักคิดที่ควรยึดถือ

> **Git blame เป็นเครื่องมือสำหรับ "เข้าใจบริบทของอดีต" เพื่อ "ตัดสินใจในปัจจุบันได้ดีขึ้น" — ไม่ใช่เครื่องมือสำหรับหาคนมารับผิดในเหตุการณ์ที่เกิดขึ้นไปแล้ว**

ทีมที่มีวัฒนธรรมทางวิศวกรรมที่ดี (healthy engineering culture) จะมองบั๊กเป็นปัญหาของ**ระบบและกระบวนการ** (เช่น ทำไม test ไม่จับบั๊กนี้ได้ก่อน ทำไม code review ไม่เจอปัญหานี้) มากกว่ามองเป็นความผิดของ**บุคคล** และ blame ก็เป็นเครื่องมือหนึ่งที่ช่วยให้การสืบสวนเชิงระบบนั้นทำได้ง่ายและรวดเร็วขึ้น ไม่ใช่เครื่องมือสำหรับหาแพะรับบาป

## Step 430: แบบฝึกหัด — สืบสวนที่มาของโค้ดที่มีปัญหาในโปรเจกต์จำลอง

ถึงเวลาลงมือปฏิบัติจริง ในแบบฝึกหัดนี้เราจะสร้างโปรเจกต์จำลองที่มีประวัติการ commit จากหลายคน (จำลองด้วยการเปลี่ยน `user.name`/`user.email` ในแต่ละ commit) แล้วฝึกใช้ทุกเทคนิคที่เรียนมาใน Part นี้เพื่อสืบหาที่มาของโค้ดที่มีปัญหา

### เตรียมโปรเจกต์จำลอง

```bash
mkdir ~/git-course/part-43-blame
cd ~/git-course/part-43-blame
git init
```

### สร้าง commit ที่ 1: Alice เขียนฟังก์ชันตั้งต้น

```bash
git config user.name "Alice Coder"
git config user.email "alice@example.com"

cat > pricing.py << 'EOF'
def calculate_price(base_price, quantity):
    total = base_price * quantity
    return total


def apply_discount(total, discount_rate):
    return total * (1 - discount_rate)
EOF

git add pricing.py
git commit -m "feat: เพิ่มฟังก์ชันคำนวณราคาและส่วนลดพื้นฐาน"
```

### สร้าง commit ที่ 2: Bob เพิ่ม edge case ที่ดูประหลาด

```bash
git config user.name "Bob Fixer"
git config user.email "bob@example.com"

cat > pricing.py << 'EOF'
def calculate_price(base_price, quantity):
    total = base_price * quantity
    return total


def apply_discount(total, discount_rate):
    if total == 999.99:
        return total * 0.5
    return total * (1 - discount_rate)
EOF

git add pricing.py
git commit -m "fix: แก้ปัญหาลูกค้า VIP เบอร์ 12345 ที่ยอดพอดี 999.99 ต้องได้ส่วนลดพิเศษ 50% ตามข้อตกลงพิเศษ (ref: ticket #892)"
```

### สร้าง commit ที่ 3: Malee รัน formatter ทั้งไฟล์

```bash
git config user.name "Malee Formatter-Bot"
git config user.email "malee@example.com"

cat > pricing.py << 'EOF'
def calculate_price(base_price, quantity):
  total = base_price * quantity
  return total


def apply_discount(total, discount_rate):
  if total == 999.99:
    return total * 0.5
  return total * (1 - discount_rate)
EOF

git add pricing.py
git commit -m "chore: ปรับ indentation ทั้งไฟล์เป็น 2 spaces ตามมาตรฐานใหม่ของทีม"
```

บันทึก hash ของ commit นี้ไว้:

```bash
FORMAT_COMMIT=$(git rev-parse HEAD)
echo "Format commit: $FORMAT_COMMIT"
```

### สร้าง commit ที่ 4: Somchai ย้ายฟังก์ชัน `apply_discount` ไปไฟล์ใหม่

```bash
git config user.name "Somchai Refactor"
git config user.email "somchai@example.com"

cat > pricing.py << 'EOF'
def calculate_price(base_price, quantity):
  total = base_price * quantity
  return total
EOF

cat > discount.py << 'EOF'
def apply_discount(total, discount_rate):
  if total == 999.99:
    return total * 0.5
  return total * (1 - discount_rate)
EOF

git add pricing.py discount.py
git commit -m "refactor: แยก apply_discount ออกไปไฟล์ discount.py เพื่อความเป็นระเบียบ"
```

### ภารกิจที่ 1: หาว่าใครเป็นคนเขียนเงื่อนไข `total == 999.99` เดิมจริง ๆ

```bash
cd ~/git-course/part-43-blame
git blame discount.py
```

ผลลัพธ์แบบธรรมดาจะโชว์ **Somchai** เป็นคนเขียนทุกบรรทัด เพราะเป็นคนล่าสุดที่ย้ายไฟล์มา — นี่คือคำตอบที่ผิดในเชิงบริบท ลองแก้ด้วย `-C`:

```bash
git blame -C discount.py
```

คราวนี้ควรเห็นว่า Git ตามรอยไปเจอว่าเนื้อหานี้เคยอยู่ใน `pricing.py` มาก่อน แต่ชื่อ author ที่โผล่มาจะเป็น **Malee** (คนที่รันฟอร์แมตล่าสุด) ไม่ใช่ Bob ที่เป็นคนเขียน logic จริง เพราะการ format บดบังไว้อีกชั้น

### ภารกิจที่ 2: มองข้าม commit ฟอร์แมตด้วย `-w` ควบคู่กับ `-C`

```bash
git blame -w -C discount.py
```

ตอนนี้ควรจะเห็นชื่อ **Bob Fixer** ปรากฏขึ้นมาสำหรับบรรทัดที่มีเงื่อนไข `total == 999.99` ซึ่งเป็นคำตอบที่ถูกต้องตรงกับความเป็นจริงของประวัติศาสตร์โค้ด

### ภารกิจที่ 3: ดูบริบทเต็มของ commit ที่ Bob เขียน

```bash
git show $(git blame -w -C -L /999.99/,/999.99/ discount.py | awk '{print $1}')
```

หรือถ้า one-liner ข้างต้นซับซ้อนเกินไป ให้ทำแบบแยกขั้นตอน:

```bash
git blame -w -C -L '/999.99/,/999.99/' discount.py
# คัดลอก commit hash ที่ได้ แล้วรัน
git show <hash-ที่ได้>
```

ควรเห็น commit message เต็มของ Bob ที่อธิบายว่า **"แก้ปัญหาลูกค้า VIP เบอร์ 12345... ตามข้อตกลงพิเศษ (ref: ticket #892)"** ซึ่งให้บริบทที่สำคัญมาก — เงื่อนไขนี้ไม่ใช่บั๊ก แต่เป็น business requirement เฉพาะกิจที่ผูกกับ ticket #892

### ภารกิจที่ 4: ตั้งค่า `.git-blame-ignore-revs` เพื่อซ่อน commit ฟอร์แมต

```bash
cat > .git-blame-ignore-revs << EOF
# Commit นี้คือการปรับ indentation ทั้งไฟล์ ไม่ได้เปลี่ยน logic ใด ๆ
$FORMAT_COMMIT
EOF

git add .git-blame-ignore-revs
git commit -m "chore: เพิ่มไฟล์ blame-ignore-revs เพื่อซ่อน commit จัดฟอร์แมต"

git config blame.ignoreRevsFile .git-blame-ignore-revs
```

ทดสอบผลลัพธ์:

```bash
git blame -C discount.py
```

ตอนนี้แม้จะไม่ใส่ `-w` ด้วยซ้ำ ผลลัพธ์ก็ควรจะข้าม commit ของ Malee ไปโดยอัตโนมัติแล้ว (เพราะถูกตั้งค่าใน `blame.ignoreRevsFile` ไว้แล้ว) และควรเห็นชื่อ Bob ปรากฏสำหรับบรรทัดเงื่อนไขพิเศษนั้น

### ภารกิจที่ 5: ใช้ `git log -S` หาว่าตัวเลข `999.99` เคยถูกใช้ที่ไหนบ้างในประวัติศาสตร์ทั้งหมด

```bash
git log -S "999.99" --oneline --all
```

ควรเห็น commit ของ Bob เป็นคนเดียวที่เพิ่มข้อความนี้เข้ามา ยืนยันผลลัพธ์จาก blame อีกครั้งด้วยวิธีที่ต่างออกไป

### ภารกิจที่ 6 (ท้าทายเพิ่มเติม): จำกัดขอบเขตด้วย `-L` แบบ regex

```bash
git blame -w -C -L '/def apply_discount/,/^def /' discount.py
```

ลองสังเกตว่าคำสั่งนี้ให้ผลลัพธ์ตรงกับที่คาดหวังหรือไม่ (คำใบ้: ไฟล์นี้มีฟังก์ชันเดียว ลอง `-L '/def apply_discount/'` เฉย ๆ ดูด้วยว่าต่างกันอย่างไร)

### เกณฑ์ความสำเร็จของแบบฝึกหัดนี้

คุณควรจะสามารถตอบคำถามต่อไปนี้ได้ทั้งหมดหลังทำแบบฝึกหัดเสร็จ:

- [ ] อธิบายได้ว่าทำไม `git blame` เปล่า ๆ บนไฟล์ `discount.py` ถึงให้คำตอบที่ทำให้เข้าใจผิด
- [ ] อธิบายบทบาทของ `-C` ในการตามรอยโค้ดข้ามไฟล์ได้
- [ ] อธิบายบทบาทของ `-w` ในการมองข้ามการเปลี่ยนแปลง whitespace ได้
- [ ] ใช้ `.git-blame-ignore-revs` ร่วมกับ `git config blame.ignoreRevsFile` เพื่อทำให้ blame ถูกต้องโดยไม่ต้องพิมพ์ flag ทุกครั้งได้
- [ ] ใช้ `git log -S` เพื่อยืนยันผลลัพธ์จาก blame ด้วยวิธีอิสระอีกทางหนึ่งได้
- [ ] อธิบายได้ว่าทำไมการอ่าน commit message ของ Bob (ที่อ้างถึง ticket #892) ถึงสำคัญกว่าการรู้แค่ชื่อคนเขียนเฉย ๆ

## สรุป Part 43

ใน Part นี้เราได้เรียนรู้ว่า:

1. **`git blame`** คือเครื่องมือแสดงว่าแต่ละบรรทัดของไฟล์ถูกแก้ไข "ล่าสุด" โดย commit ไหน ใครเขียน เมื่อไหร่ — ไม่ใช่ใครเป็น "ผู้เขียนดั้งเดิม" เสมอไป
2. ผลลัพธ์ของ blame ประกอบด้วย commit hash ย่อ, author, วันเวลา, เลขบรรทัด และเนื้อหา และสัญลักษณ์ `^` บ่งบอกว่าเป็น boundary commit
3. **`-L <start>,<end>`** ช่วยจำกัดขอบเขตการดูเฉพาะบรรทัดที่สนใจ รองรับทั้งเลขบรรทัด, `+N`/`-N` และ regular expression ของชื่อฟังก์ชัน
4. **`-w`** ช่วยมองข้ามการเปลี่ยนแปลง whitespace เพื่อไม่ให้ commit จัดฟอร์แมตบดบัง commit ที่แก้เนื้อหาจริง
5. **`-C`** (และ `-M`) ช่วยตามรอยโค้ดที่ถูก copy/move ข้ามไฟล์ พร้อมปรับระดับความเข้มข้นของการค้นหาได้
6. การใช้ blame คู่กับ **`git show`**, **`git log -p`** และ **`git log -S`/`-G`** ช่วยให้เห็นบริบทเต็มของการเปลี่ยนแปลง ไม่ใช่แค่บรรทัดเดียวที่กำลังดูอยู่
7. **`.git-blame-ignore-revs`** ร่วมกับ `git config blame.ignoreRevsFile` คือวิธีมาตรฐานของทีมในการซ่อน commit ที่เป็นแค่ reformat ออกจากผลลัพธ์ blame อย่างถาวรและใช้ร่วมกันได้ทั้งทีม รวมถึง GitHub UI ก็รองรับไฟล์นี้โดยอัตโนมัติ
8. **GitHub มีปุ่ม Blame** ในหน้าไฟล์ พร้อมฟีเจอร์ "View blame prior to this change" สำหรับไล่ตามรอยย้อนหลังโดยไม่ต้องใช้ terminal
9. Blame เป็นเครื่องมือสำหรับ **เข้าใจบริบทของอดีตเพื่อการตัดสินใจในปัจจุบัน** ไม่ใช่เครื่องมือสำหรับหาคนมารับผิดในบั๊กหรือปัญหาที่เกิดขึ้น การนำไปใช้ผิดวัตถุประสงค์ทำลายวัฒนธรรมการทำงานเป็นทีมได้
