## Step 941: ภาพรวมภารกิจปิดเฟส 9 — จำลอง Incident จริง 5 สถานการณ์และกระบวนการกู้คืนแบบมืออาชีพ

### 941.1 ทำไม Part ปิดเฟส 9 ต้องเป็นเรื่อง Incident Response

ตลอดเฟส 9 (Part 86–94) คุณได้เรียนรู้ทักษะที่แยกวิศวกรมืออาชีพระดับสูงออกจากวิศวกรทั่วไป — การเป็น Maintainer โปรเจกต์ Open Source, การเขียน Contributing Guide, การบริหาร Release ด้วย Semantic Versioning, การทำ Changelog Automation, การทำงานร่วมกันข้ามทีมในองค์กรขนาดใหญ่, การเชื่อม Git เข้ากับ Agile/Scrum, การวัดผลทีมด้วย Metrics/DORA, การ Migration จากระบบเก่า และล่าสุดใน **Part 94** คือการ Debug ปัญหา Git ที่ซับซ้อนในองค์กร

แต่ทักษะทั้งหมดนี้ถูกทดสอบจริงที่สุดในช่วงเวลาเดียว: **ตอนที่มีอะไรบางอย่างพังกะทันหันและทั้งทีมต้องแก้ไขภายใต้ความกดดัน** นี่คือสิ่งที่วงการเรียกว่า **Incident** และวิธีที่ทีมจัดการกับ incident (ไม่ใช่แค่ "แก้ให้หาย" แต่รวมถึงกระบวนการทั้งหมดก่อน ระหว่าง และหลังเหตุการณ์) คือตัวชี้วัดที่ชัดเจนที่สุดว่าทีมวิศวกรรมนั้น "เป็นมืออาชีพ" จริงหรือไม่

Part นี้ **ไม่สอนเครื่องมือใหม่แม้แต่ตัวเดียว** เช่นเดียวกับ Part 45 และ Part 85 ที่ปิดเฟสก่อนหน้า — แต่จะนำ `git reflog` (Part 94), `git filter-repo`/แนวคิด revoke-ก่อน-ลบ (Part 78), กลยุทธ์ rollback (Part 74), การวินิจฉัย performance (Part 58, 63) และ `git bisect` (Part 42) มาใช้งานจริงในสถานการณ์กดดันเวลา พร้อมปิดท้ายด้วยทักษะที่เฟส 9 ทั้งเฟสมุ่งสร้าง: **การเปลี่ยนความโกลาหลให้กลายเป็นกระบวนการที่เรียนรู้ได้และดีขึ้นเรื่อยๆ**

### 941.2 Incident คืออะไร ต่างจาก "บั๊กทั่วไป" อย่างไร

**Incident** คือเหตุการณ์ที่ทำให้ระบบ (หรือกระบวนการทำงานของทีม) หยุดทำงานตามที่ควรจะเป็น จนส่งผลกระทบต่อผู้ใช้งาน ธุรกิจ หรือทีมงานเองในระดับที่ยอมรับไม่ได้ และ **ต้องการการตอบสนองทันที** ไม่ใช่รอแก้ในรอบพัฒนาถัดไปตามปกติ

ความแตกต่างจากบั๊กทั่วไป:

| | บั๊กทั่วไป | Incident |
|---|---|---|
| ความเร่งด่วน | แก้ในรอบ sprint ถัดไปได้ | ต้องแก้ทันที นาทีต่อนาที |
| ผลกระทบ | จำกัด อาจกระทบ feature เดียว | กระทบผู้ใช้งานจริง/รายได้/ความน่าเชื่อถือ |
| กระบวนการ | เปิด issue → ทำใน backlog ปกติ | ประกาศ incident → ระดมทีมตอบสนองทันที |
| เอกสารหลังจบ | commit message / PR description | Post-mortem แบบเป็นทางการ |
| จุดสนใจหลัก | "แก้บั๊กให้ถูก" | "หยุดความเสียหายให้เร็วที่สุด" ก่อน ค่อยหาสาเหตุจริง |

### 941.3 Severity Level และบทบาทมาตรฐานตอนเกิด Incident

องค์กรวิศวกรรมมืออาชีพส่วนใหญ่ใช้ระบบจัดระดับความรุนแรง (Severity, ย่อว่า SEV) เพื่อกำหนดว่าต้องตอบสนองเร็วแค่ไหนและต้องแจ้งใครบ้าง NetiTech Solutions ใช้มาตรฐาน 4 ระดับดังนี้:

| ระดับ | คำนิยาม | ตัวอย่าง | เวลาตอบสนองที่คาดหวัง |
|---|---|---|---|
| **SEV1 — วิกฤต** | ระบบหลักล่มทั้งหมด หรือกระทบรายได้/ข้อมูลลูกค้าโดยตรง | payments-service รับชำระเงินไม่ได้เลย | ตอบสนองทันที ทุกคนที่เกี่ยวข้องหยุดงานอื่นทั้งหมด |
| **SEV2 — รุนแรง** | ฟีเจอร์สำคัญใช้งานไม่ได้ แต่ระบบหลักยังทำงาน | checkout error rate พุ่งสูงบางส่วน | ตอบสนองภายใน 15–30 นาที |
| **SEV3 — ปานกลาง** | กระทบผู้ใช้งานบางกลุ่ม มี workaround | ฟีเจอร์รองใช้ไม่ได้ในบาง browser | ตอบสนองภายในเวลาทำการ |
| **SEV4 — เล็กน้อย** | กระทบภายใน ไม่กระทบผู้ใช้จริง | dashboard ภายในโหลดช้า | จัดคิวในงานปกติ |

บทบาทมาตรฐานที่ควรกำหนดไว้ **ก่อน** เกิด incident (ไม่ใช่มานั่งเถียงกันตอนไฟไหม้):

1. **Incident Commander (IC)** — ผู้ตัดสินใจสูงสุดระหว่างเหตุการณ์ ไม่จำเป็นต้องเป็นคนแก้โค้ดเอง หน้าที่คือประสานงาน ตัดสินใจ และรับผิดชอบการสื่อสาร
2. **Ops Lead / Responder** — ผู้ลงมือแก้ไขทางเทคนิคจริง อาจมีหลายคนตามความเชี่ยวชาญ
3. **Communications Lead** — สื่อสารสถานะให้ผู้บริหาร ลูกค้า หรือทีมอื่นที่ไม่ได้อยู่ในห้อง incident ทราบเป็นระยะ ไม่ให้ Responder ต้องหยุดมือมาตอบคำถามซ้ำๆ
4. **Scribe** — จดบันทึก timeline แบบ real-time ทุกการตัดสินใจและทุกคำสั่งที่รันไป ข้อมูลนี้จะกลายเป็นวัตถุดิบหลักของ post-mortem ใน Step 947

### 941.4 วงจรชีวิตมาตรฐานของ Incident (Incident Lifecycle)

```
ตรวจพบ (Detect) → ประกาศ (Declare) → ประเมินความรุนแรง (Triage)
     → หยุดความเสียหาย (Mitigate) → แก้สาเหตุจริง (Resolve)
         → เขียน Post-mortem (Step 947) → ติดตาม Action Items (Step 949)
```

จุดที่มือใหม่มักทำผิดคือรีบกระโดดไปหา "สาเหตุจริง" (Resolve) ทันทีโดยข้าม "หยุดความเสียหาย" (Mitigate) ไปก่อน — เราจะเห็นหลักการนี้ชัดเจนที่สุดใน Step 944 (rollback ต้องเร็วกว่า debug เสมอ)

## Step 942: สถานการณ์ที่ 1 — force-push ทับประวัติ main โดยไม่ตั้งใจ กู้คืนด้วย `git reflog`

### 942.1 เกิดอะไรขึ้น

วันศุกร์ เวลา 16:47 น. วิศวกรคนหนึ่งในทีม Core Product ตั้งใจจะจัดระเบียบ branch ทดลองส่วนตัวของตัวเองด้วย `git rebase -i` แล้ว force-push แต่พิมพ์ผิดจุด — เขาสลับไปอยู่ที่ local branch `main` ของ `core-api` ที่ hard reset ไปยัง commit เก่ากว่าโดยไม่ทันสังเกต แล้วรัน:

```bash
git push origin main --force
```

ผลลัพธ์: **`main` บน remote ถูกเขียนทับด้วยประวัติเก่า** commit ที่หายไปมีทั้งหมด 14 commits จากวิศวกร 4 คนตลอด 2 วันที่ผ่านมา รวมถึง Pull Request ที่เพิ่งถูก merge เข้าไปเมื่อเช้าเพื่อแก้บั๊กระดับ Critical ตัวหนึ่งด้วย

ทีมรู้ตัวภายใน 6 นาที เพราะวิศวกรอีกคนพยายาม `git pull` แล้วเจอ error แปลกๆ ว่า local เขาแซงหน้า remote ไปไกลผิดปกติ

### 942.2 กฎเหล็กข้อแรก: หยุดก่อนลงมือ

ก่อนพิมพ์คำสั่งใดๆ เพิ่ม ให้ประกาศในช่องทางทีมทันทีว่า:

1. **ห้ามใครก็ตาม push หรือ force-push เข้า `main` ของ `core-api` เพิ่มอีกจนกว่าจะได้รับสัญญาณปลอดภัย** — เพื่อไม่ให้ SHA ที่ต้องกู้คืนถูกเขียนทับซ้ำอีกชั้น
2. **ห้ามรัน `git gc`, `git prune`, หรือ `git repack` บนเครื่องใครก็ตามที่เกี่ยวข้อง** — คำสั่งเหล่านี้อาจลบ object ที่ยัง unreachable อยู่ทิ้งไปถาวรก่อนที่จะกู้คืนทัน (ตามหลักการเรื่องอายุของ dangling object ที่เรียนใน Part 94)
3. **ห้ามรีบ force-push ซ้ำ "เพื่อแก้ไข" โดยยังไม่รู้ SHA ที่ถูกต้อง** — การกระทำโดยไม่มีข้อมูลจะยิ่งทำให้สถานการณ์สับสนกว่าเดิม

### 942.3 ทบทวนหลักการ `git reflog` จาก Part 94 แล้วขยายไปสู่ระดับทีม

Part 94 (Step 934) สอนไว้ว่า `git reflog` คือ "เครื่องบันทึกการบิน" ของ Git — มันจดจำทุกครั้งที่ HEAD หรือ branch ใดๆ **บนเครื่อง local ของคุณเอง** เปลี่ยนตำแหน่ง (commit, checkout, merge, rebase, reset ฯลฯ) โดยมีอายุจัดเก็บเริ่มต้น 90 วันสำหรับ commit ที่ยัง reachable และ 30 วันสำหรับ commit ที่ unreachable แล้ว (ควบคุมด้วย `gc.reflogExpire` และ `gc.reflogExpireUnreachable`) นั่นแก้ปัญหา "ฉันเผลอ `reset --hard` งานตัวเองหาย" ได้อย่างสมบูรณ์

แต่สถานการณ์นี้ **ใหญ่กว่านั้น** เพราะ:

> **`git reflog` เป็นข้อมูล local ล้วนๆ — repository บน GitHub (remote) เองไม่มี `git reflog` ของ branch ให้เรียกดูโดยตรง** เมื่อ `main` บน remote ถูกทับ ข้อมูลที่ต้องใช้กู้คืนจึงไม่ได้อยู่ที่เครื่องของคนที่ทำพลาด แต่กระจัดกระจายอยู่ตามเครื่องของคนอื่นในทีมที่ **เคย fetch ประวัติเดิมไว้ก่อนเกิดเหตุ**

หลักการสำคัญที่ต้องเข้าใจ: ทุกครั้งที่คุณ `git fetch` หรือ `git pull` Git จะอัปเดต **remote-tracking branch** (`origin/main`) ในเครื่องคุณ และบันทึกการอัปเดตนั้นไว้ใน reflog ของ `origin/main` ด้วยเช่นกัน (ไม่ใช่แค่ reflog ของ `main` local) ตราบใดที่มีใครสักคนในทีม fetch ข้อมูลที่ถูกต้องไว้ก่อนเกิดเหตุ และยังไม่ทัน fetch ซ้ำทับหลังเกิดเหตุ ค่า SHA เดิมก็ยังนอนอยู่ใน reflog ของเครื่องคนนั้น

### 942.4 ขั้นตอนการกู้คืนจริง

**ขั้นที่ 1 — ตรวจ reflog ของทุกคนที่อาจมี SHA เก่า**

ให้สมาชิกทีมทุกคนที่ clone `core-api` ไว้ (โดยเฉพาะคนที่เพิ่งทำงานกับ branch นี้ก่อนเกิดเหตุ) รันคำสั่งเดียวกันนี้ **โดยยังไม่ต้อง fetch ซ้ำ**:

```bash
git reflog show origin/main
```

```
a9f3c21 origin/main@{0}: fetch: fast-forward
7d81ee4 origin/main@{1}: fetch: fast-forward
7d81ee4 origin/main@{2}: fetch: fast-forward
...
```

หากใครเห็นว่า `origin/main@{0}` หรือ `{1}` เป็นค่า SHA ที่ "ยาวกว่า" หรือ "ใหม่กว่า" ค่าที่ `origin/main` มีอยู่ตอนนี้ (เทียบด้วย `git log <sha> -1`) นั่นคือผู้สมัครตัวเก็ง วิศวกรอีกคนในทีม (คนที่ pull แล้วเจอ error ตามข้อ 942.1) พบว่าเครื่องของตัวเองมี `origin/main@{1}` เท่ากับ `7d81ee4` ซึ่งตรงกับสิ่งที่หายไปพอดี

**ขั้นที่ 2 — ตรวจสอบทางเลือกอื่นประกอบ (ในกรณีไม่มีใครมี reflog ที่ตรง)**

ถ้าไม่มีใครใน local reflog เก็บค่าไว้พอดี ยังมีอีก 2 แหล่งที่ควรตรวจสอบเสมอ:

1. **Log ของ CI/CD** — ทุก pipeline run ที่ผ่านมาจะ checkout ด้วย commit SHA ที่ระบุชัดเจนในไฟล์ log (`Checking out revision 7d81ee4...`) การ build ล่าสุดที่ผ่านก่อนเกิดเหตุคือหลักฐานที่แม่นยำมาก
2. **Branch ของ Pull Request ที่ยังเปิดอยู่** — commit ที่เคย merge เข้า `main` ไปแล้วยังคง "reachable" อยู่ผ่าน ref ของ PR บน GitHub (`refs/pull/<n>/head`) ตราบใดที่ PR ยังไม่ถูกลบ ดังนั้นแม้ `main` จะถูกทับ แต่ merge commit เดิมอาจยัง clone ได้ผ่าน branch ของ PR ที่เกี่ยวข้อง
3. **GitHub Enterprise Audit Log** (ถ้าองค์กรเปิดใช้งาน) — จะบันทึกเหตุการณ์ `protected_branch.policy_override` หรือ `git.push` พร้อม `before`/`after` SHA ของการ force-push ทุกครั้งไว้อย่างแม่นยำ เป็นแหล่งข้อมูลที่น่าเชื่อถือที่สุดถ้ามี

**ขั้นที่ 3 — ยืนยันว่า SHA ที่เจอถูกต้องจริง**

```bash
git show 7d81ee4 --stat
git log 7d81ee4 -5 --oneline
```

ตรวจสอบว่า commit message, จำนวนไฟล์ที่เปลี่ยน และชื่อผู้เขียนตรงกับสิ่งที่ทีมจำได้ว่าเคยมีอยู่จริงก่อนเกิดเหตุ

**ขั้นที่ 4 — กู้คืนกลับไปที่ remote**

วิธีที่ปลอดภัยที่สุดคือสร้าง branch สำรองไว้ก่อนแตะ `main` จริง:

```bash
git branch recovery/main-restore 7d81ee4
git push origin recovery/main-restore
```

จากนั้นเปิด Pull Request จาก `recovery/main-restore` เข้า `main` เพื่อให้ทีมยืนยันเนื้อหาอีกครั้งก่อนรวมเข้าจริง (ถ้าเวลาเอื้ออำนวย) หรือในกรณีฉุกเฉินที่ต้องเร่งคืนสถานะเดิมทันที ให้ผู้ดูแลระบบที่มีสิทธิ์ bypass branch protection ชั่วคราวรันคำสั่งคืนค่าตรง โดยใช้ `--force-with-lease` แทน `--force` เสมอ:

```bash
git push origin 7d81ee4:main --force-with-lease=main:a9f3c21
```

คำสั่งนี้บอก Git ว่า "ให้ force-push ก็ต่อเมื่อค่าปัจจุบันของ `main` บน remote ยังเป็น `a9f3c21` (ค่าที่ผิดพลาดที่เรารู้อยู่แล้ว) เท่านั้น" — ถ้าระหว่างนี้มีใครแอบ push อะไรเข้าไปอีกโดยที่เราไม่รู้ คำสั่งจะ **ปฏิเสธการทำงานทันที** แทนที่จะเขียนทับข้อมูลใหม่นั้นไปอย่างไม่ตั้งใจ ซึ่งปลอดภัยกว่า `--force` ธรรมดามาก

**ขั้นที่ 5 — ให้ทุกคนซิงก์เครื่องตัวเองอย่างถูกวิธี**

สมาชิกทีมที่ยังไม่ทัน fetch ตอนเกิดเหตุอาจมี local `main` ที่เดินหน้าต่อจาก SHA ผิดไปแล้วโดยไม่รู้ตัว (เผลอ commit ต่อ) ห้ามให้ใครรัน `git reset --hard origin/main` ทันทีโดยไม่ตรวจสอบก่อน ให้สำรอง work ของตัวเองไว้เป็น branch ก่อนเสมอ:

```bash
git branch backup/my-local-work HEAD
git fetch origin
git reset --hard origin/main
```

### 942.5 ป้องกันไม่ให้เกิดซ้ำ

การกู้คืนสำเร็จไม่ใช่จุดจบ — action item ที่แท้จริงคือทำให้เหตุการณ์นี้ **เกิดขึ้นไม่ได้อีกเลย** ไม่ใช่แค่ "เกิดแล้วกู้คืนเก่งขึ้น" โดยอ้างอิงนโยบาย Branch Protection ที่วางไว้แล้วใน Part 85 Step 843:

1. เปิดใช้งานกฎ **ห้าม force-push เข้า branch ที่มีการป้องกัน (`main`, `release/*`) โดยเด็ดขาด** ที่ระดับ Organization Ruleset ไม่ใช่ตั้งทีละ repository — ถ้ากฎนี้เปิดอยู่ตั้งแต่แรก คำสั่ง `git push origin main --force` ในข้อ 942.1 จะถูก Git **ปฏิเสธทันทีตั้งแต่ต้นทาง** ด้วยข้อความ `remote: error: denied because main is protected` และ incident นี้จะไม่มีวันเกิดขึ้นเลย
2. ปลูกฝังนิสัยให้ทุกคนใช้ `git push --force-with-lease` แทน `git push --force` เป็นค่าเริ่มต้นเสมอ แม้กระทั่งกับ branch ส่วนตัว เพราะ `--force-with-lease` จะปฏิเสธการทำงานทันทีถ้าพบว่า branch เปลี่ยนสถานะไปจากที่คุณคาดไว้ล่าสุด ลดโอกาสพลาดโดยไม่รู้ตัวได้มาก
3. เพิ่ม alias เตือนความจำที่ระดับเครื่องของทุกคน เช่น ตั้ง `push.default` และ prompt ของ terminal ให้แสดงชื่อ branch ปัจจุบันเด่นชัดเสมอ เพื่อลดโอกาส "สลับ branch ผิดแล้วพิมพ์คำสั่งอันตรายโดยไม่ทันสังเกต"

## Step 943: สถานการณ์ที่ 2 — secret หลุดเข้า production repository กะทันหัน ต้องจัดการด่วน

### 943.1 เกิดอะไรขึ้น

เช้าวันจันทร์ job สแกน secret รายสัปดาห์ (workflow `secret-scan.yml` ที่วางไว้ใน Part 85 Step 844) รันตามตารางเวลาและพบสิ่งผิดปกติใน repository `payments-service`: ไฟล์ `.env.production.local` ที่มีคีย์เชื่อมต่อ payment gateway และรหัสผ่านฐานข้อมูล production ถูก commit เข้า branch `hotfix/checkout-timeout` เมื่อ 2 วันก่อน และ branch นั้นถูก merge เข้า `main` ไปแล้วผ่าน **hotfix แบบเร่งด่วนที่ได้รับการยกเว้นให้ merge โดยไม่ต้องรอ review เต็มรูปแบบ** เพราะตอนนั้นเป็นการแก้บั๊กที่กระทบผู้ใช้จำนวนมาก

สาเหตุที่หลุดผ่านชั้นป้องกันด่านแรก: วิศวกรที่ทำ hotfix รีบมากจนใช้ `git commit --no-verify` ข้าม pre-commit hook (gitleaks) ที่ควรจะดักไว้ตั้งแต่ก่อน commit

### 943.2 หลักการทองคำ: Revoke ก่อนเสมอ ไม่ใช่แค่ลบ

Part 78 (Step 773) วางหลักการนี้ไว้ชัดเจนแล้ว และในสถานการณ์จริงระดับองค์กร หลักการนี้ยิ่งสำคัญกว่าเดิม เพราะ:

> **ตราบใดที่ secret ตัวเดิมยังใช้งานได้จริงอยู่ การลบมันออกจากประวัติ Git มีค่าเท่ากับศูนย์ในแง่ความปลอดภัย** — คนที่มีสำเนาของ commit นั้นอยู่แล้ว (ไม่ว่าจะ clone ไว้ก่อนหน้า, cache ของ CI, หรือผู้ไม่หวังดีที่แอบเก็บไว้แล้ว) ยังคงใช้ secret ตัวนั้นเข้าระบบได้อยู่ดี ไม่ว่าประวัติ Git จะถูกแก้ไขสะอาดแค่ไหนก็ตาม

ลำดับการตอบสนองที่ถูกต้องมีดังนี้ (เรียงตามเวลาที่ต้องทำจริง ไม่ใช่ตามความรู้สึกว่าอะไร "สำคัญที่สุด"):

**นาทีที่ 0–5: Revoke/Rotate ที่ต้นทางทันที**

```
1. เข้า dashboard ของ payment gateway provider → revoke API key ที่หลุด → สร้างคีย์ใหม่
2. เข้า Database provider / Secrets Manager → เปลี่ยนรหัสผ่านฐานข้อมูล production
3. อัปเดตค่าใหม่เข้า Vault / GitHub Actions Secrets (ไม่ใช่แก้ไฟล์ .env ด้วยมือบนเครื่อง)
4. Trigger deployment pipeline ปกติเพื่อ deploy service ด้วยค่า secret ใหม่
5. Restart pod/process ที่ยัง cache connection เดิมค้างอยู่ เพื่อบังคับให้ต่อด้วยค่าใหม่
```

จุดสำคัญ: **ขั้นตอนนี้ต้องทำก่อนที่ใครจะไปยุ่งกับประวัติ Git แม้แต่นิดเดียว** เพราะการแก้ไขประวัติ Git ใช้เวลาและมีความเสี่ยง (ต้องประสานทั้งทีมให้ clone ใหม่) ในขณะที่การ revoke ที่ต้นทางมักใช้เวลาแค่ไม่กี่นาทีผ่านหน้า dashboard และทำให้ความเสี่ยงที่แท้จริงหมดไปทันที

**นาทีที่ 5–30: ประเมินขอบเขตความเสียหาย (Blast Radius)**

ก่อนบอกใครว่า "ไม่มีอะไรรั่วไหลจริง" ต้องมีหลักฐานสนับสนุน ไม่ใช่แค่ความรู้สึก:

- ตรวจสอบ access log/audit log ของ payment gateway ในช่วงเวลาตั้งแต่ commit ถูก push จนถึงเวลาที่ revoke สำเร็จ ว่ามีการเรียกใช้จาก IP หรือ pattern ที่ไม่คุ้นเคยหรือไม่
- ตรวจสอบ database connection log ในช่วงเวลาเดียวกันว่ามี connection จากที่อยู่ที่ไม่ใช่ระบบของบริษัทเองหรือไม่
- ตรวจสอบว่า repository เป็น private หรือ public และมีใครนอกทีมที่มีสิทธิ์เข้าถึง fork/clone ได้บ้างในช่วงเวลาที่ secret ยังอยู่ในประวัติ

ในกรณีนี้ ทีม Security ตรวจสอบแล้วพบว่า **ไม่มีการเรียกใช้จากแหล่งที่ไม่รู้จัก** ในช่วงเวลาที่ secret ยังใช้งานได้ — แต่ข้อสรุปนี้ต้องมีหลักฐานแนบในรายงานเสมอ ไม่ใช่แค่กล่าวลอยๆ

**ชั่วโมงถัดมา: ทำความสะอาดประวัติ Git**

หลังจากความเสี่ยงจริงหมดไปแล้ว (เพราะ secret เดิมใช้งานไม่ได้อีกต่อไป) จึงค่อยลบร่องรอยออกจากประวัติด้วย `git filter-repo` ตามขั้นตอนที่สอนไว้ใน Part 78 Step 774:

```bash
git filter-repo --path .env.production.local --invert-paths
```

จากนั้น force-push ประวัติที่สะอาดแล้วเข้า remote และแจ้งทุกคนที่มี local clone ของ `payments-service` ให้ **ลบ clone เดิมทิ้งแล้ว clone ใหม่** แทนการ pull/rebase ทับ (เพื่อไม่ให้ blob เก่าที่มี secret หลงเหลืออยู่ใน `.git` ของเครื่องใครโดยไม่รู้ตัว)

### 943.3 แก้สาเหตุเชิงกระบวนการ ไม่ใช่แค่สาเหตุทางเทคนิค

Incident นี้ไม่ได้เกิดจาก "ความประมาทของคนคนเดียว" แต่เกิดจาก **ช่องโหว่ 2 ชั้นในกระบวนการที่อนุญาตให้ความประมาทนั้นไปถึงจุดที่สร้างความเสียหายได้**:

1. **ช่องโหว่ที่ 1: pre-commit hook เป็นแค่แนวป้องกันฝั่ง client ที่ข้ามได้ง่าย** (`--no-verify`) — วิธีแก้ที่แท้จริงคือเปิดใช้ **GitHub Push Protection for Secret Scanning** ที่ทำงานฝั่ง server ซึ่งไม่มีทางถูกข้ามด้วย flag ใดๆ จากฝั่ง client ได้เลย ถ้าเปิดไว้ การ push ครั้งนั้นจะถูกปฏิเสธตั้งแต่ต้นทาง
2. **ช่องโหว่ที่ 2: กระบวนการ "hotfix ฉุกเฉิน" อนุญาตให้ข้าม required review ได้ทั้งหมด** รวมถึงข้ามการตรวจสอบไฟล์ที่เกี่ยวกับความปลอดภัยไปด้วย ทั้งที่ควรมีข้อยกเว้นเฉพาะจุด ไม่ใช่ยกเว้นทุกอย่างเหมารวม — action item คือกำหนดว่าแม้เป็น hotfix เร่งด่วน โฟลเดอร์/ไฟล์ที่เกี่ยวกับ secret หรือ auth ต้องยังคงต้องมี Security team อนุมัติเสมอ (ตาม CODEOWNERS ที่วางไว้ใน Part 85 Step 843) หรืออย่างน้อยต้องมีการอนุมัติภายหลัง (post-hoc approval) ที่มีการบันทึกเหตุผลไว้เป็นลายลักษณ์อักษร

> **ข้อคิดสำคัญ:** สังเกตว่าลำดับการตอบสนองทั้งหมดคือ **revoke → ประเมินผลกระทบ → ทำความสะอาดประวัติ → แก้ไขกระบวนการ** ไม่ใช่ "ลบไฟล์ commit ทับแล้วจบ" ซึ่งเป็นความผิดพลาดที่พบบ่อยที่สุดของทีมที่ไม่เคยผ่านการฝึกสถานการณ์แบบนี้มาก่อน

## Step 944: สถานการณ์ที่ 3 — deploy พังหลัง merge ต้อง rollback ด่วนที่สุด

### 944.1 เกิดอะไรขึ้น

ทีม Web merge Pull Request ฟีเจอร์ checkout ใหม่เข้า `main` ของ `web-app` เวลา 14:02 น. pipeline deploy อัตโนมัติ (ตามที่วางไว้ใน Part 74) เริ่ม rolling update ไปยัง production ทันที เวลา 14:05 น. ระบบ monitoring แจ้งเตือนว่า error rate ของ endpoint `/checkout` พุ่งจาก 0.2% เป็น 42% ทันที ผู้ใช้จำนวนมากไม่สามารถชำระเงินให้เสร็จได้ วิศวกร on-call ถูก page ทันที และประกาศ **SEV1**

### 944.2 หลักการที่ต้องยึดไว้แน่น: Rollback ต้องเร็วกว่า Debug เสมอ

นี่คือหลักการที่ Part 74 (Step 737) วางไว้แล้ว และในสถานการณ์วิกฤตจริงมันสำคัญกว่าที่คิดมาก เพราะภายใต้ความกดดัน สัญชาตญาณของวิศวกรมักบอกให้ "อ่าน log หาสาเหตุก่อน" ทั้งที่ทุกนาทีที่ผ่านไประหว่างการอ่าน log คือรายได้และความไว้วางใจของลูกค้าที่เสียไปเพิ่มขึ้นเรื่อยๆ

> **ลำดับที่ถูกต้องเสมอ: หยุดเลือดไหลก่อน (rollback) แล้วค่อยหาสาเหตุแบบสงบๆ ในภายหลัง (root cause analysis) ไม่ใช่สลับลำดับกัน**

### 944.3 เลือกวิธี Rollback ตามกลยุทธ์ deploy ที่ใช้จริง

`web-app` ของ NetiTech ใช้ Kubernetes กับ Rolling Update Strategy เพราะฉะนั้นคำสั่งที่เร็วที่สุดในการคืนสถานะคือ:

```bash
kubectl rollout undo deployment/web-app -n production
```

```
deployment.apps/web-app rolled back
```

Kubernetes เก็บ revision history ของ Deployment ไว้ให้อัตโนมัติ คำสั่งนี้จะสลับกลับไปใช้ `ReplicaSet` ก่อนหน้าทันทีโดยไม่มี downtime เพิ่มเติม (กลไกเดียวกับตอน deploy ปกติ) หากต้องการย้อนกลับมากกว่า 1 ขั้น หรือระบุ revision ที่แน่นอน:

```bash
kubectl rollout history deployment/web-app -n production
kubectl rollout undo deployment/web-app -n production --to-revision=27
```

สำหรับทีมที่ deploy ด้วยกลยุทธ์อื่นตามที่เรียนใน Part 74:

| กลยุทธ์ deploy | วิธี rollback ที่เร็วที่สุด |
|---|---|
| Rolling Update (Kubernetes) | `kubectl rollout undo` |
| Blue-Green | สลับ service selector/load balancer กลับไปที่ฝั่ง Blue ทันที |
| Canary | ปรับสัดส่วน traffic ของ canary กลับเป็น 0% ทันที |
| Image tag = commit SHA | trigger rollback pipeline job ที่รับ `ROLLBACK_TO_SHA` เป็นพารามิเตอร์ |

### 944.4 ตรวจยืนยันว่า rollback สำเร็จก่อนปิด SEV

```bash
kubectl get pods -n production -l app=web-app
```

ทีมเฝ้าดู error rate บน dashboard monitoring จนกลับสู่ระดับปกติ (ต่ำกว่า 0.5%) และรัน smoke test ชุดพื้นฐานยืนยันว่า checkout flow กลับมาทำงานได้จริง ก่อนจึงประกาศลดระดับจาก SEV1 เป็นปิดเหตุการณ์เฉพาะหน้า (แต่ยังไม่ปิด incident ทั้งหมด — ดู Step 947 และ 949)

### 944.5 รายละเอียดที่วิศวกรมือใหม่มักลืม: แก้ที่ Git ด้วย ไม่ใช่แค่ที่ Deployment

การสั่ง `kubectl rollout undo` แก้ปัญหาที่ **สถานะ deployment ปัจจุบัน** เท่านั้น แต่ commit ที่มีบั๊กยังคงอยู่บน `main` ของ Git — ถ้ามีใครสักคน merge Pull Request อื่นที่ไม่เกี่ยวข้องกันในอีก 1 ชั่วโมงถัดมา pipeline deploy อัตโนมัติจะดึงโค้ดจาก `main` (ซึ่งยังมีบั๊กฝังอยู่) มา deploy ทับการ rollback ที่เพิ่งทำไปโดยไม่มีใครตั้งใจให้เกิดเหตุการณ์ซ้ำ

วิธีป้องกันที่ถูกต้องคือ **revert merge commit ที่มีปัญหาใน Git ทันทีหลังจากระบบเสถียรแล้ว** เพื่อให้ `main` กลับมาอยู่ในสถานะที่ deploy ได้อย่างปลอดภัยเสมอ:

```bash
git revert -m 1 <merge-commit-sha>
```

แฟล็ก `-m 1` จำเป็นเสมอเมื่อ revert merge commit เพราะ merge commit มี parent มากกว่า 1 ตัว (`-m 1` หมายถึงให้ถือว่า parent ตัวแรก คือ `main` เดิมก่อน merge เป็นสายหลัก แล้ว revert เฉพาะการเปลี่ยนแปลงที่ parent ตัวที่สองนำเข้ามา) หากไม่ระบุ `-m` Git จะปฏิเสธคำสั่งพร้อม error ทันทีเพราะไม่รู้ว่าควรถือ parent ไหนเป็นหลัก

หลังจาก revert สำเร็จ ทีม Web จึงเปิด branch ใหม่เพื่อแก้ไขบั๊กจริงอย่างสงบ ทดสอบให้ครบถ้วน แล้วค่อยเปิด Pull Request ใหม่เข้า `main` ตามกระบวนการปกติ — ไม่ใช่รีบแก้แล้ว force-push ทับ revert ที่เพิ่งทำไปโดยไม่ผ่าน review

## Step 945: สถานการณ์ที่ 4 — repository ใหญ่ทำงานช้าผิดปกติ ต้องวินิจฉัยอย่างเป็นระบบ

### 945.1 เกิดอะไรขึ้น

วิศวกรในทีม Data Platform เริ่มบ่นกันหลายคนว่า `git status`, `git checkout`, และ `git commit` บน repository `data-pipelines` ที่เคยตอบสนองในเสี้ยววินาที ตอนนี้ใช้เวลาหลายวินาทีทุกครั้ง และพนักงานใหม่ที่เพิ่งเข้าทีมรายงานว่า `git clone` ใช้เวลานานถึง 25 นาที ทั้งที่ก่อนหน้านี้ใช้เวลาไม่ถึง 2 นาที

นี่ไม่ใช่ incident ที่ "ระบบล่ม" แบบ SEV1 แต่เป็นปัญหาที่กัดกร่อน productivity ของทั้งทีมอย่างต่อเนื่อง และถ้าปล่อยไว้จะแย่ลงเรื่อยๆ จึงต้องได้รับการวินิจฉัยอย่างเป็นระบบ ไม่ใช่เดาสุ่ม

### 945.2 คำถามแรกเสมอ: ช้าสำหรับคนเดียว หรือช้าทั้งทีม

ก่อนสงสัยว่า repository มีปัญหา ต้องแยกให้ออกก่อนว่าเป็นปัญหาเฉพาะเครื่อง หรือปัญหาที่ตัว repository เอง:

- **ถ้าช้าแค่เครื่องเดียว** — สาเหตุมักเป็นโปรแกรม antivirus ที่สแกนโฟลเดอร์ `.git` ทุกครั้งที่มีการเขียนไฟล์, ดิสก์ใกล้เต็มหรือเสื่อมสภาพ, การ clone ไว้บน network drive แทน local disk, หรือไฟล์ `.git/index.lock` ค้างจากการ crash ก่อนหน้า
- **ถ้าช้าทั้งทีม** — ปัญหาน่าจะอยู่ที่ตัว repository เอง นี่คือกรณีของ `data-pipelines`

### 945.3 วินิจฉัยขนาดและโครงสร้างของ Repository (อ้างอิง Part 58)

```bash
git count-objects -vH
```

```
count: 42
size: 3.10 MiB
in-pack: 891204
packs: 3
size-pack: 4.87 GiB
prune-packable: 0
garbage: 0
size-garbage: 0 bytes
```

ค่า `size-pack` ที่สูงถึงเกือบ 5 GiB ผิดปกติมากสำหรับ repository โค้ด data pipeline ที่ควรมีขนาดหลักร้อย MiB เท่านั้น สอดคล้องกับหลักการที่ Part 58 สอนไว้ว่า Git เก็บทุก object แบบ snapshot ที่ delta-compress กันในไฟล์ packfile — ถ้ามี blob ขนาดใหญ่ผิดปกติเข้ามาปนอยู่ ขนาดของ packfile ทั้งก้อนจะบวมขึ้นทันทีและติดตัวไปกับ **ทุกครั้งที่มีคน clone**

ค้นหาว่า object ก้อนไหนที่ใหญ่ที่สุดในประวัติทั้งหมด:

```bash
git rev-list --objects --all |
  git cat-file --batch-check='%(objecttype) %(objectname) %(objectsize) %(rest)' |
  sort -k3 -n -r |
  head -10
```

```
blob 9f8e7d6c5b4a3f2e1d0c9b8a7f6e5d4c3b2a1f0e 2147483648 datasets/sample-dataset-full.csv
blob 1a2b3c4d5e6f7890abcdef1234567890abcdef12 1932735283 datasets/sample-dataset-full.csv
blob 5f4e3d2c1b0a9f8e7d6c5b4a3f2e1d0c9b8a7f6e  893921840 datasets/sample-dataset-full.csv
...
```

พบต้นเหตุ: วิศวกร Data ทดลองอัปโหลดไฟล์ตัวอย่างชุดข้อมูลขนาด **2 GiB** เข้า repository โดยตรง (ไม่ผ่าน Git LFS) และแก้ไข/commit ซ้ำหลายครั้งระหว่างทดลอง ทำให้มี blob ขนาดมหึมาหลายเวอร์ชันฝังอยู่ในประวัติถาวร — ไฟล์ CSV บีบอัด (delta compress) ได้ไม่ดีนักเมื่อเทียบกับซอร์สโค้ด ทำให้ packfile บวมขึ้นตรงๆ ตามขนาดไฟล์

### 945.4 วินิจฉัยความช้าฝั่ง Working Directory (อ้างอิง Part 63)

นอกจากปัญหาเรื่อง clone/packfile ทีมยังพบว่า `git status` ช้าแม้บนเครื่องที่ clone เสร็จแล้ว ตรวจสอบต่อว่ามีไฟล์ที่ไม่ควรถูก track จำนวนมากหรือไม่:

```bash
git ls-files | wc -l
```

```
84213
```

```bash
git status --porcelain | wc -l
```

พบว่าโฟลเดอร์ `.venv/` (Python virtual environment ที่มีไฟล์นับหมื่นไฟล์) ถูก commit เข้า repository ไปโดยไม่ตั้งใจตั้งแต่ต้น เพราะไม่มีการเพิ่มเข้า `.gitignore` ตั้งแต่แรก ทำให้ Git ต้อง `stat()` ไฟล์หลักหมื่นไฟล์ทุกครั้งที่รัน `git status` ตามหลักการ performance ของ working directory ขนาดใหญ่ที่ Part 63 อธิบายไว้

### 945.5 แผนการแก้ไข

**แก้ปัญหาเฉพาะหน้า (ไม่กระทบประวัติ):**

```bash
git rm -r --cached .venv
echo ".venv/" >> .gitignore
git add .gitignore
git commit -m "เอา .venv ออกจากการ track และเพิ่มเข้า .gitignore"
```

เปิดใช้งาน `core.fsmonitor` และ `feature.manyFiles` เพื่อเร่งความเร็วคำสั่งที่ตรวจสอบ working directory ขนาดใหญ่ตามที่เรียนใน Part 63:

```bash
git config core.fsmonitor true
git config feature.manyFiles true
```

**แก้ปัญหาที่ประวัติ (ต้องประสานทั้งทีมเหมือน Step 943):**

เนื่องจาก blob ขนาดใหญ่ฝังอยู่ในประวัติเก่าถาวรแล้ว การลบไฟล์ในปัจจุบันอย่างเดียวไม่ช่วยลดขนาด `.git` ที่มีอยู่แล้วบนเครื่องทุกคน ต้องทำ history rewrite แบบเดียวกับที่ทำกับ secret ใน Step 943:

```bash
git filter-repo --path datasets/sample-dataset-full.csv --invert-paths
```

แจ้งทีมล่วงหน้าเป็นตารางเวลา (maintenance window) เพราะ SHA ทั้งหมดจะเปลี่ยน ทุกคนต้อง clone ใหม่ จากนั้นย้ายไฟล์ชุดข้อมูลขนาดใหญ่ไปเก็บผ่าน **Git LFS** หรือดีกว่านั้นคือย้ายออกจาก Git ไปเก็บใน object storage (เช่น S3) แล้วเก็บแค่ manifest/URL อ้างอิงไว้ใน repository แทน เพราะข้อมูลชุดใหญ่ที่เปลี่ยนบ่อยไม่เหมาะกับการ version ด้วย Git ตั้งแต่ต้น

```bash
git lfs track "datasets/*.csv"
git add .gitattributes
git commit -m "ตั้งค่า Git LFS สำหรับไฟล์ dataset ขนาดใหญ่ทั้งหมด"
```

### 945.6 ป้องกันไม่ให้เกิดซ้ำ

เพิ่ม CI check ที่ปฏิเสธ Pull Request ที่มีไฟล์ขนาดเกิน 5 MB โดยไม่ได้ผ่าน Git LFS โดยอัตโนมัติ ผูกเข้ากับแนวคิด "ป้องกันก่อนเกิด" แบบเดียวกับที่ใช้ป้องกัน secret ใน Part 78 — ปัญหาทั้งสองแบบ (secret หลุด, ไฟล์ใหญ่หลุด) แก้ด้วยหลักการเดียวกัน: **ดักไว้ที่ต้นทางก่อนเข้าประวัติถาวรเสมอ ดีกว่ามาตามแก้ทีหลัง**

หลังทำ `git filter-repo` และย้ายไปใช้ LFS แล้ว วัดผลซ้ำ:

```bash
git count-objects -vH
```

```
size-pack: 187.42 MiB
```

ขนาดลดลงจากเกือบ 5 GiB เหลือไม่ถึง 200 MiB และเวลา clone ของพนักงานใหม่กลับมาอยู่ที่ระดับไม่กี่วินาทีตามปกติ

## Step 946: สถานการณ์ที่ 5 — สองทีม merge กันแล้วเกิด regression หาสาเหตุยากมาก ใช้ `git bisect`

### 946.1 เกิดอะไรขึ้น

ในวันเดียวกัน ทีม Payments merge Pull Request เพิ่มโมดูลตรวจจับการฉ้อโกง (fraud-check) เข้า `core-api` และทีม Core Product ก็ merge Pull Request รีแฟกเตอร์คลาส `OrderValidator` ที่ใช้ร่วมกันทั้งระบบเข้าไปด้วยเช่นกัน ทั้งสอง Pull Request ผ่าน test suite ของตัวเองอย่างราบรื่นเมื่อทดสอบแยกกัน

สองวันถัดมา ทีม Customer Support รายงานว่ามีคำสั่งซื้อที่ถูกต้องสมบูรณ์ถูกปฏิเสธอย่างเงียบๆ ประมาณ 3% โดยไม่มี error log ใดๆ และเกิดเฉพาะกับสกุลเงินบางประเภทเท่านั้น — บั๊กประเภทนี้แทบเป็นไปไม่ได้ที่จะเจอด้วยการอ่านโค้ดด้วยตาเปล่า เพราะมี commit เกิดขึ้นกว่า 40 commits จากทั้งสองทีมนับตั้งแต่ release ที่ยังทำงานถูกต้องครั้งล่าสุด

### 946.2 ขั้นแรกที่สำคัญที่สุด: เขียนสคริปต์ reproduce ที่ deterministic

`git bisect` ทำงานได้ดีที่สุดเมื่อมีคำสั่งที่ตอบได้ชัดเจนว่า "ดี" หรือ "เสีย" แบบอัตโนมัติ ปัญหาคือบั๊กนี้ดู "เกิดเป็นบางครั้ง" (intermittent) ซึ่งมักทำให้วิศวกรท้อและคิดว่า bisect ใช้ไม่ได้ — แต่ในความเป็นจริง บั๊กที่ดู intermittent ส่วนใหญ่ **มีเงื่อนไขที่แน่นอนอยู่เบื้องหลังเสมอ** เพียงแต่ยังไม่รู้ว่าคืออะไร

ทีมจึงลงทุนเวลาสร้างสคริปต์ทดสอบที่ป้อนชุดคำสั่งซื้อจำลอง 500 รายการที่ครอบคลุมสกุลเงินที่มีปัญหาเข้าไปตรงๆ แทนที่จะรอให้บั๊กเกิดขึ้นเองแบบสุ่มบน production:

```bash
cat > scripts/repro-order-bug.sh << 'EOF'
#!/usr/bin/env bash
# คืนค่า 0 ถ้าคำสั่งซื้อทุกรายการผ่านตามที่ควรจะเป็น (ดี)
# คืนค่า 1 ถ้ามีคำสั่งซื้อที่ควรผ่านแต่กลับถูกปฏิเสธ (เสีย)
set -e
npm run build --silent
node scripts/replay-order-batch.js fixtures/known-good-orders-500.json
EOF
chmod +x scripts/repro-order-bug.sh
```

ทดสอบสคริปต์ด้วยมือก่อนกับ commit ปัจจุบัน (ที่รู้แน่ชัดว่าเสีย) และ commit ของ release ก่อนหน้า (ที่รู้แน่ชัดว่าดี) เพื่อยืนยันว่าสคริปต์ให้ผลตรงกับที่คาดไว้ทั้งสองกรณีก่อนเริ่ม bisect จริง — ขั้นตอนนี้สำคัญมาก เพราะถ้าสคริปต์ผิดเอง bisect จะชี้ไปที่ commit ผิดตัวโดยไม่มีใครรู้

```bash

git bisect bad HEAD
git bisect good v5.4.0
git bisect run ./scripts/repro-order-bug.sh
```

Git ใช้เวลาทดสอบเพียง 5-6 ครั้งเพื่อค้นหา commit ต้นตอจากทั้งหมดกว่า 40 commits ตามหลักการ binary search ที่ Part 42 อธิบายไว้ (log₂ ของจำนวน commit) — เร็วกว่าการไล่อ่านทีละ commit มหาศาล

### 946.4 อ่านผลลัพธ์และเข้าใจสาเหตุที่แท้จริง

commit `b91f4a7` เปลี่ยนวิธีปัดเศษทศนิยมในคลาส `OrderValidator` จาก `round()` มาตรฐานเป็นวิธีตัดทศนิยมแบบเร็วกว่าเฉพาะบาง locale เพื่อเพิ่มประสิทธิภาพ ซึ่ง**ทำงานถูกต้องเมื่อทดสอบแยกกับ test suite เดิมของทีม Core** แต่เมื่อรวมเข้ากับโมดูล fraud-check ใหม่ของทีม Payments ที่คาดหวังผลการปัดเศษแบบมาตรฐานเพื่อเปรียบเทียบยอดเงินสองครั้ง (ครั้งหนึ่งก่อนและหลังตรวจจับการฉ้อโกง) ความคลาดเคลื่อนเล็กน้อยจากการปัดเศษที่ต่างวิธีกันทำให้ยอดเงินสองค่าไม่เท่ากันพอดี และระบบ fraud-check ตีความว่าเป็นรายการต้องสงสัยแล้วปฏิเสธเงียบๆ

นี่คือ **regression จากการรวมกัน (integration regression)** ที่ไม่มีทีมไหนผิดเดี่ยวๆ เลย — แต่ละทีมทดสอบโค้ดของตัวเองถูกต้องสมบูรณ์แบบ แต่ไม่มี test ใดทดสอบว่าทั้งสองระบบทำงานร่วมกันถูกต้องหรือไม่

### 946.5 บันทึกและแก้ไข

```bash
git bisect log > incidents/2026-02-11-order-rejection-regression/bisect-log.txt
git bisect reset
```

การรัน `git bisect log` ก่อน `reset` สำคัญมาก เพราะจะเก็บลำดับการทดสอบทั้งหมดไว้เป็นหลักฐานประกอบ post-mortem และหากในอนาคตต้อง bisect ปัญหาที่คล้ายกันอีก สามารถ replay ลำดับเดิมได้ทันทีด้วย `git bisect replay`

เนื่องจาก commit ที่มีปัญหาอยู่ลึกกว่า `main` ปัจจุบันไปหลาย commit การ revert ตรงๆ อาจชนกับการเปลี่ยนแปลงที่เกิดขึ้นทีหลัง ทีมจึงเลือกเขียนแก้ไขใหม่แบบ forward-fix แทน โดยแก้ให้ `OrderValidator` ใช้วิธีปัดเศษมาตรฐานเดียวกันทุก locale แล้วเปิด Pull Request ปกติ พร้อมเพิ่มชุดทดสอบ integration ระหว่างสองโมดูลนี้เป็นการถาวร (รายละเอียด action item อยู่ใน Step 949)

### 947.1 ทำไมต้องเขียนเสมอ แม้ปัญหาจะแก้เสร็จแล้ว

### 947.3 ตัวอย่างการใช้เทคนิค "5 Whys" กับสถานการณ์ที่ 1 (Step 942)

เทคนิค 5 Whys คือการถามคำว่า "ทำไม" ต่อกันเป็นชั้นๆ จนกว่าจะเจอสาเหตุเชิงระบบที่แท้จริง แทนที่จะหยุดอยู่แค่สาเหตุผิวเผินอย่าง "เพราะพนักงานพิมพ์ผิด":

```
1. ทำไม main ถึงถูกทับ?
   → เพราะมีคน force-push เข้า main โดยไม่ตั้งใจ

2. ทำไมคำสั่ง force-push ถึงสำเร็จ?
   → เพราะ branch protection ของ repository นี้ยังไม่ได้บังคับ "ห้าม force-push"

3. ทำไมกฎนี้ถึงยังไม่ถูกบังคับใช้ทั้งที่มีนโยบายกำหนดไว้แล้ว?
   → เพราะกฎถูกผูกกับ Organization Ruleset ที่ทำงานกับ repository ที่ติด topic
     "tier-1-critical" เท่านั้น และ repository นี้ยังไม่ได้ติด topic ดังกล่าว

4. ทำไม repository นี้ถึงยังไม่ถูกติด topic?
   → เพราะเพิ่งถูกสร้างขึ้นเมื่อ 3 สัปดาห์ก่อน และการติด topic เป็นขั้นตอน
     ที่ต้องทำด้วยมือตาม checklist สร้าง repository ใหม่

5. ทำไมขั้นตอนสำคัญนี้ถึงต้องพึ่งพาความจำของมนุษย์?
   → เพราะยังไม่มีการบังคับผ่าน repository template หรือ automated workflow
     ที่ตั้งค่า topic/ruleset ที่จำเป็นให้อัตโนมัติตั้งแต่วินาทีที่สร้าง repository
```

จะเห็นว่าสาเหตุที่แท้จริง (root cause) ไม่ใช่ "พนักงานพิมพ์ผิด" แต่คือ **"กระบวนการสร้าง repository ใหม่พึ่งพาความจำของมนุษย์ในขั้นตอนที่ควรถูกบังคับใช้อัตโนมัติ"** — นี่คือสิ่งที่ action item ใน Step 949 ต้องแก้ ไม่ใช่การ "เตือนพนักงานให้ระวังมากขึ้น" ซึ่งแก้ปัญหาที่ผิวเผินและมักเกิดซ้ำเสมอ

## Step 948: Blameless Post-mortem Culture — วัฒนธรรมการเรียนรู้จากความผิดพลาดโดยไม่โทษคน

### 948.1 หลักการของ Blameless Post-mortem

**Blameless Post-mortem** คือแนวทางการทบทวน incident ที่มุ่งเน้นหาสาเหตุ **เชิงระบบและกระบวนการ** ที่ทำให้ความผิดพลาดของมนุษย์ (ซึ่งเกิดขึ้นได้เสมอและหลีกเลี่ยงไม่ได้ 100%) สามารถลุกลามกลายเป็นความเสียหายจริงได้ แทนที่จะจบการวิเคราะห์แค่ที่ "ใครเป็นคนทำ" แนวคิดนี้เป็นที่ยอมรับอย่างกว้างขวางในองค์กรวิศวกรรมชั้นนำ และถูกอธิบายไว้อย่างละเอียดในหนังสือ Site Reliability Engineering ของ Google รวมถึงแนวปฏิบัติของ Etsy ที่เป็นหนึ่งในผู้บุกเบิกวัฒนธรรมนี้ในวงการซอฟต์แวร์

หลักคิดสำคัญคือ:

> **มนุษย์ไม่ได้ตื่นมาตัดสินใจทำให้ระบบพังในเช้าวันนั้น — ระบบและกระบวนการรอบตัวเขาต่างหากที่ "อนุญาต" ให้การตัดสินใจในเวลานั้นนำไปสู่ความเสียหายได้**

### 948.2 ทำไมวัฒนธรรมนี้ถึงสำคัญต่อทีมวิศวกรที่ดี

**งานวิจัย Project Aristotle ของ Google** ที่ศึกษาว่าอะไรทำให้ทีมทำงานได้ดีที่สุด พบว่าปัจจัยอันดับหนึ่งคือ **Psychological Safety** — ความรู้สึกปลอดภัยที่จะพูดความจริง ยอมรับความผิดพลาด หรือขอความช่วยเหลือ โดยไม่ต้องกลัวถูกลงโทษหรือดูถูก

ผลกระทบที่เกิดขึ้นจริงเมื่อทีมมีหรือไม่มีวัฒนธรรมนี้:

| ในทีมที่มีวัฒนธรรมโทษคน (Blame Culture) | ในทีมที่มีวัฒนธรรม Blameless |
|---|---|
| คนซ่อนความผิดพลาดหรือ near-miss ไว้ ไม่รายงาน | คนรายงานปัญหาทันทีที่เจอ แม้เป็นความผิดตัวเอง |
| เลื่อนการแจ้ง incident เพราะกลัวถูกตำหนิ ทำให้ Time to Detect แย่ลง | แจ้งทันทีที่สงสัยว่ามีปัญหา แม้ยังไม่แน่ใจ 100% |
| Post-mortem กลายเป็นการหาแพะรับบาป ไม่มีใครยอมพูดความจริงทั้งหมด | Post-mortem ได้ข้อมูลครบถ้วนตรงไปตรงมา นำไปแก้ปัญหาเชิงระบบได้จริง |
| วิศวกรกลัวการทดลองสิ่งใหม่ นวัตกรรมชะงัก | วิศวกรกล้าทดลองภายใต้ความเสี่ยงที่คำนวณไว้แล้ว เพราะรู้ว่าความผิดพลาดสุจริตจะไม่ถูกลงโทษ |
| Incident แบบเดิมเกิดซ้ำเรื่อยๆ เพราะไม่มีใครแก้ที่ต้นตอจริง | จำนวน incident ซ้ำแบบเดิมลดลงต่อเนื่อง เพราะแก้ที่ระบบ ไม่ใช่แค่ตักเตือนคน |

### 948.3 วิธีปฏิบัติจริงเพื่อรักษาวัฒนธรรม Blameless

1. **ใช้ภาษาที่พูดถึงระบบ ไม่ใช่พูดถึงบุคคล** ในเอกสาร timeline ให้เขียนว่า "pipeline อนุญาตให้ hotfix ที่ยังไม่ผ่าน review เต็มรูปแบบถูก merge เข้า production" แทนที่จะเขียนว่า "คุณ ก. merge โค้ดที่ยังไม่ได้ review เข้าไป"
2. **แยก incident review ออกจาก performance review โดยเด็ดขาด** ข้อมูลจาก post-mortem ต้อง **ไม่ถูกนำไปใช้เป็นส่วนหนึ่งของการประเมินผลงานประจำปีของใครเลย** ไม่ว่ากรณีใดก็ตาม เพราะถ้าคนรู้ว่าการยอมรับความผิดพลาดจะกระทบโบนัสหรือการเลื่อนตำแหน่ง พวกเขาจะหยุดพูดความจริงทันที
3. **ผู้ดำเนินการประชุม (facilitator) มีหน้าที่ดึงบทสนทนากลับมาที่ "ระบบของเราปล่อยให้สิ่งนี้เกิดขึ้นได้อย่างไร"** ทุกครั้งที่การสนทนาเริ่มเบี่ยงไปทาง "ใครทำ" หรือ "ทำไมถึงไม่ระวังกว่านี้"
4. **ชื่อบุคคลปรากฏใน timeline ได้เท่าที่จำเป็นต่อข้อเท็จจริง แต่ไม่ใช้เพื่อตัดสิน** เช่นระบุว่า "วิศวกร A รันคำสั่ง X ตามขั้นตอนปกติ" เพื่อให้ timeline สมบูรณ์ แต่ไม่เขียนวิจารณ์การตัดสินใจของบุคคลนั้นในเอกสาร
5. **มองความผิดพลาดสุจริต (honest mistake) ว่าเป็นข้อมูล ไม่ใช่ความผิด** — ตัวอย่างจาก Step 943 ที่วิศวกรใช้ `--no-verify` ข้าม hook ตอนเร่งรีบ วัฒนธรรม Blameless จะถามว่า **"ทำไมกระบวนการของเราถึงทำให้การข้ามด่านความปลอดภัยเป็นเรื่องง่ายและจำเป็นภายใต้ความกดดันเวลา"** แทนที่จะตำหนิวิศวกรคนนั้น เพราะการลงโทษเขาคนเดียวไม่ได้ทำให้ pre-commit hook ที่ข้ามได้ง่ายๆ แข็งแกร่งขึ้นแม้แต่นิดเดียว ในขณะที่การแก้ด้วย Push Protection ระดับ server (ที่ข้ามไม่ได้) แก้ปัญหานี้ให้ **ทุกคนในทีมตลอดไป**

### 948.4 ข้อควรระวัง: Blameless ไม่ได้แปลว่าไม่มีความรับผิดชอบ

Blameless post-mortem **ไม่ได้แปลว่าไม่มีใครต้องรับผิดชอบอะไรเลย** — action item แต่ละข้อยังคงต้องมีเจ้าของที่ชัดเจนและต้องทำให้เสร็จ (ดู Step 949) ความแตกต่างคือ **ความรับผิดชอบอยู่ที่การแก้ไขปัญหาไปข้างหน้า ไม่ใช่การลงโทษสิ่งที่เกิดไปแล้วในอดีต** ทีมที่เข้าใจความแตกต่างนี้ผิดมักกลายเป็นทีมที่ไม่มีใครรับผิดชอบอะไรเลย ซึ่งอันตรายไม่แพ้วัฒนธรรมโทษคนเช่นกัน

## Step 949: การนำบทเรียนจาก Incident มาปรับปรุงกระบวนการจริง (Action Items ที่ต้อง track ให้ถึงจุดจบ)

### 949.1 Incident จะไม่มีวัน "ปิดจริง" จนกว่า Action Item จะเสร็จและได้รับการยืนยัน

หลายทีมทำพลาดตรงจุดสุดท้ายนี้: เขียน post-mortem สวยงามครบถ้วน มี action item ระบุไว้ชัดเจน แต่ไม่มีใครติดตามว่า action item เหล่านั้นถูกทำจริงหรือไม่ ผลคือ **incident แบบเดิมเกิดซ้ำใน 6 เดือนถัดมา** เพราะบทเรียนไม่เคยถูกนำไปใช้จริง

> **หลักการสำคัญ: การที่ระบบกลับมาทำงานได้ปกติ (Step 942–946) คือแค่ "การหยุดเลือดไหล" ส่วน incident จะปิดจริงก็ต่อเมื่อ action item เชิงระบบจาก post-mortem ถูกส่งมอบและตรวจสอบแล้วว่าใช้งานได้จริง**

### 949.2 แปลง Action Item จากทั้ง 5 สถานการณ์เป็นงานที่ติดตามได้จริง

NetiTech ใช้ GitHub Issues ติด label `incident-action-item` ผูกกับ milestone รายไตรมาส เพื่อให้ action item ทุกตัวมีเจ้าของ กำหนดเวลา และมองเห็นได้จากทั้งองค์กร:

| # | Action Item | ที่มา | เจ้าของ | กำหนดเสร็จ |
|---|---|---|---|---|
| 1 | เปิดกฎ "ห้าม force-push" ที่ Organization Ruleset และผูก topic อัตโนมัติผ่าน repository template ตอนสร้าง repo ใหม่ | Step 942 | ทีม Platform | 1 สัปดาห์ |
| 2 | เปิด GitHub Push Protection for Secret Scanning ทั้งองค์กร + กำหนดว่า path ที่เกี่ยวกับ secret ต้องมี Security team อนุมัติแม้เป็น hotfix ฉุกเฉิน | Step 943 | ทีม Security | 2 สัปดาห์ |
| 3 | เพิ่มขั้นตอน `git revert -m 1` เข้า runbook มาตรฐานของ rollback ทุกครั้ง + เพิ่ม smoke test gate ก่อนเลื่อนสัดส่วน canary | Step 944 | ทีม Web | 1 สัปดาห์ |
| 4 | ย้ายไฟล์ dataset ทั้งหมดของ `data-pipelines` ไปใช้ Git LFS + เพิ่ม CI check ปฏิเสธไฟล์ใหญ่เกิน 5 MB ที่ไม่ผ่าน LFS | Step 945 | ทีม Data Platform | 3 สัปดาห์ |
| 5 | เพิ่มชุด integration test ระหว่างโมดูล fraud-check ของ Payments กับ `OrderValidator` ของ Core ให้รันใน CI ทุก Pull Request ที่แตะทั้งสองโมดูล | Step 946 | ทีม Payments + ทีม Core ร่วมกัน | 1 เดือน |

### 949.3 กระบวนการติดตามให้ถึงจุดจบ ไม่ใช่แค่สร้าง Issue แล้วลืม

1. **ประชุม Ops Review ทุกสัปดาห์** ทบทวน action item ที่ยังเปิดอยู่ทั้งหมดจากทุก incident ไม่ใช่แค่ incident ล่าสุด
2. **Action item ที่ค้างเกิน 30 วันโดยไม่มีความคืบหน้า ต้องถูกยกระดับ (escalate) ไปยังผู้บริหารสายวิศวกรรม** เพื่อจัดสรรทรัพยากรหรือทบทวนความสำคัญ ไม่ปล่อยให้ค้างเงียบๆ ในกองงานปกติ
3. **การปิด action item ต้องมีการยืนยันผลจริง ไม่ใช่แค่ merge โค้ดแล้วปิด** ตัวอย่างเช่น action item #1 (ห้าม force-push) จะปิดได้ก็ต่อเมื่อมีคนทดลอง `git push --force` จริงกับ repository ทดสอบแล้วยืนยันว่าถูกปฏิเสธจริง ไม่ใช่แค่เชื่อว่าตั้งค่าถูกต้องแล้ว
4. **เชื่อมโยงกับ Metrics จาก Part 92** — ใช้ตัวชี้วัด **Repeat Incident Rate** (สัดส่วนของ incident ที่เกิดจากสาเหตุเดิมซ้ำ) และ **Action Item Aging** (อายุเฉลี่ยของ action item ที่ยังไม่ปิด) เป็นตัวชี้วัดสุขภาพองค์กรระดับผู้บริหาร หาก Repeat Incident Rate ไม่ลดลงเมื่อเวลาผ่านไป แปลว่ากระบวนการ post-mortem ของทีมยังไม่ได้ผลจริง ต้องทบทวนกระบวนการเองด้วย

### 949.4 บทเรียนสุดท้าย: Incident ที่ดีที่สุดคือ Incident ที่ไม่เกิดซ้ำ

ความสำเร็จของกระบวนการ Incident Response ไม่ได้วัดจาก "แก้ไขได้เร็วแค่ไหน" เพียงอย่างเดียว (แม้จะสำคัญมาก) แต่วัดจาก **แนวโน้มของจำนวนและความรุนแรงของ incident ที่ลดลงเรื่อยๆ เมื่อเวลาผ่านไป** เพราะนั่นคือหลักฐานว่าองค์กรเรียนรู้จากความผิดพลาดได้จริง ไม่ใช่แค่ดับไฟแล้วรอไฟไหม้รอบใหม่

| DORA Metrics (Deployment Frequency, Lead Time, MTTR, Change Failure Rate) | ชุดตัวชี้วัดมาตรฐานสากลสำหรับวัดประสิทธิภาพทีมวิศวกรรม อ้างอิงจากงานวิจัย DORA/State of DevOps |

### 950.4 Checklist ทบทวนภาพรวมเฟส 9 ทั้งหมด (Part 86–95) ก่อนเข้าสู่เฟส 10

ก่อนไปต่อ Part 96 (เริ่มต้นเฟส 10: ระดับโลก/Leadership) ให้ตรวจสอบตัวเองอย่างละเอียดตามรายการนี้ ถ้าข้อไหนยังไม่มั่นใจ แนะนำให้ย้อนกลับไปอ่าน Part ที่เกี่ยวข้องอีกครั้งก่อน:

**Maintainer และ Contributing Guide (Part 86–87)**
- [ ] อธิบายขั้นตอน triage issue/PR ที่เข้ามาจากภายนอกได้อย่างเป็นระบบ
- [ ] เขียน `CONTRIBUTING.md` และ `CODE_OF_CONDUCT.md` ที่ครบถ้วนสำหรับโปรเจกต์ของตัวเองได้

**Release Management และ Changelog (Part 88–89)**
- [ ] อธิบายกฎของ Semantic Versioning (MAJOR.MINOR.PATCH) และตัดสินใจเลือกเวอร์ชันถัดไปได้ถูกต้องจากลักษณะการเปลี่ยนแปลง
- [ ] ตั้งค่า changelog อัตโนมัติจาก commit message ที่เป็นไปตามมาตรฐานได้ด้วยตัวเอง

**Multi-team และ Agile (Part 90–91)**
- [ ] ออกแบบโครงสร้าง CODEOWNERS และขอบเขตความรับผิดชอบสำหรับหลายทีมในองค์กรขนาดใหญ่ได้
- [ ] เชื่อมโยง branch/commit/PR เข้ากับ ticket หรือ sprint ของกระบวนการ Agile ที่ทีมใช้ได้

**Metrics และ Migration (Part 92–93)**
- [ ] อธิบายความหมายและวิธีคำนวณ DORA metrics ทั้ง 4 ตัวได้
- [ ] วางแผนการย้ายระบบเก่า (SVN/Perforce) เข้าสู่ Git โดยรักษาประวัติได้อย่างเป็นระบบ

**Debugging และ Incident Response (Part 94–95)**
- [ ] ใช้ `git reflog` กู้คืนความผิดพลาดทั้งระดับบุคคลและระดับทีมได้
- [ ] ปฏิบัติตามหลักการ "revoke ก่อนลบ" ได้ทันทีเมื่อเจอ secret รั่วไหลจริง โดยไม่ลังเล
- [ ] ยึดหลัก "rollback ต้องเร็วกว่า debug เสมอ" และเลือกวิธี rollback ที่เหมาะกับกลยุทธ์ deploy ที่ใช้อยู่ได้
- [ ] วินิจฉัยปัญหา performance ของ repository ขนาดใหญ่อย่างเป็นระบบ แยกแยะได้ว่าปัญหาอยู่ที่ไหน
- [ ] เขียนสคริปต์ reproduce ที่ deterministic และใช้ `git bisect run` หาสาเหตุบั๊กที่ซับซ้อนได้ด้วยตัวเอง
- [ ] เขียน Post-mortem ที่มีโครงสร้างครบถ้วน รวมทั้ง timeline, root cause แบบ 5 Whys และ action items ที่ติดตามได้จริง
- [ ] อธิบายได้ว่าทำไมวัฒนธรรม Blameless Post-mortem ถึงสำคัญต่อ psychological safety และคุณภาพของทีมวิศวกรรมในระยะยาว
- [ ] ออกแบบกระบวนการติดตาม action item ให้ถึงจุดจบจริง ไม่ใช่แค่สร้าง issue แล้วปล่อยค้าง

**ภาพรวมทั้งเฟส 9**
- [ ] อธิบายได้ว่าทักษะ "มืออาชีพ" ที่แยกวิศวกรระดับ senior/staff ออกจากวิศวกรทั่วไปคืออะไรบ้าง โดยยกตัวอย่างจากทั้ง 10 Part ของเฟสนี้
- [ ] เชื่อมโยงความรู้จากทุกเฟสก่อนหน้า (โดยเฉพาะเฟส 4, 6, 7, 8) เข้ากับสถานการณ์วิกฤตจริงได้อย่างเป็นธรรมชาติ ไม่ใช่แค่ท่องจำคำสั่งแยกส่วน

ถ้าคุณติ๊กครบทุกข้อ (หรือเกือบครบ) แปลว่าคุณพร้อมสำหรับเฟส 10 อย่างแท้จริงแล้ว — เฟส 9 คือเฟสที่เปลี่ยนคุณจากคนที่ **"ใช้ Git เก่งในสถานการณ์ปกติ"** ไปสู่คนที่ **"ใช้ Git และกระบวนการรอบตัวมันแก้วิกฤตจริงได้อย่างสงบและเป็นระบบ"** ซึ่งเป็นทักษะที่ทีมวิศวกรรมทุกองค์กรมองหามากที่สุดในตัววิศวกรระดับสูง

## สรุป Part 95

ใน Part นี้เราได้จำลองทีมตอบสนอง incident ขององค์กร NetiTech Solutions เผชิญและกู้คืนจากวิกฤตจริง 5 สถานการณ์ ปิดท้ายด้วยกระบวนการเรียนรู้จากความผิดพลาดอย่างเป็นระบบ:

1. วางรากฐานความเข้าใจเรื่อง Incident, Severity Level, บทบาทมาตรฐาน และวงจรชีวิตของ incident ก่อนเริ่มจำลองสถานการณ์จริง (Step 941)
2. กู้คืน main ที่ถูก force-push ทับด้วยการอ่าน `git reflog` ของเพื่อนร่วมทีม ต่อยอดจากหลักการใน Part 94 แล้วขยายไปสู่ระดับทีม พร้อมป้องกันด้วย branch protection และ `--force-with-lease` (Step 942)
3. จัดการ secret ที่หลุดเข้า production ด้วยหลักการ revoke-ก่อน-ลบ ตามที่ Part 78 วางไว้ พร้อมประเมิน blast radius และแก้สาเหตุเชิงกระบวนการ ไม่ใช่แค่โทษความประมาทของบุคคล (Step 943)
4. rollback deploy ที่พังหลัง merge ด้วย `kubectl rollout undo` ตามหลัก "rollback ต้องเร็วกว่า debug เสมอ" จาก Part 74 พร้อม revert merge commit ใน Git ให้ main กลับมาปลอดภัยจริง (Step 944)
5. วินิจฉัย repository ที่ช้าผิดปกติอย่างเป็นระบบด้วยเครื่องมือจาก Part 58/63 พบต้นเหตุคือไฟล์ขนาดใหญ่ที่ไม่ผ่าน Git LFS และไฟล์ที่ไม่ควร track ปนอยู่ในประวัติ (Step 945)
6. ตามหาบั๊ก regression จากการรวมงานสองทีมด้วย `git bisect run` และสคริปต์ reproduce ที่ deterministic ตามหลักการจาก Part 42 (Step 946)
7. เขียน Post-mortem ที่มีโครงสร้างครบถ้วน พร้อมเทคนิค 5 Whys เพื่อหาสาเหตุเชิงระบบ (Step 947)
8. เข้าใจและนำวัฒนธรรม Blameless Post-mortem มาใช้ เพื่อรักษา psychological safety และคุณภาพการเรียนรู้ขององค์กรในระยะยาว (Step 948)
9. แปลง action item จากทุก incident เป็นงานที่ติดตามได้จริงจนถึงจุดจบ และเชื่อมโยงกับ metrics เพื่อวัดผลว่าองค์กรเรียนรู้ได้จริงหรือไม่ (Step 949)
10. ทบทวนภาพรวมทั้งเฟส 9 (Part 86–95) ผ่าน Cheat Sheet และ Checklist ครบทุกด้าน ก่อนข้ามไปสู่เฟสสุดท้าย (Step 950)

Part นี้คือจุดปิดฉากของ **เฟส 9: มืออาชีพ / Enterprise Practice (Part 86–95, Step 851–950)** อย่างสมบูรณ์ คุณได้ผ่านการฝึกฝนทักษะที่แยกวิศวกรที่ "ใช้ Git เก่งในสถานการณ์ปกติ" ออกจากวิศวกรที่ **"นำ Git และกระบวนการทั้งหมดรอบตัวมันมาจัดการความวิกฤตจริงได้อย่างสงบ เป็นระบบ และเปลี่ยนความผิดพลาดให้กลายเป็นความแข็งแกร่งขององค์กรได้ในระยะยาว"** มาครบทุกมิติแล้ว ตั้งแต่การดูแลโปรเจกต์ Open Source, การบริหาร Release, การทำงานร่วมกันข้ามทีม, การวัดผลด้วยข้อมูลจริง ไปจนถึงการกู้คืนจากวิกฤตและเรียนรู้จากมันอย่างไม่โทษใครแต่แก้ที่ระบบเสมอ

จากนี้ไป หลักสูตรจะพาคุณเข้าสู่ **เฟส 10: ระดับโลก / Leadership (Part 96–100, Step 951–1000)** ซึ่งเป็นเฟสสุดท้ายของหลักสูตรทั้งหมด จะพาคุณไปศึกษากรณีศึกษาจริงระดับโลกอย่าง Linux Kernel Git Workflow และทักษะการเป็นผู้นำด้านเทคนิค (Tech Lead) ที่ใช้ Git และกระบวนการทั้งหมดที่เรียนมาตลอด 95 Part เป็นเครื่องมือขับเคลื่อนองค์กรวิศวกรรมทั้งองค์กร
